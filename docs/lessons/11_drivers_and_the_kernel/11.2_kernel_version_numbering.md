### 11.2 Kernel Version Numbering

Kernel version numbers tell you which kernel a system is running, which update stream it came from, and how risky a change might be. They do not tell the whole support story by themselves. In day-to-day operations, you read the version number together with the distribution package, boot loader entries, release notes, and the symptom you are investigating.

!!! abstract "What you will learn"
    - Read Linux kernel release strings from `uname`, package tools, and `/boot`.
    - Distinguish upstream kernel versions from distribution-maintained kernel packages.
    - Explain why older odd/even development numbering is mostly historical.
    - Compare the running kernel, installed kernels, and available updates before a change.
    - Build a safer rollback plan for kernel upgrades.

!!! example "Field story"
    A server loses network connectivity after a maintenance window. The team says, "We upgraded the kernel." Your first job is to identify the kernel that is currently booted, the kernel that was booted before the change, and whether a driver, firmware, or distribution patch level changed with it.

!!! success "Operator principle"
    Treat kernel versions as evidence. Verify the running kernel, the installed package, and the boot choice before you decide that a kernel is good, bad, old, or unsupported.

## Read the running kernel

Start with the kernel that is actually running:

```bash
uname -r
uname -a
```

`uname -r` prints the kernel release string. On a distribution kernel, it usually contains more than the upstream version:

```text
6.8.0-31-generic
```

Read this as:

- `6.8.0`: the upstream kernel version base.
- `31`: the distribution package build or revision.
- `generic`: the distribution flavor or configuration profile.

Different distributions format the suffix differently. Debian, Ubuntu, Red Hat, Fedora, SUSE, and cloud images all add their own package and flavor details. Those suffixes matter because distributions backport fixes, apply configuration choices, and ship drivers or firmware on their own schedules.

## Understand upstream version fields

Upstream Linux kernel versions commonly use this shape:

```text
major.minor.patch
```

For example, in `6.8.12`:

- `6` is the major version.
- `8` is the minor version.
- `12` is the patch release.

Patch releases usually contain bug fixes, security fixes, and driver updates for that stable series. A move from `6.8.11` to `6.8.12` is normally smaller than a move from `6.1` to `6.8`, but you still verify it against your workload, drivers, and vendor support policy.

!!! note "Odd and even version history"
    Older Linux development used odd minor numbers for development kernels and even minor numbers for stable kernels. Modern Linux no longer uses that as the main rule. Current kernel stability is determined by the release stream, stable patch series, long-term support status, distribution support, and project release notes.

## Compare upstream, distribution, and running versions

A system can have several kernel-related versions at once:

| Evidence | What it tells you |
| --- | --- |
| `uname -r` | The kernel currently running in memory. |
| `/boot/vmlinuz-*` | Kernel images installed for booting. |
| Package manager output | Kernel packages installed or available from the distribution. |
| Boot loader menu | Which kernel will boot by default or can be selected manually. |
| Distribution release notes | Whether a kernel is supported for that distribution release. |

Use distribution tools to inspect installed kernel packages:

```bash
# Debian and Ubuntu
dpkg -l 'linux-image*' | awk '/^ii/ {print $2, $3}'

# RHEL, Fedora, and related distributions
rpm -qa 'kernel*' | sort

# SUSE
rpm -qa 'kernel*' | sort
```

Then compare those results with:

```bash
ls -lh /boot/vmlinuz-*
uname -r
```

The newest installed kernel is not always the running kernel. A host may still be running the old kernel because it has not rebooted, because the boot loader default was changed, or because the latest boot failed and the system fell back.

## Use versions during incident triage

When a kernel change is suspected, capture evidence before changing anything:

```bash
uname -r
cat /etc/os-release
ls -lh /boot/vmlinuz-* /boot/initrd* 2>/dev/null
journalctl -k -b --no-pager | tail -50
```

If the incident involves hardware or networking, add driver evidence:

```bash
lspci -k
lsmod | sort
modinfo DRIVER_NAME
```

Replace `DRIVER_NAME` with the module you are investigating, such as `e1000e`, `ixgbe`, `nvme`, or `amdgpu`. If `modinfo` shows a filename under `/lib/modules/$(uname -r)/`, the module belongs to the running kernel's module tree.

## Plan kernel updates safely

Before changing kernels on a real host:

1. Confirm the distribution-supported target kernel.
2. Read the distribution advisory or changelog for the update.
3. Check whether the host uses out-of-tree drivers, proprietary modules, storage drivers, or special cloud images.
4. Confirm that at least one known-good older kernel remains installed.
5. Confirm console, rescue, or cloud serial access before rebooting.
6. Schedule the reboot window and define a rollback trigger.

Avoid removing older kernels immediately after an upgrade. They are often your fastest rollback path.

!!! warning "Kernel changes can strand a host"
    A kernel update can affect boot, storage, networking, graphics, virtualization, and security modules. Practice on disposable systems first, and make sure you have a recovery path that does not depend on SSH working.

## Troubleshooting version confusion

Common version-numbering mistakes include:

- Assuming `uname -r` changed right after installing a package. The running kernel usually changes only after reboot.
- Comparing only the upstream version and ignoring distribution suffixes.
- Treating a higher version as automatically safer for a vendor-supported workload.
- Removing older kernels before testing the new one.
- Forgetting that kernel modules must match the running kernel's module tree.

Useful checks:

```bash
uname -r
find /lib/modules -maxdepth 1 -mindepth 1 -type d -printf '%f\n' 2>/dev/null | sort
ls -lh /boot/vmlinuz-* 2>/dev/null
```

If `/lib/modules/$(uname -r)` is missing, modules for the running kernel may not be available. That can break driver loading and should be treated as a serious packaging or image problem.

## Hands-on practice

Use a disposable VM or lab machine.

1. Record the running kernel:

   ```bash
   uname -r
   uname -a
   ```

2. List installed kernel images or packages with the command that matches your distribution.

3. Compare the running kernel with files under `/boot` and module trees under `/lib/modules`.

4. Find one kernel changelog or advisory from your distribution and write down whether it describes security fixes, hardware support, or general bug fixes.

5. Write a rollback note that names the currently running kernel, the target kernel, and how you would select the older kernel if the new one failed.
