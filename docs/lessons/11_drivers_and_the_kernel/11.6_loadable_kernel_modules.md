### 11.6 Loadable Kernel Modules

!!! abstract "What you will learn"
    - Explain what loadable kernel modules are and why Linux uses them.
    - Inspect loaded modules, module metadata, dependencies, parameters, and kernel logs.
    - Load or remove modules safely in a lab while recognizing production risk.
    - Use persistent configuration files for module options, aliases, blacklists, and boot-time loading.

!!! example "Field story"
    A host loses one network interface after a kernel update. The device still appears in `lspci`, but no interface is created. Your evidence trail needs to show whether the expected module exists for the running kernel, whether it loaded, whether firmware failed, and whether a blacklist or parameter is blocking it.

!!! success "Operator principle"
    Module changes touch the running kernel. Inspect freely, test in labs, and treat remote unloads of storage, network, or filesystem modules as maintenance-window work.

A loadable kernel module is code that can be linked into the running kernel without rebuilding the entire kernel. Modules commonly provide device drivers, filesystems, network features, virtualization support, security hooks, and observability helpers.

Modules are useful because one kernel can support many hardware and feature combinations without compiling everything directly into the kernel image. They are also risky because they run in kernel space. A bad, incompatible, or removed module can affect the whole system.

## Where modules live

Modules for the running kernel usually live under:

```bash
/lib/modules/$(uname -r)/
```

Start every module investigation by confirming the running kernel:

```bash
uname -r
ls /lib/modules/$(uname -r)
```

If `/lib/modules/$(uname -r)` is missing or incomplete, the system may have booted a kernel whose matching module package is not installed. That can break drivers, filesystems, networking, or container features that expect modules to be available.

## Inspect loaded modules

Use `lsmod` to list modules already loaded:

```bash
lsmod
```

Typical output has three columns:

```text
Module                  Size  Used by
overlay               212992  1
br_netfilter           32768  0
nf_tables             372736  145
```

The `Used by` column is a reference count and dependency hint, not a full explanation of why the module exists. A zero count does not always mean the module is safe to remove.

You can also inspect `/proc/modules` directly:

```bash
cat /proc/modules
```

For network drivers, connect interface evidence to module evidence:

```bash
ip link show
sudo ethtool -i enp3s0
readlink -f /sys/class/net/enp3s0/device/driver
```

## Inspect module metadata

`modinfo` reads module metadata without loading the module:

```bash
modinfo e1000e
```

Useful fields include:

- `filename`: module file path
- `version`: driver version when present
- `firmware`: firmware files the module may request
- `alias`: hardware IDs or feature aliases
- `depends`: module dependencies
- `parm`: configurable module parameters
- `signer`: Secure Boot or module-signing information when present

Example checks:

```bash
modinfo -F filename e1000e
modinfo -F firmware iwlwifi
modinfo -F depends br_netfilter
modinfo -F parm e1000e
```

If `modinfo` cannot find a module that should exist, confirm the running kernel and module tree:

```bash
uname -r
find /lib/modules/$(uname -r) -name '*e1000e*'
```

## Understand module dependencies

Prefer `modprobe` over `insmod` for normal operations.

`insmod` inserts one exact `.ko` file:

```bash
sudo insmod /lib/modules/$(uname -r)/kernel/drivers/net/dummy.ko
```

`modprobe` uses the module database, resolves dependencies, honors aliases and blacklists, and is usually the right tool:

```bash
sudo modprobe dummy
```

Inspect what `modprobe` would do before loading:

```bash
modprobe --show-depends dummy
modprobe --dry-run --verbose dummy
```

On many systems, module dependency metadata is rebuilt with:

```bash
sudo depmod -a
```

You usually run `depmod` after installing or removing module files for a kernel. Distribution package managers normally handle this for packaged kernels and driver packages.

## Load modules safely

Loading a harmless lab module is a good practice exercise:

```bash
sudo modprobe dummy
lsmod | grep '^dummy'
ip link show | grep dummy
```

The `dummy` module creates a virtual network driver and is safer than experimenting with real storage or NIC drivers.

Check kernel messages after loading:

```bash
journalctl -k -b | tail -n 50
```

If the module has parameters, you can pass them at load time:

```bash
sudo modprobe module_name parameter=value
```

Always check `modinfo -F parm module_name` first so you know which parameters exist and what they expect.

## Remove modules carefully

Modules can be removed with:

```bash
sudo modprobe -r dummy
```

Lower-level tools also exist:

```bash
sudo rmmod dummy
```

Prefer `modprobe -r` because it understands dependencies better. Removal can fail when the module is in use:

```text
modprobe: FATAL: Module dummy is in use.
```

Do not force module removal on production systems unless you have a tested recovery plan. Removing the wrong module can drop SSH, unmount storage, break filesystems, crash services, or panic the kernel.

High-risk removals include modules related to:

- active network interfaces
- root or application storage
- filesystems in use
- encryption or volume management
- container networking
- GPU display on a local workstation

## Persistent module configuration

Temporary `modprobe` commands affect the running system. Persistent policy usually lives under:

```bash
/etc/modules-load.d/
/etc/modprobe.d/
```

Load a module at boot:

```text
# /etc/modules-load.d/lab.conf
dummy
```

Set a module option:

```text
# /etc/modprobe.d/e1000e.conf
options e1000e InterruptThrottleRate=3000
```

Blacklist a module:

```text
# /etc/modprobe.d/block-driver.conf
blacklist driver_name
```

Blacklisting can be useful when a wrong driver binds to hardware, but it can also remove critical support on the next boot. Keep a rollback path and document why the blacklist exists.

Some early-boot modules and blacklists must also be reflected in the initramfs. On Debian or Ubuntu systems, that might involve:

```bash
sudo update-initramfs -u
```

On other distributions, the tool may be `dracut` or another initramfs builder. Use your distribution's documented process.

## Troubleshooting flow

When a module-related feature is missing:

1. Confirm the running kernel:

    ```bash
    uname -r
    ```

2. Confirm the module tree exists:

    ```bash
    ls /lib/modules/$(uname -r)
    ```

3. Check whether the module is loaded:

    ```bash
    lsmod | grep module_name
    ```

4. Check metadata and dependencies:

    ```bash
    modinfo module_name
    modprobe --show-depends module_name
    ```

5. Check kernel logs:

    ```bash
    journalctl -k -b | grep -iE 'module|firmware|failed|error|taint|signature'
    ```

6. Check persistent policy:

    ```bash
    grep -R 'module_name\\|blacklist' /etc/modprobe.d /etc/modules-load.d 2>/dev/null
    ```

7. Compare to the previous working kernel or boot:

    ```bash
    journalctl -k -b -1 | grep -iE 'module|firmware|failed|error'
    ```

This flow distinguishes missing module packages, failed firmware loads, blacklists, dependency problems, Secure Boot signing issues, and true hardware changes.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record the running kernel with `uname -r`.
2. List loaded modules with `lsmod` and choose one non-critical module to inspect.
3. Run `modinfo` on that module and record its filename, dependencies, and parameters.
4. In a lab VM, load the `dummy` module with `sudo modprobe dummy`.
5. Verify it loaded with `lsmod` and `ip link show`.
6. Remove it with `sudo modprobe -r dummy`.
7. Check `journalctl -k -b` for related messages.
