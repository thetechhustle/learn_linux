## 11.10 Recommended Reading

Kernel and driver topics move quickly, so treat reading as an
evidence-building habit instead of a one-time book list. Start with the
documentation that matches the kernel and distribution in front of you, then
use deeper references when you need background.

!!! abstract "What you will learn"
    - Choose references that match a real kernel, module, or boot problem.
    - Separate local system documentation, distribution guidance, upstream kernel documentation, and deeper background books.
    - Build a short reading workflow that turns references into safer operational decisions.

!!! example "Field story"
    A server loses network connectivity after a kernel update. Before rolling back or changing drivers, you need to know the running kernel version, the loaded module, the distribution's packaging policy, and whether upstream documentation describes the hardware or driver behavior.

!!! success "Operator principle"
    Prefer the closest authoritative source first: the running system, then the distribution, then upstream kernel documentation, then books and tutorials.

## Start with the local system

Local documentation is the best first stop because it reflects the software
already installed on the machine.

```bash
uname -a
uname -r
modinfo MODULE_NAME
lsmod | sort
man modprobe
man modules-load.d
man sysctl
```

For boot and kernel package questions, also inspect the files and package
metadata that your distribution owns:

```bash
ls -lh /boot
find /lib/modules/"$(uname -r)" -maxdepth 2 -type f | head
dpkg -l 'linux-image*' 2>/dev/null || true
rpm -qa 'kernel*' 2>/dev/null || true
```

Record the exact kernel release, distribution release, package version, module
name, and hardware identifier in your notes before consulting outside
references.

## Distribution documentation

Use distribution documentation when the question involves package names, update
policy, supported kernels, boot loader integration, initramfs tooling, or
vendor-supported driver choices.

- Debian and Ubuntu documentation for `apt`, `initramfs-tools`, DKMS, and kernel package handling.
- Red Hat, Rocky Linux, AlmaLinux, and Fedora documentation for `dnf`, `dracut`, kernel streams, rescue entries, and Secure Boot behavior.
- SUSE documentation for `zypper`, `wicked` or NetworkManager integration, and supported kernel modules.
- Arch documentation for fast-moving kernel variants, module loading, and boot loader examples.
- FreeBSD Handbook sections on kernel configuration, loader tunables, and base-system updates.

Distribution guidance should win over a generic tutorial when you are operating
a supported production system.

## Upstream Linux kernel references

Use upstream references when you need kernel concepts, driver behavior, sysfs
interfaces, kernel parameters, or module internals.

- The Linux kernel documentation tree: `https://docs.kernel.org/`
- Kernel command-line parameters: `https://docs.kernel.org/admin-guide/kernel-parameters.html`
- Module signing and Secure Boot background: `https://docs.kernel.org/admin-guide/module-signing.html`
- Driver API and subsystem documentation under the relevant `driver-api/`, `networking/`, `filesystems/`, or `admin-guide/` sections.
- Kernel Newbies for release summaries and orientation: `https://kernelnewbies.org/`
- Linux Device Drivers, 3rd edition, for older but still useful driver concepts: `https://lwn.net/Kernel/LDD3/`

Check the date and kernel version assumptions on every upstream article. A
driver interface that was current years ago may no longer match the running
kernel.

## Books for deeper background

Books are useful when you need the mental model behind a problem, not when you
need the current command for a distribution-specific incident.

- **The Linux Programming Interface**, Michael Kerrisk: system calls, process behavior, files, devices, and the user-space API boundary.
- **Linux Device Drivers**, Jonathan Corbet, Alessandro Rubini, and Greg Kroah-Hartman: driver architecture and module concepts. Treat code examples as historical unless you verify them against current kernel documentation.
- **Understanding the Linux Kernel**, Daniel P. Bovet and Marco Cesati: useful architecture background for schedulers, memory, interrupts, and kernel subsystems.
- **Operating Systems: Three Easy Pieces**, Remzi H. Arpaci-Dusseau and Andrea C. Arpaci-Dusseau: clear operating-system fundamentals that make kernel behavior easier to reason about.

Avoid starting an incident with a broad book search. Use books to improve your
model after you have collected local evidence and selected the relevant
subsystem.

## Reading workflow for incidents

1. Capture the symptom, kernel release, distribution release, hardware or virtual platform, and loaded module.
2. Read local man pages and package metadata for the exact tool or module.
3. Check the distribution's supported path for kernel packages, module loading, Secure Boot, and rollback.
4. Check upstream kernel documentation for the specific subsystem or parameter.
5. Compare any tutorial or forum answer against the local version and vendor guidance before running commands.
6. Save links, command output, and the final decision in the incident notes.

## Hands-on practice

Use a disposable VM or lab machine.

1. Pick one loaded module from `lsmod`.
2. Run `modinfo MODULE_NAME` and write down the filename, version, license, and parameters.
3. Find one local man page, one distribution reference, and one upstream kernel reference related to that module or subsystem.
4. Write a short note explaining which source you would trust first during a production incident and why.
