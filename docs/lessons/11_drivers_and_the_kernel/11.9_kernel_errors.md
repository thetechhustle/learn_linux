### 11.9 Kernel Errors

!!! abstract "What you will learn"
    - Recognize common kernel error patterns without treating every warning as a disaster.
    - Collect useful evidence from kernel logs, boot journals, crash dumps, and hardware signals.
    - Separate kernel panics, oopses, taints, driver failures, firmware failures, and machine-check events.
    - Choose safe first responses and escalation paths for production systems.

!!! example "Field story"
    A server reboots twice during the night. The application team sees only a gap in service metrics. Your job is to determine whether the kernel panicked, the hardware reset, the hypervisor restarted the instance, or userspace triggered a clean reboot.

!!! success "Operator principle"
    Kernel errors are evidence-heavy incidents. Preserve logs and console output before changing kernels, drivers, firmware, or hardware.

The Linux kernel reports many kinds of problems. Some are fatal, some are warnings, and some are noisy but harmless in context. Good operators do not panic at the word "kernel"; they classify the symptom, preserve evidence, and choose the lowest-risk next move.

## Common kernel error categories

| Category | What it means | Typical evidence |
| --- | --- | --- |
| Kernel panic | The kernel hit an unrecoverable condition and stopped or rebooted. | Console panic text, crash dump, abrupt boot gap |
| Oops | The kernel detected a serious bug but may continue running. | `BUG:`, stack trace, `Oops:` in kernel log |
| Warning | The kernel found suspicious behavior but continued. | `WARNING:`, call trace, subsystem messages |
| Taint | The kernel marks itself as changed or less supportable. | `Tainted:` flags in logs |
| Driver probe failure | A driver could not initialize a device. | `probe failed`, device ID, driver name |
| Firmware failure | A driver could not load required firmware. | `firmware: failed to load ...` |
| Machine check | CPU or hardware reported a low-level fault. | `mce`, `EDAC`, corrected/uncorrected error |
| I/O error | Storage or block layer reports read/write problems. | `I/O error`, device name, filesystem remount |
| Out of memory | Kernel OOM killer terminated a process. | `Out of memory`, `Killed process` |

Treat the category as a starting hypothesis. The same incident can include several categories, such as a firmware failure that leads to a missing network interface and then a service failure.

## Start with boot and kernel logs

For the current boot:

```bash
journalctl -k -b
journalctl -p warning..alert -b
```

For the previous boot:

```bash
journalctl --list-boots
journalctl -k -b -1
journalctl -p warning..alert -b -1
```

If the system crashed and rebooted, the previous boot is often more useful than the current boot.

Search for high-signal terms:

```bash
journalctl -k -b -1 | grep -iE 'panic|oops|bug:|warning:|taint|firmware|mce|edac|i/o error|segfault|oom|killed process|hung task|watchdog'
```

On systems without useful journal history, `dmesg` can still show current kernel messages:

```bash
dmesg -T | less
dmesg -T | grep -iE 'panic|oops|warning|firmware|mce|edac|oom|watchdog'
```

Do not depend on `dmesg` alone after a reboot. It normally shows only the current boot.

## Kernel panic evidence

A kernel panic often appears on the console, serial log, IPMI/iDRAC/iLO capture, cloud serial console, or crash dump. The most important evidence is the first panic text, not the last line after many repeated messages.

Capture:

- panic message
- call trace
- loaded modules line
- taint flags
- CPU and process context
- kernel version
- most recent hardware, driver, kernel, firmware, or workload change

Useful commands after recovery:

```bash
uname -a
journalctl --list-boots
journalctl -k -b -1
last -x | head
```

If the system is configured for crash dumps, check your distribution's crash directory and tooling. Common Linux crash dump stacks use `kdump`, `makedumpfile`, and the `crash` utility, but exact paths vary by distribution.

## Oopses, warnings, and taints

An oops or warning may not immediately crash the system, but it can still indicate a kernel, driver, or hardware problem.

Look for:

```bash
journalctl -k -b | grep -iE 'oops|BUG:|WARNING:|Call Trace|Tainted:'
```

Kernel taint flags indicate the kernel is running in a state that may reduce supportability. Common causes include proprietary modules, forced module loading, out-of-tree modules, machine-check events, or prior warnings.

You can inspect taint state:

```bash
cat /proc/sys/kernel/tainted
```

A nonzero number means one or more taint flags are set. The numeric value needs decoding against the kernel documentation or distribution support guidance. In practice, always include the full `Tainted:` line from logs when escalating.

## Firmware, driver, and module failures

Driver and firmware errors are common after kernel updates, new hardware, or minimal installs.

Useful checks:

```bash
uname -r
lspci -nnk
lsusb -t
lsmod
modinfo driver_name
journalctl -k -b | grep -iE 'firmware|driver|module|probe|failed'
```

Common clues:

- `firmware: failed to load`
- `Direct firmware load ... failed`
- `probe failed with error`
- `Unknown symbol`
- `module verification failed`
- `Required key not available`

`Required key not available` often points to Secure Boot or module-signing policy. Do not disable Secure Boot casually on production systems; first identify whether a signed module package or supported kernel variant exists.

## Hardware and machine-check signals

Kernel logs can surface hardware trouble:

```bash
journalctl -k -b | grep -iE 'mce|machine check|edac|ecc|thermal|nvme|ata|i/o error|reset'
```

Examples:

- ECC memory corrections or uncorrected errors
- CPU machine-check exceptions
- NVMe resets or timeouts
- SATA link resets
- thermal throttling
- filesystem remounting read-only after storage errors

Hardware errors often require correlating kernel logs with vendor tools, SMART data, cloud provider events, hypervisor events, or remote-management logs.

For disks, start with read-only inspection:

```bash
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,MOUNTPOINTS
journalctl -k -b | grep -iE 'nvme|ata|scsi|blk|i/o error|reset|timeout'
```

Use SMART or vendor tools according to the environment and approval boundaries.

## Out-of-memory events

An OOM event is a kernel decision, but the cause is often workload memory pressure.

Find OOM evidence:

```bash
journalctl -k -b | grep -iE 'out of memory|oom-killer|killed process'
```

Record:

- killed process name and PID
- memory cgroup if present
- container or service involved
- recent deploy or traffic change
- swap state
- whether the host recovered

Useful follow-up:

```bash
free -h
swapon --show
systemctl status service_name
```

Do not assume the killed process is the root cause. It may be the victim selected by the OOM killer.

## Safe first response

During a suspected kernel incident:

1. Preserve evidence before rebooting again.
2. Record the running kernel and uptime:

    ```bash
    uname -a
    uptime
    ```

3. Save kernel logs:

    ```bash
    journalctl -k -b > kernel-current.log
    journalctl -k -b -1 > kernel-previous.log
    ```

4. Record recent changes:

    - kernel updates
    - driver or firmware updates
    - new hardware
    - workload deployment
    - virtualization or cloud host events

5. Prefer rollback to a known-good kernel before experimenting with new fixes.
6. Escalate with logs, kernel version, hardware or instance type, and exact panic or warning text.

Avoid:

- repeatedly rebooting without collecting logs
- unloading critical modules over SSH
- removing old kernels before proving the new one
- applying random boot parameters from search results
- dismissing hardware errors as "just Linux"

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record the current kernel with `uname -a`.
2. Use `journalctl -k -b` to find one warning or driver message.
3. Use `journalctl --list-boots` and inspect the previous boot if available.
4. Check whether the kernel is tainted with `cat /proc/sys/kernel/tainted`.
5. Search the current boot for OOM, firmware, and I/O messages.
6. Write an incident handoff that includes symptom, kernel version, boot ID, strongest log line, and your next safest action.
