### 11.3 Devices and Their Drivers

!!! abstract "What you will learn"
    - Inventory PCI, USB, block, and network devices without changing the system.
    - Map a device to the kernel driver, module, firmware, and interface name that make it work.
    - Build a safe evidence trail when hardware disappears after a kernel, firmware, or package change.
    - Know when driver troubleshooting becomes risky enough to require console access or a maintenance window.

!!! example "Field story"
    A rack server returns from a kernel update with one network port down. The cable is seated, the switch port is active, and the host still boots. The right next move is not to unload random modules; it is to identify the device, the driver that should own it, the kernel that is running now, and the errors logged during boot.

!!! success "Operator principle"
    Treat hardware problems as evidence problems first. Device identity, driver binding, firmware load, and kernel version should all line up before you change anything.

Linux talks to hardware through kernel drivers. Some drivers are built directly into the kernel. Many others are loadable modules that can be inserted when hardware appears, removed when hardware is gone, or replaced by booting a different kernel package. Users usually do not call drivers directly; they see device files, interface names, filesystems, logs, and system services that depend on those drivers.

This is why hardware troubleshooting can feel confusing. A single symptom, such as "the disk is missing" or "the network port is down," may involve the physical device, the bus, the kernel module, firmware blobs, udev naming, persistent configuration, and the service that consumes the device.

## The layers you are looking at

Start by separating the layers instead of treating "the driver" as one vague object.

| Layer | What it tells you | Common evidence |
| --- | --- | --- |
| Hardware bus | Whether the system can see the device electrically | `lspci`, `lsusb`, `dmidecode`, firmware setup screens |
| Kernel driver | Which driver has claimed the device | `lspci -nnk`, `ethtool -i`, `/sys/.../driver` |
| Kernel module | The loadable object providing the driver | `lsmod`, `modinfo`, `modprobe --show-depends` |
| Firmware | Binary support files loaded by the driver | `journalctl -k`, `/lib/firmware`, distro packages |
| Device node or interface | The usable operating-system object | `/dev/*`, `lsblk`, `ip link`, `udevadm` |
| Service configuration | The thing expecting the device to exist | Network profiles, mount units, storage stacks, application config |

Keep those layers separate in your notes. A disk that appears in `lspci` but not in `lsblk` is a different problem from a disk that never appears on the bus.

## Inventory devices safely

These commands are read-only on a normal Linux host:

```bash
uname -r
lspci -nn
lspci -nnk
lsusb
lsblk -f
ip link show
```

Use `uname -r` early. Driver behavior often changes across kernel versions, and the installed kernel is not always the kernel that actually booted.

`lspci -nn` shows PCI devices and their numeric vendor and device IDs. Those IDs are useful because model names can be vague or reused. `lspci -nnk` adds kernel-driver information:

```text
03:00.0 Ethernet controller [0200]: Intel Corporation Ethernet Controller I225-V [8086:15f3]
        Subsystem: Example Vendor Device [1234:5678]
        Kernel driver in use: igc
        Kernel modules: igc
```

In this example, the device is visible on the PCI bus, the active driver is `igc`, and the module candidate is also `igc`.

USB devices follow a similar pattern:

```bash
lsusb
lsusb -t
```

`lsusb -t` is especially helpful because it shows the kernel driver attached to each USB device tree entry when one is present.

## Map network interfaces to drivers

Network interface names such as `eno1`, `ens160`, and `enp3s0` are not driver names. To connect an interface to its driver, use `ethtool`:

```bash
ip link show
sudo ethtool -i enp3s0
```

Typical output includes the driver, firmware version, bus info, and sometimes expansion ROM details:

```text
driver: igc
version: 6.8.0-31-generic
firmware-version: 2014:888d
bus-info: 0000:03:00.0
```

That `bus-info` value can be matched back to `lspci -nnk`. You can also use sysfs:

```bash
readlink -f /sys/class/net/enp3s0/device/driver
```

If a host has multiple adapters, this mapping prevents you from fixing the wrong port.

## Map block devices to hardware

`lsblk` shows block devices, partitions, filesystems, mountpoints, and device relationships:

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL
```

For deeper device details, use udev:

```bash
udevadm info --query=property --name=/dev/sda
udevadm info --attribute-walk --name=/dev/sda
```

`udevadm info` is verbose, but it is excellent for answering questions such as:

- Which physical path produced this `/dev` node?
- What serial number did the kernel and udev see?
- Which stable symlink exists under `/dev/disk/by-id/`?

Prefer stable identifiers such as filesystem UUIDs, labels, or `/dev/disk/by-id/` paths for persistent mounts. Names such as `/dev/sda` can change when device discovery order changes.

## Inspect modules without changing them

Loaded modules are visible with:

```bash
lsmod
```

Module metadata is visible with:

```bash
modinfo igc
```

`modinfo` can show aliases, firmware requirements, parameters, license, source version, and the module file path. Aliases are how the kernel can match a module to supported hardware IDs.

To inspect what `modprobe` would load without actually inserting a module:

```bash
modprobe --show-depends igc
```

Be careful with actual module changes:

```bash
sudo modprobe igc
sudo modprobe -r igc
```

Loading a missing module can be reasonable in a lab or during a maintenance window. Removing a storage, filesystem, GPU, or network module from a live remote host can break the session, the root filesystem, or the service you are trying to repair.

## Check kernel logs for driver and firmware evidence

The kernel log is usually the most useful place to confirm driver binding and firmware failures:

```bash
journalctl -k -b
journalctl -k -b | grep -iE 'firmware|driver|module|failed|error'
```

On systems without persistent journal access, `dmesg` may be available:

```bash
dmesg -T | grep -iE 'firmware|driver|module|failed|error'
```

Common clues include:

- `firmware: failed to load ...`
- `module verification failed`
- `Unknown symbol`
- `probe failed`
- `link is down`
- `renamed from eth0`

Do not stop at the first scary-looking line. Some warnings are harmless on a given platform. Compare the current boot to a known-good boot when possible:

```bash
journalctl -k -b -1
```

## A safe troubleshooting flow

When a device disappears or behaves differently after a change, use this sequence:

1. Record the current kernel:

    ```bash
    uname -r
    ```

2. Confirm whether the hardware is visible on its bus:

    ```bash
    lspci -nn
    lsusb
    ```

3. Confirm which driver, if any, claimed the device:

    ```bash
    lspci -nnk
    sudo ethtool -i enp3s0
    ```

4. Inspect module and firmware clues:

    ```bash
    modinfo driver_name
    journalctl -k -b | grep -iE 'firmware|driver|module|failed|error'
    ```

5. Compare against the previous working state:

    ```bash
    journalctl -k -b -1 | grep -iE 'firmware|driver|module|failed|error'
    ```

6. Choose the lowest-risk correction:

    - Boot the previous known-good kernel.
    - Install the missing firmware package.
    - Install the matching vendor or distro driver package.
    - Adjust persistent interface or mount configuration if the device name changed.
    - Schedule a maintenance window before unloading modules or replacing kernel packages on a remote host.

This flow works because it narrows the problem before it changes the machine.

## Change boundaries

Safe inspection usually includes:

- `lspci`, `lsusb`, `lsblk`, `ip link`
- `lspci -nnk`, `ethtool -i`, `udevadm info`
- `lsmod`, `modinfo`
- `journalctl -k`, `dmesg`

Potentially disruptive changes include:

- `modprobe -r`
- driver blacklists under `/etc/modprobe.d/`
- kernel package removal
- firmware package replacement
- initramfs regeneration
- rebooting into a different kernel
- changing persistent network or storage identifiers

On a remote server, assume the network driver and root-disk driver are load-bearing until proven otherwise. Get console access or an out-of-band recovery path before making changes that can sever the connection.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record your kernel version with `uname -r`.
2. Run `lspci -nnk` or `lsusb -t` and identify one device with a driver.
3. Use `modinfo` on the driver or module name you found.
4. Use `journalctl -k -b` to find one boot message related to that device class.
5. Write a short handoff note that includes the device ID, driver, module file path, firmware clue if any, and the command output that proves it.
