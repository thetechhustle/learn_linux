## 11.1 Kernel Chores for System Administrators

!!! abstract "What you will learn"
    - Identify routine kernel responsibilities for Linux administrators.
    - Inspect the running kernel, installed kernels, boot history, and kernel logs.
    - Plan kernel updates with rollback and console-access assumptions.
    - Clean up old kernels without removing your safest fallback.

!!! example "Field story"
    A server loses network connectivity after a maintenance reboot. The application team suspects a deploy, but the deploy did not change. The useful path is to compare the current and previous kernel, inspect kernel logs, identify the network driver, and confirm whether an older kernel can boot the host safely.

!!! success "Operator principle"
    Kernel chores are routine until they are not. Treat kernel updates, module changes, and bootloader changes as infrastructure changes with evidence, timing, and rollback.

## What counts as a kernel chore?

Most administrators do not write kernel code. They still manage kernel risk.

Common chores include:

- Knowing which kernel is running.
- Applying distribution-supported kernel updates.
- Rebooting at the right time after a kernel update.
- Keeping a known-good fallback kernel.
- Removing old kernels only after the new one is proven.
- Checking kernel logs after boot, hardware, or driver symptoms.
- Identifying loaded modules and module metadata.
- Verifying bootloader entries before maintenance.
- Preserving evidence from failed boots or kernel panics.

These tasks matter because a kernel problem can look like a network outage, storage issue, performance regression, container failure, or boot failure.

## Inspect the current kernel

Start with read-only facts.

```bash
uname -r
uname -a
cat /proc/version
cat /etc/os-release
```

`uname -r` gives the running kernel release. The distribution release matters too, because production systems should normally use kernels packaged and supported by the distribution or vendor.

On Debian and Ubuntu systems, list installed kernel packages with:

```bash
dpkg -l 'linux-image*' | awk '/^ii/ {print $2, $3}'
```

On RHEL, CentOS, Fedora, and similar systems:

```bash
rpm -qa 'kernel*' | sort
```

On systems using `bootctl`:

```bash
bootctl list
```

The goal is to know both the running kernel and the fallback choices available at boot.

## Read kernel logs

Kernel logs are the first place to look for driver, hardware, module, filesystem, memory, and boot-time clues.

```bash
journalctl -k -b --no-pager | tail -100
```

For the previous boot:

```bash
journalctl -k -b -1 --no-pager | tail -100
```

If persistent journald storage is not enabled, previous-boot logs may be unavailable. In that case, check file-backed logs where your distribution stores them:

```bash
ls -l /var/log
grep -iE 'panic|oops|error|fail|firmware|module' /var/log/kern.log 2>/dev/null | tail -50
grep -iE 'panic|oops|error|fail|firmware|module' /var/log/messages 2>/dev/null | tail -50
```

Use `dmesg` for the current kernel ring buffer:

```bash
dmesg --ctime | tail -100
```

`dmesg` is useful, but it is not a durable archive. Capture important output during an incident.

## Inspect modules and drivers

Modules let the running kernel support hardware and features without compiling everything directly into the kernel.

List loaded modules:

```bash
lsmod | head
```

Inspect one module:

```bash
modinfo e1000e
```

Find hardware and driver associations:

```bash
lspci -nnk
```

For network interfaces:

```bash
ip link
ethtool -i eth0
```

Replace `eth0` with the real interface name. On modern systems, names often look like `ens3`, `enp1s0`, or similar.

!!! warning "Module changes can be disruptive"
    `modinfo` and `lsmod` are inspection commands. `modprobe`, `modprobe -r`, and module blacklist changes can alter running hardware behavior. Removing a storage or network driver can break access to the system.

## Plan kernel updates

Kernel updates are often delivered through normal package management, but the new kernel usually does not take effect until reboot.

Debian and Ubuntu examples:

```bash
sudo apt update
sudo apt upgrade
```

RHEL-family examples:

```bash
sudo dnf upgrade
```

Before rebooting a production host, confirm:

1. The update installed a new kernel package.
2. The current kernel is known.
3. A previous working kernel is still available.
4. The bootloader has a usable fallback entry.
5. You have console, rescue, or out-of-band access if networking fails.
6. The reboot window is acceptable for the service.

After reboot:

```bash
uname -r
journalctl -k -b --no-pager | tail -100
systemctl --failed
ip addr
```

The update is not complete just because the host came back. Verify the service, network, storage, and kernel logs.

## Clean up old kernels carefully

Old kernels consume disk space, especially under `/boot`. But keeping at least one known-good older kernel is a practical safety measure.

Check disk usage:

```bash
df -h /boot
```

On Debian and Ubuntu, package tools may remove unused dependencies:

```bash
sudo apt autoremove
```

On Fedora and RHEL-family systems, kernel retention is usually controlled by package manager settings, such as `installonly_limit` for DNF-based systems.

Do not blindly remove every older kernel. Keep a fallback until the newer kernel has survived a real reboot and workload verification.

## Build a kernel-change record

For important hosts, record kernel changes like any other maintenance event:

```text
Host: app-03
Before kernel: 6.1.0-18-amd64
After kernel: 6.1.0-20-amd64
Reason: distribution security update
Window: 2026-05-11 05:00 ET
Rollback: boot previous kernel from GRUB console
Verification:
  - uname -r confirms new kernel
  - journalctl -k -b has no driver errors
  - systemctl --failed is clean
  - network and storage checks passed
```

That record saves time when a symptom appears hours later.

## Hands-on practice

Use a lab VM for anything that might affect boot or drivers.

1. Record your running kernel with `uname -r`.
2. List installed kernel packages or boot entries.
3. Capture current boot kernel logs.
4. Identify one loaded module and read its metadata.
5. Identify your primary network interface and driver.
6. Write a safe reboot checklist for applying a kernel update.
7. Decide how many old kernels you would keep and why.
