### 11.7 Booting

!!! abstract "What you will learn"
    - Trace the Linux boot path from firmware to bootloader, kernel, initramfs, and userspace.
    - Collect boot evidence with `journalctl`, `systemd-analyze`, `/proc/cmdline`, and bootloader files.
    - Separate boot-time failures from kernel, module, storage, network, and service failures.
    - Apply low-risk recovery habits before changing bootloader, kernel, or initramfs settings.

!!! example "Field story"
    A server is reachable through out-of-band console but not over SSH after a kernel update. You need to know whether it failed before the bootloader, in the kernel, in the initramfs, while mounting root storage, or later when networking services started.

!!! success "Operator principle"
    Boot troubleshooting is timeline work. Identify the last successful stage before changing the next thing.

Booting is the sequence that turns powered hardware into a running operating system. In Linux operations, boot knowledge matters whenever a host fails after a kernel update, a root disk move, a storage-driver change, a bootloader edit, a firmware update, or a cloud image migration.

The exact details vary by distribution and hardware, but the operational timeline is usually:

1. Firmware initializes the machine.
2. Firmware chooses a boot target.
3. The bootloader loads the kernel and initramfs.
4. The kernel initializes core hardware and starts early userspace.
5. The initramfs finds and mounts the real root filesystem.
6. The init system starts services and reaches the target boot state.

The fastest way to get unstuck is to locate the failing stage.

## The boot timeline

| Stage | Main job | Common evidence |
| --- | --- | --- |
| Firmware | Initialize hardware and choose boot device | UEFI setup, boot order, Secure Boot state, console messages |
| Bootloader | Select kernel, initramfs, and command line | GRUB menu, `/boot/grub/`, `/boot/loader/entries/` |
| Kernel | Initialize CPU, memory, drivers, and root handoff | `journalctl -k -b`, `dmesg`, `/proc/cmdline` |
| Initramfs | Load early drivers and mount real root | emergency shell, initramfs logs, storage and crypto prompts |
| Init system | Start userspace services | `systemctl`, `journalctl -b`, `systemd-analyze` |
| Application layer | Start workloads | service logs, app health checks, network tests |

Do not skip stages. A service failure after boot is a different problem from a kernel that cannot find the root filesystem.

## Firmware and boot target

Modern systems usually use UEFI. Older systems may use BIOS. Firmware decides which device or network target to boot from and may enforce Secure Boot policy.

Useful questions:

- Is the disk visible in firmware?
- Is the intended disk first in the boot order?
- Is the system using UEFI or legacy BIOS mode?
- Is Secure Boot enabled?
- Is this a local disk boot, cloud image boot, or network boot?

From Linux, you can often confirm UEFI mode with:

```bash
test -d /sys/firmware/efi && echo UEFI || echo BIOS-or-compatibility-mode
```

Inspect firmware-related boot messages:

```bash
journalctl -k -b | grep -iE 'efi|secure|firmware|bios'
```

Firmware problems often require console or provider access. Do not assume SSH-level tools can fix a machine that never reaches the bootloader.

## Bootloader responsibilities

The bootloader chooses the kernel, initramfs, and kernel command line. On many Linux systems that bootloader is GRUB. Some distributions or cloud images use systemd-boot, extlinux, or provider-specific boot mechanisms.

Key evidence:

```bash
cat /proc/cmdline
ls -l /boot
ls -l /boot/grub 2>/dev/null
bootctl status 2>/dev/null
```

`/proc/cmdline` shows the command line used for the current boot. It may include root filesystem identifiers, rescue targets, console routing, security options, module blacklists, or debugging flags:

```text
BOOT_IMAGE=/boot/vmlinuz-6.8.0 root=UUID=... ro quiet
```

Common bootloader-related issues include:

- wrong default kernel
- missing initramfs
- wrong root UUID
- stale bootloader menu after disk migration
- Secure Boot refusing an unsigned kernel or module
- a rescue or emergency target left in the command line

Before editing bootloader files, capture the current state and preserve a known-good boot entry.

## Kernel and initramfs handoff

The bootloader loads the kernel and an initramfs image. The initramfs is a small early userspace environment that contains enough tools and drivers to find the real root filesystem.

The initramfs is critical when root storage depends on:

- storage controller modules
- LVM
- software RAID
- disk encryption
- network boot
- special filesystems

If the initramfs cannot find or unlock the root filesystem, the system may drop to an emergency shell before normal services start.

Inspect installed kernel and initramfs files:

```bash
ls -lh /boot/vmlinuz-* /boot/initrd* /boot/initramfs-* 2>/dev/null
uname -r
```

On Debian or Ubuntu systems, initramfs updates commonly use:

```bash
sudo update-initramfs -u
```

On many Fedora, RHEL, and related systems, the tool is commonly:

```bash
sudo dracut -f
```

Use the tool for your distribution. Rebuilding initramfs is a boot-affecting change, so keep a rollback plan.

## Userspace startup

Once the root filesystem is mounted, the kernel starts the first userspace process. On most modern Linux systems, that is `systemd`.

Check the boot result:

```bash
systemctl is-system-running
systemctl --failed
journalctl -b
```

Analyze boot timing:

```bash
systemd-analyze
systemd-analyze blame
systemd-analyze critical-chain
```

These commands are most useful after the system reaches userspace. If the system never mounts root or never starts init, they will not be available from the broken boot.

## Current and previous boot logs

Compare current and previous boots when possible:

```bash
journalctl --list-boots
journalctl -b
journalctl -k -b
journalctl -b -1
journalctl -k -b -1
```

The `-k` flag focuses on kernel messages. The `-b` flag selects a boot. This is especially useful after a kernel update:

```bash
journalctl -k -b | grep -iE 'error|failed|firmware|module|root|mount|panic'
journalctl -k -b -1 | grep -iE 'error|failed|firmware|module|root|mount|panic'
```

If previous boot logs are missing, persistent journaling may not be enabled or logs may be stored elsewhere by the distribution.

## Boot failure patterns

Use symptoms to narrow the stage:

| Symptom | Likely stage | First evidence to collect |
| --- | --- | --- |
| Machine never shows bootloader | Firmware or hardware | Console, firmware boot order, disk visibility |
| Bootloader appears but kernel missing | Bootloader or `/boot` | Boot menu, `/boot` contents from rescue media |
| Kernel starts then panics | Kernel or driver | Console panic text, `journalctl -k` if available |
| Drops to initramfs shell | Initramfs, root disk, crypto, LVM | root UUID, storage modules, initramfs messages |
| Reaches login but no network | Userspace network or driver | `ip link`, `journalctl -u NetworkManager`, `ethtool -i` |
| Services fail after login | Init system or app config | `systemctl --failed`, service logs |

This is why console output matters. A screenshot or copied console text can save hours.

## Low-risk recovery habits

Before making boot-affecting changes:

- Confirm the currently running kernel with `uname -r`.
- Confirm available kernel and initramfs files in `/boot`.
- Keep at least one known-good previous kernel installed.
- Confirm you have console, IPMI, hypervisor, cloud serial console, or other out-of-band access.
- Record `/proc/cmdline`.
- Record `journalctl -k -b` before and after the change.
- Avoid editing bootloader defaults directly when a temporary one-time boot selection is enough.

For remote systems, assume a bad bootloader, kernel, storage, or initramfs change can remove SSH access.

## Safe inspection commands

These commands are read-only:

```bash
uname -r
cat /proc/cmdline
test -d /sys/firmware/efi && echo UEFI || echo BIOS-or-compatibility-mode
ls -lh /boot
journalctl --list-boots
journalctl -k -b
systemctl --failed
systemd-analyze
```

Potentially disruptive commands include:

- changing GRUB defaults
- editing files under `/boot`
- rebuilding initramfs
- removing kernel packages
- changing root filesystem UUIDs
- changing disk encryption, LVM, or RAID boot settings
- rebooting without a console path

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record whether the system appears to be UEFI or BIOS mode.
2. Record the current kernel with `uname -r`.
3. Save `/proc/cmdline` and identify the root filesystem argument.
4. List installed kernel and initramfs files under `/boot`.
5. Use `journalctl --list-boots` to identify available boot logs.
6. Compare the current kernel log with the previous boot if one exists.
7. Run `systemd-analyze critical-chain` and identify the slowest userspace dependency.
8. Write a short handoff note that says which boot stage you can prove succeeded.
