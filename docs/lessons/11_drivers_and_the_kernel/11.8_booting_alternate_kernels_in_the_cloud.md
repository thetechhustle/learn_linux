### 11.8 Booting Alternate Kernels in the Cloud

Cloud servers are still Linux systems, but their boot path has extra
dependencies: provider firmware, virtual disks, instance metadata, virtual
network devices, and rescue-console features. When a new kernel breaks a cloud
instance, the fastest recovery usually comes from proving what changed,
selecting a known-good kernel, and keeping a rollback path outside the instance
itself.

!!! abstract "What you will learn"
    - Identify why a cloud instance may need an alternate kernel.
    - Gather evidence about the running kernel, installed kernels, boot loader entries, and provider image.
    - Choose a lower-risk boot path for kernel testing or recovery.
    - Plan rollback options before rebooting a remote system.

!!! warning "Remote reboot safety"
    A bad kernel choice can remove SSH, block storage, networking, or the serial
    console. Before changing the default kernel on a cloud instance, confirm that
    you have a snapshot, console access, or a provider-supported rescue path.

## Why alternate kernels matter in cloud operations

Alternate kernel booting shows up in several common situations:

- A package update installs a kernel with a driver regression.
- A cloud image ships a provider-tuned kernel and you need to compare it with a generic distribution kernel.
- A security update must be tested before it becomes the default on production systems.
- A specialized workload needs a kernel flavor with different scheduling, virtualization, or device support.
- A broken default boot entry must be bypassed long enough to recover the instance.

The operational goal is not to collect kernels. It is to keep at least one
known-good boot path while you test one narrow change.

## Build the evidence trail

Start with read-only commands. Capture the output in your incident notes or
change ticket.

```bash
uname -a
uname -r
cat /etc/os-release
hostnamectl
```

List installed kernels with the package manager. Use the command that matches
the distribution.

```bash
dpkg -l 'linux-image*' | awk '/^ii/ {print $2, $3}'
rpm -qa 'kernel*' | sort
```

Inspect boot loader entries before changing the default.

```bash
sudo grubby --info=ALL
sudo grep -R "menuentry " /boot/grub /boot/grub2 2>/dev/null
sudo awk -F"'" '/menuentry / {print NR ": " $2}' /boot/grub/grub.cfg 2>/dev/null
```

On cloud instances, also record provider-facing evidence:

```bash
curl -s http://169.254.169.254/latest/meta-data/instance-id 2>/dev/null
lsblk -f
ip -brief address
lspci -nn 2>/dev/null | grep -Ei 'network|ethernet|nvme|virtio'
```

The metadata endpoint differs by provider, and some providers require headers
or tokens. If the command does not return data, record that fact instead of
forcing it during an incident.

## Compare cloud kernel paths

Cloud images commonly use one of these patterns:

| Pattern | What it means | Operational concern |
| --- | --- | --- |
| Provider-tuned kernel | The image uses a kernel package optimized for that cloud, such as an AWS, Azure, or Google flavor. | A generic kernel may lack expected drivers or tuning. |
| Distribution generic kernel | The image uses the standard distro kernel. | Provider agents and boot configuration still matter. |
| Image-baked kernel | The kernel and boot loader state came from a golden image. | Fixes may belong in the image pipeline, not only one instance. |
| Rescue or recovery kernel | The provider can attach disks to another host or boot a recovery environment. | This is your escape path if the instance cannot boot. |

Before installing anything, identify which pattern the instance is using.

## Choose a safer boot strategy

Prefer a one-time boot test when your tooling supports it. A one-time boot keeps
the old default in place unless the test kernel proves itself.

On GRUB-based systems, inspect entries first:

```bash
sudo grub-editenv list
sudo awk -F"'" '/menuentry / {print $2}' /boot/grub/grub.cfg 2>/dev/null
```

Then set a one-time entry only when you are sure of the exact menu entry name:

```bash
sudo grub-reboot "Advanced options for Ubuntu>Ubuntu, with Linux 6.8.0-31-generic"
sudo reboot
```

On many RPM-based distributions, `grubby` is the cleaner interface:

```bash
sudo grubby --info=ALL
sudo grubby --set-default /boot/vmlinuz-6.8.0-31.el9.x86_64
sudo grubby --default-kernel
```

`grubby --set-default` changes the persistent default, so use it only when you
have a tested rollback route. Some environments also support provider console
menus, serial-console intervention, snapshots, or detach-and-repair workflows.

## Install or retain an alternate kernel

Install kernel packages through the normal package manager. Avoid manually
copying random `vmlinuz` and `initramfs` files unless you are following a
distribution-specific recovery procedure.

Debian and Ubuntu examples:

```bash
apt-cache policy linux-image-generic linux-image-aws
sudo apt install linux-image-generic
sudo update-grub
```

RHEL, Fedora, and related examples:

```bash
dnf list installed 'kernel*'
sudo dnf install kernel
sudo grubby --info=ALL
```

Keep at least one older working kernel until the new kernel has survived a
reboot and a service validation window. Kernel cleanup should be a separate,
deliberate maintenance task.

## Verify after reboot

After the instance comes back, prove three things: the intended kernel booted,
the cloud devices are present, and the workload still works.

```bash
uname -r
uptime
lsblk
ip route
systemctl --failed
journalctl -k -b --no-pager | tail -50
```

For network-sensitive changes, confirm the interface driver and address state:

```bash
ip -brief link
ethtool -i eth0 2>/dev/null || true
lspci -nn 2>/dev/null | grep -Ei 'network|ethernet|virtio|ena|mlx'
```

For storage-sensitive changes, confirm boot disk and mount health:

```bash
findmnt /
lsblk -o NAME,FSTYPE,SIZE,MOUNTPOINTS
journalctl -b --no-pager | grep -Ei 'nvme|virtio|xfs|ext4|mount|timeout' | tail -30
```

## Rollback options

Plan rollback before the reboot, not after the outage starts.

- Snapshot the root volume before the kernel change.
- Confirm serial console access or provider rescue mode.
- Keep the previous kernel package installed.
- Record the exact previous default kernel or GRUB entry.
- Know how to detach the root volume and repair `/boot` from another instance.
- Avoid changing kernels and provider agents in the same maintenance window.

If the instance does not come back, use the least invasive recovery path first:
serial console, one-time boot menu, provider recovery mode, or root-volume repair
from a helper instance.

## Troubleshooting quick reference

| Symptom | First checks | Likely next step |
| --- | --- | --- |
| Instance boots but SSH is unavailable | Provider console, `ip route`, `journalctl -k -b`, security group rules | Check network driver, cloud-init, and firewall state. |
| Instance fails before login | Serial console screenshot or log, boot loader entry, root disk attachment | Boot older kernel or repair `/boot` from rescue mode. |
| Root filesystem is missing | `lsblk`, `findmnt`, kernel logs for storage drivers | Boot a kernel with the right block-device driver or rebuild initramfs. |
| New kernel is running but services fail | `systemctl --failed`, application logs, package history | Roll back the kernel or fix the service-specific compatibility issue. |

## Hands-on practice

Use a disposable cloud instance or local VM that you can rebuild.

1. Record the current kernel, OS release, boot entries, network interface state, and root disk layout.
2. Identify whether the system is using a generic distribution kernel or a cloud-specific kernel package.
3. Install or locate one alternate kernel package without removing the current working kernel.
4. Configure a one-time boot into the alternate kernel if your lab environment supports it.
5. Reboot and verify the running kernel, network route, failed services, and kernel log.
6. Restore the original default kernel and prove the rollback with `uname -r`.
7. Write a short handoff note explaining the test, evidence, result, and rollback path.
