### 11.5 FreeBSD Kernel Configuration

FreeBSD is not Linux, but Linux administrators often meet it in firewalls,
storage appliances, network appliances, and legacy Unix environments. The
important difference is packaging: FreeBSD is a complete operating system with a
base system, kernel, userland, ports/packages, and documentation released
together. Kernel configuration work should respect that integrated model.

Most FreeBSD systems should run the stock `GENERIC` kernel. Custom kernels are
for clear operational needs: removing unused hardware support in constrained
systems, enabling a kernel option that is not available as a module, building a
special-purpose appliance image, or reproducing a vendor-supported
configuration. Treat kernel changes as boot-risk changes, not as routine tuning.

!!! abstract "What you will learn"
    - Identify the running FreeBSD kernel and the kernel configuration it came
      from.
    - Find kernel modules, tunables, and boot-time settings before choosing a
      custom build.
    - Build and install a custom FreeBSD kernel only after preserving a rollback
      path.
    - Troubleshoot failed boots and missing driver support without making the
      system worse.

!!! warning "Production safety"
    Do not remove the known-good kernel before proving that the new kernel
    boots, loads storage and network drivers, and supports remote access. Kernel
    mistakes can leave a remote server unreachable.

## Start with evidence

Begin by recording what the system is running now.

```console
$ uname -a
$ freebsd-version -kru
$ sysctl kern.bootfile kern.conftxt
$ kldstat
```

Read those results as an incident note:

- `uname -a` shows the running kernel release and architecture.
- `freebsd-version -kru` compares the installed kernel, running kernel, and
  userland versions.
- `kern.bootfile` shows which kernel path the loader started.
- `kern.conftxt` may expose the compiled kernel configuration on systems that
  include it.
- `kldstat` lists loaded kernel modules.

If the problem is a missing driver, confirm whether a module can solve it before
building a custom kernel.

```console
$ kldstat | less
$ ls /boot/kernel/*.ko | less
$ man kldload
$ man loader.conf
```

For many changes, `/boot/loader.conf`, `/etc/rc.conf`, or a module package is a
lower-risk answer than rebuilding the kernel.

## Know the configuration files

FreeBSD kernel configuration files usually live under the source tree:

```console
/usr/src/sys/amd64/conf/GENERIC
/usr/src/sys/amd64/conf/MINIMAL
/usr/src/sys/arm64/conf/GENERIC
```

The architecture directory depends on the machine. Use `uname -m` to locate the
right one.

```console
$ uname -m
$ ls /usr/src/sys/$(uname -m)/conf
```

If `/usr/src` is missing, install or fetch source that matches the system
release before building. Do not mix random source branches with a production
host.

```console
$ freebsd-version -u
$ ls /usr/src
```

Follow the FreeBSD Handbook for the supported source-management method for that
release. Modern FreeBSD systems commonly use `git` for source updates; older
instructions that reference Subversion are historical and should not be copied
blindly.

## Prefer a minimal custom file

Keep custom configuration small and traceable. Start with `GENERIC`, then add
only the difference you can justify.

```console
$ cd /usr/src/sys/$(uname -m)/conf
$ sudo cp GENERIC MYKERNEL
$ sudo vi MYKERNEL
```

At the top of the file, add a short comment that explains the operational reason
for the custom kernel:

```text
# MYKERNEL - enables option X for appliance Y.
# Change ticket: INC-1234
include GENERIC
```

Where possible, use an `include GENERIC` style and append the required
differences. A full copy of `GENERIC` is harder to review later because it hides
what the system owner actually changed.

## Build with a rollback path

Before installing, preserve the known-good boot target and confirm console or
out-of-band access.

```console
$ su -
# cp -a /boot/kernel /boot/kernel.good
# cd /usr/src
# make buildkernel KERNCONF=MYKERNEL
# make installkernel KERNCONF=MYKERNEL
```

After installation, do not declare success just because the build completed.
Reboot during a maintenance window and verify the hardware and services that
matter.

```console
$ uname -a
$ freebsd-version -kru
$ kldstat
$ ifconfig
$ zpool status
$ service -e
```

If the new kernel fails, use the boot loader menu or loader prompt to boot the
saved kernel, such as `kernel.good`, then restore the previous configuration.

## Use loader tunables for boot-time behavior

Some kernel behavior is controlled at boot without recompiling. Inspect current
values first:

```console
$ sysctl -a | less
$ sysctl hw.model hw.ncpu kern.maxfiles
$ cat /boot/loader.conf
```

Add loader tunables only when the FreeBSD manual page or Handbook says the value
must be set before the kernel starts. Runtime `sysctl` values belong in
`/etc/sysctl.conf` when they need to persist.

## Troubleshooting checklist

If a FreeBSD host loses hardware support after a kernel change:

1. Boot the previous kernel if the system is unreachable or missing root storage.
2. Compare `uname -a`, `freebsd-version -kru`, and `kldstat` against the last
   known-good note.
3. Check `/boot/loader.conf` for removed or misspelled module entries.
4. Confirm that the custom configuration did not remove storage, network,
   filesystem, firewall, or virtualization support.
5. Rebuild from a clean source tree that matches the installed release.

Avoid changing several variables at once. A source update, config edit, module
change, and boot-loader edit in one maintenance window make rollback much
harder.

## Lab: compare module and kernel choices

Use a disposable FreeBSD VM or lab host.

1. Record the running kernel and userland versions:

   ```console
   $ uname -a
   $ freebsd-version -kru
   ```

2. List loaded modules and save the output:

   ```console
   $ kldstat
   ```

3. Pick one loaded module and read its manual page or related Handbook section.
   Note whether it can be loaded through `/boot/loader.conf`.

4. Find the matching architecture configuration directory:

   ```console
   $ uname -m
   $ ls /usr/src/sys/$(uname -m)/conf
   ```

5. Write a short change plan that says whether you would use a module, loader
   tunable, runtime `sysctl`, or custom kernel build. Include the rollback step.
