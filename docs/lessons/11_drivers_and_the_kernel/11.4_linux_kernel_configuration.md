### 11.4 Linux Kernel Configuration

!!! abstract "What you will learn"
    - Explain what a Linux kernel configuration controls and where it appears on installed systems.
    - Inspect the running kernel's configuration without rebuilding anything.
    - Understand the difference between built-in features, loadable modules, and disabled options.
    - Use a safe workflow for kernel configuration changes in labs, vendor builds, and production fleets.

!!! example "Field story"
    A compliance scanner says a server lacks a required kernel security option. Before anyone rebuilds a kernel, you need to prove which kernel is running, whether the option is built in, modular, or disabled, and whether the distribution already ships a supported kernel variant that meets the requirement.

!!! success "Operator principle"
    Kernel configuration is a change-control problem, not just a compile-time menu. Inspect first, preserve the previous kernel, and prefer supported vendor or distribution kernels unless you have a clear reason to own the rebuild.

The Linux kernel is built from source code plus a configuration file. That configuration decides which features are compiled directly into the kernel image, which features are built as loadable modules, and which features are left out.

Kernel configuration affects hardware support, filesystems, networking, security frameworks, virtualization, tracing, power management, and platform-specific behavior. It can make a system boot, fail to boot, expose a feature, remove a feature, or change how a driver is delivered.

Most administrators do not rebuild kernels every week. In production, the safest path is usually to use distribution kernels, vendor kernels, cloud-provider kernels, or appliance-supported kernels. But you still need to read kernel configuration evidence when troubleshooting, auditing, or preparing a specialized lab build.

## What kernel configuration controls

Kernel options usually appear as `CONFIG_` symbols:

```text
CONFIG_EXT4_FS=y
CONFIG_BTRFS_FS=m
# CONFIG_DEBUG_INFO is not set
```

The value matters:

| Value | Meaning | Operational effect |
| --- | --- | --- |
| `y` | Built in | Feature is part of the kernel image and does not need a separate module load. |
| `m` | Module | Feature can be loaded as a kernel module when needed. |
| not set | Disabled | Feature is unavailable in that kernel build. |

For example, if `CONFIG_EXT4_FS=y`, ext4 support is built in. If `CONFIG_BTRFS_FS=m`, btrfs support is delivered by a module. If `CONFIG_WIREGUARD` is not set, that kernel was not built with WireGuard support.

## Inspect the running kernel configuration

Start with the kernel that is actually running:

```bash
uname -r
```

Then look for a config file that matches that exact version:

```bash
ls /boot/config-$(uname -r)
grep '^CONFIG_EXT4_FS=' /boot/config-$(uname -r)
grep '^CONFIG_BTRFS_FS=' /boot/config-$(uname -r)
```

Some systems expose the running config through procfs:

```bash
zgrep '^CONFIG_EXT4_FS=' /proc/config.gz
```

If neither path exists, check the distribution's kernel package files or build metadata. Do not assume `/boot/config-*` from another installed kernel applies to the current boot.

Useful read-only checks:

```bash
uname -a
ls -l /boot/vmlinuz-* /boot/config-* 2>/dev/null
lsmod
modinfo module_name
journalctl -k -b
```

These commands help you connect configuration, loaded modules, and boot-time behavior.

## Built in, module, or missing

Suppose you need to understand why a filesystem does or does not mount.

Check the kernel configuration:

```bash
grep '^CONFIG_XFS_FS=' /boot/config-$(uname -r)
```

Possible results:

```text
CONFIG_XFS_FS=y
```

XFS is built in. There may be no separate `xfs` module to load.

```text
CONFIG_XFS_FS=m
```

XFS should be available as a module. You can inspect it:

```bash
modinfo xfs
```

```text
# CONFIG_XFS_FS is not set
```

This kernel does not include XFS support. Loading a module will not work unless a compatible module package exists for this exact kernel build.

This same pattern applies to drivers, netfilter features, virtualization features, tracing support, and security options.

## Common configuration evidence questions

During operations, you are usually answering one of these questions:

- Is a required feature present in the running kernel?
- Is the feature built in or modular?
- Is the expected module installed for this exact kernel version?
- Did a recent kernel update change the feature's availability?
- Is this a distribution-supported kernel or a custom build?
- Can the requirement be met by installing a supported kernel flavor instead of compiling a custom kernel?

Examples:

```bash
grep '^CONFIG_KVM=' /boot/config-$(uname -r)
grep '^CONFIG_NF_TABLES=' /boot/config-$(uname -r)
grep '^CONFIG_OVERLAY_FS=' /boot/config-$(uname -r)
grep '^CONFIG_SECURITY_SELINUX=' /boot/config-$(uname -r)
grep '^CONFIG_BPF=' /boot/config-$(uname -r)
```

Do not treat a single symbol as the whole answer. Some features depend on multiple symbols, modules, userspace packages, firmware, CPU capabilities, and boot parameters.

## Configuration tools

When building a kernel from source, the source tree provides several configuration targets:

| Target | Use case |
| --- | --- |
| `make menuconfig` | Text-based menu interface; common on servers and terminals. |
| `make nconfig` | Newer text interface with search and navigation improvements. |
| `make xconfig` | Qt graphical interface. |
| `make gconfig` | GTK graphical interface. |
| `make oldconfig` | Start from an existing config and answer prompts for new options. |
| `make olddefconfig` | Start from an existing config and accept defaults for new options. |
| `make defconfig` | Start from architecture defaults. |
| `make localmodconfig` | Build a smaller config based on currently loaded modules; useful for labs, risky as a production shortcut. |

The most important production habit is starting from a known-good config:

```bash
cp /boot/config-$(uname -r) .config
make olddefconfig
```

That preserves the distribution's baseline better than starting from scratch.

## Safe kernel configuration workflow

Use this workflow before proposing or applying a kernel configuration change:

1. Record current evidence:

    ```bash
    uname -r
    cp /boot/config-$(uname -r) kernel-config-before.txt
    journalctl -k -b > kernel-log-before.txt
    ```

2. Identify the exact option and dependency chain:

    ```bash
    grep '^CONFIG_OPTION_NAME=' kernel-config-before.txt
    ```

3. Check whether a supported kernel package already solves the problem:

    - Distribution generic kernel
    - Distribution hardware-enablement kernel
    - Cloud provider kernel
    - Realtime kernel
    - Vendor-supported appliance or hardware kernel

4. If a custom build is necessary, build and test it on non-production hardware first.

5. Preserve rollback:

    - Keep the previous kernel installed.
    - Keep bootloader entries for the previous kernel.
    - Confirm console or out-of-band access.
    - Avoid removing old kernel packages until the new boot is proven.

6. Verify after boot:

    ```bash
    uname -r
    grep '^CONFIG_OPTION_NAME=' /boot/config-$(uname -r)
    journalctl -k -b
    ```

Kernel changes need rollback planning because a bad kernel can fail before SSH, networking, storage, or logging is available.

## Boot parameters are different

Kernel configuration is compile-time. Kernel command-line parameters are boot-time.

Inspect boot parameters with:

```bash
cat /proc/cmdline
```

Examples of boot-time settings include:

- `root=...`
- `quiet`
- `systemd.unit=rescue.target`
- `intel_iommu=on`
- `apparmor=1`
- `selinux=0`
- `module_blacklist=...`

A feature might require both compile-time support and a boot-time parameter. For example, an IOMMU-related feature may depend on kernel config, firmware settings, CPU support, and a command-line parameter.

## Distribution kernels versus custom kernels

Distribution kernels carry more than a `.config` file. They also include:

- security patches
- stable backports
- module packaging
- initramfs integration
- signing and Secure Boot support
- automated updates
- crash fixes and vendor support expectations

Custom kernels can be appropriate for embedded systems, specialized appliances, research, performance experiments, or hardware enablement that cannot wait. But they also create ownership:

- Who rebuilds after security updates?
- Who signs modules?
- Who maintains the config diff?
- Who validates boot, storage, network, and rollback?
- Who documents which machines run the custom kernel?

If you cannot answer those questions, prefer a supported kernel package.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record the running kernel with `uname -r`.
2. Find the matching config file under `/boot` or `/proc/config.gz`.
3. Check five options:
    - `CONFIG_EXT4_FS`
    - `CONFIG_OVERLAY_FS`
    - `CONFIG_BPF`
    - `CONFIG_KVM`
    - one driver or feature relevant to your machine
4. For each option, label it as built in, modular, disabled, or not found.
5. Pick one loaded module from `lsmod`, inspect it with `modinfo`, and explain how it relates to kernel configuration.
6. Write a rollback note for a hypothetical kernel change that includes the previous kernel version and how you would reach the machine if networking failed.
