!!! success "Operator principle"
    Jenkins is not just a web page that runs jobs. It is a long-running automation service with credentials, plugins, workers, logs, artifacts, and deployment authority. Treat it like production infrastructure.

## What Jenkins does

Jenkins is an open source automation server. Teams use it to run repeatable work after code changes, scheduled events, or manual approvals.

Common Jenkins jobs include:

- checking out source code from Git
- installing dependencies
- running unit, integration, or security tests
- building packages, images, or documentation
- publishing artifacts
- deploying to staging or production
- notifying people or systems when a job fails

Jenkins can run a simple shell script, but its real value is coordination. It ties together source control, build tools, test tools, secret stores, artifact repositories, deployment targets, and human approval gates.

## Controller, agents, and jobs

A Jenkins environment usually has three important parts:

- **Controller:** The central Jenkins server. It stores job configuration, schedules builds, serves the web UI, manages credentials, and coordinates agents.
- **Agent:** A worker machine, VM, container, or process that actually runs build steps. Agents let Jenkins keep risky or expensive work away from the controller.
- **Job or pipeline:** The automation definition. A pipeline normally lives in a `Jenkinsfile` in the same repository as the application or infrastructure code.

Small labs often run everything on one host. Production environments should separate controller duties from build execution so a broken or hostile build does not casually damage the Jenkins controller.

## Linux service shape

On a Linux host, a package-installed Jenkins service usually creates:

- a service unit such as `jenkins.service`
- a service account such as `jenkins`
- a home directory such as `/var/lib/jenkins`
- logs available through the service manager or Jenkins logs
- a web listener, commonly on TCP port `8080`

Use read-only checks first:

```sh
systemctl status jenkins
systemctl cat jenkins
ss -ltnp | grep 8080
id jenkins
ls -ld /var/lib/jenkins
journalctl -u jenkins --no-pager -n 50
```

These commands answer basic operational questions:

- Is Jenkins running?
- Which user owns it?
- Which port is listening?
- Where is its state stored?
- What happened in recent service logs?

## Installation caution

Jenkins installation steps vary by distribution and change over time. Prefer the current official package instructions for your OS, then record the exact repository, package, Java version, and service settings you used.

After installation, verify the service before opening it broadly:

```sh
systemctl is-enabled jenkins
systemctl is-active jenkins
ss -ltnp | grep 8080
```

On a shared network, do not expose Jenkins to everyone just because the service starts. Put it behind appropriate authentication, firewall rules, TLS, and access controls before treating it as a shared automation system.

## Pipeline anatomy

A Jenkins pipeline commonly moves through stages like this:

1. **Checkout:** Pull the source revision that triggered the build.
2. **Prepare:** Install dependencies or start test services.
3. **Test:** Run automated checks.
4. **Build:** Produce a package, image, binary, site, or other artifact.
5. **Archive:** Store the output and logs needed for later inspection.
6. **Publish:** Push artifacts to a registry or repository.
7. **Deploy:** Apply the artifact to a target environment.
8. **Verify:** Confirm the deployment behaved as expected.

A pipeline should make the important evidence easy to find:

- source commit or tag
- build number
- test results
- artifact name and checksum
- deployment target
- approver, if one was required
- rollback or recovery note

## Jenkinsfile example

This simplified example shows the shape of a pipeline:

```groovy
pipeline {
    agent any

    stages {
        stage('Test') {
            steps {
                sh 'make test'
            }
        }

        stage('Build') {
            steps {
                sh 'make build'
                archiveArtifacts artifacts: 'dist/**', fingerprint: true
            }
        }
    }
}
```

The important point is not Groovy syntax. The important point is that the build steps are visible, reviewable, repeatable, and tied to the repository.

## Credentials and permissions

Jenkins often needs access to powerful systems: Git hosts, container registries, package repositories, cloud APIs, deployment hosts, and notification channels.

Keep credentials controlled:

- store secrets in Jenkins credentials or a dedicated secret manager
- avoid hardcoding tokens in `Jenkinsfile`, shell scripts, or console output
- limit credentials to the smallest environment and action possible
- separate read-only build credentials from deployment credentials
- rotate credentials when agents, plugins, or job definitions are compromised

If a Jenkins job can deploy to production, then anyone who can change that job or its repository may have a path to production. Protect the repository, branch rules, Jenkins permissions, and credential bindings together.

## Plugins are dependencies

Jenkins is flexible because of plugins. That flexibility is also a maintenance responsibility.

Track:

- which plugins are installed
- why each plugin is needed
- when plugins were last updated
- whether a plugin is abandoned or vulnerable
- whether a job depends on plugin-specific behavior

Plugin drift can break pipelines after a restart or upgrade. Treat plugin lists like part of the platform contract, not like random UI settings.

## Common failure patterns

When a Jenkins job fails, start with the smallest evidence trail:

```sh
systemctl status jenkins
journalctl -u jenkins --no-pager -n 100
```

Then inspect the failed build:

- Which stage failed?
- Did the source checkout succeed?
- Did the agent connect?
- Did the job run on the expected label or node?
- Was a credential unavailable or expired?
- Did the build run out of disk, memory, or time?
- Was the failure in the tool, the test, the environment, or the deployment target?

Frequent symptoms and likely first checks:

- **Job queued forever:** no matching agent, offline agent, exhausted executor, or label mismatch.
- **Checkout failed:** repository access, branch name, deploy key, token scope, or network path.
- **Build tool not found:** wrong agent image, missing package, changed `PATH`, or undocumented dependency.
- **Secret missing:** credential ID mismatch, permission issue, or binding removed.
- **Deployment failed:** target unavailable, bad artifact, expired cloud credentials, or missing approval.
- **Controller unstable:** plugin issue, Java mismatch, disk pressure, memory pressure, or corrupt workspace/cache.

## Operational hygiene

Good Jenkins operations include:

- backing up Jenkins configuration and job definitions
- moving job definitions into repository-controlled `Jenkinsfile` files when practical
- using agents for build execution instead of overloading the controller
- limiting who can configure jobs and credentials
- pruning old workspaces and artifacts intentionally
- monitoring disk, memory, executor use, queue length, and job failure rate
- documenting how to pause deployments during incidents
- testing Jenkins upgrades in a non-production environment first

## Hands-on practice

Use a lab Jenkins instance or a documented example. Do not experiment on a production controller.

1. Find the Jenkins service status and recent logs.
2. Identify the service account and Jenkins home directory.
3. Identify the listening port and whether it is bound to localhost or a network interface.
4. Open one pipeline or example `Jenkinsfile`.
5. Write down:
   - trigger
   - stages
   - agent label
   - credentials used
   - artifact output
   - deployment target, if any
6. Pick one failed or sample build and explain the first three pieces of evidence you would collect.
