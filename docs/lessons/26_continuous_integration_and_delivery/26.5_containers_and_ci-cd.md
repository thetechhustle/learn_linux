## 26.5 Containers and CI/CD

Containers make CI/CD more repeatable, but they do not make the process automatic or safe by themselves. A pipeline still needs clear build inputs, test stages, image tags, registry permissions, deployment controls, and rollback evidence.

!!! abstract "What you will learn"
    - Explain why containers are useful in CI/CD pipelines.
    - Build and test an image without leaking secrets into the image or logs.
    - Use immutable tags or digests so deployments are traceable.
    - Identify common container pipeline failures and the evidence that proves what happened.

!!! warning "Production caution"
    Do not deploy `latest` to production, bake secrets into images, or let CI jobs push to every registry namespace. Treat a container image as a release artifact: it should be built from reviewed source, scanned, tested, signed or attested where your platform supports it, and promoted deliberately.

## Why containers fit CI/CD

A container image gives a pipeline a portable runtime package. Instead of asking every test runner and deployment host to install the same language runtime, system packages, and application files by hand, the pipeline can build one image and run that image through checks.

Containers help most when they are used for:

- **Consistent test environments**: run the same image locally, in CI, and in staging.
- **Artifact promotion**: build once, then promote the same image digest through later environments.
- **Dependency isolation**: keep application dependencies out of the runner host.
- **Fast rollback**: redeploy a previously known-good image when a release fails.
- **Service composition**: run databases, queues, browsers, or fake services beside the application during integration tests.

They do not remove the need for host operations. The CI runners, registry, deployment platform, image cache, credentials, network access, and runtime policies are still Linux systems that need monitoring and maintenance.

## A container pipeline shape

A practical container pipeline usually follows this flow:

1. **Checkout** the exact source revision.
2. **Build** the image from a Dockerfile, Containerfile, or build definition.
3. **Test** the image with unit tests, integration tests, and smoke checks.
4. **Scan** for known vulnerabilities and obvious policy violations.
5. **Tag and push** the image to a registry only after checks pass.
6. **Deploy** by digest or immutable version tag.
7. **Verify** the running workload and keep rollback instructions close.

The important habit is to separate build identity from deployment identity. A job that builds pull requests should not have the same permissions as a job that deploys production.

## Build an image with traceable metadata

Use a tag that points back to the source revision. Many teams use the Git commit SHA, a release version, or both:

```sh
IMAGE="registry.example.com/platform/webapp"
VERSION="$(git rev-parse --short=12 HEAD)"

docker build \
  --label "org.opencontainers.image.revision=$(git rev-parse HEAD)" \
  --label "org.opencontainers.image.source=$(git config --get remote.origin.url)" \
  -t "$IMAGE:$VERSION" \
  .
```

Then inspect the image before pushing it:

```sh
docker image inspect "$IMAGE:$VERSION" \
  --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}'
```

This kind of label does not replace a release system, but it gives an operator a fast way to connect a running container back to source control during an incident.

## Run tests inside the built image

The build should prove that the image can run the same commands the deployment will run. For a Python application, a test stage might look like this:

```sh
docker run --rm "$IMAGE:$VERSION" python -m pytest
```

For a web service, add a smoke test that starts the container and checks the listening endpoint:

```sh
docker network create ci-smoke
docker run -d --rm --name web-smoke --network ci-smoke "$IMAGE:$VERSION"
docker run --rm --network ci-smoke curlimages/curl:latest \
  --fail --retry 10 --retry-delay 1 http://web-smoke:8080/health
docker stop web-smoke
docker network rm ci-smoke
```

In real CI systems, use cleanup hooks so failed jobs still stop containers and remove temporary networks.

## Keep secrets out of images

Container build logs are easy to copy, search, and retain. Never pass production secrets with plain build arguments such as `--build-arg PASSWORD=...`; they can end up in logs, image history, or cached layers.

Safer patterns include:

- Use CI secret stores for registry credentials and deployment tokens.
- Mount short-lived secrets only for the command that needs them.
- Fetch private dependencies with scoped tokens that cannot deploy or administer infrastructure.
- Confirm image history before publishing:

```sh
docker history --no-trunc "$IMAGE:$VERSION"
```

If a secret leaks into an image, deleting the tag is not enough. Rotate the secret, remove the image from every registry/cache you control, and assume the old layer may have been copied.

## Tags, digests, and registries

Tags are names. Digests identify exact image content. A tag such as `webapp:1.8.2` can be moved unless your registry policy prevents it; a digest such as `sha256:...` points to a specific image.

After pushing, record the digest:

```sh
docker push "$IMAGE:$VERSION"
docker inspect --format='{{index .RepoDigests 0}}' "$IMAGE:$VERSION"
```

Deploying by digest makes rollouts easier to audit:

```sh
kubectl set image deployment/webapp \
  webapp="$IMAGE@sha256:REPLACE_WITH_DIGEST"
kubectl rollout status deployment/webapp
```

For non-Kubernetes hosts, the same principle applies: record exactly which image digest was pulled and which service or unit file started it.

## Promotion over rebuilding

A common mistake is rebuilding the image separately for development, staging, and production. That can produce three different artifacts from the same source if base images, package repositories, or build scripts changed between runs.

A safer pipeline builds once and promotes the same digest:

- Pull request: build and test an untrusted image without deployment credentials.
- Main branch: build, test, scan, and push a candidate image.
- Staging: deploy the candidate digest and run smoke tests.
- Production: promote the already-tested digest after approval or policy checks.

This model makes the question "what changed?" easier to answer.

## Common failure patterns

| Symptom | Likely cause | Evidence to collect |
| --- | --- | --- |
| Build passed yesterday but fails today | Moving base image or package repository change | Dockerfile `FROM` line, build log, base image digest |
| Tests pass in CI but fail in production | Different runtime configuration or missing dependency | Environment variables, mounted files, image digest, container logs |
| Deployment runs old code | Tag was reused or node pulled cached image | Deployed digest, registry tag history, runtime image ID |
| Pull fails during deploy | Registry auth, network, rate limit, or missing tag | Runtime events, registry logs, CI push output |
| Image is huge or slow to pull | Build context includes unnecessary files or cached package data | Image layer history, `.dockerignore`, build output |
| Secret appears in image history | Secret passed during build or copied into a layer | `docker history --no-trunc`, registry audit logs |

## Hands-on practice

Run this in a disposable repository or lab VM with Docker or Podman installed.

1. Create a tiny application with a health endpoint or a command that exits successfully.
2. Build an image tagged with your current Git commit SHA.
3. Run the test command inside the image.
4. Inspect the image labels and history.
5. Push the image to a private test registry if you have one.
6. Record the image digest and explain why it is better deployment evidence than a mutable tag.

Example lab commands:

```sh
IMAGE="localhost/learn-linux-container-lab"
VERSION="$(git rev-parse --short=12 HEAD 2>/dev/null || date +%Y%m%d%H%M)"

docker build -t "$IMAGE:$VERSION" .
docker run --rm "$IMAGE:$VERSION" ./test.sh
docker image inspect "$IMAGE:$VERSION"
docker history --no-trunc "$IMAGE:$VERSION"
```

If you use Podman, the equivalent commands are usually the same with `podman` in place of `docker`.
