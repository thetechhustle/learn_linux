# CI/CD in Practice

!!! abstract "What you will learn"
    - Describe a practical CI/CD workflow from commit to production verification.
    - Identify the evidence a Linux operator should collect at each stage.
    - Separate build, test, release, deployment, and rollback responsibilities.
    - Troubleshoot a failed pipeline without widening the blast radius.

!!! success "Operator principle"
    A working CI/CD system is not measured by how fast it can run on a good day. It is measured by whether it gives clear evidence, safe controls, and a recovery path when a change fails.

## Start with one service

The easiest way to make CI/CD practical is to start with one service, one repository, and one deployment target.

Before automating, write down:

- where the source code lives
- how developers run tests locally
- how the build artifact is created
- where artifacts are stored
- what environment receives the deployment first
- what command or tool performs the deployment
- what health check proves the deployment worked
- how to roll back when it does not work

If those facts are unclear, automation will only make the uncertainty faster.

## A practical flow

A healthy first CI/CD flow usually looks like this:

1. A developer opens a pull request.
2. CI checks out the exact commit.
3. CI installs dependencies in a clean environment.
4. CI runs formatting, lint, unit tests, and focused integration tests.
5. CI builds an artifact from the same commit.
6. The artifact is archived or pushed to a registry.
7. A merge to the protected branch starts a deployment to staging.
8. Staging runs smoke checks or post-deployment tests.
9. A human or policy gate approves production deployment.
10. Production deployment records the artifact, commit, operator, and result.
11. Monitoring confirms the new version is healthy.

The exact tools may differ. The shape should stay recognizable.

## Local command parity

CI should run commands that developers and operators can reproduce locally.

Good examples:

```sh
make test
make build
make lint
make package
```

Weak examples:

```sh
curl https://some-script.example/install.sh | bash
ssh app01 'cd /srv/app && git pull && sudo systemctl restart app'
```

The first set is named, reviewable, and easy to document. The second set hides too much risk: remote script execution, mutable server state, direct production access, and no artifact boundary.

## Build once, deploy many times

Do not rebuild separately for staging and production if you can avoid it. Build once, attach metadata, then promote the same artifact.

For each artifact, record:

- source commit
- pipeline run ID
- dependency lockfile or image digest
- build timestamp
- artifact name and version
- checksum or container digest
- test status

That evidence lets you answer a simple but important question: what exactly is running?

## Example pipeline shape

This generic flow works across many CI systems:

```yaml
stages:
  - test
  - build
  - publish
  - deploy_staging
  - verify_staging
  - deploy_production
  - verify_production
```

Each stage should have one job:

- **test:** prove the change is acceptable.
- **build:** create an artifact.
- **publish:** store the artifact somewhere durable.
- **deploy_staging:** apply the artifact to a lower-risk environment.
- **verify_staging:** run checks against the deployed service.
- **deploy_production:** promote the same artifact after approval.
- **verify_production:** confirm the service is healthy after release.

Avoid mixing build, deploy, and verification logic into one long shell script. Separate stages make failures easier to understand.

## Deployment evidence on Linux

After a deployment, collect operating-system evidence:

```sh
systemctl status myapp
journalctl -u myapp --no-pager -n 100
ss -ltnp | grep ':8080'
curl -fsS http://localhost:8080/health
```

For containerized services, collect runtime evidence:

```sh
docker ps
docker logs --tail 100 myapp
docker inspect myapp --format '{{.Image}}'
```

For Kubernetes-style platforms, collect controller evidence:

```sh
kubectl rollout status deploy/myapp
kubectl get pods -l app=myapp
kubectl describe deploy/myapp
```

The goal is not to memorize every command. The goal is to prove that the intended artifact is running, listening, and passing health checks.

## Gates and approvals

Not every successful build should automatically reach production.

Use gates for:

- database migrations
- high-risk infrastructure changes
- security-sensitive updates
- payment, identity, or data-retention systems
- first deployments of a new service
- production deploys outside normal hours

A useful approval gate records who approved, what artifact was approved, what environment was targeted, and what rollback path was available.

## Secrets in practice

CI/CD systems often need secrets, but secrets should not become ordinary environment clutter.

Good practice:

- use a secret manager or CI credential store
- scope tokens to one repository, environment, or action
- use separate staging and production secrets
- hide secrets from logs
- rotate credentials when maintainers or agents change
- avoid deploying from personal laptops with personal tokens

Bad practice:

- putting tokens in repository files
- printing environment variables during debugging
- sharing one production token across every pipeline
- giving test jobs deployment credentials they do not need

## Rollback is part of the release

Before a pipeline deploys production, it should know how to recover.

Common rollback patterns:

- redeploy the previous artifact
- flip traffic back to the previous environment
- revert the configuration change
- pause a rollout before it reaches every instance
- restore a database from a tested backup or migration rollback

Rollback has to be realistic. If the only rollback plan is "fix forward quickly," the risk belongs in the release notes and approval gate.

## Troubleshooting a failed pipeline

When a pipeline fails, classify the failure before changing anything.

Ask:

- Did source checkout fail?
- Did dependency installation fail?
- Did a test fail because the code is wrong?
- Did a test fail because the environment is missing something?
- Did the build artifact fail to publish?
- Did deployment fail before touching the target?
- Did deployment change the target but verification failed?
- Did monitoring report a problem after the pipeline said success?

Then collect the smallest useful evidence:

- pipeline run URL or ID
- failed stage and job
- commit SHA
- relevant log excerpt
- artifact version or digest
- target environment
- last successful run
- exact command that failed

Do not rerun blindly if the first failure may have partially changed production.

## Hands-on practice

Use a disposable repository or lab service.

1. Write down the local commands for test and build.
2. Create a simple pipeline with separate test and build stages.
3. Archive or publish one artifact from the build stage.
4. Add a staging deployment or simulated deployment step.
5. Add one verification command after deployment.
6. Intentionally break a test and record the failure evidence.
7. Intentionally break a deployment target and record how that failure differs.
8. Write a short rollback note for the artifact.
