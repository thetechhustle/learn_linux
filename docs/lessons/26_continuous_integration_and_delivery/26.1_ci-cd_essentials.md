!!! success "Operator principle"
    CI/CD is a feedback system.

    It should turn a proposed change into evidence: what changed, what was
    tested, what was built, where it was promoted, and how to recover if the
    result is bad.

## The problem CI/CD solves

Without CI/CD, many teams release software through a sequence of manual steps:

1. Someone pulls the latest code.
2. Someone remembers which commands to run.
3. Someone copies files, restarts services, or pushes an image.
4. Someone checks whether the site still works.
5. Someone tries to reconstruct what happened if the release fails.

That process can work for a small lab, but it does not scale well. It depends on
memory, local machine state, informal permissions, and luck.

CI/CD turns those steps into a repeatable workflow. The workflow may still have
human approval gates, but the evidence is created the same way every time.

## Continuous integration

Continuous integration means code or configuration changes are integrated into a
shared branch often and automatically checked.

A simple CI workflow might do this for every pull request:

```text
checkout source
install dependencies
run formatting check
run unit tests
build documentation
report pass or fail
```

The goal is fast feedback. The team should know whether a change broke the
project before it is merged or released.

Good CI answers:

- Which branch or commit was tested?
- Which checks ran?
- Which checks failed?
- Is the failure caused by the change, the environment, or a flaky dependency?
- Is the result repeatable?

## Continuous delivery

Continuous delivery means the system can produce a release-ready artifact and
move it through controlled promotion steps.

An artifact might be:

- a Linux package
- a container image
- a static website
- a compiled binary
- an infrastructure plan
- a configuration bundle
- a VM or cloud image

Delivery does not always mean production changed automatically. Many delivery
pipelines stop at staging, require a human approval, or wait for a scheduled
maintenance window.

Good delivery answers:

- Which artifact was produced?
- Where was it stored?
- Which environment received it?
- Who approved the risky step?
- What verification ran after promotion?

## Continuous deployment

Continuous deployment means passing changes automatically reach production
without a manual approval gate.

This can be powerful, but it requires strong safeguards:

- reliable automated tests
- clear ownership
- small changes
- fast rollback
- useful monitoring
- low blast radius
- trustworthy secrets and access controls

If a production deployment still needs a manual approval, the team may be doing
continuous delivery rather than continuous deployment. That is not a failure.
For many systems, that is the correct risk choice.

## Pipeline inputs and outputs

Every pipeline has inputs and outputs. Operators should know both.

Common inputs:

- repository URL
- branch, tag, pull request, or commit SHA
- pipeline definition file
- build image or runner image
- dependency lock files
- secrets and tokens
- environment variables
- approval decisions

Common outputs:

- check status
- logs
- test reports
- coverage reports
- build artifacts
- container images
- release notes
- deployment records
- audit events

If a pipeline produces only "green" or "red" without enough context, it is hard
to operate.

## Runners and agents

A runner or agent is the machine that executes pipeline jobs. It might be hosted
by a platform, self-hosted in your environment, or created temporarily for each
run.

Inspect runner facts when failures are strange:

- operating system and version
- CPU architecture
- shell
- installed tools
- network access
- filesystem permissions
- available disk space
- cache state
- container runtime
- secret access

A build that passes on one runner and fails on another is often telling you
about environmental drift.

## Artifacts and traceability

An artifact is the thing a pipeline creates for later use. The most important
artifact property is traceability.

You should be able to connect:

```text
source commit -> pipeline run -> tests -> artifact -> deployment -> runtime evidence
```

For example:

```text
commit: 9f41e7c
run: github-actions/docs/25805751187
artifact: learn-linux-site-2026-05-13.tar.gz
environment: staging
verification: smoke check passed at 2026-05-13T14:31Z
```

Without traceability, rollback and incident review become guesswork.

## Gates and approvals

Not every stage should run automatically.

Use gates when a step has meaningful risk:

- production deployment
- database migration
- destructive infrastructure change
- credential rotation
- public release
- high-cost cloud operation
- security exception

A useful gate records who approved, what they approved, and what evidence was
available at approval time.

## Secrets and permissions

CI/CD systems often need credentials to fetch private dependencies, push
artifacts, deploy infrastructure, or notify other systems. That makes them
high-value targets.

Use narrow permissions:

- read-only token for validation
- publish token for artifact upload
- deployment token for one environment
- separate production credentials
- short-lived credentials when supported

Avoid broad personal tokens in shared pipelines. If a token leaks through logs,
artifacts, or malicious pipeline changes, assume it must be rotated.

## Triage a failed pipeline

Do not immediately click rerun. First capture the evidence.

1. Identify the failed run.

    ```bash
    gh run list --limit 10
    gh pr checks <pr-number>
    ```

2. Read the failed logs.

    ```bash
    gh run view <run-id> --log-failed
    ```

3. Record the basics:

    - repository
    - branch
    - commit SHA
    - run ID
    - failed job and step
    - exact error message
    - runner or agent

4. Classify the failure:

    - test failure
    - formatting or lint failure
    - missing dependency
    - missing secret
    - network or registry failure
    - runner capacity or disk issue
    - deployment verification failure

5. Decide the next action:

    - fix the code
    - fix the pipeline definition
    - rotate or restore a secret
    - rerun because the failure is clearly transient
    - pause the release and escalate

## Where Linux skills matter

CI/CD still depends on Linux fundamentals:

- shell behavior
- filesystem permissions
- package managers
- environment variables
- process exit codes
- networking and DNS
- containers
- logs
- system resource limits
- SSH keys and tokens

When a pipeline fails, Linux evidence often explains why.

Examples:

```bash
pwd
id
env | sort
df -h
ulimit -a
ps aux
ss -ltnp
```

Be careful with `env`; it can expose secrets. In shared logs, print only the
variables you actually need.

## Hands-on lab

Use a disposable repository or training project.

1. Create a small pipeline that runs one format check and one test command.
2. Push a passing change and record the commit SHA, run ID, and checks.
3. Break the format or test intentionally.
4. Read the failed logs and identify the exact failed step.
5. Fix the issue and confirm the pipeline passes again.
6. Write a short release note that links source commit, checks, artifact, and
   rollback plan.
