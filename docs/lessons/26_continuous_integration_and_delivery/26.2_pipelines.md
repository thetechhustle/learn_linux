# 26.2 Pipelines

!!! abstract "What you will learn"
    - Explain how a CI/CD pipeline turns a repository change into tested release evidence.
    - Identify common pipeline stages, jobs, runners, artifacts, gates, and notifications.
    - Design a small pipeline that fails safely before it can deploy a broken Linux change.

!!! example "Field story"
    A team keeps merging service changes that work on one laptop but fail on the staging server. You are asked to make every change leave the same evidence trail: source revision, build logs, test results, packaged artifact, approval, deployment record, and rollback note.

!!! success "Operator principle"
    A useful pipeline is not just automation. It is a repeatable control path with clear stop points, evidence, and recovery options.

Pipelines are the workflow engine of CI/CD. They describe what happens after a change reaches version control: which environment runs the work, which commands execute, which outputs are saved, and which conditions must be true before the next step starts.

For Linux operators, the value is not only faster releases. A good pipeline makes changes reviewable and repeatable. It catches missing packages, syntax errors, test failures, unsafe configuration, and deployment drift while the change is still small enough to fix.

## 26.2.1 Pipeline building blocks

Most CI/CD systems use different names, but the same concepts appear almost everywhere.

| Term | What it means | Linux operator question |
| --- | --- | --- |
| Trigger | Event that starts the pipeline, such as a pull request, tag, schedule, or manual dispatch. | Should this run for every branch, only protected branches, or only release tags? |
| Runner | Host, VM, container, or Kubernetes pod that executes jobs. | Is the runner isolated enough for untrusted code? |
| Stage | Ordered group of work, such as lint, test, package, deploy, and verify. | What evidence must exist before the next stage starts? |
| Job | A specific unit of commands inside a stage. | Can this job be rerun without damaging the target system? |
| Artifact | File saved from a job, such as a package, report, log, or container image digest. | Can a later deployment prove exactly what artifact was released? |
| Gate | Condition that blocks progress, such as tests passing, approval, or branch protection. | What prevents a bad change from reaching production? |
| Secret | Token, key, or password used by the pipeline. | Is the secret scoped, masked, rotated, and unavailable to pull requests from untrusted forks? |

A pipeline should make the failure path as intentional as the success path. If tests fail, the pipeline should stop before packaging or deployment. If deployment fails, it should preserve enough logs to diagnose the change and enough metadata to roll back.

## 26.2.2 A typical pipeline shape

A practical CI/CD pipeline often follows this order:

1. **Checkout:** fetch the exact commit that triggered the run.
2. **Prepare:** install dependencies or restore a pinned dependency cache.
3. **Lint:** run fast syntax and style checks.
4. **Test:** run unit, integration, or configuration tests.
5. **Build:** produce an artifact, image, package, or documentation site.
6. **Scan:** check for known vulnerable dependencies, leaked secrets, or unsafe configuration.
7. **Publish:** upload the artifact to a registry or release store.
8. **Deploy:** apply the artifact to a controlled environment.
9. **Verify:** confirm the service, endpoint, logs, or metrics look healthy after deployment.
10. **Notify:** send the result and evidence link to the team.

Not every repository needs every stage. A documentation repository might build and test links. A system configuration repository might validate templates and run `shellcheck`, `ansible-lint`, or `terraform plan`. A service repository might build a container image and deploy it to staging.

## 26.2.3 Keep jobs reproducible

Pipelines become hard to trust when they depend on hidden state. Prefer commands that can run the same way on a new runner.

Good pipeline habits include:

- Pin runtime versions, package repositories, and action/plugin versions.
- Make setup commands visible in the pipeline file.
- Treat generated files as build artifacts unless the project intentionally commits them.
- Use read-only validation before any command that changes infrastructure.
- Save test reports, build logs, package checksums, and image digests.
- Keep deployment credentials separate from build-only credentials.

For example, a Python documentation pipeline might install dependencies and build the site with explicit commands:

```yaml
name: docs

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m pip install -r requirements.txt
      - run: python -m mkdocs build --strict
```

The important part is not the specific CI provider. The important part is that a reviewer can see which commit ran, which dependencies were installed, which command verified the output, and whether the command passed.

## 26.2.4 Design gates before deployment

Deployment stages deserve stricter rules than build stages. The pipeline should answer these questions before it changes a shared environment:

- Is this branch or tag allowed to deploy?
- Did all required tests and scans pass?
- Is a human approval required for production?
- Is the deploy job using a short-lived or narrowly scoped credential?
- Can the exact artifact be identified after deployment?
- Is there a rollback or disablement path if verification fails?

Avoid pipelines that rebuild a fresh artifact during deployment. Build once, publish the artifact, then deploy that same artifact. This prevents "it passed CI, but production received something else" failures.

## 26.2.5 Troubleshooting pipeline failures

When a pipeline fails, debug it like a production incident: start with the first failing evidence, not the last noisy symptom.

| Symptom | First checks |
| --- | --- |
| Job never starts | Trigger rules, branch filters, runner availability, repository permissions |
| Dependency install fails | Package lockfiles, registry reachability, pinned runtime version, proxy settings |
| Tests pass locally but fail in CI | Environment variables, working directory, timezone, filesystem case sensitivity, missing services |
| Artifact is missing | Build output path, upload step condition, job dependencies, cleanup commands |
| Deploy step is blocked | Required approvals, protected environments, secret availability, branch protection |
| Deploy succeeds but service is unhealthy | Version evidence, logs, readiness checks, migrations, rollback notes |

Do not "fix" pipeline failures by disabling the stage unless the check itself is wrong and a replacement is added. A failing pipeline is often the first useful signal that a release path is unsafe.

## Hands-on practice

Use a disposable repository or lab branch.

1. Create a tiny project with one script and one test command.
2. Add a pipeline with separate `lint` and `test` jobs.
3. Make the test fail and confirm the pipeline stops before any publish or deploy step.
4. Fix the test and save the successful run URL, commit SHA, and artifact name in a lab note.
5. Add one manual or branch-based gate before a pretend deployment job.

For a shell-based lab, the test job can be simple:

```sh
set -eu
sh -n scripts/*.sh
shellcheck scripts/*.sh
```

If `shellcheck` is not installed on the runner, install it explicitly in the pipeline or choose a runner image that already includes it. Do not depend on whatever happens to be present on your laptop.
