## 26.6 Recommended Reading

!!! abstract "What you will learn"
    - Choose CI/CD references that help with real Linux operations.
    - Separate timeless release-engineering principles from tool-specific tutorials.
    - Build a small reading path for pipelines, Jenkins, containers, security, and incident response.
    - Turn reading into a local runbook instead of a pile of links.

!!! success "Operator principle"
    Good CI/CD reading should make releases safer, more repeatable, and easier to recover. Prefer sources that explain evidence, risk, and operating boundaries over sources that only show a happy-path demo.

## Start with release fundamentals

Use foundational material to learn why teams automate release work, not just which YAML syntax a tool expects.

Good topics to study:

- continuous integration
- continuous delivery
- continuous deployment
- trunk-based development
- feature flags
- deployment pipelines
- release evidence
- rollback and roll-forward strategy
- change approval and audit trails

Recommended starting points:

- Jez Humble and David Farley, *Continuous Delivery*
- Martin Fowler's articles on continuous integration and deployment pipelines
- Vendor-neutral release-engineering talks from large engineering organizations

While reading, ask:

- What evidence does this workflow preserve?
- What can fail without touching production?
- What requires human approval?
- What is the rollback path?

## Read your CI system documentation

Every CI/CD tool has its own vocabulary. Learn the vocabulary of the platform you actually operate.

For any CI system, find the official documentation for:

- triggers
- runners, agents, or executors
- environment variables
- secrets and credentials
- artifacts
- caches
- manual approval gates
- protected branches or protected environments
- deployment environments
- retention settings
- audit logs

Examples:

- GitHub Actions documentation
- GitLab CI/CD documentation
- Jenkins documentation
- CircleCI documentation
- Buildkite documentation
- Azure Pipelines documentation

Do not stop at example snippets. Read the security, permissions, and artifact-retention pages too.

## Jenkins references

If your environment uses Jenkins, focus on operations first.

Study:

- controller and agent architecture
- `Jenkinsfile` pipeline syntax
- credentials binding
- plugin management
- job configuration as code
- backup and restore
- upgrade planning
- build queue and executor behavior
- controller logs and agent logs

Useful source categories:

- official Jenkins user documentation
- official Jenkins administrator documentation
- Jenkins plugin documentation for plugins you actually use
- postmortems or incident reports involving CI/CD credential misuse or plugin risk

For each plugin in your environment, record why it exists. A plugin list with no owner is operational debt.

## Containers and artifacts

Modern CI/CD often builds container images. Learn the artifact boundary clearly.

Study:

- Dockerfile best practices
- image tags versus immutable digests
- multi-stage builds
- build contexts
- `.dockerignore`
- registry authentication
- image scanning
- software bills of materials
- signing and provenance
- Kubernetes or orchestrator rollout behavior, if relevant

Good references include:

- official Docker build documentation
- OCI image and registry concepts
- Kubernetes deployment and rollout documentation
- Sigstore, SLSA, or similar supply-chain-security references when your environment is ready for that maturity level

When you read a container tutorial, check whether it pins versions, avoids leaking secrets into layers, and explains how to verify the running image.

## Linux and deployment operations

CI/CD is still connected to Linux fundamentals.

Keep these references close:

- `systemd` service documentation
- `journalctl` and service logging references
- package manager documentation for your distribution
- SSH hardening guidance
- firewall documentation
- container runtime documentation
- reverse proxy documentation
- database migration guidance for your stack

Deployment failures are often ordinary Linux failures with a pipeline wrapped around them: bad permissions, full disks, missing environment variables, dead services, port conflicts, DNS mistakes, expired certificates, or broken credentials.

## Security reading

CI/CD systems sit near source code, secrets, artifacts, and deployment authority. Treat them as high-value targets.

Study:

- least-privilege token design
- branch protection
- environment protection
- secret masking limits
- dependency confusion
- artifact tampering
- runner isolation
- self-hosted runner risk
- supply-chain attacks
- audit logging

Practical questions:

- Can a pull request from an untrusted branch access secrets?
- Can a test job deploy to production?
- Can one compromised runner expose every repository?
- Can an artifact be replaced after tests pass?
- Who can edit pipeline definitions?

## Incident and recovery references

CI/CD reading should include recovery, not only automation.

Look for:

- deployment incident postmortems
- rollback runbooks
- failed migration reports
- blue-green and canary deployment examples
- feature-flag incident writeups
- service-level objective and error-budget material

For each incident story, identify:

- what changed
- how the change was detected
- what evidence was missing
- how the team stopped the damage
- how automation changed afterward

## Evaluate tutorials carefully

A CI/CD tutorial is useful when it names the boundaries.

Prefer tutorials that:

- use a real repository structure
- separate test, build, publish, deploy, and verify stages
- preserve artifacts
- explain secrets handling
- show a failure case
- include rollback or cleanup
- avoid direct production mutation from a casual example

Be skeptical of tutorials that:

- deploy by running `git pull` on a production server
- put tokens in plain text
- skip artifact storage
- use mutable `latest` tags without explanation
- combine every step into one opaque shell script
- never explain permissions

## Build your local runbook

Turn reading into a local reference.

Create a short CI/CD runbook for one service:

1. Repository URL
2. Pipeline file path
3. Test command
4. Build command
5. Artifact location
6. Deployment target
7. Required secrets
8. Approval gate
9. Health check
10. Rollback command or procedure
11. Useful logs
12. Last known good version

Keep this runbook near the service documentation. A future operator should not need to reverse-engineer your pipeline during an outage.

## Suggested study order

1. Read one release-engineering overview.
2. Read your CI platform's trigger, runner, artifact, and secret documentation.
3. Read your deployment platform's rollout and rollback documentation.
4. Read one container build/security reference if containers are involved.
5. Read one CI/CD incident postmortem.
6. Write or update a local runbook for one service.

## Check your understanding

- Which CI/CD reference explains the principles, not just the syntax?
- Which documentation page explains where your pipeline stores artifacts?
- Which documentation page explains how secrets are protected and exposed?
- What tutorial pattern should make you pause before copying it?
- What should your local CI/CD runbook prove during an incident?
