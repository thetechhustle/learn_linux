### 19.7 Recommended Reading

Web hosting changes age quickly. Product pages, cloud defaults, TLS
requirements, and browser behavior change faster than most printed books. Use
this reading path to keep your operational references current and to connect
the chapter's Apache, Nginx, HAProxy, cloud hosting, and HTTP lessons to real
runbooks.

!!! abstract "What you will learn"
    - Choose reliable web-hosting references for protocol, server, proxy, TLS, and deployment work.
    - Separate vendor tutorials from primary documentation before changing production systems.
    - Build a small reading note that turns a reference into a safer command or rollback step.

!!! example "Field story"
    A team is moving a site from a single Apache host to Nginx behind a load balancer. The old wiki page says to restart services directly, but nobody knows whether the TLS certificate, proxy headers, health checks, or rollback process still match the current stack. Before editing configuration, you need to collect the authoritative docs and turn them into a short change plan.

!!! success "Operator principle"
    Treat documentation like evidence: prefer primary sources, record versions, and test every command in a lab before trusting it in production.

## How to read for operations

Good administrators do not read web-hosting documentation as trivia. They read
with a change in mind. For each source, capture:

- The product and version it applies to.
- The file paths, commands, or directives it names.
- Whether the action is read-only, reversible, disruptive, or security-sensitive.
- The validation command that proves the change worked.
- The rollback step if the change breaks traffic.

Keep that note beside the ticket, lab journal, or runbook. A five-line note is
more useful during an outage than a bookmark you have to re-interpret under
pressure.

## Primary references

Start with upstream and vendor documentation when you need exact behavior.

| Topic | Start here | Why it matters |
| --- | --- | --- |
| HTTP semantics | MDN Web Docs and the current HTTP RFCs from the IETF | Explains methods, status codes, headers, caching, redirects, and request behavior without tying the concept to one server. |
| Apache HTTPD | The Apache HTTP Server official documentation | Defines directives, modules, virtual hosts, `.htaccess` behavior, logging, and `apachectl configtest` expectations. |
| Nginx | The Nginx official documentation and admin guide | Covers server blocks, reverse proxying, TLS, reload behavior, variables, upstreams, and common directive context rules. |
| HAProxy | The HAProxy configuration manual and official tutorials | Documents frontend/backend structure, health checks, ACLs, TLS termination, logging, and runtime inspection. |
| TLS certificates | Let's Encrypt documentation and Certbot documentation | Shows certificate issuance, renewal, challenge types, automation, and failure recovery for common Linux deployments. |
| Linux service management | Your distribution's `systemd`, package, and filesystem layout documentation | Confirms service names, package names, config locations, and reload behavior for the OS you are actually running. |

Official docs are not always the easiest introduction, but they are the place
to confirm syntax and version-specific behavior before a real change.

## Books and long-form references

Use books for depth, mental models, and historical context. Then verify
commands against current primary documentation before running them.

- **HTTP: The Definitive Guide** by David Gourley and Brian Totty. Useful for
  understanding request flow, proxies, caching, authentication, and why simple
  browser symptoms can hide multiple network layers.
- **High Performance Browser Networking** by Ilya Grigorik. Useful for TLS,
  TCP, HTTP/2, latency, browser behavior, and performance tradeoffs.
- **Nginx HTTP Server** by Clement Nedelcu. Useful for Nginx configuration
  patterns, reverse proxy behavior, and tuning concepts.
- **Apache Cookbook** by Ken Coar and Rich Bowen. Useful for Apache virtual
  hosts, modules, logging, redirects, and practical configuration patterns.
- **Linux Network Administrator's Guide** from the Linux Documentation Project.
  Useful background for TCP/IP, routing, DNS, and service exposure.

Older books can still explain concepts well, but web-hosting security defaults
change. Check dates carefully, especially around TLS protocols, ciphers, HTTP/2
support, certificate automation, and container or cloud deployment advice.

## Security and reliability reading

Web hosting is an exposed service. Include these topics in your regular
reading rotation:

- **OWASP Cheat Sheet Series** for TLS, secure headers, authentication, logging,
  and reverse proxy considerations.
- **Mozilla SSL Configuration Generator** for current TLS server settings and
  compatibility tradeoffs.
- **CIS Benchmarks** for Linux distribution and web-server hardening guidance
  when your organization follows compliance baselines.
- **Cloud provider load balancer documentation** for health checks, proxy
  protocol, source IP preservation, TLS policy, and failover behavior.
- **Distribution security notices** for Apache, Nginx, OpenSSL, HAProxy, and
  related packages.

Do not copy hardening snippets blindly. A setting that is correct for a public
static site can break an internal application, legacy client, API gateway, or
certificate-renewal flow.

## Tutorials and blog posts

Tutorials are useful when you are learning a workflow, but they need extra
screening before they become operational guidance.

Ask these questions before trusting a tutorial:

1. Does it name the operating system and release?
2. Does it show validation before reload or restart?
3. Does it explain rollback?
4. Does it separate lab commands from production commands?
5. Does it avoid disabling security controls just to make the demo work?
6. Does it still match current package names and config paths?

If the answer is no, keep the article as background reading only. Build your
actual runbook from primary docs and lab verification.

## Hands-on reading lab

Run this lab on a disposable VM, container, or local documentation note. The
goal is to turn reading into an operational artifact.

1. Pick one topic: Apache virtual hosts, Nginx reverse proxying, HAProxy health
   checks, TLS renewal, or cloud load balancer forwarding headers.
2. Find one primary source and one tutorial or book chapter for that topic.
3. Record the product version, OS version, config file path, and service name
   each source assumes.
4. Extract one read-only inspection command, one validation command, and one
   rollback step.
5. Run only the read-only and validation commands in a lab.
6. Write a five-line runbook note:

   ```text
   Goal:
   Source versions:
   Read-only evidence:
   Validation:
   Rollback:
   ```

7. Explain which source you would trust during an incident and why.

## Check your understanding

- Why should a runbook cite product versions instead of only linking to a web page?
- What makes a tutorial unsafe to use directly on a production web server?
- Which reading source would you use to confirm whether a config directive is valid?
- How would you update a web-hosting runbook after an upstream documentation change?
- What evidence would you collect before reloading Apache, Nginx, or HAProxy?

## Operational takeaway

The best web-hosting references do more than teach commands. They help you
prove what is running, understand what a change will affect, validate before
reload, and recover quickly if traffic breaks. Keep your reading practical:
turn every useful source into a short note that improves the next change window.
