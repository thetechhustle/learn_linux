### 19.1 HTTP: The Hypertext Transfer Protocol

HTTP is the application protocol that browsers, APIs, reverse proxies, load
balancers, and web servers use to exchange web requests and responses. For a
Linux operator, the useful skill is not memorizing every part of the protocol.
It is being able to prove what a client asked for, what the server returned,
which layer handled the request, and where a failure entered the path.

!!! abstract "What you will learn"
    - Read an HTTP request and response as operational evidence.
    - Use `curl` to inspect methods, headers, redirects, status codes, and
      timing without changing the server.
    - Separate HTTP behavior from DNS, TCP, TLS, proxy, and application
      failures.
    - Capture enough evidence for a clear web incident handoff.

!!! success "Operator principle"
    Test from the same side of the boundary as the failing user. A local
    `curl http://127.0.0.1/` test proves something different from an external
    HTTPS request through DNS, a firewall, a load balancer, and a reverse proxy.

## Requests and Responses

Every HTTP exchange starts with a client request. The first line gives the
method, path, and protocol version. Headers add context such as the requested
host name, accepted content types, authentication material, cookies, and proxy
metadata.

```text
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: curl/8.0
Accept: */*
```

The server answers with a status line, response headers, and usually a body.

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Cache-Control: max-age=300

<!doctype html>
...
```

The status code is the first triage signal:

- `2xx` means the server accepted and handled the request.
- `3xx` means the client is being redirected or told to use cached content.
- `4xx` means the server understood the request but rejected it or could not
  find the requested resource.
- `5xx` means the server, proxy, or upstream application failed while handling
  a request that reached it.

Do not stop at the status code. The `Server`, `Via`, `Location`, `Content-Type`,
`Cache-Control`, `Set-Cookie`, and application-specific headers often explain
which component generated the response.

## Inspect HTTP with curl

Start with read-only checks. The `-I` flag asks for headers only, and `-v`
prints connection and protocol details.

```bash
curl -I http://www.example.com/
curl -v http://www.example.com/
```

Follow redirects when you need to verify the final destination:

```bash
curl -IL http://www.example.com/
```

Send a request to a specific virtual host while bypassing DNS. This is useful
when a web server hosts multiple names on one address or when a DNS change has
not propagated.

```bash
curl -I --resolve www.example.com:80:203.0.113.10 http://www.example.com/
```

Inspect HTTPS separately. TLS negotiation happens before the HTTP request is
processed, so certificate and protocol errors are not the same as HTTP errors.

```bash
curl -Iv https://www.example.com/
```

For a concise timing profile, capture the response code and major timing
milestones:

```bash
curl -o /dev/null -sS -w \
  'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://www.example.com/
```

## Common Failure Patterns

`curl: Could not resolve host` points to name resolution. Check DNS before
restarting a web service.

`Connection refused` means the client reached the host, but nothing accepted
the TCP connection on that port. Check listener state with commands such as
`ss -ltnp` on the server.

`Connection timed out` often points to routing, firewall, security-group, or
load-balancer reachability. Compare tests from inside and outside the network.

`301` or `302` loops usually come from mismatched HTTP-to-HTTPS redirect rules,
proxy headers, or application base URL settings.

`403 Forbidden` usually means the server found the resource or location block
but denied access. Check file permissions, authentication rules, IP allowlists,
and web server authorization configuration.

`404 Not Found` can mean the file is missing, the route is not registered, or
the request reached the wrong virtual host.

`502 Bad Gateway` and `504 Gateway Timeout` usually come from a proxy that
could not get a healthy response from an upstream application. Check the proxy
logs and the application listener, not just the public web port.

## Safety Notes

HTTP inspection can expose sensitive data. Do not paste cookies,
authorization headers, session tokens, or full request bodies into tickets or
chat. Redact them before sharing.

Be careful with methods other than `GET`, `HEAD`, and safe diagnostics. A
`POST`, `PUT`, `PATCH`, or `DELETE` request can create, change, or remove data
even when sent from a command line.

When testing production, avoid high-rate loops. A tight `curl` loop can look
like abuse and can also hide the original symptom by creating new load.

## Hands-on Practice

Run these from a disposable VM, container, or lab machine.

1. Start with a public test endpoint or a local web server.

   ```bash
   curl -I https://example.com/
   curl -IL https://example.com/
   ```

2. Record the final status code, the `Content-Type`, and any redirect targets.

3. Compare HTTP and HTTPS behavior.

   ```bash
   curl -I http://example.com/
   curl -Iv https://example.com/
   ```

4. Capture a timing summary.

   ```bash
   curl -o /dev/null -sS -w \
     'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
     https://example.com/
   ```

5. Write a short handoff note:

   - Source of the test: laptop, server, container, or external network.
   - URL tested.
   - Final status code.
   - Redirect chain, if any.
   - Whether DNS, TCP connection, TLS, or HTTP response was the slowest or
     failing step.
