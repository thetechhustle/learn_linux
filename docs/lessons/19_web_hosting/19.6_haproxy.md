## 19.6 HAProxy

HAProxy is a high-performance TCP and HTTP load balancer. It can sit in
front of web servers, route traffic to healthy backends, terminate TLS,
apply basic request rules, and expose clear health information. Linux
operators use it when one server is not enough, when a site needs graceful
maintenance, or when traffic should be shifted between application pools.

## Where HAProxy fits

A common flow looks like this:

```text
visitor
  -> DNS
  -> firewall or cloud load balancer
  -> HAProxy
  -> Nginx, Apache, or application servers
```

HAProxy can operate at Layer 4, where it proxies TCP connections, or Layer
7, where it understands HTTP. Layer 4 is simple and fast. Layer 7 enables
host/path routing, header rules, HTTP health checks, redirects, and
application-aware decisions.

Use HAProxy when you need:

- multiple backend servers behind one address
- health checks and automatic removal of bad backends
- graceful maintenance of one server while others keep serving traffic
- TLS termination before traffic reaches application hosts
- routing by hostname, path, or headers
- a stable front door in front of changing application instances

## Packages, service, and files

On Debian or Ubuntu:

```bash
sudo apt update
sudo apt install haproxy
sudo systemctl enable --now haproxy
```

On RHEL-family systems:

```bash
sudo dnf install haproxy
sudo systemctl enable --now haproxy
```

Common paths:

| Purpose | Common location |
| --- | --- |
| Main config | `/etc/haproxy/haproxy.cfg` |
| Service | `haproxy.service` |
| Logs | system journal or syslog destination |
| Runtime socket | often `/run/haproxy/admin.sock` when enabled |
| TLS certificates | commonly `/etc/haproxy/certs/` or provider-managed |

Inspect the running service:

```bash
systemctl status haproxy --no-pager
ss -ltnp | grep haproxy
journalctl -u haproxy -n 100 --no-pager
```

## Configuration structure

HAProxy configuration is built from sections:

- `global`: process-wide settings such as logging, user, group, and socket.
- `defaults`: shared timeouts, mode, and logging behavior.
- `frontend`: where traffic enters HAProxy.
- `backend`: where HAProxy sends traffic.
- `listen`: a combined frontend/backend, often used for stats or simple
  services.

A small HTTP load balancer:

```haproxy
global
    log /dev/log local0
    user haproxy
    group haproxy
    daemon

defaults
    mode http
    log global
    option httplog
    option dontlognull
    timeout connect 5s
    timeout client  50s
    timeout server  50s

frontend web_http
    bind *:80
    default_backend web_pool

backend web_pool
    balance roundrobin
    option httpchk GET /health
    http-check expect status 200
    server web1 10.0.10.11:80 check
    server web2 10.0.10.12:80 check
```

This configuration listens on port 80 and sends requests to two backend
servers. The `check` keyword enables health checks. `option httpchk` makes
the check request `/health`, and `http-check expect status 200` says what
healthy means.

## Frontends and backends

A `frontend` answers "where does traffic enter?" A `backend` answers "where
does traffic go next?"

Useful frontend settings:

- `bind`: address and port to listen on.
- `mode`: `http` or `tcp`.
- `acl`: named condition for routing decisions.
- `use_backend`: route to a backend when a condition matches.
- `default_backend`: fallback backend.

Example hostname routing:

```haproxy
frontend public_https
    bind *:443 ssl crt /etc/haproxy/certs/example.pem
    mode http

    acl host_api hdr(host) -i api.example.com
    acl host_www hdr(host) -i www.example.com example.com

    use_backend api_pool if host_api
    use_backend web_pool if host_www
    default_backend web_pool
```

Useful backend settings:

- `balance`: load-balancing algorithm, such as `roundrobin` or
  `leastconn`.
- `server`: backend name, address, port, and options.
- `check`: enable health checks.
- `rise` and `fall`: how many successful or failed checks change health
  state.
- `maxconn`: cap connections to a backend.

Example backend with safer health thresholds:

```haproxy
backend api_pool
    mode http
    balance leastconn
    option httpchk GET /ready
    http-check expect status 200
    server api1 10.0.20.11:8080 check fall 3 rise 2 maxconn 100
    server api2 10.0.20.12:8080 check fall 3 rise 2 maxconn 100
```

## Health checks and maintenance

Health checks determine whether HAProxy sends traffic to a server. A weak
health check can make an outage worse. Checking only that a port is open is
not the same as proving the application is ready.

Good health endpoints should prove the app can handle real work without
being expensive. For example, `/ready` might verify configuration and
database connectivity, while `/live` might only prove the process is alive.

Before taking a backend down, put it into maintenance if the runtime socket
is enabled:

```bash
echo "set server web_pool/web1 state maint" | sudo socat - /run/haproxy/admin.sock
echo "show stat" | sudo socat - /run/haproxy/admin.sock | head
```

The exact socket path and permissions depend on the site configuration.
When the socket is not enabled, you can still remove a server from rotation
through a config change and reload, but that is slower and riskier.

## TLS termination

HAProxy can terminate TLS and forward plain HTTP to internal services:

```haproxy
frontend public_https
    bind *:443 ssl crt /etc/haproxy/certs/example.pem
    mode http
    http-request set-header X-Forwarded-Proto https
    default_backend web_pool
```

The certificate file usually contains the certificate chain and private key
in one PEM file. Protect it carefully:

```bash
sudo chown root:haproxy /etc/haproxy/certs/example.pem
sudo chmod 640 /etc/haproxy/certs/example.pem
```

If TLS terminates at HAProxy, backend applications often need forwarded
headers to know the original request scheme and client address:

```haproxy
option forwardfor
http-request set-header X-Forwarded-Proto https if { ssl_fc }
```

Coordinate these headers with the application framework. Trusting forwarded
headers from every source can create security bugs; the app should trust
them only from the proxy layer.

## Validating and reloading

Run a config check before reload:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy
```

For a safer change:

1. Save or commit the current config.
2. Change one section at a time.
3. Run `haproxy -c`.
4. Confirm listeners and backend targets.
5. Reload, not restart, when possible.
6. Test through HAProxy and directly against a backend.
7. Watch logs and backend health after the reload.

```bash
curl -I http://127.0.0.1/
curl -I http://10.0.10.11/
systemctl status haproxy --no-pager
journalctl -u haproxy -n 100 --no-pager
```

## Stats and observability

HAProxy can expose a stats page or runtime socket. Keep stats private; it
contains operational details.

Example local-only stats listener:

```haproxy
listen stats
    bind 127.0.0.1:8404
    mode http
    stats enable
    stats uri /stats
    stats refresh 10s
```

Then inspect it locally:

```bash
curl http://127.0.0.1:8404/stats
```

Useful evidence during incidents:

- current frontend connection count
- backend server health
- failed health-check reason
- request rate
- response status distribution
- connection errors
- queue length

## TCP mode

For some services, HAProxy should not interpret HTTP. TCP mode can load
balance protocols such as PostgreSQL replicas, Redis, MQTT, SMTP, or raw
TLS passthrough.

```haproxy
frontend tls_passthrough
    bind *:443
    mode tcp
    default_backend tls_backends

backend tls_backends
    mode tcp
    balance roundrobin
    server web1 10.0.30.11:443 check
    server web2 10.0.30.12:443 check
```

In TCP mode, HAProxy cannot use normal HTTP path routing because it is not
parsing HTTP. Choose the mode based on what HAProxy needs to understand.

## Troubleshooting guide

| Symptom | Likely area | First checks |
| --- | --- | --- |
| HAProxy will not start | Syntax or bind conflict | `haproxy -c`, `ss -ltnp`, journal logs |
| Clients get connection refused | Listener missing | `bind`, service status, firewall |
| Clients get 503 | No healthy backend | health checks, backend service status |
| One backend gets all traffic | Balance or persistence | `balance`, cookies, source hashing |
| TLS certificate mismatch | Certificate file or SNI | `bind ... ssl crt`, `openssl s_client` |
| App sees HTTP instead of HTTPS | Forwarded headers | `X-Forwarded-Proto`, app trust settings |
| Reload drops traffic | Reload method or config issue | service unit, config check, graceful reload support |
| Stats page exposed publicly | Access control | bind address, firewall, authentication |

## Hands-on practice

Use a disposable lab VM or containers.

1. Start two simple web servers on different localhost ports.
2. Install HAProxy.
3. Create a frontend on port 8080 and a backend with both test servers.
4. Add HTTP health checks.
5. Validate the config with `haproxy -c`.
6. Reload HAProxy and send repeated `curl` requests through it.
7. Stop one backend and observe how HAProxy health changes.
8. Restore the backend and confirm it re-enters rotation.
9. Record the commands and evidence in a short incident-style note.
