### 19.3 Web Hosting in the Cloud

Cloud hosting moves the web server from a machine you can touch to an
environment controlled through APIs, images, networks, disks, identity
rules, and provider consoles. The operating system is still Linux, but the
failure modes now include provider networking, security groups, instance
metadata, managed load balancers, autoscaling policies, DNS automation, and
billing limits.

    - Inspect an instance, firewall, DNS, TLS, and load-balancer path during
      a website incident.
    - Choose safer deployment and rollback patterns for cloud-hosted sites.

!!! success "Operator principle"
    A cloud VM is still a Linux host, but it is never only a Linux host.
    Debug the provider control plane and the guest operating system together.

## What cloud hosting adds

On a traditional server, you might care about the machine, the switch, the
firewall, and the web daemon. In cloud hosting, those ideas still exist,
but they are exposed as provider resources:

| Concern | Cloud form | Operator question |
| --- | --- | --- |
| Compute | VM, instance, droplet, container task | Is the workload running in the expected region and size? |
| Image | Marketplace image, custom image, container image | Is the host built from the intended version? |
| Network | VPC, subnet, route table, public IP | Can traffic reach the instance? |
| Firewall | Security group, network ACL, cloud firewall | Are ports 80 and 443 allowed from the right sources? |
| Storage | Root disk, block volume, object storage | Is persistent data on the right volume or service? |
| Identity | IAM role, service account, API token | Does the host have only the permissions it needs? |
| Front door | Load balancer, CDN, reverse proxy | Which endpoint receives public traffic? |
| DNS and TLS | Managed DNS, certificate manager, ACME client | Does the public name point to the active front door? |
| Observability | Metrics, logs, alarms, traces | Can you see health and failures before users report them? |

The provider's names differ, but the job is the same: know which resources
serve the site and which resource owns the next failure.

## Common hosting patterns

### One VM

The simplest cloud deployment is one Linux VM running `nginx` or Apache,
possibly with an application process and database on the same host. This is
easy to understand and cheap to run, but every dependency shares one
failure domain.

Good for:

- learning environments
- small static sites
- low-traffic applications
- temporary demos

Watch for:

- manual changes that cannot be reproduced
- backups that were never tested
- SSH access treated as the deployment system
- no alerting until a customer complains

### VM plus managed services

A more durable pattern keeps the web/app host on a VM but moves stateful
components to managed services: a managed database, object storage for
uploads, managed DNS, and provider-managed certificates. This reduces the
operator burden on backups, patching, and failover, but creates dependency
on provider configuration.

Good for:

- production applications with modest traffic
- teams that want ordinary Linux deployment without self-managing every
  database detail
- sites where backups and restore time matter

Watch for:

- database access rules that are too broad
- secrets copied into shell history or config files
- unmanaged migration steps
- hidden cost growth from storage, egress, snapshots, or logs

### Load-balanced fleet

When traffic or availability requirements grow, multiple web hosts sit
behind a load balancer. Each instance should be replaceable. The app should
store durable state outside the instance, usually in a database, object
store, or queue.

Good for:

- higher availability
- blue/green or rolling deploys
- horizontal scaling

Watch for:

- app servers that secretly depend on local disk
- mismatched versions during rolling deployments
- health checks that only test the web server, not the application
- session state stored on one host

### Containers and platforms

Managed container platforms, app platforms, and Kubernetes-based systems
move the unit of deployment from a VM to an image and service definition.
Linux knowledge still matters, but the operator spends more time on image
builds, environment variables, probes, logs, scaling, and rollout history.

Good for:

- repeatable deployments
- multiple services with clear runtime contracts
- teams already comfortable with CI/CD and image builds

Watch for:

- weak image provenance
- secrets baked into images
- readiness checks that do not prove real readiness
- logging gaps between app, platform, and provider layers

## Inspecting a cloud web host

When a cloud-hosted site fails, collect evidence from both sides: inside
the guest and from the provider control plane.

Inside the Linux host:

```bash
hostname -f
cloud-init status --long
ip addr show
ip route
ss -ltnp
systemctl --failed
systemctl status nginx apache2 httpd --no-pager
curl -I http://127.0.0.1/
journalctl -u nginx -n 100 --no-pager
```

From a trusted workstation or jump host:

```bash
dig example.com
curl -I http://example.com/
curl -I https://example.com/
openssl s_client -connect example.com:443 -servername example.com </dev/null
```

From the cloud provider, verify:

- instance state is `running` or equivalent
- public IP or load balancer target is the one DNS points to
- security group or firewall allows expected inbound traffic
- instance health checks are passing
- load balancer targets are healthy
- the certificate is attached to the active front door
- recent deployments, image changes, or scaling events match the incident
  window

Do not trust a single green dashboard. A load balancer can be healthy while
the application is returning bad responses. A VM can be running while the
security group blocks all traffic.

## DNS, public IPs, and front doors

Cloud sites often move traffic through a front door:

```text
visitor
  -> DNS record
  -> CDN or managed load balancer
  -> cloud firewall or security group
  -> Linux web server or container service
  -> application and data services
```

The public name should point to the intentional front door, not a random
instance IP. Direct instance IPs are easy to lose during rebuilds and make
blue/green deployments harder.

Useful DNS checks:

```bash
dig example.com A
dig example.com AAAA
dig www.example.com CNAME
dig +trace example.com
```

Useful HTTP checks:

```bash
curl -I https://example.com/
curl -H 'Host: example.com' -I http://203.0.113.10/
```

The second command is useful when you need to test one backend IP with the
same `Host` header the web server expects.

## Cloud firewalls and Linux firewalls

Traffic can be blocked in more than one place:

- provider security group or cloud firewall
- network ACL or subnet route table
- host firewall such as `nftables`, `iptables`, `ufw`, or `firewalld`
- web server access rules
- application authentication or middleware

Check outside-in and inside-out. A host can listen on `0.0.0.0:443` and
still be unreachable because the provider firewall blocks port 443. A
provider firewall can allow traffic while the service only listens on
`127.0.0.1`.

```bash
ss -ltnp
ip route
nft list ruleset
ufw status verbose
firewall-cmd --list-all
```

Use only the firewall tool actually present on the system.

## Identity and metadata

Many cloud hosts receive credentials through instance metadata or an
attached role. This is safer than copying long-lived access keys into files,
but it also means compromise of the host can become compromise of whatever
the role can access.

Good practice:

- attach the smallest useful role to the instance or service
- avoid broad administrator permissions
- rotate external API tokens
- keep application secrets outside the document root
- audit which resources the instance role can read or write
- block unnecessary metadata access from application containers when
  possible

Never paste provider access keys into a web server config, shell history,
or repository.

## Backups and rebuilds

Cloud infrastructure makes it easy to create servers. It does not
automatically make a site recoverable. You need a tested answer for:

- What data is persistent?
- Where are backups stored?
- How often are backups taken?
- How do we restore into a clean environment?
- Which parts are defined as code or scripts?
- Which manual console changes must be captured before they are forgotten?

For a VM-based site, take snapshots before risky changes, but do not treat
snapshots as the only backup. Snapshots are useful for quick rollback;
application-aware database backups are still needed for many systems.

## Deployment strategies

Cloud environments support safer deployment patterns than overwriting files
on one server.

| Strategy | How it works | Best fit |
| --- | --- | --- |
| In-place deploy | Update the running host and reload services | Small sites, low risk changes |
| Image replacement | Build a new VM image or container image and replace instances | Repeatable production deploys |
| Rolling deploy | Replace a few instances at a time behind a load balancer | Multi-instance services |
| Blue/green deploy | Bring up a full new environment, then switch traffic | Higher confidence releases |
| Canary deploy | Send a small percentage of traffic to the new version first | Risky changes with good telemetry |

The more automated the deployment, the more important health checks become.
If health checks only prove that port 443 is open, they will not catch an
application that starts but cannot reach its database.

## Cost and capacity

Cloud mistakes often become bills. Operators should know what can grow:

- instance size and count
- managed database size
- disk snapshots and unattached volumes
- object storage and lifecycle rules
- log retention
- CDN and network egress
- load balancer hourly charges
- backup retention

Set budgets or alerts for production accounts. A broken loop that creates
instances, snapshots, or log volume can cost more than the original outage.

## Troubleshooting guide

| Symptom | Likely area | First checks |
| --- | --- | --- |
| DNS resolves to an old address | DNS or deployment cutover | Hosted zone, TTL, load balancer address |
| Connection times out | Network path | Security group, route table, cloud firewall |
| Connection refused | Host listener | `ss -ltnp`, service status, bind address |
| TLS certificate mismatch | Front door or certificate attachment | Certificate manager, SNI, load balancer listener |
| Load balancer says unhealthy | Health check or backend | Target health reason, app logs, backend port |
| Site works on VM but not publicly | Provider firewall or load balancer | Security group, target group, DNS |
| Site works publicly but app actions fail | Data service or credentials | Database rules, instance role, secret config |
| Sudden high bill | Resource growth | instance count, egress, logs, snapshots, storage |

## Hands-on practice

Use a disposable cloud account sandbox or a local lab that simulates the
same roles.

1. Create or inspect one small Linux VM.
2. Identify its region, public IP, private IP, attached firewall rules, and
   attached identity role.
3. Install a web server and serve a simple page.
4. Prove the page works locally with `curl -I http://127.0.0.1/`.
5. Open the provider firewall only for the required HTTP or HTTPS port.
6. Prove the page works from outside the VM.
7. Record where DNS would point if this were production.
8. Stop the service and observe the difference between host health,
   listener health, and HTTP response health.
9. Remove the test VM, disk, public IP, and snapshots when finished.
