### 19.5 Nginx

Nginx is a web server, reverse proxy, TLS terminator, static file server,
and load-balancing front door. It is common on Linux because it handles many
concurrent connections efficiently and has a clear configuration model for
serving files, routing requests to application runtimes, and protecting the
public edge of a site.

!!! abstract "What you will learn"
    - Identify the role Nginx plays in a Linux web stack.
    - Inspect active Nginx listeners, configuration, logs, and virtual hosts.
    - Configure a basic static site and reverse proxy.
    - Validate, reload, and troubleshoot Nginx safely.

!!! success "Operator principle"
    Always test the rendered Nginx configuration before reload, and separate
    public listener problems from backend application problems.

## Where Nginx fits

Nginx often sits at the public edge of a site:

```text
visitor
  -> DNS
  -> firewall or load balancer
  -> Nginx
  -> static files, PHP-FPM, or an application service
```

It can serve `/var/www/example.com/public/index.html` directly, or it can
proxy requests to a private application on `127.0.0.1:8000`. Many sites use
both patterns at once: static assets are served by Nginx, while dynamic
requests are sent to a runtime such as Gunicorn, Uvicorn, Node.js, Puma, or
PHP-FPM.

## Packages, services, and paths

Package and service names are consistent enough to recognize:

| Purpose | Debian and Ubuntu | RHEL, CentOS, Fedora |
| --- | --- | --- |
| Package | `nginx` | `nginx` |
| Service | `nginx` | `nginx` |
| Main config | `/etc/nginx/nginx.conf` | `/etc/nginx/nginx.conf` |
| Site configs | `/etc/nginx/sites-available/`, `/etc/nginx/sites-enabled/` | `/etc/nginx/conf.d/` |
| Default web root | `/var/www/html` | `/usr/share/nginx/html` or `/var/www/html` |
| Logs | `/var/log/nginx/access.log`, `/var/log/nginx/error.log` | same common paths |

Install and enable the service on Debian or Ubuntu:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
```

Install and enable it on RHEL-family systems:

```bash
sudo dnf install nginx
sudo systemctl enable --now nginx
```

Confirm the service and listener:

```bash
systemctl status nginx --no-pager
ss -ltnp | grep nginx
curl -I http://127.0.0.1/
```

## Reading the active configuration

Do not trust only the file you edited. Nginx includes files from multiple
directories, and the active configuration is the rendered result.

```bash
nginx -T
nginx -t
systemctl cat nginx
```

`nginx -T` prints the full loaded configuration. It is the best way to find
which `server` block owns a name, which `root` is active, and which
`proxy_pass` target is used. `nginx -t` checks syntax and should be run
before every reload.

## Server blocks

Nginx uses `server` blocks to decide how to handle a request. The
selection is based mostly on `listen` and `server_name`.

```nginx
server {
    listen 80;
    server_name example.com www.example.com;

    root /var/www/example.com/public;
    index index.html;

    access_log /var/log/nginx/example.access.log;
    error_log /var/log/nginx/example.error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

Important fields:

- `listen` defines the address and port.
- `server_name` defines hostnames matched from the HTTP `Host` header or
  TLS SNI.
- `root` defines the directory used for file lookups.
- `index` defines default filenames for directory requests.
- `location` defines path-specific behavior.
- `try_files` checks files in order before returning a fallback.

On Debian-style layouts, create a file in `sites-available` and enable it
with a symlink:

```bash
sudo install -d -o root -g root -m 755 /var/www/example.com/public
printf '%s\n' 'hello from nginx' | sudo tee /var/www/example.com/public/index.html
sudo ln -s /etc/nginx/sites-available/example.com /etc/nginx/sites-enabled/example.com
sudo nginx -t
sudo systemctl reload nginx
```

On RHEL-style layouts, site files often live directly in
`/etc/nginx/conf.d/example.com.conf`.

## Reverse proxying

Nginx is frequently used as a reverse proxy in front of an application
runtime. The app listens privately, and Nginx handles the public HTTP/TLS
edge.

```nginx
server {
    listen 80;
    server_name app.example.com;

    location /static/ {
        root /srv/app/current/public;
        expires 1h;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

If users see `502 Bad Gateway`, the first question is whether the backend
exists and accepts connections:

```bash
ss -ltnp | grep ':8000'
curl -I http://127.0.0.1:8000/
systemctl status myapp.service --no-pager
journalctl -u myapp.service -n 100 --no-pager
```

A bad proxy target, stopped backend, socket permission problem, or slow app
can all look like an Nginx error from the browser.

## TLS and redirects

Production sites should use HTTPS. Many Linux sites use Let's Encrypt with
an ACME client such as `certbot`, while cloud-hosted sites may terminate TLS
at a managed load balancer or CDN.

A common Nginx pattern redirects HTTP to HTTPS and serves HTTPS separately:

```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com www.example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    root /var/www/example.com/public;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

Check the public certificate and redirect behavior:

```bash
curl -I http://example.com/
curl -I https://example.com/
openssl s_client -connect example.com:443 -servername example.com </dev/null
```

Certificate renewal needs monitoring. A site can work for months and then
fail suddenly when an ACME renewal hook stops reloading Nginx.

## Reloads and safe changes

Use this rhythm for configuration work:

1. Copy or commit the current config before changing it.
2. Edit the smallest relevant file.
3. Print the rendered config if includes are involved.
4. Run `nginx -t`.
5. Reload instead of restarting when possible.
6. Test locally and through the public hostname.

```bash
sudo nginx -T | less
sudo nginx -t
sudo systemctl reload nginx
curl -I http://127.0.0.1/
curl -I https://example.com/
```

`reload` asks Nginx to re-read configuration without dropping established
connections. `restart` stops and starts the service; use it when you need
to recover a broken process, not as the default for every config change.

## Logs and status evidence

Nginx logs separate request history from service errors:

```bash
tail -n 50 /var/log/nginx/access.log
tail -n 50 /var/log/nginx/error.log
journalctl -u nginx -n 100 --no-pager
```

Useful access-log clues:

- repeated `404` means route or file lookup mismatch
- repeated `403` means permissions or access rules
- repeated `499` means clients disconnected before Nginx responded
- repeated `502` means backend connection failure
- repeated `504` means backend timeout

Error-log clues often point to the exact problem: missing files, permission
denials, failed upstream connections, bad gateway responses, or oversized
client uploads.

## Static files, caching, and uploads

Nginx is strong at serving static files. You can set cache headers for
versioned assets:

```nginx
location /assets/ {
    root /srv/app/current/public;
    expires 7d;
    add_header Cache-Control "public";
}
```

Be careful with cache headers for HTML and API responses. Long cache times
are safe for fingerprinted assets such as `app.4f3a1c.js`; they are risky
for pages that change frequently.

Large uploads may require explicit limits:

```nginx
client_max_body_size 25m;
```

If an application accepts uploads, the upload directory and temporary
directory permissions need to match the web and app users.

## Permissions and SELinux

Nginx usually runs as `www-data`, `nginx`, or another restricted service
user. It needs read access to public files and execute permission on parent
directories.

```bash
ps -o user,group,comm -C nginx
namei -l /var/www/example.com/public/index.html
ls -ld /var/www /var/www/example.com /var/www/example.com/public
```

On SELinux-enabled systems, Unix permissions can look correct while SELinux
still blocks access. Check audit logs and contexts:

```bash
getenforce
ls -Z /var/www/example.com/public
ausearch -m avc -ts recent
```

Do not solve permission problems with `chmod 777`. Find the service user,
the expected document root, parent directory permissions, and SELinux
context when applicable.

## Troubleshooting guide

| Symptom | Likely area | First checks |
| --- | --- | --- |
| Default welcome page appears | Wrong server block | `server_name`, enabled sites, DNS host header |
| 403 Forbidden | Permissions or index rules | `namei -l`, `index`, directory execute bits |
| 404 Not Found | Wrong root or route | `root`, `try_files`, requested path |
| 413 Payload Too Large | Upload limit | `client_max_body_size` |
| 502 Bad Gateway | Backend unavailable | `proxy_pass`, backend service, socket permissions |
| 504 Gateway Timeout | Slow backend | app logs, database latency, proxy timeout |
| TLS warning | Certificate or SNI | cert path, `server_name`, load balancer listener |
| Config reload fails | Syntax or include issue | `nginx -t`, recent edits, rendered `nginx -T` |

## Hands-on practice

Use a disposable VM or container.

1. Install Nginx and confirm it is listening with `ss -ltnp`.
2. Find the active configuration with `nginx -T`.
3. Create a small static site under `/var/www/example.test/public`.
4. Add a server block for `example.test`.
5. Test the configuration with `nginx -t`.
6. Reload Nginx and fetch the site with `curl -H 'Host: example.test'
   http://127.0.0.1/`.
7. Change the root path intentionally, observe the failure, and use logs to
   explain it.
8. Restore the working config and prove the site responds again.
