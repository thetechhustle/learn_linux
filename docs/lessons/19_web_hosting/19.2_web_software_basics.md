### 19.2 Web Software Basics

Web software is not one program. A working site is usually a chain of
small pieces: DNS sends visitors to an address, TLS protects the
connection, a web server receives the request, an application runtime may
generate the response, and storage systems keep state. Linux operators do
not need to write every line of the application, but they do need to know
which layer owns each failure.

!!! abstract "What you will learn"
    - Identify the common layers in a web service stack.
    - Distinguish static sites, dynamic applications, reverse proxies, and
      application servers.
    - Inspect the services, ports, logs, and configuration files that make a
      website work on Linux.
    - Make web changes with a rollback path instead of editing production
      blindly.

!!! success "Operator principle"
    Treat the website as a chain of responsibilities. When a request fails,
    find the first broken link instead of changing every layer at once.

## The moving parts

A simple website can be only a directory of files served by `nginx`,
`apache2`, or `httpd`. A larger service might include a reverse proxy, a
Python or Node.js application, a database, background workers, object
storage, a cache, and a load balancer. The names vary, but the boundaries
are usually stable.

| Layer | Common software | Operator question |
| --- | --- | --- |
| DNS | Public DNS provider, `bind`, hosted zones | Does the name resolve to the expected address? |
| TLS | Let's Encrypt, ACME clients, reverse proxy certificates | Is the certificate valid and loaded by the service? |
| Web server | `nginx`, Apache `httpd`, Caddy | Is anything listening on ports 80 or 443? |
| Reverse proxy | `nginx`, Apache, HAProxy, Caddy | Is the request routed to the right backend? |
| Application runtime | PHP-FPM, Gunicorn, uWSGI, Puma, Node.js, Java | Is the app process running and healthy? |
| Static assets | HTML, CSS, JavaScript, images, compiled bundles | Are the files deployed where the server expects them? |
| Data stores | PostgreSQL, MariaDB, Redis, object storage | Can the app reach its stateful dependencies? |
| Workers | `systemd` services, queues, cron jobs | Are asynchronous jobs running and current? |

Use this map during incidents. A 404 from the web server, a 502 from a
reverse proxy, and a database connection timeout are different problems
even if the user only says "the site is down."

## Static versus dynamic sites

A static site serves files that already exist on disk. The web server reads
`index.html`, CSS, JavaScript, images, and downloads from a document root
such as `/var/www/example.com/public`. Static sites are simple to cache and
easy to roll back because deployment is mostly a file operation.

A dynamic site generates responses at request time. The web server might
hand requests to PHP-FPM, proxy them to a Node.js process, or forward them
to a Python app running under Gunicorn or uWSGI. Dynamic sites need more
runtime checks: process health, environment variables, secrets, database
connectivity, migrations, queue workers, and error logs.

Many production sites are both. Static files may be served directly by
`nginx`, while `/api/` is proxied to an application service on
`127.0.0.1:8000`.

## Web servers and reverse proxies

Apache and `nginx` can both serve files and proxy traffic. A reverse proxy
accepts the public request and forwards it to a private backend service.
That pattern keeps application runtimes off the public internet and lets
the proxy handle TLS, compression, buffering, redirects, and request-size
limits.

A typical `nginx` server block might include:

```nginx
server {
    listen 443 ssl http2;
    server_name example.com www.example.com;

    root /var/www/example.com/public;
    index index.html;

    location / {
        try_files $uri $uri/ @app;
    }

    location @app {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

The important idea is not the exact syntax. The operator needs to know
which requests are served from disk, which requests are proxied, and which
backend should receive the proxied traffic.

## Application runtimes

Application runtimes are usually managed as services. Common examples
include:

- PHP through `php-fpm`, often using a Unix socket or localhost TCP port.
- Python through Gunicorn, uWSGI, or an ASGI server such as Uvicorn.
- Node.js through a `systemd` service, process manager, or container.
- Ruby through Puma or Passenger.
- Java through a long-running JVM service.

Find the runtime before editing proxy configuration. If `nginx` returns
`502 Bad Gateway`, the proxy may be fine and the backend process may be
stopped, overloaded, or listening somewhere else.

## Inspecting a web host

Start with read-only evidence. These commands are safe on most systems and
help identify the active stack:

```bash
hostname -f
ip addr show
ss -ltnp
systemctl --type=service --state=running
systemctl status nginx apache2 httpd php-fpm php8.2-fpm --no-pager
ps aux | grep -E 'nginx|apache2|httpd|php-fpm|gunicorn|uwsgi|node|puma|uvicorn' | grep -v grep
curl -I http://127.0.0.1/
curl -I https://example.com/
```

On a `systemd` host, service logs are often the fastest way to narrow the
fault:

```bash
journalctl -u nginx -n 100 --no-pager
journalctl -u apache2 -n 100 --no-pager
journalctl -u myapp.service -n 100 --no-pager
```

Traditional log files are still common:

```bash
ls -lah /var/log/nginx /var/log/apache2 /var/log/httpd 2>/dev/null
tail -n 50 /var/log/nginx/error.log
tail -n 50 /var/log/apache2/error.log
```

When checking from the host itself, use both localhost and the public name.
Localhost proves the service is responding internally. The public name also
tests DNS, TLS, firewall rules, and proxy routing.

## Configuration and file locations

Linux distributions use different package names and paths, but the same
families appear often:

| Purpose | Debian and Ubuntu | RHEL, CentOS, Fedora |
| --- | --- | --- |
| Web root | `/var/www/html`, `/var/www/<site>/` | `/var/www/html`, `/usr/share/nginx/html` |
| Nginx config | `/etc/nginx/nginx.conf`, `/etc/nginx/sites-enabled/` | `/etc/nginx/nginx.conf`, `/etc/nginx/conf.d/` |
| Apache config | `/etc/apache2/`, `/etc/apache2/sites-enabled/` | `/etc/httpd/`, `/etc/httpd/conf.d/` |
| Service names | `nginx`, `apache2`, `php*-fpm` | `nginx`, `httpd`, `php-fpm` |
| Logs | `/var/log/nginx/`, `/var/log/apache2/` | `/var/log/nginx/`, `/var/log/httpd/` |

Do not assume the document root from memory. Read the active configuration:

```bash
nginx -T | less
apachectl -S
grep -R "DocumentRoot\\|root \\|proxy_pass\\|ProxyPass" /etc/nginx /etc/apache2 /etc/httpd 2>/dev/null
```

Use vendor-provided syntax checks before reloading:

```bash
nginx -t
apachectl configtest
php-fpm -t
```

Reload only after the configuration test passes:

```bash
systemctl reload nginx
systemctl reload apache2
systemctl reload httpd
```

## Ownership and permissions

Web servers usually run as a restricted user such as `www-data`, `apache`,
or `nginx`. The service must be able to read public files, but it should
not own secrets or receive broad write permission across the application
tree.

Good defaults:

- Keep deployable code owned by a deployment user or root-owned package.
- Let the web server read static files and uploaded assets as needed.
- Put secrets outside the document root.
- Make writable directories explicit, such as `uploads/`, `cache/`, or
  `tmp/`.
- Avoid `chmod 777`; fix the ownership model instead.

Check the effective service user and file access:

```bash
systemctl cat nginx
systemctl cat apache2
ps -o user,group,comm -C nginx -C apache2 -C httpd -C php-fpm
namei -l /var/www/example.com/public/index.html
```

`namei -l` is useful because every parent directory in the path needs the
right execute permission before the final file can be read.

## A safe deployment rhythm

For small sites, a safe deploy can be simple:

1. Record the current version, branch, package, or artifact.
2. Copy the new release to a separate directory.
3. Run build and smoke checks before switching traffic.
4. Change a symlink, service environment file, or proxy target.
5. Reload the smallest service that needs the change.
6. Test from localhost and from the public name.
7. Keep the previous release available for rollback.

Example release layout:

```text
/srv/example.com/
  releases/
    2026-05-12-1500/
    2026-05-12-1600/
  current -> releases/2026-05-12-1600
```

If the new release fails, move `current` back to the previous directory and
reload the service. This is easier to reason about than editing live files
in place.

## Security basics

Web services are public attack surfaces. Baseline hygiene matters:

- Keep the operating system, web server, runtime, and framework updated.
- Serve production sites over HTTPS and monitor certificate renewal.
- Expose only the ports that must be public.
- Store credentials in protected files, a secret manager, or service
  environment, not in the web root.
- Disable directory listing unless it is intentional.
- Set upload limits and validate uploaded file types.
- Run the application as a non-root user.
- Keep database ports private unless there is a deliberate network design.
- Log enough to debug incidents without logging passwords, tokens, or
  personal data unnecessarily.

Use the firewall and listening socket list together:

```bash
ss -ltnp
ufw status verbose
firewall-cmd --list-all
nft list ruleset
```

Not every host uses every firewall tool. The point is to confirm what is
listening and what is reachable.

## Troubleshooting guide

| Symptom | Likely area | First checks |
| --- | --- | --- |
| Browser cannot resolve the name | DNS | `dig example.com`, registrar and hosted-zone records |
| Connection refused | Listener or firewall | `ss -ltnp`, firewall rules, cloud security group |
| TLS certificate warning | Certificate or virtual host | `openssl s_client`, proxy config, renewal timer |
| 404 Not Found | Routing or document root | Server block, `root`, `try_files`, app routes |
| 403 Forbidden | Permissions or access rules | File ownership, directory execute bits, access directives |
| 500 Internal Server Error | Application | App logs, runtime service status, recent deploy |
| 502 Bad Gateway | Backend app | Proxy target, backend process, socket permissions |
| 504 Gateway Timeout | Slow backend or network | App latency, database, worker saturation |

Keep notes while you troubleshoot. A good incident note includes the user
symptom, the exact URL, the time window, the command outputs you trusted,
the change you made, and the result after the change.

## Hands-on practice

Use a disposable VM, container, or lab host.

1. Install a web server package such as `nginx` or Apache.
2. Find its listening port with `ss -ltnp`.
3. Find the active document root from configuration, not from memory.
4. Place a simple `index.html` file in the document root.
5. Fetch it with `curl -I http://127.0.0.1/`.
6. Run the web server syntax check.
7. Change the document root in a test configuration and reload only after
   the syntax check passes.
8. Roll back to the original configuration and prove the original page
   still works.
