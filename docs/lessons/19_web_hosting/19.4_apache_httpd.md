### Apache HTTPD

Apache HTTPD is a general-purpose web server. In Linux operations you will
usually meet it as `apache2` on Debian and Ubuntu systems, or `httpd` on Red
Hat-family systems. It can serve static files, route requests to application
runtimes, terminate TLS, enforce access rules, and host many sites from one
machine.

!!! abstract "What you will learn"
    - Explain the role Apache HTTPD plays in a Linux web stack.
    - Inspect Apache packages, services, enabled modules, virtual hosts, and logs.
    - Validate configuration before reloads or restarts.
    - Build a small virtual host safely in a lab environment.
    - Troubleshoot common Apache failures with command output instead of guesses.

!!! example "Field story"
    A team is launching a small documentation site. DNS already points at the
    server, but the first request returns the default Apache page instead of the
    new site. Your job is to prove which virtual host Apache selected, confirm
    that the document root exists, validate the config, and reload only after
    the evidence is clean.

!!! success "Operator principle"
    Treat Apache as a managed service with testable configuration. Inspect first,
    validate second, reload third, and use logs to prove what happened.

## Where Apache fits

Apache listens for HTTP or HTTPS connections, chooses a virtual host, applies
configuration directives, and returns a response. A production web stack often
has several separate responsibilities:

- **Apache HTTPD** accepts the client request and applies web-server rules.
- **Virtual hosts** map hostnames such as `www.example.com` to site-specific
  configuration.
- **Document roots** hold static content such as HTML, CSS, images, and
  downloads.
- **Modules** add behavior such as TLS, URL rewriting, proxying, compression,
  authentication, and headers.
- **Application runtimes** such as PHP-FPM, Python, Ruby, Node.js, or Java may
  run outside Apache and receive proxied requests.
- **Logs** record access attempts, errors, redirects, permission failures, and
  upstream application problems.

That separation matters during incidents. A 404 from Apache, a 503 from a
backend service, and a TLS certificate error all look like "the website is down"
to users, but they have different fixes.

## Package and service names

Apache names vary by distribution. Check the local system before copying
commands from an article:

```bash
cat /etc/os-release
systemctl list-unit-files 'apache2*' 'httpd*'
```

Common paths include:

| Distribution family | Service | Main config | Site config pattern | Logs |
| --- | --- | --- | --- | --- |
| Debian / Ubuntu | `apache2` | `/etc/apache2/apache2.conf` | `/etc/apache2/sites-available/*.conf` | `/var/log/apache2/` |
| RHEL / Fedora / Rocky / AlmaLinux | `httpd` | `/etc/httpd/conf/httpd.conf` | `/etc/httpd/conf.d/*.conf` | `/var/log/httpd/` |

You do not need to memorize every path. Build the habit of confirming what this
machine actually uses.

## Read the current Apache state

Start with read-only checks:

```bash
systemctl status apache2 --no-pager
apache2ctl -v
apache2ctl -M
apache2ctl -S
```

On RHEL-family systems, substitute `httpd` and `apachectl` where appropriate:

```bash
systemctl status httpd --no-pager
httpd -v
httpd -M
httpd -S
```

Useful questions:

- Is the service loaded, enabled, and running?
- Which configuration file is Apache reading?
- Which modules are loaded?
- Which virtual host is the default for port 80 or 443?
- Which log file records errors for the affected site?

`apache2ctl -S` or `httpd -S` is especially valuable because it shows virtual
host matching. Use it before changing DNS, firewall rules, or application code.

## Virtual host example

A minimal Debian-style virtual host for a static lab site might look like this:

```apache
<VirtualHost *:80>
    ServerName lab.example.test
    DocumentRoot /var/www/lab.example.test

    ErrorLog ${APACHE_LOG_DIR}/lab.example.test-error.log
    CustomLog ${APACHE_LOG_DIR}/lab.example.test-access.log combined

    <Directory /var/www/lab.example.test>
        Require all granted
        Options -Indexes
        AllowOverride None
    </Directory>
</VirtualHost>
```

Important details:

- `ServerName` controls hostname matching.
- `DocumentRoot` must exist and be readable by the Apache worker process.
- `ErrorLog` and `CustomLog` keep this site's evidence separate from the default
  logs.
- `Options -Indexes` prevents directory listings if an index file is missing.
- `AllowOverride None` avoids hidden `.htaccess` behavior unless you explicitly
  need per-directory overrides.

On Debian and Ubuntu, site files normally live in
`/etc/apache2/sites-available/` and are enabled with `a2ensite`. On
RHEL-family systems, drop a `.conf` file into `/etc/httpd/conf.d/`.

## Validate before reload

Do not restart Apache as the first troubleshooting step. A restart can drop
active connections and may hide the original failure. Prefer this workflow:

```bash
sudo apache2ctl configtest
sudo systemctl reload apache2
sudo systemctl status apache2 --no-pager
```

For RHEL-family systems:

```bash
sudo httpd -t
sudo systemctl reload httpd
sudo systemctl status httpd --no-pager
```

Use `reload` for configuration changes that Apache can apply without a full
stop/start cycle. Use `restart` when the module, package, or service state
requires it, and note the customer impact before you do.

## Logs and request testing

Use local requests first so DNS and public network paths do not confuse the
result:

```bash
curl -I http://127.0.0.1/
curl -I -H 'Host: lab.example.test' http://127.0.0.1/
sudo tail -n 50 /var/log/apache2/error.log
sudo tail -n 50 /var/log/apache2/access.log
```

The `Host` header test is useful when the server hosts multiple sites. It lets
you test virtual-host selection before public DNS is ready.

For HTTPS issues, separate certificate and web-server checks:

```bash
curl -vkI https://lab.example.test/
openssl s_client -connect lab.example.test:443 -servername lab.example.test </dev/null
```

Use `-k` only as a diagnostic flag. Do not teach scripts or monitoring checks to
ignore certificate validation permanently.

## Common failure patterns

| Symptom | Likely place to look | Evidence command |
| --- | --- | --- |
| Default Apache page appears | Wrong virtual host selected | `apache2ctl -S` |
| 403 Forbidden | Directory permissions or `Require` rules | `namei -l /var/www/site` and error log |
| 404 Not Found | Wrong document root or URL path | `ls -la DocumentRoot` and access log |
| 500 Internal Server Error | Application, `.htaccess`, or module error | site error log |
| 503 Service Unavailable | Backend proxy target down | `systemctl status` for backend service |
| Config test fails | Syntax or module directive issue | `apache2ctl configtest` |
| HTTPS name mismatch | Certificate SAN does not include hostname | `openssl s_client ... -servername ...` |

Avoid changing several layers at once. If you change Apache config, DNS, TLS,
and application deployment in the same window, rollback becomes guesswork.

## Hands-on practice

Run these steps on a disposable VM, container, or lab machine.

1. Identify whether the system uses `apache2` or `httpd`.
2. Run the service, version, module, and virtual-host inspection commands for
   your distribution.
3. Create a small document root under `/var/www/lab.example.test` with an
   `index.html` file.
4. Add a lab-only virtual host for `lab.example.test`.
5. Validate the configuration with `apache2ctl configtest` or `httpd -t`.
6. Reload Apache.
7. Test the site locally with `curl -I -H 'Host: lab.example.test'
   http://127.0.0.1/`.
8. Find the matching access-log entry and record the status code.
9. Disable or remove the lab virtual host when you are done.
