### 02.10 Stratagems for a Non-Booting System

!!! abstract "What you will learn"
    - Triage a non-booting Linux host without guessing at destructive fixes.
    - Separate firmware, boot loader, kernel, initramfs, filesystem, and systemd failures.
    - Use rescue and emergency targets with a clear rollback plan.
    - Capture enough evidence for a teammate or vendor escalation.

!!! warning "Safety boundary"
    Non-booting-system recovery often touches disks, boot loaders, kernels, and identity services. On a production host, stop before writing to disk unless you have console access, a backup or snapshot, and an agreed rollback path.

!!! example "Field story"
    A production VM fails after a routine kernel update. The app team asks for a quick rollback, but the console shows emergency mode rather than a boot loader prompt. The fastest safe path is to collect boot evidence, identify the failed mount, and choose a reversible repair instead of reinstalling GRUB.

!!! success "Operator principle"
    Prove which boot stage failed before changing disks, kernels, boot loader configuration, or service state.

A host that does not boot is not one problem. It is a symptom that can appear at several handoff points:

- Firmware cannot find a boot device.
- The boot loader cannot find its configuration, kernel, or initramfs.
- The kernel cannot mount the root filesystem.
- `systemd` starts but a required unit, mount, or dependency blocks normal boot.
- The operating system is healthy, but networking, storage, or authentication makes the host look unavailable.

Your first job is to identify the handoff that failed. Your second job is to make the smallest reversible change that gets the machine booted or preserves evidence for escalation.

## Start with a Recovery Runbook

Before editing anything, write down the recovery state:

```text
Host:
Impact:
Last known good boot:
Recent changes:
Console access:
Snapshot or backup available:
Observed failure text:
Current boot stage:
Rollback plan:
```

That note prevents two common incident mistakes: repeating the same failed action and forgetting which evidence existed before a repair command changed it.

## Read the Failure Stage

Use the console, cloud serial log, hypervisor screenshot, or out-of-band management display to decide where the boot stopped.

| Symptom | Likely layer | First evidence to collect |
| --- | --- | --- |
| No boot device, PXE loop, firmware setup screen | Firmware or disk presentation | Firmware boot order, virtual disk attachment, cloud volume mapping |
| `grub>` prompt or missing `grub.cfg` | Boot loader | Available disks and partitions from GRUB, `/boot` contents from rescue media |
| Kernel panic, unable to mount root filesystem | Kernel, initramfs, root device | Kernel command line, initramfs contents, root UUID, storage driver state |
| Drops to emergency mode | Filesystem, mount, unit dependency | `journalctl -xb`, failed units, `/etc/fstab`, mount output |
| Boots locally but remote login fails | Network, firewall, SSH, identity | IP address, route, `sshd` state, cloud security rules |

Do not assume the newest visible error is the root cause. A failed mount can be caused by an earlier disk rename, a kernel panic can follow an initramfs that lacks the needed storage driver, and an unreachable VM can simply have no network route.

## Safe First Commands

Once you have a shell, stay read-only until the failure layer is clear:

```bash
uname -a
cat /proc/cmdline
lsblk -f
blkid
findmnt
systemctl --failed
journalctl -xb -p warning
journalctl -xb -u systemd-fsck@*.service
```

If the system booted into rescue media, mount the installed system read-only first:

```bash
sudo mkdir -p /mnt/sysroot
sudo mount -o ro /dev/mapper/vg0-root /mnt/sysroot
sudo findmnt /mnt/sysroot
```

Replace the device name with the actual root device from `lsblk -f`. Do not run filesystem repair or boot loader installation commands until the target device is unambiguous.

## Common Recovery Paths

### Wrong Kernel or Initramfs

Symptoms include a kernel panic after an update, missing storage modules, or a root UUID that cannot be found.

Low-risk actions:

1. Try an older kernel from the boot loader menu.
2. Compare the working and failing kernel command lines.
3. Rebuild the initramfs only after booting a known-good kernel or entering a chroot from rescue media.

Evidence to preserve:

```bash
ls -lh /boot
cat /proc/cmdline
journalctl -k -b
```

### Broken `/etc/fstab`

Symptoms include emergency mode, mount timeout messages, or a root shell asking for maintenance.

Inspect before changing:

```bash
systemctl --failed
journalctl -xb | grep -iE 'mount|fstab|dependency|timeout'
findmnt --verify
cat /etc/fstab
lsblk -f
```

If a noncritical mount is blocking boot, the safer repair is usually to comment it out or add conservative options such as `nofail` and `x-systemd.device-timeout=10s`, then reboot and investigate the missing device separately. Do not weaken the root filesystem entry just to make an error disappear.

### Boot Loader Configuration

Symptoms include a GRUB prompt, missing menu entries, or a host that always boots the wrong kernel.

Read-only inspection:

```bash
ls -lh /boot
ls -lh /boot/grub /boot/grub2 2>/dev/null
grep -R "menuentry " /boot/grub /boot/grub2 2>/dev/null
efibootmgr -v
```

Only regenerate boot loader configuration or reinstall GRUB when you know the firmware mode, boot disk, EFI system partition, and distribution-specific command. A BIOS-mode repair command on a UEFI system can make the incident worse.

### Service Dependency Blocks

If the kernel boots and `systemd` starts, the problem may be a unit ordering or dependency failure rather than a boot loader issue.

Useful commands:

```bash
systemctl --failed
systemctl list-jobs
journalctl -xb -p err
systemctl status <unit>
systemctl cat <unit>
```

For a temporary boot, you can isolate a simpler target from the console:

```bash
sudo systemctl isolate rescue.target
```

Treat this as a diagnostic move, not a permanent fix. Record which unit blocks `multi-user.target` or `graphical.target`, then repair or disable only that unit after checking its purpose.

## Rescue and Emergency Targets

Linux recovery modes are intentionally limited.

- `emergency.target` gives the smallest local shell. Use it when filesystems, mounts, or early units are badly broken.
- `rescue.target` starts more of the local system. Use it when the host can mount filesystems but cannot reach normal multi-user service state.

At the GRUB menu, editing the Linux command line with one of these targets can be enough:

```text
systemd.unit=emergency.target
systemd.unit=rescue.target
```

If the root filesystem must be repaired, remount intentionally:

```bash
mount | grep ' on / '
sudo mount -o remount,rw /
```

That command changes the safety level of the session. Say it out loud in the incident notes before editing files.

## Practice Lab

Use a disposable VM with a snapshot.

1. Record the current root filesystem UUID:

    ```bash
    lsblk -f
    grep -n ' / ' /etc/fstab
    ```

2. Add a harmless missing test mount to `/etc/fstab` with `nofail` omitted.
3. Reboot and observe whether the VM enters emergency mode.
4. From the emergency shell, collect:

    ```bash
    systemctl --failed
    journalctl -xb -p warning
    findmnt --verify
    ```

5. Fix the test mount by commenting it out or adding `nofail`, then reboot.
6. Restore the VM snapshot when finished.

Do this only in the lab. Deliberately breaking boot on a shared or production system is not a training exercise.

## Incident Handoff Example

```text
Host web-03 failed after kernel update at 03:20 UTC.
Console shows emergency mode, not firmware or GRUB failure.
Evidence: systemctl --failed reports mnt-data.mount; journal shows timeout waiting for UUID=...
Root filesystem mounted read-only first; no fsck or boot loader commands run.
Temporary repair: commented stale /data fstab line after confirming volume is detached in cloud console.
Verification: reboot reached multi-user.target; ssh and app service are healthy.
Follow-up: decide whether to reattach the data volume or remove the obsolete mount permanently.
```
