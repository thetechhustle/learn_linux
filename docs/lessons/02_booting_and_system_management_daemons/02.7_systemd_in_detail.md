### Understanding systemd

`systemd` is the service manager and init system used by many Linux
distributions. After the kernel starts the first user-space process,
`systemd` usually runs as PID 1. From there, it brings the machine toward a
target state by starting units, mounting filesystems, preparing sockets,
tracking devices, and supervising long-running services.

For an operator, the most useful way to understand `systemd` is as a state
machine with evidence. A service is not just "running" or "broken"; it has a
unit file, dependencies, recent state transitions, logs, restart policy,
enablement state, and a place in the boot transaction.

!!! abstract "What you will learn"
    - Explain the role of `systemd` as PID 1 and service manager.
    - Inspect unit files, unit state, dependencies, and recent service logs.
    - Distinguish read-only checks from commands that change runtime or boot behavior.
    - Build a short incident handoff for a service managed by `systemd`.

!!! warning "Production safety"
    Most `systemctl` inspection commands are safe. Commands such as `start`,
    `stop`, `restart`, `reload`, `enable`, `disable`, and `mask` can affect live
    traffic or the next boot. On production systems, check ownership,
    dependencies, maintenance windows, and rollback steps before changing state.

## What systemd manages

`systemd` manages resources through **units**. A unit is a named object with a
type suffix:

- `.service` units manage daemons and one-shot jobs.
- `.socket` units listen on sockets and can activate services on demand.
- `.target` units group other units into a desired system state.
- `.mount` and `.automount` units manage mounted filesystems.
- `.timer` units schedule work, often replacing simple cron-style jobs.
- `.device` units represent kernel devices that `systemd` can order against.

The unit type matters because it changes how `systemd` starts, tracks, and
orders the work.

## Read the current state first

Start with read-only commands. Replace `sshd.service` with a service that exists
on your lab system, such as `cron.service`, `nginx.service`, or
`NetworkManager.service`.

```bash
systemctl status sshd.service
systemctl is-active sshd.service
systemctl is-enabled sshd.service
systemctl show sshd.service --property=Id,LoadState,ActiveState,SubState,UnitFileState,FragmentPath
```

Useful fields:

- `LoadState` tells you whether `systemd` could load the unit definition.
- `ActiveState` gives the broad state, such as `active`, `inactive`, or `failed`.
- `SubState` gives a more specific runtime state.
- `UnitFileState` tells you whether the unit is enabled for boot.
- `FragmentPath` shows which unit file `systemd` loaded.

## Inspect the unit definition

Before changing a service, inspect the effective unit file and any drop-in
overrides.

```bash
systemctl cat sshd.service
systemctl show sshd.service --property=ExecStart,Restart,RestartSec,User,Group,WorkingDirectory
```

`systemctl cat` is especially useful because it shows the base unit and override
files in the order `systemd` applies them. If a service behaves differently than
expected, a drop-in file under `/etc/systemd/system/<unit>.d/` is often the
reason.

## Check dependencies and boot ordering

Services rarely run alone. A service may require a network target, a mounted
volume, a socket, or another daemon.

```bash
systemctl list-dependencies sshd.service
systemctl list-dependencies --reverse sshd.service
systemctl show sshd.service --property=Requires,Wants,After,Before
```

Use these commands before restarting, disabling, or masking a service. The
reverse dependency view answers a practical question: "What else expects this
unit to be present?"

## Use the journal as evidence

`systemd-journald` stores structured logs. For incidents, prefer a narrow time
window and a specific unit.

```bash
journalctl -u sshd.service --since "1 hour ago"
journalctl -u sshd.service -p warning..alert --since today
journalctl -b -u sshd.service
journalctl -b -1 -u sshd.service
```

The `-b` flag means "this boot." The `-b -1` form means "previous boot" and is
useful after a reboot fixed or changed the symptom.

## Know which commands change state

These commands change the running system:

```bash
sudo systemctl start sshd.service
sudo systemctl stop sshd.service
sudo systemctl restart sshd.service
sudo systemctl reload sshd.service
```

These commands change boot behavior:

```bash
sudo systemctl enable sshd.service
sudo systemctl disable sshd.service
sudo systemctl mask sshd.service
sudo systemctl unmask sshd.service
```

The difference matters. `restart` can drop active connections immediately.
`enable` does not necessarily start the service now; it usually makes the
service start on future boots. `mask` is stronger than `disable`: it prevents the
unit from being started manually or as a dependency until it is unmasked.

## Practice: build a service handoff

Use a disposable VM, container, or lab machine.

1. Choose a service that exists on the system.
2. Run these read-only checks:

   ```bash
   systemctl status <service>
   systemctl is-enabled <service>
   systemctl cat <service>
   systemctl list-dependencies --reverse <service>
   journalctl -u <service> --since "30 minutes ago"
   ```

3. Write a short handoff:

   ```text
   Service: <service>
   Runtime state: <ActiveState/SubState>
   Boot state: <enabled/disabled/static/masked>
   Unit source: <FragmentPath and any drop-ins>
   Dependency concern: <important reverse dependency or none found>
   Recent evidence: <one journal line or "no recent warnings">
   Recommended next step: <read-only follow-up or proposed change>
   Risk: <what could break if changed>
   ```
