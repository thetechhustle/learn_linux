Daemons are background processes that provide system services without an
interactive user session. Some start during boot, some start only when another
component asks for them, and some run on timers. A healthy Linux host usually
has many daemons running at once: logging, scheduling, networking, remote
access, hardware events, and application services.

For an operator, the important question is not just "is the daemon running?" It
is "what owns it, why did it start, what does it depend on, and what evidence
shows that it is healthy?"

##### Examples of Daemons

To give you a better idea, let's discuss some classic examples of daemons in a Linux system:

**1. `sshd` (Secure Shell daemon):** This daemon enables administrators to log in to a machine remotely, performing tasks securely over an unsecured network.

**2. `crond` (CRON daemon):**  The time-based job scheduler in Unix-like operating systems makes sure that scheduled jobs run at the preset times.

**3. `syslogd` (System Logger Daemon):** It manages log files, ensuring system events get recorded for future reference.

##### Inspect Before You Change

Start with read-only commands. They give you a baseline and lower the chance of
turning a small service issue into an outage.

```bash
systemctl status ssh.service
systemctl is-enabled ssh.service
systemctl list-dependencies ssh.service
journalctl -u ssh.service -n 50 --no-pager
```

The exact service name varies by distribution. For example, Debian and Ubuntu
often use `ssh.service`, while some RHEL-family systems use `sshd.service`.
If a unit name is not obvious, search for it:

```bash
systemctl list-unit-files '*ssh*'
```

Record four facts before making a change:

- Current state: active, failed, inactive, or activating.
- Boot behavior: enabled, disabled, static, masked, or generated.
- Recent log evidence from `journalctl`.
- Dependencies that might also be affected.

##### Starting, Stopping, and Restarting Daemons

While daemons often start up during system boot, you can also start them manually. Typically, the command syntax for such operations is `/etc/init.d/daemon-name start|stop|restart` for init-based systems.

In the newer systemd-based systems, the equivalent commands are:
1. `systemctl start daemon.service`
2. `systemctl stop daemon.service`
3. `systemctl restart daemon.service`

Replace 'daemon' in the above examples with the name of the daemon you want to control.

Administrative or root permission is generally required to manage daemons.

Use the smallest action that matches the goal:

- `systemctl reload name.service` asks a service to reread configuration without a full restart, if the service supports reloads.
- `systemctl restart name.service` stops and starts the service, which can drop active connections.
- `systemctl enable name.service` changes boot behavior but does not necessarily start the service now.
- `systemctl disable name.service` changes future boot behavior but does not necessarily stop the service now.
- `systemctl mask name.service` blocks starts entirely and should be reserved for deliberate safety controls.

Before stopping, disabling, or masking a service, identify who depends on it and
how you will recover console access if remote access breaks. This is especially
important for network, SSH, storage, and identity services.

##### Daemons and Security

Managing daemons effectively plays a critical role in system security. Running unnecessary daemons might unnecessarily expose system vulnerabilities. Therefore, minimize the number of active daemons by understanding which services are essential for your machine's role.

The safest pattern is to keep only required services running, keep them patched,
limit their privileges where possible, and verify their logs after every
configuration change. When you hand off an incident, include the command you
ran, the before-and-after service state, and the journal lines that support your
conclusion.
