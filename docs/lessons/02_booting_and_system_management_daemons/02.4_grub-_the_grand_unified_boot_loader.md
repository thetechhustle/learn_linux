### 02.4 GRUB: The Grand Unified Boot Loader

GRUB is the boot loader used by many Linux distributions. It sits between
firmware and the Linux kernel. Firmware finds and starts GRUB; GRUB presents or
chooses a boot menu entry; then GRUB loads the selected kernel, initramfs, and
kernel command line.

For operators, GRUB is important because a small configuration mistake can make
a machine fail before normal Linux services ever start. Treat GRUB work as boot
path work: inspect first, change only with a rollback path, and verify at the
next reboot.

!!! abstract "What you will learn"
    - Explain where GRUB fits in the firmware-to-kernel handoff.
    - Inspect GRUB defaults, generated configuration, menu entries, kernels, and initramfs files.
    - Distinguish safe read-only checks from commands that change the next boot.
    - Build a practical handoff for a suspected GRUB or kernel-selection issue.

!!! warning "Production safety"
    Editing GRUB can break remote access if the next boot fails. Before changing
    boot options on a production host, confirm console access, a maintenance
    window, a known-good previous kernel, and how to undo the change.

## What GRUB loads

A GRUB menu entry normally points to three important pieces:

- the Linux kernel, often a file under `/boot` named `vmlinuz-*`
- the initramfs image, often `initrd.img-*` or `initramfs-*`
- the kernel command line, such as root filesystem, console, rescue, or quiet
  boot options

If the firmware stage succeeds but the machine fails before `systemd` starts,
GRUB evidence can answer whether the right kernel and initramfs were selected.

## Inspect GRUB without changing it

Start with read-only checks:

```bash
ls -lh /boot
findmnt /boot /boot/efi
test -f /etc/default/grub && sed -n '1,160p' /etc/default/grub
```

Useful evidence:

- which kernels and initramfs files exist in `/boot`
- whether `/boot` or `/boot/efi` is a separate mounted filesystem
- whether default GRUB options are set in `/etc/default/grub`

On Debian and Ubuntu systems, the generated GRUB config is usually
`/boot/grub/grub.cfg`. On RHEL-family systems, paths can differ, especially on
UEFI systems. Inspect, do not edit, generated config directly:

```bash
sudo grep -n "menuentry\\|linux\\|initrd" /boot/grub/grub.cfg | head -80
```

## Know the source files

The common GRUB file roles are:

- `/etc/default/grub`: operator-facing defaults such as timeout and kernel
  command-line options
- `/etc/grub.d/`: scripts used to generate menu entries
- `/boot/grub/grub.cfg`: generated output consumed by GRUB at boot
- `/boot/vmlinuz-*`: installed kernels
- `/boot/initrd.img-*` or `/boot/initramfs-*`: initramfs images
- `/boot/efi/EFI/...`: UEFI boot loader location on UEFI systems

Do not hand-edit `/boot/grub/grub.cfg` as your primary change. It is generated
and can be overwritten by package updates or GRUB regeneration commands.

## Commands that change boot behavior

These commands can affect future boots:

```bash
sudo update-grub
sudo grub-mkconfig -o /boot/grub/grub.cfg
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
sudo grub-install <device>
```

Distribution names vary. Debian and Ubuntu commonly use `update-grub`.
RHEL-family systems commonly use `grub2-mkconfig`. `grub-install` is more
invasive because it writes boot loader code to a disk or EFI target.

Before running these commands on a production host, record:

- the current boot mode: UEFI or BIOS
- the current kernel from `uname -r`
- the available kernels in `/boot`
- the existing GRUB defaults
- the rollback plan if the next boot fails

## Kernel command-line evidence

The running kernel command line is visible here:

```bash
cat /proc/cmdline
```

Compare it to the configured defaults in `/etc/default/grub`. If the running
system was booted with an emergency option, a serial console, a rescue target, or
a temporary root override, `/proc/cmdline` is the source of truth for the current
boot.

Common options you may see:

- `quiet` or `splash`: reduce boot output
- `systemd.unit=rescue.target`: boot into rescue mode
- `single`: older single-user boot style
- `console=...`: select console output
- `root=...`: identify the root filesystem

## Incident pattern: boot fails after a kernel update

When a host fails after a kernel update, collect evidence before changing GRUB:

1. What kernel is running on a healthy peer?
2. What kernels and initramfs files exist in `/boot`?
3. Which kernel did GRUB try to boot?
4. Does a previous kernel entry still exist?
5. Does `/boot` have enough free space?
6. Did Secure Boot, disk UUIDs, storage drivers, or root filesystem options
   change?

If console access is available, choosing a previous kernel from the GRUB menu is
often lower risk than editing config blind.

## Practice: GRUB evidence note

Use a disposable VM or lab system.

1. Capture the current kernel and command line:

   ```bash
   uname -r
   cat /proc/cmdline
   ```

2. Inspect boot files:

   ```bash
   ls -lh /boot
   findmnt /boot /boot/efi
   ```

3. Inspect GRUB defaults and generated entries:

   ```bash
   sed -n '1,160p' /etc/default/grub
   sudo grep -n "menuentry\\|linux\\|initrd" /boot/grub/grub.cfg | head -80
   ```

4. Write a handoff:

   ```text
   Current kernel: <uname -r>
   Boot mode: <UEFI/BIOS if known>
   /boot mounted: <yes/no and source>
   Available kernels: <list or summary>
   Current command line: <important options>
   Suspected issue: <kernel selection, missing initramfs, bad option, unknown>
   Safe next step: <read-only check or maintenance-window change>
   Rollback path: <previous kernel, console access, snapshot, or unknown>
   ```
