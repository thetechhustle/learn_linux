## 02.2 System Firmware

System firmware is the first operational layer in the boot path. Before Linux
can load a kernel, start `systemd`, mount filesystems, or launch services, the
machine firmware must initialize hardware, choose a boot path, and hand control
to a boot loader.

On modern servers and laptops, that firmware is usually **UEFI**. Older systems
may use legacy **BIOS** boot. In day-to-day operations, you do not need to
memorize every firmware menu. You do need to know how to collect evidence about
the boot mode, boot entries, storage visibility, and handoff point before
changing boot settings.

!!! abstract "What you will learn"
    - Explain what system firmware does before Linux starts.
    - Distinguish UEFI boot from legacy BIOS boot using Linux evidence.
    - Inspect firmware boot entries and the EFI system partition safely.
    - Identify when firmware changes require physical access or a maintenance window.

!!! warning "Production safety"
    Firmware settings can make a machine unreachable. Changing boot order,
    Secure Boot state, PXE settings, storage controller mode, or firmware
    updates can prevent normal boot. Treat those changes as maintenance-window
    work with console access, rollback notes, and a known-good boot path.

## What firmware does

At power-on, firmware performs the first hardware and boot decisions:

1. Initializes CPU, memory, storage controllers, network adapters, and platform
   devices.
2. Runs early hardware checks, often called POST.
3. Reads boot configuration from firmware storage.
4. Finds a bootable disk, removable device, network target, or EFI executable.
5. Hands control to the boot loader, which then loads the operating system.

When a machine cannot reach the boot loader, firmware evidence is often more
useful than Linux service logs because Linux may not have started yet.

## UEFI vs legacy BIOS

Use this read-only check to identify the boot mode from Linux:

```bash
if [ -d /sys/firmware/efi ]; then
  echo "UEFI boot"
else
  echo "Legacy BIOS or non-UEFI boot"
fi
```

On a UEFI system, Linux exposes firmware variables under
`/sys/firmware/efi/efivars/`. On a legacy BIOS boot, that path is usually absent.

!!! note "Virtual machines"
    A VM can boot with UEFI or BIOS depending on the hypervisor settings. When a
    VM boot issue appears only after migration, compare the source and
    destination firmware mode before changing the guest operating system.

## Inspect UEFI boot entries

On UEFI systems, `efibootmgr` shows boot entries and boot order. Reading entries
is safe; writing entries changes firmware state.

```bash
sudo efibootmgr -v
```

Look for:

- `BootCurrent`: the entry used for this boot.
- `BootOrder`: the order firmware tries entries.
- `Boot####` entries: named boot options such as Linux, Windows Boot Manager,
  PXE, or removable media.
- File paths ending in `.efi`, such as `\\EFI\\BOOT\\BOOTX64.EFI` or a
  distribution-specific loader.

Do not run `efibootmgr` commands that include `--bootorder`, `--create`,
`--delete-bootnum`, or `--active` until you understand the rollback path.

## Inspect the EFI system partition

UEFI boot loaders usually live on an EFI system partition, often mounted at
`/boot/efi` or sometimes `/efi`.

Read-only checks:

```bash
findmnt /boot/efi /efi
lsblk -f
sudo find /boot/efi/EFI -maxdepth 3 -type f 2>/dev/null
```

Useful evidence:

- Whether the EFI system partition is mounted.
- Which disk and partition contain the EFI filesystem.
- Which boot loader files exist under `EFI/`.
- Whether the expected distribution, fallback, or vendor boot path is present.

If `/boot/efi` is not mounted, avoid assuming the boot files are missing. Check
`lsblk -f` and `/etc/fstab` before making changes.

## Firmware settings that affect Linux

Firmware settings can change what Linux sees:

- **Boot order** chooses disk, USB, PXE, or another boot target.
- **Secure Boot** can block unsigned boot loaders or kernel modules.
- **UEFI vs legacy mode** changes the expected boot loader layout.
- **Storage controller mode** can change disk names or driver requirements.
- **PXE/network boot** can override local disk boot if ordered first.
- **Virtualization options** affect hypervisors and container hosts.

These settings are usually changed outside Linux, through a firmware setup UI,
out-of-band management controller, hypervisor settings, or vendor tooling.

## Incident pattern: boot stops before Linux

If a machine fails before the Linux login prompt, collect evidence in this order:

1. Console screenshot or exact firmware error text.
2. Whether firmware sees the boot disk.
3. Current boot mode: UEFI or legacy BIOS.
4. Current boot order and selected boot entry.
5. Whether the EFI system partition contains the expected loader.
6. Recent change history: firmware update, disk replacement, OS reinstall,
   hypervisor migration, Secure Boot change, or PXE change.

This evidence narrows the problem before anyone edits GRUB, rebuilds initramfs,
or changes service configuration.

## Practice: firmware evidence note

Use a disposable VM or lab machine.

1. Identify boot mode:

   ```bash
   test -d /sys/firmware/efi && echo UEFI || echo BIOS
   ```

2. If the system uses UEFI, inspect entries:

   ```bash
   sudo efibootmgr -v
   ```

3. Inspect boot-related filesystems:

   ```bash
   findmnt /boot /boot/efi /efi
   lsblk -f
   ```

4. Write a short handoff:

   ```text
   Boot mode: <UEFI or BIOS>
   Boot disk visible: <yes/no/evidence>
   EFI partition: <mount point or not mounted>
   Current UEFI entry: <BootCurrent if available>
   Boot order concern: <none or observed issue>
   Recent change: <known change or unknown>
   Safe next step: <read-only follow-up or proposed maintenance-window change>
   ```
