### 02.5 The FreeBSD Boot Process

!!! abstract "What you will learn"
    - Trace the FreeBSD boot chain from firmware to loader, kernel, `init`, and `rc`.
    - Compare FreeBSD's loader and startup scripts with the Linux bootloader/systemd path.
    - Gather read-only evidence before changing loader, filesystem, or service startup settings.

!!! example "Field story"
    A FreeBSD firewall VM stops during startup after a maintenance reboot. Linux muscle memory says to check GRUB and systemd first, but this host uses the FreeBSD loader and `rc` scripts. Your job is to identify which stage succeeded, which stage failed, and what evidence you would hand to the next operator.

!!! success "Operator principle"
    Treat FreeBSD boot incidents as a chain of handoffs. Do not edit loader or startup files until you know which handoff failed.

## Hands-on practice

Run these commands on a disposable FreeBSD VM or lab host. They are intended to be read-only. If you are using a Linux machine, read the command purposes and compare them to the equivalent Linux evidence you would collect with `journalctl`, `systemctl`, `findmnt`, and bootloader tools.

1. Confirm the operating system and kernel:

    ```sh
    freebsd-version
    uname -a
    ```

2. Inspect loader-related configuration without changing it:

    ```sh
    sed -n '1,160p' /boot/loader.conf
    sed -n '1,120p' /boot/defaults/loader.conf
    kenv | sort | sed -n '1,80p'
    ```

    `/boot/defaults/loader.conf` is the system-provided reference. Do not edit it. Local loader tunables belong in `/boot/loader.conf`.

3. Check filesystems and mount state:

    ```sh
    mount
    df -h
    cat /etc/fstab
    ```

4. Inspect startup services and `rc` configuration:

    ```sh
    service -e
    sysrc -a
    sed -n '1,160p' /etc/rc.conf
    ```

    FreeBSD uses `rc` scripts for service startup. On Linux, you would usually inspect systemd units and targets instead.

5. Review recent boot messages:

    ```sh
    dmesg -a | tail -80
    ```

6. Write a short incident note with four fields:

    ```text
    Firmware/loader evidence:
    Kernel evidence:
    Filesystem evidence:
    rc/service evidence:
    ```

    Fill each field with one command and the specific line that changed your confidence.

## How the FreeBSD boot chain works

FreeBSD boot usually follows this path:

1. Firmware initializes hardware and chooses a boot device.
2. FreeBSD boot blocks and the loader prepare the kernel environment.
3. The kernel initializes devices, mounts the root filesystem, and starts `/sbin/init`.
4. `init` transitions the machine through startup states.
5. The `rc` system reads configuration such as `/etc/rc.conf` and starts enabled services from `/etc/rc.d/` and `/usr/local/etc/rc.d/`.

The important contrast with a typical Linux server is not that one system is simpler. The contrast is where evidence lives. On many Linux systems, systemd owns most service startup evidence. On FreeBSD, the loader environment, `/etc/rc.conf`, and shell-based `rc` scripts are first-class evidence.

## Safe change boundaries

Changing boot settings can prevent remote recovery. Keep these boundaries:

- Use a console, VM snapshot, or rollback plan before editing boot-critical files.
- Do not edit `/boot/defaults/loader.conf`; it documents defaults and may be replaced by upgrades.
- Put local loader overrides in `/boot/loader.conf`.
- Prefer `sysrc` for persistent `/etc/rc.conf` changes when possible.
- Change one setting at a time and keep the exact before/after diff in your notes.
- If a system is already failing to boot, collect evidence from the console before guessing at loader tunables.

## Linux comparison

For a Linux boot issue, you might ask:

- Did firmware hand off to GRUB or another bootloader?
- Did the kernel mount the expected root filesystem?
- Did systemd reach the expected target?
- Which unit failed first?

For a FreeBSD boot issue, ask the same style of questions with different evidence:

- Did firmware reach the FreeBSD loader?
- What loader variables were set?
- Did the kernel attach the expected disks and mount root?
- Did `init` and `rc` start the expected services?
- Which `rc` script, service, or filesystem mount failed first?
