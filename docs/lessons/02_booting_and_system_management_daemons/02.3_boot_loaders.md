### 02.3 Boot Loaders

!!! abstract "What you will learn"
    - Explain what a boot loader owns between firmware and the Linux kernel.
    - Collect read-only evidence about the active boot path before changing it.
    - Identify which boot loader changes are safe in a lab and which require a rollback plan.

!!! example "Field story"
    A kernel update finishes cleanly, but the next reboot drops a VM into a GRUB prompt. The fastest useful response is not to reinstall Linux. It is to identify whether firmware found the right disk, whether the boot loader found the right kernel and initramfs, and whether the selected kernel was given a valid root filesystem.

!!! success "Operator principle"
    Treat the boot loader as production control-plane configuration. Inspect first, change one thing at a time, and keep a known-good boot entry available.

A boot loader is the handoff point between platform firmware and the operating system. BIOS or UEFI firmware finds a bootable device or EFI application; the boot loader then presents boot entries, loads a kernel and initramfs into memory, passes kernel command-line arguments, and transfers control to the kernel.

On most Linux distributions, that boot loader is GRUB 2. Other environments may use systemd-boot, a cloud provider's boot chain, or a vendor recovery loader, but the operational questions stay the same:

- Did firmware choose the expected boot device or EFI entry?
- Did the boot loader find the expected kernel and initramfs?
- Did the selected boot entry pass the expected root device and kernel options?
- Is there a previous known-good kernel entry to fall back to?

## Evidence to collect first

Start with read-only checks. These commands do not rewrite boot sectors, EFI variables, or generated boot menus.

```bash
# Show whether the running system booted through UEFI firmware.
test -d /sys/firmware/efi && echo "UEFI boot" || echo "Legacy BIOS boot"

# Show the kernel and command line used for this boot.
uname -r
cat /proc/cmdline

# List installed kernel and initramfs images.
ls -lh /boot

# On UEFI systems, inspect firmware boot entries if efibootmgr is installed.
sudo efibootmgr -v
```

When a machine still boots, capture this evidence before maintenance. It gives you a baseline if a later reboot fails. On cloud systems, also record the provider image, attached boot volume, console output location, and snapshot or backup identifier.

## What boot loader entries control

A Linux boot entry usually points to three things:

- **Kernel image:** the `vmlinuz-*` file to load.
- **Initial RAM filesystem:** the `initrd.img-*` or `initramfs-*` file with early boot drivers and userspace.
- **Kernel command line:** arguments such as `root=`, `ro`, `quiet`, `rescue.target`, or console settings.

Small differences matter. A typo in `root=`, a missing storage driver in the initramfs, or a stale menu entry after a disk rename can make a healthy installation look broken. This is why operators compare the boot menu, `/boot` contents, and `/proc/cmdline` instead of guessing.

## Safe change boundaries

Prefer distribution tools over hand-editing generated boot files. For GRUB-based systems, `/boot/grub/grub.cfg` or `/boot/grub2/grub.cfg` is usually generated output. Persistent changes typically belong in `/etc/default/grub` or files under `/etc/grub.d/`, followed by the distro-specific command that regenerates the menu.

Before changing boot loader configuration on a real system:

1. Confirm console or out-of-band access. SSH may not come back after a bad boot change.
2. Confirm a rollback path: VM snapshot, rescue ISO, serial console, previous kernel entry, or provider recovery mode.
3. Save current evidence: boot mode, boot entries, `/boot` listing, current kernel, and `/proc/cmdline`.
4. Change one setting at a time and keep the previous kernel available.
5. Reboot during a maintenance window if the host matters to other people.

!!! warning "Be careful with boot repair commands"
    Commands such as `grub-install`, `update-grub`, `grub2-mkconfig`, and `efibootmgr --create` can change how the system starts. Practice them on a disposable VM first, and do not run them on a remote production host unless you have console access and a tested recovery path.

## Hands-on practice

Run this on a disposable VM or lab machine.

1. Record the boot mode:
   ```bash
   test -d /sys/firmware/efi && echo "UEFI boot" || echo "Legacy BIOS boot"
   ```
2. Record the current kernel and command line:
   ```bash
   uname -r
   cat /proc/cmdline
   ```
3. List boot assets:
   ```bash
   ls -lh /boot
   ```
4. If the VM uses GRUB, identify where persistent configuration lives:
   ```bash
   ls -l /etc/default/grub /etc/grub.d 2>/dev/null
   ```
5. Write a short handoff note with the boot mode, current kernel, root argument from `/proc/cmdline`, and one recovery option you would use if the next boot failed.
