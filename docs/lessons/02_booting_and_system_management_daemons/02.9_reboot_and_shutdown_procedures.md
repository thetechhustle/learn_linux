### Restarting and Shutting Down Systems in Linux

Restarting or shutting down a Linux system is simple on a lab machine and risky
on a shared or remote host. A reboot can drop user sessions, interrupt jobs,
break active network connections, delay incident recovery, or strand you if the
machine does not come back cleanly.

For operators, the skill is not just knowing `reboot`. It is knowing when a
restart is justified, what evidence to collect first, how to warn users, how to
schedule or cancel the action, and how to verify the system after it returns.

!!! abstract "What you will learn"
    - Choose between reboot, poweroff, halt, and scheduled shutdown actions.
    - Inspect system state before restarting a Linux host.
    - Warn logged-in users and cancel a pending shutdown when needed.
    - Build a safe reboot handoff for production or remote systems.

!!! warning "Production safety"
    Do not reboot a production host just because a command suggests it. Confirm
    ownership, user impact, maintenance timing, console or cloud access, and a
    rollback plan. If the system is remote, make sure someone can recover it if
    networking or boot fails.

## Know the common commands

These commands request different system transitions:

```bash
sudo reboot
sudo shutdown -r now
sudo shutdown -h now
sudo poweroff
sudo halt
```

Common meanings:

- `reboot` restarts the system.
- `shutdown -r` schedules or starts a restart.
- `shutdown -h` brings the system down and halts or powers it off depending on
  platform behavior.
- `poweroff` powers off the system when supported.
- `halt` stops the system but may not remove power on all systems.

On modern systemd-based systems, these commands usually route through systemd.
You may also see:

```bash
sudo systemctl reboot
sudo systemctl poweroff
```

## Inspect before you restart

Use read-only checks before rebooting a host:

```bash
who
uptime
systemctl --failed
systemctl list-jobs
df -h
findmnt /
journalctl -p warning..alert -b --since "30 minutes ago"
```

Why these matter:

- `who` shows active logged-in users.
- `uptime` shows load and how long the system has been running.
- `systemctl --failed` shows failed units that may explain the issue.
- `systemctl list-jobs` shows pending systemd work.
- `df -h` can catch full filesystems before reboot makes recovery harder.
- `findmnt /` confirms the root filesystem source.
- `journalctl` gives recent warnings from this boot.

## Schedule and cancel safely

To schedule a reboot in 10 minutes with a warning:

```bash
sudo shutdown -r +10 "Maintenance reboot in 10 minutes. Please save work."
```

To schedule a poweroff at a specific time:

```bash
sudo shutdown -h 23:30 "System will power off at 23:30 for maintenance."
```

To cancel a pending shutdown:

```bash
sudo shutdown -c
```

If you schedule a restart, record who approved it, when it is expected to happen,
and who will verify the system after boot.

## Reboot evidence after the system returns

After the host comes back, confirm that the reboot happened and that core
services recovered:

```bash
uptime
who -b
journalctl -b -p warning..alert
systemctl --failed
systemctl is-system-running
```

Useful interpretations:

- `who -b` reports the last system boot time.
- `journalctl -b` reads logs from the current boot.
- `systemctl is-system-running` reports states such as `running`, `degraded`,
  `starting`, or `maintenance`.
- `degraded` means the system booted but at least one unit failed.

## When not to reboot first

Avoid rebooting as the first move when:

- you have not collected logs from the current failure state
- there are active user sessions or running jobs with unknown ownership
- the host is remote and has no console, IPMI, cloud console, or recovery path
- disk, network, bootloader, or filesystem health is uncertain
- the issue may be isolated to one service that can be inspected or restarted
  safely

Rebooting can clear useful evidence. It can also turn a service issue into a
boot issue.

## Incident handoff example

```text
Host: app-02
Reason for reboot: kernel update requires restart
Approval: Change CHG-1042, owner Maya
User impact: internal API unavailable for about 5 minutes
Pre-checks: no active SSH users, no failed units, / has 42% free
Recovery path: cloud serial console available, previous kernel present
Scheduled command: shutdown -r +10 "Maintenance reboot in 10 minutes"
Post-checks required: systemctl --failed, app health endpoint, journal warnings
Rollback: boot previous kernel from console if new kernel fails
```

## Practice: safe reboot plan

Use a disposable VM or lab system.

1. Run the pre-checks:

   ```bash
   who
   uptime
   systemctl --failed
   df -h
   ```

2. Schedule a reboot far enough in the future to cancel it:

   ```bash
   sudo shutdown -r +15 "Lab reboot test in 15 minutes"
   ```

3. Cancel it:

   ```bash
   sudo shutdown -c
   ```

4. Write a short handoff:

   ```text
   Host:
   Reason:
   Pre-check evidence:
   User impact:
   Scheduled time:
   Cancel command:
   Post-check plan:
   Recovery path:
   ```
