### 02.8 FreeBSD Init and Startup Scripts

!!! abstract "What you will learn"
    - Explain how FreeBSD moves from `/sbin/init` into the `rc` startup system.
    - Inspect enabled services, startup order, and service configuration without changing the host.
    - Compare FreeBSD `rc` operations with the Linux systemd workflow you are more likely to use day to day.

!!! example "Field story"
    A FreeBSD appliance boots, networking comes up, but the application service never starts. On a Linux host you might reach for `systemctl status app.service`; on FreeBSD you need to inspect `rc.conf`, the service script, and the startup order. The operational question is the same: was the service enabled, did its dependencies run, and what evidence proves the first failure?

!!! success "Operator principle"
    In FreeBSD, `rc.conf` expresses startup intent and `rc.d` scripts execute that intent. Inspect both before restarting or enabling services.

## Hands-on practice

Run these on a disposable FreeBSD VM or lab host. These commands are read-only unless explicitly marked otherwise.

1. Confirm you are on FreeBSD and identify the kernel:

    ```sh
    freebsd-version
    uname -a
    ```

2. List services that are enabled for startup:

    ```sh
    service -e
    ```

    Treat this like the FreeBSD equivalent of asking, "What services are intended to start automatically?"

3. Inspect `rc.conf` values:

    ```sh
    sysrc -a
    sed -n '1,180p' /etc/rc.conf
    ```

    `sysrc` is the safer interface for reading and updating `rc.conf` settings. For this lesson, only read values.

4. Inspect a service script before touching the service:

    ```sh
    sed -n '1,200p' /etc/rc.d/sshd
    service sshd status
    ```

    Look for dependency metadata near the top of the script, especially `PROVIDE`, `REQUIRE`, `BEFORE`, and `KEYWORD` lines.

5. Review startup order:

    ```sh
    rcorder /etc/rc.d/* /usr/local/etc/rc.d/* 2>/dev/null | sed -n '1,80p'
    ```

    This helps explain why one service starts before another.

6. Capture recent startup evidence:

    ```sh
    dmesg -a | tail -80
    tail -80 /var/log/messages
    ```

7. Write a handoff note:

    ```text
    Service investigated:
    Enabled in rc.conf:
    Script inspected:
    Dependency/start-order evidence:
    Log evidence:
    Next safe action:
    ```

## How FreeBSD startup differs from systemd

Linux distributions that use systemd describe services with unit files and manage boot state with targets. FreeBSD uses a smaller, script-oriented startup model:

- `/sbin/init` is the first userland process.
- `/etc/rc` coordinates startup.
- `/etc/defaults/rc.conf` documents default values.
- `/etc/rc.conf` and `/etc/rc.conf.local` hold local startup settings.
- `/etc/rc.d/` contains base-system startup scripts.
- `/usr/local/etc/rc.d/` contains startup scripts installed by packages and ports.

The difference matters during incidents. A Linux service may be disabled because a unit is not enabled. A FreeBSD service may be skipped because the matching `*_enable="YES"` value is absent, misspelled, or placed in the wrong file.

## Service control commands

Use `service` as the normal operator interface:

```sh
service sshd status
service sshd onestatus
service sshd rcvar
```

`status` uses the service's normal enabled state. `onestatus` asks for status even when the service is not enabled. `rcvar` shows the variable that controls whether the service starts automatically.

Do not start or stop production services just to learn. In a lab, practice with a non-critical service and record the before and after state.

## Safe change boundaries

Changing startup state can affect remote access, networking, storage, and security. Keep these boundaries:

- Do not edit `/etc/defaults/rc.conf`; it is the system default reference.
- Prefer `sysrc name=value` over hand-editing `/etc/rc.conf` when making persistent changes.
- Before enabling or disabling a service, capture `service <name> rcvar`, `service <name> status`, and the relevant `sysrc` output.
- Treat network, firewall, SSH, storage, identity, and database services as high risk.
- Make one change at a time and keep a rollback command in the handoff.

## Example incident path

A web service is missing after reboot.

1. Check whether the service is enabled:

    ```sh
    service nginx rcvar
    sysrc nginx_enable
    ```

2. Check whether it is running:

    ```sh
    service nginx onestatus
    ```

3. Inspect startup dependencies:

    ```sh
    sed -n '1,80p' /usr/local/etc/rc.d/nginx
    rcorder /etc/rc.d/* /usr/local/etc/rc.d/* 2>/dev/null | grep -n nginx
    ```

4. Inspect logs before restarting:

    ```sh
    tail -120 /var/log/messages
    ```
