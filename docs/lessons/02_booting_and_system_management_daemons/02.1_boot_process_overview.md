## Boot Process Overview

!!! abstract "What you will learn"
    - Describe the Linux boot path from firmware to a usable login or workload.
    - Identify which boot stage probably failed from the evidence available.
    - Collect read-only boot evidence before changing bootloader, kernel, or service settings.
    - Hand off a boot incident with a clear timeline and a safe next step.

!!! example "Field story"
    A production VM fails after a kernel update. The right first move is not to edit GRUB from memory. First decide whether the failure is firmware, boot loader, kernel, initramfs, filesystem, or service-manager related. Then make one reversible change and prove whether it helped.

!!! success "Operator principle"
    Follow the handoffs. Every boot failure belongs to a stage, and every stage leaves different evidence.

## The Boot Chain

Linux boot is a handoff sequence:

```text
power on
  -> firmware
  -> boot loader
  -> kernel
  -> initramfs
  -> PID 1
  -> targets and services
  -> login prompt, desktop, or workload
```

When a host does not boot, ask which handoff failed instead of treating the whole system as mysterious.

## Stage 1: Firmware

Firmware is BIOS or UEFI. It initializes hardware, chooses a boot device, and hands control to the boot loader.

Likely signs of a firmware-stage problem:

- no OS boot menu appears
- firmware setup reports missing disks
- the boot order changed
- PXE/network boot starts unexpectedly
- virtual machine console shows firmware-level errors

Read-only evidence to collect:

```bash
sudo efibootmgr -v
lsblk -f
```

`efibootmgr` may not exist or may not work on BIOS-only systems. That is useful information too.

## Stage 2: Boot Loader

The boot loader, usually GRUB on Linux, chooses the kernel and passes kernel arguments. Boot loader failures often happen after firmware but before the kernel has fully started.

Likely signs of a boot-loader problem:

- GRUB menu appears but entries fail
- the wrong kernel boots
- the system cannot find a root device
- a recent edit changed `/etc/default/grub` or files under `/boot`

Read-only evidence to collect:

```bash
ls -lah /boot
grep -v '^#' /etc/default/grub
findmnt /boot /boot/efi
```

Do not regenerate GRUB or edit boot entries on a production host until you know how to roll back.

## Stage 3: Kernel and Initramfs

The kernel initializes core hardware and mounts the root filesystem. The initramfs supplies early userspace tools and drivers needed before the real root filesystem is available.

Likely signs of a kernel or initramfs problem:

- kernel panic output appears on the console
- the system drops into an emergency shell before normal services start
- storage, encryption, or root filesystem devices are missing
- the last successful boot used a different kernel

Read-only evidence to collect after recovery or from a working boot:

```bash
uname -r
lsblk -f
journalctl -k -b
journalctl -b -p warning
```

If the current boot is broken, collect console screenshots or provider serial-console logs before rebooting again.

## Stage 4: PID 1 and Service Startup

Modern Linux systems usually start `systemd` as PID 1. At this point, the kernel is alive and the problem is often about targets, units, mounts, networking, or application services.

Read-only evidence to collect:

```bash
systemctl status
systemctl list-units --failed
systemctl get-default
journalctl -b -p warning
```

For one service:

```bash
systemctl status ssh.service
journalctl -b -u ssh.service
```

Replace `ssh.service` with the unit that matters on your system.

## A Safe Incident Handoff

A useful boot handoff is short and evidence-based:

```text
Host: app-01
Last known change: kernel update to 6.x at 02:10 UTC
Observed failure: boots to emergency mode after initramfs
Evidence: console shows root filesystem timeout; lsblk from rescue mode does not show expected disk UUID
Tried: booted previous kernel from GRUB; host reached multi-user.target
Avoided: did not regenerate GRUB or run filesystem repair yet
Next step: compare disk UUIDs in /etc/fstab and boot logs before making persistent changes
```
