# 20.15 Recommended Reading

Storage is one of the places where operators need both command fluency and
judgment. You can learn the commands quickly. The harder part is knowing which
layer you are changing, what failure mode you are protecting against, and how
you will prove the change worked.

Use this reading path to turn the rest of the chapter into a durable operating
model.

!!! abstract "What you will learn"
    - Build a staged reading plan for Linux storage operations.
    - Separate block-device, filesystem, volume-management, and backup topics.
    - Choose references for incidents, design work, and deeper study.
    - Practice storage concepts with low-risk labs before touching real data.

## Start with the Block Layer

Before studying advanced filesystems, get comfortable with how Linux sees
storage devices.

Read about:

- block devices
- device names and persistent identifiers
- partitions and partition tables
- udev and `/dev/disk/by-id/`
- kernel logs for storage events
- SMART and device-health reporting

Useful commands to practice:

```bash
lsblk -f
blkid
findmnt
udevadm info --query=all --name=/dev/sda
journalctl -k --since "1 hour ago"
```

Good references:

- `man lsblk`
- `man blkid`
- `man findmnt`
- `man udev`
- your distribution's storage administration guide

The goal is simple: know what device you are about to modify before you modify
it.

## Learn Filesystems by Operations

Do not learn filesystems only as feature lists. Learn the lifecycle:

1. inspect existing state
2. create a filesystem
3. mount it temporarily
4. mount it persistently
5. grow it
6. check capacity and inode pressure
7. repair it safely
8. restore data when repair is not enough

Focus first on ext4 and XFS:

- ext4 for broad compatibility and conservative general-purpose use
- XFS for large server filesystems and online growth workflows

Useful references:

- `man mkfs.ext4`
- `man tune2fs`
- `man e2fsck`
- `man xfs_info`
- `man xfs_growfs`
- `man xfs_repair`
- the kernel documentation for ext4 and XFS

Practice in a VM or loopback lab. Do not learn `mkfs`, `resize2fs`, or
`xfs_repair` for the first time on a production server.

## Study LVM and RAID as Layering Tools

LVM and RAID are not replacements for filesystems. They change the block layer
under the filesystem.

Learn LVM concepts:

- physical volumes
- volume groups
- logical volumes
- extents
- snapshots
- `pvmove`
- online growth workflows

Learn RAID concepts:

- mirroring
- striping
- parity
- rebuilds
- degraded operation
- write holes and controller behavior
- why RAID is not backup

Useful references:

- `man lvm`
- `man pvcreate`
- `man vgcreate`
- `man lvcreate`
- `man lvextend`
- `man pvmove`
- `man mdadm`
- the Linux RAID wiki
- your storage-controller documentation

When incidents happen, draw the stack:

```text
disk -> partition -> RAID -> LVM -> filesystem -> mountpoint -> application
```

That picture prevents many wrong-layer mistakes.

## Read ZFS and Btrfs Documentation Carefully

ZFS and Btrfs are powerful because they integrate features that traditional
Linux stacks often spread across several layers.

For ZFS, study:

- pools
- vdevs
- mirrors and RAIDZ
- datasets
- properties
- snapshots
- send and receive
- scrubs
- resilvering
- capacity planning

Useful references:

- OpenZFS documentation
- `man zpool`
- `man zfs`
- distribution-specific OpenZFS packaging notes

For Btrfs, study:

- subvolumes
- snapshots
- compression
- scrub
- balance
- send and receive
- profiles for data and metadata
- RAID cautions
- space accounting

Useful references:

- Btrfs documentation at `btrfs.readthedocs.io`
- `man btrfs`
- `man mkfs.btrfs`
- your distribution's Btrfs notes

Do not transfer assumptions blindly between ZFS and Btrfs. Similar words can
hide different operational behavior.

## Keep Backup Material Close

Every storage operator needs a backup reading stack.

Study:

- restore testing
- recovery point objective
- recovery time objective
- 3-2-1 backup design
- snapshots versus backups
- offsite copies
- immutability
- ransomware recovery
- database-consistent backups
- backup monitoring

Useful references:

- `man rsync`
- `man tar`
- `man borg`
- `man restic`
- database backup documentation for the systems you operate
- vendor documentation for object storage lifecycle and retention policies

The most important backup question is not "Did the job run?" It is "Can we
restore the service inside the time the business expects?"

## Add Performance Reading After Safety

Performance work should come after data safety. Once you understand the layers,
study:

- IOPS, throughput, latency, and queue depth
- random versus sequential I/O
- filesystem mount options
- scheduler behavior
- cache effects
- database storage patterns
- cloud volume performance limits

Useful commands:

```bash
iostat -xz 1
lsblk -D
fio --name=readtest --filename=/tmp/testfile --size=1G --rw=read --bs=1M
```

Useful references:

- `man iostat`
- `man fio`
- Brendan Gregg's Linux performance material
- cloud-provider storage performance documentation

Never benchmark production storage casually. Benchmarks can be destructive,
misleading, or disruptive if they are not designed carefully.

## Suggested Lab Sequence

Work through this sequence on a disposable VM:

1. Add a virtual disk and identify it with `lsblk -f`.
2. Partition it with GPT.
3. Create an ext4 filesystem and mount it by UUID.
4. Repeat with XFS and compare growth behavior.
5. Create an LVM volume, format it, mount it, and grow it.
6. Create an mdraid mirror with loop devices.
7. Simulate a failed member and inspect degraded state.
8. Create Btrfs subvolumes and read-only snapshots.
9. Create a file-backed ZFS lab pool and run a scrub.
10. Back up a test directory and restore it to a clean path.

Write down:

- commands used
- expected output
- actual output
- what changed
- how you would undo or recover

Good storage operators keep notes because the details matter.

## Incident References to Bookmark

Keep these close:

- your distribution's rescue-mode documentation
- cloud-provider volume snapshot and restore documentation
- RAID-controller documentation
- disk replacement procedure for your hardware
- filesystem repair manuals for ext4, XFS, Btrfs, and ZFS
- backup restore runbooks
- monitoring dashboards for disk health, capacity, and I/O latency

During an incident, your first job is not bravery. It is evidence, calm, and
the smallest safe next move.

## Check Your Understanding

- Which references help you identify a disk before formatting it?
- Which layer owns growth in an LVM-backed filesystem?
- Why should backup reading include restore testing?
- Why are ZFS and Btrfs not interchangeable even when they share features?
- What lab would you run before changing storage on a production database host?

## Operational Takeaway

Storage reading should make you safer, not just more informed. Learn the Linux
block layer, then filesystems, then LVM and RAID, then advanced filesystems, then
backups and performance. Practice on disposable systems until the evidence trail
is automatic: identify the device, understand the layer, make the smallest safe
change, verify the result, and preserve a rollback path.
