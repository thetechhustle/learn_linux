# 20.13 Btrfs: "ZFS Lite" for Linux

Btrfs is a modern Linux filesystem with copy-on-write behavior, snapshots,
subvolumes, checksums, compression, online resizing, and multi-device support.
It is sometimes described as "ZFS Lite" because it brings several ZFS-like ideas
into a Linux-native filesystem.

That nickname is useful only as a starting point. Btrfs is not ZFS, and it is
not just ext4 with snapshots. It has its own vocabulary, strengths, and sharp
edges. Operate it on its own terms.

!!! abstract "What you will learn"
    - Explain what Btrfs provides beyond traditional filesystems.
    - Inspect Btrfs filesystems, subvolumes, usage, and device health.
    - Use snapshots and subvolumes safely at an operator level.
    - Understand compression, scrub, balance, and send/receive workflows.
    - Recognize Btrfs RAID and space-accounting cautions.

!!! warning "Btrfs commands can change live storage"
    `mkfs.btrfs`, `btrfs device add`, `btrfs balance`, `btrfs replace`, and
    snapshot deletion can affect real data. Practice on disposable storage
    before using these commands on production systems.

## Why Btrfs Exists

Traditional filesystems such as ext4 and XFS are reliable, but they usually
depend on other layers for snapshots, volume management, and replication. Btrfs
integrates more of those capabilities into the filesystem itself.

Key features:

- copy-on-write updates
- checksums for data and metadata
- snapshots
- writable clones
- subvolumes
- transparent compression
- online grow and shrink
- multi-device filesystems
- send/receive replication
- scrub and balance operations

Btrfs is commonly used on Linux desktops, workstations, test systems, container
hosts, and some servers where snapshots and subvolumes are useful.

## Btrfs Vocabulary

| Term | Meaning |
| --- | --- |
| Filesystem | A Btrfs storage instance, possibly spanning one or more devices |
| Subvolume | A independently managed filesystem tree inside Btrfs |
| Snapshot | A point-in-time copy of a subvolume |
| Profile | How Btrfs stores data or metadata, such as `single`, `dup`, `raid1`, or `raid10` |
| Scrub | A checksum verification pass that can repair data when redundancy exists |
| Balance | A rewrite operation that can change allocation or profiles |

Subvolumes are one of the first concepts to understand. A Btrfs filesystem can
contain multiple subvolumes, each with independent snapshots and mount behavior.
They are not normal directories, even though they look like directories in many
commands.

## Inspect Btrfs

Show block devices and filesystem types:

```bash
lsblk -f
```

Show mounted Btrfs filesystems:

```bash
findmnt -t btrfs
```

Show Btrfs filesystem usage:

```bash
sudo btrfs filesystem usage /
```

Show Btrfs device stats:

```bash
sudo btrfs device stats /
```

List subvolumes:

```bash
sudo btrfs subvolume list /
```

Show mount options:

```bash
findmnt -no OPTIONS /
```

These commands are safe starting points. If usage or device stats are confusing,
pause before running repair, balance, or device-removal commands.

## Create a Lab Filesystem

Use a disposable loop device or scratch disk. This example uses a file-backed
loop device so you do not need a spare disk.

Create a backing file:

```bash
truncate -s 2G /tmp/btrfs-lab.img
```

Attach it:

```bash
sudo losetup --find --show /tmp/btrfs-lab.img
```

Assume the command returns `/dev/loop10`. Use your actual device name.

Create a Btrfs filesystem:

```bash
sudo mkfs.btrfs -L btrfslab /dev/loop10
```

Mount it:

```bash
sudo mkdir -p /mnt/btrfs-lab
sudo mount /dev/loop10 /mnt/btrfs-lab
```

Verify:

```bash
findmnt /mnt/btrfs-lab
sudo btrfs filesystem usage /mnt/btrfs-lab
```

Clean up when finished:

```bash
sudo umount /mnt/btrfs-lab
sudo losetup -d /dev/loop10
rm /tmp/btrfs-lab.img
```

## Subvolumes

Create two subvolumes:

```bash
sudo btrfs subvolume create /mnt/btrfs-lab/@
sudo btrfs subvolume create /mnt/btrfs-lab/@home
```

List them:

```bash
sudo btrfs subvolume list /mnt/btrfs-lab
```

A common Linux desktop layout uses separate subvolumes for `/`, `/home`, logs,
package caches, or container data. That lets you snapshot or restore one tree
without treating the entire filesystem as one unit.

Mount a specific subvolume:

```bash
sudo mount -o subvol=@ /dev/loop10 /mnt/btrfs-lab
```

Persistent `/etc/fstab` entries often include `subvol=` or `subvolid=`.

## Snapshots

Btrfs snapshots are cheap point-in-time copies of subvolumes. They are useful
before upgrades, config changes, package operations, and risky deployments.

Create a read-only snapshot:

```bash
sudo btrfs subvolume snapshot -r /mnt/btrfs-lab/@ /mnt/btrfs-lab/@-before-upgrade
```

Create a writable snapshot:

```bash
sudo btrfs subvolume snapshot /mnt/btrfs-lab/@ /mnt/btrfs-lab/@-test-copy
```

Delete a snapshot:

```bash
sudo btrfs subvolume delete /mnt/btrfs-lab/@-test-copy
```

Snapshots are not backups by themselves. They live on the same filesystem. If
the underlying filesystem is destroyed, local snapshots go with it.

## Send and Receive

Btrfs can stream read-only snapshots to another filesystem.

Create a read-only snapshot:

```bash
sudo btrfs subvolume snapshot -r /mnt/btrfs-lab/@ /mnt/btrfs-lab/@-daily
```

Send it to another mounted Btrfs filesystem:

```bash
sudo btrfs send /mnt/btrfs-lab/@-daily | sudo btrfs receive /mnt/backup-btrfs
```

Incremental sends require a parent snapshot:

```bash
sudo btrfs send -p /mnt/btrfs-lab/@-daily /mnt/btrfs-lab/@-next | sudo btrfs receive /mnt/backup-btrfs
```

Replication is only a backup if the target is independent and restore-tested.

## Compression

Btrfs supports transparent compression. `zstd` is a common modern choice.

Mount with compression:

```bash
sudo mount -o compress=zstd /dev/loop10 /mnt/btrfs-lab
```

Example `/etc/fstab` option:

```text
UUID=11111111-2222-3333-4444-555555555555  /  btrfs  defaults,compress=zstd,subvol=@  0  0
```

Compression can improve both space usage and performance for compressible data.
It will not help much with already-compressed media, encrypted archives, or many
database files. Test with your workload.

## Scrub

A scrub reads data and metadata, verifies checksums, and repairs errors when a
redundant copy is available.

Start a scrub:

```bash
sudo btrfs scrub start /mnt/btrfs-lab
```

Check scrub status:

```bash
sudo btrfs scrub status /mnt/btrfs-lab
```

Cancel a scrub:

```bash
sudo btrfs scrub cancel /mnt/btrfs-lab
```

Scrubs are useful maintenance. They are not a substitute for backups.

## Balance

A balance rewrites chunks. It can rebalance space, convert profiles, or recover
from awkward allocation states.

Show usage first:

```bash
sudo btrfs filesystem usage /mnt/btrfs-lab
```

Run a limited data balance:

```bash
sudo btrfs balance start -dusage=50 /mnt/btrfs-lab
```

Check progress:

```bash
sudo btrfs balance status /mnt/btrfs-lab
```

Do not run full balances casually on large filesystems. They can be slow and
I/O-heavy. Use targeted filters and understand why you are balancing.

## Multi-Device and RAID Cautions

Btrfs can span multiple devices and use profiles such as `raid1`, `raid10`, and
others. This is useful, but the operational rules differ from mdraid, LVM, and
ZFS.

Important cautions:

- Know whether you are setting the data profile, metadata profile, or both.
- Check current profiles with `btrfs filesystem usage`.
- Device loss behavior depends on profiles and metadata redundancy.
- Btrfs RAID5/RAID6 has historically had serious caveats; treat it as a design
  decision requiring current documentation and careful testing.
- A single-disk Btrfs filesystem can use duplicate metadata, but that does not
  protect against full disk failure.

Example lab command for a mirrored two-device filesystem:

```bash
sudo mkfs.btrfs -m raid1 -d raid1 /dev/loop10 /dev/loop11
```

Inspect profiles:

```bash
sudo btrfs filesystem usage /mnt/btrfs-lab
```

Use stable device names from `/dev/disk/by-id/` for real systems.

## Online Resize

Btrfs can grow and shrink online.

Grow to the maximum available size:

```bash
sudo btrfs filesystem resize max /mnt/btrfs-lab
```

Shrink by 1 GiB:

```bash
sudo btrfs filesystem resize -1G /mnt/btrfs-lab
```

Shrinking any filesystem has risk. Confirm backups, free space, and the lower
storage layer before changing size.

## When Btrfs Is a Good Fit

Btrfs is worth considering when you need:

- native Linux snapshots
- easy rollback workflows
- compression
- subvolume-based layouts
- send/receive replication
- online grow and shrink
- checksums without adopting ZFS

It is especially common for workstation and desktop systems that want snapshot
rollback around package updates.

## When to Prefer Something Else

Consider ext4 or XFS when:

- you need the simplest possible server filesystem
- your team already has strong ext4/XFS operational experience
- snapshots are already handled by LVM, storage arrays, cloud disks, or backups
- you want fewer filesystem-specific concepts

Consider ZFS when:

- end-to-end storage-pool design and strong replication are central
- you need ZFS properties, mature pool tooling, and established operational
  patterns
- licensing, packaging, and kernel support are acceptable for your environment

The filesystem is part of the operating model. Pick the one your team can
operate during an outage, not only the one with the most features.

## Troubleshooting Checklist

For Btrfs incidents, collect evidence before making changes:

```bash
findmnt -t btrfs
sudo btrfs filesystem usage /
sudo btrfs device stats /
sudo btrfs subvolume list /
sudo btrfs scrub status /
journalctl -k --since "1 hour ago"
```

Ask:

1. Which mountpoint is affected?
2. Which subvolume is mounted there?
3. Is the problem capacity, metadata space, device errors, or corruption?
4. Are snapshots consuming space?
5. Are device stats showing errors?
6. Is a scrub or balance running?
7. Is there an independent backup?

## Operational Takeaway

Btrfs is a powerful Linux-native filesystem for snapshots, subvolumes,
compression, checksums, and flexible layouts. It rewards operators who learn
its vocabulary and inspect before acting. Use it when its integrated features
match the job, and keep the same discipline you would use with any storage
system: backups, restore tests, monitoring, and clear change plans.
