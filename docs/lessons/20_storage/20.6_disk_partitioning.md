## 20.6 Disk Partitioning: Organizing Your Linux Space

Partitions divide a block device into regions that the operating system can
use for boot loaders, filesystems, swap, LVM physical volumes, RAID members,
or application data. Partitioning is also one of the easiest places to cause
permanent data loss. A good operator treats it as a change-control task, not a
typing exercise.

!!! abstract "What you will learn"
    - Explain why Linux systems use partition tables.
    - Distinguish GPT from legacy MBR partitioning.
    - Inspect disks and partitions before changing them.
    - Create a basic partition with modern Linux tools.
    - Verify that the kernel and userspace agree about the new layout.

!!! warning "Partitioning is destructive when aimed at the wrong disk"
    Do not run partitioning commands against a production disk just to follow a
    lesson. Practice with a disposable virtual disk, cloud volume, USB drive, or
    loopback file. Always confirm the target device by size, model, serial, and
    current mount state before writing a partition table.

## What a Partition Table Does

A disk is a stream of addressable blocks. A partition table records where
usable regions start and end. Linux then exposes those regions as child block
devices:

```text
/dev/sdb       whole disk
/dev/sdb1      first partition
/dev/sdb2      second partition
```

NVMe devices use a slightly different naming pattern:

```text
/dev/nvme0n1      whole disk
/dev/nvme0n1p1    first partition
/dev/nvme0n1p2    second partition
```

Partitioning does not create a filesystem by itself. It only creates a place
where a filesystem, swap area, LVM physical volume, RAID member, or encrypted
container can live.

## GPT and MBR

Most new Linux systems should use GPT.

| Scheme | Practical use | Main limits |
| --- | --- | --- |
| GPT | Modern servers, UEFI systems, disks larger than 2 TiB | Requires tools and firmware that understand GPT, which is normal today |
| MBR / DOS | Legacy BIOS systems and old tooling | Four primary partitions, awkward extended partitions, practical 2 TiB disk limit |

RAID is not a partitioning scheme. RAID combines devices or partitions into a
redundant or striped array. You may place RAID metadata on partitions, but GPT
or MBR still describes the underlying layout.

## Inspect Before You Change

Start read-only. Identify every disk, partition, filesystem, and mountpoint:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,PARTTYPE,MOUNTPOINTS,MODEL,SERIAL
```

Check the current partition table:

```bash
sudo parted /dev/sdb print
```

Look for signatures that might indicate existing data:

```bash
sudo wipefs --no-act /dev/sdb
sudo blkid /dev/sdb /dev/sdb1 2>/dev/null
```

Check whether anything is mounted or in use:

```bash
findmnt --source /dev/sdb1
lsblk -o NAME,PATH,TYPE,MOUNTPOINTS /dev/sdb
```

If you cannot explain what is currently on the disk, stop. The next command
should not be a write command.

## Choose a Layout

The right layout depends on the job.

| Job | Common layout |
| --- | --- |
| Simple data disk | One GPT partition using the full disk |
| Boot disk on UEFI | EFI System Partition, root partition, optional swap or LVM |
| LVM-backed server disk | One partition marked for LVM, then logical volumes inside LVM |
| RAID member disk | One partition per RAID member, or whole-disk RAID when your standard allows it |
| Encrypted data disk | Partition first, then place LUKS on the partition |

Avoid making many partitions "just in case." Extra partitions create fixed
boundaries that may become future capacity problems. LVM, filesystems, and
directory permissions are often better tools for flexible separation.

## Create a GPT Data Partition

This example creates one partition on `/dev/sdb`. Replace `/dev/sdb` with the
actual lab disk you verified.

Create a GPT partition table:

```bash
sudo parted --script /dev/sdb mklabel gpt
```

Create one partition that uses the full disk:

```bash
sudo parted --script /dev/sdb mkpart primary 1MiB 100%
```

Name the partition:

```bash
sudo parted --script /dev/sdb name 1 data
```

Ask the kernel to re-read the partition table:

```bash
sudo partprobe /dev/sdb
```

Verify the result:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,PARTLABEL,MOUNTPOINTS /dev/sdb
sudo parted /dev/sdb print
```

At this point `/dev/sdb1` exists, but it is not yet formatted. The filesystem
step is separate:

```bash
sudo mkfs.ext4 -L data01 /dev/sdb1
```

## Set Partition Type Hints

GPT stores a partition type GUID. Linux usually works without perfect type
hints, but good hints help humans and automation understand intent.

For an LVM physical volume partition:

```bash
sudo parted --script /dev/sdb set 1 lvm on
```

For an EFI System Partition:

```bash
sudo parted --script /dev/sda set 1 esp on
```

Confirm the hint:

```bash
lsblk -o NAME,PATH,PARTTYPE,PARTTYPENAME,PARTLABEL /dev/sdb
```

Do not use a type flag as your only safety check. It is metadata, not proof
that the contents are correct.

## Grow a Partition

Expanding a cloud disk or virtual disk often leaves the partition smaller than
the underlying block device.

First confirm the disk size and partition size:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS /dev/sdb
```

Then grow partition 1 to the end of the disk:

```bash
sudo growpart /dev/sdb 1
```

Re-check the partition:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS /dev/sdb
```

After that, grow the layer inside the partition. The command depends on what is
inside:

```bash
sudo resize2fs /dev/sdb1        # ext4
sudo xfs_growfs /mount/point    # XFS, run against the mounted filesystem
sudo pvresize /dev/sdb1         # LVM physical volume
```

Partition growth and filesystem growth are separate operations. Verify both.

## Delete a Partition Safely

Deleting a partition removes the map to the data. It may not immediately erase
all blocks, but it is still destructive from an operations perspective.

Before deleting anything, record the current evidence:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS,UUID /dev/sdb
sudo parted /dev/sdb unit MiB print
sudo wipefs --no-act /dev/sdb1
```

Unmount and deactivate higher layers first:

```bash
sudo umount /mnt/data
sudo swapoff /dev/sdb1
```

Then remove the partition only after confirming the number:

```bash
sudo parted --script /dev/sdb rm 1
sudo partprobe /dev/sdb
```

For production changes, keep the before-and-after output with the ticket or
change record.

## Common Failure Modes

Wrong disk:
: `/dev/sdb` today may become `/dev/sdc` tomorrow. Prefer stable paths under
  `/dev/disk/by-id/` for scripts and change records.

Mounted partition:
: The kernel may refuse to re-read a changed table if a partition is mounted or
  in use. Unmount, deactivate swap, stop services, or reboot during a planned
  window.

Mixed layers:
: LVM, RAID, encryption, multipath, and filesystems can sit above partitions.
  Use `lsblk`, `dmsetup ls`, `pvs`, `mdadm --detail`, and `cryptsetup status`
  when the stack is not obvious.

Old signatures:
: A newly partitioned disk can still contain stale filesystem, RAID, or LVM
  signatures. Use `wipefs --no-act` to inspect first, then only wipe signatures
  you intentionally want gone.

Assuming partitioning improves performance:
: Partitions organize address ranges. They do not magically create more I/O
  capacity on a single physical device.

## Lab: Partition a Loopback Disk

This lab uses a file as a disposable disk.

Create a 512 MiB lab disk:

```bash
truncate -s 512M /tmp/partition-lab.img
sudo losetup --find --show /tmp/partition-lab.img
```

Assume the command prints `/dev/loop7`. Use your actual loop device:

```bash
sudo parted --script /dev/loop7 mklabel gpt
sudo parted --script /dev/loop7 mkpart primary 1MiB 256MiB
sudo parted --script /dev/loop7 mkpart primary 256MiB 100%
sudo partprobe /dev/loop7
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE /dev/loop7
```

Clean up:

```bash
sudo losetup -d /dev/loop7
rm /tmp/partition-lab.img
```

## Operator Takeaway

Partitioning is storage map management. The safe pattern is simple: inspect the
whole device, confirm the target, write the smallest necessary layout change,
ask the kernel to re-read it, and verify the resulting block devices before
moving on to filesystems, LVM, RAID, or encryption.
