### 20.11 Next-Generation Filesystems: ZFS and Btrfs

ZFS and Btrfs are often described as next-generation filesystems because they
combine filesystem duties with storage-management features that traditionally
lived in separate layers. They can verify data with checksums, create efficient
snapshots, manage multiple devices, and recover from some classes of corruption
when redundancy is configured correctly.

The operational question is not "Which one is coolest?" It is "Which risk am I
accepting, and can I prove the system is healthy before and after the change?"

    - Inspect existing ZFS and Btrfs systems with read-only commands.
    - Identify situations where these filesystems are a poor fit.

!!! example "Field story"
    A team wants point-in-time rollback for a file server that hosts shared
    project data. One admin suggests ZFS; another suggests Btrfs because it is
    already available in the distribution. Your job is to compare the options,
    test the workflow in a lab, and write down the evidence the production team
    should monitor.

!!! success "Operator principle"
    Advanced filesystems reduce some risks and introduce others. Treat them as
    storage platforms with their own design, monitoring, backup, and recovery
    requirements.

## What makes them next-generation?

Traditional Linux filesystems such as ext4 and XFS normally expect lower layers
to provide most storage composition. You might use partitions, LVM, hardware
RAID, software RAID, and the filesystem as separate pieces.

ZFS and Btrfs move more of that responsibility into the filesystem layer:

| Capability | Why operators care |
| --- | --- |
| Copy-on-write | New data is written before metadata points to it, which helps make snapshots cheap and avoids some partial-write failure modes. |
| Checksums | Data and metadata can be verified instead of blindly trusted. |
| Snapshots | You can capture a point-in-time view before upgrades, risky edits, or large data changes. |
| Compression | You may save disk space and I/O for compressible workloads. |
| Integrated device management | The filesystem may understand mirrors, pools, or multiple devices directly. |
| Scrub operations | The system can periodically read and verify stored data, finding latent errors before a restore emergency. |

These features are powerful, but they do not replace backups. Snapshots usually
live on the same storage system, so deletion, ransomware, controller mistakes,
and site-level failures can still remove the original and the snapshot together.

## ZFS at a glance

ZFS, provided on Linux by OpenZFS, combines a filesystem, volume manager, and
integrity engine. It organizes storage into pools, virtual devices, datasets,
volumes, and snapshots.

Common strengths:

- Strong data-integrity model with end-to-end checksums.
- Mature snapshot, clone, replication, and scrub workflows.
- Clear administrative tools: `zpool` for pool health and `zfs` for datasets.
- Useful dataset properties such as compression, quotas, reservations, and mountpoints.

Common cautions:

- OpenZFS is not shipped as part of the Linux kernel because of licensing
  compatibility concerns, so installation and kernel-module support vary by
  distribution.
- Pool layout choices matter. Some vdev mistakes are hard or impossible to
  reverse without rebuilding.
- ZFS wants enough memory for its ARC cache, especially on busy systems.
- Do not layer ZFS casually on top of hardware RAID without understanding how
  failure visibility, cache behavior, and replacement workflows change.

Read-only inspection commands:

```bash
zpool status
zpool list
zfs list
zfs get compression,quota,reservation,mountpoint
```

## Btrfs at a glance

Btrfs is a Linux-native copy-on-write filesystem with checksums, subvolumes,
snapshots, compression, and multi-device support. It is common on some Linux
distributions for desktop, workstation, and server use cases.

Common strengths:

- Integrated with the Linux kernel and standard Linux tooling.
- Subvolumes and snapshots are convenient for rollback-oriented workflows.
- Compression is easy to enable and can help general-purpose systems.
- Read-only inspection is available through `btrfs filesystem`, `btrfs device`,
  and `btrfs subvolume` commands.

Common cautions:

- Btrfs RAID1 and single-device workflows are widely used, but parity RAID
  modes have historically required extra caution. Check current distribution
  guidance before using Btrfs RAID5 or RAID6 for important data.
- Copy-on-write can be a poor match for some database and VM image workloads
  unless you understand nodatacow, preallocation, and application durability
  requirements.
- Free space reporting can surprise operators because allocated chunks,
  metadata, and usable file space are not the same thing.

Read-only inspection commands:

```bash
findmnt -t btrfs
btrfs filesystem show
btrfs filesystem usage /
btrfs subvolume list /
btrfs device stats /
```

## Choosing between ZFS, Btrfs, and traditional filesystems

Use ZFS or Btrfs when you have a clear reason to use their advanced features and
the team is ready to monitor and operate them. Use ext4 or XFS when simplicity,
distribution defaults, and predictable recovery procedures matter more.

Good reasons to consider ZFS or Btrfs:

- You need frequent local snapshots before upgrades or large changes.
- You need checksummed data with regular scrub evidence.
- You want per-dataset or per-subvolume policy such as compression and quotas.
- You can test restore, rollback, disk replacement, and monitoring workflows
  before production use.

Reasons to pause:

- The team has no runbook for pool or filesystem recovery.
- The storage is already abstracted by a SAN, hardware RAID controller, or cloud
  block service whose failure model is unclear.
- The workload is a write-heavy database or VM store and nobody has tested the
  copy-on-write impact.
- There is no off-host backup. Snapshots alone are not a backup strategy.

## Safe operating habits

Before changing an advanced filesystem, collect evidence:

```bash
lsblk -f
findmnt
df -hT
```

For ZFS systems, also collect:

```bash
zpool status
zpool list
zfs list -o name,used,avail,refer,mountpoint
```

For Btrfs systems, also collect:

```bash
btrfs filesystem show
btrfs filesystem usage /
btrfs device stats /
```

Before destructive operations, confirm:

- You are on the intended host.
- You have a current off-host backup or tested restore point.
- You know which command destroys data, changes redundancy, or rewrites layout.
- You have the exact rollback or rebuild procedure written down.
- Monitoring will report pool health, scrub results, disk errors, and free space.

## Hands-on practice

Run these on a disposable VM or lab machine. Do not run filesystem creation
commands on a host that contains data you care about.

1. Create two small virtual disks or loopback files for a lab.
2. Pick one path: ZFS if OpenZFS is available, or Btrfs if your distribution
   includes Btrfs tools.
3. Create a test filesystem or pool on the lab devices.
4. Add a test file and record the filesystem health output.
5. Create a snapshot.
6. Modify or delete the test file.
7. Use the snapshot to inspect or restore the earlier version.
8. Record which commands were read-only, which commands changed state, and which
   command would have been dangerous on a real disk.

Example Btrfs lab outline:

```bash
sudo mkfs.btrfs /dev/sdb
sudo mkdir -p /mnt/btrfs-lab
sudo mount /dev/sdb /mnt/btrfs-lab
sudo btrfs subvolume create /mnt/btrfs-lab/project
sudo btrfs subvolume snapshot /mnt/btrfs-lab/project /mnt/btrfs-lab/project-snap
btrfs filesystem usage /mnt/btrfs-lab
```

Example ZFS lab outline:

```bash
sudo zpool create labpool /dev/sdb
sudo zfs create labpool/project
sudo zfs snapshot labpool/project@before-change
zpool status labpool
zfs list -t filesystem,snapshot
```

!!! warning "Lab disk warning"
    `mkfs.btrfs` and `zpool create` initialize storage and can destroy existing
    data. In a lab, use newly attached disposable disks and confirm them with
    `lsblk -f` before running these commands.
