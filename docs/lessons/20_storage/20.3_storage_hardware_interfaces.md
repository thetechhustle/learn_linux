### 20.3 Storage Hardware Interfaces

Linux storage devices do not all arrive through the same path. A local
SATA disk, an NVMe SSD, a USB drive, a Fibre Channel LUN, an iSCSI target,
and a cloud block volume can all become block devices, but their
performance, failure signals, naming, and operational risks are different.

This lesson focuses on recognizing common storage interfaces and knowing
which Linux tools give useful evidence about each one.

!!! abstract "What you will learn"
    - Distinguish media types (HDD, SSD) from transports (SATA, SAS, NVMe, USB, Fibre Channel, iSCSI) and cloud block volumes.
    - Gather per-interface evidence with `lsblk`, `smartctl`, `nvme`, `lsscsi`, and `multipath`.
    - Choose persistent device identifiers so Linux devices map back to platform volumes and physical assets.

## Interface Versus Device Type

Do not mix up these terms:

- A hard disk drive (HDD) is spinning storage media.
- A solid-state drive (SSD) is flash-based storage media.
- SATA, SAS, USB, PCIe, Fibre Channel, and Ethernet are connection paths.
- NVMe, SCSI, ATA, and USB mass storage are command/protocol families.
- A cloud block volume is virtualized storage presented by a platform.

An SSD can be attached through SATA, SAS, USB, or PCIe/NVMe. A virtual disk
may appear as SCSI, VirtIO, NVMe, or another platform-specific device. The
operator's job is to identify both what Linux sees and what the platform
is actually providing.

## Start With the Block Device View

Begin with the same read-only view you use for most storage work:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,TYPE,ROTA,TRAN,FSTYPE,MOUNTPOINTS
```

Useful columns:

- `MODEL` and `SERIAL` help map a Linux device to physical or platform
  inventory.
- `ROTA` is `1` for rotational media and usually `0` for SSD-like media.
- `TRAN` often shows transport such as `sata`, `nvme`, `usb`, or `sas`.
- `TYPE` distinguishes disks, partitions, ROM devices, multipath devices,
  and logical devices.

For more detail:

```bash
udevadm info --query=property --name=/dev/sda
sudo lshw -class disk -class storage
```

Not every field is available on every system. Cloud and virtualized
environments often hide physical details.

## SATA

SATA is common for consumer and small-server disks. You will see it on
both HDDs and SSDs.

Inspect SATA-style devices with:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,ROTA,TRAN
sudo smartctl -a /dev/sda
```

Operational notes:

- SATA HDDs have moving parts and higher seek latency.
- SATA SSDs are faster than HDDs but limited by the SATA interface.
- SMART data can be useful, but vendor fields vary.
- Device names such as `/dev/sda` can change; use persistent identifiers
  for mounts and automation.

If `smartctl` reports that SMART support is unavailable, check whether the
disk is behind a USB bridge, hardware RAID controller, hypervisor, or
cloud abstraction.

## SAS

SAS is common in servers and storage arrays. It is related to SCSI command
handling and often appears in enterprise environments with HBAs, expanders,
or hardware RAID controllers.

Useful commands:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,TRAN
lsscsi
sudo lshw -class storage -class disk
```

Operational notes:

- A SAS controller may expose individual disks, RAID virtual disks, or
  both.
- Hardware RAID can hide physical disk state from ordinary Linux tools.
- Vendor utilities may be required for battery, cache, and physical drive
  health.
- In an incident, distinguish "Linux sees one logical disk" from "the
  chassis contains many drives."

## NVMe

NVMe uses PCIe and is common for modern high-performance SSDs. NVMe device
names look different from SATA/SCSI names:

- Disk: `/dev/nvme0n1`
- Partition: `/dev/nvme0n1p1`

Inspect NVMe devices with:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,ROTA,TRAN
nvme list
sudo nvme smart-log /dev/nvme0
```

Operational notes:

- NVMe devices can be very fast, so bottlenecks may move to CPU,
  filesystem, application, or network layers.
- Namespaces allow one controller to expose one or more block devices.
- Temperature, media errors, and percentage-used fields matter for
  health checks.
- Cloud platforms may present virtual NVMe devices whose serial numbers
  map to platform volume IDs.

Do not assume `/dev/nvme0n1` is safer or riskier than `/dev/sda`; both can
be production data.

## USB Storage

USB storage is useful for recovery media, removable backups, and lab work,
but it has different reliability assumptions than internal storage.

Inspect it with:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,TRAN,FSTYPE,MOUNTPOINTS
udevadm info --query=property --name=/dev/sdX
```

Operational notes:

- Cheap USB bridges may hide SMART data.
- Device disconnects can corrupt mounted filesystems.
- Performance varies widely by USB generation, hub, cable, and enclosure.
- Removable backup drives should be unmounted cleanly before removal.

USB is not a substitute for a durable server storage design, but it is
useful in controlled recovery and transfer workflows.

## Fibre Channel and iSCSI

Fibre Channel and iSCSI present remote storage as local-looking block
devices. They are common in SAN environments.

Useful commands depend on the stack, but start with:

```bash
lsblk
lsscsi
multipath -ll
findmnt
```

For iSCSI:

```bash
iscsiadm -m session
iscsiadm -m node
```

Operational notes:

- Multipath may combine several paths into one logical device.
- Path failure does not always mean storage failure.
- Network, zoning, target, initiator, and multipath configuration all
  affect availability.
- Filesystems should usually be mounted on the stable multipath device,
  not on a single underlying path.

In SAN work, confirm with the storage team before deleting, resizing, or
relabeling a device.

## Virtual and Cloud Block Devices

Virtual machines and cloud instances often present storage through
emulated SCSI, VirtIO, NVMe, or platform-specific drivers. The device may
look local, but lifecycle operations happen outside the guest.

Inspect from Linux:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,TRAN,FSTYPE,MOUNTPOINTS
sudo dmesg | grep -iE 'nvme|scsi|virtio|xvd|vd'
```

Then cross-check the platform:

- Instance or VM attachment list.
- Volume ID and size.
- Snapshot or backup status.
- IOPS and throughput limits.
- Whether the volume can be detached, resized, or moved live.

Cloud volume expansion usually has two stages: resize the platform volume,
then grow the partition, logical volume, or filesystem inside Linux.

## Performance Clues

Interface choice affects performance, but it is not the whole story.
Before blaming the interface, inspect:

```bash
iostat -xz 1
lsblk -D
cat /sys/block/sda/queue/rotational
cat /sys/block/sda/queue/scheduler
```

Useful questions:

- Is the disk saturated or is the application waiting elsewhere?
- Is latency high because of random I/O, queue depth, or throttling?
- Is the device rotational?
- Does the filesystem or volume manager issue discard/TRIM?
- Is a cloud volume hitting provisioned IOPS or throughput limits?

For production troubleshooting, collect evidence over time instead of
trusting one sample.

## Naming and Persistence

Interface-specific names are convenient but not always stable. Prefer
persistent names when writing policy:

```bash
ls -l /dev/disk/by-id/
ls -l /dev/disk/by-uuid/
ls -l /dev/disk/by-path/
```

Common choices:

- Use filesystem UUIDs in `/etc/fstab`.
- Use `/dev/disk/by-id/` when scripts must target a specific device.
- Use multipath device names for SAN-backed filesystems.
- Use cloud volume IDs in documentation and runbooks.

The key is traceability: an operator should be able to map Linux device,
platform volume, physical asset, and application owner.

## Hands-on Practice

On a lab system, collect an interface inventory:

```bash
lsblk -o NAME,MODEL,SERIAL,SIZE,TYPE,ROTA,TRAN,FSTYPE,MOUNTPOINTS
for dev in /dev/sd? /dev/nvme?n?; do
  [ -e "$dev" ] && udevadm info --query=property --name="$dev" | grep -E 'ID_MODEL=|ID_SERIAL=|ID_BUS='
done
```

Write down:

- Which devices are rotational and which are not.
- Which transport each device uses.
- Which identifiers would be safe to use in documentation.
- Which devices are mounted and which appear unused.

Do not change partitions or filesystems for this exercise.
