# 20.12 ZFS: All Your Storage Problems Solved?

ZFS is a storage system, not just a filesystem. It combines volume management,
filesystems, snapshots, checksums, replication, quotas, compression, and RAID-like
redundancy behind one set of tools.

That power is why operators like it. It is also why ZFS deserves respect. A
good ZFS design can be simple to operate for years. A bad one can lock you into
awkward capacity, redundancy, and replacement choices.

!!! abstract "What you will learn"
    - Explain how ZFS pools, vdevs, datasets, and snapshots fit together.
    - Inspect ZFS health, capacity, properties, and scrub status.
    - Understand why vdev layout is the most important design decision.
    - Use snapshots and send/receive at an operator level.
    - Recognize common ZFS mistakes before they become data-loss events.

!!! warning "Do not experiment on production disks"
    `zpool create`, `zpool add`, `zpool replace`, and `zpool destroy` can change
    or destroy real storage. Use disposable lab devices or file-backed pools
    while learning. Do not point ZFS commands at a disk unless you are prepared
    to erase it.

## What Makes ZFS Different

Traditional Linux storage often looks like this:

```text
disk -> partition -> RAID or LVM -> filesystem -> mountpoint
```

ZFS collapses much of that into one integrated model:

```text
disks -> ZFS vdevs -> ZFS pool -> datasets -> mountpoints
```

ZFS brings several ideas together:

- pooled storage instead of one filesystem per block device
- checksums for data and metadata
- self-healing when redundancy is available
- copy-on-write updates
- snapshots and clones
- compression
- quotas and reservations
- replication with `zfs send` and `zfs receive`

This design means ZFS can detect corruption that many traditional stacks cannot.
With redundancy, it can often repair bad data automatically.

## Pools, vdevs, and Datasets

The three core terms are pool, vdev, and dataset.

| Term | Meaning | Operator impact |
| --- | --- | --- |
| Pool | The top-level storage container | Capacity and health are managed at this level |
| vdev | A redundancy group inside a pool | The pool depends on every vdev staying healthy |
| Dataset | A ZFS filesystem inside a pool | Properties, quotas, snapshots, and mountpoints live here |

A pool can contain one or more vdevs. A vdev can be:

- a single disk
- a mirror
- RAIDZ1
- RAIDZ2
- RAIDZ3
- a special device class, such as a log, cache, or metadata vdev

The most important ZFS rule:

> A pool fails if any top-level vdev fails.

For example, this pool has two mirror vdevs:

```text
tank
  mirror-0: disk-a disk-b
  mirror-1: disk-c disk-d
```

That is resilient because each top-level vdev is a mirror. If `disk-a` fails,
`disk-b` still carries `mirror-0`.

This pool has two single-disk top-level vdevs:

```text
tank
  disk-a
  disk-b
```

That is effectively striped storage. If either disk fails, the pool can fail.

## Install and Availability Notes

ZFS is not always installed by default on Linux. Many distributions package it
as OpenZFS, but packaging and kernel integration vary.

Check whether the tools exist:

```bash
command -v zpool
command -v zfs
```

Check loaded modules:

```bash
lsmod | grep '^zfs'
```

On a lab host, install using your distribution's documented OpenZFS package.
On production, confirm distribution support, kernel compatibility, patching
workflow, and recovery media before adopting ZFS.

## Inspect ZFS

List pools:

```bash
zpool list
```

Show pool health:

```bash
zpool status
zpool status -v tank
```

List datasets:

```bash
zfs list
```

Show important dataset properties:

```bash
zfs get compression,quota,reservation,mountpoint tank/data
```

Show pool I/O statistics:

```bash
zpool iostat -v tank 2
```

Show snapshot inventory:

```bash
zfs list -t snapshot
```

If `zpool status` is not clean, read it carefully before changing anything. It
usually tells you which device, vdev, or dataset needs attention.

## Create a Lab Pool with Files

This lab uses files as fake disks. It is good for learning commands, snapshots,
and pool behavior. It is not a performance test and not a production design.

Create disposable backing files:

```bash
mkdir -p /tmp/zfs-lab
truncate -s 512M /tmp/zfs-lab/disk1.img
truncate -s 512M /tmp/zfs-lab/disk2.img
```

Create a mirrored pool:

```bash
sudo zpool create zlab mirror /tmp/zfs-lab/disk1.img /tmp/zfs-lab/disk2.img
```

Verify:

```bash
zpool list zlab
zpool status zlab
zfs list zlab
```

Create a dataset:

```bash
sudo zfs create zlab/appdata
```

Set useful properties:

```bash
sudo zfs set compression=lz4 zlab/appdata
sudo zfs set mountpoint=/mnt/zlab-appdata zlab/appdata
```

Verify:

```bash
zfs list zlab/appdata
zfs get compression,mountpoint zlab/appdata
findmnt /mnt/zlab-appdata
```

Clean up when done:

```bash
sudo zpool destroy zlab
rm -rf /tmp/zfs-lab
```

## Properties Matter

ZFS properties control behavior. Some are inherited from parent datasets, which
lets you define defaults at the pool or application boundary.

Common properties:

| Property | Why it matters |
| --- | --- |
| `compression` | Often worth enabling with `lz4`; saves space with low overhead |
| `mountpoint` | Controls where the dataset is mounted |
| `quota` | Limits how much space a dataset can consume |
| `reservation` | Guarantees space for a dataset |
| `recordsize` | Affects performance for large-file or database workloads |
| `atime` | Controls access-time updates |
| `readonly` | Makes a dataset read-only |

Show all local property changes:

```bash
zfs get -s local all zlab/appdata
```

Set a quota:

```bash
sudo zfs set quota=100G tank/appdata
```

Clear a local property and return to inheritance:

```bash
sudo zfs inherit quota tank/appdata
```

Do not tune `recordsize` blindly. Databases, virtual-machine images, and large
media files can have different needs.

## Snapshots and Rollbacks

Snapshots are one of ZFS's strongest features. A snapshot captures a point in
time for a dataset.

Create a snapshot:

```bash
sudo zfs snapshot zlab/appdata@before-change
```

List snapshots:

```bash
zfs list -t snapshot
```

Roll back to a snapshot:

```bash
sudo zfs rollback zlab/appdata@before-change
```

Rollback discards changes made after the snapshot. That can be useful, but it
is still destructive to newer data. Confirm the dataset and snapshot before
running it.

Destroy a snapshot:

```bash
sudo zfs destroy zlab/appdata@before-change
```

Snapshots are not backups by themselves. If the pool is lost, local snapshots
are lost with it. Replicate important snapshots to another pool or host.

## Send and Receive

ZFS can stream snapshots for backups and replication.

Create a snapshot:

```bash
sudo zfs snapshot tank/appdata@daily-2026-05-12
```

Send it to a file:

```bash
sudo zfs send tank/appdata@daily-2026-05-12 > /backup/appdata.zfs
```

Receive it into another pool:

```bash
sudo zfs receive backup/appdata < /backup/appdata.zfs
```

Incremental sends transfer changes between snapshots:

```bash
sudo zfs send -i tank/appdata@daily-2026-05-11 tank/appdata@daily-2026-05-12 > /backup/appdata-incremental.zfs
```

Replication is powerful because it preserves ZFS structure. Test restores before
trusting a replication plan.

## Scrubs and Integrity

A scrub asks ZFS to read data and metadata, verify checksums, and repair what it
can using redundancy.

Start a scrub:

```bash
sudo zpool scrub tank
```

Check progress:

```bash
zpool status tank
```

Cancel a scrub:

```bash
sudo zpool scrub -s tank
```

Run scrubs on a schedule appropriate for the system. A common pattern is monthly
for home labs and small servers, with monitoring for failures and slow devices.

## Capacity and Replacement Traps

ZFS capacity planning is different from simple filesystems.

Watch these risks:

- Pools get unhappy when very full. Avoid running near 100 percent.
- You generally add capacity by adding vdevs or replacing all disks in a vdev
  with larger disks.
- You cannot casually remove every type of vdev from every pool design.
- RAIDZ expansion has specific support and limitations depending on OpenZFS
  version and design.
- Mixing random disk sizes and vdev layouts can create awkward usable capacity.
- A special vdev can become critical pool metadata. Losing it can lose the pool.

Check space:

```bash
zpool list
zfs list
zfs get used,available,referenced,compressratio tank/appdata
```

The easiest time to get a ZFS design right is before data lands on it.

## Common Failure Modes

Use `zpool status` as your first source of truth.

Common states:

| State | Meaning |
| --- | --- |
| `ONLINE` | Healthy from ZFS's view |
| `DEGRADED` | Pool is running with reduced redundancy |
| `FAULTED` | Device or pool has failed |
| `UNAVAIL` | Device is unavailable |
| `OFFLINE` | Device was manually taken offline |

Basic replacement flow:

```bash
zpool status tank
sudo zpool offline tank old-device-id
sudo zpool replace tank old-device-id new-device-id
zpool status tank
```

Use stable device identifiers from `/dev/disk/by-id/` rather than transient
names like `/dev/sdb`.

## ZFS Is Not a Backup Exemption

ZFS protects against important classes of failure:

- silent corruption
- some device failures
- accidental changes when snapshots exist
- efficient replication when configured

It does not protect against every problem:

- deleted snapshots
- pool destruction
- fire, theft, flood, or ransomware
- bad replication that faithfully copies bad data
- operator mistakes on the wrong pool

Keep independent backups. Test restores. Document the pool layout.

## Operational Takeaway

ZFS can solve real storage problems when you design it deliberately: integrity,
snapshots, replication, quotas, and pooled capacity all become easier to reason
about. It does not remove the need for planning. Know your vdev layout, monitor
pool health, scrub regularly, test restores, and treat destructive ZFS commands
with the same care you would give any disk operation.
