# 20.10 Traditional Filesystems: UFS, ext4, and XFS

Traditional filesystems are not old-fashioned in the sense of being obsolete.
They are traditional because they established the day-to-day operating model:
format a block device, mount it at a path, check its capacity, repair it with
the right tool, and grow it when the lower storage layer expands.

On Linux, ext4 and XFS are the two traditional filesystems you are most likely
to operate directly. UFS is more important as Unix heritage and cross-platform
context than as a default Linux choice.

!!! abstract "What you will learn"
    - Explain what UFS, ext4, and XFS are best known for.
    - Inspect traditional filesystem types and mount options.
    - Choose between ext4 and XFS for common Linux workloads.
    - Create and mount ext4 and XFS filesystems in a lab.
    - Understand growth, shrink, and repair boundaries before incidents.

!!! warning "Formatting is destructive"
    `mkfs.ext4`, `mkfs.xfs`, and similar commands create new filesystems.
    They destroy existing filesystem metadata on the target device. Only run
    them against devices you have positively identified and are prepared to
    erase.

## The Operator View

Traditional filesystems answer these questions:

- How are files and directories represented?
- How is free space tracked?
- How is metadata protected after a crash?
- How does the filesystem grow?
- Can it shrink?
- Which repair tool is authoritative?
- What mount options change behavior?

They sit above a block device and below applications:

```text
disk -> partition -> LVM or RAID -> filesystem -> mountpoint -> workload
```

Examples:

```text
/dev/vda2                 -> ext4 -> /
/dev/vg_app/lv_data       -> xfs  -> /srv/app
/dev/mapper/backup_crypt  -> ext4 -> /backup
```

The application usually sees only `/srv/app` or `/backup`. The operator must
understand the full chain.

## UFS: Unix Filesystem Heritage

UFS, the Unix File System, comes from the BSD and classic Unix world. It helped
shape many filesystem ideas that later systems built on: inodes, block groups,
directory structures, and the separation between names and file metadata.

You may encounter UFS when:

- reading older Unix documentation
- working with BSD systems
- mounting legacy disks
- studying filesystem design history

UFS is not the normal Linux server default. Linux can often read UFS variants,
but write support and compatibility depend on the exact variant and kernel
support. Treat unknown UFS media as read-only until you have verified the
platform, filesystem variant, and backup state.

Useful first checks:

```bash
lsblk -f
sudo blkid /dev/sdb1
sudo file -s /dev/sdb1
```

If the target is a production or evidence disk, mount it read-only:

```bash
sudo mkdir -p /mnt/ufs-review
sudo mount -o ro /dev/sdb1 /mnt/ufs-review
```

Do not assume a Linux recovery workflow for a BSD UFS filesystem. Use the
filesystem tools from the operating system that owns the disk whenever possible.

## ext4: The General-Purpose Linux Default

ext4 is the default filesystem on many Linux distributions because it is mature,
predictable, and well supported. It is a strong default for root filesystems,
general-purpose application directories, small and medium servers, and operator
workflows where broad tooling support matters.

Common ext4 strengths:

- widely supported across distributions and rescue environments
- familiar repair tooling with `fsck.ext4` and `e2fsck`
- online growth for mounted filesystems
- offline shrink support
- labels, UUIDs, quotas, journaling, and mature metadata behavior

Common ext4 cautions:

- very large filesystems may not be as natural a fit as XFS
- shrinking requires an unmounted filesystem and a careful procedure
- repair can take time on large or heavily damaged filesystems

Inspect ext-family metadata:

```bash
sudo tune2fs -l /dev/sdb1
```

Create an ext4 filesystem in a lab:

```bash
sudo mkfs.ext4 -L appdata /dev/sdb1
```

Mount it:

```bash
sudo mkdir -p /srv/appdata
sudo mount /dev/sdb1 /srv/appdata
findmnt /srv/appdata
df -hT /srv/appdata
```

## XFS: Large-Scale Server Filesystems

XFS came from Silicon Graphics and is now a major Linux server filesystem. It
is common on enterprise Linux systems, large data volumes, media stores,
database-adjacent storage, and workloads that need strong performance on large
filesystems.

Common XFS strengths:

- excellent support for large files and large filesystems
- strong online growth model
- good parallelism and allocation behavior
- widely supported on enterprise Linux distributions
- mature tooling with `xfs_info`, `xfs_repair`, `xfs_growfs`, and `xfsdump`

Common XFS cautions:

- no shrink support
- repair normally requires an unmounted filesystem
- some tools take mountpoints rather than block devices
- changing your mind after sizing badly can require backup, recreate, restore

Inspect XFS metadata on a mounted filesystem:

```bash
sudo xfs_info /srv/appdata
```

Create an XFS filesystem in a lab:

```bash
sudo mkfs.xfs -L appdata /dev/sdb1
```

Mount it:

```bash
sudo mkdir -p /srv/appdata
sudo mount /dev/sdb1 /srv/appdata
findmnt /srv/appdata
df -hT /srv/appdata
```

## Choosing ext4 or XFS

For many systems, either ext4 or XFS can work. Choose based on operations, not
habit.

| Need | Prefer | Why |
| --- | --- | --- |
| Root filesystem with broad rescue support | ext4 | Familiar, portable, common in recovery environments |
| General small or medium application volume | ext4 | Simple and predictable |
| Large data volume | XFS | Designed for large filesystems and large files |
| Online growth is routine | XFS or ext4 | Both can grow online in common cases |
| Shrink may be required | ext4 | ext4 can shrink offline; XFS cannot shrink |
| Enterprise Linux default alignment | XFS | Common default on RHEL-family systems |
| Maximum cross-distro familiarity | ext4 | Very widely supported |

The wrong choice is rarely fatal if backups and restore tests are good. The
danger is choosing without understanding the maintenance model.

## Inspect Current Filesystems

Show filesystem types and mountpoints:

```bash
lsblk -f
findmnt
df -hT
```

Show only one mount:

```bash
findmnt /var
df -hT /var
```

Show persistent mount configuration:

```bash
cat /etc/fstab
sudo findmnt --verify
```

Show signatures on an unmounted device:

```bash
sudo wipefs --no-act /dev/sdb1
sudo blkid /dev/sdb1
```

`wipefs --no-act` is useful because it reports what it would remove without
removing it.

## Persistent Mounts

Use UUIDs or labels in `/etc/fstab`, not volatile names like `/dev/sdb1`, when
the device order could change.

Find the UUID:

```bash
sudo blkid /dev/sdb1
```

Example ext4 entry:

```text
UUID=11111111-2222-3333-4444-555555555555  /srv/appdata  ext4  defaults,nofail  0  2
```

Example XFS entry:

```text
UUID=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee  /srv/appdata  xfs  defaults,nofail  0  0
```

The final two fields are dump and fsck order. ext4 root filesystems often use
`1`, other ext4 filesystems often use `2`, and XFS entries commonly use `0`
because XFS is not checked by the traditional fsck pass in the same way.

Test before rebooting:

```bash
sudo findmnt --verify
sudo mount -a
findmnt /srv/appdata
```

## Growth and Shrink Rules

Filesystem resizing is a layered operation. Grow the lower layer first:

- cloud disk
- partition
- RAID device
- LVM logical volume
- encrypted mapping

Then grow the filesystem.

Grow ext4:

```bash
sudo resize2fs /dev/vg_app/lv_data
```

Grow XFS:

```bash
sudo xfs_growfs /srv/appdata
```

Verify:

```bash
lsblk -f
df -hT /srv/appdata
findmnt /srv/appdata
```

Shrinking is different. ext4 can shrink only while unmounted, and the safest
procedure is backup, unmount, filesystem check, shrink filesystem, shrink lower
layer, verify, and restore if needed. XFS cannot shrink. To make an XFS volume
smaller, create a smaller filesystem elsewhere and restore data from backup.

## Repair Boundaries

Use the filesystem's own tools and avoid repair commands until you have backups
or a snapshot.

For ext4:

```bash
sudo umount /srv/appdata
sudo fsck.ext4 -f /dev/vg_app/lv_data
```

For XFS:

```bash
sudo umount /srv/appdata
sudo xfs_repair /dev/vg_app/lv_data
```

Important boundaries:

- Do not run repair tools on a mounted filesystem unless the tool explicitly
  documents that mode.
- Do not repair the wrong layer. Repair the filesystem device, not the whole
  disk when the filesystem lives on a partition or logical volume.
- If the data matters, capture evidence first: `lsblk -f`, `blkid`, `findmnt`,
  logs, SMART health, storage-controller state, and backup status.
- If hardware is failing, repeated repair attempts can make recovery worse.

## Lab: Compare ext4 and XFS with Loop Devices

This lab creates disposable files and attaches them as loop devices. It does
not require an extra physical disk.

Create two backing files:

```bash
truncate -s 512M /tmp/ext4-lab.img
truncate -s 512M /tmp/xfs-lab.img
```

Attach them:

```bash
sudo losetup --find --show /tmp/ext4-lab.img
sudo losetup --find --show /tmp/xfs-lab.img
```

Assume the commands returned `/dev/loop10` and `/dev/loop11`. Use your actual
device names.

Create filesystems:

```bash
sudo mkfs.ext4 -L ext4lab /dev/loop10
sudo mkfs.xfs -L xfslab /dev/loop11
```

Mount them:

```bash
sudo mkdir -p /mnt/ext4-lab /mnt/xfs-lab
sudo mount /dev/loop10 /mnt/ext4-lab
sudo mount /dev/loop11 /mnt/xfs-lab
```

Compare:

```bash
df -hT /mnt/ext4-lab /mnt/xfs-lab
findmnt /mnt/ext4-lab /mnt/xfs-lab
sudo tune2fs -l /dev/loop10 | head
sudo xfs_info /mnt/xfs-lab
```

Clean up:

```bash
sudo umount /mnt/ext4-lab /mnt/xfs-lab
sudo losetup -d /dev/loop10
sudo losetup -d /dev/loop11
rm /tmp/ext4-lab.img /tmp/xfs-lab.img
```

## Troubleshooting Checklist

When a traditional filesystem causes trouble, work from evidence:

1. What path is affected?
2. Which filesystem is mounted there?
3. Which block device backs that filesystem?
4. Is the device healthy?
5. Is the filesystem full, inode-full, read-only, or missing?
6. Did `/etc/fstab` change?
7. Did the lower storage layer change?
8. Is there a known-good backup or snapshot?
9. Which repair tool applies to this filesystem?
10. Does the repair require downtime?

Useful commands:

```bash
findmnt /srv/appdata
df -hT /srv/appdata
df -ih /srv/appdata
lsblk -f
journalctl -k --since "1 hour ago"
sudo dmesg --ctime | tail -100
```

## Operational Takeaway

ext4 is the conservative general-purpose Linux filesystem. XFS is a strong
server filesystem for large, growing data volumes. UFS is valuable Unix context
and occasionally a compatibility concern. Your job is to know which filesystem
you are operating, use the correct tools, and prove each change from the block
device up to the mountpoint.
