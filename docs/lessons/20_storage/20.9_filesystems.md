## 20.9 Filesystems: Turning Blocks into Files

A filesystem turns a block device into directories, files, permissions,
timestamps, free-space maps, and metadata. Disks, partitions, RAID arrays, LVM
logical volumes, and encrypted devices all present blocks. The filesystem is
the layer that makes those blocks usable by applications and people.

Choosing and operating a filesystem is not cosmetic. It affects recovery
options, growth procedures, performance behavior, metadata safety, snapshots,
quota support, and how quickly you can understand an incident.

    - Compare common Linux filesystem choices at an operator level.
    - Run safe health checks and understand repair boundaries.

!!! warning "Formatting destroys existing contents"
    `mkfs` creates a new filesystem. On a device that already contains data,
    that is a destructive action. Confirm the target device, signatures,
    mountpoints, and backups before formatting anything outside a lab.

## What a Filesystem Provides

A filesystem manages:

- file and directory names
- metadata such as ownership, permissions, timestamps, and size
- allocation of free and used blocks
- links between names and file contents
- consistency rules after crashes or power loss
- mount options that affect behavior and safety

The layers usually look like this:

```text
disk -> partition -> LVM or RAID or encryption -> filesystem -> mountpoint
```

Examples:

```text
/dev/sdb1                  -> ext4 -> /srv/data
/dev/vg_data/lv_postgres   -> xfs  -> /var/lib/postgresql
/dev/mapper/secure_backup  -> ext4 -> /backup
```

Applications normally care about the mounted path. Operators need to understand
the device stack underneath that path.

## Inspect Filesystems

Show block devices, filesystem types, labels, UUIDs, and mountpoints:

```bash
lsblk -f
```

Show mounted filesystems:

```bash
findmnt
df -hT
```

Show filesystem signatures on a device:

```bash
sudo blkid /dev/sdb1
sudo wipefs --no-act /dev/sdb1
```

Show ext-family details:

```bash
sudo tune2fs -l /dev/sdb1
```

Show XFS details:

```bash
sudo xfs_info /mnt/data
```

The safest first move is always read-only inspection. If a device has an
unexpected signature, stop before creating or repairing anything.

## Common Linux Filesystems

| Filesystem | Common use | Operator notes |
| --- | --- | --- |
| ext4 | General-purpose Linux filesystems | Mature, widely supported, offline shrink possible, straightforward recovery tools |
| XFS | Large files, servers, many enterprise distributions | Strong online growth support, no shrink support, excellent for large data sets |
| Btrfs | Snapshotting, checksums, subvolumes | Powerful but needs informed operations; know its RAID and space-accounting behavior |
| ZFS | Data integrity, snapshots, pooled storage | Excellent integrity model; not built into the mainline Linux kernel in the same way ext4/XFS are |
| vfat / exFAT | EFI partitions and removable media | Useful for compatibility, not Unix permission semantics |
| tmpfs | Memory-backed temporary filesystems | Fast and volatile; contents disappear on reboot |

There is no universal best filesystem. Pick the one that matches the workload,
distribution support, operational experience, recovery tools, and backup model.

## Create an ext4 Filesystem

This example assumes `/dev/sdb1` is a disposable lab partition you already
verified.

Check the target:

```bash
lsblk -f /dev/sdb
sudo wipefs --no-act /dev/sdb1
```

Create the filesystem with a label:

```bash
sudo mkfs.ext4 -L data01 /dev/sdb1
```

Create a mountpoint:

```bash
sudo mkdir -p /srv/data
```

Mount it:

```bash
sudo mount /dev/sdb1 /srv/data
```

Verify:

```bash
findmnt /srv/data
df -hT /srv/data
lsblk -f /dev/sdb
```

## Mount Persistently

Persistent mounts usually belong in `/etc/fstab`. Prefer UUIDs or stable labels
over transient names such as `/dev/sdb1`.

Find the UUID:

```bash
sudo blkid /dev/sdb1
```

Example `/etc/fstab` entry:

```text
UUID=11111111-2222-3333-4444-555555555555  /srv/data  ext4  defaults,nofail  0  2
```

Test the entry before rebooting:

```bash
sudo findmnt --verify
sudo mount -a
findmnt /srv/data
```

If `mount -a` fails, fix the entry before rebooting. A bad root or boot mount
can turn a simple storage task into a recovery incident.

## Choose Mount Options Deliberately

Mount options change behavior. Common examples:

| Option | Meaning |
| --- | --- |
| `defaults` | Use the filesystem's normal default options |
| `noatime` | Avoid updating access time on every read; useful for some workloads |
| `nofail` | Let boot continue if this noncritical filesystem is absent |
| `ro` | Mount read-only |
| `nodev` | Do not interpret device files on this filesystem |
| `nosuid` | Ignore setuid/setgid bits |
| `noexec` | Do not execute binaries from this filesystem |

Security options such as `nodev`, `nosuid`, and `noexec` are common for
temporary, upload, and user-writable areas. Test carefully because applications
may expect behavior those options block.

## Grow a Filesystem

Filesystem growth depends on the filesystem type and the block device under it.

First grow the lower layer if needed:

- cloud volume
- partition
- LVM logical volume
- RAID device
- encrypted container

Then grow the filesystem.

For ext4:

```bash
sudo resize2fs /dev/vg_data/lv_app
```

For XFS:

```bash
sudo xfs_growfs /srv/data
```

Verify:

```bash
df -hT /srv/data
lsblk -f
```

XFS grows while mounted and is addressed by mountpoint. ext4 can often grow
online too, but the command addresses the block device.

## Check and Repair

A mounted filesystem should not normally be repaired with offline repair tools.
Unmount it first or boot into rescue media.

For ext4:

```bash
sudo umount /srv/data
sudo e2fsck -f /dev/sdb1
```

For XFS:

```bash
sudo umount /srv/data
sudo xfs_repair /dev/sdb1
```

Before repair, capture evidence:

```bash
findmnt /srv/data
lsblk -f /dev/sdb
journalctl -k --since "1 hour ago"
```

Repair tools can make irreversible choices when metadata is damaged. If the
data matters, confirm backups and consider imaging the device before repair.

## Watch Capacity and Inodes

Disk-full incidents are not always about bytes. Filesystems can also run out of
inodes, especially when an application creates millions of small files.

Check capacity:

```bash
df -h
```

Check inode usage:

```bash
df -ih
```

Find large directories:

```bash
sudo du -xh --max-depth=1 /var | sort -h
```

Find a high count of small files:

```bash
sudo find /var -xdev -type f | wc -l
```

Use these commands carefully on large trees. They can be expensive on busy
systems.

## Lab: Filesystem on a Loopback Disk

Create a disposable disk:

```bash
truncate -s 512M /tmp/fs-lab.img
sudo losetup --find --show /tmp/fs-lab.img
```

Assume the command prints `/dev/loop7`. Use your actual loop device:

```bash
sudo mkfs.ext4 -L fslab /dev/loop7
sudo mkdir -p /mnt/fslab
sudo mount /dev/loop7 /mnt/fslab
```

Inspect it:

```bash
lsblk -f /dev/loop7
findmnt /mnt/fslab
df -hT /mnt/fslab
sudo tune2fs -l /dev/loop7 | head
```

Write a test file:

```bash
echo "filesystem lab" | sudo tee /mnt/fslab/hello.txt
cat /mnt/fslab/hello.txt
```

Clean up:

```bash
sudo umount /mnt/fslab
sudo losetup -d /dev/loop7
rm /tmp/fs-lab.img
```

## Common Failure Modes

Formatting the wrong target:
: `mkfs` is destructive. Confirm the target with `lsblk -f`, `blkid`, and
  `wipefs --no-act`.

Using unstable device names:
: `/dev/sdb1` can change. Use UUIDs, labels, or `/dev/disk/by-id/` for durable
  configuration.

Growing only one layer:
: The cloud volume, partition, LVM LV, encryption layer, and filesystem can each
  have separate sizes. Verify every layer.

Repairing while mounted:
: Offline repair tools usually require an unmounted filesystem. Running them
  against a mounted filesystem can corrupt data.

Ignoring inode exhaustion:
: `df -h` can show free bytes while `df -ih` shows no inodes left.

## Operator Takeaway

Filesystems are the contract between raw storage and application data. Treat
formatting, mounting, growth, and repair as evidence-driven changes: inspect the
stack, confirm the target, make one change at a time, and verify from both the
block-device view and the mounted-filesystem view.
