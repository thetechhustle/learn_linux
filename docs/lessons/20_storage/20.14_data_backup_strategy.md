### 20.14 Data Backup Strategy

Backups are an operational system, not a product you install once. A useful
backup strategy defines what must be protected, how often copies are made, how
long they are retained, who can restore them, and how the team proves that
restores still work.

!!! abstract "What you will learn"
    - Turn recovery requirements into a practical backup policy.
    - Separate snapshots, replicas, archives, and backups by the risks they cover.
    - Use Linux tools to inspect backup inputs, destinations, and restore evidence.
    - Test a restore without damaging the production copy.

!!! example "Field story"
    A database host has outgrown its storage. Before adding capacity or changing
    filesystems, the operations team needs proof that yesterday's backup can be
    restored, that the backup target is not full, and that the restore procedure
    is documented well enough for the on-call engineer.

!!! success "Operator principle"
    A backup that has not been restored is only a hope. Treat restore tests as
    part of the backup job, not as a separate someday task.

## Start with recovery requirements

Backups should be designed from the restore backwards. Ask these questions before
choosing tools:

- **Recovery point objective (RPO):** how much data can the service afford to
  lose? A static web site may tolerate a day; a busy database may need minutes.
- **Recovery time objective (RTO):** how long can the service stay down while
  data is restored?
- **Scope:** which directories, databases, configuration files, keys, package
  lists, and service metadata are required for a complete recovery?
- **Retention:** how long do daily, weekly, monthly, and compliance copies need
  to remain available?
- **Access control:** who can create, delete, read, and restore backup data?
- **Failure model:** are you protecting against deletion, disk failure,
  ransomware, datacenter loss, bad deployments, or long-term legal discovery?

A good strategy normally mixes several mechanisms. Local snapshots give quick
rollback. Replicas keep another system current. Offline or immutable backups
protect against compromised administrators, accidental deletion, and disasters
that affect the primary site.

## Apply the 3-2-1 rule carefully

The common 3-2-1 rule says to keep three copies of important data, on two
different media or platforms, with one copy off site. In practice, interpret it
as risk separation:

- One copy is the live production data.
- One copy should be quickly reachable for common restores.
- One copy should survive loss or compromise of the primary system.

Do not count a mounted backup share as independent protection if malware,
scripts, or a mistaken `rm -rf` can delete it from the source host. Prefer
append-only, object-lock, snapshot-protected, offline, or separately
authenticated targets for the disaster-recovery copy.

## Inventory what must be backed up

For a Linux host, backup scope usually includes more than `/home`:

- application data, such as `/var/lib/postgresql`, `/var/lib/mysql`,
  `/srv`, `/opt`, and application upload directories
- configuration in `/etc`, including service units, cron files, network
  settings, and package repository definitions
- local scripts, deployment manifests, and systemd override files
- package inventory from tools such as `dpkg -l`, `rpm -qa`, `apt-mark showmanual`,
  or equivalent configuration-management records
- secrets and keys, with encryption and access controls handled separately
- metadata needed for restore, such as owners, groups, modes, ACLs, extended
  attributes, SELinux labels, and database versions

Use read-only inspection first:

```bash
sudo find /etc /srv /opt -xdev -type f -printf '%p\n' | sort | less
sudo du -xhd1 /var /srv /home 2>/dev/null | sort -h
sudo systemctl list-timers --all
sudo systemctl list-unit-files --type=service
```

For databases and other stateful services, prefer application-aware dumps or
backup tools. A filesystem copy of a live database directory can be inconsistent
unless the service is stopped, frozen, snapshotted correctly, or backed up with
the database's own tooling.

## Choose the right backup mechanism

Different backup mechanisms solve different problems:

- **File copy:** `rsync`, `tar`, and similar tools are simple and transparent.
  They are useful for configuration trees, static content, and small systems.
- **Snapshot:** LVM, ZFS, Btrfs, cloud-volume, and storage-array snapshots create
  fast point-in-time views. They are good rollback points, but a local snapshot
  is not a disaster-recovery backup by itself.
- **Versioned backup repository:** tools such as Restic, Borg, Duplicity, and
  Amanda store deduplicated or encrypted backup sets with retention controls.
- **Database-native backup:** `pg_dump`, `pg_basebackup`, MySQL/MariaDB logical
  dumps, physical hot-backup tools, and write-ahead-log archiving preserve
  database consistency.
- **Image or volume backup:** useful for full-machine recovery, especially in
  cloud or virtualized environments, but still needs file-level restore testing.

Match the tool to the restore. If the expected restore is "recover one deleted
file from last Tuesday," prove that path. If the expected restore is "rebuild an
entire server in another region," prove that path too.

## Use safer file-level copies

`rsync` is common for file backups because it preserves metadata and transfers
only changed data. Treat `--delete` as a sharp tool: it makes mirrors accurate,
but it can also remove the only remaining copy of data.

Dry-run before destructive synchronization:

```bash
sudo rsync -aHAXvn --delete /srv/app/ /backup/app/
```

When the dry run matches expectations, run the real copy:

```bash
sudo rsync -aHAXv --delete /srv/app/ /backup/app/
```

Useful options:

- `-a` preserves common ownership, mode, symlink, and timestamp metadata.
- `-HAX` preserves hard links, ACLs, and extended attributes where supported.
- `-n` performs a dry run.
- `--delete` removes destination files that no longer exist at the source.
- `--numeric-ids` avoids owner-name surprises across systems with different
  `/etc/passwd` and `/etc/group` contents.

Never test `--delete` against the only backup copy. Use a disposable destination
or a snapshot-protected target while learning.

## Protect the backup target

Backups often fail because the destination was reachable but not protected.
Check these areas:

- free space and inode availability with `df -h` and `df -ih`
- mount state with `findmnt`, especially for backup directories that should live
  on separate storage
- ownership and permissions on backup repositories
- encryption at rest and key-recovery procedures
- retention policy enforcement and pruning logs
- immutability, object-lock, snapshot, or offline controls
- monitoring for missed jobs, partial jobs, and unusually small backup sizes

Example inspection commands:

```bash
findmnt /backup
df -h /backup
df -ih /backup
sudo ls -ld /backup /backup/app
sudo journalctl -u backup.service --since yesterday
systemctl list-timers --all | grep -i backup
```

If `/backup` fails to mount and a script writes into the empty directory on the
root filesystem, the host can fill `/` while appearing to run the backup job.
Check mount evidence before trusting backup output.

## Test restores

Restore tests should be routine and boring. Use a scratch directory, temporary
VM, container, or non-production database instance.

For a file-level restore test:

```bash
sudo mkdir -p /tmp/restore-test/app
sudo rsync -aHAXv /backup/app/ /tmp/restore-test/app/
sudo find /tmp/restore-test/app -maxdepth 2 -type f | sort | head
sudo diff -qr /srv/app /tmp/restore-test/app
```

For a database restore test, restore into an isolated database name or temporary
host, verify the schema and a few expected records, then destroy the test copy.
Never restore over production unless you are following an approved recovery
procedure during an actual incident.

Record restore evidence:

- backup set name or timestamp
- source host and path
- destination used for the test
- commands run
- elapsed restore time
- files, checksums, or application checks used for validation
- gaps found and follow-up actions

## Common failure patterns

Watch for these recurring issues:

- Backups complete successfully because they copied an empty directory.
- Database files were copied without a consistent snapshot or dump.
- Credentials needed to decrypt backups are stored only on the failed host.
- Retention pruning deletes good backups before anyone notices a bad backup run.
- Backup jobs are monitored for process exit only, not restore quality.
- Replicas mirror corruption, deletion, or ransomware faster than humans react.
- Large restores exceed the planned RTO because bandwidth was never tested.

## Hands-on practice

Use a disposable VM or lab directory.

1. Create a small source tree with a few files, nested directories, and changed
   permissions.
2. Run an `rsync -aHAXvn --delete` dry run into a backup directory.
3. Run the real `rsync` command.
4. Delete one source file and run another dry run to see what `--delete` would do.
5. Restore into a separate scratch directory.
6. Compare source and restore with `diff -qr`, then write a short restore note.
