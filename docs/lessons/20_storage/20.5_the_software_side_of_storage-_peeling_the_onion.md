### 20.5 The Software Side of Storage: Peeling the Onion

!!! abstract "What you will learn"
    - Map the common Linux storage layers from raw device to mounted filesystem.
    - Use read-only commands to identify where capacity, redundancy, encryption, and filesystems live.
    - Explain why storage changes must be planned one layer at a time.
    - Build a short evidence trail before resizing, replacing, or troubleshooting storage.

!!! example "Field story"
    A database host reports that `/var/lib/postgresql` is almost full. The disk team says the virtual disk was expanded, but the filesystem still shows the old size. Before running a resize command, you need to prove which layer changed and which layer still needs work.

!!! success "Operator principle"
    Storage failures are easier to diagnose when you can name the layer you are looking at. Do not change the filesystem when the partition table is the problem, and do not replace a disk when the issue is a full logical volume.

Linux storage is a stack of cooperating layers. A simple server may mount a filesystem directly from one partition. A production server may have physical disks, RAID, encryption, LVM, filesystems, and bind mounts in between. The commands are different at each layer, but the workflow is the same: inspect from the bottom up, change one layer, then verify from the top down.

## The common storage layers

Most Linux systems use some subset of these layers:

| Layer | What it answers | Common evidence |
| --- | --- | --- |
| Physical or virtual device | What disks does the kernel see? | `lsblk -d`, `lsscsi`, `nvme list`, cloud console |
| Partition table | How is a disk divided? | `lsblk`, `parted -l`, `fdisk -l` |
| RAID or multipath | Is data striped, mirrored, or reached through multiple paths? | `cat /proc/mdstat`, `mdadm --detail`, `multipath -ll` |
| Encryption | Is a block device protected before use? | `lsblk -f`, `cryptsetup status` |
| LVM or other volume manager | Which flexible volumes exist above disks or arrays? | `pvs`, `vgs`, `lvs` |
| Filesystem | How are files stored inside the block device? | `findmnt`, `df -hT`, `blkid` |
| Mounts and application paths | Where do users and services reach the data? | `findmnt`, `/etc/fstab`, service configuration |

Not every system has every layer. A laptop may use one encrypted partition with a filesystem inside it. A database server may use several disks joined by hardware RAID, exposed as one device, partitioned once, placed into LVM, formatted as XFS, and mounted at `/var/lib/postgresql`.

## Read the stack safely

Start with read-only commands. This sequence gives you a useful map without modifying anything:

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,FSVER,LABEL,UUID,MOUNTPOINTS
findmnt -R /
df -hT
blkid
```

For systems that use LVM, add:

```bash
sudo pvs
sudo vgs
sudo lvs -a -o +devices
```

For systems that use Linux software RAID, add:

```bash
cat /proc/mdstat
sudo mdadm --detail /dev/md0
```

The goal is to answer these questions before any change:

- Which mounted path is affected?
- Which filesystem backs that path?
- Which block device holds that filesystem?
- Is that block device a partition, an LVM logical volume, a RAID array, an encrypted device, or a plain disk?
- Which layer has free space, errors, or a size mismatch?

## Capacity grows from the bottom up

When storage is expanded, the lower layer usually changes first. The upper layers do not always notice automatically.

A common virtual-machine resize path looks like this:

1. The hypervisor expands the virtual disk.
2. Linux sees the disk's new size.
3. The partition grows, if a partition is in use.
4. The physical volume grows, if LVM is in use.
5. The logical volume grows.
6. The filesystem grows.
7. `df` finally shows more usable space.

Those are separate operations. Skipping the evidence step causes risky guesses, such as running a filesystem resize against the wrong volume or trying to grow LVM before the kernel sees the larger disk.

!!! warning "Do not guess at storage targets"
    Device names such as `/dev/sdb` can change after reboot or hardware changes. Prefer persistent identifiers from `/dev/disk/by-id/`, filesystem UUIDs, LVM names, cloud volume IDs, or a freshly captured `lsblk` map.

## Troubleshoot by locating the mismatch

When storage looks wrong, compare adjacent layers.

| Symptom | Likely place to inspect first |
| --- | --- |
| Cloud console shows a larger disk, but `lsblk` does not | Kernel rescan, VM attachment, or provider-side volume state |
| `lsblk` shows a larger disk, but the partition is unchanged | Partition table and kernel partition reread |
| Partition grew, but LVM free space did not | Physical volume resize |
| Volume group has free space, but the mount is still full | Logical volume size |
| Logical volume grew, but `df` is unchanged | Filesystem resize |
| `df` shows space, but the application still fails | Quotas, inode exhaustion, service path, permissions, or application limits |

Useful checks:

```bash
df -hT /var/lib/postgresql
df -ih /var/lib/postgresql
findmnt /var/lib/postgresql
lsblk -f
sudo lvs -a -o lv_name,vg_name,lv_size,origin,data_percent,metadata_percent,devices
```

`df -h` reports capacity. `df -i` reports inode use. A filesystem can reject new files even when it still has byte capacity if it has run out of inodes.

## Change one layer at a time

Storage commands can destroy data when pointed at the wrong target. Before running commands such as `fdisk`, `parted`, `mkfs`, `pvcreate`, `vgremove`, `lvremove`, `mdadm --create`, or `cryptsetup luksFormat`, confirm that you are in a disposable lab or that you have a tested rollback plan.

For production changes, capture:

- the current `lsblk` and `findmnt` output;
- the affected mount point and service;
- recent backup or snapshot status;
- the exact device identifier, not just a guessed `/dev/sdX` name;
- the command sequence and expected output after each layer changes;
- the rollback or stop point if the next layer does not match expectations.

## Hands-on practice

Run this on a disposable VM or lab host. Do not use a production disk.

1. Capture the current storage stack:

    ```bash
    lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS
    findmnt -R /
    df -hT
    ```

2. Pick one mounted path, such as `/`, `/home`, or `/var`, and trace it back to its block device.
3. If the host uses LVM, identify the logical volume, volume group, and physical volume behind that path:

    ```bash
    sudo lvs -a -o +devices
    sudo vgs
    sudo pvs
    ```

4. Write a short note that names each layer between the mounted path and the disk.
5. In the note, identify the first command you would run before any resize, and explain why it is read-only.
