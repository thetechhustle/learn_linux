### 20.1 I Just Want to Add a Disk!

Adding a disk is one of the most common storage jobs on a Linux system.
It is also one of the easiest jobs to make dangerous by guessing. The
workflow is simple only after you prove which device is new, what will
depend on it, and how you will recover if the change is wrong.

This lesson uses a straightforward example: a server needs a new data
volume mounted at `/srv/data`. The device might be a physical disk, a
virtual disk, an NVMe namespace, or a cloud block volume. The operational
steps are the same: inspect, partition if needed, create a filesystem,
mount it, make the mount persistent, and verify the result.

!!! abstract "What you will learn"
    - Follow the inspect, partition, format, mount, persist, and verify workflow for adding a disk.
    - Confirm the correct target device with `lsblk`, `blkid`, and `wipefs -n` before running destructive commands.
    - Create a durable UUID-based `/etc/fstab` entry and test it with `mount -a` before rebooting.

!!! warning "Do not copy device names blindly"
    Commands such as `mkfs`, `wipefs`, `parted`, and `fdisk` can destroy
    data. `/dev/sdb` in this lesson is only an example. Always identify
    the real target device on your own system before running destructive
    commands.

## The Basic Flow

The usual sequence looks like this:

1. Confirm the new device.
2. Decide whether it needs a partition table.
3. Create one partition or choose the whole device intentionally.
4. Create a filesystem.
5. Create a mount point.
6. Mount the filesystem.
7. Add a safe `/etc/fstab` entry using a persistent identifier.
8. Test remounting and verify available space.

Each step has a command and a check. Do not move to the next step until
the check makes sense.

## Inspect the Current Storage State

Start with read-only inspection:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS
findmnt
df -hT
sudo blkid
sudo journalctl -k --since "10 minutes ago"
```

Look for the new device by size, type, and absence of an existing
filesystem or mount point. On many systems, SATA/SCSI-style disks appear
as `/dev/sdX`, NVMe devices appear as `/dev/nvme0n1`, and virtual or cloud
disks may use either naming style. Device names can change across boots,
so they are useful for immediate work but poor for long-term mount policy.

If the disk is not visible, check the platform first: hypervisor settings,
cloud volume attachment, storage controller logs, kernel messages, or
cabling. Do not invent a device path.

## Confirm the Target

Suppose the new disk appears as `/dev/sdb`:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS /dev/sdb
sudo wipefs -n /dev/sdb
```

The `-n` flag makes `wipefs` print signatures without erasing them. If it
shows an existing filesystem, partition table, LVM signature, or RAID
metadata, stop and investigate. The disk may not be empty.

For a production system, also confirm:

- The application owner agrees with the mount path.
- A current backup exists for any data that will be moved.
- Monitoring and capacity expectations are understood.
- The change window allows time to roll back.

## Partition the Disk

For a simple data disk, create a GPT partition table and one partition:

```bash
sudo parted /dev/sdb --script mklabel gpt
sudo parted /dev/sdb --script mkpart primary ext4 1MiB 100%
sudo partprobe /dev/sdb
```

Then inspect the result:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,PARTTYPE,MOUNTPOINTS /dev/sdb
```

You should see a partition such as `/dev/sdb1`.

Using the whole disk without a partition can work in some environments,
but partitions make the layout more explicit and are easier for other
operators to recognize. Pick one convention and document it.

## Create a Filesystem

Create the filesystem on the partition, not the parent disk:

```bash
sudo mkfs.ext4 -L data01 /dev/sdb1
```

For many Linux workloads, ext4 is a reasonable default. XFS is also common
for large filesystems and enterprise distributions. The important point in
this lesson is not that ext4 is always best; it is that you choose a
filesystem deliberately and create it on the correct block device.

Verify:

```bash
lsblk -f /dev/sdb
sudo blkid /dev/sdb1
```

Record the UUID from `blkid`. You will use it for the persistent mount.

## Mount the Filesystem

Create the mount point:

```bash
sudo mkdir -p /srv/data
```

Mount by device for the first manual test:

```bash
sudo mount /dev/sdb1 /srv/data
findmnt /srv/data
df -hT /srv/data
```

If this mount point will be used by an application, set ownership and
permissions intentionally. For example:

```bash
sudo chown appuser:appgroup /srv/data
sudo chmod 0750 /srv/data
```

Use the actual service account and group for your system.

## Make the Mount Persistent

Avoid adding `/dev/sdb1` to `/etc/fstab`. That name can change. Use the
filesystem UUID:

```bash
sudo blkid /dev/sdb1
```

Add an entry like this to `/etc/fstab`, replacing the UUID with the real
one:

```fstab
UUID=11111111-2222-3333-4444-555555555555 /srv/data ext4 defaults,nofail 0 2
```

The `nofail` option prevents a missing non-critical data disk from
dropping the system into emergency mode during boot. Do not use it
blindly for critical boot or application volumes; decide based on the
host's role.

Before rebooting, test the entry:

```bash
sudo umount /srv/data
sudo mount -a
findmnt /srv/data
df -hT /srv/data
```

If `mount -a` fails, fix `/etc/fstab` before rebooting.

## Move Existing Data Safely

If the mount point already has data, do not mount over it and assume the
data moved. Mounting hides the old directory contents until the filesystem
is unmounted.

A safer pattern is:

```bash
sudo systemctl stop example.service
sudo rsync -aHAX --info=progress2 /srv/data/ /mnt/new-data/
sudo mv /srv/data /srv/data.old
sudo mkdir /srv/data
sudo mount /srv/data
sudo rsync -aHAX --delete /srv/data.old/ /srv/data/
sudo systemctl start example.service
```

Adapt the service name, source path, and temporary mount path to the real
system. Keep the old data until the application has been verified.

## Verify the Result

After the disk is mounted, verify from multiple angles:

```bash
findmnt /srv/data
df -hT /srv/data
lsblk -f
mount | grep ' /srv/data '
sudo journalctl -k --since "10 minutes ago"
```

Then verify the application:

- Can it read and write where expected?
- Are ownership and permissions correct?
- Are logs free of permission, SELinux, or path errors?
- Does monitoring see the new capacity?
- Is the backup job configured for the new mount point?

The job is not done until the service using the storage is healthy.

## Common Mistakes

| Mistake | Why it hurts | Safer habit |
| --- | --- | --- |
| Running `mkfs` on the wrong device | Destroys existing data | Confirm with `lsblk`, `blkid`, and `wipefs -n` |
| Using `/dev/sdb1` in `/etc/fstab` | Device names can change | Use UUID or another persistent identifier |
| Mounting over an existing data directory | Hides old files | Move or sync data intentionally |
| Forgetting ownership | Application cannot write | Set owner, group, mode, and labels |
| Skipping `mount -a` | Bad `fstab` appears at reboot | Test persistent mount before reboot |
| Confusing RAID with backup | Deletion and corruption replicate | Keep independent, tested backups |

## Hands-on Practice

Use a disposable VM or a loopback file, not an important system.

Create a 1 GiB lab disk image:

```bash
truncate -s 1G /tmp/lab-disk.img
sudo losetup --find --show /tmp/lab-disk.img
```

The `losetup` command prints a loop device such as `/dev/loop0`. Use that
device in place of `/dev/sdb` for the partitioning and filesystem steps.
When finished:

```bash
sudo umount /srv/data
sudo losetup -d /dev/loop0
rm /tmp/lab-disk.img
```

Replace `/dev/loop0` with the loop device your system printed.
