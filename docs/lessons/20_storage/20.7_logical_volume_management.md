### 20.7 Logical Volume Management (LVM)

Logical Volume Manager, usually shortened to LVM, adds a flexible storage layer
between disks and filesystems. Instead of binding a filesystem directly to one
fixed partition, LVM lets you pool storage, create logical volumes from that
pool, grow those volumes later, and move data between underlying disks with
less downtime.

LVM is powerful because it changes storage boundaries. It is risky for the same
reason. A careful operator verifies every layer before writing to it.

!!! abstract "What you will learn"
    - Explain the LVM layers: physical volumes, volume groups, and logical volumes.
    - Inspect an existing LVM layout without changing it.
    - Create a simple LVM-backed filesystem in a lab.
    - Grow a logical volume and its filesystem safely.
    - Recognize common LVM failure modes before they become outages.

!!! warning "Use a lab disk first"
    Practice LVM on a disposable disk, virtual disk, or loopback file. Commands
    such as `pvcreate`, `vgremove`, and `lvremove` can destroy access to real
    data when aimed at the wrong device.

## The LVM Stack

LVM has three main objects:

| Layer | Meaning | Example command |
| --- | --- | --- |
| Physical volume (PV) | A disk or partition prepared for LVM | `pvdisplay` |
| Volume group (VG) | A pool made from one or more PVs | `vgdisplay` |
| Logical volume (LV) | A block device carved from a VG | `lvdisplay` |

The stack looks like this:

```text
disk or partition -> physical volume -> volume group -> logical volume -> filesystem -> mountpoint
```

For example:

```text
/dev/sdb1 -> PV -> vg_data -> lv_pgdata -> ext4 -> /var/lib/postgresql
```

The logical volume appears as a normal block device:

```text
/dev/vg_data/lv_pgdata
/dev/mapper/vg_data-lv_pgdata
```

Both paths point to the same LV.

## Why Use LVM?

LVM is useful when storage needs to change over time.

Common reasons:

- grow a filesystem after adding a disk or expanding a cloud volume
- keep application data on named logical volumes instead of raw partitions
- move data from one disk to another with `pvmove`
- create snapshots for short-lived backup or migration windows
- combine several disks into one storage pool when that is operationally useful

LVM is not a backup system. It can make storage easier to rearrange, but it
does not protect you from accidental deletion, corruption, or losing every disk
in the same volume group.

## Inspect an Existing LVM System

Start with the whole block-device view:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

Show physical volumes:

```bash
sudo pvs
sudo pvdisplay
```

Show volume groups:

```bash
sudo vgs
sudo vgdisplay
```

Show logical volumes:

```bash
sudo lvs -a -o +devices
sudo lvdisplay
```

Match LVs to filesystems and mountpoints:

```bash
findmnt
df -hT
```

When troubleshooting, the `lvs -a -o +devices` view is especially useful
because it shows which physical devices back each logical volume.

## Create a Simple LVM Filesystem

This example assumes `/dev/sdb1` is a lab partition you already verified.

Prepare the partition as an LVM physical volume:

```bash
sudo pvcreate /dev/sdb1
```

Create a volume group:

```bash
sudo vgcreate vg_lab /dev/sdb1
```

Create a logical volume:

```bash
sudo lvcreate -n lv_data -L 5G vg_lab
```

Create a filesystem:

```bash
sudo mkfs.ext4 -L labdata /dev/vg_lab/lv_data
```

Mount it:

```bash
sudo mkdir -p /mnt/labdata
sudo mount /dev/vg_lab/lv_data /mnt/labdata
```

Verify every layer:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS
sudo pvs
sudo vgs
sudo lvs -a -o +devices
df -hT /mnt/labdata
```

If the output does not match your intended design, stop before adding data.

## Grow a Logical Volume

The safest growth workflow is:

1. Confirm the current LV and filesystem.
2. Confirm the VG has free space.
3. Extend the LV.
4. Grow the filesystem.
5. Verify the new size.

Check current state:

```bash
sudo lvs -o lv_name,vg_name,lv_size,devices
sudo vgs
df -hT /mnt/labdata
```

Extend the logical volume by 2 GiB:

```bash
sudo lvextend -L +2G /dev/vg_lab/lv_data
```

Grow an ext4 filesystem:

```bash
sudo resize2fs /dev/vg_lab/lv_data
```

For XFS, grow the mounted filesystem instead:

```bash
sudo xfs_growfs /mnt/labdata
```

Verify:

```bash
sudo lvs -o lv_name,vg_name,lv_size
df -hT /mnt/labdata
```

Many distributions support a shortcut that grows the filesystem with the LV:

```bash
sudo lvextend -r -L +2G /dev/vg_lab/lv_data
```

The `-r` option is convenient, but you still need to verify the result.

## Add a Disk to a Volume Group

After attaching and partitioning a new disk, prepare the new partition:

```bash
sudo pvcreate /dev/sdc1
```

Add it to the existing VG:

```bash
sudo vgextend vg_lab /dev/sdc1
```

Verify that the pool grew:

```bash
sudo pvs
sudo vgs
```

At this point the VG has more free space. Existing LVs do not automatically
grow until you extend them.

## Move Data Off a Disk

`pvmove` can migrate extents away from a physical volume while the VG remains
online. This is useful when replacing a disk.

Check where data lives:

```bash
sudo lvs -a -o +devices
```

Move data off `/dev/sdb1`:

```bash
sudo pvmove /dev/sdb1
```

Remove the old PV from the VG:

```bash
sudo vgreduce vg_lab /dev/sdb1
```

Only then consider wiping or removing the old disk. Confirm first:

```bash
sudo pvs
sudo lvs -a -o +devices
```

Do not interrupt `pvmove` casually. If the host or disk is unstable, plan the
operation during a maintenance window and make sure backups are current.

## Snapshots Are Temporary Tools

LVM snapshots preserve a point-in-time view of an LV by tracking changes after
the snapshot is created. They are useful for short backup windows and risky
changes, but they are not long-term backups.

Create a small snapshot:

```bash
sudo lvcreate -s -n lv_data_snap -L 2G /dev/vg_lab/lv_data
```

List snapshots:

```bash
sudo lvs -a
```

Remove the snapshot when finished:

```bash
sudo lvremove /dev/vg_lab/lv_data_snap
```

If a snapshot fills, it can become invalid. Monitor snapshot usage closely.

## Remove LVM Objects

Removal works from the top of the stack down.

Unmount the filesystem:

```bash
sudo umount /mnt/labdata
```

Remove the logical volume:

```bash
sudo lvremove /dev/vg_lab/lv_data
```

Remove the volume group:

```bash
sudo vgremove vg_lab
```

Remove the physical volume label:

```bash
sudo pvremove /dev/sdb1
```

These commands are destructive. Capture `lsblk`, `pvs`, `vgs`, and `lvs`
output before and after removal when doing this outside a lab.

## Common Failure Modes

Wrong device:
: `pvcreate /dev/sdb1` overwrites metadata on the target. Confirm the device by
  size, model, serial, mountpoint, and current signatures first.

No free extents:
: `lvextend` fails if the VG has no free space. Check `vgs` before extending.

Filesystem not grown:
: Extending the LV only changes the block device. Run the filesystem-specific
  growth command or use `lvextend -r`.

Missing PV:
: If a disk disappears, the VG may become partial. Check `pvs`, `vgs`, and
  system logs before trying repair commands.

Snapshots left behind:
: Old snapshots consume space and can hurt performance. Remove them after their
  short-lived job is done.

## Lab: LVM on a Loopback Disk

Create a disposable disk file:

```bash
truncate -s 1G /tmp/lvm-lab.img
sudo losetup --find --show /tmp/lvm-lab.img
```

Assume the command prints `/dev/loop7`. Use your actual loop device:

```bash
sudo pvcreate /dev/loop7
sudo vgcreate vg_looplab /dev/loop7
sudo lvcreate -n lv_notes -L 256M vg_looplab
sudo mkfs.ext4 /dev/vg_looplab/lv_notes
sudo mkdir -p /mnt/lvm-looplab
sudo mount /dev/vg_looplab/lv_notes /mnt/lvm-looplab
```

Inspect the stack:

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS /dev/loop7
sudo pvs
sudo vgs
sudo lvs -a -o +devices
df -hT /mnt/lvm-looplab
```

Clean up:

```bash
sudo umount /mnt/lvm-looplab
sudo lvremove /dev/vg_looplab/lv_notes
sudo vgremove vg_looplab
sudo pvremove /dev/loop7
sudo losetup -d /dev/loop7
rm /tmp/lvm-lab.img
```

## Operator Takeaway

LVM gives Linux storage room to change. Use it deliberately: inspect the whole
stack, name objects clearly, grow one layer at a time, verify after every
change, and keep backups separate from LVM convenience features.
