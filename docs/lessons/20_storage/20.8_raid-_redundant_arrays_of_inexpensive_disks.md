### 20.8 RAID: Redundant Arrays of Inexpensive Disks

RAID combines multiple disks into one storage device. Sometimes the goal is
speed, sometimes it is survival after a disk failure, and often it is a
careful balance between the two.

The most important operational point is this: RAID is not a backup. RAID can
keep a system online when a disk fails, but it does not protect you from
deleted files, corrupted data, ransomware, bad firmware, accidental
repartitioning, or a disaster that takes out the whole machine.

!!! warning "Production safety"
    Commands such as `mdadm --create`, `mdadm --add`, `mdadm --remove`,
    `wipefs`, `sgdisk`, and `dd` can destroy data when used on the wrong
    device. In production, identify devices by stable paths, collect current
    evidence, confirm backups, and have a rollback or recovery plan before
    changing an array.

## Where RAID fits

RAID usually sits below the filesystem. A common Linux software RAID stack
looks like this:

```text
filesystem -> LVM or direct block device -> /dev/md0 -> member disks
```

Hardware RAID controllers hide most of this stack from Linux. The operating
system might see one logical disk such as `/dev/sda` even though the controller
is using several physical drives. That can simplify installation, but it also
means health checks often require vendor-specific tools such as `storcli`,
`perccli`, `ssacli`, or the server management interface.

Linux software RAID is commonly managed with `mdadm`. It exposes arrays as
devices such as `/dev/md0`, `/dev/md1`, or `/dev/md/root`.

## Common RAID levels

| Level | Minimum disks | Survives disk failure? | Main use | Tradeoff |
| --- | ---: | --- | --- | --- |
| RAID 0 | 2 | No | Performance or scratch data | Any member failure loses the array |
| RAID 1 | 2 | Usually one disk | Simple mirroring | Capacity is limited to one member's size |
| RAID 5 | 3 | One disk | Capacity-efficient redundancy | Rebuilds can be slow and risky on large disks |
| RAID 6 | 4 | Two disks | Better parity protection | More write overhead than RAID 5 |
| RAID 10 | 4 | Usually one disk per mirror pair | Performance plus redundancy | Uses half the raw capacity |

RAID 0 is not redundant. It stripes data across disks, so losing one disk loses
the whole array. Use it only when the data is disposable or fully reproducible.

RAID 1 mirrors data. It is easy to understand, easy to recover from, and a good
choice for boot disks or small systems that need simple redundancy.

RAID 5 and RAID 6 use parity. They provide more usable capacity than mirroring,
but rebuilds place heavy load on every surviving disk. RAID 6 is usually safer
than RAID 5 for large disks because a second disk can fail during a rebuild.

RAID 10 stripes across mirrored pairs. It often gives better performance and
simpler failure behavior than parity RAID, at the cost of usable capacity.

## Read-only inspection

Start with commands that do not modify the system.

```bash
cat /proc/mdstat
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL
sudo mdadm --detail /dev/md0
sudo mdadm --examine /dev/sdb1 /dev/sdc1
sudo journalctl -k -g 'md|raid|I/O error' --no-pager
```

Useful signs in `/proc/mdstat` include:

- `[UU]`: both members of a two-disk mirror are up.
- `[U_]` or `[_U]`: one member is missing or failed.
- `recovery`, `resync`, or `reshape`: the array is doing background work.
- `finish=` and `speed=`: estimated rebuild progress and current throughput.

`mdadm --detail` gives a fuller view:

```text
State : clean
Active Devices : 2
Working Devices : 2
Failed Devices : 0
Spare Devices : 0
```

For a healthy array, you want the expected number of active devices, no failed
devices, and no surprise resync unless one is planned.

## Create arrays only in a lab

The following example is for a disposable lab VM with empty disks. Do not paste
it into a production host.

```bash
sudo mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdb /dev/sdc
cat /proc/mdstat
sudo mdadm --detail /dev/md0
```

After creating an array, administrators usually put a partition table,
filesystem, LVM physical volume, or encryption layer on top of `/dev/md0`.
The correct next step depends on the storage design.

Persist the array configuration according to the distribution's conventions.
On many Linux systems, that means updating an `mdadm.conf` file and rebuilding
the initramfs if the array is needed during boot.

```bash
sudo mdadm --detail --scan
```

Do not assume every distribution stores this file in the same place. Check the
local documentation before changing boot-critical storage.

## Failed member workflow

When an array reports a failed disk, slow down and collect evidence before
changing anything.

1. Confirm the affected array:

   ```bash
   cat /proc/mdstat
   sudo mdadm --detail /dev/md0
   ```

2. Map the failed member to a physical device or slot:

   ```bash
   lsblk -o NAME,KNAME,SIZE,TYPE,MODEL,SERIAL
   sudo mdadm --detail /dev/md0
   ```

3. Check kernel and device-health evidence:

   ```bash
   sudo journalctl -k --since '1 hour ago' --no-pager
   sudo smartctl -a /dev/sdb
   ```

4. Confirm backups and maintenance expectations. RAID rebuilds are stressful,
   and another weak disk can fail while the array is degraded.

5. Mark and remove only the confirmed failed member:

   ```bash
   sudo mdadm /dev/md0 --fail /dev/sdb1
   sudo mdadm /dev/md0 --remove /dev/sdb1
   ```

6. Add the replacement member after it has the expected partition layout:

   ```bash
   sudo mdadm /dev/md0 --add /dev/sdd1
   watch cat /proc/mdstat
   ```

The exact device names above are examples. In real work, device names can
change across boots. Prefer stable identifiers, inventory records, and physical
slot mapping instead of guessing from `/dev/sdX` order.

## Troubleshooting patterns

### The array is degraded

Check `/proc/mdstat`, `mdadm --detail`, and kernel logs. Identify whether the
member is failed, missing, or simply not assembled. Do not immediately recreate
the array; recreating with the wrong options can make recovery harder.

### The array did not assemble after boot

Check whether the expected member devices are visible with `lsblk`, then inspect
superblocks with `mdadm --examine`. If the root filesystem depends on the array,
also check initramfs and bootloader configuration.

### Rebuilds are too slow

Heavy application I/O, weak disks, controller limits, and kernel rebuild limits
can all affect speed. Before tuning rebuild settings, decide whether production
latency or faster redundancy restoration matters more for the incident.

### The replacement disk is larger

RAID normally uses the common usable size across members. A larger replacement
disk may work, but extra capacity is not automatically useful unless the whole
array design is expanded later.

### Hardware RAID hides failed disks

If Linux only sees a logical disk, use the controller tooling and out-of-band
management to inspect member health. Also confirm alerting, because the OS may
not show a failed physical disk through ordinary commands.

## Monitoring expectations

A RAID array should not rely on someone occasionally running `cat /proc/mdstat`.
Production systems need alerts for degraded arrays, failed members, controller
events, rebuild status, and disk health. For software RAID, `mdadm --monitor`
or a monitoring agent can report array state. For hardware RAID, integrate the
controller's health output with the same alerting path used for other hardware.

Monitor capacity too. RAID keeps a block device available; it does not prevent
filesystems from filling up.

## Hands-on practice

Use a disposable VM with two or more empty virtual disks.

1. Install `mdadm` using your distribution's package manager.
2. Inspect available disks:

   ```bash
   lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
   ```

3. Create a RAID 1 array from two empty lab disks.
4. Record `cat /proc/mdstat` and `sudo mdadm --detail /dev/md0`.
5. Simulate a failed member with `mdadm --fail` and observe the degraded state.
6. Re-add or replace the failed member and watch the rebuild finish.
7. Write a short note explaining which commands were read-only and which
   commands changed storage state.

Destroy the lab VM when finished if it was created only for this exercise.
