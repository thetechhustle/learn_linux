### 20.2 Storage Hardware: The Physical Layer of Storage

Storage work starts with the device you are trusting with data. Before you
partition, format, mirror, or mount anything, identify what kind of hardware is
present, how Linux sees it, and what failure signals already exist.

!!! abstract "What you will learn"
    - Distinguish HDDs, SSDs, NVMe devices, removable media, and network-backed storage.
    - Collect read-only evidence about capacity, transport, model, serial number, and health.
    - Match storage hardware choices to workload needs such as latency, throughput, endurance, and replacement safety.
    - Recognize when a storage change needs backups, maintenance windows, or vendor documentation before proceeding.

!!! example "Field story"
    A database server is running out of capacity. The request says "add a
    disk," but the incident notes do not say whether the system uses local
    SATA drives, NVMe storage, virtual disks, RAID, or network volumes. Your
    first job is to identify the hardware layer without changing it.

!!! success "Operator principle"
    Never treat a block device name as a permanent identity. Device names such
    as `/dev/sdb` can change across boots; model, serial, WWN, filesystem UUID,
    and storage controller context make a safer evidence trail.

## Common storage device types

| Type | What it is good for | Operational concerns |
| --- | --- | --- |
| HDD | Low-cost capacity, archives, backups, large sequential workloads | Moving parts, higher latency, vibration sensitivity, slower rebuilds |
| SATA/SAS SSD | General-purpose servers, VM hosts, database storage, faster boot and app data | Write endurance, firmware bugs, controller behavior, cost per TB |
| NVMe SSD | Low-latency databases, high-throughput build systems, busy virtualization hosts | Heat, PCIe slot limits, namespace layout, higher replacement planning needs |
| USB/removable media | Installers, temporary transfer, rescue work | Easy to unplug, inconsistent performance, weak long-term reliability |
| Network-backed storage | Shared data, snapshots, cloud volumes, centralized backup targets | Network dependency, latency, permissions, provider or appliance failure modes |

Cloud and virtual machines often hide the physical device. You may see a
virtual disk such as `/dev/vda`, `/dev/xvda`, or `/dev/sda` even when the real
storage is remote, replicated, or backed by an array. In that case, combine
Linux evidence with provider or hypervisor documentation before making
durability claims.

## Build a read-only hardware inventory

Start with commands that inspect rather than modify:

```bash
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,TRAN,ROTA,RM,MOUNTPOINTS
findmnt
df -hT
sudo dmesg -T | grep -Ei 'sd[a-z]|nvme|scsi|ata|error|fail|reset|timeout'
```

Useful fields from `lsblk`:

- `TYPE`: tells you whether the row is a disk, partition, loop device, LVM device, or RAID member.
- `TRAN`: often shows the transport, such as `sata`, `sas`, `nvme`, or `usb`.
- `ROTA`: `1` usually means rotational media; `0` usually means solid-state media.
- `RM`: identifies removable media.
- `MODEL` and `SERIAL`: help match Linux device names to labels, tickets, bays, or cloud volume IDs.

For NVMe devices, add:

```bash
nvme list
sudo nvme smart-log /dev/nvme0
```

For SATA, SAS, and many USB-attached disks, add:

```bash
sudo smartctl -a /dev/sdX
```

Replace `/dev/sdX` with the disk you are inspecting, not a partition such as
`/dev/sdX1`. If `smartctl` reports that a USB bridge or RAID controller blocks
SMART data, check the controller documentation before assuming the disk is
healthy.

## Health signals to collect before changes

Hardware replacement and expansion work should start with current risk, not
only free space.

- Kernel logs: look for I/O errors, resets, timeouts, link flaps, and device disappear/reappear events.
- SMART or NVMe health: check media errors, reallocated sectors, wear indicators, unsafe shutdowns, and temperature.
- Controller state: for hardware RAID, inspect the vendor tool or management UI instead of trusting only the OS view.
- Redundancy status: confirm whether the disk is standalone, part of software RAID, part of LVM, or backed by a storage appliance.
- Backup freshness: verify restore points before replacing, resizing, or rebalancing storage.

Do not run write tests, destructive benchmarks, firmware updates, or drive
secure-erase commands on production disks during discovery. Tools such as
`fio`, `badblocks -w`, `hdparm --security-erase`, and vendor firmware utilities
belong in a planned maintenance workflow with backups and rollback steps.

## Match hardware to the workload

Choose hardware based on the failure mode you are trying to reduce.

- Capacity pressure: larger HDDs, network volumes, or object storage may be better than premium NVMe.
- Latency-sensitive databases: SSD or NVMe storage usually matters more than raw TB count.
- Heavy write workloads: check endurance ratings, write amplification, and available monitoring.
- Backup targets: capacity, replaceability, and restore speed matter more than peak random I/O.
- Remote offices and edge systems: removable parts, local spares, and simple recovery procedures can matter more than perfect performance.

The right answer is rarely "fastest disk." It is the storage device whose
capacity, latency, endurance, monitoring, replacement process, and cost fit the
service.

## Hands-on practice

Run these on a disposable VM, lab machine, or non-production host.

1. Run `lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,TRAN,ROTA,RM,MOUNTPOINTS` and identify each real disk.
2. Use `findmnt` and `df -hT` to connect mounted filesystems back to the underlying storage.
3. Inspect recent kernel storage messages with `sudo dmesg -T | grep -Ei 'sd[a-z]|nvme|scsi|ata|error|fail|reset|timeout'`.
4. If the lab host supports it, run `sudo smartctl -a /dev/sdX` or `sudo nvme smart-log /dev/nvme0`.
5. Write a short handoff note that names the disk identity, transport, capacity, health evidence, and any uncertainty.
