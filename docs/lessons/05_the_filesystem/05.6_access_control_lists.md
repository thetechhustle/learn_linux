### 05.6 Access Control Lists (ACLs)

Unix mode bits answer a simple question: what can the owner, owning group,
and everyone else do with this file?

Access Control Lists answer the next question: what if one extra user or one
extra group needs access without changing the broad ownership model?

ACLs are useful, but they are also easy to make invisible. A directory can look
mostly normal in `ls -l` while `getfacl` shows extra access rules. During an
incident, that hidden detail can explain why one service account can read a
file, why another user cannot write to a shared directory, or why a permission
change did not behave the way the team expected.

!!! abstract "What you will learn"
    - Recognize when a file has ACL entries.
    - Use `getfacl` to inspect the real access rules.
    - Use `setfacl` for narrow user and group exceptions.
    - Explain the ACL mask and why it can cap effective permissions.
    - Remove ACL entries safely when the exception is no longer needed.

!!! warning "Use a lab path first"
    ACL changes can expose or block data. Practice on a disposable directory
    before changing production application, home, log, or shared-data paths.

## Spot ACLs from `ls -l`

Start with the ordinary mode view:

```console
$ ls -l shared-report.txt
-rw-rw----+ 1 root finance 1824 May 10 14:10 shared-report.txt
```

The `+` after the mode string means the file has an ACL.

Without the `+`, the owner/group/other bits are usually the complete access
story. With the `+`, inspect the ACL before assuming `chmod`, `chown`, or group
membership explains the behavior.

## Read the complete ACL

Use `getfacl`:

```console
$ getfacl shared-report.txt
# file: shared-report.txt
# owner: root
# group: finance
user::rw-
user:alice:rw-
group::r--
group:auditors:r--
mask::rw-
other::---
```

Read it in layers:

- `user::rw-` is the owning user's access.
- `user:alice:rw-` is a named-user exception.
- `group::r--` is the owning group's access.
- `group:auditors:r--` is a named-group exception.
- `mask::rw-` is the maximum effective access for named users, named groups,
  and the owning group.
- `other::---` is access for everyone else.

The owner entry and the other entry are not capped by the ACL mask. Named user
entries, named group entries, and the owning group entry are.

## Make a narrow exception

Give one user read access to a file without changing the owning group:

```console
$ sudo setfacl -m u:alice:r shared-report.txt
$ getfacl shared-report.txt
```

Give one group read and execute access to a directory tree:

```console
$ sudo setfacl -R -m g:auditors:rx /srv/reports
```

Use `x` on directories when users need to traverse the path. Read permission on
a file is not enough if the user cannot execute the directories leading to it.

## Understand the mask

The mask can make an ACL entry look more generous than it really is:

```console
$ getfacl deploy.log
# file: deploy.log
# owner: app
# group: app
user::rw-
user:alice:rw-        #effective:r--
group::r--
mask::r--
other::---
```

Here `alice` has an ACL entry that says `rw-`, but the mask is `r--`, so her
effective access is read-only.

If a teammate says "the ACL says write is granted but it still fails," check
the `#effective:` comments and the `mask::` line.

When you intentionally change the mask, be explicit:

```console
$ sudo setfacl -m m::rw deploy.log
```

Do not widen the mask casually. It may increase effective permissions for more
than the single entry you are thinking about.

## Default ACLs on directories

Directories can have default ACLs. These are templates inherited by new files
and subdirectories created under that directory:

```console
$ sudo setfacl -m d:g:auditors:rx /srv/reports
$ getfacl /srv/reports
```

Default ACL entries start with `default:` in `getfacl` output:

```console
default:user::rwx
default:group::r-x
default:group:auditors:r-x
default:mask::r-x
default:other::---
```

Default ACLs do not retroactively fix existing files. They affect new entries
created after the default rule exists. If you need to change existing data too,
handle that as a separate, deliberate recursive change.

## Remove ACL entries

Remove one named-user ACL:

```console
$ sudo setfacl -x u:alice shared-report.txt
```

Remove one named-group ACL:

```console
$ sudo setfacl -x g:auditors shared-report.txt
```

Remove all extended ACL entries from a file:

```console
$ sudo setfacl -b shared-report.txt
```

After removal, verify with both views:

```console
$ ls -l shared-report.txt
$ getfacl shared-report.txt
```

The `+` should disappear from `ls -l` when no extended ACL remains.

## Operational workflow

When troubleshooting access:

1. Identify the exact path the process or user touched.
2. Check every directory in the path for traversal permission.
3. Run `ls -l` and look for the ACL `+`.
4. Run `getfacl` on the file and relevant parent directories.
5. Check for default ACLs if new files inherit surprising permissions.
6. Make the narrowest ACL change possible in a lab or maintenance window.
7. Verify as the affected user or service account.
8. Record the before/after ACL output in the ticket or incident notes.

## Hands-on practice

Run this in a disposable lab directory:

```console
$ mkdir /tmp/acl-lab
$ cd /tmp/acl-lab
$ printf 'demo\n' > report.txt
$ ls -l report.txt
$ getfacl report.txt
```

Add and inspect an ACL entry:

```console
$ setfacl -m u:"$USER":rw report.txt
$ ls -l report.txt
$ getfacl report.txt
```

Remove the extended ACL:

```console
$ setfacl -b report.txt
$ ls -l report.txt
$ getfacl report.txt
```

If your platform lacks `setfacl` or `getfacl`, note that in your lab output.
Some minimal containers omit the ACL tools, and some filesystems may not expose
Linux-style ACL behavior.
