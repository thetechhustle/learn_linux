### 05.2 Filesystem Mounting and Unmounting

!!! abstract "What you will learn"
    - Explain how a filesystem becomes visible at a mount point.
    - Inspect mounted filesystems with `findmnt`, `lsblk`, `df`, and `/proc/mounts`.
    - Mount and unmount filesystems safely in a lab.
    - Troubleshoot common "wrong disk", "busy mount", and "full filesystem" symptoms.

!!! example "Field story"
    A deployment fails because `/var/www` reports no free space. The disk is not actually full; the application is writing to the root filesystem because the separate web-content volume is no longer mounted. Your job is to prove what is mounted, restore the expected mount, and verify that writes land on the right filesystem.

!!! success "Operator principle"
    Always prove the device, filesystem type, mount point, and current users before mounting or unmounting anything on a shared system.

Mounting attaches a filesystem to the single Linux directory tree. The storage might be a disk partition, logical volume, USB drive, ISO image, network share, or temporary in-memory filesystem. After the mount succeeds, programs use the mount point path as if the files were part of the local tree.

Unmounting detaches that filesystem from the directory tree. The command is spelled `umount`, not `unmount`.

## Read the current mount table

Start with read-only evidence. `findmnt` gives a clearer view than plain `mount` output.

```bash
findmnt
findmnt /var
findmnt -no SOURCE,FSTYPE,OPTIONS,TARGET /var
```

Correlate the mount table with block devices and capacity:

```bash
lsblk -f
df -hT
df -ih
cat /proc/mounts | column -t | less
```

Useful fields:

- `SOURCE`: the device, volume, network export, or pseudo-filesystem.
- `FSTYPE`: the filesystem type, such as `ext4`, `xfs`, `btrfs`, `nfs4`, or `tmpfs`.
- `TARGET`: the directory where the filesystem is attached.
- `OPTIONS`: flags such as `rw`, `ro`, `noexec`, `nosuid`, `nodev`, and `relatime`.

## Mount points hide existing files

If a directory already contains files, mounting another filesystem on that directory hides the original files until the filesystem is unmounted. The files are not deleted, but they are no longer visible through that path.

Before mounting on a non-empty directory, stop and confirm the intent:

```bash
sudo find /srv/app-data -maxdepth 1 -mindepth 1 -print
findmnt /srv/app-data
```

This check prevents a common incident pattern: a service writes data to `/srv/app-data` while the real data volume is absent, then the data appears to "disappear" when the volume is mounted later.

## Mount safely

On a lab machine, the basic shape is:

```bash
sudo mkdir -p /mnt/lab
sudo mount -o ro /dev/sdb1 /mnt/lab
findmnt /mnt/lab
```

Prefer a read-only first mount when you are inspecting an unfamiliar disk. Use the filesystem type explicitly when auto-detection is not enough:

```bash
sudo mount -t ext4 -o ro /dev/sdb1 /mnt/lab
```

For production changes, record the exact device identity before mounting:

```bash
lsblk -o NAME,PATH,FSTYPE,LABEL,UUID,SIZE,MOUNTPOINTS
sudo blkid /dev/sdb1
```

Device names such as `/dev/sdb1` can change across boots or cloud attach events. Persistent configuration should usually use a `UUID=` or `LABEL=` entry in `/etc/fstab`, not a transient disk name.

## Unmount safely

Unmount only after confirming what is mounted and whether processes are still using it:

```bash
findmnt /mnt/lab
sudo lsof +f -- /mnt/lab
sudo fuser -vm /mnt/lab
sudo umount /mnt/lab
findmnt /mnt/lab || echo "not mounted"
```

If `umount` reports `target is busy`, do not jump to lazy or forced unmounts. First identify the process, decide whether it can be stopped, and capture enough context for a handoff.

```bash
sudo lsof +f -- /mnt/lab
sudo fuser -vm /mnt/lab
```

Use `umount -l` or force options only when you understand the impact. They can leave running processes with confusing stale file handles or incomplete writes.

## Persistent mounts with fstab

`/etc/fstab` defines filesystems that should mount at boot or when requested with `mount /path`.

Inspect it before changing it:

```bash
findmnt --fstab
sudo cp /etc/fstab /etc/fstab.$(date +%Y%m%d%H%M).bak
```

A typical entry looks like this:

```text
UUID=11111111-2222-3333-4444-555555555555  /srv/app-data  ext4  defaults,nofail  0  2
```

After editing, test without rebooting:

```bash
sudo findmnt --verify --verbose
sudo mount --fake --verbose --all
sudo mount /srv/app-data
findmnt /srv/app-data
```

Be especially careful with mounts required for boot, remote access, identity services, or application data. A bad `fstab` entry can slow or block boot if the system waits for missing storage.

## Troubleshooting patterns

### The path is unexpectedly full

Separate block usage from inode usage and confirm the path's real mount.

```bash
df -hT /var/www
df -ih /var/www
findmnt /var/www
```

If `findmnt /var/www` reports `/` instead of the expected application volume, the service may be writing to the wrong filesystem.

### The mount is read-only

Check whether the filesystem was intentionally mounted read-only or remounted after errors.

```bash
findmnt -no SOURCE,FSTYPE,OPTIONS,TARGET /srv/app-data
journalctl -k --since "1 hour ago" | grep -Ei 'ext4|xfs|btrfs|error|readonly|read-only'
```

Do not blindly remount read-write after filesystem errors. Preserve logs and involve the owner of the storage or application.

### The device name changed

Compare labels and UUIDs instead of trusting `/dev/sdX` names.

```bash
lsblk -f
sudo blkid
findmnt --fstab
```

## Hands-on practice

Run this on a disposable VM or lab machine. It creates a small file-backed filesystem, mounts it, verifies it, and removes it.

1. Create a small lab image and filesystem:

   ```bash
   mkdir -p ~/mount-lab
   cd ~/mount-lab
   dd if=/dev/zero of=labfs.img bs=1M count=64
   mkfs.ext4 labfs.img
   ```

2. Mount it through a loop device:

   ```bash
   sudo mkdir -p /mnt/learn-linux-mount-lab
   sudo mount -o loop labfs.img /mnt/learn-linux-mount-lab
   findmnt /mnt/learn-linux-mount-lab
   df -hT /mnt/learn-linux-mount-lab
   ```

3. Write and verify a test file:

   ```bash
   echo "mount lab $(date)" | sudo tee /mnt/learn-linux-mount-lab/proof.txt
   cat /mnt/learn-linux-mount-lab/proof.txt
   ```

4. Unmount and clean up:

   ```bash
   sudo lsof +f -- /mnt/learn-linux-mount-lab || true
   sudo umount /mnt/learn-linux-mount-lab
   findmnt /mnt/learn-linux-mount-lab || echo "not mounted"
   rm -f labfs.img
   rmdir ~/mount-lab
   ```
