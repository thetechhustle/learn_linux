### 05.3 Organization of the File Tree: Know Where Things Belong

Linux presents one filesystem tree rooted at `/`. That tree is not just a
navigation convenience. It is an operational contract: configuration, logs,
package-managed programs, runtime files, user data, and application state tend
to live in different places because they have different owners and different
risk profiles.

When a system is healthy, you can usually tell what kind of data a path holds
before you edit, copy, delete, back up, or mount over it.

!!! abstract "What you will learn"
    - Recognize the operational meaning of common top-level directories.
    - Separate static package content from variable system state.
    - Find likely configuration, log, cache, runtime, and application data paths.
    - Verify whether a path is local, temporary, generated, package-managed, or app-owned.

!!! success "Operator principle"
    Before changing a path, identify what it is: configuration, state, cache,
    runtime data, user data, package-managed content, or mounted storage. The
    path's purpose tells you who owns it and how risky the change is.

## The root of the tree

The root directory `/` is the top of the visible filesystem namespace. Other
filesystems can be mounted under it, so a path may look like a normal directory
while actually pointing to a different disk, partition, network share, or
virtual filesystem.

Start with read-only evidence:

```bash
pwd
ls -ld /
findmnt /
```

`pwd` shows your current location. `ls -ld /` shows metadata for the root
directory itself. `findmnt /` shows the filesystem mounted there.

## Common top-level directories

Most Linux systems follow the Filesystem Hierarchy Standard closely enough that
these meanings are useful in day-to-day operations:

- `/bin` - essential user commands. On many modern distributions this is a
  symlink into `/usr/bin`.
- `/sbin` - essential administrative commands. On many modern distributions
  this is a symlink into `/usr/sbin`.
- `/boot` - bootloader files, kernels, initramfs images, and boot metadata.
- `/dev` - device nodes presented by the kernel and device manager.
- `/etc` - host-specific system and service configuration.
- `/home` - regular users' home directories.
- `/lib` and `/lib64` - essential shared libraries and loader files, often
  symlinks into `/usr/lib` or `/usr/lib64`.
- `/media` - removable-media mount points created by desktop or automount tools.
- `/mnt` - temporary manual mount points.
- `/opt` - optional third-party or vendor application installs.
- `/proc` - virtual process and kernel information generated by the kernel.
- `/run` - runtime state such as sockets, PID files, and service-generated
  metadata, usually cleared at boot.
- `/srv` - service data intentionally served by the system, such as web or file
  service content.
- `/tmp` - temporary files. Contents may be cleared automatically.
- `/usr` - shareable, mostly package-managed programs, libraries, and
  documentation.
- `/var` - variable state such as logs, databases, queues, spools, caches, and
  application data.

Do not assume every system has every directory, or that every directory is a
real directory. Verify:

```bash
ls -ld /bin /sbin /usr/bin /usr/sbin /etc /var /run /srv /opt 2>/dev/null
readlink /bin /sbin /lib /lib64 2>/dev/null || true
findmnt / /usr /var /home 2>/dev/null || true
```

The `readlink` command is especially useful on distributions that use the
merged `/usr` layout, where historical top-level paths point into `/usr`.

## Static content versus variable state

A useful mental split is static versus variable:

- `/usr` is mostly static package-managed content. Package managers expect to
  control it.
- `/etc` is host-specific configuration. Administrators and automation often
  control it.
- `/var` is variable system and application state. It changes while services
  run.
- `/run` is runtime state. It is usually recreated after reboot.
- `/tmp` is temporary working space. It is not a reliable long-term storage
  location.
- `/home` is user-owned data and configuration.

This split matters during incidents. A full `/var` often points to logs, cache,
spool, or application data growth. A surprising change under `/usr/bin` is more
likely a package, deployment, or integrity question. A missing socket under
`/run` may mean the service is stopped or failed to create its runtime files.

## Where to look first

Use the path type to choose the next inspection:

- Service configuration: `/etc/<service>/`, `/etc/default/`, `/etc/sysconfig/`,
  and systemd unit files.
- Logs: `/var/log/` or the systemd journal.
- Service data: `/var/lib/<service>/`.
- Caches: `/var/cache/`.
- Queues and spools: `/var/spool/`.
- Runtime sockets and PID files: `/run/`.
- Local administrator-installed software: `/usr/local/`.
- Vendor or bundled applications: `/opt/`.
- Served application data: `/srv/` or an application-specific directory.

Examples:

```bash
ls -ld /etc/ssh /var/log /var/lib /var/cache /run 2>/dev/null
systemctl cat ssh 2>/dev/null || systemctl cat sshd 2>/dev/null || true
journalctl -u ssh -n 20 --no-pager 2>/dev/null || true
```

The exact service name differs by distribution. The point is to build a short
trail from service name, to configuration, to logs, to runtime state.

## Package-managed paths and local paths

Be careful editing files under package-managed locations. Changes under `/usr`
may be overwritten by package upgrades unless the path is intentionally local,
such as `/usr/local`.

As a rule of thumb:

- Edit service configuration under `/etc`, preferably with backups or version
  control.
- Treat `/usr/bin`, `/usr/sbin`, `/usr/lib`, and package-owned files as managed
  by the operating system package manager.
- Put local admin scripts in `/usr/local/bin` when that is the site's convention.
- Treat `/var/lib/<service>` as application state, not disposable clutter.
- Treat `/var/cache` as more disposable than `/var/lib`, but still verify the
  service-specific meaning before deleting.

If available, ask the package manager who owns a file:

```bash
dpkg -S /bin/ls 2>/dev/null || rpm -qf /bin/ls 2>/dev/null || true
```

## Incident pattern: disk is full

When a deployment fails because disk is full, do not start by deleting random
large files. First identify which filesystem is full and what kind of data grew.

```bash
df -h
findmnt -T /var
du -xh --max-depth=1 /var 2>/dev/null | sort -h
```

Then interpret the result:

- Growth under `/var/log` suggests logs or journal retention.
- Growth under `/var/cache` may be cache data, often easier to rebuild.
- Growth under `/var/lib` may be databases, containers, package state, or other
  service-owned data. Treat it as high risk.
- Growth under `/tmp` may be old temporary work, but check whether active
  processes still use those files.

The safe sequence is:

1. Prove which filesystem is full.
2. Prove which top-level directory grew.
3. Identify the owning service or package.
4. Prefer service-supported cleanup commands or retention settings.
5. Re-check `df -h` and service health after the change.

## Hands-on practice

Run these on a lab machine or disposable VM:

```bash
pwd
ls -ld / /etc /usr /var /run /tmp /home 2>/dev/null
findmnt / /usr /var /home 2>/dev/null || true
readlink /bin /sbin /lib /lib64 2>/dev/null || true
du -xh --max-depth=1 /var 2>/dev/null | sort -h | tail
```

Write down:

1. Which top-level paths are real directories and which are symlinks.
2. Whether `/home`, `/var`, or `/usr` are separate mounted filesystems.
3. The largest visible child under `/var`.
4. Whether that largest child looks like logs, cache, state, or something else.
