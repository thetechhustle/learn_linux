### 05.5 File Attributes: Read the Metadata Before You Change the File

Files are more than names and contents. Linux tracks metadata that tells you
what kind of object a path is, who owns it, which permissions apply, how large
it is, when it changed, and sometimes which extra filesystem flags protect it.

Good operators inspect that metadata before changing permissions, ownership,
backup rules, cleanup scripts, or deployment paths.

!!! abstract "What you will learn"
    - Read the most important fields in `ls -l` and `stat` output.
    - Distinguish permissions from ownership, timestamps, size, links, and file type.
    - Use inode, link count, and timestamp evidence during troubleshooting.
    - Avoid common mistakes with `chmod`, `chown`, recursive changes, and immutable flags.

!!! success "Operator principle"
    Do not treat "file attributes" as only `rwx` permissions. Build a complete
    metadata picture first: type, mode, owner, group, inode, link count, size,
    timestamps, filesystem, and any extended attributes or special flags.

## Start with `ls -l`

The long listing format gives a compact view of common attributes:

```bash
ls -l /etc/passwd
```

Example output:

```text
-rw-r--r-- 1 root root 2484 Jan 10 12:20 /etc/passwd
```

Read it from left to right:

- `-` - file type. A regular file begins with `-`; directories begin with `d`;
  symlinks begin with `l`; devices, sockets, and pipes have their own markers.
- `rw-r--r--` - permission bits for owner, group, and others.
- `1` - hard-link count.
- `root` - owning user.
- `root` - owning group.
- `2484` - size in bytes for regular files.
- `Jan 10 12:20` - displayed modification time.
- `/etc/passwd` - path name shown by `ls`.

`ls` is convenient, but it is not the full truth. Use `stat` when details
matter.

## Use `stat` for exact metadata

`stat` shows the inode, device, permissions, ownership, timestamps, size, and
other metadata in a less compressed form:

```bash
stat /etc/passwd
```

Useful fields:

- `File` - the path you asked about.
- `Size` - size in bytes for regular files.
- `Blocks` - allocated disk blocks, which may differ from apparent size.
- `IO Block` - preferred I/O block size.
- `Device` - filesystem device identifier.
- `Inode` - the unique file object number within that filesystem.
- `Links` - hard-link count.
- `Access` - permission bits in symbolic and numeric form.
- `Uid` and `Gid` - owning user and group.
- `Access`, `Modify`, `Change`, `Birth` - timestamps when supported.

The exact output differs across Linux, BSD, and macOS, but the operational idea
is the same: prove the metadata instead of guessing from a path name.

## Permissions are only one attribute

Permission bits answer who may read, write, or execute:

```bash
ls -l ./script.sh
chmod u+x ./script.sh
ls -l ./script.sh
```

For regular files:

- `r` means the content can be read.
- `w` means the content can be modified or truncated.
- `x` means the kernel may execute the file as a program or script.

For directories, the bits have different operational meaning:

- `r` means directory names can be listed.
- `w` means entries can be created, renamed, or removed, if execute also allows
  traversal.
- `x` means the directory can be traversed and entries can be accessed by name.

That distinction matters. A directory without execute permission can look
especially confusing because a user may see its name but not reach files inside
it.

## Ownership and group control who the bits apply to

The permission triplets are evaluated against ownership:

```bash
ls -l /var/log
id
```

Linux checks:

1. Is the process running as the owning user?
2. If not, is the process in the owning group?
3. If not, use the "others" permission bits.

Changing ownership can be more disruptive than changing mode bits:

```bash
chown appuser:appgroup /srv/myapp/config.yml
```

Before running `chown`, verify the expected service user and group. On systemd
systems, this often comes from the unit file:

```bash
systemctl cat myapp 2>/dev/null | sed -n '/^\\[Service\\]/,/^\\[/p'
```

Do not recursively `chown` or `chmod` an application tree until you know which
subdirectories contain configuration, runtime state, logs, uploads, caches, and
package-managed files.

## Timestamps answer different questions

Linux commonly tracks:

- access time (`atime`) - when content was last read, depending on mount options.
- modification time (`mtime`) - when file content last changed.
- change time (`ctime`) - when inode metadata last changed, such as mode, owner,
  link count, or content update.
- birth/creation time - available on some filesystems and tools, not universal.

Use `stat` to inspect them:

```bash
stat ./example.txt
```

Incident examples:

- `mtime` changed after a deployment: the file content probably changed.
- `ctime` changed but `mtime` did not: ownership, permissions, or link metadata
  may have changed.
- `atime` is old: do not assume the file is unused unless you know the mount
  options and application behavior.

## Inodes and hard links

An inode is the filesystem's record for a file object. Multiple path names can
point to the same inode through hard links:

```bash
ln ./report.txt ./report-copy.txt
ls -li ./report.txt ./report-copy.txt
stat ./report.txt ./report-copy.txt
```

If two names show the same inode on the same filesystem, they are the same file
object. Editing one changes the other because there is only one underlying file
content record.

This matters for cleanup and disk usage. Removing one hard link removes one
name, not necessarily the file data. The data is freed only when the link count
drops to zero and no process still has the file open.

## Extended attributes and special flags

Some filesystems support extra metadata beyond standard mode bits. Linux tools
often include:

```bash
getfattr -d ./file 2>/dev/null || true
lsattr ./file 2>/dev/null || true
```

Common examples:

- extended attributes used by security systems, desktop tools, backup tools, or
  applications.
- immutable or append-only flags on filesystems that support `chattr`.

If a file appears writable by normal permissions but still refuses changes, look
for filesystem mount options, immutable flags, access-control lists, SELinux or
AppArmor policy, and application-level locking before forcing the issue.

## Safer change pattern

Before changing attributes:

```bash
stat ./target
ls -ld ./target
id
findmnt -T ./target
```

Then choose the smallest change:

- Use symbolic `chmod` when you want to add or remove one bit, such as
  `chmod g+w ./shared`.
- Use numeric `chmod` when you want to set the full mode intentionally, such as
  `chmod 0640 ./config.yml`.
- Use `chown user:group` only when ownership is the real problem.
- Avoid recursive changes until you can explain exactly which subtree each path
  type belongs to.

For high-risk paths, preview first:

```bash
find /srv/myapp -maxdepth 2 -printf '%M %u %g %p\n' 2>/dev/null
```

Then make one narrow change and re-check the metadata.

## Hands-on practice

Run this in a temporary lab directory:

```bash
mkdir -p /tmp/file-attributes-lab
cd /tmp/file-attributes-lab
printf 'hello\n' > example.txt
ln example.txt hardlink.txt
ln -s example.txt symlink.txt
mkdir subdir
ls -li
stat example.txt hardlink.txt symlink.txt subdir
chmod u+x example.txt
ls -l example.txt
```

Clean up after the lab:

```bash
cd /
rm -rf /tmp/file-attributes-lab
```

Do not use recursive `chmod`, `chown`, or cleanup commands outside a disposable
lab until you have practiced reading the metadata trail.
