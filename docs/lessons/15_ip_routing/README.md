# Chapter 15: IP Routing

Routing is where a Linux operator moves from asking "is this host connected?" to asking "which path will this packet take, and why?" A routing problem can look like DNS failure, firewall failure, an application outage, or random packet loss until you prove the forwarding path with evidence.

This chapter focuses on the habits that keep routing work controlled: inspect before changing, separate local host routing from router forwarding, prefer reversible tests, and record enough context that another operator can continue the investigation.

## Learning Outcomes

By the end of this chapter, you should be able to:

- Read a Linux routing table and explain the selected destination, gateway, source address, metric, and interface.
- Distinguish packet forwarding on a router from ordinary traffic generated by a host.
- Use tools such as `ip route`, `ip rule`, `ip neigh`, `tracepath`, `traceroute`, `ss`, and packet captures to build an evidence trail.
- Recognize when static routes are enough and when a routing daemon or dynamic routing protocol is a better fit.
- Compare routing protocols by operational scope, convergence behavior, failure domains, and administrative risk.
- Plan routing changes with rollback notes, out-of-band access, and pre-change reachability checks.

## A Safe Routing Workflow

Routing changes can disconnect the very session you are using to fix the system. Treat remote changes as production changes even in a small lab.

1. Record the current path with read-only commands such as `ip route get <destination>`, `ip route show`, `ip rule show`, and `tracepath <destination>`.
2. Identify the control point: local host route, default gateway, router forwarding setting, firewall policy, routing daemon, cloud route table, or upstream network device.
3. Make the smallest reversible change you can test. Prefer temporary `ip route add` commands in a lab before editing persistent network configuration.
4. Verify both directions of traffic when possible. A forward path that works without a return path is still broken.
5. Save the command, output, timestamp, and rollback command in your notes before moving to the next change.

## Lab Notes To Keep

For each routing lab or incident drill, capture:

- the source and destination addresses you tested
- the route selected by `ip route get`
- neighbor evidence for local next hops
- traceroute or tracepath output before and after the change
- any firewall, NAT, cloud, or router configuration that affects the path
- the rollback step you would use if the change made access worse

## Common Routing Failure Patterns

- A missing or wrong default route sends all off-link traffic nowhere useful.
- Two systems can reach the same router, but the router is not forwarding between networks.
- The forward route exists, but the return route is missing or points to a different gateway.
- Multiple routes match the same destination and the metric or policy rule selects the unexpected one.
- MTU problems allow small probes to pass while larger application traffic stalls.
- Firewalls or NAT rules hide the real routing symptom until you test each layer separately.
