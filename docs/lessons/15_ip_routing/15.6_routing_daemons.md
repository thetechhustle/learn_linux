## 15.6 Routing Daemons

Routing daemons are the user-space programs that learn routes from neighbors,
choose best paths, and install the selected routes into the kernel forwarding
table. Linux still forwards packets in the kernel, but a routing daemon can keep
that table updated when links, peers, or policy change.

Common examples include FRRouting (`frr`), BIRD, OpenBGPD, and vendor-specific
routing stacks. This lesson uses FRRouting because it is widely packaged on
Linux and exposes separate daemons for protocols such as BGP and OSPF.

!!! abstract "What you will learn"
    - Explain the boundary between the kernel routing table and routing daemons.
    - Inspect FRRouting service, daemon, neighbor, and installed-route state.
    - Make routing-daemon changes with a rollback path and verification plan.
    - Capture useful handoff notes when dynamic routing is part of an incident.

!!! warning "Do not experiment on production routing"
    Dynamic routing can move traffic for many hosts at once. Practice in a lab,
    out-of-band console, disposable VM, or network namespace first. On production
    routers, record the current configuration and have a rollback command before
    changing neighbors, advertisements, metrics, or route filters.

## Where the daemon fits

A routing daemon usually has three jobs:

1. Form adjacencies or sessions with routing peers.
2. Learn candidate routes and apply local routing policy.
3. Install accepted routes into the kernel routing table.

The kernel table is still the forwarding source of truth:

```bash
ip route show
ip -6 route show
```

The daemon explains why dynamic routes are present, which peer supplied them,
and why one path won over another. For FRRouting, `vtysh` is the usual command
interface:

```bash
sudo vtysh -c 'show running-config'
sudo vtysh -c 'show ip route'
```

Compare daemon output with kernel output whenever troubleshooting. If FRR thinks
a route exists but `ip route` does not show it, investigate zebra, route
installation, permissions, VRF/table selection, or a filtering rule.

## Inspect the service safely

Start with read-only evidence before changing configuration:

```bash
systemctl status frr --no-pager
systemctl is-enabled frr
journalctl -u frr -n 80 --no-pager
```

FRRouting enables individual daemons from `/etc/frr/daemons`. The important
default is `zebra`, which coordinates route installation with the kernel. Other
daemons handle specific protocols:

```text
zebra=yes
bgpd=yes
ospfd=no
isisd=no
ripd=no
```

Use package documentation for your distribution, but expect the service to read
that file during startup. A daemon set to `no` usually will not run even if its
protocol configuration exists.

## Check protocol health

For BGP, focus on session state, peer address, uptime, prefixes received, and
prefixes accepted:

```bash
sudo vtysh -c 'show bgp summary'
sudo vtysh -c 'show ip bgp'
```

For OSPF, focus on neighbor state, interface area, router ID, and the routes
selected from the link-state database:

```bash
sudo vtysh -c 'show ip ospf neighbor'
sudo vtysh -c 'show ip ospf interface'
sudo vtysh -c 'show ip route ospf'
```

Healthy output is protocol-specific, but the operator questions are consistent:

- Is the expected daemon running?
- Is the expected peer or neighbor established?
- Are routes being learned from the peer?
- Are the right routes being installed into the kernel?
- Are filters, metrics, or administrative distance changing the selected path?

## Make changes with a rollback path

Routing daemon configuration is powerful because a small edit can affect many
destinations. Treat changes like production firewall or DNS changes.

Before editing, save the current state:

```bash
sudo vtysh -c 'show running-config' > frr-before.txt
ip route show > kernel-routes-before.txt
```

Make one change at a time. For example, enabling BGP in FRRouting usually
requires enabling `bgpd` in `/etc/frr/daemons`, adding BGP configuration, and
reloading or restarting FRR:

```bash
sudoedit /etc/frr/daemons
sudo vtysh
```

Inside `vtysh`, configuration follows a network-device style:

```text
configure terminal
router bgp 64512
 neighbor 192.0.2.2 remote-as 64513
 address-family ipv4 unicast
  network 10.10.0.0/24
 exit-address-family
end
write memory
```

In a lab, restart or reload as appropriate for the distribution:

```bash
sudo systemctl reload frr || sudo systemctl restart frr
```

On a remote production router, prefer a method that can automatically roll back
or preserve your management path. Avoid restarting all routing daemons during an
incident unless you know the blast radius.

## Verify after a change

A routing-daemon change is not complete until the data plane matches the intent.
Collect before and after evidence:

```bash
sudo vtysh -c 'show bgp summary'
sudo vtysh -c 'show ip route'
ip route get 10.10.0.42
ping -c 3 10.10.0.42
traceroute 10.10.0.42
```

If the route appears but traffic fails, continue below routing:

- Check the selected outgoing interface with `ip route get`.
- Check neighbor resolution with `ip neigh show`.
- Check local firewall policy with `sudo nft list ruleset` or the host's
  approved firewall tool.
- Confirm the return path from the other network.
- Confirm MTU if large packets fail but small packets pass.

## Common failure patterns

- The protocol daemon is disabled in `/etc/frr/daemons`.
- `zebra` is unhealthy, so learned routes are not installed into the kernel.
- A BGP neighbor is stuck in `Active`, `Connect`, or idle due to addressing,
  firewall, AS-number, TTL, or authentication mismatch.
- OSPF neighbors never reach full adjacency because of area, network type,
  hello/dead timer, MTU, or authentication mismatch.
- A prefix is learned but filtered by route maps, prefix lists, administrative
  distance, or max-prefix limits.
- The forward path is correct, but the return path points somewhere else.
- A default route from the daemon overrides a safer static or management route.

## Lab: FRR evidence trail

Use a disposable VM or container lab that already has FRRouting installed.

1. Record service state:

   ```bash
   systemctl status frr --no-pager
   ```

2. Record enabled FRR daemons:

   ```bash
   grep -E '^(zebra|bgpd|ospfd|ripd|isisd)=' /etc/frr/daemons
   ```

3. Compare daemon routes with kernel routes:

   ```bash
   sudo vtysh -c 'show ip route'
   ip route show
   ```

4. If the lab has BGP or OSPF configured, capture neighbor state:

   ```bash
   sudo vtysh -c 'show bgp summary'
   sudo vtysh -c 'show ip ospf neighbor'
   ```

5. Write a short handoff note:

   ```text
   FRR service:
   Enabled daemons:
   Dynamic neighbors:
   Routes learned:
   Routes installed in kernel:
   One risk before changing:
   Rollback command or file:
   ```
