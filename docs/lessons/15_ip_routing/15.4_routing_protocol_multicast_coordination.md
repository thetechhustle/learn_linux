# 15.4 Routing Protocol Multicast Coordination

Multicast lets one sender deliver traffic to many interested receivers without sending a separate unicast stream to each host. That efficiency comes with a catch: multicast forwarding has its own control plane. Linux operators need to separate ordinary unicast routing, local multicast group membership, and multicast routing state before making changes.

This lesson focuses on how multicast coordination works operationally, how it interacts with unicast routing, and what evidence to collect before enabling or debugging it.

!!! abstract "What you will learn"
    - Distinguish multicast group membership from multicast routing.
    - Recognize the role of IGMP, MLD, PIM, and reverse path forwarding checks.
    - Inspect multicast addresses and group subscriptions on Linux.
    - Understand why multicast routing depends on the unicast routing table.
    - Troubleshoot common multicast failures without guessing.

!!! warning "Production caution"
    Multicast is often used by discovery protocols, streaming systems, monitoring tools, clustered applications, and network infrastructure. Do not enable multicast forwarding, change PIM, or modify querier behavior on a shared network without knowing which VLAN, receiver group, and upstream router will be affected.

## Multicast Is Not Broadcast

Broadcast traffic is delivered to every host in a broadcast domain. Multicast traffic is delivered to hosts that join a group. IPv4 multicast addresses live in `224.0.0.0/4`; IPv6 multicast addresses begin with `ff00::/8`.

Important IPv4 multicast ranges include:

- `224.0.0.0/24`: local network control traffic, not forwarded by routers
- `239.0.0.0/8`: administratively scoped private multicast
- `232.0.0.0/8`: source-specific multicast range

Do not treat all multicast addresses the same. Some groups are link-local control groups and should never be routed beyond the local segment.

## The Moving Pieces

Multicast forwarding usually involves several pieces:

- **Sender**: sends packets to a multicast group address.
- **Receiver**: joins a multicast group.
- **IGMP or MLD**: lets receivers tell the local network they want group traffic.
- **Multicast router**: forwards multicast traffic between networks.
- **PIM**: coordinates multicast forwarding between routers.
- **Unicast routing table**: provides the path checks multicast protocols rely on.

For IPv4, host group membership is managed by IGMP. For IPv6, the equivalent role is handled by MLD. Routing between networks is commonly handled by Protocol Independent Multicast, especially PIM Sparse Mode.

## Local Group Membership

Start by inspecting local membership before assuming a routing problem.

```bash
ip maddr show
ip -6 maddr show
netstat -g
```

You can also watch packets directly:

```bash
sudo tcpdump -ni eth0 igmp
sudo tcpdump -ni eth0 ip multicast
```

For IPv6:

```bash
sudo tcpdump -ni eth0 icmp6 and 'ip6[40] == 130 or ip6[40] == 131 or ip6[40] == 132 or ip6[40] == 143'
```

If no receiver has joined the group on a segment, a well-behaved multicast network may not forward the stream there.

## Multicast Routing Is Separate

A Linux host can join multicast groups without acting as a multicast router. Multicast routing requires kernel support plus a multicast routing daemon or tool to install multicast forwarding cache entries.

Useful inspection commands include:

```bash
ip mroute show
ip -s mroute show
cat /proc/net/ip_mr_cache
cat /proc/net/ip_mr_vif
```

On systems using FRRouting with PIM:

```bash
vtysh -c 'show ip pim interface'
vtysh -c 'show ip pim neighbor'
vtysh -c 'show ip pim upstream'
vtysh -c 'show ip mroute'
```

If `ip maddr` shows local group membership but `ip mroute` is empty, that may be normal for a host that is only receiving locally. It is a problem only if the machine is expected to route multicast between interfaces.

## Why Unicast Routing Still Matters

PIM is called protocol independent because it does not build its own full unicast topology database. It relies on the existing unicast routing table to decide where a multicast source or rendezvous point should be reached.

This creates an important operational rule: multicast routing can fail because unicast routing is wrong.

Check the reverse path toward the source:

```bash
ip route get 198.51.100.25
vtysh -c 'show ip route 198.51.100.25'
```

If the best unicast route to the source points out a different interface than the multicast packet arrived on, reverse path forwarding logic may reject the packet. That protects the network from loops, but it can surprise operators when asymmetric routing exists.

## IGMP Querier and Snooping

Switches often use IGMP snooping to avoid flooding multicast to every switch port. Snooping needs a querier on the VLAN. Without a querier, group membership state may age out and multicast delivery can become inconsistent.

Evidence to collect:

- Is IGMP snooping enabled on the switch or bridge?
- Is there exactly one expected querier for the VLAN?
- Are receiver ports listed as members of the group?
- Is the multicast sender on the expected VLAN?

On Linux bridges, inspect multicast snooping settings:

```bash
bridge link show
ip -d link show type bridge
```

Distribution and switch-specific commands vary, so keep switch evidence in the incident notes.

## PIM Sparse Mode in Plain Terms

PIM Sparse Mode assumes receivers are not everywhere. Receivers join a group, routers build a tree, and traffic flows only where requested.

The common terms are:

- **RP**: rendezvous point, a meeting place for sources and receivers.
- **RPF**: reverse path forwarding check toward source or RP.
- **Shared tree**: initial tree through the RP.
- **Shortest path tree**: optimized tree directly toward the source.

When PIM-SM fails, check:

```bash
vtysh -c 'show ip pim rp-info'
vtysh -c 'show ip pim neighbor'
vtysh -c 'show ip pim upstream'
vtysh -c 'show ip mroute'
```

Look for missing RP configuration, missing PIM neighbors, failed RPF checks, and routes that never install into the multicast routing table.

## Common Failure Patterns

### Receiver Joined, No Traffic Arrives

Check whether the receiver is actually joined:

```bash
ip maddr show dev eth0
sudo tcpdump -ni eth0 igmp
```

Then check whether multicast packets reach the receiver VLAN:

```bash
sudo tcpdump -ni eth0 host 239.1.2.3
```

If joins are present but traffic is absent, inspect switch snooping, VLAN boundaries, multicast routing state, and upstream PIM state.

### Traffic Reaches Router but Is Not Forwarded

Inspect multicast routes and RPF decisions:

```bash
ip mroute show
vtysh -c 'show ip mroute'
ip route get <source-ip>
```

If the incoming interface does not match the expected reverse path, fix the unicast route or multicast design rather than forcing traffic through blindly.

### Everything Works on One VLAN Only

That usually means hosts can join and receive locally, but no multicast routing exists between VLANs. Confirm whether the router is configured for multicast forwarding and whether PIM or the required multicast daemon is active on both interfaces.

### Multicast Floods Too Broadly

This points toward missing IGMP snooping, missing querier behavior, or a switch/router treating the group as unknown multicast. Check switch multicast state and group membership tables.

## Safe Troubleshooting Flow

Use this order to avoid chasing the wrong layer:

1. Identify source IP, group address, receiver IP, VLAN, and expected path.
2. Confirm receiver group membership with `ip maddr` or packet capture.
3. Confirm sender packets exist with `tcpdump` near the sender.
4. Confirm unicast route from router toward the source.
5. Confirm multicast routing state with `ip mroute` or FRR PIM commands.
6. Confirm switch snooping and querier state for the VLAN.
7. Test delivery near the receiver.
8. Record the evidence before changing daemon or switch configuration.

## Lab Practice

On a disposable lab network, practice reading multicast state without enabling routing first.

1. Run `ip maddr show` on a Linux host.
2. Start a packet capture for IGMP on the active interface.
3. Run an application or tool that joins a multicast group.
4. Confirm that the local group membership changed.
5. Compare `ip maddr show` with `ip mroute show`.
6. Explain why local group membership does not automatically mean the host is a multicast router.
