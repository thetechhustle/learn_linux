# 15.2 Routing Daemons and Routing Protocols

Static routes are enough when the network is small, stable, and fully known. Routing protocols matter when routers need to exchange reachability information automatically. A routing daemon is the Linux process that speaks those protocols, learns routes from neighbors, and installs selected routes into the kernel routing table.

The operator's job is not to memorize every protocol. It is to know which daemon owns a route, what neighbor supplied it, whether the route reached the kernel, and how to back out a bad routing change before traffic is damaged.

!!! abstract "What you will learn"
    - Explain the difference between the kernel routing table, a routing daemon, and a routing protocol.
    - Recognize common protocol roles: OSPF, BGP, RIP, IS-IS, and static routing inside a daemon.
    - Inspect FRRouting without guessing from stale config files.
    - Verify whether daemon-learned routes reached the Linux kernel.
    - Troubleshoot neighbor, policy, and redistribution failures safely.

!!! warning "Production caution"
    Routing protocols can affect many hosts at once. Do not enable, restart, redistribute, or advertise routes on a production router without a reviewed change plan, a rollback path, and a console or out-of-band access option.

## The Layers Involved

Linux forwarding usually has three layers:

1. The **kernel forwarding table** decides where each packet goes.
2. A **routing daemon** computes candidate routes and programs the kernel.
3. A **routing protocol** exchanges reachability information with other routers.

The kernel does not speak OSPF or BGP by itself. It forwards packets based on the routes it has. A routing daemon such as FRRouting, BIRD, or OpenBGPD handles protocol sessions, applies policy, chooses best paths, and installs selected routes into the kernel through netlink.

This separation is useful during incidents. If a packet is not forwarding as expected, ask:

- Is the route present in the kernel table?
- If not, did the daemon learn it?
- If the daemon learned it, did policy reject it?
- If the daemon never learned it, is the neighbor/session healthy?

## Common Protocol Roles

### OSPF

Open Shortest Path First is an interior gateway protocol. It is common inside one organization, data center, campus, or lab. Routers form adjacencies, flood link-state information, and independently compute shortest paths.

Use OSPF when:

- routers are under one administrative control
- topology changes should converge automatically
- internal subnets need redundant paths

### BGP

Border Gateway Protocol is a path-vector protocol. It is used between autonomous systems on the internet, but it is also common inside large private networks, Kubernetes environments, data centers, and cloud edge designs because its policy controls are strong.

Use BGP when:

- route policy is more important than automatic shortest-path behavior
- you need controlled exchange between administrative domains
- cloud, edge, or service networks advertise prefixes dynamically

### RIP

Routing Information Protocol is simple and old. It uses hop count and has limited scale. You should recognize it, but it is rarely the right new design choice.

### IS-IS

Intermediate System to Intermediate System is another link-state protocol. It is common in some service-provider and large network environments. Linux operators may encounter it through FRRouting or BIRD, but many small environments never need it.

### Static Routes in a Daemon

Routing daemons often manage static routes too. This can be useful when you want one place to apply route maps, redistribution rules, and operational visibility. It also means a route that looks static in Linux may actually be owned by the daemon.

## FRRouting on Linux

FRRouting, usually called FRR, is a common Linux routing suite. It includes separate daemons for protocols such as BGP and OSPF plus a central zebra daemon that coordinates route installation into the kernel.

Common FRR components include:

- `zebra`: kernel route interface and route manager
- `bgpd`: BGP protocol daemon
- `ospfd`: OSPFv2 daemon for IPv4
- `ospf6d`: OSPFv3 daemon for IPv6
- `staticd`: static route daemon
- `vtysh`: command shell for inspecting and configuring FRR

Package and service names vary by distribution, but the operational shape is usually similar:

```bash
systemctl status frr
systemctl status zebra
vtysh -c 'show running-config'
vtysh -c 'show ip route'
```

Many distributions control enabled FRR daemons through `/etc/frr/daemons` and configuration through `/etc/frr/frr.conf`. Always confirm how your distribution packages FRR before editing files or restarting services.

## Inspect Before Changing

Start with read-only evidence.

```bash
ip route
ip -6 route
ip route get 203.0.113.10
systemctl status frr --no-pager
vtysh -c 'show ip route'
vtysh -c 'show ipv6 route'
```

Compare the daemon's view with the kernel's view:

```bash
vtysh -c 'show ip route 10.20.0.0/16'
ip route show 10.20.0.0/16
```

If FRR shows the route but `ip route` does not, the issue is probably route installation, administrative distance, policy, table selection, or daemon/kernel communication. If FRR does not show the route, look at the relevant neighbor or protocol database.

## OSPF Evidence

For OSPF, first check whether neighbors are fully adjacent.

```bash
vtysh -c 'show ip ospf neighbor'
vtysh -c 'show ip ospf interface'
vtysh -c 'show ip ospf route'
```

Useful questions:

- Are expected neighbors present?
- Are they stuck in an intermediate state rather than `Full`?
- Are hello/dead timers compatible?
- Are interfaces in the expected area?
- Are network types and authentication settings compatible?

If neighbors are healthy but routes are missing, inspect the link-state database and route selection:

```bash
vtysh -c 'show ip ospf database'
vtysh -c 'show ip route ospf'
```

## BGP Evidence

For BGP, session state comes first.

```bash
vtysh -c 'show bgp summary'
vtysh -c 'show bgp ipv4 unicast'
vtysh -c 'show bgp ipv6 unicast'
```

Useful questions:

- Is the peer `Established`?
- Are prefixes received?
- Are prefixes accepted after route policy?
- Is the selected best path installed in the kernel?
- Are you advertising only the prefixes you intended?

To inspect one route:

```bash
vtysh -c 'show bgp ipv4 unicast 10.20.0.0/16'
ip route show 10.20.0.0/16
```

BGP often fails because of policy rather than connectivity. Prefix lists, route maps, AS numbers, next-hop handling, and maximum-prefix limits can all make a session look healthy while routes are rejected.

## Redistribution Risk

Redistribution means taking routes learned from one source and advertising them into another protocol. It is powerful and dangerous.

Examples:

- redistribute connected routes into OSPF
- redistribute static routes into BGP
- redistribute OSPF routes into BGP

The risk is accidental route leaks. A single broad redistribution rule can advertise management networks, default routes, lab networks, VPN prefixes, or routes learned from another peer.

Before redistributing, write down:

- exact prefixes that should be advertised
- exact prefixes that must never be advertised
- protocol boundary involved
- route map or prefix list enforcing the boundary
- rollback command or config restore path

Then verify the advertisement from both sides:

```bash
vtysh -c 'show running-config'
vtysh -c 'show bgp ipv4 unicast neighbors 192.0.2.2 advertised-routes'
vtysh -c 'show ip ospf route'
```

## Common Failure Patterns

### Neighbor Never Forms

Check basic reachability and local firewall rules:

```bash
ping -c 3 192.0.2.2
ip route get 192.0.2.2
sudo nft list ruleset
```

Then check protocol-specific settings: interface, area, timers, authentication, AS number, source address, and TTL/hop expectations.

### Daemon Learned the Route but Kernel Did Not

Compare daemon routes with kernel routes:

```bash
vtysh -c 'show ip route'
ip route
```

Look for route preference conflicts, route table differences, disabled zebra, service errors, or another route with a better administrative distance/metric.

### Kernel Has the Route but Traffic Still Fails

Routing is only one piece. Check forwarding, firewall policy, reverse path filtering, and return traffic:

```bash
sysctl net.ipv4.ip_forward
sudo nft list ruleset
sysctl net.ipv4.conf.all.rp_filter
sudo tcpdump -ni any host 10.20.0.10
```

### Routes Flap

Route flapping usually means instability in the underlying link, neighbor timers, interface state, or policy. Use logs and protocol timestamps:

```bash
journalctl -u frr --since '30 minutes ago'
vtysh -c 'show bgp summary'
vtysh -c 'show ip ospf neighbor'
```

Do not hide flapping by only increasing timers. Find the underlying cause.

## Safe Change Flow

Use a repeatable flow for routing daemon changes:

1. Capture current kernel routes, daemon routes, neighbor state, and config.
2. Confirm console, rollback, and maintenance-window expectations.
3. Apply the smallest config change.
4. Verify neighbor state.
5. Verify learned and advertised routes.
6. Verify kernel route installation.
7. Test real traffic in both directions.
8. Save or persist the config only after verification.

Example evidence capture:

```bash
ip route > before-ip-route.txt
ip -6 route > before-ipv6-route.txt
vtysh -c 'show running-config' > before-frr.conf
vtysh -c 'show ip route' > before-frr-routes.txt
```

## Lab Practice

On a disposable lab, install FRR and inspect its default state. Do not enable routing protocols on a production network for this exercise.

1. Start with `ip route` and `vtysh -c 'show ip route'`.
2. Identify whether FRR is installing any routes into the kernel.
3. Enable only a lab-safe daemon, such as `staticd`, if your distribution requires explicit daemon enablement.
4. Add one test route in the lab.
5. Confirm whether the route appears in FRR and in `ip route`.
6. Remove the test route and confirm the kernel table returns to the original state.
