## 15.3 Protocols On Parade

Routing problems often look like application problems at first. A web request
times out, DNS seems slow, a monitoring check goes red, or a database client
hangs. Before changing routes, identify which protocol is failing and what that
protocol can prove about the path.

!!! abstract "What you will learn"
    - Distinguish IP, TCP, UDP, ICMP, and multicast evidence during routing triage.
    - Use Linux tools to connect protocol symptoms to route, firewall, and service state.
    - Avoid treating every timeout as a routing-table problem.

!!! example "Field story"
    An application team reports that traffic between two subnets is broken.
    `ping` works, but the HTTPS client times out. The routing table is only one
    part of the evidence. You also need to prove that TCP can complete a
    connection, that return traffic is allowed, and that no firewall or listener
    issue is being misread as a route failure.

!!! success "Operator principle"
    Match the test to the protocol. ICMP reachability, TCP sessions, UDP queries,
    and multicast membership prove different things.

## Start with IP: the path decision

IP is the network-layer protocol that routing tables act on. When a packet
leaves a Linux host, the kernel chooses an outgoing interface, next hop, and
source address from the route table and local address configuration.

```bash
ip route
ip route get 203.0.113.10
ip -brief address
```

`ip route get` is especially useful because it asks the kernel what it would do
for one destination. Capture the selected source address and interface in your
notes before changing anything.

Common IP-layer findings:

- No matching route, so traffic follows the wrong default gateway.
- A more specific route sends traffic to an unexpected next hop.
- The selected source address is not allowed by the remote firewall or return path.
- A route exists, but the next-hop neighbor cannot be reached on the local link.

## ICMP: reachability and path feedback

ICMP carries control and error messages. `ping` uses ICMP echo request and echo
reply, but ICMP also reports conditions such as unreachable networks and packets
that exceed the path MTU.

```bash
ping -c 4 203.0.113.10
tracepath 203.0.113.10
traceroute 203.0.113.10
```

Use ICMP results carefully. A successful ping proves some bidirectional IP
reachability, not that TCP or UDP application traffic is allowed. A failed ping
does not prove the route is broken, because many networks block ICMP echo.

## TCP: connection setup and state

TCP is connection-oriented. When TCP fails, the routing table might be wrong,
but so might the service listener, host firewall, network ACL, return path, or
middlebox policy.

```bash
ss -nt state established
ss -lnt
curl -v --connect-timeout 5 https://example.com/
```

Look for the failure shape:

- `Connection refused` usually means the host replied but nothing is listening,
  or a firewall actively rejected the connection.
- A connection timeout often means packets or replies are being dropped.
- A completed TCP handshake followed by application failure points above routing.

For a local service, compare listener state with the route decision:

```bash
ss -lntp
ip route get 198.51.100.25
```

## UDP: request and response without a handshake

UDP has no connection handshake, so a route or firewall problem can look like
silence. DNS, NTP, syslog, DHCP, and many telemetry systems use UDP.

```bash
ss -anu
dig @8.8.8.8 example.com
nc -vzu 198.51.100.25 123
```

With UDP, prefer a protocol-aware test when one exists. A DNS query gives better
evidence than only seeing an open UDP socket. If a UDP client sends traffic and
gets no response, check both directions: outbound policy, the route to the
server, server-side policy, and the server route back to the client.

## Multicast and IGMP: group membership matters

Multicast traffic is delivered to a group, not to one ordinary unicast
destination. IGMP is used by IPv4 hosts to report multicast group membership to
local network equipment. Multicast routing and switching problems often appear
as "the sender is working but receivers see nothing."

```bash
ip maddr show
ss -g
ip route show table all | grep -i multicast
```

When multicast fails, collect:

- The multicast group address and UDP port.
- The receiver interface that joined the group.
- Whether the receiver and sender are on the same segment or require multicast routing.
- Switch, router, or cloud-network support for multicast forwarding.

## Packet capture: useful, but handle it carefully

Packet capture can prove whether traffic leaves or reaches an interface. It can
also expose sensitive data, so keep captures short, targeted, and stored only in
approved locations.

```bash
sudo tcpdump -ni eth0 host 203.0.113.10
sudo tcpdump -ni eth0 'icmp or tcp port 443 or udp port 53'
```

Before running `tcpdump` on a shared system, define the interface, host, port,
duration, and who may view the output. Prefer terminal output for short triage
and avoid writing capture files unless you need deeper analysis.

## Troubleshooting flow

Use this sequence when protocol symptoms point toward routing:

1. Identify the failing protocol, destination, and port.
2. Check the local route decision with `ip route get`.
3. Confirm local address and listener state with `ip -brief address` and `ss`.
4. Run a protocol-matched test: ICMP for reachability, TCP for connection setup,
   UDP with a protocol-aware client, or multicast group inspection.
5. If needed, capture one narrow packet sample on the expected interface.
6. Change only the smallest route, firewall, listener, or service setting that
   matches the evidence.
7. Re-run the same test and record the before/after result.

## Hands-on practice

Run these on a disposable VM, container, or lab network.

1. Pick one reachable destination and record `ip route get <destination>`.
2. Test the same destination with one ICMP command and one TCP or UDP command.
3. Use `ss` to inspect matching local socket state.
4. Write a short note explaining what each protocol test proved and what it did
   not prove.
5. Change nothing on the host unless you are in a lab you can rebuild.
