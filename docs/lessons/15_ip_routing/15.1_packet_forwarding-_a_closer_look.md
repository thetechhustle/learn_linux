## 15.1 Packet Forwarding: A Closer Look

!!! abstract "What you will learn"
    - Explain the difference between routing decisions and packet forwarding.
    - Inspect how Linux chooses an egress interface and next hop for a packet.
    - Verify whether a Linux host is acting as a router.
    - Identify common blockers such as disabled forwarding, firewall policy, reverse-path filtering, NAT, and missing return routes.

!!! example "Field story"
    A Linux VM has two interfaces: one on a private application subnet and one on a shared services subnet. Hosts on each side can ping the VM, but traffic will not cross through it. The route table looks plausible, yet forwarding still fails.

!!! success "Operator principle"
    Packet forwarding is not magic. A forwarded packet needs an ingress interface, a route decision, permission to forward, an egress interface, and a working return path.

## Routing vs Forwarding

Routing and forwarding are related, but they are not the same job.

- **Routing** decides where traffic should go. It uses routes, metrics, policy rules, and sometimes routing protocols.
- **Forwarding** moves a packet from one interface to another based on that decision.

A Linux host can have routes without forwarding packets for other machines. Most ordinary servers and laptops route their own traffic only. A router, firewall, VPN gateway, container host, or NAT box may forward traffic between networks.

## The Forwarding Decision

When Linux handles an IP packet, the broad decision flow is:

1. Packet arrives on an interface.
2. Kernel decides whether the destination is local.
3. If local, the packet is delivered to a local socket or service.
4. If not local, Linux checks whether forwarding is enabled.
5. Linux performs a route lookup for the destination.
6. Firewall, policy routing, NAT, and reverse-path checks may affect the packet.
7. Packet leaves through the selected egress interface.
8. The return packet must have a valid path back.

Any step can fail.

## Inspect The Local Routing View

Start with read-only evidence:

```bash
ip addr show
ip route show
ip rule show
ip -s link show
```

Use `ip route get` to ask Linux for the exact decision it would make for a destination:

```bash
ip route get 8.8.8.8
ip route get 10.20.30.15
ip route get 10.20.30.15 from 10.10.10.25
```

This is often better than staring at the whole route table because it shows the selected route, source address, gateway, and interface for a specific packet.

Example:

```text
10.20.30.15 via 10.10.10.1 dev enp1s0 src 10.10.10.25
```

This says Linux would send traffic for `10.20.30.15` to next hop `10.10.10.1` through `enp1s0`, using source address `10.10.10.25`.

## Check Whether Forwarding Is Enabled

IPv4 forwarding:

```bash
sysctl net.ipv4.ip_forward
```

IPv6 forwarding:

```bash
sysctl net.ipv6.conf.all.forwarding
```

Expected router-style values:

```text
net.ipv4.ip_forward = 1
net.ipv6.conf.all.forwarding = 1
```

Expected ordinary host values are often `0`.

Temporary test change for IPv4:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

Persistent changes depend on your distribution and should be made through a managed configuration file, not by typing commands during an incident and forgetting them.

## Firewall And Forwarding Policy

Forwarding can be enabled and still blocked by firewall rules.

For `nftables`:

```bash
sudo nft list ruleset
```

For systems still using iptables tooling:

```bash
sudo iptables -S
sudo iptables -S FORWARD
```

Look for:

- default drop policies
- rules that allow established traffic but not new forwarded traffic
- interface-specific rules
- source or destination subnet restrictions
- NAT rules in `postrouting`
- connection tracking state

Use counters where available. A rule with an increasing counter may tell you where traffic is being accepted or dropped.

## NAT vs Routing

Forwarding does not always mean NAT.

- **Pure routing** preserves the original source address. The destination network must know how to route back.
- **NAT** rewrites addresses, often hiding many clients behind one router address. Return traffic goes back to the NAT device.

Pure routing is cleaner when both sides can carry routes. NAT is useful at boundaries where return routes are not available or where address hiding is intentional.

Typical masquerade pattern with nftables:

```text
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat;
    oifname "enp1s0" masquerade
  }
}
```

Do not add NAT blindly. First decide whether the real problem is missing routing, missing firewall policy, or an intentional boundary.

## Reverse Path Filtering

Linux reverse-path filtering can drop packets when the return path does not match expectations. This can surprise multi-homed hosts and asymmetric routing designs.

Inspect:

```bash
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.default.rp_filter
sysctl net.ipv4.conf.<interface>.rp_filter
```

Values vary by distribution and environment. If forwarding works in one direction but not another, especially on a multi-interface Linux router, include `rp_filter` in your evidence.

## Observe Forwarded Traffic

Use packet capture carefully:

```bash
sudo tcpdump -ni enp1s0 host 10.20.30.15
sudo tcpdump -ni enp2s0 host 10.20.30.15
```

You are trying to answer:

- Does the packet arrive on the ingress interface?
- Does it leave on the egress interface?
- Does a reply come back?
- Are addresses rewritten?
- Is TTL decreasing as expected?

Capture only what you need. Packet captures can include sensitive data.

## Common Failure Patterns

### Forwarding Disabled

Symptoms:

- Linux host can reach both networks itself.
- Hosts on one side cannot reach the other side through it.
- `net.ipv4.ip_forward = 0`.

Fix direction:

- Enable forwarding only if this host is intended to be a router.
- Make the setting persistent through configuration management.

### Missing Return Route

Symptoms:

- Request leaves the forwarding host.
- Destination receives request.
- Reply goes to the wrong gateway or disappears.

Fix direction:

- Add route on the destination side.
- Use an existing router as the gateway.
- Use NAT only if hiding the source is the intended design.

### Firewall Drops Forwarded Traffic

Symptoms:

- Routes look correct.
- Forwarding is enabled.
- Firewall counters increase on drop rules.

Fix direction:

- Add narrow allow rules for the intended source, destination, protocol, and interface.
- Keep logging temporary and rate-limited.

### Wrong Source Address

Symptoms:

- Packets leave through the expected interface.
- Source address belongs to an unexpected interface.
- Reply path fails or policy blocks the packet.

Fix direction:

- Inspect `ip route get`.
- Set route source address where appropriate.
- Review policy routing rules.

## Safe Troubleshooting Flow

Use this sequence:

1. Identify source, destination, protocol, and expected path.
2. Run `ip route get <destination>` on the forwarding host.
3. Check `ip_forward` or IPv6 forwarding.
4. Check firewall forwarding policy and counters.
5. Capture on ingress and egress interfaces.
6. Verify return route from the destination side.
7. Document any temporary changes.

Avoid changing routes, NAT, and firewall rules all at once. One clear change with a test is safer than three guesses.

## Practice

In a disposable lab with two subnets and a Linux router VM:

1. Give the router VM one interface in each subnet.
2. Confirm each subnet can reach the router.
3. Leave forwarding disabled and test cross-subnet traffic.
4. Enable forwarding temporarily.
5. Add the minimum route or NAT needed for return traffic.
6. Use `tcpdump` on both interfaces to prove packet flow.
7. Write a short note explaining which evidence proved each step.
