# 15.7 Cisco Routers

Linux operators often meet Cisco routers at the edge of their environment: campus gateways, branch routers, data-center cores, lab networks, VPN edges, or provider handoffs. The goal is not to become a full Cisco administrator in one lesson. The goal is to translate routing evidence between Linux and Cisco so you can troubleshoot responsibly with the network team.

!!! abstract "What you will learn"
    - Map common Linux routing evidence to common Cisco IOS-style evidence.
    - Understand the operational boundary between a Linux host and a dedicated router.
    - Collect useful information before escalating to a network team.
    - Avoid making unsafe assumptions about Cisco configuration from Linux symptoms alone.
    - Troubleshoot route, interface, ACL, and next-hop issues across the Linux/Cisco boundary.

!!! warning "Production caution"
    Do not change a Cisco router just because a Linux host cannot reach a destination. Routers are shared infrastructure. Gather evidence, identify the expected path, and coordinate changes through the owner of the router.

## Why Cisco Routers Matter to Linux Operators

Most Linux troubleshooting eventually leaves the host. A packet may depend on:

- the Linux route table
- the Linux firewall
- the first-hop gateway
- VLAN or switch configuration
- Cisco routing protocol state
- Cisco access control lists
- NAT or VPN policy
- return-path routing

If the router is Cisco, the commands and vocabulary are different, but the questions are familiar: where should the packet go, what policy applies, and what evidence proves the chosen path?

## Linux Evidence First

Start on the Linux host. Do not begin by blaming the router.

```bash
ip addr show
ip route
ip rule show
ip route get 10.20.30.40
ss -tuna
sudo nft list ruleset
```

For packet-level proof:

```bash
sudo tcpdump -ni any host 10.20.30.40
```

Collect:

- source IP
- destination IP
- source interface
- selected next hop
- protocol and port
- whether packets leave the host
- whether replies return

That evidence makes the Cisco-side conversation much more productive.

## Cisco Evidence Equivalents

The exact command set varies by platform and OS family, but many IOS-style environments use familiar `show` commands.

| Question | Linux evidence | Cisco-style evidence |
| --- | --- | --- |
| What routes exist? | `ip route` | `show ip route` |
| Which path is chosen? | `ip route get <dest>` | `show ip route <dest>` |
| Is an interface up? | `ip link show` | `show interfaces status` or `show ip interface brief` |
| What address is assigned? | `ip addr show` | `show ip interface brief` |
| Are neighbors visible? | `ip neigh show` | `show arp` or `show ipv6 neighbors` |
| Is OSPF healthy? | `vtysh -c 'show ip ospf neighbor'` | `show ip ospf neighbor` |
| Is BGP healthy? | `vtysh -c 'show bgp summary'` | `show ip bgp summary` or `show bgp summary` |
| Is traffic filtered? | `nft list ruleset` | `show access-lists` plus interface policy |

Use this table as a translation aid, not as permission to modify router config.

## Interface and First-Hop Checks

If a Linux host uses a Cisco router as its default gateway, verify the first hop.

On Linux:

```bash
ip route show default
ip neigh show
ping -c 3 <gateway-ip>
```

On Cisco, the network team may check:

```text
show ip interface brief
show interfaces <interface>
show arp
show running-config interface <interface>
```

Useful questions:

- Is the gateway IP on the subnet the Linux host expects?
- Is the interface up/up?
- Is the VLAN correct?
- Is ARP resolving?
- Are errors, drops, or speed/duplex problems present?

## Route Selection Across the Boundary

Linux may send a packet to the right gateway while the router sends it somewhere unexpected. Compare both route decisions.

Linux:

```bash
ip route get 10.20.30.40
```

Cisco-style:

```text
show ip route 10.20.30.40
show ip cef 10.20.30.40
```

Ask the router owner to confirm:

- selected next hop
- outgoing interface
- route source, such as connected, static, OSPF, BGP, or default
- administrative distance and metric
- whether a more specific route overrides the expected route

If Linux and Cisco disagree about the route, identify which device owns the incorrect assumption.

## ACLs, NAT, and Policy

Routing can be correct while policy blocks traffic.

On Linux, inspect local policy:

```bash
sudo nft list ruleset
sudo iptables -S
```

On Cisco, the network team may inspect:

```text
show access-lists
show running-config interface <interface>
show ip nat translations
show ip nat statistics
```

Be precise when asking for help. Include source IP, destination IP, protocol, port, and time of test. A vague report like "Linux cannot reach the server" is much harder to trace than "192.0.2.15 cannot reach 10.20.30.40 TCP/443 at 14:03 ET."

## Dynamic Routing Interoperability

Linux routing daemons and Cisco routers can speak the same protocols, commonly OSPF or BGP. The protocol is shared, but configuration defaults and policy behavior may differ.

For OSPF, compare:

```bash
vtysh -c 'show ip ospf neighbor'
vtysh -c 'show ip route ospf'
```

Cisco-style:

```text
show ip ospf neighbor
show ip route ospf
show ip protocols
```

For BGP, compare:

```bash
vtysh -c 'show bgp summary'
vtysh -c 'show bgp ipv4 unicast'
```

Cisco-style:

```text
show ip bgp summary
show ip bgp
show ip bgp neighbors <peer>
```

Common mismatch areas:

- AS number
- neighbor source address
- authentication
- OSPF area
- route filtering
- prefix list or route map
- maximum-prefix limits
- next-hop handling
- MTU or TTL expectations

## Safe Escalation Packet

When you need the network team to check a Cisco router, send a concise evidence packet:

```text
Problem:
Source host:
Source IP:
Destination IP and port:
Expected path:
Observed Linux route:
Gateway:
Packet capture result:
First failure point:
Time tested:
Recent changes:
Requested router-side checks:
```

Attach command output when appropriate. This makes it clear that you checked the host first and gives the router owner enough information to inspect routes, ACLs, NAT, and protocol state.

## Common Failure Patterns

### Wrong Default Gateway

Linux sends traffic to a gateway that is not the intended router.

Evidence:

```bash
ip route show default
ip route get <destination>
```

Fix the Linux network config, DHCP source, or host route before changing the router.

### Missing Return Route

The Linux host sends traffic out, but replies never return. The Cisco router may need a route back to the Linux subnet, or another downstream router may be missing that route.

Evidence:

```bash
sudo tcpdump -ni any host <destination>
```

If outbound packets leave and no replies return, ask for route and policy checks in the return direction.

### ACL Blocks the Service

ICMP may work while TCP/443 fails, or one subnet may work while another is denied.

Evidence:

```bash
nc -vz <destination> 443
sudo tcpdump -ni any host <destination> and port 443
```

Escalate with the exact source, destination, protocol, and port.

### Dynamic Neighbor Is Down

If Linux FRR peers with a Cisco router and routes disappear, verify neighbor state from both sides before changing policy.

Linux:

```bash
vtysh -c 'show bgp summary'
```

Cisco-style:

```text
show ip bgp summary
```

## Lab Practice

In a lab or simulator such as containerlab, GNS3, EVE-NG, CML, or a safe physical lab:

1. Put a Linux host behind a router.
2. Record `ip addr`, `ip route`, and `ip route get <destination>`.
3. On the router, record interface status and route selection.
4. Add a test ACL or route change in the lab.
5. Capture the Linux-side symptom.
6. Restore the original config.
7. Write the escalation packet you would send to a network owner.
