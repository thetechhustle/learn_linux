# 15.5 Routing Strategy Selection Criteria

Route selection is an engineering decision, not a contest to find the fanciest protocol. A good routing strategy matches the network's size, failure modes, operational skill, security boundaries, and change-control needs. Linux gives you enough routing tools to build many designs; the discipline is choosing the simplest design that can be operated safely.

!!! abstract "What you will learn"
    - Choose between static routes, dynamic routing, policy routing, and overlay routing.
    - Evaluate routes using reachability, failure behavior, operational cost, observability, and security boundaries.
    - Use Linux evidence to support a route-selection decision.
    - Avoid common overengineering traps.
    - Document routing decisions so future operators can troubleshoot them.

!!! success "Operator principle"
    Pick routing that your team can explain during an incident at 2 AM.

## Start With the Requirement

Before choosing a route strategy, write down what must be true.

Useful questions:

- Which source networks need to reach which destination networks?
- Is traffic one-way or bidirectional?
- Is failover required?
- How quickly must failover happen?
- Who owns each router or gateway?
- Are there security zones, VPNs, cloud networks, or NAT boundaries?
- Does the route need to survive host reboots and interface changes?
- How will operators prove that it works?

If you cannot answer those questions, a routing protocol will not save the design. It will only make the uncertainty move faster.

## Static Routes

Static routes are best when the topology is small and stable.

Use static routes when:

- there are only a few known networks
- next hops rarely change
- failure does not require automatic rerouting
- humans can easily audit the route table
- the risk of a routing protocol is not justified

Evidence to inspect:

```bash
ip route
ip -6 route
ip route get 10.20.30.40
```

Static routes are easy to understand but easy to forget. The operational requirement is documentation: why the route exists, who owns the next hop, and how to remove it.

## Dynamic Routing

Dynamic routing is useful when routers need to exchange reachability automatically.

Use dynamic routing when:

- multiple routers share responsibility for the same environment
- failover must happen without manual route edits
- routes are added or removed often
- cloud, data center, lab, or service networks advertise prefixes dynamically
- route policy needs central enforcement

Dynamic routing adds operational cost. Someone must understand neighbor state, route policy, metrics, filtering, and rollback. That is acceptable when the network complexity justifies it.

Evidence to inspect with FRRouting:

```bash
vtysh -c 'show ip route'
vtysh -c 'show ip ospf neighbor'
vtysh -c 'show bgp summary'
```

## Policy Routing

Policy routing chooses routes based on more than destination prefix. Linux can route based on source address, firewall mark, table, incoming interface, or other selectors.

Use policy routing when:

- different source networks need different exits
- VPN traffic must use a specific tunnel
- application or tenant traffic needs separate routing tables
- asymmetric routing must be controlled explicitly

Inspect policy rules before route tables:

```bash
ip rule show
ip route show table main
ip route show table all
ip route get 8.8.8.8 from 192.0.2.10
```

Policy routing is powerful, but it is also easy to hide from teammates. If you use it, document the rule priority, matching condition, target table, and owner.

## Overlay and Tunnel Routing

Overlay networks and tunnels move traffic through an encrypted or virtual path above the physical network. Examples include WireGuard, Tailscale, IPsec, GRE, VXLAN, and cloud transit constructs.

Use overlay routing when:

- endpoints are spread across untrusted or changing networks
- encryption is required between sites or hosts
- cloud and home-lab nodes need consistent private reachability
- you cannot control the underlay routers directly

Inspect both the tunnel and the route:

```bash
ip link show
ip addr show
ip route
wg show
tailscale status
```

Overlay routing can be the right answer, but do not let it mask broken ownership. Someone still needs to know which path is expected, how keys are managed, and what happens when the overlay is down.

## Selection Criteria

### Reachability

Can the route actually deliver packets both ways?

Check:

```bash
ip route get <destination>
ping -c 3 <destination>
traceroute <destination>
```

For TCP services, test the real service path instead of stopping at ICMP:

```bash
nc -vz <host> <port>
curl -v http://<host>:<port>/
```

### Failure Behavior

What happens when a link, router, tunnel, or peer fails?

Static routing usually fails until a human changes it. Dynamic routing may converge automatically. Overlay routing may reconnect through another internet path. Policy routing may fail in surprising ways if a rule points to a dead table.

Document:

- expected failure signal
- failover target
- convergence expectation
- rollback path
- alert or monitoring source

### Operational Cost

The best strategy is one your team can operate consistently.

Ask:

- Can the on-call operator explain the route table?
- Are route changes reviewed?
- Is the config stored in version control or infrastructure tooling?
- Are there commands to prove the design after a change?
- Does the team know the difference between kernel routes and daemon routes?

Complex routing without operational ownership becomes incident debt.

### Security Boundary

Routing creates access. Every new route can cross a trust boundary.

Check:

- source networks allowed
- destination networks allowed
- firewall rules
- NAT behavior
- VPN encryption
- logging and monitoring
- return path

Do not assume that because a route exists, access should exist. Routing and authorization are different decisions.

### Observability

A routing strategy should leave evidence.

Useful Linux evidence:

```bash
ip route
ip rule show
ip route get <destination>
ss -tuna
sudo tcpdump -ni any host <host>
journalctl -u frr --since '30 minutes ago'
```

For dynamic routing, include daemon evidence:

```bash
vtysh -c 'show ip route'
vtysh -c 'show bgp summary'
vtysh -c 'show ip ospf neighbor'
```

If you cannot observe the strategy, you cannot safely operate it.

## Common Strategy Choices

### Small Office or Home Lab

Start with static routes or an overlay such as Tailscale/WireGuard. Add dynamic routing only when multiple routers and failover requirements make the added complexity worthwhile.

### Data Center or Campus

Use dynamic routing when there are redundant routers, multiple subnets, and clear operational ownership. OSPF or IS-IS may fit internal topology. BGP may fit edge, policy-heavy, or large-scale designs.

### Cloud and Hybrid Networks

Expect a mix of cloud route tables, VPNs, BGP sessions, NAT, and security groups. The Linux host route table is only part of the evidence. Record cloud-side route tables and firewall/security-group state in the same incident notes.

### Application-Specific Exit Paths

Use policy routing only when destination-only routing cannot express the requirement. Keep rule count small, priority ordering explicit, and tests written down.

## Avoid These Traps

- Using BGP because it sounds more professional when static routes would be safer.
- Adding policy routing without documenting `ip rule` priorities.
- Fixing a return-path problem with NAT without recording why.
- Assuming dynamic routing removes the need for firewall review.
- Forgetting that multicast, tunnels, and overlays may have separate control planes.
- Testing only `ping` when the real service uses TCP, UDP, TLS, or application authentication.

## Decision Record Template

Use a short decision record for real route changes:

```text
Requirement:
Source:
Destination:
Selected strategy:
Rejected alternatives:
Next hop or peer:
Failure behavior:
Security boundary:
Verification commands:
Rollback:
Owner:
Review date:
```

This record is more useful than a clever route if the next operator cannot explain the design.

## Lab Practice

On a disposable VM or lab router:

1. Inspect the default route with `ip route`.
2. Use `ip route get` for three destinations.
3. Add one temporary static route to a harmless test prefix.
4. Add one temporary policy rule in a lab table.
5. Compare `ip route get` with and without a source address.
6. Remove the test route and policy rule.
7. Write a short decision record explaining when each approach would be appropriate.
