# 15.8 Recommended Reading

IP routing is learned best in layers. Start with the tools that explain what your host is doing, then move outward to packet captures, protocol behavior, router policy, and architecture references. This reading path keeps that order so the next resource answers a question you can already ask from Linux.

!!! abstract "What you will learn"
    - Build a practical reading path for Linux IP routing.
    - Choose references that match an operational problem instead of collecting links at random.
    - Separate host-level evidence, packet evidence, dynamic routing evidence, and router-side evidence.
    - Keep a small personal routing notebook that improves with each incident or lab.

!!! success "Operator principle"
    Read enough to explain the next packet hop with evidence.

## Start With Local Routing Evidence

Use the manual pages first. They describe the exact tools installed on the system in front of you.

```bash
man ip
man ip-route
man ip-rule
man ss
man tcpdump
man nft
```

Helpful focus areas:

- address and link state: `ip address`, `ip link`
- route tables: `ip route`
- policy routing: `ip rule`
- route prediction: `ip route get`
- sockets and listeners: `ss`
- packet capture filters: `tcpdump`
- firewall and NAT policy: `nft`

After reading, run one command and write down what each field means. A short note from your own machine is more useful than a long bookmark list.

## Read The Project Documentation

The Linux networking stack changes over time, so prefer active project documentation when possible.

Good places to start:

- `iproute2` documentation and examples
- kernel documentation for networking and sysctls
- distribution networking guides for NetworkManager, systemd-networkd, Netplan, or FreeBSD `rc.conf`
- firewall documentation for nftables
- FRRouting documentation for OSPF, BGP, route maps, and redistribution

When reading distribution guides, identify what is portable and what is distribution-specific. A NetworkManager profile, a Netplan YAML file, and a systemd-networkd unit may configure the same route, but they are not edited the same way.

## Learn With Packet Captures

Packet captures turn routing from a theory problem into visible evidence.

Recommended practice:

```bash
sudo tcpdump -ni any host 10.20.30.40
sudo tcpdump -ni eth0 arp or icmp
sudo tcpdump -ni eth0 'tcp port 443'
```

Read material that explains:

- Ethernet frames
- ARP and neighbor discovery
- ICMP and ICMPv6
- TCP connection setup
- TTL and hop limits
- MTU and fragmentation
- multicast control traffic

Do not skip packet basics. Many routing incidents become obvious once you can say whether the packet left the host, reached the gateway, and came back.

## Study Dynamic Routing After Static Routing

Do not begin with OSPF or BGP before static routes make sense. Dynamic routing protocols automate route exchange, but they still produce route-table entries that must be inspected and trusted.

Suggested sequence:

1. Static routes and default routes
2. Multiple route tables and policy routing
3. OSPF adjacency and route learning
4. BGP peering and prefix policy
5. Redistribution boundaries
6. Route filtering and summarization
7. Failure behavior and convergence

For Linux labs, FRRouting is the most practical starting point. It lets you run routing protocols on ordinary Linux hosts and compare daemon state with kernel route state.

Useful commands to pair with reading:

```bash
vtysh -c 'show ip route'
vtysh -c 'show ip ospf neighbor'
vtysh -c 'show bgp summary'
ip route
ip route get 10.20.30.40
```

## Keep Cisco And Vendor References Nearby

Many Linux systems use a dedicated network device as their first hop. Cisco IOS-style documentation is useful because it teaches the router-side view of the same path.

Read Cisco or vendor references when you need to understand:

- interface state
- routing table selection
- ACL placement
- NAT policy
- OSPF neighbors
- BGP sessions
- route maps and prefix lists
- tunnel or VPN routes

Translate every vendor command back to a Linux question. For example, `show ip route <destination>` answers the same operational question as `ip route get <destination>`: which route wins right now?

## Build A Lab Reading Loop

Use each reading session to produce evidence, not just recognition.

1. Pick one scenario, such as "host A cannot reach host B."
2. Predict the expected route.
3. Run `ip route get`.
4. Capture packets at the source.
5. Check the gateway or simulated router.
6. Change one reversible variable.
7. Write down what changed.

Good lab tools include:

- Linux network namespaces
- containers connected with bridges
- VMs on an isolated virtual network
- FRRouting containers
- GNS3, EVE-NG, or vendor lab sandboxes when router behavior matters

Keep production and lab habits separate. A lab is where you break routes on purpose. Production is where you gather evidence, coordinate changes, and keep rollback clear.

## Books And Longer References

Use books when you need a durable mental model rather than a quick command reminder.

Strong categories:

- Linux networking internals for kernel packet flow
- TCP/IP fundamentals for protocol behavior
- network troubleshooting cookbooks for repeatable diagnostic patterns
- routing protocol references for OSPF and BGP
- vendor configuration guides for router policy and platform-specific commands

Choose one long reference at a time. Finish the chapters relevant to your current work before adding another.

## Build Your Personal Routing Notebook

For every useful incident, lab, or reading session, keep a short record:

```text
Date:
Scenario:
Source:
Destination:
Expected path:
Observed route:
Packet evidence:
Router or gateway evidence:
Policy involved:
Fix or explanation:
What I would check first next time:
```

Over time, this notebook becomes more valuable than a generic reading list because it captures the paths, vendors, subnets, and failure patterns you actually operate.

## Check Your Understanding

- Which reference would you use first to explain `ip route get` output on your current host?
- What packet capture would prove that traffic leaves the Linux host?
- When should you move from Linux evidence to router-side evidence?
- Why is redistribution riskier than a simple static route?
- What belongs in an escalation packet to a network team?

## Practical Next Step

Pick one destination on your lab network and build a one-page evidence note. Include `ip route get`, a packet capture, the default gateway, and a short explanation of why the packet takes that path. Then repeat the exercise with one intentionally broken route in a sandbox.
