# 1.03 Linux Distributions

!!! abstract "What you will learn"
    - Explain what a Linux distribution adds on top of the Linux kernel.
    - Identify a system's distribution, version, architecture, and package family.
    - Choose a distribution based on support, operations needs, and team experience.
    - Avoid unsafe assumptions when moving between Linux distributions.

!!! success "Operator principle"
    Identify the OS, distribution, support window, and package source before changing anything.

A Linux distribution is a complete operating system built around the Linux kernel. The
kernel handles hardware, processes, memory, networking, and filesystems. The
distribution adds the user-space tools, installer, package manager, security update
process, default configuration, documentation, and support lifecycle that make the
system usable day to day.

For administrators, the distribution matters because it shapes how you install
software, where configuration files live, how services are managed, how updates are
delivered, and how long the system will receive security fixes. Two servers can both
be "Linux" while requiring different package commands, release policies, and
operational habits.

## What A Distribution Provides

Most distributions include:

- A Linux kernel build with the vendor's configuration and patches.
- Core system libraries and command-line utilities.
- A package manager and signed package repositories.
- A release model and security update process.
- Installer images, cloud images, and container base images.
- Defaults for logging, networking, users, services, and security policy.
- Documentation, bug trackers, and support channels.

The exact mix varies. A general-purpose server distribution optimizes for stability
and maintenance. A desktop distribution may prioritize hardware support and graphical
tools. A container-focused distribution may minimize the host surface and expect most
applications to run in containers.

## Common Distribution Families

The distribution family usually tells you which package tools and conventions to
expect.

| Family | Examples | Package tools | Common use |
| --- | --- | --- | --- |
| Debian-based | Debian, Ubuntu | `apt`, `dpkg` | Servers, desktops, cloud images, containers |
| Red Hat-based | RHEL, Rocky Linux, AlmaLinux, Fedora | `dnf`, `rpm` | Enterprise servers, regulated environments, developer workstations |
| SUSE-based | SLES, openSUSE | `zypper`, `rpm` | Enterprise Linux, SAP and infrastructure workloads |
| Arch-based | Arch Linux, EndeavourOS | `pacman` | Rolling-release desktops and advanced labs |
| Container/immutable hosts | Fedora CoreOS, Flatcar, Bottlerocket | image-based updates, `rpm-ostree`, vendor tools | Kubernetes, container platforms, appliance-like hosts |

The family is not the whole story. Ubuntu and Debian share many tools, but they have
different release cadences, package versions, commercial support paths, and cloud
defaults. Fedora and RHEL are related, but Fedora moves much faster and is not a
drop-in replacement for an enterprise RHEL estate.

## Identify The System First

Before changing packages, services, repositories, or kernel settings, identify the
system you are touching.

```bash
cat /etc/os-release
uname -a
uname -m
```

`/etc/os-release` is the standard first stop. It usually reports fields such as
`ID`, `VERSION_ID`, `VERSION_CODENAME`, and `ID_LIKE`.

For package tooling, check what is present rather than guessing:

```bash
command -v apt || true
command -v dnf || true
command -v rpm || true
command -v zypper || true
```

On a systemd-based machine, you can also confirm the init system:

```bash
ps -p 1 -o comm=
systemctl --version
```

Do not assume every Linux machine uses the same init system, firewall tool, network
manager, or package manager. Embedded systems, containers, rescue images, and
minimal cloud images often differ from a full server install.

## Release Models

Distribution choice is partly a release-management decision.

- **Stable releases** prioritize predictable versions and long maintenance windows.
  Debian stable, Ubuntu LTS, RHEL, Rocky Linux, AlmaLinux, and SLES are common
  examples.
- **Short-term releases** provide newer packages but require more frequent upgrades.
  Non-LTS Ubuntu releases and recent Fedora releases fit this pattern.
- **Rolling releases** continuously update packages instead of moving between fixed
  versions. Arch Linux is the classic example.
- **Immutable or image-based hosts** update the base operating system as a unit.
  Fedora CoreOS, Flatcar, and Bottlerocket reduce host drift but require a different
  operating model.

For production servers, support lifecycle matters as much as features. An old
distribution with no security updates is a risk even when the server appears to be
working.

## Package Sources And Trust

Most distribution packages come from signed repositories maintained by the
distribution vendor or community. Third-party repositories can be useful, but they
also expand your trust boundary.

Before adding a repository, ask:

- Who maintains it?
- Is it signed?
- Does it override distribution packages?
- Is it compatible with this exact release?
- How will it be removed or upgraded later?

On Debian-based systems, repository configuration usually lives under
`/etc/apt/sources.list` and `/etc/apt/sources.list.d/`. On RPM-based systems, it is
usually under `/etc/yum.repos.d/`.

Inspect before changing:

```bash
find /etc/apt -maxdepth 2 -type f 2>/dev/null
find /etc/yum.repos.d -maxdepth 1 -type f 2>/dev/null
```

## Choosing A Distribution

There is no single best distribution. Choose the one that matches the job.

For production servers, favor:

- A supported release with a clear security update window.
- A package ecosystem that covers your required software.
- Documentation your team can actually follow.
- Cloud and automation support for your deployment target.
- A maintenance model your team can sustain.

For learning, choose a distribution that lets you practice the concepts in this
course without fighting the environment. Ubuntu LTS, Debian, Fedora, and Rocky Linux
are all reasonable lab choices. If your workplace uses a specific family, practice
on that family early.

## Operational Differences To Expect

Moving between distributions often changes:

- Package commands: `apt`, `dnf`, `zypper`, `pacman`.
- Package names: the same software may have different package names.
- Default service names and enabled units.
- Network configuration tools.
- Firewall tools and default rules.
- SELinux or AppArmor defaults.
- Release upgrade process.
- Available package versions.

The safest habit is to inspect the local system, read the distribution's current
documentation, and test changes in a disposable environment before applying them to
important machines.

