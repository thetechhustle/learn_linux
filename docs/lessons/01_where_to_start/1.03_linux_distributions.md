# 1.03 Linux Distributions

!!! abstract "What you will learn"
    - Explain what a Linux distribution includes beyond the kernel.
    - Identify a system's distribution, version, package family, and support clues.
    - Choose a distribution for a lab or service based on operational requirements.
    - Avoid common mistakes when copying commands between distribution families.

!!! example "Field story"
    A junior admin joins a small cloud team and receives access to three servers: one runs Ubuntu, one runs Debian, and one runs Rocky Linux. The team's runbook says "install the package and restart the service," but the package names, service defaults, firewall tools, and support windows are not identical. Before changing anything, the admin needs to identify each platform and adapt the procedure.

!!! success "Operator principle"
    Identify the OS, distribution, support window, and package source before changing anything.

A Linux distribution is a complete operating system built around the Linux kernel. It also includes a package manager, default configuration choices, installer, service defaults, security update process, documentation, and release lifecycle.

For day-to-day operations, the distribution matters because it affects:

- Package commands and package names.
- Service defaults and configuration file locations.
- Security update cadence and support windows.
- Kernel version and backported fixes.
- Vendor documentation and troubleshooting paths.
- Commercial support, compliance expectations, and image availability in cloud providers.

The "best" distribution is the one that fits the service, team, support model, and operating environment. A laptop, disposable lab VM, regulated production server, Kubernetes node, and network appliance may all need different choices.

## Common Distribution Families

Most Linux operations work falls into a few broad families.

| Family | Common examples | Package tools | Typical fit |
| --- | --- | --- | --- |
| Debian family | Debian, Ubuntu | `apt`, `dpkg` | General servers, cloud images, desktops, labs |
| Red Hat family | RHEL, Rocky Linux, AlmaLinux, Fedora | `dnf`, `rpm` | Enterprise servers, regulated environments, vendor-supported platforms |
| SUSE family | SLES, openSUSE | `zypper`, `rpm` | Enterprise environments, SAP-heavy estates, SUSE-supported platforms |
| Arch family | Arch Linux | `pacman` | Rolling-release labs, power-user desktops |
| Alpine family | Alpine Linux | `apk` | Small containers, minimal images, embedded-style environments |

These families share habits, but they are not interchangeable. For example, Debian and Ubuntu both use `apt`, but their release schedules, package versions, defaults, and support options differ. RHEL-like systems use RPM packages, but Fedora moves faster than RHEL, Rocky Linux, or AlmaLinux.

## First Evidence To Capture

Start with read-only facts. These commands are safe on normal systems:

```bash
cat /etc/os-release
uname -a
hostnamectl
```

The most portable distribution identity source is `/etc/os-release`:

```bash
cat /etc/os-release
```

Useful fields include:

- `NAME`: human-readable distribution name.
- `VERSION_ID`: release number.
- `ID`: distribution identifier, such as `ubuntu`, `debian`, `rhel`, or `rocky`.
- `ID_LIKE`: related distribution family.
- `VERSION_CODENAME`: codename on distributions that publish one.

For a concise report, use:

```bash
. /etc/os-release
printf 'name=%s\nversion=%s\nid=%s\nfamily=%s\n' "$NAME" "$VERSION_ID" "$ID" "${ID_LIKE:-unknown}"
```

## Package Family Checks

Confirm the package manager before following installation instructions:

```bash
command -v apt dnf yum zypper apk pacman
```

On Debian-family systems:

```bash
apt-cache policy bash
dpkg -l bash
```

On Red Hat-family systems:

```bash
dnf info bash
rpm -q bash
```

On Alpine systems:

```bash
apk info -a busybox
```

Do not assume package names match across distributions. A service might be named `apache2` on Ubuntu and `httpd` on RHEL-like systems. A firewall command might use `ufw`, `firewalld`, `nft`, or cloud security-group rules depending on the environment.

## Release And Support Clues

The version number is not enough. Operators also care whether the release is supported and how updates arrive.

Check available update metadata with the distribution's normal tools:

```bash
# Debian or Ubuntu
apt list --upgradable

# RHEL-like systems
dnf check-update
```

Those commands can contact configured repositories, so run them when network access is expected and the host is allowed to query package mirrors. For a purely local check, inspect the configured repositories:

```bash
# Debian or Ubuntu
grep -R --line-number --no-messages '^deb ' /etc/apt/sources.list /etc/apt/sources.list.d

# RHEL-like systems
dnf repolist
```

When documenting a server, capture:

- Distribution name and version.
- Package family and active repositories.
- Whether the release is still supported.
- Whether updates come from vendor, internal mirror, cloud image, or third-party repository.
- Any pinned packages, disabled repositories, or custom kernels.

## Choosing A Distribution

Use requirements instead of preference arguments. Ask:

- What distribution does the team already support well?
- Is commercial support required?
- Does the application vendor certify a specific platform?
- How long must the system receive security updates?
- Are required packages available from trusted repositories?
- Will the same distribution run in local labs, CI, cloud images, and production?
- Is a small container image more important than interactive troubleshooting tools?

For a first lab, Ubuntu LTS, Debian stable, or a RHEL-compatible distribution is usually easier than a rolling-release distribution because documentation and package behavior stay stable longer.

For production, consistency often beats novelty. A slightly older supported release with documented patching, backups, monitoring, and recovery is usually safer than a newer release that only one person understands.

## Command Portability Cautions

Many Linux commands are portable, but administration recipes often are not.

Before copying a command from a tutorial, check:

- Does it match this distribution family?
- Does it install from official repositories or an external script?
- Does it enable a service, open a firewall, alter users, or replace configuration?
- Does it assume systemd, SELinux, AppArmor, or a specific network manager?
- Does it include `curl | sh`, `sudo`, `rm`, `dd`, or package removal?

Prefer vendor documentation and distribution documentation over random snippets. If a command changes state, test it in a disposable VM or container first.

## Hands-On Practice

Run these on a disposable VM, container, or lab machine.

1. Capture distribution identity:

   ```bash
   cat /etc/os-release
   uname -r
   ```

2. Identify the package manager:

   ```bash
   command -v apt dnf yum zypper apk pacman
   ```

3. Find the package record for a common command:

   ```bash
   command -v ssh || command -v bash
   ```

4. Compare two distributions if you can. For each one, write down the distribution name, version, package manager, default shell path, and one documentation source you would trust during an incident.

5. Write a short handoff note:

   ```text
   Host:
   Distribution:
   Version:
   Kernel:
   Package manager:
   Repository source:
   Support concern:
   Next safe action:
   ```

## Troubleshooting Signals

Distribution mismatch often shows up as small confusing errors:

- A package install command says the package cannot be found.
- A service name from a tutorial does not exist.
- A configuration file path differs from the documentation.
- A firewall rule appears correct but the cloud firewall still blocks traffic.
- A security module such as SELinux or AppArmor blocks a service after installation.
- A third-party repository replaces vendor packages unexpectedly.

When that happens, go back to identity and package evidence before trying more commands.
