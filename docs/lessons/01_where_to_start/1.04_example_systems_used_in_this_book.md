## 1.04 Example Systems Used in This Book

!!! abstract "What you will learn"
    - Identify the example Linux systems used throughout the course.
    - Understand why labs use more than one distribution or environment.
    - Build a small, safe lab that matches the course examples.
    - Record enough system facts to make examples reproducible.

!!! success "Operator principle"
    Match the example to the environment before copying commands. Distribution,
    version, package manager, init system, and privilege level all matter.

Linux administration is easier to learn when you can see the same idea in more than
one environment. This course uses a small set of example systems to show how common
operator tasks look on desktop-friendly Linux, enterprise-style Linux, small-board
Linux, and isolated virtual machines.

The examples are not meant to say that one distribution is best. They are meant to
teach portability, evidence gathering, and safe habits. A good administrator learns
to ask, "What system am I actually on?" before running commands.

## Primary Example Systems

Use these systems as reference points while reading the course.

| Example system | Package family | Why it is useful |
| --- | --- | --- |
| Ubuntu LTS | Debian-based, `apt` | Common in cloud images, labs, developer machines, and tutorials |
| Debian stable | Debian-based, `apt` | Conservative base system with a strong server and package tradition |
| Rocky Linux or AlmaLinux | Red Hat-based, `dnf` and `rpm` | Enterprise-style Linux similar to RHEL operations |
| Fedora | Red Hat-based, `dnf` and `rpm` | Newer Linux features before they appear in many enterprise releases |
| Raspberry Pi OS | Debian-based, `apt` | Small-board Linux with hardware and embedded-system constraints |
| A disposable VM | Depends on image | Safe place to break and rebuild systems while learning |
| A container | Depends on image | Useful for package and shell practice, but not a full machine |

When a lesson uses one of these systems, pay attention to the command prompt,
package manager, service manager, and file paths. Those details tell you whether the
example transfers directly to your system or needs translation.

## Ubuntu LTS

Ubuntu LTS is a practical starting point for many labs because it is common, easy to
install, and well documented. It appears frequently in cloud providers, laptops,
developer workstations, and training environments.

Useful identity checks:

```bash
cat /etc/os-release
uname -r
command -v apt
```

Typical package workflow:

```bash
sudo apt update
apt list --upgradable
```

Do not run upgrades blindly on production systems. In a lab, updates are useful
practice. In production, update windows, backups, snapshots, and rollback plans
matter.

## Debian Stable

Debian stable is useful when you want a conservative server baseline. It usually
prioritizes predictable behavior over the newest package versions.

Useful checks:

```bash
cat /etc/debian_version
cat /etc/os-release
apt-cache policy bash
```

Debian and Ubuntu are related, but they are not identical. Package names, default
repositories, kernel versions, and service defaults can differ.

## Rocky Linux Or AlmaLinux

Rocky Linux and AlmaLinux are common choices for learning enterprise-style Red Hat
operations without a paid RHEL subscription. They are useful examples for lessons
that involve RPM packages, SELinux, system roles, and long-lived server practices.

Useful checks:

```bash
cat /etc/os-release
command -v dnf
rpm -q bash
```

Typical package workflow:

```bash
sudo dnf check-update
dnf info bash
```

On Red Hat-family systems, SELinux may be enforcing by default. That can affect web
servers, file sharing, containers, and custom services.

```bash
getenforce 2>/dev/null || true
```

If a command works on Ubuntu but fails on Rocky or AlmaLinux, check package names,
service names, firewall rules, and SELinux context before assuming the software is
broken.

## Fedora

Fedora moves faster than most enterprise distributions. It is a good environment for
seeing newer kernels, systemd features, desktop packages, and container tooling.

Useful checks:

```bash
cat /etc/fedora-release
dnf list installed systemd
```

Fedora is valuable in a lab, but do not treat it as a one-for-one substitute for
RHEL, Rocky Linux, or AlmaLinux. Its release cadence and package versions are
different.

## Raspberry Pi OS

Raspberry Pi OS is useful for learning Linux on small hardware. It teaches the same
core concepts while adding constraints around ARM architecture, removable storage,
power, peripherals, and hardware-specific configuration.

Useful checks:

```bash
cat /etc/os-release
uname -m
vcgencmd measure_temp 2>/dev/null || true
```

The architecture matters. A package, container image, or binary built for `x86_64`
may not work on `aarch64` or `armv7l`.

```bash
uname -m
dpkg --print-architecture 2>/dev/null || true
```

## Virtual Machines

Virtual machines are the safest way to practice system administration. You can take
snapshots, make mistakes, roll back, and compare distributions side by side.

Recommended lab pattern:

1. Create a clean VM.
2. Install the distribution.
3. Take a snapshot named `fresh-install`.
4. Run the lesson.
5. Save notes and command output.
6. Revert or take a new snapshot before risky work.

Keep lab VMs disposable. Do not store your only copy of important files inside a
practice machine.

## Containers

Containers are useful for quick shell and package experiments:

```bash
docker run --rm -it ubuntu:24.04 bash
docker run --rm -it debian:stable bash
```

They are not full replacements for VMs. A container usually does not boot its own
kernel, run a full init system, manage real hardware, or behave exactly like a
normal server. Use containers for focused experiments, not for lessons about boot,
kernel modules, system services, filesystems, or low-level networking unless the
lesson explicitly says containers are enough.

## Record System Facts

Every lab note should start with a small system inventory. This makes your results
repeatable and prevents future confusion.

```bash
cat /etc/os-release
uname -a
uname -m
ps -p 1 -o comm=
command -v apt dnf rpm zypper pacman 2>/dev/null
```

For a production machine, also record the hostname and cloud or hardware context:

```bash
hostnamectl 2>/dev/null || hostname
ip route | sed -n '1,5p'
```

Avoid posting private hostnames, IP addresses, serial numbers, keys, or customer
data in public places. Lab evidence should be useful without leaking secrets.

## Suggested Minimum Lab

If you can run only one environment, use an Ubuntu LTS VM. If you can run three,
use:

- Ubuntu LTS for common Debian-family examples.
- Rocky Linux or AlmaLinux for enterprise Red Hat-family examples.
- A container or Raspberry Pi for quick comparison work.

This small set will expose most command differences you need early in the course:
`apt` versus `dnf`, Debian-family versus Red Hat-family file locations, architecture
differences, and the limits of containers.
