### 29.3 Factors That Affect Performance

Linux performance is shaped by the whole service path. CPU speed matters, but so
do memory pressure, storage latency, network loss, application behavior,
configuration limits, background jobs, and recent changes.

Good performance analysis means identifying which factor is limiting the service
right now.

!!! abstract "What you will learn"
    - Name the main factors that affect Linux service performance.
    - Match common symptoms to likely resource or configuration problems.
    - Use read-only commands to collect first-pass evidence.
    - Separate host-level limits from application and dependency limits.

## CPU and scheduler pressure

CPU problems are not only about "high CPU." A host can be slow because it has too
much runnable work, expensive interrupts, process contention, or tasks waiting
for CPU time.

Useful first checks:

```bash
uptime
top
ps -eo pid,ppid,stat,pcpu,comm --sort=-pcpu | head
vmstat 1 5
```

Look for:

- load average much higher than the number of available CPUs
- many runnable processes
- one process consuming a large share of CPU
- high system CPU time rather than user CPU time
- CPU-heavy background jobs running during peak traffic

Do not assume high CPU is always bad. A busy batch worker may be healthy. The key
question is whether CPU pressure lines up with the user-visible symptom.

## Memory and swap behavior

Memory problems often look like random slowness. When RAM is tight, Linux may
reclaim cache, swap pages, or spend time managing memory instead of doing useful
work.

Useful first checks:

```bash
free -h
vmstat 1 5
cat /proc/meminfo | head -n 20
ps -eo pid,ppid,rss,pmem,comm --sort=-rss | head
```

Look for:

- active swap-in or swap-out activity
- a process growing unexpectedly
- low available memory during the slow period
- out-of-memory kills in the journal
- containers or services hitting memory limits

Linux uses free memory for cache, so "free" memory being low is not automatically
a problem. Watch available memory, swap activity, and service behavior.

## Storage latency and filesystem pressure

Disk performance problems are often latency problems. A system may have enough
space and still be slow because reads or writes are waiting too long.

Useful first checks:

```bash
df -h
df -ih
iostat -xz 1 5
lsblk
journalctl -k --since "1 hour ago" | grep -Ei 'error|reset|timeout|i/o'
```

Look for:

- high disk utilization with elevated await times
- filesystems near full
- inode exhaustion
- slow network-mounted filesystems
- storage error or timeout messages
- log growth or backup jobs competing with production writes

Disk fullness can also cause application failures that look unrelated. Always
check both space and inodes before chasing deeper causes.

## Network quality

Network problems can make healthy services look slow. The host may have plenty of
CPU and memory but still wait on DNS, packet retransmits, routing issues, remote
APIs, or overloaded upstream services.

Useful first checks:

```bash
ip addr
ip route
ss -s
ss -tulpen
ping -c 4 1.1.1.1
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

Look for:

- packet loss or high latency
- DNS resolution delays
- many connections stuck in unusual states
- services listening only on the wrong interface
- firewall or security group changes
- dependency timeouts in application logs

When testing network behavior, compare local, gateway, internet, and service
dependency paths. That comparison tells you where the delay begins.

## Application behavior

The application itself may be the bottleneck. Common causes include inefficient
queries, lock contention, excessive logging, cache misses, thread-pool
exhaustion, slow startup, and external API waits.

Useful first checks:

```bash
systemctl status <service>
journalctl -u <service> --since "30 minutes ago"
ss -tanp | grep <service-name-or-port>
```

Look for:

- rising request latency
- elevated error rate
- slow database or cache calls
- worker exhaustion
- queue backlog
- repeated restarts
- deployment or configuration changes near the start of the problem

Host metrics can show pressure, but application logs often explain why the
pressure exists.

## Configuration limits

Performance can be limited by configuration long before hardware is exhausted.
Examples include process limits, file descriptor limits, service worker counts,
database connection pools, queue concurrency, kernel networking settings, and
container resource limits.

Useful first checks:

```bash
systemctl show <service> -p LimitNOFILE -p TasksMax -p MemoryMax -p CPUQuota
ulimit -a
sysctl -a 2>/dev/null | grep -E 'somaxconn|ip_local_port_range|tcp_tw_reuse'
```

Look for:

- "too many open files" errors
- connection pool exhaustion
- worker or thread limits reached
- systemd service limits lower than expected
- container CPU or memory quotas
- queue concurrency set too low or too high

Change limits carefully. Raising a limit can move the bottleneck somewhere more
dangerous, such as from the web service to the database.

## Workload shape

Average load can hide bursts. A system that looks fine over five minutes may be
overwhelmed for 20 seconds at a time.

Workload shape includes:

- request rate
- request size
- read/write mix
- background job timing
- cron schedules
- backup windows
- traffic spikes
- batch imports
- cache warmup periods

When a system is slow, ask what changed in the workload. The answer may be a new
customer, a marketing campaign, a larger file upload, a monthly report, or a job
that now runs at the wrong time.

## Recent changes

Recent changes are performance factors too.

Check:

- deployments
- package updates
- configuration-management runs
- kernel upgrades
- data migrations
- infrastructure changes
- DNS, firewall, or load balancer edits
- certificate renewal or proxy changes

A performance incident that starts right after a change deserves a change-first
investigation. That does not prove the change caused the problem, but it gives
you a strong first hypothesis.

## Environment and hardware limits

Virtual machines, containers, and cloud instances can be constrained by the
environment around them.

Examples:

- CPU steal time on an oversubscribed hypervisor
- burst-credit exhaustion
- noisy neighbors
- storage IOPS limits
- network throughput caps
- container CPU quotas
- memory pressure on the host

On virtualized or cloud systems, local Linux metrics may not tell the whole
story. Compare host evidence with platform-level metrics when available.

## First-pass factor checklist

When a Linux service is slow, collect a small evidence bundle:

```bash
date -Is
uptime
free -h
df -h
df -ih
vmstat 1 5
iostat -xz 1 5
ss -s
systemctl --failed
journalctl -p warning..alert --since "30 minutes ago"
```

Then classify the strongest signal:

- CPU or scheduler pressure
- memory pressure or swap activity
- storage latency or filesystem exhaustion
- network delay or connection pressure
- application errors or dependency waits
- configuration limits
- workload burst
- recent change
- environment constraint

That classification guides the next command. It also prevents random tuning.

## Hands-on practice

Use a disposable VM, container, or lab machine.

1. Record baseline host evidence:

   ```bash
   date -Is
   uptime
   free -h
   df -h
   vmstat 1 5
   ```

2. Choose one factor to simulate, such as CPU pressure or disk activity.
3. Re-run the same evidence commands.
4. Write a short note that identifies:

   ```text
   Factor:
   Symptom:
   Evidence:
   First safe next step:
   What not to change yet:
   ```

5. Explain how you would tell the difference between the simulated factor and at
   least one similar-looking problem.
