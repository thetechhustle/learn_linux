### 29.4 Stolen CPU Cycles

Stolen CPU time is CPU time your virtual machine wanted to use but could not get
because the hypervisor was running something else. It is usually visible inside
Linux as `%st`, or steal time.

This matters most on virtual machines and cloud instances. A service can be
slow even when its own processes are not misbehaving, because the physical host
is oversubscribed or the instance is being throttled.

!!! abstract "What you will learn"
    - Explain what CPU steal time means on Linux.
    - Find steal time with common read-only tools.
    - Separate steal time from normal CPU saturation, I/O wait, and load spikes.
    - Decide when the right fix is inside the VM and when it belongs to the
      virtualization or cloud platform.

## What steal time means

Inside a virtual machine, Linux schedules work onto virtual CPUs. Those virtual
CPUs must eventually run on physical CPUs owned by the hypervisor.

Steal time is the percentage of time when the guest Linux kernel had runnable
work but the hypervisor did not give the VM physical CPU time.

In `top`, it appears as `st`:

```text
%Cpu(s):  5.5 us,  2.5 sy,  0.0 ni, 84.6 id,  0.4 wa,  0.0 hi,  0.5 si,  6.5 st
```

In this example, `6.5 st` means 6.5 percent of CPU time was stolen from the VM.
That time was not idle and not used by your application. It was unavailable to
the guest.

## Why it happens

Common causes include:

- too many busy VMs on the same physical host
- a cloud instance class with burst limits or throttling
- noisy-neighbor workload on shared infrastructure
- a VM with too many virtual CPUs for the host to schedule efficiently
- host-level maintenance, migration, or resource pressure
- container or nested-virtualization limits above the guest

Steal time is not usually fixed by changing a Linux process nice value. The
guest cannot schedule CPU time the hypervisor does not provide.

## First checks

Use read-only commands first:

```bash
top
mpstat 1 5
vmstat 1 5
uptime
lscpu
cat /proc/stat | head
```

If `mpstat` is not installed, it is usually provided by the `sysstat` package.
Do not install it during an incident unless package changes are allowed. `top`
and `vmstat` are often enough for first-pass evidence.

Look for:

- sustained nonzero `%st`
- steal time rising during the reported slowdown
- high load average with modest guest CPU usage
- application latency increasing while `%us` and `%sy` stay reasonable
- multiple virtual CPUs all showing steal at the same time

## Read `top` carefully

The CPU line in `top` separates several kinds of time:

- `us`: user-space application CPU
- `sy`: kernel CPU
- `id`: idle time
- `wa`: I/O wait
- `hi` and `si`: hardware and software interrupt time
- `st`: stolen time

Do not collapse these into "CPU is high." They point to different problems.

Examples:

- high `us`: application work is consuming CPU
- high `sy`: kernel work, networking, storage, or system calls may be heavy
- high `wa`: tasks are waiting on I/O
- high `st`: the VM is waiting on the hypervisor for CPU time

## Compare steal time to symptoms

Short steal-time spikes may be harmless. Sustained steal time during a slowdown
is more important.

Ask:

- Did `%st` rise when users reported slowness?
- Is the problem limited to one VM or visible across several VMs on the same
  host or instance type?
- Did the issue start after resizing the VM, changing instance class, or moving
  infrastructure?
- Does latency improve after moving the workload to a different host or larger
  instance?

The best evidence connects steal time to the service symptom, not just to a
single screenshot.

## Distinguish steal from local saturation

High load average can be caused by many things. Use other signals before blaming
the platform.

If CPU is locally saturated, you may see:

- high `%us` or `%sy`
- top processes consuming CPU
- queues or workers doing real work
- low idle time with little or no steal time

If steal is the dominant problem, you may see:

- elevated `%st`
- modest application CPU usage
- high response latency despite no single hot process
- improvement after host migration or instance resizing

If I/O wait is the problem, you may see:

- high `%wa`
- elevated disk latency in `iostat`
- storage or filesystem warnings
- slow reads or writes

Treat these as different lanes. Tuning one lane rarely fixes another.

## What you can do inside the VM

Guest-level improvements can reduce how much CPU the service needs:

- stop unnecessary background jobs
- move batch work away from peak traffic
- reduce expensive polling
- fix runaway processes
- tune application worker counts
- cache repeated work when safe
- optimize hot queries or code paths

These changes help if your workload is genuinely CPU-heavy. They do not solve a
badly oversubscribed host by themselves.

## What belongs to the platform

Some fixes require virtualization or cloud action:

- move the VM to a less busy host
- choose a dedicated or less oversubscribed instance class
- resize to a different CPU shape
- check burst-credit or CPU-credit exhaustion
- review cloud provider metrics for throttling
- contact the hosting provider with timestamps and evidence
- rebalance workloads across hosts

In cloud environments, compare Linux evidence with provider metrics. AWS, Azure,
Google Cloud, Proxmox, VMware, and other platforms expose different views of host
and instance pressure.

## Container note

Containers can also appear CPU-constrained, but container CPU limits are not the
same thing as hypervisor steal time.

For containers, check:

```bash
docker stats
cat /sys/fs/cgroup/cpu.max 2>/dev/null
cat /sys/fs/cgroup/cpu.stat 2>/dev/null
```

Container throttling often shows up through cgroup counters rather than `%st`.
If a container runs inside a VM, both container throttling and VM steal time can
exist at once.

## Evidence bundle for escalation

When you escalate suspected steal time, include:

- host or instance name
- VM size or instance type
- affected service
- exact time window
- `top` or `mpstat` output showing `%st`
- `uptime` and load average
- application symptom, such as latency or error rate
- recent infrastructure changes
- whether another host or instance shows the same problem

Example note:

```text
Symptom: API p95 latency rose from 240 ms to 1.8 s between 14:05 and 14:25 UTC.
Evidence: top showed 12-18% st during the same window; app CPU stayed under 35%.
Not likely: disk I/O wait stayed under 1%; no OOM kills; no deploy in the window.
Ask: migrate or inspect the physical host for oversubscription/noisy neighbor.
```

This is much stronger than saying "the VM feels slow."

## Hands-on practice

Use a disposable VM if available. If you are on bare metal, steal time will
usually be zero.

1. Check current CPU accounting:

   ```bash
   top
   vmstat 1 5
   ```

2. If `sysstat` is already installed, collect per-CPU evidence:

   ```bash
   mpstat -P ALL 1 5
   ```

3. Record whether `%st` is present.
4. Start a small CPU workload in a separate shell if safe, then re-check the
   same commands.
5. Explain whether the system shows local CPU pressure, steal time, both, or
   neither.
