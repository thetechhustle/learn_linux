### 29.2 Ways to Improve Performance

Performance improvements come from removing the bottleneck that matters to the workload, not from applying every tuning tip you can find. A good operator starts with evidence, chooses one low-risk change, and proves whether the result improved the service.

!!! abstract "What you will learn"
    - Separate performance improvements from general housekeeping.
    - Match common symptoms to CPU, memory, storage, network, and application changes.
    - Make tuning changes reversible and measurable.
    - Build a short before-and-after note for a performance change.

!!! example "Field story"
    A web server became slow after traffic doubled. The team wants to raise every sysctl value they found in a tuning blog. You collect CPU, memory, disk, network, and application evidence first, then choose the smallest change that addresses the actual constraint.

!!! success "Operator principle"
    Change the bottleneck you can prove, then measure again.

## Start with the service promise

Performance is only meaningful relative to what the system is supposed to do. Before tuning, write down the promise in plain language:

- "The API should return 95 percent of requests in under 300 ms."
- "Backups should finish before business hours."
- "Interactive SSH sessions should remain responsive during batch jobs."
- "The database should keep replication lag under 30 seconds."

That promise tells you which metric matters. A server can have high CPU usage and still be healthy if latency, errors, and queue depth are normal. A server can have low CPU usage and still be broken if every request is waiting on slow storage.

## Improve the right layer

Most performance work falls into a few lanes.

| Lane | Evidence to collect | Possible improvement |
| --- | --- | --- |
| CPU | `uptime`, `top`, `mpstat`, `pidstat` | reduce expensive work, add workers carefully, fix hot code paths, move batch jobs |
| Memory | `free -h`, `vmstat 1`, `top`, OOM logs | reduce process footprint, fix leaks, change cache sizes, add memory |
| Storage | `df -h`, `iostat -xz 1`, `iotop`, application logs | free space, move hot data, tune database I/O, use faster storage |
| Network | `ss -s`, `sar -n DEV 1`, `ip -s link`, load balancer metrics | reduce chatter, fix packet loss, scale front ends, adjust timeouts |
| Application | request logs, queue depth, error rate, tracing | fix slow queries, cache expensive reads, increase worker pools, remove retries |

Do not skip the application lane. Many "Linux performance" problems are really slow database queries, saturated thread pools, retry storms, or external dependencies.

## Use housekeeping carefully

Routine maintenance can prevent performance problems, but it is not the same as tuning.

Useful housekeeping includes:

- keeping security and bug-fix updates current;
- rotating logs so filesystems do not fill;
- removing abandoned services from startup;
- cleaning old temporary files with approved retention rules;
- checking that monitoring and alerting still cover the service.

Avoid treating housekeeping as a blind fix during an incident. For example, upgrading packages during an outage may change too many variables at once unless the evidence points to a known bug.

## Prefer reversible changes

Choose changes that can be rolled back quickly:

- restart or scale a stateless worker pool;
- move a batch job out of peak hours;
- increase an application cache with a documented memory limit;
- add an index after testing query plans on staging;
- change one sysctl value temporarily with `sysctl -w` before making it persistent;
- add capacity when the resource graph clearly shows sustained saturation.

Riskier changes need stronger controls:

- kernel upgrades;
- filesystem or mount-option changes;
- database configuration changes that affect durability;
- disabling security controls for speed;
- deleting data to free space;
- changing network timeouts without understanding clients.

When a change can damage data, security, or access, test it in a lab or staging environment first and make sure a rollback plan exists.

## Example: a slow web server

Start with read-only checks:

```bash
uptime
top -o %CPU
free -h
vmstat 1 5
iostat -xz 1 5
ss -s
journalctl -u nginx --since "30 minutes ago"
```

Then map the evidence to a likely improvement:

- High load with high CPU: reduce expensive application work, profile the hot process, or add CPU capacity.
- High load with high I/O wait: inspect storage latency, database queries, logs, and backup jobs.
- Low free memory with active swapping: reduce memory pressure or add memory before increasing concurrency.
- Many established connections and rising latency: check worker limits, keepalive behavior, upstream dependencies, and load balancer health.
- Normal host metrics with high application latency: inspect application logs, database timing, and dependency calls.

Only after that should you change something.

## Make one change at a time

A useful tuning note has five parts:

```text
Service:
Symptom:
Before evidence:
Change made:
After evidence:
Rollback:
```

Example:

```text
Service: public web front end
Symptom: p95 latency rose from 180 ms to 900 ms during backup window
Before evidence: iostat showed 65 ms await on data volume; nginx errors were normal
Change made: moved backup job from 13:00 to 02:00 UTC
After evidence: next backup window p95 stayed under 220 ms; await stayed below 8 ms
Rollback: restore previous cron entry from git if needed
```

This format keeps the change tied to proof. It also helps the next operator understand why the system is configured that way.

## Common mistakes

- Applying a tuning checklist without knowing the bottleneck.
- Increasing concurrency when the system is already CPU, memory, or database limited.
- Hiding a real application bug by adding hardware too early.
- Making permanent sysctl changes without recording the default and rollback.
- Optimizing average latency while ignoring p95 or p99 latency.
- Running destructive cleanup commands on production data without owner approval.
- Measuring only after the change and forgetting the baseline.

## Hands-on practice

Use a disposable VM, container, or lab server.

1. Pick a simple service or command to observe, such as a local web server, a database container, or a CPU-bound script.
2. Capture a baseline with `uptime`, `top`, `free -h`, `vmstat 1 5`, and one service-specific log or metric.
3. Introduce one controlled source of load, such as a test request loop or a CPU stress process in the lab.
4. Choose one reversible improvement, such as reducing the test load, moving the job, adjusting worker count, or adding a cache in the lab.
5. Record the before evidence, change, after evidence, and rollback in the tuning-note format above.

## Check your understanding

- Why is "make the server faster" not a good tuning goal by itself?
- Which command would help you tell CPU saturation from storage wait?
- Why can increasing worker count make performance worse?
- What evidence would justify adding capacity instead of changing configuration?
- What should you record before making a temporary sysctl change persistent?
