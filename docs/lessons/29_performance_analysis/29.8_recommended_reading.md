### 29.8 Recommended Reading

Performance analysis improves when you practice two habits together: read from reliable sources and immediately turn what you read into repeatable checks. A good resource should teach you what a signal means, when to trust it, and how to prove that a change actually helped.

!!! abstract "What you will learn"
    - Choose performance references that match the problem you are investigating.
    - Build a reading plan around CPU, memory, storage, network, and application evidence.
    - Convert notes from a book, article, or manual page into a short lab exercise.
    - Keep a performance notebook that helps during future incidents.

!!! success "Operator principle"
    Read for methods, not magic commands. A useful performance reference teaches you how to form, test, and retire a hypothesis.

## Start with the performance method

Before chasing individual tools, read material that teaches a systematic approach:

- **Systems Performance: Enterprise and the Cloud**, by Brendan Gregg, is the strongest general reference for Linux performance work. Use it to learn investigation methods, observability concepts, and resource-by-resource analysis.
- Brendan Gregg's public performance material is useful for quick refreshers on the USE method, CPU profiling, flame graphs, and Linux tool selection.
- The `man` pages for tools such as `uptime`, `top`, `vmstat`, `iostat`, `sar`, `ss`, `perf`, and `strace` are worth reading alongside examples. They explain field names and sampling behavior that short blog posts often skip.

Read these with a lab machine nearby. When a source introduces a metric, pause and find that metric on your own system.

## Build resource-specific shelves

Performance problems usually live in one or more resource lanes. Keep references grouped by the lane they explain best.

| Lane | What to study | Useful commands to practice |
| --- | --- | --- |
| CPU and scheduler | Load average, runnable queues, CPU saturation, steal time, context switches | `uptime`, `top`, `mpstat`, `pidstat`, `perf top` |
| Memory | Working set, cache, swap pressure, OOM behavior | `free -h`, `vmstat`, `swapon --show`, `dmesg`, `/proc/meminfo` |
| Storage | Capacity, latency, queueing, filesystem pressure, inode exhaustion | `df -h`, `df -i`, `iostat -xz`, `lsblk`, `du` |
| Network | Listeners, retransmits, packet loss, DNS latency, path changes | `ss -tulpn`, `ip route`, `ping`, `mtr`, `dig`, `tcpdump` |
| Application | Logs, request latency, dependency errors, worker limits, release changes | `journalctl`, application logs, health checks, tracing or APM tools |

Do not try to memorize every flag. Learn which command gives a first-pass answer and which command gives deeper evidence.

## Read vendor and project documentation

Books and articles teach durable concepts. Project documentation tells you how the software on your host actually behaves.

- Read your distribution's performance, package, and kernel documentation before changing kernel parameters or service defaults.
- Read the documentation for the database, web server, queue, runtime, or storage service involved in the incident.
- Prefer official docs for tunables, defaults, and version-specific behavior.
- Treat random tuning checklists as untrusted until you can explain each setting and roll it back.

!!! warning "Avoid cargo-cult tuning"
    A setting that helped one workload can hurt another. Never paste a performance tuning block into production just because it appears in a popular article.

## Keep a performance notebook

Turn reading into operational memory. A useful note is short, repeatable, and tied to evidence.

```text
Topic:
Source:
Problem it helps diagnose:
First-pass command:
Healthy-looking output:
Unhealthy-looking output:
Common false positives:
Safe next step:
Rollback or stop condition:
```

This notebook becomes more valuable than a long bookmark list because it captures what you have personally verified.

## Hands-on practice

Use a disposable VM, container host, or lab machine.

1. Choose one resource lane from the table above.
2. Read one official manual page or trusted chapter section for a tool in that lane.
3. Run the command in a healthy idle state and save the output.
4. Create a small, reversible load or pressure condition, such as a CPU-bound test process or a temporary large file in a scratch directory.
5. Run the command again and note which fields changed.
6. Write one notebook entry that explains when you would use that command during an incident.

- What makes an online performance recommendation unsafe to apply directly?

- How would you turn a reading note into a repeatable lab exercise?
