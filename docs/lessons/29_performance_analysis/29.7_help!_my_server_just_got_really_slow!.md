### 29.7 Help! My Server Just Got Really Slow!

!!! abstract "What you will learn"
    - Triage a sudden Linux server slowdown without guessing.
    - Separate user-visible symptoms from host-level resource pressure.
    - Collect enough evidence to choose a safe next action and verify recovery.

When a server suddenly becomes slow, the worst response is to start restarting random services. Slow can mean many different things: high CPU, memory pressure, disk wait, network trouble, a database lock, a bad deploy, a traffic spike, or a dependency failure.

Your first job is to preserve evidence and narrow the problem.

!!! warning "Do not erase the trail"
    Avoid reboots, service restarts, cache drops, log deletion, and package changes until you have a baseline. Those actions may be necessary later, but they can also hide the real cause.

## First 60 Seconds

Start with a timestamp and a short symptom statement:

```bash
date -Is
hostname
uptime
```

Write down what is slow:

```text
Reported symptom:
Who is affected:
When it started:
What changed recently:
Current user impact:
```

Then ask the most important operational question: is the server slow, or is one application path slow?

Examples:

- "SSH login is slow" may point to DNS, PAM, load, or storage.
- "The website is slow" may point to the web server, app, database, network, or upstream API.
- "Everything is slow" usually points toward host resource pressure, storage wait, or a broad dependency problem.

## Check the Host Pulse

Run a quick host snapshot:

```bash
uptime
free -h
df -h
df -ih
top -b -n 1 | sed -n '1,20p'
```

Look for:

- Load average much higher than CPU count.
- Very low available memory.
- Swap activity.
- Filesystems or inodes near full.
- High CPU wait time (`wa`) in `top`.
- One process dominating CPU or memory.

Get the CPU count so load average has context:

```bash
nproc
```

A load average of `12` means something very different on a 2-core host than on a 32-core host.

## Find the Busiest Processes

Sort processes by CPU:

```bash
ps -eo pid,ppid,comm,%cpu,%mem,stat --sort=-%cpu | head
```

Sort processes by memory:

```bash
ps -eo pid,ppid,comm,%mem,rss,stat --sort=-rss | head
```

Useful questions:

- Is one process clearly responsible?
- Is the top process expected for this host?
- Did the process start recently?
- Is the process in `R` running state, `D` uninterruptible sleep, or repeatedly restarting?

If `pidstat` is available, sample over time:

```bash
pidstat 1 5
```

Do not assume a process is bad just because it is busy. A busy database during a traffic spike may be doing useful work. The question is whether the work is expected and whether it explains the symptom.

## Check Memory Pressure

Use `free` and `vmstat` together:

```bash
free -h
vmstat 1 5
```

In `free`, focus on `available`, not just `free`. Linux uses memory for cache on purpose.

In `vmstat`, watch:

- `si` and `so`: swap in and swap out.
- `r`: runnable processes.
- `b`: processes blocked on I/O.
- `wa`: CPU time waiting on I/O.

Continuous swap activity during the slowdown is strong evidence of memory pressure.

## Check Disk Pressure

First check capacity:

```bash
df -h
df -ih
```

Then check I/O wait if the tool is available:

```bash
iostat -xz 1 5
```

If `iostat` is not installed:

```bash
vmstat 1 5
lsblk
```

Disk pressure clues include:

- High `%wa` in `top`.
- High `b` in `vmstat`.
- A filesystem or inode table at or near 100 percent.
- Long await times or high utilization in `iostat`.
- Processes stuck in `D` state.

To find large log growth quickly, start with known log paths:

```bash
du -h -d 1 /var/log 2>/dev/null | sort -h | tail
```

Use deletion carefully. Rotate, compress, move, or truncate only after you know what is growing and why.

## Check Network and Listeners

If the symptom is network-facing, confirm the service is reachable locally before blaming the internet.

```bash
ip -brief address
ip route
ss -tulpn
ss -s
```

For a web service:

```bash
ss -tulpn | grep -E ':80|:443'
curl -I --max-time 5 http://127.0.0.1/
```

Adjust the URL and port for your service.

Local success but public failure points toward firewall, proxy, load balancer, DNS, routing, or upstream network issues. Local failure points toward the service, application, or local host.

## Check Services and Logs

List failed services:

```bash
systemctl --failed
```

Inspect the affected service:

```bash
systemctl status nginx --no-pager
journalctl -u nginx --since "30 minutes ago" --no-pager
```

Replace `nginx` with the service you are investigating.

Also check recent warnings and errors:

```bash
journalctl -p warning..alert --since "30 minutes ago" --no-pager
```

Look for:

- Restart loops.
- Out-of-memory messages.
- Permission errors.
- Disk full errors.
- Connection timeouts.
- Database or upstream dependency failures.

## Check Recent Changes

Slowdowns often follow a change. Do this before tuning kernel parameters.

```bash
last -n 10
who
find /etc -xdev -type f -mtime -1 2>/dev/null | head
```

On Debian or Ubuntu:

```bash
grep -i " install \\| upgrade \\| remove " /var/log/dpkg.log 2>/dev/null | tail
```

On RPM-based systems:

```bash
rpm -qa --last | head
```

Also check your deployment system, scheduler, backup jobs, cron jobs, and monitoring alerts. A "server" problem is often a recent application or workload change.

## Decide the First Safe Action

Use the evidence to choose the smallest useful action.

| Evidence | Likely direction | Safer first action |
| --- | --- | --- |
| One process uses all CPU | Hot process or traffic spike | Check app logs and request volume before restarting |
| High load and high I/O wait | Storage bottleneck | Identify writer/readers and disk capacity before deleting files |
| Continuous swap activity | Memory pressure | Identify largest process and recent growth |
| Disk full | Capacity incident | Find growth source and rotate/move safely |
| Service not listening | Service failure | Inspect `systemctl status` and service logs |
| Local service fast, public path slow | Network/proxy/upstream issue | Check proxy, DNS, firewall, load balancer, and upstream status |
| Recent deploy | Regression | Compare logs, metrics, and rollback plan |

The right first action is usually reversible, narrow, and measurable.

## Verify Recovery

After any change, re-run the same checks you used to diagnose the issue:

```bash
date -Is
uptime
free -h
df -h
top -b -n 1 | sed -n '1,20p'
systemctl status nginx --no-pager
```

Also verify the user-facing path:

```bash
curl -I --max-time 5 http://127.0.0.1/
```

Do not declare recovery from a clean command alone. Recovery means the symptom improved and the supporting metrics make sense.

## Incident Note Template

Use a short note like this:

```text
Incident:
Start time:
Affected service:
User-visible symptom:
Evidence collected:
Likely cause:
Action taken:
Verification:
Follow-up:
```

Example:

```text
Incident: Web app became slow after deploy.
Start time: 2026-05-13T22:10:00-04:00
Affected service: web frontend
User-visible symptom: pages took 20+ seconds to load.
Evidence collected: CPU normal, memory normal, app logs showed database timeout spike, local nginx responded quickly.
Likely cause: application/database path, not host-wide pressure.
Action taken: rolled back the last deploy.
Verification: curl response time returned under 1 second and timeout errors stopped.
Follow-up: compare database query behavior between the failed deploy and previous release.
```

## Hands-on Practice

Use a disposable VM or lab host.

1. Start a harmless CPU workload such as `yes > /dev/null` in one terminal.
2. Use `uptime`, `top`, `ps`, and `pidstat` if available to identify it.
3. Stop the workload and verify the host returns to normal.
4. Repeat with a safe disk-space exercise in a temporary directory if you know how to clean it up.
5. Write an incident note using the template above.

!!! warning "Clean up lab workloads"
    Stop any test process you start. Do not run stress tests on production systems unless you have explicit approval.
