## 29.6 System Performance Checkup

!!! abstract "What you will learn"
    - Run a repeatable Linux performance checkup without making the incident worse.
    - Collect useful evidence about CPU, memory, storage, network, services, and recent changes.
    - Turn raw command output into a short operator note that another admin can trust.

A system performance checkup is a structured pass through the host. It is not a hunt for one magic command. The goal is to answer three questions:

1. Is the host under pressure right now?
2. Which resource is most likely limiting useful work?
3. What evidence should be saved before anyone changes the system?

Run a checkup before planned maintenance, after a complaint that "the server is slow," before scaling a service, and after recovering from an outage. A good checkup is read-heavy, timestamped, and easy to repeat.

!!! warning "Start with observation"
    Avoid restarts, cache drops, package changes, firewall edits, and tuning commands until you have a baseline. A rushed "fix" can erase the evidence you need to find the actual cause.

## Create a Checkup Note

Start every checkup with a small note. This makes your work useful to the next person.

```text
Host:
Date/time:
Reason for checkup:
Reported symptom:
Recent changes:
Main finding:
Next action:
```

Record the time before collecting data:

```bash
date -Is
hostnamectl
uptime
```

The `uptime` output gives you the current time, how long the host has been running, how many users are logged in, and the load average for the last 1, 5, and 15 minutes.

## Snapshot the Host

Collect a quick inventory first:

```bash
uname -a
lscpu | sed -n '1,20p'
free -h
df -h
df -ih
ip -brief address
```

This snapshot tells you the kernel, CPU shape, memory totals, filesystem space, inode usage, and configured addresses. It also helps you avoid comparing the current host to the wrong mental model.

## CPU and Load

Load average is useful only when you compare it to CPU capacity. A load of 8 can be normal on a 32-core host and painful on a 2-core host.

```bash
nproc
uptime
top -b -n 1 | sed -n '1,20p'
ps -eo pid,ppid,comm,%cpu,%mem,stat --sort=-%cpu | head
```

Look for:

- Load average much higher than available CPU cores.
- One process using most of the CPU.
- Many processes stuck in `R` running state.
- High `%wa` in `top`, which usually points toward storage wait rather than pure CPU pressure.

If `pidstat` is installed, sample process activity over time:

```bash
pidstat 1 5
```

One sample is a snapshot. Several samples show direction.

## Memory and Swap

Memory pressure is not the same as "free memory is low." Linux uses memory for cache because idle memory is wasted memory. Focus on available memory, swap activity, and processes growing unexpectedly.

```bash
free -h
vmstat 1 5
ps -eo pid,ppid,comm,%mem,rss --sort=-rss | head
```

In `vmstat`, watch the `si` and `so` columns. Continuous swap-in or swap-out activity means the host is working around memory shortage.

Useful questions:

- Is `available` memory very low?
- Is swap being used heavily right now?
- Did one process grow larger than expected?
- Did the issue begin after a traffic spike, deployment, import job, or backup?

## Storage Capacity and Latency

Storage problems often show up as slow applications, high load, or stuck processes.

Check capacity:

```bash
df -h
df -ih
```

Then check disk activity if the tools are available:

```bash
iostat -xz 1 5
```

Look for:

- Filesystems above about 90 percent full.
- Inodes exhausted even when disk space remains.
- High disk utilization for long periods.
- High await times during the reported slowdown.

If `iostat` is not installed, use the tools you do have:

```bash
lsblk
vmstat 1 5
```

The `b` column in `vmstat` shows processes blocked on I/O.

## Network and Listening Services

For network-facing hosts, confirm that the expected addresses and listening ports exist before blaming the application.

```bash
ip -brief address
ip route
ss -tulpn
ss -s
```

Look for:

- Missing or unexpected IP addresses.
- Routes pointing through the wrong gateway.
- A service not listening on the expected port.
- Many connections in unusual states.

For a specific port:

```bash
ss -tulpn | grep ':443'
```

Replace `443` with the port you are investigating.

## Services and Logs

The service manager and journal often explain why performance changed.

```bash
systemctl --failed
journalctl -p warning..alert --since "1 hour ago"
```

For one service:

```bash
systemctl status nginx --no-pager
journalctl -u nginx --since "1 hour ago" --no-pager
```

Replace `nginx` with the service you are checking.

Look for:

- Restart loops.
- Failed units.
- Permission errors.
- Out-of-memory messages.
- Repeated connection, disk, or timeout errors.

## Recent Changes

Performance problems often follow a change. Check what changed before tuning the system.

```bash
last -n 10
who
find /etc -xdev -type f -mtime -1 2>/dev/null | head
```

On package-managed systems, inspect the relevant package history:

```bash
grep -i " install \\| upgrade \\| remove " /var/log/dpkg.log 2>/dev/null | tail
```

For RPM-based systems, use:

```bash
rpm -qa --last | head
```

Recent deploys, package updates, configuration edits, backups, imports, and traffic changes are often more important than another minute of metric gathering.

## Triage Table

Use this table to connect symptoms to next checks.

| Symptom | First evidence to collect | Common direction |
| --- | --- | --- |
| High load, low CPU use | `top`, `vmstat`, `iostat` | Storage wait or blocked processes |
| High CPU use | `top`, `ps`, `pidstat` | Hot process, traffic spike, loop, batch job |
| Low available memory | `free`, `vmstat`, `ps --sort=-rss` | Growing process or undersized host |
| Disk full | `df -h`, `du` on known data paths | Logs, backups, uploads, package cache |
| Inodes full | `df -ih`, directory counts | Too many small files |
| Service slow or down | `systemctl status`, `journalctl -u` | Restart loop, dependency, config error |
| Network complaint | `ip route`, `ss`, service logs | Wrong route, listener missing, connection backlog |

## Finish With a Finding

Do not end a checkup with only pasted output. Write a short finding:

```text
Finding:
Evidence:
Risk:
Recommended next action:
Verification after action:
```

Example:

```text
Finding: The host is storage-bound, not CPU-bound.
Evidence: Load average is 18 on a 4-core host, top shows high wa, and iostat shows the main disk near 100 percent utilization.
Risk: Restarting the application may hide the symptom without fixing the disk bottleneck.
Recommended next action: Identify the process writing to disk and check recent log growth before deleting or rotating files.
Verification after action: Re-run uptime, top, df -h, and iostat after the change.
```

## Hands-on Practice

Use a disposable VM, lab server, or container host.

1. Create a checkup note with the template in this lesson.
2. Run the CPU, memory, storage, network, service, and recent-change checks.
3. Pick the most interesting finding and explain why it matters.
4. Re-run the same commands after starting or stopping a harmless workload.
5. Write a final finding that a teammate could use during a handoff.
