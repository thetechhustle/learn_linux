## 29.1 Performance Tuning Philosophy

Performance tuning is not a guessing contest. A good administrator starts with
a symptom, gathers evidence, changes one thing at a time, and proves whether the
change helped.

The goal is not to make every number look perfect. The goal is to make the
system meet its service requirement with acceptable risk, cost, and operational
complexity.

## Start with the service promise

Before tuning a host, define what "fast enough" means.

A batch job, a web API, a database, and a developer workstation have different
performance goals. A 30-second delay might be harmless for a nightly report and
unacceptable for an interactive checkout page.

Useful performance goals are concrete:

- page responses should usually complete in less than 300 ms
- backups should finish before the business day starts
- SSH logins should remain interactive during normal load
- database writes should not stall when the queue grows
- CPU-heavy jobs should not starve production services

Without a service promise, tuning becomes cosmetic. You may improve a benchmark
while leaving the real user problem untouched.

## Measure before changing

Most performance incidents have several plausible causes. A slow server could be
waiting on disk, short on memory, overloaded on CPU, blocked on DNS, throttled by
network loss, or delayed by an application dependency.

Read-only observations come first:

```bash
uptime
free -h
df -h
df -ih
top
vmstat 1
iostat -xz 1
ss -tulpen
journalctl -p warning..alert --since "1 hour ago"
```

You do not need every command every time. Pick the smallest set that tests the
most likely causes.

Good notes include:

- the reported symptom
- when it started
- what changed recently
- current load, memory, disk, network, and service state
- the exact command output used to support the conclusion
- the change made
- the before-and-after result

## Tune one bottleneck at a time

A bottleneck is the constrained part of the system that limits the whole service
path. Tuning a non-bottleneck usually adds complexity without improving the
result.

For example:

- Adding CPU will not help a service blocked on slow disk writes.
- Increasing memory will not fix packet loss.
- Raising a connection limit will not help if the database is saturated.
- Rewriting an application cache may not help if DNS lookup latency is the
  dominant delay.

Make a hypothesis before changing anything:

> The web service is slow because disk latency spikes when log rotation runs.

That hypothesis can be tested. If the evidence does not support it, revise the
hypothesis instead of stacking unrelated changes.

## Prefer reversible changes

Performance changes can reduce safety margins. A setting that makes the system
faster under one workload can make it unstable under another.

Prefer changes that are easy to undo:

- adjust one service worker count instead of changing every service at once
- test a sysctl setting temporarily before making it persistent
- scale a queue consumer gradually
- increase memory limits with an explicit rollback point
- change one host or one pool before rolling across the fleet

For Linux kernel settings, separate temporary testing from durable
configuration:

```bash
sysctl vm.swappiness
sudo sysctl vm.swappiness=10
```

If the change is accepted, then record it in a managed file such as
`/etc/sysctl.d/site-performance.conf` through your normal configuration
management path. Do not leave production hosts depending on forgotten shell
history.

## Know the trade-off

Performance tuning is usually a trade-off, not a free upgrade.

Examples:

- More caching can improve latency but increase stale-data risk.
- More workers can improve concurrency but increase memory pressure.
- More aggressive timeouts can release stuck requests but break slow clients.
- Disabling expensive logging can improve throughput but reduce incident
  evidence.
- Larger buffers can smooth bursts but hide backpressure until failure is more
  severe.

Write down what you are trading away. That note helps the next operator decide
whether the tuning still makes sense after traffic, hardware, or application
behavior changes.

## Baselines beat folklore

A baseline is a record of normal behavior. It gives you something to compare
against when the system feels wrong.

Useful baselines include:

- normal CPU load and run queue depth
- memory usage and swap activity
- disk latency and filesystem fullness
- network throughput, retransmits, and error counters
- request latency and error rate
- queue depth and job completion time
- deploy frequency and recent change history

Folklore says, "This value should always be X." Baselines say, "This service
normally behaves this way, and now it changed." Baselines are more useful.

## Optimize the whole path

Users experience a complete path, not a single metric. A web request may depend
on TLS negotiation, DNS, load balancer routing, application workers, database
queries, cache hits, filesystem writes, and third-party APIs.

When you tune only the local host, you can miss the real delay.

Ask:

- Where does the request enter the system?
- Which service does it wait on next?
- Which queue grows during the slowdown?
- Which dependency changed recently?
- Which metric moves at the same time as the user symptom?

End-to-end timing is often more useful than a perfect host dashboard.

## Avoid benchmark traps

Benchmarks are useful when they match the workload you care about. They are
misleading when they reward behavior that production does not need.

Be careful when:

- the benchmark uses tiny data that fits in cache
- the benchmark runs on an idle host unlike production
- the benchmark ignores startup time, tail latency, or error rate
- the benchmark measures throughput while users care about latency
- the benchmark improves after disabling safeguards you rely on

Treat benchmarks as evidence, not as the goal.

## Document the result

Every accepted tuning change should leave a short operational record:

- symptom: what was slow
- evidence: what proved the bottleneck
- change: what was adjusted
- verification: what improved
- risk: what trade-off was accepted
- rollback: how to undo the change

This record can live in an incident note, pull request, ticket, runbook, or
configuration-management commit. The important part is that the next operator
does not have to rediscover why the setting exists.

## Practical tuning loop

Use this loop during routine optimization and incidents:

1. Define the user-visible problem.
2. Capture current evidence with read-only commands.
3. Identify the most likely bottleneck.
4. Make one small, reversible change.
5. Re-measure with the same commands.
6. Keep the change only if the service goal improves.
7. Document the change and rollback path.

If the change does not help, revert it. A failed hypothesis is useful as long as
you do not leave it behind as unexplained production configuration.

## Hands-on practice

Use a disposable VM, container, or lab machine.

1. Record a baseline:

   ```bash
   uptime
   free -h
   df -h
   vmstat 1 5
   ```

2. Create a controlled workload, such as a CPU-heavy process or a local file
   copy.
3. Run the same read-only commands again and identify what changed.
4. Write a short tuning note:

   ```text
   Symptom:
   Evidence:
   Hypothesis:
   Change tested:
   Result:
   Rollback:
   ```

5. Explain why you would or would not keep the change on a real server.
