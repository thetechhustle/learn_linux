## 29.5 Analysis of Performance Problems

Performance analysis is the discipline of turning "the system is slow" into a
specific, testable explanation. A good analysis names the affected service,
captures evidence from the time window, identifies the most likely bottleneck,
and proves whether a change actually helped.

!!! abstract "What you will learn"
    - Convert vague performance complaints into measurable symptoms.
    - Capture a first-pass evidence bundle without making the incident worse.
    - Separate CPU, memory, disk, network, and application bottlenecks.
    - Validate one hypothesis at a time and document the result.

!!! example "Field story"
    A web application is slow after a marketing campaign doubles traffic. Users
    report delayed page loads, but the host is still reachable. Instead of
    restarting services at random, you capture load, process, memory, disk,
    network, and log evidence, then decide whether the bottleneck is on the
    server, the database, the network path, or the application itself.

!!! success "Operator principle"
    Diagnose from the symptom toward the resource. Do not tune a setting until
    you can say what evidence should improve afterward.

## Start with the service symptom

Begin by defining what is slow in terms a user or service owner would recognize.
This keeps the investigation from drifting into unrelated host metrics.

- What action is slow: login, search, file upload, package install, SSH login?
- Who is affected: one user, one region, one host, every request?
- When did it start: after a deploy, traffic spike, backup, patch, or hardware
  change?
- What is the expected behavior: normal latency, throughput, or completion time?
- What is the current behavior: measured latency, error rate, queue depth, or
  timeout count?

A useful incident note starts like this:

```text
Symptom: checkout API p95 latency rose from 220 ms to 4.8 s.
Scope: all requests through web-03, not web-01 or web-02.
Start: about 14:05 UTC, shortly after the 13:55 deploy.
User impact: orders complete, but many clients retry.
First guess to test: web-03 is blocked on database calls or local disk I/O.
```

## Capture the first-pass evidence bundle

Use read-only commands first. They are fast, low risk, and give you a baseline
before anyone changes the system.

```bash
date -Is
hostnamectl
uptime
top -b -n 1 | head -40
free -h
vmstat 1 5
df -hT
df -ih
ss -tan state established | head
journalctl -p warning..alert --since "30 minutes ago"
```

If the host has the `sysstat` package, add CPU, disk, and process snapshots:

```bash
mpstat 1 5
iostat -xz 1 5
pidstat -durh 1 5
```

!!! warning "Do not hide the evidence"
    Avoid clearing caches, truncating logs, rebooting, restarting services, or
    changing kernel tunables before you capture the current state. Those actions
    can remove the evidence needed to explain the incident.

## Sort the symptom into a resource lane

Most Linux performance investigations start by deciding which lane is saturated
or waiting. Use the table as a triage guide, not as proof by itself.

| Lane | Common evidence | Useful commands |
| --- | --- | --- |
| CPU saturated | High run queue, high user or system CPU, many runnable tasks | `uptime`, `mpstat`, `top`, `pidstat -u` |
| CPU stolen | High steal time on a virtual machine | `mpstat`, `top`, cloud metrics |
| Memory pressure | Low available memory, swap activity, OOM kills | `free -h`, `vmstat`, `journalctl -k` |
| Disk I/O wait | High await, high utilization, growing queues | `iostat -xz`, `pidstat -d`, `iotop` |
| Filesystem full | No free blocks or inodes, write failures | `df -hT`, `df -ih`, application logs |
| Network path | Retransmits, failed connects, packet loss, DNS delays | `ss -s`, `ip -s link`, `ping`, `mtr`, `dig` |
| Application queue | Workers busy, request queue growth, dependency timeouts | service metrics, logs, `systemctl status` |

The lane with the highest number is not always the root cause. For example,
high CPU can be caused by retry storms after a database timeout. High network
connections can be normal for a busy proxy. Tie every metric back to the user
symptom and the incident timeline.

## Build one hypothesis at a time

A hypothesis should be narrow enough that a command can support or reject it.

Weak:

```text
The server is overloaded.
```

Better:

```text
The web workers are waiting on disk because request logs are being written to a
nearly full filesystem. If true, iostat will show high await on the log device,
df will show low free space, and application logs will contain write delays or
errors.
```

Useful hypotheses usually include:

- The suspected resource or dependency.
- The evidence that would support the claim.
- The evidence that would disprove it.
- The smallest reversible change you would try if the claim is true.

## Compare before and after

A performance fix is not complete when the command succeeds. It is complete when
the measured service symptom improves and the system remains stable.

```text
Before:
  p95 latency: 4.8 s
  web-03 load average: 18 on 4 CPUs
  iostat await on xvdb: 280 ms
  /var/log filesystem: 98% full

Change:
  compressed old logs, moved archived logs to backup storage, restarted log
  rotation timer after validating the config.

After:
  p95 latency: 310 ms
  web-03 load average: 2.1 on 4 CPUs
  iostat await on xvdb: 8 ms
  /var/log filesystem: 61% full

Follow-up:
  add filesystem alert at 80%, review log retention, and check every web host.
```

If the metric does not improve, write that down too. A rejected hypothesis saves
time for the next operator.

## Common analysis mistakes

- Treating `top` as the whole investigation instead of one snapshot.
- Chasing average CPU while users are affected by tail latency.
- Ignoring the time window of the complaint.
- Restarting a service before collecting logs and queues.
- Changing several settings at once and losing the ability to tell what helped.
- Optimizing a host when the real bottleneck is a database, DNS resolver, load
  balancer, or external API.
- Declaring success because the host looks better while the user-facing symptom
  is still slow.

## Hands-on practice

Use a disposable VM, container, or lab machine.

1. Start a simple workload in one terminal:

   ```bash
   yes > /tmp/cpu-load.txt
   ```

2. In another terminal, capture a first-pass evidence bundle:

   ```bash
   date -Is
   uptime
   top -b -n 1 | head -25
   vmstat 1 5
   free -h
   df -hT /tmp
   ```

3. Identify the resource lane that changed most clearly.
4. Stop the workload with `Ctrl+C`, then remove the lab file:

   ```bash
   rm -f /tmp/cpu-load.txt
   ```

5. Re-run the evidence commands and write a short before/after note.

!!! tip "Lab variation"
    If you have `stress-ng` installed on a lab host, use `stress-ng --cpu 2
    --timeout 60s` instead of `yes`. Do not install or run stress tools on a
    production server during an incident.
