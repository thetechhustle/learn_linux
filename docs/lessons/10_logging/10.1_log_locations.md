### 10.1 Log Locations

Logs are not stored in one universal place on every Linux system. A modern
host usually has several log surfaces at once:

- the systemd journal, queried with `journalctl`
- text files under `/var/log`
- application-specific directories under `/var/log`
- package manager logs
- kernel and boot logs
- container, cloud, or service-manager logs

The operator skill is knowing where to look first, how to confirm that the log
source exists on this host, and how to preserve the evidence without making the
incident worse.

!!! abstract "What you will learn"
    - Identify the common Linux log locations and the systems that create them.
    - Distinguish journal-backed logs from text-file logs under `/var/log`.
    - Find service, authentication, kernel, package, and application logs.
    - Build a short incident evidence trail without editing or rotating logs.

!!! example "Field story"
    A web application is returning intermittent 502 errors. The dashboard only
    says "backend unavailable." Before restarting anything, you need to answer:
    did the web server reject requests, did the app crash, did systemd restart
    the service, did the kernel report resource pressure, or did a package
    update change something?

!!! success "Operator principle"
    Start with read-only discovery. Confirm which logging paths exist on the
    host before assuming a distribution, service, or logging stack.

## The first split: journal vs files

On many current Linux distributions, systemd collects service, boot, kernel,
and system messages in the journal. You inspect that with `journalctl`:

```bash
journalctl --no-pager -n 50
journalctl --no-pager -u ssh
journalctl --no-pager -b
```

The journal may be persistent across reboots or it may be stored only in memory,
depending on the system configuration. Common locations are:

- `/run/log/journal` for runtime journal data
- `/var/log/journal` for persistent journal data

Do not parse these files directly. Use `journalctl`, because the journal is a
structured binary log store.

Text logs usually live under `/var/log`:

```bash
ls -lah /var/log
find /var/log -maxdepth 2 -type f -printf '%p\n' | sort | head -50
```

Some distributions send most system messages to text files through rsyslog,
syslog-ng, or a similar service. Others rely primarily on journald. Many use a
hybrid approach.

## Common files under `/var/log`

The exact filenames vary by distribution, but these are common places to check:

| Area | Common location | What it helps answer |
| --- | --- | --- |
| General system messages | `/var/log/syslog` or `/var/log/messages` | What was happening across the host? |
| Authentication | `/var/log/auth.log` or `/var/log/secure` | Who logged in, used sudo, or failed auth? |
| Kernel messages | `/var/log/kern.log`, `/var/log/dmesg`, journal kernel stream | Did the kernel report hardware, driver, memory, or filesystem issues? |
| Package changes | `/var/log/apt/`, `/var/log/dpkg.log`, `/var/log/yum.log`, `/var/log/dnf.log` | Did software change before the incident? |
| Boot messages | `journalctl -b`, `/var/log/boot.log` when present | What happened during the current boot? |
| Cron activity | `/var/log/cron`, `/var/log/syslog`, or journal | Did a scheduled job run or fail? |

For a quick read-only inventory:

```bash
ls -lah /var/log
ls -lah /var/log/apt 2>/dev/null || true
ls -lah /var/log/journal 2>/dev/null || true
```

The `2>/dev/null || true` pattern is useful in lab notes when a path may not
exist on every distribution. It keeps the command read-only while avoiding a
false sense that one missing path means logging is broken.

## Authentication and privilege logs

Authentication logs are high-value during incidents. They can show SSH logins,
failed password attempts, sudo use, account changes, and sometimes PAM-related
messages.

Debian and Ubuntu commonly use:

```bash
sudo tail -n 50 /var/log/auth.log
```

RHEL-family systems commonly use:

```bash
sudo tail -n 50 /var/log/secure
```

On a systemd host, the journal is often the portable first stop:

```bash
journalctl --no-pager -u ssh -n 50
journalctl --no-pager _COMM=sudo -n 50
```

Use care with auth logs. They can contain usernames, IP addresses, command
lines, and operational details. Share only what the handoff needs.

## Service-specific logs

Many services write their own logs under subdirectories of `/var/log`.
Examples include:

- `/var/log/nginx/`
- `/var/log/apache2/` or `/var/log/httpd/`
- `/var/log/mysql/` or `/var/log/mariadb/`
- `/var/log/postgresql/`
- `/var/log/redis/`

Start by identifying the service manager name and then check both the journal
and the service directory:

```bash
systemctl status nginx --no-pager
journalctl --no-pager -u nginx -n 100
ls -lah /var/log/nginx 2>/dev/null || true
```

For web servers, access logs and error logs answer different questions:

- access logs show request timing, methods, paths, status codes, and clients
- error logs show application, upstream, permission, TLS, or runtime failures

Example:

```bash
sudo tail -n 50 /var/log/nginx/access.log
sudo tail -n 50 /var/log/nginx/error.log
```

Do not run `cat` on a large live log during an incident. Prefer `tail`, `less`,
`grep`, `journalctl --since`, and narrow time windows.

## Package manager logs

Package logs help answer a common incident question: "What changed recently?"

Debian and Ubuntu:

```bash
ls -lah /var/log/apt
sudo tail -n 80 /var/log/apt/history.log
sudo tail -n 80 /var/log/dpkg.log
```

RHEL-family systems:

```bash
sudo tail -n 80 /var/log/dnf.log 2>/dev/null || true
sudo tail -n 80 /var/log/yum.log 2>/dev/null || true
```

Look for installs, removals, upgrades, kernel changes, service package changes,
and timestamps close to the incident.

## Kernel and boot logs

Kernel logs can explain symptoms that application logs cannot: out-of-memory
kills, disk errors, network driver resets, filesystem remounts, device failures,
or blocked I/O.

Useful read-only checks:

```bash
journalctl --no-pager -k -n 100
dmesg -T | tail -n 100
journalctl --no-pager -b -p warning..alert
```

Some systems restrict `dmesg` to privileged users. If it fails, use `sudo` only
when you have permission, or use the journal if it is available.

## Rotated and compressed logs

`/var/log` usually contains current logs plus rotated older logs. Examples:

- `auth.log`
- `auth.log.1`
- `auth.log.2.gz`

Use `zgrep` or `zless` for compressed logs:

```bash
zgrep -i 'failed password' /var/log/auth.log*.gz 2>/dev/null | tail -20
```

Rotation means the current file may not contain the whole incident. If an event
happened yesterday or before a restart, check rotated files and the journal.

## Containers and cloud hosts

Containers and cloud images add another layer. Logs may live in the container
runtime, cloud agent, orchestration platform, or external logging service.

Examples:

```bash
docker logs --tail 100 <container>
journalctl --no-pager -u docker -n 100
journalctl --no-pager -u containerd -n 100
```

On cloud systems, also check provider-specific agents such as monitoring,
guest, SSM, cloud-init, or logging agents. `cloud-init` commonly writes under:

```bash
ls -lah /var/log/cloud-init*
```

## Build an incident log map

For a real handoff, do not dump every log. Build a small map:

```text
Host:
Incident window:
Primary service:
Journal available:
Persistent journal:
Relevant /var/log files:
Service-specific logs:
Package changes near incident:
Kernel warnings/errors:
Evidence copied to:
```

Then collect narrow evidence:

```bash
mkdir -p ~/incident-notes
journalctl --no-pager --since "1 hour ago" > ~/incident-notes/journal-last-hour.txt
journalctl --no-pager -k --since "1 hour ago" > ~/incident-notes/kernel-last-hour.txt
```

Adjust the time window to the incident. Keep copied evidence in a controlled
location and avoid changing the original logs.

## Hands-on practice

Run these on a disposable VM, container, or lab machine.

1. List the top-level contents of `/var/log`.
2. Determine whether this host has `/var/log/journal`, `/run/log/journal`, or
   both.
3. Use `journalctl -b` to inspect the current boot.
4. Find one authentication log source and one package manager log source.
5. Write a five-line incident log map for the host.

Example lab commands:

```bash
ls -lah /var/log
ls -ld /var/log/journal /run/log/journal 2>/dev/null || true
journalctl --no-pager -b -n 50
ls -lah /var/log/apt 2>/dev/null || true
```
