### 10.6 Management of Logs at Scale 📊📈

!!! abstract "What you will learn"
    - Explain why log management changes when one machine becomes many machines.
    - Identify the core parts of a scalable logging pipeline.
    - Separate collection, transport, storage, retention, search, and alerting concerns.
    - Design a small, honest logging plan for a fleet without overbuilding.

!!! example "Incident story"
    A customer-facing API fails in only one region. The application team has logs on app servers, the load balancer has access logs elsewhere, containers rotate their own stdout, and the database has slow-query logs on a separate host. At scale, the hard part is no longer finding *a* log. It is getting all relevant events into one reliable timeline.

!!! success "Operator principle"
    Centralize enough to investigate quickly, but keep ownership, retention, privacy, and cost visible.

## What "at scale" changes

On one server, you can SSH in and inspect `/var/log`. On a fleet, that approach breaks down.

Scale introduces new questions:

- Where do logs go when hosts are replaced automatically?
- How do you search across many services and regions?
- Which logs are required for security, compliance, or billing investigations?
- How long should high-volume debug logs be retained?
- Who can read sensitive logs?
- What happens when the logging system itself is slow or unavailable?
- How do you control ingestion and storage cost?

A scalable logging system is an operations pipeline, not just a bigger disk.

## The logging pipeline

Most fleet logging designs have the same building blocks:

| Stage | Purpose | Common examples |
| --- | --- | --- |
| Source | Where events are produced | Linux journals, syslog files, app logs, container stdout, load balancers |
| Agent | Collects and forwards events | Fluent Bit, Vector, Filebeat, OpenTelemetry Collector, cloud agents |
| Transport | Moves logs reliably | TLS, buffering, queues, local disk spooling |
| Parser/enricher | Adds structure and metadata | JSON parsing, hostname, service, region, environment, trace ID |
| Store/index | Makes logs searchable | Elasticsearch/OpenSearch, Loki, cloud logging, object storage |
| Retention | Controls lifetime and cost | Hot/warm/cold tiers, archive buckets, deletion policies |
| Query/alert | Turns logs into evidence | dashboards, saved searches, alert rules, incident notebooks |

The agent is often the most important operational boundary. If agents are misconfigured, too noisy, or unable to buffer during network problems, the central system will not save you.

## Start with an inventory

Before picking tooling, map what exists.

```text
Service: web-api
Hosts: app servers in us-east and us-west
Sources:
  - systemd journal for service crashes
  - application JSON logs on stdout
  - nginx access/error logs
  - kernel logs for OOM and network symptoms
Required fields:
  - timestamp, service, environment, region, host, request_id, level
Retention:
  - 14 days searchable
  - 90 days archived for incident review
Access:
  - engineering can read app logs
  - security can read auth and audit logs
  - secrets must not appear in any log
```

This inventory prevents vague "send everything everywhere" designs.

## Add structure early

Unstructured logs are useful to humans. Structured logs are useful to humans and machines.

Good application logs often include fields like:

```json
{
  "timestamp": "2026-05-11T08:58:00Z",
  "level": "error",
  "service": "checkout-api",
  "environment": "production",
  "region": "us-east-1",
  "request_id": "req-4f8c1",
  "user_id": "redacted",
  "message": "payment authorization failed",
  "error_code": "PAYMENT_TIMEOUT"
}
```

Useful metadata should be consistent across services:

- `service`
- `environment`
- `region`
- `host` or `node`
- `container` or `pod`
- `level`
- `request_id` or `trace_id`
- `version` or deployment SHA

!!! warning "Do not log secrets"
    Scaled logging multiplies mistakes. API keys, session cookies, passwords, tokens, private keys, and full payment details should never be written to logs. Use redaction at the application and collector layers.

## Plan for backpressure

Logging systems fail too. Network links drop, central stores throttle ingestion, and noisy deployments can create sudden spikes.

A serious logging agent should have an answer for:

- Local buffering when the destination is unavailable.
- Maximum disk use for the buffer.
- What gets dropped first when buffers fill.
- Whether delivery is best-effort or required.
- How operators see agent health.

For many production systems, losing some debug logs is acceptable. Losing audit logs may not be. Treat different log classes differently.

## Keep retention intentional

Retention is a balance between investigation value, compliance needs, privacy, and cost.

Example retention model:

| Log class | Searchable retention | Archive retention | Notes |
| --- | --- | --- | --- |
| Application info/debug | 7-14 days | none or short archive | High volume, lower long-term value. |
| Application errors | 30-90 days | 90-180 days | Useful for recurring incidents. |
| Access logs | 30 days | 90-365 days | Often useful for abuse and traffic analysis. |
| Authentication logs | 90 days | 1 year or policy-defined | Security-sensitive; restrict access. |
| Audit logs | Policy-defined | Policy-defined | May have compliance requirements. |

Avoid retaining everything forever by default. It is expensive, hard to search, and can increase privacy risk.

## Choose tools by operating model

Different teams choose different central logging stacks:

- **Loki + Grafana**: often strong when logs are label-oriented and teams already use Grafana.
- **Elasticsearch/OpenSearch + Kibana/OpenSearch Dashboards**: strong search and indexing, but requires careful scaling and cost control.
- **Cloud provider logging**: convenient for managed infrastructure, often easier to start with but can become expensive at high volume.
- **Object storage archives**: useful for cheap long-term retention, but not a fast interactive search tool by itself.
- **OpenTelemetry Collector, Fluent Bit, Vector, Filebeat**: common collector and forwarder options.

Tool choice matters less than whether the pipeline has clear ownership, retention, access controls, and testable failure behavior.

## Minimal fleet design

For a small production fleet, a practical starting point is:

1. Applications emit structured JSON logs to stdout or a known file.
2. Every host runs one collector agent.
3. The collector adds host, region, environment, and service metadata.
4. The collector forwards over TLS to a central store.
5. The central store has separate retention for noisy app logs and security/audit logs.
6. Dashboards and saved searches answer the common incident questions.
7. Agent health is monitored.

You can grow from there. Do not start with a complex multi-tier architecture unless the operational need is real.

## Incident workflow at scale

During an incident, ask questions in this order:

1. What service, region, and time window are involved?
2. What changed recently?
3. Are errors isolated to one version, host group, tenant, or dependency?
4. Do application logs match load balancer, database, and system logs?
5. Are logs missing because the system was quiet, or because collection failed?
6. What evidence should be preserved before retention or rotation removes it?

Good scaled logging lets you answer those questions without logging into every host.

## Hands-on practice

Use a lab VM, container stack, or cloud sandbox.

1. Pick one service or daemon and list every log source it produces.
2. Define required metadata fields for those logs.
3. Decide which fields should never appear because they are sensitive.
4. Sketch a retention policy for debug, error, access, and audit logs.
5. Identify what should happen if the central log store is unreachable for 10 minutes.
6. Write three incident queries you would want available before a real outage.

Example incident queries:

```text
service="checkout-api" level="error" region="us-east-1" last 30 minutes
service="nginx" status>=500 request_id="req-4f8c1"
host="app-17" ("oom" OR "killed process" OR "no space left")
```
