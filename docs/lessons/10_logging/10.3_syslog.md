## 10.3 Syslog: The Classic Logging Workflow

Syslog is the older text-oriented logging family that still matters on modern
Linux systems. Even when systemd-journald is present, you will often find a
syslog daemon such as `rsyslog` or `syslog-ng` writing selected messages into
plain files under `/var/log`.

For operators, syslog is useful because it is simple, portable, and common
across servers, network devices, appliances, and centralized log collectors.
The tradeoff is that syslog data is usually less structured than journal data.

!!! abstract "What you will learn"
    - Explain what syslog, rsyslog, facilities, and severities are.
    - Find common syslog text files on Debian, Ubuntu, RHEL, and similar hosts.
    - Use `logger` to generate a controlled test message.
    - Inspect syslog routing and rotation without changing production behavior.
    - Decide when to check syslog files, the journal, or both.

!!! example "Field story"
    A host reports intermittent SSH failures. `journalctl -u ssh` shows service
    activity, but the security team asks for plain-text authentication evidence
    from the central log collector. You need to know whether the host writes
    auth events to `/var/log/auth.log`, `/var/log/secure`, the journal only, or
    a remote syslog target.

!!! success "Operator principle"
    Treat syslog as a routing system: messages have a source, a severity, a
    destination, and a retention policy.

## Syslog, rsyslog, and syslog-ng

The word "syslog" can mean a few related things:

- a message format and logging convention
- a network protocol for forwarding logs
- a local logging workflow that writes text files
- a shorthand for the daemon that receives and routes messages

On current Linux hosts, the daemon is often one of:

- `rsyslog`
- `syslog-ng`
- no traditional syslog daemon, with journald handling most local logs

Check what is running:

```bash
systemctl status rsyslog --no-pager
systemctl status syslog-ng --no-pager
systemctl status systemd-journald --no-pager
```

If `rsyslog` is absent, that does not automatically mean logging is broken. The
host may be using journald only or forwarding logs through another agent.

## Common syslog file locations

Distribution families use different default filenames.

| System family | Common files | Notes |
| --- | --- | --- |
| Debian / Ubuntu | `/var/log/syslog`, `/var/log/auth.log`, `/var/log/kern.log` | Common on rsyslog-backed installs |
| RHEL / CentOS / Fedora | `/var/log/messages`, `/var/log/secure`, `/var/log/maillog` | Names vary by release and logging stack |
| Any systemd host | `journalctl` | May be primary even when text files exist |

Start with discovery:

```bash
ls -lah /var/log/syslog /var/log/messages 2>/dev/null || true
ls -lah /var/log/auth.log /var/log/secure 2>/dev/null || true
```

Then inspect a narrow window:

```bash
sudo tail -n 80 /var/log/syslog 2>/dev/null || true
sudo tail -n 80 /var/log/messages 2>/dev/null || true
```

Prefer `tail`, `less`, and targeted `grep` over dumping a whole log with `cat`.
Production logs can be large, sensitive, and actively changing.

## Facilities and severities

Syslog routes messages by facility and severity.

Facilities describe the source or category, such as:

- `auth` or `authpriv` for authentication and security
- `kern` for kernel messages
- `daemon` for background services
- `mail` for mail systems
- `cron` for scheduled jobs
- `local0` through `local7` for application-defined use

Severities describe importance, from most severe to least severe:

| Severity | Meaning |
| --- | --- |
| `emerg` | System is unusable |
| `alert` | Immediate action required |
| `crit` | Critical condition |
| `err` | Error condition |
| `warning` | Warning condition |
| `notice` | Normal but significant condition |
| `info` | Informational message |
| `debug` | Debug-level detail |

A selector like this means "auth messages at info level and above":

```text
auth.info
```

In rsyslog configuration, selectors map messages to destinations:

```text
auth,authpriv.*    /var/log/auth.log
*.info;mail.none;authpriv.none;cron.none    /var/log/messages
```

Do not edit these files during an incident unless you have a change plan and a
rollback path. Read them first.

## Inspect syslog routing

Rsyslog configuration commonly lives in:

- `/etc/rsyslog.conf`
- `/etc/rsyslog.d/*.conf`

Syslog-ng configuration commonly lives in:

- `/etc/syslog-ng/syslog-ng.conf`
- `/etc/syslog-ng/conf.d/*.conf`

Read-only inspection:

```bash
sudo grep -R --line-number --exclude='*.dpkg-*' '/var/log\\|@@\\|@' /etc/rsyslog.conf /etc/rsyslog.d 2>/dev/null || true
sudo grep -R --line-number 'destination\\|log {' /etc/syslog-ng 2>/dev/null || true
```

The `@` and `@@` patterns in rsyslog often indicate remote forwarding:

- `@host:514` usually means UDP syslog forwarding
- `@@host:514` usually means TCP syslog forwarding

Remote forwarding is operationally important. A local file may be quiet because
messages are routed elsewhere.

## Generate a safe test message with `logger`

The `logger` command sends a message through the system logging path. This is a
safe way to confirm routing in a lab or during a planned verification.

```bash
logger -p user.info -t learn-linux "syslog test from lesson 10.3"
```

Then search likely destinations:

```bash
journalctl --no-pager -t learn-linux -n 20
grep -R "syslog test from lesson 10.3" /var/log 2>/dev/null | tail -20
```

Use a clear tag with `-t` so the message is easy to find and easy to explain in
your lab notes.

Avoid creating high-severity test messages on shared systems. Do not generate
`emerg`, `alert`, or `crit` messages unless the operations team expects them.

## Syslog and journald together

On systemd systems, journald and syslog may be connected. Common patterns:

- applications write to stdout/stderr under systemd, and journald stores it
- journald forwards selected messages to syslog
- rsyslog reads from the journal and writes text files
- both journal and text files exist, with overlapping but not identical data

Compare both when the source of truth matters:

```bash
journalctl --no-pager --since "30 minutes ago" -p warning..alert
sudo grep -Ei "error|fail|warn|critical" /var/log/syslog /var/log/messages 2>/dev/null | tail -50
```

If they disagree, preserve the evidence and inspect the routing configuration.
Do not assume one path is complete.

## Rotation and retention

Syslog text files are normally rotated by `logrotate`. Common configuration
locations:

- `/etc/logrotate.conf`
- `/etc/logrotate.d/rsyslog`
- `/etc/logrotate.d/syslog`

Read-only inspection:

```bash
ls -lah /var/log/syslog* /var/log/messages* 2>/dev/null || true
sudo sed -n '1,160p' /etc/logrotate.d/rsyslog 2>/dev/null || true
sudo sed -n '1,160p' /etc/logrotate.d/syslog 2>/dev/null || true
```

Rotation affects investigations. The current file may not contain yesterday's
incident, and older files may be compressed:

```bash
zgrep -Ei "error|fail|warn|critical" /var/log/syslog*.gz 2>/dev/null | tail -50
```

Retention is a policy question as much as a technical one. If logs disappear
too quickly for incident response, record that gap instead of silently accepting
it.

## What to collect during an incident

For a syslog-related handoff, capture:

```text
Host:
Incident window:
Syslog daemon:
Journal available:
Local syslog files found:
Remote forwarding found:
Relevant facility/severity:
Rotation/retention notes:
Evidence commands run:
```

Useful commands:

```bash
systemctl status rsyslog --no-pager
journalctl --no-pager --since "1 hour ago" -p warning..alert
sudo tail -n 120 /var/log/syslog 2>/dev/null || true
sudo tail -n 120 /var/log/messages 2>/dev/null || true
sudo grep -R --line-number '@@\\|@' /etc/rsyslog.conf /etc/rsyslog.d 2>/dev/null || true
```

Keep the investigation read-only unless you are explicitly changing logging
configuration as part of a planned remediation.

## Hands-on practice

Run these on a disposable VM, container, or lab machine.

1. Determine whether `rsyslog`, `syslog-ng`, or only journald is active.
2. Find the host's general system log file, if one exists.
3. Find the host's authentication log file, if one exists.
4. Send a tagged `logger` test message at `user.info`.
5. Find the test message in the journal, a text log, or both.
6. Check whether syslog logs are rotated and how many old files are retained.

Example lab sequence:

```bash
systemctl status rsyslog --no-pager || true
logger -p user.info -t learn-linux "lesson 10.3 syslog route test"
journalctl --no-pager -t learn-linux -n 20
grep -R "lesson 10.3 syslog route test" /var/log 2>/dev/null | tail -20
ls -lah /var/log/syslog* /var/log/messages* 2>/dev/null || true
```
