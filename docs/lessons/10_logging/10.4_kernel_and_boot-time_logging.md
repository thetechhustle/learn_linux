### 10.4 Kernel and Boot-Time Logging

Kernel and boot-time logs explain problems that ordinary application logs often
cannot see. They show hardware detection, drivers, filesystems, memory pressure,
network interfaces, kernel warnings, service startup timing, and failures that
happen before a user logs in.

When a host reboots unexpectedly, hangs during startup, loses a disk, drops a
network interface, or kills a process because memory is exhausted, kernel and
boot evidence should be part of the first investigation.

!!! abstract "What you will learn"
    - Use `journalctl`, `dmesg`, and `systemd-analyze` to inspect kernel and boot evidence.
    - Find kernel warnings, boot failures, previous-boot logs, and startup delays.
    - Understand when `/var/log/kern.log`, `/var/log/dmesg`, and `/var/log/boot.log` may or may not exist.
    - Capture a read-only boot incident handoff without changing the system.

!!! example "Field story"
    A server rebooted overnight and one application did not come back cleanly.
    The app logs only show that it started late. Kernel and boot logs can show
    whether the host had a hardware reset, filesystem problem, out-of-memory
    event, slow network mount, or service dependency delay before the app
    started.

!!! success "Operator principle"
    Kernel and boot logs are timeline evidence. Preserve the relevant time
    window before restarting services or changing boot configuration.

## Kernel logs: what they contain

Kernel logs include messages from the Linux kernel and kernel drivers. They can
show:

- detected CPU, memory, disk, and network hardware
- driver load failures
- disk I/O errors
- filesystem warnings and remounts
- out-of-memory kills
- network link up/down events
- kernel module messages
- security framework messages, such as SELinux or AppArmor events

On systemd hosts, start with the journal:

```bash
journalctl --no-pager -k -n 100
journalctl --no-pager -k --since "1 hour ago"
journalctl --no-pager -k -p warning..alert
```

The `-k` flag filters to kernel messages. The `-p warning..alert` priority
range shows higher-severity messages without drowning you in normal boot noise.

## `dmesg`: the kernel ring buffer

`dmesg` reads the kernel ring buffer. It is useful for recent kernel messages,
especially hardware, driver, and boot activity.

```bash
dmesg --human --color=never | tail -n 100
dmesg --ctime --color=never | tail -n 100
dmesg --level=err,warn --color=never
```

Older systems may not support every option. A portable fallback is:

```bash
dmesg | tail -n 100
```

Some distributions restrict `dmesg` access to privileged users. If `dmesg`
returns "Operation not permitted," use `journalctl -k` when available, or use
`sudo dmesg` only when you have permission.

## Text kernel logs under `/var/log`

Depending on the distribution and syslog setup, kernel messages may also be
written to text files:

- `/var/log/kern.log`
- `/var/log/messages`
- `/var/log/syslog`
- `/var/log/dmesg`

Discover before assuming:

```bash
ls -lah /var/log/kern.log /var/log/dmesg /var/log/messages /var/log/syslog 2>/dev/null || true
```

Then inspect narrowly:

```bash
sudo tail -n 100 /var/log/kern.log 2>/dev/null || true
sudo grep -Ei "kernel|oom|i/o error|fail|warn|critical" /var/log/messages /var/log/syslog 2>/dev/null | tail -50
```

On journald-focused systems, these files may be absent or incomplete. That is a
logging design difference, not automatically a fault.

## Current boot vs previous boot

When a problem happened before the current login, you need to know which boot
you are reading.

List available boots:

```bash
journalctl --list-boots
```

Inspect the current boot:

```bash
journalctl --no-pager -b -n 100
journalctl --no-pager -b -p warning..alert
```

Inspect the previous boot:

```bash
journalctl --no-pager -b -1 -p warning..alert
journalctl --no-pager -b -1 -k
```

If previous-boot logs are unavailable, journald may not be persistent. Check:

```bash
ls -ld /var/log/journal /run/log/journal 2>/dev/null || true
```

Persistent journal storage usually lives under `/var/log/journal`. Runtime-only
journal storage usually lives under `/run/log/journal` and may disappear after a
reboot.

## Boot-time service evidence

Not every boot issue is a kernel issue. Some failures happen after the kernel
hands control to the init system.

On systemd systems, inspect boot timing:

```bash
systemd-analyze
systemd-analyze blame | head -30
systemd-analyze critical-chain
```

Then inspect failed units:

```bash
systemctl --failed --no-pager
journalctl --no-pager -b -p warning..alert
```

Use `systemd-analyze blame` carefully. A service listed near the top is slow,
but not always the root cause. It may be waiting on a disk, network, DNS, mount,
or another dependency. `critical-chain` helps show dependency ordering.

## Boot files and early startup logs

Some systems also write boot logs to files such as:

- `/var/log/boot.log`
- `/run/initramfs/`
- `/var/log/cloud-init.log`
- `/var/log/cloud-init-output.log`

Examples:

```bash
ls -lah /var/log/boot.log /var/log/cloud-init.log /var/log/cloud-init-output.log 2>/dev/null || true
sudo tail -n 100 /var/log/boot.log 2>/dev/null || true
sudo tail -n 100 /var/log/cloud-init.log 2>/dev/null || true
```

Cloud images often rely on `cloud-init` for first-boot setup. If a cloud server
comes up with missing users, SSH keys, packages, hostnames, or network settings,
check cloud-init logs early.

## Common kernel and boot symptoms

Useful search terms during incidents:

```bash
journalctl --no-pager -k --since "24 hours ago" | grep -Ei "oom|out of memory|killed process"
journalctl --no-pager -k --since "24 hours ago" | grep -Ei "i/o error|ext4|xfs|btrfs|nvme|sda|read-only"
journalctl --no-pager -k --since "24 hours ago" | grep -Ei "link is down|link becomes ready|renamed|firmware"
```

What they may indicate:

| Symptom | Possible meaning |
| --- | --- |
| `Out of memory`, `Killed process` | The kernel OOM killer terminated a process |
| `I/O error`, disk device names | Disk, storage, or filesystem trouble |
| `read-only filesystem` | Filesystem remounted to protect data |
| `firmware: failed to load` | Missing firmware or driver support |
| network link messages | NIC, cable, virtual interface, or driver changes |
| `segfault` | Process crashed at the kernel boundary |

These are starting points, not final diagnoses. Correlate them with timestamps,
service logs, package changes, and user reports.

## Preserve evidence safely

Before rebooting again or changing services, collect a narrow evidence bundle:

```bash
mkdir -p ~/boot-incident
journalctl --no-pager --list-boots > ~/boot-incident/boots.txt
journalctl --no-pager -b -p warning..alert > ~/boot-incident/current-boot-warnings.txt
journalctl --no-pager -b -k > ~/boot-incident/current-boot-kernel.txt
systemctl --failed --no-pager > ~/boot-incident/failed-units.txt
systemd-analyze critical-chain > ~/boot-incident/critical-chain.txt
```

If the issue happened before the latest reboot and previous boot logs exist:

```bash
journalctl --no-pager -b -1 -p warning..alert > ~/boot-incident/previous-boot-warnings.txt
journalctl --no-pager -b -1 -k > ~/boot-incident/previous-boot-kernel.txt
```

Do not paste huge logs into chat or tickets. Summarize the relevant timestamps
and attach the evidence when appropriate.

## What not to do first

Avoid these as first moves unless the situation demands it:

- rebooting before capturing current evidence
- editing bootloader or kernel parameters without a rollback plan
- deleting logs to free space before preserving the incident window
- assuming the app caused the issue before checking kernel and boot evidence
- treating `systemd-analyze blame` as root cause by itself

If the machine is actively failing and data is at risk, follow your incident
response process. Evidence is important, but preserving the system and data may
come first.

## Hands-on practice

Run these on a disposable VM or lab machine.

1. List available journal boots.
2. Inspect kernel warnings from the current boot.
3. Find whether `/var/log/kern.log`, `/var/log/dmesg`, or `/var/log/boot.log`
   exists.
4. Use `systemd-analyze` to inspect boot duration and the critical chain.
5. Create a small boot incident evidence folder with read-only command output.

Example lab sequence:

```bash
journalctl --list-boots
journalctl --no-pager -b -k -p warning..alert
ls -lah /var/log/kern.log /var/log/dmesg /var/log/boot.log 2>/dev/null || true
systemd-analyze
systemd-analyze critical-chain
```
