### 10.2 The systemd Journal

The systemd journal is the structured log store used by many modern Linux
systems. You read it with `journalctl`. It can contain service messages, boot
messages, kernel messages, sudo and authentication-related messages, and
metadata that plain text logs usually do not preserve.

The practical goal is not to dump every log line. The goal is to narrow a large
stream of events into a useful timeline: what happened, when it happened, which
unit or process reported it, and whether the same event is still happening.

!!! abstract "What you will learn"
    - Use `journalctl` to inspect recent, boot-specific, service-specific, and
      priority-filtered log entries.
    - Read journal metadata without parsing the binary journal files directly.
    - Check whether the journal is persistent across reboots.
    - Understand safe access-control and retention boundaries for journal data.
    - Build a short evidence trail for an incident handoff.

!!! example "Field story"
    A service failed after a package update. The application log only says
    "connection refused." The journal can show the service restart attempt, the
    exact unit failure, the dependency that was unavailable, and warnings from
    the same boot window.

!!! success "Operator principle"
    Ask the journal a narrow question. Always include a time window, a unit, a
    boot, a priority, or another selector when the host is busy.

## Start with safe reads

`journalctl` is read-only unless you pair it with administrative configuration
changes elsewhere. Start with a small recent window:

```bash
journalctl --no-pager -n 50
journalctl --no-pager --since "15 minutes ago"
journalctl --no-pager --since "2026-05-11 02:00" --until "2026-05-11 02:30"
```

`--no-pager` keeps command output predictable for lab notes, terminals, and
incident handoffs. When you are exploring interactively, leaving it off opens
the output in a pager such as `less`.

To follow new messages as they arrive:

```bash
journalctl -f
```

Use follow mode carefully on production systems. It is useful for watching a
restart or reproducing a lab issue, but it can also bury the important event in
noise. Stop it with `Ctrl-C`.

## Inspect one systemd unit

Service investigation usually starts with `systemctl status` and then a journal
query for the same unit:

```bash
systemctl status ssh --no-pager
journalctl --no-pager -u ssh -n 100
journalctl --no-pager -u ssh --since "1 hour ago"
```

Unit names vary by distribution. SSH might be `ssh.service` on Debian and
Ubuntu, but `sshd.service` on many RHEL-family systems:

```bash
systemctl list-units 'ssh*' 'sshd*' --no-pager
journalctl --no-pager -u ssh.service -u sshd.service --since today
```

Multiple `-u` flags let you build one timeline across related units. That is
useful when a web server depends on an application service, a database service,
or a timer.

## Filter by boot

The journal can separate messages by boot. This matters when a reboot happened
during the incident.

List known boots:

```bash
journalctl --list-boots
```

Read messages from the current boot:

```bash
journalctl --no-pager -b
```

Read messages from the previous boot:

```bash
journalctl --no-pager -b -1
```

For boot triage, combine boot and priority filters:

```bash
journalctl --no-pager -b -p warning..alert
journalctl --no-pager -b -1 -p err..alert
```

This helps answer whether a failure started before or after the last reboot.

## Filter by priority

Journal entries have syslog-style priorities. Common levels include `debug`,
`info`, `notice`, `warning`, `err`, `crit`, `alert`, and `emerg`.

Useful examples:

```bash
journalctl --no-pager -p err..alert
journalctl --no-pager -u nginx -p warning..alert --since today
journalctl --no-pager -b -p warning..alert
```

Priority filters are a starting point, not a complete diagnosis. A service can
log an important clue at `info`, and a noisy service can generate warnings that
are unrelated to the outage.

## Read kernel messages

The journal can show kernel messages without using `dmesg` directly:

```bash
journalctl --no-pager -k -n 100
journalctl --no-pager -k -b -p warning..alert
```

Kernel messages help explain symptoms such as out-of-memory kills, disk I/O
errors, network driver resets, blocked tasks, device disconnects, and
filesystem remounts.

Look for messages near the same time as the service symptom. A web process that
"randomly died" may have been killed by the kernel because the host ran out of
memory.

## Use metadata instead of text guessing

Journal entries include metadata fields. You can see them with:

```bash
journalctl --no-pager -o verbose -n 3
```

Common fields include:

| Field | What it can identify |
| --- | --- |
| `_SYSTEMD_UNIT` | The systemd unit associated with the message |
| `_PID` | The process ID that emitted the message |
| `_UID` | The numeric user ID for the process |
| `_COMM` | The command name |
| `_EXE` | The executable path |
| `_HOSTNAME` | The host that recorded the entry |
| `PRIORITY` | The severity level |

You can query some fields directly:

```bash
journalctl --no-pager _COMM=sudo --since today
journalctl --no-pager _UID=0 --since "30 minutes ago"
journalctl --no-pager _SYSTEMD_UNIT=cron.service --since today
```

Metadata filters reduce guesswork. They are often safer than broad `grep`
searches over a whole log stream.

## Choose an output format

The default format is good for humans. Other formats help with automation or
handoffs:

```bash
journalctl --no-pager -u ssh -n 20 -o short-iso
journalctl --no-pager -u ssh -n 5 -o verbose
journalctl --no-pager -u ssh -n 5 -o json-pretty
```

Use JSON output when another tool needs structured fields. Use `short-iso` when
you want timestamps that are easy to paste into notes and compare with other
systems.

## Check journal persistence

The journal can be volatile or persistent:

- volatile journal data usually lives under `/run/log/journal`
- persistent journal data usually lives under `/var/log/journal`

Check the current host:

```bash
ls -ld /run/log/journal /var/log/journal 2>/dev/null || true
journalctl --disk-usage
```

If `/var/log/journal` is absent, logs may not survive reboot, depending on
`journald.conf` and distribution defaults. Do not change this during an
incident unless you have an approved change window and a rollback plan.

On a lab machine, you can inspect the configured mode:

```bash
grep -E '^[# ]*Storage=' /etc/systemd/journald.conf
```

Common values are `auto`, `persistent`, `volatile`, and `none`.

## Understand retention and disk use

Journal size is managed by `systemd-journald`. Read the current disk usage:

```bash
journalctl --disk-usage
```

Configuration is commonly in `/etc/systemd/journald.conf` and drop-ins under
`/etc/systemd/journald.conf.d/`. Important knobs include:

- `SystemMaxUse`
- `RuntimeMaxUse`
- `MaxRetentionSec`
- `MaxFileSec`

Vacuum commands delete older journal data. They are destructive to evidence:

```bash
sudo journalctl --vacuum-time=14d
sudo journalctl --vacuum-size=1G
```

Do not run them during an incident until the needed evidence has been exported
or the owner approves the cleanup.

## Access control and sensitive data

Journal entries can contain usernames, IP addresses, command lines, hostnames,
service names, tokens accidentally printed by applications, and security
events. Treat journal output as operationally sensitive.

On many systems, users in the `systemd-journal` or `adm` group can read more
journal data:

```bash
getent group systemd-journal
getent group adm
```

Use the least access needed. If you paste journal excerpts into a ticket, remove
secrets and include only the narrow time window, unit, and error context needed
for the handoff.

## Export evidence for a handoff

For a short plain-text handoff:

```bash
journalctl --no-pager -u nginx --since "2026-05-11 02:00" --until "2026-05-11 02:30" -o short-iso
```

For a structured artifact:

```bash
journalctl -u nginx --since "2026-05-11 02:00" --until "2026-05-11 02:30" -o json > nginx-journal.json
```

For a journal-native export that another systemd host can read:

```bash
journalctl -u nginx --since "2026-05-11 02:00" --until "2026-05-11 02:30" -o export > nginx-journal.export
```

Avoid sharing broad exports unless the recipient is authorized to see the full
host context.

## Troubleshooting patterns

| Symptom | Useful check | What to consider |
| --- | --- | --- |
| `journalctl` shows no old logs | `journalctl --list-boots`; `ls -ld /var/log/journal` | The journal may be volatile or recently vacuumed. |
| A service has no entries | `systemctl status <unit>`; `systemctl list-units '*name*'` | The unit name may differ, or the service may log to its own file. |
| Output is too noisy | Add `-u`, `--since`, `--until`, `-b`, or `-p` | Narrow the question before searching text. |
| Permission denied | Try a narrower user-visible query or request approved access | Do not add yourself to privileged groups without approval. |
| Timestamps are confusing | Use `-o short-iso` and record the host timezone | Compare logs only after normalizing time. |

## Hands-on practice

Run this on a disposable systemd-based VM.

1. Record the host and boot context:

   ```bash
   hostnamectl
   journalctl --list-boots
   ```

2. Inspect recent journal activity:

   ```bash
   journalctl --no-pager -n 30 -o short-iso
   ```

3. Pick one service that exists on your lab host:

   ```bash
   systemctl list-units --type=service --state=running --no-pager | head
   ```

4. Query that service with a time window:

   ```bash
   journalctl --no-pager -u ssh.service -u sshd.service --since "1 hour ago" -o short-iso
   ```

5. Query warnings from the current boot:

   ```bash
   journalctl --no-pager -b -p warning..alert
   ```

6. Check whether journal data is persistent:

   ```bash
   ls -ld /run/log/journal /var/log/journal 2>/dev/null || true
   journalctl --disk-usage
   ```

7. Write a lab note with:

   - the command you ran
   - the exact time window
   - the unit or selector used
   - one relevant log line or a note that no relevant entries appeared
   - what you would check next
