### 10.5 Management and Rotation of Log Files 📚🔄📁

!!! abstract "What you will learn"
    - Explain why log rotation protects disk space, incident history, and service reliability.
    - Inspect system-wide and per-application `logrotate` policy safely.
    - Test a rotation rule before trusting it on a production system.
    - Verify that rotated logs are retained, compressed, and recreated with the right ownership.

!!! example "Incident story"
    A web server starts returning errors because `/var` is full. The application is fine, but one noisy debug log has grown for weeks without rotation. The repair is not just deleting the file. A good operator finds the owner, preserves enough history for investigation, adds or fixes rotation policy, and proves the service can continue writing new logs.

!!! success "Operator principle"
    Logs need a life cycle. Keep enough history to investigate, but never let history consume the system it is meant to explain.

## Why rotation matters

Plain text logs grow until something manages them. On many Linux systems, `logrotate` handles that job for logs under `/var/log` and for application logs that ship their own rotation rules.

Rotation usually means:

- Rename the current log, such as `app.log` to `app.log.1`.
- Create a fresh empty log so the application can keep writing.
- Compress older logs to save disk space.
- Delete logs beyond the retention window.
- Optionally run a post-rotation command so daemons reopen log files.

Rotation is operational hygiene. Without it, a quiet problem can become an outage when `/var`, `/`, or a container volume fills up.

## Find the current policy

Start with read-only inspection.

```bash
ls -lh /var/log | head
du -sh /var/log
sudo du -ah /var/log | sort -h | tail -20
```

Then inspect the main `logrotate` entry points:

```bash
cat /etc/logrotate.conf
ls -l /etc/logrotate.d/
```

The main file usually sets defaults. Package-specific rules usually live under `/etc/logrotate.d/`.

Common directives include:

| Directive | Meaning |
| --- | --- |
| `daily`, `weekly`, `monthly` | How often eligible logs rotate. |
| `rotate 7` | Keep seven old rotations. |
| `compress` | Compress older rotated logs. |
| `delaycompress` | Wait one rotation before compressing the newest old log. |
| `missingok` | Do not fail if the log file is absent. |
| `notifempty` | Do not rotate empty files. |
| `create 0640 root adm` | Create the new log with this mode, owner, and group. |
| `sharedscripts` | Run scripts once for a block, not once per matched file. |
| `postrotate` / `endscript` | Run a command after rotation, often to reload a daemon. |

!!! warning "Do not edit global policy casually"
    `/etc/logrotate.conf` affects the whole machine. Prefer application-specific files in `/etc/logrotate.d/` unless you intentionally need a system-wide default.

## Read a rule

Here is a typical application rule:

```text
/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 myapp adm
    sharedscripts
    postrotate
        systemctl reload myapp.service >/dev/null 2>&1 || true
    endscript
}
```

Read it as an operations contract:

- Rotate matching logs daily.
- Keep 14 old copies.
- Compress old copies, but leave the most recent rotated file uncompressed for tools that may still read it.
- Skip absent or empty files.
- Recreate fresh logs with controlled permissions.
- Ask the service to reopen its log files after rotation.

That last point matters. Some long-running processes keep writing to an open file handle even after the file is renamed. If the service does not reopen logs, rotation may appear to work while disk usage continues growing in a deleted or renamed file.

## Test before changing production

Use debug mode first. Debug mode prints what `logrotate` would do without rotating files.

```bash
sudo logrotate --debug /etc/logrotate.conf
```

To test one rule file:

```bash
sudo logrotate --debug /etc/logrotate.d/myapp
```

If you need a more realistic lab test, use a disposable VM or container and a temporary state file. The state file records when each log last rotated. Using a temporary one avoids interfering with the real system schedule.

```bash
sudo logrotate --state /tmp/logrotate-lab.state --debug /etc/logrotate.d/myapp
```

Forcing rotation with `--force` is useful in labs, but treat it carefully on shared systems because it can rename files, compress data, and trigger service reload scripts.

```bash
sudo logrotate --state /tmp/logrotate-lab.state --force /etc/logrotate.d/myapp
```

## Verify rotation health

After a normal rotation window or a lab force test, verify the result.

```bash
ls -lh /var/log/myapp/
sudo logrotate --debug /etc/logrotate.d/myapp
systemctl status myapp.service --no-pager
```

Look for:

- A fresh active log file exists.
- The service is still writing to the fresh file.
- Older files follow the expected naming pattern.
- Compressed files appear after the expected delay.
- Ownership and permissions match the rule.
- Retention matches the `rotate` value.
- Disk usage is stable or decreasing.

You can also check whether a process is writing to a deleted file, which is a common clue after manual cleanup or broken rotation:

```bash
sudo lsof | grep deleted | grep /var/log
```

If a service is still writing to a deleted log file, restarting or reloading that service is usually needed to release the disk space. Choose the least disruptive action that fits the service.

## Hands-on practice

Use a disposable VM, container, or lab machine for write tests.

1. Inspect `/var/log` size and identify the largest log files.
2. Open one rule under `/etc/logrotate.d/` and explain its retention policy.
3. Run `sudo logrotate --debug` against that rule.
4. Create a small lab rule for a temporary file under `/tmp/logrotate-lab/`.
5. Test the lab rule with a temporary state file.
6. Verify the active log file, rotated file, permissions, and compression behavior.

Example lab setup:

```bash
mkdir -p /tmp/logrotate-lab
printf 'first line\n' > /tmp/logrotate-lab/app.log
lab_user="$(id -un)"
lab_group="$(id -gn)"
cat > /tmp/logrotate-lab/myapp-logrotate.conf <<EOF
/tmp/logrotate-lab/app.log {
    size 1
    rotate 3
    compress
    missingok
    notifempty
    create 0640 ${lab_user} ${lab_group}
}
EOF
```

The `create` owner and group must exist on your system. The example uses your current lab account.

```bash
logrotate --state /tmp/logrotate-lab/state --debug /tmp/logrotate-lab/myapp-logrotate.conf
```
