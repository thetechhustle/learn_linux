### 10.5 Management and Rotation of Log Files

Log files are useful only while the system still has room to write them and
operators can find the time range they need. Log rotation keeps active log
files small, compresses or removes older files, and creates new files with the
right owner and permissions.

This lesson focuses on `logrotate`, the common Linux utility that rotates text
logs such as application logs under `/var/log`. It does not replace journal
retention settings for the systemd journal; use `journalctl` and
`journald.conf` controls for that store.

!!! abstract "What you will learn"
    - Explain why unmanaged logs can become an availability problem.
    - Inspect existing `logrotate` configuration without changing it.
    - Write a narrow app-specific rotation rule under `/etc/logrotate.d/`.
    - Test a rotation rule with dry-run and verbose modes before trusting it.
    - Choose retention, compression, ownership, and permission settings that fit
      the operational risk.

!!! example "Field story"
    A small web service stops accepting requests because `/var` is full. The
    largest files are unrotated application logs. The fix is not to delete
    evidence blindly; first identify the growth source, preserve what the
    incident needs, then add a tested rotation rule so the problem does not
    return.

!!! success "Operator principle"
    Rotate logs to preserve useful evidence, not just to make files disappear.

## Inspect the Current Rotation Policy

Start with read-only checks. Most systems keep the global defaults in
`/etc/logrotate.conf` and package or application rules in `/etc/logrotate.d/`.

```bash
ls -l /etc/logrotate.conf /etc/logrotate.d
sed -n '1,220p' /etc/logrotate.conf
find /etc/logrotate.d -maxdepth 1 -type f -print | sort
```

Check which logs are consuming space before changing policy:

```bash
sudo du -h -d 1 /var/log 2>/dev/null | sort -h
sudo find /var/log -type f -printf '%s %p\n' 2>/dev/null | sort -n | tail -20
```

If a single service is responsible, inspect its existing rule first:

```bash
grep -R "nginx\\|apache\\|syslog\\|messages\\|myapp" /etc/logrotate.d /etc/logrotate.conf
```

## Prefer App-Specific Rules

Avoid editing `/etc/logrotate.conf` for one application. Keep local application
policy in a dedicated file such as `/etc/logrotate.d/myapp` so it is easier to
review, disable, or remove.

```conf
/var/log/myapp/*.log {
    daily
    rotate 14
    missingok
    notifempty
    compress
    delaycompress
    create 0640 myapp adm
    sharedscripts
    postrotate
        systemctl reload myapp.service >/dev/null 2>&1 || true
    endscript
}
```

Common directives:

- `daily`, `weekly`, `monthly`: choose how often rotation is considered.
- `rotate 14`: keep 14 old rotated logs before removal.
- `missingok`: do not fail if the log file is absent.
- `notifempty`: skip empty files.
- `compress`: compress rotated logs to save space.
- `delaycompress`: wait one cycle before compressing the newest rotated log,
  which helps programs that still have the old file open briefly.
- `create 0640 myapp adm`: create the replacement log file with explicit mode,
  owner, and group.
- `postrotate`: run a command after rotation, often to reload a daemon so it
  reopens its log file.

!!! warning "Do not break evidence during an incident"
    Do not delete or truncate logs blindly on a production system. If the disk
    is already full, preserve the smallest useful evidence sample, identify the
    fast-growing writer, and make a reversible space-recovery choice with an
    incident note.

## Test Before Enabling

Use debug mode first. It parses configuration and shows what would happen
without rotating files:

```bash
sudo logrotate -d /etc/logrotate.conf
sudo logrotate -d /etc/logrotate.d/myapp
```

Use verbose mode in a disposable lab or maintenance window when you are ready
to perform a real rotation:

```bash
sudo logrotate -v /etc/logrotate.d/myapp
```

Check the result:

```bash
ls -l /var/log/myapp
sudo tail -n 20 /var/lib/logrotate/status
systemctl status myapp.service --no-pager
```

If the service keeps writing to the rotated file, the daemon probably did not
reopen its log. Review the service documentation for the right reload signal or
command.

## Retention Choices

Rotation policy is a tradeoff between disk space, troubleshooting value, and
legal or business requirements. A useful local default for noisy application
logs might be daily rotation with 7 to 30 retained copies. Security, audit, and
billing logs may need longer retention or central forwarding before local
deletion.

Ask these questions before choosing numbers:

- How long do operators normally need local logs for troubleshooting?
- Are logs already shipped to a central store?
- Are there compliance requirements for this log type?
- How much disk is available on the filesystem that holds `/var/log`?
- Could compression slow down a busy system at the wrong time?

## Troubleshooting

- `logrotate -d` reports a parse error: check braces, directive spelling, and
  file paths.
- Rotated files have the wrong owner: fix the `create` directive or the
  application's log directory ownership.
- Logs keep growing after rotation: confirm the service was reloaded or is able
  to reopen its log file.
- Rotation never happens: inspect `/var/lib/logrotate/status`, system timers,
  and cron entries.
- Disk is still filling: look for other large files under `/var/log` and check
  whether the application writes outside the path in the rotation rule.

## Hands-On Practice

Run this on a disposable VM or container with `logrotate` installed.

1. Create a lab log directory and sample log:

    ```bash
    sudo mkdir -p /var/log/logrotate-lab
    printf 'first event\nsecond event\n' | sudo tee /var/log/logrotate-lab/app.log
    sudo chown -R root:adm /var/log/logrotate-lab
    ```

2. Create `/tmp/logrotate-lab.conf`:

    ```conf
    /var/log/logrotate-lab/*.log {
        size 1
        rotate 3
        missingok
        notifempty
        compress
        create 0640 root adm
    }
    ```

3. Debug the rule without changing files:

    ```bash
    sudo logrotate -d /tmp/logrotate-lab.conf
    ```

4. Run one real lab rotation:

    ```bash
    sudo logrotate -v /tmp/logrotate-lab.conf
    ls -l /var/log/logrotate-lab
    ```

5. Clean up the lab:

    ```bash
    sudo rm -r /var/log/logrotate-lab
    rm /tmp/logrotate-lab.conf
    ```
