### 10.7 Logging Policies

!!! abstract "What you will learn"
    - Explain what a logging policy must decide before an incident happens.
    - Identify which events, systems, owners, retention periods, and access rules belong in a practical policy.
    - Verify local log permissions, rotation settings, and forwarding expectations with read-only commands.
    - Draft a small policy that balances troubleshooting, security, privacy, storage, and compliance needs.

!!! example "Field story"
    A production web service failed during a deployment window. The application logs showed a restart, the authentication logs showed who escalated privileges, and the load balancer logs showed when customer errors began. The team solved the incident quickly because the policy already said which logs were collected, how long they were retained, who could read them, and where the incident timeline should be preserved.

!!! success "Operator principle"
    A logging policy is an operations contract: collect enough evidence to answer real questions, protect that evidence, and avoid keeping unnecessary data forever.

## Why logging policies matter

Log collection is not useful just because a system writes a lot of text to `/var/log`.
A useful logging policy defines the evidence the organization expects to have when something breaks, looks suspicious, or must be audited later.

Good policy answers these questions before stress is high:

- Which events must be logged?
- Which systems are in scope?
- Which log source is authoritative for each event?
- How long should each class of log be retained?
- Who may read, export, change, or delete logs?
- Where are logs copied if the original host fails or is compromised?
- Which private or regulated data must be avoided, masked, or tightly restricted?

## Decide what must be logged

Start with events that answer operational and security questions. Most Linux environments need at least these categories:

| Category | Examples | Common evidence |
| --- | --- | --- |
| Authentication | Successful logins, failed logins, `sudo`, SSH key use | `/var/log/auth.log`, `/var/log/secure`, `journalctl _COMM=sshd` |
| Service health | Starts, stops, crashes, reloads, dependency failures | `journalctl -u <service>`, application logs |
| System changes | Package installs, configuration edits, kernel updates | package manager logs, shell history where appropriate, change tickets |
| Network exposure | Firewall changes, listening services, reverse proxy access | firewall logs, proxy logs, `ss -tulpn` snapshots |
| Data access | Application audit events, database login and query audit events | application audit logs, database audit logs |
| Resource pressure | Disk-full events, memory pressure, CPU saturation | kernel logs, monitoring logs, service logs |

Avoid the lazy rule "log everything." Excessive logging can expose secrets, increase storage cost, hide useful signals, and create data-retention obligations. The better rule is: log events that support troubleshooting, security investigation, compliance, and capacity planning.

## Verify local policy evidence

Policy writing should be grounded in the system you actually run. Use read-only commands first:

```bash
# Show the main log directory and permissions.
ls -ld /var/log
ls -l /var/log | head

# Inspect recent system journal entries without changing state.
journalctl -n 30 --no-pager

# Inspect one service's log stream.
journalctl -u ssh --since "1 hour ago" --no-pager

# Debian and Ubuntu package history.
ls -l /var/log/apt/ /var/log/dpkg.log 2>/dev/null

# RHEL, Fedora, and similar package history.
ls -l /var/log/dnf* /var/log/yum.log 2>/dev/null

# See which local log files have rotation rules.
ls -l /etc/logrotate.conf /etc/logrotate.d/
```

Not every distribution uses the same files. If a command returns "No such file or directory," treat that as evidence about the platform instead of a failure of the lesson.

## Define retention by log class

Retention should not be one global number for every log. Keep high-volume debug logs for less time, and keep security or audit records long enough to support incident response and any regulatory requirement.

Example policy table:

| Log class | Typical examples | Local retention | Central retention | Reason |
| --- | --- | --- | --- | --- |
| Debug and trace | temporary app debug logs | 1-7 days | none unless needed | high volume, low long-term value |
| Service operations | application, web server, job runner logs | 7-30 days | 30-90 days | troubleshooting and trend review |
| Authentication | SSH, PAM, `sudo` events | 30-90 days | 90-365 days | intrusion investigation |
| Security audit | audit framework, EDR, privileged actions | as required | as required | compliance and forensic evidence |
| Billing or business events | chargeable usage, account lifecycle events | business-defined | business-defined | customer and financial audit |

Use `logrotate` and `journald` settings to make the local part of the policy real:

```bash
# Read logrotate's global defaults.
sed -n '1,160p' /etc/logrotate.conf

# Read systemd-journald storage limits where available.
systemctl cat systemd-journald 2>/dev/null
grep -E '^(SystemMaxUse|RuntimeMaxUse|MaxRetentionSec|Storage)=' /etc/systemd/journald.conf 2>/dev/null
```

Do not change retention during an active incident unless disk pressure or legal guidance makes it necessary. Preserve evidence first.

## Protect access and integrity

Logs often contain usernames, IP addresses, command arguments, session IDs, file paths, customer identifiers, and sometimes accidental secrets. A logging policy must say who can read logs and who can administer the logging pipeline.

Check access with:

```bash
# Inspect ownership and mode of common logs.
ls -l /var/log/auth.log /var/log/secure /var/log/syslog /var/log/messages 2>/dev/null

# See whether this account has journal access.
journalctl -n 5 --no-pager

# Show group membership for the current operator.
id
```

Policy guidance:

- Grant read access by role, not convenience.
- Separate ordinary log reading from log pipeline administration.
- Forward important logs away from the host, especially for internet-facing systems.
- Prefer append-only or write-once storage for high-value audit records when the platform supports it.
- Document how incident responders export log evidence without weakening permissions for everyone.

## Handle privacy and sensitive data

The policy should explicitly prohibit logging secrets such as passwords, API tokens, private keys, session cookies, and full payment data. It should also define how to handle personal data, because logs can reveal user behavior even when they are not called "customer data."

For application teams, the policy should require:

- Structured log fields for useful context such as request ID, service name, host, and environment.
- Redaction of secrets before logs leave the application.
- Sampling or rate limiting for noisy debug events.
- A clear path for emergency debug logging that includes an expiration time.
- Review of new log fields during code review when they may include user data.

## Write a small policy

A practical policy can start as one page. Include:

1. **Purpose:** what decisions the policy supports.
2. **Scope:** systems, services, environments, and log sources covered.
3. **Required events:** authentication, service health, security, application, and infrastructure events.
4. **Retention:** local and central retention by log class.
5. **Access:** groups or roles that can read, export, administer, and delete logs.
6. **Integrity:** forwarding, backup, tamper resistance, and incident preservation rules.
7. **Privacy:** fields that must never be logged and fields requiring redaction.
8. **Verification:** commands, dashboards, or reports used to prove the policy is working.

## Troubleshooting policy gaps

| Symptom | Likely gap | Safer next step |
| --- | --- | --- |
| An incident timeline has missing hours | retention or forwarding is too weak | check rotation, journal limits, and central collector health |
| Only root can investigate routine service failures | access model is too narrow | create a read-only operator group instead of sharing privileged access |
| Logs fill the filesystem | volume or retention is not controlled | identify the noisiest source before deleting evidence |
| Sensitive tokens appear in logs | application redaction is missing | revoke exposed tokens and fix logging at the source |
| Local logs vanish after compromise | logs were not copied off-host | forward security-relevant logs to central storage |
| Teams disagree about what "audit log" means | policy terms are vague | define log classes and owners explicitly |

## Hands-on practice

Use a disposable VM, container, or lab machine.

1. Identify three log sources on the system:

    ```bash
    ls -l /var/log | head -20
    journalctl -n 20 --no-pager
    ```

2. Pick one service and write down:

    - where its logs are stored,
    - who can read them,
    - whether they rotate,
    - whether they should be retained locally, centrally, or both.

3. Inspect the current rotation or retention settings:

    ```bash
    ls -l /etc/logrotate.d/
    systemctl cat systemd-journald 2>/dev/null
    ```

4. Draft a five-line mini policy for that service:

    ```text
    Service:
    Required events:
    Local retention:
    Central retention:
    Allowed readers:
    ```

5. Review the draft for one privacy risk and one operational risk.
