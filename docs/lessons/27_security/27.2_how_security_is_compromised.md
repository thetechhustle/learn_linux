## How security is compromised

Security failures are rarely one dramatic event. Most compromises are chains of ordinary weaknesses: an exposed service, an unpatched package, a reused password, an overpowered account, a missed alert, and a backup plan that was never tested.

As a Linux operator, your job is to understand those chains early enough to break them. You do not need to think like a movie attacker. You need to know where real systems usually fail, what evidence those failures leave behind, and which controls reduce the blast radius when one layer gives way.

!!! abstract "What you will learn"
    - Describe the common paths attackers use to compromise Linux systems.
    - Separate initial access, privilege escalation, persistence, lateral movement, and impact.
    - Use Linux evidence to investigate whether a compromise path is possible.
    - Prioritize practical defenses that interrupt attack chains.

!!! success "Operator principle"
    A compromise is a sequence. If you can identify the sequence, you can usually break it before it becomes an incident.

## The attack chain

Most incidents can be described with a few stages:

1. **Reconnaissance**: the attacker learns what exists.
2. **Initial access**: the attacker gets a foothold.
3. **Privilege escalation**: the attacker gains more power.
4. **Persistence**: the attacker creates a way back in.
5. **Lateral movement**: the attacker reaches other systems.
6. **Impact**: the attacker steals data, disrupts service, mines crypto, encrypts files, or changes system behavior.

This model matters because each stage has different evidence. Open ports help explain reconnaissance and initial access. `sudo` rights and file permissions help explain privilege escalation. Cron jobs, systemd units, SSH keys, and new users help explain persistence.

## Common initial access paths

### Exposed services

Any network service is a possible front door. SSH, web servers, VPNs, database listeners, admin dashboards, mail services, and file-sharing services all deserve inventory.

Useful first questions:

- What is listening?
- Is it bound to the right interface?
- Is it supposed to be reachable from the internet?
- Is it patched?
- Does it require strong authentication?

Start with read-only inspection:

```bash
ss -tulpen
systemctl --type=service --state=running
```

Use external scanning only where you have permission. A host can look private from inside the machine and exposed from the outside because of firewall, NAT, cloud security group, or load balancer rules.

### Weak or stolen credentials

Attackers often log in rather than break in. Password reuse, leaked credentials, shared admin accounts, unattended SSH keys, and missing multi-factor authentication can turn a normal login path into an incident.

Check the local evidence:

```bash
last -ai
lastb -ai 2>/dev/null
journalctl _COMM=sshd --since "24 hours ago"
```

On distributions where failed login data is restricted, `lastb` may require root. Treat failed-login logs as signals, not proof by themselves. A few failed attempts on an internet-facing host may be background noise; successful logins from unexpected addresses deserve attention.

### Vulnerable software

Unpatched packages, stale container images, abandoned plugins, and exposed development servers are common entry points. A vulnerability only matters operationally when it intersects with a reachable service or a local privilege boundary, but reachable critical vulnerabilities should be handled quickly.

Inventory before patching:

```bash
uname -a
cat /etc/os-release
systemctl --type=service --state=running
```

Then use your distribution's package tools to review pending security updates. The exact commands vary by platform, but the workflow is the same: identify exposure, identify fix, test where possible, apply with a rollback plan, and record what changed.

### Unsafe application behavior

Web applications and scripts can turn user input into command execution, file disclosure, database access, or authentication bypass. Linux operators do not need to be application developers to spot the operational risk.

Look for these clues:

- services running as `root` when they do not need to
- writable application directories
- secrets stored in world-readable files
- logs showing suspicious paths, payloads, or repeated errors
- upload directories that can execute code
- admin endpoints exposed without network restrictions

Useful commands:

```bash
ps -eo user,pid,comm,args --sort=user
find /srv /var/www -xdev -type f -perm -002 2>/dev/null
find /srv /var/www -xdev -type f -name "*.env" -o -name "*secret*" 2>/dev/null
```

Be careful with broad `find` commands on production systems. Scope them to the application directories you actually own.

### Social engineering

Not every compromise starts on the server. Phishing, fake support requests, malicious attachments, and convincing login prompts can produce a valid password, OAuth token, SSH key, or cloud session.

From the Linux side, social engineering often appears as legitimate-looking access from an unusual context:

- a real user logging in from a new network
- a new SSH key added to an account
- a token used from an unexpected host
- a privileged command run by someone who normally does not run it

That is why account review, audit logs, and least privilege matter.

## Privilege escalation

Initial access is bad. Privileged access is worse. After getting a foothold, attackers look for ways to become root or to gain equivalent control.

Common escalation paths include:

- overly broad `sudo` rules
- writable scripts executed by root
- setuid binaries with unsafe behavior
- kernel or service vulnerabilities
- secrets in shell history, config files, or environment files
- group membership that grants indirect power, such as `docker`, `lxd`, or privileged service groups

Inspect carefully:

```bash
id
sudo -l
find / -xdev -perm -4000 -type f 2>/dev/null
find /etc /usr/local /opt -xdev -type f -writable 2>/dev/null
```

Do not "test" escalation paths on production systems by running exploit code. Your goal is to identify and remove risky paths, not prove an attacker can use them.

## Persistence

Persistence is how an attacker survives reboots, password resets, and service restarts. Linux gives many legitimate ways to start processes automatically, and attackers abuse those same mechanisms.

Review the common places:

```bash
systemctl list-unit-files --type=service
systemctl list-timers
crontab -l 2>/dev/null
ls -la /etc/cron.* /var/spool/cron 2>/dev/null
find ~/.ssh -type f -maxdepth 1 -print 2>/dev/null
```

Also review:

- new or modified users
- new SSH authorized keys
- unexpected systemd units
- modified shell startup files
- unfamiliar binaries in `/usr/local/bin`, `/tmp`, `/var/tmp`, or application directories
- container images or scheduled jobs that restart malicious workloads

Persistence findings need context. Some unfamiliar units and timers may be legitimate. Compare against package ownership, change history, deployment notes, and known automation.

## Lateral movement

Once one host is compromised, attackers often look for credentials, keys, mounted shares, service tokens, and network paths to other systems.

Linux operators should pay attention to:

- SSH private keys without passphrases
- shared service accounts
- NFS or SMB mounts carrying sensitive data
- cloud credentials on disk
- `.netrc`, kubeconfig, Docker registry auth, and application tokens
- database credentials reused across environments
- overly permissive firewall rules between servers

Useful checks:

```bash
find /home /root -name "id_*" -type f 2>/dev/null
find /home /root -name ".netrc" -o -name "config" 2>/dev/null
mount
ip route
```

Handle discovered secrets as sensitive data. Do not paste them into tickets, chat, or logs. Record the path, owner, and risk instead.

## Impact

Compromise impact depends on what the attacker can reach. Common outcomes include:

- data theft
- ransomware or destructive deletion
- crypto mining
- spam or phishing relay
- botnet participation
- account takeover
- silent configuration changes
- supply-chain abuse through code, packages, images, or CI credentials

Look for resource and behavior clues:

```bash
uptime
ps aux --sort=-%cpu | head
df -h
journalctl --since "24 hours ago" --priority=warning
```

High CPU, full disks, strange outbound traffic, unexpected jobs, and authentication spikes are not automatically proof of compromise, but they are worth investigating.

## Breaking the chain

Good defenses interrupt multiple stages:

- **Reduce exposure**: close unused ports, bind services to private interfaces, and use firewalls.
- **Patch reachable software**: prioritize internet-facing and privilege-boundary vulnerabilities.
- **Strengthen identity**: use unique credentials, SSH keys with passphrases, MFA where available, and no shared admin accounts.
- **Limit privilege**: narrow `sudo`, avoid running services as `root`, and remove unnecessary group membership.
- **Protect secrets**: keep secrets out of world-readable files, repos, logs, and shell history.
- **Monitor changes**: review logins, service changes, new users, new keys, and scheduled jobs.
- **Prepare recovery**: maintain offline or protected backups and test restore paths.

The goal is not perfection. The goal is to make each stage harder, noisier, and easier to recover from.

## Hands-on practice

Use a disposable VM or lab container. Do not run offensive tools against systems you do not own or administer.

1. List listening services with `ss -tulpen`.
2. Pick one service and answer: should this be reachable locally, privately, or publicly?
3. Review recent login evidence with `last -ai` and SSH logs for the last 24 hours.
4. Review privilege paths with `id`, `sudo -l`, and the setuid `find` command above.
5. Review persistence locations: systemd units, timers, cron entries, and SSH keys.
6. Write a short note with:
    - the most likely initial access path
    - the most concerning privilege path
    - one reversible control you would apply first
    - how you would verify the control worked
