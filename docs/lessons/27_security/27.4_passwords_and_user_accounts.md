### Passwords and User Accounts

!!! abstract "What you will learn"
    - Explain why account inventory, password policy, and privilege boundaries are core security controls.
    - Inspect local users, password hashes, lock state, shell access, groups, and password aging settings.
    - Make low-risk account changes with evidence before and after each change.
    - Separate human accounts, privileged access, and service accounts during routine Linux operations.

!!! example "Field story"
    A small web server has been online for six months. Nobody is sure which accounts are still active, which users can run `sudo`, or whether old contractor accounts were disabled. Before changing firewall rules or installing new tools, you need to prove who can log in and what they can do.

!!! success "Operator principle"
    Account security is evidence work: identify every account, remove stale access, require strong authentication, and grant privilege only where it is needed.

Passwords and user accounts are usually the first security boundary a Linux administrator can inspect directly. They are also easy to misunderstand. A strong password helps, but it does not compensate for stale users, shared accounts, broad `sudo` rights, unlocked service accounts, exposed SSH access, or missing review notes.

Treat account management as an operational loop:

1. Inventory who exists.
2. Verify who can authenticate.
3. Check who has elevated privileges.
4. Remove or lock access that is no longer needed.
5. Record the evidence so the next operator can audit the decision.

## Account files and what they mean

Most local Linux systems keep account metadata in a small set of text files:

| File | Purpose | Safe inspection command |
| --- | --- | --- |
| `/etc/passwd` | Usernames, UIDs, primary groups, home directories, and login shells | `getent passwd` |
| `/etc/shadow` | Password hashes, lock markers, and aging data | `sudo getent shadow` |
| `/etc/group` | Group names and membership | `getent group` |
| `/etc/sudoers` and `/etc/sudoers.d/` | Privileged command policy | `sudo visudo -c` |

Do not edit these files directly with a normal text editor. Use account tools such as `useradd`, `usermod`, `passwd`, `chage`, `groupadd`, `gpasswd`, and `visudo`. These tools reduce the chance of corrupting the account database or locking out administrators.

## Inventory local accounts

Start with read-only inspection. The goal is to find human users, service users, accounts with real shells, and accounts with unusual IDs.

```bash
getent passwd
awk -F: '$3 >= 1000 { print $1, $3, $6, $7 }' /etc/passwd
awk -F: '$7 !~ /(nologin|false)$/ { print $1, $3, $6, $7 }' /etc/passwd
```

On many Linux distributions, regular human users start at UID 1000. That is a convention, not a universal law. System users often have lower UIDs and shells such as `/usr/sbin/nologin` or `/bin/false`.

Check privileged groups next:

```bash
getent group sudo
getent group wheel
getent group adm
getent group docker
```

The exact privileged group depends on the distribution. Debian and Ubuntu commonly use `sudo`; RHEL-family systems often use `wheel`. Groups such as `docker` can effectively grant root-equivalent control because containers can mount host filesystems or reach privileged APIs.

## Understand password state

Password hashes live in `/etc/shadow`, readable only by privileged users. You do not need to print the whole file during routine review. Prefer targeted commands:

```bash
sudo passwd -S alice
sudo chage -l alice
sudo getent shadow alice
```

Common password states:

- `P` or a hash in `/etc/shadow`: the account has a usable password.
- `L`, `LK`, or a hash prefixed with `!`: password login is locked.
- `NP` or an empty password field: no password is set; investigate immediately.
- Expired aging values: the user may be forced to change a password at next login.

Locking a password is not always the same as disabling every kind of access. An account with SSH keys, active sessions, cron jobs, or service tokens may still have operational reach. Verify the access path you are trying to remove.

## Create and change accounts safely

Use a lab VM for practice. On a production host, confirm the request, owner, expiration date, and privilege need before creating an account.

```bash
sudo useradd -m -s /bin/bash alice
sudo passwd alice
id alice
getent passwd alice
sudo chage -l alice
```

To add a user to a group:

```bash
sudo usermod -aG sudo alice
id alice
```

The `-aG` flags matter. `-G sudo` without `-a` replaces the user's supplemental groups and can remove needed access. Always run `id alice` before and after a group change.

To remove login access without deleting files:

```bash
sudo passwd -l alice
sudo usermod -s /usr/sbin/nologin alice
sudo passwd -S alice
getent passwd alice
```

Lock first, observe for breakage, and then decide whether deletion is appropriate. Deleting an account with `userdel -r` removes the home directory and mail spool; use it only when retention requirements and backups are clear.

## Set password aging policy

Password aging is a control, but aggressive rotation can encourage weak behavior if users respond by choosing predictable passwords. Use aging deliberately and document the policy.

Inspect system defaults:

```bash
grep -E '^(PASS_MAX_DAYS|PASS_MIN_DAYS|PASS_WARN_AGE)' /etc/login.defs
```

Set aging for one user:

```bash
sudo chage -M 90 -m 1 -W 14 alice
sudo chage -l alice
```

Force a password change at next login:

```bash
sudo chage -d 0 alice
```

If your environment uses LDAP, Active Directory, FreeIPA, SSSD, or another identity provider, local `chage` settings may not control the real policy. Check the central identity system before assuming the local host is authoritative.

## Manage privileged access

Avoid shared `root` logins. Use named accounts and `sudo` so commands can be attributed to a person or automation identity.

Validate sudo configuration before and after edits:

```bash
sudo visudo -c
sudo -l -U alice
```

Edit sudo policy with:

```bash
sudo visudo
sudo visudo -f /etc/sudoers.d/alice-admin
```

Prefer narrow privilege rules for automation. For example, allowing one deployment command is easier to audit than granting full passwordless root access. If a rule must be broad temporarily, give it an owner and an expiration date in the change record.

## Review SSH account access

SSH access combines account state, shell state, SSH daemon policy, and keys. Inspect all of them when troubleshooting or auditing login access.

```bash
sudo sshd -T | grep -E '^(passwordauthentication|permitrootlogin|pubkeyauthentication|allowusers|allowgroups)'
sudo find /home -maxdepth 3 -path '*/.ssh/authorized_keys' -type f -print
sudo ls -ld /home/alice /home/alice/.ssh
sudo ls -l /home/alice/.ssh/authorized_keys
```

Good default habits:

- Disable direct root SSH login unless there is a documented break-glass need.
- Prefer SSH keys or centralized single sign-on over reusable passwords.
- Keep `authorized_keys` ownership and permissions tight.
- Remove keys when users leave a team or a vendor engagement ends.
- Keep emergency access documented and tested.

## Treat service accounts differently

Service accounts run daemons, jobs, and automation. They should not behave like human accounts.

Check a service account:

```bash
getent passwd nginx
id nginx
sudo passwd -S nginx
systemctl status nginx --no-pager
```

Service-account practices:

- Use `nologin` or `false` shells unless interactive login is required.
- Lock password authentication for accounts that never need password login.
- Give each service only the files, directories, sockets, and groups it needs.
- Avoid reusing a human account for a daemon or cron job.
- Document who owns the service and how its credentials rotate.

## Common failure patterns

- A former employee's account remains unlocked because nobody owns account review.
- A service account has `/bin/bash` and a valid password even though the daemon never needs interactive login.
- A user is removed from `sudo` but still has root-equivalent access through `docker`, `libvirt`, or writable deployment scripts.
- A password is locked, but SSH keys still allow login.
- `usermod -G` is used without `-a`, accidentally removing supplemental groups.
- A sudoers syntax error blocks administrative access because changes were not made with `visudo`.

## Hands-on practice

Run this on a disposable VM or container lab, not on a production host.

1. Create a lab account:

    ```bash
    sudo useradd -m -s /bin/bash labuser
    sudo passwd labuser
    ```

2. Record account evidence:

    ```bash
    id labuser
    getent passwd labuser
    sudo passwd -S labuser
    sudo chage -l labuser
    ```

3. Add and verify limited privilege:

    ```bash
    sudo usermod -aG sudo labuser
    id labuser
    sudo -l -U labuser
    ```

4. Set password aging and verify it:

    ```bash
    sudo chage -M 60 -m 1 -W 14 labuser
    sudo chage -l labuser
    ```

5. Lock password login and change the shell:

    ```bash
    sudo passwd -l labuser
    sudo usermod -s /usr/sbin/nologin labuser
    sudo passwd -S labuser
    getent passwd labuser
    ```

6. Clean up only after confirming this is the lab account:

    ```bash
    sudo userdel -r labuser
    ```
