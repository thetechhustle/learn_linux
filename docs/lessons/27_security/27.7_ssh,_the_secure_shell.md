### SSH, the Secure Shell

SSH is the normal way administrators log in to Linux hosts, copy files, run one-off commands, and tunnel traffic for maintenance. Because it is so useful, it is also one of the first services attackers look for on an internet-facing system. A good SSH setup does not just "work"; it leaves clear evidence about who can connect, which authentication methods are allowed, and how failed access attempts are handled.

!!! abstract "What you will learn"
    - Explain the SSH client/server model and the files that control it.
    - Inspect whether an SSH service is exposed and how it is configured.
    - Generate and install user keys without weakening private-key safety.
    - Apply safer server defaults for root login, password login, and access scope.
    - Troubleshoot failed SSH logins from both the client and server side.

!!! warning "Do not lock yourself out"
    SSH changes are easy to test and easy to get wrong. Keep an existing session open, validate the configuration with `sshd -t`, and test a new login before restarting or reloading the service on a remote host.

## What SSH protects

SSH replaces older remote-login tools such as Telnet and rlogin. Those protocols send sensitive data in ways that are unsafe on untrusted networks. SSH encrypts the connection, checks the server identity with a host key, and authenticates the user before opening a shell, copying a file, or forwarding a port.

Common SSH tasks include:

- interactive login with `ssh user@host`
- remote command execution with `ssh user@host 'uptime'`
- file copy with `scp` or `sftp`
- rsync over SSH with `rsync -e ssh`
- Git access to private repositories
- temporary tunnels for administrative access

Treat SSH as privileged infrastructure. Anyone who can log in over SSH can often read local data, pivot to nearby systems, or attempt privilege escalation.

## Client and server pieces

The SSH client is usually `/usr/bin/ssh`. Its system-wide defaults often live in `/etc/ssh/ssh_config`, and a user's personal settings live in `~/.ssh/config`.

The SSH server is `sshd`. Its main configuration file is usually `/etc/ssh/sshd_config`, with distribution-provided snippets sometimes placed under `/etc/ssh/sshd_config.d/`.

Useful server files include:

- `/etc/ssh/sshd_config`: server policy
- `/etc/ssh/ssh_host_*_key`: server private host keys
- `/etc/ssh/ssh_host_*_key.pub`: server public host keys
- `~/.ssh/authorized_keys`: public keys allowed for a user account
- `~/.ssh/known_hosts`: server host keys remembered by a client

The private files in these paths matter. Private keys should not be copied casually, checked into Git, pasted into tickets, or sent through chat.

## Inspect an SSH service

Start with read-only evidence. These commands show whether the service exists, whether it is listening, and what policy the daemon would apply after all included files are read:

```bash
systemctl status ssh sshd --no-pager
sudo ss -tlnp | grep ':22 '
sudo sshd -T | less
```

Service names vary by distribution. Debian and Ubuntu commonly use `ssh`; many Red Hat-family systems use `sshd`.

Check the firewall and exposure path too:

```bash
sudo ufw status verbose
sudo firewall-cmd --list-all
sudo nft list ruleset
```

You do not need all three firewall commands on every system. Use the one that matches the host.

## Generate user keys

Key authentication uses a private key on the client and a matching public key installed on the server. A modern default is an Ed25519 key with a passphrase:

```bash
ssh-keygen -t ed25519 -a 100 -C "admin@example.com"
```

This creates two files by default:

- `~/.ssh/id_ed25519`: private key; keep it secret
- `~/.ssh/id_ed25519.pub`: public key; safe to install on servers

The `-a 100` option increases the cost of offline passphrase guessing for keys stored in the modern OpenSSH private-key format. It does not make a weak passphrase strong, but it improves the default.

Install the public key with `ssh-copy-id` when available:

```bash
ssh-copy-id user@server.example.com
```

If you must install it manually, create the directory and file with strict permissions:

```bash
ssh user@server.example.com 'mkdir -p ~/.ssh && chmod 700 ~/.ssh'
cat ~/.ssh/id_ed25519.pub | ssh user@server.example.com 'cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
```

## Safer server defaults

Before changing a production server, record the current settings:

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%Y%m%d%H%M%S)
sudo sshd -T | egrep '^(permitrootlogin|passwordauthentication|pubkeyauthentication|allowusers|allowgroups|permittty|x11forwarding|allowtcpforwarding) '
```

Common hardening choices include:

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
X11Forwarding no
```

These are not universal truths. For example, disabling password authentication before keys are installed for every administrator will cause an outage. A safer workflow is:

1. Install and test key login for at least two administrator accounts.
2. Keep one existing SSH session open.
3. Edit the server configuration.
4. Validate syntax.
5. Reload the service.
6. Test a new login from another terminal.
7. Close the old session only after the new login works.

Use `AllowUsers` or `AllowGroups` when the server should accept SSH from only a small set of accounts:

```text
AllowGroups ssh-admins
```

Then put only the intended operators in that group.

## Validate and reload

Always validate the daemon configuration before applying it:

```bash
sudo sshd -t
```

If the command returns no output and exits successfully, reload the service:

```bash
sudo systemctl reload ssh || sudo systemctl reload sshd
```

If reload is not supported on your distribution, use restart only after you have a fallback access path:

```bash
sudo systemctl restart ssh || sudo systemctl restart sshd
```

## Client-side troubleshooting

Verbose client output usually explains where negotiation fails:

```bash
ssh -vvv user@server.example.com
```

Look for:

- DNS or routing failures before the SSH handshake starts
- host-key warnings that indicate a changed or unexpected server identity
- key files skipped because permissions are too open
- authentication methods refused by the server
- account restrictions after authentication succeeds

For a specific key or config stanza, test explicitly:

```bash
ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes user@server.example.com
ssh -G server-alias | less
```

`ssh -G` prints the final client configuration after includes and `Host` matches are resolved.

## Server-side troubleshooting

On the server, logs usually explain the real reason a login failed:

```bash
sudo journalctl -u ssh -u sshd --since "30 minutes ago" --no-pager
sudo tail -n 100 /var/log/auth.log
sudo tail -n 100 /var/log/secure
```

The log path depends on the distribution. Debian-family systems commonly use `/var/log/auth.log`; Red Hat-family systems commonly use `/var/log/secure`.

Common failure patterns include:

- `Permission denied (publickey)`: the key is missing, not offered, or not accepted.
- `Authentication refused: bad ownership or modes`: fix permissions on the home directory, `.ssh`, or `authorized_keys`.
- `REMOTE HOST IDENTIFICATION HAS CHANGED`: investigate whether the server was rebuilt, DNS points elsewhere, or a man-in-the-middle attack is possible.
- `Connection timed out`: check routing, firewall rules, security groups, and whether `sshd` is listening.
- `Too many authentication failures`: the client offered too many keys; use `IdentitiesOnly=yes` or adjust the agent.

## Operational checklist

For an internet-facing host, capture a short SSH evidence bundle:

```bash
hostnamectl
systemctl is-enabled ssh sshd
systemctl is-active ssh sshd
sudo ss -tlnp | grep ':22 '
sudo sshd -T | egrep '^(permitrootlogin|passwordauthentication|pubkeyauthentication|allowusers|allowgroups) '
sudo journalctl -u ssh -u sshd --since "24 hours ago" --no-pager | tail -n 50
```

Then answer these questions:

- Which accounts are allowed to log in?
- Is direct root login disabled?
- Are password logins still needed?
- Are host keys stable and known by administrators?
- Are failed logins visible in logs?
- Is port 22 exposed only where it needs to be?

## Hands-on practice

Use a disposable VM or lab server.

1. Record whether `sshd` is installed, running, and listening.
2. Generate an Ed25519 key pair with a passphrase.
3. Install the public key for a lab user.
4. Confirm key-based login works in a new terminal.
5. Run `sudo sshd -T` and identify the effective values for `PermitRootLogin`, `PasswordAuthentication`, and `PubkeyAuthentication`.
6. Make one reversible hardening change, such as disabling `X11Forwarding`.
7. Validate with `sudo sshd -t`, reload the service, and test login again.
8. Save the commands, outputs, and rollback step in a short lab note.
