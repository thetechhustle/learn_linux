## 27.11 Sources of Security Information

Security operations depend on signal quality. A good administrator does
not treat every headline as an emergency, but they also do not wait until
an attacker proves the advisory was real. The job is to know which sources
matter, compare them against the systems you actually run, and turn useful
information into a short, repeatable response.

!!! abstract "What you will learn"
    - Identify reliable sources for Linux security advisories and vulnerability data.
    - Separate urgent operational signals from generic security noise.
    - Map advisories to installed packages, exposed services, and compensating controls.
    - Record enough evidence for a patch, exception, or incident handoff.

!!! success "Operator principle"
    A security source is useful only when you can connect it to inventory, exposure, impact, and a decision.

## Start With Your Own Inventory

External information is only half of the problem. Before you can decide
whether a new advisory matters, you need to know what is running.

Useful local evidence includes:

- distribution and release: `cat /etc/os-release`
- kernel version: `uname -r`
- installed packages: `apt list --installed`, `dnf list installed`, or `rpm -qa`
- enabled services: `systemctl list-unit-files --type=service --state=enabled`
- listening sockets: `ss -tulpn`
- exposed containers: `docker ps` or `podman ps`
- application versions from service-specific commands, package metadata, or deployment manifests

Keep this inventory current enough that an advisory can be answered with
facts, not guesswork.

## Primary Sources

Primary sources are the first place to look when deciding whether to patch,
mitigate, or escalate. They are closest to the vendor, project, or
maintainer responsible for the affected software.

Common primary sources include:

- your Linux distribution security notices, such as Debian Security
  Advisories, Ubuntu Security Notices, Red Hat security advisories, SUSE
  security announcements, Arch Linux news, Alpine security updates, and
  FreeBSD security advisories
- upstream project advisories for software you run directly, such as
  OpenSSH, OpenSSL, Samba, PostgreSQL, Apache HTTP Server, Nginx, Kubernetes,
  Docker, Podman, systemd, and GitLab
- cloud-provider security bulletins when the affected layer is managed
  infrastructure
- appliance or platform vendor advisories for firewalls, VPN gateways,
  backup systems, identity platforms, hypervisors, and storage arrays
- GitHub Security Advisories for open-source dependencies in application
  code

Primary sources usually provide the most useful operational details:
affected versions, fixed versions, package names, mitigation options, and
links to patches or changelogs.

## Vulnerability Databases

Vulnerability databases help correlate advisories across vendors and
products. They are especially useful when an issue has a CVE identifier.

Important databases include:

- **CVE**: the common identifier system for public vulnerabilities
- **NVD**: NIST's enriched CVE database with severity metadata and CPE
  matching
- **CISA Known Exploited Vulnerabilities catalog**: vulnerabilities that
  are known to be exploited in the wild
- **FIRST EPSS**: probability-oriented exploit prediction data
- distribution-specific trackers, such as Debian Security Tracker and
  Ubuntu CVE Tracker

Severity scores are useful, but they are not decisions by themselves. A
medium vulnerability on an internet-facing service may matter more than a
critical vulnerability in a package you do not run or expose.

## Mailing Lists and Feeds

Mailing lists and feeds remain valuable because they reach operators
quickly and often include context that does not fit into a database entry.

Consider subscribing to:

- your distribution's security announcement mailing list
- vendor security mailing lists for major services you operate
- CERT/CC and CISA feeds
- project release feeds for critical software
- internal notification channels for your company, cloud provider, or
  managed security tooling

Use filters, labels, or a dedicated mailbox. The goal is a reviewable queue,
not a noisy stream that everyone learns to ignore.

## Community and News Sources

Security blogs, social media, podcasts, conference talks, and newsletters
can be helpful early-warning systems. They are also more likely to contain
partial, repeated, or exaggerated information.

Treat community sources as prompts for verification:

1. Find the original advisory, commit, vendor bulletin, or CVE.
2. Check whether your distribution has shipped fixed packages.
3. Confirm whether you run the affected component.
4. Decide whether the item requires patching, mitigation, monitoring, or no
   action.

Good community sources help you notice trends. They should not replace
vendor advisories or local evidence.

## Ranking a New Advisory

When a new security item appears, answer these questions in order:

1. **Do we run it?** Identify installed packages, running services,
   containers, appliances, or dependencies.
2. **Is it reachable?** Check whether the affected component is exposed to
   the internet, internal users, authenticated users, local users, or only
   disabled code paths.
3. **Is there known exploitation?** Check vendor notes, CISA KEV, public
   exploit reports, and trusted incident writeups.
4. **Is a fix available?** Confirm the fixed package version or upstream
   release.
5. **Can we mitigate safely?** Consider disabling a feature, restricting a
   port, changing configuration, adding a WAF rule, rotating credentials, or
   increasing monitoring.
6. **What is the rollback path?** Know how to revert the package or config
   change if the fix breaks production.

This turns vague security news into a concrete operational decision.

## Linux Evidence Commands

The exact command depends on your distribution, but these patterns are
common:

```bash
# Debian and Ubuntu: package and patch context
apt-cache policy openssl
apt list --upgradable
unattended-upgrade --dry-run --debug

# Red Hat family: advisory and update context
dnf updateinfo list security
dnf updateinfo info --security
rpm -q openssl

# Service exposure
systemctl status ssh
ss -tulpn

# Logs and recent auth activity
journalctl -u ssh --since "24 hours ago"
lastlog
last
```

Use read-only commands first. Save the relevant output before changing the
host so the patch decision can be reviewed later.

## Turning Information Into Action

Every meaningful advisory should end in one of four outcomes:

- **Patch now**: the system is affected, exposed, and a fix is available.
- **Mitigate now, patch soon**: the system is affected, but the patch needs
  testing or is not available yet.
- **Monitor**: the system may become affected or exploitation is developing,
  but there is no immediate exposure.
- **No action with evidence**: the system is not affected, the package is not
  installed, the service is disabled, or the vulnerable feature is not used.

Write the conclusion down. A short note is enough:

```text
Advisory: CVE-YYYY-NNNN in package/service
Hosts checked: web-01, web-02, bastion-01
Evidence: package version, service exposure, vendor fixed version
Decision: patch now / mitigate / monitor / not affected
Owner: name or team
Follow-up: date and ticket
```

## Avoiding Security Noise

Security information can become overwhelming. Keep the process disciplined:

- prefer primary sources over reposts
- compare advisories against inventory before escalating
- do not confuse CVSS score with business impact
- do not ignore low-severity issues on exposed authentication, VPN, backup,
  identity, or remote-management systems
- close the loop by documenting what was checked and why the decision was
  reasonable

The best security teams are not the ones that panic fastest. They are the
ones that convert reliable signal into timely, verifiable action.

## Hands-on Practice

Use a disposable VM or lab machine.

1. Identify your distribution and kernel:

   ```bash
   cat /etc/os-release
   uname -r
   ```

2. Pick one installed network-facing package, such as OpenSSH, Nginx, Apache,
   or Samba.
3. Find its installed version with your package manager.
4. Look up the matching distribution security advisory page or tracker.
5. Record whether the package is current, outdated, or not covered by any
   current advisory you found.
6. Check whether the service is enabled or listening with `systemctl` and
   `ss`.
7. Write a five-line advisory triage note with your decision.
