## Basic security measures

Basic security is not a one-time hardening script. It is a small set of operating habits that keep a Linux host understandable, patched, least-privileged, recoverable, and observable.

The goal is not to make a machine impossible to compromise. The goal is to remove avoidable weaknesses, make risky changes visible, and preserve enough evidence and backups to recover when something goes wrong.

!!! abstract "What you will learn"
    - Apply a practical baseline for a new or inherited Linux host.
    - Verify updates, accounts, services, firewall posture, logs, time sync, and backups.
    - Choose reversible security changes before disruptive ones.
    - Produce a short security baseline note that another operator can trust.

!!! success "Operator principle"
    Basic controls should be boring, repeatable, and easy to verify. If you cannot prove the control is in place, treat it as incomplete.

## Start with inventory

Before you change a host, identify what it is and what it does.

```bash
hostnamectl
cat /etc/os-release
uname -a
ip addr
ip route
ss -tulpen
systemctl --type=service --state=running
```

Write down:

- operating system and version
- kernel version
- primary IP addresses
- default gateway
- listening network services
- business or lab purpose of the host
- owner or responsible team

This inventory prevents accidental damage. A firewall rule that is safe on a workstation may break a production web server. A package restart that is harmless on a lab VM may interrupt a customer-facing database.

## Patch deliberately

Security updates close known weaknesses, but patching is still an operational change. Treat updates as routine maintenance with evidence, not as a blind command to paste.

On Debian or Ubuntu systems, inspect first:

```bash
sudo apt update
apt list --upgradable
```

Then apply the update when the host can tolerate it:

```bash
sudo apt upgrade
```

On Red Hat-family systems, the equivalent workflow is usually:

```bash
sudo dnf check-update
sudo dnf upgrade
```

After updates, verify whether a reboot or service restart is needed. The exact tooling varies by distribution, but the operational questions are consistent:

- Did the update finish cleanly?
- Did any important service restart?
- Is the host running the expected kernel?
- Is a reboot required to complete the fix?
- Can you roll back from backup or snapshot if the update breaks something?

## Remove unnecessary exposure

Every listening service should have a reason to exist.

```bash
ss -tulpen
systemctl --type=service --state=running
```

For each exposed service, ask:

- Who uses this?
- Should it be local-only, private-network-only, or public?
- Is it protected by authentication?
- Is it patched?
- Is it logged?

If a service is not needed, disable it instead of only blocking it:

```bash
sudo systemctl disable --now service-name
```

Replace `service-name` with the actual unit after confirming it is safe to stop. Do not disable services just because you do not recognize them; first check package ownership, documentation, and dependencies.

## Use a default-deny firewall posture

A host firewall is one layer. It does not replace cloud security groups, router rules, load balancers, VPN policy, or application authentication, but it reduces accidental exposure.

On Ubuntu systems that use UFW:

```bash
sudo ufw status verbose
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status numbered
```

On systems using `firewalld`:

```bash
sudo firewall-cmd --state
sudo firewall-cmd --list-all
sudo firewall-cmd --add-service=ssh --permanent
sudo firewall-cmd --reload
```

Many systems also use `nftables` directly:

```bash
sudo nft list ruleset
```

Before enabling or changing firewall rules on a remote host, make sure you have console access, cloud serial access, out-of-band access, or another recovery path. Locking yourself out is an availability incident.

## Harden accounts and authentication

Accounts are a major security boundary. Start by understanding who can log in and who can become root.

```bash
getent passwd
getent group sudo 2>/dev/null || getent group wheel 2>/dev/null
last -ai
sudo -l
```

Basic account measures include:

- remove or lock accounts that no longer need access
- avoid shared human accounts
- use SSH keys instead of passwords where appropriate
- protect private keys with passphrases
- limit `sudo` to the smallest useful command set
- review group membership regularly
- prefer named admin accounts over direct root login

For SSH, inspect the effective server configuration:

```bash
sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication|allowusers|allowgroups'
```

Edit SSH configuration carefully. A syntax error or overly strict rule can block legitimate access. Validate before restart:

```bash
sudo sshd -t
```

## Protect file permissions and secrets

Sensitive files should not be world-readable. Secrets should not live in repos, shell history, tickets, screenshots, or broad log files.

Useful checks:

```bash
find /home -xdev -type f -perm -004 2>/dev/null | head
find /etc -xdev -type f -name "*secret*" -o -name "*.key" 2>/dev/null
find /srv /var/www -xdev -type f -name ".env" -o -name "*secret*" 2>/dev/null
```

Treat results as leads, not automatic findings. Some public files are intentionally readable. Some secret files have safe permissions. Record the path, owner, and permission risk without copying the secret value.

Also review writable directories that influence services:

```bash
systemctl cat service-name
```

If a root-run service executes files from a directory writable by ordinary users, that is a serious privilege boundary problem.

## Keep logs and time trustworthy

Logs are only useful when they exist, are retained long enough, and have reliable timestamps.

Check system logs:

```bash
journalctl --since "24 hours ago" --priority=warning
journalctl _COMM=sshd --since "24 hours ago"
```

Check time sync:

```bash
timedatectl
```

Basic logging measures include:

- keep authentication logs available
- retain logs long enough for incident review
- forward important logs off-host where possible
- monitor failed and successful privileged access
- keep clocks synchronized
- avoid logging secrets

If an attacker can erase the only logs, your evidence disappears with the compromise. Off-host log forwarding is a practical improvement for important systems.

## Back up before you need it

Backups are a security control. They limit ransomware, deletion, broken updates, and operator mistakes.

A useful backup plan answers:

- What data is backed up?
- How often?
- Where is it stored?
- Who can delete or overwrite it?
- How long is it retained?
- When was the last restore test?

Do not claim a backup works until you have restored from it. A simple restore test is often more valuable than another backup tool.

## Establish a baseline note

For each new or inherited Linux host, create a short baseline note:

```text
Host:
Purpose:
Owner:
OS/kernel:
Network exposure:
Running services:
Admin accounts:
Patch status:
Firewall status:
Backup status:
Logging/time status:
Known risks:
Next review date:
```

This note turns basic security into operational memory. It also gives the next operator something concrete to compare against when behavior changes.

## Hands-on practice

Use a disposable VM or a lab host.

1. Record OS, kernel, IP address, default route, listening services, and running services.
2. Inspect pending updates without applying them.
3. Identify one service that should be reachable and one that should not.
4. Review admin group membership and recent logins.
5. Inspect firewall status without changing it.
6. Check `timedatectl` and recent warning logs.
7. Fill out the baseline-note template.
8. Choose one reversible improvement and write the verification command you would run afterward.
