### Recommended Reading

Security reading is most useful when it changes how you operate a system. Do
not collect links just to feel prepared. Build a short list of sources you trust,
know which ones apply to your distribution and services, and turn important
advisories into tested work.

!!! abstract "What you will learn"
    - Choose reliable security references for Linux operations.
    - Separate vendor advisories, vulnerability databases, hardening guides, and general news.
    - Turn a security article or advisory into an operator action plan.
    - Keep reading notes tied to evidence from the systems you administer.

!!! success "Operator principle"
    Read security sources with a question in mind: what system, package, account, port, policy, or recovery step should I verify next?

## Start with vendor advisories

Your distribution's security team is usually the first source to check because
it maps vulnerabilities to supported packages, fixed versions, and update
commands.

- [Ubuntu Security Notices](https://ubuntu.com/security/notices)
- [Debian Security Advisories](https://www.debian.org/security/)
- [Red Hat Product Security Center](https://access.redhat.com/security/)
- [SUSE Security Advisories](https://www.suse.com/support/security/)
- [Arch Linux Security Tracker](https://security.archlinux.org/)
- [FreeBSD Security Advisories](https://www.freebsd.org/security/advisories/)

When you read an advisory, capture the package name, affected versions, fixed
version, service impact, restart requirement, and whether the vulnerable code is
actually installed on your host.

Useful verification commands:

```bash
cat /etc/os-release
uname -a
apt list --installed 2>/dev/null | grep -Ei 'openssl|openssh|sudo|curl'
dnf list installed 2>/dev/null | grep -Ei 'openssl|openssh|sudo|curl'
systemctl list-units --type=service --state=running
```

## Track vulnerabilities carefully

Vulnerability databases are useful for common identifiers and background, but
they do not always tell you whether your distribution has backported a fix. Use
them alongside vendor advisories, not instead of them.

- [CVE Program](https://www.cve.org/)
- [NIST National Vulnerability Database](https://nvd.nist.gov/)
- [CISA Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
- [Exploit Prediction Scoring System](https://www.first.org/epss/)

For production triage, prefer this order:

1. Is the affected package installed?
2. Is the vulnerable service reachable?
3. Is there known exploitation?
4. Is a vendor fix available?
5. Does the update require a service restart or reboot?

## Read hardening guides with restraint

Hardening guides are checklists, not universal law. A control that is sensible
for an internet-facing server might break a training VM, developer workstation,
or legacy application host.

Good references include:

- [CIS Benchmarks](https://www.cisecurity.org/cis-benchmarks)
- [DISA Security Technical Implementation Guides](https://public.cyber.mil/stigs/)
- [OpenSCAP project](https://www.open-scap.org/)
- [Mozilla SSL Configuration Generator](https://ssl-config.mozilla.org/)
- [SSH server hardening guidance from the OpenSSH manual pages](https://man.openbsd.org/sshd_config)

Before applying a hardening recommendation, write down the intent, the rollback
step, the service owner, and the command you will use to prove the control is
working.

## Keep incident response references close

During an incident, you need calm checklists more than broad research. Keep a
small set of references for containment, evidence capture, communication, and
recovery.

- [NIST Computer Security Incident Handling Guide](https://csrc.nist.gov/publications/detail/sp/800-61/rev-2/final)
- [CISA Incident Response guidance](https://www.cisa.gov/resources-tools/resources/incident-response)
- [The Linux Audit documentation](https://linux-audit.com/)
- [systemd journal documentation](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html)

Useful first-look commands:

```bash
last -a | head
lastlog | head
sudo journalctl --since "24 hours ago" --priority=warning
sudo ss -tulpn
sudo find /etc /usr/local/bin /opt -mtime -7 -type f 2>/dev/null
```

Do not run cleanup commands until you have preserved the evidence you need.

## Read beyond tools

Security operations also depend on identity, change management, monitoring,
backups, and communication. These sources help connect Linux commands to a
larger operating model:

- [Open Web Application Security Project](https://owasp.org/)
- [MITRE ATT&CK](https://attack.mitre.org/)
- [CNCF Security Technical Advisory Group](https://tag-security.cncf.io/)
- [Google SRE book: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)
- [USENIX ;login: archives](https://www.usenix.org/publications/login)

## Build a reading-to-action note

Use a consistent template when a link seems important:

```text
Source:
Date read:
System or package affected:
Why it matters:
Evidence checked:
Action taken or deferred:
Rollback or recovery note:
Follow-up owner/date:
```

This habit keeps reading from becoming trivia. It also gives teammates enough
context to understand why a patch, firewall rule, configuration change, or
monitoring alert was added.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson
explicitly says otherwise.

1. Pick one vendor advisory for a package that commonly appears on Linux hosts,
   such as OpenSSH, OpenSSL, sudo, curl, or systemd.
2. Identify the affected versions, fixed versions, and any restart or reboot
   requirement.
3. On your lab host, check whether the package is installed and record the
   installed version.
4. Write a reading-to-action note that says whether the host is affected and
   what you would do next.
5. Add one monitoring or documentation follow-up that would make this easier
   during a real incident.
