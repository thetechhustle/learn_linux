## Security power tools

Security tools are useful only when they answer a clear operational question. A scanner that produces pages of findings without context can waste time. A small command used carefully can give you exactly the evidence you need.

This lesson introduces practical Linux security tools by job: inventory, exposure checks, packet inspection, firewall review, file integrity, auditing, log review, and baseline assessment. Use them to build evidence, not to create noise.

!!! abstract "What you will learn"
    - Match common Linux security tools to the questions they answer.
    - Use read-only checks before changing firewall, audit, or detection configuration.
    - Recognize when a tool needs permission, tuning, or a maintenance window.
    - Produce a short evidence bundle for a security review or incident handoff.

!!! warning "Permission boundary"
    Only scan or test systems you own or are explicitly authorized to assess. Network scanning, packet capture, brute-force testing, and intrusive vulnerability checks can disrupt systems and may violate policy or law.

!!! success "Operator principle"
    A power tool should make risk clearer. If it does not change a decision, it is probably not the next tool you need.

## Start with built-in inventory tools

Many security questions do not require extra packages.

```bash
hostnamectl
cat /etc/os-release
uname -a
ip addr
ip route
ss -tulpen
systemctl --type=service --state=running
```

These commands answer:

- What host am I looking at?
- What operating system and kernel are running?
- What networks is the host connected to?
- What services are listening?
- Which processes own those listeners?
- Which services are active?

Use this baseline before running a scanner. It keeps the scan results grounded in the host's real purpose.

## Nmap for exposure checks

`nmap` helps verify what is reachable from a network perspective. It is most useful when you compare perspectives: from the host, from the same subnet, from a VPN, from a cloud network, or from the internet.

Install it where appropriate:

```bash
sudo apt install nmap
```

A low-impact host discovery scan on a lab network:

```bash
nmap -sn 192.168.1.0/24
```

A basic TCP port scan against a host you administer:

```bash
nmap -sT -Pn 192.168.1.20
```

Version detection is more intrusive and can trigger alerts:

```bash
nmap -sV -Pn 192.168.1.20
```

Use `nmap` to confirm exposure, not to guess intent. If a port is open, ask what service owns it, who needs it, and which control should restrict it.

## Firewall inspection tools

Linux estates may use `ufw`, `firewalld`, `nftables`, or older `iptables` rules. Do not assume one tool tells the whole story until you know the distribution and management pattern.

Read-only checks:

```bash
sudo ufw status verbose
sudo firewall-cmd --list-all
sudo nft list ruleset
sudo iptables -S
```

`iptables` is still common, but `nftables` is the modern packet-filtering framework on many systems. Distribution front ends such as UFW and firewalld may generate lower-level rules for you.

Before changing firewall rules, answer:

- Am I connected remotely through a rule I might break?
- Is there console or out-of-band access?
- Is another system also enforcing policy, such as a cloud security group or router?
- What command will prove the intended service still works?
- What rollback command restores the old state?

## tcpdump for packet evidence

`tcpdump` captures packets. It is powerful because it shows what actually crosses an interface, but it can expose sensitive data and create large files quickly.

List interfaces:

```bash
ip link
```

Capture a small sample of SSH traffic metadata:

```bash
sudo tcpdump -i eth0 -nn -c 20 tcp port 22
```

Capture to a file for later analysis:

```bash
sudo tcpdump -i eth0 -nn -w /tmp/sample.pcap -c 100 host 192.168.1.20
```

Use packet capture when logs and service state disagree. Do not capture broad traffic on production networks unless you have approval and a retention plan.

## auditd for privileged activity

The Linux audit subsystem can record security-relevant events such as file access, privilege changes, and administrative commands. It is useful when you need evidence that normal logs do not provide.

Common read commands:

```bash
sudo auditctl -s
sudo ausearch -m USER_LOGIN,USER_AUTH,USER_ACCT --start recent
sudo aureport --summary
```

Audit rules should be tuned. Overbroad audit rules can generate too much data and harm performance. Good audit targets include:

- changes to `/etc/passwd`, `/etc/shadow`, and `/etc/sudoers`
- privileged command execution
- changes to SSH configuration
- changes to service units
- access to high-value application secrets

Audit logs are only useful if they are retained and reviewed.

## AIDE and file integrity monitoring

File integrity tools record known-good file metadata and report changes later. They are useful for detecting unexpected changes to binaries, configuration, and sensitive paths.

Examples include AIDE and Tripwire. AIDE is common on Linux systems:

```bash
sudo apt install aide
sudo aideinit
```

After initialization, you compare current state against the baseline:

```bash
sudo aide --check
```

File integrity monitoring requires maintenance. Package updates, configuration deployments, and legitimate admin work will change files. Update the baseline only after you understand and accept the changes.

## Fail2ban and rate limiting

`fail2ban` watches logs and applies temporary bans after repeated failures. It can reduce password-guessing noise against SSH and similar services.

Useful checks:

```bash
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

Before enabling a jail, confirm:

- the log path is correct
- the filter matches your distribution's log format
- the ban action matches your firewall stack
- trusted admin networks will not be accidentally blocked
- you have a way back in if you lock yourself out

Fail2ban is not a substitute for strong authentication. It is a noise-reduction and rate-limiting layer.

## Log review tools

Start with the system journal:

```bash
journalctl --since "24 hours ago" --priority=warning
journalctl _COMM=sshd --since "24 hours ago"
```

Other useful tools depend on the log source:

- `last` and `lastb` for login history
- `ausearch` and `aureport` for audit logs
- `logwatch` for summarized reports
- `goaccess` for web access logs

Example:

```bash
last -ai
lastb -ai 2>/dev/null
```

Summaries help, but always drill into raw logs before making a serious claim.

## Lynis for baseline assessment

`lynis` performs a local security audit and suggests hardening improvements. It is useful for discovering gaps, especially on inherited systems.

```bash
sudo apt install lynis
sudo lynis audit system
```

Treat Lynis output as a prioritized checklist, not a verdict. Some findings are irrelevant to a host's role; others are important. Record the finding, affected control, decision, and follow-up.

## Vulnerability scanners

Vulnerability scanners can identify known vulnerable software and risky configuration, but they need tuning and authorization. Examples include OpenVAS/Greenbone, Nessus, and cloud-provider scanners.

Use them when:

- you have permission to scan the target range
- you know the maintenance window or rate limit
- someone will triage findings
- false positives and compensating controls will be documented
- critical findings can be fixed or escalated

Do not treat scan output as a substitute for inventory, patch policy, and service ownership.

## Build an evidence bundle

For a small security review, collect a concise bundle:

```text
Host:
Purpose:
Scan source:
Listening services:
Firewall posture:
Recent login evidence:
Privileged account review:
Patch status:
Integrity/audit/logging status:
Notable findings:
Recommended next action:
Rollback or recovery notes:
```

Attach command names and timestamps, not secrets. If a command reveals sensitive values, redact the value and record the file path or control instead.

## Hands-on practice

Use a lab VM or a network you administer.

1. Record host inventory with built-in commands.
2. Run a basic `nmap` scan from another machine or VM on the same lab network.
3. Compare `nmap` output to `ss -tulpen` on the host.
4. Inspect firewall state with the relevant local tool.
5. Review recent SSH or login logs.
6. Run one local assessment tool, such as Lynis, and choose the top three relevant findings.
7. Write a short evidence bundle with one recommended next action and one rollback note.
