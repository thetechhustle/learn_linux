### Firewalls

!!! abstract "What you will learn"
    - Explain what a Linux firewall can and cannot protect.
    - Inspect host firewall state with `ufw`, `firewalld`, `nftables`, and `iptables`.
    - Plan a safe allowlist change without locking yourself out.
    - Capture firewall evidence for an incident handoff or service review.

A firewall enforces network policy. It decides which packets are allowed, rejected, dropped, forwarded, or translated. On a Linux host, the firewall is usually one layer in a larger design that also includes cloud security groups, load balancers, container networks, VPNs, routers, and application authentication.

Do not treat "firewall enabled" as proof that a system is secure. A useful firewall answers narrower questions:

- Which services should be reachable?
- From which sources?
- On which interfaces?
- Over which protocols and ports?
- What happens to everything else?
- Where is the policy enforced: host, cloud, router, container runtime, or all of them?

## Start with exposure

Before changing firewall rules, identify what is listening.

```bash
sudo ss -tulpen
```

Useful fields:

- `Local Address:Port` shows where the service is bound.
- `0.0.0.0` or `::` means the service may accept traffic on all IPv4 or IPv6 interfaces.
- `127.0.0.1` or `::1` means local-only.
- `users:(...)` helps connect a socket to a process.

Then inspect addresses and routes:

```bash
ip -brief address
ip route
```

The firewall policy should match the actual interfaces and services. If SSH only needs to be reachable through a VPN interface, do not allow it on every interface.

## Pick the right control surface

Many distributions provide a front end for the kernel packet filter.

Common paths:

- **UFW:** common on Ubuntu and simple single-host setups.
- **firewalld:** common on Fedora, RHEL, CentOS Stream, and zone-based hosts.
- **nftables:** modern lower-level packet filtering framework.
- **iptables:** legacy interface still present on many systems and sometimes backed by nftables compatibility mode.

Check what is active:

```bash
systemctl is-active ufw firewalld nftables 2>/dev/null
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --state 2>/dev/null
sudo nft list ruleset 2>/dev/null | sed -n '1,80p'
sudo iptables -S 2>/dev/null
```

Avoid mixing front ends casually. If `firewalld` owns the host policy, adding raw `iptables` commands can create confusing temporary state that disappears later or conflicts with the managed policy.

## Default policy

A common host stance is:

- allow established return traffic
- allow loopback
- allow required management paths
- allow explicitly published services
- deny or drop unexpected inbound traffic
- leave outbound traffic open unless there is a specific control requirement

For many single-host servers, inbound allowlisting gives most of the value with less operational risk than a rushed outbound deny policy.

Document the intended policy before implementing it:

```text
Host:
Management source:
Allowed inbound services:
Public services:
Private-only services:
Default inbound policy:
Rollback path:
Verification command:
```

## UFW workflow

Inspect current state:

```bash
sudo ufw status verbose
```

Allow SSH from a trusted management network before enabling a deny-by-default policy:

```bash
sudo ufw allow from 203.0.113.0/24 to any port 22 proto tcp comment 'SSH from admin network'
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw enable
sudo ufw status numbered
```

Delete a numbered rule only after rereading the list. Rule numbers change after deletion.

```bash
sudo ufw status numbered
sudo ufw delete 3
```

On remote systems, use a separate active session or console before enabling rules. A firewall mistake can lock you out.

## firewalld workflow

`firewalld` groups interfaces into zones. A zone carries services, ports, rich rules, masquerading, and other settings.

Inspect active zones:

```bash
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all
```

Allow a service permanently and reload:

```bash
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

Allow a specific port:

```bash
sudo firewall-cmd --permanent --add-port=8443/tcp
sudo firewall-cmd --reload
```

If a command uses `--permanent`, remember that the running configuration may not change until reload. If a command omits `--permanent`, the change may disappear at reload or reboot.

## nftables workflow

`nftables` is the modern Linux packet filtering framework. It can express filter, NAT, and routing-related policies in one ruleset.

Inspect the ruleset:

```bash
sudo nft list ruleset
```

A minimal inbound allowlist concept looks like this:

```nft
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif lo accept
    tcp dport 22 ip saddr 203.0.113.0/24 accept
    tcp dport { 80, 443 } accept
  }
}
```

Do not paste rules into a production host blindly. Validate the file and have a rollback path:

```bash
sudo nft -c -f /etc/nftables.conf
sudo systemctl reload nftables
sudo nft list ruleset
```

## iptables literacy

Some hosts still use `iptables`, and many old runbooks are written for it.

Inspect filter rules:

```bash
sudo iptables -S
sudo iptables -L -n -v
```

Inspect NAT rules:

```bash
sudo iptables -t nat -S
```

Be careful with commands such as this:

```bash
sudo iptables -A INPUT -s 198.51.100.25 -j DROP
```

It appends a runtime rule, but persistence depends on the distribution and tooling. It may not survive reboot, and it may not be visible in the higher-level front end that actually owns the policy.

## Containers and cloud firewalls

Container runtimes and cloud platforms can add firewall layers that are not obvious from a simple host check.

For Docker hosts, inspect published ports:

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

For Kubernetes or other orchestration platforms, check service, ingress, and network policy objects with the platform's own tools. A host firewall may not be the only place traffic is allowed or denied.

In cloud environments, compare host policy to the provider controls:

- security groups
- network ACLs
- load balancer listeners
- private subnet routing
- VPN or bastion access paths

The most common mistake is fixing one layer while the actual exposure lives in another.

## Verification

Verify from both sides when possible.

On the server:

```bash
sudo ss -tulpen
sudo ufw status verbose 2>/dev/null || true
sudo firewall-cmd --list-all 2>/dev/null || true
sudo nft list ruleset 2>/dev/null | sed -n '1,120p'
```

From a client or scanner host:

```bash
nc -vz server.example.com 22
nc -vz server.example.com 443
nmap -Pn -p 22,80,443 server.example.com
```

Do not scan networks you do not own or have permission to test.

## Incident handoff evidence

For a firewall change or incident review, record:

```text
Host:
Public/private IPs:
Listening services:
Firewall front end:
Default inbound policy:
Allowed inbound ports:
Allowed source ranges:
Cloud/security-group policy checked:
Container/orchestrator policy checked:
Verification from server:
Verification from client:
Rollback command:
Remaining risk:
```

This turns a firewall change from "I think it is blocked" into a repeatable operational claim.

## Hands-on practice

Use a disposable VM or lab host.

1. Record `ss -tulpen` output.
2. Identify which firewall front end is active.
3. Write a short intended policy for SSH and one web service.
4. Apply the policy in the active front end.
5. Verify from the host and from another machine.
6. Revert the change and verify that the lab is back to its starting state.
