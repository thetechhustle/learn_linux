### Cryptography primer for Linux operators

!!! abstract "What you will learn"
    - Explain what cryptography protects and what it does not protect.
    - Distinguish hashing, symmetric encryption, asymmetric encryption, signatures, and certificates.
    - Use common Linux tools to inspect hashes, keys, certificates, and TLS connections.
    - Build a short evidence trail for an encrypted service or protected file.

Cryptography is the machinery behind SSH, TLS, package signing, password storage, disk encryption, VPNs, and many backup systems. You do not need to become a cryptographer to administer Linux, but you do need to know which primitive is being used, where the secret lives, and what evidence proves the system is working.

The operator view is simple:

- **Confidentiality:** prevent unauthorized people from reading data.
- **Integrity:** detect whether data changed.
- **Authentication:** prove who created, served, or approved something.
- **Non-repudiation:** make it difficult for a signer to deny that they signed an artifact.

Cryptography does not fix weak passwords, stolen private keys, unsafe permissions, unpatched software, bad backups, or users who ignore warnings. It is a strong control only when the surrounding operations are disciplined.

## Hashing

A hash turns input into a fixed-size digest. Good cryptographic hashes are one-way and collision-resistant enough for practical integrity checks.

Common uses:

- verifying downloaded files
- detecting configuration drift
- indexing known-good artifacts
- storing password verifier data with a purpose-built password hashing function

Inspect a file hash:

```bash
sha256sum /etc/ssh/sshd_config
```

Compare a file against a published checksum:

```bash
printf '%s  %s\n' 'EXPECTED_SHA256_VALUE' 'downloaded-file.tar.gz' | sha256sum --check
```

Do not use a raw fast hash such as SHA-256 as a password storage scheme. Passwords need slow, salted password-hashing algorithms such as yescrypt, bcrypt, scrypt, or Argon2, depending on the platform and application.

Inspect local password hash metadata without exposing the hashes broadly:

```bash
sudo getent shadow "$USER" | cut -d: -f2 | cut -d'$' -f2
```

The output identifies the hash scheme on many Linux systems. Treat `/etc/shadow` content as sensitive.

## Symmetric encryption

Symmetric encryption uses the same secret to encrypt and decrypt. It is fast and is used for most bulk data encryption.

Common uses:

- encrypted disks
- encrypted backups
- TLS session data after handshake negotiation
- application secrets at rest

Encrypting a file with `openssl enc` can be useful for a lab, but production backup encryption is usually better handled by a tool designed for the job, such as `age`, `gpg`, `restic`, `borg`, LUKS, or the storage provider's native encryption controls.

Inspect encrypted block devices:

```bash
lsblk -f
sudo cryptsetup status cryptroot
```

For symmetric encryption, the operational questions are:

- Where is the key stored?
- Who can read it?
- How is it rotated?
- Is there a recovery path if the key is lost?
- Is the algorithm and mode still acceptable?

## Asymmetric keys

Asymmetric cryptography uses a key pair:

- a **public key** that can be shared
- a **private key** that must be protected

Common uses:

- SSH authentication
- TLS certificates
- package and release signing
- encrypted messages to a recipient

Inspect an SSH public key fingerprint:

```bash
ssh-keygen -lf ~/.ssh/id_ed25519.pub
```

Inspect the permissions on SSH private keys:

```bash
find ~/.ssh -type f -maxdepth 1 -name 'id_*' ! -name '*.pub' -exec ls -l {} \;
```

Private keys should not be world-readable. A typical private-key mode is `600`, and the `.ssh` directory is commonly `700`.

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
```

Use modern key types where possible. Ed25519 is a strong default for SSH user keys:

```bash
ssh-keygen -t ed25519 -a 100 -C "$USER@$(hostname)-$(date +%Y%m%d)"
```

Do not generate new production keys casually. Key creation, distribution, replacement, and revocation need an owner and an inventory.

## Digital signatures

A signature proves that a holder of a private key signed specific data. The receiver verifies the signature with the corresponding public key.

Common uses:

- package repository metadata
- release artifacts
- Git commits and tags
- container images
- configuration bundles

Verify package signatures with your distribution's package tools rather than by hand when possible:

```bash
apt-cache policy openssl
rpm -q --info openssl
```

Inspect Git signing configuration:

```bash
git config --show-origin --get commit.gpgsign
git log --show-signature -1
```

The evidence you want is not just "a signature exists." You also need to know whether the signing key is trusted for that purpose.

## Certificates and TLS

TLS certificates bind a public key to an identity, usually a DNS name. A certificate is useful because clients can build a chain from the server certificate to a trusted certificate authority.

Inspect a remote HTTPS certificate:

```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -fingerprint -sha256
```

Check what protocol and cipher a service negotiates:

```bash
openssl s_client -connect example.com:443 -servername example.com -tls1_3 </dev/null
```

For a Linux service, collect:

- certificate subject and subject alternative names
- issuer
- expiration date
- certificate chain status
- protocol and cipher negotiated by a client
- service configuration file that points to the certificate and private key

Common failure patterns:

- certificate expired
- certificate does not match the hostname
- private key file is missing or has unsafe permissions
- service was reloaded before the new certificate was installed
- intermediate certificate is missing from the served chain
- load balancer and backend certificates are being confused

## Secrets and key handling

Keys are high-value operational assets. A weak key-handling process can defeat otherwise strong cryptography.

Minimum expectations:

- keep private keys out of Git
- restrict file permissions
- separate production keys from lab keys
- rotate keys when staff, systems, or exposure changes warrant it
- keep recovery material in a controlled place
- record which service depends on which key
- prefer managed secret stores for application secrets

Search a repository for obvious accidental key material before publishing:

```bash
git grep -nE 'BEGIN (RSA|DSA|EC|OPENSSH|PRIVATE) KEY|AWS_SECRET_ACCESS_KEY|password='
```

This is only a quick local screen. It does not replace a real secret-scanning process.

## Incident handoff evidence

When cryptography is part of an incident or service review, avoid vague claims such as "TLS is enabled." Write down evidence:

```text
Service:
Hostname:
Port:
Certificate subject:
Certificate issuer:
Certificate expires:
TLS protocol observed:
Cipher observed:
Private key path:
Private key owner/mode:
Reload command used:
Verification command:
Remaining risk:
```

This evidence lets another operator repeat your check without trusting your memory.

## Hands-on practice

Run these commands on a lab machine.

1. Create a small file and record its SHA-256 hash.
2. Change one byte and record the new hash.
3. Inspect one SSH public key fingerprint.
4. Inspect one HTTPS certificate with `openssl s_client`.
5. Write a short note explaining which evidence proves integrity, which proves identity, and which proves confidentiality.
