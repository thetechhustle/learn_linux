## Virtual private networks

!!! abstract "What you will learn"
    - Explain what a VPN does in Linux operations.
    - Distinguish remote-access VPNs, site-to-site VPNs, and overlay networks.
    - Inspect VPN interfaces, routes, peers, and service state.
    - Capture evidence that traffic is using the intended path.

A virtual private network, or VPN, creates a protected network path across an untrusted network. Operators use VPNs to reach private systems, connect sites, join cloud and home-lab nodes, protect administrative traffic, and reduce public exposure.

A VPN is not magic privacy dust. It does not make weak endpoints safe, fix bad access control, or prove that a service is healthy. It gives you a controlled path. You still need identity, patching, firewall rules, logging, key rotation, and a clear routing model.

## Common VPN patterns

Most Linux operators see three broad patterns.

**Remote-access VPN**

A person or device connects into a private environment.

Examples:

- laptop to office network
- admin workstation to private cloud subnet
- phone to home network

**Site-to-site VPN**

Two networks are connected.

Examples:

- office to cloud VPC
- data center to branch location
- home lab to cloud lab

**Overlay network**

Hosts join a private mesh or coordinated network on top of the public internet.

Examples:

- Tailscale
- ZeroTier
- Nebula
- WireGuard-based private host mesh

The right pattern depends on what needs to talk, who owns the endpoints, and whether routing should expose a whole network or only specific hosts and services.

## What to inspect first

Start with the local network view.

```bash
ip -brief address
ip route
ip rule
```

Look for VPN interfaces such as:

- `tun0` or `tap0` for many OpenVPN-style setups
- `wg0` for WireGuard
- `tailscale0` for Tailscale
- provider-specific names in managed clients

Then inspect listening services and firewall state:

```bash
sudo ss -tulpen
sudo nft list ruleset 2>/dev/null | sed -n '1,120p'
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null
```

The central question is not "is a VPN connected?" The better question is "which traffic uses the VPN, and which services become reachable because of it?"

## WireGuard

WireGuard is a small, modern VPN protocol commonly used for host-to-host, remote-access, and site-to-site tunnels.

Inspect peers and transfer counters:

```bash
sudo wg show
```

Inspect the interface and routes:

```bash
ip -brief address show wg0
ip route show dev wg0
```

Common WireGuard evidence:

- interface is up
- peer public key is expected
- latest handshake is recent
- transfer counters are increasing
- allowed IPs match the intended routing design
- firewall allows only the intended UDP listener and forwarded traffic

Be careful with `AllowedIPs`. It controls routing as well as peer traffic selection. `0.0.0.0/0` routes all IPv4 traffic through a peer. A narrow subnet such as `10.20.0.0/24` routes only that private range.

## OpenVPN

OpenVPN is widely deployed and may appear on older estates or provider-managed client setups.

Inspect service state:

```bash
systemctl status 'openvpn*' --no-pager
```

Inspect client logs:

```bash
journalctl -u 'openvpn*' --since '30 minutes ago' --no-pager
```

Inspect interfaces and routes:

```bash
ip -brief address
ip route
```

Typical OpenVPN failure causes:

- expired client certificate
- wrong `.ovpn` profile
- DNS pushed through the tunnel but not applied locally
- route missing for the private subnet
- server-side firewall blocks VPN client subnet
- client connects but cannot reach target service

Do not copy random provider profiles into `/etc/openvpn` without understanding what routes, DNS settings, and scripts they apply.

## Tailscale and mesh overlays

Tailscale uses WireGuard underneath but adds identity, coordination, ACLs, MagicDNS, subnet routes, and exit nodes.

Inspect local state:

```bash
tailscale status
tailscale ip -4
tailscale netcheck
```

Inspect routes and interface:

```bash
ip -brief address show tailscale0
ip route | grep tailscale
```

Operational questions:

- Is this node logged into the expected tailnet?
- Which users or groups can reach it?
- Is it advertising subnet routes?
- Is it acting as an exit node?
- Are ACLs intentionally allowing this traffic?
- Is MagicDNS involved in name resolution?

Tailscale can make a private service easy to reach, which is useful. It can also make exposure harder to reason about if ACLs, tags, and subnet routes are not documented.

## Routing and split tunnel checks

VPN incidents are often routing incidents. The tunnel can be connected while traffic still uses the wrong path.

Check the route to a destination:

```bash
ip route get 10.20.30.40
```

Check your apparent public IP before and after enabling a full-tunnel VPN:

```bash
curl -4 https://ifconfig.me
```

Check DNS resolution:

```bash
resolvectl status 2>/dev/null
getent hosts internal.example.com
```

For split tunnels, only selected private ranges should route through the VPN. For full tunnels, default traffic should route through the VPN. Write down which model is intended before debugging.

## Firewall and forwarding

A VPN interface is just another interface from the host firewall's point of view. If the host should forward traffic between a VPN and another network, IP forwarding and firewall policy both matter.

Inspect forwarding:

```bash
sysctl net.ipv4.ip_forward
sysctl net.ipv6.conf.all.forwarding
```

Inspect routes:

```bash
ip route
```

Inspect firewall policy:

```bash
sudo nft list ruleset 2>/dev/null | sed -n '1,160p'
sudo iptables -S 2>/dev/null
sudo iptables -t nat -S 2>/dev/null
```

Do not enable forwarding or NAT on a production host without a design. A host can accidentally become a router between networks that were meant to stay separate.

## Verification workflow

Use a layered check.

1. Confirm the VPN process or service is running.
2. Confirm the interface exists.
3. Confirm the peer or session is established.
4. Confirm route selection with `ip route get`.
5. Confirm DNS if names are involved.
6. Confirm firewall allows the intended path.
7. Test the actual service from the correct source.

Example:

```bash
ip -brief address
sudo wg show 2>/dev/null || true
tailscale status 2>/dev/null || true
ip route get 10.20.30.40
nc -vz 10.20.30.40 22
```

## Incident handoff evidence

For a VPN issue or change, record:

```text
VPN type:
Local host:
Remote peer/site:
Interface:
Local tunnel IP:
Remote/private ranges:
Full tunnel or split tunnel:
DNS behavior:
Peer/session evidence:
Route evidence:
Firewall evidence:
Service test:
Rollback path:
Remaining risk:
```

Good VPN handoffs include both tunnel evidence and application evidence. A tunnel can be healthy while the target service is down, blocked, or listening only on localhost.

## Hands-on practice

Use a lab host or disposable VM.

1. Inspect current interfaces and routes.
2. Identify whether any VPN interface is present.
3. Run `ip route get` for a public IP and a private RFC1918 address.
4. If a VPN is available, connect it and repeat the route checks.
5. Write a short note explaining whether the VPN is split tunnel or full tunnel.
