# 27.1 Elements of Security

Security is not one product, one command, or one hardening checklist. It is the habit of knowing what a system is supposed to do, limiting who can change it, recording useful evidence, and preparing for the day something goes wrong.

On a Linux system, the basic elements of security show up in ordinary operations:

- **Confidentiality:** only approved people and services can read sensitive data.
- **Integrity:** files, packages, configuration, and logs are trustworthy enough to make decisions from.
- **Availability:** authorized users can still use the system when hardware fails, software breaks, or attackers create noise.
- **Authentication:** users, services, and hosts prove who they are.
- **Authorization:** authenticated identities receive only the access they need.
- **Accountability:** important actions leave evidence that can be reviewed later.
- **Recovery:** backups, rebuild instructions, and incident procedures let you restore service without guessing.

## Think in Layers

No single layer can carry the entire security model. Strong operations combine several controls so that a mistake in one place does not immediately become a full compromise.

| Layer | What it protects | Common Linux evidence |
| --- | --- | --- |
| Identity | Who can log in or run services | `/etc/passwd`, `/etc/group`, `getent passwd`, `lastlog`, `loginctl` |
| Privilege | What identities can do | `sudo -l`, `/etc/sudoers`, `/etc/sudoers.d/`, file ownership and modes |
| Software supply | What code is installed | package manager history, repository configuration, package signatures |
| Network exposure | What can be reached | `ss -tulpen`, firewall rules, cloud security groups, reverse proxy config |
| Files and secrets | What data can be read or changed | permissions, ACLs, encryption state, secret locations, backup access |
| Logging and audit | What happened | `journalctl`, `/var/log/`, audit rules, authentication logs |
| Recovery | How service returns | tested backups, restore notes, rebuild automation, incident runbooks |

Use these layers as a mental checklist. If you cannot explain a layer, inspect it before you harden it.

## Confidentiality

Confidentiality means data is visible only to the people and processes that need it. On Linux, this usually starts with user and group membership, file permissions, service accounts, encryption, and network boundaries.

Read-only checks:

```bash
id
getent group sudo
find /etc -maxdepth 1 -type f -perm -004 -ls
ss -tulpen
```

Treat world-readable configuration, exposed services, and shared administrator accounts as prompts for deeper review. Do not immediately run recursive permission changes; broad `chmod -R` commands often break services or hide the real authorization problem.

## Integrity

Integrity means the system state has not been changed unexpectedly. Package verification, configuration review, file checksums, and change control all support integrity.

Read-only checks:

```bash
systemctl --failed
dpkg -l | head        # Debian and Ubuntu
rpm -qa | head        # RHEL, Fedora, Rocky, AlmaLinux
sha256sum /etc/ssh/sshd_config
git -C /etc status    # Only if /etc is intentionally version-controlled
```

For important configuration, save a known-good copy in version control or a configuration management system. A checksum alone tells you that a file changed; it does not tell you whether the change was approved.

## Availability

Availability means the service can continue operating for authorized users. Security work should not make a system impossible to patch, monitor, restart, or restore.

Read-only checks:

```bash
uptime
df -h
free -h
systemctl list-units --state=failed
journalctl -p warning -n 50
```

Availability is part of security because outages create pressure to bypass controls. A firewall rule that blocks monitoring, a password policy that locks out every administrator, or a backup process that consumes all disk space can become a security incident.

## Authentication and Authorization

Authentication proves identity. Authorization decides what that identity may do. Keep those ideas separate when troubleshooting access problems.

Read-only checks:

```bash
getent passwd
getent group
sudo -l
find /etc/sudoers.d -maxdepth 1 -type f -print -exec sed -n '1,120p' {} \;
```

Common patterns:

- A user can authenticate but cannot run the needed command because sudo policy is missing.
- A service can start but cannot read its configuration because file ownership is wrong.
- SSH accepts a key, but the account is locked or the shell is invalid.
- A group grants more access than expected because old members were never removed.

Prefer narrow authorization changes. Add the specific group, file mode, ACL, or sudo rule that matches the job rather than granting broad administrator access.

## Accountability

Accountability means important actions can be tied to a time, identity, host, and outcome. Logs are operational evidence, not decorations.

Useful checks:

```bash
journalctl --since "1 hour ago" -p info
journalctl _COMM=sudo --since today
last -a | head
lastlog | head
```

Logs are only useful if they exist before the incident. Verify time synchronization, log rotation, retention, and remote log forwarding for systems where local logs might be deleted or lost.

## Recovery

Recovery is the security element people tend to test last, which is exactly why it fails during incidents. A backup that has never been restored is only a hope.

Minimum recovery questions:

- What data must be restored first?
- Where are backups stored, and who can delete them?
- How often is a restore tested?
- Which credentials are needed during an outage?
- Can the host be rebuilt from documented steps or automation?

Read-only checks:

```bash
systemctl list-timers
find /etc -maxdepth 2 \( -iname '*backup*' -o -iname '*restore*' \)
mount | grep -Ei 'backup|snapshot|nfs|cifs'
```

Security controls should assume that prevention sometimes fails. Recovery is how you keep a bad event from becoming a permanent loss.

## Build a Short Evidence Trail

When you first inspect a Linux host, gather enough evidence to discuss risk without making changes:

```bash
hostnamectl
uptime
ss -tulpen
systemctl --failed
getent passwd | tail
getent group sudo
sudo -l
journalctl -p warning -n 50
```

Save the command list, the date, the hostname, and the main findings. If you later change firewall rules, sudo policy, SSH settings, or package sources, rerun the relevant checks and record the difference.

## Hands-on Practice

Use a disposable VM or lab container.

1. Record the host identity and uptime with `hostnamectl` and `uptime`.
2. List listening services with `ss -tulpen` and identify one service you expected and one you need to investigate.
3. Inspect failed units with `systemctl --failed`.
4. Check your own effective identity with `id` and your sudo authorization with `sudo -l`.
5. Read the last 50 warning-or-higher journal messages with `journalctl -p warning -n 50`.
6. Write a five-line security note: confidentiality concern, integrity concern, availability concern, accountability evidence, and one recovery question.

## Common Failure Patterns

- Treating security as a one-time hardening script instead of continuous evidence gathering.
- Granting administrator access to fix a narrow file, service, or group problem.
- Opening a firewall before confirming which process is listening and why.
- Keeping backups on the same host with the same credentials as the protected data.
- Rotating logs so aggressively that incident evidence disappears before anyone reviews it.
- Changing SSH or sudo policy without keeping a second administrative session open for rollback.
