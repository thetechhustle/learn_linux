## 27.12 When Your Site Has Been Attacked

Incident response is not the art of typing the most dramatic command first.
It is the discipline of keeping the organization safe while preserving enough
evidence to understand what happened. A compromised Linux host may need to be
isolated, rebuilt, restored, or investigated by specialists. The operator's
first job is to slow the damage without destroying the trail.

!!! abstract "What you will learn"
    - Recognize common signs that a Linux system or web site may be compromised.
    - Preserve useful evidence before making major changes.
    - Separate containment, eradication, recovery, and hardening.
    - Write a clear incident handoff for teammates, leadership, or outside responders.

!!! warning "Safety boundary"
    Do not treat an incident as a normal maintenance window. If legal, customer-data, payment-card, regulated-data, or business-continuity risk is involved, escalate through the organization's incident process before making destructive changes.

## Do Not Panic, But Do Move

Panic destroys evidence. Delay lets the attacker keep working. The useful
middle ground is a simple response rhythm:

1. stabilize the situation
2. preserve evidence
3. contain the attacker
4. identify the likely entry point
5. eradicate the foothold
6. recover from trusted sources
7. close the weakness that made the compromise possible
8. document what changed

The order can change during a real emergency, but the categories should not
be skipped.

## Signs of Compromise

No single symptom proves an attack, but these signals deserve attention:

- unexplained spikes in traffic, CPU, disk, memory, or outbound bandwidth
- web pages replaced, injected, redirected, or serving unexpected JavaScript
- new users, SSH keys, cron jobs, services, containers, or systemd units
- unexpected listening ports or reverse-shell-like outbound connections
- authentication logs showing unusual users, locations, or failed attempts
- files changed under application, web root, plugin, theme, or upload paths
- security tools disabled or logs missing
- package manager history showing unexpected installs
- cloud console, DNS, object storage, or CI/CD changes that do not match a
  normal deployment

Start with facts. Do not assume the web server is the only affected system.

## Preserve Evidence First

Before deleting files, restarting services, rebuilding the host, or rotating
every credential, capture a small evidence bundle.

Useful read-only commands include:

```bash
date -u
hostnamectl
ip addr
ip route
ss -tulpn
ps auxww
systemctl --failed
systemctl list-units --type=service --state=running
systemctl list-timers
last
lastlog
journalctl --since "24 hours ago" --no-pager
```

Application-specific evidence may include:

- web server access and error logs
- application logs
- database audit logs
- authentication provider logs
- firewall and load balancer logs
- cloud audit logs
- CI/CD deployment history
- checksums or copies of suspicious files

If the incident is serious, take a disk snapshot or VM image before changing
the system. If you cannot snapshot the host, at least copy relevant logs and
record exact timestamps.

## Containment

Containment limits attacker access while preserving your ability to
investigate.

Possible containment actions:

- remove the host from a load balancer pool
- restrict ingress at the cloud firewall, security group, reverse proxy, or
  network firewall
- block a confirmed hostile source only if it is useful and not just one
  rotating address
- disable a compromised account
- revoke a leaked API token, SSH key, deploy key, or application credential
- pause a vulnerable feature, plugin, route, or scheduled job
- stop a malicious process if it is actively causing damage

Prefer reversible controls. For example, removing a host from rotation is
usually safer than immediately wiping it.

!!! note "Firewall note"
    Many older examples use `iptables`, but modern Linux fleets may use
    `nftables`, `firewalld`, `ufw`, cloud firewalls, or a load balancer. Use
    the control plane that actually governs traffic for the affected host.

## Investigation

Investigation answers three practical questions:

1. How did the attacker get in?
2. What did they access or change?
3. What has to be trusted, rebuilt, rotated, or monitored?

Start broad, then narrow:

```bash
# Recent authentication activity
journalctl _COMM=sshd --since "7 days ago" --no-pager
grep -R "Accepted\\|Failed password\\|Invalid user" /var/log/auth.log* 2>/dev/null

# New or unusual users and privileges
getent passwd
getent group sudo
getent group wheel
sudo -l

# Persistence paths
systemctl list-unit-files --state=enabled
find /etc/systemd/system -type f -mtime -14 -print
find /etc/cron* /var/spool/cron -type f -mtime -14 -print 2>/dev/null

# Web root or app changes
find /var/www -type f -mtime -14 -print 2>/dev/null
```

Adjust paths for your distribution and application. On Red Hat-family
systems, authentication logs may be in `/var/log/secure`; on Debian-family
systems, they are commonly in `/var/log/auth.log`.

## Eradication

Eradication removes the attacker's foothold. It is not the same as recovery.

Common eradication work includes:

- patching the vulnerable package, plugin, framework, or container image
- removing malicious files, cron jobs, systemd units, containers, or users
- rotating compromised credentials
- revoking stale SSH keys and deploy tokens
- fixing filesystem permissions or ownership
- disabling unsafe upload, admin, debug, or remote-management paths
- rebuilding compromised artifacts from clean source

If the host's integrity is questionable, do not try to clean it in place as a
long-term fix. Rebuild from a trusted image and restore clean data.

## Recovery

Recovery returns the service safely.

A practical recovery checklist:

1. Rebuild or patch from trusted sources.
2. Restore data from a backup taken before the compromise when needed.
3. Apply credential rotations before exposing the service again.
4. Confirm service health locally.
5. Confirm logs, monitoring, and alerting are working.
6. Return traffic gradually.
7. Watch for repeated exploit attempts, new errors, or suspicious outbound
   connections.

Recovery should be evidence-backed. Do not claim a system is clean just
because the home page loads.

## Communication

Incidents often fail because the technical response and communication plan
drift apart. Decide who needs to know:

- internal operations or engineering owners
- leadership
- legal or compliance
- customers or users
- payment, insurance, or external incident-response partners
- law enforcement or national reporting channels when appropriate

Do not speculate in written updates. Say what is known, what is unknown, what
has been contained, and what is being checked next.

## Post-Incident Hardening

After the emergency, turn the incident into better operations:

- patch the root cause
- close unnecessary ports and services
- require stronger authentication for admin paths
- improve backup restore testing
- add missing logs and alerts
- review deployment and secret-handling workflows
- document indicators of compromise
- add a runbook for the next responder
- run a short post-incident review with concrete follow-up owners

The lesson is not "never get attacked." The lesson is to reduce blast radius,
recover from trusted sources, and make the same path harder to use again.

## Incident Handoff Template

```text
Incident:
Detected at:
Detected by:
Affected systems:
Current status:
Known evidence:
Containment actions taken:
Suspected entry point:
Credentials rotated:
Backups/snapshots preserved:
Customer/data/legal risk:
Next owner:
Next action:
```

Keep this note short and factual. It should help the next person act without
having to reconstruct your thinking from shell history.

## Hands-on Practice

Use a disposable VM or lab container. Do not run incident experiments on a
production system.

1. Create a mock incident note using the handoff template.
2. Capture a read-only evidence bundle with `date -u`, `hostnamectl`, `ss`,
   `ps`, `systemctl`, `last`, and `journalctl`.
3. Identify three containment actions that would be reversible.
4. Identify one case where rebuilding the host would be safer than cleaning
   it in place.
5. Write a post-incident follow-up list with owners and due dates.

## Check Your Understanding

- Why can rebooting or wiping a host too early make an incident harder to
  understand?
- What is the difference between containment and eradication?
- When is rebuilding from a trusted image better than cleaning a compromised
  host in place?
- What evidence would you capture before rotating credentials or deleting
  suspicious files?
- What should a leadership update say when the full scope is not yet known?
