## 27.10 Certifications and Standards: Turning Requirements Into Evidence

Security standards are useful only when they change how a system is built,
reviewed, and operated. A Linux administrator does not need to memorize every
control number on day one, but they do need to understand how a requirement
turns into a repeatable check, a configuration decision, and an evidence trail.

!!! abstract "What you will learn"
    - Explain the difference between a certification, a framework, a benchmark,
      and an internal policy.
    - Map a security requirement to Linux evidence such as packages, users,
      services, logs, permissions, and backup records.
    - Use standards as operating guides without treating them as a substitute
      for local risk analysis.
    - Prepare concise evidence for an audit, review, or incident handoff.

!!! warning "Standards are not magic"
    Passing an audit does not prove a host is secure. It proves that specific
    controls were checked at a specific time. Keep standards tied to real
    operational risk: exposed services, privileged access, patch history,
    logging, backups, and recovery testing.

## Certifications, frameworks, benchmarks, and policies

These terms are often mixed together, but they answer different questions.

| Item | What it answers | Linux operator example |
| --- | --- | --- |
| Certification | Did a person, product, or organization meet a defined bar? | A team member earns Linux+ or GCUX; an organization maintains ISO/IEC 27001 certification. |
| Framework | How should we organize security work? | NIST Cybersecurity Framework categories help structure inventory, protection, detection, response, and recovery work. |
| Benchmark | What concrete settings should we check? | A CIS Linux benchmark recommends SSH, password, logging, service, and filesystem controls. |
| Internal policy | What does this organization require here? | "Production servers must disable password SSH login and keep audit logs for 180 days." |

Use the framework to organize work, the benchmark to find concrete checks, and
the internal policy to decide what your environment actually requires.

## Common standards you will meet

You do not need to become a compliance specialist to administer Linux systems,
but you should recognize the names that appear in tickets, audits, and customer
requirements.

- **ISO/IEC 27001** defines an information security management system. Operators
  usually encounter it through asset inventory, access review, change control,
  incident handling, backup, and supplier requirements.
- **NIST Cybersecurity Framework** groups work into high-level functions:
  identify, protect, detect, respond, and recover. It is helpful for explaining
  why Linux evidence matters beyond a single command.
- **NIST SP 800-series** publications provide deeper guidance on topics such as
  risk management, contingency planning, logging, identity, and cryptographic
  controls.
- **CIS Benchmarks** provide practical hardening recommendations for specific
  operating systems and services. These are often the most directly useful to a
  Linux administrator.
- **PCI DSS, HIPAA, SOC 2, and FedRAMP** are domain or assurance programs that
  may affect Linux hosts depending on data type, customer promises, or cloud
  environment.

!!! tip "Start from the data"
    Before choosing a standard, ask what the host stores, processes, or can
    reach. A public demo VM, a payment database, and a build runner with
    production deployment keys do not carry the same risk.

## Translating requirements into Linux checks

A requirement becomes useful when you can inspect it consistently. The commands
below are read-only examples you can adapt for an evidence note.

### Asset and software inventory

```bash
hostnamectl
uname -a
cat /etc/os-release
systemctl --type=service --state=running
dpkg -l | head        # Debian and Ubuntu
rpm -qa | head        # RHEL, Fedora, Rocky, AlmaLinux
```

Record the operating system, kernel, running services, and package source before
you claim a host is in scope or out of scope.

### Identity and privileged access

```bash
getent passwd
getent group sudo
getent group wheel
sudo -l
find /etc/sudoers /etc/sudoers.d -maxdepth 1 -type f -print 2>/dev/null
```

Tie the output back to a policy question: who can log in, who can become root,
and how is that access reviewed?

### SSH and remote administration

```bash
ss -tulpn | grep ':22'
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|allowusers|allowgroups)'
```

If your policy says password login is disabled, collect the effective SSH daemon
setting, not just a comment in `/etc/ssh/sshd_config`.

### Logging and audit readiness

```bash
systemctl status systemd-journald --no-pager
journalctl --disk-usage
ls -l /var/log
sudo auditctl -s 2>/dev/null || true
```

Evidence should answer whether logs exist, whether they are retained long
enough, and whether the team knows where to look during an incident.

### Backup and recovery evidence

```bash
find /etc -maxdepth 1 -type f | sort | head
systemctl list-timers --all
mount | grep -E 'backup|snapshot|nfs|smb|object|s3' || true
```

Backups are not compliant because a job exists. They become credible when the
team can show scope, schedule, protected storage, and a recent restore test.

## Using benchmarks safely

Benchmarks are valuable, but applying every recommendation blindly can break a
working system.

1. Read the benchmark item and identify the risk it addresses.
2. Check whether the host role makes the recommendation appropriate.
3. Capture current state before changing anything.
4. Test on a disposable VM or one host from a low-risk pool.
5. Apply the change with a rollback path.
6. Verify the control and the service that depends on it.
7. Record exceptions with an owner, reason, review date, and compensating control.

For example, disabling root SSH login is usually reasonable. Disabling all
password authentication without confirming key access can lock out every
operator. The benchmark is a guide; the change plan is still your responsibility.

## Certifications for Linux security work

Certifications are not a substitute for production judgment, but they can give a
learning path and a shared vocabulary.

- **CompTIA Linux+** is a broad Linux operations certification. It is useful for
  building baseline command-line, permissions, service, networking, and security
  familiarity.
- **Red Hat Certified System Administrator (RHCSA)** focuses on practical Linux
  administration tasks in a Red Hat environment, including users, storage,
  services, networking, and security basics.
- **Red Hat Certified Engineer (RHCE)** builds on administration with automation
  and larger-scale operational work.
- **GIAC Certified UNIX Security Administrator (GCUX)** focuses directly on
  securing and auditing Unix and Linux systems.

Choose certifications based on the work you actually do. A production Linux
operator benefits more from hands-on labs and incident practice than from a wall
of unrelated credentials.

## Evidence note template

Use a short template when a manager, auditor, or incident lead asks whether a
Linux control is in place.

```text
Host:
Date and timezone:
Requirement:
Policy or standard reference:
Command or source checked:
Result:
Exception, if any:
Owner:
Next review date:
```

Good evidence is boring, reproducible, and specific. Avoid vague claims such as
"server is hardened" or "logs are enabled" without the command, output source,
or review date that supports the statement.

## Hands-on practice

Use a disposable Linux VM or lab container.

1. Pick one policy statement, such as "SSH password authentication must be
   disabled on production servers."
2. Run `sudo sshd -T | grep passwordauthentication` and save the result.
3. Identify the file or configuration management source that controls the
   setting.
4. Write a one-paragraph evidence note using the template above.
5. List one situation where this control would need an exception and one
   compensating control that would reduce risk.
