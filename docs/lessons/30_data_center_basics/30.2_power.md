## The power path

A server normally depends on several layers of power equipment:

- Utility or generator power brings electricity into the building.
- Electrical panels and circuits feed the data center, closet, or rack.
- A UPS covers short outages and gives systems time to shut down cleanly.
- PDUs distribute power inside the rack and may report outlet or branch load.
- Server power supplies convert input power into the voltages used by hardware.

Linux administrators do not usually design the electrical system, but they do need to understand the path well enough to ask good questions. If a host loses power during every outage, the root cause might be a missing UPS agent, a bad UPS battery, a single-corded server plugged into the wrong PDU, or a rack load that is too close to the circuit limit.

## Watts, volts, and amps

Power planning often uses this simple relationship:

```text
watts = volts x amps
```

In North America, a common 120 V circuit rated for 20 A has a theoretical maximum of 2,400 W. Operators should not plan to run it at the limit. Local electrical code and site policy normally require headroom, and many teams treat 80 percent load as an upper planning target for continuous use.

Server power supply ratings are maximum capacity ratings, not constant usage. A server with two 800 W power supplies does not necessarily consume 1,600 W. Actual draw depends on CPU load, memory, drives, GPUs, fans, firmware settings, and whether redundant power supplies are sharing load.

Useful questions:

- What circuit, UPS, and PDU feed this rack?
- What is the normal and peak load?
- How much spare capacity remains?
- Which devices are single-corded?
- Are redundant power supplies connected to separate power paths?

## Redundancy and single points of failure

Many rack servers have two power supplies. Redundancy only helps when they are connected correctly. If both cords go to the same PDU, circuit, or UPS, that shared component is still a single point of failure.

A common rack pattern is:

- Power supply A connects to PDU A.
- Power supply B connects to PDU B.
- PDU A and PDU B are fed by separate UPS, circuit, or power paths where the site supports it.

Small environments may not have full A/B power. In that case, document the limitation plainly and make sure the shutdown plan is tested. Honest notes are better than assumed redundancy.

## UPS integration with Linux

A UPS is only useful to Linux if the host or monitoring system can see it and act on it. Common Linux UPS tooling includes Network UPS Tools, often packaged as `nut`, and vendor tools in larger environments.

Read-only checks vary by site, but these are common starting points:

```bash
systemctl status nut-monitor
upsc -l
upsc ups@localhost
journalctl -u nut-monitor -n 50 --no-pager
```

Look for:

- UPS status: online, on battery, low battery, or replace battery.
- Battery charge and estimated runtime.
- Load percentage.
- Last self-test result.
- Whether the Linux host has a shutdown policy when runtime is low.

Do not test UPS behavior by pulling production power without an approved maintenance window. Use vendor self-tests, lab equipment, or a staged maintenance plan.

## Shutdown priorities

When battery runtime is short, every system cannot be equally important. A practical shutdown plan names what stays up longest and what stops first.

Example priority order:

1. Monitoring and network gear stay up as long as possible so operators can see what is happening.
2. Stateless application workers shut down early.
3. Batch jobs and noncritical lab systems shut down early.
4. Databases, file servers, and identity systems receive clean stop procedures.
5. Core network and management systems shut down last if the outage continues.

Write the plan so another operator can execute it under pressure. Include service names, expected stop times, and who is allowed to approve shutdowns.

## Linux-side evidence

Linux cannot tell you everything about the electrical path, but it can help you build an evidence trail:

```bash
hostnamectl
uptime
last -x | head
journalctl -b -1 -p warning..alert --no-pager
systemctl list-units '*nut*' --no-pager
```

Use this evidence to answer:

- Did the host reboot unexpectedly?
- Was the previous shutdown clean?
- Is a UPS agent installed and running?
- Did logs show low battery, lost communication, or forced shutdown?
- Are services configured to recover cleanly after boot?

If smart PDUs or out-of-band management are available, add their readings to the same incident note. Keep Linux logs, PDU load, UPS status, and maintenance records together.

## Power handoff note

For each important rack or host, keep a short note like this:

```text
System or rack:
Business service:
Power feeds:
UPS/PDU:
Normal load:
Peak load:
Battery runtime target:
Linux UPS agent:
Shutdown priority:
Last tested:
Known risks:
Next fix:
```

This note is not busywork. It tells the next operator whether the system can survive a short outage, whether it will shut down cleanly, and where the weak point is.

## Common failure patterns

- A dual-power server has both cords plugged into the same PDU.
- A UPS battery is old, so runtime is much shorter than the dashboard predicts.
- A server room adds hardware over time but no one updates load calculations.
- Linux sees the UPS, but the shutdown policy was never configured.
- Network gear is on a different UPS, so servers stay up but become unreachable.
- A power event causes a filesystem, database, or RAID rebuild issue after boot.

## Hands-on practice

Run these on a disposable VM, lab host, or read-only production session where approved.

1. Check whether the host has UPS-related services:

   ```bash
   systemctl list-units '*nut*' --no-pager
   systemctl list-unit-files '*nut*' --no-pager
   ```

2. Review the previous boot for shutdown or power-loss clues:

   ```bash
   last -x | head -20
   journalctl -b -1 -p warning..alert --no-pager
   ```

3. Pick one imaginary rack and calculate a planning load:

   ```text
   120 V x 20 A = 2,400 W theoretical maximum
   2,400 W x 0.80 = 1,920 W planning target
   ```

4. Draft a power handoff note for one server. Mark unknown fields as `unknown` instead of guessing.
