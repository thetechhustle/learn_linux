# 30.4 Data Center Reliability Tiers

!!! abstract "What you will learn"
    - Explain what data center reliability tiers describe.
    - Connect facility redundancy to Linux service availability.
    - Ask practical tier and maintenance questions before placing workloads.

Reliability tiers are a way to describe how much facility redundancy a data center is designed to provide. They are not a magic guarantee that every application will stay online. A high-tier facility can still host a badly designed service, and a well-run Linux service can still fail if the building loses power, cooling, or network paths.

For Linux operators, the value of tier language is practical: it helps you ask better questions about where systems run, what failures are expected, and whether maintenance should be disruptive.

!!! warning "Use tier claims carefully"
    Some providers use tier-like language loosely in marketing. If uptime matters, ask for the actual design, maintenance model, service commitments, and incident history instead of trusting a label by itself.

## What Tiers Describe

Reliability tiers describe facility capability, especially around:

- Power capacity.
- Backup power.
- Cooling capacity.
- Redundant components.
- Multiple distribution paths.
- Maintainability during planned work.
- Fault tolerance during equipment failure.

They are mostly about the physical site. They do not automatically prove that your Linux hosts, storage, database, DNS, load balancers, application code, backups, or incident process are reliable.

## A Practical Tier Summary

The common four-tier model is often summarized like this:

| Tier | Simple meaning | Operator expectation |
| --- | --- | --- |
| Tier I | Basic capacity | Planned or unplanned work may interrupt service. |
| Tier II | Redundant components | Some components are redundant, but maintenance may still be disruptive. |
| Tier III | Concurrently maintainable | Planned maintenance should be possible without taking the site down. |
| Tier IV | Fault tolerant | The site should tolerate certain equipment failures without service impact. |

This table is simplified. Real designs are more detailed than one row of text.

## Tier I: Basic Capacity

A Tier I-style facility has the basic pieces needed to run IT equipment:

- Dedicated space.
- Power.
- Cooling.
- UPS or similar short-term protection.

This can be fine for labs, test systems, small internal workloads, or services where downtime is acceptable. It is risky for workloads that need strong availability because maintenance or a single equipment failure may cause an outage.

Linux operator question:

```text
If the UPS, cooling unit, or power path needs maintenance, will my host stay online?
```

## Tier II: Redundant Components

A Tier II-style facility adds redundant components, such as extra UPS modules, pumps, chillers, or generators. This reduces some risk, but the distribution path may still be a single point of failure.

Redundant components are helpful, but they are not the same as fully independent paths.

Linux operator question:

```text
Which components are redundant, and which paths are still single points of failure?
```

## Tier III: Concurrent Maintainability

A Tier III-style facility is designed so planned maintenance can happen without shutting down IT equipment. That usually means redundant capacity plus multiple distribution paths, with one active path serving equipment at a time.

This matters during maintenance windows. A site can replace or service major facility components without taking the customer load offline, assuming the work is planned and performed correctly.

Linux operator question:

```text
Can power and cooling maintenance happen while my rack stays online?
```

## Tier IV: Fault Tolerance

A Tier IV-style facility is designed to tolerate certain failures without service interruption. It has more redundancy and distribution independence than lower tiers.

This is expensive and operationally complex. It is normally justified for workloads where downtime is extremely costly.

Linux operator question:

```text
Which single failures can happen without service interruption, and what failures are outside the design?
```

## Facility Tier Is Not Application Availability

A facility tier helps, but Linux service reliability also depends on:

- Host redundancy.
- Storage redundancy.
- Network path redundancy.
- DNS design.
- Load balancing.
- Database replication.
- Backup and restore testing.
- Monitoring and alerting.
- Deployment discipline.
- Incident response.

A single Linux server in a high-tier data center is still one server. If its motherboard fails, the facility tier does not make the application redundant.

## Questions to Ask Providers

Ask specific questions:

```text
What tier or design standard is the facility built to?
Is it certified, self-described, or tier-like marketing language?
Are power paths A and B independent to the rack?
Can planned power maintenance happen without taking the rack offline?
Can planned cooling maintenance happen without taking the room offline?
How many carrier/network paths are available?
What are the remote-hands hours and escalation paths?
What recent facility incidents occurred?
What customer notifications are sent before maintenance?
What SLA applies, and what does it exclude?
```

Specific answers are more useful than a badge.

## Matching Workloads to Facilities

Not every workload needs the highest tier.

Examples:

- Lab systems can run in low-redundancy space.
- Internal tools may tolerate scheduled downtime.
- Customer-facing production systems need stronger design.
- Payment, identity, and critical database systems need extra scrutiny.
- Disaster recovery systems should not share the same failure domain as production.

The goal is not to buy the most expensive option every time. The goal is to match business risk to facility, architecture, and operations.

## Maintenance Windows

Tier claims matter most during maintenance.

For every important system, know:

```text
Can the rack stay online during power maintenance?
Can the rack stay online during cooling maintenance?
Will network maintenance affect one path or all paths?
How much notice is required?
Who approves maintenance risk?
How do we verify the service after maintenance?
```

For Linux services, prepare maintenance evidence:

```bash
date -Is
hostnamectl
uptime
systemctl --failed
ss -tulpen
```

These commands do not prove facility health, but they help confirm host and service state before and after a facility event.

## Failure Domains

A failure domain is the area affected when something fails.

Examples:

- One power supply.
- One server.
- One rack.
- One network switch.
- One row.
- One room.
- One building.
- One region.

Good architecture avoids putting every dependency in the same failure domain. If the web server, database, backups, and monitoring all depend on one rack, that rack is the real availability boundary.

## Common Mistakes

Avoid these:

- Treating a tier label as a complete reliability plan.
- Assuming a high-tier facility fixes single-server architecture.
- Placing primary and backup systems in the same failure domain.
- Ignoring maintenance notifications because "the data center is redundant."
- Confusing provider SLA credits with actual business continuity.
- Forgetting that network, storage, and DNS have their own failure modes.
- Asking only "what tier is it?" instead of asking how maintenance and failures behave.

## Hands-on Practice

Use a lab service, hosted VM, or hypothetical application.

1. Identify the system's largest failure domain.
2. Write down what happens if one host fails.
3. Write down what happens if one rack or availability zone fails.
4. Draft five provider questions about power, cooling, network paths, maintenance, and SLA exclusions.
5. Decide whether the workload needs better facility design, better application architecture, or both.
