## 30.6 Tools

Data center work uses two kinds of tools: physical tools in the room and software
tools that let you collect evidence from Linux, network gear, power systems, and
out-of-band management interfaces. A good operator knows which tool answers which
question, and when a tool is too risky for the situation.

!!! abstract "What you will learn"
    - Choose practical tools for Linux, hardware, network, power, and facility checks.
    - Use read-only commands first so you can build evidence before changing anything.
    - Prepare precise handoffs for remote hands, facilities teams, and hardware vendors.

!!! success "Operator principle"
    Tools do not replace judgment. Start with low-risk evidence, preserve context, and
    make changes only when you know what you are trying to prove.

## Keep a Tiered Toolbelt

Do not treat every data center problem as an SSH problem. A server can be healthy
from the operating system's point of view and still have a bad cable, overloaded
power path, blocked intake, failing fan, or mislabeled rack position.

Useful tool categories include:

- **Access tools:** SSH, serial console, KVM crash cart, VPN, bastion hosts, and
  out-of-band management such as IPMI, iDRAC, iLO, or Redfish.
- **Linux inspection tools:** `hostnamectl`, `uptime`, `dmesg`, `journalctl`,
  `systemctl`, `lsblk`, `lspci`, `ip`, `ss`, `ethtool`, `sensors`, and `smartctl`.
- **Network tools:** `ping`, `traceroute` or `tracepath`, `mtr`, `dig`, `tcpdump`,
  switch port status, LLDP/CDP neighbors, and cable testers.
- **Power and environment tools:** rack PDUs, UPS management, BMC sensor readings,
  temperature probes, airflow checks, and facility monitoring dashboards.
- **Documentation tools:** asset inventory, rack elevations, port maps, label
  standards, runbooks, ticket history, and incident timelines.

## Start with Read-Only Evidence

When a server is unhealthy, collect a short snapshot before changing it. This gives
you a baseline and helps the next person understand what was true at the time.

```bash
hostnamectl
uptime
systemctl --failed
journalctl -p warning..alert -n 50 --no-pager
ip -brief address
ss -tulpen
lsblk
```

For hardware clues, add commands appropriate to the host:

```bash
sensors
sudo smartctl -a /dev/sda
sudo ethtool eth0
sudo dmidecode -t system
```

!!! warning "Production caution"
    Some inspection tools still need care. `tcpdump` can capture sensitive data,
    `smartctl -t long` can add disk load, and vendor utilities may expose serial
    numbers or service tags. Capture only what the incident requires and avoid
    pasting secrets into tickets.

## Use Out-of-Band Management Deliberately

Out-of-band management is often the difference between a quick recovery and a long
remote-hands visit. It lets you view power state, sensor readings, boot messages,
virtual media, and sometimes a remote console even when the OS is down.

Common safe checks include:

```bash
ipmitool -I lanplus -H bmc-hostname -U operator chassis status
ipmitool -I lanplus -H bmc-hostname -U operator sensor list
ipmitool -I lanplus -H bmc-hostname -U operator sel list
```

Use power actions only with explicit authorization:

```bash
ipmitool -I lanplus -H bmc-hostname -U operator chassis power status
# Confirm impact before using: chassis power cycle
```

Record the BMC address, rack location, asset tag, current power state, and any
sensor alarms before asking someone else to touch the machine.

## Match the Tool to the Failure

| Symptom | First tools | What you are looking for |
| --- | --- | --- |
| Host unreachable | `ping`, `mtr`, switch port status, BMC console | Network path failure, link down, host powered off |
| Slow service | `uptime`, `top`, `journalctl`, `ss`, monitoring dashboard | CPU, memory, disk, network, or application pressure |
| Disk errors | `dmesg`, `lsblk`, `smartctl`, RAID controller tools | I/O errors, degraded arrays, failing media |
| Overheating | BMC sensors, `sensors`, rack temperature, visual airflow check | Fan failures, blocked vents, hot aisle leakage |
| Unexpected reboot | `last -x`, `journalctl -b -1`, BMC event log, PDU/UPS logs | Kernel panic, power loss, thermal shutdown |
| Wrong cable or port | LLDP/CDP, switch MAC table, labels, port map | Mismatched documentation or accidental recabling |

## Physical Tools Still Matter

Software cannot solve every data center problem. Keep the physical kit simple,
labeled, and controlled:

- label maker and spare labels
- flashlight or headlamp
- antistatic strap when handling components
- known-good Ethernet and power cables
- cage nuts, screws, Velcro ties, and blanking panels
- laptop with serial adapter, console cable, and tested terminal settings
- cable tester or light meter when the network team expects it

Do not improvise around power, weight, or ladder safety. If the work involves heavy
equipment, live electrical changes, fire suppression systems, or facility policy,
bring in the right team.

## Remote-Hands Request Template

Precise requests prevent accidental outages. A good remote-hands ticket includes:

```text
Site: DC2
Rack/U: Row B, rack 14, U18
Asset tag / hostname: web-42 / web-42.example.net
Current evidence: host unreachable by SSH, BMC reachable, chassis power is on
Requested action: verify link light on NIC 1 and switch patch panel port B14-18A
Do not: power cycle, move both power feeds, or reseat disks
Success signal: send photo of front label, rear cabling, and NIC link light
Contact: on-call engineer and bridge number
```

Use "do not" lines when a wrong but plausible action would be harmful.

## Hands-on Practice

Run these in a lab VM or disposable server. Do not run production hardware commands
unless you are authorized to inspect that host.

1. Build a read-only host snapshot with `hostnamectl`, `uptime`, `systemctl --failed`,
   `journalctl -p warning..alert -n 20 --no-pager`, `ip -brief address`, and `lsblk`.
2. Identify which command would help with a disk issue, a network issue, and a
   thermal issue. Write one sentence for each.
3. Draft a remote-hands request for a server that is powered on but unreachable by
   SSH.
4. Review the request and add one "do not" instruction that would prevent a risky
   misunderstanding.
