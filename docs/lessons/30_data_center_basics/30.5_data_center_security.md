## 30.5 Data Center Security

!!! abstract "What you will learn"
    - Explain how physical data center security supports Linux system security.
    - Identify common facility, rack, network, and management-plane controls.
    - Collect safe security evidence without bypassing access rules.

Data center security is not only firewalls and passwords. A Linux server is a physical object with disks, network ports, power cables, management interfaces, and people who can touch it. If an attacker can enter the room, remove a drive, connect to a management port, or impersonate remote hands, the operating system is only one layer of defense.

Linux operators need to understand both sides: the physical controls that protect the hardware and the logical controls that protect the systems running on that hardware.

!!! warning "Do not bypass security controls"
    Never tailgate into secure areas, borrow badges, share access codes, plug unknown devices into data center networks, or ask remote hands to work around identity checks. Security shortcuts create real incidents.

## Security Layers

Data center security usually combines several layers:

- Perimeter controls around the building or room.
- Visitor and badge management.
- Cameras and access logs.
- Locked cages, cabinets, or racks.
- Asset labels and inventory.
- Network segmentation.
- Management-network protection.
- Remote-hands identity verification.
- Change-management records.
- Monitoring and incident response.

The best designs assume that one layer can fail. A locked room helps, but so does encrypted storage, limited management access, and accurate inventory.

## Physical Access Controls

Common physical controls include:

- Badge readers.
- Biometric readers.
- Security desks.
- Visitor sign-in.
- Mantraps or controlled entry vestibules.
- Locked cages.
- Locked rack doors.
- Camera coverage.
- Access logs.

The Linux operator does not need to own these systems, but should know how access is requested, approved, logged, and reviewed.

Useful questions:

```text
Who can enter the room?
Who can open this rack?
How is emergency access handled?
How long are badge and camera logs retained?
Who reviews access logs after an incident?
```

## Rack-Level Security

Rack security matters because many incidents start with small physical changes:

- A cable is moved.
- A console is attached.
- A drive is removed.
- A server is power-cycled.
- A management port is connected to the wrong network.
- A label is missing or misleading.

For important racks, record:

```text
Rack:
Location:
Owner:
Lock type:
Who may open it:
Remote-hands procedure:
Camera coverage:
Inventory source:
Last physical audit:
```

Good labels help security too. If a remote-hands technician can confidently identify the right host, they are less likely to touch the wrong system.

## Management Interfaces

Out-of-band management systems such as iDRAC, iLO, IPMI, Redfish, and KVM consoles are powerful. They may allow power control, virtual media, firmware changes, console access, and hardware logs.

Protect them as privileged infrastructure:

- Put management interfaces on a dedicated management network.
- Restrict access with VPN, bastion hosts, or jump boxes.
- Use strong authentication.
- Disable default credentials.
- Log management actions.
- Patch management firmware.
- Avoid exposing management ports to the public internet.

Linux operators should treat management access like root access to the hardware.

## Linux-Side Checks

Linux can help identify security-relevant state, but it cannot prove physical security by itself.

Useful read-only checks:

```bash
hostnamectl
ip addr show
ss -tulpen
last -a | head
lastlog | head
journalctl -p warning..alert --since "24 hours ago" --no-pager
```

For SSH-focused evidence:

```bash
grep -Ei 'accepted|failed|invalid user|session opened|session closed' /var/log/auth.log 2>/dev/null | tail -n 50
journalctl -u ssh -u sshd --since "24 hours ago" --no-pager
```

Different distributions log authentication in different places. If a command returns nothing, record that and check the distro's logging path.

## Network Segmentation

Data centers often separate traffic into different networks:

- Public or internet-facing traffic.
- Private application traffic.
- Storage traffic.
- Backup traffic.
- Management traffic.
- Monitoring traffic.

Segmentation limits blast radius. A web server compromise should not automatically grant access to storage controllers, management interfaces, or backup systems.

Linux evidence can include:

```bash
ip route
ip addr show
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

These commands show host-side network configuration. They do not replace firewall, switch, cloud security group, or data center network policy review.

## Remote Hands Security

Remote hands are people who physically inspect or change equipment for you. Their work should be precise and auditable.

A good request includes:

```text
Requester:
Approval/change ticket:
Device hostname:
Serial/service tag:
Rack and rack unit:
Expected label:
Allowed action:
Forbidden actions:
Reason:
Callback or completion channel:
```

Example:

```text
Please inspect host app-04 only.
Change ticket: CHG-2026-0514-01
Rack: R07
Position: U22
Serial: ABC1234
Allowed action: confirm front label, power LEDs, and cable labels.
Forbidden actions: do not open chassis, attach console, move cables, insert USB media, or power-cycle.
Reason: verify physical identity before scheduled maintenance.
```

If someone asks remote hands to bypass identity checks, stop and escalate.

## Storage and Media Security

Disks are often the most sensitive physical asset in a server.

Important controls include:

- Full-disk encryption where appropriate.
- Secure drive disposal.
- Chain of custody for removed media.
- Drive serial tracking.
- Clear replacement procedures.
- Backup encryption.
- Restore testing.

If a drive is removed, record:

```text
Host:
Drive bay:
Drive serial:
Reason for removal:
Person handling:
Destination:
Encryption status:
Ticket/change ID:
```

Do not treat a failed disk as harmless. It may still contain readable data.

## Monitoring and Audit Trails

Useful audit sources include:

- Badge logs.
- Camera footage.
- Rack access logs.
- Remote-hands tickets.
- Change-management tickets.
- Out-of-band management logs.
- Switch port logs.
- Linux authentication logs.
- Linux service logs.

During an incident, align times across sources. Use UTC where possible and preserve original timestamps.

## Common Mistakes

Avoid these:

- Assuming cybersecurity controls compensate for weak physical access.
- Leaving management interfaces on reachable production networks.
- Keeping default passwords on out-of-band devices.
- Letting remote-hands requests say only "reboot the server" without identity details.
- Treating lost or removed disks as ordinary trash.
- Forgetting to remove access for departed staff or vendors.
- Ignoring physical access logs during a suspected host compromise.
- Plugging unknown crash carts, USB drives, or network cables into production equipment.

## Hands-on Practice

Use a lab host, a home-lab machine, or a hypothetical rack record.

1. Write a rack-level security record for one host.
2. Run `ss -tulpen` and identify which listeners should be reachable.
3. Check recent authentication logs using the commands above.
4. Draft a remote-hands request that allows inspection only.
5. Write down how a removed drive should be tracked from removal through disposal.
