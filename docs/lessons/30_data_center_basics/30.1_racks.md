## 30.1 Racks

!!! abstract "What you will learn"
    - Explain how rack units, rack positions, and labels are used to locate equipment.
    - Understand why rack layout affects power, cooling, cabling, and incident response.
    - Build a basic rack record that helps Linux operators coordinate safely with hardware teams.

A rack is the physical frame that holds servers, switches, storage shelves, patch panels, power distribution units, and cable-management hardware. Linux operators often work remotely, but the server still has a physical location. When something needs to be replaced, cabled, rebooted, inspected, or moved, rack information becomes operationally important.

Rack awareness is not trivia. It prevents mistakes.

!!! warning "Exact location matters"
    "The server in rack 3" is not enough for remote hands work. Use rack name, rack unit, hostname, serial or service tag, and the requested action.

## Rack Units

Rack space is measured in rack units, usually written as `U` or `RU`. One rack unit is 1.75 inches of vertical space.

Common examples:

- `1U`: thin server or network appliance.
- `2U`: larger server with more disks or expansion space.
- `4U`: storage-heavy server or chassis.
- `42U`: common full-height rack size.

A server mounted from U12 to U13 is not the same thing as a server mounted at U31. Exact position helps people find the right hardware quickly and safely.

## What Goes in a Rack

A rack may contain:

- Servers.
- Top-of-rack switches.
- Storage shelves.
- Patch panels.
- Keyboard/video/console equipment.
- Power distribution units, often called PDUs.
- Cable managers.
- Blanking panels.

Not every rack is arranged the same way. Some sites put switches at the top. Some put network patching in separate racks. Some reserve space for airflow management. Follow the local standard when one exists.

## Why Racks Matter to Linux Work

You may need rack information when:

- A host is down and remote hands must inspect it.
- A NIC link is down and a switch port or cable path must be checked.
- A disk or power supply has failed.
- A server is overheating.
- A rack has lost one power feed.
- A hardware asset record does not match reality.
- You are planning maintenance and need to avoid touching the wrong host.

From the Linux side, you can often identify a host:

```bash
hostnamectl
ip -brief address
sudo dmidecode -s system-serial-number
```

`dmidecode` may require root privileges and may not be available in virtual machines or containers. Use it only when appropriate for the system you are operating.

## Rack Records

Keep a simple rack record for physical hosts:

```text
Hostname:
Serial/service tag:
Rack:
Rack unit:
Front label:
Power feed A:
Power feed B:
Network switch/port:
Out-of-band management:
Owner/team:
Critical service:
Last verified:
```

This record should live somewhere the team trusts, such as an asset database, ticketing system, runbook, or source-controlled inventory. A stale rack record is dangerous because it can send someone to the wrong machine.

## Labels

Labels should be readable, consistent, and tied to inventory.

Useful labels include:

- Hostname.
- Asset tag.
- Serial or service tag.
- Rack and unit position.
- Network port label.
- Power path label.

Avoid labels that only one person understands. A useful label helps a tired operator at 2 AM identify the correct device without guessing.

## Rack Layout and Airflow

Rack layout affects cooling. Most data centers use some version of front-to-back airflow, with cold air entering the front of servers and hot air leaving the back.

Good rack hygiene includes:

- Mounting equipment in the intended direction.
- Keeping front and rear airflow paths clear.
- Using blanking panels for empty spaces when the site standard requires them.
- Keeping cables from blocking fans.
- Avoiding piles of unused cabling in airflow paths.

If several servers in the same rack report high temperatures, treat it as a rack or facility signal, not just a Linux tuning problem.

## Rack Layout and Power

Many servers have two power supplies. The point is redundancy, but redundancy only works if the power supplies use independent paths.

Bad pattern:

```text
Server PSU 1 -> PDU A -> Circuit 1
Server PSU 2 -> PDU A -> Circuit 1
```

Better pattern:

```text
Server PSU 1 -> PDU A -> Circuit 1
Server PSU 2 -> PDU B -> Circuit 2
```

Rack records should show both power feeds. During a power incident, this helps you understand whether a server lost one path or all paths.

## Rack Layout and Network Cabling

Network cabling must be traceable. If a server loses network connectivity, you may need to know:

- Which NIC is connected.
- Which switch port it uses.
- Whether the cable passes through a patch panel.
- Whether the switch is top-of-rack, end-of-row, or elsewhere.
- Whether the out-of-band management port uses a separate network.

Useful Linux checks:

```bash
ip -brief link
ethtool eth0
```

Replace `eth0` with the interface you are checking. `ethtool` may not be installed by default and may require elevated privileges for some details.

## Remote Hands Requests

When someone else will touch hardware, write a precise request:

```text
Please inspect host db-03.
Rack: R12
Position: U18-U19
Serial: ABC1234
Expected front label: db-03
Requested action: confirm both power supplies show green LEDs; do not reboot.
Reason: host is reachable but reports PSU warning in out-of-band management.
```

Notice the request says what not to do. That matters. A physical inspection is different from a reboot, cable pull, disk replacement, or power-cycle.

## Common Rack Mistakes

Avoid these:

- Updating Linux inventory but not rack inventory.
- Relying on memory instead of labels.
- Asking for physical work without serial or rack-unit details.
- Treating redundant power supplies as redundant when they share one circuit.
- Blocking airflow with unmanaged cables.
- Moving servers without updating switch-port and power records.
- Forgetting out-of-band management cabling.
