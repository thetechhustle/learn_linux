## Modern Access Control

Modern Linux access control adds policy checks around the Unix permissions and
ACLs you already inspected earlier in this chapter. The important operational
shift is that `ls -l` can say a file is writable while SELinux or AppArmor still
blocks a process from writing it. Treat those systems as an additional evidence
layer, not as a replacement for ownership, mode bits, groups, or ACLs.

!!! abstract "What you will learn"
    - Explain the difference between discretionary access control and mandatory access control.
    - Collect read-only evidence for SELinux and AppArmor state.
    - Recognize when a denial is caused by policy rather than Unix mode bits.
    - Make temporary, reversible policy changes only in an approved lab or maintenance window.

!!! example "Field story"
    A web application deploys cleanly, the files are owned by the right user, and
    the service still cannot read its content directory. Before changing file
    modes or running the service as root, you need to check whether a mandatory
    access control policy is denying the access.

!!! success "Operator principle"
    Prove the active policy layer before loosening permissions. A quick `chmod`
    rarely fixes an SELinux or AppArmor denial and often creates a second
    security problem.

## The Access Control Stack

Linux usually evaluates more than one access control layer:

1. **Discretionary access control:** owner, group, mode bits, and POSIX ACLs.
2. **Process identity:** the user and groups under which the process runs.
3. **Mandatory access control:** SELinux labels or AppArmor profiles that limit
   what a process may do even when Unix permissions allow it.
4. **Service sandboxing:** systemd options, containers, mount namespaces, and
   seccomp rules that may add more restrictions.

When troubleshooting, move from the simplest evidence to the most specific
policy layer. Do not skip the basics:

```bash
id
namei -l /srv/www/example/index.html
getfacl /srv/www/example/index.html
ps -o user,group,comm -C nginx
```

Those commands answer whether the traditional permission model explains the
problem. If they do not, inspect the mandatory access control layer.

## SELinux Evidence

SELinux is common on Fedora, RHEL, CentOS Stream, Rocky Linux, AlmaLinux, and
other RHEL-family systems. Its core idea is labels: files, processes, ports, and
other objects have security contexts, and policy decides which labeled processes
may access which labeled objects.

Start with read-only inspection:

```bash
sestatus
getenforce
ls -Zd /srv/www/example
ps -eZ | grep -E 'nginx|httpd|apache'
```

Interpret the common modes carefully:

- `Enforcing` means SELinux policy is active and denials are blocked.
- `Permissive` means denials are logged but not blocked.
- `Disabled` means SELinux is not active for the running system.

Look for denials in the audit log or journal:

```bash
sudo ausearch -m avc,user_avc -ts recent
sudo journalctl -t setroubleshoot --since "30 minutes ago"
```

If `ausearch` is unavailable, the system may not have `auditd` tooling installed.
Use the journal and distribution documentation rather than guessing.

### SELinux Safety Boundaries

Avoid using SELinux mode changes as a first response:

```bash
sudo setenforce 0
```

That command switches SELinux from enforcing to permissive until the next boot.
It can help prove that SELinux is involved, but it also reduces protection for
the whole host. Use it only in a lab, a disposable VM, or an approved
maintenance window with a rollback note.

Prefer narrow, reversible evidence and fixes:

```bash
# Inspect a directory label.
ls -Zd /srv/www/example

# Restore default labels when the packaged policy already knows the path.
sudo restorecon -Rv /srv/www/example

# Review custom local label rules before adding more.
sudo semanage fcontext -l | grep '/srv/www'
```

Do not paste random `audit2allow` output into production policy. Generated policy
may permit exactly what an attacker or broken application attempted. Read the
denial, understand the service boundary, and make the smallest approved policy
change.

## AppArmor Evidence

AppArmor is common on Ubuntu, Debian, SUSE, and some container-focused systems.
It uses named profiles that describe what a program may access, usually by path.

Start with status and profile evidence:

```bash
sudo apparmor_status
ps auxZ 2>/dev/null | head
ls /etc/apparmor.d/
```

Common AppArmor modes are:

- `enforce`: policy is active and blocks denied actions.
- `complain`: denials are logged but not blocked.
- `unconfined`: no AppArmor profile confines that process.

Look for denials in the kernel log or journal:

```bash
sudo journalctl -k --since "30 minutes ago" | grep -i apparmor
sudo dmesg | grep -i apparmor
```

### AppArmor Safety Boundaries

Profile mode changes are narrower than disabling the whole framework, but they
still change security behavior. Make the target explicit:

```bash
# Put one profile into complain mode while testing.
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx

# Return the profile to enforcing mode.
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx
```

Before changing a profile on a shared system, record the profile name, affected
service, reason for the change, and rollback command. If the service is
internet-facing, prefer a lab reproduction before changing production policy.

## Troubleshooting Pattern

Use this sequence when a service reports `Permission denied` but the Unix mode
bits look correct:

1. Confirm the process identity with `ps`, `systemctl status`, or service logs.
2. Inspect the path one component at a time with `namei -l`.
3. Check ACLs with `getfacl`.
4. Identify the mandatory access control framework with `sestatus`,
   `getenforce`, or `apparmor_status`.
5. Search recent denials in the audit log, kernel log, or journal.
6. Test the narrowest reversible change in a lab or maintenance window.
7. Document what changed and how to roll it back.

## Hands-On Practice

Run this lab on a disposable VM. Use a distribution that ships either SELinux or
AppArmor by default.

1. Identify the active access control framework:

   ```bash
   command -v sestatus && sestatus
   command -v apparmor_status && sudo apparmor_status
   ```

2. Choose one confined service, such as `nginx`, `httpd`, or `sshd`, and collect
   read-only evidence:

   ```bash
   systemctl status nginx --no-pager
   ps -eo user,group,label,comm 2>/dev/null | grep nginx || true
   journalctl -u nginx --since "30 minutes ago" --no-pager
   ```

3. Record the service account, policy mode, profile or label evidence, and one
   rollback command you would use if a policy test went wrong.
4. In the lab only, put the selected profile or framework into a non-blocking
   mode, confirm the new mode, then immediately restore enforcement.
5. Write a three-line incident handoff that says what was denied, what evidence
   proved the policy layer was involved, and what permanent fix still needs
   review.
