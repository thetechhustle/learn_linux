## 03.2 Management of the Root Account

!!! abstract "What you will learn"
    - Explain why routine administration should use delegated privilege instead of direct root sessions.
    - Inspect root-login, sudo, and group-based administrative access without changing the system.
    - Grant, verify, and remove temporary administrative access safely in a lab.

!!! example "Field story"
    A contractor needs temporary access to troubleshoot a service on a shared server. Giving them the root password would solve the immediate problem and create a larger one. Your job is to identify the smallest useful privilege, apply it safely, verify it from the contractor's account, and remove it when the work is done.

!!! success "Operator principle"
    Treat root as a break-glass account. Prefer named users, scoped `sudo`, clear evidence, and a rollback path.

## Hands-on practice

Run these on a disposable VM, container, or lab machine. Do not experiment with root, SSH, or sudo policy on a production host without console access and a recovery plan.

1. Identify your current user and groups:

    ```sh
    id
    groups
    ```

2. Inspect the root account entry:

    ```sh
    getent passwd root
    sudo -l
    ```

    `getent passwd root` shows the root account metadata. `sudo -l` shows what your current user is allowed to run through sudo.

3. Check whether SSH root login is explicitly configured:

    ```sh
    sudo sshd -T | grep -i '^permitrootlogin'
    ```

    On many systems, direct root SSH login should be disabled. Use named accounts and sudo so actions can be audited.

4. Inspect sudo policy safely:

    ```sh
    sudo visudo -c
    sudo ls -l /etc/sudoers /etc/sudoers.d
    ```

    `visudo -c` validates sudoers syntax without opening an editor.

5. In a disposable lab, create and remove a temporary access grant:

    ```sh
    sudo useradd -m contractor-lab
    sudo usermod -aG sudo contractor-lab
    sudo -l -U contractor-lab
    sudo gpasswd -d contractor-lab sudo
    sudo userdel -r contractor-lab
    ```

    Some distributions use the `wheel` group instead of `sudo`. Check your distribution's policy before changing groups.

6. Write a short access handoff:

    ```text
    User:
    Business reason:
    Granted capability:
    Verification command:
    Expiration/removal plan:
    Rollback command:
    ```

## Root, su, and sudo

The root account has unrestricted administrative power. It can change ownership, override permissions, install software, alter services, replace kernels, and delete critical files. That power is necessary for system administration, but routine root sessions make mistakes harder to attribute and easier to amplify.

Use these tools deliberately:

- `su` starts a shell as another user, commonly root, if you know that user's password.
- `sudo` runs a specific command with elevated privileges according to policy.
- `sudo -l` shows the current user's allowed commands.
- `sudo -u <user> <command>` runs a command as another user.
- `sudo -i` starts a root login-style shell and should be treated as a high-risk session.

Prefer `sudo <specific-command>` over a long-lived root shell. A single elevated command is easier to reason about, log, and review.

## Safer sudo policy changes

Never hand-edit sudo policy casually. A syntax error can lock administrators out.

Use this pattern:

1. Validate current policy:

    ```sh
    sudo visudo -c
    ```

2. Put local policy in a dedicated file under `/etc/sudoers.d/` rather than editing the main file when possible.
3. Use `visudo` to edit the file:

    ```sh
    sudo visudo -f /etc/sudoers.d/contractor-lab
    ```

4. Validate again:

    ```sh
    sudo visudo -c
    ```

5. Verify from the user's point of view:

    ```sh
    sudo -l -U contractor-lab
    ```

6. Record how to remove the grant.

## Least-privilege examples

A broad grant:

```text
contractor-lab ALL=(ALL) ALL
```

This lets the user run any command as root. It may be appropriate for a trusted administrator, but it is too broad for most temporary work.

A narrower grant:

```text
contractor-lab ALL=(root) /usr/bin/systemctl status nginx, /usr/bin/journalctl -u nginx
```

This allows specific inspection commands for a specific service. It is easier to justify, review, and remove.

Exact paths and arguments matter. Test the command the same way the user will run it, because sudoers argument matching is strict and distribution paths vary.

## Operational guardrails

- Do not share the root password.
- Do not enable remote root SSH login for convenience.
- Do not leave temporary sudo grants without an expiration or owner.
- Keep a second admin session open while testing sudo policy on a remote machine.
- Prefer group membership for standard admin roles and sudoers files for scoped exceptions.
- Verify access from the user's point of view before declaring the request complete.
- Remove access when the business reason ends.
