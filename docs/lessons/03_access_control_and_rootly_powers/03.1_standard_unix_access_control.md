# Understanding File Ownership and Permissions

Unix permissions answer three operational questions:

- Who owns this file or directory?
- Which group is associated with it?
- What can the owner, group, and everyone else do with it?

Administrators use those answers constantly. A service might fail because it cannot
read its configuration file. A deployment might leave a script non-executable. A
shared directory might let one user overwrite another user's work. Standard Unix
access control is the first evidence layer to inspect before reaching for more
advanced tools such as ACLs, SELinux, or AppArmor.

!!! abstract "What you will learn"
    - Read `ls -l` output and explain owner, group, and mode bits.
    - Distinguish file permissions from directory permissions.
    - Change permissions with `chmod` and ownership with `chown` in a reversible lab.
    - Avoid unsafe broad permissions such as `777` on shared or production paths.

!!! success "Operator principle"
    Grant the smallest useful access, then verify it as the user or service that
    needs the access.

## Read the Evidence First

Start with read-only inspection:

```bash
pwd
id
ls -ld .
ls -l important.conf deploy.sh shared/
stat important.conf
```

A long listing looks like this:

```text
-rw-r----- 1 app app 128 May 10 09:00 important.conf
drwxrws--- 2 app deploy 96 May 10 09:05 shared
```

Read the first column from left to right:

- The first character is the file type: `-` for a regular file, `d` for a directory,
  `l` for a symbolic link.
- The next three characters are the owner's permissions.
- The next three are the group's permissions.
- The last three are permissions for everyone else.

The owner and group follow the link count. In the examples above, `important.conf`
is owned by user `app` and group `app`; `shared` is owned by user `app` and group
`deploy`.

## Permission Bits

The basic permissions are:

| Bit | File meaning | Directory meaning |
| --- | --- | --- |
| `r` | Read file contents | List names in the directory |
| `w` | Modify file contents | Create, rename, or delete entries in the directory |
| `x` | Execute the file as a program or script | Traverse the directory path |

Directory execute permission is easy to underestimate. A user can have read
permission on a file and still fail to open it if they cannot traverse one of the
parent directories.

Numeric modes add the bit values together:

- `r` is `4`.
- `w` is `2`.
- `x` is `1`.

Common modes:

- `600`: owner can read and write; no one else has access.
- `640`: owner can read and write; group can read.
- `644`: owner can read and write; everyone can read.
- `750`: owner has full access; group can read and traverse/execute; others have no access.
- `755`: owner has full access; everyone can read and traverse/execute.

Treat `777` as a lab-only smell. It gives every local user read, write, and execute
access. On directories, it lets every local user create and delete entries unless
additional controls such as the sticky bit are present.

## Change Permissions Safely

Prefer symbolic changes when you are making a narrow adjustment. The `chmod`
manual is the authoritative reference for mode syntax and edge cases.[^chmod]

```bash
chmod u+x deploy.sh
chmod g+r important.conf
chmod o-r private-notes.txt
```

Use numeric modes when you want to set the entire mode deliberately:

```bash
chmod 640 important.conf
chmod 750 shared
```

After a change, inspect again:

```bash
ls -l important.conf deploy.sh
stat important.conf
```

If the access is for a service or another user, verify from that identity when
possible:

```bash
sudo -u app test -r important.conf
sudo -u app test -x deploy.sh
```

`test` exits quietly. Check `$?` or combine it with a message:

```bash
sudo -u app test -r important.conf && echo "app can read"
```

## Change Ownership Deliberately

Ownership changes usually require elevated privileges. The `chown` manual covers
owner and group syntax, including recursive changes.[^chown]

```bash
sudo chown app:app important.conf
sudo chown -R app:deploy shared/
```

Be careful with recursive ownership changes. Before using `-R`, confirm the target
path and preview what is underneath it:

```bash
pwd
ls -ld shared/
find shared/ -maxdepth 2 -ls
```

Avoid broad commands from high-level directories. A mistaken recursive `chown` or
`chmod` under `/`, `/etc`, `/var`, or a mounted data volume can break services or
expose private data quickly.

## Lab: Repair a Shared Deployment Directory

Run this in a disposable VM, container, or temporary directory:

```bash
mkdir -p ~/acl-lab/shared
cd ~/acl-lab
printf '#!/bin/sh\necho deployed\n' > deploy.sh
printf 'token = replace-me\n' > important.conf
chmod 644 deploy.sh important.conf
chmod 755 shared
ls -l
```

Scenario: members of the `deploy` group should be able to enter `shared`, list
its contents, and create files there. Everyone else should have no access. The
deployment script should be executable by its owner, but the config file should
not be world-readable.

Make the smallest changes that satisfy the scenario:

```bash
chmod u+x deploy.sh
chmod 640 important.conf
chmod 770 shared
```

If a real `deploy` group exists in your lab, you can also test group ownership:

```bash
sudo chown :"deploy" shared
chmod 2770 shared
ls -ld shared
```

The leading `2` sets the setgid bit on the directory. New files created inside
the directory inherit the directory's group, which is useful for team-owned paths.
If your lab does not have a `deploy` group, skip the `chown` command and record
what you would ask a teammate to create.
