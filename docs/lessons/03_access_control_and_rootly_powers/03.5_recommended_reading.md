### 03.5 Recommended Reading

Access control is not a topic you finish once. Good operators keep a small set
of primary references close, then use them to answer specific questions during
changes, audits, and incidents.

!!! abstract "What you will learn"
    - Build a reliable reading path for Linux permissions, ACLs, privilege
      escalation, SSH access, and mandatory access control.
    - Prefer primary references before blog posts or copied command fragments.
    - Turn reading into evidence: command output, config paths, and rollback
      notes.

!!! success "Operator principle"
    Read the source that owns the behavior before changing the system that
    depends on it.

## Start with local manual pages

The manual pages on the host are usually the best first reference because they
match the installed tools and distribution packaging.

- `man chmod`: symbolic and numeric modes, special bits, recursive changes.
- `man chown` and `man chgrp`: ownership changes and group handoffs.
- `man stat`: exact mode, owner, group, inode, and timestamp evidence.
- `man getfacl` and `man setfacl`: POSIX ACL inspection and changes.
- `man sudo`, `man sudoers`, and `man visudo`: privilege policy, validation,
  includes, and rule order.
- `man sshd_config`: SSH server access controls such as `PermitRootLogin`,
  `AllowUsers`, `AllowGroups`, and authorized-key behavior.

On systems with mandatory access control enabled, add the platform-specific
tools:

- SELinux systems: `man getenforce`, `man sestatus`, `man semanage`, and
  distribution SELinux documentation.
- AppArmor systems: `man aa-status`, `man aa-enforce`, `man aa-complain`, and
  distribution AppArmor documentation.

## Use distribution documentation

Distribution docs matter because access-control behavior is partly policy,
packaging, and default configuration.

- Debian and Ubuntu Server documentation for users, groups, `sudo`, SSH, and
  AppArmor defaults.
- Red Hat Enterprise Linux documentation for user management, `sudo`, SELinux,
  and audit workflows.
- Arch Wiki pages for file permissions, attributes, ACLs, `sudo`, and OpenSSH.
  Treat the Arch Wiki as a strong operational reference, then verify details
  against your distribution before applying changes.
- The `sudoers(5)` manual page for rule grammar, tags, aliases, include
  ordering, and validation expectations.

## Keep a few broader references

Books and benchmark documents are useful when you need the bigger model behind
the commands.

- *UNIX and Linux System Administration Handbook* by Evi Nemeth, Garth Snyder,
  Trent Hein, Ben Whaley, and Dan Mackin: practical administration patterns and
  security tradeoffs.
- *How Linux Works* by Brian Ward: strong background for how users, processes,
  filesystems, and services fit together.
- *The Linux Command Line* by William Shotts: good practice for command-line
  fluency when you are still building muscle memory.
- CIS Benchmarks for Linux distributions: policy-oriented hardening guidance.
  Use them as a baseline conversation, not as a substitute for understanding the
  service you are responsible for.
- Vendor security guides for your distribution or cloud image: the place to
  check supported hardening choices and default expectations.

## Read differently during an incident

During an access incident, the goal is not to read everything. The goal is to
find the smallest trustworthy answer that lets you act safely.

1. Identify the platform and version: distribution, release, filesystem, and
   access-control framework.
2. Identify the exact surface: file mode, ACL, `sudoers` rule, SSH setting,
   SELinux context, AppArmor profile, group membership, or service account.
3. Read the owner reference for that surface.
4. Capture evidence before changing anything.
5. Make the smallest reversible change.
6. Validate from the affected user's point of view.
7. Write down the rollback command or config restore path.

## Read-only practice

Run these on a lab VM or a system where you have permission to inspect access
state. They should not change the host.

```bash
id
groups
stat /etc/sudoers
ls -ld /etc /etc/sudoers /etc/ssh
getfacl /etc/sudoers 2>/dev/null || true
sudo -l
visudo -c
sshd -T 2>/dev/null | grep -i permitrootlogin || true
getenforce 2>/dev/null || true
sestatus 2>/dev/null || true
aa-status 2>/dev/null || true
```

For each command, write one sentence explaining what question it answers. If a
tool is missing, note what that tells you about the platform instead of treating
it as a failure.

## Check your understanding

- Which manual page would you read before editing `sudoers`, and which command
  validates the file?
- How would you prove whether a user has access because of Unix mode bits,
  group membership, or an ACL?
- Why is `sshd_config` documentation safer than copying a random SSH hardening
  snippet?
- What evidence would you collect before changing SELinux or AppArmor policy?
