### Introduction to Ansible

Ansible is an agentless configuration-management tool. It connects to managed
hosts over SSH, gathers facts about the system, and applies tasks described in
YAML playbooks. That makes it a practical first automation tool for Linux
administrators: you can start with the same SSH access you already use, then
turn repeated manual steps into reviewed, repeatable changes.

!!! abstract "What you will learn"
    - Explain Ansible's control node, inventory, modules, tasks, and playbooks.
    - Run safe read-only checks before making a managed change.
    - Write a small playbook that installs and starts a service.
    - Use check mode, diffs, and limited host selection to reduce rollout risk.

!!! warning "Production safety"
    Ansible can change many systems quickly. Start with a lab inventory, target
    one host or a small canary group, run with `--check --diff` when the module
    supports it, and keep playbooks in version control. Never test a new
    privileged playbook against every production host first.

#### Core Ansible pieces

Ansible separates the machine that runs automation from the machines being
managed:

- **Control node:** the workstation, jump host, or CI runner where `ansible` and
  `ansible-playbook` run.
- **Managed hosts:** servers reachable from the control node, usually over SSH.
- **Inventory:** the list of managed hosts and groups, such as `webservers` or
  `dbservers`.
- **Modules:** reusable units of work, such as `ansible.builtin.apt`,
  `ansible.builtin.copy`, `ansible.builtin.service`, and
  `ansible.builtin.command`.
- **Tasks:** individual module calls with arguments.
- **Playbooks:** YAML files that map tasks to hosts in a predictable order.
- **Facts:** discovered host details, such as OS family, network interfaces, and
  package manager.

Unlike Puppet or Salt minions, Ansible usually does not require a persistent
agent on each managed host. The tradeoff is that SSH access, privilege
escalation, Python availability, and inventory accuracy become especially
important.

#### Build a tiny lab inventory

Create an inventory file for disposable lab hosts. The examples below use one
group and one host, but the same pattern scales to many hosts.

```ini
[webservers]
lab-web-1 ansible_host=192.0.2.10 ansible_user=admin
```

Test basic connectivity before running a playbook:

```bash
ansible -i inventory.ini webservers -m ansible.builtin.ping
ansible -i inventory.ini webservers -m ansible.builtin.setup -a 'filter=ansible_distribution*'
```

The `ping` module checks whether Ansible can connect and run Python on the
remote host. The `setup` module gathers facts; filtering keeps the output short
enough to use as evidence in a change note.

#### A small service playbook

This playbook installs Nginx, ensures it is enabled, and starts it. The task
names are intentionally explicit because they become the change log when the
playbook runs.

```yaml
---
- name: Configure a simple web server
  hosts: webservers
  become: true
  gather_facts: true

  tasks:
    - name: Install nginx package on Debian-family hosts
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
      when: ansible_facts['os_family'] == 'Debian'

    - name: Enable and start nginx
      ansible.builtin.service:
        name: nginx
        enabled: true
        state: started
```

Run it first in check mode, then against one host:

```bash
ansible-playbook -i inventory.ini site.yml --check --diff --limit lab-web-1
ansible-playbook -i inventory.ini site.yml --limit lab-web-1
```

Check mode predicts changes when the module supports it. It is not a guarantee,
but it is still a useful review step before privilege escalation touches a real
system.

#### Verify the result

After the playbook runs, collect evidence from both Ansible and the host:

```bash
ansible -i inventory.ini lab-web-1 -m ansible.builtin.command -a 'systemctl is-enabled nginx'
ansible -i inventory.ini lab-web-1 -m ansible.builtin.command -a 'systemctl is-active nginx'
ansible -i inventory.ini lab-web-1 -m ansible.builtin.command -a 'ss -ltn sport = :80'
```

These commands verify intent from three angles: service enablement, current
process state, and the listening network socket. In production, add an
application-level check such as `curl` against the expected virtual host.

#### Common failure patterns

- **SSH succeeds manually but Ansible fails:** confirm the inventory user,
  private key, `ansible_host`, and whether the control node can reach the host
  without interactive prompts.
- **Privilege escalation fails:** verify `become: true`, sudo policy, and
  whether the remote user requires a password that has not been provided.
- **A module says Python is missing:** install the remote Python package or use
  bootstrap steps appropriate for that distribution.
- **The playbook changes too many hosts:** use `--limit`, canary groups, and
  clear inventory names before broad rollout.
- **Check mode reports nothing useful:** some modules cannot predict changes.
  Use a lab run, module documentation, and post-change verification instead of
  treating check mode as a formal proof.

#### Hands-on practice

Use disposable VMs or containers for this lab.

1. Create `inventory.ini` with one lab host in a `webservers` group.
2. Run the `ping` and filtered `setup` checks and save the output.
3. Create `site.yml` from the example playbook.
4. Run the playbook with `--check --diff --limit <host>`.
5. Run the playbook for real against the same single host.
6. Re-run the service and socket verification commands.
7. Change the playbook so the service is stopped, run check mode again, then
   decide whether that change would be safe to apply.
