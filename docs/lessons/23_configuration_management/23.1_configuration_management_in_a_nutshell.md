## 23.1 Configuration Management in a Nutshell

Configuration management is the practice of describing how systems should be
configured, applying that description repeatably, and checking whether real
machines still match the intended state.

For a Linux administrator, this is less about a specific tool and more about a
working discipline:

- known-good settings are written down as code, data, or templates
- changes are reviewed before they reach important systems
- the same change can be applied to one host, ten hosts, or a replacement host
- drift is detected instead of discovered during an outage
- rollback and recovery are planned before the change is urgent

The point is not to make every system identical. The point is to make
differences intentional.

## The Problem Configuration Management Solves

Manual administration works for a while. You install a package, edit a file,
restart a service, and move on. The problem appears when that sequence has to be
remembered, repeated, audited, or fixed months later.

Common failure patterns include:

- two web servers that were supposed to be the same but have different package
  versions
- a firewall rule added during an incident and never recorded
- a service that works on the old host but fails on the replacement
- an emergency command pasted into production without review
- a security baseline that exists in a document but not on the machines

Configuration management turns those hidden procedures into repeatable system
state.

## Desired State

Most configuration-management systems start with a desired-state model. Instead
of saying only:

```console
$ apt install nginx
```

you describe the outcome:

- the `nginx` package should be installed
- `/etc/nginx/nginx.conf` should contain the approved template
- the service should be enabled at boot
- the service should be running
- the firewall should allow only the expected ports

The tool can then compare the current host to that description and make the
small changes needed to converge the host toward the desired state.

Desired state is powerful because it gives operators a stable question to ask:

```text
What should this machine look like, and how do I prove it does?
```

## What Gets Managed

Configuration management can cover many layers of a system, but good teams
start with boring, high-value targets.

Typical managed items include:

- packages and repositories
- users, groups, SSH keys, and sudo rules
- service unit files and daemon settings
- application configuration files
- scheduled jobs and timers
- directories, ownership, and file permissions
- firewall rules and listening services
- monitoring agents and log forwarding
- backup clients and retention configuration

Some state should be managed carefully or not at all. Database contents,
per-host secrets, generated files, and emergency break-glass access usually need
clear boundaries.

## Idempotence

Idempotence means a task can run more than once without causing unnecessary
extra change.

For example, this command is not a great long-term description of state:

```console
$ echo "PermitRootLogin no" >> /etc/ssh/sshd_config
```

Run it twice and the line appears twice. Run it on a file that already has a
conflicting setting and the result may be confusing.

A better managed task says, in effect:

```text
Ensure sshd_config contains exactly the approved PermitRootLogin setting.
```

Idempotence is what lets a configuration-management run be safe as routine
maintenance instead of treated like a one-time migration script.

## Drift

Drift is the gap between the intended state and the real state.

Drift happens for normal reasons:

- an administrator hotfixes a host during an incident
- a package update changes a default
- a cloud image is rebuilt with slightly different contents
- a developer changes a service file manually for debugging
- an old server misses several maintenance runs

The danger is not that drift exists. The danger is that nobody knows it exists.

A useful configuration-management process can answer:

- What changed?
- Who approved it?
- Which hosts have it?
- Which hosts are out of policy?
- What will change if we apply the current configuration?

## Push and Pull Models

Configuration-management tools usually use either a push model, a pull model, or
a mixture of both.

In a push model, an operator or automation runner connects to managed hosts and
applies changes. Ansible often works this way over SSH. Push models are easy to
understand and fit small-to-medium fleets well.

In a pull model, each managed host runs an agent that periodically checks a
server for its assigned configuration. Puppet, Chef, and Salt can work this way.
Pull models scale well and provide continuous enforcement, but they add agent
and control-plane operations.

Neither model is automatically better. Pick based on fleet size, network shape,
security requirements, and team maturity.

## Configuration as Code

Configuration management is strongest when configuration is treated like source
code.

That means:

- store definitions in version control
- review changes before applying them
- keep secrets out of plain-text repositories
- test risky changes in a lab or staging environment first
- make production runs produce logs and change summaries
- connect changes to tickets, incidents, or maintenance windows

This is the difference between "we ran a script" and "we know what the fleet is
supposed to be."

## A Small Operator Workflow

A cautious configuration-management workflow looks like this:

1. Inspect the current host or group.
2. Write the desired state in the tool's language.
3. Run a dry run, check mode, plan, or diff if the tool supports it.
4. Apply the change to a lab host or one low-risk host.
5. Verify the service behavior, not just the tool output.
6. Expand to the rest of the group.
7. Record what changed and how to roll it back.

For example, before enforcing SSH configuration across a fleet, an operator
should know how to keep an existing session open, validate the daemon config,
restart or reload safely, and recover if a host becomes unreachable.

## What Success Looks Like

Good configuration management produces operational evidence:

- a repository shows the intended configuration
- a review shows why a change was accepted
- a run log shows where the change applied
- a verification command shows the service is healthy
- monitoring shows the expected behavior after the change

The tool's success message is not enough. A service can be "configured"
successfully and still fail because of a bad port, missing secret, broken DNS
record, or application-level dependency.

## Hands-on Practice

Use a disposable VM, container, or lab machine.

1. Pick one small piece of local state, such as a package, a test file under
   `/tmp`, or a disabled lab service.
2. Write down the desired state in plain English.
3. Inspect the current state with a read-only command.
4. Make the smallest reversible change by hand.
5. Inspect the state again and write down exactly what changed.
6. Translate that into a future configuration-management task: package,
   template, service, file, user, or command.

Example lab note:

```text
Desired state: lab host has curl installed.
Before: command -v curl returned no path.
Change: installed curl from the distribution package manager.
After: command -v curl returned /usr/bin/curl and curl --version ran.
Future managed form: package curl should be present.
Rollback: remove package if it was installed only for the lab.
```
