## 23.9 Recommended Reading

!!! abstract "What you will learn"
    - Build a practical reading path for configuration management after this chapter.
    - Choose references for Ansible, Salt, infrastructure as code, secrets, testing, and operations practice.
    - Use documentation and books as working references instead of passive reading lists.
    - Create a small team runbook that captures the parts of configuration management your site actually uses.

!!! success "Operator principle"
    Good operators read with a purpose: first to run a safe change, then to understand the tool deeply enough to debug it under pressure.

## How to use this reading list

Do not try to read every resource before using configuration management. That usually turns into procrastination.

Use this reading path in layers:

1. Read enough to operate one small lab safely.
2. Keep the official documentation open while doing the lab.
3. Read deeper when you hit a real design choice.
4. Convert what you learn into a local runbook for your own team.

Configuration management is learned by combining reference material with careful practice. The goal is not to memorize every feature. The goal is to know where to find the right answer, understand the risk, and prove the result.

## Start with your local system

Before studying a tool, understand what the tool will manage.

Useful local references include:

```bash
man systemctl
man journalctl
man sshd_config
man sudoers
man crontab
man apt
man dnf
man yum
man zypper
man pkg
```

Read the manual pages that match the services, packages, users, files, and scheduled jobs your automation will touch.

For example, before automating SSH policy, read `sshd_config(5)` and know how to validate the file:

```bash
sshd -t
```

Before automating Nginx, know:

```bash
nginx -t
systemctl reload nginx
journalctl -u nginx
```

Configuration management tools are not a replacement for understanding the managed service.

## Official tool documentation

Official documentation should be your first stop for command syntax, supported modules, behavior changes, and current examples.

For Ansible, focus on:

- installation and inventory basics
- ad hoc commands
- playbooks
- modules and collections
- variables and facts
- roles
- privilege escalation
- check mode
- Ansible Vault
- playbook strategies and serial rollout

Useful searches in the Ansible docs:

- `ansible inventory`
- `ansible playbook variables`
- `ansible check mode`
- `ansible privilege escalation`
- `ansible vault`
- `ansible.builtin.service`
- `ansible.builtin.template`
- `ansible.builtin.lineinfile`

For Salt, focus on:

- master and minion installation
- minion keys
- targeting
- execution modules
- grains
- pillar
- states
- highstate
- formulas
- test mode
- events, beacons, and reactors
- Salt SSH

Useful searches in the Salt docs:

- `salt targeting`
- `salt grains`
- `salt pillar`
- `salt states tutorial`
- `salt state.apply test=true`
- `salt highstate`
- `salt formulas`
- `salt reactor`
- `salt ssh`

Read official documentation with a terminal open. If a page describes a command, run a safe read-only version in your lab.

## Distribution documentation

Configuration behavior is often distribution-specific.

Good distribution references include:

- Debian Administrator's Handbook
- Ubuntu Server documentation
- Red Hat Enterprise Linux documentation
- Fedora documentation
- SUSE documentation
- FreeBSD Handbook

Use these references for:

- package names
- service names
- default paths
- firewall tooling
- SELinux or AppArmor behavior
- network configuration
- repository management
- release upgrade behavior

For example, a package state that works on Ubuntu may not use the same package name or service name on RHEL. Distribution docs help you avoid writing automation that only works on your laptop.

## Books for system administration foundations

Configuration management assumes you already understand Linux administration. If the underlying system is fuzzy, start there.

Strong foundation books include:

- **UNIX and Linux System Administration Handbook** by Evi Nemeth, Garth Snyder, Trent Hein, Ben Whaley, and Dan Mackin
- **How Linux Works** by Brian Ward
- **The Linux Command Line** by William Shotts
- **Linux Bible** by Christopher Negus
- **Absolute FreeBSD** by Michael W. Lucas, if your environment includes FreeBSD

Use these books to strengthen:

- boot and service management
- users and permissions
- filesystems
- networking
- logging
- package management
- shell workflows
- troubleshooting habits

They will make every configuration management tool easier to understand.

## Books and courses for Ansible

Ansible changes over time, especially around collections and best practices, so pair any book with current official documentation.

Useful Ansible learning resources include:

- **Ansible for DevOps** by Jeff Geerling
- **Ansible: Up and Running** by Bas Meijer, Lorin Hochstein, and René Moser
- official Red Hat Ansible Automation Platform documentation, especially if your organization uses the commercial platform
- community roles and examples, reviewed critically instead of copied blindly

When reading Ansible material, pay special attention to:

- inventory organization
- variable precedence
- idempotent module use
- check mode limits
- role design
- handlers
- secrets with Ansible Vault or external secret stores
- serial deployments and canaries

Do not copy old examples that use broad shell commands when a modern module exists.

## Books and courses for Salt

Salt also changes, so official docs matter here too.

Useful Salt learning resources include:

- Salt Project official documentation
- Salt user guides and state system tutorials
- Salt formulas maintained by active communities
- introductory SaltStack books or courses, checked against current docs before use

When reading Salt material, pay special attention to:

- target expressions
- key management
- execution modules
- state modules
- grains versus pillar
- highstate behavior
- formulas
- Jinja templating
- test mode
- reactors and event-driven automation

Salt's event system is powerful. Learn the basic state system first, then explore events after you can reason clearly about targets, minion identity, and rollback.

## Infrastructure as code references

Configuration management overlaps with infrastructure as code, but they are not the same thing.

Read about:

- Terraform
- OpenTofu
- Pulumi
- Packer
- cloud-init
- Kubernetes manifests
- Helm
- Kustomize
- GitOps tools such as Argo CD and Flux

The key question is ownership:

- Terraform or OpenTofu often owns cloud resources.
- Packer often owns images.
- cloud-init often owns first-boot bootstrap.
- Ansible or Salt often owns host configuration.
- Kubernetes tools often own workloads inside clusters.

Avoid letting multiple tools fight over the same setting. If two tools can change the same file, package, firewall rule, or cloud resource, define which one is authoritative.

## Secrets and security reading

Configuration management often handles secrets and privileged access. Treat this as a first-class topic.

Read about:

- least privilege
- SSH key management
- sudoers policy
- Ansible Vault
- Salt Pillar access control
- HashiCorp Vault
- cloud secret managers
- SOPS
- age and GPG encryption
- CI/CD secret masking
- audit logging

For every automation lane, document:

- where secrets live
- who can read them
- whether they appear in logs
- how they rotate
- how emergency access works
- how access is removed

Do not wait for an incident to learn how your automation exposes secrets.

## Testing and validation references

Configuration management needs tests, even if they are modest.

Read about:

- Ansible syntax checks
- ansible-lint
- Molecule
- Salt test mode
- Testinfra
- Serverspec
- InSpec
- shellcheck for helper scripts
- service-specific config validators
- CI pipelines for infrastructure repositories

Good tests answer practical questions:

- does the YAML parse?
- does the template render?
- does the service config validate?
- does the role converge on a lab host?
- does the expected package, user, file, or service exist afterward?
- does the automation avoid printing secrets?

The best test is not always complicated. A small validation command in CI is much better than no validation at all.

## Incident and operations reading

Configuration management is part of operations, not separate from it.

Read about:

- change management
- post-incident reviews
- rollback planning
- canary deploys
- service-level indicators and objectives
- monitoring and alerting
- runbook design
- operational readiness reviews

Useful books include:

- **Site Reliability Engineering** from Google
- **The Site Reliability Workbook** from Google
- **Release It!** by Michael Nygard
- **The Practice of System and Network Administration** by Thomas Limoncelli, Christina Hogan, and Strata Chalup

Use these resources to think beyond the tool. A playbook that changes a service is only one part of a safe production change.

## Evaluate examples critically

You will find many blog posts and code snippets online. Some are excellent. Some are dangerous.

Before copying an example, ask:

- Is it current?
- Does it match my distribution and tool version?
- Does it use a structured module or raw shell?
- Does it expose secrets?
- Does it validate templates before restart?
- Does it target too broadly?
- Does it restart production services unnecessarily?
- Does it explain rollback?
- Does it include verification?

Treat internet examples as starting points, not authority.

## Build a local runbook

The most useful reading artifact is the one your own team can use.

Create a short configuration management runbook that includes:

- repository location
- supported tools and versions
- inventory layout
- environment names
- how to run a dry run
- how to target one canary
- how to apply a production change
- how secrets are handled
- how templates are validated
- how logs are collected
- rollback steps
- who approves high-risk changes

Keep it close to the code. Update it when the workflow changes.

## A practical reading plan

Use this order if you are building skill from scratch:

1. Review Linux service, package, user, file, and network basics.
2. Read the official quick start for the tool your team uses.
3. Build a one-host lab.
4. Manage one harmless file.
5. Manage one package and service.
6. Add variables and templates.
7. Add secrets safely.
8. Add syntax, lint, or convergence tests.
9. Practice rollback.
10. Write the local runbook.

Then repeat with a real but low-risk service.

## Hands-on practice

Pick one resource from this page and turn it into operational knowledge.

1. Choose an Ansible or Salt official documentation page for a module or state you might actually use.
2. Run one read-only command from the documentation in a lab.
3. Write a tiny configuration example based on the documentation.
4. Run a dry-run or test-mode check.
5. Apply it only to the lab.
6. Record the result, verification command, and rollback step.
7. Add a short note to your local runbook.
