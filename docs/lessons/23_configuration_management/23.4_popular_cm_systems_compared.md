## 23.4 Popular Configuration Management Systems Compared

Configuration-management tools overlap, but they are not interchangeable in
practice. The best fit depends on your team's skill set, fleet size, network
shape, security model, and tolerance for operating a control plane.

This lesson compares common systems from an operator's point of view. The goal
is not to crown a universal winner. The goal is to choose deliberately.

!!! abstract "What you will learn"
    - Compare Ansible, Puppet, Chef, and Salt by operating model and day-to-day fit.
    - Explain the trade-offs between agentless push and agent-based pull systems.
    - Identify selection criteria for small fleets, large fleets, and regulated environments.
    - Build a lightweight evaluation checklist before adopting a tool.

## The Main Comparison Axes

When comparing configuration-management systems, ask practical questions:

- Does it need an agent on each managed host?
- Does it push changes from a control machine or do hosts pull changes?
- Is the configuration language easy for the team to read?
- How does it handle secrets?
- How easy is check mode, diff mode, or dry-run review?
- How much infrastructure is needed to operate the tool itself?
- How well does it report changed, unchanged, and failed hosts?
- Can it scale to the number of machines and teams involved?
- Does it fit the organization's review, audit, and compliance model?

Most mistakes come from ignoring these questions and choosing a tool only
because it is popular.

## Ansible

Ansible is commonly used as an agentless push-based automation tool. It usually
connects to managed Linux hosts over SSH, runs modules remotely, and records
task results.

Strengths:

- easy to start with if the team knows SSH and YAML
- no long-running agent required on each Linux host
- good fit for small and medium fleets
- useful for ad hoc operations as well as desired-state playbooks
- broad module ecosystem
- readable playbooks when kept simple

Trade-offs:

- large inventories can require careful performance tuning
- complex variable precedence can become hard to debug
- push-based access depends on network reachability from the runner
- playbooks can become procedural scripts if discipline is weak
- agentless does not automatically mean low-risk

Typical fit:

- teams that want a low-friction starting point
- environments where SSH access is already well understood
- application deploys, server bootstrap, patch orchestration, and routine Linux
  configuration

Simple Ansible-style task:

```yaml
- name: Ensure nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

## Puppet

Puppet is a mature desired-state configuration-management system. It is often
used with an agent on each managed host. Agents periodically check in, receive a
compiled catalog, and apply state.

Strengths:

- strong desired-state model
- mature reporting and compliance patterns
- good fit for large fleets with continuous enforcement needs
- clear separation between declared state and host application
- long history in enterprise environments

Trade-offs:

- steeper learning curve than simple Ansible usage
- agent and server infrastructure must be operated
- debugging catalog compilation and module interactions can take practice
- model can feel heavy for small teams or small fleets

Typical fit:

- large, long-lived fleets
- environments that need regular drift correction
- organizations that want a central policy/control-plane model

Simple Puppet-style resource:

```puppet
package { 'nginx':
  ensure => installed,
}
```

## Chef

Chef uses recipes, resources, and cookbooks to define system state, historically
with a Ruby-based DSL and agent/client model. It is powerful and flexible, but
that flexibility can also raise the skill requirement.

Strengths:

- expressive programming model
- strong ecosystem for teams already comfortable with Ruby and testing
- mature patterns for cookbooks, roles, environments, and policy
- can support complex infrastructure and application configuration

Trade-offs:

- higher learning curve for teams without Ruby familiarity
- imperative logic can become difficult to reason about if overused
- client/server or policyfile workflows require operational maturity
- may feel heavier than needed for straightforward Linux baseline management

Typical fit:

- organizations with existing Chef investment
- teams that want programmable infrastructure definitions
- environments where configuration logic is complex enough to justify the
  additional structure

Simple Chef-style resource:

```ruby
package 'nginx' do
  action :install
end
```

## Salt

Salt can operate in several modes, but it is often associated with high-speed
remote execution, an event system, and agent-based minions connected to a Salt
master. It can also run in masterless modes.

Strengths:

- fast remote execution across many systems
- event-driven automation capabilities
- flexible configuration-management and orchestration model
- Python-based ecosystem
- useful when fleet-wide command execution and state enforcement both matter

Trade-offs:

- master/minion architecture adds infrastructure to operate
- security and key management need careful attention
- broad feature set can feel complex
- teams must understand whether they are using Salt for remote execution,
  desired state, orchestration, or all three

Typical fit:

- larger fleets needing fast fan-out operations
- environments that benefit from event-driven infrastructure workflows
- teams comfortable operating a central automation service

Simple Salt state:

```yaml
nginx:
  pkg.installed: []
  service.running:
    - enable: true
    - require:
      - pkg: nginx
```

## Other Common Tools

The configuration-management landscape also includes tools that overlap with
these systems.

Terraform is primarily infrastructure provisioning, not host configuration. It
is excellent for describing cloud resources such as networks, instances,
databases, IAM roles, and load balancers. It is usually paired with a host
configuration tool rather than replacing one.

Cloud-init is useful for first-boot host initialization. It can install packages,
write files, create users, and run bootstrap commands. It is not usually the
long-term source of truth for ongoing fleet drift correction.

Image-building tools such as Packer shift configuration into machine images.
This can reduce boot-time work, but images still need patching, rotation, and
runtime configuration.

Kubernetes operators, Helm charts, and GitOps tools manage desired state inside
Kubernetes. They solve a related problem, but their target is cluster resources
rather than general Linux host configuration.

## Push Versus Pull

Ansible often starts as push-based automation: the operator or CI runner
connects to hosts and applies changes. Puppet, Chef, and Salt often use agents
that pull or receive assigned state from a central service.

Push model advantages:

- easy to understand
- fewer always-running components
- good for smaller fleets and explicit maintenance runs
- works naturally with SSH-based administration

Push model risks:

- runner must reach every host
- credentials and network paths must be carefully controlled
- very large runs can become slower or harder to coordinate

Pull model advantages:

- continuous drift correction
- scales well when hosts check in independently
- central reporting can be stronger
- works better when direct inbound access to hosts is limited

Pull model risks:

- agent lifecycle must be managed
- central service becomes important infrastructure
- policy mistakes can spread automatically
- debugging requires understanding both host agent and server behavior

## Choosing for a Small Team

For a small Linux team, the first good choice is often the tool the team will
actually read, review, and run safely.

Ansible is commonly a pragmatic starting point because SSH and YAML are familiar
and the agentless model lowers setup cost. That does not make it automatically
best forever. It means the team can start practicing inventory, review, dry-run,
and verification without first building a larger control plane.

If the organization already has Puppet, Chef, or Salt expertise, existing
operational knowledge may matter more than a clean-sheet comparison.

## Choosing for a Large Fleet

Large fleets need stronger answers for:

- reporting
- agent or runner scaling
- secrets
- inventory ownership
- drift detection
- staged rollout
- policy enforcement
- audit history

Agent-based systems can be attractive here because they continuously report and
enforce state. Push-based systems can still work, but require more attention to
execution architecture and rollout strategy.

## Evaluation Checklist

Before adopting or expanding a configuration-management tool, run a small pilot.

Evaluate:

1. How easy is it to express a package, file, service, and user?
2. Can a teammate review the change without knowing every internals detail?
3. Can the tool show what would change before applying it?
4. Can it validate generated service configuration?
5. How are secrets stored and rotated?
6. What happens when one host fails mid-run?
7. How does the tool report drift and change history?
8. How do you limit a run to one canary host?
9. How do you roll back a bad change?
10. Who operates the tool's own infrastructure?

## Hands-on Practice

Use a lab host or a written design exercise.

1. Pick a simple target state: a package installed, a file rendered, and a
   service running.
2. Write how Ansible, Puppet, Chef, or Salt would represent that state at a high
   level.
3. Identify whether the tool would push from a runner or pull through an agent.
4. Write one advantage and one risk for that model in your environment.
5. Decide how you would test the change on one host before expanding it.

Example comparison note:

```text
Target: install nginx and keep the service running.
Ansible fit: simple SSH-based task; easy first pilot.
Puppet fit: stronger continuous enforcement, but needs agent/control plane.
Risk: bad template could break all web hosts.
Canary: one staging host first; validate nginx -t and curl localhost.
```
