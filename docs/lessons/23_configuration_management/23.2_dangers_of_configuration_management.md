## 23.2 Dangers of Configuration Management

Configuration management gives administrators leverage. The same playbook,
state file, or policy bundle that fixes one host can also break a hundred
hosts in the same minute. Treat CM as production change automation, not as a
shortcut around operational discipline.

!!! abstract "What you will learn"
    - Identify common failure modes introduced by configuration management.
    - Separate safe drift detection from risky automatic remediation.
    - Build guardrails around templates, secrets, package changes, service
      restarts, and fleet-wide rollouts.
    - Explain what evidence should be captured before and after a CM run.

!!! warning "Production safety"
    Do not point a new playbook, Salt state, Puppet manifest, or Chef recipe at
    every production host first. Start with syntax checks, a disposable lab,
    one representative test host, and a small canary group before widening the
    change.

## How CM Can Hurt You

CM systems usually fail in predictable ways:

- **Bad intent becomes repeatable.** A wrong package name, file mode, or service
  target is applied consistently everywhere.
- **Templates hide destructive details.** One shared Jinja, ERB, or YAML
  template can overwrite working local configuration with invalid generated
  files.
- **Drift repair becomes an outage.** Automatically "fixing" drift can remove
  emergency hotfixes before the incident is understood.
- **Secrets spread too far.** Variables, inventory files, logs, and CI output can
  expose tokens if secret handling is bolted on after the fact.
- **Order matters more than expected.** Updating packages before config files,
  restarting services before validation, or changing firewall rules before
  access checks can lock out operators.
- **The blast radius grows quietly.** A broad inventory pattern such as `all`,
  `web*`, or an untested dynamic group can include hosts you did not mean to
  touch.

The danger is not automation itself. The danger is automation without review,
scope control, validation, and rollback thinking.

## Drift Detection Versus Remediation

Start by using CM to observe. A read-only check is much safer than an automatic
change:

```bash
# Ansible: list affected hosts before running a play
ansible-inventory --graph
ansible webservers --list-hosts

# Puppet: show what would change without enforcing it
sudo puppet agent --test --noop

# Salt: inspect planned state changes first
sudo salt-call state.apply test=True
```

Read-only or dry-run output is not perfect, but it gives you an evidence trail:
which hosts are in scope, which files would change, which services would
restart, and which commands require elevated privileges.

!!! note "No-op is not a rollback plan"
    Dry-run modes can miss runtime behavior, package-manager side effects, and
    handler-triggered restarts. Use them to reduce risk, then still test on a
    real lab or canary host.

## Control The Blast Radius

Before a CM run, answer four questions:

1. Which exact hosts are targeted?
2. Which exact files, packages, users, services, timers, or firewall rules can
   change?
3. What command proves the target service is still healthy afterward?
4. How will you back out if the change is wrong?

Useful habits include:

- Prefer explicit host groups over broad patterns.
- Limit the first run to one host or one availability-zone equivalent.
- Use serial or batch rollout settings when the tool supports them.
- Validate configuration files before restarting services.
- Keep emergency access open while firewall or SSH changes roll out.
- Record the CM tool version, repository commit, inventory source, and operator
  command used for the run.

For example, an Ansible run can be narrowed and slowed down:

```bash
ansible-playbook site.yml \
  --limit web01.example.com \
  --check --diff

ansible-playbook site.yml \
  --limit webservers \
  --serial 10% \
  --diff
```

The first command previews one host. The second rolls through a webserver group
in batches and shows file diffs where the modules support them.

## Validate Before Restarting

Many outages come from writing a bad configuration file and immediately
restarting the service. Build validation into the CM change:

```bash
# Common examples to run before reload/restart
sudo nginx -t
sudo apachectl configtest
sudo named-checkconf
sudo sshd -t
sudo visudo -cf /etc/sudoers
```

In CM code, make the restart depend on a successful validation command. If the
service supports reloads, prefer a reload over a full restart when that is
enough.

## Protect Secrets

Configuration data often includes credentials. Treat the CM repository and its
automation logs as sensitive systems:

- Store secrets in the tool's encrypted secret mechanism, not in plain YAML or
  JSON.
- Keep decrypted secret files out of shell history, CI artifacts, and chat logs.
- Restrict who can read inventories and variable files.
- Rotate credentials if they were committed or printed accidentally.
- Avoid logging command output that can include tokens.

Examples include Ansible Vault, SOPS, age-encrypted files, cloud secret managers,
Puppet Hiera backends, and Salt pillar encryption. The specific tool matters
less than having a deliberate secret lifecycle.

## When To Pause A CM Rollout

Stop and investigate when you see:

- More hosts in scope than expected.
- A dry run that wants to delete files or downgrade packages.
- A generated config diff that changes unrelated settings.
- A handler that restarts a critical service without a health check.
- A task that depends on internet access during a production incident.
- A run that fails differently across hosts in the same group.

Pausing is not failure. It is how you keep a small mistake from becoming a fleet
event.

## Hands-On Practice

Use a disposable VM, container, or lab inventory.

1. Create or inspect a small CM task that manages one harmless file such as
   `/tmp/cm-danger-lab.conf`.
2. Run the tool in dry-run or check mode and save the host list plus planned
   diff.
3. Add a validation step that must pass before any service reload would occur.
4. Limit the run to one test host and apply the change.
5. Re-run the tool and confirm it reports no further changes.
6. Write a rollback note that explains how to remove or restore the managed
   file.
