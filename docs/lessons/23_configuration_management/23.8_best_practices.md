## 23.8 Best Practices

!!! abstract "What you will learn"
    - Turn configuration management advice into concrete operating habits.
    - Reduce blast radius before applying automated changes.
    - Keep configuration code reviewable, testable, auditable, and recoverable.
    - Build a short checklist for safer day-to-day configuration management.

!!! success "Operator principle"
    Good configuration management is not just "automate everything." It is controlled, reviewable, reversible change at the right scope.

## Why best practices matter

Configuration management tools can update hundreds or thousands of systems quickly. That is the point, and it is also the risk.

When configuration management is mature, it gives a team:

- repeatable server builds
- consistent packages and services
- reviewable infrastructure changes
- less manual drift
- faster recovery after failure
- a shared source of operational truth

When it is careless, it can create outages faster than a human could type the commands by hand.

Best practices exist to make automation boring. Boring automation is good. It means changes are scoped, reviewed, tested, observable, and recoverable.

## Keep configuration in version control

Configuration code belongs in version control. That includes Ansible playbooks, Salt states, templates, inventory definitions, role defaults, formulas, policy files, and related documentation.

Version control gives you:

- a change history
- peer review
- rollback evidence
- issue or ticket links
- CI checks
- a way to compare intended state over time

A configuration change should answer:

- What changed?
- Why did it change?
- Who reviewed it?
- Which systems are affected?
- How was it tested?
- How do we roll back?

Avoid changing managed configuration directly on a server and then "cleaning it up later." That creates drift and makes the real source of truth unclear.

## Separate environments

Do not test new automation by running it across production first.

At minimum, separate:

- local or disposable lab
- development
- staging
- production

These environments do not have to be identical in size, but they should be similar enough to catch dangerous mistakes before production.

For example, a staging web host should use the same role, service layout, template path, and package family as production. It can have fewer users and less traffic, but it should exercise the same automation path.

The first question after writing a change should be:

> Where can I safely prove this before production?

## Reduce blast radius

Blast radius is the amount of damage a mistake can cause.

Configuration management can widen blast radius because a single command can affect many hosts. Reduce it deliberately.

Instead of this:

```bash
ansible all -m package -a "name=nginx state=latest"
salt '*' state.highstate
```

prefer a staged rollout:

```bash
ansible staging_web -m package -a "name=nginx state=present" --check
ansible web_canary -m package -a "name=nginx state=present" --check
ansible web_canary -m package -a "name=nginx state=present"
```

or:

```bash
salt -C 'G@role:web and G@env:staging' state.apply nginx test=true
salt 'web01.example.com' state.apply nginx
```

A safe rollout usually moves through:

1. syntax and lint checks
2. dry run or test mode
3. staging
4. one canary host
5. small production batch
6. full rollout

Do not skip straight to the full fleet unless the change is tiny, well understood, and easy to reverse.

## Make targeting explicit

Many automation incidents start with a bad target.

Examples:

- `all` matched more hosts than expected
- a glob matched production and staging
- a stale role label put a database host in the web group
- an inventory file had an old hostname
- a node was copied from another environment without changing its metadata

Before a state-changing run, prove the target with a read-only command.

Ansible:

```bash
ansible web_canary --list-hosts
ansible web_canary -m ping
```

Salt:

```bash
salt -C 'G@role:web and G@env:prod' test.version
```

Record the matched host count in the change note. If the host count is surprising, stop.

## Prefer idempotent changes

An idempotent change can run repeatedly and end in the same correct state.

For example, "ensure `nginx` is installed" is idempotent. "Run this shell command that appends a line to a file" may not be.

Prefer modules that understand state:

- package installed
- service running
- file managed
- user present
- directory exists
- line present once

Avoid generic shell commands when a structured module exists. Shell commands can be necessary, but they should be isolated, documented, and guarded with checks.

Bad pattern:

```yaml
- name: append setting every run
  shell: echo "PermitRootLogin no" >> /etc/ssh/sshd_config
```

Better pattern:

```yaml
- name: ensure root SSH login is disabled
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^PermitRootLogin '
    line: 'PermitRootLogin no'
```

Idempotence is what makes automation safe to rerun during recovery.

## Treat secrets carefully

Configuration management often needs secrets: database passwords, API tokens, TLS private keys, SSH keys, or service credentials.

Do not store plaintext secrets in ordinary repository files.

Use a secret management approach that fits the tool and environment:

- Ansible Vault
- Salt Pillar with appropriate access controls
- HashiCorp Vault
- cloud secret managers
- encrypted CI/CD variables
- operating-system key stores where appropriate

Also protect output. A secret can leak through:

- command logs
- CI logs
- task failures
- debug output
- copied ticket comments
- screenshots

Mark secret-handling tasks so they do not print sensitive values when the tool supports it. In Ansible, for example, use `no_log: true` on tasks that may expose secrets.

## Template defensively

Templates are useful because they adapt configuration files to each host or environment. They are risky because a small logic mistake can generate broken configuration everywhere.

Good templates have:

- clear variable names
- safe defaults
- minimal branching
- comments for non-obvious choices
- validation before service restart

When managing service configuration, use validation commands when available.

Examples:

```bash
nginx -t
apachectl configtest
sshd -t
named-checkconf
```

A strong pattern is:

1. render the file
2. validate the file
3. restart or reload only if validation passes

Do not reload a critical service immediately after generating an unvalidated template.

## Use handlers and restarts deliberately

Restarting a service is a production event.

It may drop connections, clear in-memory state, trigger failover, or briefly remove capacity. Configuration management tools make restarts easy, so operators must make them intentional.

Use handlers or equivalent mechanisms so a service restarts only when relevant files change.

Good restart practice:

- validate configuration before restart
- prefer reload over restart when safe
- restart canaries first
- avoid restarting all replicas at once
- check service health after restart
- document expected interruption

For clustered systems, understand quorum and leader election before automating restarts.

## Test the automation itself

Configuration code deserves tests.

Useful checks include:

- YAML syntax checks
- linting
- role or formula unit tests
- dry-run or check mode
- template rendering tests
- container or VM convergence tests
- documentation link checks
- policy checks for secrets and dangerous commands

Examples:

```bash
ansible-playbook site.yml --syntax-check
ansible-lint
salt-call --local state.apply my_state test=true
```

Testing does not need to be perfect to be valuable. Even simple syntax and lint checks catch mistakes before they reach production.

## Observe before and after

A change is not complete when the tool exits successfully. It is complete when the desired result is verified.

Before a change, record baseline evidence:

- service status
- package version
- listening ports
- current config hash or relevant setting
- application health endpoint
- recent error logs

After a change, collect the same evidence again.

Example:

```bash
systemctl is-active nginx
nginx -t
curl -fsS http://localhost/health
journalctl -u nginx --since '10 minutes ago' --no-pager
```

For remote execution tools, collect evidence through the tool when practical:

```bash
ansible web_canary -m service -a "name=nginx state=started"
salt 'web01.example.com' service.status nginx
```

The before/after evidence is what turns "I ran automation" into "I proved the system is better."

## Plan rollback before rollout

Do not wait for a failed rollout to invent the rollback.

Before applying a change, know whether rollback means:

- revert a Git commit
- restore a previous template
- pin a package version
- re-enable an old service
- restore a backup
- roll forward with a corrected config
- manually intervene on a small set of hosts

Rollback should be tested for high-risk changes.

For some changes, especially database migrations or destructive data operations, rollback may be difficult or impossible. Those require extra review and a stronger rollout plan.

## Avoid unmanaged drift

Drift is the gap between intended state and real state.

Some drift is accidental:

- manual edits during incidents
- emergency package installs
- one-off permission fixes
- local config changes that never reach the repo

Some drift is structural:

- hosts missing from inventory
- stale labels
- environment-specific exceptions
- old images

After emergency manual changes, decide quickly:

- should the automation be updated to preserve this change?
- should the manual change be reverted?
- should this host be rebuilt?

Do not leave important manual changes undocumented.

## Keep inventories and facts clean

Automation depends on accurate inventory.

Review:

- hostnames
- roles
- environments
- owners
- operating-system versions
- network locations
- lifecycle state
- custom facts or grains

Old hosts should be removed. Rebuilt hosts should have fresh identity and facts. Production and staging should not share misleading labels.

Inventory hygiene is not glamorous, but bad inventory breaks good automation.

## Document the operating contract

Every configuration management lane should have a short operating contract.

Include:

- what the automation owns
- what it does not own
- how to run it safely
- where secrets live
- how to test it
- how to roll back
- who approves production changes
- where run logs or reports are stored

This does not need to be long. A one-page runbook is better than a perfect document nobody writes.

## Practical checklist

Before applying a configuration-management change, ask:

1. Is the change in version control?
2. Was it reviewed?
3. Do I know the exact target hosts?
4. Did I run a syntax, lint, dry-run, or test-mode check?
5. Have I tested in a lower environment or on a canary?
6. Are secrets protected from repository and log exposure?
7. Will templates be validated before restart?
8. Do I know the rollback path?
9. What evidence will prove success?
10. Who needs to know if this changes production behavior?

If you cannot answer these questions, the change is not ready for a wide rollout.

## Hands-on practice

Use a lab repository or disposable VM for this exercise.

1. Choose a small configuration target, such as a managed `/etc/motd` file or a harmless package.
2. Put the configuration code in version control.
3. Add a short README that states what the automation owns and how to roll it back.
4. Run a syntax or dry-run check.
5. Apply it to one lab host.
6. Capture before/after evidence.
7. Make a small change and repeat the process.
8. Write down what would make this unsafe in production.
