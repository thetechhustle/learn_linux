## Why Salt exists

Salt, sometimes called SaltStack, is a Python-based automation system for managing fleets of machines. It can run one command across many hosts, enforce desired configuration, collect system facts, and react to events.

Salt grew around a practical operations problem: when a fleet becomes too large for one-off SSH loops, operators need a faster and more structured way to ask:

- Which hosts match this target?
- What is true on those hosts right now?
- What should be true after configuration is applied?
- Which hosts changed?
- Which hosts failed, and why?

Salt can answer those questions through both remote execution and configuration management.

Remote execution asks a host to do something now:

```bash
salt 'web*' test.ping
salt 'web*' cmd.run 'uptime'
```

Configuration management describes the intended state:

```yaml
nginx:
  pkg.installed: []
  service.running:
    - enable: true
    - require:
      - pkg: nginx
```

The same platform can inspect a fleet, push immediate commands, and converge hosts toward a repeatable state.

## The master and minion model

The classic Salt architecture has one or more Salt masters and many Salt minions.

The Salt master coordinates commands, stores states, evaluates targeting, and receives returns.

A Salt minion runs on each managed host. It connects to the master, accepts authorized jobs, executes Salt modules locally, and returns results.

The connection model matters operationally. Instead of an operator opening SSH connections to every host, minions maintain communication with the master. That can make large fan-out operations fast, but it also means the master becomes a high-value control plane.

A small Salt deployment often starts like this:

1. Install `salt-master` on the control host.
2. Install `salt-minion` on managed hosts.
3. Configure each minion with the master's address.
4. Accept minion keys on the master.
5. Run read-only tests before attempting changes.

Useful first checks include:

```bash
salt-key -L
salt '*' test.ping
salt '*' grains.item os osrelease kernel
```

Do not treat `test.ping` as a full health check. It proves the minion can answer a Salt job. It does not prove the application, network path, package state, disk health, or service configuration is correct.

## Targeting minions

Salt targeting decides which minions receive a job. This is where careful operators spend time before making changes.

The simplest target is a minion id glob:

```bash
salt 'web*' test.ping
salt 'db01.example.com' test.ping
```

Salt also supports targeting by grains, lists, regular expressions, nodegroups, and compound expressions.

Grain targeting uses facts collected from minions:

```bash
salt -G 'os:Ubuntu' test.ping
salt -G 'role:web' test.ping
```

Compound targeting combines conditions:

```bash
salt -C 'G@os:Ubuntu and web*' test.ping
salt -C 'G@role:web and not G@env:prod' test.ping
```

Targeting mistakes are one of Salt's biggest operational risks. A single broad target can run a command on every minion. Before a state-changing job, first run a harmless command against the exact same target:

```bash
salt -C 'G@role:web and G@env:staging' test.version
```

If the matched host list is surprising, stop and fix the targeting expression.

## Execution modules

Salt remote execution is built around execution modules. A module exposes functions that run on minions.

Common examples include:

```bash
salt 'web*' test.version
salt 'web*' pkg.version nginx
salt 'web*' service.status nginx
salt 'web*' disk.usage
salt 'web*' cmd.run 'systemctl is-active nginx'
```

Prefer Salt's structured modules over generic shell commands when a module exists. For example, `service.status nginx` is more intentional than `cmd.run 'systemctl status nginx'`, and `pkg.version nginx` is clearer than a distribution-specific package query.

Generic `cmd.run` is still useful, but it should raise your caution level. It can hide quoting issues, shell expansion, privilege assumptions, and distribution differences.

## Grains

Grains are facts about a minion. Salt collects many automatically, such as operating system, kernel, CPU architecture, IP addresses, and virtualization details.

Read grains with:

```bash
salt 'web*' grains.items
salt 'web*' grains.item os osfinger ipv4
```

Operators commonly use grains for targeting and templating.

Example targeting by operating system:

```bash
salt -G 'os_family:Debian' pkg.version openssh-server
```

Grains can also include custom site facts, such as:

```yaml
grains:
  role: web
  env: staging
  owner: platform
```

Custom grains are useful, but stale grains create bad automation decisions. If a host changes role or environment, make sure the grain data changes with it.

## Pillar

Pillar is Salt's mechanism for assigning managed data to minions. It is commonly used for environment-specific values, application settings, and secret material.

Grains describe what a minion is. Pillar describes what configuration data the minion should receive.

A state might reference pillar data like this:

```yaml
/etc/example/app.conf:
  file.managed:
    - source: salt://example/app.conf.j2
    - template: jinja
    - context:
        listen_port: {{ pillar['example']['listen_port'] }}
```

Pillar access should be treated as sensitive. Avoid logging pillar contents casually, especially if secrets are present.

Useful checks include:

```bash
salt 'web01*' pillar.items
salt 'web01*' pillar.get example:listen_port
```

In production, restrict who can read pillar values and be careful when copying command output into tickets or chat.

## States

Salt states describe desired configuration. State files usually use YAML with Salt's state modules.

A basic package and service state might look like this:

```yaml
nginx:
  pkg.installed: []
  service.running:
    - enable: true
    - require:
      - pkg: nginx
```

This tells Salt:

- the `nginx` package should be installed
- the `nginx` service should be running
- the service should be enabled at boot
- the service depends on the package being present first

Apply states with:

```bash
salt 'web*' state.apply
salt 'web*' state.apply nginx
```

Before applying to real hosts, use test mode:

```bash
salt 'web*' state.apply nginx test=true
```

Test mode is not magic, but it is valuable. It asks Salt to show what it expects to change without making the change. Some modules cannot perfectly predict every result, so pair test mode with review and a narrow target.

## Highstate

`state.highstate` applies the full state assignment for a minion according to the top file.

The top file maps targets to states:

```yaml
base:
  'web*':
    - nginx
  'db*':
    - postgresql
```

Then highstate applies everything selected for the minion:

```bash
salt 'web01*' state.highstate test=true
salt 'web01*' state.highstate
```

Highstate is convenient and dangerous. It can apply many states at once. Use narrow targets, test mode, and change windows when the state tree is large or unfamiliar.

## Formulas

A Salt formula is a reusable collection of states, templates, defaults, and supporting files for managing a component.

For example, an `nginx` formula might include:

```text
nginx/
  init.sls
  package.sls
  service.sls
  files/
    nginx.conf.j2
  defaults.yaml
```

Formulas help teams avoid copy-pasting state logic across environments. They also make review easier because configuration behavior is centralized.

The trade-off is abstraction. A formula with many variables and templates can become hard to reason about. Keep formulas boring, documented, and tested on a small target before wide rollout.

## Jinja templating

Salt commonly uses Jinja templates in states and managed files.

Example:

```jinja
{% if grains['os_family'] == 'Debian' %}
nginx:
  pkg.installed:
    - name: nginx
{% endif %}
```

Jinja is useful for adapting state to different systems, but too much logic in templates becomes a maintenance problem. Prefer simple conditionals and clear defaults. If a template needs complex branching, consider whether the fleet should be split into clearer roles or formulas.

## The event system, beacons, and reactors

Salt can react to events. This is one of its distinguishing features.

Beacons monitor conditions on minions and send events. Reactors listen for events and trigger actions.

Examples of event-driven patterns include:

- restart a service when a watched file changes
- run a remediation state when a process disappears
- notify operators when a host reports a specific condition
- coordinate workflows across multiple minions

This capability is powerful, but it can also create surprise automation. Event-driven remediation should be easy to audit, easy to disable, and limited to well-understood actions.

For first Salt deployments, start with explicit commands and states before adding reactors.

## Salt SSH

Salt also has a mode called Salt SSH. It can run Salt commands over SSH without installing a minion on each host.

Salt SSH is useful when:

- you are bootstrapping a new environment
- installing minions is not allowed yet
- the fleet is small
- you need an Ansible-like connection model

Classic Salt minions are usually better when you want fast fan-out, persistent fleet control, and event-driven features.

## Where Salt fits well

Salt is a strong fit when you need:

- fast remote execution across many hosts
- a persistent control plane
- desired-state configuration
- flexible targeting
- event-driven automation
- one platform for inspection, orchestration, and convergence

It can be a weaker fit when:

- your fleet is small and simple
- your team wants an agentless-first model
- you do not want to operate a master/minion control plane
- broad command fan-out creates more risk than value
- your configuration needs are already solved by image building or cloud-init

Tool choice should follow operating reality. Salt is not better just because it is powerful. It is better when your team can safely use the power.

## A safe Salt workflow

Use a disciplined sequence for Salt changes:

1. Confirm the exact target.

    ```bash
    salt -C 'G@role:web and G@env:staging' test.ping
    ```

2. Gather current evidence.

    ```bash
    salt -C 'G@role:web and G@env:staging' service.status nginx
    salt -C 'G@role:web and G@env:staging' pkg.version nginx
    ```

3. Run state test mode.

    ```bash
    salt -C 'G@role:web and G@env:staging' state.apply nginx test=true
    ```

4. Review expected changes.

5. Apply to one or a few hosts.

    ```bash
    salt 'web01.example.com' state.apply nginx
    ```

6. Verify the result.

    ```bash
    salt 'web01.example.com' service.status nginx
    salt 'web01.example.com' cmd.run 'curl -fsS http://localhost/health || true'
    ```

7. Expand gradually.

That workflow is slower than `salt '*' state.highstate`, but it is much safer.

## Common failure modes

Watch for these Salt-specific problems:

- the target expression matches more hosts than intended
- minion keys are accepted for the wrong host
- stale grains send hosts into the wrong state path
- pillar data is missing, stale, or exposed in logs
- Jinja renders invalid configuration
- a state works on one distribution but fails on another
- a highstate applies unrelated changes
- event-driven automation runs when nobody expected it
- the Salt master becomes a single high-value failure point

Good Salt operations include both automation and guardrails.

## Hands-on practice

Run these on a disposable VM or lab machine. Do not aim Salt at production while learning.

1. Install Salt master and minion packages in a small lab, or use containers if your environment provides them.
2. Configure one minion to connect to the master.
3. List pending keys with `salt-key -L`, then accept only the expected minion.
4. Run `salt '*' test.ping`.
5. Read a few grains with `salt '*' grains.item os osrelease kernel`.
6. Write a tiny state that manages a harmless package or file.
7. Run the state with `test=true`.
8. Apply it to one minion.
9. Record the before/after evidence in a lab note.

Your lab note should include:

- target expression used
- minions matched
- command or state applied
- expected change
- actual change
- verification command
- rollback or cleanup step
