## 23.3 Elements of Configuration Management

Configuration management is not one magic product. It is a set of cooperating
parts that let a team describe, review, apply, and verify system state.

When those parts are visible, a managed fleet is easier to reason about. When
they are hidden, even a popular tool can become a pile of scripts nobody trusts.

## Inventory

Inventory answers the question:

```text
Which systems can this tool change?
```

An inventory may be a static file, a directory of host definitions, a cloud
query, a CMDB, or a dynamic plugin that discovers machines from an API.

Useful inventory data includes:

- hostnames and addresses
- environment names such as development, staging, and production
- roles such as web, database, cache, worker, or bastion
- operating-system family and version
- region, site, or rack
- owner or service team
- maintenance-window expectations

Inventory must be treated carefully because it controls blast radius. A perfect
task aimed at the wrong group is still a bad change.

## Desired State

Desired state is the description of what the system should look like.

Common desired-state items include:

- packages that should be installed or absent
- files that should exist with specific content and permissions
- services that should be enabled, disabled, running, or stopped
- users, groups, SSH keys, and sudo rules
- scheduled jobs and timers
- firewall rules and listening ports
- monitoring and logging agents

Good desired-state definitions are specific enough to be testable. "Make the
server secure" is not desired state. "Disable password SSH login and verify
public-key login still works" is closer.

## Modules and Resources

Configuration-management tools usually expose reusable units for common system
operations.

Different tools use different words: modules, resources, states, providers,
recipes, formulas, or tasks. The idea is similar: use a structured operation
instead of an ad hoc command whenever possible.

For example, prefer a package module that knows how to use the distribution's
package manager over a raw command like:

```console
$ apt install -y nginx
```

A module can usually report whether it changed anything, avoid unnecessary work,
and integrate with check or diff modes.

## Variables

Variables let one definition adapt to multiple hosts or environments.

Examples:

- the package name for a service on different distributions
- the number of worker processes for a host class
- an environment-specific upstream URL
- a region-specific log endpoint
- a per-host data directory

Variables are useful, but they can also hide complexity. If a service behaves
differently in production, staging, and development, the variable source should
make that difference obvious.

Keep variable precedence understandable. If five different files can define the
same value, troubleshooting becomes harder.

## Templates

Templates generate configuration files from shared structure plus variables.

They are common for files such as:

- web-server virtual hosts
- systemd unit overrides
- application environment files
- monitoring-agent configuration
- log-forwarding rules

Templates should be readable after rendering. A generated configuration file is
still an operational artifact, and the native service must be able to validate
it.

For high-risk templates, pair rendering with validation:

```console
$ nginx -t
$ sshd -t
$ visudo -cf /etc/sudoers
```

## Handlers and Service Actions

Many configuration-management systems separate file changes from service
actions. A template can notify a handler, and the handler can reload or restart
the affected service only when needed.

That pattern matters because unnecessary restarts create avoidable risk.

Prefer the least disruptive action that applies the new state:

- reload when the daemon supports safe reloads
- restart when the service requires it
- defer restarts when a maintenance window is required
- validate configuration before touching the running service

For important services, a handler should be paired with service-level
verification.

## Secrets

Secrets need their own handling path.

Configuration management often needs to deliver credentials, but secrets should
not be stored as plain text in the same place as ordinary variables.

Use an appropriate mechanism such as:

- a dedicated secret manager
- encrypted variable files
- deployment-time environment injection
- cloud identity and short-lived credentials
- file permissions that limit who can read rendered secrets

Also define rotation behavior. A secret-management design that cannot rotate a
leaked credential is incomplete.

## Version Control and Review

Configuration definitions should live in version control. This gives the team a
history of what changed, who changed it, and why.

Version control also supports review:

- small pull requests
- linked tickets or incidents
- clear diffs
- automated checks
- rollback through known commits

Review is not bureaucracy. It is how a team catches a production-wide mistake
before automation faithfully applies it.

## Execution Engine

The execution engine is the part that applies state to hosts.

It may run from:

- an administrator's workstation
- a CI/CD runner
- a central control server
- an agent running on each host
- a scheduled job

The execution path should be predictable. Operators should know which identity
the tool uses, how it authenticates, what network access it needs, where logs
are stored, and how failures are reported.

## Testing and Validation

Configuration-management testing has several layers.

Useful checks include:

- syntax checks for the configuration-management code
- linting for style and dangerous patterns
- template-render checks
- native service validation commands
- dry-run or diff output
- lab or staging application
- post-change service health checks

No single check proves everything. A syntax check can pass while a service is
unhealthy. A service can start while the application behavior is still wrong.

## Reporting and Audit Trail

A configuration-management run should leave enough evidence for an incident
review.

Useful run records include:

- who or what started the run
- the commit or version that was applied
- the target host list
- changed, unchanged, and failed hosts
- files or services changed
- warnings and validation failures
- follow-up actions or rollback commands

If an outage happens after a change, these records help the team answer what
changed without guessing.

## Rollback and Recovery

Rollback is not only "revert the commit."

A real recovery plan may include:

- restoring a previous configuration file
- rolling back a package version
- restarting or reloading a service
- restoring access through a console
- disabling an agent temporarily
- excluding a host from future runs while it is repaired

Every high-risk managed change should have a recovery path before it touches
important hosts.

## Hands-on Practice

Use a disposable VM, container, or lab directory.

1. Pick one imaginary service, such as `webapp`.
2. Write an inventory note for two hosts: one staging host and one production
   host.
3. Write desired state in plain English: package, config file, service state,
   and verification command.
4. List which values should be variables.
5. List which values would be secrets.
6. Write the validation and rollback steps.

Example design note:

```text
Inventory: web-stg-01, web-prod-01
Desired state: webapp package present; service enabled and running.
Template: /etc/webapp/webapp.conf
Variables: listen_port, log_level, upstream_url
Secrets: database password, API token
Validation: webapp --check-config; curl localhost health endpoint
Rollback: restore previous template; reload service; revert package if needed
```
