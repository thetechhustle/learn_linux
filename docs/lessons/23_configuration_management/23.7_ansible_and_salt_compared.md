## 23.7 Ansible and Salt Compared

Ansible and Salt can both make Linux administration repeatable, but they push you toward different operating models. Ansible is usually easiest when you want reviewable playbooks, agentless access over SSH, and a workflow that feels close to "run this change against these hosts." Salt is usually stronger when you need an always-present control plane, fast remote execution, event-driven automation, or very large fleets that benefit from persistent agents.

Do not choose a tool only because it is popular. Choose the tool whose failure modes your team can operate safely.

!!! abstract "What you will learn"
    - Compare Ansible and Salt by architecture, rollout style, scale, learning curve, and operational risk.
    - Identify the evidence you should gather before choosing one for a Linux fleet.
    - Practice evaluating a small automation task without touching production hosts.

!!! example "Field story"
    A team manages 80 web servers by hand and wants to standardize package updates, service configuration, and compliance checks. Ansible looks attractive because it can start from SSH access and a Git repository. Six months later, the same team is responsible for thousands of short-lived systems and wants near-real-time remote execution. Salt's agent-based event system may now fit better. The right answer changed because the operating problem changed.

!!! success "Operator principle"
    Configuration-management tools are infrastructure with blast radius. Compare how each tool fails, how each tool rolls back, and how easily your team can prove what happened.

## Quick Comparison

| Question | Ansible | Salt |
| --- | --- | --- |
| Default connection model | Agentless SSH push from a control node | Master-minion model with persistent agents |
| First usable workflow | Inventory plus ad hoc commands or playbooks | Master setup, minion enrollment, then state or remote execution |
| Strength | Simple adoption, readable playbooks, broad community examples | Fast remote execution, event-driven automation, large-fleet control |
| Common bottleneck | Control node SSH fan-out, slow tasks, inconsistent host access | Master/minion trust, key management, agent health, control-plane complexity |
| Best fit | Smaller or moderate fleets, app deployment, repeatable admin tasks, teams new to CM | Larger fleets, frequent remote execution, event-driven jobs, teams comfortable operating agents |
| Safety habit | `--check`, `--diff`, `--limit`, small batches | `test=True`, target limits, state output review, staged minion targeting |

## Architecture Tradeoffs

Ansible's agentless model is its biggest adoption advantage. If a host accepts SSH and Python is available, you can often start with a simple inventory and a playbook. That also means the control node must connect to every target, authentication must be healthy, and large fan-out jobs can become slow or fragile.

Salt normally uses a master-minion design. Minions maintain a relationship with the master, which makes remote execution and high-scale targeting fast after the control plane is running. The tradeoff is that you now operate a distributed service: minion keys, master availability, version compatibility, job returns, and event bus behavior all matter.

## Change Workflow

For Ansible, the safe workflow often looks like this:

```bash
ansible-inventory --graph
ansible web --list-hosts
ansible-playbook site.yml --check --diff --limit web-canary
ansible-playbook site.yml --limit web-canary
ansible-playbook site.yml --limit web
```

For Salt, the matching workflow often looks like this:

```bash
salt-key --list accepted
salt 'web-canary*' test.ping
salt 'web-canary*' state.apply test=True
salt 'web-canary*' state.apply
salt 'web*' state.apply
```

In both tools, the important habit is not the exact command syntax. The habit is to prove targeting first, preview the change when the tool supports it, apply to a narrow group, verify the result, and then expand.

## What to Evaluate Before Choosing

Start with the fleet shape:

- How many hosts do you manage today, and how fast does that number change?
- Are hosts long-lived servers, short-lived instances, containers, or appliances?
- Can every host accept inbound SSH from a control node?
- Is an installed agent acceptable under your security and patching model?

Then evaluate the team:

- Which tool can the team read and review confidently during an incident?
- Who will own the control node, secrets, inventory, and CI checks?
- How will changes be peer reviewed before they touch production?
- How will failed runs be detected, paused, rolled back, and explained?

Finally, evaluate evidence:

- Can you list exactly which hosts a change will target?
- Can you preview changes before applying them?
- Can you show before-and-after service state, package versions, file diffs, and logs?
- Can you separate "tool failed to connect" from "target host applied the wrong state"?

## Risk and Failure Modes

With Ansible, watch for SSH credential drift, privilege-escalation surprises, inventory mistakes, playbooks that are not idempotent, and long-running jobs that partially complete across a fleet. The safest Ansible environments keep inventories in version control, run playbooks through CI syntax checks, and use limits for staged rollouts.

With Salt, watch for stale minion keys, compromised masters, unexpected target globbing, version mismatch between master and minions, and event-driven jobs that run faster than humans can review. The safest Salt environments treat the master as critical infrastructure, monitor minion health, and require narrow targeting for high-risk states.

Both tools can damage production quickly when targeting is wrong. Prefer host groups that map to real rollout rings such as `lab`, `canary`, `staging`, and `production`, not vague labels that invite broad changes.

## Hands-on Practice

Use a disposable VM, container lab, or documentation-only exercise. Do not run new configuration-management tooling against production for this lesson.

1. Pick a simple desired state, such as "install `curl`" or "ensure `chrony` is enabled."
2. Write the Ansible command sequence you would use to preview, limit, apply, and verify the change.
3. Write the Salt command sequence you would use to test targeting, preview, apply, and verify the same change.
4. For each tool, write down the most likely failure and the evidence that would prove it happened.
5. Choose one tool for a 20-host fleet and one tool for a 5,000-host fleet. Explain the operational reason for each choice.
