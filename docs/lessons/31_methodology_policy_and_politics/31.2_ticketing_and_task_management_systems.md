## 31.2 Ticketing and Task Management Systems 🎟️

Ticketing is how operational work survives beyond memory, chat, and hallway conversations. A good ticket tells the next person what happened, why it mattered, what changed, how it was verified, and what still needs attention.

For Linux administrators, tickets are not just project-management paperwork. They are part of incident response, change control, audit evidence, customer support, team coordination, and personal accountability.

!!! abstract "What you will learn"
    - Explain why ticketing matters in Linux operations.
    - Write useful tickets for incidents, changes, requests, and follow-ups.
    - Separate symptoms, evidence, decisions, actions, and verification.
    - Avoid common ticketing habits that create confusion or hidden risk.
    - Connect ticket records to handoffs, audits, and future troubleshooting.

!!! success "Operator principle"
    A ticket is useful when another qualified person can continue the work without guessing.

## Why Tickets Matter

Linux work often starts with a symptom:

- users cannot log in
- a deployment failed
- disk usage crossed a threshold
- backups stopped completing
- a certificate is near expiration
- a manager requested a new access group
- an auditor asked for evidence

Without a durable record, the team loses context. The same problem gets rediscovered, risky commands are repeated, and decisions become hard to defend later.

A ticket provides a shared place for:

- the problem statement
- scope and impact
- ownership
- priority
- timestamps
- evidence
- actions taken
- approvals
- rollback notes
- links to logs, dashboards, pull requests, or runbooks
- final verification
- follow-up tasks

## Ticket Types

Different ticket types need different information.

| Type | Purpose | Useful fields |
| --- | --- | --- |
| Incident | Restore service or reduce impact | impact, start time, affected users, symptoms, timeline, mitigation, recovery evidence |
| Service request | Fulfill a known operational request | requester, approval, target system, exact request, completion evidence |
| Change | Modify production or a shared system | reason, plan, risk, window, rollback, approval, validation |
| Problem | Investigate recurring or root causes | related incidents, hypothesis, findings, permanent fix |
| Project task | Track planned delivery work | goal, owner, dependencies, acceptance criteria |
| Follow-up | Capture work discovered during another task | source ticket, why it matters, next action |

Many tools support these categories directly. Even when they do not, you can still write the ticket so the category is obvious.

## Anatomy of a Good Operations Ticket

A strong ticket usually includes:

- Title: specific enough to understand at a glance.
- Context: why the work exists.
- Scope: systems, users, environments, and services involved.
- Impact: what is broken or at risk.
- Evidence: commands, logs, monitoring data, screenshots, or user reports.
- Plan: intended steps and safety boundaries.
- Owner: who is responsible right now.
- Status: current truth, not optimism.
- Verification: how success was proven.
- Follow-up: what remains after the immediate work.

Weak title:

```text
Server issue
```

Better title:

```text
Investigate high disk usage on prod-web-03 /var after log growth alert
```

Weak update:

```text
Fixed.
```

Better update:

```text
Rotated oversized app debug log on prod-web-03, confirmed /var usage dropped from 94% to 61%, and restarted only the app worker process. Follow-up opened to reduce debug log volume before the next deploy.
```

## Evidence Beats Vibes

Tickets should preserve evidence, not just conclusions. For Linux work, useful evidence often includes commands such as:

```bash
hostnamectl
systemctl status nginx --no-pager
journalctl -u nginx --since "30 minutes ago" --no-pager
df -h
free -m
ss -tulpn
ip addr
curl -I https://example.com
```

Do not paste secrets, private keys, tokens, full customer data, or sensitive log payloads into tickets. Redact carefully and link to approved secure storage when needed.

## Status Is a Contract

Ticket status should reflect reality:

- New: not yet triaged.
- Triaged: understood enough to assign priority and owner.
- In progress: someone is actively working it.
- Blocked: progress requires a specific input, access, approval, or dependency.
- Waiting: action is pending outside the team.
- Ready for review: work is done but needs verification or approval.
- Done: acceptance criteria are met and evidence is recorded.

Do not mark work done because the command ran. Mark it done when the result was verified.

## Ticketing and Change Control

For production changes, the ticket should answer:

- What will change?
- Why is the change needed?
- Who approved it?
- When will it happen?
- What systems are affected?
- What is the rollback plan?
- What monitoring or user check proves success?
- What will happen if rollback fails?

A change ticket is not a guarantee that nothing will go wrong. It is proof that the team thought about risk before acting.

## Handoffs

Tickets are especially important when work crosses shifts or teams. A good handoff update should include:

```text
Current state:
Impact:
What I checked:
What I changed:
Result:
Blocker:
Next action:
Owner:
```

This format is simple, but it prevents a lot of confusion.

## Common Mistakes

Avoid these patterns:

- vague titles
- updates that say "looking into it" without evidence
- missing affected hostnames or environments
- closing tickets without verification
- mixing several unrelated problems into one ticket
- leaving a blocked ticket without naming the blocker
- using private chat as the only source of truth
- pasting secrets into ticket comments
- creating follow-up work but never linking it

## Tool Examples

Common ticketing and task-management tools include Jira, Asana, GitHub Issues, GitLab Issues, ServiceNow, Linear, Trello, and Bugzilla. The exact tool matters less than the discipline:

- write clear titles
- preserve evidence
- keep status current
- link related work
- record decisions
- close only after verification

## Hands-On Practice

On a lab machine, create a mock ticket for a disk-space alert.

1. Run:

   ```bash
   hostname
   df -h
   du -sh /var/log 2>/dev/null
   journalctl --disk-usage 2>/dev/null
   ```

2. Write a ticket update with:

   - symptom
   - affected host
   - current disk usage
   - most likely source of growth
   - safe next action
   - verification command

3. Write a follow-up ticket title for preventing the issue from recurring.
