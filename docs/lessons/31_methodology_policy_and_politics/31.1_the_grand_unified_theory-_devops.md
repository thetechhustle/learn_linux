## 31.1 The Grand Unified Theory: DevOps

!!! abstract "What you will learn"
    - Explain DevOps as shared responsibility for building, shipping, operating, and improving systems.
    - Connect Linux administration work to change control, automation, monitoring, and incident response.
    - Identify the evidence a team should collect before and after a production change.
    - Practice a small release note that includes commands, verification, rollback, and ownership.

!!! example "Field story"
    A development team wants to deploy a new API version on Friday afternoon. Operations is worried because the last release filled a filesystem, restarted the service twice, and left no clear owner for the rollback. A DevOps-minded team does not solve this by saying "developers can deploy anything" or "operations must approve everything." It agrees on a repeatable release path: observable service health, reviewed infrastructure changes, a tested rollback, and a shared definition of done.

!!! success "Operator principle"
    DevOps is not a job title or a toolchain. It is the discipline of making change fast enough for the business and controlled enough for production.

## What DevOps means in practice

DevOps combines development and operations so that software changes, infrastructure changes, and production ownership are handled as one system. Developers understand how their code behaves in production. Operators understand how the application is built, released, monitored, and recovered. Both groups care about the same outcomes:

- A change can be reviewed before it reaches production.
- The deployment process is repeatable instead of improvised.
- Infrastructure is described in version-controlled code where practical.
- Logs, metrics, traces, and alerts show whether the service is healthy.
- Incidents produce fixes to code, automation, documentation, or process.

The point is not to erase specialties. Database administrators, network engineers, security teams, SREs, application developers, and Linux operators still bring different skills. DevOps works when those specialties share enough context to prevent handoff gaps.

## The Linux operator's part

Linux operators often meet DevOps through routine production work: restarting services, reviewing logs, applying packages, provisioning hosts, writing scripts, and explaining failures. In a healthy DevOps flow, that work is tied to a visible change record and a measurable service outcome.

Before a change, collect enough state to know what normal looks like:

```bash
hostnamectl
systemctl status nginx --no-pager
journalctl -u nginx --since "30 minutes ago" --no-pager
df -h
ss -ltnp
```

After a change, run the same checks plus an application-level test:

```bash
systemctl is-active nginx
curl -I http://localhost/
journalctl -u nginx --since "5 minutes ago" --no-pager
```

Those commands do not make a team "DevOps" by themselves. They become part of DevOps when the output is attached to a ticket, pull request, deployment record, incident timeline, or runbook so the next person can understand what changed.

## Common DevOps practices

DevOps usually shows up as a set of practical habits.

| Practice | What it means for Linux operations |
| --- | --- |
| Version control | Scripts, service files, configuration templates, and infrastructure definitions are reviewed before use. |
| Infrastructure as Code | Servers, networks, packages, and cloud resources are described with tools such as Ansible, Terraform, cloud-init, or vendor APIs. |
| Continuous integration | Automated checks run before a change is accepted. For operations code, that might include linting, syntax checks, dry runs, and test deployments. |
| Continuous delivery | Release steps are automated enough that deployments are boring, repeatable, and easy to audit. |
| Observability | Logs, metrics, traces, health checks, and dashboards make service behavior visible. |
| Blameless review | Incidents are studied to improve systems and decisions, not to find someone to punish. |

Good DevOps culture makes risky work more visible. It does not mean every change is safe, every deployment is automatic, or every operator must become a full-time software engineer.

## Change flow

A simple DevOps change flow can look like this:

1. Describe the user-facing problem or desired improvement.
2. Propose the code, configuration, package, or infrastructure change.
3. Run automated checks.
4. Review the change with the people who own the affected service.
5. Deploy to a non-production environment when possible.
6. Deploy to production during an agreed window or controlled rollout.
7. Verify service health with commands, dashboards, and user-facing checks.
8. Record the result and update the runbook if the process changed.

For Linux work, the most valuable detail is often the verification step. A deployment note that says "restarted nginx" is weak. A note that includes the service state, recent logs, listener check, HTTP status, and rollback command is much stronger.

## Safety and rollback

DevOps should reduce emergency improvisation. Before changing a production Linux system, know how you will return to a known-good state.

Examples:

- Keep the previous package version available before upgrading.
- Back up a configuration file before editing it by hand.
- Use `systemctl reload` instead of `restart` when the service supports safe reloads.
- Run a syntax check before loading a new configuration.
- Stage firewall, SSH, and network changes from a console or with an automatic rollback timer.

For example, an nginx configuration change should include a syntax check before reload:

```bash
sudo nginx -t
sudo systemctl reload nginx
systemctl status nginx --no-pager
```

If `nginx -t` fails, stop. Do not reload a known-bad configuration just to see what happens.

## DevOps failure modes

DevOps can go wrong when a team treats the label as a shortcut.

- "Everyone owns it" becomes "nobody is accountable."
- Automation spreads a bad change faster than a human could.
- Dashboards exist, but no one knows which signals matter.
- CI passes, but production prerequisites are undocumented.
- Developers can deploy, but operators are paged for failures they cannot reproduce.
- Post-incident reviews produce action items that are never tracked.

The fix is not more slogans. The fix is clearer ownership, better checks, smaller changes, and evidence that the service actually improved.

## Hands-on practice

Run these on a disposable VM, container, or lab machine.

1. Pick one local service, such as `ssh`, `cron`, `nginx`, or a small test service you created earlier.
2. Record a baseline:

    ```bash
    systemctl status SERVICE --no-pager
    journalctl -u SERVICE --since "15 minutes ago" --no-pager
    ```

3. Make a harmless change in a sandbox, such as editing a test service description, changing a non-production config value, or adding a comment to a copied configuration file.
4. Run the relevant syntax check or service validation command.
5. Reload or restart only if the validation passes.
6. Write a five-line deployment note:

    ```text
    Change:
    Reason:
    Commands run:
    Verification:
    Rollback:
    ```
