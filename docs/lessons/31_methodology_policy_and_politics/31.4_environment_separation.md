## 31.4 Environment Separation

Environment separation means keeping development, test, staging, and production work in distinct places with distinct access, data, configuration, and risk. It is not just a software-engineering idea. Linux operators use it every time they test a package update on a disposable host, validate a systemd unit before touching production, or keep production credentials out of a lab shell.

The goal is simple: make it easy to learn and validate without putting real users, real data, or real business commitments at risk.

!!! abstract "What you will learn"
    - Explain why production should be harder to change than development or test.
    - Identify the boundaries that separate Linux environments.
    - Inspect a host for clues about which environment it belongs to.
    - Plan a low-risk promotion path from test to production.
    - Avoid common environment-separation failures.

!!! warning "Production data is production risk"
    Test systems often become dangerous when they contain real customer data, real credentials, or real network access. If production data must be copied into a lower environment, sanitize it first and document who approved the copy.

## Common environment types

Most organizations use some mix of these environments:

- **Development:** Fast iteration, incomplete work, local experiments, and frequent breakage.
- **Test:** Automated or manual validation against expected behavior.
- **Staging:** A production-like environment used for release rehearsal, migration testing, and final checks.
- **Production:** The live environment that serves users, customers, partners, or business operations.
- **Disaster recovery:** A standby environment used when the primary production path fails.

Smaller teams may combine some of these. That is normal. What matters is that everyone knows which environment is safe for experiments and which one requires change control.

## What must be separated

Environment separation is more than hostnames.

| Boundary | Why it matters |
| --- | --- |
| Accounts and permissions | A developer account should not imply production root access. |
| Secrets and keys | Test credentials must not unlock production databases, APIs, or SSH hosts. |
| Data | Lower environments should not expose sensitive production records. |
| Network paths | Test systems should not be able to accidentally call production dependencies. |
| Package and image sources | A test repository can carry candidate builds; production should consume approved versions. |
| Configuration | Debug flags, log levels, feature toggles, and endpoints often differ by environment. |
| Monitoring and alerting | Production alerts need urgency; lab alerts should not wake people unnecessarily. |
| Backup and retention | Production retention rules may be legally or contractually defined. |

If two environments share all of these boundaries, they are probably not separate in any meaningful operational sense.

## Linux clues that identify an environment

When you log in to a host, verify where you are before changing anything.

```bash
hostnamectl
hostname -f
ip addr show
ip route
cat /etc/os-release
systemctl --type=service --state=running
```

Useful local conventions include:

- hostnames such as `web-prod-01`, `api-stage-02`, or `db-dev-03`
- `/etc/motd` or shell prompts that show the environment
- cloud tags, VM labels, or inventory fields
- configuration files under `/etc`, `/opt`, or application-specific paths
- monitoring labels such as `env=prod` or `environment=staging`

Do not trust a name alone. Confirm with inventory, DNS, network ranges, cloud metadata, or the deployment system before running a risky command.

## A safer promotion path

A production change should have an evidence trail. A simple path looks like this:

1. Make the change in development or a disposable lab.
2. Record the exact package version, image digest, commit, config diff, or migration file.
3. Run automated tests or documented manual checks.
4. Promote the same artifact to staging.
5. Validate staging with production-like configuration and realistic dependencies.
6. Schedule the production change through the ticket or change process.
7. Apply the change during the approved window.
8. Verify service health, logs, metrics, and user-facing behavior.
9. Record the result and rollback status.

The safest promotion process moves the same artifact forward. Rebuilding a package or container differently for production creates a new, untested thing.

## Example: checking before a package update

Before updating a production service, gather environment evidence:

```bash
hostname -f
grep -R "environment" /etc /opt 2>/dev/null | head
systemctl status nginx --no-pager
apt-cache policy nginx 2>/dev/null || dnf info nginx
```

Then write a short note:

```text
Host: web-prod-02
Environment evidence: hostname, inventory tag env=prod, production subnet
Change: upgrade nginx from 1.24.0-2 to 1.24.0-3
Test evidence: same package passed on web-stage-01
Rollback: reinstall previous package from internal repo and restore config backup
Verification: systemctl status nginx, curl health endpoint, check error logs and 5xx rate
```

That note is small, but it proves you knew where you were, what you changed, and how to recover.

## Common failure patterns

- **Production credentials in test:** A test job deletes, emails, bills, or modifies real production records.
- **Staging that is nothing like production:** The release passes staging but fails because package versions, network rules, or data volume differ.
- **Manual production-only fixes:** A change is made directly on production and never backported to source control or automation.
- **Shared mutable configuration:** One config file, bucket, or database setting affects multiple environments.
- **Ambiguous hostnames:** Operators cannot tell whether they are on test or production.
- **No rollback artifact:** The team knows how to deploy forward but not how to return to the last known good state.
- **Alerts without environment labels:** A test failure pages the on-call team as if it were a production incident.

## Practical controls

Use simple controls before complex ones:

- put the environment in hostnames, prompts, monitoring labels, and inventory
- require separate credentials for production
- keep production secrets out of developer laptops and CI logs
- use separate cloud accounts, projects, subscriptions, or resource groups when possible
- restrict production network access with firewalls, security groups, and VPN rules
- deploy through automation instead of manual shell history
- keep configuration in version control or a managed configuration system
- make rollback steps part of the change ticket

Environment separation should slow down risky work just enough to prevent accidents. If it makes routine safe work impossible, people will route around it.

## Hands-on practice

Use two disposable VMs, containers, or cloud instances. Name one `app-dev` and one `app-prod-sim`.

1. Add an environment marker to each host:

   ```bash
   echo "ENVIRONMENT=dev" | sudo tee /etc/environment-role
   ```

   Use `prod-sim` on the second host.

2. Add a login warning on the production simulation host:

   ```bash
   printf 'PRODUCTION SIMULATION - verify ticket before changes\n' | sudo tee /etc/motd
   ```

3. Create a simple service config in both environments:

   ```bash
   sudo install -d -m 0755 /etc/demoapp
   printf 'log_level=debug\n' | sudo tee /etc/demoapp/demoapp.conf
   ```

4. Change the production simulation config to use `log_level=info`.

5. Compare the two environments:

   ```bash
   hostname
   cat /etc/environment-role
   cat /etc/motd 2>/dev/null
   cat /etc/demoapp/demoapp.conf
   ```

6. Write a short promotion note that explains which config value should move from development to production simulation, how you would validate it, and how you would roll it back.
