## 31.5 Disaster Management

Disaster management is the discipline of keeping an outage from becoming a
surprise. A Linux administrator cannot prevent every hardware failure, bad
deploy, cloud-region issue, ransomware event, or accidental deletion. The
administrator can make sure the team knows what matters, where the recovery
evidence lives, who makes decisions, and how to restore service without
inventing the plan during the incident.

This lesson focuses on practical disaster management for Linux operations. The
goal is not a thick binder that nobody opens. The goal is a short, tested
recovery path that can survive stress.

!!! abstract "What you will learn"
    - Define disaster management in operational terms.
    - Separate incidents, disasters, backups, and disaster recovery plans.
    - Identify the Linux evidence needed during recovery.
    - Build a useful disaster recovery plan.
    - Test backups and recovery procedures instead of trusting them blindly.
    - Record recovery decisions so the next incident is easier to handle.

## What Counts as a Disaster?

In operations, a disaster is an event that threatens a service, a business
process, or important data enough that normal troubleshooting is no longer
sufficient.

Examples include:

- a storage array or cloud volume failure
- a database corruption event
- a bad deploy that destroys production data
- a ransomware or credential-compromise event
- a region, building, or network outage
- accidental deletion of critical configuration or customer records
- loss of monitoring, access, or control-plane systems during another incident

Not every outage is a disaster. A single failed service may be a routine
incident if it can be restarted safely. It becomes disaster-management work
when restoration requires a coordinated plan, recovery point decisions,
alternate infrastructure, executive communication, or legal/compliance review.

## Incident, Backup, and Recovery Terms

Teams often use disaster-related words loosely. Precision helps during stress.

| Term | Meaning |
| --- | --- |
| Incident | An unplanned interruption or degradation that needs response. |
| Disaster | A severe incident where normal repair is insufficient or too slow. |
| Backup | A copy of data or configuration kept for restoration. |
| Restore | The act of putting data or systems back from a backup or replica. |
| Recovery point objective (RPO) | How much data loss the organization can tolerate. |
| Recovery time objective (RTO) | How long the organization can tolerate the service being down. |
| Disaster recovery plan (DRP) | The written recovery procedure, roles, dependencies, and decision points. |
| Business continuity plan | The larger plan for continuing business operations while systems recover. |

RPO and RTO are not technical decorations. They decide what kind of backups,
replication, standby systems, staffing, and cost are justified.

## Start with Service Inventory

You cannot recover what you have not identified. A useful disaster plan begins
with a service inventory.

For each important service, record:

- service name and owner
- purpose and users
- production hostnames
- DNS names and load balancer entries
- data stores and filesystem paths
- systemd unit names or container/orchestrator objects
- credentials and secret locations
- upstream and downstream dependencies
- backup location, frequency, and retention
- RPO and RTO
- recovery procedure link
- last successful restore test

On Linux hosts, collect basic service evidence with commands such as:

```bash
hostnamectl
ip -brief address
systemctl list-units --type=service --state=running
systemctl list-timers --all
df -h
lsblk -f
mount
ss -tulpn
```

These commands do not replace documentation. They help verify whether the
documentation still describes reality.

## Backups Are Not Recovery

A backup that has never been restored is a hope, not a recovery capability.
Backups matter, but disaster management depends on the full recovery chain:

1. The backup was created.
2. The backup is complete enough to restore the service.
3. The backup is protected from the same failure that damaged production.
4. Someone can find the correct backup under pressure.
5. Someone can restore it to a working environment.
6. The restored service can be validated by application-level checks.

Common Linux backup tools and patterns include:

- `rsync` for file synchronization
- `tar` for archive creation
- `borg` or `restic` for deduplicated encrypted backups
- filesystem or volume snapshots
- database-native dumps such as `pg_dump` or `mysqldump`
- object-storage lifecycle policies
- configuration stored in Git

The right tool depends on the service. A static documentation site, a database,
and a VM image do not have the same recovery needs.

## Backup Verification

Verification should be routine and boring.

Useful checks include:

```bash
# Confirm a backup file exists and has recent modification time.
ls -lh /backup
find /backup -type f -mtime -1 -ls

# Inspect archive contents without extracting them.
tar -tf site-backup.tar.gz | head

# Compare two directory trees.
rsync -navi /srv/app/ /mnt/restore-test/app/

# Check a systemd backup timer.
systemctl list-timers --all
systemctl status backup.timer

# Review backup logs.
journalctl -u backup.service --since "24 hours ago"
```

These are still surface checks. A restore test is stronger because it proves the
backup can become a running service again.

## Disaster Recovery Plan Structure

A useful DRP is short enough to follow and specific enough to execute.

A practical structure is:

1. **Scope**
   - What service or business process this plan covers.
   - What the plan does not cover.

2. **Severity trigger**
   - Conditions that activate the DRP.
   - Who can declare the disaster.

3. **Roles**
   - Incident commander.
   - Technical recovery lead.
   - Communications lead.
   - Business decision maker.

4. **Dependencies**
   - DNS, identity provider, cloud account, network, storage, secrets, vendors,
     and monitoring systems.

5. **Recovery objectives**
   - RTO and RPO.
   - Data-loss decision process.

6. **Recovery steps**
   - Exact commands or linked runbooks.
   - Expected output or validation checks.
   - Rollback or stop conditions.

7. **Communication plan**
   - Internal status channel.
   - Customer or stakeholder update owner.
   - Escalation contacts.

8. **Validation**
   - Technical checks.
   - Application checks.
   - Business-owner signoff.

9. **Post-incident work**
   - Timeline.
   - Root-cause follow-up.
   - Documentation and backup updates.

## Recovery Command Discipline

During a disaster, commands should be copied from known-good procedures when
possible. If a command is improvised, write it down before or immediately after
running it.

Prefer commands that:

- inspect before changing
- use explicit paths
- avoid shell globs in destructive contexts
- run in a restore target before production
- produce logs or transcripts
- can be peer-reviewed quickly

Risky examples include:

```bash
rm -rf /some/path
mkfs.ext4 /dev/sdb
rsync --delete source/ destination/
kubectl delete ...
terraform apply
```

These commands may be legitimate, but in disaster recovery they need clear
target confirmation and a written reason.

## Restore Testing

A restore drill should answer a concrete question:

- Can we restore the database to a clean host?
- Can we rebuild the web service from Git and configuration backups?
- Can we recover if the primary region is unavailable?
- Can we restore without the original administrator's laptop?
- Can we prove which data was lost?

A simple restore test record should include:

```text
Service:
Date:
Backup source:
Restore target:
Person running test:
Commands used:
Validation checks:
RTO observed:
RPO observed:
Problems found:
Follow-up tickets:
```

The most valuable restore tests are not perfect. They expose missing secrets,
stale documentation, unclear ownership, firewall gaps, and backup assumptions
before a real disaster does.

## Linux Evidence During a Disaster

When a serious outage starts, preserve enough evidence to support recovery and
post-incident analysis.

Useful first-pass evidence:

```bash
date -Is
hostnamectl
uptime
systemctl --failed
journalctl -p warning..alert --since "2 hours ago"
df -h
lsblk -f
free -h
ip route
ss -tulpn
last -a | head
```

For storage or data incidents, collect extra context before making changes:

```bash
mount
findmnt
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT,UUID
dmesg -T | tail -100
```

For security-related disasters, preserve logs and avoid destroying evidence.
Security incidents may require legal, compliance, insurance, or law-enforcement
coordination. Do not "clean up" a compromised system before the response lead
decides how evidence should be handled.

## Communication Matters

Technical recovery is only part of disaster management. People need to know
what is happening, what is uncertain, and when the next update will arrive.

A useful status update includes:

- current impact
- affected users or services
- what is being done now
- what is not yet known
- next update time
- current decision needed, if any

Avoid speculative root cause language during the live response. "We are seeing
database connection failures and are restoring from the 03:00 backup" is better
than "the database is gone" when the evidence is not complete.

## Common Failure Patterns

Disaster plans fail for predictable reasons:

- backups exist but credentials to access them are missing
- restore steps depend on one person's memory
- DNS TTLs and certificate renewal are forgotten
- monitoring and paging depend on the failed environment
- backup retention does not match business needs
- test restores use small toy data instead of realistic volumes
- secrets are backed up insecurely or not backed up at all
- recovery documentation names old hosts, old paths, or retired vendors
- no one has authority to accept data loss

These are management problems as much as technical problems. The Linux
administrator's job is to make the operational truth visible.

## Hands-on Practice

Use a disposable VM, container, or lab directory.

1. Create a small service directory:

   ```bash
   mkdir -p ~/dr-lab/service
   printf 'version 1\n' > ~/dr-lab/service/app.txt
   ```

2. Create a timestamped backup:

   ```bash
   mkdir -p ~/dr-lab/backups
   tar -czf ~/dr-lab/backups/service-$(date +%Y%m%d%H%M%S).tar.gz -C ~/dr-lab service
   ```

3. Simulate damage:

   ```bash
   printf 'bad change\n' > ~/dr-lab/service/app.txt
   ```

4. Restore to a separate target first:

   ```bash
   mkdir -p ~/dr-lab/restore-test
   tar -xzf "$(ls -t ~/dr-lab/backups/service-*.tar.gz | head -1)" -C ~/dr-lab/restore-test
   cat ~/dr-lab/restore-test/service/app.txt
   ```

5. Write a short restore note:

   ```text
   Backup used:
   Restore target:
   Validation:
   Would this meet the RTO/RPO?
   ```

The habit matters more than the toy example: back up, restore somewhere safe,
validate, and document what happened.
