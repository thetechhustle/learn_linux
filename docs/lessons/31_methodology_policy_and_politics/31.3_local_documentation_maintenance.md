## 31.3 Local Documentation Maintenance 📚

Local documentation is the operating memory of a Linux environment. It explains how a system is supposed to work, how it actually works today, and what an operator should do when something changes or breaks.

Good documentation is not a museum. It is part of the system. If it is stale, hard to find, or disconnected from real operations, people stop trusting it.

!!! abstract "What you will learn"
    - Identify the documentation that Linux operators need most.
    - Keep local documentation accurate as systems change.
    - Use simple checks to find stale or risky documentation.
    - Write runbooks, service notes, and handoff records that help during real work.
    - Treat documentation updates as part of the change, not a separate chore.

!!! success "Operator principle"
    Documentation is healthy when it helps the next operator make a correct decision faster.

## What Counts as Local Documentation

Local documentation can live in several places:

- repository `README.md` files
- `docs/` directories
- internal wikis
- runbooks
- architecture notes
- service ownership pages
- incident reports
- change tickets
- shell scripts with clear usage output
- configuration comments
- local `man` pages
- onboarding notes
- diagrams and dependency maps

The location matters less than whether the team can find the current source of truth.

## What Operators Need

For each important service, useful documentation answers:

- What does this service do?
- Who owns it?
- Where does it run?
- How do users reach it?
- What are its dependencies?
- How is it deployed?
- How is it monitored?
- What does healthy look like?
- How do you restart it safely?
- How do you roll back?
- Where are logs stored?
- What secrets or credentials are involved?
- What should never be done without approval?

If those answers only exist in one person's memory, the service is fragile.

## Documentation Types

Different documents solve different problems.

| Document type | Purpose | Example |
| --- | --- | --- |
| README | First orientation point | how to run a project locally |
| Runbook | Repeatable operations procedure | restart service, rotate cert, recover disk space |
| Architecture note | Explain design and dependencies | why Redis is required and where it runs |
| Decision record | Preserve why a choice was made | why Postfix was chosen over Exim |
| Incident report | Capture what happened and what changed | outage timeline and follow-up actions |
| Inventory | Record assets and ownership | hosts, IPs, services, ports |
| Policy | Define required behavior | backup retention, access review, change approval |

Do not force everything into one giant document. Small, focused documents are easier to keep current.

## Signs Documentation Is Stale

Stale documentation usually leaves clues:

- hostnames no longer resolve
- commands reference deleted files or old paths
- screenshots show retired interfaces
- service names do not match `systemctl`
- links return 404
- setup steps fail on a clean machine
- owners listed in the doc left the team
- "temporary" notes are months old
- tickets repeatedly ask questions the docs claim to answer

When documentation is wrong, fix the document or mark it clearly as stale. Silent wrongness is worse than absence.

## Linux Checks for Documentation Accuracy

You can verify many documentation claims directly:

```bash
hostnamectl
systemctl list-units --type=service --state=running
systemctl status nginx --no-pager
ss -tulpn
ip addr
ip route
df -h
mount
crontab -l
ls -la /etc/systemd/system
grep -R "old-hostname" docs/ README.md
```

Use read-only checks first. Do not run destructive commands just to prove a runbook.

## Runbook Structure

A practical runbook should include:

```text
Purpose:
Applies to:
Owner:
Prerequisites:
Risk level:
When to use:
When not to use:
Steps:
Verification:
Rollback:
Escalation:
Last tested:
```

The `When not to use` section is important. It prevents a runbook from being applied blindly to the wrong situation.

## Documentation and Change Management

When a change modifies how a system works, update the documentation in the same change when possible.

Examples:

- A service port changes: update the service README, firewall notes, and monitoring checks.
- A cron job is replaced by a systemd timer: update the runbook and troubleshooting notes.
- A deployment path changes: update the release procedure.
- A new backup target is added: update recovery documentation and retention notes.

A common rule is: if the command, path, owner, dependency, or recovery step changed, the docs probably changed too.

## Source of Truth

Teams get into trouble when multiple documents disagree. For each subject, decide where truth lives:

- repo docs for code-specific behavior
- infrastructure inventory for hosts and network facts
- runbooks for operational procedures
- ticket history for one-time decisions and evidence
- policy docs for required behavior

Then link between them instead of copying the same paragraph everywhere.

## Writing Style

Good operational documentation is:

- specific
- current
- searchable
- versioned when possible
- written for the next operator
- honest about limits
- clear about risk
- easy to skim during pressure

Prefer direct language:

```text
Run this on the primary database host only.
```

Avoid vague language:

```text
Run this where appropriate.
```

## Hands-On Practice

Pick a lab service or a simple local process and write a one-page runbook.

1. Identify the service:

   ```bash
   systemctl list-units --type=service --state=running
   ```

2. Choose one harmless service to document.

3. Capture:

   - purpose
   - owner or assumed owner
   - status command
   - log command
   - restart command
   - verification command
   - rollback or escalation note

4. Test the read-only commands in the runbook.

5. Add a `Last tested` line with today's date.
