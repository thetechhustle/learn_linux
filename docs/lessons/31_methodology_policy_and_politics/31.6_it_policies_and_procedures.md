## 31.6 IT Policies and Procedures

IT policies and procedures turn scattered operational judgment into repeatable
work. A policy says what must be true. A procedure says how operators make it
true. Good policy does not replace skill; it gives skilled people clear guard
rails when the work is routine, risky, regulated, or urgent.

Linux administrators live inside policy even when nobody says the word
"policy." Password rules, patch windows, backup retention, firewall changes,
production access, logging standards, incident response, and data handling are
all policy areas.

!!! abstract "What you will learn"
    - Separate policies from procedures.
    - Recognize where policies show up in Linux administration.
    - Translate a high-level rule into an operator procedure.
    - Collect evidence that a system follows policy.
    - Avoid common policy failures that slow teams down or create risk.

## Policy Versus Procedure

A policy is a rule or principle. It describes the required outcome.

A procedure is an executable process. It describes the steps people follow.

Examples:

| Policy | Procedure |
| --- | --- |
| Production changes must be reviewed. | Open a change ticket, attach test evidence, get approval, deploy in the window, and record validation. |
| Administrative access must be limited. | Add users to the approved group, configure `sudo`, review membership monthly, and remove stale access. |
| Critical systems must be backed up. | Run the backup job, verify logs, perform a restore test, and record the test result. |
| Security patches must be applied within a defined window. | Check package advisories, stage updates, apply them in maintenance, reboot if needed, and verify services. |
| Logs must be retained for investigation. | Configure log rotation, forwarding, permissions, retention, and periodic access checks. |

The policy should be stable. The procedure can change as tooling improves.

## Why Policies Matter to Linux Operators

Policies make operations safer when they:

- clarify who can approve risky work
- define what evidence is required before and after a change
- prevent one-off production access from becoming permanent
- make recovery and incident response predictable
- satisfy audit, customer, insurance, or legal requirements
- reduce debates during stressful incidents
- help new team members learn the local operating model

Policies become harmful when they are vague, stale, impossible to follow, or
ignored by senior people. A Linux administrator should be willing to say,
"This policy cannot be executed as written," and then help fix it.

## Common Linux Policy Areas

Linux work frequently intersects with these policy areas.

### Access Control

Questions:

- Who may log in?
- Who may use `sudo`?
- Are shared accounts allowed?
- How quickly must access be removed after role changes?
- Is MFA required for remote access?

Evidence commands:

```bash
getent passwd
getent group sudo
getent group wheel
sudo -l
last -a | head
find /home -maxdepth 2 -name authorized_keys -print
```

### Patch Management

Questions:

- Which systems are in scope?
- How quickly are critical fixes applied?
- Who approves emergency patching?
- When are reboots allowed?
- How is patch success verified?

Evidence commands:

```bash
cat /etc/os-release
uname -a
apt list --upgradable 2>/dev/null | head
dnf check-update 2>/dev/null | head
zypper list-updates 2>/dev/null | head
systemctl list-timers --all
needs-restarting -r 2>/dev/null || true
```

### Change Management

Questions:

- What counts as a change?
- Which changes need review?
- What evidence is required before deployment?
- What is the rollback plan?
- How is success validated?

Evidence commands:

```bash
systemctl status --no-pager
journalctl --since "1 hour ago" -p warning..alert
git log --oneline -5
find /etc -type f -mtime -1 -print
```

### Backup and Retention

Questions:

- What data is backed up?
- How long is it retained?
- Where are backups stored?
- Who can restore?
- When was the last restore test?

Evidence commands:

```bash
systemctl list-timers --all | grep -i backup
journalctl -u backup.service --since "24 hours ago"
find /backup -type f -mtime -2 -ls 2>/dev/null
ls -lh /backup 2>/dev/null
```

### Logging and Monitoring

Questions:

- Which logs must exist?
- Where are logs forwarded?
- How long are logs retained?
- Who can read sensitive logs?
- Which alerts require response?

Evidence commands:

```bash
journalctl --disk-usage
ls -lh /var/log
systemctl status rsyslog 2>/dev/null || true
systemctl status systemd-journald
systemctl list-units '*agent*' --type=service
```

### Data Handling

Questions:

- Which data is sensitive?
- Can production data be copied to development?
- Must data be encrypted at rest?
- How are exports approved and tracked?
- How is data destroyed when no longer needed?

Evidence commands:

```bash
find /srv /var/lib -maxdepth 3 -type f -name '*.sql' -o -name '*.dump' 2>/dev/null
lsblk -f
findmnt
grep -R "password\\|secret\\|token" /etc 2>/dev/null | head
```

The last command is intentionally noisy. Use it carefully on systems you are
authorized to inspect, and do not paste secrets into tickets or chat.

## From Policy to Procedure

A procedure should be specific enough that a qualified teammate can repeat it.

A strong procedure includes:

- purpose
- scope
- prerequisites
- approval requirement
- exact commands or tool links
- expected output
- validation steps
- rollback or stop condition
- evidence to attach to the ticket
- owner and review cadence

Weak procedure:

> Patch the server regularly.

Better procedure:

```text
Procedure: Apply routine security patches to Ubuntu web servers
Scope: Production web servers in group web-prod
Approval: Change ticket approved by service owner
Window: Wednesdays 22:00-23:00 ET

Steps:
1. Confirm host and OS:
   hostnamectl
   cat /etc/os-release
2. Capture pending updates:
   apt list --upgradable
3. Apply updates:
   sudo apt update
   sudo apt upgrade
4. Reboot if required:
   test -f /var/run/reboot-required && sudo systemctl reboot
5. Validate:
   systemctl --failed
   curl -fsS https://service.example.com/health
6. Attach command output and close the change ticket.

Stop condition:
- If package resolver proposes removing critical packages, stop and escalate.
```

## Evidence Beats Assertion

"Compliant" is less useful than "here is the evidence."

Evidence can include:

- command output
- screenshots from management consoles
- CI logs
- ticket approvals
- backup restore test records
- package version reports
- firewall rule exports
- access review lists
- incident timelines

For Linux work, attach evidence that proves the actual system state, not just
the intended state.

Example access review note:

```text
Host: app-prod-03
Date: 2026-05-14
Policy: Only SRE group members may use sudo on production app hosts.
Evidence:
- getent group sudo -> alice,bob
- identity group roster -> alice,bob
Result: compliant
Follow-up: none
```

## Policy Exceptions

Real operations sometimes need exceptions. Exceptions should be visible and
temporary, not hidden.

An exception record should include:

- policy being excepted
- system or user affected
- business reason
- risk
- compensating control
- approver
- expiration date
- follow-up ticket

Example:

```text
Exception: Temporary SSH access for vendor support
System: db-reporting-02
Reason: Vendor troubleshooting query planner issue
Compensating control: restricted source IP, named account, session logging
Approver: database service owner
Expires: 2026-05-17 18:00 ET
Follow-up: remove account and review logs
```

## Procedures During Incidents

Incident procedures should be short. During stress, people need clarity, not a
wall of text.

An incident procedure should answer:

- Who is leading?
- Where is the live incident channel?
- What evidence must be captured first?
- What actions are safe without extra approval?
- What actions require an explicit decision?
- How often are updates sent?
- What is the handoff format?

Policies should not block urgent containment, but urgent containment still
needs notes. "Emergency" is not a reason to lose accountability.

## Common Policy Failures

Watch for these patterns:

- policy says "must" but no procedure exists
- procedure references old hosts, tools, or approval groups
- policy demands evidence nobody knows how to collect
- exceptions never expire
- production and development policy boundaries are unclear
- senior staff bypass the process
- procedure is too long to use during an incident
- compliance work is treated as separate from operations
- no owner is assigned to review the policy

The fix is usually not "write more policy." The fix is to make the policy
executable and test it against real work.

## Hands-on Practice

Use a disposable VM, container, or lab machine.

1. Pick one policy area: access, patching, backups, logging, or change
   management.
2. Write a one-sentence policy.
3. Write a five-step procedure to satisfy that policy.
4. Run at least two read-only Linux commands that would produce evidence.
5. Write a short note showing whether the system appears compliant.

Example lab note:

```text
Policy:
Only approved administrators may use sudo on this host.

Procedure evidence:
- getent group sudo
- sudo -l

Observed:
The sudo group contains alice and bob. The current user has command-specific
sudo access only.

Follow-up:
Compare group members with the approved access roster.
```
