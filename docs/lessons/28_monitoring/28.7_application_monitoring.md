## 28.7 Application Monitoring

Application monitoring asks one practical question: is the application doing
what users, operators, and dependent systems need it to do?

Host monitoring can tell you that the CPU is idle, memory is available, and the
network interface is up. Application monitoring goes one level higher. It checks
request success, latency, background jobs, queues, errors, logs, dependencies,
and business-relevant behavior. A server can look healthy while the checkout
flow, login page, API endpoint, or nightly import is failing.

!!! abstract "What you will learn"
    - Pick application signals that describe user-visible health.
    - Inspect Linux services, logs, ports, and process behavior during an incident.
    - Separate application symptoms from host, network, and dependency causes.
    - Build alerts that point to a specific operator action.

!!! success "Operator principle"
    Monitor symptoms users feel and signals operators can act on.

## Start with the user-facing path

Good application monitoring starts outside the process. Before looking at CPU
or memory, define what a working application means.

Examples:

- The home page returns `200 OK` within an acceptable latency window.
- The login endpoint accepts valid credentials and rejects invalid ones.
- The API returns valid JSON for a known health route.
- The worker queue drains within a normal amount of time.
- The scheduled import finishes before the next business day starts.
- The payment, email, storage, cache, and database dependencies are reachable.

This is why many applications expose a health endpoint such as `/health`,
`/ready`, or `/metrics`. A health endpoint should be useful but conservative.
It should not claim the application is healthy if the app cannot serve its
critical path.

!!! warning "Avoid fake green checks"
    A route that always returns `OK` only proves the web process can answer that
    one route. It does not prove login, database access, background work, or
    user-facing flows are healthy.

## Check the service boundary

On a Linux host, application monitoring often starts by confirming the service
manager, process, and listening socket agree with each other.

```bash
systemctl status myapp --no-pager
systemctl is-active myapp
systemctl show myapp -p MainPID -p Restart -p NRestarts
```

Then confirm the expected process is listening where the rest of the system
expects it to listen.

```bash
ss -ltnp | grep -E '(:80|:443|:8080)\b'
ps -fp "$(systemctl show myapp -p MainPID --value)"
```

These checks answer basic but important questions:

- Is the service active or crash-looping?
- Did systemd restart it recently?
- Is the main PID the expected binary or runtime?
- Is the application bound to the expected address and port?
- Is it listening on `127.0.0.1` when a proxy expects a local backend?
- Is it listening on `0.0.0.0` when it should be private?

## Probe the application directly

Use a direct local probe before blaming load balancers, DNS, clients, or
firewalls.

```bash
curl -i http://127.0.0.1:8080/health
curl -sS -o /dev/null -w 'code=%{http_code} time=%{time_total}\n' \
  http://127.0.0.1:8080/
```

If the app sits behind a reverse proxy, compare the local backend with the
public path.

```bash
curl -sS -o /dev/null -w 'backend code=%{http_code} time=%{time_total}\n' \
  http://127.0.0.1:8080/health

curl -sS -o /dev/null -w 'public code=%{http_code} time=%{time_total}\n' \
  https://example.com/health
```

Different results narrow the fault:

- Backend fails locally: investigate the application process and dependencies.
- Backend works locally, public path fails: investigate proxy, TLS, routing, DNS,
  firewall, or upstream configuration.
- Both work but users report failures: test the exact user path, region, method,
  headers, authentication state, or payload.

## Watch logs with context

Application logs tell you what the process thinks happened. System logs tell you
what the operating system did to the process.

```bash
journalctl -u myapp --since '30 minutes ago' --no-pager
journalctl -u myapp -f
```

For file-based logs:

```bash
tail -n 200 /var/log/myapp/app.log
tail -f /var/log/myapp/app.log
```

Look for:

- startup failures
- configuration parse errors
- permission denied messages
- database connection failures
- timeout messages
- dependency errors
- uncaught exceptions
- repeated retries
- request IDs that match user reports

When an application is behind Nginx, Apache, HAProxy, or another proxy, compare
application logs with proxy logs. A `502` in Nginx might mean the backend is
down, but it can also mean the backend accepted the connection and closed it
unexpectedly.

## Track latency, traffic, errors, and saturation

Application monitoring usually groups signals into four practical categories:

| Signal | What it tells you | Example |
| --- | --- | --- |
| Traffic | How much work is arriving | requests per second, jobs per minute |
| Errors | How much work is failing | HTTP 5xx rate, exception count |
| Latency | How long work takes | p95 request time, queue age |
| Saturation | How close the app is to a limit | worker pool full, DB pool exhausted |

These are useful because they describe both symptoms and capacity pressure. A
server with low CPU can still have terrible application latency if it is waiting
on a slow database, blocked queue, exhausted thread pool, or remote API.

## Check dependencies explicitly

Many application incidents are dependency incidents. The application may be
running correctly but unable to reach what it needs.

Common checks include:

```bash
getent hosts db.internal.example
nc -vz db.internal.example 5432
nc -vz redis.internal.example 6379
curl -I https://api.vendor.example/status
```

For local Unix sockets:

```bash
ss -lx | grep myapp
ls -l /run/myapp/
```

Dependency monitoring should distinguish between:

- DNS failure
- TCP connection failure
- TLS or certificate failure
- authentication failure
- slow response
- valid response with application-level error

Each points to a different owner and next action.

## Monitor background work

Web requests are only one part of many applications. Background workers,
scheduled jobs, message queues, imports, exports, and notification senders need
monitoring too.

Useful signals include:

- oldest queued job age
- queue depth
- failed job count
- retry count
- worker process count
- last successful scheduled run
- duration of the last batch
- number of records processed

For systemd timers:

```bash
systemctl list-timers --all
systemctl status myapp-import.timer --no-pager
systemctl status myapp-import.service --no-pager
journalctl -u myapp-import.service --since today --no-pager
```

For cron jobs, check both the schedule and the logs:

```bash
crontab -l
grep CRON /var/log/syslog | tail -n 50
```

!!! note "Silent jobs are risky"
    A scheduled job that only logs on failure may look quiet when it never ran.
    Monitor the last successful run time, not just failure output.

## Use process tools carefully

Linux tools can explain what an application is doing right now.

```bash
top -H -p "$(pgrep -n myapp)"
pmap -x "$(pgrep -n myapp)" | tail -n 20
lsof -p "$(pgrep -n myapp)" | head
```

For deeper diagnosis:

```bash
strace -p "$(pgrep -n myapp)" -tt -f
```

`strace` can reveal repeated failed opens, DNS lookups, socket timeouts, and
permission problems. It can also add overhead and produce sensitive data, so use
it briefly and intentionally on production systems.

Performance counters can help during CPU-heavy incidents:

```bash
perf stat -p "$(pgrep -n myapp)" sleep 10
```

Use these tools to answer a specific question. Do not attach heavy diagnostics
to a production process just because the tool is available.

## Alert on action, not noise

An application alert should tell the responder what is broken and what to check
next.

Weak alert:

> CPU high on app server.

Better alert:

> Checkout API p95 latency above 2 seconds for 10 minutes; error rate normal;
> database pool wait time elevated.

The better alert points toward a dependency or pool-saturation investigation.
It also avoids waking someone for a short spike that users may never feel.

Good application alerts usually include:

- affected service
- affected user path
- current value
- threshold
- duration
- recent deploy or config change if known
- first dashboard or log link to check
- runbook link or owner

## Build a small evidence trail

During an incident, save enough evidence for the next operator to continue
without starting over.

```text
Application:
User-visible symptom:
Start time:
Recent deploy/config change:
Local health check:
Public health check:
Error rate:
Latency:
Queue state:
Dependency checks:
Recent log pattern:
Action taken:
Result:
Next owner:
```

This format is simple, but it prevents vague handoffs such as "the app is down"
or "looks like networking."

## Hands-on practice

On a lab host or disposable VM:

1. Start a small web application or use an existing local service.
2. Identify its systemd service, process ID, and listening port.
3. Probe the local endpoint with `curl`.
4. Review the last 50 log lines for the service.
5. Stop or misconfigure one dependency in a reversible way.
6. Capture how the health check, logs, and latency changed.
7. Restore the dependency and prove the application recovered.

Write a short incident note using the evidence template above.
