## 28.5 Network Monitoring

Network monitoring tells you whether traffic can reach the service, how it behaves on the path, and where evidence points when users report slowness, timeouts, or intermittent failures. Good network checks start with the user symptom and then move through DNS, routing, transport, service ports, packet loss, latency, and traffic volume.

!!! abstract "What you will learn"
    - Separate reachability, latency, throughput, packet loss, and service exposure signals.
    - Use Linux tools such as `ip`, `ss`, `ping`, `mtr`, `tcpdump`, and `nmap` to collect network evidence.
    - Capture packet and port data safely without flooding a host or exposing sensitive payloads.
    - Turn network observations into actionable incident handoff notes.

!!! example "Field story"
    A web application is healthy on the server, but users in one office report timeouts. The application logs show nothing unusual. Network monitoring helps you compare local reachability, DNS answers, route path, packet loss, connection states, and firewall exposure before blaming the application.

!!! success "Operator principle"
    Monitor the network from the user's path to the service, not just from inside the server.

## Start with the question

Pick the smallest question that matches the symptom:

- **Can the host resolve the name?** Check DNS answers and resolver behavior.
- **Can packets reach the destination?** Check routes, gateways, packet loss, and latency.
- **Is the service listening?** Check local sockets and expected bind addresses.
- **Can clients complete a connection?** Check firewall rules, SYN/SYN-ACK behavior, and connection states.
- **Is the path saturated or unstable?** Check interface counters, retransmits, throughput, and recurring loss.

Avoid starting with packet captures unless simpler signals are inconclusive. Captures are powerful, but they can also collect credentials, customer data, and large files quickly.

## Local interface and route checks

Begin on the Linux host that owns or consumes the service.

```sh
ip -brief address
ip route
ip -s link
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

Useful evidence includes:

- Interface names and assigned addresses.
- The default route and gateway.
- Error, dropped, or overrun counters from `ip -s link`.
- Resolver configuration and search domains.

When an interface counter is climbing, record two samples a few seconds apart. A single snapshot proves the counter exists; repeated growth proves the issue is active.

```sh
ip -s link show dev eth0
sleep 10
ip -s link show dev eth0
```

## Listening ports and connection states

Use `ss` to confirm that the expected process is listening on the expected address and port.

```sh
ss -tulpen
ss -tan state established
ss -tan state syn-sent
ss -tan state time-wait
```

Interpret the address carefully:

- `127.0.0.1:8080` means only local clients can connect.
- `0.0.0.0:8080` means the service listens on all IPv4 interfaces.
- `[::]:8080` means the service listens on IPv6 and may also accept IPv4 depending on system settings.

During incidents, `syn-sent` often points to a client that cannot complete outbound connections. Many `time-wait` sockets can be normal on busy clients, but sudden growth may indicate connection churn.

## Reachability, latency, and path tests

Use read-only probes first.

```sh
ping -c 5 example.com
tracepath example.com
mtr --report --report-cycles 20 example.com
```

`ping` shows basic ICMP loss and latency, but many networks deprioritize or block ICMP. `tracepath` and `mtr` help identify where latency or loss appears along the route. Treat intermediate-hop loss carefully: if later hops are clean, the intermediate device may only be rate-limiting probe replies.

For TCP services, test the actual port instead of only testing ICMP.

```sh
nc -vz example.com 443
curl -I --connect-timeout 5 https://example.com/
```

Record the source host, destination, protocol, port, time, and result. Network evidence without vantage point is hard to compare.

## Packet captures

Use `tcpdump` when you need to prove what packets are entering or leaving an interface.

```sh
sudo tcpdump -i eth0 -nn 'host 203.0.113.10 and tcp port 443'
sudo tcpdump -i eth0 -nn -c 100 -w network-incident.pcap 'tcp port 443'
```

Safer capture habits:

- Filter by host, port, or protocol before writing to disk.
- Use `-c` to limit packet count.
- Use `-s 96` when headers are enough and payload is unnecessary.
- Store captures with restricted permissions.
- Do not paste packet payloads into tickets unless they have been reviewed for secrets.

Packet captures answer concrete questions: Did the SYN leave? Did the SYN-ACK return? Are resets coming from the server, client, or middlebox? Are packets retransmitting?

## Bandwidth and traffic volume

For quick interactive checks, tools such as `iftop`, `nload`, `bmon`, and `sar` can show interface traffic. On many systems, `sar` comes from the `sysstat` package and may need collection enabled.

```sh
sar -n DEV 1 5
sar -n TCP,ETCP 1 5
```

Look for:

- Interface utilization near link capacity.
- TCP retransmits increasing during the complaint window.
- One host or flow consuming unexpected bandwidth.
- Drops or errors growing at the same time as user symptoms.

Traffic volume alone is not health. A quiet interface can still be broken, and a busy interface can be healthy if latency, loss, and service response are normal.

## Port scanning and exposure checks

Use port scanning only against systems you own or have permission to test. Start with a narrow target and expected ports.

```sh
nmap -Pn -p 22,80,443 server.example.com
```

Compare scanner results with local socket data from the server:

```sh
ss -tulpen
```

If `ss` shows a service listening but `nmap` reports the port filtered or closed, investigate host firewall rules, cloud security groups, network ACLs, load balancers, or routing.

## Intrusion and abuse signals

Network monitoring often overlaps with security monitoring. Useful signals include:

- Unexpected open ports.
- Repeated failed connection attempts.
- Large outbound traffic from a host that should be quiet.
- Connections to unusual destinations.
- Firewall blocks or intrusion detection alerts.

Tools such as Fail2Ban, Suricata, Zeek, Snort, firewall logs, and cloud flow logs can help, but alerts must be tied to a clear action. A useful alert identifies the affected host, source, destination, service, evidence, and next step.

## Incident handoff note

Use a short template when handing off network evidence:

```text
Symptom:
Vantage point:
Destination and service:
Time window:
DNS result:
Route/path result:
Port/connectivity result:
Packet loss/latency:
Interface counters:
Packet capture path, if any:
Likely boundary:
Next action:
```

The "likely boundary" might be client network, DNS, host firewall, cloud load balancer, upstream provider, service process, or unknown. Naming the boundary keeps the next responder from repeating the same broad checks.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Record local interface, route, resolver, and listening-port state:
   ```sh
   ip -brief address
   ip route
   ss -tulpen
   ```
2. Pick one reachable test host and compare ICMP with a TCP service check:
   ```sh
   ping -c 5 example.com
   nc -vz example.com 443
   ```
3. Capture only DNS packets while running one lookup:
   ```sh
   sudo tcpdump -i any -nn -c 20 'port 53'
   ```
4. Write an incident handoff note that states what worked, what failed, and which boundary you would investigate next.
