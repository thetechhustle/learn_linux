## 28.4 Data Collection

!!! abstract "What you will learn"
    - Decide which system signals are worth collecting before an incident happens.
    - Collect Linux metrics, logs, and state snapshots without making the outage worse.
    - Preserve enough context that another operator can verify your conclusion later.
    - Separate useful monitoring evidence from noisy or expensive data.

Monitoring begins with a simple promise: when the system changes, you will have enough evidence to notice, understand, and respond.

Data collection is the part of monitoring that keeps that promise. It turns CPU counters, disk queues, journal entries, process lists, service states, and network statistics into an evidence trail. Without that trail, an incident becomes guesswork. With it, you can compare normal behavior to broken behavior and make safer decisions.

Good collection is selective. Collect too little and you miss the failure. Collect everything without a plan and you drown the team in noise, cost, and privacy risk.

## Start With The Question

Before adding a collector, ask what decision the data will support.

Useful monitoring questions sound like this:

- Is the service reachable?
- Is the host saturated?
- Is storage filling or failing?
- Are errors increasing?
- Did a deployment change behavior?
- Is the problem local to one host or shared across many hosts?
- Can the on-call person prove what happened after the fact?

Weak monitoring questions are vague:

- Can we collect more data?
- Can we make a bigger dashboard?
- Can we store every log forever?

The first set leads to action. The second set usually leads to cost and clutter.

## Main Data Types

Linux monitoring data usually falls into four practical groups.

### Metrics

Metrics are numeric measurements over time. They are good for trends, thresholds, and comparisons.

Common host metrics include:

- CPU usage, load average, context switches, and run queue pressure.
- Memory usage, swap activity, page faults, and cache behavior.
- Disk space, inode usage, I/O latency, queue depth, and throughput.
- Network throughput, packet drops, retransmits, and interface errors.
- Process counts, file descriptor usage, and service-specific counters.

Metrics answer questions such as "Did latency rise when CPU saturation started?" or "Did disk space run out before the service failed?"

### Logs

Logs are event records. They are good for cause, sequence, and human-readable error messages.

Common Linux log sources include:

- `journalctl` for systemd journal entries.
- `/var/log/syslog` or `/var/log/messages` on syslog-based systems.
- `/var/log/auth.log` or `/var/log/secure` for authentication events.
- Service-specific logs under `/var/log/`.
- Application logs written to stdout, files, or a logging platform.

Logs answer questions such as "What error did the service report?" or "Which account tried to authenticate?"

### State Snapshots

State snapshots capture the current shape of the system. They are useful during incidents because they preserve facts that may disappear after a restart.

Examples include:

```bash
systemctl --failed
systemctl status nginx --no-pager
ps -eo pid,ppid,stat,pcpu,pmem,comm --sort=-pcpu | head
ss -tulpen
df -h
df -ih
ip addr
ip route
```

Snapshots answer questions such as "What was listening on port 443?" or "Which filesystem was full?"

### Traces And Request Paths

Traces follow work across services. A single Linux host may not need distributed tracing, but multi-service systems often do.

Tracing helps answer:

- Which service was slow?
- Which downstream dependency failed?
- Did one user request fan out into excessive work?
- Did retries amplify the incident?

For smaller systems, a request ID in logs may be enough. For larger systems, OpenTelemetry-style traces can connect frontend, API, worker, database, and queue activity.

## Local Collection Commands

Start with read-only local commands. They are fast, reversible, and useful even before a full monitoring platform exists.

### CPU And Load

```bash
uptime
top -b -n1 | head -n 20
mpstat 1 5
vmstat 1 5
```

Look for high load with idle CPU, high I/O wait, runaway processes, or a run queue that stays above the number of CPU cores.

### Memory

```bash
free -h
vmstat 1 5
cat /proc/meminfo | head -n 20
```

Look for active swap use, allocation failures in logs, and services killed by the OOM killer.

Useful log check:

```bash
journalctl -k --since "1 hour ago" | grep -i 'out of memory\|oom'
```

### Disk And Filesystems

```bash
df -h
df -ih
lsblk
iostat -xz 1 5
```

Look for full filesystems, inode exhaustion, high disk latency, and devices with persistent utilization near 100 percent.

### Network

```bash
ip addr
ip route
ss -tulpen
ss -s
ip -s link
```

Look for missing addresses, wrong routes, unexpected listeners, packet drops, and connection states piling up.

### Services

```bash
systemctl --failed
systemctl status ssh --no-pager
journalctl -u ssh --since "30 minutes ago" --no-pager
```

Replace `ssh` with the service you are investigating. Capture both service status and recent logs. Status without logs is often too shallow; logs without status can miss restart loops.

## Timestamp Everything

Monitoring evidence is strongest when it has time context.

At the start of an investigation, record:

```bash
date -Is
hostnamectl --static
uptime
```

When copying evidence into an incident note, include:

- Hostname.
- Time zone or UTC timestamp.
- Command run.
- Short output excerpt.
- What you concluded from it.

This matters because dashboards, logs, deploy systems, and human reports often use different clocks. Time alignment is how you connect symptoms to causes.

## Keep Collection Safe

Most collection commands are read-only, but not all collection is harmless.

Be careful with:

- Packet captures, because they may contain credentials, tokens, or private payloads.
- Large recursive filesystem scans on unhealthy disks.
- Debug logging on busy services, because it can increase load or fill disks.
- Very high-cardinality labels in metrics, such as user IDs, request IDs, or full URLs.
- Long log retention without a privacy, security, and cost policy.

Safer practice:

- Start with summaries before deep captures.
- Limit packet captures by interface, host, port, size, and time.
- Use short debug windows and turn debug logging off afterward.
- Redact secrets before pasting logs into tickets or chat.
- Store incident bundles somewhere access-controlled.

Example bounded packet capture:

```bash
sudo tcpdump -i eth0 host 192.0.2.10 and port 443 -c 100 -w /tmp/incident-443.pcap
```

That command still needs care, but it is safer than an unlimited capture of all traffic.

## Choose Collection Intervals

Collection frequency affects usefulness and cost.

Use short intervals for:

- CPU, memory, disk I/O, and network troubleshooting during an active incident.
- Lab diagnosis where you are watching a change happen.
- Temporary high-resolution views around a deployment.

Use longer intervals for:

- Capacity planning.
- Long-term disk growth.
- Monthly service reliability reporting.
- Historical baselines.

A metric collected every 60 seconds can miss a 5-second spike. A metric collected every second can become expensive across thousands of hosts. Choose the interval based on the decision you need to make.

## Build A Small Evidence Bundle

During an incident, a useful bundle is better than a giant dump.

Example Linux host bundle:

```bash
mkdir -p /tmp/incident-$(hostname)-$(date +%Y%m%dT%H%M%S)
cd /tmp/incident-*

date -Is > 00-time.txt
hostnamectl > 01-hostnamectl.txt
uptime > 02-uptime.txt
systemctl --failed > 03-systemd-failed.txt
df -h > 04-df-h.txt
df -ih > 05-df-ih.txt
ss -tulpen > 06-listeners.txt
ps -eo pid,ppid,stat,pcpu,pmem,comm --sort=-pcpu | head -n 30 > 07-top-processes.txt
journalctl -p warning --since "2 hours ago" --no-pager > 08-warnings.txt
```

Review the files before sharing them. Logs and command output can contain hostnames, internal IPs, usernames, paths, tokens, or customer data.

## From Local Commands To Monitoring Systems

Local commands prove what is happening now. Monitoring systems preserve what happened before you logged in.

A practical progression looks like this:

1. Use local commands to understand which signals matter.
2. Add host agents or exporters for the signals you need repeatedly.
3. Store metrics centrally with labels for host, service, environment, and role.
4. Ship logs centrally with timestamps, hostnames, service names, and severity.
5. Add alerts only when the signal has an owner and a response.
6. Review noisy or unused data and remove it.

Do not start with the biggest possible platform. Start with the operational questions and collect the data that answers them.

## Label Data Carefully

Labels make data searchable and comparable. Bad labels make it noisy or expensive.

Good labels:

- `host`
- `service`
- `environment`
- `region`
- `cluster`
- `device`
- `status`

Risky labels:

- full request URLs
- user IDs
- session IDs
- unbounded error strings
- customer names
- raw IP addresses when privacy policy forbids it

High-cardinality labels can make metrics systems slow and costly. Put detailed request IDs in logs or traces, not in every metric label.

## Practice: Collect A Host Health Baseline

Use a lab VM or disposable system.

1. Record the host identity and time:

   ```bash
   date -Is
   hostnamectl --static
   uptime
   ```

2. Collect basic health signals:

   ```bash
   df -h
   df -ih
   free -h
   ss -tulpen
   systemctl --failed
   journalctl -p warning --since "1 hour ago" --no-pager
   ```

3. Write a short baseline note:

   ```text
   Host:
   Time:
   Services checked:
   Disk concern:
   Memory concern:
   Network concern:
   Recent warning/error concern:
   Follow-up:
   ```

4. Pick one signal that should be collected continuously and explain why.
