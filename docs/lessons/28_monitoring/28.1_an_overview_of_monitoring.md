### 28.1 An Overview of Monitoring

!!! abstract "What you will learn"
    - Explain monitoring as an operational feedback loop, not just a dashboard.
    - Separate symptoms, signals, alerts, and evidence during an incident.
    - Identify the first Linux host checks that help you decide where to look next.
    - Describe the difference between monitoring for availability, performance, capacity, and security.

Monitoring is the practice of collecting system evidence early enough that an operator can notice risk, explain behavior, and take action before users lose trust. A good monitoring setup answers four practical questions:

1. Is the service reachable?
2. Is it behaving within normal limits?
3. Is anything getting worse?
4. Who needs to do what next?

That means monitoring is not only software. It is also ownership, thresholds, dashboards, alert routing, runbooks, and habits around reviewing the data.

## The Monitoring Loop

Most monitoring work follows the same loop:

1. **Collect** signals from hosts, services, applications, and network devices.
2. **Store** those signals somewhere operators can search and compare them.
3. **Visualize** the current and historical state.
4. **Alert** when a condition needs human or automated action.
5. **Investigate** with logs, metrics, events, traces, and direct system checks.
6. **Improve** thresholds, dashboards, automation, and documentation after incidents.

If the loop stops at collection, you have data but not operations. If it stops at alerting, you have noise but not learning. The point is to make the next incident easier to understand than the last one.

## Symptoms, Signals, And Evidence

A symptom is what someone experiences:

- "The site is slow."
- "SSH keeps disconnecting."
- "The database timed out."
- "The upload failed."

A signal is measurable data that may explain the symptom:

- CPU saturation
- memory pressure
- disk latency
- full filesystems
- packet loss
- error rate
- queue depth
- certificate expiry
- failed login bursts

Evidence is the specific output you can hand to another operator:

```bash
uptime
free -h
df -h
ss -tuna
systemctl --failed
journalctl -p warning..alert --since "30 minutes ago"
```

Good monitoring narrows the distance between symptom and evidence.

## Core Monitoring Categories

Most environments monitor several overlapping categories.

| Category | What It Answers | Linux Examples |
| --- | --- | --- |
| Availability | Is it up and reachable? | ping, HTTP checks, service status |
| Performance | Is it fast enough? | CPU load, memory, disk I/O, latency |
| Capacity | Are we running out of room? | disk usage, inode usage, queue depth |
| Reliability | Is it failing too often? | error rate, restart count, failed jobs |
| Security | Is something suspicious happening? | auth failures, new listeners, file changes |
| Business or user impact | Are users blocked? | failed transactions, signups, payments |

Do not treat these as separate worlds. A disk filling up can become a performance issue, then an availability issue, then an incident.

## What To Check First On A Linux Host

When monitoring points you at a Linux host, start with broad read-only checks before making changes:

```bash
hostnamectl
uptime
top -b -n 1 | head -20
free -h
df -h
df -ih
ss -tulpn
systemctl --failed
journalctl -p err..alert --since "1 hour ago"
```

These commands help answer:

- Is the machine overloaded?
- Is memory exhausted or swapping?
- Is a filesystem full?
- Are expected services listening?
- Did systemd record failed units?
- Are recent logs showing errors that match the user symptom?

You do not need every command every time. Build a habit of gathering enough evidence to choose the next check deliberately.

## Metrics, Logs, Events, And Traces

Modern monitoring usually combines several evidence types:

- **Metrics** are numeric measurements over time: CPU percent, request latency, disk usage, error counts.
- **Logs** are timestamped messages from systems and applications.
- **Events** are notable changes: deploys, restarts, failovers, configuration changes.
- **Traces** follow one request across services.

Metrics often tell you that something changed. Logs and events often explain why. Traces help when one user-facing request crosses many services.

For Linux administration, you should be comfortable moving between all of them. A dashboard may show CPU pressure, but `journalctl`, `systemctl`, and application logs often explain which process or change caused it.

## Alerts Need Action

An alert should point to a decision or action. A weak alert says:

> CPU is high.

A stronger alert says:

> Web node `web-03` has CPU above 95 percent for 10 minutes, request latency is above target, and the current runbook is `docs/runbooks/web-latency.md`.

Useful alerts usually include:

- affected host or service
- severity
- time window
- current value and threshold
- user impact if known
- link to dashboard or logs
- runbook or owner

Noise teaches operators to ignore alerts. Make alerts specific, actionable, and reviewed after incidents.

## Dashboards Are Not Runbooks

A dashboard should help you see state quickly. A runbook should help you act correctly. Do not confuse them.

A dashboard can show:

- service health
- traffic
- error rates
- latency
- saturation
- deploy markers

A runbook should explain:

- what the alert means
- how to confirm impact
- safe read-only checks
- reversible mitigation steps
- escalation criteria
- what evidence to capture for handoff

When a dashboard raises more questions than it answers, improve the dashboard. When an operator knows what is wrong but not what to do, improve the runbook.

## Monitoring Culture

Monitoring works best when the team treats it as a shared operating system for production decisions:

- Add monitoring when you add a service.
- Review alert quality after incidents.
- Track deploys and maintenance windows as events.
- Keep dashboards aligned with real ownership.
- Remove alerts nobody acts on.
- Teach new operators where to look first.

The goal is not perfect visibility. The goal is enough trustworthy visibility to make better decisions under pressure.

## Hands-on Practice

Use a disposable VM, container, or lab machine.

1. Record a baseline:

   ```bash
   uptime
   free -h
   df -h
   systemctl --failed
   journalctl -p warning..alert --since "15 minutes ago"
   ```

2. Create a short lab note with:

   - hostname
   - time of check
   - load average
   - memory use
   - disk use
   - failed units
   - any recent warnings or errors

3. Pick one signal and explain what would make it alert-worthy.

4. Write one alert sentence that includes the host, condition, time window, possible impact, and first runbook step.
