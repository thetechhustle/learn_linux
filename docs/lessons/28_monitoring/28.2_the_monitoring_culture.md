### 28.2 The Monitoring Culture

Monitoring is not just a tool choice. It is the operating habit of deciding
which signals matter, watching them consistently, and improving the system when
those signals show risk. A team with a healthy monitoring culture can answer
three questions quickly:

- What is broken or close to breaking?
- Who is affected?
- What evidence proves the service is recovering?

The goal is not to collect every possible metric. The goal is to reduce
surprises and shorten diagnosis when a user, service, host, or network path is
unhealthy.

## Start with service behavior

Useful monitoring starts with the service, not the dashboard. Before adding a
new check, write down what "working" means for the system you operate.

For a web application, that might include:

- HTTP requests succeed from the user's network path.
- Response time stays within an agreed range.
- Error rates remain low enough that users are not blocked.
- The host has enough CPU, memory, disk, and network capacity to keep serving
  traffic.
- Logs show no repeated authentication failures, application crashes, or storage
  errors.

For an internal Linux host, that might include:

- The expected services are active.
- Scheduled jobs finish on time.
- Filesystems have enough free space.
- Backups complete and restore tests are recent.
- Security updates and reboots are tracked.

These statements are better than vague goals such as "monitor CPU" because they
tie the signal to a real operating outcome.

## Build an actionable signal set

A strong monitoring culture keeps a small set of high-value signals visible and
well understood. Start with these layers:

| Layer | Example questions | Example Linux evidence |
| --- | --- | --- |
| User experience | Can users reach the service? Is it fast enough? | `curl -fsS -w '%{http_code} %{time_total}\n' https://example.com/` |
| Service state | Are the expected daemons running? | `systemctl --failed`, `systemctl status nginx` |
| Resource pressure | Is the host out of CPU, memory, disk, or I/O? | `uptime`, `free -h`, `df -h`, `iostat -xz 1 3` |
| Logs | Are failures repeating? | `journalctl -p warning..alert --since '1 hour ago'` |
| Change context | Did a deployment, package update, or config change happen? | `git log`, package logs, deployment records |
| Security | Is there suspicious access or unexpected exposure? | `journalctl _COMM=sshd`, `ss -tulpn` |

Avoid dashboards that show hundreds of graphs without an operating decision.
Each visible signal should help someone decide whether to investigate, roll
back, scale, repair, or keep watching.

## Alert on action, not curiosity

An alert should wake or interrupt a human only when human action is expected.
If an alert does not require a decision, make it a dashboard, report, or ticket
instead.

Good alerts usually include:

- A clear symptom: "checkout HTTP 5xx rate is above 2% for 10 minutes."
- Scope: which service, host, region, or job is affected.
- Impact: what users or dependent systems may notice.
- First checks: the next two or three commands or dashboards to inspect.
- Ownership: the team or runbook responsible for the alert.

Weak alerts usually include:

- A raw threshold with no user impact.
- A condition that fixes itself every few minutes.
- A message that requires the operator to guess the service owner.
- A page for a condition no one knows how to remediate.

Tune noisy alerts aggressively. Alert fatigue trains operators to ignore the
monitoring system, which is worse than having fewer alerts that people trust.

## Keep monitoring close to change management

Most incidents are easier to diagnose when operators can see what changed.
During deployments, package upgrades, configuration edits, and firewall changes,
record enough context to correlate the change with monitoring data.

Useful change notes include:

```text
Time:
System or service:
Change made:
Expected result:
Rollback command or plan:
Signals to watch:
Owner:
```

After a change, watch both the service-level symptom and the host-level
resources. For example, a deployment can keep `systemctl status` green while
application latency, memory growth, or error logs show a problem.

## Make handoffs evidence based

During an incident or on-call handoff, do not rely on "looks fine" or "seems
bad." Hand over facts that another operator can verify.

Use a compact format:

```text
Symptom:
User impact:
Start time:
Affected systems:
Current hypothesis:
Evidence checked:
Recent changes:
Actions taken:
Next check:
Escalation owner:
```

Example:

```text
Symptom: API latency above 2 seconds for 18 minutes.
User impact: checkout requests are slow but still completing.
Start time: 14:08 UTC.
Affected systems: api-02 and api-03.
Current hypothesis: database connection pool saturation after deploy 9f31c2a.
Evidence checked: load balancer 5xx rate, journalctl for api.service, database connection count.
Recent changes: api deploy at 14:03 UTC.
Actions taken: paused rollout; restarted api-03 after confirming no active migrations.
Next check: compare latency and connection count for api-02 vs api-03 in 10 minutes.
Escalation owner: payments on-call.
```

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson
explicitly says otherwise.

1. Pick one service on the lab system, such as `ssh`, `cron`, `nginx`, or a
   local test application.
2. Write one sentence that defines what "working" means for that service.
3. Collect service evidence:

   ```bash
   systemctl status ssh --no-pager
   systemctl --failed --no-pager
   ```

4. Collect host evidence:

   ```bash
   uptime
   free -h
   df -h
   journalctl -p warning..alert --since "30 minutes ago" --no-pager
   ```

5. Write a short handoff note with the fields from this lesson.
6. Identify one signal that should page a human and one signal that belongs on a
   dashboard only.
