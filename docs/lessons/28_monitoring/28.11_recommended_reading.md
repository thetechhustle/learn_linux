### 28.11 Recommended Reading

Monitoring changes quickly because tools, vendors, and deployment patterns change quickly. A useful reading list should help you build durable habits: know what signal you need, understand where it comes from, and turn that signal into an action someone can take.

!!! abstract "What you will learn"
    - Choose monitoring references that explain concepts instead of only product screens.
    - Build a reading path for metrics, logs, traces, alerts, network signals, and security monitoring.
    - Convert reading notes into operational improvements for a Linux service.

!!! example "Field story"
    A service team keeps adding dashboards, but incidents still take too long to diagnose. The team pauses to study a smaller set of references: Linux performance methods, SRE alerting principles, Prometheus data modeling, log pipelines, and incident postmortems. Their next dashboard is smaller, their alerts are fewer, and each alert includes the first three commands an operator should run.

!!! success "Operator principle"
    Read with an outcome in mind: better symptoms, better evidence, better alerts, or better incident handoffs.

## Start with monitoring fundamentals

Before diving into a product manual, build a vocabulary for signals and failure modes.

- **Site Reliability Engineering**, edited by Betsy Beyer, Chris Jones, Jennifer Petoff, and Niall Richard Murphy: especially the chapters on monitoring distributed systems, alerting, and incident response.
- **The Site Reliability Workbook**, edited by Betsy Beyer, Niall Richard Murphy, David K. Rensin, Kent Kawahara, and Stephen Thorne: useful for turning SRE ideas into team practices.
- **The Art of Monitoring** by James Turnbull: a practical bridge between service ownership, metrics, logs, and alert design.
- **Monitoring with Prometheus** by James Turnbull: a focused introduction to Prometheus concepts such as exporters, labels, recording rules, and alerting rules.

When you read these, write down the difference between a signal, a symptom, a dashboard, and an alert. Those words shape how you design monitoring later.

## Linux and performance references

Linux monitoring is stronger when you understand what the kernel and system tools are reporting.

- **Systems Performance: Enterprise and the Cloud** by Brendan Gregg: the strongest general reference for CPU, memory, disk, network, and workload analysis.
- **BPF Performance Tools** by Brendan Gregg: useful after you already understand basic Linux performance analysis and want deeper kernel-level visibility.
- **Linux man pages** for `proc(5)`, `systemd-journald.service(8)`, `journalctl(1)`, `ss(8)`, `ip(8)`, `sar(1)`, `pidstat(1)`, `iostat(1)`, and `vmstat(8)`.
- Distribution documentation for systemd, journald, kernel logs, package-maintained service units, and security/audit logging.

Keep these references close when a dashboard shows a number you cannot explain. A graph is only useful when you know what produced it.

## Metrics, logs, and traces

Most production platforms combine several evidence streams.

- Prometheus documentation for metric types, labels, exporters, PromQL, recording rules, and alerting rules.
- Grafana documentation for dashboard design, variables, transformations, and alerting behavior.
- OpenTelemetry documentation for traces, metrics, logs, context propagation, and collector pipelines.
- Elastic, Loki, or similar log-platform documentation for parsing, retention, indexing cost, and search patterns.
- Vendor runbooks for the databases, queues, reverse proxies, and application runtimes you operate.

As you read, look for cost and cardinality warnings. A poorly chosen label, log field, or trace attribute can make a monitoring system noisy, expensive, or slow.

## Network and service monitoring

Network monitoring references should help you separate host, path, DNS, TLS, firewall, and application failures.

- **Network Warrior** by Gary A. Donahue: useful background for real network operations, switching, routing, and troubleshooting.
- `tcpdump`, `wireshark`, `ss`, `ip`, `dig`, `mtr`, and `curl` documentation for command-level evidence gathering.
- SNMP reference material for device discovery, MIBs, OIDs, polling intervals, and trap handling.
- Web server and load balancer docs for Nginx, Apache HTTP Server, HAProxy, Envoy, and cloud load balancers.

Build a small checklist from these sources: name resolution, route, connection, TLS, HTTP status, latency, retries, and server-side logs.

## Security monitoring references

Security monitoring overlaps with Chapter 27, but it adds a monitoring question: what change should make an operator investigate?

- Linux audit documentation for `auditd`, audit rules, event interpretation, and log forwarding.
- Distribution security guides for authentication logs, sudo logs, package integrity, kernel updates, and service hardening.
- CIS Benchmarks and vendor hardening guides for baseline expectations.
- Incident-response references from CISA, NIST, and cloud providers for detection, containment, evidence handling, and reporting.
- Tool documentation for fail2ban, AIDE, Wazuh, osquery, Suricata, Zeek, and EDR agents if they are used in your environment.

Do not copy every suggested rule into production. Start with high-value events: privileged account changes, repeated authentication failures, unexpected listening services, suspicious scheduled tasks, and disabled logging.

## Alerting and incident response

Monitoring is not finished until someone knows what to do with the signal.

- SRE alerting guidance on symptoms, service-level objectives, error budgets, and paging thresholds.
- Incident-response runbooks from your organization or from mature public examples.
- Postmortem collections from engineering organizations that publish concrete incident lessons.
- On-call handoff templates that include impact, current status, timeline, evidence, active mitigations, and next decision point.

Good alerting reading should make you remove weak alerts, not only add new ones.

## Reading-to-action note

Use this short note whenever you read a monitoring reference:

```text
Source:
Operational idea:
Signal or symptom:
Linux evidence command:
Dashboard or alert change:
Risk, cost, or noise concern:
How I would test it in a lab:
```

The goal is to turn reading into one small improvement: a better command in a runbook, a clearer graph, a lower-noise alert, or a stronger incident handoff.

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Pick one monitoring reference from this page.
2. Extract one monitoring idea that applies to CPU, memory, disk, network, logs, or application health.
3. Find the Linux command or log source that can prove the signal exists.
4. Write a short reading-to-action note using the template above.
5. Explain how you would avoid turning that signal into a noisy alert.
