### 28.9 SNMP: The Simple Network Management Protocol

SNMP is one of the older protocols in a monitoring stack, but it still matters.
Routers, switches, firewalls, printers, UPS devices, storage arrays, PDUs,
environmental sensors, and some Linux servers can expose useful operational
state through SNMP.

SNMP is most useful when you need to poll many devices for a small set of
structured counters: interface traffic, errors, device uptime, CPU load, fan
state, temperature, disk usage, or vendor-specific hardware health. It is less
useful as a replacement for logs, traces, application metrics, or modern
agent-based telemetry.

    - Explain what SNMP agents, managers, communities, OIDs, and MIBs do.
    - Query SNMP data safely from a Linux host.
    - Recognize the security differences between SNMPv1, SNMPv2c, and SNMPv3.
    - Decide when SNMP is the right monitoring source and when it is not.

!!! success "Operator principle"
    Treat SNMP as a read-mostly telemetry interface. Keep write access rare,
    authenticated, and tightly scoped.

## The SNMP model

SNMP uses a manager-agent model.

| Component | Role |
| --- | --- |
| Managed device | The router, switch, server, printer, UPS, sensor, or appliance being monitored. |
| Agent | The SNMP-speaking service on the managed device. It exposes management data. |
| Manager or NMS | The monitoring system that polls agents and stores or alerts on the data. |
| OID | An object identifier, such as a dotted numeric path, that names a specific value. |
| MIB | A management information base that maps OIDs to readable names and structure. |

An OID is like an address inside the device's management tree. For example, one
OID may represent system uptime while another represents inbound bytes on a
network interface.

MIB files make OIDs easier for humans to read. Without MIBs, tools may show long
numeric identifiers. With MIBs, they can show names such as `sysUpTime` or
`ifInOctets`.

## SNMP versions and security

SNMP version choice is an operational security decision.

| Version | Authentication | Encryption | Practical guidance |
| --- | --- | --- | --- |
| SNMPv1 | Community string | No | Legacy only. Avoid for new deployments. |
| SNMPv2c | Community string | No | Common for read-only polling on trusted management networks, but still weak. |
| SNMPv3 | User-based auth | Optional privacy encryption | Preferred when supported, especially across less trusted networks. |

SNMPv1 and SNMPv2c community strings are not passwords in the modern sense. They
are shared strings, often sent without encryption. If an attacker can capture or
guess a community string, they may be able to read device data. If write access
is enabled, the risk is much worse.

!!! warning "Do not expose SNMP broadly"
    SNMP should usually be limited to a management network, VPN, monitoring
    subnet, or specific manager IPs. Do not leave UDP port `161` open to the
    internet.

## Install Linux SNMP tools

On Debian or Ubuntu systems, the client tools are usually provided by the
`snmp` package:

```bash
sudo apt update
sudo apt install snmp
```

On Red Hat family systems:

```bash
sudo dnf install net-snmp-utils
```

On many systems, MIB loading is disabled or incomplete by default. You can still
query numeric OIDs without MIBs, which is often enough for troubleshooting.

## Confirm network reachability

SNMP normally uses UDP port `161` for polling and UDP port `162` for traps.
Because UDP does not behave like TCP, a simple port check is not always
conclusive. Start with basic reachability and routing.

```bash
ping -c 3 192.0.2.10
ip route get 192.0.2.10
```

Then check whether the path and firewall rules make sense from the monitoring
host.

```bash
sudo tcpdump -ni any host 192.0.2.10 and udp port 161
```

Run the SNMP query in another terminal while `tcpdump` is watching. If packets
leave but no replies return, investigate device ACLs, firewall policy,
community/user configuration, routing, and management-interface binding.

## Query basic device information

For SNMPv2c, a read-only query looks like this:

```bash
snmpget -v2c -c public 192.0.2.10 1.3.6.1.2.1.1.1.0
```

That numeric OID is commonly `sysDescr.0`, a description of the device or agent.
Another useful check is system uptime:

```bash
snmpget -v2c -c public 192.0.2.10 1.3.6.1.2.1.1.3.0
```

For SNMPv3 with authentication and privacy enabled, the command is longer:

```bash
snmpget -v3 -l authPriv \
  -u monitor-user \
  -a SHA -A 'auth-passphrase' \
  -x AES -X 'privacy-passphrase' \
  192.0.2.10 1.3.6.1.2.1.1.3.0
```

Avoid putting real credentials into shared shell history, screenshots, tickets,
or documentation. Use environment handling or your monitoring system's secret
store when available.

## Walk a subtree carefully

`snmpwalk` asks for a subtree of values.

```bash
snmpwalk -v2c -c public 192.0.2.10 1.3.6.1.2.1.1
```

This walks the system information subtree. Walking a small subtree is useful.
Walking a large vendor tree against many devices can be noisy and expensive.

For interface data:

```bash
snmpwalk -v2c -c public 192.0.2.10 1.3.6.1.2.1.2.2.1.2
```

That subtree commonly lists interface descriptions. Once you know the interface
index, you can query counters such as inbound and outbound octets.

## Understand counters

SNMP often returns counters, not ready-made rates. For example, an interface byte
counter increases over time. A monitoring system turns that into a rate by
comparing the current value with the previous value and dividing by elapsed time.

This matters because:

- a single counter reading rarely tells the whole story
- counter wrap can make a rate look wrong
- polling intervals affect how visible short spikes are
- device reboots reset many counters
- interface index changes can confuse historical graphs

For modern high-speed interfaces, prefer 64-bit interface counters when the
device supports them.

## Use traps with care

Polling means the monitoring system asks the device for state. Traps mean the
device sends an event to the monitoring system.

Traps can be useful for hardware events, link changes, UPS alerts, and vendor
faults. They should not be your only source of truth. UDP traps can be lost, and
devices can send noisy or poorly documented events.

Good practice:

- poll critical state on a regular interval
- accept traps as extra evidence
- rate-limit noisy trap sources
- document the trap source, severity, and expected operator action

## Configure Linux as an SNMP agent

Linux can expose local host metrics through `snmpd`, usually from the Net-SNMP
project. On Debian or Ubuntu:

```bash
sudo apt install snmpd
systemctl status snmpd --no-pager
```

Configuration commonly lives in:

```text
/etc/snmp/snmpd.conf
```

For a lab, you might bind the agent only to localhost and use a read-only
community:

```text
agentaddress 127.0.0.1,[::1]
rocommunity public 127.0.0.1
```

Then restart and query locally:

```bash
sudo systemctl restart snmpd
snmpget -v2c -c public 127.0.0.1 1.3.6.1.2.1.1.3.0
```

For production, prefer SNMPv3, restrict source IPs, and avoid broad write
permissions.

## Troubleshooting checklist

When SNMP polling fails, move through the layers:

1. Is the target IP correct?
2. Is the device reachable from the monitoring host?
3. Is UDP `161` allowed by host, network, and device ACLs?
4. Is the SNMP agent enabled on the correct interface?
5. Are the version and credentials correct?
6. Is the community or SNMPv3 user read-only?
7. Does `tcpdump` show requests leaving and replies returning?
8. Are MIB problems only affecting names, or is the actual query failing?
9. Did the device reboot or change interface indexes?
10. Is the polling interval too aggressive for the device?

Capture enough evidence to distinguish authentication failure, network failure,
agent failure, and naming/MIB confusion.

## When SNMP is the right tool

Use SNMP when:

- the device does not support a modern metrics exporter
- you need standard interface counters from network gear
- the vendor exposes useful hardware health OIDs
- you are integrating legacy devices into a central monitoring platform
- polling small structured counters is enough

Use another method when:

- you need application traces or request-level details
- logs are the primary evidence
- the device has a supported Prometheus, OpenTelemetry, or vendor API exporter
- SNMP would require weak community strings across an untrusted network
- write operations would create unacceptable risk

## Hands-on practice

On a disposable VM or lab host:

1. Install SNMP client tools.
2. Query a known SNMP-capable lab device or localhost `snmpd`.
3. Retrieve `sysDescr` and `sysUpTime`.
4. Walk a small subtree, not the entire device.
5. Run `tcpdump` while querying and confirm request/reply flow.
6. Change one safe lab setting, such as binding `snmpd` to localhost only.
7. Prove the expected query succeeds or fails based on that change.
8. Write an incident note using the evidence template above.
