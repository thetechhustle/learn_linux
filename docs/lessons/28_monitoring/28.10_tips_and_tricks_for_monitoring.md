### 28.10 Tips and Tricks for Monitoring

!!! abstract "What you will learn"
    - Turn raw metrics and logs into signals that help during real incidents.
    - Build baselines, alerts, dashboards, and notes that reduce guesswork.
    - Avoid common monitoring mistakes such as noisy thresholds, missing labels, and dashboards nobody trusts.

!!! example "Field story"
    A web server is slow every weekday morning. CPU is high, but only for a few minutes. The old alert fires after the peak has already ended, nobody knows whether this is normal, and the dashboard shows twenty graphs with no owner. Better monitoring does not start with more graphs. It starts with a baseline, a useful alert, and a short note that explains what to check first.

!!! success "Operator principle"
    Good monitoring turns surprise into evidence. Every alert should point to a symptom, a likely owner, and a first diagnostic step.

## Start with the service promise

Monitoring works best when it begins with what users and operators care about.

Ask these questions before adding another check:

- What does healthy look like for this service?
- What user-visible symptom should wake someone up?
- Which team or person can act on the signal?
- Which command or dashboard should they open first?
- What is normal during business hours, backups, deploys, and maintenance?

For a Linux host, the first promise might be simple:

- SSH accepts logins for administrators.
- The application process is running.
- The expected TCP port is listening.
- The disk has enough free space and inodes.
- CPU, memory, and I/O pressure stay within normal ranges.
- Logs do not show repeated authentication, dependency, or crash errors.

## Build a lightweight baseline

A baseline is a saved picture of normal behavior. It does not need to be perfect. It needs to be recent, repeatable, and easy to compare during an incident.

Capture a normal snapshot:

```bash
date -Is
hostnamectl
uptime
free -h
df -h
df -ih
ss -tulpn
systemctl --failed
journalctl -p warning..alert -n 50 --no-pager
```

If the machine has performance tools installed, add a short sample:

```bash
vmstat 1 5
iostat -xz 1 5
sar -u 1 5
```

Save the output with context:

```text
host: web-01
date: 2026-05-13
traffic state: normal weekday morning
recent deploy: none
backup window: not running
notes: CPU load usually rises for 3-5 minutes around 09:05.
```

The note matters as much as the command output. Future you needs to know whether the numbers were normal, suspicious, or collected during a special condition.

## Prefer ratios and pressure over raw totals

Raw totals can mislead. A server with 32 GB of memory and 29 GB "used" may be healthy because Linux uses free memory for cache. A service with high CPU may be fine if requests are fast and queues are empty.

Prefer signals that explain pressure:

- CPU: run queue length, load relative to CPU count, throttling, steal time, and sustained saturation.
- Memory: available memory, swap activity, OOM kills, and cache pressure.
- Disk: filesystem usage, inode usage, I/O wait, queue depth, latency, and read-only remounts.
- Network: drops, retransmits, errors, DNS failures, and connection timeouts.
- Application: request latency, error rate, queue depth, dependency failures, and background-job lag.

Quick host checks:

```bash
nproc
uptime
free -h
swapon --show
dmesg --level=err,warn --ctime | tail -40
ip -s link
ss -s
```

## Make alerts boring and actionable

An alert should not say "CPU is high" unless high CPU is itself actionable. It should explain impact or likely risk.

Weak alert:

```text
CPU above 90%
```

Better alert:

```text
web-01 CPU saturation is above 90% for 15 minutes and p95 request latency is above 1.5s.
First checks: uptime, top, journalctl -u web.service -n 100, and the web latency dashboard.
```

Good alert rules usually include:

- A symptom or user risk.
- A duration long enough to avoid one-sample noise.
- A severity that matches business impact.
- A runbook or first-check link.
- Labels for service, environment, host, region, and owner.

Use warnings for trends and pages for impact. A disk that is 80% full may deserve a ticket. A disk projected to fill in one hour deserves a page.

## Tune thresholds with real history

Static thresholds are easy to write and easy to get wrong.

Before choosing a threshold, review:

- normal weekday peak
- quiet overnight behavior
- backup and batch windows
- deploy windows
- monthly or seasonal spikes
- prior incidents

If `/var` normally sits at 62% and grows 1% per week, a 90% alert may be too late. If a batch host uses 95% CPU every night by design, a generic CPU page is noise.

Useful threshold patterns:

- absolute: `/` filesystem above 90%
- rate: log errors rising by 50% over 10 minutes
- absence: no successful backup in 24 hours
- prediction: disk will fill within 12 hours
- compound: high CPU plus high latency plus growing queue

Compound alerts are often better than single-signal alerts because they connect resource pressure to user or service impact.

## Keep dashboards small

A dashboard is not a museum. It should answer a question quickly.

Useful dashboard sections:

- Is the service up from the user's point of view?
- Are requests succeeding?
- Are requests fast enough?
- Are dependencies healthy?
- Is any host resource saturated?
- Did deploys, config changes, or traffic shifts happen recently?

For host dashboards, keep the top row boring:

- uptime or scrape health
- CPU pressure
- memory available and swap activity
- filesystem and inode usage
- disk I/O latency
- network errors and retransmits
- failed units and recent critical logs

Name dashboards by owner and purpose:

```text
payments-prod-user-impact
payments-prod-host-health
payments-prod-dependencies
```

Avoid dashboards named `Linux`, `Overview`, or `Misc`. Those names do not help an on-call engineer under pressure.

## Use labels carefully

Labels make monitoring searchable. They also create cost and confusion when they are inconsistent.

Good labels:

- `service`
- `environment`
- `host`
- `region`
- `role`
- `owner`

Risky labels:

- request ID
- session ID
- user ID
- full URL with unbounded parameters
- container ID when containers churn quickly

High-cardinality labels can overload a metrics system. Put detailed identifiers in logs or traces, not every time series.

## Watch for missing data

No data is data. A quiet graph can mean the host is healthy, the agent is down, the network path is broken, or the monitoring server is failing.

Monitor the monitoring path:

- Is the agent running?
- Is the scrape or push recent?
- Is time synchronized?
- Are logs still arriving?
- Did a firewall rule block the collector?
- Did disk pressure stop the local agent from writing buffers?

Useful checks:

```bash
systemctl status node_exporter --no-pager
systemctl status prometheus-node-exporter --no-pager
timedatectl
journalctl -u node_exporter -n 80 --no-pager
```

Service names vary by distribution and installation method. Check your actual unit names with:

```bash
systemctl list-units '*exporter*' --no-pager
```

## Keep incident notes close to the graphs

During an incident, write down what you checked. After the incident, connect the note back to monitoring.

Minimum incident note:

```text
incident:
start time:
detected by:
user symptom:
first alert:
affected hosts/services:
commands run:
important log lines:
temporary mitigation:
root cause, if known:
monitoring gap:
follow-up:
```

Good follow-up questions:

- Did the alert fire before users complained?
- Was the alert specific enough?
- Did the dashboard show the failing layer?
- Did labels point to the right owner?
- Did missing data hide part of the incident?
- Should this become a ticket, runbook update, or alert change?

## Reduce false positives aggressively

False positives train people to ignore alerts. Review noisy alerts like production bugs.

Common fixes:

- Increase the duration window.
- Add a second signal that proves impact.
- Change a page to a ticket.
- Suppress expected maintenance windows.
- Route alerts to the actual owner.
- Delete checks nobody trusts or acts on.

Do not keep a noisy alert because it "might be useful someday." If it is useful, define the situation where it is useful and tune it for that situation.

## Practice safe monitoring changes

Monitoring changes can break production if they overload hosts, expose secrets, or create alert storms.

Before changing collection or alerts:

- Test on one non-critical host.
- Estimate data volume and label cardinality.
- Avoid collecting secrets from command lines, environment files, and logs.
- Keep old and new alerts side by side until the new one proves useful.
- Record what changed and how to roll it back.

Safe rollout note:

```text
change: add filesystem inode alert
scope: web-01 only
threshold: /var above 85% inode use for 15 minutes
expected result: ticket only, no page
rollback: disable rule linux-host-inodes-warning
review date: 2026-05-20
```

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Capture a baseline with `uptime`, `free -h`, `df -h`, `df -ih`, `ss -tulpn`, `systemctl --failed`, and recent warning logs.
2. Write a short health note that says when the baseline was captured and whether the host was idle, busy, or under maintenance.
3. Pick one weak alert idea, such as "CPU above 90%", and rewrite it as an actionable alert with duration, impact, owner, and first checks.
4. Sketch a small dashboard layout for one Linux service. Limit it to the top five questions an on-call engineer needs answered.
5. Identify one signal that should create a ticket instead of waking someone up.
