## 28.6 Systems Monitoring

!!! abstract "What you will learn"
    - Monitor Linux hosts at the system level: CPU, memory, disks, filesystems, services, and kernel signals.
    - Distinguish normal load from saturation that users will feel.
    - Build a first-response checklist for a slow, unstable, or unhealthy host.
    - Capture system evidence clearly enough for another operator to trust it.

Systems monitoring answers one direct question: is this host healthy enough to do its job?

Network monitoring tells you whether traffic can move. Application monitoring tells you whether the service is behaving correctly. Systems monitoring sits underneath both. It watches the host resources that every service depends on: CPU, memory, storage, process health, kernel messages, time, and service state.

A host can be reachable and still unhealthy. A web server can accept connections while swapping heavily. A database can respond while disk latency is climbing. A worker node can look idle while one failed mount blocks every job. Systems monitoring helps you catch those failures before they become mysteries.

## What To Monitor

Start with the host signals that explain most Linux incidents.

### CPU And Scheduler Pressure

CPU monitoring is not only about percentage used. A host can show high CPU because it is doing expected work, or it can show moderate CPU while processes wait on disk, locks, or other resources.

Collect:

- CPU utilization by mode: user, system, idle, iowait, steal.
- Load average over 1, 5, and 15 minutes.
- Run queue pressure.
- Context switches and interrupts.
- Top CPU-consuming processes.

Useful commands:

```bash
uptime
top -b -n1 | head -n 25
vmstat 1 5
mpstat 1 5
ps -eo pid,ppid,stat,pcpu,pmem,comm --sort=-pcpu | head
```

Interpretation:

- High user CPU often means application work.
- High system CPU often means kernel work, I/O, networking, or process churn.
- High iowait means CPUs are idle while waiting for storage.
- High steal time on a virtual machine means the hypervisor is not giving the VM enough CPU time.
- Load much higher than CPU core count means work is backing up somewhere.

### Memory And Swap

Linux uses free memory for caches, so "low free memory" alone is not an incident. The dangerous signs are memory pressure, swap churn, allocation failures, and OOM kills.

Collect:

- Available memory.
- Swap usage and swap in/out activity.
- OOM killer messages.
- Process memory usage.
- Cache and buffer behavior.

Useful commands:

```bash
free -h
vmstat 1 5
cat /proc/meminfo | head -n 30
ps -eo pid,ppid,stat,rss,pmem,comm --sort=-rss | head
journalctl -k --since "2 hours ago" | grep -i 'out of memory\|oom\|killed process'
```

Interpretation:

- Some swap allocated is not automatically bad.
- Active swap in/out during user-visible slowness is important.
- OOM logs are evidence of forced process death.
- A single growing process may indicate a memory leak.
- Many processes growing together may indicate workload growth or bad capacity assumptions.

### Filesystems And Inodes

Full disks are common, but full inode tables can look similar while `df -h` still shows free space.

Collect:

- Filesystem capacity.
- Inode usage.
- Mount state.
- Disk latency and utilization.
- Recent storage errors.

Useful commands:

```bash
df -h
df -ih
findmnt
lsblk
iostat -xz 1 5
journalctl -k --since "2 hours ago" | grep -i 'error\\|fail\\|timeout\\|reset'
```

Interpretation:

- A filesystem above 90 percent needs a plan, not just a quick deletion.
- Inode exhaustion often comes from many tiny files, cache directories, mail queues, or broken log rotation.
- High disk utilization with high await times means storage is a likely bottleneck.
- Kernel storage errors deserve urgency because they may point to device, controller, network-storage, or filesystem trouble.

### Services And Process Health

System monitoring should tell you whether critical services are running, restarting, failed, or stuck.

Collect:

- Failed systemd units.
- Restart loops.
- Process state.
- Open file descriptors.
- Listening sockets.
- Recent service logs.

Useful commands:

```bash
systemctl --failed
systemctl list-units --state=running --type=service
systemctl status nginx --no-pager
journalctl -u nginx --since "1 hour ago" --no-pager
ps -eo pid,ppid,stat,etime,pcpu,pmem,comm --sort=stat | head
ss -tulpen
```

Replace `nginx` with the service you are investigating.

Interpretation:

- A service can be "active" while unhealthy from an application point of view.
- Restart loops may hide the original error unless logs are captured quickly.
- Processes in `D` state are waiting in uninterruptible sleep, often because of storage or network filesystems.
- Unexpected listening sockets can indicate configuration drift or exposure.

### Time Synchronization

Bad clocks break logs, TLS, Kerberos, distributed traces, scheduled jobs, and incident timelines.

Collect:

```bash
timedatectl
chronyc tracking
chronyc sources -v
```

If `chronyc` is not installed, use the time synchronization tool configured for the distribution.

Interpretation:

- A host with bad time can look like many unrelated failures.
- During incidents, time drift can make logs appear out of order.
- Authentication failures may be caused by clock skew rather than credentials.

## Build A Host Health Checklist

During an incident, do not wander randomly through commands. Use a repeatable checklist.

Example first pass:

```bash
date -Is
hostnamectl --static
uptime
systemctl --failed
df -h
df -ih
free -h
vmstat 1 5
ss -tulpen
journalctl -p warning --since "1 hour ago" --no-pager
```

This first pass answers:

- Which host am I on?
- When did I collect this?
- Is the host overloaded?
- Are services failed?
- Are filesystems full?
- Is memory pressure present?
- Is the host listening where expected?
- Are recent warnings pointing at a resource or service?

## Turn Checks Into Metrics

Manual commands are useful, but the monitoring system should collect important signals continuously.

Good host-level metrics include:

- `node_cpu_seconds_total`
- `node_load1`, `node_load5`, `node_load15`
- `node_memory_MemAvailable_bytes`
- `node_vmstat_pswpin`, `node_vmstat_pswpout`
- `node_filesystem_avail_bytes`
- `node_filesystem_files_free`
- `node_disk_io_time_seconds_total`
- `node_network_receive_errs_total`
- `node_network_transmit_errs_total`
- service-specific up/down or health indicators

Names vary by collector, but the idea is consistent: collect host resource signals with labels for host, service role, environment, and cluster.

## Alert On Symptoms And Saturation

Systems alerts should be actionable. A page should tell the on-call person what resource is exhausted, what service is affected, and what first check to run.

Good alert examples:

- Filesystem `/var` has less than 10 percent free space for 15 minutes.
- System load is above twice the CPU count and request latency is elevated.
- Swap-in activity is sustained and application error rate is increasing.
- Critical service has restarted more than three times in ten minutes.
- NTP synchronization is lost on a host that runs authentication-sensitive workloads.

Weak alert examples:

- CPU is above 70 percent once.
- Free memory is low without pressure evidence.
- Any warning appears in the logs.
- A noncritical filesystem briefly crossed a static threshold.

Every alert should have an owner, a runbook, and a quieting strategy for known maintenance.

## Watch Trends, Not Just Thresholds

Thresholds catch hard failures. Trends catch slow failures.

Useful trend questions:

- Is disk usage growing faster than expected?
- Is memory consumption climbing after every deploy?
- Is CPU steal time worse at certain hours?
- Is I/O latency gradually rising on one storage pool?
- Are service restarts more frequent this week than last week?

Capacity incidents often start as trends. The earlier you notice them, the less dramatic the fix needs to be.

## Avoid Monitoring-Induced Damage

Monitoring should not destabilize the host.

Be careful with:

- Heavy `find` scans on busy or failing filesystems.
- Debug logging on high-traffic services.
- Unlimited packet captures.
- Very frequent expensive custom checks.
- Agents that keep retrying when a central collector is unreachable.
- Log shipping that fills local disks when the destination is down.

Safer practice:

- Start with cheap kernel and system counters.
- Bound expensive checks by time, size, and scope.
- Test collectors on a noncritical host first.
- Monitor the monitoring agent's CPU, memory, and disk usage.
- Keep a local emergency path for disabling a broken collector.

## Incident Evidence Template

Use a concise template when escalating system-level findings:

```text
Host:
Time collected:
User-visible symptom:
Primary resource concern:
Commands run:
Key evidence:
Likely cause:
Immediate mitigation:
Follow-up owner:
```

Example:

```text
Host: web-03
Time collected: 2026-05-13T23:15:00Z
User-visible symptom: API latency above 3s
Primary resource concern: disk I/O saturation
Commands run: uptime, vmstat 1 5, iostat -xz 1 5, journalctl -u api
Key evidence: iowait 42 percent, xvda await 180ms, API logs show request queue growth
Likely cause: log volume spike and slow disk
Immediate mitigation: rotate/compress logs, move debug logs off critical volume
Follow-up owner: platform team
```

## Practice: Diagnose A Slow Host

Use a disposable VM or lab host.

1. Capture a baseline:

   ```bash
   date -Is
   uptime
   free -h
   df -h
   systemctl --failed
   ```

2. Generate controlled load in one terminal:

   ```bash
   yes > /dev/null
   ```

3. In another terminal, observe the host:

   ```bash
   uptime
   top -b -n1 | head -n 20
   vmstat 1 5
   ps -eo pid,pcpu,comm --sort=-pcpu | head
   ```

4. Stop the load with `Ctrl+C`.

5. Write down:

   - Which signal changed first.
   - Which command made the cause clearest.
   - What an alert should say if this happened on a production host.
