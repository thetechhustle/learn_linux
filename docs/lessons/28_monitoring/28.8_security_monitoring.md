### 28.8 Security Monitoring

Security monitoring turns ordinary Linux evidence into early warnings. It does
not mean staring at every log line or treating every unusual event as a breach.
It means knowing which signals matter, collecting them consistently, and
escalating with enough context for another operator to reproduce your findings.

!!! abstract "What you will learn"
    - Identify Linux host signals that can reveal compromise, abuse, or risky drift.
    - Use read-only commands to inspect authentication, privilege, process, network, and file-integrity evidence.
    - Separate normal operational noise from security events that need investigation.
    - Build a short security-monitoring handoff that helps responders act quickly.

!!! success "Operator principle"
    Treat security monitoring as evidence handling: preserve the signal, avoid unnecessary changes, and make every escalation reproducible.

## Start with the threat you are watching for

Useful security monitoring starts with a plain-language question. A few common
examples are:

- Are unknown users logging in?
- Are known users logging in from unusual places or at unusual times?
- Did a service start listening on a new port?
- Did a privileged file, scheduled job, or SSH key change?
- Is a host sending traffic that does not match its role?
- Did endpoint protection, an intrusion detector, or a package audit report a finding?

Without a question, a dashboard becomes a pile of blinking lights. With a
question, you can choose the right logs, metrics, and checks.

## Authentication signals

Authentication logs are often the first place to look for brute-force attempts,
stolen credentials, or surprising remote access.

On systemd-based Linux systems, inspect recent SSH and authentication messages
with `journalctl`:

```bash
sudo journalctl -u ssh --since "2 hours ago"
sudo journalctl -u sshd --since "2 hours ago"
sudo journalctl --since "2 hours ago" | grep -Ei 'failed|accepted|sudo|pam'
```

Distribution log paths vary, but these files are common:

```bash
sudo tail -n 100 /var/log/auth.log      # Debian and Ubuntu
sudo tail -n 100 /var/log/secure        # RHEL-family systems
```

Then summarize account activity:

```bash
last -a | head -20
lastb -a | head -20        # failed logins; often requires root
lastlog | head -20
who
```

Watch for patterns such as repeated failures followed by success, privileged
logins outside the change window, logins from unexpected networks, and service
accounts with interactive sessions.

## Privilege and account changes

Attackers often try to persist by changing accounts, groups, sudo policy, or SSH
keys. Baseline the files and directories that control privileged access:

```bash
sudo stat /etc/passwd /etc/shadow /etc/group /etc/sudoers
sudo find /etc/sudoers.d -maxdepth 1 -type f -ls
sudo find /home -maxdepth 3 -path '*/.ssh/authorized_keys' -ls 2>/dev/null
```

For a quick read-only account review:

```bash
getent passwd
getent group sudo
getent group wheel
sudo grep -R --line-number -E 'NOPASSWD|ALL=\(ALL' /etc/sudoers /etc/sudoers.d 2>/dev/null
```

Do not edit these files during an incident unless containment requires it and
your organization approves the action. Copy command output into the incident
record before making changes.

## Process and service evidence

Unexpected processes and services can point to persistence, crypto-mining,
unauthorized remote access, or a compromised application.

Start with the service manager:

```bash
systemctl --type=service --state=running
systemctl list-timers --all
systemctl list-unit-files --state=enabled
```

Then inspect processes with enough detail to see owners, start times, and command
lines:

```bash
ps -eo user,pid,ppid,lstart,stat,comm,args --sort=start_time | tail -40
ps -eo user,pid,pcpu,pmem,stat,comm,args --sort=-pcpu | head -20
```

Security-relevant questions:

- Is a process running as `root` when it normally runs as an unprivileged user?
- Did a new service start near the time suspicious activity began?
- Is a process running from `/tmp`, `/dev/shm`, a user home directory, or another unusual path?
- Does a command line include embedded credentials, curl-to-shell patterns, or encoded payloads?

If a process looks suspicious, collect evidence before stopping it:

```bash
PID=1234
readlink -f /proc/$PID/exe
sudo ls -l /proc/$PID/cwd /proc/$PID/exe
sudo cat /proc/$PID/cmdline | tr '\0' ' '
sudo lsof -Pan -p "$PID" 2>/dev/null | head -50
```

Replace `1234` with the process ID you are investigating.

## Network exposure and outbound traffic

Security monitoring should track both inbound exposure and outbound behavior.
A host that suddenly listens on a new port or connects to unfamiliar networks
deserves attention.

List listening sockets:

```bash
sudo ss -tulpen
```

List active TCP connections:

```bash
sudo ss -tp state established
```

Map a port back to a package or unit when possible:

```bash
sudo lsof -Pan -iTCP -sTCP:LISTEN
systemctl status ssh
```

For a short packet sample, prefer a narrow capture over a broad one:

```bash
sudo tcpdump -nn -i any host 203.0.113.10 -c 50
sudo tcpdump -nn -i any port 22 -c 50
```

!!! warning "Capture carefully"
    Packet captures can include credentials, tokens, customer data, and internal addresses. Capture the smallest useful sample, store it where access is controlled, and follow your incident-response policy.

## File integrity and persistence checks

File-integrity monitoring is most useful when it compares current state to a
trusted baseline. Tools such as AIDE, package verification, endpoint security
agents, and configuration management can all provide that baseline.

Read-only checks that work well during triage include:

```bash
sudo find /etc/cron.d /etc/cron.daily /etc/systemd/system -type f -mtime -7 -ls
sudo find /tmp /var/tmp /dev/shm -type f -mtime -1 -ls 2>/dev/null
sudo find /usr/local/bin /usr/local/sbin -type f -mtime -14 -ls 2>/dev/null
```

Verify packages with your distribution tools:

```bash
sudo rpm -Va                  # RHEL-family systems
sudo debsums -s               # Debian/Ubuntu when debsums is installed
```

Package verification can produce legitimate differences from local
configuration changes. Treat findings as leads, not proof by themselves.

## IDS, EDR, and audit signals

Host security tools can add depth that basic shell commands cannot provide:

- `auditd` records selected security-relevant system calls and policy events.
- AIDE and similar tools detect file changes against a known baseline.
- Suricata, Zeek, and Snort inspect network traffic.
- Endpoint detection and response agents can correlate process, network, file,
  and identity events.
- Cloud security tools can report suspicious instance, identity, or network
  activity around the host.

When these tools alert, capture the alert ID, timestamp, host, affected user,
rule name, severity, and the raw evidence link. Avoid paraphrasing away details
that the responder will need later.

## Alert quality

A good security alert has an owner and an action. Avoid alerts that only say
"something changed" without giving enough context to decide whether the change
is expected.

Useful alert examples:

- New SSH login for a privileged account from a country or network not seen in
  the previous 30 days.
- More than 20 failed SSH logins from one source in 10 minutes, followed by a
  successful login.
- New process listening on a public interface outside the approved service list.
- New file in `/etc/sudoers.d` or a new SSH key in a privileged account.
- Package verification reports a changed executable outside the patch window.

Each alert should include a runbook link or a short triage checklist.

## Incident handoff template

Use a compact handoff when security monitoring finds something worth escalation:

```text
Host:
Time window:
Initial signal:
User/account involved:
Source and destination:
Processes or services involved:
Commands used:
Key evidence paths or links:
Actions already taken:
Actions not taken:
Recommended next step:
```

The "actions not taken" line is important. It tells the next operator whether
you avoided stopping a process, deleting a file, rotating a key, or blocking an
address so evidence would remain intact.

## Hands-on practice

Run these commands on a disposable VM or lab host.

1. Review recent authentication activity:

   ```bash
   sudo journalctl --since "1 hour ago" | grep -Ei 'failed|accepted|sudo|pam' || true
   last -a | head -10
   ```

2. Record current listeners and running services:

   ```bash
   sudo ss -tulpen
   systemctl --type=service --state=running
   ```

3. Look for recent persistence points:

   ```bash
   sudo find /etc/cron.d /etc/systemd/system -type f -mtime -7 -ls
   sudo find /home -maxdepth 3 -path '*/.ssh/authorized_keys' -ls 2>/dev/null
   ```

4. Write a short handoff note using the template above. If everything looks
   normal, document what "normal" looked like and which commands proved it.
