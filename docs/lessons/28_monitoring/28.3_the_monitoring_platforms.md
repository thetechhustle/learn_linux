#### 28.3 The Monitoring Platforms

!!! abstract "What you will learn"
    - Compare local, host-based, and centralized monitoring platforms.
    - Pick a monitoring platform based on operational needs instead of popularity.
    - Identify what Linux evidence each platform should collect or expose.
    - Explain where lightweight tools end and fleet monitoring begins.

A monitoring platform is the place operators use to collect, query, visualize, and alert on system behavior. Some platforms are simple commands that run on one host. Others collect data from thousands of hosts and services.

The right platform depends on the question you need to answer:

- What is happening on this one machine right now?
- What changed across the fleet after a deploy?
- Which service is causing user-visible latency?
- Are we about to run out of disk, memory, CPU, or queue capacity?
- Which alert should wake a person?

No single platform answers every question equally well. Good operators understand the layers and choose the smallest tool that gives reliable evidence.

## Platform Layers

Think of monitoring platforms in layers.

| Layer | Typical Tools | Best For |
| --- | --- | --- |
| Local inspection | `top`, `htop`, `free`, `df`, `ss`, `journalctl` | Immediate host triage |
| Host agents | Netdata, node_exporter, Telegraf, collectd | Repeated host metrics collection |
| Central metrics | Prometheus, Zabbix, Graphite, InfluxDB | Historical trends and alert rules |
| Logs and events | `journald`, syslog, Loki, Elasticsearch/OpenSearch, Splunk | Searchable incident evidence |
| Synthetic checks | Blackbox exporters, uptime checks, HTTP probes | User-facing reachability |
| Full observability suites | Grafana Cloud, Datadog, New Relic, Honeycomb, Elastic | Cross-service dashboards, traces, and managed alerts |

These layers can overlap. A small environment may start with Netdata and `journalctl`. A larger environment may use Prometheus for metrics, Loki or OpenSearch for logs, Grafana for dashboards, and a paging tool for alert delivery.

## Local Tools Still Matter

Central monitoring is useful, but local Linux tools are still the fastest way to verify a host directly:

```bash
uptime
top
free -h
df -h
df -ih
ss -tulpn
systemctl --failed
journalctl -p warning..alert --since "30 minutes ago"
```

Use local tools when:

- the monitoring agent may be down
- network access to the monitoring platform is broken
- you need to confirm what the host itself sees
- you are working in a lab or recovery shell
- the dashboard does not explain the symptom

Local checks are not a replacement for centralized monitoring. They are the ground truth you can use when the dashboard is confusing.

## Host Agents

A host agent collects signals repeatedly and sends them somewhere useful. Common examples include:

- **node_exporter** for Prometheus host metrics
- **Telegraf** for plugin-based metrics collection
- **collectd** for long-running system metrics collection
- **Netdata** for real-time host dashboards and lightweight alerting
- vendor agents for managed platforms such as Datadog or New Relic

Before deploying an agent, know:

- what user it runs as
- which ports it opens
- where it writes logs
- how much CPU, memory, and disk it consumes
- what data it sends off-host
- how it is upgraded and restarted

You can inspect agents like any other service:

```bash
systemctl status node_exporter
systemctl status telegraf
systemctl status netdata
ss -tulpn
journalctl -u node_exporter --since "1 hour ago"
```

If a monitoring agent fails, the host may still be healthy. Treat missing telemetry as its own alert, not as proof the host is down.

## Prometheus And Grafana

Prometheus is a common open source metrics system. It pulls metrics from targets over HTTP, stores time series data, and evaluates alert rules. Grafana is commonly used to visualize those metrics.

Prometheus is strong when you need:

- host and service metrics over time
- labels for filtering by job, instance, region, or environment
- alert rules based on time-series queries
- pull-based collection from exporters
- simple service-level dashboards

Prometheus is not a general log search engine. Pair it with a log platform when you need full text search across logs.

Common Linux checks around a Prometheus target include:

```bash
systemctl status prometheus
systemctl status node_exporter
curl -s http://127.0.0.1:9100/metrics | head
ss -tulpn | grep -E '9090|9100'
journalctl -u prometheus --since "1 hour ago"
```

## Zabbix And Nagios

Zabbix and Nagios-style systems are often used for infrastructure monitoring, service checks, and alerting.

They are useful when you need:

- explicit host and service checks
- infrastructure inventory views
- SNMP checks for network devices
- threshold-based alerting
- centralized visibility for traditional server fleets

They can become noisy if checks are added without ownership or runbooks. The platform can tell you that something is red; the team still needs to define what red means and who acts on it.

## Logs Platforms

Metrics tell you that something changed. Logs often explain the change.

Linux logs may start locally with:

```bash
journalctl
journalctl -u ssh --since today
journalctl -k --since "1 hour ago"
tail -f /var/log/syslog
tail -f /var/log/auth.log
```

Central log platforms include:

- Loki
- Elasticsearch or OpenSearch
- Splunk
- cloud provider log services

Use a log platform when you need to search across hosts, keep logs after a host disappears, correlate deploys with errors, or preserve incident evidence.

## Managed Observability Platforms

Managed platforms such as Datadog, New Relic, Grafana Cloud, Elastic Cloud, and Honeycomb reduce operational burden by hosting parts of the monitoring stack for you. They may include metrics, logs, traces, dashboards, alerting, synthetic checks, and incident workflows.

They are useful when:

- your team wants less monitoring infrastructure to maintain
- you need cross-service traces quickly
- alert routing and integrations matter
- compliance or retention settings are manageable in the service

Watch the tradeoffs:

- monthly cost can grow quickly with hosts, logs, custom metrics, or retention
- agents may collect sensitive metadata
- outages in the provider can affect your visibility
- vendor-specific dashboards and queries can be harder to migrate

For production systems, document what data leaves your environment and who can access it.

## Choosing A Platform

Choose based on operational fit:

| Need | Good Starting Point |
| --- | --- |
| One host in a lab | Local commands, Netdata |
| Small Linux fleet | node_exporter, Prometheus, Grafana |
| Traditional infrastructure checks | Zabbix or Nagios-style checks |
| Log-heavy troubleshooting | Loki, OpenSearch, Splunk, cloud logs |
| Application latency across services | tracing or managed observability platform |
| Network device visibility | SNMP-capable platform |
| Executive uptime view | synthetic checks plus service dashboard |

Start small. A simple, trusted dashboard with a few useful alerts is better than a large platform nobody understands.

## Platform Evaluation Checklist

Before standardizing on a monitoring platform, ask:

- What signals does it collect?
- Does it support Linux host metrics clearly?
- How are agents installed, upgraded, and removed?
- Can operators query raw evidence?
- Can alert rules include time windows and labels?
- How does it integrate with incident response?
- What happens when the platform is down?
- What does it cost at expected retention and data volume?
- Who owns dashboards and alert cleanup?
- How will sensitive logs or metadata be protected?

Monitoring platforms are operational infrastructure. Treat their design and maintenance with the same care as any production service.
