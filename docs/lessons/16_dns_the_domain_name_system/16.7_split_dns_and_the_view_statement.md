# 16.7 Split DNS and the View Statement

!!! abstract "What you will learn"
    - Explain why split DNS returns different answers for different clients.
    - Read a BIND `view` configuration and predict which clients match each view.
    - Verify split-horizon answers from internal and external vantage points.
    - Identify common split DNS failure modes before they become outages.

!!! success "Operator principle"
    Split DNS is useful, but it hides complexity. Every view is a separate truth surface, so verify the internal answer, the external answer, and the fallback behavior.

## What Split DNS Solves

Split DNS, also called split-horizon DNS, lets one DNS service return different answers depending on who asks.

Common uses include:

- internal clients receive private addresses such as `10.0.20.15`
- external clients receive public addresses such as `203.0.113.15`
- internal-only hostnames are hidden from internet clients
- lab, VPN, or branch networks receive different service endpoints
- mail, identity, or application cutovers are staged by source network

The name may be the same, but the answer changes by client source.

```text
app.example.com from office LAN     -> 10.0.20.15
app.example.com from public internet -> 203.0.113.15
```

That can be a clean design when it is intentional. It can also create confusing incidents when teams test from the wrong side of the boundary.

## BIND Views

BIND implements split DNS with `view` blocks. Each view contains matching rules and its own zone definitions.

```conf
acl "trusted-lan" {
    10.0.0.0/8;
    192.168.0.0/16;
    127.0.0.1;
};

view "internal" {
    match-clients { trusted-lan; };
    recursion yes;

    zone "example.com" {
        type primary;
        file "/etc/bind/zones/internal/db.example.com";
    };
};

view "external" {
    match-clients { any; };
    recursion no;

    zone "example.com" {
        type primary;
        file "/etc/bind/zones/external/db.example.com";
    };
};
```

The first matching view wins. Put specific views before broad views. If `match-clients { any; };` appears first, it catches every query and the internal view will never be used.

## Matching Clients

The `match-clients` clause chooses the view based on the source address of the DNS query.

```conf
view "vpn" {
    match-clients { 100.64.0.0/10; };
    recursion yes;
    zone "example.com" {
        type primary;
        file "/etc/bind/zones/vpn/db.example.com";
    };
};
```

Be precise about what source address the DNS server actually sees. A client behind NAT, a VPN concentrator, or a forwarding resolver may appear as the forwarder's address, not the laptop's address.

For DNS forwarding chains, document the path:

```text
laptop -> office resolver -> authoritative BIND server
```

In that case, the authoritative server matches the office resolver source address.

## Recursion And Authority

Views commonly separate recursive service from authoritative service.

Internal view:

```conf
recursion yes;
allow-recursion { trusted-lan; };
```

External view:

```conf
recursion no;
allow-recursion { none; };
```

Never accidentally provide open recursion to the internet. Open recursive resolvers can be abused for amplification attacks and can leak internal resolution behavior.

Check recursion from an internal client:

```bash
dig @dns1.example.com www.kernel.org A
```

Check from an external vantage point:

```bash
dig @dns1.example.com www.kernel.org A
```

The external query should not be recursively resolved by your authoritative public server.

## Internal And External Zone Files

Each view can load a different zone file for the same domain.

Internal zone:

```text
$ORIGIN example.com.
$TTL 300
@       IN SOA ns1.example.com. hostmaster.example.com. (
        2026051201 3600 900 1209600 300 )
@       IN NS  ns1.example.com.
app     IN A   10.0.20.15
db      IN A   10.0.30.25
```

External zone:

```text
$ORIGIN example.com.
$TTL 300
@       IN SOA ns1.example.com. hostmaster.example.com. (
        2026051201 3600 900 1209600 300 )
@       IN NS  ns1.example.com.
app     IN A   203.0.113.15
```

The external zone omits `db.example.com` entirely. That does not make the internal host secure by itself, but it avoids publishing unnecessary internal inventory.

Keep serial numbers and SOA policy deliberate. Some teams use different serials per view; others keep them aligned for easier auditing. Pick one convention and document it.

## Validate Before Reloading

Check the BIND configuration:

```bash
named-checkconf /etc/bind/named.conf
```

Check each zone file:

```bash
named-checkzone example.com /etc/bind/zones/internal/db.example.com
named-checkzone example.com /etc/bind/zones/external/db.example.com
```

Reload after validation:

```bash
sudo rndc reload
```

Then inspect logs:

```bash
journalctl -u bind9 -n 50 --no-pager
```

On distributions that use a different service name, replace `bind9` with the local unit name, such as `named`.

## Verify Both Sides

From an internal client:

```bash
dig @dns1.example.com app.example.com A +noall +answer
dig @dns1.example.com db.example.com A +noall +answer
```

Expected result:

```text
app.example.com. 300 IN A 10.0.20.15
db.example.com.  300 IN A 10.0.30.25
```

From an external client or public network:

```bash
dig @dns1.example.com app.example.com A +noall +answer
dig @dns1.example.com db.example.com A +noall +answer
```

Expected result:

```text
app.example.com. 300 IN A 203.0.113.15
```

The `db.example.com` query should return no public answer if that host is intentionally internal-only.

If you cannot access an external network, query from a trusted remote machine, a cloud shell, or a monitoring probe outside your LAN.

## Troubleshooting View Selection

When split DNS returns the wrong answer, check:

- Did the query reach the expected DNS server?
- Which source address did the DNS server see?
- Is the specific view listed before the broad `any` view?
- Does the client query a recursive resolver that forwards from a different source address?
- Are internal and external zones both loaded without syntax errors?
- Did the resolver cache an older answer before the view change?
- Are firewalls or ACLs blocking the internal client from the intended resolver?

Useful commands:

```bash
dig @dns1.example.com app.example.com A +noall +answer
dig @dns1.example.com app.example.com SOA +noall +answer
dig @dns1.example.com chaos txt hostname.bind +short
sudo rndc status
journalctl -u bind9 -n 100 --no-pager
```

The `hostname.bind` query works only if the server permits that CHAOS-class diagnostic. Do not rely on it as a universal check.

## Operational Risks

Split DNS can cause subtle failures:

- VPN users may see internal records while non-VPN users see public records.
- Monitoring may report healthy from one view and broken from another.
- Certificate validation may fail if public validation sees a different name or address.
- Mail records can diverge between views and break delivery.
- Incident responders may test from the wrong network and chase the wrong answer.

For production changes, write down:

- which view is changing
- which clients should match that view
- the old and new record values
- the current TTL
- the validation commands for each vantage point
- the rollback value and who can apply it

## Hands-On Practice

Use a lab BIND server or read-only examples.

1. Write two sample zone files for `lab.example`: one internal and one external.
2. Write a `named.conf` view layout with a specific internal ACL before an external `any` view.
3. Run `named-checkconf` and `named-checkzone` against the files.
4. Query the internal and external views from different source networks or simulated containers.
5. Record how you proved which view answered each query.
