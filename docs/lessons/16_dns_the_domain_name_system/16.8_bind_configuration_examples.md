## 16.8 BIND Configuration Examples

BIND configuration is mostly plain text, but the operational risk is not small.
A broken `named.conf` can stop the daemon from loading, and a broken zone file can
publish bad answers to every resolver that trusts your authoritative server.

Treat the examples in this lesson as lab patterns. On production DNS servers,
copy the current files first, lower TTLs before planned migrations, validate the
syntax, reload only the affected zone when possible, and verify answers from a
client that uses the same network path as your users.

!!! abstract "What you will learn"
    - Recognize the common BIND configuration files on Debian-style systems.
    - Define a simple authoritative primary zone and a secondary zone.
    - Build a minimal forward zone file with SOA, NS, A, AAAA, CNAME, and MX records.
    - Validate BIND configuration and zone files before reloading `named`.
    - Verify DNS answers with `dig` after a configuration change.

!!! warning "Do not test on a production DNS server first"
    DNS mistakes can persist in caches until their TTLs expire. Practice these
    examples on a disposable VM or container before touching a real domain.

## Where BIND keeps configuration

On many Debian and Ubuntu systems, the main file is `/etc/bind/named.conf`.
It usually includes smaller files:

```text
include "/etc/bind/named.conf.options";
include "/etc/bind/named.conf.local";
include "/etc/bind/named.conf.default-zones";
```

The exact paths vary by distribution. Before editing, find the service and
configuration paths on the system you are using:

```bash
systemctl cat named 2>/dev/null || systemctl cat bind9
systemctl status named 2>/dev/null || systemctl status bind9
sudo named-checkconf -p | head -40
```

`named.conf.options` normally contains global behavior such as recursion,
forwarders, listen addresses, DNSSEC settings, and access controls.
`named.conf.local` is a common place to add local zone definitions.
`named.conf.default-zones` usually contains loopback and localhost zones.

## Example: authoritative primary zone

A primary zone is the writable source of truth for a DNS zone. For a lab domain
named `example.test`, a zone definition can look like this:

```text
zone "example.test" {
    type primary;
    file "/etc/bind/zones/db.example.test";
    allow-transfer { 192.0.2.53; };
    notify yes;
};
```

Older BIND examples often use `type master`; newer examples may use
`type primary`. They mean the same role. Use the wording that matches your local
documentation and team standard.

Important fields:

- `zone` is the DNS zone name served by this stanza.
- `type primary` means this server loads the editable zone file.
- `file` points to the zone file on disk.
- `allow-transfer` limits which secondary servers can copy the full zone.
- `notify yes` tells secondaries when the zone changes.

Create the zone directory with ownership that matches the local package's BIND
user and group. On Debian-style systems, read-only static zone files commonly
live under `/etc/bind/`, while dynamically updated zones often live under
`/var/cache/bind/` or another writable directory.

## Example: authoritative secondary zone

A secondary zone receives its contents from a primary server by zone transfer.
It should not be hand-edited.

```text
zone "example.test" {
    type secondary;
    file "/var/cache/bind/db.example.test";
    primaries { 192.0.2.10; };
};
```

Older examples use `type slave` and `masters`. Newer BIND versions prefer
`type secondary` and `primaries`. The important operational idea is unchanged:
the secondary has a local copy, but the primary owns the data.

After configuring a secondary, verify that transfers work and are restricted:

```bash
dig @192.0.2.10 example.test AXFR
dig @192.0.2.53 example.test SOA +norecurse
```

Do not leave unrestricted zone transfers enabled. A full transfer exposes the
zone contents to anyone who can query it.

## Example: minimal forward zone file

This is a small authoritative zone file for `example.test`.

```text
$TTL 300
@   IN SOA ns1.example.test. hostmaster.example.test. (
        2026051201 ; serial: YYYYMMDDnn
        3600       ; refresh
        900        ; retry
        1209600    ; expire
        300        ; negative cache TTL
)

    IN NS  ns1.example.test.
    IN NS  ns2.example.test.
    IN MX  10 mail.example.test.

ns1 IN A     192.0.2.10
ns2 IN A     192.0.2.53
www IN A     192.0.2.80
www IN AAAA  2001:db8::80
mail IN A    192.0.2.25
ftp IN CNAME www.example.test.
```

Read this file carefully:

- `$TTL 300` sets a five-minute default TTL for records without their own TTL.
- The SOA record identifies the primary name server and administrator contact.
- The SOA serial must increase every time the zone changes.
- NS records name the authoritative servers for the zone.
- MX records point mail delivery at a host name, not directly at an IP address.
- CNAME records create aliases, but an alias cannot safely coexist with other
  records at the same name.

For planned migrations, use a short TTL before the move, wait for the old longer
TTL to age out, make the change, verify it, then raise TTLs again when stable.

## Validate before reloading

BIND gives you two important validation tools:

```bash
sudo named-checkconf /etc/bind/named.conf
sudo named-checkzone example.test /etc/bind/zones/db.example.test
```

If both commands pass, reload the affected zone instead of restarting the whole
service:

```bash
sudo rndc reload example.test
sudo rndc status
```

If `rndc` is not configured, use the service manager as a fallback:

```bash
sudo systemctl reload named 2>/dev/null || sudo systemctl reload bind9
```

Use restart only when reload is not enough. A restart interrupts service more
than a reload and can hide whether the zone itself was the only problem.

## Verify answers after the change

Query the server directly first:

```bash
dig @127.0.0.1 example.test SOA +norecurse
dig @127.0.0.1 www.example.test A +norecurse
dig @127.0.0.1 example.test MX +norecurse
```

Then query from a client path that resembles the real user path:

```bash
dig @192.0.2.10 www.example.test A
dig @192.0.2.53 example.test SOA +norecurse
```

Check these details in the output:

- `status: NOERROR` for names that should exist.
- `ANSWER SECTION` contains the record you expected.
- `AUTHORITY SECTION` points at the expected authoritative servers.
- TTLs match the change plan.
- The SOA serial is higher than the previous version.

## Common failure patterns

- Missing trailing dots turn `ns1.example.test` into
  `ns1.example.test.example.test`.
- Forgetting to increment the SOA serial prevents secondaries from picking up
  the update.
- A CNAME at the same name as an MX, NS, or other record creates invalid data.
- `allow-transfer { any; };` exposes the whole zone.
- Reloading the service without running `named-checkzone` publishes avoidable
  syntax mistakes.
- Testing only against a public resolver can hide authoritative-server problems
  behind cached answers.

## Hands-on practice

Run these steps on a disposable lab VM.

1. Install BIND and locate the active service name.
2. Add a primary lab zone named `example.test`.
3. Create a minimal zone file with SOA, NS, A, AAAA, CNAME, and MX records.
4. Run `named-checkconf` and `named-checkzone`.
5. Reload only the lab zone.
6. Use `dig` to verify SOA, NS, A, AAAA, CNAME, and MX answers.
7. Break one copy of the zone file in a controlled way, run the validation
   commands again, and explain which check caught the issue.
