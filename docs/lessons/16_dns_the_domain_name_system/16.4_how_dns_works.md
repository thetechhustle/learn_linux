# 16.4 How DNS Works

DNS works by combining local resolver configuration, recursive lookup, delegation, authoritative zone data, and caching. When something fails, the operator's job is to identify which part of that chain produced the wrong answer or no answer.

!!! abstract "What you will learn"
    - Trace the normal DNS lookup flow from application to authoritative answer.
    - Explain recursive and iterative lookup behavior in operational terms.
    - Understand how caching and TTLs affect troubleshooting.
    - Use Linux commands to prove where a lookup succeeds or fails.
    - Build a safe DNS incident workflow for name-resolution failures.

!!! success "Operator principle"
    Follow the lookup path one hop at a time: local resolver, recursive resolver, delegation, authoritative answer, cache.

## The Lookup Flow

A typical DNS lookup moves through several layers:

```text
application
  -> system resolver
  -> recursive resolver
  -> root
  -> TLD
  -> authoritative nameserver
  -> recursive resolver cache
  -> client answer
```

The client usually asks a recursive resolver for the final answer. The recursive resolver does the upstream work, caches the result, and returns the answer to the client.

On Linux, start with the path the application is likely using:

```bash
getent hosts www.example.com
resolvectl query www.example.com
dig www.example.com A
```

`getent` uses the system name service path. `dig` asks DNS directly. If those disagree, inspect local resolver configuration before assuming public DNS is wrong.

## Recursive Lookup

In a recursive lookup, the client asks one resolver to return either an answer or an error.

```bash
dig www.example.com A
```

The recursive resolver may:

- answer from cache
- ask the root servers
- ask the TLD servers
- ask authoritative nameservers
- validate DNSSEC
- apply local policy or filtering
- return `NOERROR`, `NXDOMAIN`, `SERVFAIL`, `REFUSED`, or a timeout

For most hosts, this is the normal lookup mode.

Check which resolver answered:

```bash
dig www.example.com A | grep '^;; SERVER:'
```

Then compare against known resolvers:

```bash
dig @1.1.1.1 www.example.com A
dig @8.8.8.8 www.example.com A
```

If only one resolver disagrees, the problem may be resolver policy, cache state, split DNS, or upstream reachability.

## Iterative Lookup And Delegation

In iterative lookup, each DNS server points the resolver to the next place to ask. Root servers point to TLD servers. TLD servers point to authoritative nameservers. Authoritative nameservers provide the final zone answer.

Use `+trace` to see this path:

```bash
dig +trace www.example.com A
```

Look for:

- root referral
- TLD referral
- authoritative nameserver referral
- final answer
- where the trace stops, if it fails

If the trace stops before the final answer, investigate delegation, DNSSEC, authoritative reachability, or parent-zone data.

## Authoritative Truth

Authoritative nameservers own the zone data. If the authoritative server is wrong, recursive resolvers will eventually cache and repeat the wrong answer.

Find authoritative servers:

```bash
dig NS example.com
```

Query one directly:

```bash
dig @ns1.example.com www.example.com A
```

Compare:

```bash
dig www.example.com A
dig @ns1.example.com www.example.com A
```

If the authoritative answer is correct but recursive resolvers are stale, wait for TTL expiry or flush the resolver cache where you control it. If the authoritative answer is wrong, fix the zone data.

## Caching And TTLs

Caching is why DNS is fast and why DNS changes can feel slow.

Every cached answer has a TTL:

```bash
dig +nocmd www.example.com A +noall +answer
```

Example:

```text
www.example.com.  300  IN  A  203.0.113.20
```

The `300` means a resolver may cache the answer for 300 seconds. During migrations, old answers can legitimately remain visible until their TTL expires.

Safe migration sequence:

1. Lower TTL before the change.
2. Wait for the previous TTL to age out.
3. Change the authoritative record.
4. Verify authoritative data.
5. Compare recursive resolvers.
6. Raise TTL after stability.

## Negative Caching

DNS can also cache failures. A mistaken `NXDOMAIN` may persist because negative responses have cache lifetimes too.

Check the SOA record, which often carries negative-cache timing:

```bash
dig example.com SOA
```

If a name was accidentally missing, some resolvers may keep saying it does not exist until the negative cache expires.

## Local Cache Behavior

A Linux host may cache locally through `systemd-resolved`, `dnsmasq`, `nscd`, a container runtime, or an application cache.

Inspect local state:

```bash
resolvectl status
resolvectl statistics
systemctl status systemd-resolved
```

If appropriate in a lab or controlled maintenance window:

```bash
sudo resolvectl flush-caches
```

Do not treat cache flushing as a production fix by itself. It can prove a theory, but the real issue may still be TTL planning, bad authoritative data, or wrong resolver routing.

## DNS And Applications

Some applications cache names internally. Browsers may use DNS over HTTPS. JVMs, databases, service meshes, and HTTP clients may cache or retry differently.

When an application fails but `dig` works, gather:

- exact application error
- hostname and port
- host/container where the app runs
- `getent hosts <name>` result from that same runtime
- resolver configuration from that same runtime
- packet capture or application debug logs if needed

Always test from the same place where the failure occurs.

## Troubleshooting Workflow

Use this order for most lookup incidents:

1. Confirm the exact name and record type.
2. Test the application path with `getent` or the app's runtime.
3. Test direct DNS with `dig`.
4. Query the configured resolver.
5. Query public recursive resolvers.
6. Query authoritative nameservers.
7. Run `dig +trace` if delegation is suspect.
8. Check TTLs and recent changes.
9. Decide whether the issue is local, recursive, authoritative, delegation, or cache.

## Hands-On Practice

Pick a test domain.

1. Run `getent hosts <name>`.
2. Run `dig <name> A`.
3. Run `dig @1.1.1.1 <name> A`.
4. Find the domain's authoritative nameservers.
5. Query one authoritative nameserver directly.
6. Run `dig +trace <name> A`.
7. Record where the answer came from and how long it may be cached.
