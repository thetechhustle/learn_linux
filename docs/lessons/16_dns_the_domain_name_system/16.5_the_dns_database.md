# 16.5 The DNS Database

!!! abstract "What you will learn"
    - Describe the DNS database as a distributed set of zones, not one central table.
    - Read common DNS record types and explain their operational impact.
    - Query authoritative answers without relying on resolver cache.
    - Plan DNS record changes around TTLs, delegation, and rollback.

!!! success "Operator principle"
    DNS records are production routing data. Treat every change like a small release: know the owner, lower the TTL first when possible, make one change at a time, and verify from more than one resolver.

## The Database Is Distributed

DNS feels like one database because a lookup returns one answer. Under the hood, it is a hierarchy of delegated zones.

A zone is the portion of the namespace that one operator controls. For example:

- the root zone delegates `.com`
- the `.com` zone delegates `example.com`
- the `example.com` zone publishes records such as `www.example.com`, `mail.example.com`, and `_dmarc.example.com`

Each zone has authoritative name servers. Those servers are the source of truth for that zone. Recursive resolvers cache answers from authoritative servers so clients do not have to walk the hierarchy for every request.

```bash
dig example.com NS +short
dig @a.iana-servers.net example.com SOA +noall +answer
```

The first command asks your configured resolver which authoritative servers handle `example.com`. The second asks one authoritative server directly for the zone's SOA record.

## Records Are The Rows

A DNS record has a name, type, value, TTL, and class. The class is almost always `IN` for internet DNS.

```text
www.example.com.  300  IN  A      93.184.216.34
mail.example.com. 300  IN  A      192.0.2.25
example.com.      300  IN  MX 10  mail.example.com.
```

Read that as:

- `www.example.com` has an IPv4 address.
- `mail.example.com` has an IPv4 address.
- mail for `example.com` should be delivered to `mail.example.com` with priority `10`.

The trailing dot means the name is fully qualified. Without it, many zone-file tools may append the current zone name.

## Common Record Types

### A and AAAA

`A` records map names to IPv4 addresses. `AAAA` records map names to IPv6 addresses.

```bash
dig example.com A +noall +answer
dig example.com AAAA +noall +answer
```

Dual-stack services often publish both. If IPv6 is broken but `AAAA` is still published, some clients may appear slow or unreliable because they try IPv6 first or race IPv4 and IPv6.

### CNAME

A `CNAME` makes one name an alias of another canonical name.

```bash
dig www.example.com CNAME +noall +answer
dig www.example.com A +noall +answer
```

Do not place a `CNAME` at the same name as other record types. If `www.example.com` is a `CNAME`, it should not also have its own `A`, `AAAA`, `MX`, or `TXT` records. Also avoid using a `CNAME` at a zone apex such as `example.com` unless your DNS provider implements an explicit flattening feature.

### MX

`MX` records route mail for a domain.

```bash
dig example.com MX +noall +answer
```

Each answer includes a preference number. Lower numbers are preferred. The target should resolve to address records; mail systems expect a real host name, not an IP address written directly into the `MX` value.

### TXT

`TXT` records carry arbitrary text. In operations, they are commonly used for domain verification and email security.

```bash
dig example.com TXT +noall +answer
dig _dmarc.example.com TXT +noall +answer
```

SPF, DKIM, and DMARC mistakes can break mail delivery or allow spoofing. Treat mail-related `TXT` changes carefully and keep the previous value available for rollback.

### NS

`NS` records name the authoritative servers for a zone or delegated subzone.

```bash
dig example.com NS +noall +answer
```

Changing `NS` records changes who controls answers for that domain or subdomain. Registrar-side nameserver changes and in-zone delegation changes are related but not identical; know which layer you are editing before making the change.

### SOA

The SOA record describes zone authority and timing values.

```bash
dig example.com SOA +noall +answer
```

Important fields include:

- primary name server
- responsible party mailbox, written in DNS-name form
- serial number
- refresh, retry, expire, and negative-cache timing values

For traditional zone transfers, secondary servers use the serial number to decide whether the zone changed. Many managed DNS providers hide serial handling, but the SOA still helps during troubleshooting.

### PTR

`PTR` records map IP addresses back to names. They live under reverse DNS zones, not usually inside the forward zone for your domain.

```bash
dig -x 93.184.216.34 +noall +answer
```

Reverse DNS matters for mail reputation, inventory, and incident response. Cloud providers and ISPs often control the reverse zone for the IP ranges they assign.

## Query The Source Of Truth

Your default resolver may return a cached answer. To inspect the authoritative database, find the authoritative servers and query one directly.

```bash
dig example.com NS +short
dig @a.iana-servers.net www.example.com A +noall +answer
```

If the authoritative answer differs from your default resolver, you may be looking at cache delay, split-horizon DNS, or a resolver-specific policy.

Compare multiple public resolvers:

```bash
dig @1.1.1.1 www.example.com A +noall +answer
dig @8.8.8.8 www.example.com A +noall +answer
dig @9.9.9.9 www.example.com A +noall +answer
```

Then compare the authoritative server:

```bash
dig @a.iana-servers.net www.example.com A +noall +answer
```

The authoritative answer is what new cache fills should eventually converge toward.

## TTLs Control Cache Lifetime

The TTL tells resolvers how long they may cache a record. A `300` second TTL allows faster migrations than a `86400` second TTL.

Before a planned migration:

1. Lower the TTL well before the change window.
2. Wait at least the old TTL.
3. Change the record.
4. Verify authoritative and recursive answers.
5. Raise the TTL again after the service is stable.

Check the TTL returned with an answer:

```bash
dig www.example.com A +noall +answer
```

The second column is the remaining TTL from the resolver that answered you. It may count down if the answer came from cache.

## Zone Files And Managed DNS

On self-managed authoritative DNS, records may live in zone files such as BIND configuration.

```text
$ORIGIN example.com.
$TTL 300
@       IN  SOA ns1.example.com. hostmaster.example.com. (
            2026051201 ; serial
            3600       ; refresh
            900        ; retry
            1209600    ; expire
            300        ; negative cache
)
@       IN  NS   ns1.example.com.
@       IN  MX 10 mail.example.com.
www     IN  A    192.0.2.10
mail    IN  A    192.0.2.25
```

Managed DNS providers usually replace zone files with an API or web console. The underlying concepts remain the same: names, record types, values, TTLs, and authoritative publication.

If you operate BIND, validate zone syntax before reloading:

```bash
named-checkzone example.com /etc/bind/zones/db.example.com
sudo rndc reload example.com
```

On systems that use another authoritative server, use that server's validation and reload commands instead.

## Migration Example

Suppose `www.example.com` is moving from `192.0.2.10` to `198.51.100.40`.

Before the window:

```bash
dig www.example.com A +noall +answer
dig example.com NS +short
```

Record the current answer, TTL, and authoritative servers.

During the window:

1. Update the `A` or `AAAA` record at the authoritative provider.
2. Query the authoritative server directly.
3. Query at least two recursive resolvers.
4. Test the application by name, not only by IP.

```bash
dig @ns1.example.com www.example.com A +noall +answer
dig @1.1.1.1 www.example.com A +noall +answer
dig @8.8.8.8 www.example.com A +noall +answer
curl -I https://www.example.com/
```

Rollback is the same process in reverse: restore the old value, verify authoritative publication, and wait for caches to expire.

## Troubleshooting Checklist

When DNS data looks wrong, ask:

- Which name and record type did the client request?
- Which resolver answered the client?
- Is the resolver returning cache or a fresh authoritative answer?
- Which authoritative servers are delegated for the zone?
- Do all authoritative servers return the same value?
- Is the TTL causing an expected propagation delay?
- Is the issue forward DNS, reverse DNS, mail DNS, or application caching?

Useful commands:

```bash
dig name.example.com A +noall +answer
dig name.example.com AAAA +noall +answer
dig name.example.com CNAME +noall +answer
dig example.com MX +noall +answer
dig example.com NS +noall +answer
dig example.com SOA +noall +answer
dig +trace name.example.com A
getent hosts name.example.com
```

`dig` inspects DNS. `getent hosts` asks through the system name-service path, which may include `/etc/hosts`, mDNS, LDAP, or other configured sources.
