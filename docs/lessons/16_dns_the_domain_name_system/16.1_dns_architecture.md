# 16.1 DNS Architecture

DNS is not just "name to IP." It is a distributed control plane for names, mail routing, service discovery, certificates, and operational ownership. A Linux operator needs to know which part of the DNS path is responsible for an answer before changing records or blaming a resolver.

!!! abstract "What you will learn"
    - Explain the major parts of DNS architecture.
    - Distinguish recursive resolvers, root servers, TLD servers, and authoritative servers.
    - Use Linux tools to identify who answered a DNS question.
    - Build a safe evidence trail for DNS incidents and migrations.
    - Recognize when a problem belongs to local resolver configuration, cache behavior, delegation, or authoritative data.

!!! warning "Production caution"
    DNS changes can take time to expire from caches. Plan changes around TTLs, validate authoritative data before lowering risk, and keep a rollback record.

## The DNS Path

When an application asks for `www.example.com`, it usually does not query the root servers directly. The common path looks like this:

```text
application
  -> local resolver library
  -> stub resolver or local cache
  -> recursive resolver
  -> root servers
  -> TLD servers
  -> authoritative nameservers
  -> recursive resolver cache
  -> client answer
```

Each layer has a different responsibility:

| Layer | Responsibility | Linux evidence |
| --- | --- | --- |
| Application | Requests a name lookup | application logs, `strace`, error messages |
| Resolver library | Reads local resolver configuration | `/etc/resolv.conf`, `getent hosts` |
| Stub or local cache | Forwards or caches local queries | `resolvectl status`, `systemctl status systemd-resolved` |
| Recursive resolver | Performs the full lookup and caches results | `dig @<resolver> name type` |
| Root servers | Point to TLD servers | `dig +trace` |
| TLD servers | Point to authoritative nameservers | `dig NS example.com +trace` |
| Authoritative servers | Hold zone records | `dig @<auth-server> name type` |

Troubleshooting gets much easier when you can name the layer you are testing.

## Recursive Versus Authoritative

Two DNS roles matter constantly:

- A recursive resolver finds answers on behalf of clients and caches the result.
- An authoritative server publishes records for a zone.

That distinction is the heart of DNS troubleshooting. A recursive resolver can give you a stale or filtered answer even when the authoritative server is correct. An authoritative server can be wrong even when your local resolver is working perfectly.

Compare both views:

```bash
dig www.example.com A
dig @1.1.1.1 www.example.com A
dig @8.8.8.8 www.example.com A
dig NS example.com
dig @ns1.example.com www.example.com A
```

If the recursive answers disagree, suspect cache age, resolver policy, split DNS, DNSSEC validation, or propagation timing. If the authoritative answer is wrong, the zone data or delegation needs attention.

## Root, TLD, And Delegation

DNS is delegated from the top down:

```text
.                 root
com.              top-level domain
example.com.      delegated zone
www.example.com.  record inside the zone
```

The root zone does not store every host. It knows where TLDs live. A TLD such as `.com` knows which authoritative nameservers serve `example.com`. The authoritative nameservers know the records inside `example.com`.

Use a trace to see delegation:

```bash
dig +trace www.example.com A
```

In a healthy trace, you should be able to identify:

- root referral
- TLD referral
- authoritative nameserver
- final answer
- TTLs returned at each step

If the trace stops before the final answer, the failure is often delegation, DNSSEC, nameserver reachability, or zone publication.

## Local Resolver Configuration

On Linux, the application rarely chooses the DNS server directly. The system resolver configuration controls the first hop.

Common inspection commands:

```bash
cat /etc/resolv.conf
resolvectl status
nmcli device show | grep -i dns
getent hosts www.example.com
```

Look for:

- which resolver IPs are configured
- whether `systemd-resolved`, NetworkManager, or another local cache is involved
- search domains
- split-DNS routing
- VPN-provided resolvers
- container or namespace-specific resolver files

When containers are involved, inspect resolver state from inside the container too:

```bash
docker exec <container> cat /etc/resolv.conf
docker exec <container> getent hosts www.example.com
```

The host and container may not be using the same resolver path.

## Caches And TTLs

DNS answers include TTLs that tell caches how long an answer can be reused.

Inspect TTLs:

```bash
dig www.example.com A
dig +nocmd www.example.com A +noall +answer
```

During a migration, TTLs define how long old answers may remain valid. Lowering a TTL immediately before a migration may not help if clients already cached the old longer TTL.

Operational rule:

1. Lower TTLs well before the change.
2. Wait for the old TTL to expire.
3. Make the record change.
4. Validate authoritative answers.
5. Watch recursive resolver answers catch up.
6. Raise TTLs after the new state is stable.

## Record Types In The Architecture

Different record types support different systems:

| Type | Purpose |
| --- | --- |
| `A` | IPv4 address |
| `AAAA` | IPv6 address |
| `CNAME` | Alias to another name |
| `MX` | Mail exchanger for a domain |
| `NS` | Authoritative nameserver delegation |
| `TXT` | Verification, SPF, DKIM, DMARC, and other metadata |
| `SRV` | Service discovery |
| `CAA` | Certificate authority authorization |
| `PTR` | Reverse DNS mapping |

Use the record type that matches the incident. A web outage may need `A`, `AAAA`, `CNAME`, and `CAA` checks. A mail issue may need `MX`, `TXT`, DKIM, DMARC, and reverse DNS checks.

## DNSSEC In The Path

DNSSEC adds signed validation to DNS. When DNSSEC breaks, some resolvers may return `SERVFAIL` while others appear to work if validation is disabled.

Useful checks:

```bash
dig example.com DNSKEY
dig example.com DS
dig +dnssec www.example.com A
```

Common DNSSEC failure causes:

- stale DS record at the parent zone
- expired signatures
- incorrect key rollover
- authoritative servers serving inconsistent signed data

If DNSSEC is in use, include validation status in your incident evidence.

## Incident Evidence Template

When escalating DNS trouble, include enough evidence for the next operator to reproduce the lookup.

```text
Name:
Record type:
Expected answer:
Observed answer:
Client location:
Client resolver:
Command used:
Authoritative nameservers:
Authoritative answer:
Recursive resolver answers:
TTL observed:
Recent change:
Impact:
Rollback option:
```

This template prevents vague reports like "DNS is broken" and points the investigation at the responsible layer.

## Hands-On Practice

Use a domain you own or a public example domain.

1. Find the local resolver path with `resolvectl status` or `/etc/resolv.conf`.
2. Query the default resolver with `dig`.
3. Query two public recursive resolvers.
4. Query the authoritative nameserver directly.
5. Run `dig +trace`.
6. Record which layer would own a stale answer, a missing record, and a broken delegation.
