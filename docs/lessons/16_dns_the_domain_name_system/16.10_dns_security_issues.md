## 16.10 DNS Security Issues

DNS security work starts by deciding what role each server plays. A recursive
resolver, an authoritative name server, and a zone-signing workstation have
different risks. Treating them as one generic "DNS server" is how open
resolvers, leaked zone transfers, stale DNSSEC keys, and confusing incident
notes happen.

!!! abstract "What you will learn"
    - Identify common DNS security risks: cache poisoning, amplification, zone-transfer exposure, unauthorized dynamic updates, and DNSSEC failures.
    - Inspect DNS behavior with read-only commands before changing a resolver or authoritative server.
    - Apply safer BIND controls for recursion, transfers, dynamic updates, response policy, and rate limiting.
    - Build a short verification and handoff note for a DNS security change.

!!! warning "Safety boundary"
    DNS security changes can break many systems at once. Lower TTLs before planned authority changes, test with `named-checkconf` and `named-checkzone`, keep a rollback copy, and verify from more than one network path.

## Start With The Server Role

Record the role before you audit the configuration.

| Role | Main job | Common security failure |
| --- | --- | --- |
| Recursive resolver | Answers client lookups by querying the DNS tree | Open recursion exposed to the Internet |
| Authoritative server | Publishes zones for domains you control | Unauthorized zone transfers or stale records |
| Hidden primary | Holds editable zone files and transfers to public secondaries | Weak transfer/update controls |
| DNSSEC signer | Maintains signing keys and signed zone output | Expired signatures or mishandled keys |

Use read-only checks first:

```bash
dig @127.0.0.1 example.com A
dig @127.0.0.1 example.com A +dnssec
dig @127.0.0.1 example.com AXFR
dig @127.0.0.1 version.bind TXT chaos
sudo named-checkconf -z
sudo rndc status
```

The `AXFR` command should fail unless the client is an approved secondary. A
public `version.bind` answer is not automatically a vulnerability, but many
operators disable or mask it to avoid unnecessary fingerprinting.

## Restrict Recursion

The most important resolver rule is simple: answer recursive queries only for
clients you operate.

```text
acl internal_clients {
    192.0.2.0/24;
    2001:db8:20::/48;
    localhost;
};

options {
    recursion yes;
    allow-recursion { internal_clients; };
    allow-query-cache { internal_clients; };
    allow-query { internal_clients; };
};
```

For an Internet-facing authoritative-only server, disable recursion:

```text
options {
    recursion no;
    allow-recursion { none; };
};
```

Verify from an internal host and from an outside network if possible:

```bash
dig @dns1.example.net www.example.com A
dig @dns1.example.net linux.org A
```

An authoritative server may answer for its own zones, but it should refuse to
resolve unrelated names for arbitrary clients.

## Limit Zone Transfers

Zone transfers are normal between primary and secondary servers. They should
not be available to the world.

```text
acl secondary_servers {
    198.51.100.20;
    2001:db8:51::20;
};

zone "example.net" IN {
    type primary;
    file "/etc/bind/zones/db.example.net";
    allow-transfer { secondary_servers; };
    also-notify { secondary_servers; };
};
```

For stronger control, use TSIG keys so a source address alone is not enough:

```text
key "xfr-secondary-1" {
    algorithm hmac-sha256;
    secret "base64-secret-from-tsig-keygen";
};

server 198.51.100.20 {
    keys { "xfr-secondary-1"; };
};
```

Then verify both paths:

```bash
dig @dns1.example.net example.net AXFR
dig @dns2.example.net example.net SOA
```

The first command should fail from an untrusted host. The second should show
that secondaries still receive the current SOA serial.

## Protect Dynamic Updates

Dynamic DNS updates are powerful because they change zone data without editing
the zone file manually. Do not leave them open by client address alone.

```text
zone "dynamic.example.net" IN {
    type primary;
    file "/var/lib/bind/dynamic.example.net";
    update-policy {
        grant dhcp-updater zonesub ANY;
    };
};
```

Operational checks:

```bash
sudo rndc zonestatus dynamic.example.net
sudo journalctl -u named --since "1 hour ago" | grep -i update
```

For incident notes, record which identity updated the name, what record changed,
and whether the update came from DHCP automation, orchestration, or a manual
operator action.

## Use DNSSEC Carefully

DNSSEC gives clients a way to validate that DNS answers were signed by the
right zone owner. It does not encrypt DNS traffic and it does not prove that the
server is healthy.

Check validation from a resolver:

```bash
dig @127.0.0.1 dnssec-failed.org A +dnssec
dig @127.0.0.1 cloudflare.com A +dnssec
```

Check a signed zone before publishing:

```bash
sudo named-checkzone example.net /etc/bind/zones/db.example.net
sudo rndc signing -list example.net
dig @dns1.example.net example.net DNSKEY +dnssec
dig @dns1.example.net www.example.net A +dnssec
```

Common DNSSEC failures include expired signatures, missing DS records at the
parent zone, mismatched key tags, and unsigned records served from an old zone
copy. Keep DNSSEC key rollovers documented with dates, owners, and rollback
conditions.

## Reduce Amplification And Abuse

DNS can amplify traffic because small UDP queries can trigger larger responses.
Combine network controls with BIND controls.

```text
options {
    rate-limit {
        responses-per-second 10;
        window 5;
    };
    minimal-responses yes;
};
```

Also confirm that firewalls allow only intended DNS paths:

```bash
sudo ss -lunpt | grep ':53'
sudo nft list ruleset | grep -E ' dport 53| sport 53'
sudo iptables -S | grep -- '--dport 53'
```

The exact firewall command depends on the host. The evidence you need is the
same: which interfaces accept TCP and UDP port 53, and from which source
networks.

## Monitor The Signals That Matter

DNS security monitoring should separate routine noise from signs of exposure or
failure.

Watch for:

- repeated external recursion attempts;
- unexpected `AXFR` requests;
- dynamic update failures or updates from unusual sources;
- DNSSEC validation errors after key or parent-zone changes;
- query spikes for random subdomains;
- SERVFAIL increases after configuration changes;
- secondaries lagging behind the primary SOA serial.

Useful commands:

```bash
sudo journalctl -u named --since "30 minutes ago"
sudo rndc stats
sudo rndc recursing
dig @dns2.example.net example.net SOA +short
dig @dns1.example.net example.net SOA +short
```

Query logging can help during an incident, but leave it on only as long as
needed. It can create sensitive data and fill disks quickly.

## Common Failure Patterns

- **Open resolver:** `dig @server unrelated-domain.example A` succeeds from the Internet.
- **Broken secondary:** zone transfer controls are tightened, but the allowed secondary IP or TSIG key is wrong.
- **DNSSEC outage:** a DS record is published at the parent before the child zone serves matching DNSKEY records.
- **Stale signed zone:** the unsigned zone was edited, but the signed output was not regenerated or reloaded.
- **Overbroad dynamic updates:** one update key can modify records outside its intended subdomain.
- **Firewall mismatch:** UDP 53 is allowed, but TCP 53 is blocked, breaking large DNS responses and zone transfers.

## Hands-On Practice

Use a disposable BIND lab or a non-production resolver.

1. Identify whether the server is recursive, authoritative, or both.
2. Run read-only checks for recursion, zone transfers, DNSSEC validation, and listening sockets.
3. Add or tighten one control in a lab configuration: `allow-recursion`, `allow-transfer`, `update-policy`, `minimal-responses`, or `rate-limit`.
4. Run `sudo named-checkconf -z`.
5. Reload with `sudo rndc reload` only after validation succeeds.
6. Re-run the same `dig` checks and write a short before/after note.
