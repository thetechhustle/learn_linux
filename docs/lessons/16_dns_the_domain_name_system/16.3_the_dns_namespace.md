## 16.3 The DNS Namespace

!!! abstract "What you will learn"
    - Describe the DNS namespace as a delegated hierarchy from the root to hostnames.
    - Distinguish a domain, subdomain, fully qualified domain name, and zone.
    - Use `dig` to follow delegation evidence without changing DNS data.
    - Explain why namespace ownership matters during migrations and incident response.

!!! example "Field story"
    A company is moving `www.example.com` to a new hosting provider while keeping email on the old provider for another week. Web traffic fails after the cutover, but mail still works. Before editing records, you need to prove which part of the namespace is delegated to which name servers and which zone actually owns each record.

!!! success "Operator principle"
    Treat DNS names as paths through delegated responsibility. The right fix depends on which zone owns the name, not just on the record you hoped to change.

## Names Are Paths

DNS is organized as a tree. The root sits at the top and is written as a trailing dot: `.`. Below it are top-level domains such as `com.`, `org.`, and `net.`. Below those are registered domains such as `example.com.`, and below those are names such as `www.example.com.` or `mail.example.com.`.

A name written all the way to the root is a fully qualified domain name, often shortened to FQDN. The trailing dot matters in DNS data because it says "this name is complete." Without the trailing dot, some tools and configuration formats may treat the name as relative to another domain.

Common namespace terms:

- **Domain:** Any node in the tree, such as `example.com.` or `engineering.example.com.`.
- **Subdomain:** A domain below another domain, such as `api.example.com.` below `example.com.`.
- **Host name:** A name that commonly maps to a service endpoint, such as `www.example.com.`. A host name can have `A`, `AAAA`, `CNAME`, or other records.
- **Zone:** The part of the namespace served from one administrative data set.
- **Delegation:** The handoff from a parent zone to child-zone name servers through `NS` records.

## Domains Versus Zones

Domains and zones are related, but they are not the same thing. A domain is a position in the namespace. A zone is the administrative boundary for DNS data.

For example, `example.com.` might be one zone. If the team delegates `dev.example.com.` to another set of name servers, then `dev.example.com.` becomes a separate zone even though it is still part of the `example.com.` domain tree. The parent zone points to the child; the child zone owns its own records.

That distinction prevents common mistakes:

- Editing `example.com.` records will not fix a broken `app.dev.example.com.` record if `dev.example.com.` is delegated elsewhere.
- Changing registrar name servers affects the domain's delegation from the TLD, not just one host record.
- A `CNAME` target can live in another zone, so both the alias and target need to be checked during an outage.

## Inspect Delegation Safely

Use read-only DNS lookups first. These commands do not change DNS records.

```bash
dig +short NS example.com
dig +trace www.example.com
dig @a.gtld-servers.net example.com NS +noall +authority
dig @ns1.example.com www.example.com A +noall +answer
```

What to look for:

- `NS` answers show which name servers are authoritative for a zone.
- `dig +trace` walks from the root toward the final answer, showing delegation steps.
- Querying a specific name server with `@server` separates authoritative data from resolver cache.
- The answer section shows returned records; the authority section often shows where responsibility moves next.

If `dig +trace` and your normal resolver disagree, suspect cache, split-horizon DNS, resolver policy, or stale delegation before assuming the zone file is wrong.

## Read A Zone File

A small zone file shows how namespace data is represented:

```dns-zone
$TTL 3600
@       IN  SOA ns1.example.com. hostmaster.example.com. (
            2026051201 ; serial
            1h         ; refresh
            15m        ; retry
            1w         ; expire
            5m )       ; negative cache TTL

        IN  NS  ns1.example.com.
        IN  NS  ns2.example.com.
        IN  MX  10 mail.example.com.

www     IN  A   203.0.113.10
mail    IN  A   203.0.113.20
dev     IN  NS  ns1.dev.example.net.
```

In this example:

- `@` means the current zone origin, such as `example.com.`.
- `www` expands to `www.example.com.`.
- Names ending in `.` are already fully qualified.
- The `dev` `NS` record delegates `dev.example.com.` to another zone.
- The SOA serial should change whenever authoritative zone data changes.

## Troubleshooting Namespace Problems

Namespace mistakes often look like random DNS failures until you map the delegation path.

| Symptom | Likely cause | First check |
| --- | --- | --- |
| Parent says one set of name servers, child says another | Stale or incorrect delegation | `dig +trace name.example.com` |
| Internal users get a different answer than external users | Split DNS or resolver policy | Query internal and public resolvers separately |
| A child domain cannot be resolved | Missing or wrong child-zone `NS` records | Query the parent zone authority |
| Host works by old name but not new name | Record added to the wrong zone | Identify the authoritative zone for both names |
| Recent fix works for some users only | TTL and resolver cache delay | Compare authoritative answer with cached resolver answer |

## Safe Change Workflow

When you need to change namespace data:

1. Identify the authoritative zone for the exact name.
2. Capture current `NS`, `SOA`, and target-record answers.
3. Check the current TTL and decide whether waiting is required.
4. Make the smallest change in the owning zone.
5. Increment the SOA serial if you maintain zone files directly.
6. Query the authoritative name servers before checking recursive resolvers.
7. Keep the old value and rollback plan in the change note.

Avoid changing registrar delegation, authoritative name server lists, and production host records in the same maintenance window unless you have a tested rollback path. Combining those changes makes failures harder to isolate.

## Hands-On Practice

Run these commands from a lab machine with internet access:

1. Pick a public domain you are allowed to inspect.
2. Find its authoritative name servers:

   ```bash
   dig +short NS example.com
   ```

3. Trace a hostname through the namespace:

   ```bash
   dig +trace www.example.com
   ```

4. Query one authoritative server directly:

   ```bash
   dig @$(dig +short NS example.com | head -n 1) www.example.com A +noall +answer
   ```

5. Write a short note that names the parent domain, child domain, authoritative name servers, returned record, and TTL.
