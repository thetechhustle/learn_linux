# 16.12 Recommended Reading

DNS rewards slow reading. The protocol is old, widely implemented, and full of edge cases that only make sense when you connect the standards, the server documentation, and real operational failure reports.

!!! abstract "What you will learn"
    - Choose DNS references that match the question in front of you: protocol behavior, BIND configuration, resolver behavior, DNSSEC, or incident response.
    - Build a short reading path before making a production DNS change.
    - Capture useful notes from RFCs and vendor documentation without turning every investigation into a research project.

!!! success "Operator principle"
    Read from the source closest to the failure. Use RFCs for protocol questions, implementation manuals for server behavior, and your own logs and zone files for local truth.

## Start with protocol references

Use the core DNS RFCs when you need to understand why a resolver or authoritative server behaves a certain way.

- **RFC 1034, Domain Names - Concepts and Facilities** explains the DNS namespace, zones, delegation, and the resolver model.
- **RFC 1035, Domain Names - Implementation and Specification** defines message formats, resource records, and the wire behavior behind common tools such as `dig`.
- **RFC 2308, Negative Caching of DNS Queries** explains why NXDOMAIN and NODATA answers can persist after you fix a zone.
- **RFC 6891, Extension Mechanisms for DNS (EDNS(0))** explains larger UDP responses and options that matter when debugging truncation, firewalls, and DNSSEC.

Read RFCs with a specific question in mind. For example, "Why is this NXDOMAIN answer still cached?" is a better starting point than "Learn all DNS standards."

## Read BIND documentation for server behavior

When operating BIND, keep the current BIND Administrator Reference Manual close. It is the practical source for:

- `named.conf` syntax and statement scope.
- Zone-file loading and reload behavior.
- Views, ACLs, recursion controls, and transfer controls.
- Logging categories and severity levels.
- `named-checkconf`, `named-checkzone`, `rndc`, `dig`, and DNSSEC utilities.

Prefer the versioned documentation that matches your installed package. Distribution packages can lag upstream releases, and examples from a newer ARM can mention options your server does not support.

Check local version evidence before copying configuration:

```bash
named -v
named -V
named-checkconf -v
```

## Keep resolver and client references separate

Not every DNS problem is a BIND problem. Client-side resolution often depends on system libraries, local caching services, NetworkManager, `systemd-resolved`, `nsswitch.conf`, and `/etc/hosts`.

Useful local references include:

- `man resolv.conf`
- `man nsswitch.conf`
- `man hosts`
- `man systemd-resolved`
- `resolvectl status`
- Distribution networking documentation for your release

When a host resolves one name differently from another host, inspect the client path before changing authoritative DNS.

## Study DNSSEC and security from operational sources

DNSSEC, open recursion, zone transfers, and amplification risk are easy to describe and easy to misconfigure. Read both protocol-level and operator-level material before enabling or changing controls.

Good topics to research before production work include:

- Recursive resolver access control.
- Authoritative-only server hardening.
- TSIG keys for zone transfers and dynamic updates.
- DNSSEC validation versus authoritative signing.
- Key rollover procedures.
- Response-rate limiting and amplification controls.

For DNSSEC specifically, read your server documentation and your domain registrar or DNS provider documentation together. A correct signed zone can still fail if DS records at the parent zone are wrong.

## Build a reading note for changes

For a DNS change with user impact, write a short note before editing the zone or server config:

1. What are we changing?
2. Which authoritative servers answer for this zone?
3. Which RFC or manual page explains the behavior?
4. What is the current TTL?
5. What validation command proves the new behavior?
6. What rollback command or previous file version restores service?

Example:

```text
Change: add mail.example.com A record for new mail relay.
Reference: RFC 1035 A records; BIND ARM zone-file format.
TTL: 300 during migration.
Validate: named-checkzone example.com db.example.com; dig @ns1.example.com mail.example.com A +norecurse.
Rollback: restore db.example.com from git and reload the zone with rndc reload example.com.
```

## Hands-on practice

Use a lab zone or a copy of a real zone file.

1. Pick one unfamiliar record type from a zone file, such as `MX`, `TXT`, `SRV`, `CAA`, or `SSHFP`.
2. Find the relevant RFC, BIND documentation section, or provider documentation for that record type.
3. Write a three-line note: purpose, required fields, and one common mistake.
4. Use `dig` to query a public example of the record type.
5. Explain whether the answer came from an authoritative server, a recursive resolver, or cache.

## Check your understanding

- When would you reach for an RFC instead of the BIND Administrator Reference Manual?
- Why should you check `named -V` before applying an example from the web?
- Which local files or services can change name resolution before a query ever leaves the host?
- What DNSSEC mistake can make a zone look broken even when the authoritative server is answering?
- What should a useful pre-change reading note include?
