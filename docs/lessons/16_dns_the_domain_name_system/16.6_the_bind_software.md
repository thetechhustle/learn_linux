## 16.6 The BIND Software

BIND is the most common full-featured DNS server you will meet on Unix and
Linux systems. Its main daemon is `named`, and it can act as an authoritative
server, a recursive resolver, or both if you configure it that way. In
production, your first job is to know which role the host is supposed to play
before you change anything.

!!! abstract "What you will learn"
    - Identify the BIND packages, service, and important configuration paths on
      a Linux host.
    - Distinguish authoritative service from recursive resolver behavior.
    - Validate BIND configuration and zone files before restarting `named`.
    - Collect useful evidence when BIND is unhealthy or returning the wrong
      answer.

!!! warning "Change safety"
    DNS failures spread quickly. Lower TTLs before planned changes, keep a copy
    of the previous zone file, validate syntax offline, and know which command
    reloads one zone instead of restarting the whole daemon.

## What BIND Provides

The BIND distribution usually includes these tools:

- `named`: the DNS server daemon.
- `named-checkconf`: validates the main BIND configuration.
- `named-checkzone`: validates a zone file against a zone name.
- `rndc`: controls a running `named` process, such as reloads and status checks.
- `dig`: queries DNS servers and displays the answer, authority, and timing
  details.

Package names vary by distribution. Debian and Ubuntu commonly use `bind9` and
`bind9-utils`; Red Hat-family systems commonly use `bind` and `bind-utils`.

## Find the Running Service

Start with read-only evidence:

```bash
systemctl status named
systemctl status bind9
ss -lunpt | grep ':53'
ps -ef | grep '[n]amed'
```

Most systems use either `named.service` or `bind9.service`, not both. UDP port
53 handles most DNS queries; TCP port 53 is used for large answers, zone
transfers, and fallback behavior.

If the service is running but clients still fail, test the server directly:

```bash
dig @127.0.0.1 example.com SOA
dig @127.0.0.1 www.example.com A +norecurse
dig @192.0.2.53 www.example.com A +norecurse
```

`+norecurse` is useful when checking authoritative answers because it asks the
server to answer only from its own authority or cache.

## Configuration Layout

Common BIND paths include:

- `/etc/named.conf` on many Red Hat-family systems.
- `/etc/bind/named.conf` on many Debian-family systems.
- `/etc/bind/named.conf.local` for local authoritative zones on Debian-family
  systems.
- `/var/named/` or `/var/cache/bind/` for zone files, depending on the
  distribution.
- `/var/log/` or `journalctl -u named` / `journalctl -u bind9` for logs.

A small authoritative zone declaration might look like this:

```text
zone "example.com" {
    type primary;
    file "/etc/bind/zones/db.example.com";
    allow-transfer { 192.0.2.10; };
};
```

Older BIND examples often use `type master;`. Modern BIND accepts
`type primary;`, which describes the role more clearly.

## Validate Before Reloading

Never discover syntax errors by restarting DNS in production. Validate first:

```bash
sudo named-checkconf
sudo named-checkconf /etc/bind/named.conf
sudo named-checkzone example.com /etc/bind/zones/db.example.com
```

Then prefer a narrow reload:

```bash
sudo rndc status
sudo rndc reload example.com
sudo rndc flushname www.example.com
```

Use a full service restart only when the change requires it and you have a
rollback plan:

```bash
sudo systemctl reload named
sudo systemctl restart named
```

Reloading is usually less disruptive than restarting. A restart drops the daemon
and can interrupt active transfers or briefly remove the server from service.

## Authoritative Versus Recursive Behavior

BIND can answer for zones it hosts and can also perform recursion for clients.
Those are different jobs:

- An authoritative server should answer for its own zones and usually refuse
  recursion from the public Internet.
- A recursive resolver should answer clients it is responsible for and should
  not usually host public authoritative zones.

Useful checks:

```bash
dig @ns1.example.com example.com SOA +norecurse
dig @resolver.example.net example.org A
dig @public-ip.example.net example.org A +recurse
```

If an Internet-facing authoritative server returns recursive answers for
untrusted clients, review `allow-recursion`, `recursion`, `allow-query-cache`,
and the server's firewall exposure.

## Zone File Operations

A zone file change is not complete until all of these are true:

1. The SOA serial number increased.
2. `named-checkzone` passes.
3. The target zone reloads successfully.
4. A direct query to the authoritative server returns the expected answer.
5. A second query confirms the old answer is not being served from a stale cache
   you control.

Example workflow:

```bash
sudo cp /etc/bind/zones/db.example.com /etc/bind/zones/db.example.com.$(date +%Y%m%d%H%M).bak
sudoedit /etc/bind/zones/db.example.com
sudo named-checkzone example.com /etc/bind/zones/db.example.com
sudo rndc reload example.com
dig @127.0.0.1 www.example.com A +norecurse
```

For planned migrations, lower relevant TTLs before the change window and wait
for the old TTL to expire. Raising the TTL again is a separate post-change step.

## Troubleshooting Patterns

Use symptoms to choose the next check:

| Symptom | Likely area | Evidence to collect |
| --- | --- | --- |
| `SERVFAIL` | Syntax, DNSSEC, unreachable upstream, or broken delegation | `journalctl -u named`, `named-checkconf`, `named-checkzone`, `dig +trace` |
| `NXDOMAIN` | Missing name or wrong zone origin | Direct authoritative `dig`, zone file record, `$ORIGIN` |
| Old answer persists | TTL or cache | `dig +ttlunits`, query authoritative server directly, resolver cache status |
| Zone transfer fails | ACL, TSIG, TCP/53, secondary config | `allow-transfer`, logs on both servers, `dig AXFR` from an allowed host |
| Service will not start | Config syntax, permissions, bad include path | `systemctl status`, `journalctl -xeu named`, `named-checkconf` |

## Hands-on Practice

Run these on a disposable VM, container, or lab machine.

1. Install the BIND package and utility package for your distribution.
2. Identify whether the service name is `named` or `bind9`.
3. Run `named-checkconf` against the default configuration.
4. Create a small lab zone file for `lab.example` with an SOA, one NS record,
   and one A record.
5. Validate it with `named-checkzone`.
6. Load or reload only that zone.
7. Query the authoritative answer with `dig @127.0.0.1 host.lab.example A
   +norecurse`.
8. Break one record intentionally, run the validation again, and record the
   error message.
