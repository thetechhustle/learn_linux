# 16.11 BIND Debugging

!!! abstract "What you will learn"
    - Separate client resolver problems from authoritative BIND problems.
    - Use `dig`, `rndc`, `journalctl`, and BIND validation tools during incidents.
    - Interpret common DNS response codes such as `SERVFAIL`, `REFUSED`, and `NXDOMAIN`.
    - Build a short evidence trail before changing production DNS.

!!! success "Operator principle"
    Debug DNS from the outside in: client path, recursive resolver, authoritative server, configuration, zone data, logs. Do not start by editing files.

## Start With The Symptom

Capture the exact query that is failing:

```bash
dig app.example.test A
dig app.example.test AAAA
dig app.example.test CNAME
getent hosts app.example.test
```

Write down:

- the name
- the record type
- the resolver that answered
- the response code
- the answer section
- the TTL
- whether the problem happens from one network or every network

`dig` shows DNS behavior. `getent hosts` shows what the local system resolver path returns, which may include `/etc/hosts`, mDNS, LDAP, or other name-service sources.

## Query The Right Server

First query the normal resolver path:

```bash
dig app.example.test A +noall +answer +comments
```

Then query the authoritative server directly:

```bash
dig @ns1.example.test app.example.test A +noall +answer +comments
```

If the authoritative answer is correct but clients see the wrong answer, suspect caching, resolver configuration, split DNS, or client name-service behavior.

If the authoritative answer is wrong, inspect BIND configuration and zone data.

## Check Service Health

On Debian and Ubuntu:

```bash
systemctl status bind9 --no-pager
journalctl -u bind9 -n 100 --no-pager
```

On many Red Hat-family systems:

```bash
systemctl status named --no-pager
journalctl -u named -n 100 --no-pager
```

Ask BIND itself:

```bash
sudo rndc status
```

If `rndc` cannot connect, check the service, control-channel configuration, key permissions, and whether you are running the command with enough privilege.

## Validate Configuration And Zones

Before reloading or restarting, validate configuration syntax:

```bash
named-checkconf /etc/bind/named.conf
```

Print the parsed configuration when include files make the layout hard to follow:

```bash
named-checkconf -p | less
```

Validate a zone file:

```bash
named-checkzone example.test /etc/bind/zones/db.example.test
```

Common failures include:

- missing semicolon
- missing closing brace
- invalid record syntax
- SOA serial typo
- relative name that should have been absolute
- CNAME placed at a name that also has other records

## Response Codes

### NOERROR

`NOERROR` means the query was processed successfully. It may still have no answer.

```bash
dig @ns1.example.test example.test TXT +comments
```

No answer with `NOERROR` often means the name exists, but not for the type you asked for.

### NXDOMAIN

`NXDOMAIN` means the queried name does not exist.

```bash
dig @ns1.example.test missing.example.test A +comments
```

If `NXDOMAIN` is unexpected, check:

- the zone file name and `$ORIGIN`
- whether the record was added under the correct owner name
- whether the zone reloaded successfully
- negative-cache TTL

### REFUSED

`REFUSED` means the server declined to answer.

Common causes:

- query blocked by `allow-query`
- recursion attempted from an unauthorized network
- view matching sent the client to a view without the zone
- firewall or ACL design expects the client to use another resolver

### SERVFAIL

`SERVFAIL` means the server failed while trying to answer.

Common causes:

- DNSSEC validation failure
- upstream resolver failure
- lame delegation
- zone load failure
- permission problem reading a zone file
- broken forwarding configuration

Use logs and direct authoritative queries to narrow the cause.

## Debug Recursion Problems

If BIND is acting as a recursive resolver, test from an allowed client:

```bash
dig @10.0.0.53 www.kernel.org A +comments
```

Then test from a network that should not be allowed:

```bash
dig @public.example.test www.kernel.org A +comments
```

The public query should not get recursive service. If it does, tighten `allow-recursion` and `allow-query-cache`.

Relevant configuration:

```conf
recursion yes;
allow-recursion { trusted-clients; };
allow-query-cache { trusted-clients; };
```

## Debug Authoritative Problems

Check whether BIND is authoritative for the zone:

```bash
dig @ns1.example.test example.test SOA +noall +answer
dig @ns1.example.test example.test NS +noall +answer
```

Check the serial on primary and secondary servers:

```bash
dig @ns1.example.test example.test SOA +noall +answer
dig @ns2.example.test example.test SOA +noall +answer
```

If the secondary serial is old, check:

- `allow-transfer` on the primary
- `primaries` or `masters` on the secondary
- TCP port 53 between servers
- notify behavior
- logs on both servers

## Use `rndc` Carefully

Reload one zone:

```bash
sudo rndc reload example.test
```

Reload all zones and configuration:

```bash
sudo rndc reload
```

Show zone status:

```bash
sudo rndc zonestatus example.test
```

Increase debug logging temporarily:

```bash
sudo rndc trace 3
```

Turn it back off:

```bash
sudo rndc notrace
```

Debug tracing can produce a lot of output. Use it briefly and record when you enabled and disabled it.

## Query Logging

Query logging is useful when you need to prove whether a request reaches BIND.

Temporary runtime toggle:

```bash
sudo rndc querylog on
sudo rndc querylog off
```

Use it sparingly. Busy resolvers can generate large logs quickly.

Persistent logging example:

```conf
logging {
    channel query_log {
        file "/var/log/named/query.log" versions 3 size 20m;
        severity info;
        print-time yes;
        print-category yes;
        print-severity yes;
    };

    category queries { query_log; };
};
```

Make sure the BIND service user can write to the log path.

## Debugging Checklist

Use this order during incidents:

1. Reproduce the exact query with `dig`.
2. Compare default resolver and authoritative answers.
3. Check service status and logs.
4. Validate configuration and zone files.
5. Check response code meaning.
6. Check view matching, recursion policy, and ACLs.
7. Check SOA serials across primary and secondary servers.
8. Reload only what changed.
9. Verify from the affected client path.
10. Record before and after evidence.

Commands worth keeping close:

```bash
dig name.example.test A +comments
dig @ns1.example.test name.example.test A +noall +answer +comments
dig @ns1.example.test example.test SOA +noall +answer
getent hosts name.example.test
named-checkconf /etc/bind/named.conf
named-checkzone example.test /etc/bind/zones/db.example.test
sudo rndc status
sudo rndc zonestatus example.test
journalctl -u bind9 -n 100 --no-pager
```

## Hands-On Practice

Use a lab BIND server.

1. Query a working record through the default resolver and directly against BIND.
2. Introduce a safe syntax error in a copy of a zone file and run `named-checkzone`.
3. Query a missing name and identify the `NXDOMAIN` response.
4. Query a record type that does not exist for a valid name and compare it with `NXDOMAIN`.
5. Turn query logging on briefly, make one query, and turn query logging off.
6. Record the evidence you would include in an incident handoff.
