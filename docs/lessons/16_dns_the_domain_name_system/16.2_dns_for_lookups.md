# 16.2 DNS For Lookups

DNS lookups are often the first invisible step in an outage. A web request, package install, database connection, TLS check, mail delivery, or API call may fail before any TCP connection starts because the name could not be resolved to the expected answer.

!!! abstract "What you will learn"
    - Run forward and reverse DNS lookups from Linux.
    - Compare application-level lookups with direct DNS queries.
    - Distinguish resolver failures, authoritative failures, stale cache, and wrong record data.
    - Use `dig`, `getent`, `resolvectl`, and packet captures as complementary evidence.
    - Build a safe lookup evidence trail for incidents and migrations.

!!! success "Operator principle"
    Test the same name through the same resolver path the application uses, then compare it with authoritative truth.

## Forward Lookups

A forward lookup asks for records attached to a name. The most common examples are `A` for IPv4 and `AAAA` for IPv6.

```bash
dig www.example.com A
dig www.example.com AAAA
```

Useful compact output:

```bash
dig +short www.example.com A
dig +nocmd www.example.com A +noall +answer
```

Read the answer as evidence:

- name queried
- record type
- TTL
- answer data
- DNS server that answered
- response status, such as `NOERROR`, `NXDOMAIN`, or `SERVFAIL`

Do not stop at "it returned an IP." Confirm the IP is the expected one for the environment you are testing.

## Reverse Lookups

A reverse lookup asks which name is associated with an IP address. It usually returns a `PTR` record.

```bash
dig -x 203.0.113.10
```

Reverse DNS matters for:

- mail reputation and delivery
- logging and investigations
- inventory checks
- provider handoffs
- certificate or hostname sanity checks

Reverse DNS does not prove that the forward record points back to the same address. Check both directions when the relationship matters:

```bash
dig -x 203.0.113.10
dig host.example.com A
```

## Application Path Versus DNS Tool Path

`dig` asks DNS directly. Many applications use the system resolver library, which may include `/etc/hosts`, NSS rules, local caches, split DNS, or VPN resolver routing.

Compare both paths:

```bash
getent hosts www.example.com
dig www.example.com A
resolvectl query www.example.com
```

If `getent` and `dig` disagree, inspect local resolver behavior before blaming public DNS.

Check local resolver configuration:

```bash
cat /etc/nsswitch.conf
cat /etc/resolv.conf
resolvectl status
```

Common reasons for disagreement:

- `/etc/hosts` overrides DNS
- `systemd-resolved` or another local cache is involved
- VPN split DNS routes the domain to a private resolver
- container resolver configuration differs from the host
- search domains expand short names
- DNSSEC validation fails in one resolver path

## Response Codes

DNS response codes tell you what kind of failure you are looking at.

| Response | Meaning | Common next check |
| --- | --- | --- |
| `NOERROR` with answer | Name exists and returned the requested data | Validate expected value and TTL |
| `NOERROR` with no answer | Name exists, but not for that record type | Query another type or check zone data |
| `NXDOMAIN` | Name does not exist | Check spelling, delegation, and authoritative server |
| `SERVFAIL` | Resolver could not complete the lookup | Check DNSSEC, upstream resolver, and authoritative health |
| `REFUSED` | Server refused the query | Check resolver policy or recursion settings |
| timeout | No response reached the client | Check network path, firewall, and server availability |

Use the response code to decide the next step instead of retrying the same query repeatedly.

## Query A Specific Resolver

During incidents, query more than one resolver.

```bash
dig @1.1.1.1 www.example.com A
dig @8.8.8.8 www.example.com A
dig @9.9.9.9 www.example.com A
```

Then query the resolver the host actually uses:

```bash
dig @$(awk '/^nameserver/ {print $2; exit}' /etc/resolv.conf) www.example.com A
```

If public resolvers agree but the local resolver disagrees, focus on the local resolver, corporate DNS, VPN DNS, cache state, or split-horizon policy.

## Query Authoritative Servers

Find authoritative nameservers:

```bash
dig NS example.com
```

Then query one directly:

```bash
dig @ns1.example.com www.example.com A
```

If the authoritative answer is correct but recursive resolvers are stale, the issue is usually cache and TTL timing. If the authoritative answer is wrong, fix the zone data or delegation.

## Trace The Lookup Path

`dig +trace` walks the delegation path from the root down.

```bash
dig +trace www.example.com A
```

Use it when you suspect:

- broken delegation
- wrong nameserver at the registrar
- parent-zone mismatch
- DNSSEC chain problems
- authoritative server reachability issues

Trace output is verbose, but it tells you where the lookup stops.

## Watch DNS On The Wire

Packet capture is useful when a host appears not to query the resolver at all, or when replies never return.

```bash
sudo tcpdump -ni any port 53
sudo tcpdump -ni any host 192.0.2.53 and port 53
```

For encrypted DNS, such as DNS over HTTPS or DNS over TLS, ordinary port 53 captures may show nothing. In that case, inspect the application, browser, or resolver configuration for DoH/DoT settings.

## Lookup Evidence Template

Use this during incidents:

```text
Name:
Record type:
Expected answer:
Observed answer:
Client host:
Application error:
getent result:
dig default resolver:
dig specific resolver:
authoritative nameserver:
authoritative answer:
response code:
TTL:
Recent DNS change:
Likely owner:

```

This keeps DNS handoffs precise and avoids vague reports such as "DNS is flaky."

## Hands-On Practice

Use a test domain or a domain you own.

1. Run `getent hosts <name>`.
2. Run `dig <name> A` and `dig <name> AAAA`.
3. Query two public resolvers.
4. Find the authoritative nameservers.
5. Query one authoritative nameserver directly.
6. Run `dig +trace`.
7. Write down which answer you would trust and why.
