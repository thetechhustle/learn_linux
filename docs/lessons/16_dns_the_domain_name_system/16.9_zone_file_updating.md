# 16.9 Zone File Updating

!!! abstract "What you will learn"
    - Update a DNS zone file without breaking authoritative service.
    - Increment SOA serial numbers correctly.
    - Validate and reload a changed zone with BIND tooling.
    - Verify the new DNS answer from authoritative and client paths.

!!! success "Operator principle"
    A zone-file edit is not done when the file is saved. It is done when the syntax is valid, the serial moved forward, the zone reloaded, and the expected answer is visible from the right resolver.

## Before You Edit

Start by proving what is currently live.

```bash
dig @127.0.0.1 example.test SOA +noall +answer
dig @127.0.0.1 www.example.test A +noall +answer
named-checkzone example.test /etc/bind/zones/db.example.test
```

Record the current SOA serial and answer. This gives you a rollback reference and keeps the change auditable.

For production zones, also check the TTL:

```bash
dig @127.0.0.1 www.example.test A +noall +answer
```

If the TTL is high and the change is planned, lower the TTL in advance and wait out the previous TTL before changing the actual address.

## Zone File Anatomy

A small zone file looks like this:

```text
$ORIGIN example.test.
$TTL 300
@   IN SOA ns1.example.test. hostmaster.example.test. (
        2026051201 ; serial
        3600       ; refresh
        900        ; retry
        1209600    ; expire
        300        ; negative cache TTL
)
@       IN NS  ns1.example.test.
@       IN NS  ns2.example.test.
ns1     IN A   192.0.2.53
ns2     IN A   192.0.2.54
www     IN A   192.0.2.80
mail    IN A   192.0.2.25
@       IN MX 10 mail.example.test.
```

Important parts:

- `$ORIGIN` defines the zone suffix for relative names.
- `$TTL` defines the default TTL for records that do not set one explicitly.
- `SOA` contains the serial and zone timing values.
- `NS` records name the authoritative servers.
- record rows publish names, types, and values.

The trailing dot matters. `mail.example.test.` is absolute. Without the dot, BIND may append `$ORIGIN`.

## Serial Numbers

Secondary DNS servers use the SOA serial to decide whether the zone changed. Always move the serial forward when changing the zone.

A common format is `YYYYMMDDNN`:

```text
2026051201
```

For the second change on the same day:

```text
2026051202
```

If a serial accidentally moves backward, secondaries may ignore the update. Fixing a bad serial can require deliberate serial arithmetic, so avoid casual edits.

## Add A Record

To add `blog.example.test`:

```text
blog    IN A   192.0.2.81
```

Full change:

```diff
-        2026051201 ; serial
+        2026051202 ; serial
@@
 www     IN A   192.0.2.80
+blog    IN A   192.0.2.81
 mail    IN A   192.0.2.25
```

Validate:

```bash
named-checkzone example.test /etc/bind/zones/db.example.test
```

Reload only the changed zone:

```bash
sudo rndc reload example.test
```

Verify:

```bash
dig @127.0.0.1 example.test SOA +noall +answer
dig @127.0.0.1 blog.example.test A +noall +answer
```

## Change A Record

Suppose `www.example.test` is moving from `192.0.2.80` to `192.0.2.90`.

```diff
-        2026051202 ; serial
+        2026051203 ; serial
@@
-www     IN A   192.0.2.80
+www     IN A   192.0.2.90
```

After validation and reload, compare authoritative and recursive paths:

```bash
dig @127.0.0.1 www.example.test A +noall +answer
dig www.example.test A +noall +answer
getent hosts www.example.test
```

If the authoritative answer is new but a client still sees the old address, check TTL and resolver cache before assuming the reload failed.

## Remove A Record

Remove a record only when you understand who still uses it.

```diff
-        2026051203 ; serial
+        2026051204 ; serial
@@
-oldapp  IN A   192.0.2.70
```

Then validate, reload, and query:

```bash
named-checkzone example.test /etc/bind/zones/db.example.test
sudo rndc reload example.test
dig @127.0.0.1 oldapp.example.test A
```

For removals, also consider negative caching. The SOA negative-cache TTL controls how long resolvers may remember that a name does not exist.

## Use Journaled Dynamic Zones Carefully

Some BIND zones are updated dynamically with `nsupdate`. Those zones may have journal files such as:

```text
db.example.test.jnl
```

Do not casually edit a dynamically updated zone file while BIND has pending journal changes. Freeze the zone first:

```bash
sudo rndc freeze example.test
sudoedit /etc/bind/zones/db.example.test
named-checkzone example.test /etc/bind/zones/db.example.test
sudo rndc thaw example.test
```

`freeze` syncs journaled changes to the zone file and pauses dynamic updates. `thaw` reloads the zone and resumes dynamic updates.

## Safer Edit Workflow

Use a repeatable workflow:

1. Query the current answer and SOA serial.
2. Back up or commit the current zone file.
3. Make the smallest possible edit.
4. Increment the serial.
5. Run `named-checkzone`.
6. Run `named-checkconf` if configuration files changed.
7. Reload the specific zone.
8. Query the authoritative server directly.
9. Query through the expected client path.
10. Record the before and after evidence.

Commands:

```bash
dig @127.0.0.1 example.test SOA +noall +answer
sudo cp /etc/bind/zones/db.example.test /etc/bind/zones/db.example.test.bak.$(date +%Y%m%d%H%M%S)
sudoedit /etc/bind/zones/db.example.test
named-checkzone example.test /etc/bind/zones/db.example.test
sudo rndc reload example.test
dig @127.0.0.1 example.test SOA +noall +answer
dig @127.0.0.1 www.example.test A +noall +answer
```

If your team manages zone files in Git, commit the zone-file change instead of relying only on timestamped backups.

## Troubleshooting

If the expected answer does not appear:

- Did `named-checkzone` pass?
- Did you increment the SOA serial?
- Did `rndc reload example.test` succeed?
- Are you querying the authoritative server or a caching resolver?
- Is the client seeing an old cached answer until TTL expiry?
- Are secondary servers receiving the new serial?
- Is the zone dynamic, with unsynced journal state?

Useful checks:

```bash
sudo rndc zonestatus example.test
dig @127.0.0.1 example.test SOA +noall +answer
dig @192.0.2.54 example.test SOA +noall +answer
journalctl -u bind9 -n 100 --no-pager
```

Replace `bind9` with `named` if that is your service name.

## Hands-On Practice

Use a disposable lab zone.

1. Query and record the current `SOA` and one `A` record.
2. Add `blog.example.test` with a test IP address.
3. Increment the serial.
4. Validate with `named-checkzone`.
5. Reload the zone with `rndc reload`.
6. Verify the new record from the authoritative server.
7. Remove the record, increment the serial again, reload, and verify that it is gone.
