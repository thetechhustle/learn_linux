# 09.6 Recommended Reading

!!! abstract "What you will learn"
    - Choose cloud reading material that improves operational judgment, not just vocabulary.
    - Use official provider documentation without becoming locked into one provider's mental model.
    - Read architecture frameworks, cost guidance, security guidance, and Linux runbooks as one practice.
    - Turn reading into short lab notes and operational checklists.

!!! example "Field story"
    A teammate sends five links about cloud computing and asks which ones matter before launching a production Linux workload.

    The useful answer is not "read everything." Start with provider fundamentals, shared responsibility, identity, networking, cost, backups, monitoring, and incident response. Then turn each reading session into one checklist improvement.

!!! success "Operator principle"
    Recommended reading should make you safer during real operations. If a resource does not improve how you inspect, change, verify, secure, or explain a system, it is background reading.

## How to read cloud material

Cloud documentation is large because cloud platforms are large. Do not try to memorize every service. Read with operator questions in mind:

- What responsibility moves to the provider?
- What responsibility stays with the Linux operator?
- What evidence proves the service is healthy?
- What permission grants access?
- What change could break users?
- What backup, rollback, or cleanup path exists?
- What cost continues after the lab or incident is over?

Keep short notes. A useful note has:

- source link.
- service or concept.
- operational takeaway.
- commands, console checks, or API checks.
- risks.
- follow-up lab idea.

Example:

```text
Source: AWS Well-Architected Framework
Topic: operational excellence
Takeaway: every workload needs runbooks, alarms, and change visibility.
Linux tie-in: systemd unit state and application logs are only one evidence layer.
Follow-up: add provider health and billing checks to the service handoff template.
```

## Official provider foundations

Start with official documentation for the provider you are using. Provider docs change, but official docs are still the best source for current service behavior, limits, and console labels.

Useful starting points:

- [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)
- [Microsoft Azure Well-Architected Framework](https://learn.microsoft.com/en-us/azure/well-architected/)
- [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework)
- [DigitalOcean Documentation](https://docs.digitalocean.com/)

Read these for concepts, not just product names:

- reliability.
- security.
- operational excellence.
- performance efficiency.
- cost optimization.
- sustainability or resource efficiency, when covered.

Then map each idea back to Linux:

- What does the provider dashboard prove?
- What does the Linux host prove?
- Where do logs live?
- Where are credentials stored?
- Which firewall layer controls the path?
- Which backup or snapshot can be restored?

## Shared responsibility

Every cloud provider publishes some form of shared-responsibility guidance. Read it before touching production resources.

Focus on these questions:

- Who patches the host OS?
- Who patches the managed database engine?
- Who configures users, roles, and secrets?
- Who owns network exposure?
- Who owns application data?
- Who owns backup retention?
- Who proves restore works?
- Who responds when the provider has an incident?

For a raw VM, you usually own much more: OS updates, users, packages, services, logs, firewall state, and application runtime. For a managed database, the provider owns more of the underlying platform, but you still own credentials, network access, schema, data, queries, backup policy, and restore testing.

## Linux operations references

Cloud Linux is still Linux. Keep strengthening the fundamentals:

- package management.
- `systemd` services.
- logs and `journalctl`.
- SSH configuration.
- user and sudo management.
- filesystems and mounts.
- process inspection.
- firewall inspection.
- resource usage.
- backups and restore.

Good reading habits:

- Read the manual page after seeing a command in cloud docs.
- Test commands on a disposable VM.
- Record distro differences.
- Prefer read-only inspection before changing state.
- Write down what you expected and what actually happened.

Useful command references to revisit:

```bash
man systemctl
man journalctl
man ssh
man ssh_config
man sshd_config
man ss
man ip
man findmnt
man rsync
```

## Cloud networking references

Cloud incidents often become networking incidents. Read networking docs with the packet path in mind.

Core topics:

- VPC or virtual network design.
- subnets and route tables.
- public IPs and private IPs.
- NAT and internet gateways.
- security groups or cloud firewalls.
- host firewalls.
- load balancers.
- DNS records.
- TLS certificates.

Turn reading into a path checklist:

1. Name resolves to the expected target.
2. Route path exists.
3. Provider firewall permits the source and port.
4. Load balancer target is healthy, if present.
5. Linux host listens on the expected address and port.
6. Host firewall permits the traffic.
7. Application returns the expected response.

## Identity and security references

Identity mistakes cause expensive and dangerous cloud failures. Read identity material slowly.

Focus areas:

- users, groups, roles, and service accounts.
- least privilege.
- temporary credentials.
- SSH key handling.
- secret storage.
- audit logs.
- break-glass access.
- access review.
- root or owner account protection.
- multi-factor authentication.

For every identity resource, ask:

- Who can assume this role?
- What can it read?
- What can it change?
- Can it create new credentials?
- Is access logged?
- How is it revoked?

## Cost-control references

Cost guidance is operational guidance. Read billing docs before your first serious cloud project, not after the surprise bill.

Learn where your provider shows:

- current month spend.
- forecast spend.
- budget alerts.
- service-level breakdown.
- account or project-level breakdown.
- idle compute.
- unattached disks.
- snapshots and backups.
- object storage growth.
- egress traffic.
- reserved capacity or savings plans.

Create a habit: every new resource needs an owner, purpose, environment, and cleanup plan.

## Books and deeper study

Books can help with mental models, but they age faster than official docs. Use them for principles, architecture patterns, and operational judgment rather than exact console steps.

Useful categories:

- cloud architecture patterns.
- site reliability engineering.
- Linux administration.
- networking fundamentals.
- security engineering.
- incident response.
- cost optimization and FinOps.

When reading a book, keep a lab notebook:

- one concept.
- one command or console check.
- one failure mode.
- one safety rule.
- one question to test in a lab.

## Building a personal cloud runbook

The best result of reading is a runbook you can use later.

Create short pages for:

- launching a lab VM.
- connecting with SSH.
- checking service health.
- checking provider health.
- opening and closing firewall ports.
- creating a backup.
- restoring from backup.
- rotating an SSH key.
- finding cost by service.
- cleaning up a lab.

Each runbook should include:

- purpose.
- prerequisites.
- read-only inspection.
- change steps.
- verification.
- rollback.
- owner and date.

## Hands-on practice

Use the official docs for a provider you can access, or complete this as a paper exercise.

1. Pick one official provider architecture or well-architected page.
2. Write down three operational principles from it.
3. Map each principle to one Linux command or host check.
4. Map each principle to one provider-console or API check.
5. Add one item to a personal cloud runbook.

Example:

```text
Principle: monitor workload health.
Linux check: systemctl --failed and journalctl -u app --since "1 hour ago".
Provider check: load balancer target health and instance status checks.
Runbook update: health verification requires both host and provider evidence.
```
