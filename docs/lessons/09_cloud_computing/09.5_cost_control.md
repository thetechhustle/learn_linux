## 09.5 Cost Control

Cloud cost control is operational hygiene. A Linux system that runs well can still
surprise the team if nobody watches instance size, storage growth, network
transfer, snapshots, logs, backups, and idle resources. Your job is to make cost
visible before it becomes an incident.

!!! abstract "What you will learn"
    - Identify the cloud resources that commonly create unexpected charges.
    - Collect evidence before changing instance size, storage, or retention.
    - Use budgets, alerts, tags, and cleanup reviews to keep a Linux workload predictable.
    - Explain the tradeoff between saving money and preserving reliability.

!!! success "Operator principle"
    Treat cost like capacity: measure it, set limits, review changes, and keep rollback options.

## Where the bill usually grows

Most cloud bills are a mix of obvious compute charges and quieter supporting
services. When a Linux workload moves to the cloud, check these areas first:

- **Compute:** virtual machine size, running hours, autoscaling count, GPU or burstable CPU usage.
- **Storage:** attached disks, snapshots, object storage, backup vaults, and old images.
- **Network:** public egress, load balancers, NAT gateways, cross-region traffic, and CDN misses.
- **Managed services:** databases, queues, Kubernetes clusters, monitoring, logging, and secrets.
- **Support and licensing:** paid operating system images, marketplace images, enterprise support, and third-party agents.

Do not assume the VM is the expensive part. A small server behind a busy NAT
gateway, a chatty cross-region backup job, or months of forgotten snapshots can
cost more than the instance itself.

## Build a cost evidence trail

Before changing a workload, write down the facts that explain why the resource
exists and what would break if it disappeared.

For a cloud Linux VM, record:

- instance name, region, size, operating system image, and owner
- purpose, environment, and expected service hours
- attached disks, snapshot policy, and backup retention
- public IPs, load balancers, NAT gateways, and high-egress paths
- monitoring and log retention settings
- current CPU, memory, disk, and network utilization

Read-only Linux commands help connect billing data to system behavior:

```bash
hostnamectl
uptime
df -h
lsblk
free -h
ss -tulpn
systemctl --type=service --state=running
journalctl --disk-usage
```

Cloud consoles and CLIs provide the billing side of the same story. The exact
commands vary by provider, but the questions stay the same:

- Which project, subscription, or account owns this resource?
- Which tag or label identifies the application, environment, and owner?
- What did this resource cost in the last day, week, and month?
- Is spend increasing because of usage, size, count, region, retention, or traffic?

## Put guardrails in place

Cost controls should exist before a workload is important.

- **Budgets:** set monthly budgets for the account, project, or application.
- **Alerts:** notify people before the budget is exhausted, not after.
- **Tags or labels:** require owner, environment, service, and expiration metadata.
- **Quotas:** cap high-risk services such as GPUs, public IPs, and large instance families.
- **Retention rules:** expire old snapshots, logs, build artifacts, and test data.
- **Change review:** treat larger instances, longer retention, new regions, and public egress paths as cost-affecting changes.

!!! warning "Do not delete first"
    A resource that looks idle may still be part of backup, failover, compliance,
    or incident response. Confirm ownership and recovery impact before removing it.

## Right-size without guessing

Right-sizing means matching resources to observed demand. It does not mean making
everything as small as possible.

Use this order:

1. **Measure:** collect CPU, memory, disk, and network usage over a representative period.
2. **Classify:** decide whether the workload is steady, bursty, seasonal, or temporary.
3. **Preview:** estimate the cost difference between the current size and candidate sizes.
4. **Schedule:** make the change during a maintenance window if performance risk exists.
5. **Verify:** compare application health, system metrics, and cost after the change.

For Linux VMs, avoid shrinking based on CPU alone. Memory pressure, disk I/O,
network throughput, and application latency can be the real limit.

## Common cleanup targets

These items often survive long after they are useful:

- stopped instances that still have paid disks
- unattached disks and public IP addresses
- obsolete machine images and snapshots
- load balancers with no healthy targets
- development databases left running overnight
- old Kubernetes clusters, node pools, and persistent volumes
- debug log retention set to months instead of days
- object storage buckets with no lifecycle policy

Keep a cleanup log. Record what you removed, who approved it, and how to restore
it if the decision was wrong.

## Hands-on practice

Use a disposable cloud account, free-tier lab, or local notes from a fake billing
scenario. Do not run cleanup commands against a production account for practice.

1. Choose one Linux VM or write a short mock inventory entry for one.
2. Record its owner, purpose, region, size, disks, public access path, and backup policy.
3. Run read-only Linux inspection commands such as `df -h`, `lsblk`, `free -h`, and `journalctl --disk-usage`.
4. Identify three possible cost drivers and mark each as keep, resize, investigate, or remove.
5. Draft one budget alert and one tag policy that would make this workload easier to manage.
6. Write a short handoff note explaining the safest next cost-control action.

Example handoff:

```text
Workload: staging-web-01
Owner: web platform team
Evidence: low CPU for 14 days, 80 GiB disk 22 percent used, debug logs using 6.4 GiB
Risk: staging is used during release testing, so do not delete
Next action: reduce log retention from 30 days to 7 days, then review disk size next week
Rollback: restore previous retention value if troubleshooting needs longer history
```
