# 09.4 Clouds: VPS Quick Start by Platform

!!! abstract "What you will learn"
    - Launch a small Linux VPS safely on common cloud platforms.
    - Choose the minimum platform settings needed for a low-risk lab server.
    - Connect with SSH using key-based authentication.
    - Verify the host from both the provider console and Linux shell.
    - Apply first-hour hardening, cost controls, and cleanup steps.

!!! example "Field story"
    A teammate wants a small Linux server for a proof of concept. They ask for "just a quick VPS" and plan to leave it running for a few weeks.

    A good operator can make that safe: choose a small instance, tag the owner and purpose, use SSH keys, limit inbound ports, verify the OS, record the public IP, and set a reminder to shut it down.

!!! success "Operator principle"
    A quick-start server is still real infrastructure. Make it small, named, tagged, key-based, backed by a cleanup plan, and easy to identify later.

## Before you launch

Most VPS providers ask for the same decisions with different labels. Prepare these before clicking through a console:

- Provider account: the correct cloud account, project, subscription, or team.
- Region: close to the users or lab location, but not random.
- Image: a supported Linux distribution such as Ubuntu LTS, Debian, Rocky Linux, AlmaLinux, or Fedora.
- Size: the smallest VM that fits the lab.
- Authentication: SSH key preferred; avoid password login for internet-facing hosts.
- Network exposure: SSH only from your IP when possible; HTTP/HTTPS only if needed.
- Storage: default root disk for a lab unless the workload needs more.
- Name and tags: owner, purpose, environment, and cleanup date.
- Budget guardrail: know the hourly/monthly cost before launch.

Example naming pattern:

```text
tth-lab-web-20260511
```

Example tags:

```text
owner=bobbyd
purpose=linux-lab
environment=lab
cleanup=2026-05-18
```

## SSH key baseline

Use a dedicated key for labs when possible. Do not paste private keys into cloud consoles or tickets.

Check whether you already have a suitable public key:

```bash
ls -l ~/.ssh/*.pub
```

Create a dedicated lab key if needed:

```bash
ssh-keygen -t ed25519 -C "linux-lab-vps" -f ~/.ssh/linux_lab_vps
```

Show the public key to upload:

```bash
cat ~/.ssh/linux_lab_vps.pub
```

Keep the private key local:

```bash
ls -l ~/.ssh/linux_lab_vps
```

The private key should not be world-readable. A typical safe mode is `600`.

```bash
chmod 600 ~/.ssh/linux_lab_vps
```

## AWS EC2 quick start

AWS names virtual machines EC2 instances.

Minimum safe lab path:

1. Open the EC2 console in the correct AWS account and region.
2. Choose **Launch instance**.
3. Name the instance with owner, purpose, and date.
4. Select a current Linux image, such as Ubuntu LTS, Amazon Linux, Debian, Rocky Linux, or AlmaLinux.
5. Pick a small instance type, such as a burstable micro or small size that fits the lab.
6. Choose an existing SSH key pair or import your public key.
7. Create or select a security group that allows SSH only from your current public IP.
8. Do not open HTTP or HTTPS unless the lab needs it.
9. Keep the default root volume unless the lab has a documented storage need.
10. Add tags for owner, purpose, environment, and cleanup date.
11. Launch the instance and record the instance ID, public IP, private IP, region, and security group.

Provider evidence to capture:

- instance state is `running`.
- status checks are passing.
- public IP is assigned if you need internet SSH.
- security group allows only expected inbound ports.
- attached volume size and type are expected.
- tags are present.

Connect:

```bash
ssh -i ~/.ssh/linux_lab_vps ubuntu@<public-ip>
```

The default username depends on the image. Common examples:

- Ubuntu: `ubuntu`
- Debian: `admin` or `debian`, depending on image
- Amazon Linux: `ec2-user`
- Rocky Linux or AlmaLinux: `rocky`, `almalinux`, or `cloud-user`, depending on image

If SSH fails, do not immediately open the firewall to the world. Check the username, key pair, security group source IP, instance status checks, and route path first.

## DigitalOcean Droplet quick start

DigitalOcean names virtual machines Droplets.

Minimum safe lab path:

1. Open the correct DigitalOcean team or project.
2. Choose **Create** and then **Droplets**.
3. Select a Linux image such as Ubuntu LTS, Debian, Rocky Linux, AlmaLinux, or Fedora.
4. Choose the closest practical datacenter region.
5. Choose the smallest regular plan that fits the lab.
6. Select SSH key authentication.
7. Avoid password authentication for an internet-facing lab.
8. Enable basic monitoring if available.
9. Add the Droplet to the right project.
10. Add tags for owner, purpose, environment, and cleanup date.
11. Create the Droplet and record the Droplet ID, public IP, region, image, and tags.

Provider evidence to capture:

- Droplet is active.
- image and size match the request.
- public IP is assigned.
- firewall rules allow only expected inbound ports.
- monitoring is enabled if the provider offers it.
- tags or project assignment are correct.

Connect:

```bash
ssh -i ~/.ssh/linux_lab_vps root@<public-ip>
```

DigitalOcean often starts with `root` access. Create a normal sudo user before doing real work.

## Linode/Akamai quick start

Linode calls virtual machines Linodes.

Minimum safe lab path:

1. Open the correct Akamai Cloud or Linode account.
2. Choose **Create Linode**.
3. Select a supported Linux distribution.
4. Choose the region.
5. Choose a small shared CPU plan for a lab.
6. Add your SSH public key.
7. Use a strong root password only if the platform requires one during creation.
8. Add tags and labels that identify owner, purpose, environment, and cleanup date.
9. Create the Linode and record the Linode ID, public IP, region, image, and plan.

Provider evidence to capture:

- Linode is running.
- image, region, and plan match the lab request.
- public IP is assigned.
- firewall rules are attached if the account uses cloud firewalls.
- backups are intentionally enabled or intentionally disabled for a short lab.
- tags and labels are present.

Connect:

```bash
ssh -i ~/.ssh/linux_lab_vps root@<public-ip>
```

Then create a normal sudo user before using the server for anything beyond the first setup pass.

## Vultr quick start

Vultr calls virtual machines Cloud Compute instances.

Minimum safe lab path:

1. Open the correct Vultr account.
2. Choose **Deploy New Server**.
3. Select Cloud Compute or the smallest appropriate instance family.
4. Choose the region.
5. Select a Linux image.
6. Choose a small plan for the lab.
7. Add your SSH public key.
8. Attach a firewall group that allows only expected inbound ports.
9. Add labels or tags for owner, purpose, environment, and cleanup date.
10. Deploy the instance and record the instance ID, public IP, region, image, and firewall group.

Provider evidence to capture:

- instance is running.
- public IP is assigned.
- firewall group is attached.
- image, region, and size match the request.
- labels or tags are present.

Connect:

```bash
ssh -i ~/.ssh/linux_lab_vps root@<public-ip>
```

As with other providers, create a normal sudo user after first login.

## First login checks

After connecting, prove what you are on before changing it:

```bash
hostnamectl
uname -a
whoami
ip addr
ip route
df -hT
free -h
systemctl --failed
```

Check the external address from the host:

```bash
curl -4 ifconfig.me
```

Confirm the SSH service:

```bash
systemctl status ssh || systemctl status sshd
ss -tulpn | grep ':22'
```

Write down:

- provider and account.
- region.
- instance name and ID.
- public IP and private IP.
- image and size.
- SSH username.
- firewall or security group.
- cleanup date.

## First-hour hardening

For a disposable lab, keep this focused and reversible.

Update package metadata and apply security updates:

```bash
sudo apt update
sudo apt upgrade
```

On RPM-family distributions:

```bash
sudo dnf upgrade
```

Create a normal sudo user when the provider starts you as `root`:

```bash
adduser labops
usermod -aG sudo labops
```

On RPM-family distributions, the admin group may be `wheel`:

```bash
useradd -m labops
passwd labops
usermod -aG wheel labops
```

Copy SSH access carefully:

```bash
mkdir -p /home/labops/.ssh
cp ~/.ssh/authorized_keys /home/labops/.ssh/authorized_keys
chown -R labops:labops /home/labops/.ssh
chmod 700 /home/labops/.ssh
chmod 600 /home/labops/.ssh/authorized_keys
```

Before disabling root SSH or password login, open a second terminal and prove the new user can log in and use sudo.

```bash
ssh -i ~/.ssh/linux_lab_vps labops@<public-ip>
sudo -l
```

Only then consider tightening SSH configuration.

## Firewall discipline

For a basic SSH lab, inbound rules should usually be:

- SSH from your current IP only.
- HTTP from the internet only if you are testing a web server.
- HTTPS from the internet only if you are testing TLS.
- No database ports from the internet.
- No broad `0.0.0.0/0` SSH rule unless there is a temporary, documented reason.

Check the host firewall too:

```bash
sudo nft list ruleset
sudo iptables -S
```

Provider firewall open plus host firewall closed means traffic may still fail. Host port open plus provider firewall closed also fails. You need both layers to agree.

## Cost and cleanup

Quick-start servers are easy to forget. Record the cleanup plan at creation time.

Before walking away:

- Set a calendar reminder or ticket for the cleanup date.
- Record whether the server should be stopped, snapshotted, or destroyed.
- Record whether any DNS points to it.
- Record whether attached volumes, snapshots, reserved IPs, or backups will keep billing after deletion.
- Record who owns the decision if the lab becomes useful.

Cleanup checklist:

1. Confirm no one still needs the server.
2. Preserve required evidence, logs, or data.
3. Remove DNS records or load balancer targets.
4. Destroy the VM.
5. Delete unattached disks if they are no longer needed.
6. Delete stale snapshots if retention allows it.
7. Release reserved IPs if the provider bills for them.
8. Confirm the billing dashboard no longer shows the resource.

## Troubleshooting quick path

If SSH fails:

1. Confirm the public IP.
2. Confirm the default username for the image.
3. Confirm the private key matches the uploaded public key.
4. Confirm file permissions on the private key.
5. Confirm the provider firewall allows SSH from your current IP.
6. Confirm the instance passed provider reachability checks.
7. Confirm the VM is in the expected region/account.
8. Use the provider serial console only if normal SSH evidence is not enough.

If the web app fails:

1. Confirm the process is running.
2. Confirm the app is listening on the expected address and port.
3. Test locally on the host with `curl`.
4. Check the host firewall.
5. Check the provider firewall.
6. Check the load balancer or DNS path if one exists.
7. Read application logs.

## Hands-on practice

Use a disposable lab account or a paper exercise if you cannot spend money.

1. Pick one provider: AWS, DigitalOcean, Linode/Akamai, or Vultr.
2. Write the launch choices before creating anything: region, image, size, SSH key, firewall, tags, and cleanup date.
3. Launch the smallest practical Linux VPS.
4. Connect with SSH.
5. Run the first-login checks.
6. Record the provider evidence and host evidence.
7. Destroy the server or document the date and owner for cleanup.

Do not leave a paid resource running without an owner and cleanup date.
