# The Cloud in Context

!!! abstract "What you will learn"
    - Define cloud computing in operational terms.
    - Explain which responsibilities move to the cloud provider and which remain yours.
    - Compare local servers, VPS instances, managed services, containers, and serverless platforms.
    - Identify the facts to collect before moving a Linux workload into the cloud.
    - Build a small evidence trail around cost, access, ownership, and rollback.

!!! example "Field story"
    A small team runs an internal dashboard on a developer's laptop. It needs to move somewhere more reliable. One person says, "Put it in the cloud." Your job is to turn that vague request into a concrete hosting decision: what runs where, who can access it, how it is backed up, what it costs, and how you know it is working.

!!! success "Operator principle"
    The cloud is not a place where responsibility disappears. It is a place where responsibility is split between the provider and the operator.

Cloud computing means renting computing resources through a provider's infrastructure and APIs instead of owning every physical server, network switch, disk shelf, and datacenter facility yourself.

For a Linux operator, the useful definition is simpler:

> Cloud computing is infrastructure you can provision, change, observe, and destroy through a provider control plane.

That control plane might create a virtual machine, attach storage, open a firewall rule, issue a database password, publish a DNS record, or destroy an entire environment.

## What the Provider Owns

Cloud providers usually take responsibility for parts of the physical and platform layer:

- datacenter buildings
- power and cooling
- physical servers
- physical network equipment
- hardware replacement
- regional infrastructure
- APIs and dashboards for creating resources
- some managed-service patching and availability

This is valuable. It means a small team can create infrastructure in minutes instead of buying hardware and waiting for installation.

But it does not mean the system is automatically secure, cheap, backed up, or reliable.

## What You Still Own

You still own many operational decisions:

- which account, project, subscription, or tenant contains the work
- which region and zone the workload runs in
- which image or operating system version is used
- who has access
- which network ports are open
- how secrets are stored
- how the system is patched
- how logs and metrics are collected
- how backups and restores work
- what the monthly cost should be
- how the system is retired

If you create a public Linux server with SSH open to the world, the provider gave you tools. You still made the exposure decision.

## Hosting Models

Cloud is not one thing. It is a family of hosting models with different responsibility boundaries.

### Local server

You own or directly control the machine.

You are responsible for nearly everything: hardware, power, network, disks, operating system, backups, and security.

### VPS or cloud virtual machine

The provider owns the physical hardware and virtualization platform. You manage the guest operating system.

You are usually responsible for:

- Linux users and SSH access
- package updates
- firewall rules at the host and provider layer
- application runtime
- logs
- backups or snapshots
- cost cleanup

This is the closest cloud model to traditional Linux administration.

### Managed service

The provider operates more of the stack. Examples include managed databases, managed Kubernetes, queues, object storage, and hosted caches.

You usually manage configuration, access, data, scaling settings, and cost. The provider handles more patching and platform availability.

Managed services reduce some work, but they add provider-specific behavior and billing details.

### Containers and orchestration

Containers package applications and dependencies. Orchestrators such as Kubernetes or cloud container platforms decide where containers run.

You still need Linux fundamentals for images, networking, logs, filesystems, resource limits, and debugging. The host may be less visible, but it has not vanished.

### Serverless

Serverless platforms run functions or applications without exposing the server directly.

You manage code, configuration, IAM permissions, event triggers, logs, and cost. The provider manages the runtime infrastructure.

Serverless can reduce host administration, but it can make debugging, cold starts, permissions, and spending harder to reason about.

## The Shared Responsibility Model

Most providers describe cloud security as a shared responsibility model.

The exact boundary depends on the service:

- With a virtual machine, the provider secures the physical host. You secure the operating system and application.
- With a managed database, the provider handles the database engine infrastructure. You still control users, network access, data, backups, and configuration choices.
- With object storage, the provider stores objects reliably. You still decide bucket policy, encryption settings, lifecycle rules, and public access.

When something breaks, ask two questions:

1. Is this provider-managed state or customer-managed state?
2. Which evidence proves that?

## Moving a Linux Workload to the Cloud

Before moving a workload, collect facts.

### Workload facts

- What does the workload do?
- Who uses it?
- Is it production, staging, lab, or personal?
- What ports does it listen on?
- What data does it store?
- How much CPU, memory, and disk does it need?
- What happens if it is down for one hour?

### Access facts

- Who needs SSH access?
- Does access use SSH keys, SSO, IAM, local users, or a combination?
- Is there a break-glass account or console path?
- Which secrets does the application need?

### Network facts

- Should it be public or private?
- What inbound ports are required?
- What outbound connections does it make?
- Does it need DNS or TLS?
- Does it need to connect to a VPN or private network?

### Cost facts

- What is the expected monthly cost?
- What happens if traffic doubles?
- Are snapshots, disks, IP addresses, logs, or data transfer billed separately?
- Who owns cleanup?

### Recovery facts

- How is it backed up?
- Has restore been tested?
- What is the rollback path?
- What evidence proves the workload works after migration?

## Read-Only Inspection Examples

On an existing cloud Linux host, start with familiar Linux commands:

```bash
hostnamectl
uptime
ip addr
df -h
free -h
systemctl --failed
```

Then collect cloud context from the provider console or CLI:

- account, project, or subscription
- region and zone
- instance name and ID
- image or snapshot source
- instance size
- attached disks
- firewall or security group rules
- public and private IP addresses
- tags or labels
- estimated cost

Do not rely only on the hostname inside Linux. Cloud inventory has its own truth.

## Common Failure Modes

Watch for these cloud-specific mistakes:

- creating a server in the wrong account or region
- opening SSH, databases, or admin panels to the public internet
- assuming snapshots are automatic
- leaving stopped or unattached resources that still cost money
- using a personal SSH key for shared production access
- storing secrets in shell history or user data
- forgetting that provider IAM access and Linux user access are different
- deleting a resource before confirming backups or dependencies

## Hands-on Practice

Use a disposable lab account or low-cost sandbox.

1. Pick a cloud provider or VPS provider.
2. Create the smallest Linux VM that fits the lab.
3. Record:
    - provider
    - account/project
    - region
    - VM name
    - image
    - size
    - estimated monthly cost
4. SSH into the VM and run:

    ```bash
    hostnamectl
    ip addr
    df -h
    free -h
    systemctl --failed
    ```

5. In the provider console, find the security group, firewall, or network rule that allows SSH.
6. Shut down or destroy the VM when finished.
7. Verify cleanup in the provider console or billing view.
