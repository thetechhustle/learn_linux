## 09.2 Cloud Platform Choices

Cloud platform selection is an operations decision, not a brand contest. The best choice is the platform that fits the workload's reliability needs, team skills, identity model, network dependencies, compliance rules, and cost tolerance.

!!! abstract "What you will learn"
    - Compare cloud providers by operational fit instead of marketing features.
    - Gather Linux workload evidence before recommending a platform.
    - Identify common platform-choice risks: lock-in, surprise cost, identity gaps, and network complexity.

!!! example "Field story"
    A small team wants to move one internal Linux service from a laptop under someone's desk to a cloud VM. The application is simple, but it depends on SSH access, a private database connection, nightly backups, and predictable monthly cost. Your job is to turn that rough request into a platform recommendation the team can support.

!!! success "Operator principle"
    Choose the cloud that your team can operate calmly at 3 AM, not the one with the longest feature list.

## What to compare

Start with the workload, then compare platforms against the same questions.

| Question | Why it matters |
| --- | --- |
| Where are the users and dependencies? | Region choice affects latency, data residency, and network egress charges. |
| How will admins authenticate? | Identity integration, MFA, break-glass access, and audit logs differ by provider. |
| What network shape is required? | Private subnets, VPNs, load balancers, firewalls, and DNS can dominate the design. |
| What Linux images and instance types are supported? | Distribution, architecture, kernel, and disk options affect compatibility and support. |
| How are backups, snapshots, and restores handled? | A backup checkbox is not enough; operators need restore practice and retention policy. |
| How will cost be controlled? | Idle instances, oversized disks, NAT gateways, logs, and egress can surprise new teams. |
| What skills does the team already have? | Existing Terraform, CLI, IAM, monitoring, and incident experience reduce operational risk. |

## Major platform patterns

AWS, Azure, and Google Cloud can all run Linux well. Their differences matter most around surrounding services and team familiarity.

- **AWS** has broad service coverage, many regions, mature IAM, and a large ecosystem. It is common in startups and enterprises, but the number of service choices can make small designs more complex than necessary.
- **Azure** often fits organizations already using Microsoft Entra ID, Windows Server, Microsoft 365, or hybrid enterprise networking. Linux workloads are well supported, but access and networking choices should be planned with the identity team.
- **Google Cloud** is strong for global networking, Kubernetes, data platforms, and teams already invested in Google Workspace or Google-managed infrastructure patterns. Its IAM and project model may feel different to operators coming from AWS.
- **Smaller VPS providers** such as DigitalOcean, Linode/Akamai, Hetzner, and Vultr can be excellent for straightforward Linux servers. They are often simpler and cheaper, but may offer fewer managed services, compliance options, private connectivity patterns, or enterprise controls.

!!! warning "Avoid accidental lock-in"
    Managed databases, queues, object storage, serverless functions, and IAM policies are useful, but they are also platform-specific. Before adopting a managed service, decide whether the operational gain is worth the migration cost later.

## Evidence to gather before choosing

On the current Linux host, collect read-only facts first:

```bash
hostnamectl
uname -a
df -h
free -h
ss -tulpn
systemctl --type=service --state=running
```

Record the answers in a short migration note:

- What services must start after reboot?
- Which ports must be reachable, and from where?
- What data must be backed up?
- Which users or automation keys need access?
- What is the acceptable outage window?
- What monthly cost would trigger a review?

This evidence turns "use cloud provider X" into a supportable recommendation.

## Safe first design

For a first cloud migration, prefer a small, boring design:

1. One supported Linux distribution image.
2. One right-sized VM in a region near users or dependencies.
3. A restrictive firewall or security group.
4. SSH access through named users, MFA-protected identity, or a managed bastion pattern.
5. A separate data disk if the application stores important state.
6. Snapshot or backup policy with a tested restore.
7. Basic monitoring for reachability, CPU, memory, disk, and service health.
8. A monthly budget alert.

Do not start by using every managed feature. Add complexity when it removes a real operations burden.

## Hands-on practice

Use a paper design or a disposable lab account. Do not create paid resources in a production account for this exercise.

1. Pick one small Linux workload you understand.
2. Fill out the evidence checklist above.
3. Compare two platforms using the same criteria: region, Linux image, VM size, firewall model, backup option, identity model, and estimated monthly cost.
4. Write a one-paragraph recommendation that explains the tradeoff, not just the winner.
5. List the first three post-migration checks you would run after booting the cloud VM.
