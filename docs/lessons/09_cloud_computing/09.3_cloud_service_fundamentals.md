# 09.3 Cloud Service Fundamentals

!!! abstract "What you will learn"
    - Categorize common cloud services: compute, storage, networking, identity, observability, databases, and managed application services.
    - Map each service type to the Linux operator responsibilities that remain on the host.
    - Inspect host and provider evidence before changing a cloud workload.
    - Distinguish provider-managed signals from host-managed signals during troubleshooting.
    - Record service ownership, cost exposure, and operational risk in a handoff.

!!! example "Field story"
    A small internal application started on one cloud VM. It now needs a database, durable file storage, central logging, and a safer deployment path. Someone asks you to "make it reliable."

    The right first move is not to buy more cloud services at random. Identify the building blocks, decide which layer owns each failure mode, and write down what evidence proves the current state.

!!! success "Operator principle"
    Choose managed services when they reduce a real responsibility clearly. Do not choose them just because the word "cloud" sounds simpler.

## Cloud services are building blocks

Cloud platforms package infrastructure into services. A service is a product boundary with its own API, permissions model, billing shape, monitoring surface, and failure modes.

For Linux operators, the cloud does not remove operational thinking. It changes where the evidence lives.

Common service categories include:

- Compute: virtual machines, containers, Kubernetes nodes, and serverless functions.
- Storage: block volumes, object buckets, file shares, snapshots, backups, and archives.
- Networking: virtual networks, subnets, firewalls, security groups, load balancers, DNS, and TLS certificates.
- Identity: cloud IAM users, roles, service accounts, SSH keys, secrets, and access policies.
- Data services: managed databases, caches, queues, streams, and search clusters.
- Observability: metrics, logs, traces, alerts, audit events, and provider status feeds.
- Managed app services: platform runtimes, container apps, static hosting, CI/CD integrations, and scheduler platforms.

The useful question is always:

> Which layer owns the responsibility, and what evidence proves it is healthy?

## Compute

Compute services run the workload. The most familiar form is a cloud VM. Other forms include container services, managed Kubernetes, serverless functions, and platform runtimes.

On a VM, the Linux operator still owns much of the host:

- OS patching, unless a managed image pipeline handles it.
- system services and boot behavior.
- disk pressure and filesystem state.
- process health.
- application logs.
- host firewall rules.
- user, SSH, and sudo access.
- runtime dependencies.

Useful host-side evidence includes:

```bash
hostnamectl
uptime
df -h
free -h
systemctl --failed
systemctl status <service>
journalctl -u <service> --since "1 hour ago"
ss -tulpn
```

Provider-side evidence usually answers different questions:

- Is the VM running?
- Did the hypervisor report a host health issue?
- Did the instance fail a provider reachability or system check?
- Is the instance in the expected region, zone, network, and account?
- Did autoscaling replace or terminate it?
- Are CPU, network, and disk metrics abnormal?

Do not treat "VM is running" as "application is healthy." It only proves the provider sees a running compute resource.

## Storage

Cloud storage is not one thing. Different storage services solve different problems.

Block storage behaves like a disk attached to a VM. Linux sees it as a device, partition, filesystem, mount, or volume group. It is useful for OS disks, database data directories, and application files that need filesystem semantics.

Object storage stores objects in buckets. It is useful for backups, uploads, archives, static assets, logs, and data exchange. Linux does not treat it like a normal mounted disk unless you add a special tool or gateway.

File storage provides shared filesystem access over protocols such as NFS or SMB. It is useful when multiple hosts need shared paths, but it adds network, permission, latency, and lock-behavior concerns.

Before changing storage, inspect both the Linux layer and the cloud layer:

```bash
lsblk
findmnt
df -hT
sudo file -s /dev/<device>
sudo journalctl -k --since "1 hour ago"
```

Provider-side questions:

- Is the volume, bucket, or file share in the expected account and region?
- Is it attached to the expected host?
- Are snapshots or backups configured?
- Is lifecycle retention deleting data earlier than expected?
- Are encryption and access policies correct?
- Is the service reporting throttling, quota, or degraded health?

Do not confuse an attached disk with object storage. A snapshot protects a volume state at a point in time. A bucket stores named objects. They are operated, billed, secured, and restored differently.

## Networking

Cloud networking can make a healthy Linux service look broken. A listening process on the host is only one part of the path.

Important cloud networking objects include:

- VPC or virtual network: the private network boundary.
- Subnet: the address range where resources live.
- Route table: where packets go next.
- Internet gateway, NAT gateway, or egress service: how traffic enters or leaves.
- Security group or cloud firewall: provider-level allow rules.
- Host firewall: Linux-level allow rules.
- Load balancer: front door that routes to one or more targets.
- DNS record: the name clients use.
- TLS certificate: encrypted identity for the endpoint.

When debugging access, walk the path in order:

1. Does DNS resolve to the expected address or load balancer?
2. Does the provider firewall allow the port from the right source?
3. Does the route table send traffic where you expect?
4. Does the load balancer show healthy targets?
5. Is the Linux host listening on the expected address and port?
6. Does the host firewall allow the traffic?
7. Does the application accept the request?

Useful Linux evidence:

```bash
ip addr
ip route
ss -tulpn
curl -v http://127.0.0.1:<port>/
curl -v http://<private-ip>:<port>/
sudo nft list ruleset
sudo iptables -S
```

Provider firewalls and host firewalls are separate controls. Opening port 443 in a security group does not make Nginx listen on port 443. Starting Nginx on port 443 does not open the provider firewall.

## Identity and secrets

Cloud identity and Linux identity overlap, but they are not the same.

Cloud IAM controls access to provider APIs and managed services. It answers questions such as:

- Can this VM read from a bucket?
- Can this deployment role create a load balancer?
- Can this service account read a secret?
- Who can modify DNS or firewall rules?

Linux identity controls local host access:

- local users and groups.
- SSH authorized keys.
- sudo rules.
- service accounts.
- file ownership and permissions.
- process runtime users.

Secrets connect these worlds. A secret might be a database password, API token, private key, webhook secret, or cloud credential. A safe operator avoids storing secrets in shell history, plain text notes, image builds, public repos, or world-readable files.

Inspect identity without exposing secrets:

```bash
id
who
last -a | head
sudo -l
ls -ld ~/.ssh
find /etc/systemd/system -type f -maxdepth 1 -print
```

Provider-side questions:

- Which role or service account is attached to this workload?
- Which policies grant access?
- Are credentials long-lived or rotated?
- Where are secrets stored?
- Who can read or update the secret?
- Are audit logs available for access changes?

## Managed databases and caches

Managed data services move some operations to the provider, but they do not remove operator responsibility.

For a managed database, the provider may own hardware, database installation, storage replication, and managed backups. The operator still usually owns:

- schema and data quality.
- application queries and connection behavior.
- credentials and access policy.
- network exposure.
- backup retention choices.
- maintenance windows.
- version upgrade planning.
- restore testing.
- performance signals.
- cost and capacity choices.

Before changing a database, collect evidence:

- Which application uses it?
- Which credentials or secret reference connect to it?
- Which network paths can reach it?
- Are backups enabled, and has restore been tested?
- Is there a maintenance window?
- Are CPU, memory, storage, connections, locks, or slow queries abnormal?
- Is the issue host-side, application-side, or provider-side?

Caches and queues have similar boundary questions. A cache can improve performance, but data may be evicted. A queue can absorb bursts, but consumers can fall behind. The managed label does not remove the need for alerts, capacity planning, and runbooks.

## Observability

Observability is how you prove what happened. In cloud environments, evidence is split across host, application, provider, and account logs.

Host evidence:

```bash
journalctl --since "1 hour ago"
journalctl -u <service> --since "1 hour ago"
dmesg --ctime | tail -n 50
df -h
free -h
top
```

Application evidence:

- structured logs.
- error rates.
- request latency.
- health checks.
- dependency errors.
- deploy timestamps.

Provider evidence:

- compute metrics.
- load balancer target health.
- network flow logs.
- managed database metrics.
- object storage errors.
- audit logs.
- provider incident or status notices.

Do not rely on only one layer. A host can be healthy while the load balancer marks it unhealthy. A provider dashboard can show a healthy VM while the application is returning HTTP 500.

## Cost controls

Every cloud service has a cost shape. Operators need enough cost awareness to avoid accidental waste.

Track:

- owner and purpose tags.
- environment labels such as production, staging, lab, or temporary.
- region and account.
- budget alerts.
- idle compute.
- unattached volumes.
- oversized databases.
- stale snapshots.
- long log retention.
- high egress traffic.
- managed services left running after tests.

Cost is operational evidence. A surprise bill can indicate leaked credentials, runaway jobs, accidental retention, wrong region choice, or missing cleanup.

## Inspection checklist before changes

Before modifying a cloud service, write down:

- Service name and category.
- Account, project, subscription, or tenant.
- Region and zone.
- Environment: production, staging, lab, or unknown.
- Owner and business purpose.
- Current host evidence, if a Linux host is involved.
- Current provider health evidence.
- Related DNS, firewall, load balancer, identity, and secret dependencies.
- Backup or rollback path.
- Expected user impact.
- Cost or quota risk.
- Verification command or dashboard signal after the change.

If you cannot identify the owner, environment, rollback path, or blast radius, the next action is more discovery, not a change.

## Hands-on practice

Use a disposable lab VM or a paper architecture exercise. Do not modify production cloud resources for this practice.

1. Pick a simple web application scenario: one Linux VM, one database, one file-upload location, and one public HTTPS endpoint.
2. Classify each piece as compute, storage, networking, identity, database, observability, or managed application service.
3. For the Linux VM, list three host commands that prove local state.
4. For each cloud service, list the provider evidence you would inspect before a change.
5. Write a short handoff with ownership, risk, rollback, and verification.

Example handoff:

```text
Service: customer-portal VM
Category: compute
Environment: staging
Owner: web platform team
Risk: restart may interrupt active QA sessions
Rollback: keep current VM image snapshot and previous service config
Host evidence: systemctl status portal, journalctl -u portal, ss -tulpn
Provider evidence: VM health checks, load balancer target health, CPU and disk metrics
Verification: HTTP 200 from health endpoint and no new errors after restart
```
