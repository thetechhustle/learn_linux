#### Mounting SMB File Shares on Linux

Linux can act as an SMB server, but it can also act as an SMB client. In
client mode, the Linux host mounts a remote Windows, Samba, or NAS share into
the local filesystem so users and programs can work with it through normal
paths.

This is convenient, but it also creates an operational boundary. A mounted SMB
share depends on the network, DNS, server availability, authentication,
protocol negotiation, local UID/GID mapping, and Linux mount behavior. Treat it
as a small integration, not just as a one-line command.

!!! abstract "What you will learn"
    - Install and identify the Linux SMB client tools used for mounts.
    - Test an SMB share before mounting it.
    - Mount a share manually with `mount.cifs`.
    - Keep credentials out of command history and `/etc/fstab`.
    - Choose safer persistent mount options for `/etc/fstab` and systemd.
    - Troubleshoot common mount failures from evidence.

!!! success "Operator principle"
    Prove the server, credentials, protocol version, and local ownership model
    before making an SMB mount persistent.

## The Linux CIFS Client Stack

SMB mounts on Linux use the kernel CIFS client. The user-facing helper is
usually `mount.cifs`, which comes from the `cifs-utils` package.

Common package names:

| Platform family | Package |
| --- | --- |
| Debian / Ubuntu | `cifs-utils` |
| RHEL / Fedora | `cifs-utils` |
| SUSE | `cifs-utils` |

Check that the helper exists:

```bash
command -v mount.cifs
modinfo cifs | head
```

If `modinfo cifs` fails, the kernel module may be unavailable in that
environment. Containers and restricted lab systems often cannot mount remote
filesystems even when the userspace package is installed.

## Inspect Before You Mount

Start by proving that the server and share are reachable. `smbclient` is useful
because it tests SMB at the protocol layer without changing the local mount
table.

```bash
smbclient -L //fileserver.example.com -U alice
```

If you already know the share name, test the share itself:

```bash
smbclient //fileserver.example.com/projects -U alice -c 'ls'
```

Useful evidence to collect before mounting:

```bash
getent hosts fileserver.example.com
ping -c 2 fileserver.example.com
nc -vz fileserver.example.com 445
smbclient -L //fileserver.example.com -U alice
```

Port `445/tcp` is the normal direct-hosted SMB port. Old NetBIOS-era ports
`137-139` may appear in legacy environments, but modern Linux clients normally
mount over `445`.

## Manual Mount

Create a mount point first:

```bash
sudo mkdir -p /mnt/projects
```

Mount the share with `mount.cifs`:

```bash
sudo mount -t cifs //fileserver.example.com/projects /mnt/projects \
  -o username=alice,domain=EXAMPLE,vers=3.1.1,uid=$(id -u),gid=$(id -g),iocharset=utf8
```

Then verify the result:

```bash
findmnt /mnt/projects
mount | grep cifs
ls -la /mnt/projects
df -h /mnt/projects
```

Important options:

| Option | Why it matters |
| --- | --- |
| `username=alice` | SMB account used to authenticate to the server. |
| `domain=EXAMPLE` | Windows domain, AD realm, or workgroup where required. |
| `vers=3.1.1` | Pins the SMB dialect instead of silently falling back. |
| `uid=` / `gid=` | Controls local ownership presented for files. |
| `iocharset=utf8` | Handles common filename encoding expectations. |

For older servers, `vers=3.0`, `vers=2.1`, or `vers=2.0` may be necessary.
Avoid SMB1 (`vers=1.0`) unless you are isolating a legacy system and have a
documented exception. SMB1 is obsolete and unsafe on normal networks.

## Do Not Put Passwords In Commands

Avoid this:

```bash
sudo mount -t cifs //fileserver/projects /mnt/projects -o username=alice,password=secret
```

That leaks secrets into shell history, process listings, audit logs, or copied
runbooks.

Use a root-owned credentials file instead:

```bash
sudo install -m 0600 -o root -g root /dev/null /etc/samba/creds-projects
sudoedit /etc/samba/creds-projects
```

Example contents:

```ini
username=alice
password=replace-with-real-secret
domain=EXAMPLE
```

Then mount with:

```bash
sudo mount -t cifs //fileserver.example.com/projects /mnt/projects \
  -o credentials=/etc/samba/creds-projects,vers=3.1.1,uid=$(id -u),gid=$(id -g)
```

If the environment supports Kerberos, prefer ticket-based authentication over
stored passwords:

```bash
kinit alice@EXAMPLE.COM
sudo mount -t cifs //fileserver.example.com/projects /mnt/projects \
  -o sec=krb5,cruid=$(id -u),vers=3.1.1,uid=$(id -u),gid=$(id -g)
```

Kerberos setup depends on DNS, time sync, `/etc/krb5.conf`, the server's AD
membership, and the local login model, so validate it carefully before
standardizing on it.

## Persistent Mounts

For persistent mounts, `/etc/fstab` is common. Keep the credentials file
separate:

```fstab
//fileserver.example.com/projects  /mnt/projects  cifs  credentials=/etc/samba/creds-projects,vers=3.1.1,uid=1000,gid=1000,iocharset=utf8,_netdev,nofail,x-systemd.automount,x-systemd.idle-timeout=60  0  0
```

The safer options here matter:

| Option | Purpose |
| --- | --- |
| `_netdev` | Tells the boot process this depends on the network. |
| `nofail` | Prevents a missing share from blocking boot. |
| `x-systemd.automount` | Mounts on first access instead of hard-blocking boot. |
| `x-systemd.idle-timeout=60` | Lets systemd unmount after inactivity. |

Test the entry without rebooting:

```bash
sudo systemctl daemon-reload
sudo findmnt --verify --tab-file /etc/fstab
sudo mount /mnt/projects
findmnt /mnt/projects
```

If you used `x-systemd.automount`, trigger the mount by accessing the path:

```bash
ls /mnt/projects
systemctl status mnt-projects.automount
systemctl status mnt-projects.mount
```

## Permissions And Ownership

SMB permissions are enforced on the server first. Linux mount options only
control how the remote files appear locally.

Common local ownership options:

| Option | Effect |
| --- | --- |
| `uid=1000,gid=1000` | Present all files as one local user/group. |
| `file_mode=0640,dir_mode=0750` | Set displayed permission bits when Unix extensions are not used. |
| `multiuser` | Allow multiple Linux users to access the mount with separate SMB credentials. |
| `noperm` | Disable client-side permission checks; use cautiously. |

If a user can see files but cannot write, check both sides:

1. Does the SMB server permit that user to write to the share?
2. Does the underlying server filesystem permit the server process to write?
3. Do the Linux client mount options present ownership/modes that allow the
   local process to write?

## Troubleshooting Flow

Start with the error text, then isolate the layer.

| Symptom | Likely layer | First checks |
| --- | --- | --- |
| `No route to host` | Network | IP route, firewall, VPN, server power/state. |
| `Connection timed out` | Network/firewall | `nc -vz server 445`, routing, security groups. |
| `Permission denied` | Auth/share ACL | Username, domain, password, server share permissions. |
| `Operation not supported` | Dialect/options | Try `vers=3.0` or inspect server SMB support. |
| `Host is down` | Name/session setup | DNS, NetBIOS naming, port 445 reachability. |
| Boot pauses on mount | Persistence design | Add `nofail` and `x-systemd.automount`. |

Kernel messages often contain the decisive clue:

```bash
dmesg -T | grep -i cifs | tail -20
journalctl -k -g CIFS --since -10m
```

You can increase Samba client-side visibility by testing with `smbclient`
again:

```bash
smbclient //fileserver.example.com/projects -U alice -d 3 -c 'ls'
```

## Clean Up A Lab Mount

Unmount the share:

```bash
sudo umount /mnt/projects
```

If the mount is busy, identify the process:

```bash
fuser -vm /mnt/projects
lsof +f -- /mnt/projects
```

Avoid lazy unmounts (`umount -l`) as a routine habit. They can hide application
behavior that still depends on the mount. Use them only when you understand the
process state and recovery plan.

## Hands-On Practice

Use a lab SMB server or a disposable Samba VM.

1. Install `cifs-utils`.
2. Use `smbclient -L` to list shares on the server.
3. Create `/mnt/projects`.
4. Mount the share manually with an explicit `vers=` option.
5. Verify with `findmnt`, `df -h`, and a read/write test file if the share is
   meant to be writable.
6. Move the password into a root-owned credentials file.
7. Add an `/etc/fstab` line that uses `nofail` and `x-systemd.automount`.
8. Reboot the lab VM or use `systemctl daemon-reload` and access the path to
   prove the automount works.
9. Unmount and remove the lab mount when finished.
