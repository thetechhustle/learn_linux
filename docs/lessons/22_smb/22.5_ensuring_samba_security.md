#### 22.5 Ensuring Samba Security

Samba security is not one switch in `smb.conf`. A safe server lines up several
controls: who can authenticate, which shares they can see, what the underlying
filesystem allows, which clients can reach the service, and what evidence is
available when something goes wrong.

!!! abstract "What you will learn"
    - Separate Samba authentication, share authorization, filesystem permissions, and network exposure.
    - Inspect a Samba server for risky guest access, weak protocol choices, and overly broad shares.
    - Validate configuration changes before reloading services.
    - Collect log and command evidence for an access-control review.

!!! warning "Production safety"
    Do not tighten a production Samba server by guessing. First identify the
    clients, users, groups, shares, and applications that depend on it. A small
    change to protocol versions, group access, or filesystem ownership can break
    scanners, legacy appliances, mapped drives, or service accounts.

## Start with the security model

Think about every SMB request as passing through layers:

1. The client must reach the server over the network.
2. Samba must accept the SMB dialect and authentication method.
3. The user must be allowed into the share.
4. The Linux filesystem must allow the final read or write.
5. Logs should show enough detail to explain the result.

This layered model matters because a share can look correct in `smb.conf` and
still fail because the directory permissions are wrong. The reverse is also
dangerous: permissive directory permissions can expose data when the share
rules are broad.

## Inspect the current configuration

Use `testparm` to view the effective Samba configuration. It reports defaults
and catches syntax errors before you restart anything.

```bash
sudo testparm -s
```

Focus on security-related settings in `[global]` and each share:

```ini
[global]
    security = user
    map to guest = Bad User
    server min protocol = SMB2_10
    restrict anonymous = 2

[projects]
    path = /srv/samba/projects
    browsable = yes
    read only = no
    valid users = @projectteam
    write list = @projecteditors
    guest ok = no
```

Important questions:

- Is `security = user` set so users authenticate with named accounts?
- Is `guest ok = yes` used only for intentionally public data?
- Are `valid users`, `invalid users`, `read list`, or `write list` used to make access explicit?
- Are older SMB protocols disabled unless a documented legacy client requires them?
- Are administrative shares and writable shares limited to groups rather than loose user lists?

!!! note "About guest access"
    Guest access is not automatically wrong, but it must be deliberate. A guest
    share should contain public data, be write-protected unless there is a clear
    workflow reason, and be reachable only from trusted networks.

## Match share rules with filesystem permissions

Samba cannot safely protect data if the Linux permissions underneath the share
are not understood. Inspect the share path before changing it:

```bash
namei -l /srv/samba/projects
ls -ld /srv/samba/projects
getfacl /srv/samba/projects
```

A common pattern is to grant access through a Linux group, then reference that
same group in Samba:

```bash
sudo groupadd projectteam
sudo chgrp projectteam /srv/samba/projects
sudo chmod 2770 /srv/samba/projects
```

The `2` in `2770` sets the setgid bit on the directory so new files inherit the
directory group. That helps keep collaborative shares consistent.

!!! warning "Avoid blanket permissions"
    Do not fix Samba write failures with `chmod 777`. That hides the real access
    problem and usually creates a larger one. Identify whether the failure is
    caused by Samba share rules, Linux ownership, POSIX mode bits, ACLs, or SELinux/AppArmor.

## Control account access

Samba users usually need both a local Unix account and a Samba password entry.
Inspect accounts without printing secrets:

```bash
sudo pdbedit -L
sudo pdbedit -Lv alice
id alice
```

Add or update a Samba password only for accounts that should use SMB:

```bash
sudo smbpasswd -a alice
sudo smbpasswd -e alice
```

Remove access when it is no longer needed:

```bash
sudo smbpasswd -d alice
sudo pdbedit -x alice
```

Prefer group-based access in share definitions. It is easier to review and less
error-prone than maintaining long lists of individual users in `smb.conf`.

## Limit network exposure

SMB is normally used inside trusted networks. Do not expose TCP 445 or the older
NetBIOS ports to the public internet.

On a firewalld host, inspect before changing:

```bash
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=internal --list-services
```

Allow Samba only in the intended zone:

```bash
sudo firewall-cmd --permanent --zone=internal --add-service=samba
sudo firewall-cmd --reload
sudo firewall-cmd --zone=internal --list-services
```

On Ubuntu systems using UFW, scope the rule to a trusted subnet:

```bash
sudo ufw allow from 192.0.2.0/24 to any app Samba
sudo ufw status verbose
```

Replace `192.0.2.0/24` with the actual client network in your lab or site.

## Validate before reload

After editing `/etc/samba/smb.conf`, validate the file first:

```bash
sudo testparm -s
```

Then reload Samba instead of doing an unnecessary restart:

```bash
sudo systemctl reload smbd
```

If your distribution does not support reload for the service, use a restart
during an approved maintenance window:

```bash
sudo systemctl restart smbd
```

Confirm the services and listening sockets:

```bash
systemctl status smbd --no-pager
ss -ltnp | grep -E ':(445|139)\b'
```

## Test access like a client

Use `smbclient` from the server or another Linux host to confirm the user sees
only the intended shares:

```bash
smbclient -L //localhost -U alice
smbclient //localhost/projects -U alice -c 'ls'
```

Test a denied user too:

```bash
smbclient //localhost/projects -U unapproved_user -c 'ls'
```

A useful security test proves both sides: the authorized user can do the
expected work, and an unauthorized user cannot.

## Logging and audit evidence

Samba logs are commonly under `/var/log/samba/`, but the exact filenames vary
by distribution and configuration. Start with recent service logs:

```bash
journalctl -u smbd --since "30 minutes ago" --no-pager
ls -l /var/log/samba/
```

For a short troubleshooting window, you can temporarily increase logging:

```ini
[global]
    log level = 2 auth:3
```

Validate and reload after the change, reproduce the access attempt, collect the
evidence, then lower the log level again. High log levels can create noisy logs
and may record sensitive operational details.

## Common failure patterns

- A user authenticates successfully but cannot write because the Linux directory is not group-writable.
- A share is hidden from browsing, but direct access still works because `valid users` allows it.
- A guest share is reachable from more networks than intended because the firewall rule is too broad.
- A legacy device requires SMB1, but enabling SMB1 globally weakens the server for every client.
- A user is removed from Linux groups but still has a Samba password entry that should be disabled.
- Logs show authentication success, but SELinux or AppArmor blocks access to the share path.

## Hands-on practice

Use a disposable lab VM with Samba installed.

1. Create a lab group and share directory:

   ```bash
   sudo groupadd smb-lab
   sudo mkdir -p /srv/samba/secure-lab
   sudo chgrp smb-lab /srv/samba/secure-lab
   sudo chmod 2770 /srv/samba/secure-lab
   ```

2. Add a test share that allows only the lab group:

   ```ini
   [secure-lab]
       path = /srv/samba/secure-lab
       read only = no
       valid users = @smb-lab
       guest ok = no
   ```

3. Run `sudo testparm -s`, reload Samba, and test with `smbclient`.
4. Record one successful access attempt and one denied access attempt.
5. Restore the lab VM or remove the temporary share when finished.
