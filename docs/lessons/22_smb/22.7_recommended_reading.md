#### 22.7 Recommended Reading

Samba and SMB are deep topics because they sit at the boundary between Linux,
Windows, macOS, identity systems, local filesystems, and network policy. Use
the resources below as an operator reading path rather than a random book list.

!!! abstract "What you will learn"
    - Choose Samba references that match the problem you are solving.
    - Prefer current project documentation and local manual pages over stale
      tutorial snippets.
    - Build a practical reading path for configuration, client access,
      security, and troubleshooting.
    - Turn site-specific discoveries into a local Samba runbook.

!!! success "Operator principle"
    Read with a system in front of you. Samba knowledge sticks when every
    reference is tied to `testparm`, `smbclient`, logs, and a real share.

## Start With Local Documentation

The first references are already on most Linux systems with Samba installed.

```bash
man smb.conf
man smbd
man nmbd
man winbindd
man smbclient
man mount.cifs
man smbpasswd
man pdbedit
man smbstatus
man testparm
```

The `smb.conf` manual is especially important. It documents the exact option
names Samba understands, default behavior, and option scope. When a web post
suggests a setting, confirm it there before using it.

Useful local commands while reading:

```bash
testparm -s
testparm -v | less
smbclient --help
mount.cifs --help
```

`testparm -v` is verbose, but it shows the effective configuration including
defaults. That makes it useful when you need to understand what Samba will do
without relying on memory.

## Official Samba Project Resources

Prefer the official Samba documentation for behavior and supported features:

- Samba project documentation: https://www.samba.org/samba/docs/
- Samba wiki: https://wiki.samba.org/
- Samba manual pages: https://www.samba.org/samba/docs/current/man-html/
- Samba release notes: https://www.samba.org/samba/history/

Use the official docs when you need to answer questions such as:

- Which `smb.conf` option controls this behavior?
- Is this feature available in the Samba version we run?
- What changed between Samba releases?
- How should Samba integrate with Active Directory or Kerberos?
- Which command is authoritative for this operational check?

## Protocol And Interoperability References

SMB is a Microsoft protocol family. Samba implements interoperability with
that ecosystem, so Microsoft references are useful when debugging client
behavior or domain integration.

Good areas to study:

- SMB dialect negotiation and modern SMB versions.
- Signing, encryption, and guest-access restrictions.
- Windows client credential caching behavior.
- Active Directory, Kerberos, DNS, and time synchronization.

When debugging a mixed environment, read both sides:

1. Samba documentation for server and Linux client behavior.
2. Microsoft documentation for Windows client and AD behavior.
3. Your local policy or security baseline for allowed SMB versions and guest
   access.

## Books Worth Knowing About

Some older Samba books still help with concepts, but they often describe old
versions, old security defaults, and SMB1-era assumptions. Treat them as
background, not as direct copy-paste runbooks.

Useful titles:

| Resource | Best use |
| --- | --- |
| *Using Samba* | Conceptual grounding for Samba as a file and print server. |
| *The Official Samba-3 HOWTO and Reference Guide* | Historical context and detailed examples; verify against current docs. |
| *UNIX and Linux System Administration Handbook* | Broader operational context for network services and file sharing. |

When reading older material, check every command and security recommendation
against current Samba docs and your distribution's package version:

```bash
smbd --version
testparm -s
```

## Distribution Documentation

Distribution guides matter because package names, service names, SELinux or
AppArmor defaults, firewall tools, and filesystem layout differ.

Check your platform's documentation for:

- package installation
- service names such as `smb`, `smbd`, `nmb`, `nmbd`, or `winbind`
- firewall commands
- SELinux booleans and labels
- default log locations
- integration with system users, SSSD, LDAP, or Active Directory

Examples of distribution-specific questions:

- Does this system use `firewalld`, `ufw`, or another firewall frontend?
- Are Samba logs in `/var/log/samba/`, journald, or both?
- Is SELinux enforcing?
- Does the package split server and client tools?

## Security Reading Path

For production Samba systems, read security material before exposing shares to
real users.

Focus areas:

1. Supported SMB protocol versions.
2. Guest access policy.
3. SMB signing and encryption.
4. Share-level authorization.
5. Unix permissions and ACLs.
6. SELinux or AppArmor confinement.
7. Backup and recovery for shared data.
8. Audit logging and incident response.

Useful evidence commands while reading:

```bash
testparm -s
smbstatus
sudo ss -ltnp | grep ':445'
sudo journalctl -u smbd --since -1h
```

## Client Reading Path

If your job is mostly Linux client access to SMB shares, prioritize:

- `smbclient`
- `mount.cifs`
- systemd automounts
- credentials files
- Kerberos ticket behavior
- UID/GID and mode mapping

Practice commands:

```bash
smbclient -L //fileserver.example.com -U EXAMPLE/alice
smbclient //fileserver.example.com/projects -U EXAMPLE/alice -c 'ls'
findmnt /mnt/projects
mount | grep cifs
```

## Build A Site Runbook

General references are not enough. Every environment should have a short local
Samba runbook.

Include:

- server hostname and role
- Samba version and distribution
- important shares and their business purpose
- backing filesystem paths
- expected owner/group and permission model
- allowed SMB versions
- authentication source
- firewall exposure
- backup owner and restore process
- standard diagnostics
- escalation contact

Example skeleton:

```text
Server: fileserver01.example.com
Role: standalone Samba file server
Version: smbd 4.x on Debian
Shares: projects, finance-readonly, public-drop
Auth: local Samba users synced to Unix accounts
Ports: 445/tcp from office LAN only
Diagnostics: testparm -s; smbclient -L //localhost -U user; smbstatus
Backups: nightly snapshot, owner storage-team
```

## Hands-On Practice

1. Run `smbd --version` and record the Samba version.
2. Open `man smb.conf` and look up three options used by your lab server.
3. Use `testparm -s` to compare configured values with what Samba loads.
4. Read one official Samba wiki page related to your lab scenario.
5. Read one distribution-specific page for package/service/firewall details.
6. Draft a one-page site runbook for your lab Samba server.
7. Add a "known risks" section: guest access, old SMB dialects, weak
   permissions, missing backups, or unclear ownership.
