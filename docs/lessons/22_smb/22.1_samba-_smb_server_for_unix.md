## What Samba provides

Samba is the main open source implementation of the SMB protocol suite for Unix-like systems. SMB is the protocol family used by Windows file sharing and by many NAS devices.

With Samba, a Linux or Unix host can:

- publish file shares to Windows, macOS, and Linux clients
- publish print services in some environments
- access SMB shares as a client with tools such as `smbclient` or `mount.cifs`
- integrate with Active Directory for authentication and identity lookup
- act as an Active Directory domain controller in specific Samba-supported designs

This chapter focuses first on Samba as a file server. Domain-controller and identity-integration designs require more planning than a simple workgroup share.

## The main moving parts

Samba deployments vary, but these names appear often:

- `smbd`: serves SMB file and printer sharing.
- `nmbd`: handles older NetBIOS name service and browsing behavior.
- `winbindd`: maps Windows domain users and groups into Unix identity lookups.
- `smb.conf`: the main Samba configuration file, usually under `/etc/samba/`.
- `smbclient`: a command-line SMB client for listing and testing shares.
- `testparm`: validates and prints the effective Samba configuration.

Modern Active Directory-oriented deployments may also use the `samba` service for domain-controller roles. Do not assume every Samba host has the same service layout.

## Samba is layered

When users cannot access a Samba share, avoid guessing. Think in layers:

1. **Network path**
   - Can the client reach the server?
   - Are SMB ports reachable?

2. **SMB service**
   - Is the Samba service running?
   - Is the share actually defined?

3. **Authentication**
   - Is the user known to Samba?
   - Is the password or domain login valid?

4. **Share authorization**
   - Does `smb.conf` allow that user or group?
   - Is the share read-only or writable?

5. **Unix filesystem permissions**
   - Does the underlying directory permit the mapped Unix user or group?
   - Are ACLs involved?

6. **Client behavior**
   - Is the client using cached credentials?
   - Is it connecting to the expected server name or address?

Samba must pass all of these gates for access to work.

## Inspect a Samba server safely

Use read-only commands first:

```console
$ testparm -s
$ systemctl status smbd
$ systemctl status nmbd
$ systemctl status winbind
$ ss -lntup | grep -E ':(139|445)\\b'
```

On some distributions, service names differ:

```console
$ systemctl list-units | grep -Ei 'samba|smb|nmb|winbind'
```

List shares from the server itself:

```console
$ smbclient -L localhost -N
```

If guest access is disabled, test with a user:

```console
$ smbclient -L localhost -U alice
```

The `-L` option lists shares. It does not mount or modify data.

## Understand `smb.conf`

The main configuration file usually has a global section and one section per share.

Example shape:

```ini
[global]
   workgroup = EXAMPLE
   server role = standalone server
   security = user

[projects]
   path = /srv/samba/projects
   read only = no
   browseable = yes
   valid users = @project-team
```

This defines an SMB share named `projects` backed by the Unix path `/srv/samba/projects`.

The share being writable in Samba is not enough. The filesystem must also allow the mapped Unix user or group to write:

```console
$ ls -ld /srv/samba/projects
$ getfacl /srv/samba/projects
```

If `getfacl` is not installed, use `ls -le` or your distribution's ACL tooling where available.

## Users and passwords

In a simple standalone server setup, Samba can maintain its own SMB password database:

```console
$ sudo pdbedit -L
```

Adding or enabling users changes authentication state and should be done deliberately:

```console
$ sudo smbpasswd -a alice
$ sudo smbpasswd -e alice
```

Do this only in a lab or with an approved account plan. A production Samba server may use Active Directory or another identity source, and local `smbpasswd` changes may be the wrong layer.

## Client-side testing

From another machine, test basic reachability:

```console
$ nc -vz fileserver.example.com 445
```

List shares:

```console
$ smbclient -L //fileserver.example.com -U alice
```

Connect to a share interactively:

```console
$ smbclient //fileserver.example.com/projects -U alice
```

Inside `smbclient`, use commands such as:

```text
smb: \> ls
smb: \> pwd
smb: \> quit
```

This is often safer for first tests than mounting the share into the local filesystem.

## Common roles for Samba

Samba can fit several roles:

- **Standalone file server:** local Samba users, local Unix permissions, small office or lab.
- **Member server:** joined to Active Directory, serving files using domain identities.
- **AD domain controller:** Samba provides Active Directory-compatible domain services.
- **Client tooling only:** Linux host uses `smbclient` or CIFS mounts to access someone else's SMB server.

These roles should not be mixed casually. A quick standalone lab is not the same as an AD-integrated production file server.

## What Samba is not

Samba is not a magic permission bypass. If the Unix filesystem denies access, Samba usually cannot make the operation succeed safely.

Samba is also not always the right answer:

- Use NFS when Linux/Unix clients dominate and Unix identity is already aligned.
- Use SMB/Samba when Windows/macOS compatibility or SMB semantics matter.
- Use object storage or application-level file handling when users need remote access across untrusted networks.

## Hands-on practice

Use a disposable VM or lab container.

1. Install Samba with your distribution's package manager.
2. Run `testparm -s` and save the output.
3. Identify the Samba-related systemd units.
4. Create a lab directory such as `/srv/samba/lab`.
5. Draft a simple share in a lab note, but do not apply it on a production host.
6. Explain which layer controls network access, authentication, share authorization, and filesystem permission.

If Samba is already installed on a real system, stop at read-only inspection unless you have approval to change the service.
