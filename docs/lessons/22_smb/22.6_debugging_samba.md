#### Debugging Samba

Samba failures are easier to fix when you identify the failing layer first.
Most incidents fall into one of these buckets:

1. the client cannot reach the server
2. Samba is not listening or is bound to the wrong interface
3. the configuration is invalid or not loaded
4. authentication succeeds or fails unexpectedly
5. share authorization blocks the user
6. Unix filesystem permissions block the Samba process
7. the client and server disagree about protocol, name, or identity behavior

Do not start by changing random options in `smb.conf`. Build an evidence trail,
change one thing, and verify the result.

!!! abstract "What you will learn"
    - Separate Samba failures by network, service, configuration, identity,
      share, filesystem, and client layers.
    - Use `testparm`, `smbclient`, `pdbedit`, `smbstatus`, `journalctl`, and
      socket checks safely.
    - Raise Samba logging temporarily without leaving noisy settings behind.
    - Debug common symptoms such as `NT_STATUS_ACCESS_DENIED`,
      `NT_STATUS_LOGON_FAILURE`, and invisible shares.
    - Produce a short incident handoff that another operator can trust.

!!! success "Operator principle"
    A Samba problem is rarely just "Samba is broken." Name the failing layer
    before changing configuration.

## Start With The Symptom

Capture the exact error and the path being accessed:

```text
client: Windows 11 laptop
target: \\fileserver\projects
user: EXAMPLE\alice
error: The network path was not found
time: 2026-05-13 14:10 UTC
```

That small note prevents several common mistakes:

- debugging the wrong server
- testing a different account than the user used
- assuming a mount problem is a share permission problem
- assuming a Windows name-resolution error is a Samba daemon failure

## Layer 1: Network And Port Reachability

From a Linux client, verify name resolution and port `445/tcp`:

```bash
getent hosts fileserver.example.com
nc -vz fileserver.example.com 445
```

On the Samba server, confirm the local address and listening socket:

```bash
ip -brief addr
sudo ss -ltnp | grep ':445'
```

If `nc` cannot connect, look at firewall, routing, VPN, security group, or
server service state before touching `smb.conf`.

## Layer 2: Service State

Standalone Samba file servers usually need `smbd`. Some environments also use
`nmbd` for NetBIOS name service and `winbindd` for domain identity lookup.

```bash
systemctl status smbd
systemctl status nmbd
systemctl status winbind
```

Service names vary by distribution. Common alternatives include `smb`,
`nmb`, and `winbind`.

Check recent service logs:

```bash
journalctl -u smbd --since -30m
journalctl -u nmbd --since -30m
journalctl -u winbind --since -30m
```

If the service will not start, validate the configuration next.

## Layer 3: Configuration Syntax And Loaded Values

Use `testparm` before restarting Samba:

```bash
testparm -s
```

Useful checks:

```bash
testparm -s --parameter-name='server role'
testparm -s --section-name=projects
testparm -s --parameter-name='valid users' --section-name=projects
```

`testparm` answers two different questions:

- Is the syntax valid?
- What values does Samba actually see after defaults and includes are applied?

After changing `smb.conf`, reload or restart intentionally:

```bash
sudo systemctl reload smbd
```

If reload is unsupported or does not apply the changed option, restart during a
safe maintenance window:

```bash
sudo systemctl restart smbd
```

## Layer 4: Local SMB Tests

Test from the server itself. This separates server-side Samba behavior from
remote client network behavior.

List shares:

```bash
smbclient -L //localhost -U alice
```

Test one share:

```bash
smbclient //localhost/projects -U alice -c 'ls'
```

If local access fails, stay on the server and debug Samba configuration,
identity, share authorization, or filesystem permissions. If local access
works but remote access fails, return to network, firewall, DNS, or client
behavior.

## Layer 5: Users, Passwords, And Identity

Samba authentication may use local Samba users, local Unix users, Active
Directory, LDAP, or Kerberos depending on the server role.

For local Samba password database checks:

```bash
sudo pdbedit -L
sudo pdbedit -Lv alice
```

Set or reset a local Samba password:

```bash
sudo smbpasswd alice
```

Confirm the matching Unix account exists when local users are expected:

```bash
getent passwd alice
id alice
```

For domain/member servers, check domain lookup:

```bash
wbinfo -t
wbinfo -u | head
getent passwd 'EXAMPLE\alice'
```

If `wbinfo -t` fails, the issue is likely domain trust, DNS, time sync, or
winbind configuration rather than the individual share.

## Layer 6: Share Authorization

A valid login does not guarantee share access. Inspect the share definition:

```bash
testparm -s --section-name=projects
```

Important share-level options include:

| Option | What to check |
| --- | --- |
| `path` | Does it point to the intended directory? |
| `read only` / `writable` | Is write access expected? |
| `valid users` | Is the user or group listed correctly? |
| `write list` | Is write access limited to a subset? |
| `browseable` | Should the share appear in listings? |
| `guest ok` | Is guest access intentionally allowed or denied? |

Test with the same identity the user used:

```bash
smbclient //localhost/projects -U EXAMPLE/alice -c 'ls'
```

## Layer 7: Unix Filesystem Permissions

Samba cannot grant more access than the server filesystem allows. Check the
path from root to the share directory:

```bash
namei -l /srv/samba/projects
ls -ld /srv /srv/samba /srv/samba/projects
sudo -u alice test -r /srv/samba/projects && echo readable
sudo -u alice test -w /srv/samba/projects && echo writable
```

For SELinux systems:

```bash
getenforce
ls -Zd /srv/samba/projects
```

Common SELinux fixes depend on local policy, but the pattern is to label the
exported directory appropriately and make the change persistent with
`semanage fcontext` plus `restorecon`.

## Layer 8: Current Sessions And Locks

Use `smbstatus` to see active sessions, shares, and locks:

```bash
sudo smbstatus
sudo smbstatus --shares
sudo smbstatus --locks
```

This helps when users report that files are locked, stale sessions exist, or a
specific client is still connected.

Be careful about killing sessions. A forced disconnect can interrupt active
work. Use it only when you understand the business impact.

## Temporary Debug Logging

Samba logs may live in `/var/log/samba/`, journald, or both depending on the
distribution.

Check common locations:

```bash
ls -lah /var/log/samba/
tail -100 /var/log/samba/log.smbd
journalctl -u smbd --since -10m
```

For short investigations, raise logging temporarily:

```bash
sudo smbcontrol smbd debug 3
```

Reproduce the problem, collect the evidence, then lower it again:

```bash
sudo smbcontrol smbd debug 1
```

Avoid leaving high debug levels enabled. They can create noisy logs and may
record sensitive operational details.

## Symptom-To-Layer Guide

| Symptom | Likely layer | First move |
| --- | --- | --- |
| `Connection timed out` | Network/firewall | Test `nc -vz server 445` from the client. |
| `NT_STATUS_LOGON_FAILURE` | Authentication | Check username/domain/password and account status. |
| `NT_STATUS_ACCESS_DENIED` | Share or filesystem authorization | Test same user locally; inspect `valid users`, modes, ACLs. |
| Share missing from browse list | `browseable`, access-based enumeration, or wrong account | Connect directly to `//server/share`. |
| Service will not start | Config or service dependency | Run `testparm -s` and inspect `journalctl -u smbd`. |
| Write fails but read works | Share write policy or filesystem permissions | Check `read only`, `write list`, ownership, ACLs, SELinux. |
| Works locally, fails remotely | Network, firewall, client, DNS, protocol | Compare local `smbclient` and remote `smbclient`. |

## Incident Handoff Template

Use a compact handoff like this:

```text
Symptom: EXAMPLE\alice gets NT_STATUS_ACCESS_DENIED for //fileserver/projects.
Network: client reaches fileserver:445 successfully.
Service: smbd active; no startup errors in journal.
Config: testparm shows [projects] path=/srv/samba/projects, read only=no, valid users=@project.
Identity: getent group project includes alice.
Filesystem: /srv/samba/projects is root:project 2770; alice can write via sudo -u test.
Client test: smbclient //localhost/projects -U EXAMPLE/alice -c 'ls' works locally.
Next focus: remote client credential/domain behavior or stale cached Windows session.
```

## Hands-On Practice

Use a lab Samba server.

1. Run `testparm -s` and save the share definition for one lab share.
2. Use `smbclient -L //localhost -U user` to list shares locally.
3. Use `smbclient //localhost/share -U user -c 'ls'` to test one share.
4. Check `namei -l` and `ls -ld` for the backing directory.
5. Temporarily raise debug logging with `smbcontrol`, reproduce one failed
   login, then lower logging again.
6. Write a five-line incident handoff naming the failing layer.
