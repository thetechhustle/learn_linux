## 12.3 Troubleshooting Tips

Printing failures are noisy because several systems are involved at once: the
application, CUPS, the queue, filters or drivers, authentication policy, the
network, and the physical printer. Good troubleshooting narrows the failure stage
before making changes.

This lesson gives you a practical workflow for Linux printing incidents. The goal
is not to memorize every CUPS command. The goal is to build an evidence trail that
answers: did the job submit, did CUPS accept it, did the queue process it, did the
printer receive it, and did the physical device produce output?

!!! abstract "What you will learn"
    - Classify common printing symptoms by failure stage.
    - Inspect CUPS service, queues, jobs, printer state, and logs.
    - Separate local workstation issues from shared print-server issues.
    - Recover from paused queues, held jobs, bad printer URIs, and unreachable printers.
    - Write a useful incident handoff for a printing problem.

!!! example "Field story"
    A user says, "I printed the label, but nothing came out." You check `lpstat`
    and see the job completed. The printer display shows "Load labels in Tray 2."
    The Linux host and CUPS did their part; the remaining issue is printer media
    and tray state. That is a very different fix from reinstalling CUPS.

!!! success "Operator principle"
    Troubleshoot by stage. Do not restart services, replace drivers, or clear
    queues until you know which stage failed.

## Start With the Symptom

Ask what the user actually observed.

Common symptoms:

- The printer is missing from the print dialog.
- The job never appears in the queue.
- The job appears but stays pending.
- The queue says the printer is paused or disabled.
- The job completes but no paper comes out.
- The wrong tray, paper size, color mode, or duplex mode is used.
- Only one application, user, host, VLAN, or document type fails.
- Printing works from another OS but not Linux.

Different symptoms point to different evidence. A missing printer is often
discovery or configuration. A held job is often queue state or policy. A completed
job with no output may be printer-side state, driver mismatch, wrong destination,
or a bad backend path.

## Capture the Baseline

Run read-only commands first.

```bash
hostname
date
systemctl status cups
lpstat -t
lpstat -p
lpstat -d
lpstat -o
```

For a specific printer:

```bash
lpstat -p Office_Printer
lpoptions -p Office_Printer -l
```

Save the output in your incident note. If the issue changes while you are
working, this baseline is what lets you explain what changed.

## Check Whether CUPS Is Running

If CUPS is stopped, users may not be able to submit or manage jobs.

```bash
systemctl status cups
journalctl -u cups --since "30 minutes ago"
```

If this is a local workstation and CUPS should be running, starting it is usually
low risk:

```bash
sudo systemctl start cups
```

On a shared print server, treat a restart as more disruptive. Check logs and
active jobs before restarting.

```bash
lpstat -o
```

## Find the Queue State

Use `lpstat` to tell whether the queue is idle, printing, rejecting jobs, paused,
or disabled.

```bash
lpstat -t
lpstat -p Office_Printer
```

Typical meanings:

- `idle`: the queue is available and has no active job.
- `printing`: CUPS is actively processing a job.
- `disabled`: the queue will not process jobs until enabled.
- `rejecting requests`: CUPS will not accept new jobs for that queue.
- `held`: one or more jobs are waiting for release or another condition.

Enable a queue only when you understand why it was disabled:

```bash
sudo cupsenable Office_Printer
sudo cupsaccept Office_Printer
```

On a shared server, enabling a queue may release other users' jobs. Confirm that
is acceptable before doing it.

## Inspect the Jobs

List active jobs:

```bash
lpstat -o
lpq -P Office_Printer
```

List completed jobs if the system keeps that history:

```bash
lpstat -W completed -o Office_Printer
```

If one test job is stuck, cancel the specific job ID:

```bash
cancel Office_Printer-17
```

Avoid clearing an entire queue unless you are deliberately handling an approved
outage. Broad queue cleanup can delete other people's work.

## Send a Small Controlled Test

Do not test with a production document first. Use a one-line text job.

```bash
printf 'CUPS troubleshooting test from %s\n' "$(hostname)" | lp -d Office_Printer
lpstat -o Office_Printer
```

Record the job ID and final state.

If the test job prints, the original failure may be document-specific,
application-specific, paper-size-specific, or user-specific. If the test job does
not print, the failure is lower in the pipeline.

## Check the Printer URI

A queue can look healthy while pointing at the wrong destination.

```bash
lpstat -v Office_Printer
```

Look for stale IP addresses, old hostnames, insecure protocol assumptions, or a
printer path that does not match the current device.

Examples:

```text
device for Office_Printer: ipp://printer.example.com/ipp/print
device for Office_Printer: socket://192.0.2.50:9100
```

If the printer recently moved networks or changed DHCP leases, the queue may need
to be updated.

## Test Network Reachability

For network printers, confirm the host can reach the printer.

```bash
ping printer.example.com
ip route get 192.0.2.50
ippfind
```

Not all printers answer ping, so do not stop there. The route and discovery tests
still help you decide whether the host is on the right network and whether IPP
advertising is visible.

If only one VLAN, VPN state, or Wi-Fi network fails, the issue may be network
policy rather than CUPS.

## Read CUPS Logs

Recent service logs are often enough:

```bash
journalctl -u cups --since "30 minutes ago"
```

Some systems also write CUPS logs under `/var/log/cups/`:

```bash
sudo tail -n 100 /var/log/cups/error_log
sudo tail -n 100 /var/log/cups/access_log
```

Common clues:

- authentication failures
- filter failures
- backend connection errors
- printer not responding
- permission denied
- unsupported document format
- job canceled by policy
- queue disabled after repeated failures

Increase log verbosity only when necessary, and turn it back down afterward.

## Driver and Filter Problems

If CUPS accepts the job but fails while processing it, suspect filters, drivers,
or document conversion.

Useful checks:

```bash
lpoptions -p Office_Printer -l
lpstat -v Office_Printer
journalctl -u cups --since "30 minutes ago"
```

Modern printers often work best with driverless IPP:

```bash
sudo lpadmin -p Office_Printer -v ipp://printer.example.com/ipp/print -m everywhere
```

Do not switch drivers on a shared production queue casually. Create a temporary
test queue when possible:

```bash
sudo lpadmin -p Office_Printer_Test -E -v ipp://printer.example.com/ipp/print -m everywhere
printf 'temporary test\n' | lp -d Office_Printer_Test
```

Remove the temporary queue when finished:

```bash
sudo lpadmin -x Office_Printer_Test
```

## Permission and Policy Problems

If one user cannot print but others can, inspect user, group, and policy scope.

Questions to ask:

- Is the user submitting to the same queue?
- Is the job held for authentication?
- Is the queue configured to accept jobs from that host?
- Is the user allowed by local or server-side CUPS policy?
- Does the user have access only through a desktop portal or sandboxed app?

Check the logs around the failed submission time:

```bash
journalctl -u cups --since "10 minutes ago"
```

Avoid broad permission changes such as opening administration access to everyone.
Fix the narrow policy that matches the evidence.

## Completed Job, No Output

This is one of the most confusing printing symptoms. Possible causes include:

- the job went to the wrong printer
- the printer is waiting for paper, labels, toner, or manual feed
- the wrong tray or paper size was selected
- the document rendered blank or outside printable margins
- the printer accepted the job but discarded it due to language or driver mismatch

Useful checks:

```bash
lpstat -W completed -o Office_Printer
lpstat -v Office_Printer
lpoptions -p Office_Printer -l
```

Also inspect the physical printer display or management page. CUPS can say a job
completed because it handed the job to the printer, even if the printer then waits
for a human action.

## Recovery Order

Prefer the least disruptive recovery first.

1. Submit a controlled test job.
2. Resume a specific paused printer only if the cause is understood.
3. Cancel only the stuck test job or known bad job.
4. Correct a stale printer URI.
5. Create a temporary test queue.
6. Change drivers or queue defaults.
7. Restart CUPS only when service state or logs justify it.
8. Escalate to network, desktop, or printer hardware support with evidence.

## Incident Handoff Template

Use a short note like this:

```text
Printer issue: Office_Printer
Affected host/user: laptop-22 / ajones
Symptom: test job appears, stays pending, queue shows disabled
Baseline: lpstat -t captured at 10:42
CUPS service: active
Printer URI: ipp://printer.example.com/ipp/print
Test job: Office_Printer-17, pending
Logs: backend connection timeout at 10:43
Action taken: no queue restart; no jobs canceled
Likely next owner: network/printer admin to confirm printer IP and IPP reachability
```

This format tells the next person what failed, what was verified, and what you did
not change.

## Hands-on Practice

Use a lab machine or VM.

1. Run `lpstat -t` and identify the default printer state.
2. Submit a small test job to a safe queue or temporary queue.
3. Find the job ID and final state.
4. Read recent CUPS logs.
5. Create a short incident handoff note using the template above.
