## 12.1 CUPS Printing

CUPS is the normal printing layer on Linux. It accepts print jobs from
applications, stores them in queues, applies printer defaults, and sends the jobs
to local or network printers. When a Linux user says "the printer is broken,"
CUPS is usually the first place you look for evidence.

This lesson focuses on workstation-level printing: verifying CUPS, discovering
printers, adding a queue, sending test jobs, and checking what happened.

!!! abstract "What you will learn"
    - Verify that the CUPS service and command-line tools are available.
    - Inspect configured printers, default printers, and queued jobs.
    - Add a printer through the CUPS web interface or CLI with reversible changes.
    - Submit a small test job and confirm its queue result.
    - Capture enough evidence to troubleshoot or hand off a printing issue.

!!! example "Field story"
    A Linux laptop cannot print to the office printer, but macOS users can. The
    printer is online and the user needs labels before a shipping cutoff. You
    check whether CUPS is running, whether the Linux host has a queue, whether the
    queue points at the right printer URI, whether a test job appears, and whether
    the job is held, canceled, completed, or rejected.

!!! success "Operator principle"
    Do not treat printing as magic. Treat it as a queue and transport pipeline:
    service, queue, printer URI, options, job state, network path, and device.

## Check Whether CUPS Is Installed

Many desktop Linux systems already include CUPS. Servers and minimal VMs may not.
Start with inspection before installation.

```bash
command -v lp
command -v lpstat
command -v lpadmin
systemctl status cups
```

If the commands are missing, install the CUPS package for your distribution.

Debian and Ubuntu:

```bash
sudo apt update
sudo apt install cups
```

Fedora, Red Hat Enterprise Linux, CentOS Stream, and similar systems:

```bash
sudo dnf install cups
```

openSUSE:

```bash
sudo zypper install cups
```

After installation, start and enable the service when this host should manage
printing regularly.

```bash
sudo systemctl enable --now cups
systemctl status cups
```

On some distributions the service may be socket-activated. If `lpstat` works and
jobs can be submitted, do not fight the init model just because the service state
looks different from another distribution.

## Inspect Existing Printers

Before adding anything, find out what the host already knows.

```bash
lpstat -t
lpstat -p
lpstat -d
lpstat -o
```

Useful output to notice:

- `system default destination`: the default printer, if one exists
- `printer NAME is idle`: a configured queue that is available
- `printer NAME disabled`: a configured queue that will not accept jobs normally
- `no system default destination`: no default printer is selected
- job IDs such as `Office_Printer-17`: queued or recently active jobs

You can inspect options for a known queue:

```bash
lpoptions -p Office_Printer -l
```

The available options depend on the printer and driver. Common options include
paper size, duplex mode, color mode, tray selection, and print quality.

## Discover Network Printers

Modern printers commonly advertise driverless IPP support. Try discovery before
manually typing an address.

```bash
ippfind
```

If the printer does not appear, that does not prove it is offline. Discovery can
be blocked by network segmentation, multicast restrictions, printer settings, or
firewalls. If you know the printer hostname or IP address, check reachability.

```bash
ping printer.example.com
ip route get 192.0.2.50
```

For IPP printers, the queue URI often looks like one of these:

```text
ipp://printer.example.com/ipp/print
ipps://printer.example.com/ipp/print
```

For older raw socket printers, you may see:

```text
socket://192.0.2.50:9100
```

Prefer IPP or IPPS when the device supports it. Raw socket printing can work, but
it gives less protocol-level feedback and is easier to misdiagnose.

## Add a Printer with the Web Interface

CUPS usually exposes a local web interface:

```text
http://localhost:631
```

From the web interface:

1. Open **Administration**.
2. Choose **Add Printer**.
3. Authenticate if prompted.
4. Select the discovered printer, or provide a printer URI.
5. Give the queue a simple name such as `Office_Printer`.
6. Select driverless IPP or the closest correct driver.
7. Review default options before saving.

Use descriptive names, but avoid spaces in queue names. A queue named
`Office_Printer` is easier to use from scripts than `Office Printer`.

## Add a Printer from the CLI

For scripted setup or remote administration, use `lpadmin`.

Example using a driverless IPP URI:

```bash
sudo lpadmin \
  -p Office_Printer \
  -E \
  -v ipp://printer.example.com/ipp/print \
  -m everywhere
```

What the options mean:

- `-p Office_Printer`: create or modify this queue
- `-E`: enable the printer and accept jobs
- `-v ...`: set the printer device URI
- `-m everywhere`: use driverless IPP where supported

Set it as the default printer only when that is actually desired:

```bash
sudo lpadmin -d Office_Printer
```

After adding a queue, inspect it:

```bash
lpstat -t
lpoptions -p Office_Printer -l
```

## Send a Small Test Job

Use a harmless text job first. Do not start with a large PDF, label batch, or
customer document.

```bash
printf 'CUPS test from %s\n' "$(hostname)" | lp -d Office_Printer
```

Then check job state:

```bash
lpstat -o Office_Printer
lpstat -W completed -o Office_Printer
```

If the job remains in the queue, inspect whether the printer is paused, disabled,
or rejecting jobs.

```bash
lpstat -p Office_Printer
cupsenable Office_Printer
cupsaccept Office_Printer
```

Use `cupsenable` and `cupsaccept` carefully on shared printers. Enabling a queue
can release held work from other users.

## Cancel Test Jobs Safely

If your test job is stuck or you accidentally submitted the wrong file, cancel
only the job you own or the specific test job ID.

```bash
lpstat -o
cancel Office_Printer-17
```

Avoid broad cancellation commands on shared systems unless you are intentionally
clearing a queue during an approved maintenance window.

## Check CUPS Logs

When a job fails, look at recent logs.

```bash
journalctl -u cups --since "30 minutes ago"
```

Some systems also keep files under `/var/log/cups/`:

```bash
sudo ls -l /var/log/cups
sudo tail -n 100 /var/log/cups/error_log
```

Log clues may mention authentication failures, filter failures, printer
unreachable errors, held jobs, backend failures, or policy restrictions.

## Safe First Response

For a user-facing printing issue, use this sequence before making larger changes:

1. Identify the affected host, user, printer queue, and document type.
2. Run `lpstat -t` and save the output.
3. Confirm the CUPS service state.
4. Send one tiny test job.
5. Check whether the job appears, completes, holds, or errors.
6. Inspect recent CUPS logs.
7. Change only one thing, then test again.

That approach keeps you from mixing multiple changes together and losing track of
which one fixed or worsened the issue.

## Hands-on Practice

Use a disposable VM or lab workstation.

1. Check whether CUPS is installed and running.
2. Run `lpstat -t` and record the current printer state.
3. If a safe lab printer or PDF-backed printer is available, add a queue.
4. Submit a one-line test job with `lp`.
5. Record the job ID and final state.
6. Write a short handoff note explaining what evidence proves the test worked or
   where it failed.
