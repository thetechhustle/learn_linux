### 12.2 CUPS Server Administration

!!! abstract "What you will learn"
    - Identify the CUPS daemon, configuration files, queues, classes, jobs, and logs that define a print server.
    - Use read-only commands to inspect server state before changing printers or access rules.
    - Make small, reversible CUPS administration changes and prove the result.
    - Recognize risky printing changes, especially network listeners, shared printers, broad access rules, and driver swaps.

!!! example "Field story"
    A department printer works from one Linux workstation but fails for everyone else. The printer itself is online, but users see jobs stuck in the queue. Your task is to inspect the CUPS server, find whether the issue is service health, queue policy, network access, or driver configuration, and make one low-risk change at a time.

!!! success "Operator principle"
    Treat CUPS administration as service management plus queue management. Keep the daemon healthy, keep the queues explainable, and verify every change with a test job or a dry run.

## CUPS server components

CUPS is usually managed by the `cups` or `cupsd` service. The server accepts jobs, applies queue policy, filters documents into printer-ready formats, and sends the result to a local device or a network printer.

Useful control points include:

- `/etc/cups/cupsd.conf`: server listener, access-control, browsing, and logging policy.
- `/etc/cups/printers.conf`: printer queues managed by CUPS. Avoid hand-editing this file while CUPS is running.
- `/etc/cups/classes.conf`: printer classes that group multiple queues.
- `/etc/cups/ppd/`: queue-specific PPD files on systems that still use PPD-based drivers.
- `/var/log/cups/`: access, error, and page logs on many distributions.
- `http://localhost:631`: the local CUPS web interface, if the distribution enables it.

The web interface is convenient, but command-line evidence is easier to paste into tickets and incident notes. Use both when appropriate.

## Start with read-only evidence

Before adding printers or editing configuration, capture the current server state.

```bash
systemctl status cups --no-pager
lpstat -r
lpstat -v
lpstat -p -d
lpstat -t
lpoptions -p PRINTER_NAME -l
```

On systems without systemd, use the platform's service tool instead:

```bash
service cups status
rc-service cupsd status
```

Check logs before restarting anything:

```bash
journalctl -u cups --since "30 minutes ago" --no-pager
sudo tail -n 80 /var/log/cups/error_log
```

Record the queue name, device URI, accepting state, enabled state, default printer, recent errors, and the exact time of your inspection.

## Manage the daemon safely

Restarting CUPS can interrupt active print jobs. Prefer inspection first, then reload or restart only when the change requires it.

```bash
sudo systemctl reload cups
sudo systemctl restart cups
sudo systemctl enable --now cups
```

Use `reload` after supported configuration changes. Use `restart` when the daemon does not support reload on your distribution, when logs show the daemon is wedged, or after a package upgrade that expects a restart.

After a service action, verify the result:

```bash
systemctl is-active cups
lpstat -r
journalctl -u cups --since "2 minutes ago" --no-pager
```

If the system is a shared print server, announce restarts and check for active jobs first:

```bash
lpstat -o
```

## Add and modify queues

Use `lpadmin` for queue changes. Start with the discovered device URI, then choose the least surprising driver or model option available on the system.

```bash
lpinfo -v
lpinfo -m | head
sudo lpadmin -p office-laser -E -v ipp://printer.example.com/ipp/print -m everywhere
lpstat -p office-laser -l
```

The `-E` option enables the printer when it appears after `-p`. The `-v` option sets the device URI. The `-m everywhere` option uses IPP Everywhere when the printer supports driverless printing.

Set a default only when the host should have one:

```bash
sudo lpadmin -d office-laser
lpstat -d
```

Change queue options deliberately:

```bash
lpoptions -p office-laser -l
sudo lpadmin -p office-laser -o printer-is-shared=false
sudo lpadmin -p office-laser -o media=Letter
sudo lpadmin -p office-laser -o sides=two-sided-long-edge
```

Avoid changing driver, URI, sharing, and defaults in the same step. One change at a time makes rollback possible.

## Enable, disable, accept, and reject jobs

CUPS separates whether a printer is enabled from whether it accepts new jobs.

- Enabled: CUPS may send queued jobs to the printer.
- Disabled: jobs stay queued and do not print.
- Accepting: users may submit new jobs.
- Rejecting: new jobs are refused with a reason.

```bash
cupsenable office-laser
cupsdisable office-laser
cupsaccept office-laser
cupsreject office-laser -r "Maintenance window"
lpstat -p office-laser -a office-laser
```

This distinction is useful during maintenance. Reject new jobs before a planned outage, let existing jobs drain if appropriate, then disable the queue when work begins.

## Use printer classes for simple failover

A CUPS class groups printers behind one logical destination. Jobs submitted to the class can use any member printer that is available.

```bash
sudo lpadmin -p floor1-east -E -v ipp://east.example.com/ipp/print -m everywhere
sudo lpadmin -p floor1-west -E -v ipp://west.example.com/ipp/print -m everywhere
sudo lpadmin -p floor1-east -c floor1
sudo lpadmin -p floor1-west -c floor1
lpstat -c floor1
```

Classes help with small offices and labs, but they are not a substitute for monitoring. If both printers are misconfigured in the same way, the class only hides the problem until every job fails.

## Control network exposure

Do not expose a CUPS server to a broad network by accident. Check what the daemon is listening on before and after configuration changes.

```bash
ss -ltnp | grep -E ':(631)\b' || true
grep -nE '^(Listen|Port|Browsing|BrowseLocalProtocols|DefaultAuthType|<Location)' /etc/cups/cupsd.conf
```

Common local-only defaults look like this:

```text
Listen localhost:631
```

Shared print servers may listen on a host address or all interfaces:

```text
Port 631
```

That broader setting must be paired with clear access rules and a host firewall. After changing listener or access policy, validate locally and from an expected client network, then check logs for denied or unexpected access.

## Test without wasting paper

Use a tiny text file or a known test page, not a large document.

```bash
printf 'CUPS test from %s\n' "$(hostname)" > /tmp/cups-test.txt
lp -d office-laser /tmp/cups-test.txt
lpstat -o office-laser
```

Cancel a test job if it stalls or targets the wrong queue:

```bash
cancel JOB_ID
cancel -a office-laser
```

Be careful with `cancel -a`; it removes all jobs for the destination. On a shared print server, inspect `lpstat -o` first and avoid canceling other users' jobs without coordination.

## Troubleshooting patterns

Use symptoms to narrow the layer:

- `lpstat -r` says the scheduler is not running: inspect and restart the CUPS service.
- Jobs are submitted but never print: check `lpstat -o`, queue enabled state, printer connectivity, and `error_log`.
- Users cannot submit jobs: check accepting state, authentication, group membership, and access rules in `cupsd.conf`.
- Only one application fails: print a text file with `lp` to separate application formatting from CUPS.
- The wrong tray, paper, or duplex setting is used: compare `lpoptions -l` with queue defaults and printer capabilities.
- A network printer moved or was replaced: verify the URI with `lpstat -v`, DNS, IP reachability, and IPP response.

Prefer evidence that another administrator can reproduce:

```bash
lpstat -t
lpstat -v office-laser
lpoptions -p office-laser -l
journalctl -u cups --since "10 minutes ago" --no-pager
```

## Rollback notes

Before a risky queue change, save the current state:

```bash
lpstat -t > /tmp/cups-before.txt
lpoptions -p office-laser -l > /tmp/office-laser-options-before.txt
sudo cp /etc/cups/cupsd.conf /etc/cups/cupsd.conf.before-change
```

For queue changes, rollback may mean restoring the old URI, options, driver, or sharing flag with `lpadmin`. For server changes, restore the previous `cupsd.conf`, reload CUPS, and verify with `lpstat -r` and logs.

Do not restore stale files over a live production print server unless you know no one else changed CUPS in the meantime.

## Hands-on practice

Run these on a disposable VM or lab machine.

1. Install or enable CUPS using your distribution's package and service tools.
2. Capture `systemctl status cups --no-pager`, `lpstat -r`, `lpstat -t`, and the last 30 lines of the CUPS error log.
3. Create or inspect a test queue. If no printer is available, use a driverless network printer in a lab or stop after read-only inspection.
4. Toggle the queue between accepting and rejecting jobs, then return it to the original state.
5. Submit a one-line test file with `lp` or explain why you skipped printing.
6. Write a short handoff note with the queue name, device URI, service state, change made, verification result, and rollback command.
