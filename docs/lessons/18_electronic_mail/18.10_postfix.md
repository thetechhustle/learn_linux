### 18.10 Postfix: The Easy and Efficient MTA

Postfix is a mail transfer agent, or MTA, that accepts mail from local
programs, submits outbound mail to other mail servers, and can receive inbound
mail for local domains. It replaced Sendmail on many Linux systems because its
configuration is easier to reason about and its internal services are separated
into smaller, purpose-built processes.

For an administrator, the goal is not just "make Postfix run." The goal is to
know what role the host is supposed to play, prove how Postfix is configured,
test mail flow without creating an open relay, and leave enough evidence for
the next person who has to troubleshoot delivery.

!!! abstract "What you will learn"
    - Identify whether a Postfix host is sending local mail, relaying through a
      smarthost, or receiving mail for a domain.
    - Inspect the key Postfix files and query active settings with `postconf`.
    - Apply a small configuration change with validation, reload, and rollback
      steps.
    - Use logs and queue commands to troubleshoot common delivery failures.

!!! warning "Avoid becoming an open relay"
    Never expose a Postfix server to the Internet with permissive relay rules.
    A server that accepts mail from anyone and forwards it anywhere will be
    abused quickly, damage the domain's reputation, and may be blocked by other
    mail systems.

## The moving parts

Postfix configuration lives mostly under `/etc/postfix/`. Two files matter most
on a typical Linux system:

- `/etc/postfix/main.cf`: global configuration such as host name, domains,
  relay policy, TLS settings, mailbox delivery, and relay host.
- `/etc/postfix/master.cf`: service definitions, including which Postfix
  services listen on which ports and which helper programs they run.

You will also see queue directories under `/var/spool/postfix/`, service units
managed by `systemd`, and mail logs in the distribution's normal logging
location. Debian and Ubuntu systems often log mail events in `/var/log/mail.log`.
RHEL-family systems often send them to `/var/log/maillog` or the journal.

Query active settings with `postconf` instead of relying only on what you see in
the file:

```console
$ postconf -n
myhostname = mail.example.com
mydestination = $myhostname, localhost.$mydomain, localhost
relayhost = [smtp.example.net]:587
```

`postconf -n` prints non-default settings. `postconf parameter_name` prints a
specific setting, including defaults.

```console
$ postconf mynetworks
mynetworks = 127.0.0.0/8 [::1]/128
```

## Choose the host's role

Start every Postfix change by naming the role. The same package can be used in
very different ways.

| Role | Typical behavior | Settings to inspect |
| --- | --- | --- |
| Local-only sender | System jobs send mail to local accounts or an admin address | `inet_interfaces`, `mydestination`, aliases |
| Outbound relay client | Applications send through an upstream mail provider | `relayhost`, `smtp_sasl_auth_enable`, TLS settings |
| Inbound domain server | The host receives mail for one or more domains | `mydestination`, `virtual_mailbox_domains`, DNS MX records |
| Internal relay | Trusted hosts send mail through it | `mynetworks`, `smtpd_relay_restrictions`, firewall rules |

Be conservative with `mynetworks`. It defines clients that Postfix may trust for
relay decisions. A single broad network such as `10.0.0.0/8` might be correct in
a private lab, but it is usually too wide for production.

## Install and inspect Postfix

On Debian or Ubuntu:

```console
$ sudo apt update
$ sudo apt install postfix
```

On RHEL-family systems:

```console
$ sudo dnf install postfix
```

Then inspect before changing anything:

```console
$ systemctl status postfix --no-pager
$ postconf -n
$ sudo postqueue -p
$ journalctl -u postfix --since "30 minutes ago" --no-pager
```

If the service is running but messages are not leaving, the queue and logs are
usually more useful than the service status.

## Configure outbound relay through a smarthost

Many servers should not deliver mail directly to the Internet. Cloud providers
often block outbound TCP/25, and new mail servers have poor reputation. A common
safer pattern is to relay through a mail provider on port 587 with
authentication and TLS.

Example `/etc/postfix/main.cf` settings:

```ini
myhostname = app01.example.com
myorigin = /etc/mailname
inet_interfaces = loopback-only
mydestination = $myhostname, localhost.$mydomain, localhost
relayhost = [smtp.example.net]:587

smtp_tls_security_level = encrypt
smtp_sasl_auth_enable = yes
smtp_sasl_password_maps = hash:/etc/postfix/sasl_passwd
smtp_sasl_security_options = noanonymous
```

The square brackets around the relay host tell Postfix not to look up MX records
for that name. They are commonly used when you are targeting a specific
submission server.

Store provider credentials in a root-readable file:

```console
$ sudo sh -c 'printf "[smtp.example.net]:587 user@example.com:REDACTED-PASSWORD\n" > /etc/postfix/sasl_passwd'
$ sudo chmod 600 /etc/postfix/sasl_passwd
$ sudo postmap /etc/postfix/sasl_passwd
```

Do not commit `sasl_passwd` or paste real credentials into tickets, pull
requests, chat, or lab notes.

## Validate, reload, and test

Postfix can check its own configuration before you reload it:

```console
$ sudo postfix check
$ sudo systemctl reload postfix
```

Send a small test message from the host:

```console
$ printf 'Subject: postfix test\n\nTest from app01\n' | sendmail admin@example.com
```

Then watch the logs and queue:

```console
$ journalctl -u postfix --since "5 minutes ago" --no-pager
$ sudo postqueue -p
```

A healthy outbound test normally shows a queue ID, a connection to the relay,
and a successful delivery status such as `status=sent`.

## Queue operations

Postfix queue commands are part of daily mail operations:

```console
$ sudo postqueue -p          # list queued messages
$ sudo postqueue -f          # ask Postfix to retry queued delivery
$ sudo postsuper -r ALL      # requeue all messages after a config fix
$ sudo postsuper -d QUEUEID  # delete one queued message
```

Be careful with bulk deletes. A large queue can contain important delayed mail,
spam, broken application output, or all three. Identify the pattern before
removing messages.

## Troubleshooting patterns

Start with the queue ID from the log. It connects acceptance, routing, retry,
and final delivery messages.

Common failures include:

- `Connection timed out`: firewall, provider block, remote outage, or wrong
  relay host/port.
- `SASL authentication failed`: wrong username/password, missing `postmap`, or
  provider policy change.
- `Relay access denied`: the client is not trusted to relay or the relay host
  rejected the destination.
- `Host or domain name not found`: DNS problem, misspelled domain, or resolver
  issue on the mail server.
- `TLS is required, but was not offered`: TLS setting mismatch or wrong server
  port.

Use focused checks:

```console
$ postconf relayhost smtp_tls_security_level smtp_sasl_auth_enable
$ sudo postmap -q '[smtp.example.net]:587' /etc/postfix/sasl_passwd
$ nc -vz smtp.example.net 587
$ journalctl -u postfix --since "15 minutes ago" --no-pager
```

## Hands-on practice

Use a disposable VM or lab container. Do not run this against a production mail
server unless you already have a change window and rollback plan.

1. Install Postfix or inspect an existing lab installation.
2. Record `postconf -n`, `systemctl status postfix --no-pager`, and
   `postqueue -p`.
3. Configure a local-only sender by setting `inet_interfaces = loopback-only`.
4. Run `sudo postfix check`, reload Postfix, and send one local test message.
5. Find the queue ID in the logs and explain whether delivery succeeded,
   deferred, or bounced.
