# 18.3 The SMTP Protocol

SMTP, the Simple Mail Transfer Protocol, is the main protocol mail servers use to submit and transfer email. If you administer Linux systems that send alerts, password resets, application mail, or user mail, you need to understand enough SMTP to read a log, interpret a rejection, and prove where the message stopped.

SMTP is not a single "send mail" button. It is a conversation between systems. One side connects, identifies itself, proposes a sender, proposes one or more recipients, transfers the message data, and receives status codes at each step.

!!! abstract "What you will learn"
    - Explain the difference between SMTP submission and server-to-server SMTP transfer.
    - Recognize the common SMTP commands used during a mail transaction.
    - Interpret common SMTP status codes.
    - Use safe read-only tests to investigate delivery problems.
    - Identify where TLS, authentication, DNS, and policy checks fit into SMTP troubleshooting.

!!! success "Operator principle"
    SMTP troubleshooting is transcript work. The important question is not "did the app send mail?" but "which SMTP server accepted, deferred, rejected, or lost responsibility for the message?"

## SMTP roles and ports

SMTP appears in two common places:

- **Message submission:** a user or application submits outbound mail to a trusted service, usually on TCP port 587 with authentication and STARTTLS.
- **Message transfer:** one mail server sends mail to another mail server, usually on TCP port 25.

Some services also use TCP port 465 for implicit TLS submission. Port 25 is often blocked for ordinary cloud or residential systems because unauthenticated SMTP can be abused for spam.

The distinction matters:

- If an application cannot authenticate to the submission service, fix application credentials or submission settings.
- If a remote recipient server rejects mail on port 25, investigate routing, DNS, policy, reputation, or content.
- If the local system queues mail because it cannot reach a next hop, investigate network reachability, DNS, or relay configuration.

## A basic SMTP conversation

A simplified SMTP transaction looks like this:

```text
S: 220 mail.example.net ESMTP Postfix
C: EHLO app01.example.com
S: 250-mail.example.net
S: 250-STARTTLS
S: 250 AUTH PLAIN LOGIN
C: MAIL FROM:<alerts@example.com>
S: 250 2.1.0 Ok
C: RCPT TO:<admin@example.org>
S: 250 2.1.5 Ok
C: DATA
S: 354 End data with <CR><LF>.<CR><LF>
C: From: alerts@example.com
C: To: admin@example.org
C: Subject: test
C:
C: Test message.
C: .
S: 250 2.0.0 Ok: queued as 4F2A812345
C: QUIT
S: 221 2.0.0 Bye
```

The server responses are the evidence. The `250 ... queued as ...` line means that server accepted responsibility for the message. If the next system later rejects delivery, the accepting server should generate a bounce or keep retrying according to its queue policy.

## Common SMTP commands

You do not need to memorize the whole protocol to troubleshoot common problems, but these commands appear constantly in logs and transcripts:

- **EHLO:** starts an extended SMTP session and lets the server advertise capabilities.
- **HELO:** older greeting command without extended capability negotiation.
- **STARTTLS:** upgrades the connection to TLS when the server supports it.
- **AUTH:** authenticates a submitting user or application.
- **MAIL FROM:** sets the envelope sender.
- **RCPT TO:** sets an envelope recipient.
- **DATA:** starts the message headers and body.
- **RSET:** resets the current transaction without closing the connection.
- **QUIT:** ends the session.

The envelope sender and recipient are not always identical to the visible `From:` and `To:` headers. The envelope controls routing and bounce behavior; headers are part of the message content.

## Status codes

SMTP response codes are grouped by first digit:

- **2xx:** success
- **3xx:** more input needed
- **4xx:** temporary failure; retry later
- **5xx:** permanent failure; do not retry without a change

Common examples:

| Code | Meaning | Operator interpretation |
| --- | --- | --- |
| `220` | Service ready | The remote SMTP service accepted the connection. |
| `250` | Requested action completed | The command succeeded. |
| `354` | Start mail input | The server is ready for message data. |
| `421` | Service not available | Temporary server or connection problem. |
| `450` | Mailbox unavailable | Temporary delivery problem; retry may work. |
| `451` | Local processing error | Temporary server-side issue. |
| `452` | Insufficient storage | Temporary resource problem. |
| `550` | Mailbox unavailable or rejected | Permanent recipient, policy, or reputation failure. |
| `554` | Transaction failed | Often policy, spam, malware, or generic rejection. |

Always keep the text after the code. A `550` for "user unknown" is different from a `550` for SPF failure or IP reputation.

## TLS and authentication

Submission systems normally require authentication and TLS. A working SMTP connection can still fail if the client uses the wrong port, skips TLS, presents invalid credentials, or uses a sender address the service does not allow.

Useful questions:

- Is the client using port 587 or 465 for submission?
- Does the server advertise `STARTTLS` after `EHLO`?
- Does the server advertise `AUTH` only after TLS starts?
- Does the authenticated account have permission to send as the envelope sender?
- Is the application using the right username, password, token, or app password?

For server-to-server delivery on port 25, TLS may be opportunistic. Some environments require stricter TLS policy, but many internet deliveries still depend on graceful fallback and clear logging.

## Safe SMTP checks

Use read-only checks before sending test messages.

```bash
# Can the local host resolve recipient mail exchangers?
dig MX example.com

# Can the local host reach a remote SMTP service?
nc -vz mail.example.com 25

# What capabilities does the server advertise?
openssl s_client -starttls smtp -connect mail.example.com:25 -crlf
```

When using `openssl s_client`, you can type `EHLO test.example.com` after the connection is established to inspect advertised SMTP capabilities. Do this only against systems you are authorized to test.

For local MTA troubleshooting, start with logs and queues:

```bash
mailq
postqueue -p
journalctl -u postfix --since "30 minutes ago"
journalctl -u exim4 --since "30 minutes ago"
```

## Reading SMTP logs

Mail logs usually tell a story in pieces. A Postfix log, for example, may show:

- the local queue ID
- client or process that submitted the message
- sender address
- recipient address
- remote relay host
- delay timing
- SMTP response code
- final status such as `sent`, `deferred`, `bounced`, or `expired`

Look for lines tied together by the same queue ID.

```text
postfix/qmgr[1234]: 4F2A812345: from=<alerts@example.com>, size=842, nrcpt=1
postfix/smtp[1235]: 4F2A812345: to=<admin@example.org>, relay=mail.example.org[203.0.113.20]:25, delay=2.1, status=sent (250 2.0.0 accepted)
```

This means the local server handed the message to `mail.example.org`, and that remote server accepted it. If the recipient still cannot find the message, the next investigation belongs on the recipient side: filtering, mailbox delivery, or client retrieval.

## Common failure patterns

**Authentication failure during submission**

The app never successfully handed mail to the relay. Check credentials, port, TLS mode, sender authorization, and rate limits.

**Connection timeout to port 25**

The local server cannot reach the destination or relay. Check firewall policy, cloud-provider outbound SMTP restrictions, DNS, routing, and the next-hop hostname.

**Temporary 4xx deferral**

The message may remain queued and retry. Check the exact reason: greylisting, DNS failure, remote resource issue, or temporary reputation policy.

**Permanent 5xx rejection**

Do not keep retrying blindly. Read the rejection text. It may point to a bad recipient, blocked sender, failed SPF/DKIM/DMARC alignment, malware, spam policy, or malformed message.

**Accepted but not visible**

If the remote server returned success, inspect the recipient side: spam folder, quarantine, mailbox quota, delivery rules, forwarding, aliases, and client sync.

## Envelope versus headers

SMTP uses envelope addresses for routing:

- `MAIL FROM:<bounce@example.com>`
- `RCPT TO:<admin@example.org>`

The visible message contains headers:

- `From: Alerts <alerts@example.com>`
- `To: Admin <admin@example.org>`
- `Subject: Disk alert`

These can differ. Mailing lists, bounce handlers, forwarding systems, and transactional mail providers often use envelope senders that are different from the visible `From:` header. This matters for bounce handling and DMARC alignment.

## Hands-on practice

Use a lab host or a system you are authorized to inspect.

1. Look up MX records for a test domain:

   ```bash
   dig MX example.com
   ```

2. Check whether a mail server is reachable:

   ```bash
   nc -vz mail.example.com 25
   ```

3. Inspect the server's advertised SMTP capabilities:

   ```bash
   openssl s_client -starttls smtp -connect mail.example.com:25 -crlf
   ```

   Then type:

   ```text
   EHLO lab.example.com
   QUIT
   ```

4. On a local mail server, inspect the queue and recent logs:

   ```bash
   mailq
   journalctl -u postfix --since "30 minutes ago"
   ```

5. Write a short incident note that answers:

   - What server accepted the connection?
   - What capabilities did it advertise?
   - Was TLS available?
   - Was any message queued locally?
   - What evidence proves where responsibility moved next?
