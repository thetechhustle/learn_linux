### Email Configuration on Linux

!!! abstract "What you will learn"
    - Identify the host, DNS, queue, and TLS settings that make a Linux mail system work.
    - Separate outbound relay configuration from local mailbox and IMAP configuration.
    - Verify a mail change with logs, queue state, DNS records, and a controlled test message.

!!! example "Field story"
    A small internal app can no longer send password reset mail after being moved to a new subnet. The app logs only say "connection timed out." Your job is to prove whether the failure is local Postfix configuration, DNS, firewall egress, relay authentication, or recipient-side rejection.

!!! success "Operator principle"
    Configure mail in layers: identity, DNS, transport, authentication, delivery, then monitoring. A change is not complete until a test message leaves the queue and the logs explain the delivery path.

## Start with the mail role

Do not install every mail component by habit. First decide what the host is supposed to do.

| Role | Typical software | Main question |
| --- | --- | --- |
| Send-only application host | Postfix, nullmailer, msmtp | What relay should receive outbound mail? |
| Internet-facing mail exchanger | Postfix or Exim | What domains does this host accept for? |
| Local mailbox server | Dovecot plus an MTA | Where are messages stored and how do users read them? |
| Filtering gateway | MTA plus spam and policy tools | What mail is accepted, rejected, tagged, or forwarded? |

Most Linux servers should be send-only clients that relay through a managed mail service. Running an Internet-facing mailbox server also requires DNS, reputation, abuse handling, backups, patching, and monitoring.

## Collect the current evidence

Run these read-only checks before changing configuration:

```bash
hostname --fqdn
systemctl status postfix --no-pager
postconf -n
mailq
journalctl -u postfix -n 80 --no-pager
```

On systems that use Exim or Sendmail, replace the service and configuration commands with the local MTA's tools:

```bash
systemctl status exim4 --no-pager
exim -bP | head
mailq
```

Record the current hostname, active MTA, relay settings, queue length, and the latest delivery errors. This becomes your rollback and comparison note.

## Configure outbound relay mail

A send-only Postfix host usually needs only an identity, a relay, and credentials. On Debian or Ubuntu, the main file is `/etc/postfix/main.cf`; on Red Hat-family systems it is also commonly `/etc/postfix/main.cf`.

Common outbound settings look like this:

```ini
myhostname = app01.example.com
myorigin = /etc/mailname
inet_interfaces = loopback-only
mydestination = localhost
relayhost = [smtp.example.net]:587
smtp_tls_security_level = encrypt
smtp_sasl_auth_enable = yes
smtp_sasl_password_maps = hash:/etc/postfix/sasl_passwd
smtp_sasl_security_options = noanonymous
```

The square brackets around `smtp.example.net` tell Postfix to use that exact relay host instead of looking up MX records for the relay domain.

Store relay credentials in a root-readable file:

```bash
sudo install -m 0600 /dev/null /etc/postfix/sasl_passwd
sudoedit /etc/postfix/sasl_passwd
sudo postmap /etc/postfix/sasl_passwd
sudo systemctl reload postfix
```

The file usually contains a line like this:

```text
[smtp.example.net]:587 app01@example.com:REPLACE_WITH_RELAY_TOKEN
```

Never commit relay credentials to a repository or paste them into tickets. Rotate the token if it has been exposed.

## Configure inbound mail only when required

If the server must receive mail for a domain, configure DNS and acceptance rules before opening it to the Internet.

DNS records normally include:

- `MX` record pointing the domain to the mail exchanger.
- `A` or `AAAA` record for the mail exchanger name.
- `PTR` reverse DNS that matches the sending identity when possible.
- `SPF` policy listing authorized senders.
- `DKIM` public key if outbound signing is enabled.
- `DMARC` policy that tells receivers how to handle SPF and DKIM alignment failures.

Postfix must also know which domains it accepts. For a simple lab domain:

```ini
myhostname = mail.example.com
mydomain = example.com
mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain
inet_interfaces = all
```

Reload, then verify that port 25 is listening only where you expect:

```bash
sudo postfix check
sudo systemctl reload postfix
ss -ltnp | grep ':25'
```

Be careful with `inet_interfaces = all` on a real network. An exposed MTA without relay restrictions, spam controls, and monitoring can become an abuse problem quickly.

## Add mailbox access with Dovecot

Postfix receives or relays mail. Dovecot lets users read mail over IMAP and can also provide local delivery integration. Keep those responsibilities separate while troubleshooting.

Typical Dovecot checks:

```bash
systemctl status dovecot --no-pager
doveconf -n
ss -ltnp | grep -E ':(143|993)\b'
```

A simple IMAP-only configuration might include:

```ini
protocols = imap
mail_location = mbox:~/mail:INBOX=/var/mail/%u
ssl = required
```

Prefer IMAP over POP3 for most modern environments, and require TLS before offering mailbox access on any untrusted network.

## Send a controlled test

After a configuration change, validate with a small message and the logs:

```bash
printf 'Subject: mail test\n\nPostfix test from app01\n' | sendmail -v you@example.com
mailq
journalctl -u postfix -n 80 --no-pager
```

Successful delivery should show the message accepted, assigned a queue ID, connected to the next hop, and removed from the queue. A message that stays queued is not automatically a failure, but it needs an explanation in the log.

Useful DNS and connectivity checks:

```bash
dig MX example.com
dig TXT example.com
openssl s_client -starttls smtp -connect smtp.example.net:587 -servername smtp.example.net
```

Use `swaks` in a disposable lab if it is installed; it gives clearer SMTP test output than a full mail client:

```bash
swaks --to you@example.com --server smtp.example.net --port 587 --tls
```

## Common failure patterns

| Symptom | Likely area | First check |
| --- | --- | --- |
| `Connection timed out` | Network path or firewall | `nc -vz smtp.example.net 587` |
| `Relay access denied` | Relay policy or authenticated sender | `postconf -n | grep -E 'relayhost|sasl'` |
| `Authentication failed` | Credential map or token | `/etc/postfix/sasl_passwd` and `postmap` output |
| Mail remains in queue | Remote deferral or local routing | `mailq` and queue ID log lines |
| Recipients mark mail as spam | DNS identity and content reputation | SPF, DKIM, DMARC, PTR, and bounce text |
| IMAP login works but inbox is empty | Mail storage path mismatch | `doveconf -n | grep mail_location` |

Postfix queue IDs are the fastest way to follow one message:

```bash
mailq
journalctl -u postfix --no-pager | grep QUEUE_ID
```

Replace `QUEUE_ID` with the actual ID from `mailq` or the first log line.

## Safer change workflow

1. Save current evidence: `postconf -n`, queue length, service state, and recent logs.
2. Change one layer at a time: relay, TLS, authentication, accepted domains, or mailbox access.
3. Validate syntax with `sudo postfix check` or the equivalent MTA command.
4. Reload instead of restarting when the MTA supports it.
5. Send one controlled test message and trace its queue ID.
6. Document the final delivery result, remaining queue state, and any DNS records still pending.

Avoid flushing a large production queue until you understand why mail is queued. `postqueue -f` can create a burst of retries and may worsen rate limiting.

## Hands-on practice

Use a disposable VM or container. Do not point a lab host at a production domain.

1. Install Postfix in local-only or send-only mode.
2. Capture `postconf -n`, `mailq`, and recent Postfix logs.
3. Configure a relay placeholder in `main.cf`, but use non-production credentials.
4. Run `sudo postfix check` and reload the service.
5. Send one test message to a controlled address or a local mailbox.
6. Trace the message with its queue ID and explain whether it was delivered, deferred, bounced, or rejected.
