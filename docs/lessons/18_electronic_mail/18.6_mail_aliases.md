# 18.6 Mail Aliases

Mail aliases let a mail system redirect one local address to another local
user, a group of users, or an external address. They are simple, old, and still
operationally important because many Linux systems send important local mail to
addresses such as `root`, `postmaster`, `abuse`, or `webmaster`.

If aliases are wrong, operational mail disappears. If they are too broad, alerts
go to the wrong people. If they create loops, the queue can fill quickly.

!!! abstract "What you will learn"
    - Explain what a mail alias does and what it does not do.
    - Inspect local aliases safely before changing them.
    - Update `/etc/aliases` and rebuild the alias database.
    - Test alias expansion and delivery paths.
    - Recognize alias loops, stale recipients, and distribution-list risks.

## What an Alias Does

An alias maps one recipient name to one or more destinations. On a traditional
Unix-style system, aliases commonly live in `/etc/aliases`.

Example:

```text
root: admin@example.com
postmaster: root
webmaster: alice, bob
```

That means:

- mail addressed to local `root` is forwarded to `admin@example.com`
- mail addressed to local `postmaster` follows the `root` alias
- mail addressed to local `webmaster` goes to local users `alice` and `bob`

Aliases are not the same as DNS records, mailbox accounts, or application-level
group membership. They are local MTA routing rules.

## Where Aliases Fit

A message has already reached your MTA when aliases matter. The MTA is deciding
what local recipient or next destination should receive it.

Common alias uses:

| Alias | Typical purpose |
| --- | --- |
| `root` | Send system mail to a monitored administrator mailbox |
| `postmaster` | Required contact role for mail-system problems |
| `abuse` | Security and abuse reporting address |
| `webmaster` | Website contact role |
| `devops` | Internal operational distribution address |
| `alerts` | Monitoring notifications |

Some organizations handle these addresses in a directory, SaaS email platform,
or mailing-list manager instead. Even then, local Linux aliases still matter for
system-generated mail on servers.

## Inspect Current Aliases

Start read-only:

```bash
sudo sed -n '1,200p' /etc/aliases
ls -l /etc/aliases /etc/aliases.db 2>/dev/null || true
```

Look for:

- required role accounts such as `postmaster`
- aliases pointing to former employees
- aliases that point to unmonitored local users
- aliases that forward sensitive mail to personal accounts
- comments explaining ownership and purpose

If you are using Postfix, inspect alias-related configuration:

```bash
postconf alias_maps alias_database
postconf local_recipient_maps
```

On a Sendmail-style system, `newaliases` is the classic command that rebuilds
the alias database. Postfix supports the same command for compatibility.

## Change Aliases Safely

Before editing, preserve a timestamped copy:

```bash
sudo cp -a /etc/aliases "/etc/aliases.$(date +%Y%m%d-%H%M%S).bak"
```

Edit the file:

```bash
sudoedit /etc/aliases
```

Add or update entries:

```text
root: admin@example.com
postmaster: root
abuse: security@example.com
alerts: oncall@example.com, admin@example.com
```

Then rebuild the database:

```bash
sudo newaliases
```

If `newaliases` reports an error, fix the file before assuming mail delivery is
healthy. A malformed alias file can leave your intended change inactive.

!!! warning "Avoid blind copy-paste on production mail hosts"
    Alias changes affect real delivery. Confirm owners, destinations, and
    rollback before forwarding security, billing, monitoring, or root mail.

## Test Expansion

Use your MTA's tooling when available.

Postfix can query maps:

```bash
postmap -q root hash:/etc/aliases
postmap -q postmaster hash:/etc/aliases
postmap -q alerts hash:/etc/aliases
```

For a direct smoke test, send a low-risk message:

```bash
printf 'Alias test from %s\n' "$(hostname)" | mail -s "alias test" root
```

Then inspect logs:

```bash
sudo tail -n 100 /var/log/mail.log
sudo tail -n 100 /var/log/maillog
journalctl -u postfix --since "10 minutes ago"
```

Search for the queue ID and final recipient. A successful test should show where
the message was delivered or forwarded.

## Avoid Alias Loops

Aliases can point to other aliases. That is useful, but it can create loops.

Bad example:

```text
root: postmaster
postmaster: root
```

Another risky pattern:

```text
alerts: oncall
oncall: alerts
```

Most MTAs detect loops eventually, but detection does not make the configuration
good. It still creates queue noise and hides the intended owner.

When aliases chain through several names, document why:

```text
# System mail goes through oncall so the rotation can change in one place.
root: oncall
postmaster: oncall
oncall: sre-primary@example.com, sre-backup@example.com
```

## Local Users, External Addresses, and Pipes

Aliases can usually target:

- local usernames
- external email addresses
- files
- commands or pipes
- include files

Command and file deliveries are powerful and risky. They can become privilege,
data-loss, or injection hazards if misused.

Examples you might see:

```text
backup-report: /var/log/backup-mailbox
support-team: :include:/etc/mail/support-team
automation: "|/usr/local/bin/process-mail"
```

Before approving command or file aliases, answer:

- Which user runs the command?
- Can message content become shell input?
- Is the target writable by untrusted users?
- Are failures logged?
- Is there a safer mailbox or queue-based integration?

For most administrative aliases, plain mailbox or forwarding destinations are
safer than command delivery.

## Virtual Aliases

Local `/etc/aliases` is not the whole story on every mail server. Hosted domains
often use virtual alias maps.

Postfix examples:

```bash
postconf virtual_alias_maps
postmap -q info@example.com hash:/etc/postfix/virtual
```

A virtual alias maps a full address such as `info@example.com`, while
`/etc/aliases` commonly maps local names such as `root`. The exact behavior
depends on the MTA configuration, so verify the active maps instead of assuming
one file controls everything.

## Operational Checklist

Use this checklist when touching aliases:

1. Identify the MTA and active alias maps.
2. Back up the current alias file or map.
3. Confirm the destination owner and purpose.
4. Make the smallest change.
5. Rebuild the alias database.
6. Query the map or run an expansion test.
7. Send a low-risk test message.
8. Verify logs show the expected destination.
9. Record the change and rollback path.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Mail to `root` disappears | `root` alias, local mailbox path, mail logs |
| Alias change has no effect | forgot `newaliases`, wrong map, wrong host |
| Mail bounces with unknown user | local recipient validation, typo, virtual map mismatch |
| Queue fills after alias change | forwarding loop, remote delivery failure, bad command pipe |
| Some recipients get mail and others do not | external recipient bounce, group member typo, spam policy |
| Security reports go nowhere | stale `abuse` or `postmaster` destination |

Always prove the path with logs. The alias file says what should happen; the
mail log says what actually happened.

## Hands-on Practice

Use a lab VM or disposable mail container.

1. Inspect `/etc/aliases`.
2. Add a safe lab alias such as `lab-admin: root`.
3. Run `sudo newaliases`.
4. Query the alias if your MTA supports map queries.
5. Send a test message to the alias.
6. Find the queue ID and final destination in the mail log.
7. Restore the original alias file or remove the lab alias.
