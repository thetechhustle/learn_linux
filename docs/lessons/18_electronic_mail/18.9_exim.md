## 18.9 Exim: The Flexible Mail Transfer Agent

Exim is a full mail transfer agent (MTA). It accepts, routes, queues, and
delivers mail. It is especially common on Debian-derived systems and hosting
platforms because its routing and policy engine is highly configurable.

That flexibility is the reason operators like Exim and the reason it deserves
care. A small change in an access control list, router, or transport can affect
which messages are accepted, where they go, and whether the server becomes an
open relay.

!!! abstract "What you will learn"
    - Identify whether a Linux host is running Exim.
    - Recognize the major Exim configuration layers.
    - Inspect routing decisions, queues, and logs without changing mail flow.
    - Apply a safe change workflow for Exim configuration updates.
    - Avoid common relay, queue, and deliverability mistakes.

!!! warning "Do not experiment on a production mail host"
    Mail servers interact with real recipients, spam reputation systems, and
    authentication policy. Practice on a lab VM or container first. On a
    production host, capture evidence, back up configuration, test with
    read-only commands, and schedule changes deliberately.

## Where Exim fits

In a simple mail flow, Exim can play several roles:

- **Inbound MTA:** accepts mail for local domains over SMTP.
- **Outbound MTA:** sends locally generated mail to remote domains.
- **Submission relay:** accepts authenticated client mail and relays it onward.
- **Smarthost client:** sends all outbound mail through a provider relay.
- **Local delivery agent coordinator:** hands local mail to a mailbox, pipe,
  alias expansion, or delivery tool.

Many servers do not need to receive Internet mail directly. A web application
host, for example, might only need Exim to relay password reset and notification
mail through a trusted provider. That distinction matters because a receive
server, a submission server, and a smarthost client have different risk profiles.

## Confirm what is running

Start by identifying the package, daemon, and listening sockets:

```bash
command -v exim exim4
exim -bV 2>/dev/null || exim4 -bV
systemctl status exim4 --no-pager
systemctl status exim --no-pager
ss -ltnp | grep -E ':(25|465|587)\b'
```

Port meaning is conventional:

| Port | Common use | Operator question |
| --- | --- | --- |
| 25 | SMTP server-to-server delivery | Should this host accept Internet mail? |
| 465 | Implicit TLS submission | Is this intentionally enabled for clients? |
| 587 | Message submission | Is authentication required before relay? |

If the host only sends system mail, it may not need to listen on any public
address. If it does listen, verify the firewall, DNS, TLS, authentication, and
relay policy before calling the service healthy.

## Configuration layout

Exim installations vary by distribution.

On Debian and Ubuntu, the package is usually `exim4`. The main control file is:

```text
/etc/exim4/update-exim4.conf.conf
```

Depending on the selected mode, configuration may be generated from either a
split directory or a template:

```text
/etc/exim4/conf.d/
/etc/exim4/exim4.conf.template
/var/lib/exim4/config.autogenerated
```

Do not hand-edit the generated file under `/var/lib/exim4/`. Change the source
configuration, then regenerate:

```bash
sudo update-exim4.conf
sudo systemctl reload exim4
```

Other distributions or control panels may use paths such as:

```text
/etc/exim/exim.conf
/etc/exim.conf
```

Always confirm the active configuration before changing it:

```bash
exim -bP configure_file
exim -bP primary_hostname
exim -bP local_interfaces
exim -bP daemon_smtp_ports
```

## The Exim mental model

Exim processes messages through policy and routing stages. You do not need to
memorize every directive, but you should know the major building blocks.

| Component | Purpose | Example operator task |
| --- | --- | --- |
| ACLs | Decide what SMTP clients and messages are allowed | Require auth before relay |
| Routers | Decide where a message should go next | Send local domains to local delivery |
| Transports | Perform the delivery action | Deliver via SMTP, pipe, or mailbox |
| Authenticators | Verify SMTP client identity | Enable submission users |
| Retry rules | Decide when failed deliveries retry | Slow retries for remote failures |
| Rewrites | Adjust addresses when needed | Normalize local sender domains |

Most troubleshooting becomes easier once you ask two questions:

1. Did Exim accept the message?
2. If accepted, which router and transport did it choose?

## Inspect routing decisions

Use `-bt` to test how Exim would route an address:

```bash
exim -bt root
exim -bt user@example.com
exim -bt postmaster@your-domain.example
```

This does not send mail. It shows the selected routing path, aliases, and
delivery target. It is one of the safest first commands during an incident.

To test SMTP policy for a connecting host, use `-bh`:

```bash
exim -bh 203.0.113.10
```

That starts an interactive SMTP policy test as if the connection came from that
IP address. It is useful for checking whether ACLs would accept, reject, defer,
or require authentication.

## Inspect the queue

List queued messages:

```bash
exim -bp
```

Summarize the queue if `exiqsumm` is installed:

```bash
exim -bp | exiqsumm
```

Show details for a specific message:

```bash
exim -Mvh MESSAGE_ID
exim -Mvb MESSAGE_ID
exim -Mvl MESSAGE_ID
```

Those commands display headers, body, and delivery log for one queued message.
Use them carefully on shared systems because message bodies can contain private
data.

Force delivery of one message:

```bash
sudo exim -M MESSAGE_ID
```

Remove one message only when you are sure it should be discarded:

```bash
sudo exim -Mrm MESSAGE_ID
```

Avoid blindly flushing a large queue with `exim -qff`. If the underlying problem
is DNS, credentials, rate limiting, or a bad route, a forced flush can produce a
burst of failures or worsen provider reputation.

## Read the logs

Common Debian paths:

```text
/var/log/exim4/mainlog
/var/log/exim4/rejectlog
/var/log/exim4/paniclog
```

Common non-Debian paths:

```text
/var/log/exim/main.log
/var/log/exim/reject.log
/var/log/exim/panic.log
```

Systemd may also have service logs:

```bash
journalctl -u exim4 --since "1 hour ago" --no-pager
journalctl -u exim --since "1 hour ago" --no-pager
```

Useful patterns:

```bash
sudo grep -i 'rejected' /var/log/exim4/rejectlog | tail -n 20
sudo grep -i 'authentication failed' /var/log/exim4/mainlog | tail -n 20
sudo grep -i 'frozen' /var/log/exim4/mainlog | tail -n 20
sudo grep -i 'panic' /var/log/exim4/paniclog
```

The `paniclog` should normally be empty. Treat new entries there as important
until you understand them.

## Relay safety

The most dangerous Exim mistake is accepting mail from anyone to anywhere. That
is an open relay. It will be abused quickly.

For a public-facing server, relay policy should usually be:

- accept unauthenticated mail only for domains the server is responsible for
- require authentication for client submission
- relay outbound mail only for authenticated users or trusted local sources
- reject or defer suspicious clients early enough to protect the queue

Check relay behavior from outside the trusted network when possible. A server
that looks safe from localhost might still be misconfigured on a public
interface.

## Smarthost configuration

Many small servers should not deliver directly to the Internet. Instead, they
relay outbound mail through a smarthost such as a mail provider, transactional
email service, or organization relay.

On Debian, `dpkg-reconfigure exim4-config` can set a smarthost profile:

```bash
sudo dpkg-reconfigure exim4-config
sudo update-exim4.conf
sudo systemctl reload exim4
```

Store provider credentials in the distribution-supported credential file, often:

```text
/etc/exim4/passwd.client
```

Then protect it:

```bash
sudo chown root:Debian-exim /etc/exim4/passwd.client
sudo chmod 640 /etc/exim4/passwd.client
```

Exact ownership can vary by distribution. Match the local package expectation
instead of copying permissions blindly.

## DNS and authentication dependencies

Exim can route mail, but DNS and authentication records determine whether other
systems trust it. For a domain that sends mail, inspect:

```bash
dig MX example.com
dig TXT example.com
dig TXT default._domainkey.example.com
dig TXT _dmarc.example.com
```

For direct delivery, the sending IP also needs correct reverse DNS and a
reputation history. If you cannot control reverse DNS, direct Internet delivery
may be the wrong design. Use a smarthost instead.

## Safe change workflow

Use this pattern for production changes:

1. Record the current evidence:

    ```bash
    exim -bV
    exim -bP configure_file
    exim -bp | head
    systemctl status exim4 --no-pager
    ```

2. Back up the configuration source:

    ```bash
    sudo cp -a /etc/exim4 /etc/exim4.backup.$(date +%Y%m%d-%H%M%S)
    ```

3. Make the smallest config change.

4. Regenerate and validate:

    ```bash
    sudo update-exim4.conf
    sudo exim -bV
    sudo exim -bt postmaster@your-domain.example
    ```

5. Reload, not restart, if a reload is sufficient:

    ```bash
    sudo systemctl reload exim4
    ```

6. Send one test message and inspect logs.

7. Keep watching the queue and `paniclog` for a short period after the change.

## Failure modes

| Symptom | Likely area | First evidence to collect |
| --- | --- | --- |
| Mail stuck in queue | DNS, remote rejection, route, credentials | `exim -bp`, `exim -Mvl MESSAGE_ID` |
| Users can receive but not send | Submission auth or relay ACL | `rejectlog`, `exim -bh CLIENT_IP` |
| Local aliases do not work | Alias router or alias file rebuild | `exim -bt aliasname` |
| Remote systems reject mail | SPF, DKIM, DMARC, reverse DNS, reputation | bounce text, DNS records, provider logs |
| Exim will not start | syntax, permissions, generated config | `systemctl status`, `paniclog`, `exim -bV` |
| Queue grows suddenly | spam, compromised account, remote outage | queue summary, logs by sender, auth failures |

## Hands-on practice

Run these on a disposable Debian or Ubuntu VM.

1. Install Exim:

    ```bash
    sudo apt update
    sudo apt install exim4
    ```

2. Capture version and config evidence:

    ```bash
    exim -bV
    exim -bP configure_file
    exim -bP daemon_smtp_ports
    ```

3. Test local routing without sending mail:

    ```bash
    exim -bt root
    exim -bt postmaster
    ```

4. Inspect the queue:

    ```bash
    exim -bp
    ```

5. Find the logs and explain which one you would check first for a rejected
   SMTP session.
