## Sub-Chapter 18.5: Message Privacy and Encryption

Mail privacy is not a single switch. A message can be encrypted while it crosses
the network, signed so the recipient can detect tampering, or encrypted end to
end so intermediate mail servers cannot read the content. Linux operators need
to know which protection is in use, what it proves, and what it does not prove.

!!! abstract "What you will learn"
    - Distinguish SMTP transport encryption from end-to-end message encryption.
    - Inspect whether a mail path advertises and uses TLS.
    - Explain when GnuPG, S/MIME, and digital signatures fit an email workflow.
    - Preserve private keys, message evidence, and logs without exposing secrets.
    - Troubleshoot common privacy failures without weakening mail delivery.

!!! warning "Privacy boundary"
    STARTTLS protects one SMTP hop at a time. It does not hide message content
    from the sending server, receiving server, mailbox provider, backups,
    indexes, or anyone with access to the mailbox. Use end-to-end encryption
    when the mail servers themselves should not be able to read the message.

## The Three Privacy Layers

Email privacy usually combines three different controls:

| Layer | What it protects | Common tools | What to verify |
| --- | --- | --- | --- |
| Transport encryption | SMTP, IMAP, or submission traffic while it crosses a network hop | TLS, STARTTLS, MTA-STS, DANE TLSA | The remote service offers TLS and the certificate validates |
| Message integrity | Whether a message was changed and who signed it | OpenPGP signatures, S/MIME signatures, DKIM | The signature validates against the expected key or domain |
| Message confidentiality | The readable body and attachments | OpenPGP encryption, S/MIME encryption | Only intended recipients have usable private keys |

Do not treat these layers as interchangeable. TLS is usually expected for mail
transport, but it does not replace end-to-end encryption for confidential
content. DKIM helps prove domain-level message integrity, but it does not prove
the human sender intended every word in the message.

## Inspect SMTP Transport Encryption

Use read-only checks first. The goal is to prove what the server offers before
changing any mail configuration.

```bash
dig +short MX example.com
```

Pick the lowest-preference MX host from the output, then inspect its SMTP banner
and STARTTLS capability:

```bash
openssl s_client -starttls smtp -connect mail.example.com:25 -servername mail.example.com </dev/null
```

Useful signs in the output include:

- `Verify return code: 0 (ok)` means OpenSSL could validate the certificate
  chain with the local trust store.
- `subject=` and `issuer=` show which certificate was presented.
- `notBefore` and `notAfter` show the certificate validity window.
- `STARTTLS` in an SMTP capability listing means the server advertises
  opportunistic TLS for that hop.

For mail submission, check port 587 instead of port 25:

```bash
openssl s_client -starttls smtp -connect smtp.example.com:587 -servername smtp.example.com </dev/null
```

For IMAP mailbox access, check the TLS-wrapped service on port 993:

```bash
openssl s_client -connect imap.example.com:993 -servername imap.example.com </dev/null
```

!!! tip "Certificate names"
    The certificate normally needs to match the mail host you connected to, not
    the recipient domain. If `example.com` publishes `mail.provider.net` as its
    MX, the certificate can legitimately identify `mail.provider.net`.

## Read Received Headers for TLS Evidence

After delivery, the message's `Received` headers often show whether TLS was used
between MTAs. Look for phrases such as `with ESMTPS`, `version=TLS1.3`, or
`cipher=...`.

```text
Received: from app01.example.net (app01.example.net [192.0.2.10])
        by mx.example.com with ESMTPS id 12345
        (version=TLS1.3 cipher=TLS_AES_256_GCM_SHA384);
        Tue, 12 May 2026 12:00:00 +0000
```

This is evidence, not a guarantee about every hop. Headers can be added by each
server in the path, and untrusted upstream systems can write misleading lines.
Trust the headers added by systems you operate or by providers you trust.

## End-to-End Encryption Choices

End-to-end email encryption protects the message body and attachments before the
message is handed to SMTP. The receiving MTA can still see routing metadata such
as sender, recipient, subject in many workflows, message size, and timestamps.

OpenPGP is common in command-line and technical communities. GnuPG is the usual
Linux implementation:

```bash
gpg --list-keys
gpg --fingerprint alice@example.com
```

Before sending confidential mail, verify the recipient key fingerprint through a
separate trusted channel. Do not trust a public key just because it appeared in
an email attachment or search result.

Encrypt a file for a recipient:

```bash
gpg --encrypt --recipient alice@example.com report.txt
```

Sign a file so a recipient can verify who produced it:

```bash
gpg --clearsign release-notes.txt
```

S/MIME is common in enterprise environments because certificates can be issued
and managed through organizational certificate authorities. It provides signing
and encryption too, but it depends on certificate lifecycle management: issuing,
renewal, revocation, and private-key protection.

## Private-Key Handling

Private keys are operational secrets. A compromised key can expose old encrypted
mail if the attacker also has archived ciphertext, and it can let an attacker
impersonate the key owner.

Use these habits:

- Protect private keys with strong passphrases.
- Keep revocation certificates or recovery procedures in a separate secure
  location.
- Remove keys from shared lab machines after testing.
- Rotate or revoke keys when a laptop, workstation, or backup is lost.
- Never paste private keys into tickets, chat, CI logs, or documentation.

For GnuPG, inspect secret keys without printing secret key material:

```bash
gpg --list-secret-keys --keyid-format long
```

## Common Failure Patterns

| Symptom | Likely cause | First checks |
| --- | --- | --- |
| Remote SMTP server does not advertise STARTTLS | Legacy server, policy choice, filtering proxy, or wrong host | Re-check MX target, test port 25 and 587, inspect provider docs |
| TLS certificate mismatch | MX host differs from recipient domain, stale certificate, missing SNI | Use `-servername`, inspect `subject` and SANs, verify MX records |
| Encrypted message cannot be opened | Wrong recipient key, expired key, missing private key, broken passphrase workflow | Check recipient list, key expiration, and local secret-key inventory |
| Signature shows unknown trust | Public key is present but not verified | Compare fingerprints through a trusted channel |
| Users forward confidential mail unencrypted | Encryption policy depends on user behavior only | Add client defaults, training, or gateway rules where appropriate |

## Safer Change Workflow

When changing mail privacy settings, separate policy from delivery:

1. Capture current evidence: MX records, TLS test output, mail logs, and a sample
   message header.
2. Decide whether the change affects inbound SMTP, outbound SMTP, submission,
   IMAP, or end-user message encryption.
3. Test on a non-production domain, mailbox, or staging relay when possible.
4. Keep rollback details ready: old certificate path, old Postfix or Exim
   setting, old DNS record, and the reload command.
5. Send a test message and inspect both logs and message headers after delivery.

!!! warning "Do not break mail to enforce privacy blindly"
    Strict TLS policies such as MTA-STS or DANE can improve security, but bad DNS,
    expired certificates, or mismatched names can cause delivery failures. Roll
    out strict policies only after monitoring shows the basic TLS path is stable.

## Hands-On Practice

Use a disposable VM, test mailbox, or public test domain. Do not send real
confidential content during the lab.

1. Pick a domain and identify its MX hosts.

   ```bash
   dig +short MX example.com
   ```

2. Test STARTTLS on one MX host.

   ```bash
   openssl s_client -starttls smtp -connect mail.example.com:25 -servername mail.example.com </dev/null
   ```

3. Save the certificate subject, issuer, expiration date, and verify return code
   in your lab notes.

4. Create a temporary GnuPG key in a disposable environment, then list its
   fingerprint.

   ```bash
   gpg --quick-generate-key "Lab User <lab@example.com>" default default 1d
   gpg --fingerprint lab@example.com
   ```

5. Encrypt and decrypt a small test file locally.

   ```bash
   printf 'lab message\n' > message.txt
   gpg --encrypt --recipient lab@example.com message.txt
   gpg --decrypt message.txt.gpg
   ```

6. Remove the temporary lab key when finished.

   ```bash
   gpg --delete-secret-and-public-key lab@example.com
   ```
