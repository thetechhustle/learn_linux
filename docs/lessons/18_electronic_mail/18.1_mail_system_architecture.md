# 18.1 Mail System Architecture

Email is a chain of cooperating systems. A user sees a compose window and an inbox, but a Linux administrator has to understand what happens between those two points: message submission, queueing, DNS lookup, transport, filtering, local delivery, mailbox storage, and client retrieval.

This lesson gives you the architecture map you need before touching Postfix, Exim, Sendmail, aliases, spam controls, or mailbox configuration. The names matter because each part leaves different evidence when mail is delayed, rejected, misrouted, or silently filtered.

!!! abstract "What you will learn"
    - Identify the major components in a mail system.
    - Explain the difference between submission, transfer, delivery, storage, and retrieval.
    - Trace a message through the mail path using logs, queues, headers, and DNS.
    - Recognize where common failures occur.

!!! success "Operator principle"
    Troubleshoot email by locating the handoff that failed. Do not start by changing the MTA configuration until you know whether the problem is generation, submission, routing, remote acceptance, local delivery, mailbox access, or filtering.

## The mail system at a glance

A typical message path looks like this:

```text
sender's mail client or application
  -> submission service
  -> outbound mail transfer agent
  -> DNS lookup for the recipient domain
  -> recipient domain's mail transfer agent
  -> filtering and local delivery
  -> mailbox store
  -> recipient's mail client
```

The path can be shorter for local mail and more complicated for enterprise mail, but the main roles stay recognizable.

## Mail User Agent

The **Mail User Agent (MUA)** is the program a person uses to read or send mail. Graphical examples include Thunderbird, Apple Mail, Outlook, and webmail. Terminal examples include `mail`, `mailx`, `mutt`, and `alpine`.

The MUA is not usually responsible for final routing across the internet. It normally submits a message to a server over an authenticated submission path.

Common evidence:

- the configured outgoing server
- authentication settings
- sender address
- saved sent message
- client-side error text

Useful questions:

- Did the client actually submit the message?
- Which account and sender address did it use?
- Did the client receive a local authentication or connection error?

## Mail Submission Agent

The **Mail Submission Agent (MSA)** accepts mail from users or applications. It commonly listens on port 587 with authentication and STARTTLS. Some systems also use port 465 for implicit TLS submission.

Submission is different from unauthenticated server-to-server SMTP on port 25. This distinction helps prevent open relay abuse.

Common evidence:

- authentication logs
- TLS negotiation errors
- application SMTP settings
- submission service logs
- rate-limit or policy rejections

For an application that sends password resets or alerts, the first useful check is often whether the app reached the submission service and whether the service accepted the message.

## Mail Transfer Agent

The **Mail Transfer Agent (MTA)** routes mail between systems. Postfix, Exim, and Sendmail are common Linux MTAs. The MTA decides whether to deliver locally, relay through another server, or send to the recipient domain's mail exchanger.

The MTA usually maintains a queue. A queued message is not always a failure; it may be waiting for DNS, network recovery, retry timing, or a remote server that temporarily deferred delivery.

Common evidence:

- queue ID
- sender and recipient
- next-hop server
- DNS lookup result
- SMTP response code
- retry schedule
- final bounce message

Useful commands vary by MTA, but these are common starting points:

```bash
mailq
postqueue -p
journalctl -u postfix --since "30 minutes ago"
journalctl -u exim4 --since "30 minutes ago"
```

The queue ID is one of your best anchors. Use it to connect the log line, the sender's complaint, the remote server response, and the eventual delivery or bounce.

## DNS and routing

Mail routing depends heavily on DNS. When a server needs to send mail to `user@example.com`, it looks up mail exchanger records for `example.com`.

Important records include:

- **MX:** tells senders which hosts accept mail for the domain.
- **A/AAAA:** maps mail hostnames to IP addresses.
- **PTR:** maps sending IP addresses back to names; many receivers care about reverse DNS.
- **SPF:** declares which systems may send mail for the domain.
- **DKIM:** signs messages so receivers can verify domain-controlled integrity.
- **DMARC:** tells receivers how to evaluate and report SPF/DKIM alignment.

Useful DNS checks:

```bash
dig MX example.com
dig A mail.example.com
dig AAAA mail.example.com
dig TXT example.com
dig -x 203.0.113.10
```

DNS can break delivery even when the MTA is healthy. If MX records point to the wrong host, SPF excludes the sending system, or reverse DNS is missing, remote servers may defer, reject, or spam-folder the message.

## Mail Delivery Agent

The **Mail Delivery Agent (MDA)** handles final local delivery after a message reaches the destination system. It may place the message into a mailbox, run delivery rules, call a filter, or hand the message to another local component.

Common delivery tools and concepts include:

- `procmail`
- `dovecot-lda`
- `maildrop`
- local aliases
- virtual mailbox maps
- sieve filtering
- mbox and Maildir storage

Common evidence:

- local delivery logs
- permission errors
- mailbox quota errors
- alias expansion results
- filter actions
- final mailbox path

If the remote system accepted the message but the user cannot find it, investigate delivery and filtering rather than transport.

## Mailbox storage

The mailbox store is where accepted mail rests until a user reads it. Two classic Unix storage formats are **mbox** and **Maildir**.

**mbox** stores many messages in one file. It is simple, but locking and corruption risks can matter on busy systems.

**Maildir** stores messages as separate files under directories such as `cur`, `new`, and `tmp`. It is common on modern servers because it handles concurrent access more cleanly.

You may also encounter mailbox storage hidden behind IMAP servers, hosted mail platforms, or webmail systems.

Common evidence:

- mailbox file or directory ownership
- filesystem permissions
- quota state
- message files under Maildir
- IMAP server logs

## Mail retrieval

After delivery, users usually retrieve mail through **IMAP**, **POP3**, or webmail.

- **IMAP** keeps mail on the server and synchronizes folders across clients.
- **POP3** downloads mail and may remove it from the server depending on client settings.
- **Webmail** often uses server-side APIs or IMAP behind the scenes.

Retrieval problems can look like delivery failures. A message may be in the mailbox while one client fails to display it due to sync, folder, cache, or filter settings.

Useful questions:

- Can another client see the message?
- Is the message in a different folder?
- Did a client-side rule move or delete it?
- Do IMAP logs show login or synchronization errors?

## Filtering and security layers

Modern mail systems usually include filtering before or during delivery. Filtering may scan for spam, malware, phishing, attachment policy, sender reputation, or domain authentication failures.

Common components include:

- SpamAssassin or other spam filters
- ClamAV or other malware scanners
- Rspamd
- Sieve rules
- hosted filtering gateways
- blocklists and allowlists

Filtering can accept a message and still keep it out of the visible inbox. That is why "the remote server accepted it" is not the same as "the recipient saw it."

## Local mail is still mail

Linux systems also send local mail. Cron jobs, monitoring scripts, package tools, and system services may send messages to `root` or local users. Even if a server never handles public internet mail, local mail still matters because it can carry operational alerts.

Common checks:

```bash
mail
mailq
ls -l /var/mail
ls -l /var/spool/mail
```

Many production teams forward local `root` mail to a monitored address through `/etc/aliases` or equivalent MTA configuration.

## A practical troubleshooting map

When someone says, "email is broken," classify the failure:

1. **Generation:** Did the app or user create the message?
2. **Submission:** Did the submission service accept it?
3. **Queueing:** Is the message stuck locally?
4. **Routing:** Did DNS point to the expected mail exchanger?
5. **Transport:** Did the remote server accept, defer, or reject it?
6. **Delivery:** Did the recipient system place it in a mailbox?
7. **Filtering:** Did spam, malware, or policy controls move or quarantine it?
8. **Retrieval:** Can the recipient's client see the delivered message?

Write down the evidence for the earliest failed step. That prevents blind changes and gives you a clean handoff if another team owns the next system.

## Hands-on practice

Use a lab machine or disposable VM.

1. Identify which MTA, if any, is installed:

   ```bash
   systemctl status postfix
   systemctl status exim4
   systemctl status sendmail
   ```

2. Check the local mail queue:

   ```bash
   mailq
   ```

3. Look up the MX records for a domain you control or a public example domain:

   ```bash
   dig MX example.com
   ```

4. Inspect TXT records and identify whether they look like SPF, DKIM, or DMARC policy:

   ```bash
   dig TXT example.com
   dig TXT _dmarc.example.com
   ```

5. Write a short note explaining which component would own each failure:

   - bad app SMTP password
   - MX points to the wrong provider
   - message stuck in local queue
   - remote server rejects for SPF failure
   - message accepted but placed in spam
   - mailbox is over quota
