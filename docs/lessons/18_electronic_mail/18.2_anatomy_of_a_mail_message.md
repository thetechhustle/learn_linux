### 18.2 Anatomy of a Mail Message

!!! abstract "What you will learn"
    - Identify the envelope, headers, body, and MIME parts of an email message.
    - Inspect a raw message safely without relying only on a mail client.
    - Use message structure to troubleshoot delivery, formatting, and attachment problems.

!!! example "Field story"
    A monitoring system says it sent an alert, but the on-call engineer never saw it. The mail queue shows the message left the host. Your next task is to inspect the raw message, confirm the sender and recipient evidence, and decide whether the failure is routing, filtering, formatting, or user expectation.

!!! success "Operator principle"
    Mail clients show a friendly version of a message. Operators troubleshoot from the raw message: envelope data, ordered headers, MIME boundaries, and the body exactly as the mail system handled them.

## Envelope versus message content

Email has two layers that are easy to confuse:

- The **SMTP envelope** is used during transport. It includes the sender given by `MAIL FROM` and each recipient given by `RCPT TO`. It is similar to the outside of a physical envelope.
- The **message content** is the data sent after the SMTP `DATA` command. It contains headers, a blank separator line, and the body.

The visible `From:` and `To:` headers are part of the message content. They do not have to match the SMTP envelope. This mismatch is normal for mailing lists, aliases, bounces, and automated systems, but it is also one reason spam and phishing investigations start with the full headers instead of the pretty mail-client view.

## Basic raw message format

A minimal message looks like this:

```text
From: Alice Example <alice@example.com>
To: Bob Example <bob@example.net>
Subject: Maintenance window
Date: Tue, 12 May 2026 09:30:00 -0400
Message-ID: <20260512093000.12345@example.com>

The database maintenance window starts at 22:00 UTC.
Please pause nonurgent imports before that time.
```

The first block is the header section. Each header field uses the form `Name: value`. A blank line ends the header section. Everything after that blank line is the body.

Common fields include:

- `From`: the author shown to the recipient.
- `To`, `Cc`: visible recipients.
- `Subject`: a short summary for humans and mail clients.
- `Date`: the author's timestamp, including time zone.
- `Message-ID`: a globally unique identifier generated by the sending system.
- `Reply-To`: where replies should go if different from `From`.
- `Received`: a trace line added by each mail server that handled the message.
- `Return-Path`: the bounce address recorded by the final delivery system.
- `Authentication-Results`: SPF, DKIM, and DMARC results recorded by a receiving system.

`Bcc` is different from `To` and `Cc`. Blind-copy recipients are usually present in the SMTP envelope but removed from the delivered message headers, so a recipient normally cannot see other `Bcc` recipients by reading the message.

## Header folding and ordering

Long header values can continue on the next line if the continuation line begins with a space or tab:

```text
Subject: This is a long maintenance notice that wraps across
 two physical lines in the raw message
```

When troubleshooting, preserve header order. `Received` headers are especially order-sensitive: the newest hop is usually at the top, and older hops appear lower in the message. Read them from bottom to top to reconstruct the path the message took.

Do not edit a raw message while collecting evidence. Copy it to a lab file, then inspect the copy.

## MIME parts

Plain-text mail is simple, but most real messages use MIME, or Multipurpose Internet Mail Extensions, to carry HTML, attachments, alternate text versions, and character-set metadata.

A multipart message declares a boundary string in the `Content-Type` header:

```text
From: reports@example.com
To: admin@example.net
Subject: Daily report
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="report-boundary"

--report-boundary
Content-Type: text/plain; charset="utf-8"

The daily report is attached.

--report-boundary
Content-Type: application/pdf; name="daily-report.pdf"
Content-Disposition: attachment; filename="daily-report.pdf"
Content-Transfer-Encoding: base64

JVBERi0xLjQKJcTl8uXr...
--report-boundary--
```

Each boundary starts a new part. The final boundary ends with `--`. Every part can have its own headers, such as `Content-Type`, `Content-Disposition`, and `Content-Transfer-Encoding`.

Important MIME clues:

- `text/plain` is the plain-text body.
- `text/html` is the HTML body.
- `multipart/alternative` usually means the same content is offered in plain text and HTML.
- `multipart/mixed` usually means the message includes attachments.
- `base64` means binary content has been encoded as ASCII text for transport.
- `charset` tells the client how to decode text characters.

## Safe inspection commands

On a lab machine or mail server where you are authorized to inspect mail, start with read-only commands.

View a saved raw message:

```bash
less suspicious-message.eml
```

Show only header lines until the first blank line:

```bash
sed -n '1,/^$/p' suspicious-message.eml
```

List the delivery trace:

```bash
grep -i '^Received:' suspicious-message.eml
```

Find authentication results:

```bash
grep -Ei '^(Authentication-Results|DKIM-Signature|Received-SPF|ARC-)' suspicious-message.eml
```

Identify MIME boundaries and content types:

```bash
grep -Ei '^(Content-Type|Content-Disposition|Content-Transfer-Encoding|MIME-Version):' suspicious-message.eml
```

If a message is still queued locally, inspect it with the mail server's queue tools instead of editing queue files directly. For Postfix, use:

```bash
postqueue -p
postcat -q QUEUE_ID
```

`postcat` prints queued message content for inspection. Do not modify files under the queue directory by hand.

## Troubleshooting from message structure

Use the anatomy to narrow the failure:

- If the envelope recipient is wrong, check the sending application, alias expansion, or mailing-list software.
- If the visible `To:` header looks wrong but delivery was correct, check whether the message used `Bcc`, aliases, or list expansion.
- If attachments are missing, inspect the MIME boundaries and `Content-Disposition` fields.
- If text looks corrupted, check `charset` and `Content-Transfer-Encoding`.
- If a message is delayed, read `Received` headers from bottom to top and compare timestamps.
- If the message is marked as spam, inspect `Authentication-Results`, `DKIM-Signature`, `Return-Path`, and sending-domain alignment.

Run these on a disposable VM, container, or sample `.eml` file. Do not inspect another user's mailbox without authorization.
