# 18.8 Sendmail

Sendmail is one of the oldest Unix mail transfer agents. Many modern Linux
systems use Postfix, Exim, OpenSMTPD, or a relay-only tool instead, but Sendmail
still appears in legacy estates, appliances, and older enterprise mail paths.

You do not need to love Sendmail to operate it safely. You need to know where
its configuration comes from, how to inspect the queue and logs, and how to make
changes without directly editing generated files.

!!! abstract "What you will learn"
    - Explain where Sendmail fits in a Linux mail system.
    - Identify the active Sendmail service, queue, aliases, and configuration.
    - Understand the relationship between `sendmail.mc` and `sendmail.cf`.
    - Rebuild configuration safely from M4 source.
    - Inspect delivery logs and troubleshoot common Sendmail failures.

## What Sendmail Does

Sendmail is an MTA. It accepts messages, queues them, applies routing and policy
decisions, and attempts delivery to local or remote destinations.

Common Sendmail responsibilities:

- receive local system mail
- relay outbound mail through an upstream host
- receive inbound SMTP for a domain
- expand aliases
- manage retry queues
- hand local messages to a delivery agent

On many Linux systems, the `sendmail` command also exists as a compatibility
interface even when the real MTA is Postfix or Exim. Always verify the actual
package and service before assuming Sendmail is active.

## Inspect the Current State

Start read-only:

```bash
command -v sendmail
sendmail -d0.1 -bv postmaster 2>/dev/null | sed -n '1,80p'
systemctl status sendmail 2>/dev/null || true
ps -ef | grep '[s]endmail'
```

Check listening sockets:

```bash
ss -ltnp | grep ':25\\b' || true
ss -ltnp | grep -E ':(465|587)\\b' || true
```

Check likely configuration paths:

```bash
ls -l /etc/mail
ls -l /etc/mail/sendmail.mc /etc/mail/sendmail.cf 2>/dev/null || true
```

Distribution layouts vary. Debian-family systems often use `/etc/mail/`.
Enterprise distributions may also keep supporting files, access maps, and
database files there.

## The Important Files

| File | Purpose |
| --- | --- |
| `/etc/mail/sendmail.mc` | Human-edited M4 macro source |
| `/etc/mail/sendmail.cf` | Generated low-level Sendmail configuration |
| `/etc/aliases` or `/etc/mail/aliases` | Local alias definitions |
| `/etc/mail/access` | Optional access control map |
| `/etc/mail/mailertable` | Optional routing table by domain |
| `/etc/mail/virtusertable` | Optional virtual user mapping |
| `/var/spool/mqueue` | Traditional mail queue location |
| `/var/log/mail.log` or `/var/log/maillog` | Mail log, depending on distribution |

The most important rule: do not hand-edit `sendmail.cf` unless you have no
other choice and understand the local process. It is generated from `sendmail.mc`
and is difficult to review safely.

## M4 Configuration

Sendmail's high-level configuration is usually written as M4 macros.

Small example:

```text
divert(-1)dnl
include(`/usr/share/sendmail/cf/m4/cf.m4')dnl
VERSIONID(`example sendmail config')dnl
OSTYPE(`linux')dnl
DOMAIN(`generic')dnl
define(`SMART_HOST', `smtp.example.net')dnl
FEATURE(`use_cw_file')dnl
FEATURE(`access_db')dnl
MAILER(`local')dnl
MAILER(`smtp')dnl
```

The `dnl` marker means "delete through newline" in M4. It is commonly used to
avoid stray whitespace in generated configuration.

Common macro concepts:

| Macro | Meaning |
| --- | --- |
| `OSTYPE(...)` | Load operating-system defaults |
| `DOMAIN(...)` | Load domain-oriented defaults |
| `FEATURE(...)` | Enable optional behavior |
| `define(...)` | Set a macro value |
| `MAILER(...)` | Enable a delivery mechanism |

## Rebuild Configuration Safely

Before changing anything:

```bash
sudo cp -a /etc/mail/sendmail.mc "/etc/mail/sendmail.mc.$(date +%Y%m%d-%H%M%S).bak"
sudo cp -a /etc/mail/sendmail.cf "/etc/mail/sendmail.cf.$(date +%Y%m%d-%H%M%S).bak"
```

Edit the M4 source:

```bash
sudoedit /etc/mail/sendmail.mc
```

Rebuild using the distribution-supported method when available:

```bash
cd /etc/mail
sudo make
```

If there is no Makefile, the manual pattern is:

```bash
cd /etc/mail
sudo m4 sendmail.mc > /tmp/sendmail.cf.new
sudo install -m 0644 /tmp/sendmail.cf.new /etc/mail/sendmail.cf
```

Then reload:

```bash
sudo systemctl reload sendmail
```

If reload fails, inspect logs before changing another setting.

## Aliases and Maps

Sendmail commonly uses aliases and optional map files.

Inspect aliases:

```bash
sudo sed -n '1,200p' /etc/aliases 2>/dev/null || true
sudo sed -n '1,200p' /etc/mail/aliases 2>/dev/null || true
```

Rebuild aliases:

```bash
sudo newaliases
```

If access maps are used, you may see files such as `/etc/mail/access` and
`/etc/mail/access.db`. Rebuilding map databases is distribution-specific, but
often uses `makemap`:

```bash
cd /etc/mail
sudo makemap hash access < access
```

Do not rebuild maps blindly on production hosts. First confirm which maps are
referenced by the active configuration.

## Queue Operations

Inspect the queue:

```bash
mailq
sendmail -bp
```

Attempt a queue run:

```bash
sudo sendmail -q
```

Run a verbose delivery test to see routing decisions:

```bash
sendmail -v recipient@example.net < test-message.txt
```

Use verbose tests carefully. They can send real mail. For lab work, send only to
addresses you control.

## Logs and Evidence

Common log checks:

```bash
sudo tail -n 100 /var/log/mail.log
sudo tail -n 100 /var/log/maillog
journalctl -u sendmail --since "30 minutes ago"
```

Look for:

- queue IDs
- sender and recipient
- relay host
- DNS lookup failures
- authentication or TLS problems
- alias expansion failures
- "stat=Sent", "stat=Deferred", or "stat=User unknown"

Queue IDs are the thread that connects log lines. Use them to trace a message
from acceptance through delivery or failure.

## Common Failure Modes

| Symptom | What to inspect |
| --- | --- |
| Config change has no effect | edited `sendmail.cf` directly, forgot rebuild, reload failed |
| Mail stays queued | DNS failure, remote rejection, network block, bad relay |
| Local mail disappears | alias path, local delivery agent, mailbox permissions |
| User unknown errors | aliases, local user database, virtual user table |
| Relay denied | access map, relay settings, client network |
| Server sends spam | open relay, compromised local account, weak access controls |
| TLS errors | certificate path, permissions, hostname mismatch |

Sendmail's flexibility is powerful, but it also means many behaviors may be
configured through maps and macros. Trace the active configuration instead of
guessing.

## Safe Operating Rules

- Prefer editing `sendmail.mc`, not generated `sendmail.cf`.
- Back up both source and generated configuration before changes.
- Rebuild with the distribution's normal method.
- Reload and verify logs immediately.
- Use aliases and access maps deliberately.
- Never broaden relay access without a specific reason and a test plan.
- Keep `postmaster`, `abuse`, and `root` paths monitored.

## Hands-on Practice

Use a lab VM or container with Sendmail installed.

1. Identify whether Sendmail is the active MTA or only a compatibility command.
2. Inspect `sendmail.mc` and `sendmail.cf` timestamps.
3. Run `mailq` or `sendmail -bp`.
4. Inspect aliases and run `newaliases`.
5. Make a harmless comment change in `sendmail.mc`.
6. Rebuild configuration using the system's supported method.
7. Reload Sendmail and confirm logs show no errors.

## Check Your Understanding

- Why is `sendmail.mc` safer to edit than `sendmail.cf`?
- What does `newaliases` rebuild?
- Which command shows the Sendmail queue?
- Why can an access map create a relay risk?
- What log evidence proves a message was sent, deferred, or rejected?

Sendmail rewards careful, evidence-first operation. Treat it as a generated
configuration system with queues, maps, and logs, not as a single file to tweak
by instinct.
