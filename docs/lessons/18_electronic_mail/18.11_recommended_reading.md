## 18.11 Recommended Reading

Electronic mail is old, distributed, and full of operational edge cases. A good
mail administrator needs more than one book or tutorial. You need references
that explain the protocol, the daemons, the DNS records, the security controls,
and the failure modes you will see in logs.

This reading path is organized by operator need rather than by title alone.

!!! abstract "What you will learn"
    - Choose references for SMTP, delivery, DNS authentication, and abuse
      handling.
    - Separate durable protocol documentation from vendor-specific recipes.
    - Build a mail operations notebook you can use during incidents.
    - Know which sources to trust before changing production mail flow.

## Start with the standards

Standards are not casual reading, but they are the final source of truth when
two tools disagree.

| Topic | Primary references | Why it matters |
| --- | --- | --- |
| SMTP transfer | RFC 5321 and later updates | Defines server-to-server SMTP behavior |
| Message format | RFC 5322 and MIME RFCs | Explains headers, bodies, attachments, and encoding |
| Submission | RFC 6409 | Distinguishes client submission from server transfer |
| STARTTLS | RFC 3207 and modern TLS guidance | Explains opportunistic encryption for SMTP |
| SPF | RFC 7208 | Documents sender IP authorization records |
| DKIM | RFC 6376 and updates | Documents cryptographic message signing |
| DMARC | RFC 7489 and updates | Connects SPF/DKIM alignment to domain policy |

You do not need to memorize these documents. Learn where they live, how they
define terms, and which sections answer common arguments.

## Learn one MTA deeply

Pick the MTA you actually operate first. Depth beats shallow familiarity with
all of them.

### Postfix

Postfix is common on modern Linux systems because it has a clear component
model and safer defaults than older MTAs.

Useful references:

- The official Postfix documentation at `postfix.org`
- `postconf(5)` for configuration parameters
- `master(5)` for service process definitions
- `aliases(5)`, `access(5)`, and `transport(5)` for common lookup maps
- `postqueue(1)` and `postsuper(1)` for queue operations

Operator focus:

- understand `main.cf` versus `master.cf`
- know the difference between `postfix check`, `postfix reload`, and restart
- practice reading queue IDs through logs
- learn the relay controls before exposing port 25 or 587

### Exim

Exim is highly flexible and common on Debian-derived systems and hosting
platforms.

Useful references:

- The official Exim specification
- `exim -bP` output on the local system
- Debian's Exim4 README and split-configuration notes
- `update-exim4.conf` documentation on Debian/Ubuntu

Operator focus:

- understand ACLs, routers, transports, and authenticators
- use `exim -bt` before sending live tests
- inspect `mainlog`, `rejectlog`, and `paniclog`
- avoid editing generated configuration directly

### Sendmail

Sendmail remains important because many legacy systems and local mail tools
still expose the `sendmail` command interface.

Useful references:

- The Sendmail Installation and Operation Guide
- `sendmail.mc` and M4 macro documentation
- `aliases(5)` and `newaliases(1)`
- distribution-specific Sendmail packaging notes

Operator focus:

- change `sendmail.mc`, not generated `sendmail.cf`, on macro-based systems
- rebuild configuration with the distribution-supported toolchain
- understand queue inspection before forcing delivery
- treat legacy relay behavior as something to prove, not assume

## Build the DNS authentication layer

Modern mail reliability depends heavily on DNS. Read the operational
documentation for:

- SPF record design and lookup limits
- DKIM selector naming, key rotation, and signing boundaries
- DMARC alignment, reporting, and policy ramp-up
- MX records and backup MX risk
- reverse DNS for directly sending hosts
- MTA-STS and TLS reporting where appropriate

Good operator practice is to keep a domain mail-authentication note with:

```text
domain:
mx records:
spf record:
dkim selectors:
dmarc policy:
reporting address:
outbound senders:
last verified:
```

Use that note when adding a new provider or diagnosing deliverability problems.

## Study abuse and deliverability

Mail administrators spend a lot of time proving that legitimate mail is
legitimate and that abusive mail is contained.

Read about:

- spam-scoring systems such as SpamAssassin
- DNS blocklists and reputation systems
- rate limits and outbound throttling
- compromised-account indicators
- bounce storms and backscatter
- phishing-resistant authentication for mail users
- safe handling of suspicious attachments and links

Provider documentation is useful here because large mailbox providers publish
the rules they expect senders to follow. Compare Gmail, Microsoft, Yahoo, and
your transactional-email provider's sender requirements.

## Keep command references close

During an incident, you need commands faster than you need theory. Build a
short local reference for the MTA you run.

For Postfix:

```bash
postfix status
postfix check
postconf -n
postqueue -p
postcat -vq QUEUE_ID
postsuper -h QUEUE_ID
postsuper -d QUEUE_ID
```

For Exim:

```bash
exim -bV
exim -bP configure_file
exim -bt user@example.com
exim -bp
exim -Mvl MESSAGE_ID
exim -Mrm MESSAGE_ID
```

For Sendmail:

```bash
sendmail -d0.1 -bv root
mailq
sendmail -bp
newaliases
makemap hash /etc/mail/access < /etc/mail/access
```

Mark destructive or risky commands clearly in your own notes. Queue deletion,
queue flushes, map rebuilds, and service restarts should not be muscle memory.

## Read logs from real incidents

The fastest way to improve is to read actual mail logs and reconstruct the
message path.

Practice answering:

1. Which host accepted the message?
2. What was the envelope sender?
3. What was the envelope recipient?
4. Which queue ID tracked the message?
5. Which DNS or authentication checks passed or failed?
6. Was the message delivered, deferred, rejected, bounced, or discarded?
7. What single next command would prove the next fact?

Do this on lab logs first. On production systems, remember that mail logs and
message bodies can expose private data.

## Evaluate tutorials carefully

Mail tutorials go stale quickly. Before following one, check:

- Does it match your distribution and MTA version?
- Does it distinguish receiving mail from sending mail?
- Does it require authentication before relay?
- Does it explain DNS records and reverse DNS?
- Does it mention TLS, SPF, DKIM, and DMARC?
- Does it tell you how to test and roll back?
- Does it avoid telling you to disable security controls to "make it work"?

If a tutorial skips relay safety, do not use it for production.

## Suggested practice plan

Use a disposable lab environment and work in this order:

1. Configure local-only system mail.
2. Send mail from the server to a local mailbox.
3. Relay outbound mail through a smarthost.
4. Inspect queue and logs for every message.
5. Add SPF, DKIM, and DMARC for a test domain if you control one.
6. Simulate a failed remote delivery and explain the retry behavior.
7. Write a rollback checklist for the configuration you changed.

## Check your understanding

- Why should protocol RFCs and local man pages outrank random tutorials?
- Which MTA do you operate today, and what are its three most important files?
- What DNS records would you inspect before blaming the MTA?
- What makes a mail command risky during an outage?
- How would you teach a teammate to trace one message from submission to final
  delivery or rejection?
