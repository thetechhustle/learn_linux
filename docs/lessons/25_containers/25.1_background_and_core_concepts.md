### 25.1 Background and Core Concepts

Containers are isolated Linux processes with packaging and runtime conventions
around them. They are not tiny virtual machines, and they are not magic
security boundaries. A container still depends on the host kernel, host storage,
host networking, and the runtime that starts it.

The useful mental model is simple: a container packages a process and its
filesystem view while Linux primitives control what that process can see and
use.

## Containers in one sentence

A container is a process tree that starts from an image and runs with a
restricted view of the system.

That restricted view usually includes:

- its own process namespace;
- its own network namespace;
- a controlled filesystem root;
- resource limits;
- a selected set of Linux capabilities;
- environment variables and runtime configuration;
- mounts into or out of the host.

The container feels like a small machine from inside, but from the host it is
still a set of processes.

## Containers versus virtual machines

Virtual machines virtualize hardware. Each VM usually runs its own kernel.

Containers virtualize the process environment. Most containers share the host
kernel.

| Question | Virtual machine | Container |
| --- | --- | --- |
| Kernel | Guest has its own kernel | Shares host kernel |
| Startup | Usually slower | Usually faster |
| Isolation boundary | Hypervisor plus guest OS | Kernel isolation primitives |
| Image | Disk image or template | Layered filesystem image |
| Best fit | Strong OS boundary, mixed kernels, full system labs | App packaging, repeatable services, dense workloads |

Containers are often lighter than VMs, but "lighter" does not mean "safer."
Choose the boundary that matches the risk.

## Containers versus ordinary processes

An ordinary process and a containerized process both run on the host kernel.
The difference is how much of the host they can see and use.

From the host, inspect a process:

```console
$ ps -eo pid,ppid,user,comm,args | head
```

Container runtimes add isolation and metadata around those processes. Depending
on the runtime, you may inspect them with commands such as:

```console
$ docker ps
$ podman ps
$ crictl ps
```

The important operator habit is to connect the high-level runtime view back to
host evidence. If a container exists, there is a host process, a filesystem
view, a network arrangement, and log output somewhere.

## Images and containers

An image is a packaged filesystem plus metadata. A container is a running
instance created from an image.

Useful distinction:

- image: the recipe artifact;
- container: the running process environment;
- registry: a place to store and retrieve images;
- tag: a human label for an image reference;
- digest: a content-addressed identifier for the image.

Tags can move. Digests are better evidence.

For example, `ubuntu:24.04` is a tag. It is convenient, but it is not as precise
as an immutable digest. Production runbooks should record the exact image that
was deployed, not only a friendly tag.

## Namespaces

Namespaces limit what a process can see.

Common namespace types include:

- PID: process IDs;
- NET: network interfaces, routing, and ports;
- MNT: mount points;
- UTS: hostname and domain name;
- IPC: interprocess communication objects;
- USER: user and group ID mapping;
- CGROUP: cgroup view.

A simple lab command can demonstrate the idea:

```console
$ sudo unshare --fork --pid --mount-proc bash
# ps -ef
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 12:00 pts/0    00:00:00 bash
root           8       1  0 12:00 pts/0    00:00:00 ps -ef
# exit
```

Inside that namespace, the shell sees itself as PID 1. This is not a full
container runtime, but it shows the same kind of isolation primitive.

## Cgroups

Cgroups control and account for resource usage.

They answer questions such as:

- how much memory can this workload use?
- how much CPU time is it consuming?
- which process group owns this IO?
- what should happen if the workload exceeds its memory limit?

On systemd-based systems, cgroup state is visible under `/sys/fs/cgroup`:

```console
$ mount | grep cgroup
$ systemd-cgls
$ systemd-cgtop
```

Container runtimes use cgroups so one busy workload does not consume the entire
host by accident. Limits are operational controls, not merely performance
tuning.

## Capabilities and privilege

Linux capabilities split root privileges into smaller pieces. A container can
run as root inside its namespace while having fewer powers on the host.

Inspect capability-related information from a process:

```console
$ grep '^Cap' /proc/$$/status
```

Runtime flags such as `--privileged`, `--cap-add`, and `--cap-drop` change the
risk profile. A privileged container is much closer to a host-level process
with broad access. Treat it as exceptional and document why it is needed.

## Filesystems and layers

Container images are usually made of layers. Each layer records filesystem
changes. When a container starts, the runtime presents those layers as one
filesystem view and adds a writable layer for the running container.

Operational consequences:

- rebuilding an image can reuse unchanged layers;
- deleting a container does not necessarily delete the image;
- data written inside a container can disappear when the container is removed;
- persistent data should use a volume, bind mount, or external service;
- image size grows when builds copy unnecessary files into layers.

A container's filesystem is convenient for packaging, but it is not a backup
strategy.

## Networking

Containers need a network path just like any other service. Common patterns
include:

- bridge network on the host;
- port publishing from host to container;
- host network mode;
- overlay network in orchestrated environments;
- service discovery through the runtime or platform.

Do not confuse "the container is running" with "the service is reachable." Check
both:

```console
$ docker ps
$ ss -tulpn
$ curl -I http://127.0.0.1:8080/
```

If the runtime is not Docker, use the equivalent `podman`, `nerdctl`, or
platform command. The evidence pattern is the same: runtime state, host port
state, and application response.

## Container runtime stack

The container ecosystem has layers:

- image format and registry conventions;
- runtime tools such as Docker, Podman, containerd, CRI-O, or LXC;
- low-level runtime pieces such as `runc`;
- orchestration systems such as Kubernetes, Nomad, or Docker Swarm;
- build tools and CI/CD pipelines that create and publish images.

When troubleshooting, name the layer. "Docker is broken" is vague. Better
questions are:

- did the image build?
- did the image pull?
- did the runtime create the container?
- did the process start?
- did the health check pass?
- did the port bind?
- did the orchestrator schedule it where expected?

## What containers solve

Containers are good at:

- packaging application dependencies;
- making local, CI, and deployment environments more repeatable;
- running multiple services on the same host with clearer boundaries;
- providing fast disposable test environments;
- making deployment artifacts easier to move between machines;
- supporting scale-out platforms.

Containers do not automatically solve:

- bad application configuration;
- secret management;
- database migrations;
- network design;
- persistent storage safety;
- host kernel vulnerabilities;
- observability;
- deployment approval and rollback policy.

Use containers to improve repeatability, not to avoid operational thinking.

## Rootless containers

Rootless containers run the runtime and container processes without requiring a
root-owned daemon for normal operation. Podman is commonly used this way.

Rootless operation can reduce blast radius, but it has trade-offs:

- networking may behave differently;
- privileged ports need special handling;
- filesystem ownership maps through user namespaces;
- some kernel features may not be available;
- service startup needs user-level systemd or another supervisor.

Rootless containers are worth learning because they make the security boundary
more explicit.

## Safety checklist

Before running a container from an unfamiliar image, ask:

1. Who published the image?
2. Is the tag current and maintained?
3. Can I pin a digest?
4. Does it need privileged mode?
5. What host paths are mounted?
6. What ports are exposed?
7. What secrets are passed in?
8. Where does persistent data live?
9. How will I remove it cleanly?
10. What logs prove it worked?

This checklist catches most beginner mistakes before they become host-level
mess.

## Hands-on practice

Use a disposable VM or lab host with Docker or Podman installed.

1. List running containers with `docker ps` or `podman ps`.
2. Run a small test container from a trusted image.
3. Inspect the host process with `ps`.
4. Inspect the container's namespaces using `/proc/<pid>/ns`.
5. Publish a port and confirm it with `ss` and `curl`.
6. Stop and remove the container.
7. Confirm whether the image still exists.
8. Write down what data would have been lost if the container wrote only to its
   writable layer.
