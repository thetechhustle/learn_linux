## 25.4 Container Clustering and Management

!!! abstract "What you will learn"
    - Explain why single-container operations change when containers run as a cluster.
    - Compare Docker Swarm, Kubernetes, and managed container platforms at an operator level.
    - Inspect desired state, actual state, placement, health, rollout status, and service exposure.
    - Recognize the safety boundaries around scaling, draining, updating, and deleting workloads.
    - Build a handoff note that separates scheduler intent from runtime evidence.

!!! success "Operator principle"
    A cluster is not magic capacity. It is a control plane constantly trying to
    make actual state match declared state.

    When something is wrong, inspect both sides: what the scheduler was asked to
    do, and what the nodes are actually running.

## From container host to cluster

On one host, you can inspect containers with commands such as `docker ps`,
`docker logs`, and `docker inspect`. In a cluster, those containers become tasks,
pods, replicas, or service instances placed across multiple nodes.

That adds useful capabilities:

- restart failed workloads
- spread replicas across nodes
- publish services behind stable names or load balancers
- roll out new versions gradually
- drain a node before maintenance
- enforce resource requests, limits, and placement rules

It also adds new failure modes:

- the control plane can be healthy while a node is not
- desired replicas can differ from running replicas
- a service can be scheduled but unreachable
- a rollout can stall on image pulls, probes, or resource pressure
- storage and secrets must be handled intentionally across nodes

The most important operator habit is to avoid treating "created" as the same as
"running and serving traffic."

## The core objects

Different platforms use different names, but the operational ideas are similar.

| Concept | Kubernetes example | Docker Swarm example | Operator question |
| --- | --- | --- | --- |
| Cluster member | Node | Node | Which machines can run work? |
| Workload definition | Deployment, StatefulSet, DaemonSet | Service | What did we ask the scheduler to run? |
| Runtime instance | Pod | Task | What is actually running right now? |
| Service discovery | Service, EndpointSlice, Ingress | Service VIP, published port | How should traffic reach it? |
| Configuration | ConfigMap, Secret, environment, volume | Config, secret, environment, mount | What runtime inputs does it depend on? |
| Rollout state | ReplicaSet, rollout status | service update status | Is the new version actually live? |

The names matter when using tools, but the evidence pattern matters more.

## Inspect cluster membership first

Before touching a workload, learn whether the cluster itself is usable.

Kubernetes:

```bash
kubectl get nodes -o wide
kubectl get componentstatuses 2>/dev/null || true
kubectl cluster-info
```

Docker Swarm:

```bash
docker node ls
docker info --format 'Swarm={{.Swarm.LocalNodeState}} ControlAvailable={{.Swarm.ControlAvailable}}'
```

Useful questions:

- Are enough nodes `Ready` or active?
- Which nodes are schedulable?
- Which node is the manager or control-plane member?
- Are there version, architecture, or OS differences?
- Is the issue cluster-wide or isolated to one node?

If node health is bad, scaling a workload may only create more failed instances.

## Inspect desired state and actual state

For Kubernetes, start with the workload and then inspect the pods it created:

```bash
kubectl get deployments -A
kubectl describe deployment <name> -n <namespace>
kubectl get pods -n <namespace> -o wide
kubectl describe pod <pod-name> -n <namespace>
```

For Docker Swarm, start with the service and then inspect tasks:

```bash
docker service ls
docker service ps <service-name>
docker service inspect <service-name>
```

Look for gaps:

- desired replicas versus available replicas
- pending pods or tasks
- repeated restarts
- image pull errors
- failed health checks
- nodes that receive all the failed placements
- recently changed images, commands, environment, or mounts

For handoff, record both the declared intent and observed runtime:

```text
Desired: service api should run 3 replicas of image registry.example/api:2026-05-13.
Actual: 2/3 replicas running; one task rejected on node worker-02 due to image pull failure.
Evidence: service ps output, node name, error text, rollout timestamp.
```

## Understand scheduling and placement

Schedulers place work based on resource availability, labels, constraints,
taints, tolerations, affinity rules, and runtime health. When work is not
starting, ask why the scheduler cannot place it.

Kubernetes:

```bash
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl top nodes 2>/dev/null || true
kubectl top pods -n <namespace> 2>/dev/null || true
```

Docker Swarm:

```bash
docker service ps <service-name> --no-trunc
docker node inspect <node-name> --pretty
docker node ls
```

Common placement blockers:

- insufficient CPU or memory
- image unavailable to one or more nodes
- architecture mismatch
- node marked unschedulable or drained
- missing secret, config, volume, or device
- placement rule matches no active node

Do not fix placement by deleting random workloads unless you know the blast
radius. First capture the scheduler's reason.

## Service exposure and traffic

Clustered containers need a stable way for users or other services to reach
them. This is separate from whether the runtime instances are alive.

Kubernetes:

```bash
kubectl get service -n <namespace>
kubectl describe service <service-name> -n <namespace>
kubectl get endpoints -n <namespace>
kubectl get ingress -A
```

Docker Swarm:

```bash
docker service ls
docker service inspect <service-name> --format '{{json .Endpoint}}'
docker service ps <service-name>
```

Troubleshooting flow:

1. Confirm the workload has healthy runtime instances.
2. Confirm the service selector or routing rule points to those instances.
3. Confirm the published port, ingress, or load balancer is present.
4. Test from inside the cluster and from the client side if possible.

A service with no endpoints is usually a selection or readiness problem, not a
firewall problem.

## Scaling is a change, not a wish

Scaling changes desired state. It does not guarantee the cluster has capacity or
that the new instances are healthy.

Kubernetes:

```bash
kubectl scale deployment <name> -n <namespace> --replicas=4
kubectl rollout status deployment/<name> -n <namespace>
kubectl get pods -n <namespace> -o wide
```

Docker Swarm:

```bash
docker service scale <service-name>=4
docker service ps <service-name>
```

Before scaling up:

- check current error rate or queue pressure
- check node capacity
- confirm the app can safely run multiple replicas
- confirm storage is not single-writer local state
- confirm downstream dependencies can handle more load

Before scaling down:

- know whether active requests, jobs, or sessions will be interrupted
- check whether the platform drains gracefully
- keep enough replicas for availability

## Rollouts and rollback evidence

Cluster managers can replace old instances with new ones. The operator still
needs to know whether the rollout completed and what changed.

Kubernetes:

```bash
kubectl set image deployment/<name> <container>=registry.example/app:2026-05-13 -n <namespace>
kubectl rollout status deployment/<name> -n <namespace>
kubectl rollout history deployment/<name> -n <namespace>
kubectl describe deployment <name> -n <namespace>
```

Docker Swarm:

```bash
docker service update --image registry.example/app:2026-05-13 <service-name>
docker service ps <service-name>
docker service inspect <service-name> --format '{{json .UpdateStatus}}'
```

If a rollout fails, capture:

- previous image and new image
- failing pod/task names
- node names
- event or task error text
- health check or probe failures
- rollback command or remediation path

Rollback can be safer than debugging live if the failure is user-facing and a
known-good version exists.

## Node maintenance and draining

When a host needs maintenance, do not just shut it down and hope the cluster
absorbs the loss.

Kubernetes:

```bash
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
kubectl get pods -A -o wide | grep <node> || true
```

Docker Swarm:

```bash
docker node update --availability drain <node>
docker service ps <service-name>
```

Important cautions:

- Draining can evict workloads and interrupt users.
- Some workloads may not be safely movable because of local storage.
- Daemon-style workloads intentionally run on every node.
- A small cluster may not have enough spare capacity.

After maintenance, make the node schedulable again only after it is healthy.

## Secrets, configs, and storage

Clustered workloads usually fail at the boundaries: config, secrets, volumes,
and networks.

Questions to answer before deployment:

- Where do secrets live, and who can read them?
- Are config changes versioned and reviewable?
- Does the workload need persistent storage?
- Is storage local to a node or portable across nodes?
- Can more than one replica write to the same data?
- What backup or restore path exists?

Kubernetes and Swarm both have secret/config mechanisms. Use them instead of
baking secrets into images or typing them into ad hoc shell commands.

## Managed container services

Cloud platforms can run containers without you managing every cluster component.
Examples include managed Kubernetes, serverless container tasks, and platform
services that deploy from images.

Managed services reduce some operational burden, but they do not remove
responsibility for:

- image provenance and vulnerability response
- environment configuration and secrets
- logs, metrics, traces, and alerts
- rollout and rollback safety
- network exposure and identity boundaries
- cost and quota monitoring

Ask what the platform owns, what your team owns, and where evidence lives when
there is an incident.

## Troubleshooting checklist

1. Cluster state

    ```bash
    kubectl get nodes -o wide
    # or
    docker node ls
    ```

2. Workload desired state

    ```bash
    kubectl get deployment <name> -n <namespace> -o wide
    # or
    docker service ls
    ```

3. Runtime instances

    ```bash
    kubectl get pods -n <namespace> -o wide
    # or
    docker service ps <service-name>
    ```

4. Events and errors

    ```bash
    kubectl get events -n <namespace> --sort-by=.lastTimestamp
    kubectl describe pod <pod-name> -n <namespace>
    # or
    docker service ps <service-name> --no-trunc
    ```

5. Traffic path

    ```bash
    kubectl get service,endpoints,ingress -n <namespace>
    # or
    docker service inspect <service-name> --format '{{json .Endpoint}}'
    ```

6. Rollout state

    ```bash
    kubectl rollout status deployment/<name> -n <namespace>
    # or
    docker service inspect <service-name> --format '{{json .UpdateStatus}}'
    ```

## Hands-on lab

Use a disposable lab cluster such as kind, minikube, k3d, a Docker Swarm lab, or
a training environment. Do not run these against a production cluster.

1. List cluster nodes and record which are schedulable.
2. Deploy a small web service with two replicas.
3. Record desired replicas, running instances, node placement, and service
   exposure.
4. Scale the service up by one replica and prove the new instance is running.
5. Change the image tag or command in a controlled way and watch the rollout.
6. Capture the event or task history for the rollout.
7. Scale the service back down and remove the lab workload.
8. Write a handoff note explaining desired state, actual state, traffic path,
   and cleanup.
