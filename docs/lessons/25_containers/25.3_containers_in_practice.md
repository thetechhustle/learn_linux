### 25.3 Containers in Practice

!!! abstract "What you will learn"
    - Run a container with a deliberate name, port mapping, and lifecycle plan.
    - Inspect logs, process state, published ports, mounts, and image history.
    - Use `exec`, `cp`, environment variables, bind mounts, and named volumes safely.
    - Recreate a container when the image or runtime configuration changes.
    - Build a short evidence trail for troubleshooting and handoff.

!!! success "Operator principle"
    A container is disposable, but the service evidence is not.

    Treat the container as a repeatable runtime. Treat logs, configuration, data
    mounts, port exposure, and image identity as operational facts you must be
    able to explain.

## Start with a clean mental model

Running a container is not the same thing as "installing an app." A container is
a process tree started from an image, with a controlled filesystem view,
networking rules, environment variables, and optional storage mounts.

In practice, your job is to answer four questions:

- What image and command started this container?
- What host resources can it reach or expose?
- Where does its data live?
- What evidence shows that it is healthy or broken?

The examples below use Docker because it is common on Linux workstations and
servers. The same operating ideas apply to other container tools.

## Pull and inspect an image

Before running a workload, inspect the image you plan to use:

```bash
docker pull nginx:1.27-alpine
docker image ls nginx
docker image inspect nginx:1.27-alpine
docker history nginx:1.27-alpine
```

Useful things to look for:

- the exact tag and image ID
- the default command or entrypoint
- exposed ports declared by the image
- labels, architecture, and creation time
- unusually large layers in `docker history`

Image tags are names, not immutable proof. For production-style handoffs, record
the image digest or image ID too:

```bash
docker image inspect nginx:1.27-alpine \
  --format '{{index .RepoDigests 0}} {{.Id}}'
```

## Run a named container

Use a deliberate name so later commands and handoffs are clear:

```bash
docker run --name web-demo --detach --publish 8080:80 nginx:1.27-alpine
```

This command says:

- `--name web-demo` gives the container a stable local name.
- `--detach` runs it in the background.
- `--publish 8080:80` maps host port `8080` to container port `80`.
- `nginx:1.27-alpine` is the image to start from.

Verify the process and the port mapping:

```bash
docker ps --filter name=web-demo
docker port web-demo
curl -I http://127.0.0.1:8080/
```

If `curl` fails, do not guess. Check the evidence:

```bash
docker ps --all --filter name=web-demo
docker logs --tail 80 web-demo
docker inspect web-demo --format 'state={{.State.Status}} exit={{.State.ExitCode}}'
```

## Read logs without losing context

Logs are usually the fastest way to understand a container that started but is
not behaving correctly:

```bash
docker logs web-demo
docker logs --tail 50 web-demo
docker logs --since 10m web-demo
docker logs --follow web-demo
```

For incident notes, capture enough context to make the timeline readable:

```bash
date -Is
docker inspect web-demo --format 'image={{.Image}} started={{.State.StartedAt}}'
docker logs --since 15m --tail 200 web-demo
```

Avoid pasting secrets into tickets or chats. Logs can contain tokens, headers,
database URLs, or customer data.

## Enter a running container carefully

`docker exec` starts a new process inside an existing container. It is useful for
inspection, but it can also tempt you into making unrepeatable manual changes.

```bash
docker exec web-demo ps aux
docker exec web-demo nginx -T
docker exec -it web-demo sh
```

Good uses of `exec`:

- read effective configuration
- confirm a process is running
- test DNS or connectivity from the container's point of view
- inspect files that were baked into the image

Risky uses of `exec`:

- editing application files by hand
- installing packages into the running container
- changing permissions without recording the fix in the image or deployment
  definition

If a manual command fixes the issue, translate it into the Dockerfile,
Compose file, deployment manifest, or startup configuration before calling the
incident resolved.

## Copy files for evidence, not deployment

`docker cp` can copy files between the host and a container:

```bash
docker cp web-demo:/etc/nginx/nginx.conf ./nginx.conf.from-container
docker cp ./test-index.html web-demo:/usr/share/nginx/html/index.html
```

Copying a config file out for inspection is normal. Copying application files in
as a deployment method is fragile. The next container recreation will lose that
manual change unless it is also represented in the image or a mounted directory.

## Use environment variables deliberately

Environment variables are common for runtime configuration:

```bash
docker run --name app-demo --detach \
  --env APP_ENV=lab \
  --env LOG_LEVEL=debug \
  busybox sleep 1d
```

Inspect them:

```bash
docker inspect app-demo --format '{{json .Config.Env}}'
```

Be careful with secrets. Environment variables are often visible through
inspection commands, crash reports, shell history, process metadata, and support
bundles. Use your platform's secret mechanism when one is available.

## Choose storage before data matters

A container's writable layer is convenient but disposable. When the container is
removed, that layer disappears too.

Use a named volume when the container owns the application data:

```bash
docker volume create web-content
docker run --name volume-demo --detach \
  --mount source=web-content,target=/usr/share/nginx/html \
  --publish 8081:80 \
  nginx:1.27-alpine
```

Inspect the mount:

```bash
docker inspect volume-demo --format '{{json .Mounts}}'
docker volume inspect web-content
```

Use a bind mount when you intentionally want a host directory exposed inside the
container:

```bash
mkdir -p "$PWD/site"
printf 'hello from a bind mount\n' > "$PWD/site/index.html"

docker run --name bind-demo --detach \
  --mount type=bind,source="$PWD/site",target=/usr/share/nginx/html,readonly \
  --publish 8082:80 \
  nginx:1.27-alpine
```

Bind mounts are powerful because the container can see host files. Keep them as
narrow as possible, prefer read-only mounts when the service does not need to
write, and never bind mount broad paths like `/`, `/home`, or `/var` casually.

## Recreate instead of mutating in place

Most container configuration is fixed when the container is created. If you need
to change ports, environment variables, mounts, the image, or the command,
create a new container.

For a lab container:

```bash
docker stop web-demo
docker rm web-demo
docker run --name web-demo --detach --publish 8080:80 nginx:1.27-alpine
```

For a real service, make sure you know where state lives before removing
anything:

```bash
docker inspect web-demo --format '{{json .Mounts}}'
docker inspect web-demo --format 'image={{.Image}} command={{json .Config.Cmd}}'
```

If there is no persistent volume, database, object store, or rebuildable source
of truth, the container may contain data you are about to delete.

## Clean up with intent

Stop and remove only the lab containers you created:

```bash
docker stop web-demo volume-demo bind-demo app-demo
docker rm web-demo volume-demo bind-demo app-demo
docker volume ls
```

Be cautious with prune commands:

```bash
docker container prune
docker image prune
docker volume prune
docker system prune
```

Prune commands can remove stopped containers, unused images, networks, build
cache, and volumes. On a shared host, that can disrupt another service or remove
data that was only "unused" from Docker's narrow point of view. Inspect before
you prune.

## Troubleshooting checklist

When a containerized service is down or unhealthy, collect evidence in this
order:

1. Identify the container and image.

    ```bash
    docker ps --all
    docker inspect <container> --format 'name={{.Name}} image={{.Image}} state={{.State.Status}} exit={{.State.ExitCode}}'
    ```

2. Check logs and recent restart behavior.

    ```bash
    docker logs --tail 200 <container>
    docker inspect <container> --format 'restarts={{.RestartCount}} started={{.State.StartedAt}} finished={{.State.FinishedAt}}'
    ```

3. Check port exposure.

    ```bash
    docker port <container>
    ss -ltnp | grep ':8080' || true
    ```

4. Check mounts and data location.

    ```bash
    docker inspect <container> --format '{{json .Mounts}}'
    docker volume ls
    ```

5. Check runtime configuration.

    ```bash
    docker inspect <container> --format '{{json .Config.Env}}'
    docker inspect <container> --format '{{json .Config.Cmd}}'
    ```

6. Test from the host and, when needed, from inside the container.

    ```bash
    curl -v http://127.0.0.1:8080/
    docker exec <container> sh -c 'hostname; ip route; cat /etc/resolv.conf'
    ```

## Hands-on lab

Use a disposable Linux VM or lab machine.

1. Start a named Nginx container on host port `8080`.
2. Confirm it answers with `curl -I http://127.0.0.1:8080/`.
3. Record its image ID, container state, published port, and last 20 log lines.
4. Create a bind-mounted `site/` directory with a custom `index.html`.
5. Recreate the container so it serves that bind-mounted directory read-only.
6. Prove that the content changed with `curl`.
7. Stop and remove the lab container.
8. Explain which data would survive container removal and why.
