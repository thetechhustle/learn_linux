### Docker: the Open Source Container Engine

Docker is a container platform that packages an application process with the
libraries, files, and startup instructions it needs. The host still provides the
Linux kernel, networking, storage, process accounting, logs, and security
boundaries. That makes Docker useful, but it also means a Linux operator must be
able to inspect both the Docker objects and the host underneath them.

!!! abstract "What you will learn"
    - Identify the Docker client, daemon, images, containers, volumes, networks, and registries.
    - Inspect Docker Engine health before changing a host.
    - Run, inspect, stop, and remove a disposable container safely.
    - Build a small image from a Dockerfile and explain the risk of each instruction.
    - Troubleshoot common Docker failures with host and container evidence.

!!! warning "Production caution"
    Docker commands can pull code from the internet, start privileged processes, publish ports, mount host paths, and delete data. Practice on a disposable lab host. On production systems, collect evidence first and avoid `--privileged`, broad bind mounts such as `/:/host`, and destructive prune commands unless the change has been reviewed.

## Where Docker Fits

Docker has several moving parts:

- **Docker client**: the `docker` command-line tool you run in a shell.
- **Docker daemon**: the background service, usually `dockerd`, that creates containers.
- **Images**: read-only filesystem layers plus metadata used to create containers.
- **Containers**: running or stopped processes created from images.
- **Registries**: places that store images, such as Docker Hub or an internal registry.
- **Volumes**: Docker-managed persistent storage outside a container's writable layer.
- **Networks**: virtual networks and port publishing rules used to connect containers.

The client talks to the daemon over a local socket or a configured remote
endpoint. Membership in the `docker` group is effectively root-equivalent on a
typical host because users who can control Docker can mount host paths and start
containers with elevated access.

## First Inspection Pass

Before installing packages or restarting services, capture the current state:

```bash
docker version
docker context ls
docker info
systemctl status docker --no-pager
systemctl is-enabled docker
```

If Docker is not installed, those first commands will fail. That is useful
evidence. Record whether the host is meant to use Docker, Podman, containerd, or
a distribution-managed runtime before adding anything new.

On Debian and Ubuntu systems, Docker may come from the distribution package
(`docker.io`) or from Docker's upstream repository (`docker-ce`). Mixing package
sources can create confusing upgrades, so check the existing package source
first:

```bash
apt-cache policy docker.io docker-ce docker-ce-cli containerd.io
dpkg -l 'docker*' 'containerd*' | sed -n '1,20p'
```

On Red Hat-family systems, use the local package tools instead:

```bash
dnf list installed 'docker*' 'containerd*' 2>/dev/null
rpm -qa | grep -E '^(docker|containerd)'
```

## Running a Disposable Container

Use a small image and an explicit command for a first test:

```bash
docker run --rm hello-world
docker run --rm alpine:3.20 cat /etc/os-release
```

`--rm` removes the container after it exits, which keeps the lab tidy. The image
tag (`alpine:3.20`) is more repeatable than `alpine:latest`, but a digest is
better when the exact image must not drift:

```bash
docker image inspect alpine:3.20 --format '{{json .RepoDigests}}'
```

For a longer-running container, give it a name so it is easy to inspect and
remove:

```bash
docker run -d --name web-lab -p 8080:80 nginx:1.27-alpine
docker ps
docker logs --tail 40 web-lab
curl -I http://127.0.0.1:8080/
docker stop web-lab
docker rm web-lab
```

Port publishing maps a host port to a container port. If `curl` fails, check
whether the container is running, whether the port is already in use, and whether
the host firewall allows the traffic.

```bash
docker ps -a --filter name=web-lab
ss -ltnp | grep ':8080'
docker port web-lab 2>/dev/null
```

## Building an Image

A Dockerfile is a build recipe. Keep the example small and predictable:

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY app.py /app/app.py

USER 65534:65534
CMD ["python", "/app/app.py"]
```

Build and inspect it:

```bash
docker build -t local/hello-python:lab .
docker image ls local/hello-python
docker history local/hello-python:lab
docker run --rm local/hello-python:lab
```

Important Dockerfile habits:

- Prefer maintained base images and pin meaningful versions.
- Copy only the files the image needs; use `.dockerignore` to exclude secrets, build output, caches, and local configuration.
- Avoid baking credentials into `ENV`, `ARG`, files, or shell history.
- Use `USER` when the process does not require root.
- Keep package installation and cleanup in the same layer when practical.
- Treat image builds as supply-chain events. Review what the build downloads.

## Volumes and Bind Mounts

Containers lose changes in their writable layer when they are removed. Use
volumes for data that should survive the container:

```bash
docker volume create web-data
docker volume inspect web-data
docker run --rm -v web-data:/data alpine:3.20 sh -c 'date > /data/created.txt'
docker run --rm -v web-data:/data alpine:3.20 cat /data/created.txt
```

Bind mounts expose a host path directly inside the container:

```bash
mkdir -p "$HOME/container-lab"
docker run --rm -v "$HOME/container-lab:/data:ro" alpine:3.20 ls -la /data
```

Use read-only bind mounts (`:ro`) unless the container truly needs to write to
the host path. A writable bind mount can let a container change or delete host
files.

## Logs, Processes, and Resource Evidence

Docker gives container-level views, but host tools still matter:

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
docker stats --no-stream
docker top web-lab
docker inspect web-lab --format '{{.State.Status}} {{.State.Pid}}'
ps -fp "$(docker inspect web-lab --format '{{.State.Pid}}')"
journalctl -u docker -n 80 --no-pager
```

Use `docker exec` carefully. It is useful for inspection, but it can also turn a
container into an unmanaged snowflake if operators make manual repairs inside it.

```bash
docker exec web-lab cat /etc/nginx/conf.d/default.conf
```

## Common Failure Patterns

- **Cannot connect to the Docker daemon**: Docker is not installed, the service is stopped, the socket path is different, or the current user lacks access.
- **Image pull fails**: DNS, proxy configuration, registry authentication, rate limits, or certificate trust are broken.
- **Container exits immediately**: the main process finished, the command is wrong, required environment variables are missing, or a mounted file is absent.
- **Port is unreachable**: the port was not published, another process owns the host port, the app is listening only on localhost inside the container, or host firewall rules block access.
- **Permission denied on mounted data**: UID/GID ownership differs between the host and the container process.
- **Disk fills unexpectedly**: unused images, stopped containers, build cache, logs, or volumes accumulated.

Use read-only cleanup checks before removing anything:

```bash
docker system df
docker container ls -a
docker image ls
docker volume ls
```

`docker system prune` and `docker volume prune` can delete useful recovery data.
List what exists, identify owners, and remove only the objects that are known to
be disposable.

## Hands-On Practice

Use a disposable Linux VM with Docker installed.

1. Record `docker version`, `docker info`, and `systemctl status docker --no-pager`.
2. Run `docker run --rm alpine:3.20 cat /etc/os-release`.
3. Start an Nginx lab container on host port `8080`, verify it with `curl`, then stop and remove it.
4. Create a named volume, write one file to it from a container, and read that file from a second container.
5. Build a tiny image from a Dockerfile and inspect its layer history.
6. Write a short lab note explaining which commands changed host state and how you cleaned them up.
