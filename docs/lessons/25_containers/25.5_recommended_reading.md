### 25.5 Recommended Reading

Containers sit at the boundary between application delivery and Linux operations. The best container references are the ones that help you answer practical questions: what is running, what host resources it can reach, where the image came from, how it is updated, and what evidence proves the workload is healthy.

Use this reading path as a map. Read the official references first, then use the deeper material to understand why the commands behave the way they do.

!!! abstract "What you will learn"
    - Choose container references that match the operational question in front of you.
    - Separate Docker, OCI, Linux kernel, and orchestration documentation by responsibility.
    - Build a small reading-and-lab routine for validating container changes safely.

!!! success "Operator principle"
    Prefer vendor and project documentation for command behavior, and use books or articles to build mental models.

## Start with the official references

- [Docker documentation](https://docs.docker.com/): Use this for Docker Engine, Dockerfile syntax, Compose files, volumes, networking, logging drivers, and routine troubleshooting. When a command flag is unclear, start here before relying on a blog post.
- [Dockerfile reference](https://docs.docker.com/reference/dockerfile/): Keep this close while reviewing image builds. Pay attention to `FROM`, `RUN`, `COPY`, `USER`, `ENTRYPOINT`, `CMD`, build arguments, and cache behavior.
- [Compose specification](https://compose-spec.io/): Use this when a lab or small service stack moves beyond a single `docker run` command. Compose files are common in development, CI, and lightweight internal services.
- [Open Container Initiative specifications](https://opencontainers.org/): Read these when you need to understand the standard image and runtime formats behind Docker, containerd, Podman, and Kubernetes.

## Understand the Linux host layer

Containers are Linux processes with extra boundaries. These resources explain the host mechanisms that make those boundaries work.

- [`namespaces(7)`](https://man7.org/linux/man-pages/man7/namespaces.7.html): Namespaces explain why a container can see its own process tree, network stack, hostname, mount view, or user mapping.
- [`cgroups(7)`](https://man7.org/linux/man-pages/man7/cgroups.7.html): Control groups explain CPU, memory, and I/O limits. Read this before assuming a container memory failure is only an application bug.
- [`capabilities(7)`](https://man7.org/linux/man-pages/man7/capabilities.7.html): Capabilities explain why root inside a container is not the same as unrestricted root on the host, and why `--privileged` is risky.
- [SELinux container documentation](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/latest/html/using_selinux/using-selinux-for-containers_using-selinux): Use this when bind mounts or container processes fail because of labels rather than Unix permissions.

## Build and image security reading

Image quality determines how repeatable and patchable a containerized service is.

- [Docker build best practices](https://docs.docker.com/build/building/best-practices/): Good first stop for smaller images, repeatable builds, cache behavior, and safer Dockerfile habits.
- [Docker Scout documentation](https://docs.docker.com/scout/): Useful for understanding image vulnerability reports, base-image recommendations, and supply-chain signals.
- [Sigstore Cosign documentation](https://docs.sigstore.dev/cosign/): Read this when teams start signing images or verifying image provenance before deployment.
- [SLSA specification](https://slsa.dev/spec/): Use this for the larger software-supply-chain model around build provenance, artifact integrity, and release pipelines.

## Runtime and orchestration reading

Do not jump straight to Kubernetes before you can inspect one container on one host. Once that foundation is solid, these references help you scale the model.

- [containerd documentation](https://containerd.io/docs/): Explains the runtime layer used by many production platforms.
- [Podman documentation](https://docs.podman.io/): Useful when working on rootless containers, daemonless workflows, or Red Hat-family systems.
- [Kubernetes concepts](https://kubernetes.io/docs/concepts/): Start with Pods, Deployments, Services, ConfigMaps, Secrets, and persistent volumes.
- [Kubernetes tasks](https://kubernetes.io/docs/tasks/): Use this when you need concrete commands for inspection, rollout, debugging, and maintenance.

## Lab routine for reading

Use a disposable VM or lab host. Do not practice with production images, production credentials, or production bind mounts.

1. Pick one service image, such as `nginx`, `httpd`, or a small application image from your team.
2. Read the image page and Dockerfile, then write down the base image, exposed ports, default command, and expected logs.
3. Run it with the least access you can:

    ```bash
    docker run --rm --name web-lab -p 8080:80 nginx:stable
    ```

4. In another terminal, collect evidence:

    ```bash
    docker ps
    docker inspect web-lab
    docker logs web-lab
    docker exec web-lab ps aux
    ```

5. Stop the container, then repeat the lab with one intentional change, such as a named volume, a bind mount to a disposable directory, or a memory limit.
6. Compare what changed in `docker inspect`, process output, logs, and host files.

## Check your understanding

- Which reference would you use to confirm a Dockerfile instruction: the Dockerfile reference, the Docker CLI reference, or a Kubernetes guide?
- What Linux feature explains why a container sees a different process list from the host?
- What evidence would you collect before approving a new base image for a service?
- Why is `--privileged` a security exception rather than a normal troubleshooting step?
- When should a team read Kubernetes documentation instead of Docker documentation?

## Practice scenario

A teammate says, "The container works on my laptop, so it should be safe to deploy." Build a short reading and evidence checklist that proves or disproves that claim. Include the image source, Dockerfile review, runtime user, exposed ports, required mounts, environment variables, logs, health checks, resource limits, and rollback plan.
