## Section 13.12: Network Troubleshooting

Network troubleshooting is the discipline of proving where a connection fails. The fastest operators do not jump straight to changing settings. They collect a short evidence trail, test one layer at a time, and stop when the symptom is explained.

!!! abstract "What you will learn"
    - Build a repeatable Linux network troubleshooting sequence.
    - Separate interface, address, route, DNS, firewall, and service failures.
    - Use modern tools such as `ip`, `ss`, `dig`, `tracepath`, and `tcpdump`.
    - Capture enough evidence for an incident handoff.

!!! example "Field story"
    A container host can reach public websites but cannot connect to an internal API. The application team sees timeouts and wants the host rebooted. Before changing anything, you need to prove whether the failure is local addressing, routing, DNS, firewall policy, or the remote service.

!!! success "Operator principle"
    Troubleshoot from the local host outward: interface, address, route, neighbor, DNS, socket, firewall, remote service.

## Start with the symptom

Write the exact failing connection before running commands:

- Source host: the machine or container where the failure starts.
- Destination: hostname or IP address, protocol, and port.
- Expected result: the service, page, share, or API that should answer.
- Observed result: timeout, refused connection, wrong response, name-resolution error, or intermittent loss.
- Scope: one host, one subnet, one application, one site, or every network path.

That statement keeps troubleshooting concrete. "Networking is broken" is too broad; "host `web01` cannot connect to `api.internal.example:443`, but can reach `1.1.1.1`" is useful.

## Follow a layered checklist

### 1. Confirm local interface state

Check whether the interface exists, is up, and has the expected address.

```bash
ip -brief link
ip -brief address
```

Look for:

- `UP` on the expected interface.
- An IPv4 or IPv6 address in the expected subnet.
- Unexpected duplicate addresses, missing addresses, or link-local-only addresses.
- Virtual interfaces, bridges, bonds, VLANs, or container interfaces that may be the real traffic path.

If the interface is down, do not immediately bring it up on a production host. First find who manages it:

```bash
nmcli device status 2>/dev/null || true
networkctl status --no-pager 2>/dev/null || true
```

### 2. Check the route decision

Ask the kernel how it would send traffic to the destination.

```bash
ip route get 10.20.30.40
ip route
ip -6 route
```

Useful clues include the selected interface, next hop, source address, routing table, and whether the host says `unreachable`. A wrong source address can break firewalls and return routing even when the destination route looks correct.

### 3. Test local and remote reachability

Use `ping` carefully. It is useful for reachability, but many networks block ICMP.

```bash
ping -c 4 10.20.30.40
ping -c 4 1.1.1.1
```

Compare results:

- Local gateway responds, internet fails: likely upstream route, firewall, or provider issue.
- Internet IP responds, hostname fails: likely DNS.
- Destination IP times out, nearby hosts respond: likely destination, path, or firewall.
- Every target fails: likely local interface, address, route, or link problem.

For path testing, prefer `tracepath` when available because it does not require special privileges:

```bash
tracepath 10.20.30.40
```

`traceroute` is also useful, but it may need installation and different probe modes in filtered networks.

### 4. Separate DNS from IP connectivity

Test name resolution and then test the resolved address directly.

```bash
getent hosts api.internal.example
dig api.internal.example
dig @10.0.0.53 api.internal.example
resolvectl status 2>/dev/null || true
```

Common DNS findings:

- `NXDOMAIN`: the name does not exist in the resolver's view.
- Timeout: resolver unreachable or blocked.
- Wrong address: split DNS, stale cache, or wrong search domain.
- Different answers from different resolvers: resolver configuration or zone propagation issue.

If `curl https://api.internal.example` fails but `curl https://10.20.30.40` reaches the service, DNS or TLS name validation is now the main lead.

### 5. Inspect sockets and local listeners

On the client, check whether a connection is stuck, refused, or established.

```bash
ss -tuna
ss -tan state syn-sent
```

On the server, check whether anything is listening on the expected address and port.

```bash
ss -ltnp
```

Interpret the failure:

- `Connection refused`: packets reached a host, but no process accepted that port or a firewall rejected it.
- `No route to host`: local or intermediate routing/firewall rejected the path.
- Timeout: packets or replies are being dropped, the destination is down, or a stateful firewall is missing return traffic.
- TLS or HTTP error after connection: network path works; continue at the application layer.

### 6. Check firewall and policy controls

Local firewalls can block outgoing, incoming, or forwarded traffic. Inspect before changing.

```bash
sudo nft list ruleset
sudo iptables -S 2>/dev/null || true
sudo firewall-cmd --list-all 2>/dev/null || true
sudo ufw status verbose 2>/dev/null || true
```

For cloud or virtualized hosts, remember the policy may live outside Linux:

- Cloud security groups or network ACLs.
- Kubernetes NetworkPolicy.
- Hypervisor, SDN, or host firewall rules.
- Load balancer health checks and listener rules.

Avoid flushing firewall rules during troubleshooting. Capture the current policy and make the smallest reversible test change in a lab or maintenance window.

### 7. Capture packets when the evidence conflicts

Packet capture shows whether traffic leaves and whether replies return.

```bash
sudo tcpdump -ni any host 10.20.30.40 and port 443
```

Keep captures narrow:

- Use `-n` to avoid DNS lookups while troubleshooting DNS.
- Filter by host and port when possible.
- Avoid capturing secrets or unrelated user traffic.
- Store captures only as long as needed for the incident.

If you see outbound SYN packets but no replies, the issue is beyond the local application. If you see replies returning but the application still times out, inspect local firewall state, container networking, or the application itself.

## Common failure patterns

| Symptom | Likely area | First evidence to collect |
| --- | --- | --- |
| Host has no usable address | Interface or DHCP | `ip -brief address`, DHCP client or NetworkManager logs |
| Can reach IP, not hostname | DNS | `getent hosts`, `dig`, resolver status |
| Can reach gateway, not remote subnet | Routing | `ip route get DEST`, `tracepath DEST` |
| Connection refused | Service or reject policy | `ss -ltnp` on server, firewall rules |
| Timeout to one port only | Firewall, service, or load balancer | `tcpdump`, cloud policy, listener config |
| Works on host, fails in container | Namespace or bridge routing | `ip netns`, container network inspect, host firewall |
| Intermittent latency or loss | Link, congestion, MTU, path | `ping`, `tracepath`, interface counters |

## Check interface counters

Counters can reveal physical, driver, or virtual-network problems.

```bash
ip -s link
ethtool -S eth0 2>/dev/null | head
```

Look for rapidly increasing drops, errors, overruns, carrier changes, or retransmission-related symptoms. A few historic counters may not matter; counters that increase while you reproduce the issue are meaningful.

## Document the handoff

A useful network handoff includes:

- The exact failing source, destination, protocol, and port.
- Commands run and important output.
- What works and what fails.
- Any recent changes: firewall, DHCP, DNS, routing, cloud policy, container deployment.
- The next owner or next test.

Example:

```text
web01 cannot connect to api.internal.example:443.
DNS resolves api.internal.example to 10.20.30.40.
ip route get 10.20.30.40 selects ens5 via 10.20.0.1 source 10.20.12.15.
curl to 10.20.30.40:443 times out.
tcpdump shows outbound SYNs from web01 and no SYN-ACK replies.
Local nftables has no outbound drop for this destination.
Next check: cloud security group, network ACL, or api01 listener/firewall.
```

## Hands-on practice

Run this in a disposable VM or lab network. Do not run packet captures on production networks unless you have permission.

1. Record the baseline:

    ```bash
    ip -brief address
    ip route
    getent hosts example.com
    ```

2. Pick one reachable destination and one hostname:

    ```bash
    ip route get 1.1.1.1
    ping -c 4 1.1.1.1
    dig example.com
    ```

3. Inspect local sockets:

    ```bash
    ss -tuna
    ss -ltn
    ```

4. If you have a second lab host, test a known open port and capture the attempt:

    ```bash
    nc -vz 10.20.30.40 22
    sudo tcpdump -ni any host 10.20.30.40 and port 22
    ```

5. Write a five-line handoff that states what worked, what failed, and the next test.
