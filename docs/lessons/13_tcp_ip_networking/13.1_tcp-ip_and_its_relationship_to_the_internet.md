## 13.1 TCP/IP and Its Relationship to the Internet

TCP/IP is the protocol family that lets Linux systems talk to local networks,
private services, cloud platforms, and the public Internet. Administrators do
not need to memorize every protocol detail, but they do need a reliable mental
model for where traffic can fail and what evidence proves each layer is
working.

When someone says "the network is down," they might mean:

- the network interface has no link
- the host has no useful IP address
- routing sends packets to the wrong next hop
- DNS cannot translate a name to an address
- a firewall blocks the traffic
- the remote service is unavailable
- TCP connects but the application protocol fails

TCP/IP gives you a way to separate those possibilities instead of guessing.

## The Practical Stack

Linux networking is often explained with the TCP/IP stack. The layers are a
model, not a perfect map of every command, but they are useful during
troubleshooting.

| Layer | What it answers | Common Linux evidence |
| --- | --- | --- |
| Link | Can this host use the local network segment? | `ip link`, `ethtool`, switch or Wi-Fi state |
| Internet | Does this host have an IP path to another address? | `ip addr`, `ip route`, `ping`, `tracepath` |
| Transport | Can a process open a TCP or UDP conversation? | `ss`, `nc`, `tcpdump` |
| Application | Does the real protocol work? | `curl`, `dig`, service logs, client errors |

This order matters. If the interface is down or the route is missing, debugging
HTTP, SSH, or a database client wastes time.

## IP: Addressing and Routing

The Internet Protocol provides addressing and packet delivery. Each IP packet
has a source address, destination address, and enough metadata for routers to
move it toward the next network.

On a Linux host, start with:

```bash
ip addr show
ip route show
```

`ip addr show` tells you what addresses the host believes it owns. `ip route
show` tells you where the kernel will send packets for local networks, default
Internet traffic, and any special routes.

A healthy small-network workstation usually has:

- an active interface with an IPv4 or IPv6 address
- a route for the local subnet
- a default route for non-local destinations
- a DNS resolver configured by NetworkManager, systemd-resolved, DHCP, or local
  configuration

Example:

```bash
ip -brief addr
ip route get 1.1.1.1
```

`ip route get` is especially useful because it asks the kernel which interface,
source address, and next hop it would use for one destination.

## TCP and UDP

IP moves packets. TCP and UDP sit above IP and let applications communicate.

TCP provides connection-oriented, reliable delivery. It is used by SSH, HTTPS,
SMTP, IMAP, many databases, and most web APIs. A failed TCP connection usually
points to one of these problems:

- no route to the destination
- firewall denial
- remote service is not listening
- service is listening on a different address or port
- TLS or application-layer failure after the TCP connection succeeds

UDP is connectionless. It is used by DNS, DHCP, NTP, QUIC, many VPNs, and many
real-time protocols. UDP failures can be harder to prove because there is no
connection handshake. You often need application-specific tools or packet
capture.

Useful checks:

```bash
ss -tulpen
nc -vz example.com 443
dig example.com
```

`ss -tulpen` shows local listening sockets and established connections. `nc -vz`
tests whether a TCP port accepts a connection. `dig` checks DNS behavior without
mixing it into a browser or application client.

## DNS Is Adjacent, Not Optional

Many incidents that look like TCP/IP failures are actually name-resolution
failures. A host can have perfect IP connectivity and still fail to reach
`api.example.com` if DNS is broken.

Separate these tests:

```bash
ping -c 3 1.1.1.1
dig example.com
curl -I https://example.com
```

If the IP ping works but `dig` fails, focus on resolver configuration and DNS
reachability. If `dig` works but `curl` fails, move up to TCP, TLS, proxy, or
application behavior.

## NAT, Firewalls, and the Public Internet

Most Linux systems are not directly sitting on the public Internet. They are
behind routers, firewalls, NAT gateways, cloud security groups, container
bridges, VPNs, or service meshes.

That means a packet's path may include several policy points:

- local host firewall
- container or VM network rules
- VPN route policy
- LAN router or NAT gateway
- cloud firewall or security group
- remote host firewall
- remote service binding

When a connection fails, identify which boundary is closest to the symptom and
test from both sides when possible.

## A Reliable Triage Flow

Use a layered order for most Linux networking incidents:

1. Check the interface:

   ```bash
   ip -brief link
   ip -brief addr
   ```

2. Check routing:

   ```bash
   ip route
   ip route get <destination-ip>
   ```

3. Check reachability:

   ```bash
   ping -c 3 <gateway-or-known-ip>
   tracepath <destination>
   ```

4. Check DNS:

   ```bash
   resolvectl status
   dig <hostname>
   ```

5. Check transport:

   ```bash
   nc -vz <hostname> <port>
   ss -tulpen
   ```

6. Check the application:

   ```bash
   curl -v https://<hostname>/
   journalctl -u <service-name> --since -30m
   ```

Change only one thing at a time, and record the command output before and after
the change.

## Example: Internet Works, Internal Service Does Not

Suppose a Linux container host can reach public websites but cannot reach an
internal service at `inventory.service.local`.

Start by separating public Internet reachability from internal name and route
behavior:

```bash
ip route get 1.1.1.1
ip route get inventory.service.local
dig inventory.service.local
nc -vz inventory.service.local 443
```

Possible findings:

- `dig` fails: DNS or search-domain issue.
- `ip route get` chooses the wrong interface: route or VPN policy issue.
- `nc` times out: firewall, remote listener, or path issue.
- `nc` connects but the app fails: TLS, HTTP, authentication, or service issue.

This evidence narrows the incident quickly and gives the next person a useful
handoff.

## Hands-on Practice

Use a lab VM, disposable cloud instance, or container host.

1. Record current interface and address state:

   ```bash
   ip -brief addr
   ```

2. Ask the kernel how it would reach a public address:

   ```bash
   ip route get 1.1.1.1
   ```

3. Compare DNS and HTTP behavior:

   ```bash
   dig example.com
   curl -I https://example.com
   ```

4. Inspect local listening services:

   ```bash
   ss -tulpen
   ```

5. Write a short note that answers:

   - which interface carried default-route traffic
   - which DNS resolver answered
   - which local ports were listening
   - where you would start if HTTPS failed but DNS still worked
