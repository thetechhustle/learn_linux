## 13.14 Firewalls and Network Address Translation

Firewalls decide which packets are allowed through a host or network boundary.
Network Address Translation, usually called NAT, rewrites packet addresses or
ports so traffic can cross boundaries between private and public networks.

On modern Linux systems, firewall and NAT rules may come from several layers:
`nftables`, legacy `iptables`, `firewalld`, `ufw`, container runtimes, VPN
software, cloud security groups, or upstream network appliances. A good operator
does not guess which layer is active. They identify the owner, inspect the live
rules, make the smallest change, and prove the packet path afterward.

!!! abstract "What you will learn"
    - Explain packet filtering, stateful firewalls, and NAT in operational terms.
    - Inspect Linux firewall rules with `nft`, `iptables`, `firewall-cmd`, and `ufw`.
    - Recognize where Docker, VPNs, routers, and cloud security groups can add rules.
    - Troubleshoot blocked inbound traffic, failed outbound NAT, and port-forwarding problems.
    - Apply firewall changes with rollback in mind.

!!! success "Operator principle"
    Treat the firewall as one part of the packet path, not the whole path. Prove interface, route, listener, firewall, NAT, and upstream policy before changing rules.

## What a firewall decides

A firewall rule usually matches some combination of:

- source address
- destination address
- protocol, such as TCP, UDP, ICMP, or ESP
- source port
- destination port
- input or output interface
- connection state
- packet mark or zone

Then it takes an action:

- accept
- drop silently
- reject with an error
- log
- jump to another chain
- rate-limit
- translate an address or port

Stateful firewalls also track connection state. That is why a server can allow
responses to outbound connections without allowing arbitrary inbound traffic.

Common state names include:

- `NEW`
- `ESTABLISHED`
- `RELATED`
- `INVALID`

## What NAT changes

NAT rewrites packet addresses or ports. Common forms:

- SNAT: rewrite the source address.
- MASQUERADE: dynamic SNAT, often used when the outbound address can change.
- DNAT: rewrite the destination address.
- Port forwarding: DNAT from one destination port/address to another.
- PAT: many private hosts share one public address by translating ports.

Typical examples:

- A laptop at `192.168.1.50` reaches the internet through a home router's public address.
- A cloud VM forwards public TCP `443` to a container listening on an internal bridge.
- A VPN gateway rewrites traffic so private subnets can communicate.
- Docker publishes host port `8080` to a container port `80`.

NAT is useful, but it can hide ownership. When a packet disappears, ask what
changed the address before blaming the application.

## Identify the firewall stack

Start by discovering which tools are active:

```console
$ systemctl status firewalld --no-pager
$ systemctl status ufw --no-pager
$ systemctl status nftables --no-pager
$ command -v nft iptables firewall-cmd ufw
```

Then inspect live rules:

```console
$ sudo nft list ruleset
$ sudo iptables -S
$ sudo iptables -t nat -S
$ sudo firewall-cmd --state
$ sudo firewall-cmd --list-all
$ sudo ufw status verbose
```

On many newer distributions, `iptables` commands may be compatibility front
ends backed by `nftables`. Confirm with:

```console
$ iptables --version
```

If the output mentions `nf_tables`, the legacy-looking command is still using
the nftables backend.

## Inspect nftables

`nftables` is the modern Linux packet-filtering framework. Read all rules:

```console
$ sudo nft list ruleset
```

Filter for table and chain names:

```console
$ sudo nft list tables
$ sudo nft list table inet filter
$ sudo nft list chain inet filter input
```

A simple input chain may look like:

```nft
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    iif lo accept
    tcp dport 22 accept
    tcp dport { 80, 443 } accept
  }
}
```

Important questions:

- What is the chain policy?
- Is established traffic allowed?
- Are loopback and required management ports allowed?
- Are rules scoped to the intended interface or source range?
- Are counters increasing on the rule you expect?

Counters make troubleshooting easier:

```console
$ sudo nft list ruleset -a
```

The `-a` option shows handles, which lets you update or delete a specific rule
without flushing a whole chain.

## Inspect legacy iptables

Many environments still use `iptables`, especially older systems and some
automation. Read filter rules:

```console
$ sudo iptables -S
$ sudo iptables -L -n -v
```

Read NAT rules:

```console
$ sudo iptables -t nat -S
$ sudo iptables -t nat -L -n -v
```

Common built-in chains:

- `INPUT`: packets destined for the local host
- `OUTPUT`: packets generated by the local host
- `FORWARD`: packets routed through the host
- `PREROUTING`: early NAT decision point
- `POSTROUTING`: late NAT decision point

For a host-local service, focus on `INPUT`. For a router, gateway, container
host, or VPN node, also inspect `FORWARD` and the `nat` table.

## Understand firewalld and ufw

`firewalld` and `ufw` are front ends. They manage lower-level rules for you.
Avoid editing underneath them unless you know how the front end will reconcile
the change.

For `firewalld`:

```console
$ sudo firewall-cmd --state
$ sudo firewall-cmd --get-active-zones
$ sudo firewall-cmd --list-all
$ sudo firewall-cmd --list-all-zones
```

Open a service permanently and reload:

```console
$ sudo firewall-cmd --add-service=https --permanent
$ sudo firewall-cmd --reload
```

For `ufw`:

```console
$ sudo ufw status numbered
$ sudo ufw allow 443/tcp
$ sudo ufw delete <rule-number>
```

When using a front end, document the front-end command in runbooks. That keeps
future operators from mixing rule owners.

## Troubleshoot blocked inbound traffic

Use this order when a client cannot reach a service:

1. Confirm the service is listening:
   ```console
   $ ss -lntp 'sport = :443'
   ```
2. Confirm the host has the expected address:
   ```console
   $ ip addr show
   ```
3. Confirm the route back to the client:
   ```console
   $ ip route get <client-ip>
   ```
4. Check local firewall rules:
   ```console
   $ sudo nft list ruleset
   $ sudo iptables -S
   ```
5. Watch packets arrive:
   ```console
   $ sudo tcpdump -ni eth0 tcp port 443
   ```
6. Check upstream rules: load balancer, cloud security group, router, VPN, or
   corporate firewall.

Interpret the result:

- No SYN arrives: upstream routing, DNS, security group, router, or client path.
- SYN arrives but no SYN-ACK leaves: local firewall, service bind, or host stack.
- SYN/SYN-ACK occurs but TLS or HTTP fails: application, certificate, proxy, or backend.

## Troubleshoot failed outbound NAT

For a Linux gateway or container host, outbound NAT depends on forwarding,
routes, and NAT rules.

Check forwarding:

```console
$ sysctl net.ipv4.ip_forward
$ sysctl net.ipv6.conf.all.forwarding
```

Check routes:

```console
$ ip route
$ ip route get 8.8.8.8
```

Check NAT:

```console
$ sudo nft list ruleset
$ sudo iptables -t nat -S
```

Legacy `iptables` masquerade example:

```console
# iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

Equivalent nftables pattern:

```nft
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "eth0" masquerade
  }
}
```

Do not paste either blindly into production. Confirm the outbound interface,
private subnet, existing rule owner, and persistence method first.

## Account for containers and overlays

Container runtimes often create firewall and NAT rules:

```console
$ docker network ls
$ docker port <container>
$ sudo iptables -t nat -S | grep -i docker
$ sudo nft list ruleset | grep -i docker
```

Common container problems:

- service listens inside the container but the host port is not published
- host port is published only on `127.0.0.1`
- host firewall blocks the published port
- Docker rules bypass a distribution firewall expectation
- overlay or bridge subnet overlaps with a real network
- reverse-path filtering drops asymmetric traffic

For Kubernetes, also inspect service, node port, ingress, CNI, and cloud load
balancer rules. The host firewall is only one layer.

## Make changes safely

Firewall mistakes can lock you out. Before changing production rules:

- confirm you have console or out-of-band access
- save the current rules
- know which tool owns the rules
- make the narrowest possible change
- use a timed rollback when remote access depends on the rule
- keep a second session open
- verify with counters, `ss`, `curl`, and `tcpdump`

Examples for saving current rules:

```console
$ sudo nft list ruleset > nft-rules-before.txt
$ sudo iptables-save > iptables-before.rules
$ sudo firewall-cmd --list-all-zones > firewalld-before.txt
$ sudo ufw status numbered > ufw-before.txt
```

For a temporary remote change, schedule a rollback before applying the rule:

```console
# at now + 5 minutes
at> nft -f /root/nft-rules-before.nft
at> <Ctrl-D>
```

Cancel the rollback only after you prove access and service behavior are good.

## Firewall evidence checklist

For an incident handoff, capture:

- symptom and client source
- destination IP and port
- service listener output from `ss`
- route decision from `ip route get`
- active firewall owner: `nftables`, `iptables`, `firewalld`, `ufw`, cloud, router, or container runtime
- relevant allow/deny rule
- counters or logs showing whether the rule matched
- `tcpdump` evidence of packets arriving or not arriving
- NAT rule, if translation is involved
- exact change made and rollback plan

This makes the next operator faster and prevents repeated guessing.

## Hands-on practice

Run these on a disposable VM or lab machine.

1. Identify the firewall tooling:
   ```console
   $ command -v nft iptables firewall-cmd ufw
   $ systemctl status firewalld --no-pager
   $ systemctl status ufw --no-pager
   ```
2. Record current rules:
   ```console
   $ sudo nft list ruleset
   $ sudo iptables -S
   $ sudo iptables -t nat -S
   ```
3. Start a temporary test listener:
   ```console
   $ python3 -m http.server 8080
   ```
4. From another shell, confirm the listener and test access:
   ```console
   $ ss -lntp 'sport = :8080'
   $ curl -v http://127.0.0.1:8080/
   ```
5. Add and remove a narrow lab-only rule using the firewall tool your system
   actually uses.
6. Capture packets during the test:
   ```console
   $ sudo tcpdump -ni any tcp port 8080
   ```
7. Write down whether the firewall, listener, route, or client path determined
   the result.
