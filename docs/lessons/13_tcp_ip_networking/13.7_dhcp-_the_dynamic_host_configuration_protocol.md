## 13.7 DHCP: The Dynamic Host Configuration Protocol

DHCP gives a host the network details it needs to communicate without manually
typing an address on every machine. A successful DHCP lease usually provides:

- an IP address and prefix length
- a default gateway
- DNS servers
- lease duration
- sometimes search domains, NTP servers, static routes, or PXE boot options

When DHCP is wrong, the host may look connected but fail in confusing ways. It
might have no address, a duplicate address, the wrong default route, stale DNS
servers, or an address from the wrong VLAN.

## What DHCP Decides

On a typical IPv4 network, a client uses the DORA exchange:

1. `DISCOVER`: the client broadcasts that it needs configuration.
2. `OFFER`: one or more DHCP servers offer a lease.
3. `REQUEST`: the client requests one offered lease.
4. `ACK`: the server confirms the lease and options.

After the ACK, Linux configures the interface and installs related settings.
Those settings can change routes and DNS, not just the address.

DHCP is mostly an IPv4 habit. IPv6 can use DHCPv6, but many IPv6 networks rely
on router advertisements for the default gateway and address configuration.
Check both when troubleshooting dual-stack hosts.

## Inspect the Current Lease

Start with the interface and address:

```bash
ip link
ip addr show
ip route
```

Then check which service owns DHCP on the system:

```bash
systemctl status NetworkManager
systemctl status systemd-networkd
systemctl status dhclient
```

The right command depends on the network stack:

```bash
nmcli device show
networkctl status
journalctl -u NetworkManager --since "30 minutes ago"
journalctl -u systemd-networkd --since "30 minutes ago"
```

Useful evidence to collect:

- interface name and link state
- assigned address and prefix
- default route
- DNS server list
- DHCP server address, if reported
- lease age or renewal time
- recent DHCP log messages

## Find Lease Files

DHCP clients often keep lease data on disk. Common locations include:

```bash
ls /var/lib/NetworkManager/
ls /var/lib/systemd/network/
ls /var/lib/dhcp/
```

Do not depend on one path across every distribution. NetworkManager,
systemd-networkd, and `dhclient` store lease details differently.

If you find a lease file, inspect it as evidence. Do not edit it as your first
fix. The network manager may overwrite it, and editing stale lease files rarely
fixes the real cause.

## Renew a Lease Safely

On a desktop or laptop using NetworkManager:

```bash
nmcli device reapply <interface>
nmcli connection down <connection-name>
nmcli connection up <connection-name>
```

On a systemd-networkd host:

```bash
sudo networkctl renew <interface>
```

On older or simpler systems using `dhclient` directly:

```bash
sudo dhclient -v <interface>
```

Be careful with release commands on a remote machine. Releasing a lease can drop
your SSH session and leave the host unreachable if renewal fails.

Riskier example:

```bash
sudo dhclient -r <interface>
sudo dhclient -v <interface>
```

Use that only from a console, out-of-band access, or a disposable lab unless you
have a rollback path.

## DHCP and DNS

DHCP often provides DNS servers. That means a DHCP issue can appear as a DNS
issue.

Check the active resolver state:

```bash
resolvectl status
cat /etc/resolv.conf
```

Look for:

- unexpected DNS servers
- missing search domains
- split-DNS configuration from VPNs
- `/etc/resolv.conf` pointing at a local stub resolver

If name resolution fails but IP connectivity works, compare DHCP-provided DNS
with the expected network design before blaming the application.

## DHCP and Default Routes

DHCP can install or replace the default route.

Check:

```bash
ip route show default
ip route get 1.1.1.1
```

Common failures:

- lease has an address but no router option
- router option points to the wrong gateway
- VPN or second interface wins with a lower route metric
- host receives a lease from an unexpected network

If the address, gateway, and DNS all came from DHCP, preserve that relationship
in your incident notes. Changing only one part may hide the real problem.

## Reservations and Static Addresses

A DHCP reservation gives a specific host the same address each time, usually
based on MAC address or client identifier. This is often safer than hand-editing
static addresses on every host because the router or DHCP server remains the
source of truth.

Use reservations for:

- printers
- home-lab nodes
- small servers
- network appliances
- devices that need stable firewall or port-forwarding rules

Use static host configuration when:

- the host must work before DHCP is available
- the network has no DHCP server
- the interface is part of low-level infrastructure
- the change is documented and monitored like any other config

Avoid mixing static addresses into the DHCP pool. That creates duplicate-address
risk.

## Rogue or Wrong DHCP Servers

If a host receives the wrong network settings, ask where the lease came from.

Capture DHCP traffic from a safe troubleshooting host:

```bash
sudo tcpdump -ni <interface> port 67 or port 68
```

Signs of a rogue or wrong DHCP source:

- DHCP server address does not match the expected router or DHCP host
- offered gateway is outside the intended network
- DNS servers are unfamiliar
- several hosts suddenly receive unexpected addresses
- issue appears only on one switch, VLAN, SSID, or dock

Do not respond by randomly changing client settings. Find the DHCP source and
the network segment where it is visible.

## PXE and Boot Options

DHCP can also provide boot information for network installs. PXE and similar
flows often use DHCP options to tell a machine where to fetch boot files.

Common boot-related options:

- next server
- boot filename
- vendor class
- architecture-specific boot file

For home-lab or data-center boot work, DHCP is part of the provisioning chain.
A machine can have normal DHCP for regular clients but still fail network boot
if the boot options are missing, wrong, or sent only to the wrong client class.

## Incident Checklist

When a host cannot join or use the network, collect evidence in this order:

1. Link state:

   ```bash
   ip link show <interface>
   ```

2. Address and prefix:

   ```bash
   ip addr show <interface>
   ```

3. Default route:

   ```bash
   ip route show default
   ip route get 1.1.1.1
   ```

4. DNS:

   ```bash
   resolvectl status
   ```

5. DHCP logs:

   ```bash
   journalctl -u NetworkManager --since "30 minutes ago"
   journalctl -u systemd-networkd --since "30 minutes ago"
   ```

6. Lease or server evidence:

   ```bash
   nmcli device show <interface>
   networkctl status <interface>
   ```

7. Packet evidence when needed:

   ```bash
   sudo tcpdump -ni <interface> port 67 or port 68
   ```

## Hands-on Practice

Use a disposable VM, lab machine, or local network you are allowed to inspect.

1. Identify the active network manager.
2. Record the current address, default route, and DNS servers.
3. Find recent DHCP log entries for the active interface.
4. Ask whether the DHCP-provided gateway matches the expected network.
5. Renew the lease using the correct tool for the host.
6. Compare the before and after state.

Do not release a DHCP lease on a remote production host unless you have console
or out-of-band access.
