## Subchapter 13.16: Recommended Reading

!!! abstract "What you will learn"
    - Build a practical reading path for TCP/IP operations instead of collecting random links.
    - Separate protocol references, operating-system documentation, and troubleshooting guides.
    - Choose what to read first during design work, incident response, and skill building.

!!! success "Operator principle"
    Read with a lab open. A networking reference becomes useful when you can connect each claim to an address, route, socket, packet capture, or firewall rule on a real host.

TCP/IP networking is too large to master from one book or one web page. A useful reading plan starts with the work you are doing right now: proving reachability, explaining packet flow, configuring hosts, debugging DNS, or designing a network that someone else must operate later.

Use this chapter's reading path as a map. Start with the operational references that answer today's question, then add deeper protocol material when the evidence does not make sense.

## Core protocol references

Read protocol documents when you need exact behavior, vocabulary, or edge-case rules. They are not always friendly introductions, but they settle arguments.

- IP addressing and forwarding: study the IPv4 and IPv6 architecture documents enough to understand headers, fragmentation, TTL or hop limit, and the difference between host and router behavior.
- TCP and UDP: read the current TCP specification and the UDP specification when troubleshooting connection setup, resets, retransmission, application timeouts, or stateless service behavior.
- ICMP and ICMPv6: keep these nearby when `ping`, path MTU discovery, neighbor discovery, or unreachable messages are part of the evidence.
- ARP and Neighbor Discovery: use them when a host has the right address and route but cannot reach a local peer.
- DHCP: read DHCP and DHCPv6 references when leases, options, gateways, DNS servers, or bootstrapping behavior are unclear.
- DNS: keep resolver and authoritative-server references close, even though DNS gets its own later chapter. Name resolution is often the first network symptom users notice.

Do not try to memorize every field. Focus on what the protocol expects each participant to do and what evidence a Linux host can show you.

## Books worth owning

These books reward slow reading and repeated lab work.

- **TCP/IP Illustrated, Volume 1** by W. Richard Stevens: best for packet-level intuition. Read it with `tcpdump` or Wireshark open so each diagram connects to real traffic.
- **Internetworking with TCP/IP, Volume One** by Douglas Comer: useful for building the mental model of internetworking, routing, addressing, and layering.
- **Computer Networks** by Andrew S. Tanenbaum and David Wetherall: a broad systems view that helps connect link, network, transport, and application layers.
- **UNIX Network Programming** by W. Richard Stevens: deeper than most administrators need day to day, but excellent when socket behavior, client/server design, and application failures matter.
- **Network Warrior** by Gary A. Donahue: practical for switching, routing, and campus-network thinking around the hosts you administer.

Treat older classics as foundations, not change logs. Pair them with current Linux, FreeBSD, and vendor documentation before making production changes.

## Linux documentation to keep close

Linux networking changes over time, but these local references remain high value because they describe the tools on the system in front of you.

```bash
man ip
man ip-address
man ip-route
man ip-neighbour
man ss
man tcpdump
man nft
man firewalld
man NetworkManager
man systemd-networkd
man resolvectl
```

When a man page is long, search it with `/` for the subcommand or flag you are using. For example, in `man ip-route`, search for `default`, `metric`, `table`, and `nexthop`.

!!! tip "Build a command notebook"
    Keep a local note with the exact commands that answer common questions: current address, default route, DNS server, listening sockets, neighbor table, firewall rules, and packet captures. Update it after each incident.

## FreeBSD references

FreeBSD uses different configuration files and commands, so do not assume every Linux procedure translates directly.

- The FreeBSD Handbook networking chapters for host configuration, routing, wireless, jails, and firewalls.
- `man ifconfig` for interface state, aliases, VLANs, and media details.
- `man route` and `man netstat` for routing-table inspection and route selection.
- `man rc.conf` for persistent network configuration.
- `man pf.conf` and the FreeBSD Handbook firewall chapters when packet filtering or NAT is involved.
- `man sockstat` for process-to-socket mapping.

The best habit is to compare Linux and FreeBSD evidence side by side: address, route, resolver, listening socket, firewall, and packet trace.

## Troubleshooting and packet analysis

Packet analysis tools teach networking faster than prose alone.

- **Wireshark documentation**: use it to learn protocol fields, display filters, TCP stream reconstruction, and capture analysis.
- **tcpdump man page**: practice narrow captures that answer one question, such as ARP only, DNS only, one host pair, or one TCP port.
- **mtr documentation**: useful for path investigation, but read its limitations before blaming one intermediate hop.
- **curl documentation**: essential for separating DNS, TCP, TLS, HTTP, proxy, and application-layer failures.
- **dig documentation**: use it to inspect resolver behavior, authoritative answers, TTLs, CNAME chains, and DNSSEC symptoms.

!!! example "Read with a lab"
    Pick one service on a lab host and capture its traffic three ways: DNS lookup, TCP connection, and application request. Then write down which command proves each layer worked.

## Firewall, NAT, and policy references

Firewall documentation is most useful when you connect it to packet direction and state.

- `nftables` wiki and `man nft` for modern Linux packet filtering.
- `iptables` documentation for legacy systems and older runbooks.
- `firewalld` documentation for zone-based administration on distributions that use it.
- `ufw` documentation for Ubuntu-style host firewall workflows.
- `pf` documentation for FreeBSD and OpenBSD-style packet filtering.
- Container runtime networking docs for Docker, Podman, Kubernetes, and CNI when bridge networks, overlays, service NAT, or published ports complicate the host firewall.

When reading firewall material, draw the packet path: ingress interface, prerouting or local delivery, forwarding decision, output path, and NAT translation points.

## Cloud and provider networking

Cloud networking adds provider control planes around the same basic evidence: address, route, firewall, DNS, NAT, load balancing, and logs.

- AWS VPC documentation for route tables, security groups, network ACLs, NAT gateways, VPC endpoints, and flow logs.
- Azure Virtual Network documentation for subnets, network security groups, route tables, private endpoints, and Network Watcher.
- Google Cloud VPC documentation for firewall rules, routes, Cloud NAT, private access, load balancers, and VPC Flow Logs.
- Tailscale documentation for WireGuard-based overlay networking, subnet routers, exit nodes, ACLs, and MagicDNS.
- Cloudflare documentation for DNS, proxying, tunnels, zero trust access, and HTTP-facing network edges.

Do not let provider terms hide the basics. For every cloud feature, ask which packet is allowed, which route is selected, which address is translated, and where logs prove it.

## A practical reading sequence

If you are new to this chapter, use this order:

1. Review the Chapter 13 overview and networking basics.
2. Practice `ip addr`, `ip route`, `ip neigh`, `ss`, `resolvectl`, and `tcpdump` on a lab Linux host.
3. Read one book chapter or protocol reference about IP, TCP, and UDP.
4. Capture DNS, TCP, HTTP, and failed-connection traffic in a lab.
5. Read Linux firewall documentation and build a small `nftables` or distribution-firewall rule set.
6. Compare the same workflow on FreeBSD.
7. Rebuild the lab in one cloud provider and map the provider concepts back to routes, firewalls, NAT, DNS, and packet logs.
