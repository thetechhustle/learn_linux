## 13.2 Networking Basics

Linux networking is a set of moving parts that must agree with each other:
interfaces, addresses, routes, name resolution, firewall policy, and the
application listening on the far end. The basics are not abstract vocabulary.
They are the checklist you use when a service cannot be reached.

This lesson builds the operator model you need before you edit routes, firewall
rules, DNS settings, or service configuration.

!!! abstract "What you will learn"
    - Group networking checks into link, address, route, and name questions and run them in that order.
    - Interpret subnet prefixes, default routes, and socket state to decide whether a destination is local or needs a router.
    - Recognize firewall and virtual-network boundaries (nftables, firewalld, bridges, VPNs) before changing any policy.

## Interfaces

A network interface is the Linux kernel's representation of a network
connection. It might be a physical Ethernet port, a Wi-Fi adapter, a VPN tunnel,
a bridge, a container veth pair, a VLAN interface, or a loopback device.

Start with:

```bash
ip -brief link
ip -brief addr
```

Look for:

- the interface name, such as `eth0`, `enp0s31f6`, `wlan0`, `br0`, or `tailscale0`
- whether the interface is `UP` or `DOWN`
- whether it has an IPv4 or IPv6 address
- whether the address is expected for the network you are on

`lo` is the loopback interface. It represents the local machine itself and is
used for traffic to addresses like `127.0.0.1` and `::1`.

## Link, Address, Route, Name

Most Linux networking checks can be grouped into four questions:

1. Link: is the interface usable?
2. Address: does the host have a valid IP address?
3. Route: does the kernel know where to send packets?
4. Name: can the host resolve the service name to an address?

Those questions map to commands:

```bash
ip -brief link
ip -brief addr
ip route
resolvectl status
```

Do not start by changing DNS if the route is missing. Do not start by changing
the route if the interface is down. Keep the order boring and repeatable.

## Subnets and Prefixes

An IP address usually comes with a prefix length. The prefix tells Linux which
addresses are local to the same network.

Example:

```text
192.168.8.42/24
```

This means the host address is `192.168.8.42` and the local subnet is typically
`192.168.8.0` through `192.168.8.255`. A host on `192.168.8.42/24` can usually
reach `192.168.8.1` directly on the local network, but it needs a router to
reach `8.8.8.8`.

IPv6 uses the same prefix idea:

```text
2001:db8:1234::42/64
```

The specific address format is different, but the operational question is the
same: is the destination local, or does it need a route through another device?

## Default Route

The default route is where Linux sends packets that do not match a more specific
route. On a home or office LAN, this usually points to the router. In a cloud
network, it may point to a virtual gateway.

Check it with:

```bash
ip route show default
ip route get 1.1.1.1
```

`ip route get` is more concrete than reading the route table alone because it
shows the interface and source address Linux would use for a specific
destination.

## DNS and Resolvers

DNS converts names like `example.com` into IP addresses. Linux may get resolver
settings from DHCP, NetworkManager, systemd-resolved, a VPN client, or static
configuration.

Useful checks:

```bash
resolvectl status
dig example.com
getent hosts example.com
```

`dig` asks DNS directly and shows resolver behavior. `getent hosts` asks through
the system name-service path, which may include `/etc/hosts`, DNS, or other
sources.

If `ping 1.1.1.1` works but `dig example.com` fails, the network path may be
fine while name resolution is broken.

## Ports, Sockets, and Services

An IP address gets traffic to a host. A port gets traffic to a process on that
host. A socket is the combination of protocol, local address, local port, remote
address, and remote port.

Common examples:

| Service | Protocol | Common port |
| --- | --- | --- |
| SSH | TCP | 22 |
| HTTP | TCP | 80 |
| HTTPS | TCP | 443 |
| DNS | UDP/TCP | 53 |
| NTP | UDP | 123 |

Inspect local listeners:

```bash
ss -tulpen
```

Test a remote TCP listener:

```bash
nc -vz example.com 443
```

A successful TCP connection proves that a path to that port exists. It does not
prove the application is healthy, authenticated, authorized, or returning the
right content.

## Firewalls and Policy Boundaries

Traffic may be allowed by the route table but denied by policy. Common policy
boundaries include:

- local host firewall rules
- container bridge rules
- VPN split-tunnel policy
- cloud security groups
- network ACLs
- remote host firewall rules
- application allowlists

On a Linux host, common firewall tools include `nftables`, `iptables`,
`firewalld`, and `ufw`. The exact command depends on the distribution and
environment, so identify the active firewall before making changes.

Read-only checks include:

```bash
sudo nft list ruleset
sudo iptables -S
sudo firewall-cmd --state
sudo ufw status verbose
```

Only use the command that matches the host. Avoid changing firewall policy until
you have confirmed the interface, address, route, DNS, and service state.

## Containers, VMs, and Bridges

Modern Linux systems often route traffic through virtual networking layers:

- Docker bridge networks
- Kubernetes CNI interfaces
- libvirt bridges
- cloud-init configured interfaces
- Tailscale or WireGuard tunnels
- VLANs and bonded interfaces

The same basics still apply, but there may be more than one network namespace or
bridge involved. A container can have working DNS while the host does not, or the
host can reach a service while a container cannot.

Useful starting points:

```bash
ip link
ip route
ss -tulpen
```

For containers, also inspect the container runtime's network view before
changing host routing.

## A Minimal Troubleshooting Sequence

When a Linux host cannot reach a service, collect evidence in this order:

1. Interface state:

   ```bash
   ip -brief link
   ip -brief addr
   ```

2. Route decision:

   ```bash
   ip route get <destination-ip>
   ```

3. Name resolution:

   ```bash
   dig <hostname>
   getent hosts <hostname>
   ```

4. Port reachability:

   ```bash
   nc -vz <hostname> <port>
   ```

5. Application behavior:

   ```bash
   curl -v https://<hostname>/
   ```

6. Local and service logs:

   ```bash
   journalctl -u <service-name> --since -30m
   ```

This sequence keeps the investigation grounded and makes your handoff useful.

## Hands-on Practice

Use a lab VM, container host, or disposable cloud instance.

1. Record interface and address state:

   ```bash
   ip -brief link
   ip -brief addr
   ```

2. Record the default route and one route decision:

   ```bash
   ip route show default
   ip route get 1.1.1.1
   ```

3. Compare DNS tools:

   ```bash
   dig example.com
   getent hosts example.com
   ```

4. Inspect local listening sockets:

   ```bash
   ss -tulpen
   ```

5. Write a short incident-style note:

   - interface used for default traffic
   - current local IP address
   - configured default gateway
   - resolver source
   - one listening TCP port
   - one next check you would run if HTTPS failed
