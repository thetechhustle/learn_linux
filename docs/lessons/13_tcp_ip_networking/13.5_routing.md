## 13.5 Routing: Mapping the Data Journey

Routing is how Linux decides where to send packets. A host can have a valid IP
address and working DNS but still fail because the route points to the wrong
interface, the wrong gateway, or a policy path that cannot reach the
destination.

When troubleshooting, routing answers one core question:

> If this host sends a packet to that destination, which path will the kernel
> choose?

## Read the Route Table

Start with the modern `ip` command:

```bash
ip route
ip -6 route
```

Typical IPv4 output might look like:

```text
default via 192.168.8.1 dev en0
192.168.8.0/24 dev en0 proto kernel scope link src 192.168.8.42
100.64.0.0/10 dev tailscale0 scope link
```

This tells you:

- traffic with no more-specific match uses the default gateway `192.168.8.1`
- local `192.168.8.0/24` traffic goes directly through `en0`
- Tailscale carrier-grade-NAT range traffic goes through `tailscale0`
- the preferred source address for local LAN traffic is `192.168.8.42`

Do not rely on old `route` output as your primary view. It is still present on
some systems, but `ip route` is clearer and matches the rest of modern Linux
networking.

## Ask the Kernel for One Decision

The fastest routing diagnostic is not reading every route. It is asking Linux
what it would do for one destination:

```bash
ip route get 1.1.1.1
ip route get 192.168.8.1
ip route get <internal-service-ip>
```

The output shows the selected route, interface, gateway, and source address.

Example:

```text
1.1.1.1 via 192.168.8.1 dev en0 src 192.168.8.42
```

That means Linux would send traffic for `1.1.1.1` to gateway `192.168.8.1`
through interface `en0`, using source address `192.168.8.42`.

If the source address or interface is wrong, the route may be the issue even if
the host has network connectivity.

## Longest Prefix Wins

Linux chooses the most specific matching route. This is called longest-prefix
match.

Given these routes:

```text
default via 192.168.8.1 dev en0
10.0.0.0/8 via 192.168.8.254 dev en0
10.20.30.0/24 dev wg0
10.20.30.55/32 dev lo
```

Traffic to:

- `8.8.8.8` uses the default route
- `10.5.1.20` uses `10.0.0.0/8`
- `10.20.30.40` uses `10.20.30.0/24`
- `10.20.30.55` uses the host route `/32`

More-specific routes override broader routes. This is why VPNs, containers, and
cloud routes can change traffic paths without changing the default route.

## Default Routes

The default route is the fallback for destinations that do not match a more
specific route.

Check it with:

```bash
ip route show default
ip -6 route show default
```

Common problems:

- no default route
- default route points at the wrong gateway
- default route uses the wrong interface
- multiple default routes compete unexpectedly
- VPN replaces the default route when split tunneling was expected

If there are multiple default routes, look at metrics:

```bash
ip route show default
```

Lower metric values usually win. NetworkManager, systemd-networkd, VPN clients,
and DHCP can all influence route metrics.

## Direct Routes and Gateways

A direct route sends packets onto a local link. A gateway route sends packets to
another device that forwards them.

Direct route example:

```text
192.168.8.0/24 dev en0 proto kernel scope link src 192.168.8.42
```

Gateway route example:

```text
default via 192.168.8.1 dev en0
```

For a gateway route to work, the gateway itself must be reachable on a directly
connected network. If Linux cannot reach the next hop, the route is not useful.

Check neighbor state:

```bash
ip neigh
```

If the gateway neighbor entry is failed or missing, investigate link, VLAN,
Wi-Fi, ARP, or IPv6 neighbor discovery before changing application settings.

## Policy Routing

Most small systems use one main routing table. More complex systems may use
policy routing, where Linux chooses a route table based on source address,
interface, firewall mark, or other rules.

Check rules with:

```bash
ip rule
ip route show table main
```

If `ip rule` shows extra tables, inspect them before assuming the main route
table explains everything:

```bash
ip route show table <table-name-or-number>
```

Policy routing is common with:

- VPNs
- containers
- multi-homed servers
- cloud hosts with multiple interfaces
- advanced firewall or traffic-shaping setups

## Containers, VPNs, and Overlays

Routing gets more interesting when extra network layers exist.

Examples:

- Docker may add bridge routes for container subnets.
- Kubernetes may install CNI routes.
- Tailscale or WireGuard may add tunnel routes.
- Cloud agents may add metadata or VPC routes.
- Virtualization tools may add NAT or bridge interfaces.

Use the same approach:

```bash
ip -brief addr
ip route
ip rule
ip route get <destination>
```

Then compare the host's route decision with the container, VM, or VPN control
plane's view.

## Tracing the Path

After Linux chooses a route, you can test how far packets travel.

Useful tools:

```bash
ping -c 3 <gateway-or-destination>
tracepath <destination>
traceroute <destination>
```

`tracepath` is often available without special privileges and can reveal MTU
issues along the path. `traceroute` may need installation or privileges,
depending on the system.

Remember that firewalls may block ICMP or traceroute probes even when the actual
application traffic works. Treat these tools as evidence, not absolute truth.

## Temporary Route Changes

Temporary route changes are useful in labs and during controlled incident
response. They do not usually survive reboot or network-manager reloads.

Examples:

```bash
sudo ip route add 203.0.113.0/24 via 192.168.8.1 dev en0
sudo ip route del 203.0.113.0/24 via 192.168.8.1 dev en0
```

Before changing routes on a remote host:

1. Confirm console or out-of-band access.
2. Record current routes:

   ```bash
   ip route
   ip rule
   ```

3. Keep the existing SSH session open.
4. Prefer adding a narrow route over changing the default route.
5. Test from another host.
6. Make the persistent change only after the temporary change is proven.

Changing the default route on the same path you are using for SSH can disconnect
you.

## Persistent Route Changes

Persistent routing depends on the system's network manager:

- NetworkManager connection profiles
- systemd-networkd `.network` files
- Netplan YAML
- distribution-specific interface files
- cloud-init network configuration
- container or orchestration networking config

Do not edit random files until you know which tool owns the interface. Check:

```bash
nmcli connection show
networkctl status
ls /etc/netplan 2>/dev/null
```

Only one system should own a given interface's persistent configuration.

## Incident Checklist

For routing incidents, collect:

```bash
ip -brief addr
ip route
ip -6 route
ip rule
ip route get <destination-ip>
ip neigh
tracepath <destination>
```

Then answer:

- Which interface did Linux choose?
- Which source address did Linux choose?
- Which gateway or next hop did Linux choose?
- Was there a more-specific route than the default route?
- Did policy routing affect the decision?
- Can the host reach the gateway?
- Does the path differ inside a container, VPN, or VM?

## Hands-on Practice

Use a lab VM, disposable cloud instance, or container host.

1. Record the route table:

   ```bash
   ip route
   ```

2. Ask Linux how it would reach a public address and your default gateway:

   ```bash
   ip route get 1.1.1.1
   ip route get <default-gateway-ip>
   ```

3. Inspect routing rules:

   ```bash
   ip rule
   ```

4. Trace a path:

   ```bash
   tracepath example.com
   ```

5. Write a short note that includes the selected interface, selected source
   address, default gateway, and one risk you would manage before changing a
   route remotely.
