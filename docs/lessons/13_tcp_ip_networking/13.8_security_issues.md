## 13.8 Security Issues

Network security starts with knowing what the host exposes, what paths traffic
can take, and what controls enforce the intended boundary. Do not begin with a
tool name. Begin with evidence.

For a Linux operator, the useful questions are:

- What is listening?
- Who can reach it?
- Is the traffic protected in transit?
- Which firewall or policy layer makes the decision?
- What logs or alerts would show abuse?
- What changed recently?

!!! abstract "What you will learn"
    - Inventory a host's exposure with `ss -tulpen` and interpret localhost, private, and all-address binds.
    - Reduce attack surface through bind addresses, TLS and SSH verification, and the firewall layer the host actually uses.
    - Recognize how NAT, VPNs, DHCP, and DNS change trust boundaries, and preserve evidence during a suspected incident.

## Start With Exposure

List listening sockets:

```bash
ss -tulpen
```

Focus on:

- `Local Address:Port`
- process name and PID
- whether the socket binds to `127.0.0.1`, a private address, or all addresses
- whether the protocol is TCP or UDP

Examples:

```text
127.0.0.1:5432
0.0.0.0:22
[::]:443
```

These mean different things:

- `127.0.0.1:5432` is local-only on IPv4
- `0.0.0.0:22` listens on all IPv4 interfaces
- `[::]:443` listens on IPv6 and may also accept IPv4 depending on system
  configuration

Pair socket evidence with route and interface evidence:

```bash
ip addr
ip route
ip -6 route
```

A service bound to all addresses on a laptop, cloud VM, or container host can
become reachable from more places than intended.

## Reduce Listening Surface

The strongest network control is often not exposing the service at all.

Before writing firewall rules, ask:

- Can the service bind only to localhost?
- Can the admin interface move to a private network or VPN?
- Can the feature be disabled?
- Can the port be restricted to a smaller interface or address family?

Configuration examples vary by service, but the pattern is common:

```text
listen_address = 127.0.0.1
bind = 10.0.10.20
```

After changing a bind address, prove it:

```bash
ss -tulpen
```

Then test from the network segment that should and should not have access.

## Encrypt Traffic in Transit

Encryption protects data from passive inspection and many active attacks. For
common services, prefer protocol-native TLS or SSH rather than custom
encryption commands.

Check a remote TLS service:

```bash
openssl s_client -connect example.com:443 -servername example.com
```

Useful things to inspect:

- certificate subject and issuer
- expiration date
- hostname match
- negotiated protocol and cipher
- whether the chain verifies

For SSH, check server reachability and host-key behavior:

```bash
ssh -v user@host
ssh-keygen -F host
```

Do not disable certificate or host-key verification to make an error disappear.
That usually removes the control that is protecting you.

## Understand Firewall Layers

Linux firewall policy may be managed by several tools:

- `nftables`
- `iptables` compatibility tooling
- `firewalld`
- `ufw`
- cloud security groups
- container runtime rules
- Kubernetes network policies

Identify the active local layer:

```bash
sudo nft list ruleset
sudo iptables -S
sudo firewall-cmd --state
sudo ufw status verbose
```

Use the tool your distribution or host already uses. Mixing firewall front ends
without understanding ownership can create confusing policy.

For a quick local view, combine sockets and firewall state:

```bash
ss -tulpen
sudo nft list ruleset
```

Then verify externally from the correct network:

```bash
nc -vz <host> <port>
nmap -Pn -p <port-list> <host>
```

Only scan systems you own or have permission to test.

## Legacy `iptables` Literacy

Many older systems still use `iptables`, but new designs should evaluate
`nftables` or a distribution front end such as `firewalld` or `ufw`.

Read rules safely:

```bash
sudo iptables -S
sudo iptables -t nat -S
```

Be careful with commands like:

```bash
sudo iptables -P INPUT DROP
```

Changing a default policy over SSH can disconnect you immediately if allow
rules are incomplete. Use a console, a tested rollback, or a timed safety job
when modifying remote firewall policy.

## NAT Is Not a Security Boundary

NAT changes addresses. It is not the same as a firewall.

Common NAT evidence:

```bash
ip route
sudo nft list ruleset
sudo iptables -t nat -S
```

NAT can hide internal addressing, but it does not replace:

- patching services
- authentication
- least-privilege firewall policy
- TLS or SSH
- logging and alerting

For containers and VMs, NAT rules may be created automatically. If a container
port is published to `0.0.0.0`, it may be reachable from outside the host even
when the service inside the container seems private.

Check containers:

```bash
docker ps
docker port <container>
```

## VPNs Change Trust Boundaries

A VPN can make remote systems appear local. That is useful, but it changes who
can reach internal services.

Inspect VPN effects:

```bash
ip addr
ip route
ip rule
resolvectl status
```

Check:

- new interfaces such as `tun0`, `wg0`, or `tailscale0`
- default-route changes
- split-tunnel routes
- DNS changes
- services now reachable from the VPN address range

Do not assume "behind VPN" means safe. VPN access still needs identity,
authorization, logging, and patching.

## DHCP and DNS Risks

DHCP and DNS can redirect traffic before it reaches the application.

DHCP risks:

- rogue DHCP server offers wrong gateway or DNS
- wrong VLAN or SSID gives the host an unexpected lease
- malicious or mistaken PXE options affect boot behavior

DNS risks:

- poisoned or compromised resolver
- wrong search domain expands names unexpectedly
- split-DNS points a name to different systems on and off VPN
- stale records send traffic to old infrastructure

Useful checks:

```bash
resolvectl status
dig example.com
dig @<resolver-ip> example.com
ip route get <destination-ip>
```

When security symptoms look strange, verify name resolution and routing before
changing application credentials.

## Intrusion Detection and Logging

Firewalls prevent or limit access. Detection tools help you notice suspicious
traffic.

Common options include:

- Suricata
- Zeek
- Snort
- host logs from `journald`, auditd, web servers, SSH, and firewalls

Start with the logs already present:

```bash
journalctl -u ssh --since "24 hours ago"
journalctl -p warning --since "24 hours ago"
sudo journalctl -k --since "24 hours ago"
```

Firewall logs depend on policy. If you add logging, rate-limit it. A noisy drop
rule can fill disks or hide the useful signal.

Packet capture can support incident response:

```bash
sudo tcpdump -ni <interface> host <ip-address>
sudo tcpdump -ni <interface> port <port>
```

Capture only what you need. Packets may contain sensitive data.

## Patch and Configuration Hygiene

Network security is not only packets. Old services and weak configs are common
entry points.

Check service versions:

```bash
systemctl --type=service --state=running
ss -tulpen
```

Then map exposed services to package ownership:

```bash
dpkg -S /path/to/binary
rpm -qf /path/to/binary
```

Keep a short exposure inventory:

```text
service: ssh
port: 22/tcp
bind: 0.0.0.0 and [::]
allowed from: VPN and admin LAN
owner: infrastructure
logs: journald
patch source: distro package
```

This turns "security" into something you can review and maintain.

## Incident Checklist

For a suspected network-security issue:

1. Preserve current evidence:

   ```bash
   date -Is
   hostnamectl
   ip addr
   ip route
   ss -tulpen
   ```

2. Identify exposed services and owning processes.
3. Check firewall and cloud/security-group policy.
4. Check recent auth and service logs.
5. Verify DNS and routes for affected names or IPs.
6. Capture packets only when needed and with a narrow filter.
7. Make the smallest containment change first.
8. Record what changed and how you verified the result.

Containment examples:

- stop a vulnerable service
- restrict a bind address
- remove a published container port
- add a narrow firewall deny or allow rule
- revoke a credential
- disable a compromised account

Avoid broad changes that destroy evidence or create a larger outage unless the
risk demands it.

## Hands-on Practice

Use a disposable VM or lab host.

1. List listening sockets with `ss -tulpen`.
2. Identify one service that listens only locally and one that listens on a
   network address.
3. Inspect the local firewall manager.
4. Check DNS resolver state.
5. Run a permitted port test from another host or VM.
6. Write a short exposure inventory for one service.
