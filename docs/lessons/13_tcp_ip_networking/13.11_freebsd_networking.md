## 13.11 FreeBSD Networking

FreeBSD networking feels familiar if you already understand TCP/IP, routes, DNS,
and firewalls. The operational surface is different, though. Linux lessons lean
on `ip`, `ss`, `systemctl`, and NetworkManager. FreeBSD usually leans on
`ifconfig`, `route`, `netstat`, `sockstat`, `service`, `/etc/rc.conf`, and
often `pf`.

That distinction matters during incidents. Copying a Linux command into a
FreeBSD shell wastes time and can hide the actual fault. A good FreeBSD network
workflow starts with the same questions as Linux work, but gathers evidence with
the native tools.

!!! abstract "What you will learn"
    - Inspect FreeBSD interfaces, addresses, routes, DNS, sockets, and firewall state.
    - Make temporary and persistent network changes without confusing the two.
    - Restart FreeBSD network services deliberately.
    - Recognize common FreeBSD-specific trouble spots around aliases, VLANs, jails, and `pf`.

!!! success "Operator principle"
    FreeBSD separates live kernel state from persistent boot-time configuration. Prove both before you call a network change complete.

## Start with the interface

Use `ifconfig` as your first view of FreeBSD link and address state:

```console
$ ifconfig
$ ifconfig em0
```

Look for:

- `status: active` or `status: no carrier`
- the interface name, such as `em0`, `igb0`, `re0`, `vtnet0`, `bge0`, or `lo0`
- `inet` IPv4 addresses and prefix lengths
- `inet6` IPv6 addresses
- `ether` MAC address
- flags such as `UP`, `RUNNING`, `PROMISC`, and `SIMPLEX`
- VLAN, bridge, lagg, or jail-related interfaces

Example:

```console
$ ifconfig em0
em0: flags=8863<UP,BROADCAST,RUNNING,SIMPLEX,MULTICAST> metric 0 mtu 1500
        options=481209b<RXCSUM,TXCSUM,VLAN_MTU,VLAN_HWTAGGING,VLAN_HWCSUM,WOL_MAGIC>
        ether 00:25:90:12:34:56
        inet 192.0.2.25 netmask 0xffffff00 broadcast 192.0.2.255
        media: Ethernet autoselect (1000baseT <full-duplex>)
        status: active
```

If the interface has no carrier, stop chasing DNS and routing. Check the cable,
switch port, hypervisor NIC attachment, VLAN tag, or cloud console attachment
first.

## Read the route table

Show the routing table with `netstat`:

```console
$ netstat -rn
```

The default route is the line with `default` as the destination:

```text
Destination        Gateway            Flags     Netif Expire
default            192.0.2.1          UGS         em0
192.0.2.0/24       link#1             U           em0
192.0.2.25         link#1             UHS         lo0
```

For a single destination, ask the kernel which route it will use:

```console
$ route -n get 8.8.8.8
$ route -n get 192.0.2.80
```

Useful fields include `gateway`, `interface`, and `flags`. If the interface or
gateway is wrong, you have a routing problem, not an application problem.

## Check DNS separately

FreeBSD normally reads resolver configuration from `/etc/resolv.conf`:

```console
$ cat /etc/resolv.conf
```

Use DNS tools to separate name resolution from connectivity:

```console
$ host example.com
$ drill example.com
```

If `ping 8.8.8.8` works but `host example.com` fails, the host has a DNS
problem. If neither works, continue with routes, gateways, link state, and
firewall state.

## Inspect listening services

FreeBSD does not use Linux `ss` by default. Use `sockstat` and `netstat`:

```console
$ sockstat -4 -6 -l
$ netstat -an | less
```

Common checks:

- Is the service listening on the expected port?
- Is it bound to `127.0.0.1` only when clients need a network address?
- Is it listening on IPv6 only?
- Is the jail or host namespace you are checking the one that owns the socket?

For example:

```console
$ sockstat -4 -l | grep ':80'
www      nginx      1462  7  tcp4   *:80                  *:*
```

This proves a process is listening. It does not prove a firewall, route, or
upstream load balancer allows traffic to reach it.

## Separate temporary changes from persistent changes

A temporary address change updates live kernel state:

```console
# ifconfig em0 inet 192.0.2.25/24
# route add default 192.0.2.1
```

Those changes may disappear at reboot or when network services restart.
Persistent interface configuration usually lives in `/etc/rc.conf`:

```conf
hostname="freebsd-lab-01"
ifconfig_em0="inet 192.0.2.25 netmask 255.255.255.0"
defaultrouter="192.0.2.1"
```

DHCP is also configured through `/etc/rc.conf`:

```conf
ifconfig_em0="DHCP"
```

After editing persistent configuration, restart deliberately:

```console
# service netif restart em0
# service routing restart
```

On remote systems, restarting the network can cut off your shell. Prefer an
out-of-band console, a timed rollback, or a second confirmed access path before
changing interface, route, or firewall configuration.

## Add aliases and VLANs carefully

FreeBSD commonly uses aliases for extra addresses:

```conf
ifconfig_em0="inet 192.0.2.25 netmask 255.255.255.0"
ifconfig_em0_alias0="inet 192.0.2.26 netmask 255.255.255.255"
```

VLAN interfaces are also common on servers and firewalls:

```conf
vlans_em0="20"
ifconfig_em0_20="inet 198.51.100.10 netmask 255.255.255.0"
```

When a host can reach one network but not another, confirm that the packet is
leaving through the expected physical interface and VLAN:

```console
$ ifconfig
$ netstat -rn
$ tcpdump -ni em0 vlan
```

## Check the firewall

Many FreeBSD systems use `pf`, though `ipfw` and `ipfilter` may also appear.
First identify what is enabled:

```console
$ grep -E '^(pf|ipfw|ipfilter)_enable=' /etc/rc.conf
```

For `pf`, inspect the live rules and state:

```console
# pfctl -s info
# pfctl -sr
# pfctl -ss
```

Use counters and state to answer concrete questions:

- Is `pf` enabled?
- Does a rule allow the expected source, destination, protocol, and port?
- Is there existing state for the connection?
- Are packets blocked before they reach the service?

Avoid flushing or disabling a production firewall as a first move. If you need a
test, add a narrow, temporary rule through a console or maintenance window, then
remove it after proving the result.

## Remember jails and VNET

FreeBSD jails can use host networking or their own VNET network stack. That
changes where you must look for truth.

Start from the host:

```console
$ jls
$ jexec <jid> ifconfig
$ jexec <jid> netstat -rn
$ jexec <jid> sockstat -4 -6 -l
```

If a service runs inside a jail:

- check whether the jail has the expected address
- confirm the jail route table if it uses VNET
- confirm the host firewall is not blocking forwarded or bridged traffic
- confirm the service is bound inside the jail, not only on the host

Do not assume a socket visible on the host is the same as a socket inside the
jail.

## Use tcpdump as the tie-breaker

When route, DNS, service, and firewall evidence disagree, capture packets:

```console
# tcpdump -ni em0 host 192.0.2.80
# tcpdump -ni em0 tcp port 443
# tcpdump -ni em0 icmp
```

Ask one question at a time:

- Do outbound packets leave the expected interface?
- Do replies return?
- Does the source address match what the peer expects?
- Is traffic tagged with the expected VLAN?
- Does the firewall create or deny state?

Packet evidence turns vague complaints like "networking is down" into a
specific failure: no carrier, no route, bad DNS, service not listening, firewall
drop, asymmetric routing, or upstream loss.

## Safe FreeBSD network incident workflow

Use this order during a real incident:

1. Confirm the interface is up and has carrier: `ifconfig`.
2. Confirm the address and subnet are correct: `ifconfig em0`.
3. Confirm the default and destination routes: `netstat -rn`, `route -n get <target>`.
4. Test IP reachability before DNS: `ping <gateway>`, `ping <known-ip>`.
5. Test DNS separately: `host <name>` or `drill <name>`.
6. Confirm the service is listening: `sockstat -4 -6 -l`.
7. Inspect firewall state and rules: `pfctl -s info`, `pfctl -sr`, `pfctl -ss`.
8. Use `tcpdump` to prove packet direction and loss point.
9. Apply the smallest reversible change.
10. Update `/etc/rc.conf` only after the live fix is proven and intended to survive reboot.

## Hands-on practice

Run these on a disposable FreeBSD VM or lab machine.

1. Record interface, route, DNS, socket, and firewall evidence:
   ```console
   $ ifconfig
   $ netstat -rn
   $ route -n get 8.8.8.8
   $ cat /etc/resolv.conf
   $ sockstat -4 -6 -l
   ```
2. Identify which values come from live kernel state and which should be made
   persistent in `/etc/rc.conf`.
3. Add a temporary alias on a lab interface, then remove it:
   ```console
   # ifconfig em0 alias 192.0.2.50/32
   # ifconfig em0 -alias 192.0.2.50
   ```
4. Explain how you would safely make that alias persistent if it were required.
5. Capture a short `tcpdump` while pinging the default gateway and describe what
   each packet proves.
