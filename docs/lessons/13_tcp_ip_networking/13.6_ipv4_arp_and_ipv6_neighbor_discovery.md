## 13.6 - IPv4 ARP and IPv6 Neighbor Discovery

ARP and IPv6 Neighbor Discovery answer a simple local-network question:
which link-layer address should receive the next Ethernet frame?

Routing chooses the next IP hop. ARP or Neighbor Discovery then maps that
next-hop IP address to a MAC address on the local link. When this mapping is
missing, stale, or blocked, a host can have the right IP address, default
route, and DNS answer but still fail to reach a machine on the same VLAN or
the configured gateway.

!!! abstract "What you will learn"
    - Explain how IPv4 ARP and IPv6 Neighbor Discovery connect IP routing to Ethernet delivery.
    - Inspect neighbor-cache entries with modern Linux commands.
    - Recognize stale, failed, incomplete, and suspicious neighbor entries during an incident.
    - Refresh neighbor state safely before changing interface, routing, or firewall configuration.

!!! example "Field story"
    A container host can reach the internet but cannot reach an internal
    service on the same subnet. DNS returns the expected address and the route
    points out the correct interface. The next useful evidence is the neighbor
    cache: does the host know the service's MAC address, and is that mapping
    still valid?

!!! success "Operator principle"
    Treat ARP and Neighbor Discovery as local-link evidence. If the neighbor
    cache is broken, higher-level tools such as `curl`, `ssh`, and package
    managers will fail in misleading ways.

## The Local-Link Job

For an IPv4 destination on the same subnet, the sender broadcasts an ARP
request such as "who has 192.0.2.25?" The owner of that address replies with
its MAC address. The sender caches the mapping and uses it until the entry
expires or is refreshed.

For a destination outside the local subnet, the sender does not ARP for the
remote server. It ARPs for the default gateway or the route-selected next hop,
then sends the frame to that router's MAC address.

IPv6 uses Neighbor Discovery instead of ARP. Neighbor Discovery is built on
ICMPv6 and handles neighbor solicitation, neighbor advertisement, router
discovery, duplicate-address detection, and some reachability tracking.

## Inspect Neighbor State

Use `ip neigh` for both IPv4 and IPv6 neighbor-cache inspection.

```bash
ip neigh show
ip -4 neigh show
ip -6 neigh show
```

Common fields include the neighbor IP address, the interface, the learned MAC
address, and a state such as `REACHABLE`, `STALE`, `DELAY`, `PROBE`,
`INCOMPLETE`, or `FAILED`.

```text
192.0.2.1 dev eth0 lladdr 52:54:00:12:34:56 REACHABLE
192.0.2.25 dev eth0 lladdr 52:54:00:aa:bb:cc STALE
2001:db8::1 dev eth0 lladdr 52:54:00:12:34:56 router REACHABLE
```

`STALE` does not always mean broken. It often means the entry has not been
used recently and will be verified when traffic resumes. `INCOMPLETE` and
`FAILED` are stronger signs that the host cannot resolve or verify the
neighbor.

## Match Neighbor Evidence to Routes

Always compare neighbor state with the selected route. The neighbor entry that
matters is usually the route-selected next hop, not necessarily the final
destination.

```bash
ip route get 192.0.2.25
ip route get 198.51.100.10
ip -6 route get 2001:db8::25
```

If the destination is local, expect a neighbor entry for the destination
itself. If the destination is remote, expect a neighbor entry for the gateway.
When `ip route get` chooses an unexpected interface or source address, fix
that routing problem before clearing neighbor entries.

## Troubleshooting Patterns

Start with read-only evidence. Replace the sample addresses with the gateway
or lab host you are investigating.

```bash
ip link show
ip address show
ip route show
ip neigh show dev eth0
ping -c 3 192.0.2.1
ping -c 3 192.0.2.25
```

For IPv6, remember that ICMPv6 is required for normal network operation.
Blocking all ICMPv6 can break Neighbor Discovery, path MTU discovery, and
router discovery.

```bash
ip -6 address show
ip -6 route show
ip -6 neigh show dev eth0
ping -6 -c 3 2001:db8::1
```

Look for these common failures:

- `INCOMPLETE` for the gateway: the host is asking but not receiving a usable reply.
- `FAILED` for a local service: the target may be down, on another VLAN, blocked, or using a different address.
- The same IP address appears with changing MAC addresses: possible duplicate IP address, failover event, or spoofing.
- The expected gateway MAC is missing after a network move: stale state, VLAN mismatch, or switch-port issue.
- IPv6 has no router entry: router advertisements may be absent or blocked.

## Refresh Neighbor State Safely

Prefer targeted refreshes over broad network changes. Re-run traffic to the
specific destination first:

```bash
ping -c 3 192.0.2.25
ip neigh show 192.0.2.25
```

If an entry is clearly stale or wrong, delete only that entry and let the
kernel relearn it:

```bash
sudo ip neigh del 192.0.2.25 dev eth0
ping -c 3 192.0.2.25
ip neigh show 192.0.2.25
```

Avoid flushing the entire neighbor table on a production host unless you have
a rollback window and understand the blast radius. A full flush can briefly
disrupt active connections while the host relearns neighbors.

## Security and Operations Notes

ARP has no built-in authentication. A malicious or misconfigured host on the
same layer-2 network can claim another host's IPv4 address. IPv6 Neighbor
Discovery has stronger structure, but it still depends on local-link trust
unless additional controls are deployed.

Useful network-side controls include DHCP snooping, dynamic ARP inspection,
RA guard, port security, and sensible VLAN boundaries. On the Linux host,
your best first response is usually evidence collection: neighbor entries,
routes, interface state, switch-port context, and timestamps.

## Hands-On Practice

Run this on a disposable VM, lab machine, or non-production subnet.

1. Record interface, address, route, and neighbor state.

   ```bash
   ip -brief link
   ip -brief address
   ip route show
   ip neigh show
   ```

2. Pick your default gateway and confirm which neighbor entry is used.

   ```bash
   ip route show default
   ip route get 1.1.1.1
   ip neigh show
   ```

3. Generate traffic to the gateway or another lab host.

   ```bash
   GW=$(ip route show default | awk '{print $3; exit}')
   ping -c 3 "$GW"
   ip neigh show "$GW"
   ```

4. Delete one lab neighbor entry and watch it return.

   ```bash
   IFACE=$(ip route show default | awk '{print $5; exit}')
   sudo ip neigh del "$GW" dev "$IFACE"
   ping -c 3 "$GW"
   ip neigh show "$GW"
   ```

5. Write a short incident note: selected route, relevant neighbor entry,
   state before and after the refresh, and whether the evidence points to the
   host, the local link, or the gateway.
