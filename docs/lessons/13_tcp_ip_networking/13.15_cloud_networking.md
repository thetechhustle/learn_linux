### 13.15 Cloud Networking

Cloud networks still move packets with addresses, routes, names, and filters. The difference is that many of the control points live outside the Linux host: virtual networks, subnets, route tables, gateways, security groups, network ACLs, load balancers, private DNS zones, and managed firewalls. Good troubleshooting connects both views instead of staring at only the VM.

!!! abstract "What you will learn"
    - Map common cloud-networking objects to the Linux evidence they affect.
    - Inspect a cloud VM's addresses, routes, DNS, sockets, and firewall state before changing provider settings.
    - Separate host misconfiguration from subnet, route table, security group, network ACL, DNS, and load balancer issues.
    - Plan low-risk cloud network changes with rollback notes and verification commands.

!!! example "Field story"
    A container host can reach the internet but cannot reach an internal database endpoint. The fix might be a wrong route table, a missing security-group rule, a DNS name resolving to the wrong address, or a host firewall. Your job is to gather enough evidence to change the right layer.

!!! success "Operator principle"
    Prove the packet path from the Linux host outward: interface, address, route, DNS, socket, local firewall, cloud filter, gateway, and destination.

## Cloud Objects and Linux Evidence

Cloud providers use different product names, but the operational ideas are similar.

| Cloud object | What it controls | Linux evidence to compare |
| --- | --- | --- |
| Virtual network, VPC, or VNet | The private address space for a group of resources | `ip address`, `ip route`, instance metadata |
| Subnet | The smaller address range attached to a zone or availability domain | Interface address, default gateway, route table association |
| Route table | Where traffic goes next | `ip route get DESTINATION`, traceroute output |
| Internet gateway or NAT gateway | Internet ingress or egress path | Public IP, source NAT behavior, outbound connection tests |
| Security group | Stateful instance or interface firewall rules | Listening sockets, expected source and destination ports |
| Network ACL | Stateless subnet-level allow or deny rules | Failed return traffic, asymmetric allow rules |
| Private DNS zone | Internal names for services | `resolvectl`, `dig`, `getent hosts` |
| Load balancer | Front door for one or more backends | Health checks, backend listener ports, access logs |
| Private endpoint or peering | Private path to a managed service or another network | Route selection, DNS target address, provider attachment state |

Do not assume a provider console is correct just because a diagram looks right. Capture the Linux view and the provider view, then compare them.

## Start From the Host

Begin with read-only commands on the affected VM. These commands show whether the host received the expected network identity and where it will send traffic.

```bash
hostname -f
ip -brief address
ip route
ip route get 10.20.30.40
resolvectl status 2>/dev/null || cat /etc/resolv.conf
ss -tulpen
```

Record:

- The interface name and private address.
- The default route and gateway.
- The route chosen for the destination you are testing.
- The DNS servers and search domains in use.
- The local service ports that are listening.

If the route selected by `ip route get` does not match the expected subnet, VPN, peering, or private endpoint path, pause before editing application config. The network path is already suspect.

## Check Name Resolution

Cloud networking failures often look like application failures because a name resolves to an unexpected address. Test the name and the connection separately.

```bash
getent hosts internal-db.example
dig +short internal-db.example
ip route get "$(getent hosts internal-db.example | awk 'NR==1 {print $1}')"
```

Look for these patterns:

- An internal service name resolves to a public address when it should resolve privately.
- A private endpoint name resolves to an address in the wrong region or virtual network.
- The host uses a public resolver instead of the provider or organization resolver.
- Split-horizon DNS returns different answers from different subnets.

When DNS is wrong, fix the zone association, resolver forwarding rule, or search-domain policy before changing firewalls.

## Security Groups and Network ACLs

Security groups are usually stateful. If inbound traffic is allowed, return traffic for that connection is allowed automatically. Network ACLs are often stateless, so both request and response directions must be allowed. That difference matters during incident response.

Ask four questions:

1. Is the source address you expect actually the source address the destination sees?
2. Is the destination listening on the expected port?
3. Does the destination security group allow that source and port?
4. Does any subnet-level ACL block either request traffic or return traffic?

Use Linux to prove the host side:

```bash
ss -tnp
nc -vz internal-db.example 5432
curl -v --connect-timeout 5 http://internal-service:8080/health
```

Use provider tooling or the console to prove the cloud side. Prefer describe/list commands before edit commands. For example, on AWS:

```bash
aws ec2 describe-instances --instance-ids i-0123456789abcdef0
aws ec2 describe-security-groups --group-ids sg-0123456789abcdef0
aws ec2 describe-network-acls --filters Name=association.subnet-id,Values=subnet-0123456789abcdef0
```

Do not paste production account IDs, public IPs, hostnames, or internal CIDR plans into public tickets. Summarize the relevant rule shape instead.

## Routes, Gateways, and Private Paths

A cloud VM can have a perfect Linux route table and still fail because the subnet route table points to the wrong next hop. Compare the two layers.

Common route failures:

- The subnet route table sends private service traffic to an internet gateway instead of a private endpoint, NAT gateway, VPN, or peering attachment.
- Return traffic uses a different path and is dropped by stateful devices.
- Peered networks have overlapping CIDR blocks, so a route cannot be installed cleanly.
- A managed service endpoint requires both a private DNS association and a private route.
- Egress-only hosts depend on a NAT gateway that has failed, hit a quota, or lacks an allowed route.

From Linux, test the selected route and first hops:

```bash
ip route get 10.20.30.40
tracepath 10.20.30.40
traceroute -T -p 443 internal-api.example 2>/dev/null || true
```

Some cloud networks do not reveal every hop. A trace that stops early is evidence, not proof by itself. Combine it with provider route-table and flow-log data.

## MTU and Encapsulation

VPNs, overlays, tunnels, and load balancers can reduce the usable maximum transmission unit. Small packets work, but large transfers stall or reset.

Check the interface MTU:

```bash
ip link show
tracepath internal-service.example
```

If you suspect an MTU problem, test in a lab or maintenance window. Lowering MTU on production interfaces can disrupt active connections. Prefer confirming the path MTU, tunnel configuration, and provider recommendations before making persistent changes.

## Use Flow Logs and Load Balancer Logs

Provider flow logs are useful when Linux evidence says "the packet left" but the destination never responds. They can show accepted traffic, rejected traffic, source addresses after NAT, and which interface saw a flow.

For a blocked connection, capture:

- Source private IP and port.
- Destination private IP and port.
- Protocol.
- Timestamp with timezone.
- Cloud interface, subnet, or load balancer name.
- Whether the provider log shows allow, deny, timeout, or no record.

"No record" is also useful. It often means the traffic never reached that provider boundary, DNS pointed somewhere else, or the source host did not send what you thought it sent.

## Safer Change Pattern

Cloud network edits can disconnect whole fleets. Use a narrow change workflow.

1. State the symptom in one sentence.
2. Save host evidence: `ip address`, `ip route get DESTINATION`, DNS answer, and connection test.
3. Save provider evidence: subnet route table, security group, ACL, load balancer target health, or endpoint status.
4. Change one rule, route, association, or DNS record.
5. Verify the exact failing path.
6. Record rollback: the previous rule, route, association, or DNS value.
7. Remove temporary broad rules after the incident.

Avoid emergency rules such as "allow all from 0.0.0.0/0" unless there is a documented break-glass process and a timed cleanup owner.

## Troubleshooting Patterns

| Symptom | Likely layer | First evidence |
| --- | --- | --- |
| VM has no private address | DHCP, subnet attachment, interface state | `ip -brief address`, metadata, provider NIC status |
| Internet works but private service fails | Route, security group, DNS, peering | `ip route get`, `getent hosts`, provider route table |
| Private name resolves publicly | DNS zone or resolver association | `dig`, resolver config, private zone links |
| Connection times out | Firewall, route, ACL, destination listener | `nc -vz`, flow logs, `ss -tulpen` |
| Connection refused | Destination host reached but service not listening | `ss -tulpen`, service logs |
| Large transfers hang | MTU, tunnel, load balancer | `tracepath`, interface MTU, tunnel settings |
| Works from one subnet but not another | Route-table association, ACL, DNS scope | subnet route tables and ACL associations |

## Hands-On Practice

Use a disposable cloud VM or a local lab that simulates separate subnets. Do not run these steps on a production network.

1. Capture the host network baseline:

   ```bash
   ip -brief address
   ip route
   resolvectl status 2>/dev/null || cat /etc/resolv.conf
   ```

2. Pick one reachable endpoint and one intentionally unreachable endpoint. For each endpoint, record:

   ```bash
   getent hosts ENDPOINT
   ip route get ENDPOINT_IP
   nc -vz ENDPOINT PORT
   ```

3. In the provider console or CLI, inspect the subnet route table and security group for the VM. Do not change anything yet.

4. Make one reversible lab change, such as removing a temporary inbound rule from a test security group or restoring one that you intentionally removed.

5. Re-run the same Linux commands and explain whether the failure moved from "timeout" to "connected," "refused," or "same as before."

6. Write a handoff note with the symptom, commands, provider object inspected, change made, verification, and rollback.
