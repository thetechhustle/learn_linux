## 13.13 Network Monitoring

Network monitoring turns "the network is slow" into evidence. It shows whether
packets are leaving the host, whether replies are coming back, whether a service
is listening, whether an interface is dropping frames, and whether latency or
loss changed over time.

Good monitoring is not a pile of dashboards. It is a set of small, trusted
signals that help you answer better questions during an incident.

!!! abstract "What you will learn"
    - Separate host-level monitoring from network-path and service monitoring.
    - Use Linux tools to inspect interface counters, sockets, bandwidth, packets, and logs.
    - Capture enough evidence to prove loss, latency, saturation, DNS failure, or service exposure.
    - Design alerts that catch real risk without paging on harmless noise.

!!! success "Operator principle"
    Monitor symptoms and causes separately: user-visible reachability, host resource pressure, interface health, route/DNS behavior, and packet evidence all answer different questions.

## Start with the monitoring question

Before choosing a tool, name the question:

- Is the host reachable?
- Is the service listening?
- Are clients reaching the host?
- Is the interface dropping packets?
- Is bandwidth saturated?
- Did latency or packet loss increase?
- Is DNS failing?
- Is a firewall or route blocking the path?

Different questions need different evidence. A successful `ping` does not prove
HTTPS is healthy. An open TCP socket does not prove clients can reach it. A full
bandwidth graph does not prove which application caused the traffic.

## Watch interface counters

Interface counters reveal local link symptoms:

```console
$ ip -s link show dev eth0
$ cat /proc/net/dev
```

Look for:

- `RX` and `TX` packet counts increasing
- errors
- dropped packets
- overruns
- carrier changes
- unexpected interface resets

Example:

```console
$ ip -s link show dev eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc mq state UP mode DEFAULT group default qlen 1000
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
    RX: bytes  packets  errors  dropped missed  mcast
    987654321  812345   0       0       0       45
    TX: bytes  packets  errors  dropped carrier collsns
    123456789  456789   0       0       0       0
```

Counters are most useful when compared over time. A single snapshot tells you
state; repeated snapshots tell you direction.

```console
$ watch -n 2 'ip -s link show dev eth0'
```

If drops or errors rise during a complaint window, check NIC drivers, virtual NIC
limits, switch ports, duplex/speed negotiation, host CPU pressure, queue sizing,
and packet bursts.

## Monitor sockets and listeners

Use `ss` to prove what the host is listening on:

```console
$ ss -lntup
$ ss -tan state established
```

Useful checks:

- Is the expected port listening?
- Is it bound to `127.0.0.1`, a private address, or `0.0.0.0`?
- Are many connections stuck in `SYN-SENT`, `SYN-RECV`, `TIME-WAIT`, or `CLOSE-WAIT`?
- Which process owns the socket?

Examples:

```console
$ ss -lntp 'sport = :443'
$ ss -tan state syn-recv
$ ss -tan '( dport = :5432 or sport = :5432 )'
```

Socket state is local evidence. If the service is listening but clients still
fail, continue with firewall, route, DNS, and packet evidence.

## Track bandwidth by interface and process

Use lightweight tools for a quick view:

```console
$ iftop -i eth0
$ nload eth0
$ bmon
```

Use process-oriented tools when you need ownership:

```console
$ nethogs eth0
```

On servers where those tools are not installed, start with standard counters:

```console
$ sar -n DEV 1 5
$ sar -n TCP,ETCP 1 5
```

The `sar` command comes from the `sysstat` package on many distributions. It is
especially useful because it can keep historical samples for later review.

Bandwidth monitoring should answer:

- Which interface is busy?
- Is traffic inbound, outbound, or both?
- Did the spike align with user complaints?
- Is the traffic expected backup, replication, deployment, media, or abuse?
- Is the host limited by network, CPU, disk, or upstream service latency?

## Capture packets when counters are not enough

Use `tcpdump` when you need to prove what crossed the interface:

```console
# tcpdump -ni eth0 host 192.0.2.50
# tcpdump -ni eth0 tcp port 443
# tcpdump -ni eth0 'icmp or arp'
```

Capture to a file for later analysis:

```console
# tcpdump -ni eth0 -s 0 -w incident-eth0.pcap host 192.0.2.50
```

Keep captures narrow:

- interface: `-i eth0`
- host: `host 192.0.2.50`
- port: `tcp port 443`
- direction when useful: `src`, `dst`
- protocol: `icmp`, `arp`, `udp`, `tcp`

Packet capture answers questions that dashboards cannot:

- Did the client SYN arrive?
- Did the server reply with SYN-ACK?
- Did DNS queries leave the host?
- Did ARP or neighbor discovery resolve the gateway?
- Are replies coming back on a different interface?
- Is traffic retransmitting?

Be careful with packet captures. They can include secrets, customer data, tokens,
cookies, and private traffic. Capture the smallest useful filter, store files
securely, and delete captures when retention is no longer justified.

## Probe services from the outside

Host metrics are not enough. Monitor the path users actually take:

```console
$ curl -fsS https://example.com/health
$ curl -w '%{http_code} %{time_connect} %{time_starttransfer} %{time_total}\n' -o /dev/null -s https://example.com/
$ nc -vz example.com 443
```

For ICMP and path checks:

```console
$ ping -c 5 192.0.2.1
$ traceroute example.com
$ mtr -rw example.com
```

For DNS:

```console
$ dig example.com
$ dig @1.1.1.1 example.com
```

External probes catch problems that local host checks miss:

- bad DNS records
- expired certificates
- firewall blocks
- load balancer health-check failures
- CDN or edge routing issues
- regional packet loss
- asymmetric paths

## Use logs as monitoring signals

Network symptoms often appear in logs before a dashboard looks dramatic:

```console
$ journalctl -u NetworkManager --since '30 minutes ago'
$ journalctl -k --since '30 minutes ago' | grep -Ei 'eth|link|drop|reset|timeout'
$ journalctl -u nginx --since '30 minutes ago'
$ journalctl -u ssh --since '30 minutes ago'
```

Depending on the distribution and service, also check:

```console
$ tail -f /var/log/syslog
$ tail -f /var/log/messages
$ tail -f /var/log/nginx/access.log
$ tail -f /var/log/nginx/error.log
```

Useful log signals include:

- link up/down events
- DHCP renew failures
- DNS resolver errors
- firewall denies
- TLS handshake failures
- connection resets
- backend timeout errors
- load balancer health-check failures

Logs help connect packet symptoms to application impact.

## Know what to alert on

Alert on user impact and durable risk, not every noisy metric.

Good alert candidates:

- public health check fails from more than one location
- sustained packet loss to a critical dependency
- interface errors or drops increasing quickly
- default route disappears
- DNS resolution fails for a critical hostname
- certificate expiration is approaching
- firewall deny rate spikes for an expected service
- TCP connection failures rise sharply
- bandwidth saturation persists long enough to affect users

Weak alert candidates:

- one failed ping
- one short bandwidth spike
- any single dropped packet
- CPU or bandwidth briefly above a round number
- logs that always appear during normal deploys

Every alert should have:

- a human-readable symptom
- the affected host, service, and interface when known
- a threshold and duration
- a link to graphs or logs
- a first diagnostic command
- an owner or escalation path

## Build a small monitoring baseline

For a single Linux host, a useful baseline might include:

- uptime and reachability from outside the host
- HTTP health-check status and response time
- DNS resolution for the service name
- interface RX/TX bytes, errors, and drops
- TCP connection states
- service listen ports
- firewall deny counters
- key service logs
- certificate expiration

For a multi-host service, add:

- load balancer health per backend
- per-region latency and error rate
- dependency reachability
- packet loss between service tiers
- saturation on NAT gateways, VPNs, tunnels, or overlays
- container or virtual-network interface counters

The goal is not to monitor everything. The goal is to preserve enough evidence
to tell whether the fault is local host, local service, network path, name
resolution, firewall, upstream dependency, or client-side behavior.

## Incident workflow

When a network incident starts:

1. Confirm the user-facing symptom with an external probe.
2. Check the service listener with `ss -lntup`.
3. Check interface health with `ip -s link`.
4. Check current routes with `ip route` and `ip route get <target>`.
5. Check DNS with `dig` against the normal resolver and a known public resolver.
6. Check logs from the network manager, kernel, firewall, and service.
7. Capture packets with a narrow `tcpdump` filter.
8. Compare current metrics to a normal baseline.
9. Apply the smallest reversible fix.
10. Keep the evidence that explains the failure and the recovery.

## Hands-on practice

Run these on a disposable VM or lab host.

1. Record a baseline:
   ```console
   $ ip -s link
   $ ss -lntup
   $ ip route
   $ dig example.com
   ```
2. Watch interface counters while generating test traffic:
   ```console
   $ watch -n 2 'ip -s link show dev eth0'
   ```
3. Run a narrow packet capture while making a request:
   ```console
   # tcpdump -ni eth0 tcp port 443
   ```
4. Use `curl` timing output to capture service latency:
   ```console
   $ curl -w '%{http_code} connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n' -o /dev/null -s https://example.com/
   ```
5. Write a short incident note that separates symptoms, evidence, likely cause,
   and next command.
