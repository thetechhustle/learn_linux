## 13.9 Basic Network Configuration

Network configuration is the point where the earlier TCP/IP ideas become operational. An address, route, DNS setting, or interface state can be correct in isolation and still produce a broken system if the pieces do not agree.

!!! abstract "What you will learn"
    - Inspect a host's current interface, address, route, DNS, and manager state before changing anything.
    - Distinguish temporary `ip` command changes from persistent configuration managed by NetworkManager, netplan, or systemd-networkd.
    - Apply a low-risk static or DHCP configuration plan and verify the result from the host's point of view.
    - Capture enough evidence to roll back or hand off a network change during an incident.

!!! example "Field story"
    A container host can reach the internet, but containers cannot reach an internal package mirror. The host has an address, but the default route and DNS resolver came from the wrong VLAN. You need to identify the active interface, prove which manager owns it, make one reversible change, and verify both internet and internal connectivity.

!!! success "Operator principle"
    Change only the layer you have evidence for: link, address, route, DNS, or firewall.

## Start with read-only evidence

Begin by recording what the system believes right now. These commands do not change network state:

```bash
ip -brief link
ip -brief address
ip route
ip route get 8.8.8.8
resolvectl status 2>/dev/null || cat /etc/resolv.conf
nmcli device status 2>/dev/null || true
networkctl status 2>/dev/null || true
```

Look for five things:

- **Interface state:** the relevant device is `UP` and has carrier when it should.
- **Address:** the interface has the expected IPv4 or IPv6 address and prefix length.
- **Default route:** traffic to off-link destinations uses the intended gateway.
- **DNS resolver:** name lookups use the intended resolver and search domain.
- **Configuration owner:** NetworkManager, systemd-networkd, netplan, distro scripts, or cloud-init may be managing the device.

Do not edit a random file just because it exists. Modern distributions often ignore older files such as `/etc/network/interfaces` or `/etc/sysconfig/network-scripts/ifcfg-*` unless that specific networking stack is active.

## Temporary changes with `ip`

The `ip` command is useful for lab tests and emergency changes because most changes disappear after reboot or service restart. Use a disposable VM or maintenance window for practice:

```bash
sudo ip link set dev ens3 up
sudo ip address add 192.0.2.50/24 dev ens3
sudo ip route replace default via 192.0.2.1 dev ens3
```

Verify immediately:

```bash
ip -brief address show dev ens3
ip route get 192.0.2.10
ping -c 3 192.0.2.1
```

Rollback is also explicit:

```bash
sudo ip address del 192.0.2.50/24 dev ens3
sudo ip route del default via 192.0.2.1 dev ens3
```

Temporary commands are not a substitute for persistent configuration. They are a safe way to prove a hypothesis before writing files or changing a connection profile.

## Persistent configuration paths

Find the active manager before choosing a command or file.

### NetworkManager

NetworkManager is common on desktops, many servers, and cloud images. It stores connection profiles rather than relying only on interface names.

```bash
nmcli device status
nmcli connection show
nmcli connection show "Wired connection 1"
```

A static IPv4 example:

```bash
sudo nmcli connection modify "Wired connection 1" \
  ipv4.method manual \
  ipv4.addresses 192.0.2.50/24 \
  ipv4.gateway 192.0.2.1 \
  ipv4.dns "192.0.2.53 198.51.100.53"
sudo nmcli connection up "Wired connection 1"
```

Return a profile to DHCP:

```bash
sudo nmcli connection modify "Wired connection 1" ipv4.method auto ipv4.addresses "" ipv4.gateway "" ipv4.dns ""
sudo nmcli connection up "Wired connection 1"
```

### netplan

Ubuntu Server commonly uses netplan YAML to generate NetworkManager or systemd-networkd configuration. Inspect first:

```bash
ls -l /etc/netplan
sudo netplan get
```

After editing a netplan file, prefer a timed apply when you might lose remote access:

```bash
sudo netplan try
```

`netplan try` gives you a chance to confirm the change. If you do not confirm, it rolls back automatically.

### systemd-networkd

Some servers use `.network` units under `/etc/systemd/network/`.

```bash
networkctl list
networkctl status ens3
ls -l /etc/systemd/network
```

After changing a `.network` file, restart only when you have console access or an out-of-band rollback path:

```bash
sudo systemctl restart systemd-networkd
```

## DNS is part of network configuration

A host can have a correct address and route but still fail application traffic because DNS is wrong. Separate name resolution from connectivity:

```bash
ping -c 3 192.0.2.1
getent hosts internal-mirror.example.com
resolvectl query internal-mirror.example.com 2>/dev/null || nslookup internal-mirror.example.com
```

When debugging, test both an IP address and a hostname. If IP connectivity works and name lookup fails, keep the fix focused on resolver configuration, search domains, or split-DNS routing.

## Safety checklist for remote changes

Network changes can disconnect your own session. Before applying a persistent change on a remote machine, write down:

1. Current interface, address, default route, and DNS evidence.
2. The exact manager that owns the interface.
3. The command or file change you plan to make.
4. A rollback command.
5. An alternate access path such as serial console, cloud console, IPMI, or a scheduled rollback job.

A simple timed rollback can save a remote session during practice:

```bash
sudo sh -c 'sleep 120; nmcli connection up "Known good profile"' &
```

Cancel the background rollback only after the new configuration is verified.

## Hands-on practice

Use a disposable VM, lab instance, or local network namespace. Do not practice on a production host over your only SSH session.

1. Record interface, address, route, DNS, and manager evidence with the read-only commands above.
2. Identify whether NetworkManager, netplan, systemd-networkd, or another stack owns the active interface.
3. Add a temporary secondary address with `ip address add` and verify it appears.
4. Remove the temporary address and prove the original state returned.
5. Write a short change plan for converting the interface to static addressing, including rollback steps, without applying it unless this is a disposable lab.
