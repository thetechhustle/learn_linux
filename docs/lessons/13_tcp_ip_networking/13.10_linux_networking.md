## 13.10 Linux Networking

Linux networking is a stack of small decisions: interface state, addresses,
routes, DNS, sockets, firewall policy, and persistent configuration. The best
operators move through those layers in order instead of guessing at one command.

This lesson pulls the Chapter 13 pieces together into a practical Linux
workflow.

!!! abstract "What you will learn"
    - Identify the active network manager before editing any interface configuration.
    - Move through interface, address, route, DNS, socket, firewall, and log evidence in a repeatable order.
    - Apply a record, change, verify, and persist pattern so network changes stay safe and reversible.

## Know the Active Network Manager

Different Linux systems persist network configuration in different places.
Before editing files, identify what owns the interface.

```bash
systemctl status NetworkManager
systemctl status systemd-networkd
networkctl list
nmcli device status
```

Common owners:

- NetworkManager on desktops, laptops, many servers, and cloud images
- systemd-networkd on minimal servers and appliance-style hosts
- distribution-specific tooling such as Netplan, ifupdown, or legacy
  `ifcfg-*` files
- container runtimes for bridge and overlay networks

Do not edit a file just because it exists. If a manager owns the interface, it
may overwrite manual changes or ignore the wrong file entirely.

## Interface Evidence

Start with the link layer:

```bash
ip link
ip -br link
```

Look for:

- interface name
- `UP` or `DOWN`
- carrier state
- MAC address
- MTU
- virtual interfaces such as bridges, VLANs, tunnels, and containers

Short output is useful during incidents:

```bash
ip -br addr
```

Example:

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s31f6        UP             192.168.8.42/24 fe80::.../64
tailscale0       UNKNOWN        100.64.12.34/32 fd7a:.../128
docker0          DOWN           172.17.0.1/16
```

That output immediately tells you the host has a LAN address, a Tailscale
address, and a Docker bridge.

## Address Configuration

Inspect addresses:

```bash
ip addr show
ip -4 addr show
ip -6 addr show
```

Ask:

- Does the host have the expected address?
- Is the prefix length correct?
- Is the address dynamic, static, link-local, or temporary?
- Is IPv6 present and intended?
- Does the source address match what peer systems expect?

Temporary changes can be useful in a lab:

```bash
sudo ip addr add 192.168.8.50/24 dev enp0s31f6
sudo ip addr del 192.168.8.50/24 dev enp0s31f6
```

Temporary `ip` changes do not survive reboot or network-manager reload. Use them
for testing, not as undocumented production configuration.

## Routing Evidence

Check route tables:

```bash
ip route
ip -6 route
```

Ask the kernel for one decision:

```bash
ip route get 1.1.1.1
ip route get <service-ip>
```

Important route clues:

- default gateway
- interface selected for a destination
- source address selected for a destination
- route metrics
- VPN or container routes
- policy-routing rules

Check policy routing when the main table does not explain behavior:

```bash
ip rule
ip route show table main
```

## DNS Evidence

Name resolution is separate from IP reachability.

```bash
resolvectl status
cat /etc/resolv.conf
getent hosts example.com
dig example.com
```

Look for:

- local stub resolver such as `127.0.0.53`
- DHCP-provided DNS servers
- VPN split-DNS rules
- search domains
- resolver differences between interfaces

If `ping 1.1.1.1` works but `getent hosts example.com` fails, keep the
incident in DNS territory until proven otherwise.

## Socket Evidence

Use `ss` to see what is listening or connected:

```bash
ss -tulpen
ss -tanp
```

Common filters:

```bash
ss -tulpen '( sport = :22 )'
ss -tanp state established
```

Focus on:

- local bind address
- port
- process
- protocol
- whether the socket is listening on localhost, one interface, or all
  addresses

This is often the fastest way to prove whether a service is actually listening.

## Firewall and Policy Evidence

Linux firewall policy may be controlled by `nftables`, `iptables`,
`firewalld`, `ufw`, cloud security groups, or container rules.

Read before changing:

```bash
sudo nft list ruleset
sudo iptables -S
sudo iptables -t nat -S
sudo firewall-cmd --state
sudo ufw status verbose
```

Pair firewall evidence with socket evidence. A port can be listening but
blocked, or exposed by a container rule even when the application config looks
private.

For remote hosts, avoid broad firewall changes over SSH unless you have a
rollback plan. A bad rule can lock you out.

## Persistent Configuration

Use the system's active network manager for durable changes.

NetworkManager examples:

```bash
nmcli connection show
nmcli connection show <connection-name>
nmcli connection modify <connection-name> ipv4.method auto
nmcli connection up <connection-name>
```

systemd-networkd examples:

```bash
networkctl list
networkctl status <interface>
ls /etc/systemd/network/
```

Netplan examples:

```bash
ls /etc/netplan/
sudo netplan try
sudo netplan apply
```

Prefer validation commands such as `netplan try` when available. They reduce
the chance of permanent remote lockout.

## Containers and Virtual Networks

Containers, VMs, and VPNs add interfaces and routes.

Docker examples:

```bash
docker network ls
docker ps
docker port <container>
ip addr show docker0
```

Bridge and namespace evidence:

```bash
ip link show type bridge
ip netns list
```

Do not assume the host route table fully explains container behavior. Published
ports, NAT, overlays, and namespace-specific routes can all affect the path.

## Troubleshooting Flow

Use this order for most Linux network incidents:

1. Interface:

   ```bash
   ip -br link
   ```

2. Address:

   ```bash
   ip -br addr
   ```

3. Route:

   ```bash
   ip route get <destination>
   ```

4. DNS:

   ```bash
   getent hosts <name>
   resolvectl status
   ```

5. Socket:

   ```bash
   ss -tulpen
   ```

6. Firewall:

   ```bash
   sudo nft list ruleset
   ```

7. Logs:

   ```bash
   journalctl --since "30 minutes ago"
   ```

8. Packet capture when needed:

   ```bash
   sudo tcpdump -ni <interface> host <peer-ip>
   ```

Keep notes as command plus output. That makes handoff easier and prevents the
same hypothesis from being retested repeatedly.

## Safe Change Pattern

For any network change:

1. Record current state.
2. Make the smallest reversible change.
3. Test from the source and destination that matter.
4. Confirm logs did not reveal a new failure.
5. Persist the change only after the temporary test proves the fix.
6. Record the rollback.

Example note:

```text
Before: ip route get 10.20.30.10 selected enp0s31f6 via 192.168.8.1.
Change: added temporary route 10.20.30.0/24 via 192.168.8.254.
After: ip route get 10.20.30.10 selected enp0s31f6 via 192.168.8.254.
Rollback: sudo ip route del 10.20.30.0/24 via 192.168.8.254.
```

## Hands-on Practice

Use a disposable VM, lab host, or machine you are allowed to inspect.

1. Identify the active network manager.
2. Capture `ip -br link`, `ip -br addr`, and `ip route`.
3. Use `ip route get` for an internet address and a local gateway.
4. Inspect DNS with `resolvectl status`.
5. List listening sockets with `ss -tulpen`.
6. Identify the active firewall layer.
7. Write a five-line incident handoff summarizing what is healthy and what is
   unknown.
