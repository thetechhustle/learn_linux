## 13.3 Packet Addressing

Packet addressing is the part of networking that answers two operational
questions:

- Where did this packet come from?
- Where is it trying to go?

Every IP packet carries a source address and a destination address. Routers,
firewalls, load balancers, cloud gateways, and the local host all use those
addresses to decide whether the packet should be forwarded, dropped, translated,
or delivered to a local process.

!!! abstract "What you will learn"
    - Explain the difference between source and destination addresses.
    - Read local interface addresses and route decisions from a Linux host.
    - Recognize common private, loopback, link-local, multicast, and public
      address ranges.
    - Use source and destination evidence when troubleshooting failed
      connections.

!!! success "Operator principle"
    Prove the packet's source, destination, and route before changing DNS,
    firewall, or application settings.

## Source and destination addresses

When a program opens a network connection, the operating system chooses a source
IP address from one of the host's configured interfaces. The remote service,
command, or library provides the destination address, often after a DNS lookup.

For example, a laptop might send an HTTPS request like this:

| Field | Example | Meaning |
| --- | --- | --- |
| Source IP | `192.168.1.44` | Address assigned to the laptop on the local network |
| Destination IP | `93.184.216.34` | Address for the remote web server |
| Source port | `51532` | Temporary local port chosen by the OS |
| Destination port | `443` | HTTPS service port |

This lesson focuses on the IP addresses. Ports matter too, but they belong to
transport protocols such as TCP and UDP.

## Address families

Linux commonly works with two IP address families:

- IPv4 addresses use dotted decimal notation, such as `192.0.2.10`.
- IPv6 addresses use hexadecimal groups separated by colons, such as
  `2001:db8::10`.

Both examples above are documentation ranges. They are safe for examples and
should not be assigned to production hosts.

## Common address ranges

Administrators should recognize these ranges quickly during troubleshooting:

| Range | Family | Common use |
| --- | --- | --- |
| `127.0.0.0/8` | IPv4 | Loopback; traffic stays on the local host |
| `::1/128` | IPv6 | IPv6 loopback |
| `10.0.0.0/8` | IPv4 | Private networks |
| `172.16.0.0/12` | IPv4 | Private networks |
| `192.168.0.0/16` | IPv4 | Private networks |
| `169.254.0.0/16` | IPv4 | Link-local fallback when DHCP fails |
| `fe80::/10` | IPv6 | IPv6 link-local addresses |
| `224.0.0.0/4` | IPv4 | Multicast |
| `ff00::/8` | IPv6 | Multicast |

Private addresses are routable inside internal networks but not directly across
the public internet. To reach the internet, they usually pass through a NAT
gateway, firewall, cloud egress gateway, or proxy.

## Inspect local addresses

Start with the local interface state:

```bash
ip -brief address
```

Typical output:

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s3           UP             192.168.56.24/24 fe80::a00:27ff:fe4e:66a1/64
```

Useful questions:

- Is the expected interface `UP`?
- Does the host have an address in the expected subnet?
- Did the host fall back to a link-local address such as `169.254.x.x`?
- Is the service listening only on loopback when remote clients need access?

For more detail on one interface:

```bash
ip address show dev enp0s3
```

## Predict the source address

When a host has multiple interfaces, the source address is not always obvious.
Ask the kernel how it would send traffic to a destination:

```bash
ip route get 8.8.8.8
```

Example output:

```text
8.8.8.8 via 192.168.56.1 dev enp0s3 src 192.168.56.24 uid 1000
    cache
```

The important fields are:

- `via 192.168.56.1`: the next-hop gateway.
- `dev enp0s3`: the outgoing interface.
- `src 192.168.56.24`: the source address Linux plans to use.

For IPv6, use the same pattern:

```bash
ip -6 route get 2001:4860:4860::8888
```

## Packet addressing in incidents

Packet addressing mistakes often look like application failures. Before blaming
the application, capture the addressing evidence:

```bash
ip -brief address
ip route get 203.0.113.20
getent hosts app.internal.example
ss -tuna
```

Then compare what each layer believes:

| Evidence | What it answers |
| --- | --- |
| `ip -brief address` | What addresses does this host currently own? |
| `ip route get DEST` | Which source, interface, and gateway will Linux use? |
| `getent hosts NAME` | What address did name resolution return? |
| `ss -tuna` | What local sockets are listening or connected? |

If DNS returns a public address but the intended service is private, fix the
name-resolution path. If `ip route get` chooses the wrong source interface, look
at routing policy, metrics, VPN state, or cloud route tables. If the service is
bound to `127.0.0.1`, remote clients cannot reach it even when the route is
healthy.

## Address translation

Network Address Translation changes packet addresses as traffic crosses a
gateway. A container, VM, or laptop may use one private source address locally
and a different public source address on the internet.

You can see the local side from the host:

```bash
ip route get 1.1.1.1
```

You can compare it with the address seen by the outside world:

```bash
curl -4 https://ifconfig.me
```

Run external lookup commands only from lab systems or systems where outbound
traffic is expected. In managed environments, provider metadata, firewall logs,
or NAT gateway logs may be the approved source of truth instead.

## Troubleshooting patterns

- A `127.0.0.1` or `::1` destination means the traffic never leaves the host.
- A `169.254.x.x` address often means DHCP did not provide a usable IPv4
  address.
- A `fe80::/10` address needs an interface scope, such as `fe80::1%eth0`.
- A private source address reaching the public internet usually depends on NAT.
- A route that selects the wrong `src` address can break VPN, cloud, and
  multi-homed hosts.
- A firewall rule may match on source or destination address even when routing
  is correct.

## Hands-on practice

Use a disposable Linux VM, container host, or lab machine.

1. Record the host's addresses:

   ```bash
   ip -brief address
   ```

2. Pick one public documentation address and ask Linux how it would route to it:

   ```bash
   ip route get 203.0.113.20
   ```

3. Record the selected source address, interface, and gateway.

4. Resolve a hostname and compare DNS output with the route decision:

   ```bash
   getent hosts example.com
   ip route get "$(getent ahostsv4 example.com | awk 'NR == 1 {print $1}')"
   ```

5. Inspect listening sockets and identify which ones are bound to loopback only:

   ```bash
   ss -tuln
   ```

6. Write a short lab note that answers:

   - Which local address would this host use for outbound internet traffic?
   - Which addresses are loopback, private, link-local, or public?
   - Which service bindings would be reachable only from the local host?

## Check your understanding

- Why is `127.0.0.1` a valid destination for local tests but not for remote
  clients?
- What evidence would make you suspect DHCP failure?
- Where might NAT change a packet's source address?
