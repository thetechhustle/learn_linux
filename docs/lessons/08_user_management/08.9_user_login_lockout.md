### 08.9 User Login Lockout

!!! abstract "What you will learn"
    - Separate account locking from failed-login lockout policy.
    - Inspect whether a user is locked, expired, or blocked by failed authentication attempts.
    - Lock and unlock an account deliberately with `passwd`.
    - Use modern failed-login tools such as `faillock` where available.
    - Build a small evidence trail before changing login access.

!!! example "Field story"
    A teammate says they cannot SSH into a Linux server after several password mistakes. At the same time, security asks you to disable a departing contractor's account. Both situations involve login access, but they are not the same problem. One may be a temporary failed-login lockout. The other is an intentional account lifecycle change.

!!! success "Operator principle"
    Prove why the login is blocked before you change it. A locked password, expired account, disabled shell, missing SSH key, failed-login counter, and PAM policy can all produce similar symptoms.

Login lockout work falls into two categories:

- **Account lock state**: an administrator deliberately disables password login for a user.
- **Failed-login lockout policy**: the system temporarily blocks authentication after too many failed attempts.

Do not treat these as interchangeable. Unlocking the wrong thing can restore access you meant to disable, or leave a legitimate user blocked while you think the problem is fixed.

## Start with evidence

Inspect the account before changing it.

Check the passwd database:

```bash
getent passwd andrea
```

Check UID, groups, and account identity:

```bash
id andrea
```

Check password and lock status:

```bash
sudo passwd -S andrea
```

On many Linux systems, `passwd -S` reports whether the password is usable, locked, or has no password. The exact letters and wording vary by distribution, so read the output alongside the local manual page:

```bash
man passwd
```

Check account aging and expiration details:

```bash
sudo chage -l andrea
```

Check the configured login shell:

```bash
getent passwd andrea | cut -d: -f7
```

If the shell is `/usr/sbin/nologin`, `/sbin/nologin`, or `/bin/false`, the account may be intentionally non-interactive.

## Locking an account password

To lock a user's password login:

```bash
sudo passwd -l andrea
```

This usually changes the password hash field so password authentication cannot succeed. It is a common quick containment step for a human account.

Verify afterward:

```bash
sudo passwd -S andrea
sudo chage -l andrea
```

Important: locking the password may not stop every access path. A user may still have active sessions, SSH key access depending on PAM and SSH configuration, sudo sessions, cron jobs, processes, API tokens, or application-level credentials. Treat `passwd -l` as one control, not complete offboarding.

For a stronger account disablement, administrators may also expire the account:

```bash
sudo chage -E 0 andrea
```

Use this only when your site policy supports it and you understand the effect. Record the reason and verification in your handoff.

## Unlocking an account password

To unlock a password that was intentionally locked:

```bash
sudo passwd -u andrea
```

Then verify:

```bash
sudo passwd -S andrea
```

Do not unlock an account just because someone says they cannot log in. First confirm whether the lock was intentional, whether the account is expired, and whether there is an open offboarding or incident ticket.

## Failed-login lockouts

Failed-login lockout is usually controlled through PAM and distribution-specific tooling. Modern Linux distributions commonly use `pam_faillock` with the `faillock` command. Older systems may use `pam_tally2` or `faillog`.

Check which tools exist:

```bash
command -v faillock
command -v pam_tally2
command -v faillog
```

On systems with `faillock`, inspect a user's failed-login records:

```bash
sudo faillock --user andrea
```

To reset the failed-login counter for that user:

```bash
sudo faillock --user andrea --reset
```

Verify again:

```bash
sudo faillock --user andrea
```

This is different from `passwd -u`. Resetting a failed-login counter does not intentionally unlock a password that an administrator locked.

## Finding the policy

Failed-login behavior is usually configured through PAM and authselect/authconfig tooling, depending on the distribution.

Useful places to inspect include:

```bash
grep -R "pam_faillock" /etc/pam.d /etc/security 2>/dev/null
```

On some distributions, policy may be managed by `authselect`:

```bash
authselect current
```

Do not hand-edit PAM files casually on production systems. A bad PAM change can lock out administrators. Follow distribution documentation, keep a root console or recovery path available, and test in a disposable lab before changing policy.

## Practical troubleshooting flow

When a user reports login failure:

1. Confirm the exact login path: local console, SSH password, SSH key, sudo, desktop login, or application login.
2. Confirm the username:

    ```bash
    getent passwd andrea
    ```

3. Check password lock and expiration:

    ```bash
    sudo passwd -S andrea
    sudo chage -l andrea
    ```

4. Check failed-login counters:

    ```bash
    sudo faillock --user andrea
    ```

5. Check recent authentication logs using the tool your system provides:

    ```bash
    sudo journalctl -u ssh --since "1 hour ago"
    ```

    On some systems, SSH logs may be under `sshd`, `ssh.service`, `/var/log/auth.log`, or `/var/log/secure`.

6. Change only the control that matches the evidence.

## Handoff notes

For any lockout or unlock action, record:

- Who requested the change.
- The account name.
- The evidence you inspected.
- Whether this was a password lock, account expiration, failed-login reset, shell change, or another control.
- The command you ran.
- The post-change verification.
- Any remaining access paths that need review, such as SSH keys, active sessions, tokens, or application accounts.

## Hands-on practice

Run this only on a disposable VM, container, or lab machine.

1. Create a disposable user if one does not already exist:

    ```bash
    sudo useradd -m -s /bin/bash lab-lockout
    sudo passwd lab-lockout
    ```

2. Inspect the account:

    ```bash
    getent passwd lab-lockout
    sudo passwd -S lab-lockout
    sudo chage -l lab-lockout
    ```

3. Lock the password:

    ```bash
    sudo passwd -l lab-lockout
    sudo passwd -S lab-lockout
    ```

4. Unlock it:

    ```bash
    sudo passwd -u lab-lockout
    sudo passwd -S lab-lockout
    ```

5. If your lab has `faillock`, inspect the failed-login state:

    ```bash
    sudo faillock --user lab-lockout
    ```

6. Write a short note explaining the difference between a locked password and a failed-login counter.
