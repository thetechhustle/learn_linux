### 8.10 Risk Reduction with PAM

!!! abstract "What you will learn"
    - Explain what Pluggable Authentication Modules (PAM) control on a Linux system.
    - Inspect PAM service policy without making changes.
    - Read the basic PAM rule format: module type, control flag, module, and arguments.
    - Identify common risk-reduction modules and where they fit.
    - Plan PAM changes safely so you do not lock yourself out.

!!! example "Field story"
    Security wants SSH password logins to enforce account lockout after repeated failures. A teammate suggests editing `/etc/pam.d/sshd` directly. Before touching production, you need to understand which PAM stack SSH uses, how the distribution manages PAM, and how to test the change with a recovery path.

!!! success "Operator principle"
    PAM is a shared authentication control plane. Inspect first, change in a lab, keep a recovery session open, and verify the exact service you changed.

PAM stands for **Pluggable Authentication Modules**. It lets Linux services use a common authentication framework instead of each program implementing its own login policy.

Programs such as `login`, `sudo`, `su`, `passwd`, desktop login managers, and SSH can call PAM. PAM then decides which modules run and in what order.

PAM can help reduce risk with controls such as:

- denying access when `/etc/nologin` exists
- checking account expiration
- enforcing password quality rules
- limiting repeated failed login attempts
- requiring multi-factor authentication
- setting session limits
- recording login sessions

That power cuts both ways. A bad PAM change can prevent normal users, administrators, or automation from authenticating.

## Where PAM policy lives

PAM service files usually live in:

```bash
/etc/pam.d/
```

List them:

```bash
ls /etc/pam.d/
```

Each file normally maps to a PAM-aware service. For example:

- `/etc/pam.d/sshd` controls PAM behavior for OpenSSH when SSH is configured to use PAM.
- `/etc/pam.d/sudo` controls PAM behavior for `sudo`.
- `/etc/pam.d/su` controls PAM behavior for `su`.
- `/etc/pam.d/passwd` controls password-change behavior for `passwd`.

Distribution layout matters. Debian and Ubuntu commonly include shared stacks such as `common-auth`, `common-account`, `common-password`, and `common-session`. Red Hat-family systems commonly use generated or managed stacks such as `system-auth` and `password-auth`, often through `authselect`.

## Read PAM rules

A typical PAM line has this shape:

```text
type control module arguments
```

Example:

```text
auth required pam_nologin.so
```

The fields mean:

- `auth`: module type. This phase proves identity or grants authentication.
- `required`: control flag. Failure matters, but PAM may continue running later modules before returning failure.
- `pam_nologin.so`: module name.
- arguments: optional settings passed to the module.

Common module types:

- `auth`: authenticates a user, often with a password, key-related check, token, or MFA prompt.
- `account`: checks whether the account is allowed to log in now.
- `password`: handles password changes and password policy.
- `session`: runs setup or cleanup when a session starts or ends.

Common control flags:

- `required`: must succeed, but PAM continues processing the stack.
- `requisite`: must succeed, and failure can stop processing immediately.
- `sufficient`: if it succeeds and no prior required module failed, PAM may accept the result.
- `optional`: normally does not decide success by itself.
- `include` or `substack`: pull in rules from another PAM file.

Do not skim past `include` lines. A short service file may delegate most real policy to a shared stack.

## Inspect before changing

Start with read-only inspection:

```bash
sed -n '1,220p' /etc/pam.d/sshd
sed -n '1,220p' /etc/pam.d/sudo
```

Find shared stacks:

```bash
grep -R "pam_faillock\\|pam_pwquality\\|pam_limits\\|pam_nologin" /etc/pam.d /etc/security 2>/dev/null
```

On Red Hat-family systems, check whether `authselect` manages PAM:

```bash
command -v authselect
authselect current
```

If PAM is managed by `authselect`, use that tooling and profile workflow instead of hand-editing generated files.

For SSH specifically, confirm whether OpenSSH is using PAM:

```bash
sudo sshd -T | grep -i usepam
```

Some systems use `sshd -T`; others may need the full path such as `/usr/sbin/sshd -T`.

## Common risk-reduction modules

These modules are common examples. Availability and exact arguments vary by distribution, so always read local manual pages.

### pam_nologin

`pam_nologin.so` blocks non-root logins when `/etc/nologin` exists. It is often used during maintenance.

Inspect:

```bash
grep -R "pam_nologin" /etc/pam.d 2>/dev/null
```

### pam_faillock

`pam_faillock.so` tracks failed authentication attempts and can temporarily lock users after repeated failures.

Inspect:

```bash
grep -R "pam_faillock" /etc/pam.d /etc/security 2>/dev/null
command -v faillock
```

This connects to the failed-login lockout workflow from the previous lesson. Resetting a `faillock` counter is not the same thing as unlocking a deliberately locked password.

### pam_pwquality

`pam_pwquality.so` helps enforce password quality rules during password changes.

Inspect:

```bash
grep -R "pam_pwquality" /etc/pam.d /etc/security 2>/dev/null
```

### pam_limits

`pam_limits.so` applies limits from files such as `/etc/security/limits.conf` and `/etc/security/limits.d/`.

Inspect:

```bash
grep -R "pam_limits" /etc/pam.d 2>/dev/null
ls /etc/security/limits.d 2>/dev/null
```

### pam_google_authenticator and MFA modules

Some environments add MFA through modules such as `pam_google_authenticator.so`, Duo PAM, or vendor-specific modules.

Inspect before assuming:

```bash
grep -R "google_authenticator\\|duo\\|mfa\\|otp" /etc/pam.d /etc/security 2>/dev/null
```

MFA modules can change the login experience dramatically. Test with a recovery path and document enrollment expectations.

## Safe change workflow

Use this workflow before changing PAM on any important system.

1. Identify the exact service and stack:

    ```bash
    sed -n '1,220p' /etc/pam.d/sshd
    ```

2. Confirm whether distribution tooling owns the stack:

    ```bash
    command -v authselect
    authselect current
    ```

3. Make a backup with permissions preserved:

    ```bash
    sudo cp -a /etc/pam.d/sshd /etc/pam.d/sshd.bak.$(date +%Y%m%d%H%M%S)
    ```

4. Keep an existing root or sudo session open while testing.

5. Test in a second terminal before closing the recovery session.

6. Verify the exact service path that changed. For SSH, use a new SSH connection. For `sudo`, test `sudo -v` in a separate terminal.

7. Record what changed and how you verified it.

For production systems, prefer configuration management, peer review, and a documented rollback plan.

## What not to do

Avoid these failure patterns:

- Editing PAM over a single SSH session with no console or recovery path.
- Changing shared stacks without realizing multiple services use them.
- Copying PAM lines from a different distribution.
- Treating `include` files as decorative instead of policy-bearing.
- Enabling MFA without an enrollment and break-glass plan.
- Assuming SSH, `sudo`, desktop login, and service accounts all use the same PAM path.

## Hands-on practice

Run this on a disposable VM or lab machine.

1. List PAM service files:

    ```bash
    ls /etc/pam.d/
    ```

2. Pick one service file and identify all four fields on at least three lines:

    ```bash
    sed -n '1,120p' /etc/pam.d/sudo
    ```

3. Search for common risk-reduction modules:

    ```bash
    grep -R "pam_nologin\\|pam_faillock\\|pam_pwquality\\|pam_limits" /etc/pam.d /etc/security 2>/dev/null
    ```

4. Write a short note answering:
    - Which service file did you inspect?
    - Which shared stacks did it include?
    - Which module looked most security-sensitive?
    - What recovery path would you keep open before changing it?
