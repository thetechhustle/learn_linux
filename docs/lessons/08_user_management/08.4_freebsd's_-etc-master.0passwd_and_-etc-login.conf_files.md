### 08.4 FreeBSD Account Files: `/etc/master.passwd` and `/etc/login.conf`

!!! abstract "What you will learn"
    - Compare FreeBSD account files with the Linux `/etc/passwd` and `/etc/shadow` model.
    - Explain why `/etc/master.passwd` and generated password databases must stay in sync.
    - Inspect login classes and resource limits without changing production systems.
    - Choose safer tools for FreeBSD account-file edits.

!!! example "Field story"
    You inherit a small FreeBSD server during an incident. A teammate says, "It is basically Linux." Before you touch user access, you need to know which files are authoritative, which files are generated, and which tools rebuild the account database safely.

!!! success "Operator principle"
    Treat FreeBSD account management as familiar but not identical to Linux. Read first, use FreeBSD-native tools, and never hand-edit generated account databases.

## Why this matters in a Linux course

Linux and FreeBSD are both Unix-like systems, but their account-file layouts are not identical. If you administer mixed environments, the concepts carry over while the exact files and tools change.

On Linux, you usually think about:

- `/etc/passwd` for public account identity
- `/etc/shadow` for password hashes and aging metadata
- `/etc/group` for group membership

On FreeBSD, important local account files include:

- `/etc/master.passwd` for the authoritative local password file
- `/etc/passwd` as a public, derived compatibility file
- `/etc/pwd.db` and `/etc/spwd.db` as generated password databases
- `/etc/group` for group membership
- `/etc/login.conf` for login classes and resource limits

The lesson is not "FreeBSD is Linux with different filenames." The lesson is that account evidence depends on the operating system's account database model.

## `/etc/master.passwd`

FreeBSD's `/etc/master.passwd` is the authoritative local account file. It contains sensitive fields and is not meant to be world-readable.

A simplified entry looks like this:

```text
alice:$6$...:1001:1001::0:0:Alice Example:/home/alice:/bin/sh
```

The common fields are:

- **login name:** account name.
- **password:** encrypted password field or lock marker.
- **UID:** numeric user ID.
- **GID:** primary group ID.
- **login class:** class name from `/etc/login.conf`; empty usually means `default`.
- **password change time:** when the password must be changed, if set.
- **account expiration time:** when the account expires, if set.
- **GECOS/comment:** human-readable account metadata.
- **home directory:** default directory after login.
- **shell:** login shell.

Do not paste raw password fields into tickets or chat. Redact them the same way you would redact Linux `/etc/shadow` output.

## Derived account databases

FreeBSD also uses generated database files such as `/etc/pwd.db` and `/etc/spwd.db` so account lookups are fast and consistent.

That means a manual edit to the wrong file can create confusing behavior. The text file and the generated databases may disagree until they are rebuilt.

FreeBSD tools handle this rebuild for you. When changing local account files, prefer tools such as:

```bash
sudo vipw
sudo pw usermod alice -s /bin/sh
sudo pw lock alice
```

`vipw` edits the master password file with locking and rebuild behavior. The `pw` utility provides account-management commands for scripted or explicit changes.

If you are recovering from a controlled manual change, `pwd_mkdb` rebuilds the password databases from the master file:

```bash
sudo pwd_mkdb -p /etc/master.passwd
```

Do not run rebuild commands casually on production systems. Know what changed, keep a backup, and verify afterward.

## `/etc/login.conf`

FreeBSD's `/etc/login.conf` defines login classes. A login class can set environment defaults, password policy details, and resource limits for accounts assigned to that class.

A simplified class might look like this:

```text
staff:\
        :datasize-max=2048M:\
        :maxproc=512:\
        :openfiles=8192:\
        :tc=default:
```

Operationally, login classes help answer:

- What resource limits apply to this account?
- Does the account inherit from `default`?
- Is this a normal human class, a service class, or a restricted class?
- Could a login problem be caused by limits rather than the password itself?

After changing `/etc/login.conf`, FreeBSD systems commonly require rebuilding the capability database:

```bash
sudo cap_mkdb /etc/login.conf
```

Again, do this only when you are intentionally changing login classes and have a verification plan.

## Read-only inspection workflow

On a FreeBSD host, start with read-only commands:

```bash
id alice
getent passwd alice
getent group staff
```

Inspect the account through FreeBSD's account utility:

```bash
pw usershow alice
```

Inspect login classes:

```bash
grep -n '^[[:alnum:]_-][[:alnum:]_-]*:' /etc/login.conf
```

Inspect a specific class carefully:

```bash
grep -n '^staff:' /etc/login.conf
```

If you need to inspect `/etc/master.passwd`, keep the raw output local and redact the password field in any handoff.

## Linux-to-FreeBSD comparison

Use this mental map:

- Linux `/etc/passwd` is public account identity; FreeBSD `/etc/passwd` is also public but derived from the master file.
- Linux `/etc/shadow` keeps sensitive password metadata; FreeBSD keeps sensitive local account data in `/etc/master.passwd` and generated secure databases.
- Linux account changes often use `usermod`, `passwd`, and `chage`; FreeBSD account changes often use `pw`, `passwd`, and `vipw`.
- Linux PAM and limits are often split across PAM files, `/etc/security/limits.conf`, systemd, and other services; FreeBSD login classes centralize many login-time capabilities in `/etc/login.conf`.

The safe habit is the same on both systems: identify the account, inspect current state, change one thing with the platform-native tool, then verify.

## Handoff checklist

For a FreeBSD account review, capture:

- account name, UID, primary GID, and supplemental groups
- home directory and shell
- login class
- whether the account appears locked, expired, or active
- whether active processes or sessions exist
- which command you used to verify each claim
- whether any raw password field was redacted

Example redacted note:

```text
Account alice inspected on freebsd-host-01.
UID/GID: 1001/1001.
Login class: staff.
Home/shell: /home/alice, /bin/sh.
Password field: present but redacted from handoff.
Verification: id alice; pw usershow alice; getent passwd alice.
No account-file edits were made.
```
