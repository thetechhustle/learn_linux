### Safe Removal of a User's Account and Files

Removing an account is not just the reverse of creating it. A user account can own running processes, cron jobs, SSH keys, service files, mail, home-directory data, shared files, and records that might matter during an audit. Good removal work preserves evidence first, disables access before deleting anything, and only removes data after you know what must be kept.

!!! abstract "What you will learn"
    - Build a short evidence trail before removing a Linux account.
    - Disable login access while you review processes, files, and scheduled work.
    - Use `userdel` safely, including when to avoid `userdel -r`.
    - Find leftover files by UID and hand off unresolved ownership cleanly.

!!! example "Field story"
    A contractor named `ashley` leaves the team. Security wants her login closed today, but the application team says she might own deployment scripts and shared project files. Your job is to stop new access immediately without destroying useful evidence or breaking services.

!!! success "Operator principle"
    Disable first, archive deliberately, delete last.

## Start with evidence

Record the account state before making changes. This gives you rollback context and helps the next administrator understand what happened.

```bash
getent passwd ashley
id ashley
lastlog -u ashley
last ashley | head
sudo passwd -S ashley
sudo chage -l ashley
```

Check for processes and scheduled work:

```bash
pgrep -a -u ashley
sudo crontab -l -u ashley
sudo find /var/spool/cron /var/spool/cron/crontabs -maxdepth 1 -type f -name ashley 2>/dev/null
```

Look for obvious SSH and shell-access clues:

```bash
sudo ls -la /home/ashley
sudo ls -la /home/ashley/.ssh 2>/dev/null
sudo grep -R "ashley" /etc/sudoers /etc/sudoers.d 2>/dev/null
```

Do not paste private keys, password hashes, or sensitive file contents into tickets. Record paths, ownership, timestamps, and the commands you ran.

## Disable access before removal

If the account should stop working immediately, lock it before deleting it. Locking is safer than removal when teams still need to inspect files, processes, or ownership.

```bash
sudo passwd -l ashley
sudo usermod --expiredate 1 ashley
sudo usermod --shell /usr/sbin/nologin ashley
```

Verify the lock state:

```bash
sudo passwd -S ashley
getent passwd ashley
```

This does not necessarily kill existing sessions. If the account has active processes, inspect them before terminating anything:

```bash
pgrep -a -u ashley
```

Terminate only after you understand whether those processes are user shells, batch jobs, or services someone still depends on.

## Archive before deleting files

The riskiest part of account removal is data removal. Decide what to keep before running a command that removes the home directory.

Create an archive from a trusted administrative directory:

```bash
sudo mkdir -p /var/local/account-archives
sudo tar --xattrs --acls -cpf /var/local/account-archives/ashley-home.tar /home/ashley
sudo chmod 0600 /var/local/account-archives/ashley-home.tar
sudo tar -tf /var/local/account-archives/ashley-home.tar | head
```

If your organization uses snapshots, backups, object storage, or legal-hold tooling, follow that process instead of inventing a local archive.

## Remove the account

Use plain `userdel` when you want to remove the account records but leave the home directory for review:

```bash
sudo userdel ashley
```

Use `userdel -r` only when you are sure the home directory and mail spool can be removed:

```bash
sudo userdel -r ashley
```

!!! warning "Be careful with `userdel -r`"
    `userdel -r` removes the user's home directory and mail spool. It does not find every file the user owns elsewhere on the system. It can also remove data before another team has confirmed what should be retained.

After removal, verify that the account no longer resolves:

```bash
getent passwd ashley || echo "account removed"
getent shadow ashley 2>/dev/null || echo "shadow entry removed"
```

## Find leftover ownership

Files outside the home directory can remain owned by the removed account's numeric UID. Record the UID before deletion with `id ashley`; if you forgot, check your evidence notes or backups.

Search one filesystem at a time to avoid crossing into network mounts or system pseudo-filesystems unexpectedly:

```bash
sudo find / -xdev -uid 1007 -ls
sudo find /var -xdev -uid 1007 -ls
sudo find /srv -xdev -uid 1007 -ls
```

For each leftover path, choose one of these outcomes:

- Reassign it to a service owner or manager-approved user with `chown`.
- Archive it and remove the original after approval.
- Leave it in place temporarily and document why.

Avoid broad ownership changes such as `sudo chown -R newuser /` or cleanup commands based only on a username string. Work from the numeric UID evidence.

## Troubleshooting

- `userdel: user is currently used by process`: inspect with `pgrep -a -u username`, stop the relevant service or session deliberately, then retry.
- `userdel: mail spool ... not found`: this is often harmless; verify the account records and home directory state.
- `userdel: group username not removed`: another account or file may still reference the group. Check `getent group username` and decide whether `groupdel` is appropriate.
- The account still logs in through SSO: local `userdel` is not enough for centralized identity. Disable the account in the directory provider and review cached credentials.
- Files show a number instead of a username: the account record is gone but files still have the old UID. Use UID-based `find` and reassign or archive them.

## Hands-on practice

Run this on a disposable VM or container:

1. Create a lab account and a shared file:

   ```bash
   sudo useradd -m labremove
   sudo install -o labremove -g labremove -m 0644 /etc/hosts /tmp/labremove-owned
   id labremove
   ```

2. Capture evidence:

   ```bash
   getent passwd labremove
   sudo find /tmp -xdev -user labremove -ls
   ```

3. Lock the account and verify the lock:

   ```bash
   sudo passwd -l labremove
   sudo passwd -S labremove
   ```

4. Remove only the account record:

   ```bash
   sudo userdel labremove
   getent passwd labremove || echo "account removed"
   ```

5. Find and clean up the leftover file by numeric UID from your `id labremove` output:

   ```bash
   sudo find /tmp -xdev -uid UID_FROM_YOUR_NOTES -ls
   sudo rm /tmp/labremove-owned
   ```
