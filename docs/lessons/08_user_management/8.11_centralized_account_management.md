## 8.11 Centralized Account Management

Local accounts work for one machine. They do not scale well once you
administer fleets, shared services, remote access, or compliance-sensitive
systems. Centralized account management moves identity data and access policy
into a directory or identity provider so that accounts can be created, changed,
disabled, audited, and removed consistently.

This lesson focuses on the operator view: how a Linux host consumes centralized
identity, what evidence proves it is working, and where the risk boundaries are
before you change anything.

!!! abstract "What you will learn"
    - Explain the difference between local account files and centralized identity.
    - Identify the role of LDAP, Active Directory, Kerberos, SSSD, and NSS/PAM.
    - Use read-only commands to prove where a user's identity and group data come from.
    - Plan safe changes for onboarding, offboarding, and access troubleshooting.

!!! warning "Do not lock yourself out"
    Directory, SSSD, NSS, PAM, and sudo changes can break login for many users at once.
    Keep a tested local administrative account or console path available before changing
    identity configuration on a remote system.

## The moving parts

Centralized account management usually combines several pieces:

- **Directory service**: stores users, groups, attributes, and sometimes host or
  sudo policy. Common examples are LDAP directories and Active Directory.
- **Authentication service**: proves the user is who they claim to be. Kerberos
  is common in Active Directory and many Unix directory environments.
- **Client integration**: lets Linux tools ask the directory for users and groups.
  Modern Linux systems commonly use SSSD for this.
- **Name service switch (NSS)**: controls where commands such as `getent passwd`
  and `id` look for identity records.
- **PAM**: controls how login services authenticate users and apply session rules.

The important habit is to inspect the whole path. A user can exist in the
directory but still fail to log in because DNS, time sync, Kerberos, SSSD, NSS,
PAM, shell settings, home-directory creation, or host access rules are broken.

## Local files versus centralized identity

Local files still matter on centrally managed systems:

- `/etc/passwd` usually keeps local service and emergency accounts.
- `/etc/group` usually keeps local groups.
- `/etc/shadow` stores local password hashes for local accounts.
- `/etc/nsswitch.conf` decides whether lookups consult only `files` or also a
  provider such as `sss`, `ldap`, or `winbind`.
- PAM files under `/etc/pam.d/` decide which login services use the central
  authentication path.

Use `getent` instead of reading only `/etc/passwd` when you want the system's
actual account view:

```bash
getent passwd alice
getent group platform
id alice
```

If `getent passwd alice` returns a record that is not present in `/etc/passwd`,
the host is resolving that user through a centralized source.

## Inspect the client configuration

Start with read-only evidence. These commands are safe on production systems:

```bash
grep '^passwd:\|^group:\|^shadow:' /etc/nsswitch.conf
grep -R 'pam_sss\|pam_ldap\|pam_winbind' /etc/pam.d 2>/dev/null
systemctl status sssd --no-pager
sssctl domain-list 2>/dev/null
```

On systems joined to Active Directory, you might also see tools such as
`realm`, `adcli`, or Samba's `winbind`:

```bash
realm list
wbinfo -u 2>/dev/null | head
```

Tooling varies by distribution. The evidence pattern is the same: confirm the
directory domain, the local client service, the NSS lookup path, and the PAM
login path before you change anything.

## Query identity data

LDAP directories can be queried directly when you have the right server,
search base, and credentials:

```bash
ldapsearch -x -H ldap://ldap.example.com -b dc=example,dc=com '(uid=alice)'
```

Active Directory environments often rely on Kerberos and domain join tooling.
These commands help prove whether the host can reach and trust the domain:

```bash
realm list
klist
id alice@example.com
```

For SSSD-based systems, prefer SSSD-aware checks when available:

```bash
sssctl user-checks alice
sssctl domain-status example.com
```

If `id alice` works but login fails, the account lookup path is probably healthy
and the next investigation should move to authentication, PAM access rules,
home-directory creation, shell policy, sudo policy, or service-specific logs.

## Operational workflows

### Onboarding a user

1. Create or request the identity in the directory or identity provider.
2. Add the user to the least-privilege groups needed for the role.
3. Verify the host sees the new identity:

   ```bash
   getent passwd alice
   id alice
   ```

4. Confirm the target service grants only the expected access.
5. Record the ticket, approver, groups, and verification command output.

### Changing access

Group changes can take time to reach every host because of caches and active
sessions. Check the current view before and after the change:

```bash
id alice
getent group platform
```

If a change is urgent, you may need to clear a client cache or terminate active
sessions, but do that deliberately and according to local policy:

```bash
sudo sss_cache -u alice
loginctl list-sessions
```

### Offboarding a user

Centralized account management makes offboarding safer only if it is treated as
a complete workflow:

1. Disable or expire the central account.
2. Remove high-risk group membership, privileged roles, tokens, keys, and sudo
   rights according to policy.
3. Check for active sessions:

   ```bash
   who
   loginctl list-sessions
   ```

4. Preserve required evidence before deleting local files or homes.
5. Verify the host no longer resolves or permits the account where appropriate:

   ```bash
   getent passwd alice
   id alice
   ```

Do not assume disabling the directory account removes access everywhere. SSH
keys, application-local users, cloud IAM roles, API tokens, scheduled jobs, and
cached credentials may need separate cleanup.

## Troubleshooting patterns

- **`getent passwd alice` returns nothing**: check DNS, network reachability,
  `/etc/nsswitch.conf`, SSSD or winbind status, domain join state, and directory
  search filters.
- **`id alice` works but login fails**: inspect PAM rules, account expiration,
  host access policy, shell path, home-directory policy, MFA requirements, and
  authentication logs.
- **Group membership looks stale**: check active sessions, SSSD cache state,
  directory replication, and whether the user needs a new login session.
- **Only one service fails**: inspect that service's PAM file and logs instead
  of assuming the whole identity stack is broken.
- **Many users fail at once**: treat it as an identity-service incident. Preserve
  logs, avoid repeated blind restarts, and verify whether DNS, time sync,
  directory reachability, certificates, or Kerberos are failing.

Common log locations include:

```bash
journalctl -u sssd --since "30 minutes ago"
journalctl -u ssh --since "30 minutes ago" 2>/dev/null
journalctl -u sshd --since "30 minutes ago" 2>/dev/null
```

## Hands-on practice

Use a disposable VM, container, or lab host. Do not point a learner lab at a
production directory.

1. Inspect how the host resolves users and groups:

   ```bash
   grep '^passwd:\|^group:\|^shadow:' /etc/nsswitch.conf
   getent passwd root
   id "$(id -un)"
   ```

2. Check whether the host has a centralized identity client configured:

   ```bash
   systemctl status sssd --no-pager
   realm list
   ```

3. Write down which commands worked, which tools were not installed, and what
   that tells you about the host.
4. Explain how you would prove whether a user's group change had reached this
   machine.
