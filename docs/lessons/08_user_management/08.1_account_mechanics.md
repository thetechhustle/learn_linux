### 08.1 Account Mechanics

!!! abstract "What you will learn"
    - Identify the parts that make up a Linux account.
    - Inspect account identity without changing the system.
    - Explain how UIDs, GIDs, groups, homes, shells, and lock state affect access.
    - Plan safe account lifecycle work during an operational handoff.

!!! example "Field story"
    A teammate leaves the company at 5 PM. You need to remove their interactive access without deleting evidence, breaking files they owned, or disabling a service that runs under a similar account name.

!!! success "Operator principle"
    Treat accounts as lifecycle objects: create, inspect, modify, disable, archive, and remove deliberately.

## What an account is

A Linux account is more than a username. It is a bundle of identity and login settings that the system uses to decide who a process is, what files it can touch, and what happens when someone signs in.

The important parts are:

- **Username:** the human-readable login name, such as `alice` or `deploy`.
- **UID:** the numeric user ID. Linux permissions are enforced against this number, not the display name.
- **Primary GID:** the default group ID used when the account creates files.
- **Supplemental groups:** extra groups that grant access to shared files, devices, or administrative tools.
- **Home directory:** the account's default working area, usually under `/home`.
- **Login shell:** the program started for an interactive login, such as `/bin/bash`, `/bin/zsh`, or a non-login shell.
- **Password or lock state:** whether password-based login is possible for the account.

This matters because usernames can change, but file ownership and running processes are usually tied to numeric IDs. During a cleanup, `alice` becoming `a.smith` is less important than whether UID `1001` still owns critical files or has active sessions.

## Human accounts and service accounts

Most systems have both human accounts and service accounts.

Human accounts are used by people. They usually have a home directory, an interactive shell, and membership in groups that match job duties.

Service accounts are used by programs. They often have limited shells, tightly scoped file ownership, and names that describe the workload, such as `nginx`, `postgres`, or `backup`. Do not disable a service account just because it does not look like a person. First identify what uses it.

## Read account identity

Use read-only commands first. They give you evidence before you change anything.

Show your current identity:

```bash
id
```

Show another account's UID, primary group, and supplemental groups:

```bash
id alice
```

Ask the system account database for an account record:

```bash
getent passwd alice
```

Ask for a group record:

```bash
getent group sudo
```

Check the home directory itself:

```bash
ls -ld /home/alice
```

On many systems, password and lock state lives in the shadow database. Reading it requires elevated privileges:

```bash
sudo getent shadow alice
```

Do not paste shadow output into tickets or chat. It can reveal sensitive password metadata even when it does not show a plaintext password.

## Understand UID and GID ownership

Files store numeric owners. A listing usually translates those numbers back into names for readability:

```bash
ls -ln /home/alice
ls -l /home/alice
```

The `-n` form shows numeric UID and GID values. This is useful when an account was renamed, deleted, restored from backup, or copied between systems.

Renaming an account does not automatically make every historical reference safe. Before changing a username, UID, GID, or home path, check:

- whether the account owns files outside its home directory
- whether scripts refer to the old username
- whether scheduled jobs run as that account
- whether services, SSH keys, or deployment tools depend on the current name

## Shells and home directories

The login shell controls what starts after an interactive login. A normal human account might use `/bin/bash` or `/bin/zsh`. A service account might use `/usr/sbin/nologin` or `/bin/false` to prevent interactive login.

The home directory stores user-specific files such as shell configuration, SSH keys, application settings, and local work. When offboarding a person, preserving the home directory is often safer than deleting it immediately.

## Account lifecycle

A safe account lifecycle usually follows this order:

1. **Create:** make the account with the correct purpose, home, shell, and group membership.
2. **Audit:** inspect UID, GID, groups, home ownership, shell, lock state, active sessions, and owned files.
3. **Modify:** adjust groups, shell, home path, or metadata with account-management tools.
4. **Disable:** lock interactive access when a person leaves or an account is under review.
5. **Archive:** preserve home directories, SSH keys, crontabs, and evidence required by policy.
6. **Remove:** delete the account only when ownership, services, and retention requirements are understood.

The safest first move during offboarding is often to disable login, not to delete the account.

## Active sessions and processes

Before disabling or removing an account, check whether it is active:

```bash
who
w
pgrep -u alice -a
```

Active sessions or processes do not always mean "do not act." They mean "understand the impact before acting." For a compromised account, you may need to act quickly. For normal offboarding, you may need to coordinate a graceful handoff.

## Hands-on practice

Run this on a disposable VM, container, or lab machine. Keep it read-only unless you intentionally created a test account for practice.

1. Pick a non-root account to inspect.
2. Record its account record:

   ```bash
   getent passwd USERNAME
   ```

3. Record its UID, primary group, and supplemental groups:

   ```bash
   id USERNAME
   ```

4. Inspect its home directory:

   ```bash
   ls -ld /home/USERNAME
   ```

5. Check whether it has active processes:

   ```bash
   pgrep -u USERNAME -a
   ```

6. Write a short handoff note that answers:
   - Is this account likely human or service-owned?
   - What UID and primary GID does it use?
   - Which groups grant extra access?
   - Does the home directory exist and match the account?
   - Is anything currently running as this account?
