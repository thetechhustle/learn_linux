### Reading `/etc/passwd`

The `/etc/passwd` file is the local account directory that many tools consult
when they need to translate a login name into numeric identity, home directory,
and login shell information. It does not normally store password hashes on
modern Linux systems; those live in `/etc/shadow`, which is readable only by
privileged users.

!!! abstract "What you will learn"
    - Explain what each `/etc/passwd` field means and why the UID/GID fields matter more than the display name.
    - Inspect local account records without exposing secrets or editing system files directly.
    - Validate account-file consistency with purpose-built tools before and after a user-management change.

!!! warning "Do not hand-edit account databases casually"
    A malformed `/etc/passwd` entry can break logins, ownership lookups, service
    accounts, and automation. Prefer `useradd`, `usermod`, `userdel`, `chsh`,
    and `chfn`. If direct repair is unavoidable, use `vipw`, keep a root shell
    open, and validate with `pwck` before closing your recovery path.

## Why `/etc/passwd` matters

Every file owner and running process is ultimately identified by numeric IDs.
Names are the readable labels that administrators use, but the kernel tracks
UIDs and GIDs. The account database connects those pieces:

- A username maps to a UID.
- A UID maps back to a username for tools such as `ls`, `ps`, and `find`.
- A primary GID points to the account's default group.
- A home directory tells login sessions where the user's files should start.
- A shell defines the command interpreter or non-login program started at login.

This makes `/etc/passwd` useful during account audits, offboarding, file
ownership investigations, and login troubleshooting.

## Field format

Each line has seven colon-separated fields:

```text
username:password:UID:GID:GECOS:home_directory:shell
```

| Field | Meaning | Operational notes |
| --- | --- | --- |
| `username` | Login name | Must be unique in the local file. Avoid reusing names for different people. |
| `password` | Historical password field | Usually `x`, meaning the password hash is in `/etc/shadow`. A blank value is dangerous. |
| `UID` | Numeric user ID | This is the primary identity. File ownership follows this number, not the name. |
| `GID` | Primary group ID | Should map to an entry in `/etc/group` or another configured identity source. |
| `GECOS` | Comment field | Often full name, owner, or service description. Do not store secrets here. |
| `home_directory` | Initial directory after login | Missing or wrong paths cause confusing login and application failures. |
| `shell` | Login shell or command | Interactive users need a valid shell; service accounts often use `nologin` or `false`. |

Example:

```text
backup:x:34:34:backup service account:/var/backups:/usr/sbin/nologin
```

That line says `backup` is a local account with UID `34`, primary GID `34`, a
home directory at `/var/backups`, and a shell that prevents interactive login.

## Safe inspection commands

Start with read-only commands. They avoid accidental edits and show what the
system resolver sees, not just what one file contains.

```bash
getent passwd
getent passwd root
getent passwd "$USER"
```

`getent passwd` respects Name Service Switch configuration. That matters on
systems that combine local files with LDAP, SSSD, Active Directory, or another
directory source.

To inspect the local file directly:

```bash
less /etc/passwd
awk -F: '{ print $1, $3, $4, $6, $7 }' /etc/passwd
```

To find accounts that can start an interactive shell:

```bash
awk -F: '$7 !~ /(false|nologin)$/ { print $1 ":" $7 }' /etc/passwd
```

To connect an account to file ownership:

```bash
id alice
find /home -xdev -uid "$(id -u alice)" -ls
```

Run ownership searches carefully on production systems. Large filesystems can
make broad `find /` commands slow and noisy.

## Consistency checks

Use account-aware validators before assuming a file is healthy:

```bash
sudo pwck -r
sudo grpck -r
```

The `-r` flag asks for read-only checking. These commands can identify malformed
entries, missing home directories, invalid shells, or group inconsistencies
without applying repairs.

Other useful checks:

```bash
getent group "$(id -g alice)"
getent passwd | awk -F: '{ print $3 }' | sort -n | uniq -d
getent passwd | awk -F: '$3 == 0 { print }'
```

Duplicate UIDs and extra UID `0` accounts deserve immediate review. UID `0` is
root-equivalent, regardless of the username printed in the first field.

## Making changes safely

Use account tools instead of editing `/etc/passwd` directly:

```bash
sudo usermod -c "Alice Rivera" alice
sudo usermod -d /home/alice -m alice
sudo chsh -s /bin/bash alice
sudo usermod -s /usr/sbin/nologin old-service
```

Before changing an account, capture evidence:

```bash
getent passwd alice
id alice
sudo pwck -r
```

After the change, repeat the same checks and compare the result. If the account
owns files, confirm ownership still matches the intended UID:

```bash
find /home/alice -xdev -not -user alice -ls
```

When disabling a person or service account, changing the shell is only one
control. Also review passwords, SSH keys, sudo rights, group membership,
running processes, cron jobs, systemd timers, and application-level access.

## Troubleshooting patterns

- **`ls` shows numeric owners**: the UID has no matching name in the configured account sources. Check `getent passwd <uid>` and recent account deletion or directory-service outages.
- **A user lands in `/` or cannot create files after login**: inspect the home-directory field, directory existence, ownership, and permissions.
- **Login fails after a shell change**: confirm the shell path exists and is listed in `/etc/shells` when the service requires it.
- **A service account can log in interactively**: set a non-login shell if interactive access is not required, then confirm the service still starts.
- **Two names map to one UID**: treat this as an identity and audit problem unless it is a deliberate, documented exception.

## Lab: audit a test account

Run this only on a disposable VM or lab container.

1. Create a test account:

   ```bash
   sudo useradd -m -c "Lab User" lab-passwd
   ```

2. Capture its account evidence:

   ```bash
   getent passwd lab-passwd
   id lab-passwd
   sudo pwck -r
   ```

3. Change its comment and login shell with account tools:

   ```bash
   sudo usermod -c "Lab User - disabled" lab-passwd
   sudo usermod -s /usr/sbin/nologin lab-passwd
   ```

4. Verify the exact fields that changed:

   ```bash
   getent passwd lab-passwd
   ```

5. Remove the test account and its home directory:

   ```bash
   sudo userdel -r lab-passwd
   ```

6. Confirm the account is gone:

   ```bash
   ! getent passwd lab-passwd
   ```
