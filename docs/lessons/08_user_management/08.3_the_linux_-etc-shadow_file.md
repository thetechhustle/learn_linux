### 08.3 The Linux `/etc/shadow` File

!!! abstract "What you will learn"
    - Explain why Linux keeps password metadata outside `/etc/passwd`.
    - Inspect shadow and password-aging information without exposing sensitive hashes.
    - Recognize account lock, expiration, warning, and inactivity fields.
    - Collect safe evidence during an access review or offboarding handoff.

!!! example "Field story"
    A departing teammate's login must be disabled today, but their home directory and owned files need to stay available for review. You need to prove the account can no longer use password login without pasting password hashes into a ticket.

!!! success "Operator principle"
    Treat `/etc/shadow` as sensitive evidence. Inspect only what you need, redact what you report, and prefer purpose-built account tools over manual edits.

## Why `/etc/shadow` exists

Early Unix systems stored account names and password hashes in `/etc/passwd`. That file has to stay readable by normal users because many tools need to map usernames, UIDs, GIDs, home directories, and shells.

Modern Linux systems keep password hashes and password-aging metadata in `/etc/shadow` instead. The file is normally readable only by `root` or tightly controlled privileged tools.

Use `/etc/passwd` for public account identity. Use `/etc/shadow` only when you need password, lock, or aging evidence.

## Look without leaking

Do not paste raw `/etc/shadow` lines into chat, tickets, or documentation. Even though the password field stores a hash rather than a plaintext password, it is still sensitive material.

Safer inspection commands include:

```bash
sudo passwd -S alice
sudo chage -l alice
```

`passwd -S` summarizes password state. `chage -l` summarizes password aging and account-expiration policy in a more readable form.

If you must inspect the raw entry, keep the output local and redact the password field before sharing:

```bash
sudo getent shadow alice
```

A redacted handoff should look like this:

```text
alice:[REDACTED]:19844:0:90:14:::
```

## Shadow fields

A raw shadow entry is colon-separated:

```text
username:password:lastchange:min:max:warn:inactive:expire:reserved
```

The fields mean:

- **username:** account name.
- **password:** password hash, lock marker, or other password-state marker.
- **lastchange:** date of last password change, stored as days since 1970-01-01.
- **min:** minimum days before the password may be changed again.
- **max:** maximum password age in days.
- **warn:** days of warning before password expiration.
- **inactive:** days after password expiration before the account is disabled.
- **expire:** date when the account itself expires, stored as days since 1970-01-01.
- **reserved:** usually empty; reserved for future use.

Empty fields matter. They usually mean that the corresponding aging control is not set.

## Password state and account state

Password state is not the same thing as account existence.

An account can exist while password login is locked. That is often useful for service accounts, break-glass reviews, and offboarding, because files, UID ownership, and audit history remain intact.

Common states you may see through `passwd -S` include:

- `P`: usable password is set.
- `L`: password is locked.
- `NP`: no password is set.

Exact output varies by distribution, so confirm with the local man pages:

```bash
man passwd
man chage
man shadow
```

For offboarding, locking password login is usually safer than deleting the account immediately:

```bash
sudo passwd -l alice
```

Unlocking reverses that specific password lock:

```bash
sudo passwd -u alice
```

Do not run those commands on a real account during practice. Use a disposable lab account.

## Password aging

Password-aging policy helps answer questions like:

- When was the password last changed?
- Is the password expired?
- When will the user be warned?
- Will the account become inactive after expiration?
- Does the account itself have an expiration date?

Inspect aging policy with:

```bash
sudo chage -l alice
```

Set aging policy only when you have a clear operational reason and a rollback path. For example, a lab-only password max-age change might look like:

```bash
sudo chage -M 90 alice
```

In production, document the reason, affected account, previous value, new value, and verification output.

## Safer access-review workflow

For a real account review, use this order:

1. Identify the account:

   ```bash
   getent passwd alice
   id alice
   ```

2. Check active sessions and processes:

   ```bash
   who
   pgrep -u alice -a
   ```

3. Check password and aging state:

   ```bash
   sudo passwd -S alice
   sudo chage -l alice
   ```

4. If password login must be disabled, lock the password instead of deleting the account:

   ```bash
   sudo passwd -l alice
   ```

5. Verify and record a redacted handoff:

   ```bash
   sudo passwd -S alice
   sudo chage -l alice
   ```

The handoff should say what changed and what remains preserved, such as home directory, UID ownership, service dependencies, and any active processes that still need follow-up.

## Hands-on practice

Use a disposable VM, container, or lab account. Do not practice on a real user's account.

1. Create or choose a lab account.
2. Inspect public identity:

   ```bash
   getent passwd LABUSER
   id LABUSER
   ```

3. Inspect password state and aging:

   ```bash
   sudo passwd -S LABUSER
   sudo chage -l LABUSER
   ```

4. Write a redacted note that answers:
   - Is password login set, locked, or absent?
   - When was the password last changed?
   - Is there a maximum password age?
   - Is there an account expiration date?
   - What exact command would you use to verify this again?

5. If you intentionally created the lab account and it is safe to modify, lock it and verify the state changed:

   ```bash
   sudo passwd -l LABUSER
   sudo passwd -S LABUSER
   ```
