### 08.5 The `/etc/group` File

Groups let administrators grant shared access without copying the same
permission changes across every account. The `/etc/group` file is the local
map of group names, group IDs, and supplemental members. You will inspect it
often when troubleshooting file access, service ownership, and account cleanup.

!!! abstract "What you will learn"
    - Read the four fields in `/etc/group` and explain what each one controls.
    - Compare primary groups from `/etc/passwd` with supplemental groups from
      `/etc/group`.
    - Use `getent`, `id`, `groups`, and `grep` to collect group-membership
      evidence without editing account files by hand.
    - Add, remove, and validate group membership with safer account tools.

!!! warning "Do not edit first"
    Do not start by opening `/etc/group` in a normal editor. A typo can break
    group lookups or leave a user with unexpected access. Prefer `groupadd`,
    `groupmod`, `groupdel`, `usermod`, and `gpasswd`. If a direct edit is
    unavoidable, use `vigr`, which locks the file and checks syntax before
    saving.

## The Record Format

Each line in `/etc/group` describes one group:

```text
group-name:password:GID:member-list
```

The fields are:

- `group-name`: the human-readable group name, such as `sudo`, `wheel`,
  `developers`, or `www-data`.
- `password`: usually `x`, meaning encrypted group password data is not stored
  here. Group passwords are rare on modern systems.
- `GID`: the numeric group ID. File ownership stores this number, not the group
  name.
- `member-list`: a comma-separated list of supplemental members. This list does
  not include users whose primary group is this GID in `/etc/passwd`.

For example:

```text
developers:x:2001:alex,sam
```

This record says that `developers` is GID `2001` and that `alex` and `sam` have
it as a supplemental group.

## Primary vs. Supplemental Groups

Linux account membership comes from two places:

- The user's primary GID is the fourth field in `/etc/passwd`.
- Supplemental group membership is listed in `/etc/group`.

That distinction matters during incident response. A user may have access to a
directory because their primary GID owns it even when their name does not appear
in that group's `/etc/group` member list.

Collect evidence with lookup tools instead of reading only one file:

```bash
getent passwd alex
getent group developers
id alex
groups alex
```

`getent` is preferred over plain `cat /etc/group` because it asks the configured
name-service stack. On systems using LDAP, Active Directory, or another central
directory, not every group is local.

## Common Inspection Tasks

List a local group record:

```bash
getent group developers
```

Find groups that name a user as a supplemental member:

```bash
getent group | awk -F: '$4 ~ /(^|,)alex(,|$)/ { print }'
```

Show every group the system currently grants to a user:

```bash
id alex
```

Show files owned by a specific group under a project path:

```bash
find /srv/project -group developers -ls
```

!!! note "Session refresh"
    Group changes do not always affect sessions that are already logged in.
    After changing group membership, have the user start a new login session, or
    test with a fresh `su - username`, SSH session, or container shell.

## Safer Group Changes

Create a group:

```bash
sudo groupadd developers
getent group developers
```

Add a user to a supplemental group without removing their existing groups:

```bash
sudo usermod -aG developers alex
id alex
```

The `-aG` combination is important. `-G developers` without `-a` replaces the
user's supplemental group list.

Remove a user from one supplemental group:

```bash
sudo gpasswd -d alex developers
id alex
```

Rename a group:

```bash
sudo groupmod -n platform developers
getent group platform
```

Delete a group only after checking ownership references:

```bash
getent group oldteam
find / -xdev -group oldteam -ls 2>/dev/null | head
sudo groupdel oldteam
```

If `groupdel` reports that the group is a user's primary group, change that
user's primary group first or keep the group.

## Validate Account Files

After group changes, run the local consistency check:

```bash
sudo grpck
```

Some distributions also provide `pwck` for checking `/etc/passwd` and
`/etc/shadow` relationships:

```bash
sudo pwck
```

Treat warnings as evidence to review, not as decoration. Duplicate GIDs,
unknown users in a member list, or missing group names can create confusing
access behavior.

## Troubleshooting Patterns

Use these checks when access does not match expectations:

- The user is not in the group: confirm with `id username`, not only
  `/etc/group`.
- The user is in the group but still denied: check directory execute bits,
  parent-directory permissions, ACLs, SELinux/AppArmor policy, and whether the
  session is stale.
- The group name looks right but access is wrong: compare numeric GIDs with
  `stat` and `getent group`.
- A file shows a numeric group instead of a name: the GID exists on disk, but no
  current group database entry maps that number to a name.
- `getent group name` returns nothing: check whether the group is local,
  centrally managed, misspelled, or unavailable because name-service lookup is
  failing.

## Lab: Add and Remove a Project Group

Run this on a disposable VM, container, or lab machine.

1. Create a test user and group:

   ```bash
   sudo useradd -m labuser
   sudo groupadd labproject
   getent passwd labuser
   getent group labproject
   ```

2. Add the user to the group and collect evidence:

   ```bash
   sudo usermod -aG labproject labuser
   id labuser
   getent group labproject
   ```

3. Create a shared directory owned by the group:

   ```bash
   sudo mkdir -p /tmp/labproject
   sudo chgrp labproject /tmp/labproject
   sudo chmod 2770 /tmp/labproject
   stat /tmp/labproject
   ```

   The leading `2` in `2770` sets the setgid bit on the directory, so new files
   created inside inherit the directory's group.

4. Remove the user from the supplemental group and verify:

   ```bash
   sudo gpasswd -d labuser labproject
   id labuser
   getent group labproject
   ```

5. Clean up:

   ```bash
   sudo rmdir /tmp/labproject
   sudo userdel -r labuser
   sudo groupdel labproject
   ```

## Key Takeaways

- `/etc/group` maps group names to GIDs and supplemental members.
- Primary group membership comes from `/etc/passwd`; supplemental membership
  comes from `/etc/group`.
- Use `getent`, `id`, and account-management tools before touching local account
  files directly.
- Validate changes with `grpck`, inspect numeric GIDs, and refresh user sessions
  before declaring an access issue fixed.
