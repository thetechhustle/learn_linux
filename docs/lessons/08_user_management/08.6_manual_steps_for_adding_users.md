### 08.6 Manual Steps for Adding Users

!!! abstract "What you will learn"
    - Explain what account-creation tools do behind the scenes.
    - Identify the files, directories, ownership, groups, shell, and password state involved in a new account.
    - Practice a safe inspection-first workflow for creating a lab user.
    - Avoid brittle manual edits on production systems.

!!! example "Field story"
    A runbook says "add a temporary contractor account by hand." Before you type commands, you need to know what "by hand" really means, which parts are safe to inspect, and why direct account-file edits are risky.

!!! success "Operator principle"
    Manual user creation is a learning exercise and a recovery skill. In normal operations, use account-management tools and verify every side effect.

## What "manual" really means

Creating a Linux user is not one action. A complete local account may require:

- an `/etc/passwd` record
- an `/etc/shadow` record
- a primary group or existing group assignment
- optional supplemental groups
- a home directory
- ownership and permissions for that home directory
- starter files copied from `/etc/skel`
- a login shell
- a password, lock state, or other authentication policy

Tools such as `useradd`, `adduser`, and `newusers` coordinate those pieces for you. Editing account files directly with a normal text editor is fragile. A typo can break logins, create duplicate IDs, or leave the system with inconsistent account databases.

Use this lesson to understand the moving parts. Use the next lesson for the higher-level account-creation tools you should prefer.

## Start with the policy

Before creating an account, answer:

- Is this a human, service, or temporary account?
- What username format is expected?
- Should the account have an interactive shell?
- Should it have a home directory?
- Which primary and supplemental groups are required?
- When should access expire?
- Who approves the account?
- What evidence must be recorded?

Those decisions matter more than the command syntax.

## Inspect before creating

Check whether the account already exists:

```bash
getent passwd alice
id alice
```

Check whether the intended group exists:

```bash
getent group contractors
```

Check available shells:

```bash
cat /etc/shells
```

Check the home-parent directory:

```bash
ls -ld /home
```

If any of those checks produce surprising output, stop and resolve that before creating the account.

## The safer tool-driven version

Even in a "manual steps" lesson, use account tools for actual changes. This example creates a lab account with a home directory, a shell, and one supplemental group:

```bash
sudo useradd -m -s /bin/bash -G contractors alice
```

What this asks the system to do:

- create the account record
- create or reference the primary group according to local defaults
- add `alice` to the supplemental `contractors` group
- create `/home/alice`
- copy starter files from `/etc/skel` when configured
- set the login shell to `/bin/bash`

Set the password only if the lab requires password login:

```bash
sudo passwd alice
```

For many operational accounts, password login should remain locked and access should be handled through SSH keys, identity providers, or service-specific mechanisms.

## Verify every side effect

After creating the account, inspect the result:

```bash
getent passwd alice
getent shadow alice
id alice
ls -ld /home/alice
sudo passwd -S alice
```

Do not paste raw shadow output into tickets. Redact the password field if you need to record the raw line.

Also confirm the shell exists:

```bash
command -v bash
grep -x '/bin/bash' /etc/shells
```

If `/bin/bash` is not an approved login shell on that system, choose a shell that is.

## What direct manual edits would involve

In a recovery scenario, you may need to understand the direct pieces:

1. Add an account entry to `/etc/passwd`.
2. Add password metadata to `/etc/shadow`.
3. Create or select a primary group in `/etc/group`.
4. Add supplemental group memberships.
5. Create the home directory.
6. Set owner and permissions.
7. Copy starter files from `/etc/skel`.
8. Set or lock password authentication.
9. Verify lookups through `getent`, `id`, and login tools.

That is a lot of room for mistakes. If you ever must edit account files directly, use locking tools designed for it, such as `vipw` and `vigr`, and keep a root shell open until you verify that account lookup and privileged access still work.

## Common failure modes

Watch for:

- duplicate UIDs or GIDs
- home directory owned by the wrong account
- shell path that does not exist
- account created without intended supplemental groups
- password accidentally enabled for a service account
- stale group membership in an existing login session
- account file edited but lookup cache or generated database not updated

When in doubt, compare the account with a known-good account of the same type.

## Handoff note

A useful creation handoff says:

```text
Created lab account alice.
Purpose: disposable contractor-access practice.
Command: sudo useradd -m -s /bin/bash -G contractors alice
Verified: getent passwd alice; id alice; ls -ld /home/alice; sudo passwd -S alice.
Password state: locked until explicitly set.
Expiration: not configured.
```

For production, include the approval source, owner, expiration date, and removal plan.

## Hands-on practice

Use only a disposable VM, container, or lab host.

1. Choose a lab username, such as `labuser01`.
2. Inspect first:

   ```bash
   getent passwd labuser01
   getent group users
   cat /etc/shells
   ```

3. Create the lab account with a home directory:

   ```bash
   sudo useradd -m -s /bin/bash labuser01
   ```

4. Verify the result:

   ```bash
   getent passwd labuser01
   id labuser01
   ls -ld /home/labuser01
   sudo passwd -S labuser01
   ```

5. Write a short handoff note that records the command, verification, shell, home directory, and password state.

6. Remove the lab account only if this is truly disposable and you understand what will be deleted. Prefer a lab VM snapshot you can reset.
