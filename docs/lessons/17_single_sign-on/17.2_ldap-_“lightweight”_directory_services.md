# 17.2 LDAP: "Lightweight" Directory Services

!!! abstract "What you will learn"

    - Use safe `ldapsearch` checks to verify reachability, TLS, bind credentials, and directory data.

!!! success "Operator principle"
    LDAP is a directory lookup protocol. It can provide identity data, but login also depends on NSS, PAM, SSSD, Kerberos, TLS trust, and local fallback policy.

LDAP stands for **Lightweight Directory Access Protocol**. In Linux administration, you most often meet it as the protocol used to query a central directory for users, groups, hosts, SSH keys, email addresses, sudo rules, or application identity records.

LDAP is not the same thing as single sign-on. It is one building block. A working login path might use LDAP for account data, Kerberos or another provider for password verification, SSSD for caching, NSS for name lookups, and PAM for the login decision. When an operator says "LDAP is down," the first job is to find which layer is actually failing.

## What LDAP Stores

An LDAP directory is a tree of entries. Each entry has a **distinguished name** (DN) and a set of attributes.

Example entry:

```ldif
dn: uid=ada,ou=People,dc=example,dc=com
objectClass: inetOrgPerson
objectClass: posixAccount
uid: ada
cn: Ada Lovelace
uidNumber: 10042
gidNumber: 10042
homeDirectory: /home/ada
loginShell: /bin/bash
mail: ada@example.com
```

Read the DN from left to right as the specific entry, then its containers:

- `uid=ada` is the relative distinguished name for the user entry.
- `ou=People` is an organizational unit.
- `dc=example,dc=com` is the directory naming context for `example.com`.

Attributes matter because Linux clients often need specific ones. A user may exist in LDAP but still fail Linux login if `uidNumber`, `gidNumber`, `homeDirectory`, group membership, or access-control attributes are missing or mapped differently than the client expects.

## Safe Inspection Workflow

Start with read-only checks. Use a lab server or a known test account when possible, and avoid pasting real bind passwords into shell history.

```bash
# Confirm the client tools are installed on Debian or Ubuntu.
dpkg -l ldap-utils

# Confirm the client tools are installed on RHEL, CentOS, or Fedora.
rpm -q openldap-clients
```

Check anonymous or unauthenticated discovery only if the directory allows it:

```bash
ldapsearch -x -H ldap://ldap.example.com -s base -b "" namingContexts
```

Expected useful output includes one or more naming contexts:

```ldif
namingContexts: dc=example,dc=com
```

Query a narrow base and filter before you run broad searches:

```bash
ldapsearch -x \
  -H ldap://ldap.example.com \
  -b "ou=People,dc=example,dc=com" \
  "(uid=ada)" dn uid uidNumber gidNumber homeDirectory loginShell
```

That command is read-only. It asks one server for one user and returns only the attributes useful for a Linux account check.

## Bind Methods And Secrets

A **bind** is LDAP's authentication step. Common modes include:

- Anonymous bind: useful for public discovery, often disabled for security.
- Simple bind: username and password sent inside the LDAP protocol. Use it only over trusted TLS.
- SASL bind: stronger mechanisms such as GSSAPI/Kerberos, common in enterprise environments.

Avoid putting passwords directly on the command line. Prefer prompting:

```bash
ldapsearch -x -W \
  -H ldaps://ldap.example.com \
  -D "cn=readonly,ou=Service Accounts,dc=example,dc=com" \
  -b "dc=example,dc=com" \
  "(uid=ada)" dn uid
```

The `-W` flag prompts for the password. Using `-w secret` is convenient in examples but can expose credentials through shell history, process listings, terminal logs, or incident transcripts.

## TLS And Certificate Checks

LDAP commonly runs in three patterns:

- `ldap://host:389` without StartTLS: plain text, usually unsafe outside a protected lab.
- `ldap://host:389` with StartTLS: begins plain, then upgrades to TLS.
- `ldaps://host:636`: TLS from the start.

Check StartTLS explicitly:

```bash
ldapsearch -x -ZZ \
  -H ldap://ldap.example.com \
  -s base -b "" supportedLDAPVersion
```

Use `-ZZ` when StartTLS is required. A lowercase `-Z` only tries StartTLS and can continue without it depending on client behavior.

If TLS fails, gather certificate evidence before changing trust settings:

```bash
openssl s_client -connect ldap.example.com:636 -servername ldap.example.com </dev/null
```

Do not "fix" TLS by disabling certificate checks on production clients. A setting such as `TLS_REQCERT never` can hide a real trust problem and make credential interception easier.

## Filters And Scope

LDAP filters control which entries come back. A few common examples:

```text
(uid=ada)
(objectClass=posixAccount)
(&(objectClass=posixAccount)(uid=ada))
(|(uid=ada)(mail=ada@example.com))
```

Search scope controls how much of the tree is searched:

- `base`: only the exact entry named by `-b`.
- `one`: immediate children below the base.
- `sub`: the full subtree below the base.

For troubleshooting, start with `base` or `one` when you can. Broad subtree searches from the directory root can be slow, noisy, and misleading in large environments.

## Common Failure Patterns

LDAP outages often look like login problems. Separate the symptoms:

- **Network failure:** `ldapsearch` cannot connect, times out, or only one site is affected.
- **Name resolution failure:** the LDAP hostname resolves to the wrong address or only IPv6/IPv4 works.
- **TLS trust failure:** certificate expired, hostname mismatch, missing CA, or StartTLS policy mismatch.
- **Bind failure:** bad service-account password, locked bind account, wrong DN, or changed access policy.
- **Search-base failure:** client searches `dc=example,dc=com` while users live under another base.
- **Schema or mapping failure:** required POSIX attributes are absent or group membership uses a different attribute than the client expects.
- **Authorization failure:** the user exists and authenticates, but access filters, PAM rules, sudo policy, or host restrictions deny login.

Keep the handoff precise. "LDAP returned the user but SSSD denied access because the access filter did not match" is much more useful than "LDAP login is broken."

## Lab: Read An LDAP Directory Safely

Use a disposable LDAP container, a lab VM, or a provided training directory.

1. Record the LDAP URI, search base, and whether TLS is required.
2. Run a base-scope search for naming contexts.
3. Run one user lookup with a narrow `(uid=...)` filter.
4. Identify the user's DN, `uidNumber`, `gidNumber`, home directory, and login shell.
5. Repeat the query with StartTLS or LDAPS if your lab supports it.
6. Write a short incident note that states whether the server, TLS, bind, search base, and user attributes look healthy.
