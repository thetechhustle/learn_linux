# 17.3 Using Directory Services for Login

Directory services become operationally useful when Linux hosts can use them for account lookup and login decisions. The important idea is not "install one package and reboot." The important idea is that login depends on several layers: name lookup, authentication, account policy, session setup, and service-specific rules.

This lesson uses SSSD as the modern default client because it integrates with NSS and PAM, supports caching, and can talk to LDAP, Kerberos, FreeIPA, and Active Directory environments.

!!! abstract "What you will learn"
    - Explain how Linux uses directory data during login.
    - Distinguish NSS account lookup from PAM authentication and account checks.
    - Inspect SSSD, PAM, SSH, and logs before changing configuration.
    - Use a cautious rollout pattern for directory-backed login.

## The Login Path

When a directory-backed user logs in over SSH, the flow usually looks like this:

1. `sshd` receives the login attempt.
2. PAM applies authentication and account rules.
3. NSS resolves the username, UID, groups, shell, and home directory.
4. SSSD talks to the configured identity source or uses a cache.
5. SSH and PAM decide whether the user may start a session.
6. Session modules create the environment and record the login.

A failure in any layer can look like "login is broken." Separate the layers before changing anything.

## Prefer SSSD for New Linux Clients

Older tutorials often use `pam_ldap` and `nss_ldap` directly. Those stacks still exist in some environments, but SSSD is usually the safer default for modern Linux systems because it provides:

- one service for identity and authentication integration
- credential and identity caching
- offline login policy
- better diagnostics through `sssctl`
- integration with Kerberos, LDAP, FreeIPA, and Active Directory

On Debian or Ubuntu-family systems, common packages are:

```bash
sudo apt install sssd sssd-tools libnss-sss libpam-sss
```

On Red Hat-family systems, common packages are:

```bash
sudo dnf install sssd sssd-tools oddjob-mkhomedir authselect
```

Install packages only in a lab or approved change window. Production identity changes can lock out administrators quickly.

## Inspect the Current Host

Before adding directory login, identify how the host currently resolves accounts and authenticates users.

```bash
grep '^passwd:' /etc/nsswitch.conf
grep '^group:' /etc/nsswitch.conf
grep -E "^(auth|account|password|session)" /etc/pam.d/sshd
grep -E "^(UsePAM|PasswordAuthentication|PubkeyAuthentication|AllowUsers|AllowGroups|DenyUsers|DenyGroups)" /etc/ssh/sshd_config
```

Then test local account lookup:

```bash
getent passwd root
id root
```

If these basic checks fail, fix the local system first. Directory integration will not make an unhealthy login stack safer.

## Configure SSSD Carefully

SSSD configuration lives at `/etc/sssd/sssd.conf`. The file usually needs mode `0600` because it can contain sensitive connection details.

A simplified LDAP-style example:

```ini
[sssd]
services = nss, pam
config_file_version = 2
domains = example

[domain/example]
id_provider = ldap
auth_provider = ldap
ldap_uri = ldaps://ldap.example.com
ldap_search_base = dc=example,dc=com
cache_credentials = true
enumerate = false
```

This example is not a drop-in production configuration. Real environments must decide:

- whether authentication uses LDAP bind, Kerberos, FreeIPA, or Active Directory
- how TLS certificates are trusted
- whether offline credentials are allowed
- which groups may log in
- how home directories are created
- whether sudo rules come from local files or the directory

After editing SSSD configuration, validate and restart the service:

```bash
sudo chmod 600 /etc/sssd/sssd.conf
sudo systemctl restart sssd
systemctl status sssd --no-pager
```

## Wire NSS and PAM

NSS controls account and group lookup. A directory-backed host commonly includes `sss` in `passwd` and `group` lines:

```text
passwd: files systemd sss
group:  files systemd sss
```

PAM controls authentication, account checks, password changes, and session setup. On many distributions, installing `libpam-sss` or using the system authentication tool wires this automatically.

Distribution tools are safer than hand-editing PAM:

```bash
# Red Hat-family example
sudo authselect current
sudo authselect select sssd with-mkhomedir

# Debian/Ubuntu-family inspection
grep -R "pam_sss" /etc/pam.d
```

Do not overwrite PAM files from memory. Compare the distribution's expected configuration and keep a rollback path.

## Verify Account Lookup Before Login

Before testing SSH login, prove that Linux can resolve the directory user.

```bash
getent passwd username
id username
groups username
```

If lookup fails:

- check DNS for the directory service
- check network reachability
- check TLS trust
- check `/etc/sssd/sssd.conf`
- check SSSD logs
- confirm the user exists in the directory

Useful SSSD commands:

```bash
sssctl config-check
sssctl domain-status
sssctl user-checks username
```

If `sssctl` is unavailable, verify whether SSSD is actually the configured client.

## Test Login Without Losing Access

Directory login testing should be staged:

1. Keep an existing local admin session open.
2. Keep a tested local emergency account.
3. Use a second terminal or console for the directory login test.
4. Test account lookup before testing SSH.
5. Test SSH with verbose client output.
6. Review logs before making a second change.

Example SSH test:

```bash
ssh -vvv username@host.example.com
```

Server-side logs:

```bash
journalctl -u ssh --since "30 minutes ago"
journalctl _COMM=sshd --since "30 minutes ago"
journalctl -u sssd --since "30 minutes ago"
```

Different distributions name the SSH service differently, such as `ssh` or `sshd`.

## Home Directories and Shells

A directory user can authenticate successfully and still fail to get a usable session.

Check these fields:

```bash
getent passwd username
```

Look for:

- valid UID and GID
- usable home directory path
- valid login shell
- expected group membership

If home directories are created on first login, verify the session module:

```bash
grep -R "mkhomedir" /etc/pam.d
```

If the shell path does not exist on the host, login may fail after successful authentication.

## Access Control

Do not let every directory user log in just because the directory is reachable. Restrict access deliberately.

Controls may include:

- SSSD access provider rules
- host groups in FreeIPA or Active Directory
- SSH `AllowGroups` or `AllowUsers`
- PAM access rules
- sudoers policy

Inspection examples:

```bash
grep -E "^(access_provider|simple_allow|simple_deny)" /etc/sssd/sssd.conf
grep -E "^(AllowUsers|AllowGroups|DenyUsers|DenyGroups)" /etc/ssh/sshd_config
sudo -l -U username
```

Document which layer owns host access. Avoid spreading the same rule across SSSD, SSH, PAM, and sudo unless there is a clear reason.

## Troubleshooting Checklist

Use this sequence when a directory login fails:

1. Confirm the host can resolve the identity source in DNS.
2. Confirm time synchronization.
3. Confirm SSSD is running.
4. Confirm `getent passwd username` works.
5. Confirm `id username` shows expected groups.
6. Confirm PAM includes the expected SSSD modules.
7. Confirm SSH permits PAM and does not deny the user or group.
8. Confirm account policy permits login.
9. Confirm the shell and home directory are valid.
10. Review SSH, PAM, and SSSD logs for the same timestamp.

Do not clear caches or restart services repeatedly without preserving the log evidence.

Run these on a lab host or disposable VM.

1. Inspect `passwd` and `group` lookup sources in `/etc/nsswitch.conf`.
2. Inspect the SSH PAM stack and identify whether `pam_sss` is present.
3. If SSSD is installed, run `sssctl config-check` and `sssctl domain-status`.
4. Pick one local user and record `getent passwd`, `id`, and shell/home-directory fields.
5. Write a short troubleshooting note that separates lookup, authentication, authorization, and session setup.
