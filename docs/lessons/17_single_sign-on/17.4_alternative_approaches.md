# 17.4 Alternative Approaches

LDAP-backed login is only one way to centralize identity. Real Linux environments often combine directory services, Kerberos, FreeIPA, Active Directory, web SSO, SSH certificates, and cloud identity systems. The right choice depends on what needs to authenticate: Linux shells, web applications, APIs, laptops, servers, containers, or cloud workloads.

This lesson compares common approaches from an operator's point of view.

!!! abstract "What you will learn"
    - Compare common SSO and centralized identity patterns.
    - Identify which pattern fits Linux login, web SSO, API access, and SSH access.
    - Recognize operational tradeoffs around audit, lifecycle, availability, and lockout risk.
    - Choose evidence to collect before changing identity architecture.

## Start With the Access Problem

Do not choose an identity technology by name recognition alone. Start with the access path.

Ask:

- Are users logging in to Linux hosts?
- Are users opening browser-based applications?
- Are services calling APIs?
- Are administrators using SSH?
- Are workloads running in Kubernetes or a cloud platform?
- Does the organization already run Active Directory, FreeIPA, Okta, Entra ID, Google Workspace, or another identity provider?
- What is the emergency access path if the identity provider is unavailable?

Different access paths need different protocols.

## Kerberos

Kerberos is a ticket-based authentication protocol. Instead of sending a password to every service, the user receives tickets from a trusted Key Distribution Center.

Kerberos is a good fit when:

- Linux systems need domain-style authentication.
- Time synchronization is reliable.
- Services can validate Kerberos tickets.
- The environment already uses Active Directory or FreeIPA.

Operational strengths:

- avoids repeated password transmission
- supports strong mutual authentication
- integrates well with SSH, NFS, FreeIPA, and Active Directory environments

Operational risks:

- depends heavily on DNS and time synchronization
- realm and keytab mistakes are common
- troubleshooting can be confusing if logs are not collected carefully

Useful evidence:

```bash
timedatectl
klist
klist -k 2>/dev/null || true
realm list 2>/dev/null || true
```

If time is wrong, fix that before debugging Kerberos.

## FreeIPA

FreeIPA is an integrated Linux identity management platform. It combines LDAP, Kerberos, certificate services, DNS integration, host enrollment, sudo policy, and host-based access control.

FreeIPA is a good fit when:

- the environment is primarily Linux or Unix-like
- administrators want Linux-native identity management
- host enrollment and host-based access rules matter
- centralized sudo policy is needed

Operational strengths:

- combines several identity services behind one administrative model
- integrates cleanly with SSSD
- supports host groups, sudo rules, and HBAC policy
- gives Linux administrators a coherent identity platform

Operational risks:

- adds infrastructure that must be backed up and monitored
- requires careful DNS, certificate, and replication planning
- may overlap with an existing Active Directory environment

Useful evidence on a joined host:

```bash
ipa --version 2>/dev/null || true
realm list 2>/dev/null || true
sssctl domain-status 2>/dev/null || true
```

## Active Directory

Active Directory is common in mixed Windows and Linux environments. Linux hosts usually integrate through SSSD, realmd, Samba tooling, or vendor-specific agents.

Active Directory is a good fit when:

- the organization already uses AD for users and groups
- Windows and Linux access should share the same identity lifecycle
- Kerberos and LDAP are already available through domain controllers
- group policy, compliance, or existing operations require AD as the source of truth

Operational strengths:

- often already exists
- centralizes lifecycle for many organizations
- supports Kerberos and LDAP-compatible queries
- integrates with cloud identity in many Microsoft environments

Operational risks:

- Linux group and access mapping must be designed, not guessed
- nested groups and large directories can affect lookup behavior
- DNS, time, and site topology problems can cause intermittent login failures

Useful evidence:

```bash
realm list 2>/dev/null || true
adcli info example.com 2>/dev/null || true
id username@example.com
sssctl user-checks username@example.com 2>/dev/null || true
```

## SAML

SAML is commonly used for browser-based enterprise SSO. It exchanges signed XML assertions between an identity provider and a service provider.

SAML is a good fit when:

- users access web applications through a browser
- enterprise SaaS apps need centralized login
- the organization has an identity provider such as Okta, Entra ID, Google Workspace, or Ping

Operational strengths:

- mature enterprise web SSO pattern
- widely supported by SaaS vendors
- can carry group or attribute claims

Operational risks:

- not a native Linux shell-login protocol
- certificate rollover can break login
- clock skew and assertion validation failures can be subtle
- group/attribute mapping must be tested

Useful evidence is usually collected from the identity provider, service provider, and browser trace, not from `/etc/passwd`.

For Linux administrators, the key point is simple: SAML may authenticate users into a web dashboard, but it does not by itself make `ssh username@host` work.

## OAuth 2.0 and OpenID Connect

OAuth 2.0 is an authorization framework for delegated access. OpenID Connect adds an identity layer on top of OAuth 2.0.

OIDC is a good fit when:

- web applications need modern SSO
- APIs need bearer-token access
- applications run in cloud or Kubernetes environments
- short-lived tokens are preferred over passwords

Operational strengths:

- common in modern application stacks
- supports short-lived tokens and scopes
- works well with API gateways, service meshes, and cloud identity providers

Operational risks:

- token audience, issuer, scope, and expiration must be validated correctly
- storing long-lived refresh tokens carelessly creates security risk
- OIDC does not automatically solve Linux host login

Useful evidence:

```bash
jq -R 'split(".") | .[0], .[1] | @base64d | fromjson?' 2>/dev/null
```

Use token-inspection tools carefully. Do not paste real production tokens into untrusted websites or logs.

## SSH Certificates

SSH certificates centralize SSH trust without requiring every host to list every user's public key. A trusted certificate authority signs short-lived user certificates, and hosts trust that CA.

SSH certificates are a good fit when:

- the main problem is administrator SSH access
- short-lived access is preferred
- teams want to remove static keys from many servers
- identity is already handled by another system that can issue certificates

Operational strengths:

- reduces static key sprawl
- supports short-lived access
- can encode principals and validity windows
- works well with bastions and access brokers

Operational risks:

- CA key protection is critical
- host configuration must trust the right CA
- principal mapping must be clear
- revocation and emergency access need planning

Useful host-side evidence:

```bash
grep -E "^(TrustedUserCAKeys|AuthorizedPrincipalsFile|AuthorizedKeysFile)" /etc/ssh/sshd_config
ssh-keygen -Lf user-cert.pub 2>/dev/null || true
```

## Cloud Identity and Workload Identity

Cloud platforms provide identity services for users, services, and workloads. Examples include IAM roles, workload identity federation, managed identities, and service accounts.

These are a good fit when:

- workloads run in AWS, Azure, Google Cloud, or Kubernetes
- services need access to cloud APIs without static credentials
- identity should be tied to instance, pod, service account, or workload metadata

Operational strengths:

- avoids long-lived static secrets
- supports least privilege through roles and policies
- integrates with audit logs
- works well for automation and service-to-service access

Operational risks:

- policy language can be complex
- privilege boundaries can be misunderstood
- metadata-service exposure can become a security issue
- local Linux login may still need a separate plan

Useful evidence depends on the platform. For Linux operators, record the role or workload identity, the policy attached, the token source, and the audit log entry proving use.

## Choosing an Approach

Use this rough map:

| Need | Common approach |
| --- | --- |
| Linux host login in a Linux-heavy environment | FreeIPA or LDAP/Kerberos with SSSD |
| Linux host login in a Windows-heavy environment | Active Directory with SSSD/realmd |
| Enterprise web application SSO | SAML or OpenID Connect |
| API access | OAuth 2.0/OIDC tokens |
| Administrator SSH access | SSH certificates, bastion, or access broker |
| Cloud workload access | Cloud IAM or workload identity |

Most organizations use more than one approach. The goal is not one protocol for everything. The goal is a coherent identity lifecycle, auditable access, and a tested emergency path.

## Migration Questions

Before changing identity architecture, answer:

- What is the source of truth for users and groups?
- Which systems must be reachable during login?
- What happens during an identity-provider outage?
- How are contractors, service accounts, and emergency admins handled?
- How are group changes propagated and audited?
- Which logs prove successful and failed access?
- What is the rollback plan?

## Hands-on Practice

Use a lab or documentation-only review.

1. Pick one access path: Linux SSH, web app SSO, API access, or cloud workload access.
2. Identify the likely protocol or product for that path.
3. List the source of truth, client, verifier, and audit log.
4. Write one failure scenario and classify whether it is lookup, authentication, authorization, session, token, or policy failure.
5. Identify the emergency access path.
