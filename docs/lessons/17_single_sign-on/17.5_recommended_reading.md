### 17.5 Recommended Reading

SSO work crosses several layers: identity data, authentication
protocols, authorization policy, Linux account lookup, and application
integration. The best reading path is not one giant book. It is a set of
references you can use to answer specific operator questions before you
change a login path.

!!! abstract "What you will learn"
    - Choose the right reference for LDAP, Kerberos, SSSD, PAM, NSS, OAuth, or OpenID Connect questions.
    - Separate vendor setup guides from protocol specifications and Linux client documentation.
    - Build a short reading note before changing production authentication.
    - Identify which parts of an SSO design need lab validation instead of trust in documentation alone.

!!! success "Operator principle"
    Read protocol references for behavior, vendor docs for supported configuration, and local logs for what your system actually did.

## Start with the local Linux integration path

When a Linux host uses centralized identity, the most important question is:
"Which local component made this login decision?" Start with the local client
stack before reading cloud or application SSO guides.

- **SSSD documentation:** Use the upstream SSSD manuals for domain
  configuration, cache behavior, offline logins, access providers, TLS
  settings, and debug levels. They are the most practical reference when
  Linux hosts join LDAP, FreeIPA, or Active Directory backed environments.
- **PAM manual pages:** Read `pam(8)`, `pam.conf(5)`, and the relevant module
  pages before editing files under `/etc/pam.d/`. PAM ordering controls
  whether a user can authenticate, whether a session is created, and which
  restrictions apply.
- **NSS manual pages:** Read `nsswitch.conf(5)` and service-specific NSS
  documentation when account or group lookups fail even though
  authentication succeeds.
- **FreeIPA and realmd documentation:** Use these when the environment relies
  on FreeIPA, Active Directory enrollment, Kerberos, and SSSD together.
  Confirm the commands against your distribution version before running
  join or leave operations.

## LDAP and directory service references

LDAP documentation is useful when you need to understand directory shape,
search filters, TLS, bind behavior, and replication symptoms.

- **LDAP for Rocket Scientists:** A detailed, practical LDAP reference for
  entries, distinguished names, schemas, filters, referrals, and common
  OpenLDAP patterns.
- **OpenLDAP Administrator's Guide:** Use the versioned OpenLDAP guide when
  you manage OpenLDAP servers directly. Pay close attention to TLS, access
  control, replication, and backup documentation.
- **RFC 4510 through RFC 4519:** These RFCs define the LDAP technical
  specification family. They are dense, but they are the right source when
  you need precise behavior for LDAP URLs, filters, schemas, or protocol
  operations.
- **Vendor directory docs:** Active Directory, FreeIPA, Okta LDAP interface,
  and other managed directory products can differ in supported schemas,
  controls, and bind methods. Treat vendor docs as the source of support
  boundaries.

## Kerberos references

Kerberos often sits underneath enterprise Linux SSO even when the visible
user experience is just "log in with the company password."

- **RFC 4120, The Kerberos Network Authentication Service (V5):** Read this
  for protocol vocabulary: principals, realms, tickets, KDCs, TGTs, service
  tickets, and clock-skew behavior.
- **MIT Kerberos documentation:** Use this for `krb5.conf`, `kinit`,
  `klist`, keytabs, encryption types, and client troubleshooting.
- **Active Directory Kerberos documentation:** Use Microsoft documentation
  when Linux clients authenticate against AD. AD-specific SPN, keytab,
  encryption, and domain trust behavior matters in mixed environments.

## OAuth, OpenID Connect, and SAML references

Application SSO often uses browser-centered protocols rather than direct
Linux account lookup. These references help you understand the boundary
between web app access and Unix login.

- **OAuth 2.0 RFC 6749 and OAuth 2.1 drafts:** Read these for delegation
  flows, clients, authorization servers, access tokens, and refresh tokens.
  OAuth alone is not an authentication protocol.
- **OpenID Connect Core:** Read this when an application says it supports
  "login with SSO" through an identity provider. Focus on ID tokens, claims,
  redirect URIs, scopes, and discovery metadata.
- **SAML 2.0 technical overview and vendor guides:** Read these for older
  enterprise application integrations. Pay attention to metadata exchange,
  signing certificates, assertion attributes, and clock synchronization.
- **Your identity provider's application integration docs:** Okta, Entra ID,
  Google Workspace, Keycloak, Authentik, and other IdPs expose different
  policy controls and claim-mapping behavior. Use provider docs for the
  supported configuration path.

## Security and operations reading

SSO changes can lock out users quickly. Pair protocol reading with operational
security references.

- **CIS Benchmarks for Linux distributions:** Use these to compare local
  authentication hardening, password policy, sudo policy, SSH configuration,
  and audit settings against a recognized baseline.
- **NIST Digital Identity Guidelines:** Use NIST SP 800-63 for identity
  assurance, authenticator assurance, federation concepts, and MFA risk
  framing.
- **Distribution security guides:** Red Hat, Ubuntu, Debian, SUSE, and
  FreeBSD each document supported ways to integrate authentication services.
  Prefer distribution guidance over old blog posts for production hosts.
- **Incident response runbooks:** Keep local runbooks for emergency break-glass
  accounts, SSO outage response, IdP certificate rotation, and rollback from
  failed PAM/SSSD changes.

## Pre-change reading note

Before a production SSO change, write a short note that answers these
questions:

1. Which component will change: PAM, NSS, SSSD, Kerberos, LDAP, SSH, sudo, or an application SSO client?
2. Which documentation version matches the installed package or provider tenant?
3. What command will prove the current behavior before the change?
4. What command will prove the new behavior after the change?
5. What local or out-of-band access remains if centralized login fails?
6. Which logs will show authentication, account lookup, authorization, and session setup results?

## Hands-on practice

Run this in a disposable VM or lab environment.

1. Pick one Linux SSO component, such as SSSD, PAM, NSS, Kerberos, or LDAP.
2. Find the authoritative manual page or project documentation for that component.
3. Write a five-line reading note with the exact version you read, one risk,
   one rollback step, and two verification commands.
4. Run one read-only verification command, such as:

    ```bash
    getent passwd "$USER"
    id "$USER"
    sssctl config-check
    klist
    ldapsearch -x -LLL -s base -b "" namingContexts
    ```

5. Compare the command output with the behavior the documentation says to expect.
