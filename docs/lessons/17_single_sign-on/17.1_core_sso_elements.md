# 17.1 Core SSO Elements

Single sign-on works because several identity systems cooperate. When Linux administrators debug SSO, they need to separate those systems instead of treating every login failure as a password problem.

This lesson names the core pieces and shows how to collect evidence from a Linux host.

!!! abstract "What you will learn"
    - Distinguish authentication, authorization, account data, and session state.
    - Identify the systems involved in a Linux SSO login.
    - Gather read-only evidence before changing PAM, NSS, SSSD, or directory settings.
    - Explain an SSO failure in terms of the component that failed.

## Authentication

Authentication answers one question: **is this user who they claim to be?**

Common authentication mechanisms include:

- Password checks against a directory or identity provider.
- Kerberos tickets.
- SSH public keys.
- Multi-factor authentication challenges.
- Short-lived tokens from an identity provider.

On a Linux host, authentication is often coordinated through PAM. PAM modules decide which checks apply for SSH, console login, sudo, graphical login, and other entry points.

Read-only inspection examples:

```bash
grep -R "pam_" /etc/pam.d/sshd /etc/pam.d/login /etc/pam.d/sudo
grep -E "^(auth|account|password|session)" /etc/pam.d/sshd
```

Do not edit PAM files during an active remote-only SSH session unless you have a tested fallback console or another administrative path.

## Authorization

Authorization answers a different question: **what is this authenticated user allowed to do?**

Examples include:

- Whether a user may log in to this host.
- Whether a user can run `sudo`.
- Which Unix groups the user belongs to.
- Which application roles the user receives.
- Whether host access is restricted by policy.

Linux authorization can come from multiple places at once: local groups, LDAP groups, SSSD access rules, sudoers policy, SSH settings, and application-specific role mapping.

Useful checks:

```bash
id username
getent group admin
sudo -l -U username
grep -E "^(AllowUsers|AllowGroups|DenyUsers|DenyGroups)" /etc/ssh/sshd_config
```

If authentication succeeds but authorization fails, the logs often show messages about account restrictions, access denied, missing groups, or sudo policy instead of bad credentials.

## Account Data

Account data tells Linux who a user is after identity has been resolved. It includes:

- username
- numeric UID
- primary GID
- supplementary groups
- home directory
- login shell
- account expiration or lock status

The Name Service Switch, or NSS, controls where Linux looks for this information. Common sources are local files, LDAP, SSSD, or systemd-based resolvers.

Read-only checks:

```bash
getent passwd username
getent group groupname
getent shadow username
grep '^passwd:' /etc/nsswitch.conf
grep '^group:' /etc/nsswitch.conf
```

If `id username` works but login still fails, the problem may be PAM policy, SSH policy, home-directory access, shell validity, or service-specific restrictions.

## Sessions

A session begins after authentication and authorization succeed. Linux then starts the user's environment and applies session rules.

Session setup may include:

- creating or mounting a home directory
- setting environment variables
- applying resource limits
- registering the login with systemd-logind
- starting a shell, desktop session, or command

Useful checks:

```bash
loginctl list-sessions
loginctl show-user username
journalctl -u ssh --since "30 minutes ago"
journalctl _COMM=sshd --since "30 minutes ago"
```

Session failures can look like login failures. For example, a user might authenticate successfully but be disconnected because the home directory is missing or the configured shell does not exist.

## Directory Services

A directory service stores identity data centrally. LDAP is a common protocol for querying that data, while products such as FreeIPA and Active Directory provide broader identity management around it.

Directory service health affects Linux login in several ways:

- Can the host reach the directory server?
- Does DNS resolve the directory service correctly?
- Is TLS trust configured?
- Does the user object exist?
- Does the group mapping match what Linux expects?
- Are cached credentials stale?

Read-only checks vary by client, but these are common starting points:

```bash
getent passwd username
getent group groupname
sssctl domain-status 2>/dev/null || true
sssctl user-checks username 2>/dev/null || true
```

If `sssctl` is not installed, the host may not use SSSD. Inspect `/etc/nsswitch.conf`, `/etc/pam.d/`, and installed packages before assuming the identity stack.

## Tokens and Tickets

Many SSO designs avoid sending a password to every service. Instead, a user authenticates once and receives a ticket or token that other services can validate.

Examples:

- Kerberos tickets for domain-style authentication.
- OAuth 2.0 access tokens for API access.
- OpenID Connect ID tokens for identity assertions.
- SAML assertions for browser-based enterprise SSO.

On Linux hosts, Kerberos is the most common ticket system administrators inspect directly.

```bash
klist
klist -A 2>/dev/null || true
```

Ticket failures often involve time drift, DNS, realm configuration, expired credentials, or keytab problems. Check time synchronization early:

```bash
timedatectl
```

## Cache and Offline Behavior

SSO clients often cache identity data so hosts can continue working during short outages. That cache can help availability, but it can also confuse troubleshooting.

Questions to ask:

- Is the user being found from live directory data or cache?
- Was group membership recently changed?
- Are cached credentials still allowed?
- Should this host allow offline login?

SSSD-specific checks:

```bash
sssctl cache-status 2>/dev/null || true
sssctl domain-status 2>/dev/null || true
```

Do not clear identity caches casually on production hosts. Cache invalidation can interrupt active users or hide the evidence you need.

## A Practical Failure Model

When a login fails, classify it before making changes:

1. **Identity lookup:** Can Linux find the user and groups?
2. **Authentication:** Did the credential, key, ticket, or MFA challenge succeed?
3. **Authorization:** Is the authenticated user allowed onto this host or into this role?
4. **Session setup:** Did the shell, home directory, limits, and session hooks succeed?
5. **Service path:** Is this failure specific to SSH, sudo, console login, or an application?

Capture the command, timestamp, host, username, client address, and relevant logs before changing configuration.

## Hands-on Practice

Run these on a disposable VM, lab host, or read-only production check window.

1. Inspect `/etc/nsswitch.conf` and identify where `passwd` and `group` lookups come from.
2. Run `getent passwd root` and `id root`, then repeat with a non-root account.
3. Inspect the PAM stack for SSH or console login.
4. Check recent SSH authentication logs with `journalctl`.
5. If SSSD or Kerberos is installed, run the read-only status commands above.
6. Write a short note that separates identity lookup, authentication, authorization, and session setup evidence.
