## 14.5 Building Wiring

!!! abstract "What you will learn"
    - Explain why structured cabling is operational infrastructure, not decoration.
    - Identify the wiring details that matter before blaming Linux, switches, or applications.
    - Use Linux evidence to separate host, switch-port, patch-panel, and cable-run problems.
    - Write a useful cabling handoff for facilities, network engineers, or the next on-call operator.

!!! example "Field story"
    A team moves into a new office. One desk negotiates at 100 Mbps, another drops every few hours, and a small conference-room switch loops the network whenever someone plugs in a patch cable. The servers, laptops, and access points look like the problem until you trace the physical path.

!!! success "Operator principle"
    A network path is only as reliable as its weakest physical segment. Labels, cable category, patch-panel discipline, power, bend radius, grounding, and test results are part of the system.

## The Physical Path

For an Ethernet device in a building, the packet's path usually crosses several physical boundaries before it reaches the rest of the network:

1. The host NIC and its short patch cable.
2. A wall jack or floor box.
3. Horizontal cabling through the wall, ceiling, or conduit.
4. A patch panel in a telecom room or rack.
5. Another patch cable from patch panel to switch.
6. The switch port, power source, and upstream uplink.

When a host has network symptoms, you need to know which segment you have actually tested. Swapping a laptop patch cable does not prove the in-wall run is good. Moving a switch port does not prove the wall jack is good. A clean `ping` test does not prove the cable can sustain speed under load.

## Cable Types You Will See

Most office Ethernet wiring uses twisted-pair copper cable:

- **Cat 5e** commonly supports 1 Gbps to 100 meters when properly installed.
- **Cat 6** improves noise margin and is common for modern office runs.
- **Cat 6A** is the usual copper choice for 10 Gbps at full 100-meter channel distance.
- **Shielded cable** can help in noisy environments, but only when the grounding and termination plan is correct.

Fiber appears between closets, floors, buildings, data-center racks, and high-speed uplinks:

- **Multimode fiber** is common for shorter building and data-center links.
- **Single-mode fiber** is common for longer runs and carrier-style paths.
- **Transceiver type, fiber type, connector cleanliness, and light levels** matter as much as the switch configuration.

Coaxial cable still appears for broadband handoffs, older camera systems, and television distribution. Treat it as a separate access or facilities medium, not normal office Ethernet cabling.

## Structured Cabling Terms

You do not need to become a cable installer, but you should know the language:

- **MDF**: main distribution frame, often the primary network or telecom room.
- **IDF**: intermediate distribution frame, usually a floor or area wiring closet.
- **Demarc**: provider handoff point where responsibility changes between carrier and site.
- **Patch panel**: rack-mounted termination point for building cable runs.
- **Horizontal cabling**: permanent cable run from telecom room to work area.
- **Patch cable**: short flexible cable between device and jack, or patch panel and switch.
- **Run number / jack label**: the identifier that lets humans trace a path.
- **Certification test**: installer-grade proof that a cable meets category requirements.

Good labels turn a physical-layer incident into a short workflow. Bad labels turn it into a scavenger hunt.

## Linux Evidence From the Host

Start with what the Linux host can prove. These commands are read-only:

```bash
ip link show
ip addr show
ip route show
ethtool enp0s31f6
ethtool -S enp0s31f6 | less
journalctl -k --since "1 hour ago" | grep -Ei 'link|eth|enp|rename|carrier|duplex|speed'
```

Replace `enp0s31f6` with the actual interface name.

Useful fields from `ethtool` include:

- `Speed`: negotiated link speed, such as `100Mb/s`, `1000Mb/s`, or `10000Mb/s`.
- `Duplex`: half duplex is a serious red flag on modern switched Ethernet.
- `Auto-negotiation`: usually expected for copper Ethernet.
- `Link detected`: whether carrier is present.

Common physical-layer clues:

- A gigabit-capable port negotiates at `100Mb/s`.
- Link flaps appear repeatedly in `journalctl`.
- CRC, alignment, frame, or receive errors increase under traffic.
- The same host works on a different jack with the same patch cable.
- A different host fails on the same jack.

Linux cannot inspect the in-wall cable directly, but it can show symptoms that justify a physical path test.

## Switch And Patch-Panel Evidence

If you have switch access, pair host evidence with switch-port evidence:

- Administrative state: is the port enabled?
- Operational state: is the link up?
- Negotiated speed and duplex.
- Error counters: CRC, input errors, runts, giants, drops.
- PoE status for access points, phones, cameras, and small switches.
- MAC address learned on the port.
- VLAN assignment and trunk/access mode.
- Link-flap history, if the platform records it.

The patch panel matters because the switch port is rarely connected directly to the wall jack. Confirm the full chain:

```text
Host -> patch cable -> wall jack -> building run -> patch panel -> patch cable -> switch port
```

Do not move patch cords blindly in a production closet. Photograph the current patching first, change one thing at a time, and keep a rollback path.

## Power And Environmental Details

Many "network" failures are physical environment failures:

- A PoE access point is connected to a non-PoE switch port.
- A device needs PoE+ or PoE++ but receives less power than required.
- A small unmanaged switch is hidden under a desk and power-cycles when the strip is bumped.
- Patch cables are bent sharply, crushed by furniture, or stretched.
- Copper data cable runs parallel to high-power electrical wiring.
- A rack has poor airflow, loose cable strain relief, or unlabeled changes.
- A ceiling access point has a bad cable termination above the tile.

Physical work should follow building, electrical, fire, and ladder-safety rules. If a fix requires opening walls, running cable, entering ceilings, modifying conduit, or changing power, involve qualified facilities or cabling staff.

## A Safe Troubleshooting Flow

Use this order to reduce guesswork:

1. **Confirm the symptom.**
   Record host, interface, jack label, time, negotiated speed, and user-visible impact.

2. **Check the local patch cable.**
   Try a known-good patch cable. Keep the original cable aside and label it suspect if the issue follows it.

3. **Check another jack or switch port when available.**
   If the same host works elsewhere, the original path is suspect. If multiple hosts fail on the same jack, the path is strongly suspect.

4. **Read host and switch evidence.**
   Compare Linux link data with switch-port counters and speed/duplex.

5. **Trace labels.**
   Match wall jack, patch-panel port, switch port, VLAN, and expected location.

6. **Request or run cable certification.**
   For permanent wiring, a proper cable tester can find opens, shorts, split pairs, distance to fault, and category compliance.

7. **Document the result.**
   Update labels, diagrams, ticket notes, and any inventory records.

## What Not To Do

Avoid these habits:

- Do not force speed or duplex as a first fix unless you have a specific compatibility reason.
- Do not assume a green link light means the cable path is healthy.
- Do not use random unlabeled patch cords in a production rack.
- Do not leave temporary desk switches undocumented.
- Do not run cable through unsafe paths, under doors, across walkways, or near heat sources.
- Do not change several patch-panel connections at once and then try to remember what moved.

Physical-layer mistakes are easy to create and hard to diagnose after the fact.

## Cabling Handoff Template

When you escalate or close a wiring issue, include enough detail for someone else to reproduce the trail:

```text
Location:
Wall jack label:
Patch-panel port:
Switch and port:
Host/device:
Observed speed/duplex:
Host evidence:
Switch evidence:
Patch cable swapped?:
Alternate jack tested?:
Cable certification result:
Change made:
Rollback or follow-up:
```

The goal is not a long essay. The goal is a path someone can inspect without starting from zero.

## Practice

In a lab or non-production environment:

1. Identify a Linux host's Ethernet interface.
2. Run:

   ```bash
   ip link show
   ethtool <interface>
   ```

3. Record the negotiated speed, duplex, and link state.
4. Move only the host patch cable to another known-good port or jack.
5. Run the same checks again.
6. Explain which part of the physical path changed and which parts stayed the same.

If you do not have a wired lab, write a cabling handoff from a hypothetical incident: "desk 4B negotiates at 100 Mbps while nearby desks negotiate at 1 Gbps."
