## 14.8 Recommended Vendors

!!! abstract "What you will learn"
    - Evaluate network vendors using operational criteria instead of brand familiarity alone.
    - Compare hardware, software, support, lifecycle, automation, and security considerations.
    - Ask practical questions before introducing a new switch, router, firewall, Wi-Fi, or monitoring platform.
    - Connect vendor choices to Linux operations and incident response.

!!! example "Field story"
    A team buys inexpensive switches for a new office because the port count looks right. Six months later, they need VLANs, PoE telemetry, configuration backups, alerting, and predictable firmware updates. The devices technically work, but they do not fit the operational job.

!!! success "Operator principle"
    The best vendor is the one your team can operate, secure, monitor, update, and replace under pressure.

## Vendor Choice Is An Operations Decision

Network vendors are not just logos on boxes. A vendor choice affects:

- how you configure devices
- how you recover from failure
- how you patch security issues
- how you monitor health
- how you automate repeatable work
- how much training your team needs
- how quickly support can help during incidents
- how long hardware and software remain supported

For small environments, simple gear can be the right answer. For regulated, multi-site, or high-availability networks, operational maturity may matter more than sticker price.

## Common Vendor Categories

You will usually evaluate vendors across several categories:

- **Switching**: access switches, aggregation switches, data-center switches, PoE switches.
- **Routing**: edge routers, WAN routers, virtual routers, cloud routing appliances.
- **Firewalls**: perimeter firewalls, internal segmentation firewalls, VPN gateways.
- **Wireless**: access points, controllers, cloud-managed Wi-Fi, guest access.
- **Optics and cabling**: transceivers, DAC cables, fiber, patch panels, structured-cabling systems.
- **Monitoring and management**: controllers, NMS tools, telemetry collectors, log platforms.
- **Cloud and SDN**: cloud networking control planes, overlays, service meshes, virtual networking appliances.

A single vendor may cover several categories. A mixed-vendor network can work well, but only if the handoffs are documented and the team understands each platform.

## Evaluation Criteria

Before choosing a vendor, write down the criteria that matter for your environment.

### Technical Fit

Ask:

- Does the product support the speeds, port counts, optics, PoE budget, and environmental requirements?
- Does it support the VLANs, routing protocols, VPNs, firewall policy, or Wi-Fi features you need?
- Does it interoperate with your existing switches, routers, firewalls, identity systems, and monitoring stack?
- Can you lab-test the feature you are buying it for?
- Are there hidden license tiers for features that seem basic?

### Operational Fit

Ask:

- Can the team configure it confidently?
- Is the CLI, API, or controller understandable?
- Can configuration be backed up and restored?
- Can changes be reviewed before deployment?
- Can logs and metrics be exported to your normal tools?
- Does the device expose useful interface, PoE, routing, and health telemetry?
- Can firmware updates be scheduled and rolled back safely?

### Support Fit

Ask:

- What support level is included?
- What is the response time for production-impacting issues?
- How long are hardware replacement and software updates available?
- Is documentation public and searchable?
- Are security advisories timely and specific?
- Is there an active user community or partner ecosystem?

### Lifecycle Fit

Ask:

- When does the product reach end of sale?
- When does it reach end of support?
- Can you standardize on a small number of models?
- Are replacement units available quickly?
- Are licenses annual, perpetual, subscription-only, or feature-gated?
- Does the total cost include support, optics, controllers, cloud management, and spares?

## Linux Operator View

Even when Linux is not the network device operating system, Linux hosts reveal whether the network vendor choice is working in practice.

From a Linux host, collect:

```bash
ip addr show
ip route show
ip neigh show
resolvectl status
ethtool <interface>
journalctl -k --since "30 minutes ago" | grep -Ei 'link|carrier|dhcp|dns|route'
```

Useful questions:

- Does the host get the intended IP address, gateway, and DNS resolver?
- Does link speed match what the switch port and cabling should support?
- Does the host see stable carrier, or are links flapping?
- Does the route path match the design?
- Can monitoring correlate host symptoms with switch, firewall, or Wi-Fi telemetry?

Vendor platforms that make these questions easy to answer are easier to operate.

## Avoid Brand-Only Decisions

Brand reputation matters, but it is not enough. Avoid these shortcuts:

- "Everyone uses this vendor, so it must be right."
- "This is cheapest, so it is best for a small office."
- "This is enterprise-grade, so it will solve our process problems."
- "The dashboard is pretty, so operations will be easy."
- "The datasheet says it supports the feature, so the feature is production-ready."

Instead, demand proof:

- a lab test
- a pilot
- a configuration backup and restore test
- a firmware update test
- a monitoring integration test
- a support or RMA expectation
- a rollback plan

## Single Vendor vs Mixed Vendor

A single-vendor network can simplify:

- support ownership
- staff training
- controller integration
- firmware planning
- configuration templates
- procurement and spares

A mixed-vendor network can improve:

- cost control
- feature fit
- negotiation leverage
- avoidance of lock-in
- use of best-fit tools in each layer

The tradeoff is operational complexity. Mixed-vendor designs need clear documentation for configuration style, routing boundaries, support ownership, monitoring, and escalation.

## Questions Before Buying

Use this checklist before introducing a new vendor or model:

```text
What problem are we solving?
Which current product or process fails to meet the requirement?
What feature is mandatory?
What feature is nice to have?
How will we configure it?
How will we back it up?
How will we monitor it?
How will we patch it?
How will we replace it?
How will Linux hosts prove it is working?
Who owns support cases?
What is the rollback plan if the pilot fails?
```

If the answers are vague, the purchase is not ready.

## Practical Vendor Shortlist Examples

The exact vendor market changes over time. Treat this as a category map, not a permanent recommendation:

- **Large enterprise networking**: often chosen for broad product coverage, support depth, certification paths, and long lifecycle planning.
- **Data-center and cloud networking**: often chosen for automation, high-speed switching, telemetry, and integration with large-scale operations.
- **Small-business and prosumer networking**: often chosen for lower cost, easier setup, and simpler cloud-managed operations.
- **Security-focused platforms**: often chosen for firewall policy, VPN, threat inspection, logging, and compliance workflows.
- **Open or Linux-based network operating systems**: often chosen by teams that want automation control and are prepared to own deeper operational responsibility.

Do not copy another organization's shortlist blindly. Their risk, team skill, support contract, and failure tolerance may be different from yours.

## Pilot Plan

For a meaningful pilot, test the real operational path:

1. Install the device or platform in a non-critical segment.
2. Apply a small version of the real configuration.
3. Connect Linux and non-Linux clients.
4. Verify DHCP, DNS, VLAN, routing, firewall, and monitoring behavior.
5. Export and restore configuration.
6. Apply a firmware update.
7. Trigger or simulate a common failure.
8. Write the support and rollback notes.

A pilot is not successful because the device powered on. It is successful when operators know how it behaves under normal work and controlled failure.
