## 14.4 Network Testing and Debugging

Network debugging is not a single command. It is a ladder of evidence: prove the
link, prove local addressing, prove the route, prove name resolution, then prove
the application path. When you skip steps, a bad cable can look like a DNS
failure and a blocked port can look like a broken server.

!!! abstract "What you will learn"
    - Build a repeatable test order for physical and IP network incidents.
    - Use Linux commands to separate link, address, route, DNS, and service
      failures.
    - Capture enough evidence for a clean escalation or handoff.
    - Avoid risky fixes while you are still identifying the failing layer.

!!! success "Operator principle"
    Test from the bottom up. Start with local, read-only evidence before changing
    routes, firewall rules, DNS records, switch ports, or service configuration.

## Start with a precise symptom

Write down the failing source, destination, protocol, port, and time window before
you touch the system. "The network is down" is not actionable. "Host
`web-01` cannot reach `db-01` on TCP port 5432 after the 14:00 switch move" gives
you a testable path.

Useful first questions:

- Is the problem one host, one subnet, one switch, one application, or everyone?
- Does it affect IP addresses, names, or both?
- Is the failure total, intermittent, slow, or only visible for large transfers?
- What changed most recently: cable, switch port, VLAN, firewall, DNS, MTU, route,
  interface configuration, or service deployment?

## Layer-by-layer test order

Use this sequence when you do not yet know where the fault lives.

| Layer | Question | Linux evidence |
| --- | --- | --- |
| Physical link | Is the interface up and seeing carrier? | `ip -br link`, `ethtool eno1` |
| Local address | Does the host have the expected address? | `ip -br addr`, `ip addr show dev eno1` |
| Local neighbor | Can the host resolve the next hop? | `ip neigh`, `arp -n` |
| Route | Which path will the kernel choose? | `ip route get 198.51.100.10` |
| DNS | Does the name resolve to the expected target? | `getent hosts app.example.com`, `resolvectl query app.example.com` |
| Transport | Is the remote port reachable? | `nc -vz host 443`, `ss -tanp` |
| Application | Does the service protocol succeed? | `curl -v https://host/health`, service logs |

The exact command varies by distribution and installed tools, but the order stays
useful: link, address, neighbor, route, DNS, port, application.

## Link and interface evidence

Start on the affected host. Confirm the interface name, state, addresses, and
error counters.

```console
$ ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
eno1             UP             52:54:00:12:34:56 <BROADCAST,MULTICAST,UP,LOWER_UP>

$ ip -br addr show eno1
eno1             UP             192.0.2.45/24 fe80::5054:ff:fe12:3456/64
```

`UP` means the interface is administratively enabled. `LOWER_UP` usually means
carrier is present. If `UP` is present but `LOWER_UP` is missing, suspect cable,
switch port, transceiver, adapter state, or a disabled port.

Use `ethtool` when available:

```console
$ sudo ethtool eno1
Speed: 1000Mb/s
Duplex: Full
Auto-negotiation: on
Link detected: yes
```

Error counters help distinguish bad media from higher-layer problems:

```console
$ ip -s link show dev eno1
```

Rising CRC, frame, dropped, or carrier errors point toward cable, optic, speed,
duplex, driver, or switch-port issues. Do not clear counters until you have saved
the current values.

## Reachability tests

`ping` is useful, but it only proves that ICMP echo is working. Many networks rate
limit or block ICMP. Treat a failed ping as a clue, not a verdict.

```console
$ ping -c 4 192.0.2.1
$ ping -c 4 app.example.com
```

Compare address and name tests. If the IP succeeds but the name fails, focus on
DNS. If the gateway fails, focus on local link, VLAN, address, mask, or gateway
configuration. If the gateway works but a remote address fails, inspect routing,
firewalls, and upstream paths.

For TCP services, test the actual port:

```console
$ nc -vz db-01.example.com 5432
Connection to db-01.example.com 5432 port [tcp/postgresql] succeeded!

$ curl -v --connect-timeout 5 https://app.example.com/health
```

Port tests are often more relevant than ping during application incidents.

## Routes, neighbors, and DNS

Ask the kernel how it would reach a destination:

```console
$ ip route get 203.0.113.25
203.0.113.25 via 192.0.2.1 dev eno1 src 192.0.2.45 uid 1000
```

This shows the chosen interface, gateway, and source address. If the source
address is unexpected, the remote firewall or application may reject the traffic.

Check the neighbor table for the gateway or same-subnet peer:

```console
$ ip neigh show dev eno1
192.0.2.1 lladdr 00:11:22:33:44:55 REACHABLE
```

`FAILED` or repeated `INCOMPLETE` states usually mean the host cannot resolve the
peer's MAC address on the local link. That points back to VLAN, switch, cable,
addressing, or duplicate-address problems.

Check DNS with the resolver path the system actually uses:

```console
$ getent hosts app.example.com
$ resolvectl query app.example.com
```

If `getent` succeeds but an application fails, the issue may be the application
resolver, search suffixes, IPv4 versus IPv6 preference, proxy settings, or cached
results.

## Path tracing

Use `traceroute`, `tracepath`, or `mtr` to learn where packets stop, but remember
that routers may deprioritize or block the probe traffic.

```console
$ tracepath app.example.com
$ traceroute app.example.com
$ mtr -rw app.example.com
```

Interpret path tools carefully:

- Asterisks on one hop do not always mean packet loss for real application
  traffic.
- Loss shown at one hop but not later hops usually means that router is rate
  limiting replies.
- Loss that begins at one hop and continues through every later hop is stronger
  evidence of a path problem.
- A sudden MTU drop or `pmtu` message can explain large-transfer failures.

## Packet capture

Packet capture is the strongest way to prove whether packets leave or arrive, but
it can capture sensitive data. Use tight filters, short windows, and protected
storage.

```console
$ sudo tcpdump -ni eno1 host 203.0.113.25 and tcp port 443
```

Common interpretations:

- SYN leaves, no SYN-ACK returns: remote service, firewall, route back, or path
  issue.
- SYN and SYN-ACK appear, then reset: service or policy rejected the connection.
- DNS query leaves, no reply returns: resolver, firewall, or upstream path issue.
- ARP request repeats with no reply: local link, VLAN, address, or gateway issue.

Save a short capture only when needed:

```console
$ sudo tcpdump -ni eno1 -w incident-eno1-443.pcap host 203.0.113.25 and tcp port 443
```

Do not attach packet captures to public tickets unless you have reviewed them for
secrets, customer data, cookies, tokens, and internal addresses.

## Common failure patterns

| Symptom | Likely places to inspect |
| --- | --- |
| Interface has no carrier | Cable, switch port, optic, disabled port, VM NIC mapping |
| Gateway ARP fails | VLAN mismatch, wrong subnet mask, duplicate IP, switch port issue |
| IP works but names fail | Resolver config, DNS server, search domain, split DNS |
| Ping works but app fails | Firewall, service listener, wrong port, TLS/SNI, proxy |
| Small packets work, large transfers hang | MTU, tunnels, jumbo frames, path MTU discovery |
| One direction works only | Asymmetric routing, stateful firewall, wrong return route |
| Intermittent drops | Bad cable, duplex mismatch, overloaded link, flapping route |

## Safer change boundaries

Prefer read-only tests until you can state the likely layer. When a change is
necessary:

- Change one thing at a time.
- Save current state first: `ip addr`, `ip route`, resolver config, firewall
  rules, switch port, or cloud security policy.
- Use temporary tests before persistent configuration when possible.
- Keep an out-of-band path for remote hosts.
- Schedule risky switch, firewall, DNS, and routing changes with rollback notes.

Avoid "fixing" DNS, firewall rules, routes, and cabling at the same time. That
makes the incident harder to understand and harder to reverse.

## Lab: debug a path with evidence

Use two disposable VMs, containers, or lab hosts on the same network.

1. Record the source host's interface and address:
   `ip -br link` and `ip -br addr`.
2. Choose a target address and ask the kernel for the route:
   `ip route get TARGET_IP`.
3. Test the target by IP with `ping -c 4 TARGET_IP`.
4. If a TCP service is available, test the port with `nc -vz TARGET_IP PORT`.
5. Query a name for the target with `getent hosts TARGET_NAME`.
6. Run a short packet capture while repeating one failed or successful test:
   `sudo tcpdump -ni IFACE host TARGET_IP`.
7. Write a handoff note that states the symptom, commands run, key outputs, and
   the next safest action.
