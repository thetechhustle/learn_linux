## 14.2 Wireless: Ethernet for Nomads

Wireless networking feels like Ethernet because it carries IP packets to the same applications, but the operating problem is different. A cable gives you a private physical path. Wi-Fi is a shared radio system where distance, walls, interference, client behavior, roaming, access-point placement, airtime, and authentication all affect reliability.

!!! abstract "What you will learn"
    - Explain how Wi-Fi differs from wired Ethernet in day-to-day Linux operations.
    - Inspect wireless interfaces, signal, SSID, access point, security mode, and roaming state.
    - Separate weak-signal, authentication, DHCP, DNS, routing, and application symptoms.
    - Build a practical wireless troubleshooting note for an incident handoff.

!!! success "Operator principle"
    A wireless problem is not proven by "the Wi-Fi is bad." Prove the association, signal, access point, channel, authentication, address, route, DNS, and packet path before choosing a fix.

## What makes Wi-Fi different

Wi-Fi adds radio conditions and access-point behavior to the normal networking stack.

- **Shared airtime:** clients on the same channel contend for transmit time.
- **Signal quality:** distance, walls, metal, water, people, and antenna placement affect throughput and stability.
- **Interference:** neighboring networks, Bluetooth, microwaves, cordless devices, and other radios can degrade service.
- **Roaming:** clients decide when to move between access points, and they do not always choose well.
- **Security negotiation:** WPA2, WPA3, enterprise authentication, and captive portals can fail before IP configuration begins.
- **Power saving:** laptops and mobile devices may change radio behavior to preserve battery.
- **Driver and firmware quality:** a bad wireless chipset, firmware, or kernel driver can look like a network-wide problem.

Treat wireless as a layered problem: radio first, association second, IP third, service reachability last.

## Linux wireless tools

Modern Linux systems commonly use NetworkManager on laptops and general-purpose hosts. Servers and embedded systems may use `systemd-networkd`, `wpa_supplicant`, or distribution-specific tooling.

Read-only checks:

```bash
ip link show
iw dev
iw dev wlan0 link
nmcli device status
nmcli device wifi list
nmcli connection show --active
journalctl -u NetworkManager --since -1h
journalctl -k --grep='wlan\\|wifi\\|iwlwifi\\|ath\\|brcm'
```

Useful questions:

- Does Linux detect a wireless interface?
- Is the radio blocked by hardware or software?
- Which SSID is active?
- Which BSSID, or access-point MAC address, is the client using?
- What is the signal level?
- What security mode is negotiated?
- Did the client roam recently?
- Are kernel or NetworkManager logs reporting authentication, firmware, or link failures?

For radio-block checks:

```bash
rfkill list
```

For deeper `wpa_supplicant` state, when applicable:

```bash
wpa_cli status
wpa_cli scan_results
```

!!! warning "Do not casually reset wireless remotely"
    Restarting NetworkManager, disconnecting an SSID, changing credentials, or cycling the radio can drop your management session. Make sure you have a wired, console, or out-of-band path before changing the interface you are using.

## Connecting with NetworkManager

NetworkManager can scan and connect from the command line:

```bash
nmcli device wifi list
nmcli device wifi connect "ExampleSSID" password "example-password"
nmcli connection show --active
nmcli device show wlan0
```

For enterprise Wi-Fi, avoid putting secrets in shell history. Use a profile, secure secret storage, or the distribution's supported NetworkManager workflow.

The connection is only the first checkpoint. After association, confirm IP behavior:

```bash
ip addr show dev wlan0
ip route get 1.1.1.1
resolvectl status
ping -c 3 <gateway-ip>
curl -I https://example.com
```

If association works but DHCP does not, the failure is different from weak signal. If DHCP works but DNS fails, the radio is probably not your first suspect.

## Wireless security

Common security modes:

- **Open networks:** no link-layer encryption; useful for public hotspots but unsafe for trusted work without higher-layer protection.
- **WPA2-Personal:** password-based and still common.
- **WPA3-Personal:** stronger password-based authentication where client and access point support it.
- **WPA2/WPA3-Enterprise:** identity-backed authentication, often with certificates, RADIUS, and organization-managed policy.
- **Captive portals:** web login flows that can make DNS and HTTP behavior look strange until the portal is completed.

Operator habits:

- Prefer WPA3 where supported, with WPA2 compatibility only when needed.
- Use strong unique passphrases for personal networks.
- For enterprise networks, validate certificate and identity configuration instead of disabling checks to "make it work."
- Keep guest networks separated from trusted internal networks.
- Record SSID, BSSID, security mode, and authentication errors in the incident note.

## Troubleshooting flow

Use this order for a client-side wireless problem:

1. Confirm scope: one device, one location, one access point, one SSID, or many users?
2. Check radio block and interface presence with `rfkill`, `ip link`, and `iw dev`.
3. Check association and signal with `iw dev wlan0 link`.
4. Identify the access point BSSID and compare it with the expected AP for that location.
5. Review recent NetworkManager and kernel logs.
6. Confirm IP address, default route, DNS, and gateway reachability.
7. Compare with a known-good client at the same location.
8. If many clients are affected, inspect access-point health, channel utilization, uplink, DHCP, and authentication services.

!!! example "Wireless incident note"
    Good handoff notes include: client hostname, time window, SSID, BSSID, signal level, IP address, gateway, DNS server, recent roam events, error messages, and whether another client in the same location worked.

## Access-point and design issues

Wireless performance is often a design problem, not a Linux command problem.

Check for:

- too few access points
- too many access points on overlapping channels
- bad placement behind walls, metal, racks, or appliances
- insufficient wired uplink capacity
- overloaded 2.4 GHz channels
- clients clinging to distant APs
- mixed old and new Wi-Fi standards
- weak guest/trusted network separation
- no monitoring for AP health, client counts, or channel utilization

Linux operators should know when to stop changing the client and ask for infrastructure evidence: controller logs, AP health, RF scans, channel plan, switch-port status, DHCP logs, and authentication logs.

## Common symptom patterns

| Symptom | Likely evidence to collect |
| --- | --- |
| Cannot see SSID | `nmcli device wifi list`, radio block state, AP broadcast status |
| Sees SSID but cannot connect | security mode, credentials, certificate, NetworkManager logs |
| Connects but no IP | DHCP logs, `ip addr`, AP VLAN, switch trunk, DHCP scope |
| Has IP but no internet | default route, DNS, captive portal, firewall, upstream path |
| Works near AP but not elsewhere | signal level, roaming behavior, AP placement |
| Random drops | kernel logs, firmware, power saving, roaming, interference |
| Slow but connected | signal, channel utilization, band, client count, uplink capacity |

## Practice

On a lab laptop or disposable test host:

1. List nearby wireless networks with `nmcli device wifi list`.
2. Connect to a known test SSID.
3. Record `iw dev wlan0 link`, `ip addr`, `ip route`, and resolver state.
4. Move to a weaker signal location and record what changes.
5. Compare application symptoms with radio evidence.
