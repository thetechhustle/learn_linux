## 14.3 SDN: Software-Defined Networking

Software-defined networking, or SDN, moves network intent into software-controlled policy, controllers, APIs, overlays, and automation. It does not remove the need to understand packets. It changes where configuration lives and how operators prove the path a packet should take.

!!! abstract "What you will learn"
    - Explain control plane, data plane, northbound API, southbound API, overlay, and underlay in operational terms.
    - Inspect Linux hosts that participate in SDN-style networks through bridges, virtual interfaces, tunnels, and routes.
    - Separate controller policy problems from host, switch, tunnel, firewall, and physical-link problems.
    - Build a practical evidence trail for SDN incidents.

!!! success "Operator principle"
    SDN adds a controller, but packets still traverse interfaces, routes, tunnels, firewalls, and physical links. Debug both the intended policy and the observed forwarding path.

## The basic model

Traditional networking spreads configuration across switches, routers, firewalls, and hosts. SDN tries to centralize or automate the intent:

- **Control plane:** decides what should happen. Examples: route calculation, policy decisions, endpoint identity, network intent, controller state.
- **Data plane:** moves packets. Examples: switches, virtual switches, NICs, kernel forwarding, tunnel endpoints, firewall hooks.
- **Northbound API:** how applications, orchestration systems, or administrators tell the controller what they want.
- **Southbound API:** how the controller programs devices, virtual switches, agents, or datapaths.
- **Underlay:** the real physical or routed network that carries traffic.
- **Overlay:** the virtual network built on top, often using tunnels such as VXLAN, Geneve, GRE, or WireGuard-like encrypted paths.

The promise is better automation and consistency. The risk is that a simple packet path now depends on controller state, host agents, tunnel endpoints, policy engines, and the physical network underneath.

## Where Linux appears in SDN

Linux often acts as a workload host, tunnel endpoint, router, firewall, or virtual switch participant.

Common Linux evidence:

```bash
ip link show
ip addr show
ip route show table all
bridge link
bridge vlan show
ip -d link show
ip tunnel show
ss -lnptu
nft list ruleset
journalctl -k --since -1h
```

Depending on the platform, you may also inspect:

```bash
ovs-vsctl show
ovs-ofctl show br-int
tc filter show dev eth0 ingress
conntrack -L
```

Do not assume every environment uses Open vSwitch, OpenFlow, or one specific controller. Kubernetes CNI plugins, cloud VPC fabrics, service meshes, network virtualization platforms, campus SDN controllers, and data-center fabrics all use different implementation details.

## Control plane versus data plane

When an SDN system fails, ask two questions:

1. What does the control plane intend?
2. What does the data plane actually do?

Control-plane evidence might include:

- endpoint registration
- desired policy
- assigned network, subnet, VLAN, or VNI
- controller health
- agent health
- recent reconciliation errors
- API or event logs

Data-plane evidence might include:

- local interface state
- route tables
- bridge membership
- tunnel interface state
- firewall rules
- packet captures
- drop counters
- switch-port or underlay reachability

If policy says traffic is allowed but the packet never leaves the host, inspect the host datapath. If the host sends the packet into a tunnel but the remote endpoint never receives it, inspect underlay routing, MTU, firewall, and tunnel endpoint health. If the packet arrives but is dropped by policy, inspect the controller's intended rules and the local enforcement point.

## Overlay and underlay troubleshooting

An overlay cannot be healthier than the underlay that carries it.

Start with underlay checks:

```bash
ip route get <remote-tunnel-endpoint>
ping -c 3 <remote-tunnel-endpoint>
tracepath <remote-tunnel-endpoint>
```

Then inspect the overlay:

```bash
ip -d link show
ip addr show
ip route get <overlay-destination>
tcpdump -ni any host <overlay-destination>
```

MTU is a common overlay failure source. Tunnels add headers, so a path that handles ordinary traffic may fail for larger packets. Use `tracepath`, packet captures, interface MTUs, and platform documentation before guessing.

!!! tip "Think in two paths"
    For overlay networking, draw both paths: the logical overlay path between workloads and the physical underlay path between tunnel endpoints. A good incident note names both.

## Practical incident flow

Use this order when an SDN-style network path fails:

1. Identify source, destination, port, protocol, workload, host, and time window.
2. Confirm whether the controller thinks the endpoints and policy exist.
3. Check host agent health, if the platform has an agent.
4. Inspect local interfaces, bridges, routes, tunnels, and firewall rules.
5. Prove underlay reachability between tunnel endpoints.
6. Capture traffic at the source host, tunnel interface, underlay interface, and destination host when possible.
7. Compare intended policy with observed packet behavior.
8. Record whether the failure is control-plane intent, data-plane programming, underlay transport, host firewall, MTU, or endpoint configuration.

## Common SDN environments

You may encounter SDN ideas in several places:

- **Kubernetes networking:** CNI plugins create pod networks, service routing, policies, and overlays or routed fabrics.
- **Cloud VPCs:** provider control planes manage routes, security policy, load balancers, private endpoints, and flow logs.
- **Open vSwitch environments:** virtual bridges and flow tables connect VMs, containers, tunnels, and physical NICs.
- **Campus fabrics:** controllers manage switches, VLANs, segmentation, wireless integration, and access policy.
- **Data-center fabrics:** EVPN/VXLAN and related designs separate overlay tenant networks from routed underlays.
- **Zero-trust overlays:** identity-aware encrypted networks build logical reachability over ordinary IP paths.

The details differ, but the operator habit is the same: prove policy, prove programming, prove packet movement.

## What to document

For each SDN-managed environment, keep a short map:

- controller or platform name
- where desired policy is defined
- where endpoint identity comes from
- host agent or datapath component
- overlay type, if any
- underlay dependencies
- observability sources
- rollback path for bad policy
- known MTU, firewall, or routing constraints

This documentation prevents a common failure mode: everyone can change intent, but nobody knows where packet forwarding is actually enforced.

## Practice

On a lab host with containers or virtual networking:

1. Create or inspect a Linux bridge.
2. Attach a network namespace, VM, or container.
3. Record `ip link`, `bridge link`, `ip route`, and `nft list ruleset`.
4. Capture a packet moving from one endpoint to another.
5. Change one reversible policy or route and record which evidence changed.
