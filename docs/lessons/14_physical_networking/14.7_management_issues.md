## 14.7 Management Issues

Physical networks fail in ways that look like Linux problems: a server loses its
default gateway, a service becomes slow, DNS queries time out, or a new VLAN
appears to "break" an application. Good network management keeps those failures
small, explainable, and reversible.

For a Linux administrator, management is the discipline around the technical
work: naming, labeling, monitoring, configuration control, access boundaries,
capacity planning, and incident notes. The commands matter, but the management
process around the commands is what prevents the same outage from returning next
week.

!!! abstract "What you will learn"
    - Separate physical-network management evidence from host-level symptoms.
    - Build a small inventory record for ports, cables, VLANs, addresses, and owners.
    - Use Linux commands to monitor link health, throughput, queues, firewall state, and route changes.
    - Plan network changes with rollback notes and post-change verification.
    - Hand off a network incident with enough context for another operator to continue safely.

!!! success "Operator principle"
    Manage the evidence before managing the device. A clean port map, change log,
    and verification note often solve the next outage faster than a clever command.

## Start with an inventory record

Keep enough information to answer "what is this connected to?" without opening a
rack door during an incident.

A useful record includes:

- hostname and role
- interface name, MAC address, and IP address
- switch name, switch port, patch panel port, and cable label
- VLAN, subnet, gateway, and DNS servers
- service owner or escalation contact
- last known-good speed, duplex, MTU, and route
- date, reason, and operator for the last change

On Linux, collect the host side of that record with read-only commands:

```bash
hostnamectl
ip -brief link
ip -brief address
ip route
ip -details link show dev eth0
ethtool eth0
```

If the interface name is different, replace `eth0` with the name from
`ip -brief link`.

!!! warning "Do not guess at cable labels"
    A guessed label is worse than no label because other operators will trust it.
    If a label is missing, record it as unknown, trace it during a maintenance
    window, then update the inventory.

## Monitor the right layers

Monitoring should show both host symptoms and physical-network causes. Start with
cheap, local signals before reaching for packet captures.

Check link state and counters:

```bash
ip -s link show dev eth0
ethtool eth0
ethtool -S eth0 | less
```

Look for:

- interface flaps
- receive or transmit errors
- dropped packets
- speed or duplex changes
- MTU mismatches
- steadily increasing carrier errors

Check addresses, routes, and neighbor entries:

```bash
ip address show dev eth0
ip route get 8.8.8.8
ip neigh show dev eth0
```

Check DNS and transport symptoms separately:

```bash
resolvectl status
getent hosts example.com
nc -vz example.com 443
```

If throughput matters, test deliberately instead of guessing from user reports:

```bash
iperf3 -c iperf-server.example.com
```

Run bandwidth tests only against approved test endpoints. A careless throughput
test can become the outage you are trying to diagnose.

## Manage configuration drift

Network configuration can live in several places: NetworkManager profiles,
Netplan YAML, systemd-networkd units, distribution-specific interface files,
firewall rules, switch configuration, DHCP reservations, DNS records, and cloud
network objects.

Before changing anything, identify the source of truth:

```bash
nmcli connection show
networkctl status
ls /etc/netplan 2>/dev/null
systemctl is-active NetworkManager systemd-networkd
```

For each change, write down:

1. current evidence
2. intended change
3. expected effect
4. rollback command or backup file
5. verification command
6. person or ticket approving the change

Example change note:

```text
Host: web-03
Change: move eth0 from access VLAN 20 to access VLAN 30 on switch sw1 port Gi1/0/14
Reason: migrate web tier to new subnet
Before: 10.20.5.13/24 via 10.20.5.1, link 1000/full, no rx/tx errors
Rollback: restore sw1 Gi1/0/14 to VLAN 20 and renew DHCP lease
Verify: ip addr, ip route, curl health check, application synthetic check
```

!!! tip "Keep host and switch changes paired"
    If a Linux address, gateway, or MTU change depends on a switch or cloud-network
    change, track them in the same change note. Split notes hide dependencies.

## Control access to network changes

Network changes can isolate machines, bypass security policy, or expose services
that were meant to stay private. Limit who can change each layer.

Common controls include:

- `sudo` access only for operators who need network commands
- configuration review for persistent interface, firewall, DNS, and routing changes
- read-only monitoring access for incident responders
- switch, wireless controller, and cloud console access tied to named accounts
- separate break-glass credentials with logging

Check local privilege and firewall evidence:

```bash
sudo -l
sudo nft list ruleset
sudo iptables -S
sudo firewall-cmd --list-all 2>/dev/null
sudo ufw status verbose 2>/dev/null
```

Use the firewall command that matches the host. Many modern Linux systems use
`nftables` directly or through `firewalld`; older systems may still use
`iptables`.

## Capacity and quality of service

Capacity management is not only "buy a faster link." It is knowing which traffic
is important, which links saturate first, and which queues or drops prove the
problem.

Useful checks:

```bash
sar -n DEV 1 5
ip -s link show dev eth0
tc qdisc show dev eth0
ss -s
```

If `sar` is unavailable, install the `sysstat` package in a lab or use your
monitoring system's interface graphs.

Quality-of-service changes deserve extra care because they can make one class of
traffic better by making another worse. Before changing `tc`, switch QoS, or
cloud bandwidth policy, record:

- the affected service
- the current peak traffic pattern
- the class of traffic being prioritized
- the class of traffic that may be deprioritized
- the rollback path
- the metric that proves success

## Common management failures

| Symptom | Management issue to check |
| --- | --- |
| Server works from one rack but not another | port map, VLAN assignment, trunk/access mode, patch panel label |
| Problem returns after reboot | temporary host change was never made persistent |
| Only one application is slow | QoS, firewall inspection, MTU, overloaded upstream dependency |
| Monitoring says the host is down but users can connect | stale monitoring target, wrong interface, NAT, DNS drift |
| Incident takes too long to hand off | missing owner, missing recent changes, unclear rollback note |
| New firewall rule did not behave as expected | wrong firewall frontend, rule order, IPv4-only or IPv6-only change |

## Incident handoff checklist

When you hand a network issue to another operator, include:

- when the issue started and who reported it
- affected hostnames, IP addresses, VLANs, ports, and services
- current link, address, route, DNS, firewall, and counter evidence
- commands already run and their important output
- recent changes from tickets, commits, switch logs, or cloud audit logs
- current workaround, if any
- next safest test
- rollback notes for any change made during the incident

Short handoff example:

```text
web-03 intermittently fails health checks since 14:10 UTC.
eth0 is up at 1000/full, IP 10.30.5.13/24, default route 10.30.5.1.
ip -s link shows RX drops increasing by ~200/min; no DNS failures observed.
Switch sw1 Gi1/0/14 was moved to VLAN 30 at 13:55 UTC.
No host firewall changes in journal since boot.
Next safe test: move a known-good patch cable during the maintenance window.
Rollback: restore sw1 Gi1/0/14 to VLAN 20 and renew DHCP lease.
```

## Hands-on practice

Use a disposable VM, lab machine, or documentation-only exercise. Do not change a
production network for this lab.

1. Pick one lab host and record its hostname, interface, MAC address, IP address,
   default route, DNS server, and link speed.
2. Run `ip -s link show`, `ip route`, and `ip neigh`; save the important output.
3. Identify which tool manages networking on the host: NetworkManager,
   systemd-networkd, Netplan, or another distribution-specific mechanism.
4. Draft a fake change note for moving the host to a new subnet. Include the
   rollback and verification steps.
5. Write a short incident handoff for a made-up cable or VLAN fault using the
   checklist above.
