## 14.9 Recommended Reading

!!! abstract "What you will learn"
    - Build a focused reading path for physical networking operations.
    - Match books, standards, vendor docs, and Linux references to the problem you are solving.
    - Avoid reading passively when the goal is operational competence.
    - Turn each source into lab notes, diagrams, and troubleshooting checklists.

!!! example "Field story"
    A Linux operator is asked to help troubleshoot an office network, but the problem might be cabling, Wi-Fi, switch configuration, DHCP, DNS, routing, or vendor management. A random stack of networking books is less useful than a staged reading path tied to real evidence.

!!! success "Operator principle"
    Read with a job in mind. The goal is not to collect sources; it is to improve decisions during installation, change review, and incidents.

## How To Use This Reading Path

Physical networking spans cabling, Ethernet, wireless, switch behavior, routing boundaries, operational process, and vendor platforms. No single book or manual covers all of it at the right depth for every operator.

Use this order:

1. Read one source for fundamentals.
2. Lab one small behavior.
3. Read one source for operations or troubleshooting.
4. Apply it to a real or simulated handoff.
5. Add one vendor or standards reference only when it answers a concrete question.

Keep a notebook with:

- terms you can now explain
- commands you tested
- diagrams you can redraw
- design assumptions you would verify
- questions to ask facilities, network engineering, or vendors

## Fundamentals

Start here if you need durable mental models:

- **Computer Networking: A Top-Down Approach** by James Kurose and Keith Ross.
  Good for protocol and application-path context.

- **Computer Networks** by Andrew S. Tanenbaum and David J. Wetherall.
  Good for broad networking foundations and historical context.

- **TCP/IP Illustrated, Volume 1** by W. Richard Stevens.
  Good for protocol behavior, packets, and careful observation.

These sources are broader than physical networking, but they help explain why link-layer, addressing, routing, and transport symptoms can look similar during an incident.

## Linux-Focused Networking

Use Linux documentation and references to connect the network design to host evidence:

- `iproute2` documentation and `man` pages:

  ```bash
  man ip
  man ip-link
  man ip-address
  man ip-route
  man ip-neighbour
  ```

- `ethtool` manual:

  ```bash
  man ethtool
  ```

- `systemd-networkd`, NetworkManager, and resolver documentation, depending on your distribution:

  ```bash
  man networkctl
  man resolvectl
  man nmcli
  ```

Read these beside a live or lab system. For each command, capture one normal output and one failure-oriented question it could answer.

## Physical Layer And Cabling

For building wiring and structured cabling, prioritize practical installation and certification concepts:

- TIA/EIA structured cabling concepts and summaries.
- BICSI-style cabling references, when available to your organization.
- Cable tester vendor documentation for wiremap, length, split-pair, attenuation, and certification reports.
- Switch vendor documentation for interface counters, transceiver diagnostics, and PoE telemetry.

You do not need to memorize every standard. You do need to know when to ask for a certification test, how to read the result, and what evidence separates a bad patch cable from a bad permanent run.

## Ethernet, Switching, And VLANs

For Ethernet and switching operations, read sources that explain:

- auto-negotiation
- duplex and speed mismatch
- MAC address learning
- spanning tree
- VLAN tagging
- trunks and access ports
- link aggregation
- interface error counters

Useful source types:

- vendor configuration guides for your actual switch platform
- IEEE 802.1Q and spanning-tree overviews
- operational books such as **Network Warrior** by Gary A. Donahue
- platform command references for switch-port counters and logs

Pair the reading with Linux checks:

```bash
ip link show
ethtool <interface>
ip neigh show
journalctl -k --since "30 minutes ago" | grep -Ei 'link|carrier|eth|enp'
```

## Wireless

Wireless requires different instincts than wired Ethernet. Read about:

- radio frequency basics
- channels and channel width
- interference
- SSIDs and BSSIDs
- authentication and encryption modes
- roaming
- access-point placement
- controller or cloud-management behavior

Useful sources:

- vendor Wi-Fi design guides
- CWNA-level wireless fundamentals
- Linux `iw`, NetworkManager, and `wpa_supplicant` references

Lab commands:

```bash
iw dev
iw dev <interface> link
nmcli dev wifi list
journalctl -u NetworkManager --since "30 minutes ago"
```

## Network Design And Operations

For design, read with an operator's questions in mind:

- What are the failure domains?
- Where are the security boundaries?
- Which paths are redundant?
- How are changes reviewed?
- How are logs, metrics, and configuration backups collected?

Useful source types:

- your organization's network diagrams and standards
- vendor validated design guides
- cloud networking architecture docs
- incident reports from past network outages
- runbooks for DHCP, DNS, firewall, VPN, Wi-Fi, and switch changes

If a source does not help you answer "how would I operate this on a bad day?", it is probably not the next source to read.

## Vendor Documentation

Vendor documentation is most useful when tied to your actual models and software versions. Prioritize:

- installation guides
- release notes
- end-of-life notices
- security advisories
- command references
- configuration backup and restore docs
- firmware upgrade and rollback docs
- support/RMA process docs

Keep links in your team runbook. During an incident, operators should not have to search the web for the correct command reference.

## Standards And RFCs

Standards are valuable when you need precise behavior or language. Start with approachable summaries, then read the standard sections that answer your question.

Examples:

- Ethernet and VLAN standards for switching behavior.
- DHCP RFCs for lease behavior and options.
- DNS RFCs when resolver behavior matters.
- IPv4 and IPv6 RFCs for addressing, neighbor discovery, and routing assumptions.

Do not read standards cover to cover unless the job calls for it. Read them like reference material.

## Practice: Build A Reading Backlog

Pick one real environment or lab network and create a short reading backlog:

```text
Goal:
Source:
Question this source should answer:
Lab or inspection command:
Diagram or note to produce:
Done when:
```

Example:

```text
Goal: Understand why a host negotiates at 100 Mbps.
Source: switch interface counter docs + ethtool manual.
Question this source should answer: which side reports speed, duplex, and errors?
Lab or inspection command: ethtool enp0s31f6; switch show interface.
Diagram or note to produce: host-to-switch physical path.
Done when: I can state whether the evidence points to host NIC, patch cable, wall run, or switch port.
```
