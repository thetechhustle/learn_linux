## 14.1 Ethernet: The Swiss Army Knife of Networking

Ethernet is the default local-network technology for servers, desktops,
switches, access points, hypervisors, storage arrays, and many cloud-adjacent
appliances. Linux usually exposes it as an interface such as `eth0`, `ens3`,
`enp5s0`, or `eno1`; your job is to connect what Linux reports to the physical
path: adapter, cable, patch panel, switch port, VLAN, and upstream network.

!!! abstract "What you will learn"
    - Read Ethernet link state, speed, duplex, MAC address, MTU, and error counters from Linux.
    - Explain how Ethernet frames carry IP, ARP, IPv6 neighbor discovery, and VLAN-tagged traffic.
    - Separate host configuration problems from cable, switch-port, or negotiation failures.
    - Capture enough evidence for a network handoff without making risky production changes.

!!! example "Operational scenario"
    A new rack server has the right IP address, but no one can reach it. The
    application team sees a Linux host with a default route. The network team
    sees a switch port that was patched recently. Ethernet troubleshooting is
    where those two views meet.

## Ethernet in the Stack

Ethernet is a layer 2 technology. It moves frames between devices on the same
local link. IP routing, DNS, TCP, and application protocols depend on it, but
they do not replace it. A host can have a correct IP address and still fail if
the Ethernet link is down, negotiated at the wrong speed, assigned to the wrong
VLAN, or dropping frames because of a bad cable.

Modern Ethernet networks are switched. Each host connects to a switch port, and
the switch learns which MAC addresses appear behind each port. Broadcast and
multicast traffic still matter: ARP for IPv4, neighbor discovery for IPv6, DHCP,
and some service-discovery protocols all rely on local-link delivery.

## The Evidence to Collect First

Start with read-only commands. They let you distinguish "Linux is configured
wrong" from "the physical or switch path is broken."

```bash
ip -brief link
ip -details link show dev eth0
ip address show dev eth0
ip route
```

Replace `eth0` with the actual interface name. The important fields are:

- `state UP` or `state DOWN`: whether the kernel considers the interface administratively and operationally usable.
- `LOWER_UP`: whether the driver sees carrier from the physical link.
- `link/ether`: the interface MAC address.
- `mtu`: the largest layer 3 packet Linux will place in an Ethernet frame.
- RX/TX counters: packet, byte, error, dropped, and carrier counters.

Use `ethtool` for link-specific evidence:

```bash
sudo ethtool eth0
sudo ethtool -S eth0
```

Look for:

- `Link detected: yes` or `no`
- speed, duplex, and auto-negotiation state
- driver and firmware information
- CRC, alignment, carrier, timeout, reset, or dropped-packet counters

!!! tip "Modern networking command"
    Older tutorials often use `ifconfig`. This course favors `ip address`,
    `ip link`, `ip route`, `ss`, and `ethtool` because they are available on
    modern Linux distributions and expose better operational detail.

## Ethernet Frames

An Ethernet frame contains:

- destination MAC address
- source MAC address
- optional VLAN tag
- EtherType, such as IPv4, IPv6, or ARP
- payload
- frame check sequence, handled by the network hardware

Linux usually hides the frame check sequence from you, but it exposes the
effects through interface counters. A rising CRC or frame-error count points
toward cabling, transceiver, speed, duplex, or switch-port problems more often
than application configuration.

You can inspect local-link traffic with `tcpdump`:

```bash
sudo tcpdump -ni eth0 -e arp
sudo tcpdump -ni eth0 -e 'icmp6 and ip6[40] == 135'
```

The `-e` flag prints link-layer details such as source and destination MAC
addresses. On a production system, keep captures narrow, time-bounded, and
approved; packet payloads can contain sensitive data.

## Common Failure Patterns

### Link down

Symptoms:

- `ip link` lacks `LOWER_UP`
- `ethtool` reports `Link detected: no`
- no RX/TX counters move

Likely causes:

- unplugged or failed cable
- disabled switch port
- wrong patch-panel path
- failed NIC, SFP, transceiver, or switch port
- VM virtual NIC disconnected from the virtual switch

### Wrong VLAN

Symptoms:

- link is up
- ARP or IPv6 neighbor discovery fails for the gateway
- DHCP requests leave the host but no useful reply returns
- the switch sees the host MAC on an unexpected access or trunk VLAN

Linux can show VLAN subinterfaces with:

```bash
ip -details link show
```

Switch-side evidence is usually required to finish this diagnosis.

### Speed, duplex, or physical errors

Symptoms:

- intermittent packet loss
- poor throughput on a link that appears up
- rising CRC, frame, carrier, or dropped counters
- speed lower than expected, such as 100Mb/s on a 1Gb/s or 10Gb/s path

Auto-negotiation normally should stay enabled. Forcing speed or duplex is a
change of last resort and must match the switch port exactly.

### MTU mismatch

Symptoms:

- small pings work, large transfers stall
- tunnels, storage, or virtualization traffic behaves inconsistently
- jumbo-frame networks fail only on certain paths

Check MTU on the interface and the route:

```bash
ip link show dev eth0
ip route get 192.0.2.10
```

Use packet-size tests only in a lab or during an approved troubleshooting
window; many networks filter ICMP, so a failed ping is not proof by itself.

## Safe Change Boundaries

These commands are usually read-only:

```bash
ip link show
ip address show
ip route
ethtool eth0
ethtool -S eth0
```

These commands can disrupt connectivity and need a rollback path, especially
over SSH:

```bash
sudo ip link set dev eth0 down
sudo ip link set dev eth0 mtu 9000
sudo ethtool -s eth0 speed 1000 duplex full autoneg off
```

Before changing an interface remotely, make sure you have console access, an
out-of-band management path, or a timed rollback mechanism.

## Lab: Build an Ethernet Evidence Note

Use a disposable VM, spare lab machine, or noncritical host.

1. Identify the active interface:

   ```bash
   ip -brief link
   ip route
   ```

2. Record link and address evidence:

   ```bash
   ip -details link show dev eth0
   ip address show dev eth0
   ```

3. Record physical-link evidence:

   ```bash
   sudo ethtool eth0
   sudo ethtool -S eth0 | head -40
   ```

4. Capture a narrow local-link sample:

   ```bash
   sudo timeout 15 tcpdump -ni eth0 -e arp
   ```

5. Write a short handoff:

   - interface name and MAC address
   - link state, speed, duplex, and MTU
   - gateway reachability evidence
   - error counters that are rising, if any
   - what needs switch-side confirmation
