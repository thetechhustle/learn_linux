## 14.6 Network Design Issues

!!! abstract "What you will learn"
    - Translate business and operations requirements into concrete network-design constraints.
    - Recognize common design choices around segmentation, addressing, routing, redundancy, and observability.
    - Use Linux evidence to verify whether a host is seeing the network design you intended.
    - Review a proposed network change before it creates avoidable incident risk.

!!! example "Field story"
    A small company grows from one office switch to multiple VLANs, Wi-Fi networks, cloud VPNs, and remote users. The original "flat network" was easy to understand, but now printers, laptops, build servers, cameras, and guest devices all have different risk and availability needs.

!!! success "Operator principle"
    Network design is a set of tradeoffs. Good designs make traffic paths, failure domains, security boundaries, and ownership clear before the incident.

## Start With Requirements

Do not begin network design by picking hardware. Start by writing down what the network must support:

- How many users, servers, devices, access points, and locations exist today?
- What growth is likely in the next 12 to 24 months?
- Which services are critical during an outage?
- Which traffic must be isolated for security or compliance?
- Which systems need low latency, high throughput, or predictable jitter?
- Who operates the network after deployment?
- What budget, skill, cabling, power, and vendor constraints are real?

Requirements keep the design honest. Without them, every debate turns into preference: bigger subnets, smaller subnets, more VLANs, fewer VLANs, cloud-first, site-first, single vendor, mixed vendor.

## Draw The Traffic Paths

A useful design sketch shows where packets actually go. Include:

- User networks.
- Server or application networks.
- Management networks.
- Guest and untrusted device networks.
- Internet egress.
- VPN or remote-access entry.
- Cloud or data-center links.
- DNS, DHCP, identity, logging, monitoring, and backup paths.

For each important application, ask:

```text
Client -> access network -> routing/firewall boundary -> service -> dependency
```

If you cannot explain that path before a migration, you will have trouble debugging it during an outage.

## Addressing And Subnet Design

IP addressing should be boring and predictable:

- Give each subnet a clear purpose.
- Reserve room for growth.
- Avoid overlapping private ranges with VPN peers, cloud networks, and partner sites.
- Keep management networks separate from ordinary user or guest networks.
- Document gateway addresses, DHCP ranges, static reservations, and excluded ranges.
- Use DNS names and DHCP reservations instead of relying on random static addresses.

Example layout:

```text
10.20.10.0/24   office-wired-users
10.20.20.0/24   office-wifi-corporate
10.20.30.0/24   office-wifi-guest
10.20.40.0/24   printers-and-shared-devices
10.20.50.0/24   servers
10.20.90.0/24   network-management
```

The exact numbers matter less than the discipline: each range has a purpose, owner, and route policy.

## Segmentation

Segmentation limits blast radius. Common boundaries include:

- Guest Wi-Fi isolated from corporate devices.
- Cameras and IoT separated from laptops and servers.
- Printers separated from sensitive server networks.
- Network management separated from normal user access.
- Development, staging, and production separated by route and firewall policy.
- Payment, identity, or regulated systems isolated with explicit access rules.

Segmentation is not just VLAN creation. A VLAN without routing policy, firewall rules, DHCP/DNS handling, monitoring, and documentation is only a label.

When adding a segment, define:

- Who can initiate traffic into it?
- Who can initiate traffic out of it?
- What DHCP, DNS, NTP, logging, and monitoring services it uses?
- How operators reach it during an incident?
- What success looks like from a Linux host inside the segment?

## Routing And Default Gateways

Every subnet needs a clear gateway and routing policy. On a Linux host, verify what it sees:

```bash
ip addr show
ip route show
ip -6 route show
resolvectl status
```

Important questions:

- Is the host in the subnet you expected?
- Is the default gateway correct?
- Is traffic taking the intended VPN, firewall, router, or cloud path?
- Is IPv6 enabled, disabled, or half-configured?
- Does DNS point to the intended resolver for that segment?

Use targeted route checks:

```bash
ip route get 8.8.8.8
ip route get <internal-service-ip>
tracepath <internal-service-name>
```

`ip route get` is especially useful because it shows the route decision Linux will make for a specific destination.

## Redundancy And Failure Domains

Redundancy should match the service need. More redundancy also means more complexity.

Common design questions:

- Is one switch failure allowed to take down an entire office?
- Do access switches have redundant uplinks?
- Is there a single firewall, router, ISP, power strip, or DNS server?
- Are critical services split across racks, rooms, zones, or providers?
- Is failover automatic, manual, or intentionally not provided?
- Has failover actually been tested?

Avoid fake redundancy:

- Two switches plugged into the same power strip.
- Two uplinks using the same buried cable path.
- Redundant routers with no tested failover.
- Multiple DNS servers hosted behind one broken network path.
- Cloud backup that cannot be reached when the only VPN is down.

Write down what each failure domain is supposed to contain. A good design says what fails together.

## Capacity And Performance

Capacity planning is not only bandwidth. Consider:

- Access-port speeds.
- Uplink oversubscription.
- Wi-Fi airtime and channel contention.
- Firewall throughput with inspection enabled.
- VPN throughput and client count.
- Latency between users, applications, and dependencies.
- Storage, backup, and build traffic windows.
- Monitoring and logging volume.

On Linux, combine interface and path checks:

```bash
ethtool <interface>
ip -s link show <interface>
ss -s
tracepath <destination>
```

For active throughput testing, use tools such as `iperf3` only in a controlled lab or approved maintenance window. Throughput tests can disrupt production networks.

## Security And Trust Boundaries

Security design should be explicit:

- Which networks are trusted?
- Which are untrusted?
- Which services are allowed across boundaries?
- Where are firewall logs reviewed?
- Which admin paths require VPN, MFA, or bastion access?
- How are switches, routers, access points, and firewalls managed?
- How are secrets and certificates distributed?

Do not rely on "inside the office" as a trust model. Laptops move, guests visit, devices get compromised, and cloud networks become part of the same operational surface.

## Observability And Operations

A design is incomplete if operators cannot see or change it safely. Plan for:

- Device inventory.
- Interface descriptions.
- VLAN and subnet documentation.
- DNS and DHCP ownership.
- Central logs.
- Network monitoring.
- Alert thresholds.
- Backup configuration exports.
- Change records and rollback notes.

From a Linux host, your minimum evidence bundle during a network incident is:

```bash
hostnamectl
ip addr show
ip route show
resolvectl status
ip neigh show
journalctl -k --since "30 minutes ago" | grep -Ei 'link|dhcp|carrier|dns|network'
```

This bundle does not replace switch and firewall evidence, but it gives the host-side view of the design.

## Reviewing A Proposed Change

Before changing addressing, VLANs, routing, Wi-Fi, VPN, or firewall rules, ask:

1. What problem does this change solve?
2. Which users, systems, and dependencies are in scope?
3. What traffic path changes?
4. What security boundary changes?
5. What monitoring or logging changes?
6. What is the rollback plan?
7. What is the proof that the change worked?

For production changes, define the validation commands before the change starts. Example:

```bash
ip route get <service-ip>
getent hosts <service-name>
curl -I https://<service-name>
tracepath <service-name>
```

The exact commands depend on the service. The point is to test the design behavior, not just whether the command completed.

## Common Design Smells

Watch for these warning signs:

- One flat network for everything.
- No documented IP plan.
- DHCP ranges mixed with undocumented static addresses.
- Guest and corporate Wi-Fi using the same trust boundary.
- Printers, cameras, and servers all reachable from user laptops.
- A single unlabeled switch or router that everyone is afraid to reboot.
- Firewall rules named after incidents instead of services.
- No record of why a route, NAT rule, or VLAN exists.
- No rollback notes for recent network changes.

These are not automatically failures, but they deserve review.

## Practice

Design a small office network for:

- 30 employee laptops.
- 6 printers.
- 8 conference-room devices.
- 1 server rack.
- Guest Wi-Fi.
- Site-to-site VPN to a cloud network.

Write:

1. Your subnet list.
2. Your trust boundaries.
3. Your default gateway and DNS plan.
4. Your redundancy choices.
5. Your Linux validation commands for one wired laptop and one server.

Keep it simple enough that another operator could maintain it.
