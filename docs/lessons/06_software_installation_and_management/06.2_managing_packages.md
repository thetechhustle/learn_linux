## 06.2 Managing Packages

Package management is how Linux systems install, update, remove, and verify
most of their software. It is also one of the fastest ways to break a working
machine if you change too much without checking the blast radius.

The operator mindset is simple: know what is installed, know where it came
from, preview what will change, and verify the system after the package manager
finishes.

!!! abstract "What you will learn"
    - Inspect installed packages and package metadata.
    - Distinguish package inventory, repository metadata, and package files.
    - Preview package changes before applying them.
    - Install, upgrade, remove, and purge packages deliberately.
    - Verify package changes and keep a rollback path.

!!! success "Operator principle"
    Treat package changes like production changes: identify source, scope,
    dependencies, and rollback before touching the system.

## What a package contains

A package is more than a program binary. It usually includes:

- executable files
- libraries
- service units or init scripts
- default configuration files
- documentation and manual pages
- dependency declarations
- maintainer scripts that run during install, upgrade, or removal
- metadata such as version, architecture, source package, and repository

The package manager uses this metadata to decide what else must be installed,
what can be upgraded safely, and what will be removed if a dependency changes.

## Inventory the system first

Before changing packages, capture the current state.

On Debian or Ubuntu:

```console
$ apt list --installed | less
$ dpkg -l | less
$ apt show nginx
$ apt-cache policy nginx
```

On Red Hat, Fedora, or similar systems:

```console
$ dnf list installed | less
$ rpm -qa | sort | less
$ dnf info nginx
$ dnf repoquery --info nginx
```

Useful questions:

- Is the package already installed?
- Which version is installed?
- Which repository will provide the candidate version?
- Is the package from the distribution, a vendor repository, or a local file?
- What dependencies will be added, upgraded, or removed?

## Refresh repository metadata

Package managers keep local metadata about available packages. Refreshing that
metadata is not the same as upgrading packages.

On Debian or Ubuntu:

```console
$ sudo apt update
```

On Fedora:

```console
$ sudo dnf check-update
```

`apt update` updates the local package index. `apt upgrade` changes installed
packages. Keep those two operations mentally separate.

## Preview the change

Preview before applying.

For apt:

```console
$ apt list --upgradable
$ sudo apt install --simulate nginx
$ sudo apt upgrade --simulate
```

For dnf:

```console
$ sudo dnf check-update
$ sudo dnf install nginx --assumeno
$ sudo dnf upgrade --assumeno
```

Read the proposed transaction. Look for:

- packages to be installed
- packages to be upgraded
- packages to be removed
- new repositories involved
- kernel, libc, OpenSSL, database, web server, runtime, or agent changes
- service restarts or daemon reloads expected after installation

If the preview removes a package you did not expect, stop and investigate.

## Install packages deliberately

Install one named package:

```console
$ sudo apt install nginx
```

or:

```console
$ sudo dnf install nginx
```

For production systems, avoid "while I am here" package changes. Install the
package needed for the ticket, verify it, and leave unrelated upgrades for a
separate maintenance window.

## Upgrade packages

On Debian or Ubuntu:

```console
$ sudo apt upgrade
```

`apt upgrade` upgrades packages without removing installed packages. `apt
full-upgrade` may remove packages to satisfy dependencies, so it deserves more
care and a stronger rollback plan.

On Fedora:

```console
$ sudo dnf upgrade
```

Kernel, driver, libc, database, and runtime upgrades deserve special attention.
They can change behavior even when the package manager transaction succeeds.

## Remove or purge packages

Remove package binaries while keeping configuration:

```console
$ sudo apt remove nginx
```

Remove package binaries and packaged configuration files:

```console
$ sudo apt purge nginx
```

On dnf-based systems:

```console
$ sudo dnf remove nginx
```

Before removing a package, check reverse dependencies when possible:

```console
$ apt-cache rdepends nginx
$ dnf repoquery --whatrequires nginx
```

Do not remove shared libraries, runtimes, database clients, or system agents
without checking what depends on them.

## Verify after the transaction

After a package operation:

```console
$ systemctl status nginx
$ nginx -v
$ journalctl -u nginx --since "10 minutes ago"
$ apt-cache policy nginx
```

Use commands that match the service you changed. Good verification answers:

- Is the expected version installed?
- Did the service start or reload cleanly?
- Are there new errors in the journal or application logs?
- Is the listening port present if the package provides a network service?
- Does the application still pass its basic health check?

## Keep a rollback path

Package rollback depends on the distribution and the change:

- keep the previous package version available when possible
- snapshot the VM or disk before risky upgrades
- record exact package versions before and after
- preserve important configuration files before changing packages
- know whether the package manager history can undo a transaction

Examples:

```console
$ apt-cache policy nginx
$ sudo dnf history
$ sudo dnf history info last
```

Do not assume rollback is automatic. Test the rollback path in a lab for
important systems.

## Hands-on practice

Use a disposable VM or container.

1. Pick a harmless package such as `curl`, `tree`, or `htop`.
2. Check whether it is installed.
3. Inspect its candidate version and repository.
4. Simulate the install.
5. Install it.
6. Verify the installed version.
7. Remove it.
8. Confirm it is gone.

Example on Debian or Ubuntu:

```console
$ apt-cache policy tree
$ sudo apt install --simulate tree
$ sudo apt install tree
$ tree --version
$ sudo apt remove tree
```

Write down the commands and the package manager output that proved each step.
