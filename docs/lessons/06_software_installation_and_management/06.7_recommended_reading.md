### 06.7 Recommended Reading

!!! abstract "What you will learn"
    - Choose references that match the package manager and operating system you are working on.
    - Separate vendor documentation, community documentation, and command-specific help.
    - Build a short reading plan for safe installation, upgrade, rollback, and troubleshooting work.

!!! success "Operator principle"
    Prefer the documentation closest to the system you are changing. Read general books for concepts, but confirm commands, repository policy, and rollback steps in vendor or project documentation before touching production.

This chapter covered operating system installation, package managers, repositories, high-level tools, FreeBSD software management, and software localization. The best next reading is not a random pile of Linux books. It is a small set of references you can reach for when you need to answer one of four operational questions:

- What system and release am I changing?
- Which package manager owns this file or application?
- Which repository supplied the package, and do I trust it?
- How do I preview, apply, verify, and roll back the change?

## Start with local documentation

Use these first because they match the system in front of you.

```sh
man apt
man dnf
man zypper
man pkg
man ports
apt help
dnf help
zypper help
pkg help
```

Also inspect distribution-specific release notes before major upgrades. Package-manager behavior, repository names, Python/Ruby versions, OpenSSL versions, initramfs tooling, and default configuration paths can change between releases.

## Distribution and project references

- [Debian Reference](https://www.debian.org/doc/manuals/debian-reference/) - practical Debian administration, including package management, upgrades, services, and system recovery.
- [Ubuntu Server documentation: package management](https://ubuntu.com/server/docs/package-management) - a focused starting point for Ubuntu package operations on servers.
- [Fedora documentation: DNF](https://docs.fedoraproject.org/en-US/quick-docs/dnf/) - common DNF workflows for Fedora-family systems.
- [openSUSE Zypper usage](https://en.opensuse.org/SDB:Zypper_usage) - command examples for package installation, repository handling, updates, and queries.
- [Arch Wiki: pacman](https://wiki.archlinux.org/title/Pacman) - detailed package-manager behavior and troubleshooting notes. Use it as an Arch reference, not as a direct substitute for Debian, Fedora, or Ubuntu policy.
- [FreeBSD Handbook: installing applications](https://docs.freebsd.org/en/books/handbook/ports/) - the primary reference for FreeBSD packages and ports.

## Conceptual references

- **How Linux Works**, Brian Ward - useful background on how packages relate to filesystems, boot, processes, libraries, and services.
- **Linux Pocket Guide**, Daniel J. Barrett - a compact command reference for shell work around package operations.
- **The Linux Command Line**, William Shotts - good practice for the shell habits that make package investigation safer and more repeatable.
- **The Debian Administrator's Handbook**, Raphael Hertzog and Roland Mas - strong context for Debian packaging, repository policy, and administration workflows.

Books are useful for mental models, but do not treat them as the final authority for command syntax or current repository behavior. Confirm live commands with the local man page and the distribution documentation for the release you are running.

## Build a reading habit

For any package-management task, read in this order:

1. The local man page for the exact command you plan to run.
2. The distribution documentation for the installed release.
3. Release notes for the version you are upgrading to or from.
4. Project documentation for third-party repositories or vendor packages.
5. General books or tutorials for background after the immediate risk is understood.

## Hands-on practice

Run this on a disposable VM or container.

1. Pick one package-manager command from this chapter, such as `apt`, `dnf`, `zypper`, or `pkg`.
2. Open its local help and man page.
3. Find the matching distribution documentation page.
4. Write a three-line note:
   - the command you would run to preview a change
   - the command you would run to show package source or repository information
   - the command or evidence you would use to verify the result

## Check your understanding

- Why should local man pages and release-specific documentation outrank a general tutorial?
- Which reference would you use before enabling a third-party repository, and what risk are you trying to reduce?
- If a package upgrade breaks a service, what documentation would help you identify rollback or downgrade options?
- How would you explain your chosen reference path to a teammate during an incident handoff?
