## 06.3 Linux Package Management Systems

Linux distributions do not all use the same package tools. Debian and Ubuntu
families use `apt` and `dpkg`. Red Hat, Fedora, Rocky, AlmaLinux, and similar
systems use `dnf` and `rpm`. Arch Linux uses `pacman`.

The names differ, but the operating questions are the same:

- What package owns this file?
- Which version is installed?
- Which repository would provide an update?
- What dependencies or removals will this transaction cause?
- Where did the package manager record what happened?

!!! abstract "What you will learn"
    - Identify the package-management stack used by common Linux families.
    - Separate high-level dependency tools from low-level package databases.
    - Inspect package ownership, version, repositories, and logs.
    - Compare common `apt`, `dnf`, `rpm`, and `pacman` workflows.
    - Troubleshoot package issues with evidence instead of guesswork.

!!! success "Operator principle"
    Learn the local package stack before changing software. The wrong tool may
    bypass dependency handling or hide the evidence you need later.

## High-level and low-level tools

Most distributions have two layers:

- A high-level tool that resolves repositories and dependencies.
- A low-level database/tool that knows exactly which package files are
  installed on disk.

Common pairings:

| Distribution family | High-level tool | Low-level tool |
| --- | --- | --- |
| Debian / Ubuntu | `apt` | `dpkg` |
| Fedora / RHEL family | `dnf` | `rpm` |
| Older RHEL / CentOS | `yum` | `rpm` |
| Arch Linux | `pacman` | `pacman` |

Use the high-level tool for normal installs, removals, upgrades, repository
queries, and dependency resolution. Use the low-level tool when you need to
inspect the local package database or answer "who owns this file?"

## Debian and Ubuntu: `apt` plus `dpkg`

Common read-only checks:

```console
$ apt-cache policy nginx
$ apt show nginx
$ apt list --installed | less
$ dpkg -l | less
$ dpkg -S /usr/sbin/nginx
$ dpkg -L nginx | less
```

Common change previews and changes:

```console
$ sudo apt update
$ sudo apt install --simulate nginx
$ sudo apt upgrade --simulate
$ sudo apt install nginx
$ sudo apt remove nginx
```

Useful logs:

```console
$ less /var/log/apt/history.log
$ less /var/log/apt/term.log
$ less /var/log/dpkg.log
```

Repository configuration usually lives in:

```console
$ ls /etc/apt/sources.list
$ ls /etc/apt/sources.list.d/
```

If a package appears from an unexpected repository, check `apt-cache policy`
before changing it.

## Red Hat and Fedora family: `dnf` plus `rpm`

Common read-only checks:

```console
$ dnf info nginx
$ dnf list installed | less
$ dnf repoquery --info nginx
$ rpm -qa | sort | less
$ rpm -qf /usr/sbin/nginx
$ rpm -ql nginx | less
```

Common change previews and changes:

```console
$ sudo dnf check-update
$ sudo dnf install nginx --assumeno
$ sudo dnf upgrade --assumeno
$ sudo dnf install nginx
$ sudo dnf remove nginx
```

Useful history and logs:

```console
$ sudo dnf history
$ sudo dnf history info last
$ journalctl -u dnf-makecache --since today
$ less /var/log/dnf.log
```

Repository configuration usually lives in:

```console
$ ls /etc/yum.repos.d/
```

On modern systems, `dnf` replaced `yum` as the main high-level tool. Some
commands and habits still mention `yum`, especially in older runbooks. Confirm
which tool the host actually uses.

## Arch Linux: `pacman`

Arch uses `pacman` for both repository operations and the local package
database.

Common read-only checks:

```console
$ pacman -Q | less
$ pacman -Qi nginx
$ pacman -Qo /usr/bin/nginx
$ pacman -Ql nginx | less
```

Common change previews and changes:

```console
$ pacman -Qu
$ sudo pacman -S nginx
$ sudo pacman -Syu
$ sudo pacman -R nginx
```

Useful logs:

```console
$ less /var/log/pacman.log
```

Arch expects full-system upgrades. Mixing partial upgrades with ad hoc package
changes can create dependency problems.

## Package ownership: who put this file here?

When you find an unfamiliar binary, config file, library, or service unit, ask
the package database who owns it.

Debian/Ubuntu:

```console
$ dpkg -S /path/to/file
```

RHEL/Fedora:

```console
$ rpm -qf /path/to/file
```

Arch:

```console
$ pacman -Qo /path/to/file
```

If no package owns the file, it may have been installed manually, generated by
an application, created by a configuration-management tool, or left behind by a
previous removal. That is important incident evidence.

## Repository trust and drift

Repositories define where packages come from. They are part of the system's
supply chain.

Before enabling or trusting a repository, identify:

- who publishes it
- what key signs it
- which packages it can replace
- whether it is pinned or prioritized
- who owns patching and support for packages from that repository

Unexpected repositories can explain surprising upgrades. Missing repositories
can explain why a package cannot be found or why a host is stuck on an old
version.

## Troubleshooting workflow

When package management behaves strangely:

1. Identify the distribution and package tools.
2. Capture the exact error message.
3. Check repository reachability and metadata freshness.
4. Check package candidate versions and repository source.
5. Inspect dependencies and proposed removals.
6. Check package manager logs.
7. Verify whether configuration management is also changing packages.
8. Make the narrowest correction and verify again.

Examples:

```console
$ cat /etc/os-release
$ apt-cache policy package-name
$ sudo dnf history info last
$ dpkg -S /path/to/file
$ rpm -qf /path/to/file
```

## Hands-on practice

Use a disposable VM or container.

1. Identify the distribution with `cat /etc/os-release`.
2. Identify the high-level and low-level package tools.
3. Choose a harmless package such as `curl`, `tree`, or `htop`.
4. Inspect its candidate version and repository source.
5. Find which files the package installs.
6. Find which package owns one installed file.
7. Locate the package manager history or log file.

Write down the command output that proves each answer.
