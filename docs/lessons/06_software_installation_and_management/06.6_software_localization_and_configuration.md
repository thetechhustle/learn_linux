### 06.6 Software Localization and Configuration

!!! abstract "What you will learn"
    - Explain the difference between localization, system configuration, and application configuration.
    - Inspect locale, language, timezone, and keyboard settings on a Linux system.
    - Find package-installed configuration files and distinguish defaults from local overrides.
    - Make small configuration changes with backups, syntax checks, and service reloads.
    - Build a clear before-and-after evidence trail for configuration work.

!!! example "Field story"
    A service works in staging but fails in production because timestamps, decimal formatting, and config paths differ. The package installed correctly. The problem is configuration drift: the system locale, timezone, environment, and service override are not what the team expected.

!!! success "Operator principle"
    Software is not fully installed until its local assumptions are known, documented, and verified.

## Localization versus configuration

Localization controls how software adapts to a region, language, or cultural convention. It affects things such as:

- language
- character encoding
- date and time formatting
- currency and number formatting
- sorting behavior
- keyboard layout
- timezone display

Configuration controls how software behaves in a specific environment. It affects things such as:

- ports and bind addresses
- file paths
- feature flags
- logging destinations
- authentication settings
- resource limits
- service startup options

The two overlap. A database import might fail because of character encoding. A log parser might misread dates because of locale. A cron job might run at the wrong business hour because the timezone is different from the application team's assumption.

## Inspect localization state

Start with read-only commands.

Show active locale variables:

```shell
locale
```

Show generated or available locales:

```shell
locale -a
```

Show timezone state on a systemd-based distribution:

```shell
timedatectl
```

Show the local timezone link directly:

```shell
ls -l /etc/localtime
```

Show keyboard and console settings on systems that provide `localectl`:

```shell
localectl status
```

!!! tip "Prefer UTF-8"
    Modern Linux systems should normally use UTF-8 locales, such as `en_US.UTF-8`. Non-UTF-8 locales can cause subtle failures with filenames, logs, scripts, terminal output, and application data.

## Locale environment variables

Locale behavior is usually controlled by environment variables:

| Variable | Purpose |
| --- | --- |
| `LANG` | Default locale when no narrower variable is set. |
| `LC_ALL` | Overrides all other locale categories. Use carefully. |
| `LC_CTYPE` | Character classification and encoding behavior. |
| `LC_TIME` | Date and time formatting. |
| `LC_COLLATE` | Sort order. |
| `LC_NUMERIC` | Number formatting. |
| `LC_MESSAGES` | Language for messages where supported. |

Avoid setting `LC_ALL` permanently unless you have a specific reason. It overrides narrower settings and can hide the real source of behavior.

For one command, set a temporary locale:

```shell
LC_ALL=C sort names.txt
```

The `C` locale is useful when you need predictable byte-oriented sorting in scripts. It is not a user-friendly interactive default.

## Distribution tools for locale changes

Locale-generation tools vary by distribution.

On Debian and Ubuntu, common commands include:

```shell
sudo dpkg-reconfigure locales
sudo update-locale LANG=en_US.UTF-8
```

On RHEL-family systems, use `localectl` when available:

```shell
sudo localectl set-locale LANG=en_US.UTF-8
```

Set timezone with `timedatectl`:

```shell
sudo timedatectl set-timezone America/New_York
```

Before changing a real server, confirm whether the application expects UTC. Many production fleets intentionally keep servers on UTC and handle user-facing timezones in the application layer.

## Where configuration lives

Linux configuration is split across several places:

| Location | Typical use |
| --- | --- |
| `/etc` | System-wide configuration. |
| `/etc/<app>/` | Application or daemon configuration. |
| `/etc/default/` | Debian-style service defaults and environment. |
| `/etc/sysconfig/` | RHEL-style service defaults and environment. |
| `/etc/systemd/system/` | Local systemd unit files and overrides. |
| `/usr/lib/systemd/system/` or `/lib/systemd/system/` | Package-provided systemd units. |
| `/usr/share/doc/` | Package documentation and examples. |
| `~/.config/` | User-specific application configuration. |
| dotfiles such as `~/.bashrc` | User shell and tool configuration. |

The operational rule is simple: package-owned defaults are not the same as local policy. Do not edit package-managed files casually when the software supports an override directory or local config file.

## Find package-owned configuration files

Use your package manager to learn where files came from.

On Debian and Ubuntu:

```shell
dpkg -L nginx
dpkg -S /etc/nginx/nginx.conf
```

On RHEL-family systems:

```shell
rpm -ql nginx
rpm -qf /etc/nginx/nginx.conf
```

On Arch:

```shell
pacman -Ql nginx
pacman -Qo /etc/nginx/nginx.conf
```

This matters during upgrades. If a file is package-managed and locally modified, the package manager may prompt about replacement, create `.rpmsave` or `.rpmnew` files, or leave local changes in place. The exact behavior depends on the distribution and package format.

## Safe configuration workflow

Use a repeatable workflow for config changes:

1. Capture the current state:

    ```shell
    systemctl status nginx --no-pager
    nginx -t
    ```

2. Back up the file:

    ```shell
    sudo cp -a /etc/nginx/nginx.conf /etc/nginx/nginx.conf.$(date +%Y%m%d%H%M%S).bak
    ```

3. Edit the smallest necessary setting:

    ```shell
    sudoedit /etc/nginx/nginx.conf
    ```

4. Run the application's syntax check:

    ```shell
    sudo nginx -t
    ```

5. Reload instead of restarting when reload is supported:

    ```shell
    sudo systemctl reload nginx
    ```

6. Verify service and logs:

    ```shell
    systemctl status nginx --no-pager
    journalctl -u nginx -n 50 --no-pager
    ```

!!! warning "Reload is not magic"
    Some applications support graceful reloads. Others require a restart. Some accept the reload command but do not apply every setting until restart. Check the application's documentation and verify the behavior.

## systemd drop-in overrides

For systemd-managed services, prefer drop-in overrides over editing package-provided unit files.

Create or edit an override:

```shell
sudo systemctl edit nginx
```

Example override:

```ini
[Service]
Environment="LANG=en_US.UTF-8"
```

Then reload systemd metadata and restart or reload the service as appropriate:

```shell
sudo systemctl daemon-reload
sudo systemctl restart nginx
```

Inspect the final merged unit:

```shell
systemctl cat nginx
systemctl show nginx --property=Environment
```

`systemctl cat` is one of the best tools for proving which unit file and overrides are active.

## Environment files and application config

Many services read environment files. Debian-style packages may use `/etc/default/<service>`. RHEL-style packages may use `/etc/sysconfig/<service>`.

Inspect the unit to confirm:

```shell
systemctl cat <service>
```

Look for lines such as:

```ini
EnvironmentFile=-/etc/default/example
```

The leading `-` means systemd will not fail if the file is missing.

When troubleshooting, identify every layer:

- package default config
- local config file
- environment file
- systemd drop-in
- command-line arguments in the unit
- application runtime state

## Configuration drift after package upgrades

Package upgrades can introduce new defaults while preserving local files. That is usually correct, but it can hide drift.

Look for distribution-specific conflict files:

```shell
sudo find /etc -name "*.rpmnew" -o -name "*.rpmsave" -o -name "*.dpkg-dist" -o -name "*.dpkg-old"
```

Review these files deliberately. They often contain new upstream defaults or old local versions that need reconciliation.

## Hands-on practice

Use a disposable VM, container, or lab machine.

1. Capture localization state:

    ```shell
    locale
    locale -a | head
    timedatectl
    ```

2. Run a command with a temporary locale:

    ```shell
    printf "z\na\nä\n" | LC_ALL=C sort
    printf "z\na\nä\n" | LC_ALL=en_US.UTF-8 sort
    ```

3. Pick a harmless service or package and identify its config files:

    ```shell
    systemctl cat <service>
    ```

4. If the application has a syntax-check command, run it before changing anything.

5. Make one reversible lab-only config change, validate it, reload or restart the service, then restore the original value.

6. Write a note with:

    - the original setting
    - the changed setting
    - validation command
    - reload or restart command
    - rollback command
