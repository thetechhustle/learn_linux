### 06.5 FreeBSD Software Management

!!! abstract "What you will learn"
    - Explain why a Linux operator should understand FreeBSD software management.
    - Compare FreeBSD's binary package workflow with Linux package-manager workflows.
    - Use `pkg` to inspect, install, upgrade, remove, and audit installed software.
    - Describe when the FreeBSD Ports Collection is useful and why it carries more operational risk.
    - Build a short verification trail before and after package changes.

!!! example "Field story"
    A team inherits a small FreeBSD firewall, storage appliance, or build host next to a mostly Linux fleet. Security updates are due, but the host is unfamiliar. The safe move is not to treat it like Ubuntu or Fedora. The safe move is to identify the package source, preview the change, preserve evidence, and make the smallest reversible update.

!!! success "Operator principle"
    FreeBSD software management has the same operational goals as Linux package management: know what is installed, know where it came from, preview changes, verify the result, and keep rollback options close.

## Why FreeBSD belongs in a Linux course

FreeBSD is not Linux, but it is common enough in infrastructure that a Linux operator should not be surprised by it. You may see FreeBSD in network appliances, storage systems, firewalls, build hosts, and older Unix-oriented environments.

The useful comparison is not "which operating system is better." The useful comparison is how each operating system answers the same operational questions:

- What software is installed?
- Which repository or build source supplied it?
- What would an upgrade change?
- Which files belong to a package?
- How do I audit known vulnerabilities?
- How do I return the system to a known-good state?

FreeBSD answers these questions mainly through `pkg` for binary packages and the Ports Collection for source-based builds.

## Binary packages with `pkg`

`pkg` is FreeBSD's binary package manager. It is the normal choice for routine server operations because it installs prebuilt packages, tracks dependencies, records package metadata, and supports audits.

Use read-only inventory commands first:

```shell
pkg info
```

Show details for one package:

```shell
pkg info nginx
```

Find which package owns a file:

```shell
pkg which /usr/local/sbin/nginx
```

List files installed by a package:

```shell
pkg info -l nginx
```

Search available packages:

```shell
pkg search nginx
```

Install a package:

```shell
sudo pkg install nginx
```

Remove a package:

```shell
sudo pkg delete nginx
```

!!! tip "Path clue"
    Many third-party packages on FreeBSD install under `/usr/local`, such as `/usr/local/bin`, `/usr/local/sbin`, and `/usr/local/etc`. Base system files usually live outside that tree. That split is one of the first clues that you are not on a Linux distribution.

## Updating repository metadata and packages

Refresh package repository metadata:

```shell
sudo pkg update
```

Preview and apply package upgrades:

```shell
sudo pkg upgrade
```

`pkg upgrade` shows the packages it plans to install, upgrade, reinstall, or remove before asking for confirmation. Read that preview. It is the FreeBSD equivalent of slowing down before an `apt upgrade`, `dnf upgrade`, or `pacman -Syu` transaction.

After an upgrade, capture evidence:

```shell
pkg info
pkg version -v
```

`pkg version -v` compares installed package versions against the repository index and makes drift visible.

## Auditing vulnerabilities

FreeBSD provides package vulnerability auditing through `pkg audit`.

Fetch the current vulnerability database:

```shell
sudo pkg audit -F
```

Audit installed packages:

```shell
pkg audit
```

When `pkg audit` reports vulnerable packages, treat it as an evidence source, not as a blind instruction to upgrade everything immediately. Confirm exposure, check service impact, review the upgrade plan, and schedule the change using the same discipline you would use on Linux.

## The Ports Collection

The FreeBSD Ports Collection is a tree of build recipes under `/usr/ports`. A port includes Makefiles, patches, metadata, dependency rules, and build options for compiling software from source.

Ports are useful when you need:

- build-time options that are not available in the binary package
- a local patch
- a version or flavor not available from the package repository
- a deeper understanding of how a package is built

They also add operational cost:

- builds take longer than binary installs
- local build options can drift from fleet standards
- dependency builds can change more than expected
- upgrades need more careful documentation

Install from ports only when the reason is clear and written down.

!!! warning "Old commands and current practice"
    Older FreeBSD material often uses `portsnap` to fetch the ports tree. Modern FreeBSD systems commonly use Git for `/usr/ports`. Check the FreeBSD Handbook and the host's existing practice before changing how ports are maintained.

Example ports workflow:

```shell
cd /usr/ports/editors/nano
sudo make config
sudo make install clean
```

That workflow builds from source. It is powerful, but it is not the safest default for routine patching.

## Services and configuration after package changes

Installing software is only part of the job. FreeBSD service configuration often involves `/etc/rc.conf` or files under `/usr/local/etc/rc.d`.

For example, after installing `nginx`, you might enable it with:

```shell
sudo sysrc nginx_enable=YES
```

Then start or restart the service:

```shell
sudo service nginx start
sudo service nginx status
```

Before you do this on a real host, confirm the package documentation and local service policy. The package manager installs files; it does not prove the service is safe to run in that environment.

## Package-change checklist

Use this short checklist for FreeBSD package work:

1. Identify the host and OS version:

    ```shell
    freebsd-version
    uname -a
    ```

2. Capture current package evidence:

    ```shell
    pkg info
    pkg version -v
    ```

3. Check vulnerabilities:

    ```shell
    sudo pkg audit -F
    pkg audit
    ```

4. Preview the change:

    ```shell
    sudo pkg upgrade
    ```

5. Apply only the intended change.

6. Verify package and service state:

    ```shell
    pkg info <package>
    pkg which <important-path>
    sudo service <service> status
    ```

7. Record what changed, why it changed, and how to roll back.

## Troubleshooting clues

If a FreeBSD package change fails, gather facts before trying a second fix:

- `pkg info` shows installed package inventory.
- `pkg version -v` shows packages behind or ahead of repository versions.
- `pkg check -d` checks dependency problems.
- `pkg check -s` checks package checksums.
- `pkg audit` shows known vulnerable packages.
- `/var/log/messages` may show system or service errors.
- `/usr/local/etc` often contains third-party package configuration.

Do not mix binary packages and custom ports builds casually. If a host uses ports for important software, document that policy before upgrading related packages.

## Linux comparison

The patterns should feel familiar:

| Operational question | Debian/Ubuntu | RHEL/Fedora | Arch | FreeBSD |
| --- | --- | --- | --- | --- |
| Installed package inventory | `apt list --installed`, `dpkg -l` | `dnf list installed`, `rpm -qa` | `pacman -Q` | `pkg info` |
| Package owns file | `dpkg -S` | `rpm -qf` | `pacman -Qo` | `pkg which` |
| Files in package | `dpkg -L` | `rpm -ql` | `pacman -Ql` | `pkg info -l` |
| Search repositories | `apt search` | `dnf search` | `pacman -Ss` | `pkg search` |
| Upgrade packages | `apt upgrade` | `dnf upgrade` | `pacman -Syu` | `pkg upgrade` |
| Vulnerability audit | distro/security tooling varies | distro/security tooling varies | Arch advisories/manual review | `pkg audit` |

The commands differ, but the operator discipline is the same.

## Hands-on practice

Use a disposable FreeBSD VM or lab machine.

1. Record OS and package state:

    ```shell
    freebsd-version
    pkg info
    pkg version -v
    ```

2. Search for a small package:

    ```shell
    pkg search jq
    ```

3. Install it:

    ```shell
    sudo pkg install jq
    ```

4. Prove ownership and files:

    ```shell
    pkg info jq
    pkg info -l jq
    pkg which /usr/local/bin/jq
    ```

5. Remove it:

    ```shell
    sudo pkg delete jq
    ```

6. Write a short note with the package name, command transcript, installed files, and removal result.
