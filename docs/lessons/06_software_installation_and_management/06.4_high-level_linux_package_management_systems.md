## 06.4 High-level Linux Package Management Systems

High-level package tools sit above the low-level package database. They choose
repositories, resolve dependencies, download packages, order transactions, and
often handle signatures, update notices, and desktop application metadata.

For an operator, the important question is not "which command installs
software?" It is "what will this tool change, where will it get the software,
and how can I prove the system is still healthy afterward?"

!!! abstract "What you will learn"
    - Explain the difference between low-level package tools and high-level front ends.
    - Inspect repository and package metadata before installing or upgrading software.
    - Use simulation, download-only, and history commands to reduce package-change risk.
    - Choose the right front end for terminal, graphical desktop, and fleet workflows.

!!! success "Operator principle"
    A package manager is a change engine. Treat every install, upgrade, and remove action as a planned change with source, scope, and rollback evidence.

## What high-level tools add

Low-level package tools such as `dpkg` and `rpm` know how to install, query,
verify, and remove individual package files. They do not make broad policy
decisions by themselves.

High-level tools add the operational layer:

- repository selection and package search
- dependency resolution
- upgrade planning
- signature and metadata checks
- conflict handling
- transaction history
- graphical or API-driven workflows

Common Linux examples include `apt`, `dnf`, `zypper`, PackageKit, Synaptic, and
GNOME Software. They often manage the same underlying package database, so
mixing them without awareness can lead to lock conflicts or confusing change
history.

## Start with evidence

Before changing packages, collect a short baseline. The exact command depends
on the distribution, but the habit is the same.

Debian and Ubuntu systems:

```bash
apt policy
apt list --upgradable
apt-cache policy openssh-server
```

Fedora, RHEL, and related systems:

```bash
dnf repolist
dnf check-update
dnf info openssh-server
```

SUSE systems:

```bash
zypper repos
zypper list-updates
zypper info openssh
```

These commands answer three practical questions:

- Which repositories are enabled?
- Which packages would change?
- Which version and source would be selected?

## Preview the transaction

High-level package managers can often show their plan before making changes.
Use that preview when the system is production-like, remote, or hard to
recover.

Debian and Ubuntu:

```bash
sudo apt install --simulate nginx
sudo apt upgrade --simulate
sudo apt install --download-only nginx
```

Fedora, RHEL, and related systems:

```bash
sudo dnf install --assumeno nginx
sudo dnf upgrade --assumeno
sudo dnf download nginx
```

SUSE:

```bash
sudo zypper install --dry-run nginx
sudo zypper update --dry-run
```

Read the proposed removals and dependency changes carefully. A safe-looking
install is not safe if it removes a desktop environment, database client,
kernel package, network service, or authentication component that the system
depends on.

!!! warning "Remote-system safety"
    Be extra cautious when updating packages that affect SSH, networking, boot, disks, identity, or firewall behavior. Keep a second access path available before changing them on a remote host.

## Know the front ends

### APT

`apt` is the usual high-level command on Debian and Ubuntu systems. It combines
repository metadata, dependency resolution, and package transactions in one
operator-facing command.

```bash
sudo apt update
apt search nginx
sudo apt install nginx
sudo apt remove nginx
```

Use `apt-get` in scripts when you need a stable command-line interface. Use
`apt` interactively when a human is reading the output.

### DNF and YUM

`dnf` is the standard high-level package manager for Fedora, modern RHEL, and
many RHEL-derived distributions. Older systems may still expose `yum`, but on
many current systems `yum` is an alias or compatibility wrapper around `dnf`.

```bash
dnf search nginx
sudo dnf install nginx
sudo dnf upgrade
dnf history
```

`dnf history` is especially useful during troubleshooting because it shows what
changed and when.

### Zypper

`zypper` is the high-level package manager for openSUSE and SUSE Linux
Enterprise systems.

```bash
zypper search nginx
sudo zypper install nginx
sudo zypper update
zypper history
```

SUSE systems often make repository and product-channel state explicit. Check
that state before assuming an update problem is caused by the package itself.

### PackageKit

PackageKit provides a common service layer that desktop tools can use across
multiple distributions. GNOME Software and other graphical tools may talk to
PackageKit instead of calling `apt`, `dnf`, or `zypper` directly.

Useful read-only commands include:

```bash
pkcon get-updates
pkcon search name nginx
```

PackageKit is convenient on workstations, but servers should still have a clear
terminal-friendly change record.

### Synaptic and GNOME Software

Synaptic and GNOME Software are graphical front ends. They are useful when a
desktop user needs to browse application descriptions, inspect optional
packages, or install common desktop software.

They are not a substitute for operational evidence. If a GUI tool changes a
package on a managed system, record what changed in the same way you would for
a terminal transaction.

## Repository trust and third-party packages

High-level tools make installation easy, which makes repository trust more
important. Before adding a third-party repository, PPA, vendor script, or
desktop app source, answer these questions:

- Who signs the packages?
- How is the signing key installed and rotated?
- Which packages can this repository override?
- Is the repository needed permanently, or only for one package?
- How will you remove or disable it later?

Do not paste a vendor install script into a shell on a production system unless
you have reviewed what it does and have a rollback plan.

## Troubleshooting package-manager problems

Package-manager failures usually come from a small set of causes:

- stale metadata
- unreachable or misconfigured repositories
- package-manager lock conflicts
- broken dependencies
- interrupted transactions
- disk space exhaustion
- signature or key problems

Start with read-only checks:

```bash
df -h
ps aux | grep -E 'apt|dpkg|dnf|rpm|zypper'
```

Then use the distribution-specific history and verification tools:

```bash
grep -E " install | upgrade | remove " /var/log/apt/history.log
dnf history
zypper history
```

Do not remove lock files just because a command says the database is locked.
First confirm that no real package-manager process is running.

!!! warning "Lock-file safety"
    A lock file can mean "another transaction is active." Removing it while `dpkg`, `rpm`, `apt`, `dnf`, or `zypper` is still running can corrupt the package database.

## Hands-on practice

Run this lab on a disposable VM, container, or test host.

1. Identify the distribution and package system:

   ```bash
   cat /etc/os-release
   ```

2. List enabled repositories with the native high-level package tool.

3. Pick a harmless package such as `tree`, `jq`, or `curl`, then inspect which
   version and repository would be selected.

4. Simulate the install or run it with an "assume no" option.

5. Install the package only if the preview looks safe.

6. Capture the package-manager history entry or log entry for the change.

7. Remove the package and confirm the system returns to the expected state.

## Summary

High-level package managers save time because they combine repositories,
dependency resolution, downloads, and transactions. That convenience also gives
them broad authority over the system. Use them deliberately: inspect sources,
preview changes, capture history, and verify service health after the change.
