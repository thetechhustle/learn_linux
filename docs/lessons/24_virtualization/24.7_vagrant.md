### 24.7 Vagrant

Vagrant is a workflow tool for repeatable virtual machines. It gives an
operator a small project directory, a `Vagrantfile`, and commands that can
create, start, stop, rebuild, and inspect a lab system without remembering all
of the underlying hypervisor details.

Vagrant does not replace VirtualBox, VMware, libvirt, or cloud providers. It
sits above them. The provider runs the machine; Vagrant records how the machine
should be created and gives everyone on the team the same entry point.

    - Read a `Vagrantfile` before trusting it.
    - Manage VM lifecycle, SSH access, synced folders, and cleanup.
    - Decide when Vagrant is useful and when it is the wrong layer.

!!! success "Operator principle"
    Treat a `Vagrantfile` like executable infrastructure documentation: review
    it, version it, and prove what it created.

## Where Vagrant fits

Vagrant is useful when a team needs the same disposable machine repeatedly:

- a developer lab that should match a service dependency;
- a training environment for package, network, or configuration-management
  practice;
- a reproduction case for a bug that should not depend on one person's laptop;
- a local VM that bootstraps the same way every time;
- a short-lived test machine for Ansible, shell scripts, or service setup.

The main artifact is the `Vagrantfile`. It can define the base image, hostname,
networking, forwarded ports, synced folders, memory, CPUs, and provisioning
commands.

Vagrant is less useful when the real target is a long-running production
cluster, an image-building pipeline, or a container-only development workflow.
For those cases, use the platform's native tooling, Packer, Terraform, Docker,
Kubernetes, or the cloud provider API.

## Install and provider checks

Vagrant needs both the Vagrant CLI and a provider. The most common local
provider is VirtualBox, but Vagrant can also use VMware, libvirt, Hyper-V, and
cloud plugins.

On Debian or Ubuntu systems, package names vary by release:

```console
$ apt-cache policy vagrant virtualbox
$ sudo apt update
$ sudo apt install vagrant virtualbox
```

On Fedora:

```console
$ sudo dnf install vagrant
```

Before creating a machine, record the local versions:

```console
$ vagrant --version
Vagrant 2.4.3
$ vagrant plugin list
No plugins installed.
$ VBoxManage --version
7.1.8r168469
```

If the chosen provider is not installed or not healthy, `vagrant up` fails
early. Fix the provider before debugging the `Vagrantfile`.

## Start from an empty project

Create Vagrant environments in their own directories. That keeps state,
configuration, and synced files easy to inspect and remove.

```console
$ mkdir ubuntu-lab
$ cd ubuntu-lab
$ vagrant init ubuntu/jammy64
```

This creates a `Vagrantfile`. Read it before starting the machine:

```console
$ sed -n '1,180p' Vagrantfile
```

The default generated file is mostly comments. The key line is usually:

```ruby
config.vm.box = "ubuntu/jammy64"
```

The box name identifies the base image. Use current, maintained boxes whenever
possible. Old examples often use `ubuntu/trusty64`, which is obsolete and
should not be copied into new labs.

## Bring the machine up

Start the VM:

```console
$ vagrant up
```

Then inspect what Vagrant created:

```console
$ vagrant status
Current machine states:

default                   running (virtualbox)
$ vagrant global-status --prune
id       name    provider   state    directory
9f4a2d1  default virtualbox running  /home/admin/ubuntu-lab
```

For VirtualBox-backed machines, confirm the provider sees the VM too:

```console
$ VBoxManage list runningvms
"ubuntu-lab_default_..." {9f4a2d1c-...}
```

That two-layer check matters. `vagrant status` tells you Vagrant's view;
`VBoxManage`, `virsh`, or the provider's native command tells you whether the
hypervisor agrees.

## SSH access

Use Vagrant's SSH wrapper:

```console
$ vagrant ssh
vagrant@ubuntu-jammy:~$ hostname
ubuntu-jammy
vagrant@ubuntu-jammy:~$ exit
```

For automation or troubleshooting, ask Vagrant for the SSH details:

```console
$ vagrant ssh-config
Host default
  HostName 127.0.0.1
  User vagrant
  Port 2222
  IdentityFile /home/admin/ubuntu-lab/.vagrant/machines/default/virtualbox/private_key
```

Do not copy private keys or generated `.vagrant/` state into source control.
The `Vagrantfile` is the durable config; `.vagrant/` is local runtime state.

## Synced folders

By default, Vagrant syncs the project directory into the guest at `/vagrant`.
That makes it easy to edit files on the host and run them inside the VM:

```console
$ echo 'hello from host' > note.txt
$ vagrant ssh -c 'cat /vagrant/note.txt'
hello from host
```

Synced folders are convenient, but they can hide permission or filesystem
differences. If a service behaves differently in production, check whether the
lab is using a synced host folder where production would use an ordinary Linux
filesystem.

You can define a clearer mount point:

```ruby
config.vm.synced_folder ".", "/srv/lab"
```

## Networking

Vagrant normally sets up NAT so the guest can reach the network while staying
behind the host. For local services, forward one host port into the VM:

```ruby
config.vm.network "forwarded_port", guest: 8080, host: 18080
```

After `vagrant reload`, verify from the host:

```console
$ vagrant ssh -c 'python3 -m http.server 8080 --directory /vagrant' &
$ curl -I http://127.0.0.1:18080/
HTTP/1.0 200 OK
```

For multi-VM labs or host-to-guest access, use a private network:

```ruby
config.vm.network "private_network", ip: "192.168.56.20"
```

Avoid bridged/public networks unless the lab really needs to appear on the
physical LAN. A bridged VM can expose services to other devices on the network,
which changes the risk profile.

## Provisioning

Vagrant can run shell commands when the machine is created:

```ruby
config.vm.provision "shell", inline: <<-SHELL
  apt-get update
  apt-get install -y nginx
SHELL
```

Provisioning should be idempotent: running it twice should not break the
machine. Test it explicitly:

```console
$ vagrant provision
$ vagrant provision
```

For larger labs, prefer a configuration-management tool such as Ansible. Keep
the `Vagrantfile` responsible for the machine boundary and let the provisioner
own service configuration.

## Lifecycle commands

Use the least destructive lifecycle command that solves the problem:

```console
$ vagrant status
$ vagrant suspend
$ vagrant resume
$ vagrant halt
$ vagrant up
$ vagrant reload
$ vagrant provision
```

Destroy removes the VM:

```console
$ vagrant destroy
```

Treat `destroy` as destructive. The base box can be downloaded again and the VM
can be rebuilt, but data written only inside the guest is gone unless it was in
a synced folder or deliberately backed up.

## Boxes and trust

Boxes are base images. List downloaded boxes:

```console
$ vagrant box list
ubuntu/jammy64 (virtualbox, 20240529.0.0)
```

Update a box when you need a newer base image:

```console
$ vagrant box outdated
$ vagrant box update
```

Only use boxes from sources you trust. A box is a full operating-system image;
it can contain users, services, packages, and configuration you did not create.
For serious internal use, build your own boxes with Packer or use a vetted
organization namespace.

## Multi-machine labs

Vagrant can define more than one VM in a single file:

```ruby
Vagrant.configure("2") do |config|
  config.vm.define "web" do |web|
    web.vm.box = "ubuntu/jammy64"
    web.vm.network "private_network", ip: "192.168.56.21"
  end

  config.vm.define "db" do |db|
    db.vm.box = "ubuntu/jammy64"
    db.vm.network "private_network", ip: "192.168.56.22"
  end
end
```

Start one machine or all machines:

```console
$ vagrant up web
$ vagrant up
$ vagrant status
```

Multi-machine labs are good for learning network boundaries, service
dependencies, and configuration-management targeting. Keep them small enough
that a learner can still explain every VM.

## Common failure patterns

Provider not found:

:   Install or repair the provider. Verify with `VBoxManage --version`,
    `virsh version`, or the provider-specific command before rerunning Vagrant.

Box download fails:

:   Check DNS, proxy settings, and the box name. Prefer current boxes from
    trusted publishers.

SSH timeout:

:   Inspect `vagrant status`, the provider console, CPU virtualization support,
    and host firewall rules. Run `vagrant ssh-config` to see the expected port.

Synced folder errors:

:   Confirm Guest Additions or provider tools are compatible. As a temporary
    workaround, use rsync-backed synced folders or avoid host-mounted paths.

Port collision:

:   If the host port is already in use, choose another host port in the
    `Vagrantfile` and run `vagrant reload`.

Provisioning fails halfway:

:   Fix the provisioning script, then run `vagrant provision`. If the VM is in
    an unknown state, destroy and recreate it after preserving any needed data.

## Hands-on practice

Use a disposable workstation or lab host with Vagrant and a provider installed.

1. Create a new directory named `vagrant-lab`.
2. Run `vagrant init ubuntu/jammy64`.
3. Read the generated `Vagrantfile` and remove comments you do not need.
4. Add a forwarded port from guest `8080` to host `18080`.
5. Start the VM with `vagrant up`.
6. Record `vagrant status`, `vagrant ssh-config`, and provider-native evidence.
7. Start a small HTTP server inside the guest and test the forwarded port.
8. Add a note to the synced folder and read it from inside the guest.
9. Halt the VM.
10. Destroy it only after writing down what data would be lost.
