### 24.4 VMware

!!! abstract "What you will learn"
    - Describe where VMware Workstation, ESXi, and vSphere fit in Linux operations.
    - Inspect a Linux guest running on VMware and identify VMware-specific devices.
    - Explain the operational trade-offs around VMware snapshots, tools, storage, and networking.
    - Ask the right questions before moving a workload into or out of VMware.

!!! example "Field story"
    A Linux service runs fine on a developer laptop in VMware Workstation, but the
    production target is a vSphere cluster. The guest operating system may look
    similar, but the storage, networking, snapshots, migration process, backups,
    and support boundaries are different. Operators need evidence before treating
    those environments as interchangeable.

!!! success "Operator principle"
    VMware is not one product. Treat each VMware environment as a platform with
    its own lifecycle, management plane, and operational contract.

## The VMware family

VMware has been one of the dominant enterprise virtualization platforms for a
long time. In practice, Linux operators usually encounter VMware in a few
different forms:

- **VMware Workstation Pro / Player**: desktop virtualization on a laptop or
  workstation.
- **VMware Fusion**: desktop virtualization on macOS.
- **VMware ESXi**: bare-metal hypervisor installed directly on server hardware.
- **vCenter / vSphere**: management plane for ESXi hosts, clusters, templates,
  storage, networking, permissions, and lifecycle operations.
- **VMware Tools / open-vm-tools**: guest-side integration for better drivers,
  time sync, shutdown handling, IP reporting, and management integration.

The names matter because the operational model changes. A local Workstation VM
is often a personal lab artifact. A vSphere VM may be tied to production change
control, backups, disaster recovery, cluster placement, and storage policies.

## Workstation versus ESXi

**VMware Workstation** is a hosted desktop hypervisor. It runs as an application
on a normal operating system. It is useful for:

- local Linux labs
- testing installers
- running disposable training systems
- building or inspecting VM images
- reproducing simple user-reported environments

**ESXi** is a bare-metal hypervisor. It runs directly on server hardware and is
usually managed through vCenter in enterprise environments. It is useful for:

- production server virtualization
- clustered VM operations
- shared storage integrations
- centralized templates
- resource scheduling
- high availability and migration workflows

The same Linux distribution can run in both places, but do not assume equivalent
behavior. Check CPU, storage, network, firmware, and guest-tool state.

## Identify a Linux guest on VMware

Inside a Linux guest, start with read-only inspection:

```bash
systemd-detect-virt
hostnamectl
lscpu
lsblk -o NAME,TYPE,SIZE,MODEL
ip addr
```

Common signs of VMware include:

- `systemd-detect-virt` returning `vmware`
- virtual disks with VMware-style models
- VMware virtual network adapters
- `open-vm-tools` service installed and running

Check guest tools:

```bash
systemctl status vmtoolsd --no-pager
ps aux | grep -i '[v]mtoolsd'
```

On many Linux distributions, the preferred package is `open-vm-tools`, not the
older bundled VMware Tools installer.

Debian or Ubuntu:

```bash
sudo apt install open-vm-tools
```

RHEL-compatible distributions and Fedora:

```bash
sudo dnf install open-vm-tools
```

Then verify:

```bash
systemctl enable --now vmtoolsd
systemctl status vmtoolsd --no-pager
```

## Virtual hardware choices

VMware can present different virtual hardware to a guest. The choices affect
performance and compatibility.

Important examples:

- **VMXNET3**: high-performance paravirtualized network adapter.
- **E1000/E1000E**: emulated Intel network adapters, often easier for old guests
  but less ideal for modern Linux.
- **PVSCSI**: paravirtualized SCSI adapter for better storage performance.
- **LSI Logic SAS**: broadly compatible virtual storage adapter.
- **UEFI versus BIOS firmware**: affects boot behavior, disk layout, and secure
  boot options.

Inside Linux, collect evidence before changing devices:

```bash
lspci
lsblk -o NAME,HCTL,TYPE,SIZE,MODEL
ethtool -i <interface>
```

Changing a virtual storage controller or firmware mode can make a guest fail to
boot. Treat those changes like production maintenance, not cosmetic cleanup.

## Storage concepts

VMware virtual disks are often stored as **VMDK** files. In vSphere, those files
usually live on a datastore backed by local disks, SAN, NAS, vSAN, or another
storage platform.

Operator questions:

- Is the virtual disk thin-provisioned or thick-provisioned?
- What datastore backs the disk?
- Is the datastore near capacity?
- Does the backup system protect this VM?
- Are snapshots present?
- Is storage latency affecting the guest?

Inside Linux, you can see the guest view:

```bash
lsblk
df -h
iostat -xz 1
```

That does not show the whole platform. A guest can look healthy while the
datastore is overloaded. If storage performance is suspicious, correlate guest
metrics with vSphere datastore and host metrics.

## Networking concepts

VMware networking ranges from simple Workstation NAT to complex vSphere
distributed switches.

Common terms:

- **Virtual NIC**: the guest-facing network adapter.
- **Port group**: a vSphere network attachment point with VLAN and policy.
- **vSwitch**: virtual switch on an ESXi host.
- **Distributed switch**: vCenter-managed switch spanning multiple hosts.
- **NAT network**: common desktop mode where the guest exits through the host.
- **Bridged network**: guest appears on the external network.

Inside Linux, inspect the guest view:

```bash
ip addr
ip route
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

If a VM cannot reach the network, do not only debug Linux. Also confirm the VM is
connected to the expected VMware network and VLAN.

## Snapshots are not backups

VMware snapshots are useful for short maintenance windows and test rollback.
They are not a long-term backup strategy.

Snapshot risks:

- snapshots can grow and consume datastore space
- long snapshot chains can hurt performance
- backups may behave differently when snapshots exist
- reverting can discard valid guest changes
- application consistency may require guest coordination

Before using a snapshot, write down:

- why it exists
- when it should be removed
- what rollback would lose
- whether the application needs a quiesced snapshot
- whether a real backup also exists

If you inherit a VMware environment, old snapshots are one of the first things to
look for.

## Templates, clones, and customization

VMware environments often use templates to create new VMs quickly. A **template**
is a prepared source VM used for cloning. A **clone** is a new VM copied from an
existing VM or template.

Good templates include:

- current OS patches
- `open-vm-tools`
- sane disk layout
- cloud-init or customization support if used
- no host-specific secrets
- clear ownership and update process

Bad templates create drift. If every VM is manually fixed after cloning, the
template is not carrying the real operating contract.

## Migration and portability

Moving VMs between VMware products, KVM, cloud platforms, or image formats is
possible, but not automatic.

Before migration, inventory:

- firmware mode: BIOS or UEFI
- disk controller type
- network adapter type
- guest tools package
- filesystem layout
- static IP assumptions
- application licensing
- attached ISO files or extra disks
- backup and rollback path

VM conversion often fails because of boring details: missing boot drivers, stale
network configuration, different device names, or platform-specific guest tools.

## Linux guest checklist on VMware

For a Linux VM that someone asks you to support, collect this minimum evidence:

```bash
hostnamectl
systemd-detect-virt
lscpu | sed -n '1,25p'
lsblk -o NAME,TYPE,SIZE,MODEL
ip addr
ip route
systemctl status vmtoolsd --no-pager
df -h
```

Then answer:

- Is this Workstation, ESXi, or unknown?
- Does the guest have VMware tools running?
- What virtual disk and NIC models are visible?
- Is storage full inside the guest?
- Is the network configuration static or DHCP?
- Who owns the VMware management plane?
- Is there a backup or snapshot policy?

## Common operational failures

**Guest does not shut down cleanly from VMware**

Likely causes:

- `open-vm-tools` missing or stopped
- guest OS is hung
- ACPI or systemd shutdown path broken

Evidence:

```bash
systemctl status vmtoolsd --no-pager
journalctl -b -p warning
```

**Network adapter changed after migration**

Likely causes:

- different virtual NIC model
- persistent network naming changed
- static IP tied to old interface name

Evidence:

```bash
ip link
ip addr
networkctl status 2>/dev/null || true
```

**Disk performance is poor**

Likely causes:

- overloaded datastore
- unsuitable virtual storage controller
- snapshot chain
- guest filesystem pressure

Evidence:

```bash
iostat -xz 1
df -h
lsblk -o NAME,HCTL,TYPE,SIZE,MODEL
```

**VM appears healthy but application is unreachable**

Likely causes:

- wrong port group or VLAN
- guest firewall
- service bound to localhost
- stale DNS
- upstream load balancer or security policy

Evidence:

```bash
ss -lntp
ip route
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```
