### 24.1 Virtual Vernacular

!!! abstract "What you will learn"
    - Explain the core vocabulary used around Linux virtualization.
    - Distinguish virtual machines, containers, emulation, and machine-image tooling.
    - Ask sharper questions when selecting or troubleshooting a virtualization stack.

!!! example "Field story"
    A teammate says, "The app works in my VM, but not in the cloud image."
    Before you can help, you need to know which layer they mean: the guest
    operating system, the hypervisor, the image, the virtual disk, the virtual
    network, or a provisioning step that ran after boot.

!!! success "Operator principle"
    Virtualization terms are not trivia. They describe operating boundaries,
    failure domains, and who is responsible when something breaks.

## Why the vocabulary matters

Virtualization lets one physical machine present many isolated computing
environments. That sounds simple until you have to debug a failed boot, choose
between KVM and VirtualBox, resize a virtual disk, or explain why a container is
not the same thing as a full virtual machine.

A good operator does not need to memorize vendor slogans. You need enough shared
language to answer practical questions:

- What owns the hardware?
- What operating system is actually running the workload?
- How isolated is the workload from the host?
- Where are CPU, memory, disk, and network resources assigned?
- Can the environment be rebuilt from code?
- What evidence proves the virtual system is healthy?

This lesson gives you the terms you will use throughout the rest of the chapter.

## Host, guest, and workload

The **host** is the physical or upstream system that provides the resources. On a
Linux laptop running KVM, the laptop's Linux installation is the host. In a cloud
provider, the host is usually hidden from you, but it still exists somewhere in
the provider's fleet.

The **guest** is the operating system running inside a virtual machine. If you
boot Ubuntu inside a VM on Fedora, Ubuntu is the guest and Fedora is the host.

The **workload** is the application or service you care about. Sometimes the
workload runs directly inside a guest VM. Sometimes it runs inside a container
inside a guest VM. Keep those layers separate when troubleshooting.

Common evidence:

```bash
hostnamectl
systemd-detect-virt
lscpu
lsblk
ip addr
```

These commands help you identify what machine you are on, whether Linux detects a
virtual environment, and what virtual hardware is visible.

## Hypervisor

A **hypervisor** is the layer that creates and manages virtual machines. It
presents virtual CPUs, memory, disks, network cards, and other devices to each
guest.

Two common categories appear in documentation:

- **Type 1 hypervisor**: runs directly on hardware or is tightly integrated with
  the host operating system's kernel. Examples include VMware ESXi, Microsoft
  Hyper-V, Xen, and Linux KVM in practical use.
- **Type 2 hypervisor**: runs as an application on top of a normal desktop
  operating system. VirtualBox and VMware Workstation are typical examples.

The distinction is useful, but do not overfit it. Modern systems blur the line.
For Linux operators, the more important question is usually: what kernel module,
daemon, or platform actually owns the VM lifecycle?

For KVM on Linux, the stack often includes:

- `kvm` kernel support for hardware-assisted virtualization
- `qemu-system-*` for device emulation and VM execution
- `libvirt` for management APIs and lifecycle control
- `virt-install`, `virsh`, or graphical tools for operator workflows

## Virtual machine

A **virtual machine** is a complete machine-shaped environment. It normally has:

- virtual CPUs
- assigned memory
- one or more virtual disks
- one or more virtual network interfaces
- firmware or bootloader state
- a guest operating system

VMs are useful when you need a full operating system boundary. They are heavier
than containers, but they give you stronger separation and let you run different
kernels or operating systems on the same host.

Typical VM use cases:

- testing Linux distributions
- running Windows or FreeBSD on a Linux workstation
- isolating risky software
- building lab environments
- running cloud instances
- preserving legacy systems

## Hardware-assisted virtualization

Most modern CPUs include virtualization extensions. On Intel systems you will see
terms such as **VT-x** and **EPT**. On AMD systems you will see **AMD-V** and
**RVI/NPT**.

These features let the CPU run guest operating systems efficiently instead of
forcing the hypervisor to translate every privileged operation in software.

Useful checks:

```bash
lscpu | grep -i virtualization
egrep -c 'vmx|svm' /proc/cpuinfo
lsmod | grep kvm
```

If virtualization support is missing, check firmware settings. Many machines
ship with virtualization disabled in BIOS/UEFI.

## vCPU, memory, and overcommit

A **vCPU** is a virtual CPU presented to a guest. It maps onto physical CPU time
scheduled by the host. If you give four VMs four vCPUs each on an eight-core
machine, you have assigned more virtual CPU capacity than physical cores. That is
called **CPU overcommit**.

Overcommit is not automatically bad. Most systems are idle much of the time. It
becomes a problem when too many busy guests compete for the same physical CPU.

Memory can also be overcommitted, depending on the platform and configuration.
Memory pressure is usually less forgiving than CPU pressure. When memory is
oversold, guests may swap, stall, or be killed by host-side policy.

Operator questions:

- Are the guests CPU-bound, memory-bound, or I/O-bound?
- Is the host swapping?
- Are VM limits explicit or inherited from defaults?
- Is the workload latency-sensitive?

Useful checks:

```bash
free -h
vmstat 1
top
```

## Virtual disk and image

A **virtual disk** is the block device a guest sees. It may be backed by a file,
a logical volume, a raw disk, or network storage.

A **disk image** is a file or storage object containing a virtual disk. Common
formats include:

- `raw`: simple byte-for-byte disk image
- `qcow2`: QEMU Copy-On-Write format with snapshots and sparse allocation
- `vmdk`: VMware disk format
- `vdi`: VirtualBox disk format

Sparse images can appear small on the host while presenting a larger disk to the
guest. That is convenient, but it means the host can run out of real storage even
when the guest thinks it still has room.

Useful checks:

```bash
qemu-img info disk.qcow2
du -h disk.qcow2
lsblk
df -h
```

## Snapshot, clone, and template

A **snapshot** records a point-in-time state. Depending on the platform, it may
capture disk state, memory state, or both. Snapshots are excellent for short lab
experiments, but they are not a backup strategy by themselves.

A **clone** is a copied VM or disk. A full clone has independent storage. A
linked clone depends on a parent image and stores only the changes.

A **template** is a reusable base image for creating new machines. Operators use
templates to avoid rebuilding the same base OS repeatedly.

Practical rule: before changing a VM, know whether you can roll back with a
snapshot, rebuild from a template, or restore from backup. Those are different
promises.

## Virtual network

Virtual machines need network paths just like physical machines do. The common
modes are:

- **NAT**: the guest can reach outside networks through the host, but outside
  systems cannot directly reach the guest without forwarding rules.
- **Bridged networking**: the guest appears directly on the same network as the
  host, usually with its own IP address.
- **Host-only networking**: the guest can communicate with the host and other
  guests on an isolated virtual network.
- **Internal or private network**: guests can talk to each other, but not
  necessarily to the host or outside LAN.

Network mode changes the troubleshooting path. If SSH to a VM fails, you need to
know whether the VM is supposed to be reachable from the LAN, only from the host,
or only through a port-forward.

Useful checks:

```bash
ip addr
ip route
ss -lntp
ping -c 3 <target>
```

## Emulation

**Emulation** means one system imitates another. In virtualization, the guest
usually runs on the same CPU architecture with hardware assistance. In emulation,
software may translate instructions for a different CPU or device.

Examples:

- running an ARM image on an x86 laptop
- using QEMU to emulate older hardware
- testing firmware or boot behavior for a different platform

Emulation is flexible, but it is usually slower than hardware-assisted
virtualization. If a VM feels unexpectedly slow, confirm whether it is actually
using KVM acceleration or falling back to emulation.

Useful check:

```bash
ps aux | grep qemu
```

Look for acceleration flags and the architecture of the QEMU binary.

## Containerization

A **container** packages a process and its dependencies while sharing the host
kernel. Containers are not full virtual machines. They isolate processes,
filesystems, users, networks, and resource limits using kernel features such as
namespaces and cgroups.

Containers are useful when you want fast startup, high density, and repeatable
application packaging. VMs are useful when you need a stronger OS boundary,
different kernels, or full-machine behavior.

It is common to run containers inside VMs. Many cloud platforms do exactly this:
the VM provides the machine boundary, and containers provide the application
packaging boundary.

## Image building and provisioning

Virtualization is not only about running machines. Operators also need to create
repeatable machines.

Important terms:

- **Image**: a reusable machine or container filesystem artifact.
- **Golden image**: a trusted base image used to create many systems.
- **Provisioning**: configuring a machine after or during creation.
- **Cloud-init**: common first-boot configuration system for cloud images.
- **Packer**: a tool for building machine images from code.
- **Vagrant**: a tool for creating repeatable local development environments.

The stronger your image and provisioning process is, the less hand-built state
you have to remember.

## Paravirtualized drivers

Some virtual devices are designed specifically for virtual environments. These
are often called **paravirtualized** devices or drivers.

Examples include `virtio` network and disk devices on Linux/KVM. They usually
perform better than fully emulated hardware because the guest and host cooperate
through virtualization-aware interfaces.

If a VM has poor disk or network performance, check whether it is using optimized
virtual drivers.

## Live migration and high availability

**Live migration** moves a running VM from one host to another with little or no
downtime. This usually requires shared storage or careful storage replication,
compatible CPU features, and management tooling.

**High availability** means the platform can restart or relocate workloads after
a host failure. HA does not remove the need for backups, monitoring, capacity
planning, or application-level resilience.

These terms matter because vendors may make broad promises. Ask what happens to
CPU state, disk writes, network connections, and application sessions during the
event.

## Lab: identify your virtualization layers

Use a disposable VM or lab machine. Do not run destructive commands.

1. Check whether Linux detects a virtual environment:

   ```bash
   systemd-detect-virt
   ```

2. Inspect visible CPU virtualization details:

   ```bash
   lscpu | sed -n '1,25p'
   ```

3. Inspect virtual disks:

   ```bash
   lsblk -o NAME,TYPE,SIZE,MODEL
   ```

4. Inspect network interfaces and default route:

   ```bash
   ip addr
   ip route
   ```

5. Write a short note answering:

   - What is the host?
   - What is the guest?
   - What evidence suggests this is or is not virtualized?
   - Is the network NAT, bridged, host-only, or unclear?
   - What would you need to know before resizing disk, CPU, or memory?

## Quick reference

| Term | Practical meaning |
| --- | --- |
| Host | System providing compute, memory, disk, and network resources |
| Guest | Operating system running inside a VM |
| Hypervisor | Layer that creates and manages VMs |
| vCPU | Virtual CPU scheduled onto physical CPU time |
| Virtual disk | Disk device presented to a guest |
| Disk image | Host-side file or storage object backing a virtual disk |
| Snapshot | Point-in-time state used for rollback or testing |
| Clone | Copy of a VM or disk |
| Template | Reusable base VM or image |
| NAT network | Guest reaches out through host-managed translation |
| Bridged network | Guest appears directly on the external network |
| Emulation | Software imitates another machine or CPU architecture |
| Container | Process isolation that shares the host kernel |
| Provisioning | Automated configuration of a machine |
