### 24.5 VirtualBox

!!! abstract "What you will learn"
    - Explain where VirtualBox fits among Linux virtualization tools.
    - Create a practical VirtualBox VM plan with CPU, memory, disk, network, and ISO choices.
    - Use `VBoxManage` and Linux guest commands to collect useful evidence.
    - Avoid common VirtualBox pitfalls around networking, guest additions, snapshots, and host resources.

!!! example "Field story"
    You need to test a Linux installer on your laptop without touching the host
    operating system. VirtualBox is enough for the job, but only if you write
    down the VM settings, know how the network is attached, and keep snapshots
    from becoming a substitute for backups.

!!! success "Operator principle"
    VirtualBox is great for local labs. Treat it as a reproducible lab platform,
    not as a vague pile of click-through settings.

## What VirtualBox is good for

VirtualBox is a hosted desktop hypervisor. It runs on top of an existing host
operating system and lets you run guest operating systems in virtual machines.

It is commonly used for:

- Linux training labs
- testing installers and boot media
- running a different operating system temporarily
- safe experiments on a laptop
- simple reproducible demos
- Vagrant-based local development environments

VirtualBox is usually not the first choice for production server virtualization.
For production Linux hosts, KVM/libvirt, VMware ESXi, cloud VMs, or platform
services are more common. VirtualBox shines when the goal is local learning,
portability, and convenience.

## Install with distribution awareness

Many Linux distributions provide VirtualBox packages, and Oracle also publishes
packages. Prefer the source your organization supports.

On Debian or Ubuntu, the distribution package may be enough for a lab:

```bash
sudo apt update
sudo apt install virtualbox
```

On Fedora:

```bash
sudo dnf install VirtualBox
```

Package names and repository availability vary. If the package is not available,
check your distribution documentation before adding third-party repositories.

After installation, confirm the command-line tool exists:

```bash
VBoxManage --version
```

VirtualBox depends on host kernel modules. If the GUI opens but VMs fail to
start, check module and secure-boot issues before blaming the guest OS.

## Host readiness checks

Start with read-only host checks:

```bash
lscpu | grep -i virtualization
egrep -c 'vmx|svm' /proc/cpuinfo
VBoxManage --version
```

If CPU virtualization flags are missing, check BIOS/UEFI settings. If VirtualBox
kernel modules are missing or unsigned, Linux may prevent VMs from starting,
especially on secure-boot-enabled hosts.

Common host questions:

- Is hardware virtualization enabled?
- Does another hypervisor already own virtualization support?
- Is secure boot blocking VirtualBox kernel modules?
- Does the host have enough memory and disk for the guest?
- Is this a laptop that may sleep while a VM is running?

## Plan the VM before clicking

Before creating a VM, write down:

- VM name
- guest operating system and version
- ISO path
- vCPU count
- memory allocation
- virtual disk size and format
- network mode
- shared folder needs
- snapshot or rollback plan
- cleanup plan

This turns a GUI-created VM into an operating artifact someone else can
understand.

## Create a VM with the GUI

The GUI path is fine for learning:

1. Click **New**.
2. Choose a clear name such as `ubuntu-lab-01`.
3. Select the OS type and version.
4. Assign memory conservatively.
5. Create a virtual disk.
6. Attach the installer ISO.
7. Confirm the network mode.
8. Start the VM and install the guest OS.

Use conservative settings first. A lab VM does not need half your host's memory
or every CPU core. If the host starts swapping, every VM will feel broken.

## Inspect VMs with VBoxManage

The GUI is convenient, but `VBoxManage` gives repeatable evidence.

List VMs:

```bash
VBoxManage list vms
VBoxManage list runningvms
```

Inspect one VM:

```bash
VBoxManage showvminfo "ubuntu-lab-01"
```

Inspect host networking choices:

```bash
VBoxManage list hostonlyifs
VBoxManage list natnets
```

These commands are useful when helping someone remotely because they expose VM
settings without relying on screenshots.

## Network modes

VirtualBox network mode controls who can reach the guest.

Common modes:

- **NAT**: the guest can reach the internet through the host. This is usually the
  safest default for labs.
- **Bridged Adapter**: the guest appears directly on the same network as the
  host. Use this only when the VM needs LAN reachability.
- **Host-only Adapter**: the guest can communicate with the host and other
  host-only guests, but not directly with the external network.
- **Internal Network**: VMs can communicate with each other on a private virtual
  network.
- **NAT Network**: multiple guests share a VirtualBox-managed NAT network.

If SSH into a VirtualBox guest fails, first ask what network mode the VM uses.
With plain NAT, you may need port forwarding.

Example NAT port-forward concept:

```bash
VBoxManage modifyvm "ubuntu-lab-01" \
  --natpf1 "ssh,tcp,127.0.0.1,2222,,22"
```

Then the host can connect with:

```bash
ssh -p 2222 user@127.0.0.1
```

Do not expose guest ports broadly unless you understand the host firewall and
network risk.

## Guest additions

VirtualBox Guest Additions improve integration between host and guest. They can
provide better display resizing, shared clipboard behavior, shared folders, and
some device integration.

For many Linux guests, distribution packages are preferable:

Debian or Ubuntu guest:

```bash
sudo apt install virtualbox-guest-utils virtualbox-guest-x11
```

Headless server guests may only need utilities, not desktop integration.

After installation, verify related services and modules:

```bash
lsmod | grep -i vbox
systemctl --type=service | grep -i vbox || true
```

Shared clipboard and shared folders are convenient, but they reduce isolation.
Disable them when testing untrusted software.

## Disks and storage

VirtualBox commonly uses **VDI** disks, but it can also use VMDK and other
formats.

Common disk choices:

- **Dynamically allocated**: grows as the guest writes data.
- **Fixed size**: allocates the full size up front.

Dynamically allocated disks are convenient for labs, but host disk exhaustion is
still possible. A guest can believe it has free space while the host filesystem
is nearly full.

Check host and guest space:

```bash
df -h
du -h ~/VirtualBox\\ VMs/*/*.vdi 2>/dev/null || true
```

Inside the guest:

```bash
df -h
lsblk
```

Keep VM images out of random desktop folders when they become important. Put
them somewhere backed up intentionally.

## Snapshots and clones

Snapshots are useful before risky lab changes:

- OS upgrades
- package experiments
- service configuration changes
- security testing in a disposable guest

Snapshot risks:

- old snapshots consume host disk
- reverting loses guest changes
- snapshot chains can confuse lab state
- snapshots are not backups

Use snapshot names that explain intent:

```text
before-nginx-upgrade-2026-05-13
clean-install-with-ssh
before-network-reconfigure
```

Clones are better when you want a new independent lab machine. Snapshots are
better when you want a short rollback point.

## Resource management

VirtualBox guests compete with the host for CPU, memory, and disk I/O. A slow VM
may be a host resource problem.

On the host:

```bash
top
vmstat 1
df -h
```

Inside the guest:

```bash
top
free -h
df -h
```

Guidelines:

- Leave enough memory for the host OS.
- Avoid assigning all CPU cores to one VM.
- Do not run several heavy guests on a laptop without checking heat and battery.
- Shut down VMs you are not using.

## Common failure patterns

**VM will not start**

Likely causes:

- hardware virtualization disabled
- VirtualBox kernel modules not loaded
- secure boot blocking modules
- another hypervisor conflict

Evidence:

```bash
VBoxManage --version
lscpu | grep -i virtualization
dmesg | grep -i vbox | tail
```

**Guest has no network**

Likely causes:

- wrong network mode
- NAT port forwarding missing
- guest DHCP failure
- host firewall or VPN interaction

Evidence:

```bash
VBoxManage showvminfo "ubuntu-lab-01" | grep -i nic
ip addr
ip route
```

**Shared folder does not work**

Likely causes:

- Guest Additions missing
- user not in the expected guest group
- path or mount option mismatch
- host folder permission issue

Evidence:

```bash
lsmod | grep -i vbox
id
mount | grep -i vbox || true
```

**Host runs out of disk**

Likely causes:

- dynamically allocated disks grew
- snapshots accumulated
- unused VMs were never deleted

Evidence:

```bash
df -h
du -h ~/VirtualBox\\ VMs/* 2>/dev/null
```

## Lab: build a VirtualBox runbook

You can complete this lab without creating a VM if the current host is not safe
for virtualization.

1. Check host readiness:

   ```bash
   lscpu | grep -i virtualization
   VBoxManage --version
   ```

2. Pick a guest OS and ISO.

3. Write the VM plan:

   - name
   - vCPUs
   - memory
   - disk size
   - network mode
   - ISO path
   - snapshot plan
   - cleanup plan

4. If safe, create the VM in the GUI.

5. Record evidence:

   ```bash
   VBoxManage list vms
   VBoxManage showvminfo "<vm-name>"
   ```

6. Inside the guest, record:

   ```bash
   hostnamectl
   ip addr
   df -h
   ```

7. Clean up the VM when the lab is complete, or write down why it should remain.
