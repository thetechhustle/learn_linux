### 24.8 Recommended Reading

Virtualization changes quickly, but the best learning path stays steady:
understand the host kernel, understand the hypervisor or provider, learn the
guest operating system, and keep a small lab where you can prove the behavior
before using it in production.

This page is a reading path for that work. Use it to turn Chapter 24 into a
maintainable operator bookshelf instead of a list of random links.

!!! abstract "What you will learn"
    - Choose virtualization references by job: host, guest, network, storage,
      image building, or lab automation.
    - Prefer official documentation for commands, supported versions, and
      safety boundaries.
    - Build a personal virtualization runbook from repeatable lab notes.
    - Recognize which references age quickly and which stay useful for years.

!!! success "Operator principle"
    Read for evidence. A good virtualization reference should help you predict,
    inspect, and recover a real machine or lab.

## Start with local documentation

Before searching the web, inspect the documentation already installed on the
system. Local docs match the tools and versions on the machine you are using.

Useful starting points include:

```console
$ man qemu-system-x86_64
$ man virt-install
$ man virsh
$ man libvirt
$ man VBoxManage
$ man ssh_config
```

Package-provided docs are also valuable:

```console
$ dpkg -L qemu-system-x86 | grep -E 'README|doc|examples'
$ rpm -qd qemu-kvm libvirt virt-install
```

When local documentation disagrees with a blog post, trust the local docs for
the installed version and then verify in a disposable lab.

## Linux KVM, QEMU, and libvirt

For Linux virtualization, read in this order:

1. Distribution virtualization docs for your operating system.
2. libvirt documentation for domain lifecycle, storage pools, networks, and
   XML concepts.
3. QEMU documentation when you need device, CPU, disk, and machine-type detail.
4. `virt-install`, `virsh`, and `virt-manager` docs for day-to-day operation.

Good operator questions while reading:

- What command proves hardware virtualization is available?
- Where are VM definitions stored?
- Which network mode is being used?
- Where are virtual disks stored?
- How do I cleanly shut down, snapshot, migrate, or delete the VM?
- Which logs would I inspect first when startup fails?

Create a lab note for each of those questions. The result is more useful than
memorizing command examples.

## VirtualBox

VirtualBox documentation is useful for desktop labs, cross-platform teaching,
and quick local reproduction environments.

Focus on:

- VM settings that affect boot behavior;
- NAT, bridged, host-only, and internal networking;
- Guest Additions and shared-folder behavior;
- snapshot and clone behavior;
- `VBoxManage` command-line equivalents for GUI actions;
- troubleshooting provider and kernel-driver errors.

Do not treat old screenshots as authoritative. VirtualBox UI labels and host
integration behavior change across versions. Use screenshots only as a map,
then verify the actual setting with the current GUI or `VBoxManage`.

## VMware and enterprise virtualization

VMware references are often split between workstation use and enterprise
platform use.

For workstation learning, read about:

- VM hardware versions;
- VMware Tools or `open-vm-tools`;
- NAT, host-only, and bridged networking;
- snapshots versus clones;
- moving VMs between hosts.

For ESXi and vSphere concepts, read about:

- datastores;
- virtual switches and port groups;
- templates;
- resource reservations and limits;
- migration and compatibility boundaries;
- backups and snapshot risk.

Even if you do not administer vSphere, those concepts help you understand how
enterprise virtualization teams talk about capacity, risk, and ownership.

## FreeBSD bhyve

Read FreeBSD's handbook and manual pages when working with bhyve. The
terminology, device model, and service management differ from Linux/KVM.

Useful manual pages include:

```console
$ man bhyve
$ man bhyvectl
$ man vm
$ man ifconfig
$ man zfs
```

When reading bhyve examples, pay close attention to storage and networking.
Those are usually where a copied command stops matching the local host.

## Image building with Packer

Packer reading should focus on reproducibility and trust.

Prioritize:

- the official Packer documentation;
- builder documentation for the platform you actually use;
- provisioner behavior and idempotence expectations;
- variable handling and secrets boundaries;
- plugin version pinning;
- artifact naming and retention;
- validation and build logs.

An image-building reference is only useful if it helps answer three questions:

1. What base image did we start from?
2. What exact steps changed it?
3. How do we prove the resulting artifact is the intended one?

## Vagrant and disposable labs

Vagrant references are best read as lab workflow documentation. Focus less on
"getting started" snippets and more on how Vagrant models repeatability.

Read about:

- `Vagrantfile` structure;
- box trust and update behavior;
- provider-specific settings;
- synced folders;
- forwarded ports and private networks;
- provisioning with shell or Ansible;
- multi-machine labs;
- cleanup and `.vagrant/` state.

Be careful with old examples. Many still use obsolete boxes such as
`ubuntu/trusty64`. Replace them with current, maintained boxes before teaching
or reusing the lab.

## Containers and virtualization boundaries

Containers are not virtual machines, but the operational conversations overlap.
Read enough container material to explain the boundary clearly.

Useful topics:

- Linux namespaces;
- cgroups;
- container images versus VM images;
- bind mounts and volumes;
- container networking;
- rootless containers;
- when a VM is a better isolation boundary.

Docker, Podman, LXC, and systemd-nspawn can all teach useful lessons, but do
not blur the difference when writing runbooks. A VM has its own kernel boundary;
a typical container shares the host kernel.

## Networking and storage references

Virtualization failures often look like VM failures but come from network or
storage decisions.

Keep references for:

- Linux bridges and tap devices;
- NAT and firewall behavior;
- DHCP and DNS basics;
- VLANs when working with enterprise or home-lab networks;
- block devices, qcow2, raw images, and sparse files;
- snapshots, backups, and clone semantics;
- NFS, SMB, iSCSI, and shared datastore behavior.

When reading examples, ask what layer owns the problem:

- guest operating system;
- virtual NIC or disk;
- hypervisor;
- host network or storage;
- physical network or storage;
- cloud provider.

Good incident notes name the layer instead of saying "the VM is broken."

## Books that age well

Books are strongest for fundamentals and mental models. They are weaker for
current command syntax and version-specific steps.

Look for books or long-form references that explain:

- operating-system concepts;
- storage and filesystems;
- networking fundamentals;
- Linux administration;
- configuration management;
- infrastructure automation;
- failure analysis.

Use official docs for exact commands. Use books for durable explanations of why
those commands matter.

## How to evaluate tutorials

Before following a tutorial, check:

- publication date and updated date;
- operating-system version;
- tool version;
- whether commands are destructive;
- whether secrets or keys are handled safely;
- whether cleanup steps are included;
- whether the author explains verification, not just setup;
- whether the tutorial distinguishes lab behavior from production behavior.

Avoid tutorials that require running unknown scripts as root before explaining
what they do.

## Build your own virtualization runbook

Create one local runbook page per tool you use. Keep each page short and
evidence-oriented:

```text
Tool:
Version checked:
Provider or host:
Common commands:
Where configs live:
Where disks live:
Where logs live:
Safe startup check:
Safe shutdown check:
Snapshot or backup rule:
Most common failure:
Cleanup command:
Reference links:
```

Update the runbook every time a lab fails in a new way. That turns reading into
operational memory.

## Suggested study order

If you are new to virtualization, use this order:

1. Host readiness: CPU virtualization, kernel modules, storage, and network.
2. One local provider: KVM/libvirt or VirtualBox.
3. VM lifecycle: create, inspect, stop, snapshot, delete.
4. Guest access: SSH, console, tools/drivers, logs.
5. Networking: NAT, forwarded ports, private networks, bridging.
6. Storage: disk formats, snapshots, growth, backups.
7. Image building: Packer or another repeatable image tool.
8. Lab automation: Vagrant or configuration management.
9. Enterprise concepts: templates, migration, datastores, clusters.
10. Incident practice: reproduce and fix one common failure at a time.

## Hands-on practice

Build a reading-based lab plan:

1. Pick one virtualization tool from this chapter.
2. Find its official documentation and one distribution-specific reference.
3. Write down the installed version on your lab host.
4. Create a one-page runbook using the template above.
5. Run one safe lab command from the official docs.
6. Record the command, output, and cleanup step.
7. Add one "do not do this in production without review" warning.
