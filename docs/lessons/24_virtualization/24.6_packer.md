### 24.6 Packer

Packer is HashiCorp's image-building tool. Instead of installing an
operating system by hand, clicking through a cloud console, or cloning an old
virtual machine, you describe the build in a template and let Packer produce a
repeatable machine image.

That image might become an AWS AMI, an Azure image, a Google Compute image, a
VMware template, a VirtualBox box, a QEMU disk, or a Docker image. The important
operational idea is the same everywhere: the image should be built from known
inputs, tested before promotion, and replaced instead of edited in place.

!!! abstract "What you will learn"
    - Explain when Packer is useful and when a normal configuration-management
      run is enough.
    - Read the major parts of a Packer template: required plugins, variables,
      sources, builds, provisioners, and post-processors.
    - Validate and inspect a template before launching a potentially expensive
      or destructive image build.
    - Identify common image-build failures from logs, SSH setup, package
      prompts, missing plugins, and cloud permissions.

!!! example "Field story"
    A team has three slightly different "golden" Linux images: one in AWS, one
    in VMware, and one on a laptop used for labs. Nobody is sure which one has
    the current CIS hardening, SSH banner, monitoring agent, or emergency
    account policy. Packer lets the team put the image build in version control,
    review the changes, and rebuild each platform from the same intent.

!!! success "Operator principle"
    Treat images as build artifacts. Keep the template in Git, keep secrets out
    of it, validate before building, and promote only images that can be traced
    back to a commit, build log, and test result.

## Where Packer Fits

Packer does not replace every operations tool. It sits before deployment, at
the point where a base machine image is created.

Use Packer when you need:

- A repeatable base image for autoscaling groups, lab VMs, desktop templates,
  or appliance-style systems.
- Faster bootstraps because common packages, users, agents, and baseline files
  are already baked into the image.
- A reviewed image pipeline instead of a long wiki page of manual console
  steps.
- A consistent image across multiple targets, such as cloud and local
  virtualization.

Use normal configuration management or startup scripts when:

- The change is environment-specific, such as hostnames, IP addresses,
  certificates, or runtime secrets.
- The setting must change frequently after the instance is deployed.
- Rebuilding and rolling out a new image would be slower or riskier than a
  controlled in-place change.

## Template Anatomy

Modern Packer templates are commonly written in HCL. Older examples may use
JSON, and you will still see them in existing repositories, but HCL is easier
to validate, compose, and review.

A small template usually contains these parts:

- `packer.required_plugins`: the builder plugins and versions the template
  expects.
- `variable` blocks: inputs such as region, source image, instance type, and
  image name prefix.
- `source` blocks: where the temporary build machine comes from.
- `build` blocks: which sources to build and which provisioners to run.
- `provisioner` blocks: shell, file, Ansible, or other steps that customize the
  machine.
- `post-processor` blocks: optional packaging or manifest output after the
  image is built.

Here is a deliberately small example for an Amazon EBS-backed image:

```hcl
packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = "~> 1"
    }
  }
}

variable "region" {
  type    = string
  default = "us-east-1"
}

source "amazon-ebs" "ubuntu_lab" {
  region        = var.region
  source_ami    = "ami-0123456789abcdef0"
  instance_type = "t3.micro"
  ssh_username  = "ubuntu"
  ami_name      = "learn-linux-lab-{{timestamp}}"
}

build {
  sources = ["source.amazon-ebs.ubuntu_lab"]

  provisioner "shell" {
    inline = [
      "set -eux",
      "sudo apt-get update",
      "sudo DEBIAN_FRONTEND=noninteractive apt-get -y install curl jq",
      "curl --version",
      "jq --version"
    ]
  }
}
```

Do not copy a real cloud image ID from a lesson into production. Pick source
images through your organization's approved image catalog or current vendor
image lookup process.

## Safer Build Workflow

Run image builds from a disposable project, build account, or CI job with
limited permissions. A Packer build may create instances, disks, snapshots,
images, security groups, temporary keys, and logs.

Start with read-only and validation commands:

```bash
packer version
packer plugins installed
packer fmt -check .
packer validate .
```

Then initialize the plugins declared in the template:

```bash
packer init .
```

If validation passes, run a build with enough logging to debug failures:

```bash
PACKER_LOG=1 packer build .
```

For cloud builds, tag everything Packer creates. Tags help you find temporary
resources if the build is interrupted:

```hcl
run_tags = {
  Project = "learn-linux"
  Owner   = "image-pipeline"
}

snapshot_tags = {
  Project = "learn-linux"
  Owner   = "image-pipeline"
}
```

## Handling Secrets

Avoid baking secrets into images. Secrets copied into an image can leak into
snapshots, backups, logs, shell history, package-manager caches, and future
clones.

Safer patterns include:

- Install the agent or client in the image, but fetch the token at first boot
  from an approved secret store.
- Pass short-lived credentials to Packer through environment variables or CI
  secret handling, not hardcoded template values.
- Use temporary build credentials with the narrowest permissions possible.
- Clean package caches and temporary files before image capture.
- Review provisioner output so tokens are not echoed into build logs.

If you need to prove a secret was not baked into an image, boot a test instance
from the artifact and inspect common locations:

```bash
sudo grep -R "TOKEN\\|PASSWORD\\|PRIVATE KEY" /etc /opt /var/log 2>/dev/null
history
sudo find /root /home -maxdepth 3 -type f -name '*history' -print
```

Treat those commands as a starting point, not a formal security audit.

## Troubleshooting Packer Builds

Most failed builds fall into a few categories.

Plugin problems:

```bash
packer init .
packer plugins installed
```

If the builder type is unknown, the plugin may be missing or pinned to an
incompatible version.

Source image problems:

```bash
packer inspect .
```

Check whether the source image exists in the selected region or virtualization
platform, whether it allows the chosen instance type, and whether the expected
SSH user is correct.

Connection problems:

```bash
PACKER_LOG=1 packer build .
```

Look for SSH timeouts, firewall rules, missing cloud-init completion, wrong
usernames, or images that require a different communicator.

Provisioner problems:

```bash
set -eux
sudo systemctl status ssh --no-pager
sudo journalctl -xe --no-pager
```

Package prompts, service restart prompts, missing repositories, and
distribution-version differences often break shell provisioners. Keep
provisioner scripts idempotent enough that they fail clearly when re-run in a
debug VM.

Cleanup problems:

After an interrupted cloud build, check for leftover instances, volumes,
snapshots, temporary keys, and security groups in the build account. Do this
before launching another build so you do not confuse old failures with new
ones.

## Hands-on Practice

Use a disposable lab account or local virtualization target. Do not run a first
Packer build in a production cloud account.

1. Install Packer from your operating system package source or HashiCorp's
   current installation instructions.
2. Create a new directory and write a minimal template for a local or lab cloud
   target.
3. Run `packer fmt -check .`, then `packer init .`, then `packer validate .`.
4. Add one harmless provisioner step, such as installing `curl` or writing a
   lab marker file under `/etc`.
5. Build the image and save the Packer log, image ID, and source Git commit in
   a lab note.
6. Boot a test machine from the image and verify the expected package, file,
   service state, and login method.
7. Destroy temporary build resources and record what was cleaned up.
