### 24.2 Virtualization with Linux

!!! abstract "What you will learn"
    - Identify the Linux virtualization stack around KVM, QEMU, and libvirt.
    - Install and inspect virtualization support without guessing.
    - Create a simple VM workflow with evidence for CPU, memory, disk, and network state.
    - Troubleshoot common Linux virtualization failures safely.

!!! example "Field story"
    A developer needs a disposable Ubuntu server to test an upgrade. They do not
    need a cloud account yet. They need a repeatable local VM, a known network
    mode, a way to snapshot or rebuild, and enough notes that someone else can
    reproduce the lab.

!!! success "Operator principle"
    Linux virtualization is strongest when the VM lifecycle is treated like an
    operating procedure: inspect, create, verify, document, and clean up.

## Linux as a virtualization host

Linux can run virtual machines efficiently because the kernel includes
**KVM**, the Kernel-based Virtual Machine. KVM turns Linux into a practical
hypervisor when the CPU and firmware support hardware-assisted virtualization.

Most Linux VM setups combine several layers:

- **KVM**: kernel support for running guest CPUs with hardware acceleration.
- **QEMU**: the machine emulator and device model that runs the VM process.
- **libvirt**: a management API and service layer for defining and controlling VMs.
- **virt-install**, **virsh**, and **virt-manager**: common tools for creating and
  managing VMs.
- **virtio**: virtualization-aware disk and network devices for better guest
  performance.

You do not need every tool for every job. A desktop user might use
`virt-manager`. A server operator might use `virt-install` and `virsh`. A CI
system might use image-building tools such as Packer.

## Confirm host support

Start with read-only checks. These commands tell you whether the host is likely
to support accelerated virtualization:

```bash
lscpu | grep -i virtualization
egrep -c 'vmx|svm' /proc/cpuinfo
lsmod | grep kvm
```

Interpretation:

- `vmx` usually indicates Intel VT-x support.
- `svm` usually indicates AMD-V support.
- Loaded `kvm_intel` or `kvm_amd` modules indicate Linux has KVM support active.

If CPU flags are absent, check BIOS/UEFI settings before assuming the machine is
incapable. Virtualization is often disabled in firmware.

You can also ask systemd whether the current machine is itself virtualized:

```bash
systemd-detect-virt
```

That matters because nested virtualization may be disabled. A VM inside a VM can
work, but only if the outer host exposes the required CPU features.

## Install common tooling

Package names vary slightly by distribution. Use your distribution documentation
for production systems, but these are common starting points.

Debian or Ubuntu:

```bash
sudo apt update
sudo apt install qemu-kvm libvirt-daemon-system libvirt-clients virtinst virt-manager
```

Fedora:

```bash
sudo dnf install @virtualization virt-install virt-manager
sudo systemctl enable --now libvirtd
```

RHEL-compatible distributions:

```bash
sudo dnf install qemu-kvm libvirt virt-install virt-manager
sudo systemctl enable --now libvirtd
```

After installation, verify the service and default connection:

```bash
systemctl status libvirtd --no-pager
virsh list --all
```

If `virsh list --all` works, libvirt is responding. If it fails with a permission
error, your user may not be allowed to manage system VMs.

## Operator permissions

Many guides tell you to add your user to the `libvirt` group. That can be fine
on a lab workstation, but it is still administrative access to VM management.
Understand the local policy before doing it on shared systems.

Common lab setup:

```bash
sudo usermod -aG libvirt "$USER"
```

You normally need to log out and back in before group membership changes apply.
Check with:

```bash
id
```

On servers, prefer explicit administrative procedures over casual group changes.

## Create a VM with virt-install

`virt-install` defines a VM and starts the OS installation. The exact command
depends on your ISO path and desired resources.

Example lab command:

```bash
virt-install \
  --name linux-lab-01 \
  --memory 2048 \
  --vcpus 2 \
  --disk size=20,bus=virtio \
  --cdrom /var/lib/libvirt/images/ubuntu-server.iso \
  --os-variant ubuntu24.04 \
  --network network=default,model=virtio \
  --graphics spice
```

Before running this on your own machine, adjust:

- VM name
- memory size
- vCPU count
- disk size and storage location
- ISO path
- OS variant
- network mode
- graphical or console install method

If you do not know available OS variants, inspect them:

```bash
osinfo-query os | grep -i ubuntu
```

Not every system has `osinfo-query` installed. Missing OS metadata is usually a
tooling issue, not a VM blocker.

## Inspect VM lifecycle

Use `virsh` to inspect and control VMs:

```bash
virsh list --all
virsh dominfo linux-lab-01
virsh start linux-lab-01
virsh shutdown linux-lab-01
```

Avoid `virsh destroy` unless you understand it. Despite the name, it usually
means a hard power-off, not deletion. It is the VM equivalent of pulling the
power cable.

To remove a lab VM after you no longer need it:

```bash
virsh shutdown linux-lab-01
virsh undefine linux-lab-01 --remove-all-storage
```

The `--remove-all-storage` option deletes associated storage. Do not use it on a
VM that has data you need.

## Storage basics

libvirt stores many default disk images under:

```text
/var/lib/libvirt/images/
```

List storage pools:

```bash
virsh pool-list --all
virsh vol-list default
```

Inspect a disk image:

```bash
qemu-img info /var/lib/libvirt/images/linux-lab-01.qcow2
```

Use `qcow2` for common lab workflows because it supports sparse allocation and
snapshots. Use `raw` when you need simpler storage behavior or better
performance in specific environments. The right answer depends on the platform,
backup tooling, and performance requirements.

Watch host free space. A sparse VM disk can grow until the host filesystem fills:

```bash
df -h /var/lib/libvirt/images
du -h /var/lib/libvirt/images/*.qcow2
```

## Network basics

The default libvirt network usually provides NAT. Guests can reach out through
the host, and the host can often reach guests on the virtual network, but other
LAN machines cannot reach those guests directly without additional routing or
port forwarding.

Inspect libvirt networks:

```bash
virsh net-list --all
virsh net-info default
virsh net-dhcp-leases default
```

Inside the guest, inspect normal Linux networking:

```bash
ip addr
ip route
ping -c 3 1.1.1.1
```

Choose network mode based on the lab goal:

- Use **NAT** for disposable labs and outbound package installation.
- Use **bridged networking** when the VM must appear directly on the LAN.
- Use **isolated networks** when you want guests to talk only to each other.

Do not switch to bridged networking casually on a corporate or shared network.
It changes where the VM appears and may trigger security controls.

## Snapshots and rollback

Snapshots are useful before risky package upgrades or configuration tests:

```bash
virsh snapshot-create-as linux-lab-01 before-upgrade
virsh snapshot-list linux-lab-01
```

Reverting a snapshot can discard guest changes:

```bash
virsh snapshot-revert linux-lab-01 before-upgrade
```

Snapshot support depends on disk format and VM state. Treat snapshots as lab
rollback tools, not as your only backup.

## Performance checks

When a VM is slow, identify the bottleneck before changing resource settings.

On the host:

```bash
top
vmstat 1
iostat -xz 1
```

Inside the guest:

```bash
top
free -h
df -h
```

Questions to ask:

- Is the host CPU saturated?
- Is the host swapping?
- Is the storage device overloaded?
- Is the guest using `virtio` disk and network devices?
- Did the VM get enough memory for the workload?
- Is the workload slow only during boot, package installs, or normal runtime?

Adding vCPUs does not fix every performance issue. It can make scheduling worse
on an already busy host.

## Graphical management with virt-manager

`virt-manager` is useful on workstations because it exposes common VM lifecycle,
console, CPU, memory, disk, and network settings visually.

It is especially helpful when:

- installing a guest from an ISO
- checking console output during boot
- changing simple lab resource settings
- learning how libvirt represents VMs

For repeatable operations, still write down the equivalent command or XML-backed
configuration. A VM created only by clicking through a GUI can be hard to
recreate exactly.

## Common failure patterns

**KVM acceleration unavailable**

Evidence:

```bash
lscpu | grep -i virtualization
lsmod | grep kvm
```

Likely causes:

- virtualization disabled in BIOS/UEFI
- running inside a VM without nested virtualization
- missing KVM packages or modules

**Permission denied from virsh**

Evidence:

```bash
id
virsh list --all
```

Likely causes:

- user not in the expected management group
- session has not picked up new group membership
- system libvirt socket permissions differ by distribution

**Guest has no network**

Evidence:

```bash
virsh net-list --all
virsh net-dhcp-leases default
ip addr
ip route
```

Likely causes:

- libvirt default network inactive
- guest did not receive DHCP
- firewall or NetworkManager interaction
- wrong network mode for the intended reachability

**Host disk fills unexpectedly**

Evidence:

```bash
df -h
du -h /var/lib/libvirt/images/*
qemu-img info <disk-image>
```

Likely causes:

- sparse disks expanded
- old snapshots retained
- unused lab VMs not removed
- logs or package caches growing inside guests

## Lab: create a documented local VM plan

You do not need to create a VM to complete this lab if your current machine is
not safe for it. The goal is to build the operator plan first.

1. Check virtualization support:

   ```bash
   lscpu | grep -i virtualization
   egrep -c 'vmx|svm' /proc/cpuinfo
   ```

2. Check whether libvirt is installed:

   ```bash
   virsh list --all
   ```

3. Write a VM plan:

   - guest OS
   - vCPU count
   - memory
   - disk size
   - network mode
   - ISO or image source
   - rollback method
   - cleanup command

4. If this is a disposable lab host, create the VM using `virt-install` or
   `virt-manager`.

5. Record evidence after first boot:

   ```bash
   virsh list --all
   virsh dominfo <vm-name>
   virsh domifaddr <vm-name>
   ```

6. Clean up only when you are sure no data is needed:

   ```bash
   virsh shutdown <vm-name>
   virsh undefine <vm-name> --remove-all-storage
   ```
