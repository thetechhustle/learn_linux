### 24.3 FreeBSD bhyve

`bhyve` is the native FreeBSD hypervisor. Linux administrators do not need to
use it every day, but they should recognize it when FreeBSD hosts appear in a
lab, edge, storage, or network-appliance environment. The operating model is
similar to KVM in one important way: the host kernel provides the virtualization
support, and the administrator still has to prove CPU support, storage layout,
network attachment, boot firmware, and guest health.

!!! abstract "What you will learn"
    - Explain where bhyve fits compared with KVM, VMware, and VirtualBox.
    - Check whether a FreeBSD host can run bhyve guests.
    - Identify the files, services, and commands that make a bhyve VM work.
    - Troubleshoot common boot, network, and storage failures safely.

!!! success "Operator principle"
    Treat a FreeBSD virtualization host like any other production hypervisor:
    collect read-only evidence first, make one reversible change at a time, and
    keep VM state separate from host state.

## Where bhyve fits

`bhyve` is a type-1 hypervisor built into FreeBSD. It can run FreeBSD, Linux,
and other guests on supported x86-64 hardware. It is commonly managed through
wrapper tools such as `vm-bhyve`, but the core pieces are still FreeBSD kernel
modules, virtual disks, virtual network interfaces, and a boot firmware package.

Use bhyve when you already operate FreeBSD hosts and want a lightweight native
hypervisor. Use KVM/libvirt when Linux is the host platform. Use VMware when the
environment already depends on enterprise VMware management. Use VirtualBox when
you need a workstation-friendly teaching or desktop lab.

## Check host support first

Run read-only checks before installing or creating anything:

```sh
freebsd-version
sysctl hw.vmm.vmx hw.vmm.svm
kldstat | grep -E 'vmm|nmdm|if_tap|if_bridge'
pciconf -lv | grep -A4 -E 'VGA|display'
ifconfig
zpool list
```

Interpret the evidence:

- `hw.vmm.vmx` is for Intel VT-x; `hw.vmm.svm` is for AMD-V. At least one should
  be available for hardware-assisted virtualization.
- `vmm` is the bhyve kernel module. It may load automatically, but production
  hosts usually make module loading explicit.
- `if_tap` and `if_bridge` are common for bridged guest networking.
- `zpool list` matters because many bhyve hosts keep VM disks on ZFS volumes or
  datasets.

If CPU virtualization is disabled in firmware, package installation will not fix
the host. Record the finding and schedule a firmware/BIOS change window.

## Install the management layer

A minimal bhyve host can be managed directly with `bhyve`, `bhyvectl`, and
`bhyveload`, but most operators use `vm-bhyve` because it gives VMs a predictable
directory layout and lifecycle commands.

```sh
pkg install vm-bhyve grub2-bhyve uefi-edk2-bhyve
sysrc vm_enable="YES"
sysrc vm_dir="zfs:zroot/vm"
```

The exact `vm_dir` depends on the host. Use a dataset or filesystem that is
large enough, backed up appropriately, and excluded from unrelated application
data. Do not put VM images in a random home directory on a production host.

Load required kernel modules through `/boot/loader.conf` when the host should be
a durable hypervisor:

```sh
vmm_load="YES"
nmdm_load="YES"
if_tap_load="YES"
if_bridge_load="YES"
```

After a reboot or manual module load, verify the state instead of assuming it:

```sh
kldstat | grep -E 'vmm|nmdm|if_tap|if_bridge'
service vm status
vm list
```

## Prepare guest networking

For a simple lab host, guests often attach to a bridge that includes the host's
physical interface and a tap interface:

```sh
vm switch create public
vm switch add public em0
vm switch list
ifconfig bridge0
```

Replace `em0` with the real host interface. Be careful on remote systems:
changing bridge membership can interrupt network access. On a production host,
make this change from console access or during a maintenance window.

Common network checks:

```sh
vm switch info public
ifconfig tap0
arp -an
sockstat -4 -l
```

If the guest boots but has no network, check bridge membership, DHCP availability,
guest interface naming, host firewall policy, and VLAN expectations before
recreating the VM.

## Create and inspect a VM

This example creates a small FreeBSD guest with `vm-bhyve`. Adjust the template,
disk size, memory, and CPU count for the lab:

```sh
vm iso https://download.freebsd.org/releases/ISO-IMAGES/14.1/FreeBSD-14.1-RELEASE-amd64-bootonly.iso
vm create -t freebsd -s 20G lab-freebsd01
vm configure lab-freebsd01
vm install lab-freebsd01 FreeBSD-14.1-RELEASE-amd64-bootonly.iso
```

Useful lifecycle commands:

```sh
vm list
vm info lab-freebsd01
vm console lab-freebsd01
vm stop lab-freebsd01
vm start lab-freebsd01
```

Before deleting or resizing anything, locate the VM storage:

```sh
vm info lab-freebsd01 | grep -E 'datastore|disk|zvol'
zfs list | grep vm
du -sh /path/to/vm/datastore/lab-freebsd01
```

## Troubleshooting checklist

Use symptoms to narrow the layer:

- Host cannot start any VM: check CPU virtualization, `vmm` module loading, and
  whether another hypervisor already owns the hardware virtualization feature.
- VM exits immediately: inspect the VM log, boot firmware package, disk path, and
  template syntax.
- Installer cannot see a disk: confirm the virtual disk exists and the guest
  template uses a controller the installer supports.
- Guest has no network: inspect the switch, bridge, tap interface, DHCP server,
  VLAN, and firewall rules.
- Console is blank: try `vm console`, verify UEFI versus legacy boot settings,
  and check whether the guest expects a graphical display.
- Host storage is filling: inspect snapshots, zvol reservations, ISO files, and
  old VM images before deleting anything.

Safe evidence commands:

```sh
vm list
vm info VMNAME
tail -100 /var/log/messages
zpool status
zfs list -o name,used,avail,refer,mountpoint
ifconfig
```

## Hands-on practice

Use a disposable FreeBSD host or nested lab that is explicitly allowed to run
virtual machines.

1. Verify CPU virtualization support and record the exact `sysctl` result.
2. Install `vm-bhyve` and firmware packages, then enable the service.
3. Create a bhyve switch and attach it to a lab-safe interface.
4. Create a small FreeBSD test VM and boot the installer.
5. Record `vm list`, `vm info`, storage usage, and bridge/interface output.
6. Stop the VM cleanly and explain how you would remove it without touching
   unrelated host data.
