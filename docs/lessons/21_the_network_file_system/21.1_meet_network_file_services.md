### 21.1 Meet Network File Services

Network file services let one system publish a directory so other systems can
use it over the network. To a client, the remote files appear under a normal
mount point such as `/mnt/builds` or `/srv/shared`. To an operator, they are a
contract between storage, network reliability, identity, permissions, and
client behavior.

NFS is the classic Unix and Linux answer to this problem. It is useful when a
set of trusted systems need shared access to files: home directories, build
artifacts, read-mostly software trees, shared application data, or lab
datasets. It is not a substitute for every storage design. Databases, object
stores, block devices, and file synchronization tools solve different problems.

## What network file services provide

At minimum, a network file service has four moving parts:

- **Server**: the system that owns the storage and exports one or more
  directories.
- **Export or share**: the server-side path and policy that define what clients
  may access.
- **Client**: the system that mounts and uses the remote directory.
- **Mount point**: the local directory where the remote filesystem appears.

For example, this command mounts an NFS export from `nfs01` at `/mnt/builds`:

```bash
sudo mount -t nfs nfs01:/exports/builds /mnt/builds
```

That command is simple, but the behavior behind it is not. A process reading
`/mnt/builds/report.txt` may now depend on DNS, routing, firewall policy, NFS
server health, export policy, user and group identity, mount options, and the
health of the underlying storage.

## When NFS fits

NFS is a good candidate when:

- Linux or Unix-like clients need shared file access on a trusted network.
- The workload is mostly normal file reads and writes, not raw block access.
- Operators can control client identity, server exports, and firewall policy.
- Applications tolerate network latency and temporary server unavailability.
- You need simple shared paths rather than object-store APIs.

Consider another tool when:

- Windows compatibility is the main requirement. SMB/Samba is usually a better
  fit.
- The workload needs transactional database semantics. Use a database service
  or storage design supported by the database vendor.
- Clients are untrusted or spread across the public Internet. Prefer an
  authenticated application protocol, VPN, or object storage.
- The requirement is one-way publication or backup. `rsync`, artifact storage,
  or object storage may be safer and easier to reason about.

## First evidence to collect

Before changing NFS configuration, collect read-only evidence from both sides.
On a client, start with the active mounts and filesystem types:

```bash
findmnt -t nfs,nfs4
mount -t nfs,nfs4
df -hT
```

Then inspect how the client reaches the server:

```bash
getent hosts nfs01
ip route get nfs01
```

On a server, inspect exported directories without changing them:

```bash
exportfs -v
sudo cat /etc/exports
```

If a client says a file is missing or permission is denied, do not stop at the
application error. Compare the client-side UID/GID, the server-side ownership,
and the mounted path:

```bash
id
ls -ld /mnt/builds
ls -ln /mnt/builds
```

## Safety notes

Treat network filesystem changes as shared infrastructure changes.

- Avoid testing with production application directories first.
- Do not use broad exports such as entire root filesystems.
- Prefer read-only exports until write access is required and understood.
- Be careful with `no_root_squash`; it can give client root users powerful
  access to server files.
- Document mount options such as `ro`, `rw`, `hard`, `soft`, `timeo`, and
  `vers` because they change failure behavior.
- Validate firewall and export scope so the service is reachable only by the
  intended clients.

## Common failure patterns

Network file service incidents usually fall into a small set of buckets:

- **Name or route failure**: the client cannot resolve or reach the server.
- **Service failure**: the server is reachable, but NFS services are down or
  blocked.
- **Export mismatch**: the path is not exported to that client or network.
- **Identity mismatch**: UIDs, GIDs, or NFSv4 identity mapping do not line up.
- **Permission mismatch**: Unix mode bits or ACLs deny access after the mount
  succeeds.
- **Performance problem**: latency, packet loss, server disk pressure, or mount
  options make ordinary file operations slow.
- **Availability surprise**: a server outage turns local-looking file access
  into stuck processes or application errors.

## Hands-on practice

Use a disposable Linux VM or lab host. Do not use a production NFS server for
this exercise.

1. Inspect whether the system already has NFS mounts:

   ```bash
   findmnt -t nfs,nfs4
   ```

2. Create a short lab note with these headings:

   ```text
   Client hostname:
   Existing NFS mounts:
   Candidate server/export:
   Intended mount point:
   Expected access: read-only or read-write
   Rollback command:
   ```

3. If you have a lab NFS export available, create a temporary mount point and
   mount it read-only first:

   ```bash
   sudo mkdir -p /mnt/nfs-lab
   sudo mount -t nfs -o ro nfs01:/exports/lab /mnt/nfs-lab
   findmnt /mnt/nfs-lab
   ```

4. Verify what changed, then unmount it:

   ```bash
   ls -la /mnt/nfs-lab
   sudo umount /mnt/nfs-lab
   findmnt /mnt/nfs-lab
   ```

5. If you do not have a lab export, write the exact command you would run and
   list the evidence you would collect before running it.
