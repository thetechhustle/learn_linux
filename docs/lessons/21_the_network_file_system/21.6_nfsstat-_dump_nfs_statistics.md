### Digging Deeper: `nfsstat`: Dump NFS Statistics

!!! abstract "What you will learn"
    - Use `nfsstat` to separate NFS client, server, RPC, and version-specific evidence.
    - Read NFS statistics during troubleshooting without overreacting to raw counters.
    - Reset counters safely in a lab so you can measure one workload at a time.
    - Pair `nfsstat` with mount, kernel, and network evidence during an incident.

!!! example "Field story"
    A build farm stores shared dependencies on an NFS export. Developers say builds feel slow, but the server CPU looks normal and the network graph is not obviously saturated. Before changing mount options or blaming the storage array, you need evidence: are clients retransmitting calls, are reads or writes dominating, and is the problem visible on one client or on the NFS server itself?

!!! success "Operator principle"
    `nfsstat` is a counter tool, not a verdict. Use it to find where to look next, then confirm the story with workload timing, logs, mount options, and network checks.

## What `nfsstat` shows

`nfsstat` reports counters from the kernel's NFS client, NFS server, and RPC layers. These counters help answer questions such as:

- Is this host acting as an NFS client, an NFS server, or both?
- Which NFS protocol versions are active?
- Are remote procedure calls succeeding cleanly, or are there retransmissions and timeouts?
- Which operations dominate the workload: lookup, getattr, read, write, commit, create, remove, or rename?

The command does not show every detail of a slow file operation. It is best used as a starting point for narrowing the failure domain.

## Start with the broad view

Run the default command first:

```console
$ nfsstat
```

On an NFS client, you may see client RPC counters and client NFS operation counters. On an NFS server, you may see server RPC counters and server NFS operation counters. A host that is not using NFS may show little or no data.

The exact section names vary by distribution and NFS utilities version, but the broad categories are usually:

- Client RPC statistics
- Server RPC statistics
- Client NFS operation counts
- Server NFS operation counts
- Per-version NFS statistics

!!! tip "Read counters as a trend"
    A large counter is not automatically bad. A busy, healthy server should have large counters. The useful question is what changed between two measurements.

## Separate client and server evidence

To look only at client-side NFS statistics:

```console
$ nfsstat -c
```

To look only at server-side NFS statistics:

```console
$ nfsstat -s
```

This split matters because an NFS incident often looks different from each side:

- A client may show retransmissions or timeouts while the server appears healthy.
- A server may show a heavy operation mix even though one complaining client is idle.
- A single client may have a bad mount option, DNS issue, firewall path, or network segment.
- Many clients showing similar symptoms usually points closer to the server, export, storage, or network core.

## Check the protocol version

Modern Linux systems commonly use NFSv4, but NFSv3 is still common in older environments and appliances. Version matters because mount behavior, locking, identity handling, and operation names differ.

Show NFSv3 statistics:

```console
$ nfsstat -3
```

Show NFSv4 statistics:

```console
$ nfsstat -4
```

Combine options when you want a narrow view:

```console
$ nfsstat -c -4
$ nfsstat -s -4
```

If you expected NFSv4 but only see NFSv3 activity, inspect the live mounts:

```console
$ findmnt -t nfs,nfs4
$ mount | grep -E ' type nfs| type nfs4'
```

## Watch RPC health

NFS uses Remote Procedure Calls. RPC counters are often the first clue that an issue is about transport reliability rather than file permissions or application behavior.

Look for fields that describe:

- total calls
- retransmissions
- bad calls
- timeouts
- authentication failures
- dropped or rejected calls

For a client, rising retransmissions during a workload can indicate packet loss, server overload, an unreachable server path, or an overly aggressive timeout/retry pattern. For a server, rejected or bad calls can point toward version mismatch, firewall state, service registration, or authentication trouble.

!!! warning "Do not diagnose from one number"
    A few retransmissions over a long uptime may be normal. Rapidly increasing retransmissions while users report slowness is a stronger signal.

## Read the operation mix

NFS operation counters show what the workload is actually asking the server to do.

Common operations include:

- `getattr`: read file metadata
- `lookup`: find a pathname component
- `read`: read file data
- `write`: write file data
- `commit`: flush unstable writes to stable storage
- `create`: create files
- `remove`: delete files
- `rename`: rename files
- `readdir`: list directory contents

This can reveal workload shape:

- High `lookup` and `getattr` counts often come from metadata-heavy workloads such as builds, dependency scans, and directory walks.
- High `read` counts suggest read-heavy sharing, artifact access, or cache misses.
- High `write` and `commit` counts suggest write-heavy workloads or applications that force frequent sync behavior.
- High `readdir` counts can point to large directories or polling tools.

The operation mix does not prove the cause of slowness, but it tells you which part of the NFS workload deserves closer inspection.

## Reset counters in a lab

On many Linux systems, `nfsstat -z` zeroes NFS statistics:

```console
$ sudo nfsstat -z
```

Use this carefully. Resetting counters on a production server can erase useful incident evidence for other administrators.

In a lab, zeroing counters is useful:

1. Record the current counters.
2. Reset the counters.
3. Run one known workload.
4. Run `nfsstat` again.
5. Compare the counters to the workload you just ran.

For production, prefer capturing a before-and-after snapshot without resetting:

```console
$ date
$ nfsstat -c
$ sleep 60
$ date
$ nfsstat -c
```

## Pair `nfsstat` with other evidence

`nfsstat` is stronger when it sits beside a small evidence bundle:

```console
$ findmnt -t nfs,nfs4
$ nfsstat -c
$ nfsiostat 1 5
$ dmesg --ctime | grep -i nfs | tail -20
$ ip route get <nfs-server-ip>
```

On the server, useful companions include:

```console
$ exportfs -v
$ nfsstat -s
$ ss -lntup | grep -E ':(2049|111)\\b'
$ journalctl -u nfs-server --since -1h
```

Use `nfsiostat` when you need per-mount latency and throughput detail:

```console
$ nfsiostat 1 5
```

The `1 5` arguments ask for five samples, one second apart. This is usually more useful than an endless stream during a first pass.

## Troubleshooting flow

When an NFS user reports slowness:

1. Identify the client, server, export, and mount path.
2. Confirm the live mount with `findmnt -t nfs,nfs4`.
3. Capture client counters with `nfsstat -c`.
4. Capture per-mount timing with `nfsiostat 1 5`.
5. If you can access the server, capture server counters with `nfsstat -s`.
6. Compare whether the issue is isolated to one client or visible on the server.
7. Look for rapidly increasing retransmissions, timeouts, or a workload-heavy operation mix.
8. Only then consider changing mount options, export options, network paths, or application behavior.

## Hands-on practice

Use a disposable lab VM or a nonproduction NFS client.

1. Confirm whether the machine has NFS mounts:

   ```console
   $ findmnt -t nfs,nfs4
   ```

2. Capture a client statistics snapshot:

   ```console
   $ nfsstat -c
   ```

3. If a test NFS mount exists, run a small read-only workload:

   ```console
   $ find /mnt/test-nfs -maxdepth 2 -type f | head
   ```

4. Capture counters again:

   ```console
   $ nfsstat -c
   ```

5. Write down which counters changed and what that says about the workload.

If you do not have an NFS mount, use the commands to learn what an idle or non-NFS host looks like. That is still useful baseline knowledge.
