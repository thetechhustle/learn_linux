### 21.2 The NFS Approach

NFS makes remote storage look like part of a local Linux directory tree. A
client mounts an exported directory from a server, then applications read and
write paths under that mount point as if the files were local.

That simple idea is powerful, but it is also easy to misunderstand. NFS does
not copy a directory to every client. It does not remove the need for Linux file
permissions. It does not make network latency disappear. It gives clients a
filesystem interface backed by a remote server, so normal file operations now
depend on server policy, client mount behavior, identity mapping, and the
network between them.

## The Basic Model

An NFS deployment has two main roles:

- **Server**: owns the real directory, local filesystem, disks, permissions, and
  export policy.
- **Client**: mounts the exported directory into its own filesystem tree and
  sends file operations over the network.

The server chooses what to export. The client chooses where to mount it.

```text
NFS server
  real directory: /srv/projects
  export policy: allow selected clients

NFS client
  mount point: /mnt/projects
  visible path: /mnt/projects/app.tar.gz
```

From the client's point of view, `/mnt/projects/app.tar.gz` behaves like a
regular path. From the operator's point of view, every access crosses several
boundaries:

- client process
- local VFS and NFS client code
- network path
- NFS server service
- server-side filesystem and permissions
- underlying storage

That is why NFS troubleshooting often requires checking both machines.

## Exports Are Not Mounts

An **export** is the server-side permission to share a directory. On many Linux
systems, exports are described in `/etc/exports` and applied by the NFS server.

Example shape:

```text
/srv/projects  192.0.2.25(ro,sync,root_squash)
```

This says the server is willing to share `/srv/projects` with client
`192.0.2.25` using the listed options.

A **mount** is the client-side act of attaching that remote export to a local
path.

Example shape:

```bash
sudo mount -t nfs server.example.com:/srv/projects /mnt/projects
```

The export says, "this server allows access." The mount says, "this client is
using that access here." You need both.

## Permissions Have Layers

NFS access is controlled in more than one place:

- Network reachability: can the client reach the server and NFS ports?
- Export policy: is this client allowed by the server export?
- Export options: is the export read-only or read-write, synchronous or
  asynchronous, root-squashed or not?
- Filesystem permissions: do the effective user and group have access to the
  files on the server?
- Identity mapping: do users and groups mean the same thing on both sides?

This layering explains a common beginner trap: the directory may look writable
locally, but writes can still fail because the export is read-only, root is
squashed, the server sees a different UID, or the backing filesystem denies the
operation.

## Why NFS Feels Local

Linux applications usually do not need special NFS support. They call normal
filesystem operations such as `open`, `read`, `write`, `stat`, and `rename`.
The kernel routes those operations through the NFS client when the path lives
under an NFS mount.

That transparency is the whole point. It also creates operational risk because
applications may not know that their storage depends on a remote service. A
slow server can become a slow application. A lost network path can create
blocked processes. A stale file handle can appear after server-side changes
that invalidate what the client has cached.

## Statelessness and Modern NFS

Classic NFS designs were often described as stateless because the server did
not need to remember much client session state to recover after a crash. Modern
NFS, especially NFSv4, has more stateful features such as locking, delegations,
and sessions. The practical lesson is not to memorize a slogan; it is to know
which NFS version you are using and what recovery behavior your clients expect.

Check mounts with:

```bash
findmnt -t nfs,nfs4
```

Or inspect the kernel mount table:

```bash
cat /proc/mounts | grep ' nfs'
```

## Operational Tradeoffs

NFS is often a strong fit when:

- multiple Linux systems need shared read-mostly files
- workloads expect POSIX-style paths rather than object storage APIs
- the network is reliable and low latency
- identity and permissions are centrally understood
- operators can monitor the server and clients together

NFS is often a poor fit when:

- clients are spread across unreliable or high-latency networks
- many writers need strict coordination under heavy load
- identity is inconsistent between machines
- the data needs object-storage durability semantics
- an application cannot tolerate storage stalls

The right question is not "can NFS share this directory?" It is "what happens
to the workload when this shared directory is slow, unavailable, or
misconfigured?"

## Hands-On Practice

On a lab system, inspect NFS-related support without mounting anything:

```bash
findmnt -t nfs,nfs4
cat /proc/filesystems | grep nfs
modinfo nfs 2>/dev/null | head
```

If you have a disposable two-machine lab, create a read-only export with test
data first. Mount it on the client, read a file, then unmount it cleanly. Do not
start with writable home directories or application data.

Keep a note with:

- the server export path
- the client mount point
- the NFS version in use
- the export options
- the mount options
- one command that proves a read works
- one command that proves unmounting works
