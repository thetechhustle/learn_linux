### 21.3 Server-Side NFS

The NFS server owns the real files. Clients may see a remote directory as a
local path, but the server controls what is exported, which clients can mount
it, what access they receive, and how server-side file permissions are enforced.

Server-side NFS work is therefore not just "turn on sharing." It is a storage,
network, identity, and security decision. A careless export can expose private
data, allow unexpected writes, or give client root users more influence than
intended.

!!! abstract "What you will learn"
    - Identify the main server-side NFS components on Linux.
    - Create a safer read-only lab export.
    - Understand common export options such as `ro`, `rw`, `sync`, and `root_squash`.
    - Verify server exports without relying on guesswork.

!!! warning "Do not start with a wide-open export"
    Avoid examples such as `*(rw,no_root_squash)` and avoid `chmod 777` on shared data. Those patterns are useful only as examples of what can go wrong.

## Server Responsibilities

An NFS server is responsible for:

- storing the real data on a local filesystem
- running the NFS server services
- defining exports
- limiting which clients can mount each export
- enforcing export options
- relying on Linux ownership and mode bits, ACLs, or other filesystem controls
- exposing enough monitoring evidence for troubleshooting

The client can request access, but the server decides whether that request is
allowed.

## Install the Server Package

Package names vary by distribution. On Debian and Ubuntu, the server package is
typically:

```bash
sudo apt update
sudo apt install nfs-kernel-server
```

On Fedora, RHEL, and similar systems, the package and service names are usually
provided by `nfs-utils`:

```bash
sudo dnf install nfs-utils
```

Verify the service name on your system:

```bash
systemctl list-unit-files | grep -E 'nfs|rpc'
```

Do this in a lab first. Production file servers deserve a change plan, a
rollback plan, and a client-impact window.

## Create a Lab Export Directory

Start with a small, read-only export. This lets you prove the server/client path
without risking important data.

```bash
sudo mkdir -p /srv/nfs/read-only-demo
echo "hello from the NFS server" | sudo tee /srv/nfs/read-only-demo/hello.txt
sudo chown -R root:root /srv/nfs/read-only-demo
sudo chmod -R a+rX /srv/nfs/read-only-demo
```

This creates test data that clients can read but ordinary users cannot modify
on the server.

## Define an Export

Exports are usually declared in `/etc/exports`.

Use a narrow client range. The documentation block below uses the reserved
documentation subnet `192.0.2.0/24`; replace it with your lab network.

```text
/srv/nfs/read-only-demo 192.0.2.0/24(ro,sync,root_squash,subtree_check)
```

Option meanings:

- `ro`: clients can read but not write.
- `sync`: the server replies after changes are committed according to the
  server's sync behavior; this is safer than optimizing for speed first.
- `root_squash`: root on the client is mapped to an unprivileged identity on
  the server.
- `subtree_check`: asks the server to verify exported subdirectories; this can
  be useful for subdirectory exports, though some environments choose
  `no_subtree_check` for stability and performance.

For many whole-filesystem exports, you will see `no_subtree_check`. The
important point is to know why the option is present instead of copying it
blindly.

## Apply and Inspect Exports

After editing `/etc/exports`, apply the export table:

```bash
sudo exportfs -ra
```

Inspect what the server believes it is exporting:

```bash
sudo exportfs -v
```

You can also inspect active NFS-related services:

```bash
systemctl status nfs-server 2>/dev/null || systemctl status nfs-kernel-server
```

On systems using firewalld, check service exposure:

```bash
sudo firewall-cmd --list-services
```

Do not open firewall services until you know which clients should be allowed.
For a real deployment, network controls should be as narrow as the export
policy.

## Safer Export Patterns

A conservative export often starts read-only:

```text
/srv/nfs/reports 192.0.2.25(ro,sync,root_squash,no_subtree_check)
```

A writable export should be narrower and should rely on real server-side
ownership:

```text
/srv/nfs/project-builds 192.0.2.25(rw,sync,root_squash,no_subtree_check)
```

For writable shares, ask:

- Which exact clients need write access?
- Which Unix users or groups should own the files?
- Do clients and server agree on UIDs and GIDs?
- What happens if two clients write the same path?
- How is this directory backed up?
- What monitoring shows latency, errors, and capacity pressure?

## Root Squashing Matters

`root_squash` protects the server from trusting root on every client. Without
it, root on an allowed client may be able to act like root against files in the
export, depending on the rest of the setup.

That is rarely the right default. Use `no_root_squash` only when you can clearly
explain why the client should be trusted that deeply, what the blast radius is,
and how the server is protected.

## Common Server-Side Failure Points

When a client cannot mount or use an export, check the server for:

- export syntax errors in `/etc/exports`
- export table not reloaded after changes
- client IP or hostname not matching the export rule
- firewall blocking NFS-related traffic
- NFS service not running
- backing directory missing or mounted somewhere unexpected
- server-side file permissions denying access
- UID/GID mismatch between server and client
- disk full or inode exhaustion on the backing filesystem

Useful read-only checks:

```bash
sudo exportfs -v
findmnt /srv/nfs/read-only-demo
df -h /srv/nfs/read-only-demo
df -i /srv/nfs/read-only-demo
ls -ld /srv/nfs/read-only-demo
```

## Hands-On Practice

In a disposable lab:

1. Create `/srv/nfs/read-only-demo` with one test file.
2. Add a read-only export for one test client or lab subnet.
3. Reload exports with `sudo exportfs -ra`.
4. Verify with `sudo exportfs -v`.
5. Mount from a client and confirm the file is readable.
6. Try to write from the client and confirm the server denies it.
7. Remove the export when finished and reload the export table.

Keep a lab note with the export line, `exportfs -v` output, client mount
command, and the read/write test results.
