### 21.9 Recommended Reading

!!! abstract "What you will learn"
    - Choose NFS references that match a real operational question.
    - Separate protocol documentation, Linux implementation notes, and troubleshooting guides.
    - Build a small NFS learning plan that moves from safe lab practice to production readiness.
    - Know which topics to study next before changing NFS identity, mount, or server behavior.

!!! example "Field story"
    You inherit a small NFS environment. It works most days, but nobody can explain the export rules, why clients use different mount options, or what to check when users report slow builds. A random web search gives you snippets. A good reading path gives you a sequence: protocol basics, Linux implementation, exports, identity, automounting, and troubleshooting evidence.

!!! success "Operator principle"
    Read NFS material with a question in mind. The best reference is the one that helps you make a safer decision on the system in front of you.

## Start with local documentation

Your first NFS references are already on the machine.

Use manual pages to confirm command behavior:

```console
$ man nfs
$ man nfsstat
$ man exports
$ man exportfs
$ man mount.nfs
$ man idmapd.conf
$ man autofs
```

Manual pages are not always friendly tutorials, but they are close to the implementation you are running. They are especially useful for option names, default behavior, and distribution-specific details.

Check package-provided documentation too:

```console
$ rpm -qd nfs-utils 2>/dev/null
$ dpkg -L nfs-common 2>/dev/null | grep -E 'doc|README'
$ dpkg -L nfs-kernel-server 2>/dev/null | grep -E 'doc|README'
```

Use the command that matches your distribution family. It is normal for one of these commands to be absent.

## Read the Linux NFS project documentation

The Linux NFS project maintains practical documentation for the Linux client and server implementation. Prioritize it when you need implementation-specific context.

Look for material about:

- NFS client behavior
- NFS server behavior
- NFSv4 identity mapping
- `nfs-utils`
- pNFS and advanced layouts
- mount option behavior
- common troubleshooting notes

This category is more useful than generic protocol summaries when you are changing Linux hosts.

## Read protocol references when behavior seems strange

NFS is a protocol family, not a single command. Protocol references are useful when you need to understand why a Linux tool behaves a certain way.

Use protocol-level references for questions such as:

- What changed between NFSv3 and NFSv4?
- Why does NFSv4 use a single well-known port more often than older NFS stacks?
- How do locking, delegations, compound operations, and callbacks fit together?
- Why does identity mapping look like `user@domain`?
- What does a specific NFS operation mean?

Protocol documents can be dense. Do not start there when the immediate problem is a wrong export path or typo in `/etc/fstab`.

## Use books for structured background

Books are useful when you need context that is broader than one incident.

Good reading themes include:

- classic NFS and Unix file service administration
- Linux storage and filesystems
- Unix identity and directory services
- TCP/IP troubleshooting
- performance analysis

Older NFS books can still be valuable for concepts, but verify commands and defaults against current Linux documentation. NFSv4, systemd, firewalls, Kerberos practice, and distribution service names have changed since many classic texts were written.

## Build a reading path by task

Use this sequence when you are new to an environment:

1. **Inventory**
   - Read `man nfs`, `man exports`, and `man mount.nfs`.
   - Inspect live mounts with `findmnt -t nfs,nfs4`.
   - Inspect exports with `exportfs -v` on the server.

2. **Mount behavior**
   - Study `hard`, `soft`, `timeo`, `retrans`, `_netdev`, and systemd automount behavior.
   - Read the local `systemd.mount` and `systemd.automount` manual pages if using systemd.

3. **Identity**
   - Read `man idmapd.conf`.
   - Confirm UID/GID consistency and NFSv4 domain behavior.
   - Learn what `nobody` ownership means before changing permissions.

4. **Troubleshooting**
   - Read `man nfsstat`.
   - Practice `nfsstat`, `nfsiostat`, `journalctl`, `findmnt`, and `exportfs` together.
   - Learn which counters are trends, not immediate conclusions.

5. **Security**
   - Read about export options such as `ro`, `rw`, `root_squash`, `sync`, and client restrictions.
   - Study Kerberos-backed NFS only after the basic export and identity model is clear.

6. **Operations**
   - Learn backup, monitoring, patching, and failover expectations for the NFS server.
   - Document what happens when the server is down.

## Evaluate online tutorials carefully

Many NFS tutorials are written for a quick lab and are not safe production patterns.

Be careful with tutorials that:

- export writable directories to entire networks without explanation
- use `no_root_squash` casually
- skip firewall and service verification
- assume all clients share the same UID/GID database
- recommend `chmod 777` to fix access problems
- ignore what happens when the server is unavailable
- mix NFSv3 and NFSv4 instructions without saying so

Useful tutorials explain why each option exists, how to verify the result, and how to undo the lab.

## Keep your own NFS runbook

After reading, write a local runbook for the environment you actually operate.

Include:

- NFS servers and their roles
- exported paths and intended clients
- expected NFS versions
- mount points and mount options
- identity source and NFSv4 domain
- firewall requirements
- restart and reload commands
- normal `nfsstat` or `nfsiostat` baseline notes
- known failure modes and escalation contacts

This runbook is more valuable during an incident than a long list of bookmarks.

## Hands-on practice

Use a lab machine or disposable VM.

1. Pick one command from this chapter, such as `exportfs`, `findmnt`, `nfsstat`, or `nfsiostat`.
2. Read its manual page.
3. Run the safest read-only form of the command.
4. Write three facts the command can prove.
5. Write one thing the command cannot prove by itself.
6. Add the result to a short NFS runbook note.

Repeat this process for each NFS tool before using it during a production incident.
