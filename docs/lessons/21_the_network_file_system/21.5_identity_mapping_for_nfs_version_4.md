### 21.5 Identity Mapping for NFS Version 4

NFS permissions depend on identity. The server may export a directory
correctly, and the client may mount it successfully, but users can still see
wrong owners or get unexpected `permission denied` errors when identity mapping
does not line up.

NFSv4 made identity more explicit by using names such as `alice@example.com`
instead of relying only on raw numeric UIDs and GIDs in every part of the
protocol. Linux still enforces permissions through local users, groups, and
numeric IDs, so clients and servers need a consistent way to translate between
names and numbers.

!!! abstract "What you will learn"
    - Explain why NFSv4 identity mapping exists.
    - Inspect the NFSv4 domain and ID mapping services.
    - Recognize common symptoms of identity mismatch.
    - Avoid changing identity settings blindly on production clients or servers.

!!! success "Operator principle"
    NFS identity problems are permission problems with two machines involved. Check both sides before changing either side.

## Why Identity Mapping Matters

Linux files are owned by numeric UIDs and GIDs. Names such as `alice` and
`developers` are local interpretations of those numbers.

Example:

```bash
id alice
```

Output shape:

```text
uid=1001(alice) gid=1001(alice) groups=1001(alice),2000(developers)
```

If the server thinks UID `1001` is Alice, but the client thinks UID `1001` is
someone else, permissions and ownership displays become misleading. If the
client and server disagree about the NFSv4 identity domain, names may fail to
map and show up as anonymous users such as `nobody`.

## The NFSv4 Identity Shape

NFSv4 identities commonly use a name plus a domain:

```text
alice@example.com
developers@example.com
```

The domain is not always the public DNS domain you use for websites. In NFS
configuration, it is the administrative identity domain that the NFS client and
server agree on.

On Linux, this is commonly configured in:

```text
/etc/idmapd.conf
```

The important setting is usually:

```ini
[Domain]
Domain = example.com
```

Changing this on one side only can break mappings. Treat it as shared
infrastructure configuration.

## Inspect Before Changing

Start with read-only checks.

On both client and server:

```bash
hostname -f
test -r /etc/idmapd.conf && grep -E '^[[:space:]]*Domain[[:space:]]*=' /etc/idmapd.conf
id
getent passwd "$(id -un)"
getent group "$(id -gn)"
```

Check whether NFS ID mapping services are present:

```bash
systemctl status nfs-idmapd 2>/dev/null || true
systemctl status rpc.idmapd 2>/dev/null || true
```

Different distributions expose these pieces differently, so absence of one
unit name is not automatically a failure. Use the output to understand your
system before making changes.

## Common Symptoms

Identity mapping problems often look like:

- files owned by `nobody` or `nfsnobody`
- correct-looking mounts but unexpected `permission denied`
- users able to read on one client but not another
- group permissions not applying as expected
- ownership appearing differently on client and server
- NFSv4 mounts behaving differently from older NFSv3-style expectations

These symptoms are easy to misdiagnose as a mount-option problem. Check
identity before widening export permissions.

## A Safe Troubleshooting Flow

When a user cannot access a file on an NFSv4 mount:

1. Identify the mounted path on the client.

   ```bash
   findmnt -t nfs,nfs4
   ```

2. Check the user's identity on the client.

   ```bash
   id username
   ```

3. Check the same user and group names on the server.

   ```bash
   getent passwd username
   getent group groupname
   ```

4. Compare ownership from both sides.

   ```bash
   ls -ln /path/to/file
   ls -l /path/to/file
   ```

   `ls -ln` shows numeric IDs. This is useful because names can lie when name
   service configuration differs.

5. Inspect export policy without changing it.

   ```bash
   sudo exportfs -v
   ```

6. Check the configured NFSv4 identity domain on both systems.

   ```bash
   grep -E '^[[:space:]]*Domain[[:space:]]*=' /etc/idmapd.conf
   ```

Only after this evidence is collected should you change names, groups, domain
settings, or export options.

## UID/GID Consistency Still Matters

Even with NFSv4 identity mapping, many Linux environments are simplest when
UIDs and GIDs are consistent across clients and servers. Central identity
systems such as LDAP, Active Directory integration, FreeIPA, or another
directory-backed approach reduce surprises because machines agree on who users
and groups are.

For small labs, manually matching a test user may be enough. For production,
manual identity drift becomes an incident waiting to happen.

## Cache and Restart Caution

Identity mapping may involve caches. After changing identity configuration, you
may need to restart NFS-related services or clear relevant caches, depending on
the distribution and setup.

Do not reflexively restart NFS services on a busy file server. A restart can
interrupt clients. Plan the change, identify active mounts, and understand the
impact first.

Useful evidence before a maintenance window:

```bash
sudo exportfs -v
ss -tan | grep ':2049'
findmnt -t nfs,nfs4
```

## Hands-On Practice

In a disposable two-machine lab:

1. Create the same test user on the client and server.
2. Confirm whether the UID and GID match with `id testuser`.
3. Mount a read-only NFSv4 export.
4. Create a test file on the server owned by that user.
5. Compare `ls -l` and `ls -ln` from the server and client.
6. Record the NFSv4 domain setting from both systems.

Do not intentionally break production identity mapping for practice. If you
want to test failure behavior, do it in a lab you can rebuild.
