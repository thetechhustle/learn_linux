### 21.7 Dedicated NFS File Servers

!!! abstract "What you will learn"
    - Decide when a dedicated NFS server is justified instead of sharing files from an existing general-purpose host.
    - Separate storage, network, identity, monitoring, and backup responsibilities for an NFS service.
    - Inspect a production NFS server without changing exports or interrupting clients.
    - Plan safe maintenance, capacity growth, and failover tests for shared file service.

!!! success "Operator principle"
    A dedicated NFS server is not just a host with `nfsd` installed. It is a storage service with explicit ownership, capacity, availability, identity, and recovery expectations.

A small lab can run NFS from any Linux machine. A production environment should be more deliberate. When many clients depend on one shared filesystem, the NFS server becomes part of the reliability boundary for builds, home directories, application data, package mirrors, or research datasets.

Dedicated NFS servers reduce accidental coupling. They keep file-serving workloads away from login shells, application deployments, package experiments, and unrelated service restarts. That separation makes performance easier to understand and failures easier to contain.

## When a dedicated server makes sense

Use a dedicated NFS server when one or more of these are true:

- Many clients mount the same export and user-visible outages matter.
- The export needs predictable throughput, latency, or maintenance windows.
- Storage growth, snapshots, replication, or backups need their own operational plan.
- The same data must survive application server rebuilds.
- Permissions and identity mapping need careful control across teams.
- Audit, retention, or change-control requirements apply to shared data.

Do not create a dedicated NFS server just because NFS exists. For small, temporary, or single-client use, a simpler share may be enough. For cross-platform desktop file sharing, SMB may fit better. For object-style application data, object storage may be a better boundary than a mounted filesystem.

## Design the service before installing packages

Write down the service contract before you edit `/etc/exports`:

- **Clients:** Which hosts or networks may mount the export?
- **Data owner:** Which team owns the data and approves destructive changes?
- **Identity source:** Are user and group IDs local, LDAP-backed, FreeIPA-backed, or managed another way?
- **Availability:** What outage window is acceptable for patching, storage replacement, or reboot?
- **Capacity:** What are the warning and critical thresholds for space and inode use?
- **Recovery:** What restore point and restore time are expected?
- **Security:** Is the export read-only, read-write, root-squashed, Kerberos-protected, or network-restricted?

The answers shape the server more than the `apt install` or `dnf install` command.

## Inspect the current server

Start with read-only evidence. These commands are safe to run on a production server:

```bash
hostnamectl
ip -brief address
findmnt -t nfs,nfs4
exportfs -v
cat /proc/fs/nfsd/versions
cat /proc/fs/nfsd/threads
ss -tulpn | grep -E ':(111|2049)\b|rpcbind|nfsd|mountd' || true
systemctl status nfs-server --no-pager
df -hT /srv /exports 2>/dev/null || true
df -ih /srv /exports 2>/dev/null || true
```

On Debian and Ubuntu, the service may be named `nfs-kernel-server`; on many Red Hat-family systems it is `nfs-server`.

Capture enough context to answer three questions:

1. Which filesystems back the exports?
2. Which clients are allowed to mount them?
3. Which NFS protocol versions and supporting services are active?

## Keep exports narrow

Avoid broad exports such as this:

```exports
/srv/share *(rw,sync,no_root_squash)
```

That example grants every client read-write access and allows remote root users to act as root on the exported files. It is rarely appropriate.

Prefer explicit clients or networks and safer defaults:

```exports
/srv/builds 10.20.30.0/24(ro,sync,root_squash,sec=sys)
/srv/team   build01.example.com(rw,sync,root_squash,sec=sys)
```

For stronger authentication, plan NFSv4 with Kerberos rather than relying only on client IP addresses:

```exports
/srv/team *.example.com(rw,sync,root_squash,sec=krb5p)
```

Kerberos-protected NFS requires working DNS, time synchronization, service principals, keytabs, and client configuration. Treat it as an identity project, not as a one-line export change.

## Storage layout

Dedicated NFS servers should make the exported storage obvious:

- Put shared data under a small number of intentional paths such as `/srv/nfs`, `/exports`, or `/data`.
- Mount export backing filesystems explicitly in `/etc/fstab` or the local storage manager.
- Keep operating system filesystems separate from data filesystems.
- Monitor both block usage and inode usage.
- Use labels, UUIDs, or stable storage device names rather than volatile `/dev/sdX` names.
- Document whether snapshots, quotas, compression, or replication are active.

Before growing, shrinking, or replacing storage, list the layers:

```bash
lsblk -f
findmnt /srv/nfs
df -hT /srv/nfs
df -ih /srv/nfs
sudo lvs 2>/dev/null || true
sudo zpool status 2>/dev/null || true
sudo btrfs filesystem usage /srv/nfs 2>/dev/null || true
```

Do not resize or repair filesystems during an incident unless you understand the storage stack and have a recovery path.

## Network and performance boundaries

NFS performance depends on server disks, server CPU, network path, client mount options, and application access patterns. A dedicated server helps only if you can observe those boundaries.

Useful read-only checks include:

```bash
nfsstat -s
nfsiostat 1 5
sar -n DEV 1 5
iostat -xz 1 5
ss -tan state established '( sport = :2049 )'
```

Some commands may require packages such as `nfs-utils` or `sysstat`. Install tools during normal maintenance, not during the first minute of an outage.

Look for patterns:

- High disk wait suggests storage pressure.
- High retransmits suggest network loss, congestion, or overloaded clients.
- Many small metadata operations may point to application behavior rather than raw throughput.
- One client can consume server capacity for everyone else.

## Availability and maintenance

Clients often treat NFS as local storage. A server restart can freeze shells, builds, application processes, and batch jobs. Plan maintenance as a shared-service event.

Before planned work:

1. Identify mounted clients from monitoring, `ss`, logs, or client inventory.
2. Confirm backups or snapshots are current.
3. Announce the maintenance window and expected client behavior.
4. Reapply exports in a controlled shell before restarting the service:

   ```bash
   sudo exportfs -ra -v
   ```

5. Restart or reload in a controlled window.
6. Confirm clients can remount and read expected data.

For high-availability NFS, test failover with real clients before calling the service redundant. Shared storage, virtual IPs, locking behavior, DNS TTLs, and client mount options all affect whether failover is clean or merely theoretical.

## Backup and restore

RAID, replication, and snapshots are not backups by themselves. A dedicated NFS server needs a restore story:

- Back up the data and the export configuration.
- Keep at least one backup independent of the NFS server.
- Test restores to a separate path or test host.
- Record file ownership and ACL behavior after restore.
- Confirm that snapshots cannot be modified or deleted by normal NFS clients.

For a restore drill, pick a small directory and verify:

```bash
stat restored-file
getfacl restored-file 2>/dev/null || true
sha256sum restored-file
```

The important result is not only that bytes came back. Ownership, permissions, ACLs, and timestamps often matter just as much.

## Troubleshooting dedicated servers

When clients report an NFS outage, separate the problem into layers:

- **Name resolution:** Can clients resolve the server name to the expected address?
- **Network path:** Can clients reach TCP port 2049?
- **Server process:** Is the NFS service running and exporting the expected paths?
- **Storage:** Is the backing filesystem mounted, writable if required, and not full?
- **Identity:** Do user and group IDs map to the expected owners?
- **Client mount:** Are clients using the intended NFS version and mount options?
- **Application behavior:** Is the application creating too many small files or lock-heavy workloads?

Start with evidence:

```bash
sudo journalctl -u nfs-server -u nfs-kernel-server --since -30min --no-pager
exportfs -v
nfsstat -s
df -hT
df -ih
```

Then compare with one affected client:

```bash
mount | grep ' type nfs'
nfsstat -m
id
ls -ld /mount/point
```

Avoid changing exports, disabling firewalls, or rebooting the server until you know which layer is failing.

## Hands-on practice

Use two disposable Linux VMs or containers with systemd support if possible.

1. On the server, create `/srv/nfs/lab` and one test file.
2. Export it read-only to a specific lab client, not to `*`.
3. Run `sudo exportfs -ra -v` and capture the resulting export.
4. From the client, mount the export read-only and read the test file.
5. Try to write a file from the client and confirm that the write fails.
6. On the server, inspect `nfsstat -s`, `ss`, `df -hT`, and the service journal.
7. Unmount the client and remove the lab export.

Keep a short lab note with the export line, mount command, verification output, and cleanup steps.
