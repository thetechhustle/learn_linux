### 21.8 Automatic Mounting

!!! abstract "What you will learn"
    - Explain why NFS mounts are often better handled on demand instead of mounted permanently at boot.
    - Compare systemd automount units and `autofs`.
    - Configure an NFS automount safely in a lab.
    - Verify when a mount is idle, active, mounted, or waiting for the server.

!!! example "Field story"
    A group of developers uses an NFS share for build artifacts. When the NFS server is offline during a reboot, several workstations pause during startup because the share is listed as a normal boot-time mount. The fix is not to stop using NFS. The fix is to mount it when someone accesses the path and let the machine boot normally when the share is unavailable.

!!! success "Operator principle"
    Automounting turns a network dependency into an on-demand dependency. That makes startup safer, but you still need clear timeout, ownership, and failure behavior.

## Why automount NFS?

Traditional static mounts in `/etc/fstab` are simple, but network filesystems are not always available when a machine boots. A static NFS mount can cause problems when:

- the NFS server is down
- DNS is not ready yet
- the client boots before the network is fully online
- a laptop moves between networks
- a rarely used share stays mounted for no reason

Automatic mounting delays the mount until a process accesses the mount path. After a period of inactivity, the mount can be released.

This is useful for:

- home directories hosted over NFS
- shared build artifacts
- read-only software repositories
- archival or infrequently used exports
- lab shares that should not slow every boot

## Two common approaches

Linux commonly uses one of two approaches:

- `systemd` automount units, often configured through `/etc/fstab`
- `autofs`, a dedicated automount daemon with map files

Both can work. Choose based on local standard and operational needs.

Use `systemd` automounts when:

- you want a simple path in `/etc/fstab`
- you already manage mounts with systemd
- you need one or a few predictable mount points

Use `autofs` when:

- you need many dynamic mounts
- you need wildcard maps
- you want mature automount behavior across many Unix-like environments
- your organization already manages `auto.master` maps

## Inspect current mounts

Before changing anything, inspect the current state:

```console
$ findmnt -t nfs,nfs4
$ systemctl list-units --type=automount
$ mount | grep -E ' type nfs| type nfs4'
```

If `autofs` is installed, check it too:

```console
$ systemctl status autofs
$ automount -m
```

The `automount -m` command prints the active autofs maps on many systems. It is a useful way to confirm what the daemon thinks it should manage.

## Option 1: systemd automount through `/etc/fstab`

Here is an example `/etc/fstab` entry:

```fstab
nfs-server.example.com:/srv/share  /mnt/share  nfs4  rw,noauto,x-systemd.automount,_netdev,timeo=14  0  0
```

Important options:

- `noauto`: do not mount immediately at boot with normal mount processing
- `x-systemd.automount`: create an automount unit for on-demand mounting
- `_netdev`: mark the mount as network-dependent
- `timeo=14`: set an NFS timeout value, expressed in tenths of a second for NFS

Create the mount point:

```console
$ sudo mkdir -p /mnt/share
```

Reload systemd and start the automount unit:

```console
$ sudo systemctl daemon-reload
$ sudo systemctl restart remote-fs.target
```

Access the path:

```console
$ ls /mnt/share
```

Then inspect what happened:

```console
$ findmnt /mnt/share
$ systemctl status mnt-share.automount
$ systemctl status mnt-share.mount
```

Systemd derives unit names from paths. `/mnt/share` becomes `mnt-share.automount` and `mnt-share.mount`.

!!! warning "Be careful with boot-critical paths"
    Do not experiment with automounting core paths such as `/usr`, `/var`, or application data directories on a production host. Use a lab path like `/mnt/share` first.

## Option 2: `autofs`

Install `autofs` with your distribution's package manager:

```console
$ sudo apt install autofs
```

On Fedora-family systems:

```console
$ sudo dnf install autofs
```

Create a master map entry. Depending on the distribution, this may go in `/etc/auto.master` or a file under `/etc/auto.master.d/`.

Example:

```text
/mnt/nfs  /etc/auto.nfs  --timeout=60
```

Create `/etc/auto.nfs`:

```text
share  -fstype=nfs4,rw,soft,timeo=14  nfs-server.example.com:/srv/share
```

This means the export will appear at:

```text
/mnt/nfs/share
```

Restart `autofs`:

```console
$ sudo systemctl restart autofs
```

Access the path:

```console
$ ls /mnt/nfs/share
```

Verify:

```console
$ findmnt /mnt/nfs/share
$ automount -m
$ systemctl status autofs
```

!!! note "Direct and indirect maps"
    The example above is an indirect map: `autofs` manages names under `/mnt/nfs`. Direct maps can manage exact paths, but indirect maps are easier to learn and safer for labs.

## Hard, soft, and timeout behavior

NFS mount options control what happens when the server is slow or unavailable.

`hard` mounts keep retrying NFS operations. This protects data integrity for many workloads, but stuck operations can look like hung processes.

`soft` mounts eventually return an error. This can be useful for read-mostly or noncritical shares, but it can also surprise applications that expect filesystem operations to complete reliably.

There is no universal answer. Choose based on the data and workload:

- Use conservative settings for important writable data.
- Use more failure-tolerant settings for disposable caches or read-only convenience shares.
- Document the behavior so application owners know what to expect.

## Troubleshooting automounts

If access to the path hangs or fails, check these in order:

1. Confirm the path and unit:

   ```console
   $ findmnt /mnt/share
   $ systemctl status mnt-share.automount
   $ systemctl status mnt-share.mount
   ```

2. Confirm the NFS server is reachable:

   ```console
   $ getent hosts nfs-server.example.com
   $ ping -c 3 nfs-server.example.com
   $ nc -vz nfs-server.example.com 2049
   ```

3. Confirm the server export:

   ```console
   $ showmount -e nfs-server.example.com
   ```

   `showmount` is most useful for NFSv3-era export discovery. Some NFSv4-only environments may restrict or avoid it.

4. Check logs:

   ```console
   $ journalctl -u autofs --since -30m
   $ journalctl -b | grep -i nfs
   ```

5. Compare mount options:

   ```console
   $ findmnt -no OPTIONS /mnt/share
   ```

## Cleanup in a lab

For a systemd automount lab:

```console
$ sudo systemctl stop mnt-share.automount
$ sudo systemctl stop mnt-share.mount
```

Then remove or comment the test line in `/etc/fstab` and reload:

```console
$ sudo systemctl daemon-reload
```

For an `autofs` lab, remove or comment the test map entries and restart:

```console
$ sudo systemctl restart autofs
```

## Hands-on practice

Use a disposable lab VM or a nonproduction NFS client.

1. Create a test mount point such as `/mnt/share`.
2. Add a systemd automount entry in `/etc/fstab` for a test NFS export.
3. Run `sudo systemctl daemon-reload`.
4. Access the directory with `ls /mnt/share`.
5. Confirm the mount appeared with `findmnt /mnt/share`.
6. Stop accessing it, wait, and inspect the automount and mount units.
7. Remove the lab entry when finished.

If you do not have an NFS server, write the `/etc/fstab` line in a lab note and identify which options are responsible for on-demand mounting and network dependency.
