### 21.4 Client-Side NFS

An NFS server publishes a filesystem, but the client decides how that export becomes part of the local tree. Client-side NFS work is mostly about proving the server is reachable, choosing mount options that fit the workload, testing the mount safely, and making persistence changes without breaking boot.

!!! abstract "What you will learn"
    - Install and inspect the Linux NFS client components.
    - Mount an NFS export manually and verify the result.
    - Choose safer client mount options for read-only tests, background retries, and timeouts.
    - Add an NFS mount to `/etc/fstab` with validation before reboot.
    - Troubleshoot common client-side failures with command output instead of guesses.

!!! example "Field story"
    A build team stores release artifacts on `nfs01:/exports/builds`. A new CI worker needs access, but the worker must not hang during boot if the file server is unavailable. Your job is to verify the path, mount it with conservative options, and leave a rollback note for the next operator.

!!! success "Operator principle"
    Treat every NFS client mount as a contract between network reachability, server exports, local mount options, UID/GID identity, and application expectations.

## Client packages and services

Most Linux systems need NFS client utilities before they can mount an export. Package names vary by distribution:

```bash
# Debian and Ubuntu
sudo apt install nfs-common

# Fedora, Rocky Linux, AlmaLinux, and RHEL-like systems
sudo dnf install nfs-utils
```

Before changing anything, collect basic evidence:

```bash
findmnt -t nfs,nfs4
mount -t nfs,nfs4
systemctl status remote-fs.target
rpcinfo -p nfs01.example.com
showmount -e nfs01.example.com
```

`findmnt` shows current mounted filesystems in a structured format. `showmount -e` can list exports from many NFS servers, but it depends on server-side services and policy; a missing list does not always prove NFS is down.

## Manual test mounts

Create a local mount point and test the export manually before editing persistent configuration:

```bash
sudo mkdir -p /mnt/builds
sudo mount -t nfs4 -o ro,vers=4.2 nfs01.example.com:/exports/builds /mnt/builds
findmnt /mnt/builds
ls -la /mnt/builds
```

Start with `ro` when you only need to inspect the share. A read-only test reduces the chance that a typo, wrong export, or identity mismatch damages shared data.

If the server supports only older NFS versions, you may need a different version option:

```bash
sudo mount -t nfs -o ro,vers=3 nfs01.example.com:/exports/builds /mnt/builds
```

Do not guess versions indefinitely. Check server documentation, export policy, firewall rules, and logs if both NFSv4 and NFSv3 fail.

## Important mount options

NFS mount options change failure behavior. Choose them deliberately:

| Option | Why it matters |
| --- | --- |
| `ro` | Mounts read-only; useful for first tests and reference data. |
| `rw` | Allows writes; use only after identity and permission checks pass. |
| `vers=4.2` | Requests a specific protocol version. Use the version your server supports and your estate standardizes on. |
| `hard` | Retries interrupted operations until the server returns. This is usually safer for data integrity. |
| `soft` | Allows some operations to fail after retries. This can avoid indefinite waits but can corrupt application assumptions. |
| `timeo=` and `retrans=` | Tune retry timing. Change only with a clear workload reason. |
| `_netdev` | Marks the mount as network-dependent for boot ordering. |
| `nofail` | Lets boot continue if the mount is unavailable. Useful for non-critical shares. |
| `x-systemd.automount` | Creates an on-demand systemd automount so boot is less likely to block on NFS. |

For general-purpose Linux clients, prefer `hard` over `soft` unless the application owner has explicitly accepted partial I/O failures. `soft` mounts can turn a temporary network interruption into confusing application errors.

## Persistent mounts with fstab

After a manual mount works, add the mount to `/etc/fstab`. Keep a backup and validate before reboot:

```bash
sudo cp /etc/fstab /etc/fstab.$(date +%Y%m%d%H%M).bak
sudoedit /etc/fstab
```

Example entry for a non-critical artifact share:

```fstab
nfs01.example.com:/exports/builds  /mnt/builds  nfs4  ro,vers=4.2,hard,_netdev,nofail,x-systemd.automount  0  0
```

Then test the file without rebooting:

```bash
sudo systemctl daemon-reload
sudo mount -a
findmnt /mnt/builds
systemctl status mnt-builds.automount
```

If `mount -a` fails, do not reboot until you understand the error. Restore the backup or comment out the new line if needed.

## Verify permissions and identity

A successful mount does not prove users can work with files. NFS permissions usually depend on numeric UIDs and GIDs, with NFSv4 adding domain and identity-mapping concerns.

Use low-risk checks:

```bash
id
stat -c '%u:%g %A %n' /mnt/builds
ls -ln /mnt/builds | head
touch /mnt/builds/.client-write-test
rm /mnt/builds/.client-write-test
```

Run the write test only on a scratch path or with explicit permission. If files appear owned by `nobody`, `nfsnobody`, or unexpected numeric IDs, investigate identity mapping before changing permissions recursively.

## Troubleshooting client-side failures

Use the error message to choose the next check:

| Symptom | Likely area | Useful evidence |
| --- | --- | --- |
| `No route to host` or timeout | Network path or firewall | `ping`, `traceroute`, `nc -vz nfs01 2049`, firewall logs |
| `access denied by server` | Export policy or client address | `showmount -e`, server `/etc/exports`, server logs |
| `mount.nfs: Protocol not supported` | NFS version mismatch or missing client support | `modinfo nfs`, `rpcinfo -p`, explicit `vers=` test |
| Mounted but empty or wrong data | Wrong export path or bind mount | `findmnt`, server export config, `df -hT /mnt/builds` |
| Files owned by unexpected IDs | UID/GID or NFSv4 identity mapping | `id`, `ls -ln`, `/etc/idmapd.conf`, domain setting |
| Commands hang during outage | Mount retry behavior | `findmnt -o OPTIONS`, review `hard`, `soft`, `timeo`, automount choices |

Kernel and system logs often have the best client-side clues:

```bash
journalctl -k -g nfs --since -30m
journalctl -u remote-fs.target --since -30m
dmesg | tail -50
```

## Safe unmounting

Unmount only after checking active users and processes:

```bash
findmnt /mnt/builds
fuser -vm /mnt/builds
sudo umount /mnt/builds
```

If the server disappeared and the mount is stuck, document the impact before escalating to lazy or forced unmounts. `umount -l` detaches the mount from the namespace but can hide still-pending I/O from operators who are not expecting it.

## Hands-on practice

Use a disposable lab client and a known test export.

1. Install the NFS client package for your distribution.
2. Use `showmount -e` or server documentation to identify one export.
3. Create `/mnt/nfs-lab` and mount the export read-only with an explicit NFS version.
4. Record `findmnt /mnt/nfs-lab`, `df -hT /mnt/nfs-lab`, and `ls -ln /mnt/nfs-lab`.
5. Add a temporary `/etc/fstab` entry with `ro,_netdev,nofail,x-systemd.automount`.
6. Run `sudo mount -a`, verify the mount, then remove the lab entry and unmount the share.
