### 04.4 Interactive Monitoring with `top`

`top` is a live process monitor. It is useful when a static `ps` snapshot is not
enough and you need to watch CPU, memory, load, and process behavior change over
time.

!!! abstract "What you will learn"
    - Read the main system and process fields shown by `top`.
    - Sort, filter, and inspect processes without making changes.
    - Know which interactive commands are safe for observation and which can
      change the system.

!!! example "Field story"
    An API server is slow during a traffic spike. `ps` showed a few likely
    workers, but you need to see whether CPU pressure is sustained, whether
    memory is growing, and whether load is improving or worsening.

!!! success "Operator principle"
    Use `top` first as an observation tool. Treat interactive actions like kill
    and renice as changes that require evidence and rollback thinking.

## Start `top`

Run:

```bash
top
```

The display has two main parts:

- a system summary at the top
- a process table below it

The values refresh every few seconds. That makes `top` good for watching trends,
but it also means the screen can change while you are trying to reason about it.
Pause and capture notes before acting.

## Read the system summary

The summary usually includes:

- **load average**: runnable or waiting work over recent time windows.
- **task counts**: running, sleeping, stopped, and zombie processes.
- **CPU percentages**: user time, system time, idle time, I/O wait, and other
  categories.
- **memory and swap**: total, free, used, and cache/buffer values.

High CPU is not automatically bad. High I/O wait, growing swap use, or a load
average far above available CPU count may point to a different bottleneck than
the loudest process row.

## Read the process table

Common columns:

- `PID`: process ID.
- `USER`: process owner.
- `PR`: scheduler priority.
- `NI`: nice value.
- `VIRT`: virtual address space.
- `RES`: resident memory currently in RAM.
- `SHR`: shared memory.
- `S`: process state.
- `%CPU`: current CPU share.
- `%MEM`: current memory share.
- `TIME+`: accumulated CPU time.
- `COMMAND`: command name or command line.

Use these fields together. A process with high `TIME+` may simply be old. A
process with high `%CPU` for one refresh may be normal. A process whose `RES`
keeps growing may deserve closer inspection.

## Useful observation keys

These keys help you inspect without changing the system:

- `P`: sort by CPU.
- `M`: sort by memory.
- `T`: sort by accumulated CPU time.
- `c`: toggle command name versus full command line.
- `1`: show per-CPU summary lines.
- `H`: toggle threads, if supported.
- `/`: search for a process name, if supported.
- `q`: quit.

Support varies by implementation. If a key does not work, check `h` for help on
that host.

## Keys that change the system

`top` can do more than observe:

- `k`: send a signal to a process.
- `r`: renice a process.

Do not use these as reflexes. Before killing or renicing from `top`, capture the
PID, command, owner, parent process, state, CPU, memory, elapsed runtime, and the
reason a graceful service-manager action is not better.

In many incidents, the safer path is to leave `top`, inspect the process with
`ps`, check the service manager, and use the service's normal stop or restart
path.

## Batch mode for notes

Interactive screens are hard to paste into incident notes. Batch mode captures a
snapshot:

```bash
top -b -n 1 | head -40
top -b -n 3 -d 2 | head -80
```

The first command captures one snapshot. The second captures three snapshots two
seconds apart. This is often better evidence than a vague note like "top looked
bad."

## Investigation pattern

1. Open `top` and sort by CPU with `P`.
2. Watch at least two refreshes.
3. Sort by memory with `M`.
4. Toggle the full command line with `c`.
5. Record the top suspect's PID, owner, state, CPU, memory, and command.
6. Leave `top` and verify with `ps`.
7. Check whether a service manager owns the process.
8. Decide whether observation, restart, renice, or escalation is appropriate.

## Read-only practice

Run these on a lab system:

```bash
top -b -n 1 | head -40
top -b -n 3 -d 2 | head -80
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -10
```

Then open interactive `top` and practice only observation keys:

- sort by CPU
- sort by memory
- show full command lines
- quit cleanly

Do not use `k` or `r` during this practice.

- What is the difference between `%CPU`, `TIME+`, and elapsed runtime?
- Why might high load with high I/O wait point away from a CPU-only problem?
- What evidence should you collect before using `k` or `r` inside `top`?
