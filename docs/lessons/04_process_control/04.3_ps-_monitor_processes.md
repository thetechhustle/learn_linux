### 04.3 `ps`: Monitor Processes

`ps` gives you a point-in-time process snapshot. It does not continuously watch
the system, and it does not explain everything by itself, but it is one of the
fastest ways to answer the first incident question: "What is running right now?"

!!! abstract "What you will learn"
    - Use `ps` to inspect process identity, parentage, state, CPU, memory, and
      command lines.
    - Choose output fields that support an operational question.
    - Avoid common mistakes such as treating one snapshot as a full diagnosis.

!!! example "Field story"
    An API server is slow after a deploy. `top` shows CPU pressure, but the
    process names are similar. You use `ps` to identify the exact PID, owner,
    parent, elapsed runtime, and command before deciding what to restart.

!!! success "Operator principle"
    Start with a clear question, then make `ps` show only the fields needed to
    answer it.

## Basic snapshot

Running `ps` with no options shows processes attached to your current terminal.

```bash
ps
```

Common columns include:

- `PID`: process ID.
- `TTY`: controlling terminal.
- `TIME`: accumulated CPU time, not wall-clock runtime.
- `CMD`: command name.

This default view is intentionally small. It is useful for shell-local work, but
it is not enough for service incidents.

## All processes

Use `-e` to include every process, then select the fields you care about with
`-o`.

```bash
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd
```

Useful fields include:

- `pid`: process ID.
- `ppid`: parent process ID.
- `user`: effective user.
- `stat`: process state and flags.
- `%cpu`: recent CPU usage estimate.
- `%mem`: resident memory percentage.
- `etime`: elapsed wall-clock time since the process started.
- `cmd`: command with arguments.

Prefer explicit fields over memorizing one "perfect" `ps` command. The right
output depends on the question.

## Sort for pressure

To find likely CPU or memory suspects, sort the snapshot:

```bash
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -10
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%mem | head -10
```

These commands show candidates, not verdicts. CPU and memory usage can change
quickly, and the top process may be doing legitimate work. Take more than one
sample before acting.

## Filter the view

Common filters:

```bash
ps -p 1 -o pid,ppid,user,stat,etime,cmd
ps -u root -o pid,ppid,user,stat,etime,cmd | head
pgrep -a sshd || true
```

Use filters when you already have a hypothesis: a PID, a user, a service name,
or a command pattern.

## Understand `STAT`

The `STAT` column is compact but important.

- `R`: running or runnable.
- `S`: sleeping.
- `D`: uninterruptible sleep, often kernel I/O.
- `T`: stopped or traced.
- `Z`: zombie.
- `s`: session leader.
- `l`: multithreaded.
- `+`: in the foreground process group.

Do not overreact to one state letter. A sleeping daemon can be healthy. A short
CPU spike can be normal. A persistent `D` state or growing zombie count deserves
closer inspection.

## Process tree

Parent-child relationships help you avoid killing the wrong thing.

```bash
ps -ef --forest
```

If `--forest` is unavailable on your platform, fall back to explicit parent
fields:

```bash
ps -eo pid,ppid,user,stat,etime,cmd
```

In a service incident, look for the service manager, master process, worker
processes, and short-lived child commands.

## Safe investigation pattern

1. Capture a broad snapshot sorted by the suspected pressure type.
2. Capture a second snapshot after a short wait.
3. Filter to the suspect PID or service.
4. Note PID, PPID, user, state, CPU, memory, elapsed time, and command.
5. Check whether a service manager owns the process before killing anything.
6. Include the `ps` command and output in your incident note.

## Read-only practice

Run these on a lab system:

```bash
ps
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -10
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%mem | head -10
ps -ef --forest | head -30
ps -p 1 -o pid,ppid,user,stat,etime,cmd
```

Pick one process from the output and write down:

- what started it, based on `PPID` or the tree view
- who owns it
- how long it has been running
- whether its current state looks normal
- what you would inspect next before changing it
