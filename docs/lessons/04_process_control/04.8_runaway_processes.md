### 04.8 Runaway Processes

Runaway processes are processes that keep consuming CPU, memory, file descriptors, disk I/O, or child-process slots after they should have settled down. The fix is not always to kill the busiest PID. A good operator first proves what is happening, identifies whether the process is doing useful work, and chooses the least disruptive action that restores service.

!!! abstract "What you will learn"
    - Identify processes that are consuming abnormal CPU, memory, or process-tree resources.
    - Build a short evidence trail with `ps`, `top`, `/proc`, logs, and service status.
    - Escalate from observation to `renice`, `systemctl restart`, `kill`, and `kill -9` safely.
    - Explain the difference between a busy process, a stuck process, and a process that must be terminated.

!!! example "Field story"
    An API server starts timing out. Load average is high, one worker is using a full CPU core, and the service owner is asking whether you can just kill it. Your job is to capture enough evidence to decide whether the process is legitimately busy, looping, wedged on I/O, leaking memory, or safe to restart.

!!! success "Operator principle"
    Preserve evidence before terminating the process; after it exits, the best clues may be gone.

## Start With System Impact

Use a few read-only commands to confirm whether this is a system problem, a service problem, or a single noisy process.

```bash
uptime
free -h
ps -eo pid,ppid,user,stat,ni,pcpu,pmem,etime,comm --sort=-pcpu | head
ps -eo pid,ppid,user,stat,ni,pcpu,pmem,etime,comm --sort=-pmem | head
```

Useful signals:

- High CPU with normal memory often points to a loop, compression job, build, query, or compute-heavy worker.
- High memory growth over time may indicate a leak, cache pressure, or a workload that needs more capacity.
- Many processes with the same parent can indicate a fork storm or an overloaded supervisor.
- `STAT` values such as `D`, `R`, `S`, `T`, and `Z` help distinguish running, sleeping, stopped, uninterruptible, and zombie processes.

If the host is production, save the command output in your incident notes before you change anything.

## Inspect the Candidate Process

After you have a PID, collect enough context to understand what it is and who owns it.

```bash
PID=1234
ps -fp "$PID"
ps -o pid,ppid,user,stat,ni,pcpu,pmem,etime,args -p "$PID"
pstree -asp "$PID"
sudo ls -l /proc/"$PID"/fd | head
sudo tr '\0' ' ' < /proc/"$PID"/cmdline; echo
```

Then connect the process to its service, logs, and recent changes:

```bash
systemctl status --no-pager <service>
journalctl -u <service> --since "15 minutes ago" --no-pager
```

Ask these questions before acting:

- Is this process part of a managed service, an interactive user session, a batch job, or a container?
- Is it still making progress, or is it repeating the same work?
- Would killing only this PID leave stale locks, partial writes, orphaned children, or customer-facing errors?
- Is there a service owner or runbook that defines the normal restart path?

## Choose the Least Disruptive Response

Prefer responses that preserve data and let the service clean up.

| Situation | Safer first action | Escalation |
| --- | --- | --- |
| Process is busy but useful | Observe, notify owner, or lower priority with `renice` | Restart during a maintenance window |
| Service worker is wedged | Use the service manager if available: `systemctl restart <service>` | Terminate only the bad worker if the service supports it |
| Process ignores normal shutdown | Send `SIGTERM` with `kill <pid>` | Wait briefly, then consider `SIGKILL` |
| Fork storm or runaway children | Stop or restart the parent service | Use cgroups/service controls or targeted kills |
| Zombie process | Restart or fix the parent process that failed to reap it | Killing the zombie itself will not work |
| Uninterruptible `D` state | Investigate storage, NFS, driver, or kernel wait | Avoid repeated `kill -9`; it often cannot exit until the kernel wait clears |

`kill -9` sends `SIGKILL`. It does not let the process flush buffers, remove locks, close network sessions cleanly, or write a useful shutdown log. Use it as an escalation, not as the default.

## Practical Signal Sequence

For a standalone lab process or a process whose owner has approved termination:

```bash
kill "$PID"
sleep 5
ps -p "$PID" -o pid,stat,etime,args
kill -9 "$PID"
```

For managed services, prefer service-aware commands:

```bash
sudo systemctl restart <service>
systemctl status --no-pager <service>
journalctl -u <service> --since "5 minutes ago" --no-pager
```

This gives the supervisor a chance to stop, start, track, and log the process correctly.

## Hands-on Practice

Run this only in a disposable shell on a lab machine.

1. Start a CPU-heavy process:

    ```bash
    yes > /dev/null &
    PID=$!
    ```

2. Capture evidence:

    ```bash
    ps -o pid,ppid,user,stat,ni,pcpu,pmem,etime,args -p "$PID"
    top -b -n 1 -p "$PID"
    ```

3. Reduce its scheduling priority instead of killing it immediately:

    ```bash
    renice 10 -p "$PID"
    ps -o pid,ni,pcpu,etime,args -p "$PID"
    ```

4. Terminate it cleanly and verify that it exited:

    ```bash
    kill "$PID"
    sleep 2
    ps -p "$PID" || echo "process exited"
    ```

5. If it is still present in your lab, escalate:

    ```bash
    kill -9 "$PID"
    ```

Write a short note with the PID, evidence, action, verification, and what you would tell a service owner.
