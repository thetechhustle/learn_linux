### 04.6 The `/proc` Filesystem: Inspect Kernel and Process Truth

`/proc` is a live view into the kernel. It looks like a filesystem, but most
entries are generated on demand from current kernel state. Operators use it when
normal tools are too summarized and they need direct evidence about a process,
memory pressure, CPU layout, mounts, kernel parameters, or file descriptors.

Treat `/proc` as evidence, not as a scrapbook. The values can change while you
are reading them, process directories disappear when processes exit, and some
files are writable knobs that can change system behavior immediately.

!!! abstract "What you will learn"
    - Explain why `/proc` is a pseudo-filesystem rather than ordinary disk data.
    - Inspect process command lines, status, limits, open files, and file descriptors.
    - Use system-wide `/proc` files to confirm CPU, memory, mount, and uptime facts.
    - Avoid unsafe writes under `/proc/sys` during incident response.

!!! success "Operator principle"
    Prefer read-only `/proc` inspection first. Write to `/proc` only when you know
    the exact kernel knob, the blast radius, and the rollback command.

## Why `/proc` Matters

Many familiar commands read from `/proc`:

- `ps` reads process metadata.
- `top` and `uptime` read load and CPU accounting.
- `free` reads memory counters.
- `mount` and `findmnt` can use mount information exposed by the kernel.

Using those tools is usually better for routine work because they parse and
format the data for you. Reading `/proc` directly is useful when you need to
verify what those tools are seeing, inspect a detail the tool hides, or capture
raw evidence for a handoff.

## Process Directories

Every running process has a directory named after its PID:

```bash
ls /proc/1
```

Start with read-only files that explain what the process is and how it is
running:

```bash
pid=1

tr '\0' ' ' < "/proc/$pid/cmdline"
cat "/proc/$pid/status"
cat "/proc/$pid/limits"
readlink "/proc/$pid/exe"
readlink "/proc/$pid/cwd"
```

Important entries include:

- `cmdline`: the command and arguments, separated by null bytes.
- `status`: human-readable state, IDs, memory counters, signal masks, and thread count.
- `limits`: resource limits such as maximum open files and process count.
- `exe`: symlink to the executable.
- `cwd`: symlink to the process working directory.
- `fd/`: symlinks for open file descriptors.
- `environ`: environment variables, often permission-restricted and sensitive.

Do not paste `environ` into tickets or chat by default. It can contain tokens,
database URLs, API keys, and session secrets.

## Open File Descriptors

When a service cannot rotate logs, delete files do not free disk space, or a
process appears to hold a socket open, inspect its file descriptors:

```bash
pid=1234

ls -l "/proc/$pid/fd" | head
readlink -f "/proc/$pid/fd/1"
readlink -f "/proc/$pid/fd/2"
```

Useful patterns:

- `socket:[12345]` means the descriptor is a socket; use `ss -p` when available
  to connect it back to network details.
- A path ending in `(deleted)` means the process still has an unlinked file open.
  Disk space may not return until that descriptor closes or the process restarts.
- Descriptor `0`, `1`, and `2` are standard input, output, and error.

Prefer `lsof -p "$pid"` when it is installed. Use `/proc/$pid/fd` as the direct
fallback when you need the kernel view.

## System-Wide Evidence

System-level `/proc` files answer quick questions without changing state:

```bash
cat /proc/uptime
cat /proc/loadavg
grep -E '^(MemTotal|MemAvailable|SwapTotal|SwapFree):' /proc/meminfo
grep -E '^(processor|model name|cpu cores)' /proc/cpuinfo | head -20
cat /proc/mounts | head
```

Read these as current snapshots:

- `/proc/uptime`: system uptime and idle time.
- `/proc/loadavg`: recent load averages and runnable process counts.
- `/proc/meminfo`: memory and swap counters.
- `/proc/cpuinfo`: CPU inventory and features.
- `/proc/mounts`: currently mounted filesystems.

For scripted checks, prefer tools with stable output formats when available:
`findmnt --json`, `ps -o`, `free -b`, `ss -H`, and similar commands are often
easier to parse safely than raw text under `/proc`.

## Writable Kernel Knobs

Some `/proc` paths are writable, especially under `/proc/sys`:

```bash
sysctl net.ipv4.ip_forward
cat /proc/sys/net/ipv4/ip_forward
```

These two commands read the same kind of kernel setting. Operators usually use
`sysctl` because it is clearer and supports persistent configuration through
files such as `/etc/sysctl.conf` or `/etc/sysctl.d/*.conf`.

Do not experiment with writes like this on a shared host:

```bash
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward
```

That command changes live networking behavior. Before writing a kernel knob,
confirm the exact setting, capture the old value, know whether the change is
temporary or persistent, and have the rollback ready.

## Incident Pattern

When investigating a suspicious process:

1. Identify the PID with `ps`, `top`, `pgrep`, or service tooling.
2. Capture the command line and executable:

    ```bash
    pid=1234
    tr '\0' ' ' < "/proc/$pid/cmdline"
    readlink "/proc/$pid/exe"
    ```

3. Check ownership, state, threads, and memory:

    ```bash
    grep -E '^(Name|State|Uid|Gid|VmRSS|Threads|voluntary_ctxt_switches|nonvoluntary_ctxt_switches):' "/proc/$pid/status"
    ```

4. Inspect open files and sockets:

    ```bash
    ls -l "/proc/$pid/fd" | head -30
    ss -tpn 2>/dev/null | grep "pid=$pid" || true
    ```

5. Use service-specific logs or `journalctl` to connect the raw evidence to user
   impact before changing anything.

If the process exits during the investigation, `/proc/$pid` disappears. That is
evidence too: record that the process was short-lived or restarted.

## Hands-On Practice

Run these commands on a lab machine or disposable VM:

```bash
sleep 300 &
pid=$!

tr '\0' ' ' < "/proc/$pid/cmdline"
grep -E '^(Name|State|Pid|PPid|Uid|VmRSS|Threads):' "/proc/$pid/status"
ls -l "/proc/$pid/fd"
readlink "/proc/$pid/exe"

kill "$pid"
```

Then inspect system-wide files:

```bash
cat /proc/uptime
cat /proc/loadavg
grep -E '^(MemTotal|MemAvailable):' /proc/meminfo
```

Write a short note answering:

- Which `/proc/$pid` entries proved what command was running?
- Which entries were symlinks instead of regular files?
- What changed after the process was killed?
