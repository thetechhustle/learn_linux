### 04.1 Components of a Process

A process is a running program plus the operating-system state needed to manage
it. When a service is slow, stuck, noisy, or unsafe to restart, you need to know
which process you are looking at before you change anything.

!!! abstract "What you will learn"
    - Identify the core parts of a Linux process: PID, parent, owner, state,
      command, environment, memory, file descriptors, and signals.
    - Use read-only commands to inspect process evidence before acting.
    - Explain why killing a process is rarely the first move in an incident.

!!! example "Field story"
    An API server starts timing out. One process is consuming CPU, but several
    worker processes have similar names. Your job is to identify the exact
    process, understand what it owns, and decide whether to observe, restart,
    renice, or escalate.

!!! success "Operator principle"
    Collect process evidence before killing, renicing, or restarting anything.

## Process identity

Every Linux process has identifiers that let the kernel, tools, and operators
refer to it.

- **PID**: the process ID. This is unique while the process is alive, but PIDs
  are reused after processes exit.
- **PPID**: the parent process ID. This shows which process started or adopted
  the process.
- **UID/GID**: the user and group identity the process runs as. This affects
  file access, signal permissions, and blast radius.
- **Command and arguments**: the executable plus the arguments used to start it.
- **Start time**: useful for distinguishing a long-running service from a newly
  restarted one with the same name.

Inspect these with:

```bash
ps -eo pid,ppid,user,stat,lstart,cmd | head
ps -p 1 -o pid,ppid,user,stat,lstart,cmd
```

## Process state

Process state tells you what the kernel currently knows about the process.
Common states include:

- `R`: running or runnable.
- `S`: sleeping, usually waiting for I/O or a timer.
- `D`: uninterruptible sleep, often waiting on kernel I/O.
- `T`: stopped or traced.
- `Z`: zombie, meaning the process exited but its parent has not collected its
  status.

A single state snapshot is not enough for a conclusion. Compare state, CPU,
memory, and time over a short interval before deciding what is abnormal.

```bash
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%mem | head
```

## Memory, files, and environment

A process also has resources attached to it:

- **Memory mappings**: code, libraries, heap, stack, and mapped files.
- **Open file descriptors**: files, sockets, pipes, devices, and logs.
- **Working directory**: the directory the process treats as its current
  location.
- **Environment variables**: inherited configuration such as `PATH`, locale,
  service settings, or secrets.

On Linux, much of this is visible under `/proc/<pid>/`.

```bash
pid=1
ls -l /proc "$pid" 2>/dev/null || true
readlink "/proc/$pid/cwd" 2>/dev/null || true
ls -l "/proc/$pid/fd" 2>/dev/null | head
tr '\0' '\n' < "/proc/$pid/environ" 2>/dev/null | head
```

Be careful with environment output. It can contain secrets. Collect only what
you need, and avoid pasting full environments into tickets or public logs.

## Signals and control

Signals are one way operators and the kernel communicate with processes.

- `TERM` asks a process to shut down cleanly.
- `HUP` often asks daemons to reload configuration, depending on the program.
- `INT` is similar to pressing `Ctrl-C` in a terminal.
- `KILL` stops the process immediately and cannot be handled by the process.

`kill -9` sends `KILL`. It can be necessary, but it skips application cleanup,
can interrupt writes, and may hide the evidence you needed to understand the
failure. Prefer identifying the service manager and graceful stop path first.

```bash
kill -l
ps -p 1 -o pid,ppid,user,stat,cmd
```

## Investigation pattern

When a process looks suspicious:

1. Identify the exact PID and command.
2. Confirm owner, parent, runtime, and current state.
3. Check CPU and memory over time, not from one sample.
4. Inspect open files or sockets if they explain impact.
5. Find whether a service manager owns the process.
6. Choose the least disruptive action.
7. Record what you saw, what you changed, and how the system responded.

## Read-only practice

Run these on a lab machine or disposable VM:

```bash
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -10
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%mem | head -10
ps -p 1 -o pid,ppid,user,stat,lstart,cmd
pgrep -a sshd || true
kill -l | head
```

Pick one process you recognize and write down:

- PID and PPID
- owning user
- state
- command line
- elapsed runtime
- one reason it would be unsafe to kill it blindly
