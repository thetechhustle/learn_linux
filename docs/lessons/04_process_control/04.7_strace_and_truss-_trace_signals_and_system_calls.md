### 04.7 `strace` and `truss`: Trace System Calls and Signals

When a process is running but not doing what you expect, the problem is often at
the boundary between the program and the operating system. It may be trying to
open a missing file, waiting on a socket, receiving a signal, failing a
permission check, or looping through the same syscall over and over.

`strace` on Linux and `truss` on several Unix systems let you watch that boundary
directly. They show system calls, return values, errors, and signals. Used well,
they turn "the process is stuck" into a short evidence trail.

!!! abstract "What you will learn"
    - Explain what a system-call tracer can and cannot prove.
    - Trace a command from startup and attach to a running process.
    - Filter noisy output to files, networking, signals, and timing.
    - Capture trace evidence safely without leaking secrets or destabilizing production.

!!! warning "Production caution"
    Attaching a tracer can slow a process, expose sensitive arguments or paths,
    and may be blocked by kernel security settings. Use it deliberately, capture
    only what you need, and detach as soon as you have enough evidence.

## What Tracers Show

A process asks the kernel to do privileged work through system calls. Examples
include:

- `openat`: open a file.
- `read` and `write`: move bytes.
- `connect`, `accept`, `sendto`, and `recvfrom`: use the network.
- `stat`: inspect file metadata.
- `clone`, `fork`, and `execve`: create or replace processes.
- `wait4`: wait for a child process.

`strace` prints those calls with arguments and results:

```bash
strace -o /tmp/ls.trace ls /tmp
tail -20 /tmp/ls.trace
```

Look for failed calls such as:

```text
openat(AT_FDCWD, "/missing/config.yml", O_RDONLY) = -1 ENOENT (No such file or directory)
```

The important part is not just the syscall name. It is the path, return value,
and error code. `ENOENT`, `EACCES`, `ECONNREFUSED`, `ETIMEDOUT`, and `EPIPE`
usually explain more than a vague application error does.

## Start a Command Under Trace

Trace a command from the beginning when startup is the problem:

```bash
strace -f -o /tmp/app.trace ./start-app
```

Common options:

- `-f`: follow child processes.
- `-o FILE`: write output to a file instead of the terminal.
- `-s 200`: increase captured string length.
- `-tt`: include timestamps.
- `-T`: show time spent in each syscall.

A useful incident capture often starts like this:

```bash
strace -f -tt -T -s 200 -o /tmp/app.trace ./start-app
```

Do not commit trace files or paste them into public tickets without review. They
can contain file paths, command-line arguments, tokens, request fragments, and
customer data.

## Attach to a Running Process

Attach when the process is already stuck or misbehaving:

```bash
pid=1234
sudo strace -p "$pid" -tt -T -s 200 -o /tmp/process-"$pid".trace
```

Stop tracing with `Ctrl-C`. That detaches `strace`; it does not kill the traced
process.

Before attaching, collect basic evidence:

```bash
ps -p "$pid" -o pid,ppid,user,stat,%cpu,%mem,etime,cmd
readlink "/proc/$pid/exe"
tr '\0' ' ' < "/proc/$pid/cmdline"
```

Some Linux systems restrict attaching to processes you do not own. If attachment
fails with `Operation not permitted`, check ownership, container boundaries,
capabilities, and `kernel.yama.ptrace_scope` policy. Do not weaken host security
settings just to make a quick trace easier.

## Filter the Noise

Raw traces are noisy. Use filters when you already have a hypothesis:

```bash
strace -e trace=file ls /does/not/exist
strace -e trace=network curl -I https://example.com
strace -e trace=process ./start-app
strace -e signal=all -p "$pid"
```

Useful filters:

- `trace=file`: file opens, stats, and path lookups.
- `trace=network`: socket and network calls.
- `trace=process`: fork, clone, exec, and wait calls.
- `trace=%desc`: file descriptor operations.
- `signal=all`: signal delivery.

Timing helps identify waits:

```bash
strace -T -tt -p "$pid" -o /tmp/wait.trace
```

Repeated slow `connect`, `read`, `futex`, `poll`, or `epoll_wait` calls tell
different stories. A process waiting in `futex` may be blocked on thread
coordination. A process stuck in repeated `connect` calls may be chasing an
unreachable dependency.

## `truss` on Unix Systems

On Solaris, FreeBSD, and some other Unix systems, `truss` fills a similar role:

```bash
truss -o /tmp/ls.truss ls /tmp
truss -p 1234
```

The exact options and output differ by platform. The operating principle is the
same: follow the process at the system-call boundary, then connect syscall errors
and waits back to the user-visible symptom.

## Incident Pattern

Use this order during troubleshooting:

1. Define the symptom: startup failure, hang, missing file, permission error, or
   dependency timeout.
2. Identify the process or command path with `ps`, service tooling, and logs.
3. Choose a narrow trace:
   - startup issue: run the command under trace
   - stuck process: attach briefly
   - file issue: use `trace=file`
   - network issue: use `trace=network`
4. Capture to a file under `/tmp` or another controlled location.
5. Stop as soon as the trace shows the relevant error or wait.
6. Summarize the finding in plain English and include only the necessary trace
   lines.

Bad handoff:

```text
App is broken. strace attached.
```

Better handoff:

```text
Startup fails because the process tries to open /etc/example/config.yml and gets
ENOENT. Trace captured with strace -f -e trace=file; no service restart was done.
```

## Hands-On Practice

Run these on a lab machine:

```bash
strace -e trace=file -o /tmp/missing-file.trace ls /definitely-not-here
grep ENOENT /tmp/missing-file.trace | head
```

Then trace a harmless command with timing:

```bash
strace -tt -T -o /tmp/date.trace date
tail -20 /tmp/date.trace
```

If `strace` is unavailable, install it in a disposable lab environment or use the
platform equivalent. Do not install tools on a production host during an incident
without following the host's change process.
