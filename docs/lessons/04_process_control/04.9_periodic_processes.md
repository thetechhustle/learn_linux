### 04.9 Periodic Processes: Cron, Timers, and Scheduled Work

Periodic processes run because a schedule says they should. Backups, log
rotation, certificate renewal, report generation, cleanup jobs, and batch imports
all depend on this pattern. When scheduled work fails, the symptom often appears
somewhere else: stale data, full disks, expired certificates, missing reports, or
unexpected load at the top of the hour.

Operators need two skills: find what is scheduled, and prove whether it ran.

!!! abstract "What you will learn"
    - Identify user crontabs, system crontabs, cron directories, and systemd timers.
    - Read cron schedule syntax without guessing.
    - Verify recent execution through logs and timer metadata.
    - Troubleshoot common scheduled-job failures safely.

!!! success "Operator principle"
    A scheduled command is not verified just because it exists. Confirm the
    schedule, the user, the environment, the last run, and the result.

## Where Scheduled Work Lives

Linux systems commonly use both classic cron and systemd timers. You may see all
of these on the same host:

```bash
crontab -l
sudo crontab -l
ls -l /etc/cron.d /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly
cat /etc/crontab
systemctl list-timers --all
```

Key locations:

- User crontabs: per-user schedules edited with `crontab -e`.
- Root's crontab: root-owned schedule, inspected with `sudo crontab -l`.
- `/etc/crontab`: system crontab with an explicit user field.
- `/etc/cron.d/`: package or administrator-provided cron files.
- `/etc/cron.daily`, `/etc/cron.weekly`, `/etc/cron.monthly`: periodic script directories.
- systemd timers: timer units that trigger service units.

Do not assume a job runs as root. The execution user changes permissions,
environment, working directory, and file ownership.

## Cron Syntax

A normal user crontab has five schedule fields followed by the command:

```text
# minute hour day-of-month month day-of-week command
15 1 * * * /usr/local/bin/nightly-report
```

This runs at 01:15 every day.

Common examples:

```text
*/5 * * * * /usr/local/bin/check-queue
0 2 * * * /usr/local/bin/backup
30 3 * * 0 /usr/local/bin/weekly-maintenance
0 9 1 * * /usr/local/bin/monthly-report
```

Remember:

- `*` means every value.
- `*/5` means every five units.
- Day-of-week `0` and `7` both commonly mean Sunday.
- Cron usually uses the system timezone unless configured otherwise.
- Cron commands run with a minimal environment.

System crontabs such as `/etc/crontab` and files under `/etc/cron.d/` include a
user field:

```text
# minute hour dom month dow user command
15 1 * * * appuser /usr/local/bin/nightly-report
```

## systemd Timers

Modern Linux distributions often use systemd timers instead of cron for system
jobs:

```bash
systemctl list-timers --all
systemctl cat logrotate.timer
systemctl cat logrotate.service
systemctl status logrotate.timer
```

Timer output tells you the next run, last run, and the service unit triggered by
the timer. Use the service status and journal to inspect the result:

```bash
journalctl -u logrotate.service --since "24 hours ago"
```

Timers are easier to supervise than many cron jobs because each run maps to a
unit with status, logs, dependencies, and exit state.

## Proving a Job Ran

A job may be scheduled but never succeed. Check evidence in this order:

1. Confirm the schedule exists.
2. Confirm the intended user.
3. Confirm the command path exists and is executable.
4. Confirm recent logs.
5. Confirm the expected output or side effect.

Useful commands:

```bash
grep CRON /var/log/syslog 2>/dev/null | tail -50
journalctl -u cron --since "24 hours ago" 2>/dev/null
journalctl -u crond --since "24 hours ago" 2>/dev/null
systemctl list-timers --all
```

Log locations vary by distribution. Debian and Ubuntu commonly log cron activity
to `/var/log/syslog`; Red Hat-family systems often use `/var/log/cron` or
`journalctl -u crond`.

## Common Failure Modes

Scheduled jobs fail for predictable reasons:

- The command relies on `PATH` entries that are present in an interactive shell
  but missing in cron.
- The job assumes a working directory.
- The job writes to a path the scheduled user cannot access.
- Output is discarded, so errors are invisible.
- A previous run overlaps with the next run.
- The host was asleep or powered off.
- Timezone or daylight-saving assumptions are wrong.
- A script works manually but depends on interactive prompts or a TTY.

Make cron commands boring and explicit:

```text
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

15 1 * * * cd /srv/app && /usr/local/bin/nightly-report >> /var/log/nightly-report.log 2>&1
```

For important jobs, prefer a wrapper script with logging, locking, and clear exit
codes rather than a long one-line crontab command.

## Avoiding Overlap

A job scheduled every five minutes can pile up if one run takes longer than five
minutes. Use a lock:

```bash
flock -n /tmp/check-queue.lock /usr/local/bin/check-queue
```

In cron:

```text
*/5 * * * * flock -n /tmp/check-queue.lock /usr/local/bin/check-queue >> /var/log/check-queue.log 2>&1
```

With systemd timers, use service configuration and unit state to control overlap
instead of hand-rolled locking when possible.

## anacron and Missed Runs

Cron is time-specific. If a laptop or workstation is off at the scheduled time,
the job may be missed. `anacron` is designed for jobs that should run daily,
weekly, or monthly even if the machine was off at the exact scheduled time.

Inspect anacron configuration with:

```bash
cat /etc/anacrontab
ls -l /etc/cron.daily /etc/cron.weekly /etc/cron.monthly
```

Use anacron-style scheduling for maintenance that should happen eventually. Use
cron or systemd timers when exact timing matters.

## Hands-On Practice

On a lab machine, inspect schedules without changing them:

```bash
crontab -l 2>/dev/null || true
cat /etc/crontab 2>/dev/null || true
ls -l /etc/cron.d 2>/dev/null || true
systemctl list-timers --all 2>/dev/null | head -30
```

Then create a disposable user cron entry only on a lab host:

```bash
(crontab -l 2>/dev/null; echo '* * * * * date >> "$HOME/cron-lab.log"') | crontab -
sleep 70
tail "$HOME/cron-lab.log"
crontab -l | grep -v 'cron-lab.log' | crontab -
```

The cleanup command removes the lab entry. Confirm it is gone:

```bash
crontab -l
```
