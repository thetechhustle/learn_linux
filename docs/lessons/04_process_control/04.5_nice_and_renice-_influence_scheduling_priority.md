### 04.5 Nice and Renice: Influence Scheduling Priority

Linux can run many runnable processes at once, but the CPUs still make one scheduling decision at a time. `nice` and `renice` let you influence those decisions without stopping the process. They are useful when a batch job, backup, compiler, report, or one-off script is competing with interactive or latency-sensitive work.

!!! abstract "What you will learn"
    - Explain what a process nice value does and what it does not do.
    - Inspect scheduling priority fields with `ps` and `top`.
    - Start a command with a lower CPU priority by using `nice`.
    - Adjust an existing process with `renice` and verify the result.
    - Decide when renicing is safer than killing a process.

!!! example "Field story"
    An API server is slow during business hours. `top` shows a report generator using a large share of CPU, but the report still needs to finish. Instead of killing it, you lower the report process priority, watch whether API latency recovers, and leave a note explaining the temporary change.

!!! success "Operator principle"
    Renice the least-important CPU consumer only after proving it is competing with work that matters more.

## Nice values in plain terms

A nice value is a hint to the Linux scheduler. A lower number gets more favorable CPU scheduling; a higher number is more willing to yield CPU time.

| Nice value | Meaning |
| --- | --- |
| `-20` | Highest scheduling favor |
| `0` | Normal default for most processes |
| `19` | Lowest scheduling favor |

Two boundaries matter in operations:

- A regular user can usually make their own processes nicer, such as moving from `0` to `10`.
- Raising priority, such as moving from `10` to `0` or from `0` to `-5`, usually requires root or a configured resource limit.

Nice values do not reserve CPU, cap CPU, fix memory pressure, repair bad application behavior, or override every scheduler decision. They are one small lever for CPU contention.

## Inspect current priority

Use explicit `ps` fields so the evidence is clear:

```bash
ps -eo pid,ppid,user,ni,pri,stat,pcpu,pmem,comm --sort=-pcpu | head
```

Key fields:

- `NI`: the nice value.
- `PRI`: the scheduler priority shown by `ps`; lower values are generally favored.
- `STAT`: process state, useful for separating runnable CPU pressure from sleeping or stopped work.
- `%CPU`: recent CPU usage, not proof by itself but a useful lead.

For a live view, press `r` in `top` only in a lab or when you are authorized to change priority. In production, use `top` first as an observer:

```bash
top -o %CPU
```

## Start lower-priority work with nice

Use `nice` when you already know a command is background or best-effort work:

```bash
nice -n 10 tar -czf logs.tgz /var/log
```

That command starts `tar` at nice value `10`, making it more willing to yield CPU time to normal-priority processes.

To verify:

```bash
pgrep -af 'tar -czf logs.tgz'
ps -o pid,user,ni,pri,stat,pcpu,comm -p <PID>
```

If you need a command to survive logout, combine priority decisions with the right job-control or service-management tool. Nice values are not a replacement for `systemd`, `tmux`, `nohup`, or a proper batch scheduler.

## Change an existing process with renice

Use `renice` when the process is already running:

```bash
renice -n 10 -p 12345
ps -o pid,user,ni,pri,stat,pcpu,comm -p 12345
```

You can target a process ID, process group, or user:

```bash
renice -n 10 -p 12345
renice -n 10 -g 23456
renice -n 15 -u buildbot
```

Be careful with broad user-level changes. Renicing every process owned by a service account can affect unrelated jobs, monitoring agents, or helper processes that only happen to share the same user.

## A safe response pattern

When CPU contention looks real, use a short evidence loop:

1. Identify the competing process:

   ```bash
   ps -eo pid,ppid,user,ni,stat,pcpu,pmem,etime,comm --sort=-pcpu | head -20
   ```

2. Confirm what the process is and who owns it:

   ```bash
   ps -fp <PID>
   pstree -sp <PID>
   ```

3. Decide whether the process is less important than the affected service.
4. Lower the process priority in the smallest useful step:

   ```bash
   renice -n 5 -p <PID>
   ```

5. Re-check both the process and the affected service:

   ```bash
   ps -o pid,user,ni,pri,stat,pcpu,comm -p <PID>
   systemctl status <service>
   journalctl -u <service> -n 50 --no-pager
   ```

6. Record the original nice value, the new value, the reason, and the rollback command.

Rollback is usually another `renice`:

```bash
renice -n 0 -p <PID>
```

## When renice is the wrong tool

Do not reach for `renice` when the evidence points elsewhere:

- The process is stuck in uninterruptible I/O wait; investigate storage or network I/O.
- The service is out of memory; inspect memory pressure and logs.
- A process is clearly unsafe or malicious; isolate and follow incident response.
- The workload needs durable limits; use service configuration, cgroups, containers, or a scheduler.
- You need to protect production latency every day; build capacity or workload isolation instead of relying on manual renice commands.

## Hands-on practice

Run this on a disposable VM, container, or lab machine.

1. Start a CPU-heavy lab process:

   ```bash
   yes > /dev/null &
   LAB_PID=$!
   ```

2. Inspect it:

   ```bash
   ps -o pid,user,ni,pri,stat,pcpu,comm -p "$LAB_PID"
   ```

3. Lower its scheduling priority:

   ```bash
   renice -n 10 -p "$LAB_PID"
   ```

4. Verify the new nice value:

   ```bash
   ps -o pid,user,ni,pri,stat,pcpu,comm -p "$LAB_PID"
   ```

5. Clean up the lab process:

   ```bash
   kill "$LAB_PID"
   ```

Lab note:

```text
Original nice value:
New nice value:
Command used:
Observed CPU behavior:
Rollback or cleanup:
```
