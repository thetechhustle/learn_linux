## 04.2 The Life Cycle of a Process

!!! abstract "What you will learn"
    - Describe how a Linux process moves from creation to exit.
    - Use `ps` to inspect parent processes, process state, CPU time, and command names.
    - Distinguish running, sleeping, stopped, zombie, and orphaned processes during troubleshooting.
    - Decide when to observe, wait, signal, or escalate a process-control incident.

!!! example "Field story"
    An API server is slow after a deploy. One worker process is consuming CPU, another appears stuck, and a few short-lived children keep coming and going. Before killing anything, you need to know which processes are active work, which are waiting on I/O, and which are leftovers that point back to a parent-process problem.

!!! success "Operator principle"
    Process state is evidence. Confirm where a process is in its lifecycle before deciding whether to wait, trace, restart, or terminate it.

A Linux process is not just a command name. It has a parent, an owner, a process ID, a state, resource counters, open files, signal handlers, and an exit status when it finishes. The lifecycle explains how those pieces change from process creation through cleanup.

## Lifecycle Map

Most process investigations follow this path:

1. **Created:** A parent process calls `fork()` or `clone()` to create a child. The child inherits many attributes from the parent, including environment variables and open file descriptors.
2. **Execed:** The child often calls `exec()` to replace its inherited program image with the command it is supposed to run.
3. **Runnable or running:** The scheduler can place the process on a CPU when it is ready to run.
4. **Sleeping or waiting:** The process is waiting for a resource such as disk I/O, network I/O, a timer, or a lock.
5. **Stopped:** A signal or job-control action has paused the process.
6. **Exited:** The process has finished or was terminated by a signal.
7. **Reaped:** The parent collects the child's exit status. Until this happens, the child may appear as a zombie.

## Inspect Process State

Use `ps` to collect a compact view of the process tree and state:

```bash
ps -eo pid,ppid,user,stat,etime,time,cmd --forest
```

The most useful fields during an incident are:

| Field | Why it matters |
| --- | --- |
| `PID` | The process ID you use for focused inspection or signals. |
| `PPID` | The parent process. This often identifies the service manager, shell, worker supervisor, or application master process. |
| `USER` | The account that owns the process and its permissions. |
| `STAT` | The process state plus modifiers. This is the fastest lifecycle clue. |
| `ELAPSED` / `ETIME` | How long the process has existed. |
| `TIME` | CPU time consumed by the process, not wall-clock runtime. |
| `CMD` | The command line that started the process. |

Common `STAT` values include:

| State | Meaning | Operator response |
| --- | --- | --- |
| `R` | Running or runnable. | Check whether CPU use is expected before changing priority or sending a signal. |
| `S` | Interruptible sleep. | Often normal; the process is waiting for I/O, a timer, or another event. |
| `D` | Uninterruptible sleep. | Treat carefully. It often points to disk, network filesystem, or kernel-level waiting. Killing may not work. |
| `T` | Stopped or traced. | Check job control, debugger use, or a deliberate `SIGSTOP`. |
| `Z` | Zombie. | The process already exited; investigate the parent that has not reaped it. |

Modifiers can add context. For example, `s` marks a session leader, `l` indicates a multithreaded process, and `+` means the process is in the foreground process group for its terminal.

## Parent And Child Clues

Parentage tells you where control belongs. A worker process with a parent like `systemd`, `supervisord`, `nginx`, `apache2`, `gunicorn`, or a shell should not all be handled the same way.

```bash
ps -o pid,ppid,stat,etime,time,cmd -p 1234
ps -o pid,ppid,stat,etime,time,cmd --ppid 1234
```

Use the first command to inspect one process. Use the second to see its direct children. If the parent is a service manager, the safer operational action is often a service-level restart during a maintenance window rather than killing one child at random.

## Zombie And Orphan Processes

A **zombie** process has already exited. It remains in the process table only because its parent has not collected the exit status. A single short-lived zombie can be harmless. A growing pile of zombies usually means the parent process is unhealthy or has a bug in child handling.

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/ { print }'
```

An **orphan** process is a child whose parent exited while the child kept running. Modern Linux systems normally re-parent orphans to a subreaper such as `systemd`, which can then collect them when they exit. Orphans are not automatically bad, but unexpected orphaned workers can explain why a deploy or shell logout did not stop work as intended.

## Safe Troubleshooting Sequence

When a process looks suspicious, move from least invasive to most invasive:

1. Identify the process and its parent.

    ```bash
    ps -o pid,ppid,user,stat,etime,time,cmd -p <PID>
    ```

2. Check whether the process is part of a managed service.

    ```bash
    systemctl status <service-name>
    ```

3. Inspect nearby processes before acting.

    ```bash
    ps -eo pid,ppid,user,stat,etime,time,cmd --forest | less
    ```

4. Prefer graceful signals when termination is justified.

    ```bash
    kill -TERM <PID>
    ```

5. Use `kill -KILL` only after you have evidence that graceful shutdown failed and you understand what cleanup the process may skip.

!!! warning "Do not use `kill -9` as a first response"
    `SIGKILL` gives a process no chance to flush buffers, release locks, remove temporary files, or close network sessions cleanly. It can be appropriate, but only after you have collected evidence and tried safer options.

## Hands-On Practice

Run these commands on a disposable VM, container, or lab machine.

1. Start a long-running process in one terminal:

    ```bash
    sleep 300
    ```

2. In another terminal, find its lifecycle details:

    ```bash
    ps -o pid,ppid,user,stat,etime,time,cmd -C sleep
    ```

3. Stop and resume it:

    ```bash
    kill -STOP <PID>
    ps -o pid,ppid,stat,cmd -p <PID>
    kill -CONT <PID>
    ps -o pid,ppid,stat,cmd -p <PID>
    ```

4. End it gracefully:

    ```bash
    kill -TERM <PID>
    ps -o pid,ppid,stat,cmd -p <PID>
    ```

Record which `STAT` values you observed and what each one meant.
