### 07.2 Shell Basics

!!! abstract "What you will learn"
    - Explain what a shell does for an operator.
    - Read the parts of a command: command name, options, arguments, and environment.
    - Use quoting, redirection, pipelines, and exit status safely.
    - Navigate command history without rerunning risky commands by accident.
    - Build a repeatable inspection command from smaller shell pieces.

!!! example "Field story"
    During an incident, an operator needs to inspect disk usage, find the largest log directories, and save the evidence for handoff. The shell is the fastest path, but only if the commands are clear, quoted correctly, and safe to rerun.

!!! success "Operator principle"
    Shell fluency is not typing speed. It is knowing exactly what a command will read, what it will change, and what evidence it leaves behind.

## What the shell does

A shell is a command interpreter. It reads what you type, expands parts of the command line, starts programs, connects their input and output, and reports whether they succeeded.

Common Linux shells include:

- `sh`: the historical/POSIX-style shell interface
- `bash`: common on many Linux systems
- `zsh`: common on macOS and some operator workstations
- `dash`: a small fast `/bin/sh` implementation on some Debian/Ubuntu systems

The shell is not the whole operating system. When you run `ls`, `grep`, `find`, or `systemctl`, the shell starts those programs. The shell's job is to interpret the command line and wire the pieces together.

## Command anatomy

Most commands follow this pattern:

```sh
command [options] [arguments]
```

Example:

```sh
ls -lh /var/log
```

In that command:

- `ls` is the command name
- `-lh` is a combined set of short options
- `/var/log` is an argument

Long options are usually easier to read in scripts and notes:

```sh
ls --human-readable --size /var/log
```

Not every command uses options the same way. Always check the local manual page or help output before using an unfamiliar option:

```sh
man ls
ls --help
```

Some minimal systems do not include full manual pages. In that case, use the command's help output and distribution documentation.

## Working directory

Every shell has a current working directory. Relative paths are resolved from that directory.

```sh
pwd
ls
cd /var/log
pwd
```

Use absolute paths when documenting an operational procedure:

```sh
du -sh /var/log
```

An absolute path starts at `/`. A relative path starts from wherever the shell is currently located. This difference matters in scripts and scheduled jobs because the working directory may not be what you expect.

## Environment variables

Environment variables are name/value pairs passed to programs.

Inspect common examples:

```sh
printf '%s\n' "$SHELL"
printf '%s\n' "$HOME"
printf '%s\n' "$PATH"
```

`PATH` tells the shell where to search for commands. To see exactly which program will run:

```sh
command -v ls
command -v python3
```

For one command, you can set a temporary environment variable:

```sh
LC_ALL=C sort names.txt
```

That value applies only to the `sort` command. It does not permanently change the shell environment.

## Quoting

Quoting controls how the shell treats spaces, special characters, and variables.

Use double quotes around variable expansions unless you intentionally want word splitting:

```sh
target="/var/log"
printf 'target=%s\n' "$target"
```

Single quotes preserve text literally:

```sh
printf '%s\n' 'Use $HOME literally here'
```

Double quotes still allow variable expansion:

```sh
printf '%s\n' "home is $HOME"
```

Unquoted variables are a common source of bugs:

```sh
name="Q2 report.txt"
ls "$name"
```

Without quotes, the shell would split that filename into multiple words.

## Globs

Globs are shell patterns expanded before the command runs.

```sh
ls *.log
```

If the current directory contains `app.log` and `worker.log`, the shell turns the command into:

```sh
ls app.log worker.log
```

Globs are useful, but be careful with destructive commands. First print what the shell will match:

```sh
printf '%s\n' *.log
```

Then decide whether a changing command is appropriate.

## Input, output, and error

Unix programs usually have three standard streams:

| Stream | Number | Purpose |
| --- | --- | --- |
| standard input | `0` | data the program reads |
| standard output | `1` | normal output |
| standard error | `2` | errors and diagnostics |

Redirect standard output to a file:

```sh
df -h > disk-report.txt
```

Append instead of overwrite:

```sh
date >> disk-report.txt
df -h >> disk-report.txt
```

Redirect errors separately:

```sh
find /var/log -type f > files.txt 2> errors.txt
```

Be careful with `>`. It truncates the destination file before the command writes new content. If the destination matters, use a new filename or append with `>>`.

## Pipelines

A pipe connects the output of one command to the input of another.

```sh
ps aux | grep nginx
```

Pipelines are powerful because each command can do one job:

```sh
find /var/log -type f -name '*.log' | sort | head
```

For process searches, prefer tools that understand processes instead of grepping the full `ps` output when available:

```sh
pgrep -a nginx
```

Pipeline readability matters. During an incident, a clear three-command pipeline is better than a clever one-liner nobody can safely edit.

## Exit status

Every command exits with a status code. By convention:

- `0` means success
- nonzero means failure or a condition the command reports as unsuccessful

Inspect the previous command's status:

```sh
test -d /var/log
printf 'status=%s\n' "$?"
```

Use `&&` when the second command should run only after success:

```sh
mkdir -p /tmp/shell-lab && cd /tmp/shell-lab
```

Use `||` for a fallback or clear error:

```sh
test -d /var/log || printf 'missing /var/log\n' >&2
```

Avoid long chains that hide what failed. For operational notes, separate commands can be easier to audit.

## Command history

Shell history is useful, but it can also rerun a risky command too easily.

Safer habits:

- use the up arrow to inspect before pressing Enter
- edit recalled commands carefully before rerunning
- avoid storing secrets directly in commands
- prefer scripts or notes for repeatable operational sequences
- do not rely on history as the only record of what happened

To review recent commands:

```sh
history | tail
```

If a command contains a secret, assume it may be stored in history and logs. Rotate or revoke the secret when appropriate.

## Build an inspection command

Start with a simple question: "Which directories under `/var/log` are using the most space?"

First inspect the top-level sizes:

```sh
du -sh /var/log/* 2>/tmp/du-errors.txt
```

Then sort the result:

```sh
du -sh /var/log/* 2>/tmp/du-errors.txt | sort -h
```

Then keep the largest entries:

```sh
du -sh /var/log/* 2>/tmp/du-errors.txt | sort -h | tail
```

Finally, save the evidence:

```sh
{
    date
    hostname
    du -sh /var/log/* 2>/tmp/du-errors.txt | sort -h | tail
} > /tmp/log-size-report.txt
```

This command still only inspects. It does not delete or compress logs. That makes it safe to use as a first incident evidence step.

## Hands-on practice

Run these commands on a disposable VM, container, or lab machine.

1. Create a lab directory:

    ```sh
    mkdir -p /tmp/shell-basics-lab
    cd /tmp/shell-basics-lab
    printf 'alpha\nbeta\ngamma\n' > words.txt
    printf 'one two\nthree four\n' > "spaced name.txt"
    ```

2. Practice command anatomy:

    ```sh
    wc -l words.txt
    sort words.txt
    command -v wc
    ```

3. Practice safe quoting:

    ```sh
    ls "spaced name.txt"
    printf '%s\n' "$PWD"
    ```

4. Practice redirection and append:

    ```sh
    date > report.txt
    wc -l words.txt >> report.txt
    cat report.txt
    ```

5. Practice a read-only pipeline:

    ```sh
    find . -type f -print | sort
    find . -type f -print | wc -l
    ```

6. Check exit status:

    ```sh
    test -f words.txt
    printf 'status=%s\n' "$?"
    test -f missing.txt
    printf 'status=%s\n' "$?"
    ```
