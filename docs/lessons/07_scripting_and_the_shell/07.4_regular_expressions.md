### 07.4 Regular Expressions

!!! abstract "What you will learn"
    - Explain what regular expressions do in everyday Linux operations.
    - Use anchors, character classes, repetition, and grouping to match text.
    - Choose between basic and extended regular expressions in common tools.
    - Test patterns safely before using them in changing commands.
    - Build repeatable log and config inspection commands with `grep`, `sed`, and `awk`.

!!! example "Field story"
    A service is noisy after a deploy. The logs contain thousands of lines, but the operator needs only failed requests from one API route during a narrow time window. A regular expression can reduce the haystack to the handful of lines worth reading.

!!! success "Operator principle"
    Treat regular expressions as filters first. Prove what they match before using them to edit, move, or delete anything.

## What regular expressions are

A regular expression is a pattern for matching text. Linux operators use regular expressions to search logs, filter command output, validate small pieces of input, and transform text in scripts.

Regular expressions show up in many tools:

- `grep` searches for lines that match a pattern
- `sed` edits or prints text based on patterns
- `awk` filters and processes fields
- `find` can match names with patterns or call regex-capable tools
- editors and pagers often support regex search

Regular expressions are not the same as shell globs. A shell glob such as `*.log` is expanded by the shell against filenames. A regular expression is interpreted by the tool receiving the pattern.

## Start with fixed strings

Do not reach for regex when a fixed-string search is enough.

```sh
grep -F 'error' app.log
```

`grep -F` treats the search text literally. This avoids surprises when the text contains characters that have regex meaning, such as `.`, `*`, `[`, or `?`.

Use regex when you need a pattern:

```sh
grep 'error [0-9][0-9][0-9]' app.log
```

That pattern matches `error ` followed by three digits.

## Basic building blocks

These are common regular expression pieces:

| Pattern | Meaning |
| --- | --- |
| `.` | any single character |
| `^` | start of a line |
| `$` | end of a line |
| `[abc]` | one character: `a`, `b`, or `c` |
| `[^abc]` | one character that is not `a`, `b`, or `c` |
| `[0-9]` | one digit |
| `*` | zero or more of the previous item |
| `\+` | one or more of the previous item in basic grep |
| `\?` | zero or one of the previous item in basic grep |

Examples:

```sh
printf '%s\n' cat cut cot act | grep '^c.t$'
printf '%s\n' 200 404 500 abc | grep '^[0-9][0-9][0-9]$'
printf '%s\n' error warning info | grep '^err'
```

The first command matches `cat`, `cut`, and `cot`, but not `act`, because the pattern is anchored to lines that start with `c` and end with `t`.

## Basic versus extended regex

Traditional `grep` uses basic regular expressions by default. Some useful operators need backslashes in basic mode:

```sh
grep 'error [0-9]\+' app.log
```

Extended regular expressions are often easier to read. Use `grep -E`:

```sh
grep -E 'error [0-9]+' app.log
```

Common extended operators include:

| Pattern | Meaning |
| --- | --- |
| `+` | one or more |
| `?` | zero or one |
| `a|b` | `a` or `b` |
| `(abc)` | group |
| `{2,4}` | repeat between 2 and 4 times |

Example:

```sh
printf '%s\n' info warn error fatal | grep -E '^(error|fatal)$'
```

Pick one mode and make it visible in scripts. If the pattern depends on extended syntax, include `-E` so the next operator does not have to guess.

## Character classes

Bracket expressions can use named classes that are clearer than ranges in some locales:

```sh
grep '^[[:digit:]][[:digit:]][[:digit:]]$' status-codes.txt
grep '^[[:space:]]*Listen' sshd_config
```

Useful classes include:

- `[[:digit:]]`
- `[[:alpha:]]`
- `[[:alnum:]]`
- `[[:space:]]`
- `[[:lower:]]`
- `[[:upper:]]`

When exact byte ordering matters, especially in scripts, run with a stable locale:

```sh
LC_ALL=C grep -E '^[A-Z]+=' env.txt
```

## Quoting regex patterns

Quote regex patterns so the shell does not interpret special characters first.

Prefer single quotes for most regex patterns:

```sh
grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}' app.log
```

Use double quotes only when you intentionally need shell variable expansion:

```sh
code='500'
grep "status=$code" app.log
```

If user-provided text is involved, be careful. A variable may contain regex metacharacters. Use fixed-string search when you want literal text:

```sh
needle='user.name@example.com'
grep -F "$needle" app.log
```

## Test before changing

The safe workflow is:

1. print sample input
2. run a read-only match
3. count matches
4. inspect matches
5. only then use the pattern in an editing command

Example:

```sh
grep -E 'status=(500|502|503)' app.log
grep -E 'status=(500|502|503)' app.log | wc -l
grep -E 'status=(500|502|503)' app.log | head
```

Do not use a regex inside `rm`, `mv`, `sed -i`, or a broad automation script until you have proven the match set.

## Grep for operational evidence

Use `grep` to reduce noisy output while preserving enough context.

Find failed HTTP statuses:

```sh
grep -E 'status=(500|502|503|504)' app.log
```

Find lines for one route:

```sh
grep -F 'path=/api/orders' app.log
```

Combine fixed-string and regex filters:

```sh
grep -F 'path=/api/orders' app.log | grep -E 'status=5[0-9][0-9]'
```

Show context around matches:

```sh
grep -n -C 2 -E 'status=5[0-9][0-9]' app.log
```

`-n` prints line numbers. `-C 2` prints two lines before and after each match.

## Sed substitutions

`sed` can replace text with a regex:

```sh
sed 's/status=[0-9][0-9][0-9]/status=XXX/' app.log
```

That prints edited output to the terminal by default. It does not modify the file.

To preview only changed lines:

```sh
sed -n 's/status=[0-9][0-9][0-9]/status=XXX/p' app.log
```

Be cautious with in-place editing. `sed -i` differs between GNU/Linux and BSD/macOS, and it can rewrite files immediately. For operational work, write to a new file first:

```sh
sed 's/status=[0-9][0-9][0-9]/status=XXX/' app.log > app.redacted.log
```

Then compare:

```sh
diff -u app.log app.redacted.log | head
```

## Awk pattern matching

`awk` can combine regex matching with field-aware processing.

Print lines where the third field is a 5xx status code:

```sh
awk '$3 ~ /^5[0-9][0-9]$/ { print }' access.log
```

Count matches:

```sh
awk '$3 ~ /^5[0-9][0-9]$/ { count++ } END { print count }' access.log
```

This is often clearer than building a long pipeline when you need both matching and a small calculation.

## Common mistakes

Watch for these:

- using `.` when you meant a literal dot; use `\.` in regex
- forgetting anchors and matching too much
- using regex when `grep -F` would be safer
- assuming every tool uses the same regex dialect
- testing against one line and applying to a full file without counting matches
- using in-place editing before saving a reviewed output file

Example:

```sh
grep 'example.com' domains.txt
grep 'example\.com' domains.txt
```

The first pattern treats `.` as any character. The second pattern matches a literal dot.

## Hands-on practice

Run these commands on a disposable VM, container, or lab machine.

1. Create a sample log:

    ```sh
    mkdir -p /tmp/regex-lab
    cat > /tmp/regex-lab/app.log <<'EOF'
    2026-05-10T12:00:01Z path=/api/orders status=200 user=alice
    2026-05-10T12:00:02Z path=/api/orders status=503 user=bob
    2026-05-10T12:00:03Z path=/api/users status=404 user=carol
    2026-05-10T12:00:04Z path=/api/orders status=500 user=dave
    EOF
    ```

2. Match only `/api/orders` lines:

    ```sh
    grep -F 'path=/api/orders' /tmp/regex-lab/app.log
    ```

3. Match only 5xx statuses:

    ```sh
    grep -E 'status=5[0-9][0-9]' /tmp/regex-lab/app.log
    ```

4. Combine filters:

    ```sh
    grep -F 'path=/api/orders' /tmp/regex-lab/app.log | grep -E 'status=5[0-9][0-9]'
    ```

5. Count matches before acting:

    ```sh
    grep -E 'status=5[0-9][0-9]' /tmp/regex-lab/app.log | wc -l
    ```

6. Redact statuses to a new file:

    ```sh
    sed 's/status=[0-9][0-9][0-9]/status=XXX/' /tmp/regex-lab/app.log > /tmp/regex-lab/app.redacted.log
    diff -u /tmp/regex-lab/app.log /tmp/regex-lab/app.redacted.log
    ```
