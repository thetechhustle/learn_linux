### 07.8 Revision Control with Git

!!! abstract "What you will learn"
    - Explain how Git protects operational scripts and documentation from accidental drift.
    - Inspect repository state before changing files.
    - Make small commits with clear evidence.
    - Use branches to separate work.
    - Recover from common mistakes without destructive commands.

!!! example "Field story"
    A production helper script needs a one-line fix. The change is easy; the risk is losing track of what changed, why it changed, and how to back it out. Git gives the team an evidence trail before the script reaches another operator.

!!! success "Operator principle"
    Treat Git as an audit log. Before changing files, know the branch, the status, the diff, and the intended review path.

## What Git does

Git is a distributed version control system. It tracks file changes in a repository so you can answer operational questions:

- What changed?
- Who changed it?
- Why was it changed?
- Which version is deployed?
- How can we compare this version with an earlier one?
- How can we undo a bad change safely?

Git does not replace tests, review, or backups. It gives those practices a reliable change history.

## Inspect before changing

Start every repository session by checking where you are.

```sh
pwd
git status --short --branch
```

The branch line matters. It tells you whether you are on `main`, a feature branch, or a detached commit.

Inspect remotes:

```sh
git remote -v
```

Inspect recent history:

```sh
git log --oneline --decorate -n 8
```

Read the current diff before adding anything:

```sh
git diff
```

If the working tree already has changes you do not recognize, stop and identify them before editing. On a shared machine, those changes may belong to another operator or automation run.

## Configure identity

Git commits carry a name and email address. Check the current config:

```sh
git config --get user.name
git config --get user.email
```

Set them for one repository:

```sh
git config user.name "Your Name"
git config user.email "you@example.com"
```

Use repository-local config when you need different identities for different work. Use `--global` only when that identity should apply to all repositories for your user account.

## Create a branch

Do not make routine changes directly on `main` unless the project explicitly says that is the workflow.

Create and switch to a branch:

```sh
git switch -c fix/script-log-path
```

Older Git versions may use:

```sh
git checkout -b fix/script-log-path
```

Use branch names that describe the change:

- `fix/log-parser-empty-lines`
- `docs/operator-handoff-checklist`
- `feature/json-status-output`

## Stage deliberately

After editing, inspect the diff:

```sh
git diff
```

Stage the intended file:

```sh
git add scripts/summarize_logs.py
```

Inspect what is staged:

```sh
git diff --cached
```

This is the last easy checkpoint before committing. Make sure the staged diff contains only the intended change.

## Commit small, useful changes

Commit with a concise message:

```sh
git commit -m "Handle empty log lines in summary script"
```

A good commit should usually answer one operational question: what changed and why would a teammate care?

Better messages:

- `Fix log parser on empty lines`
- `Document rollback command for service restart`
- `Add JSON output to status script`

Weak messages:

- `updates`
- `fix`
- `stuff`

## Compare and review

Compare your branch with the base branch:

```sh
git diff main...HEAD
```

Show commits on your branch:

```sh
git log --oneline main..HEAD
```

If the project uses pull requests or merge requests, push the branch and open a review:

```sh
git push -u origin fix/script-log-path
```

The review boundary is important. It lets tests, humans, and automation inspect the change before it becomes shared truth.

## Pull safely

Before updating from a remote, inspect your local state:

```sh
git status --short --branch
```

If the tree is clean, fetch remote history:

```sh
git fetch origin
```

Then inspect what changed:

```sh
git log --oneline --decorate HEAD..origin/main
```

Only then update your branch according to the project's workflow:

```sh
git merge origin/main
```

or:

```sh
git rebase origin/main
```

Use the workflow the project expects. Rebase rewrites local branch history; merge preserves it.

## Common safe recovery commands

Unstage a file while keeping the edit:

```sh
git restore --staged path/to/file
```

Discard changes in one file:

```sh
git restore path/to/file
```

Show a file from the last commit:

```sh
git show HEAD:path/to/file
```

Create a new commit that reverses an earlier commit:

```sh
git revert COMMIT_SHA
```

`git revert` is usually safer than rewriting shared history because it records the rollback as a normal commit.

## Be careful with destructive commands

These commands can destroy local work:

```sh
git reset --hard
git clean -fd
```

Do not run them on a shared repository or unfamiliar working tree unless you have confirmed exactly what will be lost.

Preview untracked files before cleaning:

```sh
git clean -fdn
```

The `-n` means dry run. It shows what would be removed without removing it.

## Ignore generated files

Generated files should usually not be committed. Use `.gitignore` to exclude build output, caches, virtual environments, and temporary files.

Common examples:

```gitignore
.venv/
__pycache__/
*.log
dist/
build/
```

Do not ignore lockfiles blindly. Files such as `Gemfile.lock`, `package-lock.json`, and some Python lockfiles may be important for repeatable builds.

## Operational Git checklist

Before making a change:

```sh
git status --short --branch
git remote -v
git log --oneline --decorate -n 5
```

Before committing:

```sh
git diff
git diff --cached
```

Before handing off:

```sh
git status --short --branch
git log --oneline --decorate -n 3
```

Record the branch, commit SHA, verification command, and review link in the handoff.

## Hands-on practice

Run these in a disposable repository or lab directory.

1. Create a temporary directory and run `git init`.
2. Add a small text file with one line.
3. Check `git status --short --branch`.
4. Commit the file with a meaningful message.
5. Create a branch and change the file.
6. Inspect `git diff`, then commit the branch change.
7. Use `git log --oneline --decorate --graph --all` to view the history.
8. Practice `git restore --staged` by staging a file and unstaging it.
