### 07.9 Recommended Reading

Scripting references are most useful when they help you answer a specific
operational question: what will this command read, what will it change, what
happens if it fails, and how can I prove the result? Use this reading list as a
working map rather than a bookshelf to finish.

!!! abstract "What you will learn"
    - Choose the right reference for shell, regex, Python, Ruby, or Git work.
    - Start with local documentation before trusting a copied internet answer.
    - Keep scripts maintainable by reading about error handling, portability, and tests.
    - Turn a reference page into a small lab note with commands and evidence.

!!! success "Operator principle"
    Read just enough to make the next script safer, then prove the behavior in a
    disposable environment before using it on a real system.

## Start with local documentation

Local docs match the tools installed on the system in front of you. They also
work during outages, rescue sessions, or restricted maintenance windows.

- `man sh`, `man bash`, and `help set` explain shell syntax, builtins, and
  execution options.
- `man grep`, `man sed`, `man awk`, `man find`, and `man xargs` document the
  text-processing tools most scripts depend on.
- `python3 --help`, `python3 -m pydoc pathlib`, and `python3 -m pydoc subprocess`
  are useful when you need file handling or external command execution.
- `ruby --help`, `ri File`, and `ri OptionParser` help with Ruby scripts that
  need safe file operations and command-line flags.
- `git help <topic>`, such as `git help commit` or `git help revisions`, is the
  fastest way to confirm Git behavior without leaving the terminal.

When a command supports both a short help page and a full manual page, read the
short help first to orient yourself, then use the manual page for exact option
semantics.

## Shell and text-processing references

The shell is where administrators often glue systems together. Prefer references
that explain failure behavior and quoting, not only clever one-liners.

- **The POSIX shell command language**: use it when a script must run under
  `/bin/sh` across many Unix-like systems.
- **Bash Reference Manual**: use it for Bash-specific features such as arrays,
  `[[ ... ]]`, `set -o pipefail`, and advanced parameter expansion.
- **Advanced Bash-Scripting Guide** by Mendel Cooper: useful as a broad example
  catalog, but verify examples against current shell manuals before copying them.
- **GNU Grep, Sed, Awk, and Findutils manuals**: use these for exact option
  behavior, portability notes, and edge cases around filenames, delimiters, and
  regular expressions.

!!! warning "Do not learn scripting from paste-only examples"
    A script copied from a forum can hide assumptions about shells, filenames,
    locales, privileges, and installed tools. Test each pipeline with sample
    input, quote variables, and add a dry-run mode before it changes files.

## Regular expressions

Regular expressions vary by tool. A pattern that works in Python might not work
the same way in `grep`, `sed`, or Ruby.

- **`man 7 regex`** on systems that provide it explains POSIX basic and extended
  regular expressions.
- **GNU Grep manual** documents basic, extended, fixed-string, and Perl-compatible
  modes where available.
- **Python `re` documentation** is the source of truth for Python regex behavior.
- **Ruby Regexp documentation** explains Ruby pattern syntax and match objects.
- **Mastering Regular Expressions** by Jeffrey Friedl is helpful for the deeper
  mental model, especially when a production pattern has become too clever to
  debug quickly.

For operational scripts, prefer readable patterns with named variables and test
fixtures over dense patterns that only the original author understands.

## Python and Ruby

Use language documentation when the task has outgrown shell: structured data,
clear error handling, reusable tests, or cross-platform behavior.

- **Python documentation tutorial and library reference**: start with `pathlib`,
  `argparse`, `json`, `csv`, `logging`, `subprocess`, and `venv`.
- **Python Crash Course** by Eric Matthes: a good guided path if you need a
  beginner-friendly Python foundation before writing automation.
- **Ruby documentation**: focus on `File`, `Pathname`, `OptionParser`, `JSON`,
  `Logger`, and `Open3` for administrator-friendly scripts.
- **The Well-Grounded Rubyist** by David A. Black: useful for building a durable
  Ruby foundation beyond short scripts.

For both languages, read packaging and environment-management docs before
installing dependencies globally. A script that only works on one administrator's
laptop is not yet an operations tool.

## Git and change control

Every nontrivial script should live in version control. Git references help you
make changes small, reviewable, and recoverable.

- **Pro Git** by Scott Chacon and Ben Straub is the best long-form Git reference
  for branching, remotes, history, and collaboration.
- `git help status`, `git help diff`, `git help add`, `git help commit`, and
  `git help restore` are the day-to-day safety references.
- `git help log`, `git help bisect`, and `git help reflog` are useful when a
  script changed behavior and you need to find when it happened.

Commit scripts with sample inputs, expected outputs, and rollback notes. Future
operators should be able to review both the code and the operational intent.

## A practical reading workflow

Use this loop when a reference page is dense:

1. Write the operational question in one sentence.
2. Read the local manual or official docs for the command or language feature.
3. Copy the exact option, function, or behavior you plan to use into a lab note.
4. Build a tiny input fixture that exercises success, empty input, and failure.
5. Run the command or script against the fixture.
6. Record the command, output, exit status, and what you learned.
7. Update the script, comments, or README with the decision.

This keeps reading tied to evidence. It also creates notes you can reuse during
incidents, code review, or handoff.

## Hands-on practice

Run these in a disposable directory:

```sh
mkdir -p /tmp/script-reading-lab
cd /tmp/script-reading-lab
printf '%s\n' 'web01 ok' 'web02 failed' 'db01 ok' > hosts.txt
```

1. Use `man grep` or `grep --help` to find the option that prints line numbers.
2. Run `grep` against `hosts.txt` to list only the failed host with its line
   number.
3. Read `python3 -m pydoc pathlib` or the official `pathlib` docs, then write a
   five-line Python script that prints whether `hosts.txt` exists.
4. Run `git init`, commit the fixture and script, then use `git status` and
   `git log --oneline` to prove the lab is tracked.
5. Add a short note explaining which reference answered each question.

## Check your understanding

- Which local reference would you check before using a shell option in a
  production script?
- Why should regex examples be tested in the same tool that will run them?
- What makes a Python or Ruby script safer than a long shell pipeline?
- What should be committed with a script so another operator can review it?
- How would you document a reading decision in an incident handoff?
