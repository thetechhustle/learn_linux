### 07.7 Library and Environment Management for Python and Ruby

!!! abstract "What you will learn"
    - Explain why language libraries should usually be isolated from the system package manager.
    - Inspect Python and Ruby versions before installing dependencies.
    - Use virtual environments, Bundler, and lockfiles to make scripts repeatable.
    - Recognize common dependency failures without making the host worse.
    - Build a small read-only dependency audit checklist for operator handoffs.

!!! example "Field story"
    A teammate hands you a maintenance script that worked on their laptop but fails on a server. The script itself is fine; the server has a different Python version and a different library version. Your job is to make the runtime explicit before anyone starts changing production packages.

!!! success "Operator principle"
    Treat language environments as part of the script. Record the interpreter, dependency source, install scope, and verification command.

## Why environments matter

Linux already has a package manager. Python and Ruby also have package tools. Mixing them casually is how small scripts become fragile hosts.

The system package manager owns files installed by tools such as:

- `apt`
- `dnf`
- `pacman`
- `zypper`
- `pkg`

Language package managers install libraries for a programming language:

- Python: `pip`
- Ruby: `gem`
- Ruby projects: `bundler`

The operational risk is overlap. If a production service depends on the system Python or system Ruby, a casual `sudo pip install` or `sudo gem update` can change shared files and break unrelated software.

## Start with inspection

Before installing anything, record the interpreter and package tool versions.

```sh
command -v python3
python3 --version
python3 -m pip --version
```

```sh
command -v ruby
ruby --version
command -v gem
gem --version
```

If Ruby Bundler is installed, check it too:

```sh
command -v bundle
bundle --version
```

These commands are read-only. They give the next operator evidence about what was actually present on the host.

## Python: use a virtual environment

Python's built-in `venv` module creates an isolated environment for a project or script.

Create one inside a project directory:

```sh
python3 -m venv .venv
```

Activate it:

```sh
. .venv/bin/activate
```

Confirm that Python and `pip` now point into the environment:

```sh
command -v python
command -v pip
python --version
python -m pip --version
```

Install dependencies through the interpreter you intend to use:

```sh
python -m pip install requests
```

Prefer `python -m pip` over plain `pip` in runbooks. It makes the interpreter/package-manager relationship explicit.

Leave the environment:

```sh
deactivate
```

## Python: pin dependencies

A script that needs third-party libraries should describe them in a dependency file.

Simple `requirements.txt` example:

```txt
requests==2.32.3
```

Install from it:

```sh
python -m pip install -r requirements.txt
```

Freeze the current environment only when you intentionally want an exact snapshot:

```sh
python -m pip freeze > requirements.txt
```

Be careful with `freeze` on a messy environment. It can capture unrelated libraries and make the script look more complicated than it is.

## Python: avoid host-wide pip changes

Avoid this on shared systems:

```sh
sudo pip install some-package
```

Also avoid:

```sh
sudo python3 -m pip install some-package
```

Those commands can modify shared interpreter paths. If a system package is needed, prefer the OS package manager:

```sh
apt search python3-requests
```

For application-specific libraries, prefer a virtual environment under the application or automation directory.

## Ruby: understand gems and Bundler

Ruby libraries are called gems. The low-level tool is `gem`; the project-level tool is usually Bundler.

Inspect the Ruby environment:

```sh
ruby --version
gem env home
gem env path
```

Install a gem directly only for simple local experiments or clearly scoped operator tools:

```sh
gem install json
```

For a project, use Bundler and a `Gemfile`.

```ruby
source "https://rubygems.org"

gem "colorize", "1.1.0"
```

Install:

```sh
bundle install
```

Bundler writes `Gemfile.lock`. Commit or preserve that lockfile when the goal is repeatability. It records the exact resolved gem versions.

## Ruby: run through Bundler

When a Ruby script depends on a `Gemfile`, run it through Bundler:

```sh
bundle exec ruby script.rb
```

That tells Ruby to use the dependency set recorded by the project instead of whatever gems happen to be available globally.

You can inspect outdated project gems without changing them:

```sh
bundle outdated
```

## Version managers

Some hosts use version managers:

- Python: `pyenv`, `asdf`
- Ruby: `rbenv`, `rvm`, `asdf`

These tools can be useful on developer workstations and controlled automation hosts. They can also confuse operations if the active version depends on shell startup files.

Look for version markers:

```sh
ls -a | grep -E '(^\\.python-version$|^\\.ruby-version$|^\\.tool-versions$)'
```

Inspect the active executable path:

```sh
command -v python3
command -v ruby
```

If the path points into a user home directory, document that in the handoff. A service account or cron job may not see the same runtime.

## Common failure patterns

### Missing library

Python:

```text
ModuleNotFoundError: No module named 'requests'
```

Ruby:

```text
cannot load such file -- colorize
```

Likely cause: the script is running outside the environment where the dependency was installed.

### Wrong interpreter

A script may use a different interpreter than the one you inspected. Check the first line:

```sh
head -n 1 script.py
head -n 1 script.rb
```

Common shebangs:

```sh
#!/usr/bin/env python3
#!/usr/bin/env ruby
```

`/usr/bin/env` searches `PATH`, so the result can change between an interactive shell, cron, systemd, SSH, and CI.

### Native extension build failure

Some packages compile native code. Failures may mention missing headers, compilers, or development libraries.

Do not blindly install random build tools on production hosts. First identify:

- the package being installed
- whether a prebuilt package exists
- whether the install belongs in a build image instead of on the host
- whether the OS package manager provides the required development headers

## Operator dependency checklist

For any Python or Ruby script being handed to another operator, record:

- interpreter command and version
- package manager command and version
- whether dependencies are system packages, a Python virtual environment, or Bundler gems
- dependency file path, such as `requirements.txt`, `Gemfile`, or `Gemfile.lock`
- setup command
- run command
- verification command
- whether the script is read-only or makes changes

Example handoff:

```text
Script: summarize_logs.py
Runtime: python3 3.12.2
Environment: .venv in repo root
Dependencies: requirements.txt
Setup: python3 -m venv .venv && . .venv/bin/activate && python -m pip install -r requirements.txt
Run: . .venv/bin/activate && python summarize_logs.py /var/log/app.log
Verification: python -m pytest
Safety: read-only log parsing
```

## Hands-on practice

Run these on a disposable VM, container, or lab machine unless the lesson explicitly says otherwise.

1. Inspect the local Python and Ruby versions with read-only commands.
2. Create a temporary Python virtual environment under `/tmp`.
3. Install one harmless Python package inside that environment.
4. Confirm that `python -m pip --version` points into the temporary environment.
5. Create a small Ruby `Gemfile` in a temporary directory and run `bundle install` if Bundler is available.
6. Write a short handoff note that records the runtime, dependency file, setup command, and cleanup command.
7. Remove the temporary directory when done.
