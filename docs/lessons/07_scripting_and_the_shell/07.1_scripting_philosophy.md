### 07.1 Scripting Philosophy

!!! abstract "What you will learn"
    - Explain when a repeated command sequence is ready to become a script.
    - Design scripts with clear inputs, outputs, logging, and failure behavior.
    - Add dry-run, confirmation, and review steps before risky changes.
    - Recognize when automation would hide uncertainty instead of reducing work.
    - Convert a manual runbook into a small, observable script.

!!! example "Field story"
    A team has a weekly cleanup checklist: inspect large logs, archive old reports, restart one service, and send a status note. The commands are familiar, but people keep skipping different steps. The right first script should not be clever. It should make the existing checklist repeatable, visible, and safe.

!!! success "Operator principle"
    A good script turns known manual work into repeatable evidence. It should not hide uncertainty or automate guesses.

## Why operators script

Linux operators script because real systems reward repeatability. A script can preserve a known sequence of commands, reduce typing mistakes, collect the same evidence every time, and make routine work easier to review.

Scripts are useful for tasks such as:

- collecting diagnostic output from a host
- checking file or service state before maintenance
- creating consistent backups or reports
- preparing a lab environment
- applying a small, well-understood configuration change
- wrapping a long command with safer defaults

Scripting is not just about speed. The bigger gain is consistency. If a human types ten commands from memory during an incident, the result depends on fatigue, time pressure, and attention. If those ten commands are captured in a reviewed script, the operator can focus on interpreting the output.

## Start from a runbook

The safest scripts usually begin as runbooks. A runbook is a written procedure that a human can follow manually. It should already answer:

- what problem the procedure solves
- what system or directory it touches
- what command gathers evidence before the change
- what command performs the change
- how to verify the result
- how to stop or roll back if the result is wrong

Do not automate a procedure until you can perform it manually and explain each step. If the manual process is confusing, the script will make confusion faster.

A good progression is:

1. Write the commands in a note.
2. Run them manually on a safe host.
3. Add expected output and verification checks.
4. Turn the read-only parts into a script.
5. Add a dry-run mode for planned changes.
6. Add the changing step only after the evidence path is reliable.

## When not to script

Some tasks should stay manual until the risk is better understood.

Be cautious when a task:

- deletes, overwrites, or reformats data
- changes boot, storage, network, or firewall behavior
- depends on facts that the script cannot verify
- requires judgment from incomplete evidence
- affects many hosts at once
- has no tested recovery path

Automation can make a bad assumption expensive. A script that removes the wrong files on one host is a mistake. A script that removes the wrong files on every host is an outage.

If you are unsure, script the inspection first and leave the action manual.

## Design questions

Before writing a script, answer these questions in plain language.

| Question | Why it matters |
| --- | --- |
| What triggers the script? | Prevents accidental use in the wrong situation. |
| What input does it accept? | Makes assumptions visible. |
| What output should it produce? | Gives the operator evidence to review. |
| What state does it change? | Defines the blast radius. |
| What failure should stop the script? | Prevents continuing after partial success. |
| What log or note should remain? | Makes the run auditable later. |
| How can the result be verified? | Separates "the command ran" from "the system improved." |

The answers do not have to be complicated. A five-line script can still have clear input, output, and failure behavior.

## Make scripts observable

An operator should be able to tell what a script did without opening the script in an editor during an incident.

Useful script output includes:

- the host or target path being inspected
- the mode being used, such as dry run or apply
- the commands or checks being performed
- the files, services, or packages found
- the final status and next manual step

Avoid silent scripts for operational work. Silence makes sense for small Unix filters that are designed to be composed with other commands. For maintenance scripts, useful output is part of the safety model.

For longer-running scripts, write logs to a predictable place, or print a clear path to the log file:

```sh
log_file="./maintenance-$(date +%Y%m%d-%H%M%S).log"
printf 'writing log to %s\n' "$log_file"
```

## Add safety rails

Shell scripts can fail in surprising ways. Start with conservative defaults.

```sh
#!/usr/bin/env sh
set -eu
```

`set -e` exits when many commands fail. `set -u` treats unset variables as errors. These options are not magic, but they catch common mistakes.

In Bash-specific scripts, operators often add `set -o pipefail` so a failed command inside a pipeline is not hidden by a successful later command. POSIX `sh` does not require `pipefail`, so use it only when the script is explicitly Bash:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

Other useful rails include:

- a dry-run mode that prints planned actions
- confirmation before destructive changes
- refusal to run as root unless root is required
- refusal to run outside an expected directory or host
- temporary files created with `mktemp`
- cleanup handlers for temporary files
- lock files for jobs that must not overlap
- clear exit messages for known failure cases

The goal is not to make mistakes impossible. The goal is to make common mistakes visible before they become damage.

## Prefer dry-run first

A dry run is a mode that reports what the script would do without changing the system.

This pattern is especially useful when the script will eventually move, delete, restart, or rewrite something. The first version can be read-only:

```sh
#!/usr/bin/env sh
set -eu

target_dir="${1:-/var/log}"
dry_run="${DRY_RUN:-1}"

printf 'target_dir=%s\n' "$target_dir"
printf 'dry_run=%s\n' "$dry_run"
printf 'log files older than 14 days:\n'

find "$target_dir" -type f -name '*.log' -mtime +14 -print

if [ "$dry_run" = "1" ]; then
    printf 'dry run only; no files changed\n'
    exit 0
fi

printf 'review the file list above before adding an archive or cleanup action\n'
exit 1
```

This script does not delete anything. It creates a repeatable evidence step. Once the output is trusted, a later version can add an archive action, another verification step, and a rollback note.

## Design for idempotence

An idempotent operation can run more than once without causing unwanted extra change. Operators value idempotence because scripts are often rerun after partial failures.

For example:

- creating a directory with `mkdir -p` is usually idempotent
- appending the same line to a config file every run is not idempotent
- checking whether a package is already installed before installing it is safer than assuming state
- restarting a service repeatedly may be technically possible but still disruptive

Ask: "What happens if this script runs twice?"

If the answer is "it duplicates config, deletes too much, or hides the real state," redesign before using it on a real system.

## Choose the right tool

Shell is excellent for gluing together commands, inspecting files, and calling existing system tools. It is usually the right first choice for small operational scripts.

Shell becomes harder to maintain when a script needs:

- complex data structures
- heavy JSON or YAML manipulation
- detailed error handling
- unit tests around business logic
- cross-platform behavior beyond standard utilities

For those tasks, Python, Ruby, Perl, or another general-purpose language may be clearer. The operator principle stays the same: clear inputs, visible output, safe failure, and a verification path.

## From script to scheduled job

A script that runs well by hand is not automatically ready for cron, systemd timers, or CI.

Before scheduling a script, confirm:

- it does not depend on your interactive shell aliases
- it uses absolute paths where needed
- it logs enough context for later review
- it has a predictable working directory
- it handles missing environment variables
- it cannot overlap with itself in a harmful way
- it reports failure somewhere humans will see it

Scheduled automation needs stronger evidence than interactive automation because nobody is watching the terminal.

## Hands-on practice

Run these commands on a disposable VM, container, or lab machine.

1. Create a small lab directory:

    ```sh
    mkdir -p /tmp/script-philosophy-lab/logs
    printf 'old log\n' > /tmp/script-philosophy-lab/logs/app.log
    printf 'new log\n' > /tmp/script-philosophy-lab/logs/current.log
    ```

2. Write a read-only inspection script:

    ```sh
    cat > /tmp/script-philosophy-lab/audit-logs.sh <<'EOF'
    #!/usr/bin/env sh
    set -eu

    target_dir="${1:-/tmp/script-philosophy-lab/logs}"

    if [ ! -d "$target_dir" ]; then
        printf 'error: target is not a directory: %s\n' "$target_dir" >&2
        exit 1
    fi

    printf 'target_dir=%s\n' "$target_dir"
    printf 'regular files:\n'
    find "$target_dir" -type f -print | sort
    printf 'total bytes:\n'
    du -sb "$target_dir" 2>/dev/null || du -sk "$target_dir"
    EOF

    chmod +x /tmp/script-philosophy-lab/audit-logs.sh
    ```

3. Run it twice and compare the output:

    ```sh
    /tmp/script-philosophy-lab/audit-logs.sh
    /tmp/script-philosophy-lab/audit-logs.sh /tmp/script-philosophy-lab/logs
    ```

4. Explain what the script accepts as input, what it prints as evidence, and what failure stops it.

5. Add one more read-only check, such as file ownership or modification time:

    ```sh
    find /tmp/script-philosophy-lab/logs -type f -exec ls -l {} \;
    ```

Do not add deletion to this lab. The purpose is to practice turning inspection into repeatable evidence before writing changing automation.
