### 07.3 SH Scripting

Shell scripts turn a sequence of commands into a repeatable operation. That is useful only when the script is easier to inspect, safer to run, and more predictable than typing the commands by hand.

For system administration work, start with portable POSIX `sh` unless you need a specific Bash feature. A script that runs under `/bin/sh` is often easier to move between distributions, rescue environments, containers, and minimal cloud images.

!!! abstract "What you will learn"
    - Write small POSIX `sh` scripts with clear inputs, output, and exit status.
    - Use quoting, tests, variables, loops, and functions without hiding failures.
    - Add safety checks before a script changes files or services.
    - Practice turning a manual checklist into a script you can review and rerun.

!!! success "Operator principle"
    A useful operations script should be boring: explicit inputs, predictable output, early failure, and no surprising side effects.

## Start with a checklist

Do not begin by writing a long script. Begin with the exact commands you already trust.

```sh
id
hostname
df -h /
systemctl is-active ssh 2>/dev/null || true
```

Run the commands manually, confirm the output, then copy the working sequence into a script. This keeps the first version grounded in evidence instead of guesses.

## A minimal script

Create `check-host.sh`:

```sh
#!/bin/sh

set -eu

echo "Host: $(hostname)"
echo "User: $(id -un)"
echo "Root filesystem:"
df -h /
```

Make it executable and run it:

```sh
chmod +x check-host.sh
./check-host.sh
echo "$?"
```

The `#!` line selects the interpreter. `set -e` stops the script when a simple command fails. `set -u` treats unset variables as errors. The final `echo "$?"` shows the script exit status; `0` means success.

!!! warning "Use `set -e` carefully"
    `set -e` is helpful, but it is not a complete error-handling strategy. Commands inside conditionals, pipelines, and compound expressions can behave differently than beginners expect. For important scripts, check critical command results explicitly and test failure paths.

## Quote variables by default

Unquoted variables split on spaces and can expand globs such as `*`. That is a common source of broken scripts and accidental file changes.

Prefer this:

```sh
target_dir="/var/log"
printf 'Checking %s\n' "$target_dir"
du -sh "$target_dir"
```

Avoid this:

```sh
du -sh $target_dir
```

Quoting is especially important for filenames, usernames, paths, and values read from users or files.

## Inputs and defaults

Scripts should make their inputs obvious. Positional parameters are fine for small tools:

```sh
#!/bin/sh
set -eu

log_dir=${1:-/var/log}

if [ ! -d "$log_dir" ]; then
  printf 'error: %s is not a directory\n' "$log_dir" >&2
  exit 1
fi

du -sh "$log_dir"
find "$log_dir" -maxdepth 1 -type f -name '*.log' -print
```

`${1:-/var/log}` means "use the first argument, or `/var/log` if no first argument was provided." Sending errors to `>&2` keeps normal output separate from diagnostics, which helps when another command captures the script output.

## Tests and conditionals

The portable test command is usually written with brackets:

```sh
if [ -f /etc/os-release ]; then
  . /etc/os-release
  printf 'Distribution: %s\n' "${PRETTY_NAME:-unknown}"
else
  printf 'No /etc/os-release file found\n' >&2
fi
```

Use file tests before you read or change a path:

- `-e` checks that a path exists.
- `-f` checks for a regular file.
- `-d` checks for a directory.
- `-r` checks whether the current user can read it.
- `-w` checks whether the current user can write it.
- `-x` checks whether it is executable or searchable.

## Loops for repeated work

Loops are useful when the operation is identical for each item:

```sh
for path in /etc/passwd /etc/group /etc/shadow
do
  if [ -r "$path" ]; then
    printf '%s: readable\n' "$path"
  else
    printf '%s: not readable by %s\n' "$path" "$(id -un)"
  fi
done
```

Keep each loop body small. If a loop grows past a few commands, move the repeated work into a function.

## Functions for readable scripts

Functions let you name a repeated operation:

```sh
#!/bin/sh
set -eu

check_path() {
  path=$1

  if [ -e "$path" ]; then
    ls -ld "$path"
  else
    printf 'missing: %s\n' "$path" >&2
    return 1
  fi
}

check_path /etc/passwd
check_path /etc/ssh
```

Use `return` inside a function and `exit` when the whole script should stop.

## Add a dry-run path before changing systems

Before a script deletes files, restarts services, changes permissions, or edits configuration, add a dry-run mode. The script should show what it would do before it does it.

```sh
#!/bin/sh
set -eu

dry_run=true

if [ "${1:-}" = "--apply" ]; then
  dry_run=false
fi

run() {
  printf '+ %s\n' "$*"
  if [ "$dry_run" = false ]; then
    "$@"
  fi
}

run mkdir -p ./lab-output
run cp /etc/os-release ./lab-output/os-release.copy
```

Run it first without arguments:

```sh
./copy-os-release.sh
```

Then apply it only after the displayed commands look correct:

```sh
./copy-os-release.sh --apply
```

!!! warning "Do not automate uncertainty"
    If you would not run a command manually on a production system, do not hide it inside a script. Add checks, use a lab environment, or stop for review.

## Troubleshooting shell scripts

When a script fails, collect evidence before editing randomly:

```sh
sh -n ./script.sh
sh -x ./script.sh
printf 'exit=%s\n' "$?"
```

- `sh -n` checks syntax without running commands.
- `sh -x` traces commands as the shell executes them.
- `shellcheck ./script.sh` catches many quoting, portability, and logic mistakes when ShellCheck is installed.

If a script behaves differently from your interactive shell, check the interpreter line. A script that starts with `#!/bin/sh` should not rely on Bash-only syntax such as arrays, `[[ ... ]]`, or process substitution.

## Hands-on practice

Use a disposable VM, container, or temporary lab directory.

1. Create a script named `audit-lab.sh` that prints the hostname, current user, root filesystem usage, and whether `/etc/os-release` exists.
2. Add `set -eu` and quote every variable expansion.
3. Add one argument that selects the directory to inspect, defaulting to `/tmp`.
4. Add a dry-run function named `run` and use it to create `./lab-output`.
5. Run `sh -n ./audit-lab.sh`, then run the script normally, then run it with an explicit directory argument.
6. Save the command output and one failure case in your lab notes.
