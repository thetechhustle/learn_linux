## 07.6 Ruby Programming

Ruby is a general-purpose scripting language that is still useful for Linux
administrators. It reads well, has strong text-processing features, and ships
with a practical standard library for files, JSON, CSV, HTTP, dates, command
execution, and option parsing.

Use Ruby when a shell script is getting too large for comfort but the task is
still local, text-heavy, and operational. Common examples include parsing a
report, checking a directory tree, reshaping CSV or JSON output, and wrapping a
repeatable maintenance command with clearer validation.

!!! abstract "What you will learn"
    - Decide when Ruby is a better fit than a shell script.
    - Write a small Ruby command-line script with arguments and exit codes.
    - Read files safely and handle missing input with useful error messages.
    - Run external commands without hiding failures.
    - Package a script so another operator can run and review it.

!!! success "Operator principle"
    A useful operations script should be boring: clear inputs, predictable
    output, explicit failures, and no surprise changes.

## Confirm Ruby is available

Most distributions package Ruby through the normal system package manager.
Install it from trusted repositories instead of copying an interpreter from an
unknown web page.

```bash
ruby --version
command -v ruby
```

On Debian or Ubuntu systems, Ruby is commonly installed with:

```bash
sudo apt update
sudo apt install ruby
```

On Fedora, CentOS Stream, or RHEL-family systems, the package manager may be:

```bash
sudo dnf install ruby
```

Before changing a production host, check whether Ruby is already part of the
approved baseline. Some environments prefer Python-only or shell-only tooling
for support reasons.

## Start with a script file

A Ruby operations script usually starts with a shebang, strict enough argument
handling, and output that a person or another tool can read.

Create `check-log.rb` in a lab directory:

```ruby
#!/usr/bin/env ruby
# Count matching lines in a log-like text file.

pattern = ARGV[0]
path = ARGV[1]

if pattern.nil? || path.nil?
  warn "usage: #{$PROGRAM_NAME} PATTERN FILE"
  exit 64
end

unless File.file?(path)
  warn "error: #{path} is not a readable file"
  exit 66
end

count = 0

File.foreach(path) do |line|
  count += 1 if line.include?(pattern)
end

puts "#{path}: #{count} matching line(s)"
```

Make it executable and run it against a disposable file:

```bash
chmod +x check-log.rb
printf 'ok\nerror: disk\nok\nerror: network\n' > sample.log
./check-log.rb error sample.log
```

The script uses `warn` for errors because `warn` writes to standard error. It
uses `exit 64` and `exit 66` so calling scripts can distinguish usage errors
from missing input. The exact numeric codes are less important than being
consistent and documenting what they mean.

## Ruby basics for operations work

Variables are assigned without declaring a type:

```ruby
service = "sshd"
restarts = 2
enabled = true
```

Strings interpolate values with `#{...}` inside double quotes:

```ruby
puts "service=#{service} restarts=#{restarts}"
```

Arrays and hashes are the data structures you will use most often:

```ruby
services = ["sshd", "cron", "nginx"]
status = {
  "sshd" => "running",
  "cron" => "running",
  "nginx" => "failed"
}

services.each do |name|
  puts "#{name}: #{status[name]}"
end
```

Conditionals and loops are explicit and easy to scan:

```ruby
if status["nginx"] == "failed"
  warn "nginx needs investigation"
else
  puts "nginx looks healthy"
end
```

## Parse command-line options

For scripts another operator might run, named options are safer than positional
arguments. Ruby includes `OptionParser` in the standard library.

```ruby
#!/usr/bin/env ruby

require "optparse"

options = {
  threshold: 10,
  dry_run: true
}

parser = OptionParser.new do |opts|
  opts.banner = "usage: #{$PROGRAM_NAME} [options] FILE"

  opts.on("-t", "--threshold N", Integer, "warning threshold") do |value|
    options[:threshold] = value
  end

  opts.on("--apply", "make changes instead of reporting only") do
    options[:dry_run] = false
  end
end

parser.parse!

path = ARGV.shift
if path.nil?
  warn parser
  exit 64
end

puts "file=#{path} threshold=#{options[:threshold]} dry_run=#{options[:dry_run]}"
```

Default to dry-run behavior when a script can change files, accounts, services,
or network configuration. Make the operator opt in to changes with a visible
flag such as `--apply`.

## Read files safely

Use `File.file?` to make sure the input is a regular file. Use `File.foreach`
for large files so Ruby does not load the entire file into memory.

```ruby
path = "/var/log/syslog"

unless File.file?(path)
  warn "error: expected a regular file: #{path}"
  exit 66
end

File.foreach(path).with_index(1) do |line, number|
  puts "#{number}: #{line}" if line.include?("ERROR")
end
```

When writing output, write to a temporary file first if a partial file would be
dangerous. Then rename it into place after the write succeeds.

```ruby
require "tempfile"

target = "report.txt"

Tempfile.create(["report", ".tmp"], ".") do |tmp|
  tmp.puts "generated at #{Time.now.utc}"
  tmp.flush
  File.rename(tmp.path, target)
end
```

Do not use Ruby scripts to overwrite system configuration until you have a
backup, a rollback plan, and a human-reviewed diff.

## Run external commands deliberately

Ruby can run shell commands, but the same shell-injection risks apply. Prefer
array-form command execution when user input is involved.

```ruby
service = ARGV.fetch(0, "sshd")
ok = system("systemctl", "is-active", "--quiet", service)

if ok
  puts "#{service} is active"
  exit 0
else
  warn "#{service} is not active"
  exit 1
end
```

Avoid building command strings from untrusted values:

```ruby
# Risky: user input can change the command line.
system("systemctl status #{service}")
```

When you need command output, use `Open3.capture3` so you can inspect standard
output, standard error, and the exit status separately.

```ruby
require "open3"

stdout, stderr, status = Open3.capture3("systemctl", "show", "--property=ActiveState", service)

unless status.success?
  warn stderr.empty? ? "systemctl failed" : stderr
  exit status.exitstatus
end

puts stdout
```

## Troubleshooting Ruby scripts

Use these checks before assuming the script is wrong:

```bash
ruby --version
ruby -c check-log.rb
./check-log.rb --help
echo $?
```

`ruby -c` checks syntax without running the script. `echo $?` shows the exit
status of the previous command, which matters when scripts are used by cron,
systemd timers, CI jobs, or other automation.

If a script works interactively but fails from cron or systemd, inspect the
environment:

```ruby
puts "PATH=#{ENV.fetch('PATH', '')}"
puts "PWD=#{Dir.pwd}"
```

Cron and systemd units often have a smaller `PATH` and a different working
directory than your interactive shell.

## Hands-on practice

Run this lab in a disposable directory.

1. Create `sample.log`:

    ```bash
    mkdir -p ruby-lab
    cd ruby-lab
    printf 'INFO boot\nWARN disk 82%% full\nERROR backup failed\nINFO done\n' > sample.log
    ```

2. Create `log-summary.rb`:

    ```ruby
    #!/usr/bin/env ruby

    path = ARGV.fetch(0, "sample.log")

    unless File.file?(path)
      warn "error: missing log file: #{path}"
      exit 66
    end

    counts = Hash.new(0)

    File.foreach(path) do |line|
      level = line.split.first
      counts[level] += 1 if level
    end

    counts.sort.each do |level, count|
      puts "#{level}=#{count}"
    end
    ```

3. Check and run it:

    ```bash
    chmod +x log-summary.rb
    ruby -c log-summary.rb
    ./log-summary.rb sample.log
    ```

4. Confirm the failure behavior:

    ```bash
    ./log-summary.rb missing.log
    echo $?
    ```

5. Add one more log line, rerun the script, and explain what changed.
